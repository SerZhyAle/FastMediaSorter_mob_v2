---
name: spec-all-concurrent-red-tree
description: Owner runs /spec-all on sub-specs in parallel with a foreground /spec-dev; the shared src tree can go red from another ticket's half-written file
metadata:
  type: project
---

When the owner spins out sub-specs (e.g. S0348 -> S0349/S0350/S0351/S0353 widget tickets) and runs `/spec-all` on them, those runs execute CONCURRENTLY with whatever `/spec-dev` is doing in the foreground, mutating the SAME `app_v2/src` tree (flavor manifests, new `widget/` classes, FEATURES docs).

**Why:** `/spec-all` is unattended and edits shared files (e.g. `src/lite|photos/AndroidManifest.xml` gained `CaptureOcrPanelWidgetProvider`/`AudioNowPlaying` removals while S0348 owned them; `AudioNowPlayingSnapshotStore.kt` referenced a not-yet-created `AudioNowPlayingWidgetProvider`, making `compileStandardDebugKotlin` fail tree-wide).

**How to apply:**
- A whole-tree build failure during your ticket may be caused by a *different* ticket's in-flight file. Read the `a.ps1 bf` compiler-error paths: if every error is in a class/file you did not touch and that belongs to a sibling sub-spec, it is NOT your regression. Confirm your own code compiled at its last phase gate.
- Do not try to fix the sibling ticket's file (it is actively being written by `/spec-all` and you will conflict).
- Your manifest edits can coexist with the sibling's adjacent `tools:node="remove"` entries - the merger added both; no conflict.
- If finalizing to `BlockNeedUserTest`, state plainly that the device build is gated on the concurrent `/spec-all` tree going green; do not claim a green whole-tree build you could not produce.
- **kapt variant (seen 2026-07-30, S1176):** a sibling gradle run mutating `app_v2/build/` while yours executes makes `kaptStandardDebugKotlin` FAIL with no message at all - just "A failure occurred while executing KaptExecutionWorkAction", no `error:` line, no stack. Do NOT jump to the `correctErrorTypes` unmask dance from [[kapt-npe-unmask]]: that is for a masked *real* Kotlin error, and this one has no error to unmask. Tell them apart by re-running when `lock-status.ps1 -Name Build` reports free - the identical source compiles clean. `a.ps1 bf` is useless here (it reports the last *saved* log, which may be an older successful build). Note also that BUILD.LOCK does not protect you: sibling sessions run for minutes, and your `a.ps1` target refuses with "BUILD.LOCK held" rather than queueing, so wrap the call as `until ! lock-status ... | grep -q HELD; do sleep 15; done; <build>` to actually get a turn.
- **Shared-emulator variant (seen 2026-08-06, S1359 vs S1209/S1432):** concurrent sessions drive the SAME `emulator-5554`, and the sibling's navigation looks exactly like a product defect in your screen. Symptom: your activity is torn down mid-test by `ActivityTaskManager: START ... cat=[category.HOME] ... from uid 0`, at irregular intervals (28 s and 100 s in one session), with nothing in logcat naming idle/timeout/screensaver. Before drafting a ticket for it, grep the same logcat window for another ticket id (`S1209: placing cell` was the tell) and for touch events your session never made. Also check `lock-status.ps1 -Name Code` - the CODE.LOCK reason names the sibling. Two further consequences: your own `input tap` lands inside their test and can corrupt it, so stop driving the device rather than fighting for it; and `uiautomator dump` starts failing with `ERROR: could not get idle state` because their animations never settle.
- **Same-ticket planning-race variant (seen 2026-08-08, S1428):** two `/spec-all` runs on the SAME ticket both reach Stage F2 and write `PLAN/<Sxxxx>_<slug>/` concurrently. Nothing serializes them: `CODE.LOCK` covers source edits, not `PLAN/**`, so both `lock-status -Name Code` and `-Name Build` read "free" while the race is happening. Symptom: your `Write` succeeds, then a system note says the file "was modified, either by the user or by a linter" and its content is a *different, internally coherent* plan. Result after ~9 min: ten files describing two incompatible plans - same-numbered phases under different slugs (`PHASE_01__cell-kind-foundations` vs `PHASE_01__section-cell-domain`), and colliding filenames overwritten outright. The sibling also flips the catalog to `Tactical`, so the catalog points at its plan, not yours. Detect it with `Get-ChildItem -Recurse <plan folder> | Sort-Object LastWriteTime` - interleaved timestamps you did not produce are the proof; do not diagnose it from the content alone. Do NOT keep writing (a write-war corrupts the plan and burns tokens) and do NOT delete the sibling's files unilaterally: stop, show the owner the timestamp table, and ask which plan survives. Standing down + grafting your unique findings into the winner is usually right, because the loser's files are silently orphaned (the INDEX never references them) and a duplicate `/spec-dev` would put two agents in the same `.kt`.
- **Stage-0 pre-flight detector (added 2026-08-08, second `/spec-all S1178`):** the same-ticket race is catchable *before* the first write, and cheaply. `lock-status.ps1 -Name Code -Queue` prints each waiter's free-text `reason`, and `/spec-dev`/`/spec-all` put the ticket id and phase in it verbatim (`spec-dev S1178 phase 03`). So at Stage 0, before resolving the Resume Map, run `-Queue` and grep the reasons plus the held lock's reason for your own `Sxxxx`: a hit means a sibling owns the ticket. Confirm liveness by the waiter session's transcript mtime under `~/.claude/projects/p--ANDROID-FastMediaSorter-mob-v2/<sessionId>.jsonl` (written within the last couple of minutes = alive, not a crashed enqueue). This detector fires even while the tree still looks clean, because the sibling is *queued* and has not written anything yet - the F2 variant above is only detectable after files interleave. Note the queue reason is the only signal: `PLAN/**` mtimes look like ordinary recent work, and the catalog `status` reads `In Progress` exactly as it would for a stalled ticket you are meant to resume.
- **Draft-then-copy-back can silently revert a sibling (seen 2026-08-18, S1649):** while queued behind `CODE.LOCK` the productive move is to prepare the edit as a draft under `temp/` so the lock is held for seconds. The trap is the last step: `cp draft/File.kt src/.../File.kt` writes the file **as it was when you copied it out**, so any edit a sibling made to that file in between is gone, with no conflict and no warning. Two rules that keep the pattern safe: copy back only files you created or that nobody else is plausibly touching, and for a *small* change to a shared file apply it in place under the lock (`sed -i`, or the Edit tool) instead of overwriting the whole file. Detect a suspected clobber by diffing the file against `HEAD` and looking for changes that are neither yours nor in HEAD - `git show HEAD:<path> | grep -c <marker>` against the working copy is enough.
- **Test-source-set variant (seen 2026-08-18, S1802 vs S1781, `wear` module):** the sibling adds a member to an interface in `src/main` and its **test fake** in `src/test` has not caught up, so YOUR unrelated targeted unit test cannot run - the whole test source set fails to compile before any test executes. The tell that it is not yours: `a.ps1 fw` (or `fk`) exits **0** on the same tree while `-Mode Unit` fails, and the reported file is a fake in a package you never touched (`FakeWearPreferencesRepository` in `ApplyWearSettingsUseCaseTest.kt`) whose mtime is HOURS older than the interface change. Confirm by grepping the new member name in `src/main` - it lands in the sibling's repository/contract, not in yours. Do NOT repair their fake: their own phase-done criteria require the module to compile, and editing it races their in-flight work. Record the step as written-but-unverified with the exact re-run command, close the rest through `post-change.ps1` (which does not compile tests and passes), and re-run later. Also seen the same session: a compile error in a file you never touched (`MainActivity.kt`, `Unresolved reference 'collectAsState'`) that disappears a minute later - the sibling had saved the usage before the import. Check the file's mtime against your own edits before diagnosing anything; a half-saved file is not a defect.
- Ticket-log gate variant (seen 2026-07-11, S0960 vs S0961 in the same DiagnosticXrActivity.kt): a sibling session's `Timber.d("Sxxxx:` probe whose spec has not YET reached `BlockNeedUserTest` fails YOUR `post-change.ps1` at `ticket-log-audit` (reported as "stale probe"). Check the sibling id via `select.ps1` + look for its `CODE.LOCK` reason: recent `updated` timestamp / live lock = WIP, NOT stale - do not "remove on sight". Resolution: leave their probe, run the remaining post-change gates directly (`assert-neuroslop`, `assert-flavor-flags-not-growing`, `assert-deprecated-pm-flags`, `assert-listener-symmetry`, `assert-focus-highlight`, `assert-fgs-notifications`, `assert-detekt -ChangedFiles <your file>`), record the cause in the final report. The gate goes green once the sibling flips to BlockNeedUserTest.
