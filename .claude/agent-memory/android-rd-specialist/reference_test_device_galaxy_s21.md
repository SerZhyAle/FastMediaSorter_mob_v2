**Different phones appear, and they carry different permissions. Read the serial first.**

- **SM-G996U1 / RFCR110NBQJ - Galaxy S21+, Android 15.** Dedicated test device, blanket "do anything" authorization (details below).
- **SM-G781B / RFCRA133MXB - Galaxy S20 FE, Android 13 (SDK 33), 1080x2400.** A **working phone** of the owner, attached 2026-07-26 for one specific ticket. No blanket authorization: it carries his Telegram, his launcher layout, his lock screen (secure - adb cannot unlock it, ask him). Treat every change as borrowed: restore what you touch, and never grant a system role or change a default app on it. See [[never-grant-system-roles-on-owner-phone]].
- **SM-L310 - Galaxy Watch 7, Wear OS on Android 16 (SDK 36), round 480x480 @ 340dpi, `ro.build.characteristics=nosdcard,watch`.** Identity: sales code **DBT** (Germany), `ro.csc.country_code=Germany` / iso **DE**, firmware `L310OXM2BZF4` - i.e. a **different sales region from the phone** (EUX/PL), which matters for any Samsung region-gated feature. First real Wear target, attached 2026-08-15; the `wear` module (minSdk 28) installs and launches on it. **No cable exists** - Samsung watches charge inductively, so adb reaches it only over wireless debugging, and the adb id is a service name, not a serial: `adb-RFGL1148CRZ-<token>._adb-tls-connect._tcp`. **The `<token>` rotates on every re-pairing** (`7Fo2T4` on 2026-08-15, `2fv3Pn` on 2026-08-18), so never reuse a literal from a memory or an old command - read it from `adb devices` and pass it to `-s` verbatim. The serial part `RFGL1148CRZ` is stable. **The watch is usually absent from `adb devices` at session start** (measured 2026-08-19): discover it with `adb mdns services` - the FIRST call often prints an empty list while discovery warms up, so run it twice - then `adb connect <ip>:<port>` from that line and target the resulting `<ip>:<port>` with `-s` (the device then shows twice, as the service name and as ip:port - same transport, either works). `scripts/devtest/adb.ps1` cannot target it for app verbs - its `-Flavor` set has no `wear` value, so use raw adb for install/launch on the watch. Since S1681 (2026-08-15) the debug package is **`com.sza.fastmediasorter.debug`** - the same id as the phone debug build, deliberately, see [[wear-data-layer-applicationid-mismatch]]. Launcher component is therefore `com.sza.fastmediasorter.debug/com.sza.fastmediasorter.wear.MainActivity` - the package lost its `.wear`, the activity kept it. Exported, so `am start` works. A fresh install asks for media access; grant `READ_MEDIA_AUDIO/VIDEO/IMAGES` with `pm grant` instead of tapping the watch dialog.
- **SM-S731B / R5CY9070WNB - Galaxy S25 FE, Android 16 (SDK 36). The owner's personal phone** (his since 2026-07-28; **first seen on adb 2026-08-20**, so the older "never attached over adb" note is void). Multi-lens Samsung, system camera offers 0.5x; camera tickets S1260/S1261/S1262 are acceptance-tested on it by the owner himself. Same borrowed-phone caution as the S20 FE - read-only probing, never a system role, a default-app change or a `pm clear`. See [[never-grant-system-roles-on-owner-phone]]. Identity: sales code **EUX** (Europe open market, `ro.omc.multi_csc=OXM`), `ro.csc.country_code=POLAND` / iso **PL**, firmware `S731BOXM8BZG1`. Its live SIM/network signals disagree with that CSC on purpose - `gsm.sim.operator.iso-country=mt,ua` (Malta + Ukraine dual SIM), timezone `Europe/Malta` - so **never read the phone's country off one source**: CSC, SIM MCC, timezone and the Samsung-account region are four different answers, and Samsung features gate on different ones. The **Galaxy Store storefront is a fifth, and none of the props predict it** - on 2026-08-20 the store logged `[SA_INIT] mcc : 278` (Malta, from SIM1) while its actual storefront was **Germany**. Reading the MCC line as the storefront produced a wrong conclusion twice. Read it from the store's own UI instead: Galaxy Store -> settings gear -> Settings -> About Galaxy Store -> **Business information**, which names the responsible legal entity (`Samsung Electronics GmbH .. Eschborn, Deutschland`) and so the country. SIM2 (Kyivstar, MCC 255) sits in "Emergency calls only", so it is not a usable alternate MCC source. Two further signals were read off the device on 2026-08-20, bringing the count to six: the **Samsung account country is Germany** (Settings -> account card -> Profile info -> Country or region - the authoritative place to read it; `dumpsys account` and the `ro.csc.*` props do not expose it, and `SamsungAccount: getSamsungAccountCountryCode` appears in logcat without its value), while **Samsung Members serves Italian content and its "Send feedback" gate accepts only Italian (Italy)**, refusing an English report outright. Members' region is therefore its own signal and is NOT the account country - guessing Italy from the Members UI and stating it was a wrong call, corrected only by opening the profile. **How to apply:** read each country signal from its own surface, never infer one from another.

**Why:** owner connected it mid-session and said "do anything on it", removing the usual device-state caution.

**How to apply:** when this serial/model is connected, drive device tests freely without asking about destructive permission grants or settings changes. Quirk: the device blips adb-offline mid-drive (Samsung) - on "device not found", just re-run `adb.ps1 devices` and continue; the prior tap usually registered. Verify it is still connected (serial may differ on reconnect) before acting.

**A tap near the right or bottom screen edge is eaten by the system gesture zone, and it looks like a dead button (2026-08-11, S1447).** In landscape (viewport 2400x1080) a settings row's trailing icon buttons sit flush against the edge - `btnClearAllScheduled` spans `[2232,628][2366,763]`, `btnDelete` spans `[2209,978][2344,1080]`. `input tap` at the *center* of either does nothing at all, or worse, registers as the back gesture and drops the app out of the foreground, which then reads as a crash. Three separate probes were scored as "no dialog appeared" before the cause was found; a neighbouring button 270px further from the edge worked every time.
**How to apply:** never tap the center of a control whose bounds touch the screen edge - read the bounds from the uiautomator dump and aim at the interior corner (~20-30px inside the near edges). If the app vanishes to the launcher mid-drive, check the pid before diagnosing: an unchanged pid means the gesture backed you out, not a crash.

**One UI automation limits (recurring, confirmed 2026-06-28 sweep):** Samsung One UI blocks several end-to-end UI paths from mobile-mcp - the OS EdgePanel **intercepts automated left-edge swipes**, and the launcher **does not auto-place pinned widgets/shortcuts** (drag-to-place isn't drivable; trampolines/panel activities are non-exported). So "swipe-to-trigger-gesture" and "tap-pinned-shortcut/widget-to-launch" sub-steps are NOT automatable. Verdict pattern that round: verify the request/seed *fires* (logcat `Timber.d("Sxxxx:` probe) + DataStore/overlay state + code path, mark the final launch/tap **manual** (still Verified, not FAIL) - applied to S0663/S0637/S0662(RIGHT/DOWN)/S0683; S0568 widget-tap had no probe fire at all so it stayed BlockNeedUserTest. Also: overlay windows (gesture strip 4px) are **excluded from MediaProjection screencap**, so visual overlay rendering needs a human eye, not a screenshot. Real device also reproduced two defects the specs blamed on emulators: S0613 `PrintManager.print()` "Can print only from an activity" IllegalStateException, and S0700 grid first-frame thumbnail black (ExoPlayer releases before frame lands).
