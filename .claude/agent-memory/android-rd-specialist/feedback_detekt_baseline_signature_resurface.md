---
name: detekt-baseline-signature-resurface
description: Adding a constructor param to an already-baselined LongParameterList class resurfaces the finding under scoped detekt
type: feedback
---

Adding/removing a constructor (or function) parameter to a class that already has a baselined detekt finding (e.g. `LongParameterList`, `LongMethod`) **resurfaces that finding** even though it was "accepted" debt.

**Why:** detekt baseline entries are keyed by a full signature string (the whole param list). Change one param and the signature no longer matches the baseline entry -> detekt treats it as a NEW finding. Under `post-change.ps1 -ScopeToFile` (diff-scoped detekt), that file is in your diff, so the gate FAILs on a finding you didn't really introduce.

Also: a class sitting *exactly at* the threshold (10 params, threshold 10 = no finding) tips into a genuine new finding at +1.

**How to apply (preferred - avoid the signature change entirely):** discovered 2026-07-06 on S0962. I first threaded a gate flag + callback (`vrCinemaAvailable`, `onOpenInVrCinema`) through `BrowseFileOverflowMenuManager.showFor` (already 20 params, baselined `LongParameterList` + `CyclomaticComplexMethod`) AND up through `BrowseManagerInitializer`'s 40-param constructor + `BrowseActivity`. Adding those params resurfaced BOTH baselined findings on both god-methods, plus a `ComplexCondition` from a 4-term `if`. Fix that worked cleanly: **inject the new small helper (`BrowseVrCinemaLaunchManager`, @ActivityScoped) DIRECTLY into the menu manager's own tiny constructor (1->2 params, no threshold), and add a body-only branch to `showFor` that reads `helper.isAvailable` and calls `helper.launch(file)`.** The god-method SIGNATURE is unchanged -> its baseline entry still matches -> `LongParameterList`/`CyclomaticComplexMethod` stay suppressed even though the body grew. It also reverted the BMI + Activity edits (blast radius 4 files -> 2). Keep any new `if` to <=3 boolean sub-expressions or `ComplexCondition` fires as a genuine NEW finding (a directory is never `MediaType.VIDEO`, so I dropped the redundant `!isDirectory` term to get from 4 to 2).

**Do NOT reach for `@Suppress` first:** CLAUDE.md Rule 19 forbids adding `@Suppress` to a method that already carries a baselined finding - it shifts the baseline signature and surfaces a *different* finding (e.g. `FunctionNaming`). Prefer the inject-into-helper route above; re-baselining the whole project is also wrong (captures others' WIP). If a stale report shows the OLD signature after your edit, force a fresh report with `:app_v2:detekt --rerun-tasks` and check the report mtime (see [[project_detekt_baseline_hand_edit_daemon_stale]], [[detekt-ktlint-import-layout]]).

**Second shape - ONE new import resurfaces `ImportOrdering` (2026-07-26, S1197).** The `ImportOrdering` baseline signature is the whole import block concatenated into one string, so a file whose imports were already mis-sorted carries a baselined finding keyed to that exact list. Add a single import and the signature stops matching - the diff-scoped gate reports it as NEW in your changed file even though the disorder predates you. Fix by actually sorting the imports (lexicographic ASCII: `com.*` before `timber.*`), never `@Suppress`. Budget one extra gate round-trip whenever you add an import to an old file.

**Third shape - the drift is OLD and the bill lands on a stranger (2026-07-31, S1315 -> parked as S1334).** The two shapes above assume *your* edit changed the signature. The nastier case: a ticket months ago grew the constructor, the baseline entry silently stopped matching, and nothing reported it. The finding then sits dormant until some unrelated ticket edits the file, and the diff-scoped gate presents it as that ticket's problem. Diagnostic: grep the baseline for the class and **count the parameters in the frozen signature against the live constructor** - if the baseline lists fewer, the debt thawed and predates you. On `BrowseStateSyncManager` the entry froze 10 params while the live code had 11 (`materializeFavoritesUseCase`, added by S0783). Do NOT re-freeze at the new count to make the gate green: that quietly accepts one more than was ever approved. Park it as its own ticket, same as the honest per-class debt family. Worth knowing: an entry whose signature matches no current finding is *either* fixed debt that should be pruned *or* drifted debt that is silently live, and today nothing distinguishes or reports either - a gate for that is the real fix.

**Fourth shape - EXTRACTING a baselined body into a new function moves the finding with it (2026-08-11, S1573).** Wanting `withContext(Dispatchers.IO)` around `CameraCaptureSaver.save`, I first split the body into a private `saveOnIoDispatcher(..)` and left `save` as a one-line delegate. Compiles, tests pass - and the scoped gate reports a NEW `NestedBlockDepth`, because the baseline id is `NestedBlockDepth:CameraCaptureSaver.kt$CameraCaptureSaver$suspend fun save( .. ): SaveResult` and the deep body now lives under a different signature. **The cheap shape is almost always to keep the signature and change only the body:** `): SaveResult {` -> `): SaveResult = withContext(Dispatchers.IO) {`, `return when {` -> `when {`. Two lines, baseline still matches, no baseline edit.
**And do NOT re-indent when you do that:** a `= withContext(..) { .. }` lambda body sits at the *same* indent as the function body it replaced. I added four spaces, which is wrong Kotlin style, would trip ktlint `Indentation`, and pushes any line already near 120 over the limit. Leaving the indentation alone also keeps every `MaxLineLength`/`ArgumentListWrapping` id in that file matching, since those are keyed on element text - `grep` the baseline for your file first and you can predict exactly which ids survive an edit.

**Co-resident WIP surfaces in YOUR scoped gate (2026-07-18, S1088).** Because signatures are content-based (`Rule:File.kt$Class$(<arg-list-text>)`), pure line shifts do NOT resurface a finding - only a content change does. So when `assert-detekt -Gate -ChangedFiles` flags an `ArgumentListWrapping`/`LongParameterList` in a big shared file you edited (e.g. `GeneralSettingsFragment`), it may be **another ticket's uncommitted WIP**, not yours: grep the baseline for that call and compare arg counts. S1088: baseline had `GeneralSettingsObserversHelper( .. { isUpdatingSpinner = it } )` (5 args); the working tree had a 6th arg `capabilityAvailability` added by an unrelated ticket -> flagged as new in my changed file. Per dirty-tree philosophy, **leave it** (don't fix another ticket's WIP), fix only findings your own diff introduced, and note the residual. Also: `assert-detekt.ps1` runs `:app_v2:detekt` **without** `--rerun-tasks`, so after you fix a finding it can serve a STALE cached report (shows your already-fixed finding) - force `gradlew :app_v2:detekt --rerun-tasks`, then grep `app_v2/build/reports/detekt/detekt.xml` for your files directly instead of trusting the wrapper's verdict.
