`/spec-prerelease` Maestro full suite goes red on the emulator from TWO harness problems, not app defects (tracked by S0666; prepare.ps1 part fixed 2026-06-24).

**Why:** A 2026-06-24 sweep went Maestro 3/14 then 6/14. Both red runs were 100% harness; the app was healthy (in-app player, perf, logcat all clean, 0 error toasts).

**How to apply:**
- Onboarding cascade: `prerelease-prepare.ps1` adb-injected only `welcome_completed=true` into `welcome_prefs.xml`; the running app's next SharedPreferences commit (setFirstRunCompleted / gesture-seeding) rewrote the file WITHOUT it -> app reverted to WelcomeActivity mid-suite -> `go_home.yaml` can't exit onboarding -> every later flow cascade-fails (incl. app_launch/local_browse that passed in smoke). Fix applied: prepare now seeds the full 4-key map (welcome_completed + first_run_after_welcome=false + onboarding_default_player_shown=true + gesture_defaults_seeded=true). Genuine UI onboarding completion is durable across restart (proven) - so a mid-suite revert = harness, never an app onboarding bug.
- Player/slideshow flows (edge_cases, player_*, slideshow_basic) fail on viewer-not-visible (id photoView/playerView/btnPlaybackControl) even when durably onboarded. The in-app player WORKS when driven manually (tap media -> PlayerActivity + photoView/playerView, no external app, no "built-in player" toggle exists). Treat these as flaky oracles (first-open hint overlay intercepts first tap / wrong-id/timing), not app defects - still unfixed in S0666.
- Verdict gotcha: log-audit reports ~80+ "actionable" clusters on the emulator that are all system/Maestro noise (RoleControllerServiceImpl, SmsApplication, HCPackageInfoUtils dev.mobile.maestro, persistent_data_block, android.xr flags, GFXSTREAM egl, Maestro gRPC-netty). Trust `toastCount` (0 = no user-facing error) + crashBlocks over the raw actionable count. Aggregator FAIL was Maestro-only; log+perf were clean.
- Flaky UI tap-injection on the Android-17 / `sdk_gphone16k_x86_64` preview emulator (diagnosed 2026-07-19, corrected from an initial wrong "OOM" read): Maestro AND mobile-mcp taps intermittently do not land - the app never sees the tap (flow log shows `Tap on "X" FAILED` after the element's assert already COMPLETED; mobile-mcp `click` + adb `input tap` on btnSettings both no-op while the a11y tree stays live; mobile-mcp screenshots come back all-black). It is NOT memory and NOT the app: on a clean wiped emulator a 5-flow smoke logged 0 `OutOfMemoryError`, 0 app FATAL, 0 `lowmemorykiller` pressure, yet still failed 2/5 on taps. The `Killing ...fastmediasorter (adj 0): stop ... due to from pid` lines are Maestro's own `stopApp` between flows, NOT LMK; `lowmemorykiller: process_mrelease ... No such process` is LMK racing an already-stopped pid (noise). PROOF it is flaky-harness not a deterministic bug: DIFFERENT flows fail across identical fresh-emulator runs (run1 smoke failed only add_resource_forms; run2 smoke failed local_browse + settings_toggle_sweep and add_resource_forms PASSED). A real regression fails the same flow every time. Over a long 32-min `-Suite all` the per-flow flakiness compounds to ~16/17 fail and the emulator window/input stack degrades further (`SettingsActivity` "Input dispatching timed out (Application does not have a focused window)", one framework Application-creation FATAL on a BOOT_COMPLETED delivery - masked by an `LoadedApk.makeApplicationInner` NPE, not app logic). CORRECTION (same 2026-07-19 session, after more evidence): switching to a STABLE `sdk_gphone64_x86_64` API-35 image did NOT help (smoke 4/5 fail, worse), and `adb kill-server`/`start-server` + Maestro-driver uninstall (which itself failed `DELETE_FAILED_INTERNAL_ERROR`) did NOT help - so the root cause is NOT the emulator image. It is the UI-automation harness on THIS host: Maestro's on-device driver `dev.mobile.maestro` returns `io.grpc.StatusRuntimeException: UNAVAILABLE` and "Unable to launch app", and mobile-mcp taps/screenshots fail, while a background `adb logcat` stream died with exit 255 - i.e. an unstable Maestro-gRPC / adb-transport layer on the host. CRITICAL WORKAROUND: adb-DIRECT works perfectly even when both harnesses are down - `adb shell input tap X Y` navigates (verified MainActivity->SettingsActivity->BrowseActivity), `adb exec-out screencap -p` renders real frames, `dumpsys window | grep mCurrentFocus` confirms focus. So when Maestro/mobile-mcp flake, VERIFY APP HEALTH with a manual adb walk (input tap + screencap + dumpsys focus + `logcat -d | grep FATAL`) instead of trusting or fighting the harness - a clean adb walk (nav across Settings/Browse, 0 FATAL, real thumbnails) is a valid release-sanity verdict. To actually fix the automated suite: reinstall/upgrade the Maestro CLI + its driver, check Maestro<->adb version compatibility, reduce concurrent adb consumers (don't run `adb logcat` streaming during a Maestro run), or reboot the host/adb.
- Never propose `/skill-release` on this red gate (ADR-1). Manually verify the exercised surfaces, park harness findings, recommend fixing the harness + re-running.
