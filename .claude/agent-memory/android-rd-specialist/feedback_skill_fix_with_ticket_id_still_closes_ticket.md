When `/skill-fix` (or `/quick`) is invoked with an **existing ticket id** as its argument, finish the ticket too: fill the spec body from what the fix actually did, run `post-change.ps1`, and transition the status. The landing status is **`BlockNeedUserTest`, not `Implemented`** - which means the run also owes a `Timber.d("Sxxxx: ..")` probe. Do not stop at the code edit and cite the command's "skip bureaucracy" step.

**Why:** owner, 2026-08-12, S1593. After `/skill-fix S1593` landed the code fix and reported the deliberate skips, his whole reply was "why it is still draft?" - and when the ticket was then set to `Implemented`, he corrected that too: "если я прошёл /skill-fix то как минимум тикет должен стать в ожидание на тестирование пользователем". Both commands' skip-lists were written for the *ad-hoc* invocation form (`/skill-fix кнопка Delete не реагирует`), where no ticket exists to update. Passing an `Sxxxx` changes the contract twice over: the ticket is the reason the work happened, so leaving it at its old status parks it in `PLAN/RELEASE_QUEUE.md` as unfinished work at its original priority while the fix is already in the tree; and `/skill-fix` validates only locally (a compile check, at most a narrow test), which is never device proof - so `Implemented` overclaims and the honest landing state is the one that asks the owner to test.

**How to apply:** on `/quick Sxxxx` or `/skill-fix Sxxxx`, treat the skip-list as covering only *new* spec creation. Still do, in this order: fill the spec sections the fix answers (§1 symptom, §2 root cause, §3 the actual edit, §4 how to prove it) -> insert the probe tag in the changed flow -> `update.ps1 -Id Sxxxx -Status BlockNeedUserTest -StatusNote '<what to test on device>'` -> compile check -> gates. Status before gate, or the ticket-log audit fails on your own probe. Verify the reconciliation landed by grepping both `RELEASE_QUEUE.md` and `RELEASE_READY.md` - the catalog write moves the row between them. The skip-list still holds for a genuinely id-less fast patch. See [[finish-mechanical-followups-in-context]], [[blockneedusertest-status-before-gate]], [[timber-tags-before-test]].
