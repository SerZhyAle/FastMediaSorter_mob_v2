Build/tooling gotchas observed while running builds.

1. **`build-debug.PS1` flaky daemon stop.** The Gradle build sometimes fails with `FAILURE: ... Gradle build daemon has been stopped: stop command received` (or a Windows file-lock `NoSuchFileException` in `temp/gradle-tmp/kotlin-backups/*.backup`) at the `:app_v2:compileStandardDebugKotlin` step. Likely cause: the IDE (VSCode/Android Studio with the project open) runs its own Gradle sync after file changes and stops daemons. `build-debug.PS1` only auto-retries for `Failed to store cache entry` and `kapt3/incrementalData` lock errors - **not** for daemon-stop. **Fix:** run `./gradlew --stop`, ensure `temp/gradle-tmp` exists (`mkdir -p temp/gradle-tmp`), then re-run `build-debug.PS1` - it succeeds on retry. A `e: Daemon compilation failed: null` / `Backend Internal error: IR fake override builder` line can appear and the build still succeeds (falls back to in-process compile). Don't treat a single daemon-stop as a real build failure - retry first.
   **How to apply:** When a build fails with daemon-stop / kotlin-backups file-lock, retry once before reporting a build failure.
   **Escalation (observed 2026-05-30, S0291 noLegalDebug):** repeated rapid CLI builds while the IDE Gradle is also active produce a *cascade* of corruption that simple retry does NOT cure: first `Could not close incremental caches ... class-attributes.tab/proto.tab ... already registered` + `Detected multiple Kotlin daemon sessions` (Kotlin incremental cache), then `kaptGenerateStubs ... Failed to create MD5 hash for ...$Companion.class` (kapt incremental), then `merge/packageResources FAILED ... NoSuchFileException: ...incremental/.../stripped.dir/layout/<untouched>.xml` (resource intermediates vanishing mid-compile, for layouts you never touched). Each aborted daemon-stop run corrupts another incremental layer. The reliable cure is a **full `./gradlew :app_v2:clean` then a single build with no concurrent invocations** - NOT more incremental retries. Critically: source that compiles is provable from an *early* run reaching post-compile tasks (`buildCMakeDebug`, `compileNoLegalDebugKotlin`, `mergeNoLegalDebugNativeLibs`, `stripNoLegalDebugDebugSymbols`) - if those passed once, later resource/cache failures are environmental, not your code. Don't burn >3 builds chasing a green APK when the IDE is fighting you; validate compile from the early run and, for device-test specs, hand the APK mint to the owner's clean environment.
   **Exit-code trap:** `pwsh -File a.ps1 nd | tee log` and `pwsh -File a.ps1 nd > log; echo $?` both report exit 0 regardless of build outcome (tee / the trailing echo own the exit). ALWAYS verify by `grep -E "BUILD SUCCESSFUL|BUILD FAILED" log`, never trust the reported exit code of a piped/`;`-chained build.
   **Stale-daemon cascade (observed 2026-06-05, S0360 standardDebug).** Signal: the Gradle startup line climbs - `Starting a Gradle Daemon, N stopped Daemons could not be reused` with N growing build-to-build (saw it reach 15). Each `build-debug.PS1` run then dies with `Gradle build daemon has been stopped: stop command received` at a *post-compile* stage (dexBuilder / transformClassesWithAsm / mergeNativeLibs), sometimes preceded by `FileNotFoundException: ...build/kotlin/.../shrunk-classpath-snapshot.bin`. Critically: `compileStandardDebugKotlin` + `compileStandardDebugJavaWithJavac` + `hiltJavaCompileStandardDebug` all completed cleanly in every aborted run - so the source compiles; the stop is external/environmental. `recover-kapt-stall.ps1 -Task ...assembleStandardDebug` (which retries `--no-daemon`) did NOT cure it - the external stop kills even the single-use daemon. The cure that worked: `pwsh -NoProfile -File scripts/builders/clean-gradle-caches.ps1` (nukes `.gradle/`, `build/`, `app_v2/build/`, runs `gradlew clean`) - its embedded clean ran green with no stop, and the next full `build-debug.PS1` succeeded in ~2m49s. Order of escalation: (1) retry once, (2) `recover-kapt-stall.ps1` for kapt-stub/incremental corruption, (3) `clean-gradle-caches.ps1` when the daemon-count keeps climbing and stop-commands recur across runs.
   **Owner actively in the IDE -> hand off, do NOT clean/kill (observed 2026-06-19, S0523 spec-dev).** Distinct from the stale-daemon cases: when the working tree shows the owner's *live* in-flight refactor (untracked half-extracted helper files appearing/changing between builds, line numbers shifting under you, system-reminders "modified by a linter"), the build contention is a LIVE session, not a disposable stale daemon. Fingerprints: `clean`/`cd` dies with `java.io.IOException: Unable to delete directory '...app_v2/build' ... a process has files open` (Android Studio holds build/ locks, so clean is impossible), and `d` dies with `e: Daemon compilation failed: null` (Kotlin daemon OOM-killed by concurrent gradle) - with ZERO `e: file://` source errors. Do NOT surgical-kill their daemons or force-clean (disrupts their work). Validate the source compiles from the green per-phase `fk`/`fc` runs, leave the spec `In Progress` (remove any staged `Timber.d("Sxxxx:` tags to keep the iff-BlockNeedUserTest invariant), journal the milestone, and hand off: "idle the IDE, run `a.ps1 cd`, then `/spec-dev <Sxxxx> --resume`". Recognize this fast - don't burn 5 builds first.

   **Surgical cure when the IDE daemon is the culprit (observed 2026-06-16, S0459 Phase 01).** Signal: `1 busy ... Daemons could not be reused` + `Could not close incremental caches ... class-attributes.tab ... already registered` recurring across every retry, and `recover-kapt-stall.ps1`'s own `--stop` does NOT clear it (a *busy* external daemon ignores `--stop`). Root cause confirmed: **Android Studio's own Gradle/Kotlin daemon** (JVMs under `...\Android Studio\jbr\bin\java`) was holding + concurrently corrupting the kapt incremental cache. Fast cure: kill the daemon JVMs by command line, which targets only the disposable daemons and never Android Studio itself - `Get-CimInstance Win32_Process -Filter "Name='java.exe' OR Name='javaw.exe'" | ? { $_.CommandLine -match 'GradleDaemon|KotlinCompileDaemon' } | % { Stop-Process -Id $_.ProcessId -Force }` - then `recover-kapt-stall.ps1`, then build. Cleared 2 AS daemons; `a.ps1 fk` went green first try (2m05s). Prefer this surgical kill over the heavier `clean-gradle-caches.ps1` when the signal is specifically "busy daemon could not be reused".

3. **`dev/CATALOG/app_v2.jsonl` and `app_v2.md` are gitignored** (confirmed via `git check-ignore`). CLAUDE.md says "commit updated dev/CATALOG/<module>.jsonl + <module>.md together with the code change" - but they're not tracked, so there's nothing to commit. Still run `scan.ps1` + `render.ps1` after `.kt` changes (the catalog is a local index used by `query.ps1`), just don't expect/require a git diff for them.
   **How to apply:** After `.kt` edits, regenerate the catalog but skip the "commit catalog files" step for app_v2 - they're gitignored.

4. **Stale `JAVA_HOME` after a JDK point-update (observed 2026-06-13, re-hit 2026-07-29).** A fresh Bash-tool shell had `JAVA_HOME=C:/Program Files/Java/jdk-21.0.10`, but only `jdk-21.0.11` (and `jdk-17`, `latest`) existed on disk, so `a.ps1 fk`/gradlew died with `ERROR: JAVA_HOME is set to an invalid directory`. Cure: export a valid JDK for the invocation - `export JAVA_HOME="/c/Program Files/Android/Android Studio/jbr"` (the toolchain `gradle.properties` documents as `org.gradle.java.home`) or `jdk-21.0.11`. The Android Studio JBR is itself `21.0.10` and builds fine.
   **The tool matters, and this is the cheap fix:** the **PowerShell** tool's shell has a VALID `JAVA_HOME` (`C:\Program Files\Java\latest\jdk-21` -> `jdk-21.0.11`); only the **Bash** tool's shell carries the stale one. Neither `~/.gradle/gradle.properties` (`org.gradle.java.home=.../Android Studio/jbr`) nor any repo script names `21.0.10` - don't go hunting for it in the repo, it is purely the Bash shell's inherited env.
   **How to apply:** Launch gradle-backed `a.ps1` targets from the **PowerShell tool**, not the Bash tool - that alone avoids this. If you must use Bash, `export JAVA_HOME="/c/Program Files/Android/Android Studio/jbr"` first. Symptom is instant: the build dies before any Gradle task with "JAVA_HOME is set to an invalid directory".
   **Compounding trap that hid it (2026-07-29):** the failing build was launched as `pwsh -File ./a.ps1 dq 2>&1 | tail -40` in a backgrounded Bash task; the harness reported **exit code 0** because `tail` owned the exit status, so the completion notification read as success while the build had actually failed. Same family as gotcha #12 and [[background-task-exit-code-is-echo]]. Never pipe a build through `tail`/`tee`; redirect to a log and grep for `BUILD SUCCESSFUL|BUILD FAILED`.

5. **`a.ps1` / builder wrappers hang idle after the Gradle work finishes (observed 2026-06-15, S0414).** Both `build-standard-device.ps1` (build+install) and `a.ps1 fk` ran the actual Gradle task to completion (APK on disk / `compileStandardDebugKotlin` done, daemon CPU flatlined) but the wrapper process never exited - the background task sat for 10-30 min with no notification and a 0-byte/buffered output file. Two compounding traps: (a) piping a wrapper through `| tail -N` buffers ALL output until EOF, so you see nothing until/unless it exits; (b) the wrapper itself can hang post-work (install step or trailing logic). **Cure:** don't pipe builds through `tail`; write Gradle output straight to a file and grep it, or bypass the wrapper and call `./gradlew.bat :app_v2:<task> --console=plain > temp/x.log 2>&1` directly (compiled clean in ~4s when run direct). If a wrapper task is alive but its daemon CPU is idle and the APK/classes are already freshly built on disk, kill the task and finish the step manually (e.g. `adb install -r` the APK yourself) rather than waiting.
   **How to apply:** When a backgrounded `a.ps1`/builder task runs far longer than the work should take, check the APK/class mtime + daemon CPU; if the work is done, kill it and proceed. Never gate progress on a `tail`-piped build's notification.

6. **`verifyNoPlatformNames` denylist gate (S0286, observed 2026-06-16 in S0459).** A `verification` Gradle task (`app_v2/build.gradle.kts`, `VerifyNoPlatformNamesTask`) fails the build EARLY (at `:app_v2:verifyNoPlatformNames`, before compile) when a denylisted brand literal appears in market sources or public FEATURES docs. Denylist file: `app_v2/compliance/platform-name-denylist.txt` - currently `Instagram, TikTok, Threads, threads.com/.net, Facebook, Snapchat, Twitter, X.com, Reddit, Pinterest, LinkedIn, Tumblr, Vimeo, Dailymotion` (NOT WhatsApp / Telegram / YouTube - those pass). Brand tokens are case-sensitive with word boundaries `(?<![A-Za-z0-9_])TOKEN(?![A-Za-z0-9_])`, so `com.instagram.android` (lowercase) and identifiers like `InstagramShareTargetHandler` do NOT match - only a standalone `Instagram`. Comment-only lines are skipped (`//`,`*`,`<!--`). Three escapes (per the failure message): (a) inline `allow-platform-literal: <reason>` marker ON the literal's line, (b) a reviewed legacy entry in `compliance/platform-name-baseline.txt` (tab-separated `relativePath<TAB>trimmedLine`), (c) remove the literal. **Preferred fix for share/integration features (S0459 owner decision):** don't hardcode the brand string at all - resolve the label dynamically from the installed app via `PackageManager.getApplicationLabel` (mirrors the dynamic app-icon approach), keeping the brand out of the codebase; the resource string becomes a neutral fallback.
   **How to apply:** Before adding a brand name to `strings.xml`/FEATURES, check the denylist. For a user-facing receiver/integration label of a denylisted app, prefer a dynamic `PackageManager` label + neutral fallback string over a hardcoded literal; reserve the `allow-platform-literal:`/baseline escapes for cases where the literal is unavoidable and reviewed.

7. **Reusable `dq`/`d` APK has a stable (older) versionCode -> `INSTALL_FAILED_VERSION_DOWNGRADE` over a `dav` install (observed 2026-06-23, S0623 device-test gate).** The fast reusable debug APK (`a.ps1 d`/`dq`) carries a fixed versionCode, while `a.ps1 dav` stamps a timestamped (date-encoded) versionCode. If the emulator already has a `dav`-built install (e.g. versionCode `260623164`), `adb install -r` of a freshly built `dq` APK (`260621154`) fails with `INSTALL_FAILED_VERSION_DOWNGRADE: Update version code ... is older than current ...`. A streamed install over a different emulator state can also throw the unrelated `INSTALL_FAILED_INVALID_APK: ... code is missing` quirk (retry with `adb install -r --no-streaming`). Neither is a code defect - the build itself was SUCCESSFUL (full dex+package). To device-test a `dq`/`d` build over a newer install you must `adb uninstall` first (wipes app data - and a fresh install creates the DB straight at the latest schema version, so it does NOT exercise a Room migration path), or build with `dav` to get a higher versionCode. In an autonomous loop, prefer leaving the owner's emulator state intact and deferring runtime checks to the `BlockNeedUserTest` note rather than uninstalling.
   **How to apply:** When `adb install` of a fresh `dq`/`d` APK fails with VERSION_DOWNGRADE, don't treat it as a build failure; either `dav`-build for a higher versionCode or uninstall first (accepting data loss + no migration coverage). For edge-gesture / overlay / consent features that are flaky to drive on an emulator, declare runtime INCONCLUSIVE after a bounded attempt and keep `BlockNeedUserTest`.

2. **Chaquopy variant gate (S0174/S0175).** When `local.properties` has `chaquopy.enabled=true` (set for IDE sync on noLegal flavor), `isNoLegalBuild=true` fires in `app_v2/build.gradle.kts` and a `beforeVariants` block **disables all non-noLegal variants**. This makes `assembleStandardDebug` and all other non-noLegal tasks invisible. Fixed 2026-05-12 by: (a) making explicit `-Pchaquopy.enabled` Gradle property take strict precedence over `local.properties`, (b) adding `-Pchaquopy.enabled=false` to ALL non-noLegal build scripts in `scripts/builders/` and `dev/build-with-version.ps1`. If symptoms recur (task not found, only `noLegal` variants visible), check: does `local.properties` have `chaquopy.enabled=true`? If yes, ensure the build script passes `-Pchaquopy.enabled=false`.
   **How to apply:** When adding new non-noLegal build scripts, always include `-Pchaquopy.enabled=false` in the Gradle invocation.

8. **`-Pchaquopy.enabled=false` BREAKS noLegal Kotlin compile (observed 2026-06-26, S0672).** The inverse of #2: `-Pchaquopy.enabled=false` speeds up standard/lite/photos compile checks (they have no Python), but noLegal's yt-dlp/Python integration (`src/noLegal/.../ChaquopyRuntimeHolder.kt`, `YtDlpExtractionStrategy.kt`) depends on the Chaquopy-generated `com.chaquo.python.*` classes. Compiling `:app_v2:compileNoLegalDebugKotlin -Pchaquopy.enabled=false` fails with a wall of `Unresolved reference 'chaquo' / 'Python' / 'callAttr' / 'PyObject'` - NOT a code defect, just the wrong flag. Re-run noLegal compiles WITHOUT the chaquopy flag.
   **How to apply:** Use `-Pchaquopy.enabled=false` only for standard/lite/photos/legacy compile checks. For any `compileNoLegalDebug*` / `nd` / `nl` task, drop the flag (noLegal needs Chaquopy). If a noLegal compile fails only on `chaquo`/`Python`/`callAttr`/`PyObject` unresolved refs, it is this flag, not your change.

10. **Mixing a `noLegal` and a `standard` variant task in ONE gradle invocation makes the standard task vanish (observed 2026-06-26, S0724).** Ran `./gradlew :app_v2:compileStandardDebugKotlin :app_v2:compileNoLegalDebugKotlin -Pfms.edgeGestureOverlay=on` to compile-check both flavor source sets at once; it died at task-name resolution with `Cannot locate tasks that match ':app_v2:compileStandardDebugKotlin' as task 'compileStandardDebugKotlin' not found`. Cause: any `nolegal` substring in the requested task names flips the build into noLegal/XR mode (`isXrNativeBuildRequested`, `build.gradle.kts` ~L183-185, matches `nolegal`/`vr`; same family as the `isNoLegalBuild` variant-gate in #2), and the `beforeVariants`/variant filtering then drops every non-noLegal variant - so the `standard` Kotlin task no longer exists in that configuration. NOT a code error. **Cure:** compile each flavor in its OWN gradle invocation - `compileStandardDebugKotlin` (+ any `-Pfms.*` flag) alone, then `compileNoLegalDebugKotlin` alone. Both ran green separately (standard 14s with `-Pfms.edgeGestureOverlay=on`, noLegal 1m24s).
   **How to apply:** Never batch a `*NoLegal*` task together with a `*Standard*`/`*Lite*`/`*Photos*`/`*Legacy*` task in a single `gradlew` call. One flavor per invocation (serial). If a standard task reports "task not found" and your command line also contains "nolegal", that is the cause.

9. **`processStandard*Manifest` does not re-detect a `-P` config delta on incremental runs (observed 2026-06-26, S0672).** Toggling a `-Pfms.<gate>=on/off` that drives a `variant.sources.manifests.addStaticManifestFile(..)` injection in `build.gradle.kts` does NOT reliably re-run `:app_v2:processStandardDebugMainManifest` - the on-disk merged manifest can stay stale, so a grep of `build/intermediates/merged_manifest/.../AndroidManifest.xml` shows a FALSE "injected service absent". Verified injection deltas by appending `--rerun-tasks` (forces the manifest task) - then the newly-injected `<service>` appears. The compile task itself (mounting the gated source set) re-runs fine; only the manifest-merge up-to-date check is the culprit.
   **How to apply:** When verifying that a flag-gated manifest injection landed (or was excluded), run the manifest task with `--rerun-tasks` (or after a clean) before grepping the merged manifest. Do not trust an incremental merged-manifest grep for a `-P`-toggled injection.

11. **A NEW Room migration trips detekt `MagicNumber` on its version literals (observed 2026-06-28, S0761).** Adding `val MIGRATION_36_37 = object : Migration(36, 37) { .. }` gets flagged `MagicNumber` on the `36`/`37`, even though every sibling (`Migration35To36` etc.) has the same bare literals and passes. Reason: the siblings are in the detekt **baseline** (frozen), so only the new file is analyzed live. There is NO suppression pattern in the siblings to copy. **Fix:** add `@Suppress("MagicNumber")` directly on the new `val MIGRATION_X_Y` declaration (version numbers are inherent to a migration; do not invent named constants for them, and do not re-baseline for your own new code). Same class of trap for any brand-new file whose pattern mirrors a baselined sibling - the baseline hides the sibling's identical findings, so yours surfaces alone.
   **How to apply:** When you add a Room migration (or any new file mirroring a baselined one) and detekt flags `MagicNumber`/`ImportOrdering`/etc. that the sibling "also has", it is the baseline hiding the sibling - fix yours (e.g. `@Suppress("MagicNumber")` on the migration val), do not assume the sibling proves it is allowed.
   **Subagent ktlint trap (same ticket):** a delegated impl agent placed `import timber.log.Timber` AFTER `import javax.inject.Inject`, tripping `ImportOrdering`. `timber` (and `kotlinx`) belong in the leading `*` group, BEFORE the `java`/`javax`/`kotlin` trailing groups - confirmed by clean baselined files (`WorkManagerScheduler` orders timber before java/javax). Subagents cannot run detekt under a no-build constraint, so ALWAYS re-run `:app_v2:detekt --rerun-tasks` centrally after a delegated impl and fix import placement yourself.

12. **`a.ps1 d`/`dq` builds + copies the APK but does NOT install it to a connected device (observed 2026-07-11, S0994 device-test).** After a green `a.ps1 d`, the emulator kept running the OLD APK - the new contextual button was absent in the UI dump until I ran `scripts/devtest/adb.ps1 install` (installs the freshly built debug APK) and re-launched. The `d` build only writes the APK to `app_v2/build/outputs/apk/...` and copies it to DOWNLOADS/Google Drive; there is no `adb install` step (that's `ivn` for noLegal, or `adb.ps1 install` for standard). So an on-device smoke that shows your change missing is very likely testing the stale install, not a real bug.
   **How to apply:** Before verifying a UI change on a device, `adb.ps1 install` (or `a.ps1 ivn` for noLegal) the freshly built APK first, then relaunch - never trust the on-device state right after `a.ps1 d` alone. Confirm the running version via the Settings footer / `versionName`.

13. **`build-and-push-all.ps1` one-shot 12-variant invocation OOMs the Kotlin daemon (observed 2026-07-12).** The script's Pass 1 runs `assembleStandardDebug assembleLiteDebug assemblePhotosDebug assembleLegacyDebug assembleVrDebug assembleStandardRelease ... :wear:assembleDebug :wear:assembleRelease` - 12 variants - in ONE `gradlew` call with `org.gradle.workers.max=8`. Reproduced twice in a row (including the script's own built-in retry): `compilePhotosDebugKotlin FAILED` with `java.lang.OutOfMemoryError: GC overhead limit exceeded`, then the Kotlin daemon crashes and every subsequent flavor's compile cascades `DaemonCrashedException` / `Connection refused` / `Connection reset` (kotlin.daemon.jvm.options is `-Xmx4g`; org.gradle.jvmargs is `-Xmx6g`). Machine has 63.7GB total RAM (17GB free measured right after the crash) so it is concurrency/peak-pressure, not a hard ceiling - up to 8 parallel workers each potentially spinning a Kotlin daemon, plus native CMake compiles (armeabi-v7a/x86/x86_64) running alongside, spikes past what a single 4GB daemon tolerates during heavy IR/backend work. Distinct from gotcha #10 (task-name-triggered noLegal variant-gating) - this is pure memory pressure, and retry-as-is does NOT cure it (failed identically twice).
   **How to apply:** Don't blindly retry a `build-and-push-all.ps1` OOM a third time. Fix options in increasing order of invasiveness: (a) pass `--max-workers=4` (or lower) to just this script's gradlew call to cut concurrent daemon count; (b) raise `kotlin.daemon.jvm.options` `-Xmx` in `gradle.properties` (global, affects every build, room exists given 63.7GB total); (c) serialize the 12-variant command into one-flavor-at-a-time sequential gradlew calls (mirrors the proven fix for gotcha #10, most robust, slowest wall-clock). Get the owner's call before spending another ~20min cycle on a guess - this is a resource-tuning tradeoff, not a single obviously-correct fix.
