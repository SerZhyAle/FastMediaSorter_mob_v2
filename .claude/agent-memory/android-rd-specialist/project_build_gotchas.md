Build/tooling gotchas observed while running builds.

1. **`build-debug.PS1` flaky daemon stop.** The Gradle build sometimes fails with `FAILURE: ... Gradle build daemon has been stopped: stop command received` (or a Windows file-lock `NoSuchFileException` in `temp/gradle-tmp/kotlin-backups/*.backup`) at the `:app_v2:compileStandardDebugKotlin` step. Likely cause: the IDE (VSCode/Android Studio with the project open) runs its own Gradle sync after file changes and stops daemons. `build-debug.PS1` only auto-retries for `Failed to store cache entry` and `kapt3/incrementalData` lock errors - **not** for daemon-stop. **Fix:** run `./gradlew --stop`, ensure `temp/gradle-tmp` exists (`mkdir -p temp/gradle-tmp`), then re-run `build-debug.PS1` - it succeeds on retry. A `e: Daemon compilation failed: null` / `Backend Internal error: IR fake override builder` line can appear and the build still succeeds (falls back to in-process compile). Don't treat a single daemon-stop as a real build failure - retry first.
   **How to apply:** When a build fails with daemon-stop / kotlin-backups file-lock, retry once before reporting a build failure.
   **Escalation (observed 2026-05-30, S0291 noLegalDebug):** repeated rapid CLI builds while the IDE Gradle is also active produce a *cascade* of corruption that simple retry does NOT cure: first `Could not close incremental caches ... class-attributes.tab/proto.tab ... already registered` + `Detected multiple Kotlin daemon sessions` (Kotlin incremental cache), then `kaptGenerateStubs ... Failed to create MD5 hash for ...$Companion.class` (kapt incremental), then `merge/packageResources FAILED ... NoSuchFileException: ...incremental/.../stripped.dir/layout/<untouched>.xml` (resource intermediates vanishing mid-compile, for layouts you never touched). Each aborted daemon-stop run corrupts another incremental layer. The reliable cure is a **full `./gradlew :app_v2:clean` then a single build with no concurrent invocations** - NOT more incremental retries. Critically: source that compiles is provable from an *early* run reaching post-compile tasks (`buildCMakeDebug`, `compileNoLegalDebugKotlin`, `mergeNoLegalDebugNativeLibs`, `stripNoLegalDebugDebugSymbols`) - if those passed once, later resource/cache failures are environmental, not your code. Don't burn >3 builds chasing a green APK when the IDE is fighting you; validate compile from the early run and, for device-test specs, hand the APK mint to the owner's clean environment.
   **Exit-code trap:** `pwsh -File a.ps1 nd | tee log` and `pwsh -File a.ps1 nd > log; echo $?` both report exit 0 regardless of build outcome (tee / the trailing echo own the exit). ALWAYS verify by `grep -E "BUILD SUCCESSFUL|BUILD FAILED" log`, never trust the reported exit code of a piped/`;`-chained build.
   **Stale-daemon cascade (observed 2026-06-05, S0360 standardDebug).** Signal: the Gradle startup line climbs - `Starting a Gradle Daemon, N stopped Daemons could not be reused` with N growing build-to-build (saw it reach 15). Each `build-debug.PS1` run then dies with `Gradle build daemon has been stopped: stop command received` at a *post-compile* stage (dexBuilder / transformClassesWithAsm / mergeNativeLibs), sometimes preceded by `FileNotFoundException: ...build/kotlin/.../shrunk-classpath-snapshot.bin`. Critically: `compileStandardDebugKotlin` + `compileStandardDebugJavaWithJavac` + `hiltJavaCompileStandardDebug` all completed cleanly in every aborted run - so the source compiles; the stop is external/environmental. `recover-kapt-stall.ps1 -Task ...assembleStandardDebug` (which retries `--no-daemon`) did NOT cure it - the external stop kills even the single-use daemon. The cure that worked: `pwsh -NoProfile -File scripts/builders/clean-gradle-caches.ps1` (nukes `.gradle/`, `build/`, `app_v2/build/`, runs `gradlew clean`) - its embedded clean ran green with no stop, and the next full `build-debug.PS1` succeeded in ~2m49s. Order of escalation: (1) retry once, (2) `recover-kapt-stall.ps1` for kapt-stub/incremental corruption, (3) `clean-gradle-caches.ps1` when the daemon-count keeps climbing and stop-commands recur across runs.

3. **`dev/CATALOG/app_v2.jsonl` and `app_v2.md` are gitignored** (confirmed via `git check-ignore`). CLAUDE.md says "commit updated dev/CATALOG/<module>.jsonl + <module>.md together with the code change" - but they're not tracked, so there's nothing to commit. Still run `scan.ps1` + `render.ps1` after `.kt` changes (the catalog is a local index used by `query.ps1`), just don't expect/require a git diff for them.
   **How to apply:** After `.kt` edits, regenerate the catalog but skip the "commit catalog files" step for app_v2 - they're gitignored.

4. **Stale `JAVA_HOME` after a JDK point-update (observed 2026-06-13).** A fresh Bash-tool shell had `JAVA_HOME=C:/Program Files/Java/jdk-21.0.10`, but only `jdk-21.0.11` (and `jdk-17`, `latest`) existed on disk, so `a.ps1 fk`/gradlew died with `ERROR: JAVA_HOME is set to an invalid directory`. Cure: export a valid JDK for the invocation - `export JAVA_HOME="/c/Program Files/Android/Android Studio/jbr"` (the toolchain `gradle.properties` documents as `org.gradle.java.home`) or `jdk-21.0.11`. The Android Studio JBR is itself `21.0.10` and builds fine.
   **How to apply:** If a build aborts immediately with "JAVA_HOME is set to an invalid directory", point JAVA_HOME at `C:/Program Files/Android/Android Studio/jbr` for the call instead of debugging the shell profile.

2. **Chaquopy variant gate (S0174/S0175).** When `local.properties` has `chaquopy.enabled=true` (set for IDE sync on noLegal flavor), `isNoLegalBuild=true` fires in `app_v2/build.gradle.kts` and a `beforeVariants` block **disables all non-noLegal variants**. This makes `assembleStandardDebug` and all other non-noLegal tasks invisible. Fixed 2026-05-12 by: (a) making explicit `-Pchaquopy.enabled` Gradle property take strict precedence over `local.properties`, (b) adding `-Pchaquopy.enabled=false` to ALL non-noLegal build scripts in `scripts/builders/` and `dev/build-with-version.ps1`. If symptoms recur (task not found, only `noLegal` variants visible), check: does `local.properties` have `chaquopy.enabled=true`? If yes, ensure the build script passes `-Pchaquopy.enabled=false`.
   **How to apply:** When adding new non-noLegal build scripts, always include `-Pchaquopy.enabled=false` in the Gradle invocation.
