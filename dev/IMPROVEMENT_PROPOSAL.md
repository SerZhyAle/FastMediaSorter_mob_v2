## II. ВИЗУАЛЬНЫЙ ИНТЕРФЕЙС (UI/UX)

### II.1 Отсутствие Navigation Component

**Проблема**: Навигация полностью реализована через `Intent` / `startActivity()`. Нет navigation graph. Это затрудняет: deep linking, анимации переходов, backstack management, type-safe аргументы.

**Предложение**: Рассмотреть миграцию ключевых переходов на AndroidX Navigation Component. Как минимум — для новых экранов. Существующие Activity можно интегрировать постепенно.

**Как это проявляется для пользователя (пример):**
- Пользователь открывает `Main` → `Browse` → `Player`, затем нажимает Back и ожидает вернуться в тот же контекст (тот же фильтр/позиция списка).
- При частых переходах между экранами состояние может вести себя неравномерно, потому что back stack собирается вручную в разных местах.

**Как должно выглядеть (целевое UX):**
- Единый предсказуемый сценарий Back: всегда возврат в предыдущий экран с сохранением контекста.
- Глубокие ссылки (например, открыть конкретный экран настроек) работают одинаково из уведомления, виджета и внешнего интента.
- Переходы и аргументы описаны централизованно, без расхождений между экранами.

### II.2 Minimal Compose adoption

**Проблема**: Из 11 Activity только 1 использует Compose (ResourceLaunchWidgetConfigActivity). Остальные — XML + ViewBinding. Проект уже подключил compose-bom и material3-compose. Недоиспользование.

**Предложение**: Определить стратегию миграции на Compose. Не обязательно переписывать всё — но новые экраны (и рефакторинги крупных) делать на Compose. Это уменьшит количество XML-файлов (109 layout + 28 landscape = 137 XML) и упростит landscape-адаптацию.

**Как это проявляется для пользователя (пример):**
- На разных экранах похожие элементы могут визуально/поведенчески отличаться (отступы, размеры, состояния кнопок), потому что интерфейс собирается разными подходами.
- Изменение UI на одном экране не всегда автоматически подтягивает одинаковое поведение на другом.

**Как должно выглядеть (целевое UX):**
- Единый набор UI-паттернов: одинаковые карточки, кнопки, состояния loading/error/empty.
- Быстрые итерации интерфейса без дублирования в нескольких XML-вариантах.
- Новые экраны добавляются быстрее и визуально консистентнее.

### II.3 Tablet/Large screen support (ограничен)

**Проблема**: Только 2 layout override для sw480dp/sw720dp (welcome screen). Нет tablet-адаптации для основных экранов: Browse, Player, Settings, Add Resource. На планшетах UI просто растягивается.

**Предложение**: Добавить responsive layout для ключевых экранов (минимум Browse и Player). Рассмотреть two-pane layout (list-detail) для планшетов. Это особенно актуально для сценария «цифровая фоторамка» и ChromeOS.

**Как это проявляется для пользователя (пример):**
- На планшете в `Browse` пользователь видит тот же «телефонный» сценарий: список, затем отдельный полноэкранный просмотр.
- При этом большой экран не используется эффективно: много пустого места, лишние переходы «вперёд-назад».

**Как должно выглядеть (целевое UX):**
- Two-pane режим: слева список/сетка, справа предпросмотр выбранного файла.
- Для `Settings` и `Add Resource` — более широкие формы, логичные группировки и меньше вертикального скролла.
- Для ChromeOS/desktop-режима — плотный, функциональный layout без «растянутого телефона».

## III. ФУНКЦИОНАЛЬНОСТЬ

### III.2 Undo недоступен для сетевых ресурсов

**Проблема**: Документированное ограничение. Удалённые с сетевых ресурсов файлы невозвратимы. Пользователь может случайно удалить важный файл.

**Предложение**: Для сетевых ресурсов — показывать confirmation dialog перед удалением (более заметный, чем для локальных). Рассмотреть реализацию сетевой корзины (временная папка на сервере).

**Как это проявляется для пользователя (пример):**
- Пользователь удаляет фото на SMB/NAS, по привычке рассчитывая на Undo.
- Файл удалён безвозвратно, потому что undo для сети не поддерживается.

**Юс-кейс:**
1. Пользователь выделяет файл на сетевом ресурсе и жмёт Delete.
2. Видит предупреждение: «Удаление без возможности отмены».
3. Явно подтверждает действие или отменяет.

**Как должно выглядеть (целевое UX):**
- Для network/cloud удалений всегда показывается усиленный confirm-диалог.
- В диалоге явно указано: «Undo недоступен».
- В идеале: режим «сетевая корзина» (перемещение в `/.trash` на сервере, если доступно).

### III.3 Нет синхронизации избранного между устройствами

**Проблема**: Избранное хранится локально в Room DB. При смене устройства — теряется. Нет экспорта/импорта.

**Предложение**: Минимально — экспорт/импорт списка избранного в JSON/CSV. Продвинуто — синхронизация через облачные провайдеры (GDrive/Dropbox).

**Как это проявляется для пользователя (пример):**
- Пользователь настроил избранное на телефоне, затем переходит на другой телефон/планшет.
- Все флаги избранного отсутствуют, коллекцию нужно собирать заново.

**Юс-кейс:**
1. На устройстве А пользователь делает «Экспорт избранного».
2. На устройстве Б делает «Импорт избранного».
3. Получает восстановленную коллекцию без ручной разметки.

**Как должно выглядеть (целевое UX):**
- В `Settings` есть пункт «Экспорт/Импорт избранного».
- Формат переносимый (JSON), с понятным отчётом: «Импортировано N записей».
- Следующий этап: автосинхронизация через облачный профиль.

### III.4 Нет бэкапа избранного

**Проблема**: В FAQ явно сказано: «Favorites are NOT included in backup (future feature)». Бэкап настроек существует, но избранное не включено.

**Предложение**: Включить избранное в механизм бэкапа/восстановления настроек.

**Как это проявляется для пользователя (пример):**
- Пользователь делает backup перед переустановкой приложения.
- После restore настройки возвращаются, а избранное — нет.

**Юс-кейс:**
1. Пользователь нажимает «Создать backup».
2. Переустанавливает приложение.
3. Нажимает «Восстановить backup».
4. Получает и настройки, и избранное.

**Как должно выглядеть (целевое UX):**
- Backup содержит отдельный блок избранного.
- В restore-диалоге есть чекбокс: «Восстановить избранное».
- При восстановлении показывается итог: добавлено/пропущено/конфликты.

### III.5 RAW-форматы не поддерживаются

**Проблема**: CR2, NEF, ARW, DNG и прочие RAW-форматы не отображаются. Для фотографов это критичное ограничение.

**Предложение**: Добавить базовую поддержку RAW через существующие библиотеки (Adobe DNG для встроенного JPEG-preview, или LibRaw/RawDecoder). Начать с preview (embedded JPEG), полное декодирование — опционально.

**Как это проявляется для пользователя (пример):**
- Фотограф открывает папку с `CR2/NEF/ARW`.
- Вместо превью видит «неподдерживаемый формат» и теряет сценарий быстрой сортировки.

**Юс-кейс:**
1. Пользователь открывает RAW-папку после съёмки.
2. Видит миниатюры RAW (через embedded preview).
3. Быстро отмечает годные/брак и сортирует по папкам.

**Как должно выглядеть (целевое UX):**
- На первом этапе — корректный предпросмотр и базовая навигация по RAW.
- Ясная маркировка в UI: «RAW preview mode».
- Полное декодирование RAW — как расширение, не блокирующее MVP.

### III.6 Wear OS — только локальные файлы

**Приоритет**: Высокий.

**Проблема**: Документированное ограничение. Wear OS не поддерживает сетевые/облачные ресурсы. Пользователь не может передать на часы ни список ресурсов, ни содержимое с телефона.

**Предложение (MVP)**: Добавить в Settings (или в экран управления ресурсами) две кнопки:
- **«Экспорт ресурсов на часы»** — отправляет конфигурацию настроенных ресурсов (имя, тип, параметры подключения) на Wear через `Wearable.DataClient`.
- **«Импорт ресурсов с часов»** — синхронный pull или receive из Data Layer.

Полный SMB на часах нецелесообразен, но прокси через телефон и передача конфигурации — реализуемы.

**Юс-кейс:**
1. Пользователь нажимает «Экспорт ресурсов на часы» в мобильном приложении.
2. Список ресурсов отправляется через Wearable Data Layer API.
3. На часах появляется синхронизированный список ресурсов без ручного ввода.
4. Опционально: телефон проксирует запросы к сети/облаку для Wear.

### III.7 Нет batch-rename

**Проблема**: Можно переименовать файлы по одному. Нет массового переименования (шаблон, нумерация, замена подстроки).

**Предложение**: Добавить batch-rename в режиме множественного выбора (BrowseActivity). Шаблон: `{name}_{counter}`, замена подстроки, добавление даты к имени.

**Как это проявляется для пользователя (пример):**
- После импорта 200 файлов нужно привести имена к единому формату.
- Переименование по одному файлу делает задачу непрактичной.

**Юс-кейс:**
1. Пользователь выделяет группу файлов.
2. Выбирает «Batch rename».
3. Задаёт шаблон: `Trip_2026_{counter}`.
4. Проверяет предпросмотр и применяет.

**Как должно выглядеть (целевое UX):**
- Массовое переименование с preview до применения.
- Поддержка сценариев: добавить префикс/суффикс, заменить подстроку, нумерация.
- Возможность отката последней операции (где технически возможно).

### III.8 Нет поддержки тегов/меток

**Проблема**: Единственная система организации — папки + избранное (boolean). Нет пользовательских тегов/меток для файлов.

**Предложение**: Рассмотреть систему тегов (цветных меток, как в macOS Finder). Хранить в Room DB. Позволит фильтровать коллекцию по тегам помимо папок.

**Как это проявляется для пользователя (пример):**
- Пользователь хочет помечать файлы по смыслу: «в работу», «отправить», «архив».
- Папки и избранное не покрывают такие поперечные сценарии.

**Юс-кейс:**
1. Пользователь добавляет метку `В работу` к файлам из разных ресурсов.
2. Применяет фильтр по метке.
3. Получает единый список «задач» независимо от папок.

**Как должно выглядеть (целевое UX):**
- Добавление/удаление тегов из контекстного меню.
- Быстрый фильтр по тегам в `Browse`.
- Комбинация тегов с существующими фильтрами и сортировкой.

### III.9 Нет статистики использования

**Проблема**: Нет информации о: сколько файлов отсортировано, сколько места освобождено, самые крупные файлы, дубликаты.

**Предложение**: Добавить экран «Статистика» — общее количество файлов по ресурсам, объём занятого кэша, топ-форматы, история операций.

**Как это проявляется для пользователя (пример):**
- Пользователь не понимает, какой объём уже отсортирован и что именно занимает кэш.
- Нет метрик прогресса, сложно оценить пользу приложения во времени.

**Юс-кейс:**
1. Пользователь открывает «Статистика».
2. Видит: отсортировано за неделю, освобождено места, топ источников.
3. Решает, что чистить/оптимизировать дальше.

**Как должно выглядеть (целевое UX):**
- Простой dashboard без перегрузки.
- Ключевые KPI: обработанные файлы, перемещено/удалено, размер кэша.
- Переход к действиям: «Очистить кэш», «Открыть проблемные ресурсы».

### III.10 Отсутствие drag-and-drop

**Проблема**: Для ChromeOS/desktop-режима (который поддерживается через клавиатуру/мышь) было бы естественно поддерживать drag-and-drop для файловых операций.

**Предложение**: Реализовать drag-and-drop в BrowseActivity для перемещения/копирования файлов между папками (особенно актуально в two-pane tablet layout).

**Как это проявляется для пользователя (пример):**
- На ChromeOS с мышью и клавиатурой пользователь ожидает desktop-модель взаимодействия.
- Сейчас операции делаются через меню/кнопки, что медленнее для массовых действий.

**Юс-кейс:**
1. Пользователь в two-pane режиме перетаскивает файлы из левой панели в папку справа.
2. Видит подсказку действия: `Copy` или `Move`.
3. Подтверждает и получает результат без лишних диалогов.

**Как должно выглядеть (целевое UX):**
- Drag-and-drop активен для мыши/тачпада, с визуальным feedback.
- Поддержка multi-select drag.
- Понятные ограничения и fallback на текущие кнопки/меню.

## IV. СТАБИЛЬНОСТЬ И ТЕХДОЛГ

### IV.1 Файлы-гиганты (14 файлов > 1000 LOC)

**Проблема**: Проектное ограничение — max 1000 строк на файл. Нарушают:

| Файл | LOC | Превышение |
|------|-----|------------|
| BrowseViewModel | 3290 | 3.3× |
| PlayerActivity | 3204 | 3.2× |
| MediaFileAdapter | 2290 | 2.3× |
| BrowseActivity | 2080 | 2.1× |
| EpubViewerManager | 2050 | 2.1× |
| GeneralSettingsFragment | 1883 | 1.9× |
| AddResourceActivity | 1817 | 1.8× |
| VideoPlayerManager | 1737 | 1.7× |
| ImageLoadingManager | 1674 | 1.7× |
| TextViewerManager | 1624 | 1.6× |
| AddResourceViewModel | 1550 | 1.6× |
| PdfViewerManager | 1399 | 1.4× |
| PlayerViewModel | 1303 | 1.3× |
| TranslationManager | 1007 | 1.0× |

**Предложение**: Поэтапный рефакторинг. Приоритет — BrowseViewModel (выделить группы UseCase), PlayerActivity (дальнейшая декомпозиция на managers), BrowseActivity (выделить UI-логику). Целевой порог: ≤800 LOC.

### IV.2 TrustAllX509TrustManager (БЕЗОПАСНОСТЬ)

**Проблема**: В lint baseline — 2 вхождения `TrustAllX509TrustManager`. Это подавленное предупреждение о **принятии всех SSL-сертификатов** без проверки. Потенциальная уязвимость MITM.

**Предложение**: Провести аудит. Если это для самоподписанных SFTP-серверов — реализовать certificate pinning или user-confirmation flow («Этот сертификат не доверенный. Продолжить?»). Не оставлять TrustAll в release.


### IV.4 40 устаревших зависимостей

**Проблема**: 40 `GradleDependency` предупреждений в lint baseline. Зависимости зафиксированы на конкретных версиях с обоснованием (раздел 11 TECH_REQUIREMENTS), но некоторые могут быть обновлены без рисков.

**Предложение**: Для каждой из 40 зависимостей — проверить, есть ли безопасный апдейт (patch/minor). Обновить те, что не требуют миграции. Для остальных — документировать причину блокировки в TECH_REQUIREMENTS.


### IV.8 Тестовое покрытие — неопределённое

**Проблема**: Есть unit test infrastructure (JUnit, MockK, Robolectric) и Maestro E2E (56+ тестов), но неизвестен процент покрытия unit-тестами. Нет CI/CD pipeline видимого в репозитории.

**Предложение**: Запустить coverage report (`jacoco`). Определить baseline и целевой порог. Добавить GitHub Actions для автоматического прогона тестов на PR.

### IV.9 Отсутствие CI/CD

**Проблема**: Нет конфигурации GitHub Actions / другого CI. Билды и тесты запускаются вручную через PowerShell-скрипты.

**Предложение**: Настроить базовый CI pipeline:
- На push/PR: lint + unit tests
- На tag/release: build APK + upload artifacts
- Maestro E2E — по расписанию или вручную

## V. БЕЗОПАСНОСТЬ (дополнение к IV.2)

### V.1 WebView JavaScript в EPUB-ридере (БЕЗОПАСНОСТЬ)

**Проблема**: В `EpubViewerManager.kt` (строка ~215) включён JavaScript для WebView, отображающего EPUB-контент. EPUB-файлы — пользовательский (недоверенный) контент. JavaScript в WebView позволяет: DOM manipulation, потенциальный XSS, доступ к file:// протоколу.

**Что уже хорошо**: `addJavascriptInterface()` не вызывается, WebViewClient перехватывает запросы.

**Предложение**:
- Отключить JavaScript, если определение scroll position можно реализовать через CSS
- Добавить Content-Security-Policy заголовки в генерируемый HTML
- Установить `setAllowFileAccess(false)` и `setAllowFileAccessFromFileURLs(false)`
- Или: включать JS только для locally-generated HTML (trusted), не для контента из EPUB

### V.2 Тестовые credentials в production-сборке

**Проблема**: В `app_v2/src/main/res/xml/sza_resources.xml` (строки 38–61) находятся **plaintext** логины и пароли для SMB/SFTP серверов. Ресурс доступен при декомпиляции APK.

**Предложение**:
- Исключить `sza_resources.xml` из release-сборки (flavor-specific sourceSets)
- Оставить только в debug flavor
- Добавить Gradle-проверку, блокирующую release-билд при наличии этого файла

### V.3 Отсутствие FTP deprecation / SFTP migration path

**Проблема**: FTP (commons-net 3.10.0) передаёт данные и учётные записи в открытом виде. TrustAllX509TrustManager в библиотеке создаёт MITM-риски для FTPS. При наличии SFTP — FTP избыточен для большинства пользователей.

**Предложение**:
- Показывать предупреждение при создании FTP-ресурса: «FTP не шифрует данные. Рекомендуем SFTP»
- Рассмотреть deprecation FTP в будущих версиях
- Как минимум — документировать risk в Troubleshooting

## VIII. ДОСТУПНОСТЬ И СОВМЕСТИМОСТЬ

### VIII.1 Accessibility: текст меньше 12sp

**Проблема**: В `dimens.xml` определены размеры ниже минимума WCAG:
- `text_size_tiny` = 10sp
- `text_size_11sp` = 11sp
- `browse_filter_badge_text_size` = 10sp
- `sleepTimerBadge` в `activity_player_unified.xml` = 11sp (hardcoded)

**Предложение**: Установить минимум 12sp для всех текстовых элементов. Для badge/chip элементов — использовать scaling с учётом system font size.

### VIII.2 TalkBack-тестирование отсутствует

**Проблема**: `contentDescription` есть на 50+ элементах плеера (хорошо). Однако:
- В lint-baseline есть `ClickableViewAccessibility` нарушения (TextViewerManager, строка 173)
- Нет артефактов TalkBack-тестирования
- Empty state / error state иконки в Browse не имеют описаний
- Touch Zones (невидимые 3×3 зоны) полностью невидимы для screen reader

**Предложение**:
- Исправить `performClick()` для custom ScrollView в TextViewerManager
- Добавить доступные описания для empty/error states
- Для TalkBack: touch zones должны аннонсировать своё назначение при фокусе
- Добавить ручной TalkBack-чеклист в TEST_SCENARIOS.md

### VIII.3 Wear OS — отсутствие локализации

**Проблема**: `wear/src/main/res/values/strings.xml` содержит ~45 строк только на английском. Нет `values-ru/` и `values-uk/`. Wear-пользователи с русским/украинским языком видят только английский интерфейс.

**Предложение**: Добавить `values-ru/strings.xml` и `values-uk/strings.xml` в wear-модуль. Синхронизировать ключи с главным приложением, где naming совпадает.

### VIII.4 Landscape-варианты для диалогов отсутствуют

**Проблема**: Из 104 portrait-layouts только 28 имеют landscape-варианты (27% покрытие). Все диалоги (rename, delete, filter, sort, color picker — 25+ layouts) не имеют landscape-адаптации. На планшетах в ландшафтной ориентации диалоги сжимаются или обрезаются.

**Предложение**: Создать landscape-варианты для критичных диалогов (file operations, filter, sort). Рассмотреть использование `ConstraintLayout` с процентными размерами и гибкими ограничениями для автоматической адаптации.

### VIII.5 RTL-поддержка: формально включена, фактически непроверена

**Проблема**: `android:supportsRtl="true"` включено в манифесте, но нет `values-ldrtl/` ресурсов для кастомных layout-overrides. При добавлении арабского/иврита интерфейс может сломаться.

**Предложение**: Если поддержка RTL планируется — провести визуальный аудит ключевых экранов в режиме Developer Options → Force RTL layout. Зафиксировать результат. Если RTL не в планах — задокументировать ограничение.

## IX. АРХИТЕКТУРА И ТЕХДОЛГ (дополнение к IV)

### IX.1 Фрагментированные Result-типы

**Проблема**: В проекте используется 5+ различных Result-типов: `FileOperationResult`, `CloudResult<T>`, `SmbResult<T>`, `AuthResult`, `kotlin.Result<T>`. Нет единого error wrapper, нет классификации ошибок (retryable vs permanent vs auth-required). Это усложняет error handling в ViewModel и создаёт дублирование логики.

**Предложение**: Ввести единый `sealed class AppResult<T>` с поддержкой ErrorCode, retryable flag, причины (cause). Мигрировать постепенно, начиная с новых Use Cases.

### IX.2 IntegrationTestRunner в production-коде

**Проблема**: `IntegrationTestRunner.kt` (~2400 строк) — in-app тестовый фреймворк, находится в `domain/usecase/`. Это увеличивает размер APK, нарушает принцип разделения (тесты ≠ бизнес-логика), потенциально может быть вызван в production.

**Предложение**: Перенести в `androidTest/` модуль или выделить в debug-only source set. Если нужен in-app тест — оставить лёгкую обёртку с lazy-загрузкой из debug flavor.

### IX.3 FileMetadataCache без TTL

**Проблема**: `FileMetadataCacheEntity` (EXIF, duration, resolution, artist, album, title) хранится в Room без ограничения по времени. При каждом сканировании папок метаданные добавляются, но никогда автоматически не удаляются. БД бесконтрольно растёт.

**Предложение**: Добавить `cachedAt` timestamp (если отсутствует) и периодическую очистку записей старше N дней через `OrphanCleanupWorker`. Или ограничить кэш по количеству записей (LRU).

### IX.4 WorkManager — нет exponential backoff

**Проблема**: 4 Worker'а (Trash, Sync, Orphan, Revocation) используют дефолтный retry policy. При устойчивых сбоях (нет сети, сервер недоступен) — повторы идут с одинаковой частотой, создавая ненужную нагрузку.

**Предложение**: Добавить `BackoffPolicy.EXPONENTIAL` с начальным delay 30 секунд. Для сетевых worker'ов — добавить `Constraints.Builder().setRequiredNetworkType(NetworkType.CONNECTED)`.

### IX.5 Отсутствие database migration rollback

**Проблема**: 18 Room-миграций без возможности отката. Откат на предыдущую версию приложения приведёт к SQL-ошибке и, вероятно, к потере данных. Migration 8→9 деструктивна (drop + recreate cached_file_lists).

**Предложение**: Документировать schema versioning. Для критичных миграций — добавить pre-migration backup в SharedPreferences или отдельный файл. Рассмотреть `.fallbackToDestructiveMigration()` с уведомлением пользователя.

## X. НОВЫЕ ЮС-КЕЙСЫ И ИДЕИ

### X.1 Обнаружение дубликатов файлов

**Проблема**: Нет инструмента для поиска дубликатов. При работе с множественными ресурсами (локальный + NAS + облако) одні и те же файлы легко могут дублироваться.

**Юс-кейс**: Пользователь запускает «Найти дубликаты» → анализ по размеру + хешу → список групп → выбор: удалить / переместить / пропустить.

**Предложение**: Начать с обнаружения по имени + размеру (быстро, не требует чтения содержимого). В продвинутой версии — partial MD5/SHA256 для точного сравнения.

### X.2 Cast / Screen Mirror для слайдшоу

**Проблема**: Слайдшоу с музыкой — сильная функция. Но нет возможности вывести его на TV (Chromecast / DLNA / Miracast). Для сценария «цифровая фоторамка» это критично.

**Юс-кейс**: Пользователь запускает слайдшоу → нажимает Cast → изображения показываются на ТВ, музыка воспроизводится через ТВ-динамики или телефон.

**Предложение**: Интеграция Google Cast SDK. Начать с изображений (JPEG/PNG rendering на receiver). Видео — следующий этап.

### X.3 Quick Actions (App Shortcuts)

**Проблема**: Для быстрого доступа есть виджеты, но нет App Shortcuts (long-press на иконку приложения → меню в стиле iOS 3D Touch). Это стандартная Android-функция с API 25.

**Юс-кейс**: Пользователь зажимает иконку → видит «Последний ресурс», «Избранное», «Продолжить чтение» → одно нажатие → сразу в нужный контекст.

**Предложение**: Добавить static shortcuts в `res/xml/shortcuts.xml`. Динамические shortcuts — через `ShortcutManager` для последних 3 активных ресурсов.

### X.4 Индикация устаревшего кэша

**Проблема**: Приложение кэширует файловые списки для оффлайн-доступа (`CachedFileListRepository`), но пользователь не видит, когда кэш устарел. При повторном просмотре сетевого ресурса в оффлайне — данные выглядят свежими, хотя могут быть устаревшими.

**Юс-кейс**: В режиме оффлайн (или при ошибке подключения) Browse показывает stamp: «Данные от 10.03.2026 14:30 (кэш)». Pull-to-refresh обновляет при наличии сети.

**Предложение**: Хранить lastFetchedAt в `CachedFileListEntity`. Показывать Chip/Badge «Cached: {time}» в toolbar Browse при использовании кэшированных данных.

### X.5 Поддержка HEIF/HEIC-форматов

**Проблема**: Современные iPhone сохраняют фото в HEIC. При переносе на NAS/SMB и просмотре через FastMediaSorter — формат может не отображаться на устройствах без аппаратного декодера HEIF (Android 9–10 со старыми SoC).

**Предложение**: Проверить текущую поддержку HEIC через Glide. Если не работает — добавить HEIF-decoder как fallback. Документировать device-specific ограничения.

### X.6 Пакетное управление метаданными (Batch EXIF edit)

**Проблема**: Приложение уже умеет читать EXIF и audio metadata. Но нет возможности редактировать — ни для отдельных файлов, ни массово. Для фотографов: изменить дату съёмки, добавить копирайт. Для аудио: исправить artist/album/title.

**Юс-кейс**: Пользователь выделяет группу фото → «Редактировать EXIF» → устанавливает дату/автора → применяет ко всем.

**Предложение**: Начать с базового EXIF write (дата, copyright) для JPEG. Audio metadata write для MP3 (ID3 tags). Массовое применение через selection mode в Browse.

### X.7 Встроенный медиа-сервер (DLNA/UPnP)

**Проблема**: Приложение — потребитель медиа с NAS/SMB. Но телефон может быть и источником. Нет возможности расшарить локальные папки по сети для просмотра на другом устройстве.

**Юс-кейс**: Пользователь включает «Поделиться папкой» → другие устройства в сети видят контент через DLNA/UPnP player (Smart TV, ПК).

**Предложение**: Рассмотреть интеграцию lightweight DLNA/UPnP media server. Позиционирование: «двусторонний медиа-хаб» вместо «только просмотрщик».

### X.8 Голосовые команды для управления плеером

**Проблема**: Плеер управляется через touch zones и кнопки. Для hands-free сценариев (фоторамка, готовка, вождение) голосовое управление было бы удобнее.

**Юс-кейс**: «Следующее фото», «Пауза», «Удалить», «Добавить в избранное» — голосом через Google Assistant или встроенный speech recognition.

**Предложение**: Начать с базовых MediaSession интентов (play/pause/next/prev уже поддерживаются). Для кастомных команд — рассмотреть on-device SpeechRecognizer API.

### X.9 Автоматическая сортировка по правилам

**Проблема**: Сортировка файлов — ручной процесс (выбрал файл → выбрал папку → переместил). Для типовых сценариев это можно автоматизировать.

**Юс-кейс**: Пользователь создаёт правило: «Все .CR2 > 5MB → /Photos/RAW», «Все .mp4 с датой 2026-03 → /Videos/March». Автосортировка по расписанию или при добавлении файлов.

**Предложение**: Система правил с условиями (расширение, размер, дата, EXIF-данные) и действиями (move, copy, tag). Минимально — rule builder в Settings + manual trigger.

### X.10 Crashlytics / Firebase Performance

**Проблема**: В коде есть подготовленные TODO-заглушки (`ScanMetricsRecorder`, `OperationMetricsRecorder`) для Firebase Analytics и Crashlytics, но интеграция не завершена. В production нет отчётов о крашах и метрик производительности.

**Предложение**: Активировать Firebase Crashlytics для автоматического сбора crash-логов. Firebase Performance — для мониторинга времени запуска, сетевых операций. Это позволит выявлять проблемы раньше, чем пользователи напишут в поддержку.

### X.11 Фоновая предзагрузка миниатюр

**Проблема**: Миниатюры загружаются on-demand при скролле. Для больших коллекций (5000+ файлов) первый просмотр ощущается как «дёрганый». Для сетевых ресурсов это ещё заметнее.

**Предложение**: Опциональная фоновая предзагрузка миниатюр для активных ресурсов (WorkManager, при зарядке + Wi-Fi). Параметр в Settings: «Предзагружать миниатюры» с ограничением по объёму.
