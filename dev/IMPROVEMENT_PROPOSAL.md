## II. ВИЗУАЛЬНЫЙ ИНТЕРФЕЙС (UI/UX)

### II.1 Отсутствие Navigation Component

**Проблема**: Навигация полностью реализована через `Intent` / `startActivity()`. Нет navigation graph. Это затрудняет: deep linking, анимации переходов, backstack management, type-safe аргументы.

**Предложение**: Рассмотреть миграцию ключевых переходов на AndroidX Navigation Component. Как минимум — для новых экранов. Существующие Activity можно integrировать постепенно.

**Как это проявляется для пользователя (пример):**
- Пользователь открывает `Main` → `Browse` → `Player`, затем нажимает Back и ожидает вернуться в тот же контекст (тот же фильтр/позиция списка).
- При частых переходах между экранами состояние может вести себя неравномерно, потому что back stack собирается вручную в разных местах.

**Как должно выглядеть (целевое UX):**
- Единый предсказуемый сценарий Back: всегда возврат в предыдущий экран с сохранением контекста.
- Глубокие ссылки (например, открыть конкретный экран настроек) работают одинаково из уведомления, виджета и внешнего интента.
- Переходы и аргументы описаны централизованно, без расхождений между экранами.

### II.2 Minimal Compose adoption

**Проблема**: Из 11 Activity только 1 использует Compose (ResourceLaunchWidgetConfigActivity). Остальные — XML + ViewBinding. Проект уже подключил compose-bom и material3-compose. Недоиспользование.

**Предложение**: Определить стратегию миграции на Compose. Не обязательно переписывать всё — но новые экраны (и рефакторинги крупных) делать на Compose. Это уменьшит количество XML-файлов (109 layout + 28 landscape = 137 XML) и упростит landscape-адаптацию.

**Как это проявляется для пользователя (пример):**
- На разных экранах похожие элементы могут визуально/поведенчески отличаться (отступы, размеры, состояния кнопок), потому что интерфейс собирается разными подходами.
- Изменение UI на одном экране не всегда автоматически подтягивает одинаковое поведение на другом.

**Как должно выглядеть (целевое UX):**
- Единый набор UI-паттернов: одинаковые карточки, кнопки, состояния loading/error/empty.
- Быстрые итерации интерфейса без дублирования в нескольких XML-вариантах.
- Новые экраны добавляются быстрее и визуально консистентнее.

### II.3 Tablet/Large screen support (ограничен)

**Проблема**: Только 2 layout override для sw480dp/sw720dp (welcome screen). Нет tablet-адаптации для основных экранов: Browse, Player, Settings, Add Resource. На планшетах UI просто растягивается.

**Предложение**: Добавить responsive layout для ключевых экранов (минимум Browse и Player). Рассмотреть two-pane layout (list-detail) для планшетов. Это особенно актуально для сценария «цифровая фоторамка» и ChromeOS.

**Как это проявляется для пользователя (пример):**
- На планшете в `Browse` пользователь видит тот же «телефонный» сценарий: список, затем отдельный полноэкранный просмотр.
- При этом большой экран не используется эффективно: много пустого места, лишние переходы «вперёд-назад».

**Как должно выглядеть (целевое UX):**
- Two-pane режим: слева список/сетка, справа предпросмотр выбранного файла.
- Для `Settings` и `Add Resource` — более широкие формы, логичные группировки и меньше вертикального скролла.
- Для ChromeOS/desktop-режима — плотный, функциональный layout без «растянутого телефона».

### II.4 Accessibility (a11y) — неизвестно

**Проблема**: В lint baseline 19 `ClickableViewAccessibility` issue. Нет документации об accessibility. Неизвестно, работает ли приложение с TalkBack.

**Предложение**: Провести базовый accessibility-аудит. Убедиться, что contentDescription задан для всех иконок действий. Проверить контрастность тем.

**Как это проявляется для пользователя (пример):**
- Пользователь с TalkBack фокусируется на иконке, но слышит неинформативное «button» вместо «Удалить файл» или «Открыть настройки».
- На некоторых сочетаниях темы/фона текст и элементы управления читаются хуже.

**Как должно выглядеть (целевое UX):**
- Все кликабельные элементы имеют понятные voice-labels.
- Порядок фокуса логичный (сверху вниз, слева направо).
- Контраст и размеры интерактивных зон соответствуют минимуму доступности.

### II.5 Onboarding — одноразовый

**Проблема**: WelcomeActivity — экран welcome wizard, показывается один раз. Нет повторного доступа к обучающим материалам из настроек. Новые функции (EPUB, перевод, тач-зоны) требуют объяснения.

**Предложение**: Добавить раздел "Справка" / "Обучение" в Settings, с доступом к welcome-страницам и in-app tips для новых функций. Или контекстные подсказки при первом использовании фичи (Coach Marks).

**Как это проявляется для пользователя (пример):**
- Пользователь пропустил onboarding при первом запуске.
- Через неделю пытается понять, как включить перевод/EPUB/тач-зоны, но внутри приложения нет краткого повторного обучения «в 2 клика».

**Как должно выглядеть (целевое UX):**
- В `Settings` есть раздел «Справка/Обучение» с быстрыми мини-гайдами по ключевым фичам.
- Для сложных функций — короткие контекстные подсказки в момент первого использования.
- Пользователь может вручную повторно открыть обучение без переустановки приложения.

### II.6 Touch Zones — непрозрачная механика

**Проблема**: Touch Zones — ключевая механика плеера (3×3 сетка невидимых зон). Но: (а) по умолчанию зоны невидимы; (б) объяснение только в FAQ и welcome; (в) нет контекстного хинта «нажми сюда для X». Пользователю сложно обнаружить эту фичу органически.

**Предложение**: При первом открытии Player показывать полупрозрачный overlay с подписями зон (один раз). Добавить кнопку «?» в toolbar плеера для повторного показа.

**Как это проявляется для пользователя (пример):**
- Пользователь открывает `Player`, нажимает по экрану «как обычно», но не понимает, где зоны `COPY`, `MOVE`, `DELETE`, `MENU`, `PLAY`.
- В результате он использует только очевидные кнопки и не получает основную ценность быстрого управления жестами/тапами.

**Как должно выглядеть (целевое UX):**
- При первом входе в `Player` показывается краткий оверлей 3×3 с подписями действий.
- Кнопка `?` в toolbar повторно открывает эту схему по запросу.
- В настройках есть понятный переключатель: «Всегда показывать схему touch zones».

**Мини-сценарий (ожидаемое поведение):**
1. Пользователь открыл `Player` первый раз.
2. Видит прозрачную сетку с подписями действий.
3. Нажимает «Понятно».
4. Далее использует зоны осознанно; при необходимости открывает подсказку через `?`.

## III. ФУНКЦИОНАЛЬНОСТЬ

### III.1 Отсутствие поиска по файлам

**Проблема**: Есть фильтрация и сортировка, но нет полнотекстового поиска по имени файла в Browse. Для коллекций 1000+ файлов это критично.

**Предложение**: Добавить SearchView / поисковую строку в BrowseActivity. Фильтрация по подстроке имени. Поиск по метаданным (artist/album для аудио) — бонус.

**Как это проявляется для пользователя (пример):**
- В папке 3000+ файлов нужно найти `IMG_20240115` или `invoice_2024.pdf`.
- Сейчас пользователь вручную скроллит список/сетку или пытается сужать выбор фильтрами, что медленно.

**Юс-кейс:**
1. Пользователь открывает `Browse`.
2. Вводит часть имени файла в строку поиска.
3. Список сразу сокращается до совпадений.
4. Открывает нужный файл за 2–3 действия.

**Как должно выглядеть (целевое UX):**
- Поисковая строка в верхней панели `Browse`.
- Поиск работает мгновенно по имени, опционально — по метаданным аудио.
- Есть кнопка очистки запроса и сохранение последнего запроса до выхода из экрана.

### III.2 Undo недоступен для сетевых ресурсов

**Проблема**: Документированное ограничение. Удалённые с сетевых ресурсов файлы невозвратимы. Пользователь может случайно удалить важный файл.

**Предложение**: Для сетевых ресурсов — показывать confirmation dialog перед удалением (более заметный, чем для локальных). Рассмотреть реализацию сетевой корзины (временная папка на сервере).

**Как это проявляется для пользователя (пример):**
- Пользователь удаляет фото на SMB/NAS, по привычке рассчитывая на Undo.
- Файл удалён безвозвратно, потому что undo для сети не поддерживается.

**Юс-кейс:**
1. Пользователь выделяет файл на сетевом ресурсе и жмёт Delete.
2. Видит предупреждение: «Удаление без возможности отмены».
3. Явно подтверждает действие или отменяет.

**Как должно выглядеть (целевое UX):**
- Для network/cloud удалений всегда показывается усиленный confirm-диалог.
- В диалоге явно указано: «Undo недоступен».
- В идеале: режим «сетевая корзина» (перемещение в `/.trash` на сервере, если доступно).

### III.3 Нет синхронизации избранного между устройствами

**Проблема**: Избранное хранится локально в Room DB. При смене устройства — теряется. Нет экспорта/импорта.

**Предложение**: Минимально — экспорт/импорт списка избранного в JSON/CSV. Продвинуто — синхронизация через облачные провайдеры (GDrive/Dropbox).

**Как это проявляется для пользователя (пример):**
- Пользователь настроил избранное на телефоне, затем переходит на другой телефон/планшет.
- Все флаги избранного отсутствуют, коллекцию нужно собирать заново.

**Юс-кейс:**
1. На устройстве А пользователь делает «Экспорт избранного».
2. На устройстве Б делает «Импорт избранного».
3. Получает восстановленную коллекцию без ручной разметки.

**Как должно выглядеть (целевое UX):**
- В `Settings` есть пункт «Экспорт/Импорт избранного».
- Формат переносимый (JSON), с понятным отчётом: «Импортировано N записей».
- Следующий этап: автосинхронизация через облачный профиль.

### III.4 Нет бэкапа избранного

**Проблема**: В FAQ явно сказано: «Favorites are NOT included in backup (future feature)». Бэкап настроек существует, но избранное не включено.

**Предложение**: Включить избранное в механизм бэкапа/восстановления настроек.

**Как это проявляется для пользователя (пример):**
- Пользователь делает backup перед переустановкой приложения.
- После restore настройки возвращаются, а избранное — нет.

**Юс-кейс:**
1. Пользователь нажимает «Создать backup».
2. Переустанавливает приложение.
3. Нажимает «Восстановить backup».
4. Получает и настройки, и избранное.

**Как должно выглядеть (целевое UX):**
- Backup содержит отдельный блок избранного.
- В restore-диалоге есть чекбокс: «Восстановить избранное».
- При восстановлении показывается итог: добавлено/пропущено/конфликты.

### III.5 RAW-форматы не поддерживаются

**Проблема**: CR2, NEF, ARW, DNG и прочие RAW-форматы не отображаются. Для фотографов это критичное ограничение.

**Предложение**: Добавить базовую поддержку RAW через существующие библиотеки (Adobe DNG для встроенного JPEG-preview, или LibRaw/RawDecoder). Начать с preview (embedded JPEG), полное декодирование — опционально.

**Как это проявляется для пользователя (пример):**
- Фотограф открывает папку с `CR2/NEF/ARW`.
- Вместо превью видит «неподдерживаемый формат» и теряет сценарий быстрой сортировки.

**Юс-кейс:**
1. Пользователь открывает RAW-папку после съёмки.
2. Видит миниатюры RAW (через embedded preview).
3. Быстро отмечает годные/брак и сортирует по папкам.

**Как должно выглядеть (целевое UX):**
- На первом этапе — корректный предпросмотр и базовая навигация по RAW.
- Ясная маркировка в UI: «RAW preview mode».
- Полное декодирование RAW — как расширение, не блокирующее MVP.

### III.6 Wear OS — только локальные файлы

**Проблема**: Документированное ограничение. Wear OS не поддерживает сетевые/облачные ресурсы.

**Предложение**: Добавить поддержку отправки файлов/превью с телефона на часы через Wearable Data Layer API. Полный SMB на часах — нецелесообразно, но прокси через телефон — реализуемо.

**Как это проявляется для пользователя (пример):**
- На телефоне пользователь работает с SMB/Cloud, на часах не видит этот же контент.
- Возникает ощущение, что Wear-часть «урезана» и не продолжает сценарий телефона.

**Юс-кейс:**
1. Пользователь выбирает на телефоне альбом/плейлист для часов.
2. Телефон отправляет превью/список файлов в Wear через Data Layer.
3. На часах доступен просмотр без ручного поиска.

**Как должно выглядеть (целевое UX):**
- В мобильном приложении есть режим «Отправить на часы».
- На Wear отображается синхронизированный список последних/избранных.
- Пользователь получает «продолжение» сценария, а не отдельное приложение.

### III.7 Нет batch-rename

**Проблема**: Можно переименовать файлы по одному. Нет массового переименования (шаблон, нумерация, замена подстроки).

**Предложение**: Добавить batch-rename в режиме множественного выбора (BrowseActivity). Шаблон: `{name}_{counter}`, замена подстроки, добавление даты к имени.

**Как это проявляется для пользователя (пример):**
- После импорта 200 файлов нужно привести имена к единому формату.
- Переименование по одному файлу делает задачу непрактичной.

**Юс-кейс:**
1. Пользователь выделяет группу файлов.
2. Выбирает «Batch rename».
3. Задаёт шаблон: `Trip_2026_{counter}`.
4. Проверяет предпросмотр и применяет.

**Как должно выглядеть (целевое UX):**
- Массовое переименование с preview до применения.
- Поддержка сценариев: добавить префикс/суффикс, заменить подстроку, нумерация.
- Возможность отката последней операции (где технически возможно).

### III.8 Нет поддержки тегов/меток

**Проблема**: Единственная система организации — папки + избранное (boolean). Нет пользовательских тегов/меток для файлов.

**Предложение**: Рассмотреть систему тегов (цветных меток, как в macOS Finder). Хранить в Room DB. Позволит фильтровать коллекцию по тегам помимо папок.

**Как это проявляется для пользователя (пример):**
- Пользователь хочет помечать файлы по смыслу: «в работу», «отправить», «архив».
- Папки и избранное не покрывают такие поперечные сценарии.

**Юс-кейс:**
1. Пользователь добавляет метку `В работу` к файлам из разных ресурсов.
2. Применяет фильтр по метке.
3. Получает единый список «задач» независимо от папок.

**Как должно выглядеть (целевое UX):**
- Добавление/удаление тегов из контекстного меню.
- Быстрый фильтр по тегам в `Browse`.
- Комбинация тегов с существующими фильтрами и сортировкой.

### III.9 Нет статистики использования

**Проблема**: Нет информации о: сколько файлов отсортировано, сколько места освобождено, самые крупные файлы, дубликаты.

**Предложение**: Добавить экран «Статистика» — общее количество файлов по ресурсам, объём занятого кэша, топ-форматы, история операций.

**Как это проявляется для пользователя (пример):**
- Пользователь не понимает, какой объём уже отсортирован и что именно занимает кэш.
- Нет метрик прогресса, сложно оценить пользу приложения во времени.

**Юс-кейс:**
1. Пользователь открывает «Статистика».
2. Видит: отсортировано за неделю, освобождено места, топ источников.
3. Решает, что чистить/оптимизировать дальше.

**Как должно выглядеть (целевое UX):**
- Простой dashboard без перегрузки.
- Ключевые KPI: обработанные файлы, перемещено/удалено, размер кэша.
- Переход к действиям: «Очистить кэш», «Открыть проблемные ресурсы».

### III.10 Отсутствие drag-and-drop

**Проблема**: Для ChromeOS/desktop-режима (который поддерживается через клавиатуру/мышь) было бы естественно поддерживать drag-and-drop для файловых операций.

**Предложение**: Реализовать drag-and-drop в BrowseActivity для перемещения/копирования файлов между папками (особенно актуально в two-pane tablet layout).

**Как это проявляется для пользователя (пример):**
- На ChromeOS с мышью и клавиатурой пользователь ожидает desktop-модель взаимодействия.
- Сейчас операции делаются через меню/кнопки, что медленнее для массовых действий.

**Юс-кейс:**
1. Пользователь в two-pane режиме перетаскивает файлы из левой панели в папку справа.
2. Видит подсказку действия: `Copy` или `Move`.
3. Подтверждает и получает результат без лишних диалогов.

**Как должно выглядеть (целевое UX):**
- Drag-and-drop активен для мыши/тачпада, с визуальным feedback.
- Поддержка multi-select drag.
- Понятные ограничения и fallback на текущие кнопки/меню.

### IV.2 TrustAllX509TrustManager (БЕЗОПАСНОСТЬ)

**Проблема**: В lint baseline — 2 вхождения `TrustAllX509TrustManager`. Это подавленное предупреждение о **принятии всех SSL-сертификатов** без проверки. Потенциальная уязвимость MITM.

**Предложение**: Провести аудит. Если это для самоподписанных SFTP-серверов — реализовать certificate pinning или user-confirmation flow («Этот сертификат не доверенный. Продолжить?»). Не оставлять TrustAll в release.

### IV.3 373 неиспользуемых ресурса

**Статус**: ⚠️ Реализовано частично (safe-pass x2, 2026-03-04). Удалены только подтверждённо неиспользуемые ресурсы с нулём реальных ссылок: `layout/activity_player.xml`, флаги `is_small_screen`, `enable_compact_layout`, `reduce_animations`, `use_single_pane_layout` из `values/bools.xml` и `values-sw480dp/bools.xml`, а также 10 неиспользуемых drawable (`badge_background`, `bg_progress_dialog`, `button_hover_selector`, `error_placeholder`, `ic_add_24`, `ic_image_error`, `ic_save`, `ic_swap_vert`, `ic_video_error`, `ic_video_placeholder`). Перед изменениями созданы бэкапы: `temp/backups/20260304_202949/` и `temp/backups/20260304_203222/`.

**Проблема**: Lint baseline содержит 373 `UnusedResources`. Это: строки, drawables, layouts, которые не используются в коде. Раздувают APK.

**Предложение**: Провести чистку. Удалить гарантированно неиспользуемые ресурсы. Цель: уменьшить APK размер и улучшить build time.

### IV.4 40 устаревших зависимостей

**Проблема**: 40 `GradleDependency` предупреждений в lint baseline. Зависимости зафиксированы на конкретных версиях с обоснованием (раздел 11 TECH_REQUIREMENTS), но некоторые могут быть обновлены без рисков.

**Предложение**: Для каждой из 40 зависимостей — проверить, есть ли безопасный апдейт (patch/minor). Обновить те, что не требуют миграции. Для остальных — документировать причину блокировки в TECH_REQUIREMENTS.

### IV.5 28 LogNotTimber

**Проблема**: 28 мест в коде используют `Log.d()` вместо `Timber`. Нарушение проектного правила.

**Предложение**: Заменить все `Log.d()` / `Log.e()` / `Log.w()` на `Timber.d()` / `Timber.e()` / `Timber.w()`. Автоматизируемо скриптом.

### IV.6 82 SetTextI18n — конкатенация строк

**Проблема**: 82 случая конкатенации строк в `setText()` вместо использования string resources с плейсхолдерами.

**Предложение**: Рефакторить к формату `getString(R.string.key, arg1, arg2)`. Это улучшит локализацию и стандартизирует сообщения.

### IV.7 Room DB — 17 миграций

**Проблема**: 17 миграций (v1→v18) в AppDatabase. Каждая новая фича добавляет миграцию. Цепочка становится хрупкой.

**Предложение**: Рассмотреть «fallback to destructive migration» для debug-сборок. Для release — добавить integrationType tests всей цепочки миграций. Документировать текущую схему.

### IV.8 Тестовое покрытие — неопределённое

**Проблема**: Есть unit test infrastructure (JUnit, MockK, Robolectric) и Maestro E2E (56+ тестов), но неизвестен процент покрытия unit-тестами. Нет CI/CD pipeline видимого в репозитории.

**Предложение**: Запустить coverage report (`jacoco`). Определить baseline и целевой порог. Добавить GitHub Actions для автоматического прогона тестов на PR.

### IV.9 Отсутствие CI/CD

**Проблема**: Нет конфигурации GitHub Actions / другого CI. Билды и тесты запускаются вручную через PowerShell-скрипты.

**Предложение**: Настроить базовый CI pipeline:
- На push/PR: lint + unit tests
- На tag/release: build APK + upload artifacts
- Maestro E2E — по расписанию или вручную

## V. ЛЕНДИНГ И ВЕБЛИЦА

### V.1 YouTube-ссылка — баг разметки

**Проблема**: В index.html между тегами вставлена сырая YouTube-ссылка без HTML-обёртки. Возможно, отображается как текст.

**Предложение**: Оформить как embed (`<iframe>`) или как стилизованную ссылку с иконкой YouTube.

### V.2 Нет favicon

**Проблема**: Лендинг не имеет `<link rel="icon">`. Во вкладке браузера — дефолтная иконка.

**Предложение**: Добавить favicon (использовать icon.png, сконвертировав в .ico или добавив как PNG-ссылку). Добавить Open Graph мета-теги для социальных сетей.

### V.3 CSS дублирование

**Проблема**: Все три версии лендинга (EN/RU/UK) содержат идентичный CSS (~280 строк) inline. Любое изменение стиля требует правки трёх файлов.

**Предложение**: Вынести CSS в общий файл `styles.css`. Подключать через `<link rel="stylesheet">`.

### V.4 Нет SEO-оптимизации

**Проблема**: Есть базовые мета-теги (description, keywords), но нет: Open Graph, Twitter Cards, structured data (JSON-LD), sitemap.xml, robots.txt.

**Предложение**: Добавить OG-теги, Twitter Cards (для превью при шаринге), sitemap.xml, robots.txt. Рассмотреть schema.org/SoftwareApplication для structured data.
