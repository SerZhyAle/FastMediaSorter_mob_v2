# Спецификация: Оптимизация главного окна и Browse/Player pipeline (DEV)

## 1. Цель

Повысить отзывчивость и стабильность главного окна (`Main`/`Browse`), устранить визуальное мигание при обновлении списков и снизить задержки при первом входе в плеер без изменения бизнес-функциональности.

## 2. Scope

### Включено

1. Anti-flicker обновление списка в `Browse`.
2. Batch-загрузка статусов избранного.
3. Удешевление хеширования состояния директории.
4. Оптимизация `RecyclerView` listeners.
5. Проверка и точечное применение `ViewStub` для редких тяжелых узлов.
6. Опциональный warm-up плеера при высокой вероятности видео-сценария.
7. Контроль Main-thread I/O через `StrictMode` в debug.

### Не включено

1. Полный редизайн экранов.
2. Переход на Compose.
3. Изменение пользовательского поведения сортировки/фильтрации.
4. Переписывание media/network stack.

## 3. Проблемы текущего состояния

1. В `reloadFiles()` очистка списка до загрузки вызывает визуальный "пустой кадр".
2. Проверка избранного выполняется поштучно (`N` запросов), что тормозит рендер иконок.
3. `computeDirectoryHash` масштабируется плохо на больших директориях.
4. В адаптере создаются лишние listener-объекты при биндинге.
5. Первый запуск player-сценария может давать микро-фриз на lazy-инициализации.

## 4. Целевые решения

### 4.1 Browse Anti-Flicker

1. Запретить `mediaFiles = emptyList()` в стандартном refresh-пути.
2. Обновлять `StateFlow` только готовым снимком данных (после загрузки + сортировки).
3. Разрешить промежуточную очистку только в сценариях hard-reset:
   - смена ресурса;
   - радикальная смена фильтра/типа данных;
   - forced clear по явному действию пользователя.

### 4.2 Batch Favorites

1. Добавить API массовой проверки:
   - `getFavoritesForPaths(paths: List<String>): Map<String, Boolean>`.
2. Выполнять один запрос к БД вместо `N` синхронных вызовов.
3. Собирать итоговый список файлов и favorite-статусов до одного `updateState` (предпочтительный путь).
4. Допустимый fallback: двухфазный рендер (файлы -> избранное) только если первый кадр существенно ускоряется.

### 4.3 Directory Hash Optimization

1. Убрать полную конкатенацию строк для хеша.
2. Использовать инкрементальный/компактный алгоритм:
   - rolling hash по `(name, size, mtime)`;
   - либо XOR/64-bit mix с фиксированным seed.
3. Вычисления выполнять в `Dispatchers.Default`.

### 4.4 Adapter Optimization

1. Перенести установку click listeners в `ViewHolder.init`.
2. В обработчиках использовать `bindingAdapterPosition` + `getItem(position)`.
3. Исключить создание новых listener-объектов в `onBindViewHolder`.

### 4.5 ViewStub Policy

1. Провести аудит `item_media_file.xml` и связанных layout.
2. Вынести в `ViewStub` только редкие и реально тяжелые элементы.
3. Не применять `ViewStub` к frequently-visible элементам, чтобы не ухудшить scroll-path.

### 4.6 Player Warm-up (опционально)

1. Ввести feature-flag для warm-up.
2. Запускать warm-up при явном сигнале вероятности видеосценария (например, >= 80% видео в текущем наборе).
3. Warm-up ограничить подготовкой инфраструктуры (без preload контента и без побочных эффектов UI).
4. Гарантировать безопасную отмену warm-up при уходе с экрана.

### 4.7 StrictMode и Glide

1. В debug включить `StrictMode` для детекции Main-thread I/O/Network.
2. Зафиксировать процесс профилирования Glide декодирования на больших миниатюрах.
3. Любые найденные Main-thread нарушения закрывать до релиза фазы.

## 5. Нефункциональные требования

1. Нулевая функциональная регрессия в навигации и фильтрации.
2. Отсутствие новых ANR/crash по затронутым путям.
3. Все тяжелые операции файлов/БД/сети вне Main Thread.

## 6. KPI и целевые метрики

### UI/UX

1. Исключить визуальный empty-frame при обычном refresh в Browse.
2. Сократить задержку появления favorite-иконок после загрузки списка.

### Performance

1. Снизить время пост-обработки списка (после чтения файлов) за счет batch favorites.
2. Снизить CPU-время хеширования больших директорий.
3. Снизить allocation pressure в scroll-path адаптера.

### Player Entry

1. Уменьшить latency первого открытия видео при активном warm-up feature-flag.

## 7. Acceptance Criteria

### Browse

1. При стандартном refresh список не мигает пустым состоянием.
2. Favorite-статусы загружаются массово без `N` последовательных sync-проверок.
3. Хеширование директории не использует строковую конкатенацию полного списка.

### Adapter

1. В `onBindViewHolder` отсутствует создание новых click listeners.
2. Скролл остается плавным без роста jank по сравнению с baseline.

### Player

1. Warm-up отключаем флагом и не влияет на функциональность при `OFF`.
2. При `ON` нет фоновых утечек и неконтролируемых инициализаций.

### Debug/Quality

1. По затронутым сценариям отсутствуют `StrictMode` нарушения Main-thread I/O.
2. Build проходит без новых критичных ошибок.

## 8. План внедрения

1. **Фаза 1 (High):** Anti-flicker в `BrowseViewModel`.
2. **Фаза 2 (High):** Batch favorites API и интеграция в pipeline загрузки.
3. **Фаза 3 (Medium):** Hash optimization + `Dispatchers.Default`.
4. **Фаза 4 (Medium):** Adapter listeners refactor + ViewStub audit.
5. **Фаза 5 (Low/Flagged):** Player warm-up и стабилизация.
6. **Фаза 6 (QA):** StrictMode run, profiling, regression pass.

## 9. Риски и меры

1. **Риск:** скрытая логика зависит от промежуточного empty-state.  
   **Мера:** добавить явные UI-state transitions и проверить edge-cases.
2. **Риск:** batch favorites увеличит latency первого кадра.  
   **Мера:** ограничить размер batch и предусмотреть controlled fallback.
3. **Риск:** warm-up создаст лишние фоновые расходы.  
   **Мера:** feature-flag + жесткая отмена по lifecycle.

## 10. Definition of Done

1. Все acceptance criteria выполнены.
2. Нет новых критичных проблем производительности/стабильности в затронутых сценариях.
3. Документация и feature-flag поведение зафиксированы.
