# Спецификация для разработчика: Кеширование и отображение расширенных метаданных

## 1. Управление документом

- **ID:** FMS-SPEC-METADATA-CACHE-002
- **Статус:** Ready for implementation
- **Модуль:** `app_v2`
- **Дата:** 2026-02-19

## 2. Цель

Обеспечить извлечение, сохранение и отображение расширенных метаданных медиафайлов в списке файлов для ресурсов с включённой опцией «Запоминать список файлов», без деградации стабильности UI и с сохранением обратной совместимости кеша.

## 3. Область действия

### 3.1 In Scope

1. Извлечение метаданных при сканировании файлов.
2. Сохранение метаданных в кеш списка файлов.
3. Отображение метаданных в UI списка.
4. Сортировка/фильтрация по новым метаданным (в рамках данного релиза).

### 3.2 Out of Scope

1. Редактирование/запись метаданных обратно в файлы.
2. Фоновый сервис воспроизведения/индексации.
3. Полнотекстовый индекс метаданных.

## 4. Бизнес-правила

1. Обогащение метаданными выполняется только если для ресурса `rememberFileList = true`.
2. При отсутствии метаданных файл остаётся валидным элементом списка; блокировка/падение сканирования недопустимы.
3. Для документов расширенные метаданные не извлекаются (текущий этап).

## 5. Функциональные требования

### FR-1. Извлечение метаданных

1. Все операции извлечения выполняются в `Dispatchers.IO`.
2. Ошибка извлечения для одного файла не должна прерывать обработку остальных файлов.

### FR-2. Аудио

Извлекать:

1. `track_artist`
2. `track_title`
3. `duration_ms`
4. thumbnail из тегов (если доступен)

Ограничение: при активной опции «НЕ Загружать миниатюры» thumbnail не извлекать и не кешировать.

### FR-3. Видео

Извлекать:

1. `duration_ms`
2. `width`
3. `height`

### FR-4. Фото

Извлекать:

1. `width`
2. `height`
3. `date_taken` (из EXIF, если есть)

### FR-5. Отображение в списке

1. Для аудио: показать исполнителя, трек, длительность.
2. Для видео: показать длительность и разрешение.
3. Для фото: показать разрешение и дату съёмки.
4. При неполных данных использовать текущий fallback-формат строки информации.

### FR-6. Сортировка и фильтрация

Добавить поддержку сортировки/фильтрации по:

1. исполнителю
2. названию трека
3. длительности
4. дате съёмки

Требование: null-safe поведение, без крашей и без нарушения существующих сортировок.

## 6. Контракт данных

### 6.1 Поля кеша

В сущности кеша (`UnifiedFileCache` или эквивалент) должны быть доступны поля:

1. `track_artist: String?`
2. `track_title: String?`
3. `duration_ms: Long?`
4. `width: Int?`
5. `height: Int?`
6. `date_taken: Long?`

### 6.2 Совместимость

1. Старые записи кеша должны читаться без миграционных ошибок.
2. Новые nullable поля не должны ломать десериализацию legacy payload.

## 7. Техническая реализация

### 7.1 Изменяемые компоненты

1. `UnifiedFileCache` (entity/model)
2. DAO/mapper кеша
3. Сканер/UseCase, создающий `MediaFile`
4. `MediaFileAdapter` и форматтеры строки метаданных

### 7.2 API извлечения

Использовать:

1. `MediaMetadataRetriever` для аудио/видео
2. `ExifInterface` для фото

Обязательно:

1. освобождать ресурсы retriever в `finally`/`use`
2. логировать ошибки через `Timber`

## 8. Нефункциональные требования

1. Запрещены операции извлечения на Main thread.
2. Обработка повреждённых файлов должна завершаться безопасно (skip + log).
3. Производительность: не допускать непропорционального роста времени сканирования; целевой прирост времени <= 20% на локальном хранилище относительно базовой ветки.

## 9. Критерии приёмки

1. При `rememberFileList=true` метаданные отображаются после первичного сканирования.
2. После перезапуска приложения метаданные загружаются из кеша.
3. При `rememberFileList=false` расширенное извлечение не выполняется.
4. Сортировка/фильтрация по новым полям работает и не ломает старые режимы.
5. `assembleStandardDebug` проходит успешно.

## 10. План тестирования

### 10.1 Unit

1. Форматтер строки метаданных: полные/частичные/пустые данные.
2. Компараторы сортировки: null-safe и стабильный порядок.

### 10.2 Интеграционные/ручные

1. Аудио: файл с полными тегами, с частичными тегами, без тегов.
2. Видео: разные разрешения и длительности.
3. Фото: с EXIF-датой и без EXIF-даты.
4. Повреждённые/unsupported файлы.
5. Перезапуск приложения и валидация чтения из кеша.

## 11. Риски и меры

1. **Риск:** замедление сканирования.  
 **Мера:** IO-only обработка, минимизация повторных чтений, профилирование.
2. **Риск:** регрессии в десериализации старого кеша.  
 **Мера:** тест с legacy payload/старой БД.
3. **Риск:** нестабильность на сетевых ресурсах.  
 **Мера:** timeout/retry policy текущего сканера + graceful fallback.

## 12. Definition of Done

1. Все FR реализованы.
2. Пройдены критерии приёмки.
3. Нет новых критичных lint/build ошибок в затронутых файлах.
4. В PR добавлены заметки о backward compatibility и ограничениях.
