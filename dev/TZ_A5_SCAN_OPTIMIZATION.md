# ТЗ A5: Оптимизация сканирования

## Статус: 📋 Запланировано
## Приоритет: 🟡 Высокий
## Зависимости: B4 (DB Indexes)

---

## Описание проблемы

Сканирование медиафайлов работает полным проходом при каждом запуске, не использует кэш метаданных и не ограничивает параллелизм по типам источников. Это приводит к долгому времени загрузки и избыточной нагрузке.

## Цель

Инкрементальное сканирование с кэшированием метаданных и контролем параллелизма.

---

## Требования

### 1. Инкрементальный проход
- При повторном сканировании проверять только изменённые файлы (mtime + size).
- Новые файлы добавлять, удалённые помечать как отсутствующие.
- Поддерживать флаг `forceFullScan` для принудительного полного прохода.

### 2. Кэш метаданных
- Кэшировать: thumbnail path, duration, resolution, EXIF data.
- Хранилище: Room (`file_metadata_cache`).
- TTL кэша настраиваемый.
- Инвалидация при изменении файла (mtime + size).

### 3. Ограничение параллелизма
- LOCAL: до 4 параллельных потоков.
- NETWORK (SMB/SFTP/FTP): до 2 параллельных потоков.
- CLOUD (API): до 1 параллельного запроса.
- Реализация через `Semaphore` / ограниченный dispatcher.

## Критерии приёмки

- [ ] Повторное сканирование без изменений < 2 секунды (1000 файлов).
- [ ] Инкрементальное сканирование обрабатывает только изменённые файлы.
- [ ] Параллелизм не превышает лимиты по типу источника.
- [ ] Кэш метаданных корректно инвалидируется при изменении файлов.
- [ ] Снижение median scan time ≥ 30%.

## Проверка полноты

- [ ] Поведение при отсутствии изменений не вызывает полный scan path.
- [ ] Metadata cache не возвращает устаревшие данные после модификации файла.
- [ ] Лимиты параллелизма соблюдаются для LOCAL/NETWORK/CLOUD.
