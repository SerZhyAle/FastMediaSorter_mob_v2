## Фаза P0 — Стабилизация (Выполнить до написания нового функционала)

Блокируют производительность, стабильность и корректность работы приложения прямо сейчас.

---

### P0-1. Исправление `CleanupOrphanedTempFilesUseCase` для путей `cloud://`
*   **Проблема:** Приложение падает с исключением или генерирует ошибку во время попытки удалить устаревшие временные файлы (orphan temp files) из-за отсутствия стратегии файловых операций (FileOperationStrategy) для путей `cloud://`.
*   **Решение:** Внести ранний возврат (эвристику пропуска) в логику `CleanupOrphanedTempFilesUseCase` для любых путей, начинающихся с `cloud://`. В качестве альтернативы можно реализовать заглушку / базовую стратегию `CloudFileOperationStrategy`, которая будет корректно рапортовать о невозможности прямого удаления локального кэша через стандартное API файловой системы.

### 2. Снижение нагрузки на главный поток (Main Thread) в стартовых экранах
*   **Проблема:** В логах зафиксировано большое количество пропущенных кадров (skipped frames) на этапах запуска приложения (`MainActivity`), открытия настроек (`SettingsActivity`) и экрана управления ресурсами (`AddResourceActivity`). Это указывает на блокировку UI-потока тяжелыми синхронными операциями (например, множественными запросами к базе данных через `SettingsRepo.getSettings()`).
*   **Решение:** Провести профилирование методов `onCreate` и логики инициализации ViewModel в указанных Activity. Перевести обращения к `SettingsRepo` (и чтение SharedPreferences / Room) в асинхронные потоки (через `viewModelScope.launch { ... }` или `Flow`), чтобы главный поток не прерывался на ожидание ввода-вывода.

### 3. Базовый замер оптимизации сканирования облачных ресурсов
*   **Проблема:** Сканирование больших облачных ресурсов (например, Google Drive) занимает очень много времени (зафиксировано в логе: 24.5 секунды), что вызывает подвисания или задержки при обновлении списков. При этом нет четкого бенчмарка (эталонного замера), по которому можно судить об улучшениях.
*   **Решение:** Разработать и задокументировать процедуру тестирования скорости сканирования (базовую линию), включающую фиксацию продолжительности (duration), количества проверенных файлов (file count) и профиля задержек (latency profile). В дальнейшем это позволит проверить эффективность инкрементального сканирования и кэширования метаданных файловой системы (API пагинации).

## Фаза P1 — Завершение инициативы B5 (Усиление безопасности)
Улучшение приватности пользователей и предотвращение утечек токенов доступа облачных провайдеров.

### 1. (B5-T1) Добавление метода `revokeToken()`
*   **Проблема:** Токены облачных хранилищ (Google Drive, OneDrive, Dropbox) при необходимости не аннулируются на стороне провайдера, а лишь удаляются локально. Это оставляет активные сессии "висеть" на стороне серверов облака, что потенциально небезопасно.
*   **Решение:** Реализовать метод `revokeToken()` (или эквивалентный HTTP-вызов) в клиенте каждого интегратора облачного провайдера.

### 2. (B5-T2) Вызов `revokeToken()` при удалении ресурса/выходе
*   **Проблема:** При удалении аккаунта или отключении облачного ресурса из приложения токены по-прежнему остаются валидными на сервере.
*   **Решение:** Внедрить вызов реализованного `revokeToken()` при событиях явного выхода (logout) или полного удаления привязанного облачного ресурса пользователем через UI.

### 3. (B5-T3) Очередь ожидания на отзыв токенов (Pending revocation)
*   **Проблема:** Если при попытке вызова `revokeToken()` у пользователя нет интернета, токен так и не будет отозван и "зависнет" в статусе активного навсегда.
*   **Решение:** Хранить неактуальные токены, ожидающие отзыва, в специальной таблице БД. Создать фоновый воркер (WorkManager), который периодически будет пытаться отправить запросы на отзыв по этой "очереди", пока не получит успех (HTTP 200).

## Фаза P2 — Внедрение инициативы A1 (Мульти-аккаунтность)
Поддержка подключения нескольких учетных записей одного типа (например, два Google Drive, три OneDrive). В данный момент архитектура сильно привязана к концепции "Один провайдер = Один аккаунт".

### 1. (A1-T1..T4) Модель данных и миграция БД
*   **Проблема:** Текущая схема БД не предназначена для хранения нескольких сессий/токенов одного провайдера для разных пользователей.
*   **Решение:** Обновить схему БД (репозитории, таблицы токенов). Каждая запись токена должна привязываться к уникальному ID аккаунта (Account ID), а не просто к типу провайдера (Google/Microsoft). Настроить скрипты миграции (Room Migration), чтобы текущие одиночные аккаунты конвертировались в новую схему без сброса авторизации у текущих пользователей.

### 2. (A1-T5..T8) Логика авторизации и дедупликация
*   **Проблема:** При попытке авторизовать тот же самый аккаунт во второй раз, может возникнуть дублирование ресурсов или перезапись чужих токенов.
*   **Решение:** Переработать поток авторизации. Если возвращается тот же Account ID (Email или UID из облака), предотвращать создание дубликата и просто обновлять валидный токен существующей записи.

### 3. (A1-T9..T12) Выбор аккаунта в UI
*   **Проблема:** Пользователю нужно понимать, какой аккаунт он подключает или использует (например, `personal@gmail.com` против `work@gmail.com`).
*   **Решение:** Добавить компонент (UI account picker) в настройки и интерфейсы добавления ресурсов. Аккаунты должны визуально выделяться с помощью меток (labeling) и поддерживать локализацию (i18n).

### 4. (A1-T13..T15) Интеграция и регрессионное тестирование (Expiry)
*   **Проблема:** Новая система может нарушить текущий (уже хрупкий) механизм обновления истекающих токенов (Refresh token flow).
*   **Решение:** Провести Smoke-тестирование связи «Ресурс -> Креденшл -> Аккаунт». Написать тесты на процесс протухания (token expiry) и прозрачного обновления токена для нескольких аккаунтов одновременно.

## Фаза P3 — Вставка инициативы B1 (Унификация облачной авторизации)
Снижение дублирования кода между различными интеграциями (GDrive, OneDrive, Dropbox).

### 1. (B1-T1..T9) Унифицированная стейт-машина авторизации
*   **Проблема:** Каждый облачный провайдер сейчас управляет процессом авторизации (открытие Intent, перехват Callback, обработка ошибок, сохранение токенов) самостоятельно, что порождает дублирование (оркестрацию) и усложняет добавление новых провайдеров.
*   **Решение:**
    1. Создать единую стейт-машину (Unified auth state machine).
    2. Вынести специфичные детали провайдеров в отдельные плагины-имплементации.
    3. Создать единую точку входа для коллбэков (Unified callback entry) и реализовать единообразную обработку ошибок для всех облаков.

## Фаза P4 — Завершение инициативы B3 (Наблюдаемость / Observability)
Улучшение механизмов сбора логов и отладки багов на устройствах (особенно production).

### 1. (B3-T4..T7) Инструментарий логгирования
*   **Проблема:** Сложно отследить конкретный поток данных пользователя (например, сканирование или авторизацию) среди общего спама в логах.
*   **Решение:** Добавить систему проброса Correlation ID (сквозного идентификатора сессии) через основные потоки (auth/resource/scan/file ops).

### 2. (B3-T8) Скользящий файловый аппендер логов (Rolling file appender)
*   **Проблема:** Файл логов может либо неограниченно расти, забивая память устройства, либо затираться слишком быстро.
*   **Решение:** Реализовать (на базе Timber или другой библиотеки) механизм `Rolling file appender`, который будет хранить ограниченное количество файлов логов (например, `log.1`, `log.2`) с заданным лимитом по размеру.

### 3. (B3-T9) UI экспорт логов
*   **Проблема:** У пользователя нет простого инструмента отправить разработчикам логи прямо из приложения.
*   **Решение:** В меню "О приложении" или "Настройки" для дебаг и (опционально) релиз сборок добавить кнопку "Экспорт логов", которая будет зиповать (ZIP) текущие файлы логов и вызывать стандартный системный `Share Intent`.

### 4. (B3-T10) Принудительное скрытие секретов (Secret masking)
*   **Проблема:** Существует риск случайного вывода в лог пользовательских секретов, OAuth паролей, Refresh-токенов.
*   **Решение:** Внедрить правила фильтрации в систему логгирования для поиска и автоматической замены токенов и паролей на `***` перед записью на диск (masking enforcement).

## Важные пометки из документа: Врата релизов и качества (Release and Quality Gates)
*   **Build/Test Gates:** Прохождение Lint, Unit тестов и Release билда обязательно. Запрещено вносить новые Lint-варнинги.
*   **Quality Gates:** Обязательная ревалидация процесса авторизации и работы сетевых компонентов, если были внесены изменения. Строгий контроль метрики падений.
*   **Security Gates:** Категорический запрет на Hardcoded Secrets. Логи проверяются на правильный маскинг(фильтрацию).
*   **Цикл поставки:** Работать маленькими, вертикальными "срезами" (vertical slices) c обновлением статуса `WORK_PLAN_UNIFIED.md` как единственного источника истины.
