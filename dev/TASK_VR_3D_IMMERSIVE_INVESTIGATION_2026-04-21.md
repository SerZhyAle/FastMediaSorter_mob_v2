# Задача: расследование сбоя открытия 3D-файла в VR-режиме

Дата: 2026-04-21
Источник: пользовательский отчёт + logs/current.log
Статус: исследование завершено, нужна реализация по отдельной спецификации

## 1. Формулировка проблемы

Пользователь открывает трёхмерный файл в VR-сборке и ожидает следующий сценарий:
- приложение выходит из panel mode,
- запускает immersive mode,
- отображает стереоскопический 3D-контент,
- при любой ошибке показывает хотя бы toast или диалог.

Фактическое поведение:
- immersive mode не поднимается,
- приложение возвращает пользователя обратно,
- явного сообщения об ошибке нет.

## 2. Подтверждённое текущее поведение в коде

Ключевой файл: `app_v2/src/vr/java/com/sza/fastmediasorter/vr/VrPlayerActivity.kt`.

Подтверждено:
- текущая маршрутизация immersive рассчитана только на `MediaType.VIDEO`;
- для `currentFile.type != MediaType.VIDEO` код сознательно уходит в `launchStandardPlayerFallback()`;
- это поведение объяснено inline-комментарием: для image/doc support ещё не сделан явный переход `panel -> immersive`.

Следствие:
- если пользователь открывает 3D-изображение или иной non-video 3D asset, система даже не пытается поднять XR-сессию для этого сценария;
- возврат в обычный player сейчас является проектным недоделанным fallback, а не случайной аномалией.

## 3. Что подтвердили логи

Файл `logs/current.log`:
- 1739 строк;
- Quest 3;
- flavour `vr`.

Жёсткого падения приложения по логу не видно.

В хвосте есть симптом teardown/race:
- `MessageQueue` warning про отправку сообщения в `Handler` мёртвого потока Media3;
- затем остановка inline player и уход app в background.

Это выглядит как вторичный эффект остановки/перемаршрутизации, а не как первичная причина отсутствия immersive.

## 4. Зафиксированный root cause

Основной root cause:
- VR build пока не реализует immersive handoff для non-video 3D media.

Второй дефект:
- ранний fallback выполняется молча;
- пользователь не получает понятного сообщения, почему immersive не был запущен.

Третий риск:
- порядок teardown может оставлять Media3 в гонке с уже остановленным потоком.

## 5. Уточнённые ожидания для реализации

Принятые требования для дальнейшей реализации:
- supported 3D image/photo assets должны уметь переходить из panel mode в immersive mode;
- если immersive entry невозможен, пользователь всегда должен увидеть явное сообщение об ошибке;
- silent fallback без уведомления недопустим;
- stop/release path нужно стабилизировать, чтобы не провоцировать dead-thread warning при возврате.

## 6. UI/UX решения, достаточные для старта реализации

Считаем согласованными следующие решения:
- Для supported stereoscopic image/photo media приложение должно пытаться открыть immersive автоматически.
- Если media family пока не поддержан для immersive, показывается user-facing error и выполняется контролируемый fallback.
- Если XR init не удался, показывается user-facing error до закрытия immersive host.
- Минимальное требование на UX ошибки: toast или error dialog. Лучше - обычный project-standard `showError()` path.

Неурегулированные, но уже не блокирующие для спецификации детали:
- точный текст сообщений EN/RU/UK;
- нужен ли отдельный reason code для unsupported-non-video-immersive vs xr-init-failed;
- оставаться ли после ошибки в panel player или возвращаться в browse.

## 7. Следующий артефакт

Для реализации нужна отдельная спецификация в `PLAN/`, где будут:
- scope по flavour'ам `vr` и `vrUnlicensed`;
- архитектура non-video immersive routing;
- user-facing error policy;
- тесты для 3D image open/fail/fallback path.
