# Spec catalog rationale - incidents, measurements and design history

Moved verbatim from `.claude/rules/spec-catalog.md` by S3151. That rule keeps each contract's statement, gate and fix and is loaded with any `PLAN/` file; this document keeps why each contract exists and is read on demand.


## Debug verification tags (CLAUDE.md section 2)

- Invariant: `Timber.d("Sxxxx: <desc>")` exists in `.kt` **if and only if** spec `Sxxxx` is in `BlockNeedUserTest`.
- **Into BlockNeedUserTest**: insert one tag at entry point of changed flows before final build.
- **A probe owns its line, whole (owner ruling 2026-09-02).** One `Timber.d("Sxxxx: ..")` statement, alone on its own line, ending in `)`, never wrapped across lines, never sharing a line with code that has to survive it - a probe is deleted in bulk, so dropping the line must drop exactly the probe. Gate: the `probe-line-shape` check in `scripts/quality/assert-no-ticket-logs.ps1`, whose refusal lists every forbidden shape and the build break that produced them.
- **Out of BlockNeedUserTest**: delete all matching `Timber.d("Sxxxx:` lines immediately. **A release archives that status too (owner ruling 2026-09-02), and that is an exit like any other** - `/skill-release` step 12c sweeps `Implemented` + `Verified` + `BlockNeedUserTest` into `PLAN/archive/`, so it deletes their probes in the same sweep and proves it with `assert-no-ticket-logs.ps1`. Skipping the deletion leaves a tag whose ticket is `Archived`, which fails every later closure in every session.
- **A probe lost while the status stays (S3348, 2026-09-20).** S3251 sat in `BlockNeedUserTest` carrying no probe, and the gap reached the operator only as the advisory half of another ticket's closure, which had no way to cure it. Every catalog path is gated - `check-probe-present.ps1` on entry and on a same-status re-affirmation (S2656), `check-probe-absent.ps1` on exit - and `remove-ticket-probes.ps1` has refused a live ticket since S2639, so no script could have produced the state; a hand edit deleting the probe line with no status move is the one remaining path, and it is unguarded by design, because the tree gate cannot be fatal about debt its caller did not create (S1912). The cure is therefore a reading rule rather than a gate: the advisory names the owning ticket, and that ticket's probe is restored or excused in the baseline. S3251 was re-probed and verified on device the same day, which is why the concrete row is gone while the reading rule stays.
- Permanent logs must not contain `Sxxxx`.

## Closing gates (CLAUDE.md section 4)

All of them are invoked from `Assert-ClosingGates` in `_lib.ps1`, which `update.ps1`, `close.ps1` and `bulk-update.ps1` all call - a gate wired into only one of them guards the path used least (S1607). The scripts are canon-shipped forwarders (S2402); their bodies live in the `sza` plugin.

- **Block* note (mandatory, gated since S2581):** every transition INTO a `Block*` status must supply `-StatusNote '<reason>'` to `update.ps1` / `close-and-log.ps1` / `bulk-update.ps1`. `BlockNeedUserTest` -> describe what the user must test on device. `BlockExternal` / `BlockByOtherTask` / `BlockQuestions` -> describe the blocker and what resolves it. For `BlockByOtherTask` that description must additionally carry the id as a literal `Blocker: Sxxxx` token, in the note or in section 10, or the spec must carry a `**Depends on:**` line: those are the only channels the tooling reads, because section 10 prose lists consumers and neighbours next to blockers and as often denies the dependency it mentions, so a bare id there cannot state which way the arrow points (S1482). A ticket that records none is skipped as `blocker-unresolvable`, which means "fix the spec", not "wait". The note is written to the spec header as `**Status note:**` immediately after `**Status:**` so it is readable at a glance. Leaving a `Block*` status auto-clears the note.

  Until S2581 this bullet, `CLAUDE.md` section 4 and `AGENTS.md` all called it gated and nothing implemented it: `Assert-ClosingGates` ran for `Implemented`, `Verified` and `BlockNeedUserTest` only, so three of the four `Block*` statuses never reached a gate, and `update.ps1` wrote the note without ever requiring one. The only consequence was the picker's, arriving silently and later - measured 2026-09-05, exactly one of 151 `Block*` records carried no note, and that one (S1126) had been unselectable since 2026-08-21 with its own diagnosis reaching nobody. 99.3% compliance is why the gate needed no baseline file: it landed green after a single one-record repair. Two design points worth keeping: the checker judges the note **being written**, passed down from the mutator, because at gate time the journal still holds the previous note and on a `Block*` -> `Block*` transition that note describes a different blocker; and the three lightweight `Block*` statuses run the note checker **alone** rather than joining `$gatedStatuses`, because widening that list would pull `check-headings-unique.ps1` into `BlockQuestions` - `/spec-tech`'s escape hatch when a placement decision is missing and asking is forbidden - leaving a stuck pipeline with nowhere to park its ticket. Gate: `scripts/spec_catalog/check-block-note.ps1`; the two directional channels are resolved by `_blocker-links.ps1`, shared with `preview.ps1` so the refusal at write time and the skip at selection time cannot disagree (the S1621 rule).
- **Carried open item (mandatory on closing, S1607):** a transition INTO `Implemented` or `Verified` requires every item in the spec's research section ("Открытые вопросы / Research items") to be `Resolved`, or to carry a literal `Carrier: Sxxxx` token naming the ticket that now owns the question. Like `Blocker: Sxxxx` above, only the literal token is read - the surrounding prose names neighbours as often as owners. The carrier is an ordinary catalog record, so it reappears in `PLAN/RELEASE_QUEUE.md` on its own and the queue's ordering rule 6 batches it into `/spec-quiz`; no separate registry of owner decisions exists. Without this, a closed ticket leaves the queue and takes the question with it - measured 2026-08-13, 134 of 1506 closed specs stranded 372 such items. `Archived` is deliberately not gated: it closes a ticket that already passed. Gate: `scripts/spec_catalog/check-open-items-carried.ps1`, invoked with the durable-evidence gate (S1606).
- **Recorded audit (mandatory on `Verified`, S2298):** `Verified` means "the audit passed", and the audit's verdict lives in exactly one place - the spec's `## Last Audit` block, which `/spec-check` writes and `/spec-fix` reads; no separate audit registry exists. A transition INTO `Verified` therefore requires that block to be present and non-empty, a heading with nothing under it being the same absence of evidence with a table of contents. `Implemented` is deliberately **not** gated: it asserts only that the code is done, which is true before any audit has run, so demanding the block there would require a verdict ahead of the run that produces one. Measured 2026-09-01 across every live `Verified` spec: 7 of 129 carried no block (`S1783`, `S1872`, `S2002`, `S2053`, `S2197`, `S2263`, `S2280`), and their files attributed the closure to `/spec-all`, to `/spec-code` and to no marker at all - three paths, one missing check, which is why it sits in `Assert-ClosingGates` rather than in a command. The block is found by heading TEXT, so the numbered form `## 6. Last Audit` counts: the literal `## Last Audit` test that preceded this reported it as absent both in the measurement that opened the ticket and in `preview.ps1`'s `last_audit_present`, whose false negative reaches `/spec-all` step 0a-drift and re-audits finished work. Gate: `scripts/spec_catalog/check-audit-recorded.ps1`; the shared heading pattern lives beside the research parse in `_research-items.ps1` so the gate's verdict and the operator's flag cannot disagree (S1621).
- **Present probe (mandatory on `BlockNeedUserTest`, S2324):** that status parks a ticket for a human to watch on a device, so a transition INTO it requires one of exactly two things - at least one `Timber.d("Sxxxx: ..")` in `app_v2` or `wear`, or a row in `scripts/quality/blockneedusertest-probe-baseline.txt` giving the reason a probe cannot exist. Without the probe the log cannot tell "the scenario went through the new code" from "the scenario never reached it", so the device pass proves nothing. The refusal names **both** exits, because refusing a ticket that changed only documentation, scripts or resources would make it unclosable, which is worse than the gap. This is section 2's reverse half; the forward half (a probe whose ticket is not in the status) is `assert-no-ticket-logs.ps1`, and the two decide "carries a probe" through one shared helper, `scripts/quality/lib/blockneedusertest-probes.ps1`, so the closing gate cannot refuse what the tree gate passes (S1621) - not hypothetical, since a Timber call may span physical lines and a per-line search finds a strictly smaller set. Why a gate and not a sweep: measured 2026-09-02, 17 tickets sat in the status with no probe, and the set had turned over rather than shrunk, gaining three in a day. Why nothing caught it: `post-change.ps1` hands the tree gate `-ChangedFiles` under `-ScopeToFile`, which by S1912's design downgrades the missing-probe half to an advisory exit 3, leaving the project-wide `.\a.ps1 fg` as the only fatal run - red for whichever session happened to run it, over debt belonging to other tickets that session could not fix. Unlike the closing statuses this brings this checker alone and the capability advisory is suppressed: a ticket entering it has not finished shipping anything. An id no record carries exits 2, not 1 - "this ticket does not exist" and "this ticket forgot its probe" call for opposite reactions. Gate: `scripts/spec_catalog/check-probe-present.ps1`.

  **And the probe must be one this status can be LEFT with (S2934).** The same checker now asks a second question of every probe it finds, not just the first: does it own its physical line, judged by `probes.ownLineRegex`. Until this, the moment a probe was created was the one moment nothing asked whether it could ever be removed - the shape predicate lived only in the consumer's `assert-no-ticket-logs.ps1`, so the violation surfaced later, on a project-wide run belonging to a session that had not written it. That is the S1621 split S2324 closed for the presence half and left open for the shape half. Both questions live in one checker deliberately: split across two, presence answers PASS about the very line shape answers FAIL about, and an operator holding two verdicts for one line believes the kinder one - so a malformed probe does not satisfy presence at all. One exit code covers both refusals, because the reaction is the same (fix the source, re-run) and the refusal text names which half fired; exit 2 stays the bad invocation. The predicate moved to a **profile key** rather than a library function on purpose: `Merge-SzaProfileNode` carries a key unknown to the harness defaults into the merged tree, so `.sza-profile.json` makes it readable by the already-deployed harness, while a new library function would be undefined in every sibling session until a plugin deploy no project session can perform.
- **Absent probe (mandatory on leaving `BlockNeedUserTest`, S2934):** Rule 2 states the probe invariant as an equivalence and exactly half of it was guarded. `Assert-ClosingGates` judged `$NewStatus` only, so `BlockNeedUserTest -> In Progress` - a status in neither gated list - left through its early return with no checker reached at all, which is the transition S2531 took, leaving three probes behind. A transition OUT of the status now runs `scripts/spec_catalog/check-probe-absent.ps1` **before** that early return, and it refuses while any probe of the ticket is still in source. Why it kept coming back: the leftover probe is visible to every session and owned by none - under `-ScopeToFile` the tree gate prints it as outside the changed set and the closure passes, while the project-wide run fails for whoever happens to run it - so it was cleaned three times in five weeks (S2639, S2656, S2929) and refilled each time, because only the symptom was ever fixed. A refusal and not a deletion: removing the probes from a catalog mutator would write source outside any code-domain lock and outside the closure that judges a source edit, so the refusal prints `probes.removeCommand` filled in with the id instead - one line, and it carries the force flag because the ticket is still in the status at that moment, the journal not yet written. The baseline is deliberately not consulted: an excused ticket has no probe to leave behind. **`archive.ps1` is untouched and stays ungated**, which is not an oversight - it never calls `Assert-ClosingGates` at all, it is the path the release sweep takes, and that sweep deletes the probes of everything it archives and proves it with `assert-no-ticket-logs.ps1`; gating the three mutators' `Archived` writes alone would lock the door nobody uses. A hand-written `update.ps1 -Status Archived` does reach the gate, like any other exit. Suite: `scripts/spec_catalog/assert-closing-gates.tests/Run-Tests.ps1` cases E1-E3, which SKIP by name while the resolved harness predates the fix.

  **A re-confirmation of the same status runs this gate too, and runs only this one (S2656).** Writing `BlockNeedUserTest` over itself - the shape a `-StatusNote` replacement takes - used to leave through `Assert-ClosingGates`'s same-status early return with every checker unreached, so the one path that touches a parked ticket without moving it was also the one path that never re-asked the question. The split is by what a checker's subject IS: the audit, evidence, open-item, heading and note checkers ask what the ticket ACHIEVED or what its own spec says, which was answered at the entry transition and does not decay on its own, so re-judging them turns a housekeeping rewrite into a refusal. `check-probe-present.ps1` alone asks what is true of the ticket NOW, and its subject is the source tree, which changes under a standing ticket by other hands. This does not make the invariant continuously enforced and is not meant to: a ticket nobody re-confirms still drifts, and the project-wide `.\a.ps1 fg` run stays the sweep that catches that; it closes the last path that wrote the status while skipping the gate. Measured 2026-09-06, after S2324 and S2639: 134 tickets in the status, 127 carrying a probe, 29 excused in the baseline, none missing - so the change refuses no ticket alive on that tree. Suite: `scripts/spec_catalog/assert-closing-gates.tests/Run-Tests.ps1`, which SKIPs by name while the resolved harness predates the fix.
- **Unique section heading (mandatory on every gated transition, S2357):** a spec file may carry the same section twice, and no other check can see it - the shared parser `Get-SpecSectionLines` stops at the next `## ` once it has entered a section, so all four body-reading gates read the FIRST copy and the rest of the file does not exist for them. The duplicate therefore does not add noise, it silently substitutes whichever copy sorted higher, and it can **invert** an existing gate rather than merely evade it: measured 2026-09-02, S1884's `## Last Audit` block had been split in two, and `check-audit-recorded.ps1` - the S2298 gate whose entire job is to refuse a `Verified` with no recorded verdict - answered PASS on the resulting three-line stub carrying no `**Outcome:**`, while the real block with its counts and eight device checks sat below, unread by anything. Two other shapes existed in the same sweep of all 1395 files under `PLAN/`: S1955's `PHASE_02` held `## Phase Done Criteria` twice with opposite ticks, all `[x]` against all `[ ]`, so one file asserted both that the phase was done and that it had not started; S2156 carried an unfilled skeleton. The repeat is judged **inside one level-1 block, not across the file**, because a compact spec holds several `# Phase NN` blocks that each legitimately own `## Steps` and its neighbours - judging per file reports six offenders on the current tree of which three are those legitimate compact specs, judging per block reports exactly the three real ones. Scope is the ticket's own files, strategic spec plus every `.md` in its tactical folder, which is where S1955's copy lived. It runs for **every** gated status including `BlockNeedUserTest`: whether a file contradicts itself does not depend on the ticket being finished. Origin is agent-side, not scripted - no `spec_catalog` script writes spec body content and no command driver instructs an append, and S1884's newline seam (CRLF through line 293, LF from 294, exactly where the duplicate starts) shows a second writer appending onto the first one's file. Gate: `scripts/spec_catalog/check-headings-unique.ps1`.
- **Audit block on `BlockNeedUserTest` (S2367):** **`BlockNeedUserTest` carries the S2298 audit-block requirement**, because it hands work to a human and is therefore a coverage claim exactly as `Verified` is: measured 2026-09-02, 72 of the 158 tickets sitting in that status carried no audit block at all. That was not forgetfulness but a written instruction - `/spec-code` step 4 forbids running `/spec-check` before parking, since it would flip the ticket out of the status and delete the probes the device test needs (S2324) - so the verdict is written by the parking command itself as a **pre-handoff block** (`.claude/reference/spec-all.md` section 11a), which touches no `.kt` and moves no status. `Implemented` stays ungated for S2298's reason: it asserts only that the code is done, before any audit has run. Gate: the widened `scripts/spec_catalog/check-audit-recorded.ps1`.
- **Open manual check (mandatory on closing, S1899):** the principle has one home, canon `rules/TESTING_AND_QA.md` section 1 - a check only a human can run has not happened yet, and the incident it carries is this repo's S1697 (declared done on one unticked device line; an hour on a real phone-watch pair failed one of its five acceptance criteria). Repo mechanism: `/spec-check` counts every unticked `- [ ]` line in a spec's `## Last Audit` as `MANUAL`, and `MANUAL` no longer satisfies `Verified` - a run with zero WARN and FAIL but at least one open manual line scores `BlockNeedUserTest` instead. Only a device pass converts it, which is what `/spec-sweep` drains.
- **A found problem ends `BlockNeedUserTest` (owner ruling 2026-08-31).** `BlockNeedUserTest` means "the verdict is not in yet", never "a known defect is parked here". The moment a problem is found - by a device test, a sweep, an audit, a log read or the owner - the ticket leaves that status in the same action: `update.ps1 -Id Sxxxx -Status <Broken|Partial|In Progress|Approved|Draft> -StatusNote '<the finding, and what must happen next>'`, picking the state by what the finding needs - research reopens it as `Draft`/`Approved`, a known fix as `In Progress`/`Partial`, a regression as `Broken`. This puts it back into `PLAN/RELEASE_QUEUE.md` (work still left), which is the only place unfinished work is safe from being lost; left in `BlockNeedUserTest` it sits in `PLAN/RELEASE_READY.md` and reads as finished content. Never write the finding into the spec and leave the status alone, and never re-close a ticket to `BlockNeedUserTest` for a re-test while the finding is still open. Section 2's probe invariant follows automatically: leaving `BlockNeedUserTest` deletes every `Timber.d("Sxxxx:` line, and re-entering it re-inserts them.

## Release plan and queue (CLAUDE.md section 4)

- **Two files, split by "is there work left".** `PLAN/RELEASE_QUEUE.md` = work still left (every status below `Implemented`, blocked included). `PLAN/RELEASE_READY.md` = finished content (`Implemented`, `Verified`, `BlockNeedUserTest`). **All three of those statuses archive at the release** (owner ruling 2026-09-02): a device check that has not happened by then was written against a build the release supersedes, so it does not survive it - a defect found later is a fresh ticket against the released version, written from what the user saw. That is why `BlockNeedUserTest` sits in the READY file at all: its code ships either way.
- **The queue decides what gets worked on next - always recommend from it, and obey it.** Package ascending, then the owner's line order inside it; catalog `priority` is only a tiebreak for tickets neither file lists. A deviation needs a stated reason. Catalog owns STATUS, the two files own ASSIGNMENT + ORDER - every catalog write reconciles both automatically, in either direction; no other script may reorder lines or change the package a row sits under. Enforcing scripts: `scripts/spec_catalog/spec-next-preflight.ps1`, `release-plan.ps1`, `release-queue.ps1` (`-Reconcile`/`-Validate`/`-List`/`-SetCurrent`/`-Ship`).
- **BlockExternal review cadence (`next-review:` convention).** A ticket in `BlockExternal` has no exit path the catalog drives: `spec-next-preflight.ps1` excludes it from the eligible set, `release-plan.ps1` lists it as "Deferred" with no commands, and `run-spec-queue.ps1` treats it as terminal. Without a re-check mechanism the blocker accumulates dead weight - measured 2026-09-10, 19 tickets sat in `BlockExternal` across all four packages, the oldest since 2026-06-19, none carrying a review date. The convention: the `**Status note:**` written at entry (required by the S2581 gate) should carry a `next-review: yy-MM-dd` token naming the date the owner intends to re-evaluate the blocker. The default interval is 14 days from entry; `/spec-sweep` Phase B re-confirms with the same default when the owner says "still blocked". The token is plain text in the note - no gate parses it, no script owns it beyond the sweep's regex (`next-review:\s*(\d{2}-\d{2}-\d{2})`). A `BlockExternal` ticket whose `next-review:` is in the past, or carries no token, is **overdue** and `/spec-sweep` Phase B surfaces it to the owner for a decision. The sweep never auto-unblocks: it re-confirms the date or transitions out only on owner confirmation.

### File shape (S2852)

The owner sorts these files by hand, so everything a machine needs is here and only the plan itself is in the file.

- **The package is a section heading**, a line holding the number and nothing else (`37`, or `--` for unscheduled). Every ticket row below it belongs to that package until the next heading. Re-packaging a ticket is therefore a plain line move, with nothing on the row to keep in step - which is why the row carries no package column any more.
- **Row:** `ticket  changed  status`. `ticket` = the spec file name in `PLAN/` without the extension. `changed` = `YY-MM-DD HH:mm`, when the STATUS last moved, never when the spec text was edited; a ticket can move status several times in a working day and a date alone cannot order those moves. `status` is mirrored from `PLAN/spec-catalog.jsonl` - never edit it here, the next catalog write overwrites it.
- **`current-next-release: N`** in the header names the open package. The `DEBUG-v0NN` branch only labels it and may lag after a package ships without a branch, as a Wear release does.
- **`[taken 15:42, /spec-all, be08adb0]`** - a live agent session holds this ticket: claim time, what it runs, session id prefix. Rendered from the lease store under `temp/` on every write, so a session that died loses its marker on the next write; a row without the marker is free to pick up.
- **`[idle 2, timeout]`** - this many runs in a row handed the ticket back without moving its status, and how the last one ended. While it shows, automatic ranking passes the ticket over and takes the next line of the package; an explicit `/spec-all Sxxxx` still runs it. Rendered from the runner's journals, so the first run that moves the status erases it. **Only `ok` and `timeout` count** (`runner.idleOutcomes` in `.sza-profile.json`): those two mean the run reached the ticket and left it where it was, while a lost claim, a failed launch or a `child-failed` describes the runner and says nothing about the ticket - so such a run ends the series instead of extending it, and the ticket goes back into ranking. Narrowed by S2871, measured 2026-09-08: one six-minute window of children exiting 1 in zero minutes had held nine tickets, one of them a ticket a sibling was working at that moment. `child-failed` is S2873's: until it existed the runner read no exit code at all, so 10 of 985 journal rows kept the name `ok` for a child that had exited non-zero, and `ok` counts here - S1565 was held as `[idle 2, ok]` on 2026-09-10 by one of them. A canon deploy is owed before the new name reaches the journals. **The held set is reviewed by `/spec-sweep` Phase C** - it is neither blocked nor finished, so nothing else asks about it.
- **A brand-new row lands in the open package's block, immediately above that package's owner-gated boundary row** (S2921). Until then the writer knew only "the last ticket line of this package", which put every new ticket below the release line - the heading above it said 37 and the position said 38, and six tickets had stacked up under `S2687_prerelease-release-r37` before anyone read the file closely. A package holding a heading and no rows yet was worse: indistinguishable from a package the file does not carry, so its first row went past the end of the file and grew a second heading with the same number. The boundary is recognised by the owner-gate marker in the ticket's own spec, the same marker `preview.ps1` reads to refuse the ticket to an automatic picker - one definition, so the row nothing is appended below is the row nobody is handed. Reconcile still never reorders what is already there: rows already sitting below a boundary stay until the owner moves them.
- A `#` comment line is the owner's own note and is carried through untouched, as is every blank line. Scripts may add a ticket, refresh its status and date, move it to the sibling file or drop an archived one; they never reorder lines and never re-home a row into another package.
- The reader accepts the pre-S2852 shape too - a leading package column, a date with no time - so a stale copy still parses; the writer emits only the current shape, so the first write normalises it.

### Line order inside a package, top to bottom

1. Work already in flight - an In Progress ticket is half-paid for.
2. Whatever the rest of the package is validated against: broken unit suites, leaks, tooling that costs every session.
3. Ready-to-build work, closest to done first - Tactical before Approved before Draft.
4. A blocker sits above the ticket that waits for it, so the chain reads downwards.
5. String-only work (bulk translation) goes last, after every feature that will add keys.
6. Anything waiting on an owner answer sinks to the bottom - batch those into one `/spec-quiz`.
7. Anything waiting on hardware or a third party sinks below that. It is not schedulable, so it must not sit where it looks like the next task.

A dependency releases as soon as the blocker reaches **BlockNeedUserTest** *and the blocker's own tactical plan is finished* - never make a dependent wait for `Verified` (owner ruling 2026-08-07), and never release it while the blocker is parked mid-plan (S2834). The reason that ruling gives is "the code is in the tree by then", which is a claim about the tree: a blocker showing `**Phases:** 0 / 5 done` in its `INDEX.md` has not put it there, so the counter decides beside the status and `M > N` holds the dependent. A blocker with no tactical folder or no counter line releases on status alone. An unresearched capture whose triage will SPAWN more tickets is an exception to rule 3 and sits near the top of its band despite being a Draft (owner ruling 2026-08-16).

### Packages

- `37` - **the ordinary phone app: fixes and small improvements.** No Wear, no VR, no new subsystem. The default package for a defect.
- `38` - **hardware that is not the phone: Wear and VR/XR.** Everything for a watch or a headset, a one-line tile fix exactly as much as a store submission - kind decides this one, not size. Both families are built and validated on hardware no phone session can reach, and each ships on its own cadence: the watch to `wear:production`, VR to its stores.
- `39` - **big improvements to the Android app** (owner ruling 2026-09-07). More than a fix or a polish pass, less than an epic: a real feature on the shipped phone app, a reworked surface, an existing subsystem taken further.
- `40` - **the complex epics.** A new distribution channel, store or flavor; a whole-site or localization campaign; an external compliance or licensing process; a brand-new subsystem, subprogram or gadget class; strategic positioning; an engineering programme rather than an engineering fix.

Placing a new ticket: **does it need a watch or a headset to finish?** That is 38. Otherwise judge its size on the phone app - a fix or polish is 37, a substantial improvement is 39, a programme or something the app has never done is 40. Repo tooling that merely mentions the watch is not a Wear ticket: a gate script or a guard hook is validated by this repository, so it stays in 37 (S1809, S2596).

Every package ends with its own prerelease/release boundary ticket. That row is the release line - everything below it belongs to the next package. **A boundary ticket is never picked up automatically** (owner ruling 2026-09-07): its spec carries the owner-gate marker `**Автоматическая передача отключена**`, so `preview.ps1` returns `auto_skip: owner-gate` and `/spec-next`, `/spec-do` and `.\a.ps1 r1|r2|r3` walk past it to the next row. Only the owner starts it, by hand, when the package is actually closing. A new boundary ticket gets that marker at birth, or the first unattended run of an empty package will try to release it.
