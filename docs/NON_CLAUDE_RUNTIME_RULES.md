# Rules you enforce yourself - every runtime that is not Claude Code

Claude Code refuses these mistakes at the tool call; for you nothing refuses anything, and nothing announces the absence. This sheet is the rule text - `docs/AGENT_HOOKS.md` is the mechanism behind it, `CLAUDE.md` is the full rule set, and neither restates what is below.

## What a session costs

Every request sends the whole session again: the system prompt, this repository's always-loaded file, and every command output read so far. A session's bill is therefore the number of requests times the size of the context, and an output read early is paid on every later request. Measured on S3103, a two-line Wear change (S3177): 200 requests, context 23k -> 207k, 25.45M input tokens; 16.8M of it was reading done before the first edit and then carried to the end, and the five-hour limit ran out before the final report. The same change on the Trivial path costs a few dozen requests. Claude Code keeps the same rules cheaper only because it loads path-scoped rules on demand, reads in subagents and batches calls in one request; rules 17-19 give you the same economy by hand.

## The rules

Before reading `temp/AGENT-CHAT`, take only the newest records and explicit matches for the active `Sxxxx`. Full chat history is not normal session context; widen the read only when the current ticket lacks the needed fact.

1. Run a `find` only with a concrete start path **and** `-maxdepth N` - a disk-wide walk costs minutes and returns noise; prefer `dev/CATALOG/scripts/query.ps1` or a plain glob (`guard-find-command`).
2. Never put a `.ps1` in Bash command-head position - Bash cannot execute one and the failure still returns **exit 0**, so a red build reads as green; always `pwsh -NoProfile -File ./a.ps1 <cmd>` (`guard-ps1-in-bash`).
3. Never background a gate, a closure facade or a catalog mutator - `post-change.ps1`, any `assert-*.ps1`, the `spec_catalog` CLI, `add_to_dev_log.ps1`, `catalog_sync.ps1`, `a.ps1 fk/fkn/fc/fr/fg/dq/ch/ss/bf`. A verdict nobody reads in the same turn is not a verdict; a real long job (`gradlew`, `a.ps1 d/db/dav/cd/nd/nl/r/fu`) still backgrounds normally (`guard-fire-and-forget`).
4. Never put a PowerShell cmdlet, `node`/`npm`/`npx`, or the `& { .. }` idiom in Bash - each is an `exit 127` returning nothing; run the pipeline in PowerShell or `pwsh -NoProfile -Command "<pipeline>"` (`guard-bash-unavailable-command`).
5. Double a leading slash in an argument value - Git Bash rewrites `-Reason "/spec-dev .."` into a Windows path silently, at exit 0, and the corruption lands in the lock, queue and lease diagnostics; write `"//spec-dev .."` or call from PowerShell (External: canon `guard-bash.ps1`, check 6 - it ships with the `sza` plugin under `hooks/`, it is not a script of this repository).
6. Read a long file in explicit windows, through `scripts/utils/read-window.ps1 -Id <Sxxxx>` - a combined multi-file read that stayed in session history was the largest measured cost source in a real Codex session (S3141, `PLAN/S3141_codex-session-context-amplification/research/01__s3137-transcript-measurement.md`); an unwindowed read of a large file wastes context you cannot get back, and you will not notice which part you missed (`guard-uncapped-read`). **One read per `exec_command`:** never chain several `read-window.ps1` calls, or a `read-window.ps1` call and a `Get-Content -Raw`, with `;` in one command - the offload threshold applies per read, so a chained call returns the sum inline. The first three Codex sessions after S3141 landed chained 3-6 reads per call and each still carried 9-10 oversized and 5 truncated outputs; the transcript gate now reports this as `chained-read`. **An offloaded read prints the file's `outline:` lines with line numbers** - go straight to `read-window.ps1 -Id <Sxxxx> -Pattern '<heading>' -SearchPath <evidence path>`; a separate `rg '^#'` over the evidence file is a wasted turn (S3176).
7. Query `dev/CATALOG/scripts/query.ps1` before grepping `.kt` across the tree - the class index answers "where is X" in one call, a tree-wide grep in dozens (`guard-catalog-before-kt-search`, armed each session by `reset-catalog-touch-marker`).
8. Re-run an empty search without your path filter before concluding "not here" - a scoped miss is usually the wrong scope, and a wrong "not here" becomes a wrong design decision (`observe-empty-grep`).
8a. Never end a turn that left a red `.ps1` verdict you did not look at. Exit **1** is a failure and exit **2** is could-not-verify, from any command whose head is a `.ps1` or `a.ps1`; run `pwsh -NoProfile -File scripts/quality/explain-last-failure.ps1` and judge what it prints before you finish. Exit 3 (advisory) and exit 4 (queued, not your turn) are normal flow and need nothing, and a `grep` returning 1 means "no match". In Claude Code this is refused rather than asked; a runtime without hooks owes it by itself, and the failure it prevents is the ordinary one - a gate came back red, the output scrolled away, and the work carried on (`refuse-unexplained-red-verdict`).
9. Try `/quick` and `/skill-fix` before a spec pipeline when the request is genuinely micro. S3328 (2026-09-19) re-ruled the tier question on transcript measurement over 2026-09-17..19: the advisory nudge had zero addressable prompts (0 of 17 owner free-text prompts matched it, 69% of pipeline entries are headless runner children it cannot reach, owner-typed pipeline entries start with `/` which it skips), so the small tiers are an owner-facing command surface, not a process control. The 2026-08-05 corpus count stands as baseline: 2 cheap-tier fires against 135 pipeline entries (`nudge-small-task-tier`).
9a. Pick the check by what you actually changed, not by habit: a changed set that is resources only is proved by `..ps1 fr` (phone) or `fwr` (wear), a set that ships nothing by no gradle target at all. Where an installable artifact IS needed - a device install, a packaging question - build ONCE and LAST, after the ticket's final edit. Measured 2026-09-18 (S3193): four `strings.xml` files were proved by a full `a.ps1 dq` run mid-ticket - ~3 min queued behind `Build.Phone` plus ~4 min building against ~20 s for the declared target - the edits that followed went unproved by it anyway, and the closure's own resource-link gate re-proved the resources afterwards (`nudge-check-target-by-change-type`).
10. Post your own session lines: `agent-chat.ps1 -Verb Post -Kind session -Note "session started (<runtime>)"` at the start and `"session ended (<reason>)"` at the end, after setting `FMS_AGENT_ID` in your process (`$env:FMS_AGENT_ID = '..'`, never `setx` or a User/Machine-scope write, which every later session on the machine inherits) - the end reason is the one fact separating "died mid-phase" from "finished and left" (`post-agent-chat-session`).
11. Never end a `/spec-do` loop yourself - only the operator ends it; recover or wait, and if you are waiting, say so and keep waiting (`refuse-spec-do-stop`).
12. Run a one-way device action through an MCP tool - install, uninstall, a Maestro flow that clears app data - only on an emulator; on a physical device read `docs/DEVICE_FLEET.md` first and use `scripts/devtest/adb.ps1 install`, `uninstall -Yes` or `wipe-data -Yes`, because the device you did not check may hold content that cannot be restored (`guard-mcp-one-way-tools`).
13. Do not OPEN a new ticket while a release sweep holds the tree freeze - check `release-freeze.ps1 -Verb Status` and, if one is held by another session, finish the ticket you are already on instead of claiming another. Every gate at `/spec-prerelease` steps 0.4 and 0.8 measures the whole tree, so a ticket opened mid-sweep can re-open a gate the sweep has already cleared: measured over r37 on 2026-09-12, 31 of the 33 changelog rows in the sweep window were siblings', and the costliest was a Wear screen whose ticket was opened after the wear gate it invalidated had passed. Work under `PLAN/` and `temp/`, reading and analysis are never refused (`guard-release-freeze`).

13a. Never hand-roll a wait on a task your runtime already tracks - a backgrounded command or subagent reports when it finishes, so polling its output file cannot make it finish sooner. Measured 2026-09-18: four such waits in one run, the longest 9 min 19 s for an empty result. Read a background command's interim output with your runtime's own reader, never a shell loop; never read a subagent's transcript at all - it overflows the context the delegation was meant to save. Rule 14 fixes the shape of a wait that is owed; this one says the wait is not owed (`guard-manual-task-wait`).

14. Run a long wait - a build, a lock, a gate - as a single blocking call with a sufficient timeout inside one `exec_command`, never a sequence of separate `Start-Sleep` calls spread across several turns: five such turns in one measured session sent 664,133 repeated input tokens for output that said nothing new (S3141, `research/01`). A loop of `Wait-Process -Id N -Timeout 55` (or `Wait-Job`/`Wait-Event` with `-Timeout`) re-checked turn after turn is the same waste under another name - S3142 spent about ten turns on it. The blocking form is one call: start the command itself in the foreground with `yield_time_ms` covering its duration, or `Wait-Process -Id N` with no `-Timeout`, then read the verdict in that same call.
15. Read a file under `PLAN/` only when its ticket id matches the active ticket, unless the active ticket's own spec names the other id via `Blocker:`, `Carrier:` or a direct reference - the same check `scripts/utils/read-window.ps1` refuses without `-AllowCrossTicket -Reason`. A mistyped id has already cost one real session roughly 326,000 repeated tokens reading the wrong ticket's spec (S3141).
16. Move plan state in batches: one `plan-tick.ps1` call per pass - `-Steps 1,2,3` for steps, `-Checkbox 'a,b,c'` for a phase's exit criteria, the whole proof in one `-Log`. One call per box cost the S3103 session 22 turns of 160-207k context each (S3176).

17. Pass `max_output_tokens` of at most 2000 (`codexContext.maxOutputTokens` in `.sza-profile.json`) on every `exec_command`. An answer that does not fit is a question asked too widely: narrow the path or the pattern (`rg -l`, `rg -c`, `rg -m 20`), or read the evidence file `read-window.ps1` wrote, one section at a time. The S3103 session asked for 10000-50000 on every call, and a single `rg -C 3` over a whole document landed 22 KB inline and was resent 120 times; the transcript gate reports it as `uncapped`.
18. Read only what your path needs - decide the path (`/spec-all` section 0c) before opening anything else, and open each document at the section you need through `-Pattern`, never whole.
    - Every path: the ticket's own spec, the files you will change, the build target of the module you touch (`a.ps1 fw` for `wear/`). `AGENTS.md` and this sheet are already paid for.
    - Trivial: add `.claude/commands/spec-all.md` sections `### 0c` and `## Trivial Path`, `.claude/templates/trivial-spec.md`, and `.claude/reference/spec-dev.md` section `## Finalization` at the closure. Nothing else - no research-order documents, no memory, no `REFUTED_APPROACHES`, no other path's templates, no audit protocol.
    - Simple: add `## Simple Path`, the compact-layout header of `.claude/templates/phase-file.md`, and at most the one memory `INDEX_*.md` for the module you touch.
    - Full: open each stage's driver only on entering that stage; a research-order document only at the section the feature map or the class catalog points at.
    - Add a document only when the task triggers it: `-m` -> `.claude/reference/mono-mode.md`; a user-visible string -> `docs/COMMUNICATION_POLICY.md` section 6; an undecided placement -> `.claude/commands/ui-clarify.md`.
19. Check the bill at every stage boundary - strategic spec written, tactical plan written, each phase done: `pwsh -NoProfile -File scripts/quality/measure-codex-transcript.ps1 -Id <Sxxxx> -StageCheck`. Exit 3 means the context is over `codexContext.stageContextBudget`: write `scripts/utils/write-codex-handoff.ps1 -Id <Sxxxx> ..` with the facts, the changed paths and the next action, and end the session with one line to the owner - `handoff written - continue in a new chat: <the command you were running>`. The next session reads only the newest handoff, so the finished stage's reading is never paid for again. You cannot compact your own context; this is the only reset you have.
20. Tick every plan step you finished in the same pass with ONE `plan-tick.ps1 -Steps a,b,c -State Done` call - a second `-State Done` on the same `-Id` and `-Phase` seconds after the first is bookkeeping that could have ridden along with it, and one `-Log` should cover what all of those steps proved (`observe-plan-tick-batching`).

## Before you say done

- Run `pwsh -NoProfile -File scripts/utils/preflight-checks.ps1` and read its exit code. It judges the state you leave behind - identity, session lines, held locks, queued lock tickets, outlived ticket leases - and names the remedy for each finding. Exit 0 clean, 1 something is leaked, 2 could not verify.
- It deliberately judges nothing about the tree. That is `scripts/post-change.ps1 -Files "a,b" -ScopeToFile` for a change and `pwsh -NoProfile -File ./a.ps1 fg` for the fast static gates - run those too, and read both verdicts.

## Not portable

These hooks give you no rule to follow, so this sheet states no imperative for them. They are listed by name because the sync gate in `scripts/quality/assert-hook-inventory.ps1` requires every hook in the inventory to appear here or above, and because knowing a hook exists is cheaper than wondering why it is missing.

- `warn-context-size` and `nudge-context-budget` tell the owner that a session has grown expensive. You cannot reset your own context - `/clear` and `/compact` are his - so the only action is his.
- `sweep-agent-lock-queues` evicts dead reservations left by sessions that died. It is housekeeping over other agents' state, not a decision of yours. Your own half of that obligation comes from `CLAUDE.md` Rule 23: withdraw your queue ticket with `scripts/utils/withdraw-lock-ticket.ps1` when you abandon a queued intent, and `preflight-checks.ps1` above checks you did.
- `reset-catalog-touch-marker` arms rule 7 once per session. It is the mechanism of a rule already stated, never a second rule.
