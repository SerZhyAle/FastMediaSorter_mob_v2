## 2 / S0029 · priority 70 · Tier 2

### Сохранённая позиция воспроизведения зацикливает короткие файлы

**Спека:** `PLAN/S0029_bugfix-resume-position-end-of-file.md`

**Промпт для агента:**

```
Реализуй тактическую и имплементационную фазу для спеки S0029.

Контекст:
- Стратегическая спека: PLAN/S0029_bugfix-resume-position-end-of-file.md
- Ticket S0029, Tier 2, priority 70
- Проблема: если видео досмотрено до конца (или авто-переключилось на следующий файл),
  сохранённая позиция НЕ очищается. При следующем открытии плеер стартует с конца,
  мгновенно доходит до финала и снова переключается — пользователь не успевает ничего сделать.
  Лог-подтверждение: в сессии 2026-04-29 флаг completed=false всегда, 
  clearState reason=playback-completed ни разу не появляется.

Шаг 1: /spec-tech S0029
  Создай тактическую спеку PLAN/S0029_bugfix-resume-position-end-of-file/INDEX.md.
  Ключевые реализационные точки (из §5 стратегической спеки):
  a) Определить точку "воспроизведение завершено": ExoPlayer EVENT_ENDED либо
     позиция >= (duration - threshold). Threshold = min(5% duration, 5000ms).
  b) При достижении точки: вызвать ResumeStateRepository.clearState(reason="playback-completed").
  c) Лог-маркер: Timber.d("ResumeState: clearState reason=playback-completed uri=...")
     — отдельный от user-exited и resource-changed.
  d) Поведение единое для VR-плеера и панельного плеера.
  e) Без миграции DataStore — старые "грязные" позиции остаются до следующего просмотра.
  
  Граничные случаи:
  - Плейлист: clearState срабатывает только для текущего файла, следующий не трогается.
  - Файл < 10 с: threshold не должен быть больше половины длительности.
  - Seek к концу вручную: тоже должен триггерить clearState при EVENT_ENDED.

Шаг 2: /spec-dev S0029
  Реализуй. Обязателен unit-тест: файл 30с, позиция 28с → после EVENT_ENDED → clearState вызван.
  После реализации: scripts/spec_catalog/update.ps1 -Id S0029 -Status Implemented
```

## 4 / S0032 · priority 45 · Tier 2

### getFrameAtTime null для VR180-файлов — пустой постер

**Спека:** `PLAN/S0032_bugfix-vr180-frameat-null.md`

**Промпт для агента:**

```
Реализуй тактическую и имплементационную фазу для спеки S0032.

Контекст:
- Стратегическая спека: PLAN/S0032_bugfix-vr180-frameat-null.md
- Ticket S0032, Tier 2, priority 45
- Проблема: при открытии 7K VR180-файла (21 ГБ) на Quest 3 вызов
  MediaMetadataRetriever.getFrameAtTime() возвращает null.
  Лог: "VideoPlayerManager: getFrameAtTime returned null for ...7K_180_180x180_3dh.mp4" (line 3301).
  Native heap free в тот момент: 9 MB. ExoPlayer уже держит аппаратный декодер.
  Эффект: превью-кадр при паузе — чёрный экран.

Шаг 1: /spec-tech S0032
  Создай тактическую спеку PLAN/S0032_bugfix-vr180-frameat-null/INDEX.md.
  Ключевые точки реализации (из §5 стратегической спеки):
  
  a) ПРЕВЕНТИВНЫЙ SKIP:
     Перед вызовом getFrameAtTime проверить:
     - Runtime.getRuntime().freeMemory() + maxMemory() — если native heap low (< ~50MB) → skip
     - ExoPlayer.isPlaying() || ExoPlayer.isLoading() для того же uri → skip
     При skip — сразу к fallback-иерархии, без вызова getFrameAtTime.

  b) FALLBACK-ИЕРАРХИЯ (в порядке приоритета):
     1. Browse-кэш thumbnail из Glide memory cache (синхронно, без IO).
        Если нет в памяти — не идти на диск.
     2. Последний доступный Bitmap из VideoPlayerManager (если есть ссылка).
     3. Статичная заглушка: серый фрейм + ic_broken_image (или аналог).
        ContentDescription = "Thumbnail unavailable" (локализовать EN/RU/UK).

  c) ENRICHED LOG:
     Перед вызовом: Timber.d("VideoPlayerManager: getFrameAtTime attempt uri=... nativeFree=...MB")
     При null: Timber.w("VideoPlayerManager: getFrameAtTime returned null reason=<причина> fallback=<что использовали>")
     Причина определяется по порядку: oom → decoder-busy → unsupported → unknown.

Шаг 2: /spec-dev S0032
  Без изменения общего UI плеера при паузе.
  Нулевой регресс для обычных (≤1080p) файлов — обязателен тест с small.mp4.
  После реализации: scripts/spec_catalog/update.ps1 -Id S0032 -Status Implemented
```
