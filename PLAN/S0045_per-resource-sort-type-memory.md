# Стратегическая спецификация: S0045 — Память типа сортировки per-resource

**Ticket:** S0045

**Roadmap entry:** Ad-hoc — запрос пользователя 2026-05-01
**Tactical plan:** `PLAN/S0045_per-resource-sort-type-memory/INDEX.md`

> **Scope:** STRATEGIC. Цели, ограничения, открытые вопросы. Без имён классов, путей, лимитов строк, миграций Room, модулей Hilt.

---

## 1. Проблема

Когда пользователь меняет тип сортировки (по имени / дате / размеру / типу / случайному порядку и т.д.) внутри Browse или Slideshow конкретного ресурса, выбор действует только до закрытия экрана. При следующем открытии того же ресурса сортировка возвращается к глобальному дефолту или к значению из настроек ресурса, и пользователь вынужден переключать её заново. Это создаёт неприятное трение при ежедневной работе с одной и той же папкой / шарой / облачным каталогом и противоречит ожидаемому поведению "приложение помнит, как я смотрю эту папку".

---

## 2. Цели

1. Тип сортировки, выбранный пользователем для конкретного ресурса, сохраняется автоматически — без явного действия "запомнить".
2. При следующем входе в Browse того же ресурса список открывается уже отсортированным по сохранённому типу.
3. При запуске Slideshow для того же ресурса используется тот же сохранённый тип сортировки (порядок проигрывания согласован с тем, что пользователь видел в Browse).
4. Поведение единообразно для ресурсов любого типа: локальная папка, SMB, SSH/SFTP, Google Drive, Dropbox, OneDrive и любых будущих провайдеров.
5. Если для ресурса ещё нет сохранённого значения — применяется текущий дефолт (глобальный или из настроек ресурса, как сейчас).

**Non-goals:**

- Сохранение конкретного порядка элементов или seed для случайной сортировки. Запоминается только тип; конкретная последовательность пересчитывается при каждом открытии.
- Сохранение направления сортировки (asc/desc) и режима manual order — рассматриваются отдельно (см. §6).
- Синхронизация сохранённого типа сортировки между устройствами / облаком.
- Изменение UI выбора сортировки. Меню остаётся прежним; меняется только то, что выбор запоминается per-resource.
- Бэкпорт или миграция исторических предпочтений из логов / `dev/archive/`.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Минимально-инвазивный storage layer — переиспользовать существующий механизм per-resource настроек, не плодить параллельные хранилища.
2. Запись должна быть дешёвой (не блокировать UI, не вызывать лишний рекомпоз/рескан списка после смены сортировки — только сохранение факта выбора).
3. Желательно, чтобы при удалении ресурса из приложения сохранённое значение сортировки удалялось вместе с ним (не оставлять "осиротевшие" записи).

### 3.2 Жёсткие ограничения

- **Flavor:** все варианты сборки (`standard`, `lite`, `photos`, `legacy`). Сортировка одинаково есть во всех.
- **API level:** без специфики — `minSdk 26` для основной линейки и `minSdk 23` для `legacy` достаточны.
- **Wear OS:** не затрагивается на этой итерации (Wear-модуль использует упрощённый просмотр без полного набора сортировок).
- **Производительность:** запись типа сортировки — единичная операция per выбор, должна быть асинхронной и не должна вызывать повторный листинг файлов; чтение — однократно при открытии ресурса.
- **Совместимость данных:** при отсутствии сохранённого значения для уже существующего ресурса поведение должно быть идентично текущему (никаких форс-миграций пользовательских настроек).
- **Локализация:** EN/RU/UK — обязательно для любых новых пользовательских строк (если фича добавит видимый текст в UI; см. §8).
- **Доступность:** без новых UI-элементов фича не вводит требований к TalkBack/touch-target сверх существующих.

## 4. Контекст текущей архитектуры

В проекте уже есть концепция per-resource настроек: каждый ресурс может иметь индивидуальные параметры (включая дефолтный sort mode, поддерживаемые типы медиа, режим отображения и т.д.). Однако текущий дефолт sort mode задаётся пользователем через настройки ресурса как явное предпочтение и не обновляется автоматически при смене сортировки во время просмотра. Текущая сортировка живёт во временном состоянии экрана Browse и не переживает пересоздание сцены / перезапуск приложения. Slideshow при старте читает либо глобальный дефолт, либо настройки ресурса, но не "последний выбор пользователя".

Таким образом, инфраструктура per-resource настроек существует, но между ней и runtime-выбором сортировки в UI нет двусторонней связи: UI читает дефолт при входе, но обратно ничего не пишет.

---

## 5. Предлагаемый подход

Ввести понятие "последний применённый тип сортировки" как отдельное per-resource свойство, отличающееся от "дефолтного sort mode" в настройках ресурса:

- **Дефолт ресурса** — то, что пользователь явно настроил в свойствах ресурса (опционально, может отсутствовать).
- **Последний выбранный тип** — то, что пользователь по факту выбрал в Browse/Slideshow в последний раз; обновляется автоматически.

Приоритет применения при открытии ресурса: последний выбранный тип → дефолт ресурса → глобальный дефолт.

### 5.1 Основные столпы / модули

1. **Хранилище предпочтения сортировки per-resource.** Минимальная сущность: идентификатор ресурса + тип сортировки + метка времени последнего обновления. Реализуется как расширение существующего слоя per-resource настроек, без отдельной таблицы, если структура настроек это позволяет; иначе — компактная независимая таблица, ключ — стабильный идентификатор ресурса, который уже используется системой.
2. **Слой применения при открытии.** Точка входа в Browse и точка входа в Slideshow читают это значение и применяют как стартовый тип сортировки. Если значения нет — fallback на текущий дефолт.
3. **Слой записи при выборе.** Когда пользователь выбирает новый тип сортировки в UI Browse/Slideshow, факт выбора асинхронно записывается в хранилище. Запись не блокирует пересортировку списка.
4. **Слой очистки.** При удалении ресурса соответствующая запись удаляется (cascade).

### 5.2 Потоки данных и событий

- **Открытие ресурса в Browse:** UI запрашивает сохранённый тип → слой применения возвращает либо сохранённое значение, либо fallback → список загружается уже с нужной сортировкой.
- **Смена сортировки пользователем в Browse:** UI применяет новый тип к текущему списку (как сейчас) и параллельно отправляет факт смены в слой записи. Ошибка записи не должна влиять на UX просмотра.
- **Запуск Slideshow:** независимо от того, открыт ли Browse, плеер запрашивает тот же сохранённый тип через тот же слой применения; для случайной сортировки seed/последовательность пересчитываются заново.
- **Удаление ресурса:** запись о сортировке удаляется в той же транзакции, что и сам ресурс.

### 5.3 Точки расширяемости

- В будущем рядом с типом сортировки можно хранить направление (asc/desc) и/или manual-порядок без изменения формы хранилища — только расширение полей записи.
- Возможность опционального экспорта/импорта пользовательских предпочтений вместе с другими per-resource настройками.
- Возможность добавления флага "не запоминать сортировку для этого ресурса" в настройках ресурса, если в будущем появится такой запрос.

## 6. Резолюция вопросов (closed 2026-05-02)

Все исследовательские вопросы закрыты ответами владельца. Реализация согласована с фактической архитектурой: `SortMode` enum в кодовой базе уже кодирует и тип, и направление, и режим `MANUAL` единым значением, поэтому хранение "одного `SortMode` per resource" автоматически удовлетворяет п. 1–2 без расширения схемы.

1. **Направление сортировки (asc/desc).** **Resolved:** запоминается вместе с типом, включая `MANUAL`. Технически — отдельного поля направления не требуется: `SortMode` enum (`NAME_ASC`, `NAME_DESC`, `DATE_ASC`, .., `MANUAL`) уже представляет тип+направление одним значением. ADR-2 пересмотрен соответственно.

2. **Manual / drag-to-reorder режим.** **Resolved:** да, `MANUAL` — это один из значений `SortMode` и сохраняется/восстанавливается тем же путём. Конкретный пользовательский порядок остаётся в существующем хранилище ручного порядка (per-directory) и не дублируется здесь.

3. **Идентификатор ресурса как ключ хранения.** **Resolved:** отдельного ключа нет — значение хранится прямо в записи ресурса (`ResourceEntity.sortMode`). Жизненный цикл, cascade-удаление и идентичность совпадают с самим ресурсом по построению.

4. **Сценарий "Open with .." и временные ресурсы.** **Resolved:** вариант (а) — сохраняем только для зарегистрированных в приложении ресурсов. У ad-hoc открытий (системный share/intent через `StandalonePlayerViewModel`) нет стабильного `resource.id`, поэтому память сортировки к ним не применяется.

5. **Глобальный сброс / "очистить запомненные сортировки".** **Resolved:** нет. Очистка происходит естественным путём при удалении ресурса (cascade, см. п. 3). Отдельного UI-пункта не требуется.

## 9. Архитектурные решения (ADR)

**ADR-1: Разделение "явный дефолт ресурса" и "последний автозапомненный выбор"**

- **Решение:** ввести два независимых слоя — существующий "default sort mode" в настройках ресурса остаётся как явное пользовательское предпочтение (опциональное); новое значение "последний выбранный тип" живёт отдельно и обновляется автоматически.
- **Альтернативы:** (а) перезаписывать "default sort mode" каждый раз при смене сортировки в UI; (б) хранить только "последний выбранный", без понятия явного дефолта.
- **Почему:** перезапись явной настройки незаметно для пользователя — антипаттерн UX. Явный дефолт должен оставаться явным; автозапоминание — отдельный механизм, прозрачный по своей природе.

**ADR-2: Хранение единым значением `SortMode` (тип + направление + MANUAL)**

- **Решение:** запоминается одно значение `SortMode` per resource — оно одновременно кодирует тип, направление (`*_ASC` / `*_DESC`) и режим `MANUAL`. Конкретная последовательность элементов в `MANUAL` не дублируется здесь — она остаётся в существующем хранилище ручного порядка.
- **Альтернативы:** (а) хранить только тип, направление — отдельным полем; (б) хранить только тип без направления.
- **Почему:** существующий enum `SortMode` уже представляет (тип, направление) единым символом, и Browse уже сохраняет его в `ResourceEntity.sortMode`. Введение отдельного поля направления было бы избыточной денормализацией. Ответ владельца в §6.1 подтверждает: запоминать направление вместе с типом, включая `MANUAL`.
- **Изменено:** 2026-05-02 после резолюции §6.1 — первоначальная редакция предполагала хранение только типа.

## 11. Критерии готовности (strategic-level)

1. Пользователь открывает Browse ресурса A, переключает сортировку с "по имени" на "по дате". Закрывает Browse, открывает Browse того же ресурса A снова — список отсортирован по дате без ручных действий.
2. Тот же сценарий, но повторное открытие — через Slideshow: слайдшоу стартует с порядком, соответствующим типу "по дате".
3. Изменение типа сортировки в Browse ресурса A не влияет на тип сортировки ресурса B при его последующем открытии.
4. Удаление ресурса не оставляет видимых пользователю артефактов; повторное создание ресурса с тем же содержимым ведёт себя как "новый" — применяется текущий дефолт, а не значение от удалённого предка (или явно подтверждённое поведение из §6.3).
5. Производительность открытия Browse и старта Slideshow для типичных размеров каталога не ухудшается заметно для пользователя.
6. Поведение одинаково для всех типов ресурсов (локальные, SMB, SSH/SFTP, облака) в поддерживающих эти типы flavor'ах.
