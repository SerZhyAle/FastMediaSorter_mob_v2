## 1. Проблема

При запросе у пользователя специальных разрешений (Manage Media, All Files Access) приложение запускает соответствующий системный экран Settings через стандартный intent. На устройствах с многооконной средой по умолчанию (Android XR / Meta Horizon, foldable в режиме freeform, ChromeOS, некоторые планшеты в split-screen) система открывает этот экран в маленьком плавающем окне, чьи края обрезают содержимое слева и справа. Пользователь видит только середину диалога — без заголовка приложения и без переключателя справа — и не может включить разрешение. На обычных телефонах в полноэкранном режиме проблема не воспроизводится.

---

## 2. Цели

1. На устройствах с многооконной средой системный экран запроса разрешения открывается в окне, в которое полностью помещается заголовок, описание и переключатель (без обрезки слева/справа).
2. На обычных телефонах поведение не меняется — экран по-прежнему открывается на весь экран (никакой визуальной регрессии).
3. Пользователь XR-устройства может включить Manage Media и All Files Access в один заход, без ручного перетаскивания окна.

**Non-goals:**

- Менять собственное оформление системного экрана Settings — он принадлежит ОС, его layout не контролируется приложением.
- Делать обходной путь через собственный onboarding-экран с инструкцией.
- Отключать запрос Manage Media на XR (разрешение опциональное, но пользу даёт — оставляем).
- Поддерживать сценарий "окно обрезает Top/Bottom" — на текущих устройствах не наблюдается.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Решение должно покрыть **все** точки, где приложение запускает системный экран запроса специальных разрешений, а не только тот случай, на котором баг обнаружен.
2. Желательно вынести подсказку системе размера окна в одно место, чтобы будущие новые intent-запросы автоматически получали то же поведение.

### 3.2 Жёсткие ограничения

- **Flavor:** все варианты сборки (`standard`, `lite`, `photos`, `legacy`) — все они умеют работать с локальными файлами и могут запросить эти разрешения.
- **API level:** минимум API 26 (наш `minSdk` для большинства flavor) и API 23 для `legacy`. Используемый системный приём подсказки границ окна доступен с API 24, для `legacy` (API 23) поведение должно деградировать тихо — без падений и без эффекта.
- **Wear OS:** не затрагивается (на часах нет этих разрешений и нет многооконного режима).
- **Производительность:** нейтрально — добавляется один вычислительный шаг при разовом нажатии пользователя.
- **Совместимость данных:** изменений в хранимых данных нет.
- **Локализация:** не затрагивается — никакого нового UI/строк не добавляется.
- **Доступность:** улучшение доступности по факту — пользователь, который сейчас не может физически дотянуться до переключателя, получит к нему доступ.

---

## 4. Контекст текущей архитектуры

Запросы специальных разрешений сегодня инициируются из нескольких независимых точек: первичный onboarding, повторный запрос из главного экрана и универсальный путь из утилит-помощников. Каждая точка самостоятельно собирает системный intent и передаёт его в стандартный механизм запуска активити. Подсказку системе об ожидаемом размере и положении открываемого окна никто не передаёт, поэтому система использует свой default — на телефоне это полноэкранный режим, на XR / freeform / foldable это маленький плавающий прямоугольник, который не помещает содержимое.

Решить задачу одной заплаткой по месту бага нельзя — пять точек запуска ведут себя одинаково и в равной мере нуждаются в исправлении.

---

## 5. Предлагаемый подход

Ввести единую точку запуска системных Settings-диалогов разрешений, которая перед стартом активити подсказывает системе желаемые границы окна — прямоугольник, центрированный относительно текущего дисплея и достаточно крупный, чтобы вместить содержимое (порядка 80% от рабочей области). На устройствах, где система игнорирует подсказку (телефон в полноэкранке), поведение остаётся прежним. На устройствах со свободным расположением окон подсказка применяется и диалог открывается в нужном размере.

Все существующие точки, инициирующие подобные intent'ы, переводятся на эту единую точку. Будущие новые запросы должны идти через неё же — это закрепляется как архитектурное правило проекта.

### 5.1 Основные столпы / модули

**Единая точка запуска системных Settings-intent'ов**

- Ответственность: принять готовый системный intent и код-результата, запустить активити с подсказкой о границах окна.
- Требование: подсказка границ строится на основе актуальных метрик дисплея вызывающего экрана, чтобы корректно отрабатывать смену ориентации, складывание устройства и подключение внешнего дисплея.
- Требование: активити запускается в новой задаче — это технически необходимое условие для применения подсказки границ системой.

**Существующие сценарии запроса разрешений**

- Все известные на момент спеки точки переключаются на единый launcher.
- Никаких новых пользовательских флоу не появляется — изменение чисто внутреннее.

### 5.2 Потоки данных и событий

- UI-слой (onboarding / основной экран / помощник) формирует системный intent → передаёт его в единый launcher → launcher вычисляет рекомендуемые границы по метрикам дисплея → launcher запускает системную активити с этой подсказкой и переданным кодом результата → результат возвращается в исходный UI-слой обычным механизмом.

### 5.3 Точки расширяемости

- Если в будущем появится отдельный intent для нового специального разрешения (Notifications, Schedule Exact Alarm, и т.п.), его запуск должен идти через тот же единый launcher без дополнительных изменений в коде launcher'а.
- Стратегия вычисления границ должна быть локализована в одном месте, чтобы её можно было заменить (например, перейти от "80% дисплея" к адаптивной формуле от плотности контента) без правки вызывающих экранов.

## 6. Открытые вопросы / Research items

1. **Размер окна по умолчанию**
   - **Вопрос:** какую долю дисплея использовать как ширину/высоту по умолчанию?
   - **Варианты:** 80% × 80% (текущий ориентир) / 70% × 85% (более книжное, удобнее для длинного описания) / фиксированный минимум в dp с верхней границей.
   - **Нужно выяснить:** на эмуляторе XR проверить, при каком размере содержимое перестаёт обрезаться с запасом, и нет ли побочного эффекта на маленьких foldable.
   - **Статус:** Open

2. **Поведение при складывании устройства / повороте**
   - **Вопрос:** требуется ли пересчёт границ при изменении ориентации между нажатием и открытием активити?
   - **Варианты:** считать один раз в момент запуска (проще) / отказаться от подсказки, если ориентация поменялась за миллисекунды до старта (избыточно).
   - **Нужно выяснить:** наблюдается ли проблема в практике или это теоретический риск.
   - **Статус:** Open

3. **API 23 (`legacy` flavor)**
   - **Вопрос:** на API 23 системный приём подсказки границ недоступен. Допустимо ли просто запускать intent без подсказки (как сейчас), или нужна явная ветка-комментарий в коде?
   - **Варианты:** тихая деградация / явный no-op-ветвь.
   - **Нужно выяснить:** имеет ли `legacy`-сборка вообще флоу запроса этих разрешений (она работает только с локальным хранилищем без облаков).
   - **Статус:** Open

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Подсказка границ применяется на телефоне и портит ощущение "родного" Settings | Низкая | Системный диалог открывается окном меньше экрана | Подсказка границ на телефонах в полноэкранке игнорируется системой; явно проверить на минимум двух телефонах (старый и новый Android) |
| Запуск активити в новой задаче ломает ожидания возврата (callback не приходит) | Средняя | После закрытия Settings приложение не перепроверяет разрешение | Сохранить существующий механизм получения результата; убедиться, что новая задача не блокирует доставку результата в исходный экран |
| На неизвестной модели XR-устройства подсказка границ всё ещё обрезается | Низкая | Часть устройств не получает фикса | Стратегию вычисления границ держать в одном месте, чтобы быстро подкрутить долю/минимум по сообщениям пользователей |
| `legacy` сборка падает на API 23 из-за вызова более позднего API | Низкая | Старые устройства теряют возможность запросить разрешение | Защитить вызов уровнем API; на 23 — обычный запуск intent |

## 9. Архитектурные решения (ADR)

**ADR-1: Подсказка границ окна вместо собственного onboarding-обхода**

- **Решение:** при запуске системных Settings-диалогов разрешений передавать системе подсказку о желаемых границах окна.
- **Альтернативы:**
  1. Показывать собственный полноэкранный экран-инструкцию со скриншотом и стрелкой "тяни сюда" перед запуском Settings — добавляет лишний шаг и не решает корневую проблему.
  2. Пропускать запрос Manage Media на XR-устройствах — приложение продолжает работать, но пользователь получает дополнительные системные подтверждения на каждое удаление.
  3. Открывать общий экран App Info вместо специального — у пользователя становится больше кликов, не меньше.
- **Почему:** подсказка границ — штатный системный механизм, ровно для этой цели предусмотренный платформой; не требует собственного UI, не ломает обычные телефоны, прозрачно отрабатывает на XR / freeform / foldable.

**ADR-2: Единая точка запуска вместо точечной правки пяти мест**

- **Решение:** ввести один общий launcher и перевести все известные точки на него.
- **Альтернативы:** добавить ту же логику локально в каждое из существующих мест — пять копий одной формулы.
- **Почему:** при появлении новых intent'ов или необходимости подкрутить стратегию границ изменение делается в одном файле, а не в пяти; снижается риск, что новая точка запуска забудет применить подсказку.

## 11. Критерии готовности (strategic-level)

1. На эмуляторе Android XR SDK после нажатия "Запросить разрешение Manage Media" пользователь видит полностью весь системный экран запроса — включая название приложения слева и переключатель справа — без обрезки.
2. То же самое для запроса All Files Access — все существующие точки запуска ведут себя одинаково корректно.
3. На обычном телефоне (Android 12 или новее) поведение визуально не отличается от текущего: системный экран по-прежнему открывается на весь экран.
4. После закрытия системного экрана приложение получает результат и обновляет своё состояние — как до изменения.
5. Падений на устройствах с API 23 (`legacy` flavor) нет.
