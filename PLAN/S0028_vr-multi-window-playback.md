## 1. Проблема

В VR-флейворе на Quest 3 многооконная среда HorizonOS уже сейчас допускает «клонирование» приложения: при открытии стерео-файла иммерсивный плеер открывается **в отдельном окне**, окно Browse при этом не закрывается, а отдельно показывается панельный плеер, и из основного окна можно дальше запускать второй файл — он откроется как ещё одно окно. Эта возможность возникла как побочный эффект архитектуры активити, а не как осознанная фича. У этого две стороны:

**Бытовая (баг):** окна копятся, пользователь должен закрывать каждое отдельно; не понятно, какое из них «главное»; неясно, что произойдёт с фоновой задачей при закрытии Browse-окна, если из него запущена воспроизводящаяся слайдшоу/музыка.

**Полезная (фича):** на VR-устройствах с большим polished-пространством сценарий «слайдшоу фотографий в одном окне + плеер фоновой музыки в другом + основной экран приложения в третьем» — естественен и востребован. Пользователь явно просит это как future-feature: «вынести как отдельную спецификацию для реализации на будущее».

Текущая ситуация: фактическое поведение не поддерживается явно, не задокументировано и не покрыто тестами. Любой рефакторинг лайфцикла активити может случайно убить или, наоборот, сделать менее удобной. Нужно зафиксировать ожидаемое поведение и набор сценариев.

---

## 2. Цели

1. **Поддержанный сценарий «несколько окон одновременно»** на VR-устройствах: пользователь может одновременно воспроизводить (a) слайдшоу фото в одном окне, (b) аудио-трек или плейлист в другом, (c) видео в третьем. Каждое окно работает независимо: пауза/возобновление, prev/next, выход — не влияют на остальные.
2. **Явная точка запуска нового окна.** В существующих экранах появляется команда «открыть в новом окне» (или эквивалент через системное меню Quest 3). Пользователь не «вынужден» получить новое окно как побочный эффект — это его осознанный выбор.
3. **Корректное закрытие окна** не убивает соседние воспроизведения. Закрытие Browse-окна не останавливает запущенный из него аудио-плеер в другом окне, если у того окна свой собственный лайфцикл.
4. **Фоновое аудио во второстепенных окнах** работает: пользователь свернул окно с музыкой, музыка продолжает играть; восстановление окна возвращает к точке.
5. **Состояние ресурса** между окнами синхронизировано на уровне источника данных (Room/DataStore). Изменения, сделанные в одном окне (удалить файл, переименовать ресурс), видны в других без ручного refresh.
6. **Документация для пользователя**: в документацию FEATURES появляется раздел «многооконный режим», описывающий поддержанные сценарии и ограничения.

**Non-goals:**

- Не вводится поддержка многооконности на телефонной сборке (стандартный split-screen Android не входит в скоп).
- Не покрывается одновременное воспроизведение **двух видео** через ExoPlayer в одном процессе с двумя SurfaceView (это техническое ограничение Media3 — допустимо разрешить только одно видео одновременно, остальные окна берут аудио/фото).
- Не вводится «менеджер окон» внутри приложения — управление окнами остаётся за HorizonOS.
- Не покрывается распределённая аудио-сцена (spatial audio mixing нескольких источников) — пользователь слышит сумму аудио-выходов, как делает HorizonOS.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Главный целевой сценарий: «слайдшоу фото + фоновая музыка + основное окно». Это должно работать «из коробки», без ручных настроек.
2. Желательно, чтобы команда «открыть в новом окне» была доступна для каждого ресурса в Browse — пользователь сам решит, что в каком окне запускать.
3. Желательно, чтобы окна выглядели как разные «приложения» в трее Quest 3 (разный заголовок, разная иконка-индикатор) — не «три копии одной программы».
4. Если открыть тот же файл, который уже играет в другом окне, — поведение должно быть осознанным: либо переключение фокуса на существующее окно, либо явное предупреждение.

### 3.2 Жёсткие ограничения

- **Flavor:** только VR-флейвор (где HorizonOS поддерживает multi-instance).
- **API level:** без новых API-зависимостей; используются стандартные Android-механизмы task affinity / launchMode / multi-instance.
- **Wear OS:** не затрагивается.
- **Производительность:** одновременная работа трёх окон (фото-слайдшоу + аудио + UI) не должна давать просадки FPS ниже 72 в активном иммерсивном окне; фоновые окна допустимо ставить на пониженный priority.
- **Совместимость данных:** между окнами разделяется один Room-DB и один DataStore. Конфликтные записи (например, два окна одновременно меняют sortMode ресурса) разрешаются last-writer-wins с обновлением UI.
- **Локализация:** все новые строки UI (команда «открыть в новом окне», пункт документации) — EN/RU/UK.
- **Доступность:** команда «открыть в новом окне» доступна с контроллера и hand-tracking (там где S0007 поддерживает).

## 4. Контекст текущей архитектуры

Приложение собрано как single-task Android-приложение: главный экран → Browse-экран → экраны плеера (панельный и иммерсивный) живут в одном task'е по умолчанию. На Quest 3 HorizonOS позволяет запустить второй экземпляр приложения через системное меню; технически это второй процесс или второй task — точное поведение определяется launchMode и taskAffinity манифеста.

Текущее поведение «второе окно появляется при открытии стереофайла» — следствие того, что иммерсивный плеер-экран запускается с флагами intent'а, заставляющими систему создать новую task (вероятно флаг создания новой задачи или специальный launchMode). Это не задокументировано, не контролируется и не покрыто тестами.

Состояние приложения — Room-DB + DataStore + in-memory ViewModel. Между процессами Room и DataStore делятся (это observed via SharedPreferences/DataStore single-process model — нужна проверка), ViewModel — нет. Сейчас экраны не рассчитаны на одновременную работу: например, репозиторий состояния возобновления хранит «последний открытый файл» в одной записи, что в multi-window даст конфликт.

Аудио в фоне технически возможно через сервис медиасессии — приложение уже использует Media3, но текущая реализация привязывает плеер к лайфциклу активити. Закрытие активити — остановка плеера.

## 5. Предлагаемый подход

Подход разделён на пять блоков: декларация manifest, изоляция состояния, фоновое аудио, явные команды UI, документация.

### 5.1 Основные столпы / модули

**Manifest declaration of multi-instance support.**
В манифесте VR-флейвора экраны, которые могут жить в нескольких экземплярах (слайдшоу фото, аудио-плеер, возможно иммерсивный плеер для отдельных файлов), помечаются атрибутами multi-instance (launchMode, affinity). Конкретные значения — задача тактической спеки. Цель: HorizonOS получает от приложения явный сигнал «этот экран может быть multi-instance».

**Изоляция per-window state.**
ViewModel и in-memory кэш плеера/слайдшоу — per-instance активити. Глобальные репозитории состояния расширяются ключом-идентификатором окна — каждое окно имеет свою запись «последний файл», «текущий ресурс», «позиция воспроизведения». Это требует миграции Room-схемы (детали — в тактике).

**Фоновое аудио через сервис медиасессии.**
Аудио-плеер и аудио-режим слайдшоу (если у пользователя включён background-music) выносятся в сервис медиасессии, лайфцикл которого не привязан к активити. Закрытие окна — это остановка UI окна, но сервис продолжает играть, пока пользователь не нажал «стоп» в системном пультовом меню или явно не закрыл сервис из приложения.

**Явные команды «открыть в новом окне».**
В Browse popup-меню ресурса и popup-меню файла появляется команда «открыть в новом окне». На VR-устройстве — видна; на телефоне — скрыта. Команда отправляет intent с флагами, явно гарантирующими новую task. Сценарий «в одном окне выбрал ресурс, нажал — открылся новый плеер» — это фича, а не побочный эффект.

**Поведение при дубликате.**
Если пользователь открывает файл, уже играющий в другом окне, поведение — задача §6 research item 1 (ниже). По умолчанию: открывается ещё одно окно (пользователь явно попросил), без блокировки. Альтернатива — переключить фокус — рассматривается как опция.

### 5.2 Потоки данных и событий

```text
User → "Open in new window" (Browse popup)
        │
        ▼
Intent (new task, new instance, target screen: player|slideshow|immersive-player)
        │
        ▼
HorizonOS creates new window
        │
        ▼
Screen initialises with window-id (saved in instance state)
        │
        ▼
Per-window ViewModel + per-window resume-state entry
        │
        ▼
For audio/slideshow background: bind to background media service
        │
        ▼
User closes window → service keeps playing if media session still active
```

### 5.3 Точки расширяемости

- Новый тип «окна» (например, выделенный аудио-плейлист с визуализацией) добавляется как новый экран в манифесте без изменений в существующих окнах.
- Если в будущем понадобится «переключить фокус на существующее окно вместо нового» — добавляется как опция в settings, но дефолт остаётся «новое окно».
- Если HorizonOS добавит API «снять snapshot окна для миниатюры» — он подключается без изменения core логики приложения.

## 6. Открытые вопросы / Research items

1. **Поведение при дубликате окна для одного и того же файла.**
   - **Вопрос:** «открыть в новом окне» файл, уже играющий в другом окне, — открывает ещё одно окно или переключает фокус?
   - **Варианты:** (a) всегда новое окно (полный multi-instance); (b) переключить фокус на существующее (singleTop-like для конкретного файла); (c) опция в settings с дефолтом (a).
   - **Ответ:** вариант (a) — всегда новое окно без каких-либо проверок на дубликат.
   - **Статус:** Resolved

2. **Два видео одновременно через ExoPlayer.**
   - **Вопрос:** Media3 ExoPlayer в одном процессе допускает несколько одновременных экземпляров с разными SurfaceView, но при ограниченных аппаратных декодерах (Quest 3 ≈ 2 H.265 hardware decoders) возможны конфликты. Можно ли позволить два видеоокна?
   - **Варианты:** (a) запретить два видео одновременно (одно в видео-окне, остальные в фото/аудио); (b) разрешить, fallback на программный декодер при дефиците; (c) разрешить только если пользователь явно подтвердил.
   - **Ответ:** разрешить без ограничений и без отслеживания — пользователь осознанно открыл второе окно. При HW-конфликте вероятно один из плееров встанет на паузу сам. Без явного предупреждения.
   - **Статус:** Resolved

3. **Per-window state vs global state.**
   - **Вопрос:** что такое «глобальное» состояние (одно на всё приложение) vs «оконное» (на окно)?
   - **Варианты:** глобально — настройки приложения, тема, тумблеры; оконно — текущий ресурс, текущий файл, позиция, sort-режим (?).
   - **Ответ:** новые окна содержат **только плеер** — Browse в multi-instance не открывается (два Browse — не скоп). Из плеера в настройки зайти нельзя. Таким образом: оконное состояние — текущий файл, позиция воспроизведения. Настройки (тема, sort, тумблеры) — глобальные. Sort-per-resource — выяснить не нужно: в новом окне-плеере этот экран недоступен.
   - **Статус:** Resolved

4. **Сервис медиасессии vs воспроизведение, привязанное к экрану, для VR-плеера.**
   - **Вопрос:** иммерсивный плеер-экран нельзя свернуть в фон без выхода пользователя из VR-сцены. Имеет ли смысл сервис медиасессии для VR?
   - **Варианты:** (a) только аудио и слайдшоу через сервис медиасессии; VR-видео всегда foreground; (b) VR-видео тоже через сервис медиасессии (для возможности фоновой паузы).
   - **Ответ:** вариант (a) — приоритет стабильности. Аудио и слайдшоу фото — через сервис медиасессии. VR-видео (иммерсив) — всегда foreground, привязан к активити. Сложные сценарии с OpenXR background-lifecycle — вне скопа.
   - **Статус:** Resolved

5. **Закрытие Browse-окна и его последствия.**
   - **Вопрос:** Browse-окно — «корневое»? Если пользователь его закрыл, остальные окна остаются жить? Или Browse — это «launcher», без него процесс умирает?
   - **Варианты:** (a) каждое окно независимо, Browse не привилегировано; (b) Browse — launcher, при его закрытии остальные тоже завершаются (предупреждение пользователю).
   - **Ответ:** вариант (a) — каждое окно полностью независимо. Browse-окно можно закрыть и снова открыть; плеер-окна продолжают работать. Browse не имеет привилегированного статуса.
   - **Статус:** Resolved

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
| ------ | :-----------: | ------------- | ----------- |
| Multi-instance экранов ломает состояние Room/DataStore (writer-conflicts, race) | Высокая | Удаление файла в одном окне «возвращает» файл в списке другого | Все mutations через Repository-слой с in-memory invalidation; Flow-based UI получает обновления автоматически |
| Hardware decoders Quest 3 не тянут два видео — одно из воспроизведений встаёт на паузу или деградирует | Средняя | Пользователь видит неожиданное поведение без объяснений | Принято решение (§6 #2): разрешить без блокировок. Деградация под управлением Media3. Не документировать как поддержанный сценарий — только как возможный. |
| Репозиторий состояния возобновления хранит «последний файл» одной записью — окна перезаписывают друг друга | Высокая | После закрытия и открытия окна оно показывает файл, открытый в другом окне | Миграция: состояние возобновления per-window; ключ — идентификатор окна |
| Фоновое аудио через сервис медиасессии конфликтует с системным «do not disturb» Quest 3 | Низкая | Аудио заглушено в неожиданные моменты | Проверить взаимодействие с HorizonOS audio-policy; задокументировать ограничения |
| Команда «открыть в новом окне» дублирует существующее поведение и запутывает пользователя | Средняя | Пользователь не понимает разницу между «открыть» и «открыть в новом окне» | UX-копирайт чёткий; возможно «открыть в новом окне» только для слайдшоу/аудио, обычное «открыть» — текущее поведение |
| Manifest-изменения (multi-instance) ломают сборку non-VR-флейворов | Средняя | Регрессия в standard/lite/photos/legacy | Изменения изолированы в манифесте VR-флейвора без затрагивания основного манифеста |

## 10. Архитектурные решения (ADR)

**ADR-1: Multi-instance — явная фича, через manifest declarations.**

- **Решение:** в манифесте VR-флейвора экраны, поддерживающие multi-instance, помечаются явно. Случайное «второе окно» через intent-флаги — больше не сценарий.
- **Альтернативы:** (а) оставить случайное multi-instance — отвергнуто, потому что не контролируется и не тестируется; (б) полностью запретить multi-instance — отвергнуто, противоречит запросу пользователя.
- **Почему:** контроль через manifest даёт детерминированное поведение и проверяется на стадии сборки.

**ADR-2: Фоновое аудио через сервис медиасессии — отвязано от активити.**

- **Решение:** аудио-плеер и фоновая музыка слайдшоу живут в сервисе, лайфцикл которого не привязан к активити. Закрытие окна не останавливает фоновое аудио.
- **Альтернативы:** (а) аудио в активити — отвергнуто, потому что закрытие окна = остановка музыки; (б) глобальный singleton-плеер — отвергнуто, не масштабируется на несколько окон.
- **Почему:** сервис медиасессии — стандартный Android-механизм для фоновой медиапотоковой работы; интегрируется с системным «media-pult» Quest 3.

**ADR-3: Per-window state через идентификатор окна в репозиториях.**

- **Решение:** репозитории состояния расширяются полем-ключом идентификатора окна. Каждое окно имеет свою запись.
- **Альтернативы:** (а) глобальное состояние — отвергнуто, окна перезаписывают друг друга; (б) state в ViewModel без персистенции — отвергнуто, не переживает recreate.
- **Почему:** идентификатор окна — стабильный ключ на жизнь экрана; persists через recreate; естественно ложится в Room.

**ADR-4: Команда «открыть в новом окне» видима только на VR-флейворе.**

- **Решение:** popup-меню Browse показывает команду «открыть в новом окне» только при активном флаге VR-флейвора. На остальных сборках команда не существует.
- **Альтернативы:** показывать везде, но на phone-сборке открывать как обычно — отвергнуто, путает пользователя.
- **Почему:** multi-window — VR-only фича; на phone это не имеет смысла.

## 12. Критерии готовности (strategic-level)

1. На Quest 3 пользователь явной командой «открыть в новом окне» создаёт второе/третье окно приложения; каждое работает независимо.
2. Сценарий «слайдшоу фото в окне A + аудио-плейлист в окне B + Browse в окне C» работает одновременно: переключение фокуса не останавливает остальные.
3. Закрытие окна B (аудио) останавливает только аудио в этом окне; слайдшоу A продолжается.
4. Закрытие Browse-окна (C): согласно решению §6 #5 (зафиксировать в ADR на стадии тактики).
5. Per-window состояние возобновления: открыть файл в окне A, открыть другой файл в окне B; закрыть B и открыть его заново — окно B восстанавливает свой файл, не файл A.
6. Документация раздела «VR Multi-Window Mode» в EN/RU/UK содержит описание поддержанных сценариев и ограничений.
7. Одновременное открытие двух видеоокон разрешено и не блокируется приложением; поведение при HW-конфликте декодеров определяет Media3 (допустима пауза одного из плееров).

## 14. Field evidence — Quest 3, 2026-04-30

Лог `logs/fastmediasorter_20260430_031429.log` подтверждает: за одну сессию (03:14–03:20) exitImmersive трижды запускает новый `VrPlayerActivity.onCreate`:

```
[2372] VrPlayerActivity: onCreate ENTRY
       intent=launchFlags=0x10010100;component=VrPlayerActivity;
       initialFilePath=18VR_The_Best_is_Yet_to_Come_7K_180_180x180_3dh.mp4

[3479] VrPlayerActivity: onCreate ENTRY
       intent=launchFlags=0x10010100;component=VrPlayerActivity;
       initialFilePath=Boersensaal_Hamburg_stereo_360_8K_25s.webm
```

`launchFlags=0x10010100` содержит `FLAG_ACTIVITY_NEW_TASK` — каждый выход из иммерсива создаёт отдельное окно HorizonOS.

**Вывод:** до реализации S0028 необходим фикс `S0038` (убрать лишний `FLAG_ACTIVITY_NEW_TASK` из `exitImmersive`). Без S0038 отличить «случайное» multi-window от «осознанного» (цель S0028) технически невозможно.
