## 1. Проблема

На Chrome OS (ARC++) физическая клавиатура не печатает текст в текстовые поля форм — в частности, поля «пользователь по умолчанию», IP-адрес, пароль и аналогичные в экранах добавления ресурса. Chrome OS (ARC++) доставляет события физической клавиатуры через `dispatchKeyEvent` с нестандартным порядком: обработчик горячих клавиш на уровне Activity получает событие раньше, чем сфокусированный `EditText`. В результате символьные клавиши и клавиши навигации по тексту (Tab, Enter, стрелки) перехватываются делегатом горячих клавиш и не достигают поля ввода. На стандартных Android-устройствах такой проблемы нет, поскольку сфокусированный View обрабатывает событие первым.

---

## 2. Цели

1. Ввод текста в любом текстовом поле формы работает на Chrome OS так же, как на обычном Android-устройстве.
2. Клавиша Space набирает пробел в поле ввода, а не активирует сфокусированный элемент.
3. Enter/Tab переводят фокус на следующее поле (стандартное IME-поведение) вместо того чтобы выполнять команду навигации поверх поля.
4. Стрелки влево/вправо перемещают курсор внутри поля, а не переключают фокус между виджетами.
5. Горячие клавиши (Escape, F1, Ctrl+Z, Ctrl+F и т.д.) продолжают работать корректно, когда поле ввода не сфокусировано.

**Non-goals:**

- Устранение других Chrome OS-специфичных проблем (папочный picker через SAF, Cast, раскладка клавиатуры).
- Переработка архитектуры обработки клавиш на других экранах (плеер, браузер файлов).

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Исправление должно применяться ко всем экранам приложения, содержащим текстовые поля: форма добавления/редактирования ресурса, настройки.
2. Желательно не разбивать логику — единый гард в базовом Activity или общем делегате.

### 3.2 Жёсткие ограничения

- **Flavor:** все (standard, lite, photos, legacy).
- **API level:** без API-специфики; должно работать от minSdk 23.
- **Wear OS:** не затрагивается.
- **Производительность:** гард — одна проверка на каждое событие клавиши, нет аллокаций, нет IO.
- **Совместимость данных:** нет миграций.
- **Локализация:** EN/RU/UK — строки UI не затрагиваются.
- **Доступность:** исправление улучшает доступность — экранный диктор на Chrome OS тоже использует клавиатуру.

## 4. Контекст текущей архитектуры

Каждый экран с формой переопределяет `onKeyDown` на уровне Activity и направляет все события через делегат горячих клавиш. Делегат опирается на поверхностно-специфичную таблицу соответствий (Enter → «открыть», Space → «активировать», Tab → «следующий фокус», стрелки → «переместить фокус»). На стандартном Android сфокусированный `EditText` перехватывает свои события ещё до того, как они добираются до `onKeyDown`, поэтому конфликта нет. Chrome OS ARC++ нарушает эту последовательность: некоторые физические клавиши приходят в `onKeyDown` Activity раньше обработки View, либо IME-механизм Chrome OS не выполняет вставку символов через стандартный `TextWatcher`-путь, если Activity пометила событие как обработанное.

---

## 5. Предлагаемый подход

Добавить гард непосредственно перед вызовом делегата горячих клавиш: если текущий сфокусированный View является текстовым полем ввода, символьные и редакторские клавиши не передаются делегату. Горячие клавиши, которые не конфликтуют с текстовым вводом (Escape, F1, F10, Alt+F4), должны работать везде, в том числе когда активно текстовое поле.

### 5.1 Основные столпы

**Гард текстового поля.** Перед вызовом делегата проверяется тип сфокусированного View. Если это текстовое поле — символьные клавиши, стрелки, Enter (без модификаторов), Space, Home, End, Page Up/Down передаются стандартному `super.onKeyDown()`, минуя делегат.

**Список «безопасных» горячих клавиш в поле.** Ограниченный набор клавиш остаётся активным даже в текстовом поле: Escape (закрыть форму), F1 (помощь), F10 / Alt+F4 (выход).

**Единая точка применения.** Логику размещается в базовом уровне так, чтобы все экраны с формами получили исправление автоматически, а не через дублирование на каждом Activity.

### 5.2 Потоки данных и событий

Событие клавиши → `Activity.onKeyDown()` → гард (сфокусировано текстовое поле?) → да: `super.onKeyDown()` (стандартный путь EditText) / нет: делегат горячих клавиш → действие.

### 5.3 Точки расширяемости

Гард должен быть параметризуемым (набор «безопасных» клавиш конфигурируется для каждого экрана), чтобы экраны с нестандартными потребностями могли расширить список.

## 6. Открытые вопросы / Research items

1. **Scope экранов**
   - **Вопрос:** Какие именно экраны приложения содержат текстовые поля и одновременно переопределяют `onKeyDown`?
   - **Нужно выяснить:** Перечислить все Activity с `onKeyDown` override и текстовыми полями; убедиться, что исправление покрывает все из них.
   - **Статус:** Open

2. **Точный механизм Chrome OS**
   - **Вопрос:** Нарушен ли порядок dispatch (Activity раньше View), или Chrome OS не доставляет KEY-события в EditText вообще, заменяя их IME-событиями?
   - **Варианты:** (а) порядок dispatch инвертирован; (б) ARC++ отправляет KEY-события в обход View; (в) проблема специфична для конкретных версий Chrome OS.
   - **Нужно выяснить:** Проверить в logcat поведение `dispatchKeyEvent` и `onKeyDown` на Chrome OS при наличии сфокусированного EditText.
   - **Статус:** Open

## 9. Архитектурные решения (ADR)

**ADR-1: Гард в `onKeyDown` vs. override `dispatchKeyEvent`**

- **Решение:** Гард в `onKeyDown` с ранним возвратом, когда сфокусировано текстовое поле.
- **Альтернативы:** Override `dispatchKeyEvent` с аналогичной проверкой; перенос гарда в `KeyboardShortcutHandler`.
- **Почему:** `onKeyDown` — уже переопределённая точка в каждом Activity; минимальный diff, нет риска задеть `dispatchKeyEvent`-цепочку, которая также обрабатывает жесты и touch.

## 11. Критерии готовности (strategic-level)

1. Пользователь вводит любой текст (буквы, цифры, пробел) в поле «пользователь по умолчанию» и аналогичные на Chrome OS с физической клавиатурой.
2. Tab переводит фокус на следующее поле без перехвата командой делегата.
3. Escape закрывает форму добавления ресурса, даже если активно текстовое поле.
4. На обычном Android-планшете с Bluetooth-клавиатурой горячие клавиши (F5, F6, F8, Ctrl+F) работают как прежде в Browse и других экранах без текстовых полей.
5. Стрелки влево/вправо перемещают курсор внутри EditText, а не переключают фокус между кнопками формы.
