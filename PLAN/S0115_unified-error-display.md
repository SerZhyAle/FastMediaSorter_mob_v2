# Стратегическая спецификация: S0115 — Унификация отображения ошибок

**Ticket:** S0115
**Status:** Approved
**Priority:** 50

**Tier:** 3 — Moderate
**Roadmap entry:** Ad-hoc — запрос 2026-05-08
**Tactical spec:** `PLAN/S0115_unified-error-display/` (будет создан через `/spec-tech`)

> **Scope:** STRATEGIC. Цели, ограничения, открытые вопросы. Без имён классов, путей, лимитов строк, миграций Room, модулей Hilt.

---

## 1. Проблема

В приложении нет единого стандарта для визуального вывода ошибок: критические ошибки, отладочные предупреждения и информационные сообщения выглядят одинаково и показываются с одинаковой длительностью, которой не хватает для прочтения. Порядка 89 файлов используют системный Toast напрямую, минуя централизованную обработку. Существующий диалог «детальных ошибок» не позволяет ни сохранить текст ошибки в файл, ни передать его внешнему приложению, что затрудняет сбор и передачу диагностики. Между различными экранами приложения нет единой точки входа для вывода ошибок — каждый компонент решает это самостоятельно.

---

## 2. Цели

1. Критические ошибки (показываются в релизных и отладочных сборках) отображаются с красной индикацией.
2. Отладочные предупреждения (только в DEBUG-сборках) отображаются с жёлтой/янтарной индикацией.
3. Уведомления об ошибках удерживаются на экране дольше обычного, чтобы пользователь успевал прочитать текст.
4. Диалог «детальных ошибок» (при включённой настройке) позволяет сохранить текст ошибки в файл на устройстве.
5. Диалог «детальных ошибок» позволяет передать текст через системный механизм «Отправить» (Intent.ACTION_SEND).
6. Текст в диалоге доступен для выделения и копирования, прокручивается по вертикали, не обрезается по горизонтали.
7. Все экраны приложения используют единый централизованный механизм вывода ошибок вместо прямых обращений к системному Toast.

**Non-goals:**

- Изменение алгоритма классификации ошибок (критические / не критические) — только визуальный уровень.
- Добавление удалённого логирования или телеметрии.
- Реализация нотификаций в строке состояния.
- Wear OS — не затрагивается.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Возможность «заморозить» уведомление нажатием, чтобы оно не пропало, пока читают.
2. Показывать имя экрана / контекст ошибки в заголовке диалога (например, «Browse — Ошибка»).
3. В диалоге отображать только понятный пользователю текст по умолчанию; стек трассировки — под спойлером или отдельной кнопкой «Подробности».

### 3.2 Жёсткие ограничения

- **Flavor:** все флейворы (`standard`, `lite`, `photos`, `legacy`).
- **API level:** минимум Android 8 (API 26); на Android 13+ (API 33+) пользовательские виды Toast из фонового контекста заблокированы системой — решение должно работать в этом ограничении.
- **Wear OS:** не затрагивается.
- **Производительность:** уведомление не должно инициировать сетевых запросов или IO в главном потоке.
- **Совместимость данных:** настройка `showDetailedErrors` уже существует и сохраняется; новые опции должны добавляться совместимо с резервным копированием.
- **Локализация:** EN/RU/UK — все строки диалога и уведомлений обязательны.
- **Доступность:** цвет не является единственным отличительным признаком — критические уведомления должны иметь иконку или иную нецветовую метку.

## 4. Контекст текущей архитектуры

В приложении уже существует инфраструктура для вывода ошибок: утилита троттлинга Toast, объектный диалог ошибки с прокруткой и копированием, менеджер отображения ошибок для раздела Browse, а также ряд вспомогательных форматтеров ошибок в core/domain слоях. Однако эта инфраструктура разрозненна: у каждого компонента своя точка входа, стили не унифицированы, и большинство экранов обходят инфраструктуру, обращаясь к системному Toast напрямую.

Проблема усугубляется тем, что критичность ошибки (показывать всегда vs только в debug) задаётся на стороне вызывающего кода, а не через единый контракт — это создаёт расхождения между компонентами при определении, какую ошибку показывать.

---

## 5. Предлагаемый подход

Единая точка входа для всех уведомлений об ошибках в приложении — один фасадный компонент, через который проходит весь вывод ошибок. Компонент принимает уровень серьёзности ошибки (`CRITICAL` / `DEBUG_ONLY`), текст и опциональный контекст (заголовок экрана), и самостоятельно выбирает способ отображения.

### 5.1 Основные столпы / модули

**Уровень серьёзности (ErrorSeverity):**
- Перечисление с двумя значениями: `CRITICAL` (красная индикация, показывается везде) и `DEBUG_ONLY` (жёлтая индикация, только в DEBUG-сборках).
- Живёт в общем слое — доступен всем слоям архитектуры.

**Унифицированное уведомление об ошибке (замена Toast):**
- На Android API 26–32: допустимо использовать стилизованный Toast с пользовательским видом.
- На Android API 33+: Snackbar, прикреплённый к корневому виду активности, или кастомный оверлей.
- Реализует расширенную длительность (дольше стандартного LENGTH_LONG).
- Критические ошибки: красный фон / красная иконка с нецветовой меткой (восклицательный знак).
- DEBUG_ONLY ошибки: жёлтый/янтарный фон / соответствующая иконка; полностью подавляются в релизных сборках.

**Расширенный диалог ошибки (когда `showDetailedErrors = true`):**
- Сохраняет всю функциональность текущего диалога (прокрутка, копирование в буфер).
- Добавляет кнопку «Сохранить в файл» — записывает текст ошибки в файл в директории Downloads или в настроенный ресурс.
- Добавляет кнопку «Отправить» — запускает системный Intent.ACTION_SEND с текстом ошибки, позволяя передать данные в любое установленное приложение.
- Текст в диалоге — выделяемый, прокручиваемый по вертикали, с переносом строк по горизонтали (wordWrapEnabled).
- Пользователь видит краткое читаемое сообщение; подробности (стек трассировки, технические детали) скрыты за кнопкой «Подробности» и раскрываются по запросу.

**Фасадный менеджер ошибок:**
- Единственная публичная точка входа для всего приложения.
- Принимает `ErrorSeverity`, текст, опциональный заголовок экрана и опциональный `Throwable`.
- Читает настройку `showDetailedErrors` и самостоятельно решает, показать уведомление или диалог.
- Все прямые вызовы системного Toast по всему приложению заменяются на этот фасад.

### 5.2 Потоки данных и событий

При вызове фасадного менеджера:
- `DEBUG_ONLY` + релизная сборка → сообщение только в Timber, ничего на экране.
- `DEBUG_ONLY` + debug-сборка + `showDetailedErrors = false` → жёлтое уведомление.
- `DEBUG_ONLY` + debug-сборка + `showDetailedErrors = true` → диалог ошибки (жёлтая индикация).
- `CRITICAL` + `showDetailedErrors = false` → красное уведомление.
- `CRITICAL` + `showDetailedErrors = true` → диалог ошибки (красная индикация в заголовке).

### 5.3 Точки расширяемости

- Перечисление `ErrorSeverity` должно допускать добавление новых уровней (например, `WARNING`) без переработки фасада.
- Диалог ошибки должен принимать пользовательские действия (кнопка в диалоге для контекстных операций, как «Открыть во внешнем плеере»).

## 6. Открытые вопросы / Research items

1. **Стратегия цветного Toast на API 33+**
   - **Вопрос:** Toast с пользовательским видом на API 33+ из фонового контекста заблокирован. Как обеспечить цветную индикацию во всех активностях, включая те, у которых нет явной корневой View?
   - **Варианты:** (а) Snackbar везде (требует rootView для каждой активности); (б) кастомный Dialog-overlay; (в) на API 33+ обычный Toast без цвета, только иконка в тексте.
   - **Нужно выяснить:** покрытие активностей, в которых сейчас показывается Toast без rootView (AddResource, CloudFolderPicker и т. д.).
   - **Статус:** Open

2. **Директория для «Сохранить в файл»**
   - **Вопрос:** Куда сохранять файл с текстом ошибки — в Downloads напрямую через MediaStore, в configurable ресурс, или показывать системный folder picker?
   - **Варианты:** (а) Всегда Downloads (простота, предсказуемость); (б) папка выбирается через системный пикер; (в) используется первый доступный writable ресурс из настроенных.
   - **Нужно выяснить:** ожидания пользователя; совместимость с SAF на API 26+.
   - **Статус:** Open

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Массовая замена Toast в 89 файлах вносит регрессии | Средняя | Сломанное отображение сообщений в редких сценариях | Постепенная замена по компонентам; начать с критических путей (Browse, Player) |
| Snackbar требует rootView — не все активности его имеют | Средняя | Crash при вызове из активности без иерархии вью | Добавить защитный fallback на обычный Toast если rootView недоступен |
| «Сохранить в файл» в диалоге — IO в UI-потоке | Низкая | ANR при медленном хранилище | Всегда выполнять IO в корутине; показывать прогресс-индикатор |

## 8. Влияние на пользователя (docs/FEATURES)

- **EN:** Unified error display: critical errors shown in red, debug-only warnings in yellow with extended on-screen duration; the detailed-errors dialog adds Save to file and Share actions for diagnostics export.
- **RU:** Унификация отображения ошибок: критические ошибки показываются красным цветом, отладочные предупреждения — жёлтым, с увеличенным временем отображения; диалог детальных ошибок дополнен действиями «Сохранить в файл» и «Отправить».
- **UK:** Уніфікація відображення помилок: критичні помилки показуються червоним, налагоджувальні попередження — жовтим, з подовженим часом відображення; діалог детальних помилок доповнено діями «Зберегти у файл» та «Надіслати».

## 9. Архитектурные решения (ADR)

**ADR-1: Snackbar вместо кастомного Toast на API 33+**

- **Решение:** На API 33+ использовать стилизованный Snackbar с расширенной длительностью как замену цветному Toast. На API ≤ 32 — пользовательский вид Toast.
- **Альтернативы:** Кастомный Dialog-overlay поверх Activity; стандартный Toast без цветового оформления.
- **Почему:** Snackbar — стандартный Material компонент, работает надёжно на всех версиях, допускает стилизацию цветом и иконками, не требует специальных разрешений.

**ADR-2: Двухуровневый диалог (краткое / подробно)**

- **Решение:** В диалоге ошибки основной текст — читаемое пользователем сообщение. Стек трассировки и технические детали скрыты за раскрываемым блоком.
- **Альтернативы:** Показывать всё сразу; всегда скрывать технические детали.
- **Почему:** Разработчик при включённой настройке `showDetailedErrors` ожидает видеть полный стек; обычный пользователь, случайно включивший настройку, не должен пугаться нечитаемого текста.

## 11. Критерии готовности (strategic-level)

1. Критическая ошибка (например, ошибка передачи файла) отображается с красным визуальным маркером и держится на экране не менее 5 секунд.
2. Сообщения, помеченные как DEBUG_ONLY, не появляются на экране в release-сборке.
3. В debug-сборке DEBUG_ONLY сообщение показывается с жёлтой/янтарной индикацией.
4. При `showDetailedErrors = true` диалог ошибки содержит кнопки «Закрыть», «Скопировать», «Сохранить в файл» и «Отправить».
5. Текст в диалоге выделяется и копируется нативным жестом; прокрутка по вертикали работает на тексте любой длины; длинные строки переносятся по горизонтали без обрезки.
6. «Сохранить в файл» создаёт текстовый файл с текстом ошибки в директории Downloads и показывает подтверждение.
7. «Отправить» открывает системный шаринг с текстом ошибки; работает в любом приложении-получателе.
8. Все существующие экраны (Browse, Player, AddResource, Settings) используют единый фасад вместо прямых вызовов Toast.
