## 1. Проблема

В VR-флейворе тумблер «Авто-вход в иммерсив на стерео-контенте» не выполняет своего обязательства: при выключенном тумблере стерео- и 360-видео всё равно автоматически уходят в иммерсивный кинотеатр вместо плоской панели. Лог-доказательство в свежей сессии на Quest 3 однозначно показывает рассинхрон между логически принятым решением маршрутизатора (reason `auto-immersive-disabled` обязан давать «остаться на панели») и фактическим маршрутом (`CINEMA_IMMERSIVE`). Дополнительно отмечается шум в репозитории настроек («updateSettings called but NO fields changed») при каждом открытии экрана настроек, что ставит под сомнение надёжность сохранения самого тумблера. Проблема видна на 4+ файлах подряд и блокирует пользовательский сценарий «смотреть стерео-контент на плоском экране без надевания шлема в иммерсив-режим».

## 2. Цели

1. При выключенном «Авто-вход в иммерсив» любой стерео/спефический-сферический файл воспроизводится на 2D-панели; вход в иммерсив возможен только явным действием пользователя.
2. При включённом тумблере поведение совпадает с прежним (стерео-файлы автоматически уходят в иммерсив).
3. Отображаемая в логе причина решения (reason) всегда консистентна с фактическим маршрутом запуска — рассинхрон невозможен.
4. Открытие экрана настроек не приводит к холостым записям в хранилище настроек.
5. Регрессия покрыта автоматическими тестами на каждой комбинации «авто-иммерсив × тип содержимого × формат стерео», чтобы предотвратить повторное протекание.

**Non-goals:**
- Не вводится новых пользовательских настроек.
- Не меняется поведение ручного входа в иммерсив (кнопка «3DVR»).
- Не меняется логика выхода из иммерсива в панель управления (это объём другой спеки).
- Не вводится изменения в логику автоопределения формата стерео.

## 4. Контекст текущей архитектуры

VR-плеер обращается к выделенному маршрутизатору, чтобы принять одно из решений: остаться на 2D-панели, перейти в иммерсивный кинотеатр или в иммерсивный сферический режим. Источник истины для пользовательских настроек — слой репозитория, читающий значения из персистентного хранилища. Логика маршрутизатора уже имеет ветку «авто-иммерсив отключён → отдать на панель», но её фактический результат не доходит до места применения: либо ветка не используется, либо последующий код переписывает маршрут, либо в развёрнутой сборке исполняется устаревшая версия маршрутизатора. Точную причину рассинхрона нужно установить на стадии тактической спеки. Дополнительно слой репозитория настроек умеет сохранять каждое изменение, но открытие экрана настроек инициирует серию холостых записей — это указывает на отсутствие проверки «что-то реально изменилось» перед записью.

## 5. Предлагаемый подход

Подход состоит из четырёх параллельных линий: восстановить контракт маршрута, гарантировать единый источник истины для решения, защитить контракт автотестами и убрать побочный шум сохранения настроек.

### 5.1 Основные столпы / модули

**Маршрутизация запуска плеера.**
Решение маршрутизатора и фактический маршрут запуска должны вытекать из одной структуры данных. Никакой код после решения не имеет права изменять маршрут — только реагировать на него. Если решение «остаться на панели», то любой обработчик обязан выполнить именно фолбэк на стандартный плеер, а не запускать иммерсив-инициализацию.

**Тумблер «Авто-вход в иммерсив».**
Состояние тумблера читается из хранилища настроек на каждый запуск плеера; повторно использовать кэш нельзя. Семантика однозначна: «выключено» — ни один файл не уходит в иммерсив без явной команды пользователя.

**Дисциплина диагностики.**
Текстовый идентификатор причины и значение маршрута строго связаны: рассинхрон в логе считается багом и ловится тестом. Из этого следует, что reason формируется в той же точке, где принимается решение, и не дописывается «постфактум».

**Гигиена сохранения настроек.**
Слой репозитория настроек должен либо проверять «что-то изменилось» перед записью, либо публиковать настройки лишь при реальном изменении. Холостые записи допустимы только в сценариях явной пользовательской команды «сохранить» (которой в текущем экране нет).

### 5.2 Потоки данных и событий

UI настроек → слой репозитория → DataStore → поток состояния. Запуск плеера → чтение настроек из репозитория → маршрутизатор принимает единое решение (route + причина + эффективный режим стерео) → плеер применяет решение без правок. На уровне диагностики вся пара «route + причина» логируется одним вызовом, чтобы исключить расхождение полей.

### 5.3 Точки расширяемости

- Добавление новых маршрутов (например, новый тип иммерсив-сцены) должно требовать минимального изменения маршрутизатора, без распространения новых веток в плеер.
- Тест-сьют пишется так, чтобы добавление нового стерео-формата автоматически попадало в матрицу.

1. **Источник рассинхрона маршрут vs reason.**
   - **Вопрос:** ветка «авто-иммерсив отключён» возвращает «фолбэк на панель», но фактический маршрут — иммерсив. Где переписывается?
   - **Варианты:** (a) условие в плеере вне маршрутизатора форсит иммерсив; (b) развёрнутый APK скомпилирован из устаревшего исходника (косвенный признак — наличие в логе строки причины, отсутствующей в текущем исходнике); (c) маршрутизатор имеет дублирующее решение в другом месте кода.
   - **Нужно выяснить:** сличить исходник на момент сборки артефакта с текущим main; пройтись грепом по присвоениям маршрута; проверить, нет ли второго маршрутизатора.

2. **Корректность поведения для смешанных сценариев.**
   - **Вопрос:** какой ожидается маршрут для VR-фото при выключенном тумблере (фолбэк на панель тоже допустим, или фото остаётся в иммерсив-просмотре)?
   - **Варианты:** «панель», «иммерсив», «как настроено отдельным переключателем».

   - **Нужно выяснить:** трассировка стека одного холостого вызова; решение — guard либо отвязка listener'а на время первоначальной отрисовки.

## 9. Архитектурные решения (ADR)

**ADR-1: Один источник истины для маршрута и причины.**
- **Решение:** маршрут запуска и текстовая причина формируются в одной точке (структуре решения маршрутизатора) и распространяются вместе. Никакой код после маршрутизатора не правит маршрут отдельно от причины.
- **Альтернативы:** (а) оставить как есть, добавив пост-валидатор, который сверяет route и reason — отвергнуто, потому что это лечит симптом, а не источник; (б) разнести решение на два этапа с явным «contract verification» — отвергнуто как избыточное усложнение.
- **Почему:** наблюдаемый баг возможен только при наличии двух точек присвоения маршрута. Жёсткая инвариантность поля исключает класс ошибок целиком.

**ADR-2: No-op-защита на уровне репозитория настроек.**
- **Решение:** запись новых значений настроек в DataStore выполняется только при отличии от текущего состояния.
- **Альтернативы:** (а) починить только UI-слой, чтобы не вызывать сохранение при инициализации — отвергнуто, потому что не предотвращает других путей шумной записи; (б) принять холостые записи как «безопасные» — отвергнуто, потому что они засоряют диагностику и могут маскировать настоящие гонки.
- **Почему:** репозиторий — единственная точка, обязанная знать текущее состояние; защита там автоматически ловит все upstream-источники.

## 11. Критерии готовности (strategic-level)

1. На устройстве с выключенным «Авто-вход в иммерсив» 360-видео и стереофайлы открываются на плоской панели; ни одна тестовая дорожка не уходит в иммерсив без ручной команды.
2. На устройстве с включённым «Авто-вход в иммерсив» все ранее работавшие сценарии стерео-просмотра автоматически переходят в иммерсив без регрессии.
3. В логе любой ветки маршрутизатора пара «route + reason» консистентна; ручная инспекция 30 решений подряд не находит расхождений.
4. Открытие экрана настроек не порождает записи «NO fields changed — possible no-op write» в логе.
5. Новый тест-сьют в CI зелёный и покрывает все комбинации тумблера, типа содержимого и формата стерео; намеренно «сломанная» ветка маршрутизатора в pull-request падает в CI.
