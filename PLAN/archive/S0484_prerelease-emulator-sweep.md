## 1. Проблема

Pre-release проверка перед релизом сейчас выполняется руками по `dev/PRE_RELEASE_MANUAL_TESTS.md` - долго, неповторяемо, легко пропустить регрессию. Нет единого сквозного прогона, который на эмуляторе чисто ставит сборку, поднимает все типы ресурсов, гоняет основные пользовательские сценарии и выносит машинный вердикт go/no-go.

Инструменты есть по отдельности (посев медиа, ad-hoc adb, device-test скиллы, анализ логов, релизный пайплайн), но сценарий и критерии прохождения держатся в голове человека. Нужен скилл `/spec-prerelease`, который связывает их в один автоматический gated прогон.

---

## 2. Цели

1. Один скилл `/spec-prerelease` выполняет сквозной pre-release сценарий на эмуляторе без участия человека вплоть до вердикта.
2. Чистое окружение: удаление прежней сборки, установка standard debug с нуля, посев тест-медиа при его отсутствии.
3. Проверка трёх классов ресурсов: локальный, сетевой, SFTP.
4. Непрерывный сбор и анализ логов плюс скриншоты на ключевых чек-поинтах.
5. Замеры перф-метрик с порогами как часть критерия прохождения.
6. При PASS - стоп с отчётом и предложением запустить `/skill-release` (релиз только по подтверждению владельца).
7. При FAIL - авто-создание `/spec-draft` на новые дефекты (с дедупом) и обновление статусов ожидающих тестирования тикетов.

**Non-goals:**

- Не запускает релиз автоматически - финальное go/no-go за владельцем.
- Не покрывает non-standard флейворы (vr/noLegal/lite/photos/legacy) в первой итерации.
- Не заменяет ручной QA на реальных устройствах - это автоматический smoke перед релизом, не полное покрытие.
- Не вводит тест-харнес внутрь приложения.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Переиспользовать существующие скрипты (посев тест-медиа, ad-hoc adb, проверка готовности устройства) и скиллы (device-test, sweep, анализ логов, релиз).
2. Идемпотентность: повторный запуск не ломает состояние и доводит окружение до чистого старта.
3. Артефакты прогона (логи, скриншоты, метрики, итоговый отчёт) складываются в `temp/` с таймстампом.
4. Прогон параметризуется целевым эмулятором (несколько подключённых устройств - выбор по id).

### 3.2 Жёсткие ограничения

- **Flavor:** только standard (debug). Прочие флейворы вне объёма первой итерации.
- **API level:** эмулятор с minSdk standard (26+); конкретный уровень API эмулятора - параметр прогона.
- **Wear OS:** не затрагивается.
- **Производительность:** вводятся пороги (холодный старт, скролл списков, открытие плеера, открытие сетевого/SFTP ресурса); пороги - часть PASS-гейта, точные значения уточняются research item 1.
- **Совместимость данных:** настройки приложения меняются программно поверх чистой установки; прогон не должен зависеть от прежнего состояния устройства.
- **Локализация:** скилл - инструментарий разработчика, пользовательских строк не вводит; логи и отчёты EN-only.
- **Сеть/SFTP:** используется существующая готовая инфраструктура тест-серверов; эндпоинты и креды берутся из предопределённых ресурсов приложения (конфигурация `one-click` ресурсов), не дублируются и не хардкодятся в скилле. Доступность каждого эндпоинта с эмулятора проверяется пред-шагом - часть адресов в LAN-сегменте может быть недостижима из песочницы эмулятора.

### 3.3 Owner inputs (Approval gate)

- **Performance budget:** стартовый набор порогов - холодный старт ≤ 3 с, скролл списка без видимых фризов (типовое время кадра ≤ 32 мс), открытие плеера ≤ 2 с до первого кадра, открытие сетевого/SFTP листинга ≤ 5 с; точные значения уточняются research item 1 перед impl. Несоблюдение бюджета = FAIL.
- **Validation level:** прогон на эмуляторе standard debug; вердикт сводится из трёх источников - отсутствие ERROR/FATAL/ANR/краш в логах, попадание в перф-пороги, скриншот-проверка ключевых экранов.

- **Related tickets:** none (композиционная зависимость от `/skill-release`, `/spec-draft`, `/spec-test-device`, `/spec-sweep`, без блокировки).

## 4. Контекст текущей архитектуры

Существует ручной план `dev/PRE_RELEASE_MANUAL_TESTS.md` и набор точечных инструментов: посев структурированного тест-медиа на устройство, ad-hoc adb-обёртка, проверка готовности устройства, прогон Maestro-флоу. Поверх них есть device-test скиллы (одиночный прогон и batch-sweep по ожидающим тестирования тикетам), скилл анализа логов и релизный пайплайн. Источники тест-окружения уже готовы: скрипт посева структурированного тест-медиа и конфигурация предопределённых (`one-click`) ресурсов с именованными тест-ресурсами всех типов - локальный, SMB, SFTP, FTP - и кредами, плюс блок integration-test инструкций.

Чего нет: оркестратора, который связывает эти блоки в один сквозной прогон, ведёт сценарий по чек-поинтам, агрегирует наблюдения в машинный PASS/FAIL и ветвится на релиз либо на работу с каталогом тикетов. Сейчас связку и критерии держит человек, поэтому проверка не воспроизводима и не масштабируется.

---

## 5. Предлагаемый подход

Новый скилл-оркестратор поверх существующих инструментов. Скилл не вносит runtime-кода в приложение - он управляет эмулятором, собирает наблюдения и выносит вердикт.

### 5.1 Основные столпы / модули

**Подготовка окружения.** Выбор целевого эмулятора, удаление прежней сборки при наличии, чистая установка standard debug, посев тест-медиа при его отсутствии, базовая верификация запуска по логам.

**Конфигурация и ресурсы.** Программное применение набора существенных настроек, создание и проверка трёх ресурсов - локального, сетевого, SFTP - из конфигурации инфраструктуры.

**Сценарный прогон.** Проигрывание файлов разных типов в приложении; закрытие; запуск standalone player для файла и переход из него в приложение; повторный вход в приложение без переустановки; скролл списков и проигрывание на сетевом ресурсе.

**Наблюдаемость.** Непрерывный сбор логов, скриншоты на чек-поинтах, перф-замеры на размеченных шагах.

**Вердикт и реакция.** Сведение наблюдений в PASS/FAIL. PASS → отчёт и предложение запустить релиз (стоп на go/no-go). FAIL → авто-создание `/spec-draft` на новые дефекты с дедупом плюс обновление статусов ожидающих тестирования тикетов.

### 5.2 Потоки данных и событий

Подготовка окружения → конфигурация настроек и ресурсов → сценарный прогон (UI-драйв) → сбор логов, скриншотов и метрик → агрегатор вердикта → ветвление PASS (отчёт + предложение релиза) либо FAIL (мутация каталога тикетов).

Прогресс сценария отслеживается по маркерам в логах, а не по фиксированным задержкам, чтобы прогон был устойчив к разной скорости эмуляторов.

### 5.3 Точки расширяемости

- Набор сценариев и чек-поинтов - декларативный список, расширяемый без переписывания оркестратора.
- Перф-пороги - конфигурация, не хардкод.
- Матрица флейворов заложена на расширение: standard в первой итерации, добавление non-standard позже без смены архитектуры скилла.
- Источник ресурсов (локальный/сетевой/SFTP) абстрагирован от конкретного сервера через конфигурацию инфраструктуры.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Сетевой/SFTP ресурс недоступен с эмулятора | Средняя | Ложный FAIL всего прогона | Проверка доступности эндпоинта пред-шагом; явный SKIP/блокер при недоступности вместо FAIL |
| Флак UI-драйв шагов из-за таймингов и разных эмуляторов | Высокая | Ложные FAIL | Ожидание по маркерам логов, а не фиксированные задержки; идемпотентные чек-поинты и ретраи |
| Ложный PASS - регрессия не замечена | Средняя | Плохой релиз | Строгий лог-вердикт + скриншот-проверка ключевых экранов + перф-пороги |
| Авто-мутация каталога плодит дубли тикетов | Средняя | Шум в каталоге | Обязательный дедуп по симптому перед `/spec-draft` |
| Авто-чейн в релиз при ложном PASS | Низкая | Необратимый плохой релиз | Стоп на go/no-go - релиз только по подтверждению владельца |

## 9. Архитектурные решения (ADR)

**ADR-1: Стоп на go/no-go вместо авто-релиза**

- **Решение:** при PASS скилл печатает вердикт и предлагает запустить `/skill-release`, но сам его не запускает.
- **Альтернативы:** полный авто-чейн pre-release → release.
- **Почему:** релиз необратим; даже при зелёном прогоне выпуск подтверждает человек.

**ADR-2: Композиция существующих инструментов, без кода в приложении**

- **Решение:** скилл оркеструет существующие скрипты и скиллы, не добавляя runtime-кода в app.
- **Альтернативы:** встроить тест-харнес внутрь приложения.
- **Почему:** pre-release проверка внешняя по отношению к продукту; не раздуваем APK и не тащим тест-логику в прод.

## 11. Критерии готовности (strategic-level)

1. `/spec-prerelease <emulator>` выполняет полный сценарий без ручного вмешательства вплоть до вердикта.
2. На чистом эмуляторе прежняя сборка удалена, поставлен standard debug, при отсутствии медиа выполнен посев.
3. Созданы и проверены три ресурса: локальный, сетевой, SFTP.
4. Прогнаны сценарии: проигрывание файлов разных типов, закрытие, standalone player и переход в приложение, повторный вход без переустановки, скролл списков и плеер на сетевом ресурсе.
5. На ключевых шагах собраны логи и скриншоты, замерены перф-метрики.
6. Вынесен машинный вердикт PASS/FAIL по логам и перф-порогам.
7. При PASS напечатан отчёт и предложение запустить `/skill-release` без авто-запуска.
8. При FAIL созданы `/spec-draft` на новые дефекты с дедупом и обновлены статусы ожидающих тестирования тикетов.
9. Артефакты прогона сохранены в `temp/` с таймстампом.
