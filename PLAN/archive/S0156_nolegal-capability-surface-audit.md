# Стратегическая спецификация: S0156 — глобальный аудит возможностей `noLegal`

**Ticket:** S0156
**Status:** Archived
**Priority:** 50
**Date:** 2026-05-11
**Tier:** 4 — Strategic
**Roadmap entry:** Ad-hoc — запрос 2026-05-11
**Tactical spec:** `PLAN/S0156_nolegal-capability-surface-audit/` (создаётся после первого завершённого аудиторского прохода и явного решения владельца, что накопленного объёма уже достаточно для декомпозиции)

> **Scope:** STRATEGIC. Цели, границы, исследовательские вопросы и критерии отбора. Без имён классов, путей, лимитов строк, миграций Room, модулей Hilt.

---

## 1. Проблема

В проекте уже существует `noLegal`-flavor как sideload-only зона для возможностей, которые нежелательны или непроходимы для публичных магазинов из-за правил распространения, лицензионных ограничений, патентных рисков, store policy или избыточно тяжёлого runtime. Сейчас это покрытие появлялось точечно и реактивно: под конкретную задачу, а не как системный аудит всего продукта.

Из-за этого нет единой карты возможностей вида «что уже есть», «что технически возможно», «что запрещено для market-flavors», «что допустимо только в личной sideload-only сборке владельца», «что принципиально нельзя делать даже там». В результате потенциальные улучшения уровня `yt-dlp`, дополнительных OCR-движков, расширенных кодеков, format-support, site-specific extractors и других sideload-only расширений не инвентаризированы и не приоритизированы.

Нужна отдельная research-спека, которая не внедряет функционал, а создаёт полную карту потенциальных `noLegal`-улучшений по всему приложению и определяет границы допустимого.

---

## 2. Цели

1. Провести полный аудит всего функционального surface приложения и выявить возможности, которые можно улучшить только в `noLegal`-сборке.
2. Разделить найденные улучшения по типу ограничения: store-policy, лицензия, патент/redistribution, тяжёлый runtime, закрытый SDK, size/perf budget, security/privacy risk.
3. Зафиксировать, какие улучшения допустимы для личной sideload-only сборки владельца, а какие остаются вне границ даже такого канала.
4. Сформировать backlog follow-up направлений: URL/download extraction, OCR/translation, codecs/decoders, containers, subtitle/transcription, AI-assisted features, VR/media pipelines, network/cloud integrations и другие найденные категории.
5. Сохранить compile-time и дистрибуционную изоляцию `noLegal` относительно всех market-flavors.
6. Подготовить основу для следующих узких спецификаций, каждая из которых уже будет разбирать один конкретный cluster улучшений.

**Non-goals:**

- Реализация любого нового `noLegal`-функционала в рамках этой спеки.
- Обход DRM, подписок, paywall, приватности, CAPTCHA-защит или доступа к контенту, недоступному самому пользователю.
- Любые действия, нарушающие закон, условия владения контентом или права третьих лиц.
- Публикация `noLegal` в Google Play, Meta Horizon Store или другом публичном магазине.
- Превращение `noLegal` в «свалку всего спорного» без классификации, приоритета и границ.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Исследование должно смотреть на весь продукт, а не только на URL-downloader или media player.
2. В аудит должны войти как минимум примеры класса `yt-dlp`, новые OCR-подходы, расширенная поддержка видеоформатов и другие подобные sideload-only улучшения.
3. Результат должен явно показывать не только «что можно добавить», но и «почему это нельзя класть в market-build».
4. Открытые вопросы должны остаться в самой стратегической спеке, а не потеряться в чате.
5. Конечный результат должен разложить весь найденный surface по следующим группам: можно исследовать дальше, можно проектировать, нельзя делать, пока не решён policy/licensing вопрос.
6. Исследование должно идти по принципу «максимум полезных функций»: bundled-библиотеки, sidecar-бинарники, external bridges и другие тяжёлые решения допустимы хотя бы на уровне ресёрча, если они реально расширяют возможности `noLegal`.
7. Если текущая реализация уже работает хорошо, её не нужно менять ради самой замены; замена оправдана только при реальном приросте функциональности, покрытия форматов или качества.
8. Целевая capability-topology должна быть такой: VR = standard + VR-возможности; `noLegal` = VR + непубликуемые sideload-only возможности.
9. Публичные docs и feature inventory должны молчать о `noLegal`; отдельная документация для него допустима только как локальная, непубличная и исключённая из публичного репозитория.

### 3.2 Жёсткие ограничения

- **Flavor:** все новые capability-кандидаты рассматриваются только как `noLegal`-scope, пока отдельным решением не доказано иное. Целевая модель на текущем этапе — один `noLegal` без разветвлений, логически стоящий выше VR capability-surface.
- **Distribution:** `noLegal` рассматривается как личная sideload-only сборка владельца, не предназначенная для публичных магазинов и не заявляемая как store-safe variant.
- **Market isolation:** никакие `noLegal`-зависимости, class names, runtime helpers, notices или capability hints не должны утекать в market-flavors.
- **Правовая граница:** исследование не должно заходить в обход DRM, кражу контента, нелегальное получение доступа, credential abuse, reverse-engineered обход платных ограничений, доступ к чужому контенту без права доступа или другой контур с вероятной криминальной ответственностью.
- **Лицензионная граница:** любое улучшение обязано быть классифицировано по типу лицензии и последствиям для redistribution. Публичная доступность кода в интернете считается сигналом для ресёрча, но не автоматическим разрешением на включение в продукт.
- **Security/privacy:** исследование обязано отдельно помечать кандидатов, которые несут повышенный риск для учётных данных, cookies, токенов, локальной приватности или supply-chain безопасности.
- **API level:** текущая базовая гипотеза — `noLegal` повторяет обычный `noLegal` baseline без отдельного legacy-варианта, пока ресёрч не докажет необходимость дополнительных flavor forks.
- **Локализация:** сама эта research-спека не требует пользовательских строк; любые follow-up реализации по-прежнему обязаны соблюдать EN/RU/UK parity.
- **Communication policy:** если по итогам follow-up задач появятся новые user-visible strings, они обязаны проходить через `docs/COMMUNICATION_POLICY.md` и его зеркала.
- **Repo publication:** локальные `noLegal`-docs и нераспространяемые third-party артефакты могут жить вне публичного репозитория или в ignore-контуре; публичный форк проекта не обязан уметь собирать `noLegal`.

## 4. Контекст текущей архитектуры

В проекте уже есть compile-time паттерн изоляции дистрибуционно-чувствительного функционала по flavor-границе. Этот паттерн уже применён как минимум в двух формах: отдельный sideload-only канал для VR-сборки и отдельный `noLegal`-канал для части URL-download возможностей. Это доказывает, что техническая основа для жёсткой изоляции уже существует.

При этом текущий `noLegal` покрывает только узкий фрагмент общего продукта: site-specific extraction и связанный лицензионный disclosure. В shared-части приложения уже есть дополнительные жёсткие границы, которые потенциально важны для sideload-only расширений: гибридный OCR stack, ограниченная remux/mux-compatible codec surface, build-time decoder selection, store-sensitive distribution decisions для DTS и смежных расширений. Но общего аудита, который бы проходил по всем feature areas и искал `noLegal`-дельту, сейчас нет.

Именно поэтому нужен отдельный research-ticket уровня всего продукта: не о конкретной библиотеке, а о полной capability-surface карте.

### Реализованный S0117-baseline (справка для аудита)

S0117 (`url-media-downloader-nolegal-flavor`, Archived) был первым узким vertical slice. Ниже зафиксированы факты текущей реализации, которые аудит должен принять как данность, а не переизобретать.

- **Flavor:** `noLegal` productFlavor в `app_v2/build.gradle.kts`; `applicationIdSuffix = ".nolegal"`, `versionNameSuffix = "-NoLegal"`, `BuildConfig.IS_NO_LEGAL_FLAVOR = true`.
- **SourceSet:** `src/noLegal/java/` — compile-time isolated, market-flavors не видят этот код.
- **Зависимость:** `noLegalImplementation("com.github.TeamNewPipe:NewPipeExtractor:v0.24.0")` — GPL v3, только в `noLegal`.
- **Site-Resolver (Столп H):** `NewPipeSiteExtractionStrategy` регистрируется первой в `LinkExtractionRegistry`; нераспознанный URL прозрачно падает в generic-цепочку S0116.
- **Album batch:** `NewPipeSiteExtractionStrategy.MAX_BATCH_ITEMS = 30`; playlist → `OpenResult.Batch`; batch coordinator разворачивает в N последовательных операций `LinkDownloadWriter`.
- **GPL notice:** секция в `OpenSourceLicensesFragment`, видна только при `IS_NO_LEGAL_FLAVOR == true`.
- **Строки:** 9 ключей `s0117_*` в EN/RU/UK — полный paritety.
- **Открытый gap:** lint-rule, запрещающая `import org.schabi.newpipe.*` вне `src/noLegal/`, не реализована (см. §6 вопрос 11).

## 5. Предлагаемый подход

Эта спека вводит не новую runtime-архитектуру приложения, а архитектуру исследования. Результатом должен стать capability-audit, который проходит по каждому крупному feature area приложения, ищет потенциальное sideload-only усиление, классифицирует blocker и выдаёт решение: rejected, deferred, follow-up spec, direct candidate for design.

### 5.1 Основные столпы / модули

**Столп A — Taxonomy и decision policy для `noLegal`.**

- Нужно ввести единый словарь ограничений: store-policy, redistribution-license, patent/codec-risk, heavy-runtime, external-binary, privacy-risk, security-risk, maintenance-risk.
- Каждый найденный capability-кандидат обязан получить ровно один primary blocker и, при необходимости, secondary blocker.
- Для каждого blocker-типа должна быть определена decision rule: допустимо к дальнейшему проектированию, допустимо только после отдельного legal/policy review, запрещено даже для `noLegal`, или требуется отдельный fork/канал распространения.

**Столп B — Полный feature-surface audit.**

- Аудит проходит по всем крупным областям продукта: resource/source management, media browsing, file operations, viewers/players, OCR/translation, network/cloud, VR, widgets, settings/search, background/system features, Wear OS companion и другим доступным разделам.
- Для каждой области фиксируется: текущее состояние, возможная `noLegal`-дельта, тип blocker-а, rough expected value, rough complexity, rough risk.
- Задача этого столпа — не придумать «что угодно», а пройти весь уже существующий продукт и найти реальные улучшения, которые сейчас отсутствуют по внешним ограничениям, а не по отсутствию идеи.

**Столп C — Кластеры sideload-only возможностей.**

- Исследование обязано отдельно искать как минимум следующие семейства кандидатов:
  - site-specific extractors и downloader runtimes (`yt-dlp`-класс, NewPipe-подобные решения, album/channel/feed expansion);
  - расширенные OCR/translation engines и модели;
  - codec/decoder/container/transcode расширения;
  - тяжёлые native/runtime-зависимости, нежелательные для store-distribution;
  - экспериментальные media/AI/automation/VR-интеграции, если их основной blocker именно distribution/policy, а не отсутствие продуктовой ценности.
- Для каждого семейства нужно отдельно оценивать не только добавление новой подсистемы, но и осмысленную замену уже существующей, если новая база реально даёт больше форматов, лучшее качество или более широкий capability-surface.
- При этом каждое семейство должно пройти через фильтр допустимости: не всё технически возможное автоматически попадает в backlog.

**Столп D — Output artifacts и follow-up decomposition.**

- Выходом этого ресёрча должен стать capability matrix, risk matrix и список follow-up спецификаций.
- Один большой список улучшений недостаточен; нужен разбор по кластерам, чтобы после исследования можно было открывать узкие спеки без переисследования всего поля.
- Отдельно должен существовать rejected-list: идеи, которые были рассмотрены, но намеренно исключены из дальнейшей работы.
- Исследование допускает несколько итераций накопления. Оно завершается не по заранее фиксированному числу artefact-ов, а по явному решению владельца, что покрытие уже достаточно полное.
- **Правило именования follow-up спек:** каждая дочерняя спека, рождённая из S0156, обязана содержать `nolegal` в slug файла (`Sxxxx_nolegal-<cluster>.md`) и иметь в заголовочном блоке строку `**Epic:** S0156`. Это обеспечивает трассируемость при навигации по каталогу и grep.

**Столп E — Стартовые поисковые направления первого прохода.**

- **Изображения:** искать поддержку новых графических форматов, улучшенные decoder/encoder chain, продвинутые механизмы редакции, восстановления, конвертации, разметки и пакетной обработки.
- **Видео:** искать поддержку новых контейнеров и кодеков, улучшения viewer experience, дополнительные аудиодорожки, субтитры, расширенные механизмы выбора/обработки дорожек и другие улучшения playback surface.
- **Музыка и аудио:** искать поддержку новых аудиоформатов, улучшенное распознавание музыки и тегов, построение активной анимации по реально текущему аудиосигналу, а также полезные audio-edit сценарии вроде вырезания фрагмента под рингтон.
- **Документы:** искать чтение новых форматов документов, расширение export/import surface и механизмы редактирования закрытых или частично закрытых форматов, включая PDF, в пределах допустимых лицензий и runtime-моделей.
- **Архивы:** искать поддержку дополнительных архивных форматов, включая как минимум `7z` и `rar`, а также дополнительные сценарии упаковки, распаковки, просмотра содержимого и выборочного извлечения.
- **Сеть:** искать более стабильные соединения, улучшенные reconnect/retry политики, расширенное сканирование сетевых устройств и ресурсов, а также дополнительную диагностику доступности и проблем транспортного слоя.
- **Интернет-контент:** искать механизмы локального сохранения сетевого контента, который уже правомерно доступен пользователю, в том числе при сложной доставке, нестабильных transport/session-сценариях и ограничениях generic pipeline. DRM, неавторизованный доступ и обход чужих защит по-прежнему вне scope.
- **P2P и децентрализованные сети:** искать возможности загрузки и раздачи медиаконтента через BitTorrent (torrent, magnet-ссылки), IPFS и другие протоколы децентрализованного обмена, которые часто блокируются или пессимизируются политиками публичных магазинов.
- **Heavy-AI и локальные ML-модели:** искать варианты интеграции тяжёлых локальных нейросетей (например, полные версии Whisper для транскрибации, vision-модели для тегирования и поиска), которые радикально повышают качество автономного распознавания контента, но неприменимы в market-build из-за гигантского size/perf budget.
- **Продвинутый Scraping и Headless-движки:** искать сценарии применения headless-браузеров (stealth WebView, GeckoView) или внедрения тяжеловесных JS-окружений для извлечения легально доступного контента со сложных SPA-сайтов, где классические URL-экстракторы не справляются.
- **APK install flow из Browse:** искать возможность запускать user-confirmed установку сторонних APK напрямую из Browse activity в `noLegal`, включая корректный handoff в `PackageInstaller`, `FileProvider`/URI-grants, UX для trusted-source подтверждения, переход в системное разрешение unknown app sources и жёсткий запрет на silent install, hidden behavior и любые обходы системной модели безопасности.
- **Интеграция с ОС (System / Root / Shizuku):** искать power-user сценарии, такие как глубокий фоновый перехват буфера обмена, чтение недоступных обычным приложениям медиа-кэшей (при наличии прав) и создание агрессивных фоновых демонов для автосортировки, обходящих строгие лимиты магазинов на background execution.
- **Защищённые медиа-контейнеры (Vaults / Steganography):** искать механизмы скрытия файлов, создания защищённых томов, криптографических контейнеров или применения стеганографии, внедрение которых может нарушать политики публичных магазинов относительно «hidden behavior» или обхода модерации контента.
- **Локальные сети (NAS / SMB / FTP) с copyleft-лицензиями:** искать решения для работы со сложными сетевыми файловыми системами (расширенный SMB, NFS), где самые качественные библиотеки могут распространяться под строгими лицензиями вроде GPLv3, несовместимыми с проприетарной маркет-сборкой.
- **Подкасты, аудиокниги и RSS-медиа:** искать механизмы агрегации RSS/Atom/podcast-фидов, автоматической загрузки выпусков по расписанию, навигации по главам (OPDS, chapter markers) и управления историей прослушивания, которые систематически ограничиваются store-политиками как «автоматизированная фоновая загрузка» или требуют библиотек с ограничительными redistribution-условиями.
- **IPTV, live-потоки и веб-радио:** искать воспроизведение и запись live-контента по HLS, DASH, RTSP, RTMP, MPEG-TS, поддержку форматов IPTV-плейлистов (M3U, XSPF, XMLTV EPG) и интернет-радиопотоков, где полноценные реализации часто требуют copyleft-компонентов для demux/decrypt или патентно-чувствительных транспортных слоёв.
- **RAW-форматы камеры и расширенный HDR:** искать полноценный decode производительских RAW-форматов (CR2, NEF, ARW, ORF, RAF и другие) через LibRaw и аналоги; искать обработку HDR/HLG/PQ-содержимого, 16-bit pipeline и tone-mapping для вывода на SDR-дисплей, где качественные нативные реализации идут с LGPL- или GPL-компонентами, нежелательными в store-build.
- **Комиксы, manga и специализированные e-book форматы:** искать поддержку CBR/CBZ (RAR-based архивы с redistribution ограничениями), MOBI/AZW (patent-sensitive parsing), DjVu (специфическая лицензия декодера djvulibre), CHM и других форматов, где лицензионные условия декодеров или redistribution-ограничения форматов создают препятствия для market-build.
- **Медиасервер на устройстве (DLNA / UPnP / Casting):** искать возможности раздачи контента с устройства на Smart TV, игровые консоли и другие медиаплееры по DLNA/UPnP и Casting-протоколам, где полноценные серверные библиотеки (Cling и аналоги) распространяются под LGPL/GPL и несут нежелательный redistribution-риск для market-build.
- **Синхронизированные тексты и расширенные субтитры:** искать поддержку LRC/Enhanced LRC для синхронизации текста с аудио, CDG karaoke (исторически патентно-чувствительный формат), расширенного рендеринга SSA/ASS с цветным текстом, анимацией и position-override, а также burn-in pipeline для экспорта с встроенными субтитрами.
- **Акустический фингерпринтинг, метаобогащение и перцептивная дедупликация:** искать интеграцию AcoustID/Chromaprint для автоматической идентификации аудио и обогащения метаданных через MusicBrainz; искать perceptual hash механизмы (pHash, dhash, SSIM) для обнаружения визуально идентичных или похожих изображений и видео в больших библиотеках, где нативные и FFT-интенсивные реализации нежелательны в лёгком store-build.
- **Пространственное аудио и высококачественный DSP:** искать поддержку бинаурального рендеринга (HRTF), Hi-Res и lossless spatial форматов (DSD, SACD, MQA), а также полноценное декодирование Dolby TrueHD/Atmos и DTS-HD/X, где ключевые декодеры либо патентно защищены, либо недопустимы для redistribution, либо несут тяжёлый native runtime, неприемлемый в store-build.
- **Интеграция с self-hosted медиасерверами:** искать полноценный client для Jellyfin (GPL), Plex (proprietary API), Emby, Navidrome, Audiobookshelf и подобных локальных бэкендов, где API-клиент может содержать GPL-производный код или требовать лицензионных соглашений, несовместимых с условиями публичного store-build или нежелательных в открытом repo.
- **Глубокая автоматизация и межсистемное взаимодействие:** искать plugin API и deep hook интеграцию с системами автоматизации (Tasker, Automate, MacroDroid), агрессивный мониторинг уведомлений для автоматического захвата медиаконтента, scheduling-демоны и accessibility-service hooks, которые систематически ограничиваются или пессимизируются store-политиками на background execution и system-level доступ.

**Столп F — Формат и правила research-output документов.**

По каждому направлению из Столпа E создаётся отдельный независимый документ. Документы живут в `PLAN/S0156_nolegal-capability-surface-audit/`. Каждый документ самодостаточен: из него можно открыть follow-up спеку, не читая остальные.

Обязательная структура каждого документа:

- **Что найдено** — конкретные библиотеки, инструменты, существующие реализации; текущее состояние приложения по этому направлению; в чём именно `noLegal`-дельта и почему она не входит в market-build.
- **Просто и быстро** — кандидаты с минимальным integration cost: добавить зависимость, написать thin wrapper, лицензия чистая или допустимая для sideload. Каждый пункт содержит название решения, тип лицензии и краткую оценку объёма.
- **Сложно но возможно** — кандидаты с известным путём реализации, но значительным объёмом: нативный слой, сложная интеграция, нетривиальный migration path, неочевидный licensing workaround. Каждый пункт содержит описание пути и type blocker-а.
- **Фантастика, но хочется** — кандидаты технически достижимые, но требующие героических усилий, нестабильного внешнего компонента, неразрешённого policy вопроса или зависимости от ещё не существующей инфраструктуры.
- **Блокеры** — список с типом каждого: `store-policy`, `redistribution-license`, `patent`, `heavy-runtime`, `external-binary`, `privacy-risk`, `security-risk`, `maintenance-risk`. Каждый блокер указывает конкретную причину, а не общую категорию.
- **Потенциальные follow-up спеки** — 1–3 кандидата на узкие спецификации, которые могут родиться из этого документа; без id (id присваивается только при реальном открытии через `next-id.ps1`).

Дополнительные правила:

- **Именование follow-up спеки (обязательно):** slug файла должен содержать `nolegal` → `Sxxxx_nolegal-<cluster>.md`; в заголовочном блоке спеки обязательна строка `**Epic:** S0156`. Без этих двух маркеров спека не считается корректно связанной с этим эпиком.
- Документ не имеет статуса «выполнен» — он накапливает находки итеративно.
- Новая итерация ресёрча дописывает в существующий документ, а не создаёт новый.
- Каждое добавление находок сопровождается датой в заголовке раздела или комментарием перед абзацем.
- Рекомендации внутри группы упорядочены по убыванию ожидаемой ценности, а не по дате добавления.
- Из одного документа может родиться несколько follow-up спек — по одной на каждый самостоятельный кластер.
- Follow-up спека ссылается на этот документ как на источник классификации; документ не пересматривает границы допустимости — для этого есть Столп A.

### 5.2 Потоки данных и событий

Функциональная область продукта → поиск возможной `noLegal`-дельты → определение primary blocker → оценка личной sideload-only допустимости → решение:

- `Rejected` — вне правовых, этических, security или support-границ;
- `Deferred` — идея допустима, но преждевременна или упирается в незакрытый внешний вопрос;
- `Follow-up spec` — идея признана валидной и требует отдельной narrow spec;
- `Needs policy decision` — идея технически ценна, но блокируется неуточнённым product/legal решением.

Все результаты собираются в единый audit-output, который затем становится источником для следующих спецификаций.

### 5.3 Точки расширяемости

- Taxonomy должна позволять добавлять новые blocker-классы без переписывания всей матрицы.
- Аудит должен поддерживать поэтапное пополнение новыми feature areas, если позже в продукте появятся новые подсистемы.
- Follow-up спеки должны ссылаться на эту research-спеку как на источник классификации и допустимости, а не формулировать границы заново.

## 6. Открытые вопросы / Research items

1. **Что именно считается `noLegal`-кандидатом**
   - **Вопрос:** включаем только то, что блокируется политиками магазинов и redistribution-лицензиями, или также всё, что не подходит market-build из-за размера, тяжёлого runtime, приватных SDK, sidecar-бинарей и подобного?
   - **Решение:** scope широкий. В аудит входят не только случаи store-policy и redistribution-license, но и всё, что не подходит market-build из-за размера, тяжёлого runtime, приватных SDK, sidecar-бинарей, external-tool bridges и сходных ограничений.
   - **Статус:** Resolved

2. **Какой уровень правовой осторожности обязателен даже внутри `noLegal`**
   - **Вопрос:** где проходит граница между «не проходит публичный store» и «вообще недопустимо даже для личной сборки владельца»?
   - **Решение:** базовая модель — личная локальная sideload-only сборка владельца. При этом из scope исключаются контуры с вероятной криминальной ответственностью, обход DRM, обход платных ограничений, credential abuse, кража контента и неавторизованный доступ. Публичная доступность кода в интернете считается поводом изучить решение, но не считается единственным юридическим критерием его допустимости.
   - **Статус:** Resolved

3. **Какие классы лицензий считаются допустимыми для дальнейшего исследования**
   - **Вопрос:** рассматриваем только GPL-подобные случаи, или также AGPL, SSPL, source-available, закрытые SDK с особыми redistribution terms и патентно-чувствительные media stacks?
   - **Решение:** аудит не ограничивается фиксированным списком буквенных лицензий. Любая публично доступная реализация, библиотека, спецификация или reference-код может быть рассмотрена как технический кандидат или reference point.
   - **Ограничение:** переход от ресёрча к внедрению всё равно требует классификации redistribution-условий и publication-risk.
   - **Статус:** Resolved

4. **Разрешены ли sidecar runtime и внешние исполняемые компоненты**
   - **Вопрос:** можно ли исследовать `yt-dlp`-класс решений только как bundled library, или также как sidecar binary, embedded interpreter, external process, termux-like companion и подобные контуры?
   - **Решение:** bundled-библиотеки, sidecar-бинарники, embedded interpreters и external-tool bridges разрешены как объекты ресёрча.
   - **Правило замены:** если существующая реализация уже работает хорошо, её не меняем ради самой замены. Замена оправдана только при реальном расширении функций, покрытия форматов или качества.
   - **Статус:** Resolved

5. **Граница codec/format расширений**
   - **Вопрос:** исследование должно смотреть только на дополнительные decoders и demuxers, или также на transcode/remux pipelines, software conversion, subtitle burn-in, audio extraction и другие media-processing улучшения?
   - **Решение:** scope максимально широкий по media/document/network направлению. В audit входят decoder/demux/remux/transcode/conversion/subtitle/extraction и другие полезные улучшения для медиафайлов, документов, сетевой работы и смежных сценариев.
   - **Статус:** Resolved

6. **Граница OCR/AI-ветки**
   - **Вопрос:** ограничиваемся OCR и переводом, или также включаем transcription, caption generation, handwriting OCR, layout OCR, detector models, LLM-assisted extraction и смежные AI-функции?
   - **Решение:** OCR/translation остаётся priority-example, в частности улучшение кириллического OCR и связанных ограничений. Audit не ограничивается только им и может включать смежные AI-assisted media/document capabilities, если их blocker лежит в store/policy/runtime плоскости и они реально полезны продукту.
   - **Статус:** Resolved

7. **Какие service-specific интеграции допустимы к рассмотрению**
   - **Вопрос:** рассматриваем только доступ к контенту, который уже доступен пользователю через его собственную авторизацию, или также anonymous public-page extraction, album/channel/feed expansion и batch-операции?
   - **Решение:** в ресёрч входят auth-bound и public-page сценарии, а также album/channel/feed/batch expansion, если resulting media уже доступно пользователю по его правам или является публично доступным.
   - **Ограничение:** неавторизованный доступ, кража контента и обход ограничений остаются вне scope.
   - **Статус:** Resolved

8. **Остаётся ли topology ровно с одним `noLegal` flavor**
   - **Вопрос:** исследование должно предполагать только единый `noLegal`, или нужно заранее учитывать возможные forks вроде `legacy-noLegal`, `vr-noLegal`, отдельный desktop-like sideload channel и подобные разветвления?
   - **Решение:** остаётся один `noLegal` без разветвлений.
   - **Target topology:** capability-wise он стоит выше VR: `VR = standard + VR-возможности`; `noLegal = VR + новые непубликуемые sideload-only возможности`.
   - **Build topology resolution (2026-05-12):** реализуется единым APK через split ABI filters — `ndk.abiFilters` включает все 4 ABI (`arm64-v8a`, `armeabi-v7a`, `x86`, `x86_64`), APK устанавливается на любое устройство; `externalNativeBuild.cmake.abiFilters` = `arm64-v8a`, OpenXR native bridge компилируется только для Quest slice. На смартфонах с non-arm64 или без OpenXR runtime `VrPlayerActivity` обязан реализовать graceful fallback на `PlayerActivity` — смартфон получает `standard + noLegal` без падения. `noLegal` добавляется в `build-and-push-all.ps1` (debug + release). CMake revision bump: `-DFMS_BUILD_REVISION=4` для инвалидации stale cmake cache при первой noLegal нативной сборке. См. ADR-8.
   - **Статус:** Resolved

9. **Как документировать `noLegal` после появления реальных capabilities**
   - **Вопрос:** сохраняется ли публичная тишина в `docs/FEATURES*.md`, а все `noLegal`-возможности живут только во внутренней или sideload-only документации?
   - **Решение:** публичная тишина сохраняется. `noLegal` не упоминается в публичной документации и feature inventory.
   - **Documentation policy:** для `noLegal` допускается отдельная локальная sideload-only документация, исключённая из публичного репозитория.
   - **Repo policy:** нераспространяемые third-party артефакты и фрагменты чужого кода, нужные только для `noLegal`, могут храниться в локальном ignore-контуре. Публичный форк проекта не обязан собирать `noLegal`.
   - **Статус:** Resolved

10. **Какой формат итогового output обязателен у этого ресёрча**
   - **Вопрос:** достаточно одной umbrella-спеки с capability matrix, или нужно сразу создать набор дочерних follow-up spec tickets по ключевым кластерам?
   - **Owner decision (2026-06-14):** накопленного объёма уже достаточно. Обязательный output этого эпика = umbrella-спека S0156 + набор per-direction research-документов в `PLAN/S0156_nolegal-capability-surface-audit/` + уже рождённые из них узкие follow-up спеки.
   - **Правило закрытия:** S0156 не остаётся открытой до завершения каждого дочернего тикета. После первого завершённого audit pass новые находки больше не накапливаются в этой umbrella-спеке; дальнейшая работа идёт только в дочерних спеках или в новых эпиках.
   - **Статус:** Resolved

11. **Lint-rule для изоляции NewPipe-импортов (gap из S0117 §11.10)**
   - **Вопрос:** критерий §11.10 S0117 требовал Android lint-rule, которая запрещает `import org.schabi.newpipe.*` вне `src/noLegal/`, и делает CI красным при нарушении. Rule так и не была реализована — есть только compile-time sourceSet-изоляция, но нет явного lint-сигнала.
   - **Что нужно решить:** добавить dedicated source-set/compliance guard до или в рамках отдельной future implementation спеки, если next round рефакторов снова затронет `NewPipe`-зону.
   - **Статус:** Deferred — follow-up hygiene item, не блокирует закрытие и архивирование umbrella-аудита S0156

12. **Канал распространения sideload APK (deferred из S0117 §6.4)**
   - **Вопрос:** где публикуется `noLegal` APK — собственный сайт, GitHub Releases, F-Droid, или только локальная раздача?
   - **Последствие:** выбор канала влияет на update-механизм, раскрытие возможностей в release notes и scope этого исследования.
   - **Статус:** Deferred — не блокирует текущий audit pass.

## 9. Архитектурные решения (ADR)

**ADR-1: сначала umbrella research, потом узкие capability-спеки**

- **Решение:** не открывать случайные follow-up implementation tickets без общего capability-audit.
- **Альтернативы:** продолжать точечные `noLegal`-добавления по мере идеи.
- **Почему:** без общей карты project drift почти гарантирован.

**ADR-2: классификация по blocker type важнее классификации по библиотекам**

- **Решение:** первичная ось исследования — тип ограничения, а не список конкретных библиотек.
- **Альтернативы:** строить исследование вокруг перечисления `yt-dlp`, `ffmpeg`, OCR SDK и т.д.
- **Почему:** библиотека может смениться, а blocker-класс и decision policy остаются.

**ADR-3: один `noLegal` остаётся максимальной compile-time isolated сборкой**

- **Решение:** сохраняется один `noLegal` без разветвлений; capability-wise он рассматривается как максимальная локальная сборка, включающая VR-возможности и непубликуемые sideload-only расширения. Все кандидаты оцениваются исходя из compile-time изоляции от market-flavors.
- **Альтернативы:** runtime flags внутри общего market APK; семейство отдельных `noLegal` forks.
- **Почему:** один верхний sideload build проще держать концептуально и он лучше защищает market surface от утечки restricted-capabilities.

**ADR-4: личное sideload-использование не отменяет security и ethics review**

- **Решение:** даже для личной сборки не допускаются идеи, которые требуют явного обхода чужих ограничений, DRM, подписок, неавторизованного доступа или доступа к чужому контенту. Публичная доступность кода сама по себе не отменяет эту границу.
- **Альтернативы:** считать sideload-only сборку зоной без ограничений.
- **Почему:** задача состоит в расширении допустимого capability surface, а не в снятии базовых границ.

**ADR-5 (из S0117): compile-time sourceSet-изоляция, не runtime feature flag**

- **Решение:** GPL-код живёт в `src/noLegal/java/`; `IS_NO_LEGAL_FLAVOR` — только safety belt, а не primary isolation. Market-flavors физически не видят `noLegal`-классы на этапе компиляции.
- **Альтернативы рассмотрены:** runtime flag (GPL-классы всё равно попадают в market APK); общий код с `if (IS_NO_LEGAL_FLAVOR)` (не даёт compile-time изоляции).
- **Почему важно для S0156:** каждый capability-кандидат, чей blocker — redistribution-license или store-policy, должен изолироваться тем же compile-time sourceSet-паттерном. Это задаёт обязательную форму для всех follow-up реализаций.

**ADR-6 (из S0117): фиксированная версия зависимости, не remote-loaded**

- **Решение:** все `noLegal`-only зависимости подключаются через `noLegalImplementation` с конкретной версией на момент сборки. Никакой динамической загрузки rules с сервера, Firebase Remote Config, server-managed extractor logic или hot-swap.
- **Почему важно для S0156:** Google Play политика на динамический исполняемый код применяется к signing key developer-а, даже если конкретная сборка не публикуется в Play. Общий signing key `noLegal` и market-flavors делает dynamic loading рискованным для всего портфолио.

**ADR-7 (из S0117): reuse инфраструктуры S0116, не дублирование**

- **Решение:** `noLegal`-стратегии встраиваются в существующий `LinkExtractionRegistry` и получают cookie-injection, quality policy и WebView auth «бесплатно». Аналогичный принцип должен применяться к будущим capability-кандидатам: sideload-only код расширяет существующие pipeline-точки входа, а не форкает их.
- **Почему важно для S0156:** определяет архитектурный паттерн расширения — add, не replace — для всех follow-up реализаций.

**ADR-8: noLegal использует единый APK с split ABI filters для совместной поддержки смартфона и Quest**

- **Решение (2026-05-12):** `ndk.abiFilters` = все 4 ABI (`arm64-v8a`, `armeabi-v7a`, `x86`, `x86_64`) — APK устанавливается на любое устройство без ограничений. `externalNativeBuild.cmake.abiFilters` = `arm64-v8a` — OpenXR native bridge собирается только для Quest slice; остальные ABI-срезы его не содержат и не падают при отсутствии. `VrPlayerActivity` обязан реализовать graceful fallback на `PlayerActivity` при `UnsatisfiedLinkError` или отсутствии OpenXR runtime — смартфон получает `standard + noLegal`, Quest получает `standard + VR + noLegal`. CMake revision bump `-DFMS_BUILD_REVISION=4` для инвалидации stale cmake cache. `noLegal` добавляется в `build-and-push-all.ps1` (debug + release).
- **Альтернативы рассмотрены:** два отдельных APK (vr-capable и phone-only) — сложнее в дистрибуции; arm64-only APK — теряем 32-bit телефоны и эмуляторы; отдельный `vr-noLegal` flavor — нарушает ADR-3.
- **Почему:** split ABI/CMake filter — задокументированный паттерн проекта (см. комментарии в блоках `vr` и `vrUnlicensed` в `app_v2/build.gradle.kts`); единый APK удобнее для sideload-распространения по любому каналу.
