## 1. Проблема

На устройствах с Android 8.1 (в частности автомагнитолы с широким низким экраном) toolbar вторичных экранов рисуется с координаты y=0 и полностью перекрывается непрозрачным системным статус-баром. Контент экрана прижат к самому верху дисплея: заголовок не виден, кнопки toolbar недоступны. Навигация «назад» работает только через кнопку в системном статус-баре. Вертикальная прокрутка в затронутых экранах недоступна.

Затронуты вторичные экраны (настройки, редактирование и добавление сетевых ресурсов, управление сессиями авторизации и аналогичные). Основной экран просмотра файлов и плеер работают корректно.

---

## 2. Цели

1. На всех устройствах, включая Android 8.1 OEM-магнитолы, toolbar вторичных экранов отображается полностью ниже системного статус-бара.
2. Кнопки toolbar реагируют на касание (не перекрыты системным оверлеем).
3. Правка не меняет поведение на устройствах, где toolbar уже отображается корректно.
4. Основной экран и плеер не затрагиваются.

**Non-goals:**

- Изменение внешнего вида или структуры toolbar.
- Поддержка «прозрачного» или «погружённого» статус-бара на вторичных экранах.
- Исправление каких-либо проблем на Wear OS.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Использовать тот же принцип обработки системных отступов (insets), что уже работает на основном экране — не изобретать отдельный механизм.
2. Не вводить новых пользовательских настроек.

### 3.2 Жёсткие ограничения

- **Flavor:** все варианты сборки (`standard`, `lite`, `photos`, `legacy`).
- **API level:** минимальный уровень поддержки — API 23 (flavor `legacy`); исправление должно работать корректно на всём диапазоне API 23–35, включая OEM-поведение Android 8.1 (API 27).
- **Wear OS:** не затрагивается.
- **Производительность:** изменения в пути отрисовки должны ограничиваться одним вызовом `OnApplyWindowInsetsListener` на экран — без дополнительных перемеров.
- **Совместимость данных:** данные не затрагиваются.
- **Локализация:** визуальное исправление, строки не меняются.
- **Доступность:** toolbar, переставший перекрываться, становится доступен для TalkBack автоматически; дополнительных действий не требуется.

---

## 4. Контекст текущей архитектуры

Приложение использует режим edge-to-edge: все Activity рисуют контент от y=0 до нижнего края экрана, системные панели (статус-бар, панель навигации) становятся прозрачными и отрисовываются поверх контента. Чтобы контент не залезал под панели, каждый экран обязан получить и применить window insets — добавить отступ равный высоте статус-бара к toolbar'у сверху.

Основной экран использует стандартный контейнер AppBar, который обрабатывает insets автоматически через системный механизм `fitsSystemWindows`. Большинство вторичных экранов либо вообще не имеют обработчика insets, либо содержат ручное вычисление высоты toolbar, которое на нестандартных OEM-устройствах даёт некорректный результат (отрицательное или нулевое значение высоты).

На Android 8.1 OEM-магнитолах системный статус-бар непрозрачен, и его inset может не доставляться стандартным путём; при этом сам toolbar оказывается нарисован ровно там, где стоит статус-бар, а не под ним.

---

## 5. Предлагаемый подход

Централизовать логику применения insets в базовом классе Activity. Вторичные экраны вызывают единый хелпер после установки layout'а — хелпер регистрирует обработчик window insets, который добавляет к toolbar'у отступ сверху, равный высоте статус-бара. Никакой ручной арифметики с `actionBarSize` не остаётся.

В экранах с текущим ручным вычислением высоты toolbar'а (SettingsActivity и аналогичные) — удалить проблемную арифметику и подключить хелпер вместо неё. Добавить защитный минимум: вычисленная высота toolbar'а не может быть ≤ 0.

### 5.1 Основные столпы / модули

**Базовый класс Activity (централизация):**
- Добавить защищённый хелпер-метод, принимающий view-контейнер toolbar'а.
- Хелпер устанавливает `ViewCompat.setOnApplyWindowInsetsListener`: применяет `paddingTop = insets.statusBars.top`.
- Инсеты потребляются (consumed) только в части `statusBars`, остальные передаются дочерним view.

**Вторичные экраны без insets-обработки:**
- Вызвать хелпер после `setContentView`.
- Убедиться, что `requestApplyInsets()` вызывается на root view, чтобы инсеты были доставлены.

**SettingsActivity (специфичный случай):**
- Удалить ручное вычисление `toolbarHeight = actionBarSizePx - statusBarInsetPx` — оно даёт ≤ 0 на OEM-устройствах с нестандартным `actionBarSize`.
- Высота toolbar'а фиксируется через атрибут темы `?attr/actionBarSize`; отступ сверху выставляется через общий хелпер.
- В компактном режиме высоты строк остаются без изменений; только inset-отступ теперь приходит через хелпер, а не вручную.

### 5.2 Потоки данных и событий

```
Activity.onCreate
  → setContentView(layout)
  → base.setupToolbarInsets(toolbarContainer)
      → ViewCompat.setOnApplyWindowInsetsListener(toolbarContainer)
          → toolbarContainer.updatePadding(top = statusBarInsets.top)
  → requestApplyInsets()  // инициирует доставку инсетов от системы
```

### 5.3 Точки расширяемости

- Хелпер принимает любой `View` — новые вторичные экраны могут подключиться одной строкой.
- Логика компактного режима в SettingsActivity остаётся отдельной и не смешивается с insets.

   - **Вопрос:** доставляет ли OEM-прошивка инсеты статус-бара через `WindowInsetsCompat` или они нулевые?

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| На устройстве инсеты статус-бара приходят нулевыми (OEM-поведение) | Средняя | Toolbar по-прежнему у y=0 | Добавить fallback: если inset=0 и статус-бар системы присутствует, применить `windowInsets.systemWindowInsetTop` как запасной путь |

| Регрессия на телефонах (нормальных устройствах) | Низкая | Избыточный отступ или смещение контента | Прогнать задымочное тестирование на стандартном телефоне после правки |

## 9. Архитектурные решения (ADR)

**ADR-1: Централизация insets-логики в базовом классе Activity**

- **Решение:** единый хелпер в базовом Activity, вместо разрозненных ad-hoc реализаций в каждом вторичном экране.
- **Альтернативы:** (а) Фиксировать каждый экран независимо — `android:fitsSystemWindows="true"` в layout XML или отдельный `setOnApplyWindowInsetsListener` в каждом экране; (б) Не вызывать `enableEdgeToEdge()` в базовом классе для вторичных экранов.
- **Почему:** вариант (б) (отключить edge-to-edge для вторичных экранов) наиболее прост, но создаёт визуальный разрыв на устройствах с жестовой навигацией (полоса снизу). Вариант (а) с `fitsSystemWindows` ненадёжен на OEM Android 8.1 (известное поведение). Централизованный хелпер даёт полный контроль над применением insets и тестируемость без рисков разрыва на современных устройствах.

**ADR-2: Удаление ручной арифметики высоты toolbar в SettingsActivity**

- **Решение:** удалить вычисление `toolbarHeight = actionBarSizePx - statusBarInsetPx`.
- **Альтернативы:** добавить guard `max(result, minToolbarHeightPx)` без удаления арифметики.
- **Почему:** ручная арифметика принципиально ненадёжна на OEM-устройствах с нестандартными атрибутами темы. Применение insets как padding не затрагивает измеренную высоту view — это ортогональный механизм. Защитный guard не устраняет причину, только притупляет симптом.

3. На стандартном Android-телефоне внешний вид вторичных экранов не изменился.
4. Основной экран и плеер не затронуты.
