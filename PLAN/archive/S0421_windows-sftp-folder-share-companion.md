## 1. Проблема

Пользователю нужно открыть доступ к папке(ам) на своём Windows-ПК для Android-клиентов FastMediaSorter, чтобы просматривать и сортировать фото/видео. Неподготовленному человеку трудно даже поднять и настроить SFTP-сервер и тем более пробросить порт на роутере; а проброс порта вдобавок по умолчанию заблокирован для пользователей за CGNAT. Нужен помощник, который доводит SFTP-сервер «под ключ» (выбор папок, ключи, помощь с доступом), а в идеале даёт ещё и доступ «по уникальному ID + пароль» без ручной настройки роутера. Область - десктоп-компаньон плюс существующий на Android стек сетевых ресурсов (в первую очередь SFTP).

**Каноничный целевой сценарий (валидирующий дизайн):** дома Win10 на проводе за роутером (с уже проброшенным вручную портом); в дороге Android-голова в машине по WiFi с раздачи телефона (мобильный оператор, CGNAT) слушает музыку с домашнего SFTP. Это работает сегодня, но требует ручной настройки SFTP-сервера и проброса порта. По NAT-раскладу это пара «лёгкий дом + жёсткий мобильный клиент» - тот самый случай, который обслуживает и port-forward (уровень A), и P2P-hole-punching без релея (уровень B). Задача S0421 - **облегчить «лэндинг»**: довести обычного пользователя до этого рабочего состояния без ручного поднятия сервера и проброса порта, и чтобы один и тот же ресурс работал и дома (локальная сеть), и в дороге (интернет) без перенастройки.

## 2. Цели

Доступ организуется в два уровня, и оба используют SFTP как файловый протокол (один и тот же сервер на ПК).

**Уровень A - помощник SFTP (ядро, без зависимости от серверов владельца):**

1. Пользователь на ПК выбирает папку(и), и компаньон сам поднимает/настраивает SFTP-сервер, генерирует ключи и работает в фоне с автозапуском.
2. Компаньон помогает с доступом из локальной сети (анонс по mDNS) и из интернета (автопроброс порта через UPnP/NAT-PMP/PCP, при неудаче - пошаговая инструкция по роутеру и DDNS).
3. Компаньон формирует конфигурацию ресурса (адрес/порт/отпечаток ключа), которую Android-сторона импортирует одним действием и сразу получает рабочий SFTP-ресурс.

**Уровень B - доступ «по ID» (опциональное расширение, зависит ТОЛЬКО от дешёвого rendezvous владельца, без релея):**

4. Пользователь на ПК получает уникальный идентификатор; на Android он вводит этот ID + пароль и подключается без настройки роутера и без видимого IP/порта.
5. Данные идут строго P2P (прямое соединение после «знакомства» через rendezvous); медиа никогда не проходит через серверы владельца.
6. Трафик зашифрован; видео воспроизводится с перемоткой так же, как у обычного SFTP-ресурса (туннель сохраняет random-access чтение SFTP).

**Сквозная цель - лёгкий «лэндинг» (онбординг):**

7. На ПК - минимум шагов: установить, выбрать папку, готово (сервер, ключи, автозапуск, попытка автопроброса - автоматически).
8. На Android - подключение без ручного ввода хоста/порта/ключа: импорт конфигурации одним действием (QR-код или короткий код/файл).
9. Один ресурс сам выбирает достижимый путь без перенастройки: локальная сеть, когда устройства рядом; интернет (port-forward), когда нет; доступ «по ID» как опция уровня B.

**Non-goals:**

- Не запускать и не оплачивать релей (TURN/DERP), переносящий медиатрафик; при невозможности прямого P2P соединение честно не устанавливается.
- Не гарантировать соединение «по ID» в 100% сетевых сочетаний: пара «обе стороны за симметричным NAT/CGNAT» структурно не обслуживается без релея.
- Не строить собственный протокол NAT-traversal/STUN/hole-punching и собственную крипту PAKE/Noise - брать готовый OSS.
- macOS в этой итерации; Linux-компаньон - позже.
- Не тащить тяжёлую транспорт-зависимость в «лёгкие» варианты сборки.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Уровень A (SFTP-помощник) - стартовый и самодостаточный; должен работать без каких-либо серверов владельца.
2. Дешёвый интернет-узел владельца выполняет ТОЛЬКО роль rendezvous/signaling (раздача ID и сведение сторон) и, при необходимости, STUN; никакого переноса медиа.
3. UX уровня B максимально близко к «прочитал ID, ввёл пароль».
4. Импорт конфигурации/тикета пейринга (а не только ручной ввод) для облегчения сопряжения.
5. Десктоп-компаньон: Windows сейчас, Linux - в планах позже.
6. Облегчить «лэндинг» обычного пользователя до рабочего состояния каноничного сценария (дом на проводе + клиент на мобильной раздаче) без ручного поднятия SFTP и проброса порта; один ресурс работает и дома (LAN), и в дороге (интернет).

### 3.2 Жёсткие ограничения

- **Инфраструктура владельца:** только rendezvous/signaling (+ опционально STUN), без релея. Прямой P2P или честный отказ.
- **Flavor:** уровень A опирается на существующий SFTP-стек (доступен там, где есть SFTP). Транспорт-зависимость уровня B - только в варианте standard (решение quiz 2026-06-19); исключается из lite/photos/legacy на уровне сборки.
- **API level:** клиент работает как сетевой трафик; уточнить разрешение локальной сети (mDNS/NsdManager) и совместимость с legacy (minSdk23).
- **Wear OS:** не затрагивается.
- **Производительность:** обязательны дешёвое random-access чтение с произвольного offset (для перемотки видео) и управление буфером/flow-control туннеля; контроль батареи (Doze, foreground-service на окно передачи).
- **Совместимость данных:** новые возможности добавляются без изменения формы хранения существующих ресурсов; учётные данные (ID+пароль, пиннуемый ключ ПК) кладутся в существующее раздельное хранилище учёток.
- **Локализация:** EN/RU/UK - обязательно.
- **Доступность:** UI добавления/импорта ресурса поддерживает клавиатуру/D-pad/мышь и две ориентации.

## 4. Контекст текущей архитектуры

На Android уже есть зрелый SFTP-стек: доменный enum `ResourceType` с типом SFTP, источник данных поверх media3 `BaseDataSource` с нативной перемоткой (ranged-чтение), клиент с пулом соединений, сканером каталога, файловыми операциями и пиннингом host-key. Учётные данные хранятся отдельно от ресурса. Цепочка слоёв: UI -> ViewModel -> UseCase -> Repository -> DataSource. Десктопной половины у проекта нет вовсе.

Текущий путь не решает §1, потому что: (1) обычному пользователю всё равно надо вручную поднять SFTP и пробросить порт; (2) проброс порта ломается под CGNAT. Уровень A автоматизирует (1) и смягчает (2) автопробросом. Уровень B убирает проброс совсем, заменяя «маршрутизируемый адрес» на «P2P-туннель, сведённый через rendezvous», но требует слоя посредника и P2P-транспорта, которого в текущей архитектуре нет.

## 5. Предлагаемый подход

Ключевая идея: **SFTP - единый файловый протокол на всех уровнях**, а способ дотянуться до сервера - сменный. Тогда Android-сторона переиспользует существующий SFTP-источник (включая перемотку видео), а новизна сосредоточена в десктоп-компаньоне и в P2P-транспорте уровня B.

### 5.1 Основные столпы / модули

- **Десктоп-компаньон (Windows, отдельный субпроект вне Android-репозитория, корень `P:\windows\fms_companion`):** выбор папок, поднятие/настройка SFTP-сервера, генерация ключей, фоновый автозапуск. Корректная форма автозапуска - фоновый воркер + интерактивный tray-компаньон как раздельные процессы (изоляция Session 0 в Windows).
- **Слой доступности (уровень A):** анонс по mDNS в локальной сети; автопроброс порта через UPnP/NAT-PMP/PCP с откатом на инструкцию по роутеру/DDNS; экспорт конфигурации ресурса для импорта на Android.
- **P2P-транспорт (уровень B) на готовом OSS:** прямое соединение по принципу WebRTC reliable/ordered DataChannel + свой signaling + STUN, БЕЗ TURN (отсутствие TURN структурно гарантирует «медиа не идёт через релей»). Поверх установленного туннеля прокидывается локальный сокет, через который существующий Android-клиент говорит по SFTP к удалённому серверу.
- **Слой безопасности:** PAKE по короткому ID+паролю (rendezvous и сеть не могут перебрать пароль офлайн), сквозное шифрование туннеля, недоверенный rendezvous, TOFU-пиннинг ключа ПК с подтверждением короткой строки при первом сопряжении.
- **Rendezvous/signaling-узел владельца:** дешёвый интернет-сервер, который раздаёт ID, сводит стороны и (опционально) отвечает как STUN; медиатрафик через него не проходит.

### 5.2 Потоки данных и событий

- **A (LAN):** компаньон поднимает SFTP и анонсирует его по mDNS; Android находит сервис, импортирует параметры и подключается существующим SFTP-стеком.
- **A (интернет):** компаньон поднимает SFTP, пытается автопробросить порт (UPnP/NAT-PMP/PCP), выясняет внешний адрес/DDNS, экспортирует конфигурацию; Android импортирует и подключается по SFTP.
- **B (по ID):** компаньон держит исходящее соединение к rendezvous под своим ID; Android по ID обращается к rendezvous, тот сводит стороны; через PAKE из пароля выводится сессионный ключ; стороны устанавливают прямой P2P-туннель (при невозможности - честный отказ с подсказкой); поверх туннеля Android говорит по SFTP, перемотка/миниатюры работают как обычно.

### 5.3 Точки расширяемости

- Способ доступа (LAN / port-forward / P2P-по-ID) скрыт за общим понятием «как дотянуться до SFTP-сервера», чтобы добавлять/менять транспорты, не трогая чтение файлов.
- Один ресурс хранит несколько способов доступа и выбирает достижимый автоматически (сначала локальная сеть, затем интернет, затем «по ID»), чтобы дома и в дороге работала одна и та же запись без перенастройки.
- Импорт конфигурации - через сканируемый код/короткий код/файл, чтобы исключить ручной ввод параметров на Android.
- Адрес rendezvous/STUN конфигурируется (узел владельца по умолчанию; допускается пользовательский).
- Уровень B по возможности оформляется как способ подключения к SFTP-ресурсу, а не как полностью новый тип, - чтобы не дублировать весь SFTP-стек (решается спайком, см. §6).
- Модель учётных данных рассчитана на постоянный (unattended) доступ (сопряжение один раз); одноразовые коды шаринга - вне текущего объёма, но модель не должна их исключать на будущее.
- Бустеры связности (предпочтение IPv6; автопроброс на стороне ПК) подключаются независимо и повышают долю успешных прямых соединений.

## 9. Архитектурные решения (ADR)

- **ADR-1:** SFTP - единый файловый протокол на всех уровнях; способ доступа сменный. Причина: переиспользование зрелого Android-SFTP-стека (включая перемотку видео) и минимум нового кода на клиенте.
- **ADR-2:** Уровень A (SFTP-помощник) - стартовый и самодостаточный, без зависимости от серверов владельца. Причина: ценность сразу, ноль инфраструктуры и операционных рисков.
- **ADR-3:** Уровень B - P2P без релея; инфраструктура владельца только rendezvous/STUN. Реализация на WebRTC-подобном DataChannel без TURN, потому что отсутствие TURN структурно гарантирует, что медиа не пойдёт через релей. Принятый компромисс: пара «обе стороны симметричные/CGNAT» не обслуживается (честный отказ + бустеры IPv6/UPnP).
- **ADR-4:** Не реализовывать NAT-traversal и крипту самостоятельно - брать проверенный OSS (прецедент уязвимостей самодельного PAKE).

## 10. Связи с другими спеками

- S0530 (rendezvous/signaling-сервер) - инфраструктура уровня B; уровень A от него не зависит.
- S0046 (SFTP key-auth hardening) - паттерн пиннинга host-key переиспользуется для TOFU-пиннинга ключа ПК.
- S0466 / S0494 / S0496 - смежные сетевые тикеты для согласования поведения.

## 11. Критерии готовности (strategic-level)

1. Пользователь на ПК за один проход выбирает папку(и), и компаньон поднимает работающий SFTP-сервер с автозапуском после перезагрузки.
2. В локальной сети Android автоматически находит сервер и подключается; для интернета компаньон автопробрасывает порт (или даёт понятную инструкцию) и экспортирует конфигурацию, которую Android импортирует одним действием.
3. Удалённые миниатюры и метаданные отображаются, а видео воспроизводится с перемоткой на уровне обычного SFTP-ресурса.
4. (Уровень B) Пользователь подключается по ID + паролю без настройки роутера и без ввода IP/порта, когда сеть это позволяет; соединение строго P2P, медиа не проходит через серверы владельца.
5. (Уровень B) При невозможности прямого P2P приложение честно сообщает об этом и подсказывает действия (IPv6/UPnP/смена сети/уровень A); релея нет.
6. Трафик зашифрован; при первом сопряжении уровня B пользователь подтверждает короткую строку/отпечаток, далее ключ ПК пиннится.
7. Функция присутствует только в предусмотренных вариантах сборки и не увеличивает размер «лёгких»/legacy сборок сверх допустимого (проверено на release-сборках).
8. Один импортированный ресурс работает в каноничном сценарии и дома (локальная сеть), и в дороге (интернет) без перенастройки; импорт на Android выполняется сканированием кода/импортом файла без ручного ввода хоста, порта и ключа.
