## 1. Проблема

Документация о версии схемы Room расходится с фактической схемой приложения: текущий операционный документ указывает устаревшее значение, а два исторических документа ошибочно называют свой снимок текущим. Существующая проверка контролирует только один из текущих документов, поэтому повторное расхождение не останавливает проверку документации. Это замедляет разработку и может привести к неверному планированию миграций.

## 2. Цели

1. Текущие технические документы всегда сообщают фактическую версию схемы Room.
2. Проверка документации завершается ошибкой, если любой текущий документ о версии схемы расходится с исходным кодом.
3. Исторические оценки и handoff-документы явно описывают свой снимок и не заявляют, что он является текущей схемой.

**Non-goals:**

- Не менять состав схемы, миграции или данные пользователя.
- Не превращать исторические снимки в автоматически обновляемые документы.

2. Регрессионная проверка должна доказывать отказ для каждого текущего документа.

## 4. Контекст текущей архитектуры

Версия схемы определяется декларацией базы данных в исходном коде, а инженерные документы повторяют её для операционной работы и планирования. Существующий контроль извлекает каноническое значение и сопоставляет его с перечнем объявленных документов. Исторические документы используют старые экспортированные снимки, поэтому они должны сохранять контекст снимка, но не участвовать в утверждениях о текущем состоянии.

## 5. Предлагаемый подход

Расширить единый манифест документационного дрейфа перечнем всех текущих документов, которые обязаны сообщать версию схемы. Обновить устаревший текущий документ и скорректировать исторические тексты, чтобы они маркировали зафиксированный базовый снимок вместо текущего значения.

### 5.1 Основные столпы / модули

#### Контролируемые текущие документы

Проверка хранит явный список текущих документов и извлекает из каждого значение версии по устойчивому контексту текста.

#### Исторические снимки

Оценка сложности и handoff сохраняют полезные сведения о старой схеме, но описывают их как исторический baseline.

#### Регрессионное доказательство

Тестовый контур проверяет успешный baseline и отдельный отказ при рассогласовании каждого обязательного текущего документа.

### 5.2 Потоки данных и событий

Исходная декларация схемы → извлечение канонической версии → манифест контролируемых документов → извлечение документированных значений → сравнение → результат инженерской проверки.

### 5.3 Точки расширяемости

Манифест остаётся единой точкой добавления будущего текущего документа о версии схемы. Исторические документы не включаются в него, пока не начнут заявлять актуальное состояние.

## 9. Архитектурные решения (ADR)

**ADR-1: Контролировать только текущие утверждения о версии схемы**

- **Решение:** Автоматически проверять операционные документы, а исторические документы переписать как baseline.
- **Альтернативы:** Сканировать все числовые упоминания версии; удалять версию из каждого исторического документа.
- **Почему:** Историческому документу нужна воспроизводимая ссылка на его исходный снимок, но утверждение о текущем состоянии должно иметь один проверяемый контур.
