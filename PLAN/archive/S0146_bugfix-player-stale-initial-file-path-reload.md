> **Scope:** STRATEGIC. Поведение плеера при переоткрытии после перемещения/удаления текущего файла. Без имён классов, путей, лимитов строк, миграций Room, модулей Hilt.

---

## 1. Проблема

После того как пользователь в Player перемещает или удаляет несколько файлов (основной сценарий сортировки), при следующем переоткрытии плеера (например, после поворота экрана или возврата из фона) плеер получает «начальный файл» из исходного запуска — а этого файла в ресурсе уже нет. Загрузчик плеера трактует «начального файла нет в кэше» как «кэш загружен в неправильном объёме» и перечитывает каталог с диска целиком; затем не находит и текущий файл по сохранённому пути, и откатывается дальше по цепочке вплоть до первого файла списка. В логах полевой сессии 2026-05-10 это видно как повторяющиеся `cache scope mismatch — cached N files do not contain initialFilePath=..` и `Current file not found: .., trying initialFilePath` для пути, который был удалён несколькими секундами ранее, причём один и тот же мёртвый путь срабатывает повторно при следующих переоткрытиях. Эффект на пользователя: после поворота экрана плеер может «прыгнуть» не на тот файл, который был открыт, плюс лишнее перечитывание каталога (заметный микрофриз на больших папках и медленном хранилище).

---

## 2. Цели

1. При переоткрытии/пересоздании плеера он остаётся на том файле, который был показан, если этот файл ещё существует — независимо от того, что «начальный файл» исходного запуска уже удалён.
2. Отсутствие «начального файла» в кэше, вызванное его удалением/перемещением, больше не приводит к перечитыванию каталога с диска — перечитывание происходит только при настоящем расхождении объёма кэша.
3. «Протухший» начальный путь не используется повторно при последующих переоткрытиях в той же сессии.
4. Если ни текущий, ни начальный файл больше недоступны — плеер делает осмысленный выбор (ближайший по порядку к прежней позиции), а не безусловно прыгает на первый файл.

**Non-goals:**

- Не менять сам процесс перемещения/удаления файла из плеера (он работает; см. S0094).
- Не менять стратегию формирования и инвалидации кэша списков файлов в целом — только реакцию загрузчика плеера на отсутствие нужного файла.
- Не вводить новых пользовательских настроек поведения при потере позиции.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Минимальная инвазивность: поправить логику восстановления позиции и распознавания «расхождения объёма кэша», не переписывая загрузчик плеера.
2. Сохранить существующую очистку записей о реально отсутствующих файлах (мёртвая запись должна вычищаться из кэша/БД, а не просто игнорироваться).
3. Поведение при «обычном» переоткрытии (файл на месте) не должно измениться вообще.

### 3.2 Жёсткие ограничения

- **Flavor:** все — плеер общий для всех флаворов.

- **Совместимость данных:** миграции данных нет; используется уже существующее сохранение позиции.
- **Локализация:** новых пользовательских строк не предполагается; если появятся — EN/RU/UK обязательно.
- **Доступность:** не визуальная фича; требований нет.

## 4. Контекст текущей архитектуры

Плеер запускается с «начальным файлом» (путь, на котором его открыли) и работает поверх кэша списка файлов ресурса. При пересоздании экрана загрузчик плеера перечитывает список: сначала пытается восстановить позицию по сохранённому текущему файлу, затем — по начальному файлу из запуска, иначе — на первый элемент. Отдельно загрузчик проверяет «попадание объёма»: если начальный файл не найден в кэше, считается, что кэш загружен в более узком объёме, и каталог перечитывается с диска.

Решить проблему «как есть» нельзя, потому что обе проверки опираются на начальный путь из запуска как на ориентир, не учитывая, что за время сессии этот файл мог быть перемещён или удалён самим пользователем. Тогда «начального файла нет в кэше» — это не сигнал о неправильном объёме, а нормальное следствие сортировки; а «текущий» файл (реально показанный) при этом может быть вполне валиден и присутствовать в кэше. Сохранение позиции в проекте уже есть — оно просто не приоритезируется над начальным путём в этом сценарии.

## 5. Предлагаемый подход

Сделать ориентиром восстановления и проверки объёма кэша *текущую* позицию плеера, а начальный путь запуска — лишь резервом; «протухший» путь явно отбрасывать, а не использовать повторно.

### 5.1 Основные столпы / модули

**Столп 1 — Приоритет текущей позиции при пересоздании.**
- Цель: при пересоздании экрана плеер сначала пытается встать на файл, который был показан (по сохранённой позиции), и только если его нет — на начальный путь запуска, и только потом — на ближайший по порядку.
- Требования: при «файл на месте» поведение неотличимо от текущего; начальный путь больше не перебивает валидную сохранённую позицию.

**Столп 2 — Корректная диагностика «расхождения объёма кэша».**
- Цель: перечитывание каталога с диска инициируется только когда кэш действительно загружен в более узком объёме, а не когда конкретный файл (начальный или текущий) просто отсутствует из-за удаления/перемещения.
- Требования: отсутствие удалённого файла в кэше — не повод для полного перечитывания; настоящее расхождение объёма по-прежнему обрабатывается.

**Столп 3 — Отбрасывание «протухшего» начального пути.**
- Цель: если начальный путь запуска указывает на отсутствующий файл, он перестаёт использоваться как ориентир в этой сессии (и соответствующая мёртвая запись вычищается из кэша/БД, как сейчас).
- Требования: повторные переоткрытия не воспроизводят один и тот же `cache scope mismatch` по уже мёртвому пути.

**Столп 4 — Осмысленный фолбэк позиции.**
- Цель: когда ни текущий, ни начальный файл недоступны, плеер встаёт на ближайший по порядку к прежней позиции, а не безусловно на первый элемент.
- Требования: выбор детерминирован и не зависит от способа сортировки списка сверх того, что уже задано.

### 5.2 Потоки данных и событий

`Пересоздание экрана плеера → загрузчик: взять кэш списка → восстановить позицию (текущий файл → начальный путь → ближайший по порядку) → перечитать каталог только при настоящем расхождении объёма → отдать список и позицию в UI`.

### 5.3 Точки расширяемости

- Логика выбора позиции при недоступности — единая точка, куда при необходимости добавляются другие резервные стратегии.
- Признак «настоящего расхождения объёма» отделён от признака «конкретный файл отсутствует» — оба переиспользуемы независимо.

## 6. Открытые вопросы / Research items

1. **Источник повторного появления «протухшего» начального пути**
   - **Вопрос:** начальный путь приходит заново при каждом пересоздании из аргументов запуска экрана, или ещё откуда-то?
   - **Варианты:** только из аргументов запуска / также из сохранённого состояния / из обоих.
   - **Нужно выяснить:** где именно зафиксировать «этот путь уже мёртв, не использовать» на время жизни экрана.
   - **Статус:** Open — уточняется на этапе тактики чтением кода загрузчика плеера.

2. **Критерий «настоящего расхождения объёма кэша»**
   - **Вопрос:** по какому признаку отличать «кэш слишком узкий» от «нужного файла нет, потому что его удалили»?
   - **Варианты:** сравнение «корня» кэша с папкой запрошенного файла / наличие в кэше хотя бы части файлов из той же папки / иной признак.
   - **Нужно выяснить:** какой признак не даёт ложных срабатываний на виртуальных агрегирующих ресурсах (рекурсивный обход подпапок).
   - **Статус:** Open.

3. **Определение «ближайшего по порядку» при потере позиции**
   - **Вопрос:** как выбрать ближайший файл, если прежняя позиция указывала на удалённый элемент?
   - **Варианты:** по сохранённому индексу в текущем порядке / по соседям удалённого файла, запомненным до удаления / на первый, если ничего не известно.
   - **Нужно выяснить:** что из этого уже доступно загрузчику без новых дисковых операций.
   - **Статус:** Open.

## 9. Архитектурные решения (ADR)

**ADR-1: Текущая позиция — основной ориентир, начальный путь запуска — резерв.**
- **Решение:** при восстановлении позиции и при проверке «нужен ли перечитывать каталог» первичен реально показанный файл, а не путь из аргументов запуска.
- **Альтернативы:** оставить начальный путь основным ориентиром и просто молча игнорировать его отсутствие.
- **Почему:** в сценарии сортировки начальный путь устаревает почти сразу; ориентация на него — корень и ложного «расхождения объёма», и прыжков позиции.

**ADR-2: Сохранить вычистку мёртвых записей.**
- **Решение:** обнаружив, что путь указывает на отсутствующий файл, плеер по-прежнему удаляет соответствующую запись из кэша/БД.
- **Альтернативы:** просто пропускать отсутствующий файл, не трогая кэш.
- **Почему:** без вычистки мёртвая запись будет всплывать снова; текущее поведение в этой части правильное и остаётся.

## 11. Критерии готовности (strategic-level)

1. После перемещения/удаления нескольких файлов в плеере и поворота экрана плеер остаётся на том же файле, что был показан (если он существует).
2. В логах после такого сценария нет `cache scope mismatch` и нет перечитывания каталога с диска, если фактический объём кэша корректен.
3. Один и тот же удалённый путь не вызывает повторных `cache scope mismatch` при следующих переоткрытиях в сессии.
4. Если показанный файл удалён к моменту пересоздания, плеер встаёт на ближайший по порядку к прежней позиции, а не на первый файл (когда данные о соседях доступны).
5. Штатное переоткрытие плеера (без перемещений) ведёт себя ровно как до изменений.
