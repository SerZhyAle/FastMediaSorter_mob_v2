## 1. Проблема

OCR, перевод и связанные ML-механизмы поставляются в каждую сборку и устанавливаются у каждого пользователя при инсталляции, хотя большинству они нужны позже или никогда. Их нативные библиотеки (перевод ~16.4 МБ, ML Kit OCR ~11 МБ, Tesseract-стек ~7 МБ, language-id ~1 МБ на arm64-устройство, плюс ML-модели в ассетах - суммарно ~35.5 МБ) занимают место и трафик у всех. В FEATURES заявлено, что приложение умеет OCR и перевод, но не заявлено, что это уникальная встроенная разработка - значит доставка этой способности по запросу допустима и обещаний не нарушает.

Та же проблема шире OCR/перевода: в базовой сборке лежат и другие тяжёлые встроенные ассеты, не нужные большинству при установке - в частности фоновые видео-визуализации аудио-плеера (~6.35 МБ), которые видит лишь часть пользователей. Их разумно доставлять тем же механизмом по запросу. Источник доставки должен быть нашим собственным (наш репозиторий-хостинг), чтобы не зависеть от чужих ссылок третьих сторон, которые могут смениться или пропасть.

Нужен механизм, при котором OCR/перевод выключены по умолчанию для всех профилей устройств, а сам тяжёлый функционал докачивается и устанавливается только когда пользователь его осознанно включает; при отказе от загрузки - мягкая недоступность без потери остального функционала.

## 2. Цели

1. Базовая сборка (APK/AAB) каждого флейвора больше не несёт тяжёлые ML/OCR-нативные библиотеки и модели, тяжёлые опциональные ассеты (фоновые видео-визуализации аудио-плеера) и первопартийный FFmpeg DTS-декодер - они доставляются отдельно по запросу.
2. Доставка устойчива к отказу источника: каждый набор имеет упорядоченный список источников - официальная ссылка производителя там, где она есть, плюс наша стабильная зеркальная ссылка на нашем хостинге (напр. GitHub Releases/raw). Если ссылка производителя «не отвечает» (таймаут/ошибка/недоступна), программа автоматически переходит к нашему зеркалу. Для наборов без официальной ссылки наше зеркало - основной источник. Все зеркала и наборы предварительно залиты к нам и под нашим контролем.
3. OCR, перевод и связанные механизмы выключены сразу после установки для всех профилей устройств и пресетов первого запуска.
4. При включении любой из этих способностей пользователю предлагается скачать и установить функционал с понятной оценкой размера, виден прогресс, и после однократной установки на устройство функционал используется автоматически при последующих включениях без повторной докачки.
5. При отказе пользователя скачивать - способность остаётся выключенной, выдаётся понятное сообщение, приложение не падает и не навязывает загрузку повторно агрессивно.
6. Установленный функционал переживает обновления приложения и не вычищается фоновой очисткой кэша.
7. Поведение «по запросу» описано во всей пользовательской документации.
8. Функциональность OCR/перевода после установки идентична текущей (качество распознавания/перевода не деградирует). Видео-визуализации аудио-плеера после докачки отображаются как сейчас.
9. В настройках есть кнопка перехода на экран «Загружаемые расширения» - единый список всего, что можно скачать: и модули (наборы OCR/перевод/видео-виз/FFmpeg), и языковые данные (Tesseract `.traineddata`, языковые паки перевода, модели Paddle). По каждому пункту виден статус (доступно к загрузке / качается / установлено и работает), его размер, и есть удаление установленного для освобождения места. Реестр расширяемый - в будущем пополняется новыми пунктами без переписывания экрана.

**Non-goals:**

- Не менять алгоритмы и видимое качество OCR/перевода после установки.
- Не убирать OCR/перевод как заявленную возможность - меняется только способ доставки и дефолт.
- Механизм доставки выбран владельцем (§6.1, решено 2026-06-08); следующий шаг - тактическая декомпозиция `/spec-tech`, не прямая реализация из этой спеки.
- Помимо OCR/перевода/связанных ML, видео-визуализаций аудио-плеера и FFmpeg DTS-декодера (Set D), не выносить по запросу прочие тяжёлые модули в этой итерации (Chaquopy/Python и прочее - отдельные тикеты при необходимости).
- Не реализовывать собственный магазин/обновлятор - только точечная докачка известных наборов с нашего хостинга.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Механизм доставки единообразен по поведению для пользователя независимо от флейвора (даже если технически различается под капотом для store и sideload).
2. Сохранить возможность в будущем доставлять по тому же механизму другие опциональные тяжёлые способности.
3. Оценка размера загрузки показывается пользователю до старта, чтобы решение было осознанным.

### 3.2 Жёсткие ограничения

- **Flavor:** затрагивает все. `standard`/`photos`/`legacy` устанавливаются из магазина (могут использовать store-механизм доставки); `noLegal` и `vr` - sideload/Quest, надёжной store-доставки не имеют, для них обязателен самостоятельный download. Реализация следует `dev/FLAVOR_DEVELOPMENT_RULES.md`: контракт способности в общем source-set, механизм доставки и реальные ML/OCR-реализации - в source-set/флейвор-специфичных слоях, no-op/недоступность при отказе или отсутствии доставки, привязка через флейвор-специфичные DI-модули. Гейты `BuildConfig.SUPPORT_*` / `ENABLE_*` в общем source-set для новой развязки запрещены (Rule 15).
- **API level:** без снижения минимумов; нативные библиотеки должны сохранять 16 КБ выравнивание страниц (требование Play с ноября 2025), targetSdk 35.
- **Производительность:** доставка и тяжёлые зависимости загружаются лениво, строго по требованию; cold start не должен деградировать; до установки модуль не должен тянуть нативные библиотеки в процесс.
- **Совместимость данных:** установленный функционал хранится так, чтобы пережить обновление приложения и не попасть под очистку кэша; настройка состояния пополняется признаком «модуль установлен/доступен»; миграция настроек без потери ранее заданных пользователем значений.
- **Локализация:** EN/RU/UK обязательно для всех новых строк (предложение скачать, прогресс, успех, ошибка, мягкий отказ).
- **Доступность:** диалог загрузки и его состояния - TalkBack, корректный фокус, различимость не только цветом; все три режима ввода (клавиатура/D-pad/мышь) по Rule 17.
- **Безопасность:** при самостоятельной загрузке - проверка целостности и подлинности скачанных бинарей до `System.load`; не загружать в процесс непроверенный код.
- **Системные бары:** новые экраны/диалоги соблюдают safe-bounds системных баров и выреза (Rule 18).

- **Flavor scope:** все флейворы. Store-доставка возможна для `standard`/`photos`/`legacy`; `noLegal`/`vr` (sideload/Quest) требуют самостоятельной загрузки. `lite` сейчас и так без перевода/OCR - получает только выключенный по умолчанию контракт.

## 4. Контекст текущей архитектуры

Сейчас ML/OCR-зависимости подключены безусловно и их нативные библиотеки пакуются в базовую сборку всех флейворов (исследование S0385). Способность перевода/OCR реализована в общем коде проигрывателя и документ-вьюеров, напрямую обращается к ML/Tesseract и инжектится по всему стеку плеера, PDF/EPUB/Text-вьюеров, камеры и настроек; центральный узел - монолитный менеджер перевода (см. S0385 §6.1, ~37 файлов поверхности). Переключатели OCR/перевода по умолчанию включены.

Решить из §1 «в лоб» нельзя, потому что библиотеки физически лежат в сборке и грузятся как часть приложения; чтобы убрать их из базовой поставки и доставлять по запросу, нужна (а) развязка способности за контрактом, чтобы базовый код не зависел от ML напрямую, (б) механизм доставки и загрузки/верификации/подключения внешнего кода в рантайме, (в) смена дефолта на «выключено» и UX перехвата включения. В проекте уже есть прецедент доставки кода по запросу для sideload-флейвора (Python-рантайм и связанные инструменты в `noLegal`), что подтверждает применимость самостоятельной загрузки.

## 5. Предлагаемый подход

Сделать OCR/перевод/связанный ML «доставляемой по запросу способностью» за единым контрактом: базовая сборка несёт только контракт и UX перехвата, а тяжёлая реализация и её нативные библиотеки приходят отдельной доставкой, проверяются, подключаются и далее используются автоматически. Поведение для пользователя единое; технический канал доставки может различаться для магазинных и sideload-флейворов.

### 5.1 Основные столпы / модули

**Столп A - Контракт способности и состояние «установлено/доступно».**
Ввести абстракцию «доступность OCR/перевода»: установлено ли, доступно ли к установке, выключено по выбору. Базовый код спрашивает контракт, а не ML напрямую. Состояние персистентно и переживает обновление/очистку кэша.

**Столп B - Дефолт «выключено» для всех профилей.**
Переключатели OCR/перевода и связанных механизмов по умолчанию выключены после установки; пресеты первого запуска для всех профилей устройств ставят их в выключенное состояние; ранее заданные пользователем значения при миграции не теряются.

**Столп C - Канал доставки с автофейловером по источникам.**
Загрузчик берёт для каждого набора упорядоченный список источников и пробует их по очереди до первого, который ответил и прошёл проверку: официальная ссылка производителя (если есть) → наша зеркальная ссылка на нашем хостинге (напр. GitHub Releases/raw). Так ссылки и наборы под нашим контролем и не зависят от стабильности чужих ссылок: при «не отвечает» у производителя автоматически берётся наше зеркало; для наборов без официальной ссылки наше зеркало - первый и единственный источник. Скачанное проверяется на целостность/подлинность до подключения и хранится в защищённом месте. Канал самостоятельной загрузки с фейловером выбран единым для всех флейворов (решение §6.1, 2026-06-08): он базовый и обязательный, штатная магазинная доставка отдельно не реализуется. Доставляемые наборы (см. §5.4): перевод, OCR-движки, видео-визуализации аудио-плеера, FFmpeg DTS-декодер.

**Столп D - UX перехвата включения и загрузки.**
Любая точка, включающая OCR/перевод (настройки и кнопки/действия в плеере и камере), при «не установлено» показывает предложение скачать с оценкой размера, прогресс, и итог (успех/ошибка/отказ). При отказе - мягкая недоступность, способность остаётся выключенной, без краша и навязывания.

**Столп E - Подключение и автозапуск установленного.**
После успешной установки функционал подключается и далее используется автоматически при последующих включениях без повторной докачки; интеграция остаётся ленивой (грузится в процесс только при реальном использовании).

**Столп G - Экран управления расширениями.**
Кнопка в настройках открывает экран «Загружаемые расширения» - единый список модулей и языковых данных под общим реестром. По каждому пункту: статус (доступно/качается/установлено), размер, действие скачать или удалить. Удаление снимает payload и возвращает пункт в «не установлено» (для модуля - способность снова выключается; повторная докачка возможна). Экран читает состояние из контракта способностей (для модулей) и из менеджеров языковых данных (для языков), не дублируя их логику. Реестр пополняется новыми пунктами декларативно - экран их показывает без переписывания.

Уточнение размещения и структуры (запрос владельца 2026-06-10):
- Экран - общеприложенческий агрегатор всех загрузок, а не часть OCR/перевода. Основная точка входа - на вкладке настроек «Общее», после всех сворачиваемых групп и перед прочими кнопками; ширина ограниченная (не растягивать на весь экран ни в портрете, ни в ландшафте).
- В группе настроек «Перевод, OCR и Google Lens» остаётся вторичная точка входа - контекстный ярлык «перейти и скачать пакеты для OCR/перевода», ведущий на тот же экран.
- Внутри экрана пункты разбиты на разделы: «OCR», «Перевод», «Проигрывание медиа». OCR - движки OCR (Set B) и языковые данные OCR (Tesseract `.traineddata`, модели Paddle). Перевод - модуль перевода (Set A) и языковые пакеты перевода. Проигрывание медиа - видео-визуализации (Set C) и FFmpeg DTS (Set D).
- Языковые данные OCR и перевода, которые сейчас управляются в группе «Перевод, OCR», переносятся поверхностью управления в соответствующие разделы экрана загрузок - они уже существуют, переиспользуются их менеджеры.

**Столп F - Документация поведения.**
Описать «по запросу, выключено по умолчанию, докачивается при включении» в пользовательской документации (FEATURES трёхъязычно; для noLegal-специфики - в noLegal-документации).

### 5.2 Потоки данных и событий

- Поток включения: пользователь включает OCR/перевод → контракт способности сообщает «не установлено» → UX предлагает загрузку (с размером) → канал доставки скачивает и проверяет → состояние «установлено» персистится → способность подключается → действие выполняется.
- Поток отказа: пользователь отклоняет загрузку → способность остаётся выключенной → понятное сообщение → точки OCR/перевода ведут себя как недоступные.
- Поток повторного использования: способность «установлена» → при включении сразу доступна, докачки нет → ленивое подключение при первом фактическом вызове.
- Поток сборки: базовый артефакт не содержит ML/OCR-нативных библиотек/моделей; они существуют только как доставляемый набор.

### 5.3 Точки расширяемости

- Вводится контракт «доставляемой способности» в общем source-set с реализациями по флейвору/каналу доставки (магазинная доставка vs самостоятельная загрузка) и no-op/недоступностью, привязываемыми флейвор-специфичными DI-модулями - так канал доставки заменяется без правки базового кода.
- Контракт доставки обобщаем для будущих опциональных тяжёлых способностей (тот же UX и состояние).
- Точка перехвата включения едина для настроек и для триггеров в плеере/камере.

### 5.4 Доставляемые наборы (решено 2026-06-08)

Артефакты группируются по границам независимых нативных библиотек (у наборов нет общих `.so`, поэтому они доставляются и отказывают раздельно). Каждый набор ставится целиком (решение §6.3) - без состояния «часть установлена».

- **Set A - Перевод.** ML Kit Translate `.so` + language-id `.so` (~17.4 МБ/ABI). Языковые паки ML Kit и так качаются в рантайме, поэтому набор - только нативные движки. Канал по флейвору (решение владельца 2026-06-09, **отменяет self-load из B4** - проприетарные `.so` Google наш GitHub не хостит): на **store** (`standard`/`photos`/`legacy`) - официальный **Play dynamic-feature** (on-demand split, `playstore-dynamic-feature-support` + `SplitInstallHelper.loadLibrary`), бинари Google доставляет Play, перезаливки нет; на **sideload/VR** (`noLegal`/`vr`) ML Kit Translate **остаётся в базе (bundled)** - вес ~17.4 МБ там не вычитается (для sideload размер листинга не критичен). Гейт B4-PoC снят (self-load не применяется).
- **Set B - OCR-движки.** Tesseract `.so` (~7 МБ/ABI) + для `noLegal` нативные `.so` PaddleOCR (~9.6 МБ arm64, сейчас закоммичены в репозиторий). Это первопартийные/standalone `.so` под нашим контролем - чистая доставка каналом C без self-load хака. ML Kit Text-Recognition (~11 МБ) **исключается из проекта**: OCR-латиница покрывается Tesseract (`eng.traineddata`), движок по умолчанию и так Tesseract - так хрупкая self-load техника остаётся только у перевода. `.traineddata`/`.nb`-модели уже на доставке по запросу. OCR отделён от перевода: пользователю, которому нужен только OCR-в-буфер, не докачивается перевод.
- **Set C - Видео-визуализации аудио-плеера.** `res/raw/anim_audio_bg_1..5.mp4` (~6.1 МБ). Чистый ресурс без `System.load` и без верификации подписи - наименее рискованный набор, кандидат в первый пилот канала. Касается флейворов с анимациями (`standard`/`legacy`/`vr`/`noLegal`); из `lite`/`photos` release-шринкер их уже вырезает.
- **Set D - FFmpeg DTS-декодер.** Первопартийный `fms-ffmpeg-dts.aar` (~11.5 МБ, arm64 `libffmpegJNI.so`), флейворы `standard`/`noLegal`/`legacy`/`vr`. Самый крупный первопартийный нативный артефакт; включён в эту итерацию (решение 2026-06-08). UX-перехват - в точке запроса DTS-воспроизведения.

**Phase 0 - предпосылка для раздельных Set A и Set B.** Монолитный `TranslationManager` (~981 строка) владеет и OCR (`vision.text`), и переводом (`nl.translate` + language-id); даже чистый OCR-вызов идёт через него. Нативные библиотеки независимы, но код склеен, поэтому первой фазой S0386 идёт разнесение монолита на recognize-фасад (OCR) и translate-фасад (перевод) по образцу фасад+бэкенд из S0385 §6.1 (~37 файлов поверхности). До сплита Set A и Set B технически раздельны, но практически неразделимы.

### 5.5 Фикс регрессии: ленивый доступ к ML Kit (device-test, 2026-06-11)

- Симптом: `IllegalStateException: MlKitContext has not been initialized` при открытии Settings на `standard` (краш в `<init>`).
- Причина: на store-флейворах `MlKitInitProvider` удалён из базового манифеста и приезжает только с on-demand `:translate_feature`, поэтому `RemoteModelManager.getInstance()` падает до установки движка. `PrewarmTranslationModelUseCase` (`@Singleton`) строится жадно вместе с `SettingsViewModel`, и жадный `getInstance()` в инициализаторе поля ронял экран.
- Тот же жадный паттерн был в `TranslationBackend` (поле `modelManager`).
- Фикс: оба `modelManager` переведены на `by lazy` - ML Kit трогается только при первом реальном использовании (в `prewarm()` и за капабилити-гейтом `translateDirect()`), не при конструировании. Существующие try/catch деградируют до `Failed`/`null` без краша.
- Ре-тест: открыть Settings на `standard` (нет краша); сменить язык перевода -> prewarm; перевод в плеере после установки движка - всё работает.

## 6. Открытые вопросы / Research items

1. **Механизм доставки (требует решения владельца до реализации)**
   - **Вопрос:** какой канал доставки выбрать, с учётом того, что sideload-`noLegal` и `vr`/Quest не имеют надёжной магазинной доставки?
   - **Варианты:**
     - (A) Магазинная доставка по запросу (dynamic feature / on-demand split) - нативно для магазинных установок (`standard`/`photos`/`legacy`), но не работает для sideload-`noLegal` и Quest/Horizon.
     - (B) ML Kit unbundled (модели через сервисы Google Play) - модели качаются вне APK, но требует Google Play Services; неприменимо к Quest/sideload и не покрывает Tesseract (нативный).
     - (C) Самостоятельная загрузка нами размещённых бинарей/моделей с проверкой целостности/подлинности и подключением из защищённого хранилища - работает везде включая sideload/Quest; больше работы и ответственность за хостинг/безопасность на нас.
     - Гибрид: (A или B) для магазинных + (C) для sideload/Quest, либо (C) единообразно.
   - **Нужно выяснить:** выбор владельца (рекомендация - (C) самостоятельная загрузка с нашего хостинга, единообразно для всех, из-за критичного ограничения sideload/Quest и нежелания зависеть от чужих ссылок); затем формат проверки подлинности и политика обновления доставляемого набора при апдейте приложения.
   - **Уточнение владельца (2026-06-08):** все языковые пакеты и модели (для `standard` и `noLegal`) предварительно залить на наш GitHub как стабильное зеркало; в программе наша ссылка используется автоматически как ВТОРАЯ (fallback), если ссылка производителя «не отвечает». То есть это не «только наш хостинг», а упорядоченный список источников с автопереключением (производитель → наше зеркало). Для артефактов без официальной ссылки (напр. нативные `.so` ML Kit лежат в Maven-AAR, отдельного vendor-URL нет; модели Tesseract/прочее имеют официальные GitHub-источники) наше зеркало - первый/единственный источник.
   - **Решение владельца (2026-06-08):** вариант (C) - единый канал самостоятельной загрузки с автофейловером (производитель → наше зеркало) для всех флейворов; штатная магазинная доставка отдельно не реализуется. Хостинг зеркала: старт на GitHub Releases/raw, миграция на объект-сторадж/CDN при росте аудитории и троттлинге fair-use (клиент берёт URL из удалённого манифеста, поэтому переезд зеркала без релиза приложения).
   - **B4 - фисибилити выноса ML Kit `.so` (спайк 2026-06-08):** нативные `.so` ML Kit нельзя доставлять каналом C «штатно» - официальные пути on-demand у ML Kit только два, и оба не покрывают наш кейс: (1) Play dynamic-feature (`playstore-dynamic-feature-support` + `SplitInstallHelper.loadLibrary`) работает лишь при установке из Google Play - мимо sideload-`noLegal` и Quest/`vr`; (2) ML Kit unbundled (модели через Google Play Services) требует GMS, которого на Quest нет. **Следствие по способностям:** OCR от ML Kit не зависит (движок по умолчанию Tesseract, в `noLegal` - Paddle), поэтому ML Kit Text-Recognition исключается, а Set B доставляется чисто; перевод завязан только на ML Kit Translate. **Решение владельца (2026-06-08, ОТМЕНЕНО 2026-06-09):** была идея self-load - вытащить `.so`, залить на GitHub, грузить из `filesDir`. **Пересмотрено 2026-06-09:** проприетарные `.so` Google публично не перезаливаем. Итоговое решение по Set A: **store** - Play dynamic-feature (официальная on-demand доставка Google), **sideload/VR** - ML Kit Translate остаётся bundled в базе. Self-load ML Kit и гейт B4-PoC сняты; риск хрупкости self-load и юр-риск перезаливки устранены. OCR/Tesseract/Paddle/FFmpeg/видео-виз доставляются нашим каналом как прежде (OSS, перезаливка легальна).
   - **B1 источники (решено 2026-06-09):** модульные наборы `.so`/ассетов не имеют vendor-URL (Maven-AAR либо первопартийные), поэтому **primary = наше GitHub-зеркало**: Set A (ML Kit Translate + language-id `.so`), Set B (Tesseract `.so` + Paddle `.so`), Set C (видео-виз), Set D (FFmpeg DTS `.so`). Для store-установок Set A может позже получить primary = Play dynamic-feature, наш канал - fallback. Языковые данные сохраняют vendor primary и получают **наше зеркало как автофейловер**: Tesseract `.traineddata` - `raw.githubusercontent.com/tesseract-ocr/tessdata_best/4.1.0/` → зеркало; Paddle `.nb` - `paddlelite-demo.bj.bcebos.com/paddle-x/ocr/models/` → зеркало. Языковые паки ML Kit Translate качает её внутренний downloader - в наши наборы не входят (докачку на Quest проверить в B4-PoC).
   - **B2 подлинность (решено 2026-06-09):** SHA-256, **app-pinned** (как `SHA256_RUS`/`MIN_RUS_SIZE` в `TesseractModelManager`) - ожидаемый хеш и min-size зашиты в APK под версию приложения и служат якорем подлинности (зеркало не подменит payload - хеш не сойдётся). Детач-подпись отвергнута (лишнее управление ключами). Удалённый манифест отдаёт **только URL-ы** (чтобы менять эндпоинты без релиза), не хеши нативных `.so`. Проверка size + SHA-256 до `System.load`/использования; несовпадение → payload не устанавливается, мягкая недоступность, фейловер к следующему источнику.
   - **B2 версионирование (решено 2026-06-09; уточнено 2026-06-10):** реальное «версионирование» нативного кода живёт в зашитых в APK pinned-хешах/размерах (app-pinned), а не в URL. Поэтому:
     - payload'ы лежат на **фиксированном** релиз-теге зеркала (`delivery-so-v1`), общем для всех версий приложения, как GitHub Release-ассеты (бесплатно, не раздувают git-репо);
     - **версия элемента — в ИМЕНИ файла, не в пути** (решение владельца 2026-06-10): `<abi>-<soname>-<rev>.so` (напр. `arm64-v8a-libtesseract-v1.so`), `<name>-<rev>.mp4`. Новый несовместимый элемент (напр. новый OCR, требующий правок приложения) заливается под **новым именем** `…-v2.so` рядом со старым; старое `…-v1.so` остаётся навсегда → уже выпущенные версии приложения продолжают качать своё. Каждая версия приложения пинит в `DeliverableDescriptorCatalog` точное имя + SHA-256 + размер. Старые ревизии не удаляются. На устройстве файл — под обычным именем (`libtesseract.so`), версия только в удалённом. Видимый индекс хостинга — `delivery/INVENTORY.md`;
     - удалённый манифест URL-оверрайдов - **стационарный файл** (`delivery-so-v1/delivery-manifest.json`), НЕ ключуется по `versionCode` в пути (отменяет прежний `delivery-v<versionCode>/`). Пер-версийная изоляция URL не нужна: манифест отдаёт только URL, хэши app-pinned, при несовпадении - откат на bundled. Стационарный адрес и есть смысл манифеста: один файл, правится на месте для переезда эндпоинтов без релиза. Если пер-версийные URL когда-нибудь понадобятся - ключевать внутри JSON по `versionCode`, не в пути;
     - в APK зашит fallback-дескриптор (bundled URLs), поэтому первый запуск и отсутствие манифеста работают без сети-манифеста.
   - **B3 (2026-06-09, частично закрыт):** проверка `llvm-readelf` показала, что все доставляемые `.so` **уже ≥16 КБ-выровнены** (ML Kit Translate/language-id/Tesseract - `0x4000`; Paddle - `0x10000`; FFmpeg DTS - `0x4000`) - **пересборка не нужна**, только извлечь + залить. SHA-256 и размеры всех `.so` (arm64-v8a) посчитаны (app-pinned константы B2, см. `temp/S0386_B3_so_staging.md`). **OSS-наборы захостены и проверены:** GitHub-релиз `delivery-so-v1` несёт Tesseract+leptonica/jpeg/png (Set B), Paddle (Set B/noLegal), FFmpeg DTS (Set D); публичная докачка подтверждена (HTTP 200, SHA-256 совпал). База URL: `https://github.com/SerZhyAle/FastMediaSorter_mob_v2/releases/download/delivery-so-v1/arm64-v8a-<soname>`. **Остаётся:** (1) извлечь и захостить OSS `.so` для `armeabi-v7a`, чтобы 32-бит store-флейворы могли пройти Phase 05/07 без arm64-only допущения; (2) захостить Set C видео-ассеты до фактического de-bundle аудио-визуализаций. **Set A больше не входит в mirror-hosting scope:** на store он идёт через Play dynamic-feature, на sideload/VR остаётся bundled.
   - **Статус:** Partially resolved. Механизм + B1/B2/B4 закрыты; внешний остаток B3 - non-arm64 OSS hosting и hosting Set C ресурсов перед release/device-проверкой.

2. **Состав доставляемых наборов**
   - **Вопрос:** что именно входит в доставляемые наборы - перевод, два (три с PaddleOCR) OCR-движка, language-id, camera-OCR, прогрев моделей перевода, а также видео-визуализации аудио-плеера (~6.35 МБ)?

OCR отделён от перевода (независимые `.so`). Состав и размеры - в §5.4. Surprising-находки: нативные `.so` PaddleOCR (~9.6 МБ) закоммичены в репозиторий (не Maven); FFmpeg DTS AAR (~11.5 МБ) - крупнейший первопартийный нативный артефакт, внесён в scope как Set D; модели (traineddata/`.nb`/ML-паки) уже на доставке по запросу, приз - нативные библиотеки, не модели.
   - **Статус:** Resolved

3. **Поведение при частичной доступности**

## 9. Архитектурные решения (ADR)

**ADR-1: Единое поведение для пользователя при разном канале доставки по флейвору**

- **Решение:** один контракт способности и один UX перехвата; технический канал доставки выбирается по флейвору (магазинный для store, самостоятельная загрузка для sideload/Quest).
- **Альтернативы:** один канал для всех (только магазинный - не покрывает sideload/Quest; только самостоятельный - больше работы для всех).
- **Почему:** sideload-`noLegal` и Quest физически не получают магазинную доставку, а единый UX важен для пользователя.

**ADR-2: Дефолт «выключено»; апгрейд-реконсиляция тумблера и установленности**

- **Решение:** новые установки - OCR/перевод выключены. При **обновлении** с версии, где код был в базе, на версию с де-бандлом возникает рассинхрон: у активного пользователя тумблер сохранён ON, но payload физически ушёл из базы и не скачан. Это примиряется так (запрос владельца 2026-06-10):
  - **Выбрано - вариант 1.1 (force-OFF при апгрейде):** одноразовая миграция при первом запуске после де-бандл-апгрейда выключает тумблеры наборов-загрузок, которые ON, но набор не установлен. Состояние становится честным (OFF); повторное включение запускает штатный prompt с оценкой размера. Проще и безопаснее автозагрузки.
  - **Отклонено - вариант 1.2 (автозагрузка при апгрейде):** тихо докачивать ушедший код после установки. Противоречит §2.3-2.5 (осознанная загрузка, без навязывания), возвращает вес на первый запуск, сложнее (ошибки/прогресс в момент апгрейда).
  - **Подстраховка (1.0, уже в коде):** даже без миграции перехват включения работает в точке использования - кнопка перевода в плеере (`TranslationButtonManager`), камера-OCR (`CameraOcrFlowManager`) и тумблеры настроек при не-установленном наборе предлагают скачать (с размером); ничего не падает. 1.1 добавляет честность состояния тумблера сверх этой подстраховки.
- **Альтернативы:** оставить как 1.0 (тумблер ON при неустановленном наборе - слегка вводит в заблуждение); 1.2 (отклонено).
- **Почему:** требование §2.3/§2.4 - выключено по умолчанию и осознанная докачка по размеру; де-бандл делает «ON без payload» нечестным состоянием, которое 1.1 устраняет без тихих загрузок.

**ADR-3: Обязательная проверка подлинности самостоятельно загружаемых бинарей**

- **Решение:** для канала (C) - верификация целостности/подписи до подключения.
- **Альтернативы:** доверять источнику без проверки (недопустимо).
- **Почему:** загрузка исполняемого нативного кода в процесс - вектор атаки.

## 11. Критерии готовности (strategic-level)

1. Базовый release-артефакт каждого затронутого флейвора не содержит ML/OCR-нативных библиотек и моделей, нативных `.so` PaddleOCR (`noLegal`), FFmpeg DTS `.so`, а также видео-визуализаций аудио-плеера (`res/raw/anim_audio_bg*`) - проверяется распаковкой.
2. После чистой установки OCR/перевод и связанные механизмы выключены на всех профилях устройств.
3. Включение OCR/перевода у пользователя без установленного функционала показывает предложение скачать с оценкой размера и прогрессом; после успешной установки действие выполняется.
4. Повторное включение уже установленного функционала не запускает докачку.
5. Отказ от загрузки оставляет способность выключенной с понятным сообщением и без краша.
6. Установленный функционал доступен после обновления приложения и очистки кэша без повторной докачки.
7. Качество OCR/перевода после установки совпадает с текущим.
8. Поведение «по запросу» отражено в пользовательской документации (трёхъязычно; noLegal-специфика - в noLegal-документации).
9. В настройках есть кнопка на экран «Загружаемые расширения»; экран показывает единый список модулей и языковых данных со статусом и размером, позволяет скачать недостающее и удалить установленное (с освобождением места); удаление модуля возвращает способность в «не установлено».
