# Research 02 - Стратегия стартового таймаута докачки/стрима (столп A)

**Спек:** S0529
**Статус:** Resolved (2026-06-19, решение владельца)

## Текущие значения (по коду политики пред-кэша)

- Общий сетевой стартовый таймаут аудио: 20 000 мс.
- Специальный ранний таймаут для SFTP-аудио: 5 000 мс, с флагом «прямой стрим как фолбэк».
- То есть для SFTP сейчас один короткий порог на весь старт: не успели за 5 c - сразу прямой стрим (привязанный к экрану плеер).

## Проблема единого короткого порога

- 5 c меряют сразу всё: и установление соединения, и начало передачи. На живом-но-медленном сервере 5 c не хватает на передачу, и происходит фолбэк, ломающий продолжаемость.
- При этом длинный единый таймаут (20 c) вреден для недоступного сервера: пользователь ждёт 20 c впустую.

## Решение владельца: разделить connect и transfer

- **Connect-таймаут** - короткий и фиксированный (порядка 5 c). Недоступный сервер ловится быстро, пользователь не ждёт.
- **Transfer-таймаут** (после успешного connect) - адаптивный от последней измеренной скорости соединения, грубо, без оверинжиниринга. Сервер уже ответил, значит можно щедро ждать передачу.
- **Fallback при отсутствии измерения** (первое обращение к серверу в сессии) - умеренный дефолт порядка существующего сетевого (20 c).
- **Без пользовательской настройки** таймаута - чтобы не путать пользователя.

## Опора в существующем коде

- Измеренная скорость соединения уже доступна (последнее измерение по ключу ресурса) - её можно использовать для адаптивного transfer-таймаута.
- Регулятор сетевого параллелизма уже различает деградированное состояние ресурса (повторные таймауты) - это пригодный сигнал для расширенных таймаутов.

## Связь с prefetch следующего трека

- Короткий стартовый бюджет SFTP не должен применяться к фоновой подготовке следующего трека - у неё есть всё время звучания текущего (см. research/03).
