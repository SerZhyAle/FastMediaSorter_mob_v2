# Research 01 - Потоковое воспроизведение сетевых/облачных источников фоновым сервисом

**Спек:** S0529
**Статус:** Resolved (2026-06-19, по коду) - вариант 1 признан реализуемым и предпочтительным

## Вопрос

Может ли движок фонового сервиса воспроизводить SMB/SFTP/FTP и облачные источники напрямую (тем же механизмом источников данных, что и встроенный плеер), без обязательной полной докачки в локальный файл?

## Ответ: да, вариант 1 реализуем

Ключевые факты по коду:

- Фоновый аудио-сервис строит свой движок воспроизведения **без** кастомной фабрики источников медиа - используется фабрика по умолчанию, которая умеет только локальные/HTTP-источники. Именно поэтому сетевые и облачные треки сейчас требуют предварительной полной докачки в локальный кэш, после чего сервис играет из `file://`.
- В проекте уже есть протокольные фабрики источников данных для SFTP, SMB, FTP и облака. Встроенный (привязанный к экрану) плеер именно ими стримит сеть напрямую: соответствующие протокольные помощники воспроизведения собирают фабрику источника медиа и подставляют её в движок.
- Фоновый сервис помечен как Hilt entry point, то есть может получить через DI тот же репозиторий учётных данных и собрать те же протокольные фабрики, что и встроенный плеер.

Вывод: подставив протокольную фабрику источников медиа в движок сервиса (как это делает встроенный плеер), сервис сможет воспроизводить сетевой и облачный источник потоково без обязательной полной локальной копии. Это единым образом закрывает все три грани спека:

- продолжаемость при выходе (трек изначально в сервисе - механизм «всегда продолжать» применяется);
- старт без раннего фолбэка на привязанный к экрану плеер;
- межтрековую паузу (следующий трек ставится в очередь сервиса потоково - см. research/03).

## Остаточные риски / что подтвердить при реализации

- **Учётные данные в процессе сервиса.** Путь получения учётных данных ресурса в сервисе должен переиспользовать существующий механизм; подтвердить, что протокольные фабрики получают их так же, как во встроенном плеере.
- **Батарея и устойчивость.** Потоковое сетевое воспроизведение в фоне при нестабильном канале: предусмотреть деградацию к докачке/буферизации, сравнить расход с текущим путём.
- **Сохранение позиции.** Сервис сохраняет позицию по стабильному сетевому пути (не по пути кэша) - при потоковом источнике ключ позиции должен остаться сетевым путём, не URI кэша.

## Отклонённые варианты

- Вариант 2 (передавать сервису уже идущую сессию запасного пути на выходе) - сложнее по состоянию, не чинит межтрековую паузу.
- Вариант 3 (оставить докачку, завершать её в фоне после выхода) - паллиатив, не делает потоковый старт продолжаемым сразу.
