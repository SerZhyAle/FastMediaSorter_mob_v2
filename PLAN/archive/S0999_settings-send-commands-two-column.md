## 0. Захваченный материал (inbox)

**Захвачено:** 2026-07-11

**Текст:**

в ландшафте, а так же когда ширина экрана позволяет в портрете показывать список элементов настроек "Плеер" группы "Команды отправлять файл в.."  в две колонки

**Технический контекст (на момент захвата, для будущего расследования):**
- Группа «Send file to..» = `settings_send_commands_group`, контейнер `containerSendCommands` в `app_v2/src/main/res/layout/fragment_settings_playback.xml` (+ `layout-land/` двойник) - вертикальный `LinearLayout`.
- Строки НЕ статичны: генерятся в рантайме в `PlaybackSettingsFragment.setupSendCommandsGroup()` (по одному `SettingsToggleRow` на каждый зарегистрированный ShareTarget, каждая `MATCH_PARENT`).
- Существующий канон мультиколонки (S0609) - чистый XML weighted-LinearLayout, только `layout-land/`; здесь НЕ применим напрямую: (1) строки динамические, надо менять логику населения в Kotlin; (2) требование «в портрете, когда ширина позволяет» - адаптив по ширине, который S0609 осознанно отложил (sw-qualified бакеты).

---

## 1. Проблема

- Группа «Send file to..» (таб Playback настроек) рендерит тогглы ShareTarget одной вертикальной колонкой при любой ширине экрана.
- В ландшафте и на широких экранах правая половина карточки пустует, список неоправданно длинный - лишний вертикальный скролл и худшая обзорность, особенно при большом числе зарегистрированных таргетов.

---

## 2. Цели

1. В ландшафте список тогглов «Send file to..» раскладывается в две колонки.
2. Число колонок читается из ресурса - механика готова к включению широкого портрета без правки Kotlin.
3. Узкий портрет остаётся одноколоночным - без регрессий текущего поведения.

**Non-goals:**

- Мультиколонка других групп настроек (только «Send file to..»).
- Изменение самих `SettingsToggleRow`, их данных, async-догрузки лейблов/иконок установленных приложений.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Двухколоночность не только в ландшафте, но и в портрете «когда ширина позволяет» (порог = `sw600dp`, см. §6).

### 3.2 Жёсткие ограничения

- **Flavor:** все (общий экран настроек, `src/main`).
- **API level:** без API-специфики.
- **Wear OS:** не затрагивается.
- **Производительность:** пересборка группы - редкое событие (открытие таба / поворот); бюджет некритичен.
- **Совместимость данных:** настройки и данные не меняются.
- **Локализация:** новых строк не вводится (переиспользуются существующие тогглы) - EN/RU/UK не затрагиваются.
- **Доступность:** порядок фокуса D-pad / TalkBack при двух колонках обязан оставаться логичным.

### 3.3 Owner inputs (Approval gate)

- **Related tickets:** S0609 (канон мультиколоночных настроек), S0452 (происхождение группы «Send file to..»).

## 4. Контекст текущей архитектуры

- Экран - `PlaybackSettingsFragment` (таб Playback в `SettingsActivity`). Группа «Send file to..» - карточка `cardSendCommands`, контент - `containerSendCommands`: вертикальный `LinearLayout`, идентичный в `layout/` и `layout-land/`.
- Строки динамические: `setupSendCommandsGroup()` очищает контейнер и добавляет по одному `SettingsToggleRow` (`MATCH_PARENT`) на каждый ShareTarget из реестра; лейблы и launcher-иконки установленных приложений догружаются с IO-потока и применяются к уже добавленным строкам.
- Поэтому S0609-канон (чистый weighted-XML в `layout-land`) напрямую не применим: число колонок и их население задаются из Kotlin, а XML лишь описывает контейнер.

---

## 5. Предлагаемый подход

### 5.1 Основные столпы / модули

- **Ресурс числа колонок:** `@integer/settings_send_commands_columns` (`values/`=1, `values-land/`=2, `values-sw600dp/`=2). Единственный источник правды «сколько колонок» - декларативный, кэшируется системой per-config. Бакет `values-sw600dp/` даёт 2 колонки и в портрете, и в ландшафте на экранах `sw>=600dp`; конфликта с `values-land` нет (оба значения = 2), поэтому combined `values-sw600dp-land/` бакет не нужен (sw-квалификатор перекрывает `land`, но значение то же).
- **Контейнер-раскладка:** `containerSendCommands` становится горизонтальным контейнером, население которого - N взвешенных (`weight=1`, `width=0`) вертикальных колонок, создаваемых из Kotlin.
- **Популяция:** `setupSendCommandsGroup()` читает число колонок, создаёт колонки, распределяет строки-тогглы по колонкам, добавляет колонки в контейнер. При `columns=1` поведение идентично текущему (одна колонка на всю ширину).

### 5.2 Потоки данных и событий

- Открытие таба Playback / rebuild -> `setupSendCommandsGroup()` -> `getInteger(columns)` -> построение колонок -> распределение строк -> async-апгрейд лейблов/иконок (без изменений).
- Поворот -> пересоздание фрагмента ИЛИ `onConfigurationChanged` -> повторный `setupSendCommandsGroup()` с актуальным ресурсом -> число колонок обновляется (см. риск в §7).

### 5.3 Точки расширяемости

- Широкий портрет и 3+ колонки - добавлением бакетов ресурса (`values-sw600dp/`, `values-sw720dp/`) без правки Kotlin.

## 6. Открытые вопросы / Research items

Все четыре решены владельцем через `/spec-quiz` (2026-07-11); детали - в блоке решений ниже:

1. **Портретный порог.** RESOLVED: `sw600dp`. 2 колонки в портрете от 600dp ширины (7"+ планшеты, раскладные); комфортные ~300dp на колонку под длинные RU/UK имена приложений. Новый бакет `values-sw600dp/`.
2. **Число колонок на очень широких экранах.** RESOLVED: максимум 2. Совпадает с названием тикета «двухколоночный» и каноном S0609 (3-up обрезает RU/UK лейблы). 3+ - будущее расширение бакетом ресурса без правки Kotlin.
3. **Порядок распределения строк.** RESOLVED: column-major (заполнить левую колонку сверху вниз, затем правую). Сохраняет вертикальный порядок чтения и логичный D-pad / TalkBack (§3.2).
4. **Один таргет / нечётное число.** RESOLVED: `<=1` таргет -> 1 колонка на всю ширину; нечётное `n>1` -> column-major balanced (левая колонка длиннее на 1). Решено без вопроса владельцу - единственный логичный вариант (одиночный тоггл в полуколонке с пустой правой = сломанный вид).

### Quiz decisions (2026-07-11)

- Портретный порог 2 колонок -> `sw600dp` (комфортная ширина колонки под длинные RU/UK имена; проект расширяется sw-бакетами).
- Максимум колонок на широких экранах -> 2 (название тикета «двухколоночный» + канон S0609; 3+ отложено в расширяемость через бакет ресурса).
- Порядок раскладки -> column-major (вертикальный порядок чтения, логичный D-pad / TalkBack per §3.2).
- Один / нечётное число таргетов -> `<=1` таргет = 1 колонка; нечётное = column-major balanced (resolved without asking - единственный логичный вариант).

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Нелогичный порядок фокуса D-pad / TalkBack при 2 колонках | Средняя | плохая доступность | column-major сохраняет вертикальный порядок чтения; при необходимости задать `nextFocus*` между колонками |
| Поворот не пересобирает группу (если `SettingsActivity` на `configChanges`) | Средняя | колонки не переключаются до переоткрытия таба | пересобрать в `onConfigurationChanged`, если пересоздания фрагмента нет |
| Неравная высота колонок при нечётном числе | Низкая | косметика | column-major balanced (левая колонка длиннее на 1) |

## 9. Архитектурные решения (ADR)

- **ADR-1: число колонок через `@integer`-ресурс, не через runtime-измерение ширины View.** Декларативно, кэшируется системой per-config, тривиально расширяется sw-бакетами; runtime-измерение дублировало бы то, что квалификаторы ресурсов дают бесплатно.
- **ADR-2: колонки строятся в Kotlin, а не чистым XML (в отличие от S0609).** Строки населяются динамически из реестра ShareTarget - XML не знает их число.

## 11. Критерии готовности (strategic-level)

1. В ландшафте тогглы «Send file to..» видны в две колонки; все таргеты присутствуют и переключаются.
2. В узком портрете - одна колонка, как раньше (без регрессий).
3. Поворот портрет <-> ландшафт переключает число колонок без потери состояния тогглов.
4. Порядок фокуса (D-pad / TalkBack) по колонкам логичен.
5. Портретный порог `sw600dp` включает 2 колонки на портрете шириной `>=600dp`; на более узком портрете - 1 колонка.
