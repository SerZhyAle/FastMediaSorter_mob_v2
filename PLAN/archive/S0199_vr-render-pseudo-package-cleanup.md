## 1. Проблема

В `src/main/java/com/sza/fastmediasorter/vr/render/` лежат шесть flavor-нейтральных data-классов (enum, sealed, interface, factory), название пакета которых явно сообщает "это VR-код". Имя вводит в заблуждение: оно намекает, что классы — часть VR-сборки и должны находиться в `src/vr/java/`, тогда как фактически они компилируются во все flavor'ы и используются как контракт между общим кодом и реальной VR-реализацией. Любой агент или новый разработчик, читая структуру каталогов, делает неверный вывод о том, где располагать новый код, связанный со стереоскопическим рендерингом.

## 2. Цели

1. Имя пакета корректно сообщает читателю, что классы внутри flavor-нейтральные.
2. Никакого VR-специфичного исполняемого кода не остаётся в `src/main/java/` под путём, содержащим сегмент `vr`.
3. Существующие потребители (через интерфейс) продолжают работать без поведенческих изменений.
4. Каталог классов (`dev/CATALOG/app_v2.jsonl`) отражает новое расположение и помечает классы как используемые во всех flavor'ах.

**Non-goals:**

- Не трогать остальные 169 точек `BuildConfig.SUPPORT_*` в `src/main/java/` — это отдельный техдолг.
- Не переносить классы физически в `src/vr/java/` — это потребует interface'ов и сломает их доступность из других flavor'ов; они flavor-нейтральны по сути.
- Не менять публичное API классов (имена типов, методов, поля sealed-иерархии).

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Желательно за один коммит, обратимый одной командой revert.
2. Если переименование пакета затрагивает много use-site'ов — допустимо разнести на 2 фазы: переименование + обновление импортов.

### 3.2 Жёсткие ограничения

- **Flavor:** изменение видно во всех flavor'ах (`standard`, `lite`, `photos`, `legacy`, `vr`, `vrUnlicensed`, `noLegal`), реализация остаётся flavor-нейтральной согласно `dev/FLAVOR_DEVELOPMENT_RULES.md`.
- **API level:** без API-специфики.
- **Wear OS:** не затрагивается.
- **Производительность:** без бюджета — чистый rename, время выполнения не меняется.
- **Совместимость данных:** не применимо — нет персистентных классов в затронутом пакете.
- **Локализация:** не применимо — нет user-facing строк.
- **Доступность:** не применимо — нет UI-кода.

## 4. Контекст текущей архитектуры

Пакет `vr/render` появился исторически как место для классов, описывающих абстракцию слоя композиции (типы слоёв, фабрика для создания, контекст рендеринга, планировщик). Реальная реализация рендеринга живёт в `src/vr/java/.../vr/render/` (другая папка с тем же именем), но в качестве **контракта** между общим UI/доменом и VR-реализацией классы из main используются. По мере накопления знаний оказалось, что имя пакета `vr/render` в main сбивает с толку: на этапе аудита flavor-изоляции (2026-05-14) этот пакет первым вызвал подозрение о compile-time leak, хотя по факту классы являются flavor-нейтральной абстракцией. Прямой переход на `src/vr/` невозможен, потому что некоторые потребители живут вне vr-flavor'ов (например, общий слой управления плеером ссылается на типы layer-descriptor для логики выбора пути отрисовки).

## 5. Предлагаемый подход

Переименовать пакет так, чтобы имя сообщало назначение (общая абстракция стереоскопического / специализированного рендеринга), без сегмента `vr`. Все use-site'ы обновляются механически. Поведение не меняется.

### 5.1 Основные столпы / модули

- **Переименование пакета.** Сегмент `vr` уходит из имени пакета классов, остающихся в main.
- **Обновление потребителей.** Все импорты в `src/main/`, `src/vr/`, `src/noLegal/` и других flavor source-set'ах синхронно переезжают на новый путь.
- **Каталог.** Записи в `dev/CATALOG/app_v2.jsonl` пересоздаются по новому пути с сохранением manual-полей (`role`, `status`, function descriptions) через `scan.ps1` (merge ключ — `path + class`, поэтому при смене path записи будут пересозданы; manual поля нужно перенести вручную или допустить регенерацию).

### 5.2 Потоки данных и событий

Без изменений. Контракт между общим кодом и VR-реализацией остаётся тем же: общий код знает только interface/sealed, VR-реализация в `src/vr/` поставляет конкретные стратегии через Hilt-биндинг.

### 5.3 Точки расширяемости

Открытым остаётся вопрос имени нового пакета. Кандидаты: `core/render/stereoscopic`, `domain/render`, `domain/visualization/layer`. Выбор финального имени делается на стадии `/spec-tech` после проверки коллизий и согласованности с соседними пакетами.

## 9. Архитектурные решения (ADR)

**ADR-1: Классы остаются в `src/main/java/`, переименовывается только пакет.**

- **Решение:** не переносить шесть классов из main в `src/vr/java/`.
- **Альтернативы:** (a) физический перенос в `src/vr/java/` + interface'ы в main; (b) текущий status quo с псевдоименем `vr/render`.
- **Почему:** классы flavor-нейтральные (data + abstraction), используются в non-vr flavor'ах. Перенос в `src/vr/` создаст compile-time leak в обратную сторону — потребуется новый interface слой в main, который не нужен по существу проблемы. Status quo с псевдоименем нарушает принцип "имя пакета не должно врать".
