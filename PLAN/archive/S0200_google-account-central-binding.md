# Стратегическая спецификация: S0200 — Central Google Account binding

**Ticket:** S0200
**Status:** Verified
**Priority:** 50
**Date:** 2026-05-14
**Tier:** 3 — Moderate (ad-hoc)
**Roadmap entry:** Ad-hoc — запрос 2026-05-14 (привязка единого Google-аккаунта для прозрачной работы Drive и сопутствующих Google-интеграций)
**Tactical plan:** `PLAN/S0200_google-account-central-binding/INDEX.md`

> **Scope:** STRATEGIC. Цели, ограничения, открытые вопросы. Без имён классов, путей, лимитов строк, миграций Room, модулей Hilt.

---

## 1. Проблема

Google-интеграции в приложении живут разрозненно. Drive требует отдельной авторизации на каждый добавляемый ресурс — повторный sign-in для одного и того же аккаунта пользователя. Прочие Google-сервисы (YouTube Music search, Lens, отправка по email) работают через intent и не знают, какой Google-аккаунт пользователь считает «своим» в нашем приложении. Используемый для Drive Google Sign-In API устарел: Google рекомендовал миграцию на Credential Manager в 2024. Дополнительно, для in-app браузера используется WebView, что несовместимо с политикой OAuth Google для google.com / youtube.com — пользователь не может корректно войти в свой Google-аккаунт прямо внутри приложения для тех источников, где это нужно.

---

## 2. Цели

1. Пользователь один раз привязывает свой Google-аккаунт к приложению, после чего этот аккаунт считается «основным» (primary) для всех Google-интеграций.
2. Добавление нового Drive-ресурса под основным аккаунтом не требует повторного интерактивного входа — приложение использует уже сохранённую привязку.
3. Для добавления Drive-ресурса с другим Google-аккаунтом сохраняется существующий путь (явный выбор/добавление другого аккаунта в момент создания ресурса).
4. Открытие Google-домен URL внутри встроенного браузера приложения происходит через системный механизм Chrome Custom Tabs, наследующий сессию Chrome пользователя; WebView для Google-доменов больше не используется.
5. Текущая авторизация Drive переведена с устаревшего Google Sign-In на современный Credential Manager без потери уже добавленных Drive-ресурсов и сохранённых аккаунтов.
6. Архитектура хранения аккаунта изолирует «привязку Google-аккаунта» как самостоятельную единицу, способную обслуживать произвольный набор OAuth scope-ов (не только Drive) — для последующего подключения других Google API без правок ядра.
7. Sign-out из основного Google-аккаунта помечает связанные Drive-ресурсы как «требуется вход», но конфигурации этих ресурсов (выбранные папки, имена, флаги синхронизации) сохраняются для последующего восстановления одним повторным входом.
8. После обновления приложения сохранённый auth-стейт Drive (закэшированные токены, сериализованные identity-данные предыдущих версий) очищается; конфигурации Drive-ресурсов сохраняются. Пользователь видит, что ресурсы перешли в режим «требуется вход», и регистрирует primary-аккаунт заново через карточку настроек — это ожидаемая часть обновления, а не сбой.

**Non-goals:**

- Интеграция Gmail API для отправки писем (restricted scope, требует формального security assessment Google; UX уже покрыт системным share intent).
- Интеграция YouTube Data API / YouTube Music API для in-app поиска или воспроизведения (нет публичного API стриминга YouTube Music; текущий intent-flow в YouTube Music app достаточен).
- Интеграция Google Photos API (restricted scope, вне инвентаря фич).
- Регистрация Google-аккаунта на уровне ОС через системный `AccountManager` (избыточно для нашего use case; не даёт ощутимой пользы относительно in-app хранилища).
- Перевод не-Google источников аутентификации (Instagram, Facebook, Threads и т.п.) во встроенном браузере на Chrome Custom Tabs — они продолжают работать через WebView.
- Поддержка одновременно нескольких primary-аккаунтов: primary — ровно один.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Карточка «Google Account» в настройках показывает текущий привязанный аккаунт (email, отображаемое имя, аватар) и предоставляет действия sign-in / sign-out.
2. При sign-in приложение запрашивает минимальный набор scope-ов, нужный текущему набору фич (изначально — Drive + email + profile); добавление новых Google-фич в будущем должно уметь дозапрашивать дополнительные scope-ы без отвязки primary-аккаунта. При показе диалога дозапроса пользователь видит список уже выданных scope-ов и пояснение, зачем нужен новый.
3. Состояние «требуется вход» для Drive-ресурса визуально отражается в списке ресурсов (иконка или метка), а не открывается тихо ошибкой при попытке доступа.
4. Текст карточки и сообщений соответствует `docs/COMMUNICATION_POLICY.md` (тон, формулировки, выбор формул обратной связи).

### 3.2 Жёсткие ограничения

- **Flavor:** все cloud-enabled флаворы по фактической матрице `app_v2/build.gradle.kts` (`SUPPORT_CLOUD = true`): `standard`, `noLegal`, `photos`, `legacy`, `vr`, `vrUnlicensed`. Cloud-функционал и Google-аккаунт привязки недоступны в `lite` (`SUPPORT_CLOUD = false`). Реализация следует `dev/FLAVOR_DEVELOPMENT_RULES.md` по образцу уже существующего split-а `streamingEnabled/streamingDisabled` (S0116): контракт привязки и no-op fallback описываются в общем коде (`src/main/java`); реальная Credential Manager реализация и её Hilt-биндинг живут в shared source set `src/cloudEnabled/java`, монтируемом в каждый cloud-enabled флавор; для `lite` монтируется `src/cloudDisabled/java` с no-op биндингом. Внутри общего кода запрещено использовать `BuildConfig.SUPPORT_*` проверки.
- **API level:** `minSdk 26` (standard). Credential Manager поддерживается через совместимый shim для API <28 — это не накладывает дополнительных ограничений.
- **Wear OS:** не затрагивается. Wear-модуль не имеет Drive и не получает привязки Google-аккаунта.
- **Производительность:** интерактивный sign-in запускается один раз, последующие операции работают через silent token refresh; визуальных задержек на старте приложения быть не должно (инициализация привязки — асинхронная, ленивая).
- **Совместимость данных:** сохранённый auth-стейт Drive (закэшированные токены, сериализованные identity-данные, multi-account credentials записи) полностью очищается при первом запуске обновлённой версии. Конфигурации Drive-ресурсов (выбранные папки, имена, флаги синхронизации) сохраняются — пользователь видит свои ресурсы в списке, но в состоянии «требуется вход». Primary-аккаунт регистрируется заново через карточку настроек; вторичные Drive-аккаунты пересоздаются по мере того, как пользователь подтверждает доступ к каждому ресурсу. Автоматический выбор «какой из старых аккаунтов сделать primary» не выполняется.
- **Локализация:** все новые пользовательские строки добавляются на EN, RU, UK одновременно. После добавления — обязательный прогон аудита локализации.
- **Доступность:** карточка «Google Account» доступна через TalkBack (контентные описания для email и состояния); состояние «требуется вход» у Drive-ресурса не должно отличаться только цветом.
- **Политика OAuth Google:** для in-app браузерных потоков, открывающих google.com / accounts.google.com / youtube.com / music.youtube.com, использовать только системный Chrome Custom Tabs. Использование WebView для этих доменов запрещено. Fallback на внешний VIEW-intent либо WebView для Google-доменов запрещён.
- **Зависимость от CCT-провайдера:** функционал привязки primary-аккаунта и Google-домен auth-flows в in-app browser требует наличия на устройстве хотя бы одного браузера, поддерживающего Chrome Custom Tabs. При отсутствии CCT-провайдера приложение отказывает в выполнении sign-in и Google-домен auth-flow с явным объяснением и предложением установить совместимый браузер; повторная попытка возможна без перезапуска приложения. Прочая функциональность (локальные ресурсы, SMB/FTP/SFTP, не-Google встроенный браузер) продолжает работать без ограничений.
- **Коммуникационная политика:** все user-visible строки (карточка аккаунта, диалог sign-out, уведомления «требуется вход», ошибки авторизации, CTA) проходят чек-лист `docs/COMMUNICATION_POLICY.md` §6 перед интеграцией.
- **Restricted scopes:** в спецификации запрещено вводить scope-ы из категории Google Restricted (Gmail, Google Photos, YouTube user-data) без явного отдельного тикета и явного решения о прохождении Google Security Assessment.

## 4. Контекст текущей архитектуры

Авторизация Google Drive сейчас централизована внутри Drive-стека и не выходит за пределы cloud-слоя. Сохранение токенов и identity-данных — в зашифрованном prefs-хранилище под отдельным именем. Multi-account для Drive реализован через per-account ключи в том же хранилище. Прочие фичи, упоминающие Google (Lens, YouTube Music, share), не имеют точки входа к этой identity — каждая использует ОС-уровневое поведение (intent в установленное Google-приложение, использующее системный аккаунт устройства). In-app браузер использует WebView с собственным cookie jar и список известных auth-источников; YouTube включён в этот список, но фактически исключён из WebView-extraction для медиа. Поток отправки текстовых/файловых сообщений на email использует системный `ACTION_SEND`.

Из-за такой раздробленности нет компонента, который бы хранил «primary Google account приложения». Каждое расширение Google-интеграций (например, добавление YouTube Data API для метаданных или замена in-app браузера на CCT для Google-сайтов) сейчас потребовало бы дублирования логики идентификации и привязки. Cloud-слой к тому же опирается на устаревший Google Sign-In API, что блокирует чистое расширение scope-ов и накапливает долг подавлений deprecation-предупреждений.

## 5. Предлагаемый подход

Ввести самостоятельный домен «Google identity» как отдельную ответственность вне cloud-слоя. В этом домене хранится ровно одна primary-привязка, идентифицирующая основной Google-аккаунт пользователя, и интерфейс выдачи/обновления OAuth-токенов под произвольный набор scope-ов. Cloud-слой (Drive) перестаёт быть единоличным владельцем sign-in логики и становится клиентом этого домена. In-app браузер получает отдельную точку маршрутизации Google-домен URL во внешний/системный авторизационный канал (CCT) вместо WebView.

### 5.1 Основные столпы / модули

- **Identity-домен Google-аккаунта.** Содержит контракт привязки, состояние primary-аккаунта (привязан / не привязан / помечен как «требует повторного входа»), реактивный поток состояния для UI, операции sign-in, sign-out, дозапроса дополнительных scope-ов, выдачи access-токена под запрошенный scope с прозрачным silent-refresh. Источник истины об «основном Google-аккаунте» приложения.
- **Реализация identity-домена через Credential Manager.** Реальная имплементация шарится через source set `src/cloudEnabled/java` и монтируется в `standard`, `noLegal`, `photos`, `legacy`, `vr`, `vrUnlicensed` (см. §3.2). Для `lite` через `src/cloudDisabled/java` поставляется no-op Hilt-биндинг, гарантирующий, что попытки получить identity в lite корректно возвращают «не доступно».
- **Cloud-слой Drive.** Перестраивается как потребитель identity-домена. Логика «получить токен под Drive-scope» делегируется identity-домену. Multi-account Drive остаётся, но primary-аккаунт идентифицируется не Drive-слоем, а identity-доменом. Вторичные Drive-аккаунты остаются в существующей multi-account модели без подъёма в primary.
- **Состояние Drive-ресурсов «требуется вход».** Cloud-слой получает способ маркировать ресурс как требующий повторного входа без удаления конфигурации. Состояние видно в списке ресурсов и инициирует поток восстановления одним действием пользователя.
- **In-app browser routing для Google-доменов.** Слой встроенного браузера получает гейт, отделяющий Google-домены (google.com, accounts.google.com, youtube.com, music.youtube.com и поддомены) от остальных. Google-домен auth-потоки направляются в Chrome Custom Tabs; не-Google источники продолжают идти через WebView. Список Google-доменов определяется в одном месте и допускает расширение.
- **Настройки → Google Account.** Новая карточка в настройках для управления primary-привязкой: текущее состояние, sign-in, sign-out, диагностика. Размещение и иерархия — в тактической спеке.

### 5.2 Потоки данных и событий

- UI настроек → identity-домен (sign-in) → Credential Manager-консент → identity-домен (сохранение primary, эмиссия состояния) → UI обновляется.
- UI добавления Drive-ресурса → identity-домен (запрос текущей primary-привязки) → если primary существует → cloud-слой (выдача access-токена под Drive-scope без UI) → переход к выбору папки. Если primary отсутствует или пользователь выбрал «другой Google-аккаунт» → существующий interactive Drive-sign-in path с записью аккаунта в multi-account хранилище.
- Drive-операция получает 401 → cloud-слой запрашивает у identity-домена freshen-token → identity-домен выполняет silent-refresh → cloud-слой повторяет запрос. При неуспехе silent-refresh → cloud-слой помечает ресурс как «требуется вход» и эмитит сигнал в UI.
- Sign-out пользователя → identity-домен сбрасывает primary-привязку и эмитит событие → cloud-слой проходит по Drive-ресурсам, привязанным к этому primary-аккаунту, и помечает их как «требуется вход» (конфигурации сохраняются). Прочие Drive-ресурсы (под другими аккаунтами в multi-account модели) не затрагиваются.
- In-app браузер открывает URL → routing-слой проверяет хост против Google-домен набора → если совпадает → запуск CCT с базовым intent; если нет → продолжается стандартный WebView-flow.

### 5.3 Точки расширяемости

- Identity-домен принимает scope-ы как параметр выдачи токена, не имеет хардкода «только Drive» — добавление будущего Google API сводится к расширению набора запрашиваемых scope-ов и подключению клиента-потребителя без правок identity-домена.
- Дозапрос дополнительных scope-ов следует поведению Credential Manager по умолчанию (incremental authorization при поддержке, иначе полный re-consent); UI диалога дозапроса унифицирован и показывает уже выданные scope-ы и обоснование нового. Эта логика инкапсулирована в identity-домене и переиспользуется любым новым клиентом Google API.
- Контракт identity-домена определяется в общем коде; конкретная реализация — в source-set флавора, где доступен Credential Manager. Это позволяет в будущем подключать или отключать identity-домен по флаворам, не разрезая код.
- Список Google-доменов для in-app browser routing — отдельная константа уровня данных. Добавление новой Google-сущности (например, drive.google.com web-flow) — изменение одного списка.
- UI-слой настроек и состояние «требуется вход» Drive-ресурса используют существующие реактивные потоки приложения; добавление новых Google-фич не требует изменения UI-инфраструктуры этих экранов.

## 6. Открытые вопросы / Research items

1. **Стратегия миграции multi-account Drive в момент первого запуска после обновления.**
   - Вопрос: какой из существующих Drive-аккаунтов автоматически становится primary?
   - Решение: автоматической миграции нет. Существующие сохранённые Drive-credentials (включая multi-account записи) очищаются при первом запуске обновлённой версии. Все Drive-ресурсы помечаются как «требуется вход»; пользователь регистрирует primary-аккаунт с нуля через карточку настроек, а каждый существующий Drive-ресурс восстанавливает доступ повторным входом. Конфигурации ресурсов (выбранные папки, имена, флаги) сохраняются — теряется только закэшированный auth-стейт. Причина: накопленный мусор сохранённых state-ов от ранних версий не должен переноситься в новую identity-модель.
   - Статус: Resolved.

2. **Поведение при отсутствии Chrome Custom Tabs провайдера на устройстве.**
   - Вопрос: что делать, когда на устройстве нет браузера, поддерживающего CCT (редкие Android TV / head units)?
   - Решение: фича отказывает в работе. Карточка «Google Account» при попытке sign-in выполняет проверку наличия CCT-провайдера; если его нет — sign-in не запускается, пользователю показывается объяснение, почему функционал недоступен (требуется браузер, поддерживающий Chrome Custom Tabs) и предложение установить совместимый браузер. После установки браузера повторная попытка возможна без дополнительных действий. Drive-ресурсы в этом сценарии остаются в режиме «требуется вход» — пользователь по-прежнему может пользоваться приложением без Google-функционала. Fallback на WebView для google.com / accounts.google.com запрещён политикой Google. Fallback на внешний VIEW-intent в системный браузер также не годится, потому что разрывает поток sign-in и не наследует Chrome-сессию.
   - Статус: Resolved.

3. **Гранулярность scope-ов при дозапросе.**
   - Вопрос: при добавлении новой Google-фичи в будущем, запрашивать дополнительный scope тихо (incremental authorization) или показывать новый consent screen с полным списком?
   - Решение: использовать дефолтное поведение Credential Manager (incremental authorization, если оно поддерживается на текущем уровне API; иначе полный re-consent). В UI диалога дозапроса показывается список scope-ов, которые уже выданы primary-аккаунту, и явное обоснование, зачем приложение просит новый scope. Решение о техническом режиме передачи (incremental vs full re-consent) принимается на тактическом уровне и не влияет на смысловую часть UX.
   - Статус: Resolved.

4. **Phase 04 — атомарный кластер или декомпозиция?**
   - Вопрос: реализовывать Phase 04 (миграция cloud-слоя Drive на identity-домен) одним атомарным многосессионным раундом или разбить на 04a (additive plumbing) / 04b (token-source switchover with deprecated-stub bridge) / 04c (legacy purge)?
   - Контекст: `/spec-all S0200` round 2 (2026-05-16) выполнил call-site инвентаризацию. Кластер содержит 1500+ LOC изменений в 11 файлах с тремя видами лока: (а) внутри RestClient 20 `auth.accessToken` reads ломаются одновременно; (б) удаление `getSignInIntent`/`handleSignInResult` каскадно ломает 6 UI-сайтов; (в) `InteractiveCloudAuthenticator` protocol change затрагивает Dropbox/OneDrive плагины.
   - Решение: **A — split 04a/04b/04c.** Принято оператором 2026-05-16 round 3. Монолит `PHASE_04__drive-identity-migration.md` заменён тремя файлами (`PHASE_04A__token-source-plumbing.md` · `PHASE_04B__token-source-switchover.md` · `PHASE_04C__legacy-purge.md`), INDEX обновлён, Phases counter бамп до 9 подфаз (01, 02, 03, 04a, 04b, 04c, 05, 06, 07).
   - Статус: Resolved.

## 7. Риски

## 9. Архитектурные решения (ADR)

**ADR-1: Identity-домен как отдельная единица вне cloud-слоя**

- **Решение:** ввести самостоятельный identity-домен Google-аккаунта, не подчинённый cloud-слою. Cloud-слой становится клиентом identity-домена.
- **Альтернативы:** оставить логику внутри cloud-слоя и просто переписать её на Credential Manager; это сохранило бы текущую сцепленность и не дало бы возможности подключать non-cloud Google-фичи к той же привязке.
- **Почему:** идентификация Google-аккаунта пользователя — отдельная сквозная концепция приложения; cloud — лишь один из её потребителей. Изоляция уменьшает связанность и открывает путь к будущим Google API без правок cloud-стека.

**ADR-2: Один primary + сохранение Drive multi-account**

- **Решение:** primary-аккаунт ровно один; для Drive дополнительно сохраняется существующая multi-account модель.
- **Альтернативы:** (a) только primary без multi-account; (b) полностью multi-account без выделенного primary.
- **Почему:** «account-transparent UX» требует понятия «основной аккаунт приложения». Полная замена multi-account на single-primary ломает существующие пользовательские конфигурации (пользователи, добавившие несколько Drive-аккаунтов). Гибрид сохраняет совместимость и даёт прогнозируемое поведение при добавлении нового Drive-ресурса.

**ADR-3: Sign-out не удаляет Drive-ресурсы, а помечает их как «требуется вход»**

- **Решение:** при sign-out primary-аккаунта связанные Drive-ресурсы остаются в списке с пометкой «требуется вход»; конфигурации не уничтожаются.
- **Альтернативы:** (a) удалять ресурсы целиком; (b) спрашивать пользователя при sign-out.
- **Почему:** sign-out — частое действие диагностики и смены аккаунта, потеря конфигурации воспринимается как нежелательное побочное действие. Помеченное состояние даёт восстановление одним действием.

**ADR-4: Chrome Custom Tabs для Google-доменов вместо WebView**

- **Решение:** Google-домен auth-flows маршрутизируются в Chrome Custom Tabs; не-Google источники продолжают идти через WebView.
- **Альтернативы:** (a) перевести весь in-app browser на CCT (ломает извлечение медиа из не-Google источников, которое работает через WebView и cookie jar); (b) оставить WebView для всего (нарушает политику OAuth Google).
- **Почему:** Google явно запрещает WebView для своих OAuth-потоков; CCT — единственный поддерживаемый и согласованный путь. Прочие хосты не накладывают этого ограничения и сохраняют существующий механизм.

**ADR-5: Credential Manager как единственный канал sign-in**

- **Решение:** новый identity-домен использует Credential Manager API; устаревший Google Sign-In удаляется из проекта после миграции.
- **Альтернативы:** держать оба API параллельно как промежуточное состояние.
- **Почему:** двойной API увеличивает поверхность атаки и техдолг подавлений deprecation; миграция за один тикет проще, чем поддержание двух путей.

**ADR-6: Полная очистка существующего auth-стейта Drive, без авто-миграции primary**

- **Решение:** при первом запуске обновлённой версии сохранённый auth-стейт Drive (закэшированные токены, сериализованные identity-данные, multi-account credentials записи) очищается. Конфигурации Drive-ресурсов сохраняются. Пользователь регистрирует primary-аккаунт заново; вторичные Drive-аккаунты пересоздаются по мере доступа к каждому ресурсу.
- **Альтернативы:** (a) выбрать primary по первому существующему Drive-аккаунту; (b) спросить пользователя при первом запуске, какой из существующих аккаунтов сделать primary; (c) попытаться silent-refresh каждый сохранённый аккаунт и выбрать тот, по которому удалось получить актуальный токен.
- **Почему:** существующий auth-стейт накопил остатки от ранних версий приложения (legacy single-account key + per-account ключи, частично-несовместимые сериализации). Перенос этих данных в новую identity-модель привносит риски некорректных состояний и затрудняет диагностику. Полная очистка с понятным CTA на повторный вход даёт чистый старт и однозначно интерпретируемое поведение. Конфигурации ресурсов (папки, имена) при этом не теряются.

**ADR-7: Жёсткое требование CCT-провайдера; отказ функционала без него**

- **Решение:** в отсутствие на устройстве хотя бы одного браузера, поддерживающего Chrome Custom Tabs, функционал привязки primary-аккаунта и Google-домен auth-flows в in-app browser отказывают в работе с понятным объяснением. Fallback на WebView или внешний VIEW-intent для Google-доменов не вводится.
- **Альтернативы:** (a) WebView с предупреждением о возможной блокировке Google; (b) внешний VIEW-intent в системный браузер.
- **Почему:** WebView для Google OAuth явно запрещён политикой Google и приводит к стабильно неуспешному sign-in. Внешний VIEW-intent разрывает поток sign-in (приложение теряет результат), и без CCT нет наследования Chrome-сессии, ради которой и вводится эта маршрутизация. Прозрачный отказ с инструкцией для пользователя — менее болезненный сценарий, чем рабочий-но-сломанный путь.

## 11. Критерии готовности (strategic-level)

1. Пользователь в Настройках видит карточку «Google Account» и может войти в свой Google-аккаунт одной операцией; после успешного входа карточка показывает email, имя и аватар.
2. После привязки primary-аккаунта добавление нового Drive-ресурса с тем же аккаунтом не показывает экран Google sign-in.
3. Добавление Drive-ресурса с другим Google-аккаунтом продолжает работать через interactive sign-in; новый аккаунт сохраняется в multi-account списке Drive.
4. После sign-out primary-аккаунта связанные Drive-ресурсы видны в списке с пометкой «требуется вход»; повторный sign-in тем же email-ом восстанавливает доступ ко всем им без дополнительных действий.
5. Не связанные с primary-аккаунтом Drive-ресурсы (под другими Google-аккаунтами) сохраняют доступ при sign-out primary.
6. Открытие URL Google-домена внутри встроенного браузера приложения происходит через Chrome Custom Tabs; WebView для google.com / accounts.google.com / youtube.com / music.youtube.com не запускается.
7. На устройстве без CCT-провайдера попытка sign-in или открытия Google-домен URL во встроенном браузере вызывает понятное сообщение об ограничении и не падает; после установки совместимого браузера повторная попытка проходит без перезапуска приложения.
8. После обновления приложения существующие пользователи видят свои Drive-ресурсы в списке в состоянии «требуется вход» (конфигурации сохранены); повторный sign-in в primary-аккаунт через карточку настроек восстанавливает доступ к ресурсам этого аккаунта одним действием. Доступ к ресурсам не-primary Google-аккаунтов восстанавливается отдельным interactive sign-in при первом обращении к каждому такому ресурсу.
9. EN / RU / UK строки нового UI присутствуют и проходят аудит локализации.
10. После завершения миграции в репозитории нет ссылок на устаревший Google Sign-In API и нет `@Suppress("DEPRECATION")` подавлений в файлах, затронутых миграцией.
