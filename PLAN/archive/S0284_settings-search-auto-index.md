## 1. Проблема

Поиск по экрану настроек устроен как вручную поддерживаемый реестр записей. Пользователь вводит «3D» — ничего не находится, хотя в настройках есть несколько 3D/VR-блоков (одноглазый стерео-просмотр, VR-секция воспроизведения, переопределение формата 3D из плеера). Реестр последний раз пополнялся 2026-05-19, а layout-ы настроек дополнялись и после — за пределами реестра остались около тридцати реально существующих строк настроек, кнопок и блоков. Любой новый параметр в настройках по умолчанию невидим поиску, пока разработчик не вспомнит дописать запись с переводами на трёх языках вручную. Это структурная проблема, а не пропущенная итерация.

---

## 2. Цели

1. Поиск по настройкам перестаёт зависеть от ручного реестра — индекс собирается из настоящих layout-ов и строковых ресурсов автоматически.
2. Запрос на любом из поддерживаемых языков (EN/RU/UK) находит запись по её фактическому заголовку, подзаголовку и подсказке так, как они отображаются пользователю.
3. Новая строка настроек, добавленная в layout, становится находимой без правки какого-либо отдельного файла реестра.
4. Запросы «3D», «стерео», «VR», «180», «360», «SBS», «OU», «single eye», «одним глазом», «одне око» возвращают соответствующие записи 3D/VR-кластера.
5. Фильтрация записей по флагам поддержки медиа-типов (изображения, видео, аудио, документы) продолжает работать ровно так, как сейчас.

**Non-goals:**

- Поиск по диалогам, не относящимся к экрану настроек (диалог переопределения формата 3D из плеера).
- Добавление новых строк настроек как фичи.
- Нечёткий поиск, стемминг, синонимы сверх того, что уже даёт `strings.xml`.
- Перевод существующих пользовательских строк или их перефразирование.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Покрытие всех вкладок настроек: General, Media (со всеми подвкладками), Playback, Operations (Destinations и Backup/Restore).
2. Видимая в результатах поиска подсказка/описание (а не только заголовок), если у строки есть подзаголовок или help-текст — это даёт пользователю контекст без перехода.
3. Долгосрочная цель: добавление нового параметра в настройки не требует никаких действий со стороны разработчика по части поиска, кроме обычного оформления строки в layout-е.

### 3.2 Жёсткие ограничения

- **Flavor:** все варианты сборки (`standard`, `lite`, `photos`, `legacy`); при добавлении в проект флейворов `vr` и `noLegal` они тоже должны работать без специальных веток. Реализация следует `dev/FLAVOR_DEVELOPMENT_RULES.md`: никаких новых `BuildConfig.SUPPORT_*` / `BuildConfig.IS_*` ветвлений в `src/main/`. Фильтрация по поддержке медиа-типов остаётся на той же гранулярности, что и сейчас (категория, а не отдельная запись).
- **API level:** без API-специфики, baseline проекта (minSdk 26 для не-legacy, 23 для legacy).
- **Wear OS:** не затрагивается.
- **Производительность:** холодный старт `SettingsActivity` не должен заметно деградировать (бюджет — менее десяти миллисекунд дополнительной работы при первом открытии экрана). Если рантайм-разбор layout-ов и строк выходит за бюджет, индекс собирается на этапе сборки (gradle-таска или KSP), а не во время запуска приложения.
- **Совместимость данных:** изменений хранилища нет; никаких миграций Room, никаких персистентных индексов поиска.
- **Локализация:** EN/RU/UK — всегда обязательно. Ключевые слова конкретной локали берутся из её ресурсов, а не подбираются переводом «по аналогии».
- **Доступность:** результаты поиска остаются доступны для TalkBack, навигации D-pad и мыши на тех же условиях, что и сейчас (см. CLAUDE.md Strict Rule 17).

### 3.3 Owner inputs (Approval gate)

- **Flavor scope:** все варианты сборки приложения (`standard`, `lite`, `photos`, `legacy`) и будущие `vr`/`noLegal` — индексация одинаковая, разница только в фильтрации записей по флагам поддержки медиа-типов, как сейчас.
- **Performance budget:** холодный старт `SettingsActivity` — рост не более десяти миллисекунд при первом открытии экрана; при превышении бюджета индекс собирается на этапе сборки.
- **Localization:** EN/RU/UK; ключевые слова берутся из соответствующего `strings.xml`, без ручного дублирования.
- **UI placement contract:** структура экрана поиска не меняется — то же поле ввода, тот же overlay, тот же ListAdapter; меняется только источник данных за этим adapter-ом.
- **Accessibility:** TalkBack-чтение записи результата = заголовок + название вкладки (как сейчас); фокус D-pad по результатам — без изменений.

## 4. Контекст текущей архитектуры

Экран настроек состоит из четырёх вкладок (General, Media, Playback, Operations) и подэкранов внутри Media (Images, Video, Audio, Documents, Other) и Operations (Destinations, Backup/Restore). Каждая строка настройки — это либо переиспользуемый виджет с атрибутами `str_title`/`str_subtitle`, либо стандартный Material-контрол с `android:text`/`android:hint`. Текст уже локализован — в проекте поддерживается три языка: EN, RU, UK, и каждой строке настройки соответствует тройка локализованных значений в `strings.xml`.

Поиск сегодня — отдельный список объектов с захардкоженными заголовками и ключевыми словами на трёх языках. Ни UI-layout, ни `strings.xml` не являются источником истины для поиска: реестр их дублирует с дрейфом. Из-за этого дрейфа поиск выдаёт устаревшие подсказки и не находит относительно новых параметров.

## 5. Предлагаемый подход

Источником истины становятся layout-ы экранов настроек и локализованные строковые ресурсы. Реестр поиска — производный артефакт, собираемый автоматически из этих двух источников, без ручного шага «дописать запись».

### 5.1 Основные столпы / модули

**Сборщик индекса.** Берёт каждый layout-файл, относящийся к экранам настроек, проходит по элементам, у которых есть стабильный `id` и атрибуты-источники текста (`str_title`/`str_subtitle`, `android:text`, `android:hint`, `app:text`, label у спиннеров/AutoComplete). На каждый такой элемент производит одну запись индекса.

**Локализационный обогатитель.** Для каждой записи извлекает значение строкового ресурса (а не ссылку) на каждом из трёх поддерживаемых языков. Эти значения становятся пулом ключевых слов: пользователь, набирающий слово в EN, RU или UK, находит запись по фактической строке, видимой в этой локали.

**Категоризатор и навигатор.** Каждая запись принадлежит вкладке (General/Media/Playback/Operations) и подкатегории (Images/Video/Audio/Documents/Other/Destinations/Backup-Restore — там, где это применимо). Эта классификация определяется по layout-у, в котором найдена запись, а не повторно прописывается. Результат поиска по-прежнему переводит пользователя на нужную вкладку и подсвечивает целевой элемент через его стабильный `id`.

**Фильтр доступности.** При выдаче результатов запись фильтруется тем же контрактом, что и сегодня: подкатегории Images/Video/Audio/Documents видимы только при включённой поддержке соответствующего медиа-типа в текущем флейворе. Контракт остаётся на уровне «категория целиком включена или выключена», без появления записей-исключений.

**Адаптер потребителя.** Существующий компонент, рендерящий результаты, продолжает потреблять объект записи той же формы: заголовок + название категории + дополнительный текст (подзаголовок/подсказка, если есть) + стабильный идентификатор для навигации.

### 5.2 Потоки данных и событий

- Источники: layout-файлы экранов настроек + строковые ресурсы трёх локалей.
- Сборщик читает источники → формирует промежуточный список записей с локализованными текстами для всех трёх языков.
- Локализационный обогатитель прикладывает к каждой записи пул её локализованных строк → этот пул используется как ключевые слова.
- Категоризатор фиксирует вкладку и подкатегорию каждой записи по правилу «один layout-файл = одна вкладка/подкатегория».
- Готовый индекс предоставляется фильтру доступности; на выдаче применяются те же флейвор-фильтры, что и сегодня.
- UI поиска читает индекс через тот же контракт, что и раньше, и продолжает работать без изменений.

### 5.3 Точки расширяемости

- **Источник записи.** Появление нового виджета-строки (например, нового стилизованного контрола) не должно требовать переписывания сборщика — список «атрибутов-источников текста» вынесен в одно место и расширяется добавлением атрибута, а не правкой кода сборщика.
- **Источник локалей.** При добавлении новой локали (ещё одного `values-XX/strings.xml`) индекс автоматически включает её строки в пул ключевых слов — без правки сборщика.
- **Контракт фильтрации.** Если в будущем понадобится более тонкая фильтрация (отдельные записи, а не категории целиком), точка расширения — фильтр доступности; источник истины индекса не затрагивается.
- **Способ сборки (рантайм против билдтайма).** Способ извлечения остаётся внутренней деталью. Если рантайм-парсинг укладывается в бюджет производительности — допустим он; если нет — индекс генерируется на этапе сборки и поставляется как сгенерированный ресурс. Решение фиксируется в `/spec-tech`.

## 6. Открытые вопросы / Research items

1. **Способ сборки индекса**
   - **Вопрос:** собирать индекс на рантайме при первом открытии экрана настроек или на этапе сборки приложения?
   - **Варианты:** (a) рантайм-обход layout-ов и строковых ресурсов через инспекцию ресурсов; (b) gradle-таска / KSP-процессор, генерирующий статический индекс как ресурс или Kotlin-объект.
   - **Решение:** (a) рантайм через `Resources.getXml`. Экран настроек открывается явным действием пользователя, overlay поиска — ещё одним явным действием внутри настроек. Лениво инициализируемый разбор поэтому выполняется не на холодном старте приложения, а в момент, когда пользователь уже взаимодействует с настройками. Build-time-вариант (gradle-таска / KSP) увеличивает сложность сборки без измеримой выгоды для поверхности, которая никогда не была критичной по производительности.
   - **Статус:** Resolved (2026-05-21)

2. **Источник «человеческого» заголовка для атипичных строк**
   - **Вопрос:** что делать с теми элементами, у которых нет ни `str_title`, ни `android:text` (например, текстовое поле ввода с одной только подсказкой `android:hint`)?
   - **Варианты:** (a) брать `android:hint`, (b) брать соседний label, (c) исключать из индекса.
   - **Решение:** (a) `android:hint` как fallback. Если у поля есть только hint — этот hint и есть тот текст, который пользователь видит на экране и по которому он будет узнавать поле. Исключение таких записей создаёт пробелы в индексе для числовых полей ввода (например, интервал слайдшоу, минимальный размер изображения). Соседний label требует эвристики обхода соседей и плохо предсказуем — без устойчивой пользы.
   - **Статус:** Resolved (2026-05-21)

3. **Записи дочерних диалогов**
   - **Вопрос:** включать ли в индекс заголовки настроек, доступных только через диалоги/help-блоки внутри экрана настроек (например, текст внутри `str_helpTitle`/`str_helpMessage`)?
   - **Варианты:** (a) только видимые поверхностные строки экранов; (b) плюс help-блоки; (c) плюс заголовки дочерних диалогов настроек.
   - **Решение:** (a) только поверхностные строки. Help-popup-ы — вспомогательный контент, открываемый по запросу. Их добавление в keyword pool раздуло бы выдачу за счёт текстов, которых пользователь не видит без явного действия. Title/subtitle самой настройки уже несут её поисковую идентичность. Если по факту регрессионного теста окажутся важные пропуски — расширить отдельной спекой.
   - **Статус:** Resolved (2026-05-21)

4. **Кнопки действий**
   - **Вопрос:** включать ли в индекс кнопки (импорт/экспорт, очистка кэша, бэкап в Google Drive, добавление назначения, синхронизация сейчас и так далее) наряду с переключателями параметров?
   - **Варианты:** (a) только параметры (переключатели/спиннеры/поля ввода), (b) параметры плюс кнопки действий, (c) гибкая разметка с пометкой типа записи.
   - **Решение:** (b) параметры + все кнопки действий с видимым `android:text`. Действия вроде «Очистить кэш», «Экспортировать настройки», «Backup to Google Drive» — пользовательские поисковые сущности наравне с переключателями. Старый ручной реестр уже включал часть кнопок (`btnClearCache`, `btnExportSettings`, `btnBackup`, `btnRestore`) — консистентность требует включить все.
   - **Статус:** Resolved (2026-05-21)
   - **Статус:** Open

## 9. Архитектурные решения (ADR)

**ADR-1: Источник истины — layout + strings, не отдельный реестр**

- **Решение:** индекс поиска становится производным артефактом, а не первичной структурой данных.
- **Альтернативы:** (a) сохранить ручной реестр и ввести ритуал «обязательно дописывать запись при добавлении строки настроек»; (b) ввести аннотацию-метку на view-id в layout-е и собирать индекс по аннотированным id.
- **Почему:** (a) не работает в долгую — спека возникла из-за того, что ритуал нарушался; (b) добавляет ручной шаг «не забыть аннотацию», по сути та же ловушка дрейфа. Source-of-truth-подход устраняет ритуал целиком.

**ADR-2: Способ сборки индекса откладывается до тактической спеки**

- **Решение:** рантайм против билдтайма решается в `/spec-tech` после замера производительности.
- **Альтернативы:** зафиксировать билдтайм на стратегическом уровне.
- **Почему:** билдтайм-вариант сложнее (gradle-таска или KSP). Если бюджет позволяет рантайм-разбор — он проще и держит индекс синхронным буквально с тем, что увидит пользователь.

## 11. Критерии готовности (strategic-level)

1. Запрос «3D» в поиске настроек возвращает как минимум запись стерео-просмотра одним глазом.
2. Запросы «стерео», «VR», «180», «360», «SBS», «OU», «single eye», «одним глазом», «одне око» возвращают соответствующие записи 3D/VR-кластера, найденные в реальных настройках.
3. Запросы «темнее», «брайтнес», «brightness», «гучність», «sound» (или эквиваленты для других параметров, не входивших в ручной реестр на 2026-05-21) возвращают записи, если в настройках есть соответствующая строка.
4. Добавление новой строки в layout настроек делает её находимой при следующем открытии экрана поиска без правки какого-либо отдельного индекса-файла.
5. На флейворе `lite` (`SUPPORT_AUDIO=false`, `SUPPORT_DOCUMENTS=false`) аудио- и документ-записи не появляются в результатах поиска.
6. Холодное открытие экрана настроек после изменения не вырастает по времени более чем на десять миллисекунд относительно текущего поведения.
7. TalkBack читает результат поиска так же, как сейчас: заголовок + название вкладки.
