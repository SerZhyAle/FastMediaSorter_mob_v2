## 1. Проблема / симптом

В immersive при реальном просмотре фильма (запуск из обычного плеера, не диагностика) по центру виден прямоугольник HUD - пустой и серый. Ожидается либо наполненный баннер (тёмный фон + имя файла + формат), либо отсутствие HUD. Серый пустой прямоугольник = квад HUD показывается с ненаполненной/дефолтной текстурой.

---

## 2. Корневая причина

Уточнено статическим анализом (2026-07-11):

- Первичная гипотеза «видео-путь не вызывает `queueHud`» кодом НЕ подтверждается: `onRenderThreadSessionReady` (DiagnosticXrActivity, ~строка 1309) re-queue'ит filename-баннер для каждого типа медиа, включая видео, и вызывается до `runFrameLoop()` - pending-байты гарантированно доезжают до аплоада следующего кадра.
- Фактический механизм симптома: нативная текстура HUD создаётся как 1x1 пиксель `{64,64,64,255}` - непрозрачный серый (`xr_session.cpp` createGlAssets, ~строка 1147). Квад HUD рендерится всегда при `visible && hudTex != 0` (`xr_hud_world.cpp::xr_hud_render`), то есть любой сбой цепочки «generate -> queue -> upload» на устройстве экспонирует серый плейсхолдер как «пустой серый прямоугольник» по центру взгляда (квад 0.3x0.113 м на -1.5 м, head-locked).
- Какой именно шаг цепочки падает на Quest 3 - определимо только device-логом. Кандидаты: (а) `generateFilenameHudBytes` вернул нули (класс сбоев S0290: `first pixel RGBA=0,0,0,0`); (б) `hud upload` не выполнился в текущей GL-сессии; (в) рендер идёт со старым texture id.
- Альтернативная интерпретация симптома: при FLAT-видео экран фильма использует ту же серую 1x1 заглушку `g.texture`; если видео не стартовало, серый прямоугольник - это экран фильма, а не HUD. Различается на устройстве: виден ли сам фильм вокруг.

Подтверждение на устройстве - `adb logcat` во время реального просмотра, маркеры пайплайна:
- `xr_session_queue_hud STORED <w>x<h> ...; first pixel RGBA=...`
- `hud upload: <w>x<h> to texture=...`
- `xr_hud_render ok: eye=... hudTex=... quad.center=(...)`

## 3. Исправление

Root-agnostic фикс, санкционированный вариантом «не показывать квад HUD пока нет контента»: серый плейсхолдер не должен экспонироваться ни при каком сбое выше по цепочке.

1. `xr_session.cpp`: флаг `hudContentUploaded` рядом с pendingHud-полями; ставится в `true` в точке `hud upload` (frame loop); сбрасывается в shutdown вместе с очисткой pendingHud.
2. Call-site рендера (строка ~1375): передавать `hudTex = 0` пока `hudContentUploaded == false` - переиспользует существующий early-return и его диагностический лог `xr_hud_render EARLY RETURN .. hudTex=0`.
3. Поведение при рабочем аплоаде не меняется; бонус - исчезает серый кадр-вспышка между стартом сессии и первым аплоадом.
4. Kotlin-probe (BlockNeedUserTest): `Timber.d("S0961: ..")` в `queueFilenameHud` - сквозная точка баннера; нативные маркеры уже существуют.

Если device-лог покажет, что аплоад на видео-пути не выполняется вовсе (HUD после фикса отсутствует, а не наполнен), потребуется отдельный фикс аплоада - оформить follow-up тикетом; для S0964 (tracks-HUD) рабочий аплоад обязателен.

## 4. Проверка

Build-гейт (локально): `assembleNoLegalDebug` - компилирует и Kotlin `src/vr`, и нативный CMake-таргет.

On-device Quest 3 (noLegal, sideload):

1. Открыть VR-фильм в immersive из обычного плеера (реальный просмотр, не диагностика).
2. Снять `adb logcat -b all` (см. memory: raw capture, не -s фильтр) с маркерами §2 + probe `S0961:`.
3. Ожидаемо после фикса: серый пустой прямоугольник отсутствует в любом исходе. Либо HUD-баннер наполнен (имя файла + проекция/лейаут - маркеры STORED/upload есть), либо HUD-квада нет вовсе (маркер `xr_hud_render EARLY RETURN .. hudTex=0` - аплоад не дошёл, оформить follow-up на аплоад).
4. Зафиксировать, виден ли сам фильм (различение баннер-vs-экран из §2).
