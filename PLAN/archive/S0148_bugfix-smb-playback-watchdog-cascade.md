# Стратегическая спецификация: S0148 — Каскад отказов воспроизведения SMB после срабатывания read-watchdog

**Ticket:** S0148
**Status:** BlockNeedUserTest
**Priority:** 80
**Date:** 2026-05-11
**Implemented date:** 2026-05-11
**Tier:** 3 — Moderate (ad-hoc)
**Roadmap entry:** Ad-hoc — полевой инцидент 2026-05-11, лог `logs/fastmediasorter_20260511_005409.log` (00:57:31–00:57:44)
**Tactical spec:** реализовано напрямую (primitive, 2 файла) — отдельная тактическая спека не создавалась.

> **Scope:** STRATEGIC. Цели, ограничения, открытые вопросы. Без имён классов, путей, лимитов строк, миграций Room, модулей Hilt.

> Журнальный статус — `BlockNeedUserTest`: нужна проверка на устройстве. Сценарий: воспроизведение SMB-аудиоплейлиста; дождаться `[SMB-PLAY] read watchdog` на одном треке (или спровоцировать стопор сети) → пролистнуть на соседний трек — он должен играть, без мгновенного `fail-fast`. Debug-тег: `Timber.d("S0148: SMB playback open uri=… failFast=…")` в `SmbDataSource.open()` — должен появляться в logcat при каждом открытии SMB-файла плеером.

---

## 1. Проблема

При воспроизведении плейлиста медиа по SMB одна остановка чтения с сервера (read-watchdog срабатывает через ~15 c) помечает текущее соединение «подозрительным» и взводит короткий fail-fast lockout по адресу сервера. Пока lockout активен, любая следующая попытка воспроизведения файла **с того же сервера** прерывается мгновенно, без попытки переподключения — даже если пользователь сам пролистнул на соседний трек или сработал авто-переход к следующему файлу плейлиста. В поле это выглядит так: один трек «завис», и вслед за ним подряд не открываются ещё несколько соседних треков плейлиста; пользователь видит серию ошибок воспроизведения там, где сервер уже доступен. Это тот же класс каскада «один отказ → серия отказов соседних файлов», который для копирования/листинга закрывал S0061, но здесь действует отдельный механизм fail-fast воспроизведения, который S0061 не покрывал.

---

## 2. Цели

1. Переход к следующему файлу, инициированный пользователем (ручное пролистывание) или штатным авто-переходом плейлиста, снимает fail-fast lockout по этому серверу — следующий файл получает честную попытку открыть соединение.
2. Первая попытка воспроизведения нового файла после lockout идёт через заведомо свежее соединение (как при «холодном» старте), а не отбивается мгновенно по флагу недавнего watchdog.
3. Fail-fast по недавнему watchdog продолжает срабатывать только там, где он реально полезен: внутренний retry той же самой попытки воспроизведения того же файла (ExoPlayer пересоздаёт DataSource на ретрае) — чтобы не получить серию 12-секундных зависаний подряд на один и тот же зависший сервер.
4. После реального переподключения (новое живое соединение получено) lockout считается снятым — он не должен «тянуться» дольше, чем актуальна его причина.
5. Серия `Playback error` на соседние файлы плейлиста, воспроизводимая на той же конфигурации, после фикса не повторяется.

**Non-goals:**

- Не менять сам механизм read/open-watchdog (пороги тайм-аутов, инвалидцию протухшего соединения) — меняется только область действия fail-fast lockout.
- Не трогать восстановление SMB-сессии после простоя (S0061) и многопротокольную инвалидцию stale-соединений (S0067) — это смежные подсистемы.
- Не вводить новый UI и новые пользовательские уведомления; существующие сообщения об ошибке воспроизведения остаются как есть.
- Не менять поведение для FTP/SFTP/WebDAV/Cloud — фокус только на SMB-воспроизведении.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Желательно, чтобы lockout автоматически снимался при любом явном пользовательском действии в плеере, связанном со сменой файла (next/prev, выбор из списка, повторное открытие).
2. Желательна явная диагностика в логе: одна строка «lockout снят — причина: переход к новому файлу / получено свежее соединение», а не молчаливое поведение.
3. Желательно не наказывать пользователя за кратковременный сетевой провал: если сервер «моргнул» на секунду, следующий трек должен играть.

### 3.2 Жёсткие ограничения

- **Flavor:** `standard`, `lite`, `legacy` (везде, где активно SMB-воспроизведение; `photos` SMB не использует).
- **API level:** без API-специфики; затрагивает все поддерживаемые версии Android.
- **Wear OS:** не затрагивается.
- **Производительность:** снятие lockout — операция в памяти, без сетевых round-trip; не должна добавлять задержки на «горячем» пути воспроизведения.
- **Совместимость данных:** изменений хранимых настроек/кэшей не требуется.
- **Локализация:** новых пользовательских строк не предполагается; если появятся — EN/RU/UK обязательно.
- **Доступность:** не применимо (нет UI-нововведений).

## 4. Контекст текущей архитектуры

За воспроизведение медиа по SMB отвечает источник данных плеера поверх пула SMB-соединений; жизненный цикл «соединение для воспроизведения» (создано / подтверждено успешным открытием файла / подозрительное / инвалидировано) и отметки о сработавших watchdog трекаются в отдельном синглтоне, потому что ExoPlayer создаёт новый источник данных на каждом ретрае и per-instance состояние между попытками не живёт. Сейчас этот трекер взводит метку «недавний watchdog» по ключу сервера на фиксированное окно времени, и любой источник данных, который пытается открыть файл с этого сервера в течение окна, отбивается без попытки. Окно не различает «это ретрай той же зависшей попытки» и «это уже другой файл / другая пользовательская попытка», поэтому штраф распространяется на соседние файлы плейлиста. Механизм снятия метки по пользовательской навигации в коде есть, но путь авто-перехода к следующему файлу после ошибки его не вызывает.

## 5. Предлагаемый подход

Сузить область действия fail-fast lockout до того, для чего он задумывался — подавления повторных зависаний на одной и той же попытке воспроизведения одного и того же файла — и явно снимать его при любом событии, означающем «начинаем воспроизводить другой файл» или «получено новое живое соединение».

### 5.1 Основные столпы / модули

- **Привязка lockout к попытке, а не только к серверу.** Метка «недавний watchdog» должна нести достаточно контекста, чтобы отличить ретрай той же попытки воспроизведения от старта нового файла. Fail-fast применяется только в первом случае.
- **Снятие lockout при смене файла.** Любой вход в воспроизведение нового файла — ручной next/prev, выбор из списка, авто-переход плейлиста (в т.ч. после ошибки предыдущего файла), повторное открытие — сбрасывает lockout по серверу до начала попытки.
- **Снятие lockout при успешном переподключении.** Как только пул выдал новое живое соединение к этому серверу (а не переиспользовал старое), причина lockout исчерпана — метка снимается.
- **Диагностический канал.** Снятие lockout и его срабатывание логируются по одной информативной строке с причиной; шум не растёт.
- **Совместимость со смежными механизмами.** Поведение не должно дублировать или конфликтовать с восстановлением соединения после простоя (S0061) и многопротокольной инвалидцией stale-соединений (S0067) — fail-fast остаётся «надстройкой над» ними, а не параллельной логикой ретраев.

### 5.2 Потоки данных и событий

- Вход в воспроизведение нового файла → снять lockout по серверу → обычный путь открытия соединения (через пул, с health-пробой) → при успехе пометить соединение подтверждённым.
- Чтение зависло → read-watchdog → пометить соединение подозрительным, инвалидировать его, взвести lockout, привязанный к текущей попытке.
- ExoPlayer ретраит ту же попытку (новый источник данных, тот же файл) → lockout активен и относится к этой попытке → fail-fast (как сейчас).
- Плеер переходит к следующему файлу (пользователь или авто-next, в т.ч. после ошибки) → событие «новый файл» → lockout снят → новый файл получает честную попытку.
- Пул выдал свежее живое соединение к серверу → lockout снят.

### 5.3 Точки расширяемости

- Гранулярность привязки lockout (по файлу / по сессии воспроизведения / по серверу) должна оставаться параметром, чтобы при необходимости ужесточить или ослабить без переписывания механизма.
- Набор событий «считается новым воспроизведением» (next/prev/выбор/повтор/авто-next) должен расширяться добавлением нового источника события без изменения логики трекера.
- Диагностическая причина снятия/срабатывания lockout — структурированное значение (новый файл / свежее соединение / окно истекло / ретрай той же попытки), чтобы при необходимости вывести в диагностику.

## 6. Открытые вопросы / Research items

1. **Что именно считать «той же попыткой воспроизведения» при ретрае ExoPlayer**
   - **Вопрос:** по чему привязывать lockout — к URI текущего файла, к идентификатору сессии воспроизведения, или к обоим.
   - **Резолюция:** по URI текущего файла. ExoPlayer на ретрае пересоздаёт источник данных с тем же URI media item'а, а на переходе к другому файлу — с другим URI; этого достаточно, чтобы отличить ретрай зависшей попытки от старта нового файла. Пограничный случай «повторное открытие того же файла как новая пользовательская попытка» уже покрыт существующим сигналом ручной навигации (`clearAllWatchdogs()` при `manual=true`).
   - **Статус:** Resolved.

2. **Нужно ли вообще сохранять fail-fast lockout, если уже есть инвалидция протухшего соединения (S0061)**
   - **Вопрос:** возможно, после физической инвалидции соединения и health-пробы перед арендой (S0061) отдельный fail-fast по watchdog больше не нужен.
   - **Резолюция:** lockout сохраняется, но в двух режимах. (1) Привязан к URI зависшей попытки — ретрай того же файла отбивается мгновенно; другой файл получает честную попытку. (2) Эскалация: если в пределах окна watchdog срабатывает ≥ 2 раз для одного и того же сервера (для разных файлов) — это признак реально мёртвого сервера, и на остаток окна fail-fast расширяется до серверного (как было до фикса), чтобы не получить серию многосекундных зависаний на каждом следующем файле. Полный отказ от lockout отклонён: «honest retry на свежем соединении» к действительно зависшему серверу даёт зависание длиной с open-watchdog на каждый файл, что и было исходной причиной введения lockout.
   - **Статус:** Resolved.

## 9. Архитектурные решения (ADR)

**ADR-1: fail-fast lockout привязан к попытке воспроизведения, а не только к адресу сервера**

- **Решение:** метка «недавний watchdog» применяется как fail-fast только для ретрая той же самой попытки воспроизведения (тот же файл / та же сессия), а не для любого обращения к серверу в течение фиксированного окна.
- **Альтернативы:** оставить привязку только к серверу (текущее поведение → каскад); убрать lockout совсем (риск серии зависаний).
- **Почему:** lockout вводился против повторных 12-секундных зависаний на одну и ту же зависшую попытку; на соседние файлы он распространяться не должен.

**ADR-2: смена файла и получение свежего соединения снимают lockout явно**

- **Решение:** входы «воспроизводим другой файл» (включая авто-next после ошибки) и «пул выдал новое живое соединение» сбрасывают lockout до начала попытки.
- **Альтернативы:** ждать естественного истечения окна; снимать только по ручной навигации (текущий неполный путь).
- **Почему:** причина lockout (одна зависшая попытка) к моменту смены файла или свежего соединения уже неактуальна; держать штраф дольше — наказывать пользователя без причины.

## 10. Связи с другими спеками

- **S0061 (bugfix-smb-stale-connection-invalidation, Implemented):** тот же класс проблемы (каскад отказов соседних файлов), но другая подсистема — там мёртвый Connection после простоя, здесь fail-fast lockout воспроизведения; реализация S0148 должна опираться на инвалидцию + health-пробу из S0061, а не дублировать их.
- **S0067 (enh-network-stale-connection-invalidation-multi-protocol, Verified):** общая модель stale-инвалидции по протоколам; fail-fast воспроизведения остаётся надстройкой над ней.
- **S0066 (enh-network-transient-failure-classification-multi-protocol, Verified):** классификация transient-ошибок — read-watchdog timeout логически попадает в неё; согласовать терминологию.

## 11. Критерии готовности (strategic-level)

1. После того как один файл плейлиста по SMB «завис» и сработал read-watchdog, переход к следующему файлу (ручной или авто-next) воспроизводит его, если сервер уже доступен — без мгновенного fail-fast.
2. Повторное открытие того же зависшего файла, инициированное пользователем, получает честную попытку, а не отбивается по флагу недавнего watchdog.
3. Внутренний ретрай ExoPlayer той же попытки воспроизведения того же файла к действительно зависшему серверу по-прежнему отбивается быстро, без серии многосекундных зависаний.
4. В логе на инцидент «один файл завис, дальше пролистали плейлист» нет серии `Playback error` на соседние файлы — есть один отказ по зависшему файлу и (если сервер вернулся) штатное воспроизведение дальше.
5. Снятие и срабатывание lockout видно в логе одной информативной строкой с причиной.
