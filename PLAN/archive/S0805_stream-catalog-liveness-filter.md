---

## 1. Проблема

Сборщик каталога трансляций при добавлении новых каналов проверяет только HTTP-статус плейлиста (поверхностный probe). Канал, у которого плейлист отвечает `2xx`, но реального медиа-сегмента нет ("заявлен, но не играет"), помечается как живой и попадает в публикуемый каталог. Пользователь при импорте получает псевдо-актуальные каналы, которые в итоге не отвечают. Область - инструментальный пайплайн сбора каталога (delivery/stream-catalog), не рантайм приложения.

---

## 2. Цели

1. Новые каналы попадают в каталог только после подтверждения реального медиа-сигнала, а не одного лишь `2xx` на плейлисте.
2. Псевдо-живые каналы (плейлист `2xx`, но сегмент/тело пустые или `404`) отбраковываются на этапе сбора, до аппенда и публикации.
3. Отчёт по кандидатам показывает причину отбраковки, чтобы решение было проверяемым человеком.
4. Строгая проверка сигнала - поведение по умолчанию для сбора; есть явный опт-аут для быстрого прогона.

**Non-goals:**

- Автоматический prune существующего каталога по глубокому сигналу. Удаление остаётся консервативным и человеко-контролируемым: канал, мёртвый с машины сборщика, может быть живым на устройстве пользователя (гео-ограничения).
- Изменение рантайм-проверки живости в приложении (смежная тема - S0700).
- Смягчение политики включения: по-прежнему берём каждый достижимый канал с реальным сигналом.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Пересмотреть процесс сбора перед текущим релизом, чтобы каталог не рос за счёт нерабочих каналов.

### 3.2 Жёсткие ограничения

- **Flavor:** не затрагивает сборку приложения - изменение только в оффлайн-скрипте сборщика каталога.
- **API level:** без API-специфики.
- **Wear OS:** не затрагивается.
- **Производительность:** глубокая проверка дороже поверхностной (тянет байты медиа), поэтому применяется только к подмножеству, прошедшему поверхностный probe, а не ко всем сырым кандидатам.
- **Совместимость данных:** схема streams.csv не меняется; меняется только критерий отбора добавляемых строк.
- **Локализация:** не применимо (инструментальный скрипт, вывод - служебный EN).
- **Доступность:** не применимо.

### 3.3 Owner inputs (Approval gate)

- **Related tickets:** S0700 (runtime stream-refresh health-probe - смежная тема живости каналов, но в рантайме, не на этапе сбора каталога).
- **Асимметрия append vs prune:** для добавления - строгость (не впускать псевдо-живые), для удаления - осторожность (не выбрасывать возможно-живые). Подтверждено политикой каталога: dead-from-here может быть alive на устройстве пользователя.
- **Дефолт:** строгая проверка включена по умолчанию для сбора; опт-аут через флаг для быстрого прогона.

## 4. Контекст текущей архитектуры

Сбор каталога выполняет один PowerShell-скрипт с двумя режимами: discovery/append (обнаружение и добавление новых строк) и catalog-only maintenance (probe текущего каталога и опциональный prune). Глубокая проверка сигнала уже реализована, но доступна только в режиме maintenance. Discovery/append-путь использует лишь поверхностный probe, поэтому строгую проверку нельзя получить на этапе, где решается, что уйдёт в публикацию. Проблему из §1 нельзя решить существующими флагами: `-DeepSignal` не влияет на discovery-гейт.

---

## 5. Предлагаемый подход

Двухступенчатый гейт живости в discovery/append-пути:

1. Поверхностный probe как первичный дешёвый фильтр (отсекает очевидно мёртвое - DNS-fail, refused, `404/410`).
2. Глубокая проверка сигнала на переживших первый шаг кандидатах: подтверждение реальных байтов медиа (HLS: мастер -> медиа-плейлист -> первый сегмент; DASH: разбор манифеста; прогрессив/ICECAST: тело; RTSP: OPTIONS-хендшейк).
3. В каталог добавляются только строки, подтверждённые глубокой проверкой как живые. Псевдо-живые переклассифицируются и исключаются.

### 5.1 Основные столпы / модули

- Первичный фильтр живости (существующий поверхностный probe).
- Вторичный гейт сигнала (существующая функция глубокой проверки, применённая к новому месту вызова).
- Опт-аут для быстрого прогона без глубокой проверки.

### 5.2 Потоки данных и событий

`сырые кандидаты -> дедуп против каталога -> поверхностный probe -> подтверждение сигнала на живых -> аппенд только подтверждённых -> отчёт с причиной отбраковки`.

### 5.3 Точки расширяемости

- Порог/таймаут/объём глубокой проверки настраиваются существующими параметрами.
- Опт-аут симметричен существующему пропуску поверхностной проверки.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Гео-ограниченный канал читается мёртвым с машины сборщика и не добавляется | Средняя | Реально живой канал не попадёт в каталог | Строгость применяется только к *добавлению* новых строк; существующие не трогаются; prune остаётся консервативным |
| Таймаут глубокой проверки отбраковывает медленный, но живой канал | Низкая | Отдельные валидные каналы пропущены | Настраиваемый таймаут; поведение соответствует цели «не впускать не отвечающие» |
| Замедление сбора из-за тяги байтов | Низкая | Прогон дольше | Глубокая проверка только на подмножестве, прошедшем поверхностный probe (обычно немного после дедупа); есть опт-аут |

## 11. Критерии готовности (strategic-level)

1. Прогон сбора по умолчанию подтверждает реальный сигнал перед добавлением новых строк.
2. Канал с плейлистом `2xx`, но без сегмента, не добавляется в каталог.
3. Отчёт по кандидатам показывает причину отбраковки псевдо-живых.
4. Быстрый прогон без глубокой проверки доступен через явный флаг.
5. Prune существующего каталога остаётся консервативным и не завязан на глубокий сигнал автоматически.
