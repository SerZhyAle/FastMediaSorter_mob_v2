## 1. Проблема

Способность «краевой жест → снимок экрана → сохранение в ресурс» реализована (S0405) и обкатана только на флаворе `noLegal` (sideload, вне ревью Google Play). В Play-флаворах (`standard`, `photos`) её нет: пользователь основного релиза не может из любого приложения краевым жестом снять текущий экран и положить снимок в ресурс FastMediaSorter.

Перенести as-is нельзя: на noLegal тихий захват идёт через `AccessibilityService.takeScreenshot`, а использование accessibility-сервиса для скриншотов - главный вектор отклонения/снятия приложения в Google Play. S0405 осознанно отложил Play-фазу в этот тикет (S0405 §6.4, ADR-6), оставив открытым вопрос допустимого для Play механизма захвата.

---

## 2. Цели

1. Дать Play-флаворам (`standard`, `photos`) ту же пользовательскую способность: краевая жест-полоса поверх других приложений → снимок текущего экрана → сохранение в выбранный ресурс или папку скриншотов.
2. Сделать это Play-безопасно: на Play-флаворах захват идёт только механизмом, санкционированным политикой Play, без accessibility-сервиса для скриншотов.
3. Сохранить продуктовое требование видимого индикатора захвата (S0405 §3.2).
4. Не задеть и не изменить поведение `noLegal`: тихий a11y-путь остаётся его эксклюзивом.
5. Переиспользовать уже flavor-агностичную часть способности (сохранение, выбор назначения, настройки, восстановление после старта) без её дублирования.

**Non-goals:**

- Тихий захват (без диалога согласия) на Play-флаворах - запрещён выбранным механизмом; это эксклюзив `noLegal`.
- Accessibility-сервис для скриншотов в Play-флаворах - вне объёма (Play-риск).
- Выкатка на `lite`, `legacy`, `vr` - вне объёма.
- Изменение noLegal-реализации захвата - вне объёма (порт только добавляет Play-слой).
- Расширенный UX-набор из S0405 §3.1 (выбор края, несколько полос, набор жестов) - наследуется в зафиксированном S0405 виде, не расширяется здесь.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Поведение фичи на Play-флаворе - максимально близкое к noLegal в части включения, краевого жеста, выбора назначения и сохранения; отличается только механизмом захвата.
2. Цена Play-безопасности (диалог-согласие на захват) принимается осознанно как компромисс ради публикуемости основного релиза.

### 3.2 Жёсткие ограничения

- **Flavor:** Play-таргеты `standard` + `photos`. Исключить `lite` (позиционирование «лёгкий»), `legacy` (старые устройства), `vr` (Store-VR shell). `noLegal` не трогается. Реализация обязана следовать `dev/FLAVOR_DEVELOPMENT_RULES.md`: интерфейс способности уже в `src/main/`, Play-реализация - в flavor-source-set, без `BuildConfig.IS_*`-проверок способности в `src/main/` (CLAUDE.md Rule 15).
- **Механизм захвата (Play):** только захват с явным посессионным согласием пользователя и системным индикатором записи. Тихий accessibility-путь на Play-флаворах запрещён; accessibility-сервис в их манифесте не объявляется.
- **API level:** minSdk Play-флаворов - 26. Способность работает на 26+. На устройствах, где захват с согласием недоступен, способность деградирует предсказуемо (вход скрыт/неактивен).
- **Разрешения:** «Показ поверх других приложений» и связанные с выбранным механизмом захвата системные разрешения foreground-сервиса - чувствительные; включаются строго по явному действию пользователя. Для Play требуется заполнение деклараций Play Console на чувствительные разрешения (см. §6).
- **Индикатор захвата:** каждый снимок сопровождается видимым индикатором (системный индикатор записи + тост с назначением и именем файла). Тихий захват на Play-флаворах не допускается.
- **Производительность/батарея:** foreground-сервис под оверлей/захват лёгкий, явно останавливаемый; ресурсы захвата освобождаются сразу после снимка (CLAUDE.md Rule 18).
- **Совместимость данных:** снимок встраивается в существующую модель ресурсов/сохранения; новой формы хранения и миграции не предполагается.
- **Конфликт с системным жестом «Назад»:** наследуется продуктовое решение S0405 (§6.9): левый край осознанно занимается полосой; различение целевого жеста по вектору; системный «Назад» не ломается программно.
- **Локализация:** EN/RU/UK обязательно для всех новых пользовательских строк (если появятся Play-специфичные).
- **Доступность:** прозрачная полоса не озвучивается как элемент; альтернативный доступ к действию «скриншот» (через UI приложения) обязателен (наследуется из S0405).
- **Системные границы:** оверлей уважает `systemBars` + `displayCutout` в обеих ориентациях (CLAUDE.md Rule 17, наследуется).

## 4. Контекст текущей архитектуры

Способность уже расслоена на flavor-агностичное ядро и flavor-реализацию. Ядро (контракт способности, восстановление после холодного старта, сохранение снимка, политика выбора назначения, хранилище настроек, поля модели настроек, гейтинг входа в UI по наличию реализации) живёт во flavor-агностичном слое и не знает деталей захвата. Реализация (оверлей-полоса, foreground-сервисы захвата, маршрутизация) живёт во flavor-слое; флавор без реализации компилируется с пустым набором способности, и вход в UI скрывается сам.

Сейчас flavor-реализация существует только для `noLegal`. Поэтому в `standard`/`photos` ядро присутствует, но набор способности пуст и вход скрыт. Проблема §1 недостижима без добавления Play-безопасной flavor-реализации захвата для этих флаворов.

## 5. Предлагаемый подход

Добавить Play-безопасную flavor-реализацию способности для `standard` и `photos`, переиспользуя flavor-агностичное ядро без изменений и не трогая noLegal-реализацию.

### 5.1 Основные столпы / модули

**A. Play-реализация захвата (consent-based).**
- Роль: на Play-флаворах выполнять захват только механизмом с явным согласием и системным индикатором; accessibility-путь не используется и не объявляется.
- Переиспользует существующую consent-машинерию захвата, отделённую от a11y-специфики.

**B. Краевая жест-полоса для Play-флаворов.**
- Роль: держать у края always-on-top прозрачную зону, распознавать жест-триггер и инициировать захват по Play-пути.
- Поведение полосы и распознавание жеста - как в S0405; отличается только тем, какой путь захвата запускается.

**C. Flavor-проводка способности.**
- Роль: подключить Play-реализацию к контракту способности в ядре по принятому в проекте механизму регистрации flavor-реализаций, и объявить нужные компоненты/разрешения в манифестах Play-флаворов (без accessibility-сервиса).
- Декомпозиция общего и flavor-эксклюзивного кода (общий consent-путь vs noLegal-эксклюзивный a11y-путь) решается на `/spec-tech` по конвенции проекта о разделяемых source-set.

### 5.2 Потоки данных и событий

- Включение: пользователь явно активирует способность в настройках Play-флавора → запрос чувствительных разрешений → запуск foreground-сервиса, показывающего полосу.
- Снимок: жест от полосы → Play-путь захвата запрашивает согласие и снимает кадр (с индикатором) → существующее ядро сохранения применяет назначение → запись через существующий слой файловых операций → обратная связь.
- Выключение: пользователь убирает полосу → сервис и оверлей снимаются, ресурсы захвата освобождаются.
- Восстановление после старта и сохранение - через существующее flavor-агностичное ядро, без изменений.

### 5.3 Точки расширяемости

- Контракт способности в ядре не меняется - Play-реализация подключается как ещё одна flavor-реализация.
- Механизм захвата остаётся за абстракцией: Play-флаворы выбирают consent-путь, noLegal - тихий a11y-путь; добавление новой flavor-стратегии не требует переписывания ядра.
- Общая (не a11y) машинерия захвата выносится так, чтобы Play-флаворы и noLegal делили её без дублирования, а a11y-специфика осталась эксклюзивом noLegal.

## 9. Архитектурные решения (ADR)

**ADR-1: На Play-флаворах захват только consent-механизмом (MediaProjection); a11y - эксклюзив noLegal.**

- **Решение:** `standard`/`photos` захватывают экран только через путь с явным согласием и системным индикатором; accessibility-сервис для скриншотов в этих флаворах не объявляется и не используется. Тихий a11y-путь остаётся только в `noLegal`.
- **Альтернативы:** портировать тихий a11y-путь и в Play (отвергнуто - главный вектор отклонения); не выкатывать в Play вовсе (отвергнуто - цель §1).
- **Почему:** снимает основной Play-policy-риск (S0405 §6.4); цена - диалог согласия, принятая владельцем осознанно (решение 2026-06-15).

**ADR-2: Порт переиспользует flavor-агностичное ядро, не дублируя его.**

- **Решение:** сохранение, выбор назначения, настройки, восстановление после старта и гейтинг входа в UI берутся из существующего ядра; добавляется только Play-flavor-реализация захвата и проводка.
- **Альтернативы:** отдельная параллельная реализация для Play.
- **Почему:** ядро уже flavor-агностично и подключается через набор реализаций; дублирование нарушило бы Rule 20 и плодило бы дрейф.

**ADR-3: noLegal-реализация неприкосновенна; общий код выносится без её регрессии.**

- **Решение:** общая (не a11y) машинерия захвата выносится в разделяемый source-set по конвенции проекта; a11y-специфика остаётся в noLegal; изменения noLegal минимизируются и проверяются сборкой.
- **Альтернативы:** оставить всё в noLegal и дублировать в Play (дрейф); агрессивно рефакторить noLegal (риск регрессии shipped-фичи).
- **Почему:** баланс между Rule 20 (без дублирования) и неприкосновенностью обкатанной фичи.

## 11. Критерии готовности (strategic-level)

1. На `standard` (и `photos`) пользователь включает способность в настройках, и краевая полоса активна поверх других приложений.
2. Жест от полосы снимает текущий экран Play-безопасным механизмом с видимым индикатором и сохраняет снимок в назначение (по умолчанию - папка скриншотов устройства, иначе Downloads).
3. В собранном Play-флаворе accessibility-сервис для скриншотов не объявлен в манифесте.
4. Способность полностью выключается пользователем; после выключения полоса и сервис не остаются активными.
5. Реализация `noLegal` и её тихий a11y-путь не изменены (сборка noLegal зелёная, поведение прежнее).
6. Системный жест «Назад» при активной полосе работает приемлемо (по наследованной митигации S0405).
