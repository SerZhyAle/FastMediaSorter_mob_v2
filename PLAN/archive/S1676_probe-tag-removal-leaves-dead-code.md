## 0. Захваченный материал (inbox)

**Захвачено:** 2026-08-15 (авто-захват по CLAUDE.md 3.1 при работе над S1664)

**Симптом:**

Отладочный зонд `Timber.d("Sxxxx: ..")` удаляется по выходу тикета из `BlockNeedUserTest`, но удаляется только сама строка. Всё, что стояло вокруг неё, остаётся: пустой блок `if`, потерявший единственное содержимое, и импорт `timber.log.Timber`, которым больше никто не пользуется. Формально инвариант зондов соблюдён - строки `Sxxxx:` нет; фактически в дереве накапливается мёртвый код, который ни один гейт не видит.

**Доказательство (найдено попутно, два файла из одного пакета за один заход):**

- `app_v2/src/launcherEnabled/java/com/sza/fastmediasorter/ui/launcher/helpers/LauncherAllAppsGestureManager.kt` - метод `isDesktopAtTop()` содержит `if (!atTop) { }` с пустым телом, и импорт `timber.log.Timber` в файле больше не используется ни разу.
- `app_v2/src/launcherEnabled/java/com/sza/fastmediasorter/ui/launcher/helpers/LauncherSectionCollapseManager.kt` - импорт `timber.log.Timber` не используется.

Обе находки имеют одинаковую подпись: осталась оболочка вокруг удалённой строки лога. Это не совпадение двух опечаток, а след процедуры.

**Что выяснить:**

- Сколько таких следов в дереве на самом деле: два найдены случайно, в одном пакете, за одно чтение по другому поводу. Оценивать объём по этим двум нельзя.
- Ловится ли пустой блок `if` и неиспользуемый импорт существующей конфигурацией detekt/ktlint, и если да - почему эти два прошли (baseline? исключённый source set `launcherEnabled`?).
- Чинить ли причину, а не следствие: удаление зонда должно убирать осиротевшую оболочку, либо гейт снятия зонда должен отказывать, пока она осталась.

**Границы:** не трогать сам инвариант зондов и `assert-no-ticket-logs` - они работают правильно, речь про то, что остаётся после них.

**Захвачено во время:** S1664, чтение пути отрисовки рабочего стола лаунчера.

## 1. Измерение (2026-08-16)

Прогон по всему дереву `app_v2/src` показал, что двух находок было мало на порядок.

- **Пустой блок `if` - 4 штуки**, все с одной подписью «осталась оболочка»:
  `LauncherAllAppsGestureManager.kt:60` (`if (!atTop) { }` в `isDesktopAtTop`),
  `HostReachabilityCheckerImpl.kt:28`, `EpubViewerManager.kt:401` (`if (startChapter > 0) { }`),
  `PdfViewerManager.kt:445` (`if (startPage > 0) { }`).
  Ещё шесть совпадений оказались ложными - это пустые блоки `catch`, а не `if`.
- **Неиспользуемый импорт `timber.log.Timber` - 102 файла.** Признак: импорт есть, ни одного `Timber.`
  ниже нет. Затронуты все наборы исходников, не только `launcherEnabled`.

Почему это не ловится: `NoUnusedImports` в конфигурации detekt работает - он поймал такой импорт в
`BrowseStateUiUpdater.kt` в этот же день, как только файл попал в изменённый набор. Но гейт судит только
изменённые файлы, а счётчики по проекту храповые: 102 старых импорта - это принятый долг, который никогда не
попадает в набор, потому что никто эти файлы не трогает.

## 2. Что сделано

- Удалены все четыре оболочки. `isDesktopAtTop()` при этом сократился до выражения - тело функции состояло
  только из вычисления и мёртвой ветки.
- Удалены все 102 неиспользуемых импорта.
- Проверено: `.\a.ps1 fk` и `.\a.ps1 fkn` - exit 0, то есть ни один импорт не был нужен на самом деле;
  `.\a.ps1 fu` - без новых падений.

## 3. Причина, а не следствие

Осталось нерешённым и вынесено сюда явно: удаление зонда по-прежнему удаляет только строку. Пока снятие
зонда не убирает осиротевшую оболочку (или пока гейт снятия не отказывает, увидев её), след будет
накапливаться снова - медленнее, потому что теперь дерево чистое, но по той же причине. Это правка
процедуры снятия зонда в `/spec-check`, а не правка кода приложения.
