# Стратегическая спецификация: S0076 — DVD VOB по сети не должен идти через Blu-ray TS-маршрут

## 1. Проблема

Файлы `.vob` из DVD-структур по сети сейчас могут ошибочно попадать в тот же маршрут, который предназначен для Blu-ray Transport Stream. Полевой лог 2026-05-04 показал сигнатуру: сначала выбирается BD-TS-ветка, затем поток читается 192-байтовыми порциями, после чего Media3 не распознаёт контейнер и выдаёт source-format ошибку. Сразу после этого network fallback пропускается, а проигрыватель автоматически пытается открыть следующий файл, из-за чего вся `VIDEO_TS`-цепочка может быть «пролистана» за секунды без понятного объяснения пользователю.

Эффект для пользователя двойной: DVD-файл, который должен либо воспроизводиться, либо дать одну ясную ошибку, вместо этого попадает в каскад мгновенных провалов; а смежные соседние сегменты воспринимаются как будто они тоже битые. Проблема проявляется именно как дефект маршрутизации контейнера, а не как случайная сетевая нестабильность.

---

## 2. Цели

1. `.vob`-файлы с сетевых источников больше не попадают в BD-TS-маршрут и не подвергаются 4-байтовому stripping-шагу.
2. Для DVD Program Stream выбирается корректный playback-path: либо воспроизведение стартует, либо пользователю показывается одна понятная ошибка без ложного авто-перехода по соседним сегментам.
3. Ошибка на одном `.vob`-сегменте не запускает каскадный auto-skip по всей текущей DVD-цепочке без явного решения пользователя.
4. Уже исправленный `.m2ts` / `.m2t` network-path не регрессирует из-за новой развилки контейнеров.
5. Добавляется как минимум одна автоматическая проверка маршрутизации контейнера и один воспроизводимый manual-сценарий на реальном сетевом DVD-наборе.

**Non-goals:**

- Полная DVD-навигация по IFO/BUP, меню диска и главы.
- Поддержка ISO-образов, зашифрованных DVD и любых optical-disc extras.
- Генерация миниатюр для `.vob` / `VIDEO_TS` в браузере файлов — это отдельная задача S0077.
- Переписывание всей политики auto-next для всех типов медиа; в объёме только защитный контур для format-route failures на VOB-цепочках.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Если сеть и контейнер позволяют, желательно воспроизводить `.vob` без дополнительных ручных переключателей или отдельного «DVD mode».
2. Если воспроизведение конкретного `.vob` действительно невозможно, предпочтительнее одна явная причина с остановкой на текущем файле, чем молчаливое пролистывание соседних сегментов.
3. Желательно, чтобы диагностика различала минимум три состояния: `dvd-ps`, `bd-ts`, `unknown-container`.

### 3.2 Жёсткие ограничения

- **Flavor:** все флейворы с видеоплеером (`standard`, `lite`, `legacy`, `vr`); `photos` не затрагивается.
- **API level:** без новых API-зависимостей; поведение должно укладываться в текущий стек Android/Media3.
- **Wear OS:** не затрагивается.
- **Производительность:** классификация контейнера не должна требовать заметного прогрева всего файла; допустим только лёгкий initial sniff или надёжная типизация по уже доступным признакам.
- **Совместимость данных:** без миграций Room и без пользовательских настроек миграции.
- **Локализация:** любые новые user-facing ошибки обязательны в EN/RU/UK.
- **Доступность:** если появляется новый blocking-dialog или toast, он должен быть корректно озвучиваем TalkBack.

## 4. Контекст текущей архитектуры

Сетевое воспроизведение видео в проекте строится вокруг выбора transport/wrapper-ветки до фактической инициализации проигрывателя. Для Blu-ray TS уже есть отдельный маршрут с преобразованием 192-байтового BD-TS в обычный TS-поток. Этот маршрут нужен для `.m2ts`, но полевой лог показал, что граница между TS-контейнерами и DVD Program Stream сейчас недостаточно жёсткая.

Дополнительная проблема в том, что форматная ошибка на network-path сейчас связана с политикой перехода к следующему файлу. В результате дефект контейнерной маршрутизации маскируется под обычный «неудачный текущий файл», хотя на самом деле пользователь теряет контроль сразу над целой цепочкой `.vob`-сегментов.

---

## 5. Предлагаемый подход

Контейнер должен классифицироваться до выбора transport-wrapper, а не после него. Для `.vob` это означает отдельную DVD PS-ветку без Blu-ray stripping, с отдельным правилом обработки format-route failures.

### 5.1 Основные столпы / модули

**A. Container-first classification**

Перед выбором TS-обработки система должна различать как минимум три класса: BD-TS, обычный TS и DVD Program Stream. `.vob` не должен зависеть от логики, предназначенной для TS-контейнеров, даже если соседние пути используют общий network/media bootstrap.

**Б. Безопасный network-route для DVD VOB**

Для `.vob` выбирается маршрут без BD-TS stripping. Если текущий стек способен воспроизвести контейнер напрямую, он должен получать исходные байты без дополнительных преобразований; если не способен — отказ должен происходить явно и предсказуемо.

**В. Containment для цепочек сегментов**

Format-route failure на `.vob` не должен автоматически перекидывать проигрыватель через десятки соседних сегментов. Для DVD-цепочки нужен защитный контур: один ясный отказ на текущем файле, без лавинообразного auto-next до тех пор, пока пользователь сам не решит продолжать.

**Г. Диагностика маршрута**

Лог должен однозначно показывать классификацию контейнера, выбранный playback-route и причину fallback/skip-решения. Это позволит отличать «неверно выбранный маршрут» от «контейнер реально не поддерживается».

### 5.2 Потоки данных и событий

```text
Открытие сетевого .vob
  → классификация контейнера
      → DVD Program Stream → прямой VOB playback-route
      → BD-TS / TS → существующие TS-ветки
      → unknown → единая понятная ошибка
  → попытка воспроизведения
      → success → playback продолжается штатно
      → failure on current VOB → одна ошибка без каскадного auto-next по соседним сегментам
```

### 5.3 Точки расширяемости

- Таблица контейнерной классификации должна допускать добавление новых optical-disc сценариев без переписывания всего network bootstrap.
- Политика обработки consecutive format failures должна быть отделима от общей логики `next/previous`, чтобы её можно было использовать и для других chain-based форматов, если такие случаи появятся позже.

## 6. Открытые вопросы / Research items

1. **Нужен ли отдельный chain-policy для DVD-сегментов?**
   - **Вопрос:** достаточно ли просто не auto-skip'ать format-route failure, или нужно распознавать «главный фильм vs сервисные сегменты» внутри DVD-цепочки?
   - **Исследование:** Текущий путь ошибки уже подтверждён кодом: `PlayerPlaybackCallbackImpl.onPlaybackError()` безусловно вызывает `PlayerActivity.handleMediaLoadErrorAndSkip()`, а тот сразу делает toast + `navigateNextFromControl()`. То есть каскадный skip сейчас общий и не различает причины ошибки.
   - **Вывод:** Для первой итерации не вводить специальную playlist-эвристику по сегментам. Достаточно перехватить VOB route-error до общего `onPlaybackError()` и остановиться на текущем файле с отдельным диалогом. Общий `next/previous` слой не трогать.
   - **Статус:** Verified

2. **Затронут ли локальный и облачный VOB-path?**
   - **Вопрос:** проблема ограничена сетевыми маршрутами или shared container-bootstrap уже влияет и на другие источники?
   - **Исследование:** Локальный путь зондирует только `.m2ts` / `.m2t` и для `.vob` сразу использует MPEG-2 MIME без BD-TS route. Облачный путь тоже запускает `detectTsFormatSuspend()` только для `.m2ts` / `.m2t`. Полевой дефект проявился именно на SMB/SFTP/FTP ветках, где `UNKNOWN` ошибочно трактуется как повод включить BD-TS обёртку.
   - **Вывод:** Scope первой итерации — network-only (`smb://`, `sftp://`, `ftp://`). Local/cloud VOB-path не менять.
   - **Статус:** Verified

3. **Разрешать ли fallback через альтернативный проигрыватель/прокси?**
   - **Вопрос:** нужен ли отдельный fallback-path для `.vob`, если основной стек не принимает контейнер на конкретном протоколе?
   - **Исследование:** Текущий `MediaPlayer` fallback уже жёстко ограничен локальными путями; для сетевых URI он намеренно пропускается. Проблема S0076 воспроизводится ещё до полезной проверки fallback и вызвана именно неверным route-selection.
   - **Вывод:** В первой итерации не добавлять новый network fallback. Исправить route-selection и containment ошибки; fallback вынести в отдельную задачу только если после этого останется реальный форматный пробел.
   - **Статус:** Verified

## 9. Архитектурные решения (ADR)

**ADR-1: Контейнер классифицируется до transport-wrapper**

- **Решение:** сначала определить тип контейнера, затем выбирать route/wrapper.
- **Альтернативы:** продолжать выбирать route по расширению, соседнему path или общей эвристике network-video.
- **Почему:** VOB и BD-TS требуют принципиально разной подготовки байтового потока; перепутанный маршрут ломает воспроизведение ещё до реальной проверки формата.

**ADR-2: Format-route failure на DVD-цепочке не равен «следующий файл, пожалуйста»**

- **Решение:** каскадный auto-next ограничивается, если отказ вызван маршрутизацией/классификацией контейнера на `.vob`.
- **Альтернативы:** оставить текущий blind auto-next после каждой format error.
- **Почему:** в optical-disc сценарии ошибка маршрута затрагивает не один файл, а целую последовательность сегментов; молчаливый пролёт ухудшает UX сильнее, чем один честный стоп.

## 11. Критерии готовности (strategic-level)

1. Пользователь открывает сетевой `.vob` из DVD-структуры и получает либо успешное воспроизведение, либо одну понятную ошибку на текущем файле.
2. После format-route failure на `.vob` приложение не пролистывает автоматически длинную цепочку соседних DVD-сегментов.
3. В диагностическом логе для `.vob` больше не видно признаков Blu-ray TS-маршрута.
4. Сетевой `.m2ts` / `.m2t` продолжает воспроизводиться по своему существующему TS-path без регрессии.
5. Если для новой ошибки добавлен user-facing текст, он присутствует в EN/RU/UK.
