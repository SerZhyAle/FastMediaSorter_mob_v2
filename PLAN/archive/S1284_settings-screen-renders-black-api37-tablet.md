## 0. Захваченный материал (inbox)

**Захвачено:** 2026-07-29

**Захвачено во время:** device-теста S1103 (`/spec-test-device`) на emulator-5554.

**Симптом:** `SettingsActivity` (и все её диалоги) рисуется полностью чёрной - на экране не видно ни одного элемента, кроме системного статус-бара. Иерархия представлений при этом целая: `uiautomator dump` возвращает корректные `text`/`bounds` для всех строк настроек, тапы по этим координатам работают и меняют состояние. То есть layout проходит, а отрисовка даёт чёрный кадр.

**Окружение:**

- Устройство: `emulator-5554`, `sdk_gphone16k_x86_64`, Android 17 (SDK 37), 1600x2560 @320dpi, портрет.
- Сборка: `com.sza.fastmediasorter.debug`, `versionName=2.60.7262.102-DEBUG`, `versionCode=260726210`, standard debug.
- Образ AVD - 16 KB page size (`gphone16k`), что само по себе частый источник графических аномалий.

**Измерения (скриншот `screencap` на устройстве, доля чёрных пикселей):**

- `LauncherHomeActivity`: 25757 уникальных цветов, чёрного 0.1% - рисуется нормально.
- `SettingsActivity`: 254 уникальных цвета, чёрного 99.9% - видны только иконки статус-бара.
- Тот же результат в свежем процессе после `am force-stop`.
- Тот же результат при `cmd uimode night yes` и при `night no`.
- Системные диалоги поверх (`ACCESS_FINE_LOCATION`, battery-exemption) рисуются корректно - значит `screencap` и композитор работают, чёрная именно наша activity.

**Что проверено и исключено:**

- Нет `wm size`/`wm density` override: `Physical size: 2560x1600`, `Physical density: 320`.
- `color_theme_prefs.xml` = `AUTO` - не форсированная тёмная/AMOLED тема.
- `animator_duration_scale` = null (по умолчанию).
- В logcat нет исключений; HWUI рапортует нормальные кадры (`SwapBuffers`, `GpuCompleted`), только медленные (`Davey! duration=952..1207ms`, `Skipped 34..37 frames`).

**Обходной путь, применённый в S1103:** экран водился «слепо» по координатам из `uiautomator dump` - содержимое и границы целые, поэтому навигация возможна без картинки.

## 1. Проблема

На эмуляторе API 37 (планшетная геометрия, 16k-образ) экран настроек визуально недоступен: пользователь видит чёрный прямоугольник вместо списка настроек. Иерархия и обработка нажатий целы, значит проблема в отрисовке/композиции конкретного окна, а не в разметке. Неизвестно, воспроизводится ли на реальном устройстве с API 37 - если да, экран настроек нерабочий для целого API level.

## 7. Разбор - это не дефект отрисовки, а FLAG_SECURE

Установлено 2026-07-31. Экран настроек рисуется нормально; чёрным получается **снимок**, а не экран.

Доказательства, каждое проверяемо:

- `SettingsActivity.isSensitiveScreen()` возвращает `true` (`SettingsActivity.kt:56`).
- `AppSettings.secureSensitiveScreens` по умолчанию `true` (`AppSettings.kt:387`).
- `BaseActivity.applySecureFlagIfEnabled` при этом сочетании вешает `WindowManager.LayoutParams.FLAG_SECURE` (`BaseActivity.kt:381-388`). Это S1045, сделано намеренно: блокировать скриншоты и превью в Recents на экранах с учётными данными.
- Платформа это подтверждает: `dumpsys window windows` для окна `SettingsActivity` на `emulator-5556` печатает `fl=KEEP_SCREEN_ON LAYOUT_IN_SCREEN SECURE LAYOUT_INSET_DECOR ..`.

Второе устройство (закрывает первый вопрос §6): `emulator-5556`, Android 13 (SDK 33), 1080x2400 @420dpi, не 16k-образ. Там `screencap` на этом экране отдаёт файл **нулевой длины**, тогда как контрольный снимок домашнего экрана в том же прогоне - валидный PNG на 1.37 МБ. То есть дефект не привязан ни к API 37, ни к 16 KB page size: защищённое окно просто не попадает в захват, а разные версии платформы «глушат» его по-разному - где-то пустым файлом, где-то чёрным кадром.

Это объясняет **все** наблюдения из §0, ни одно не приходится списывать на совпадение: иерархия цела и тапы работают (окно живо и обрабатывает ввод), системные диалоги поверх снимаются нормально (это отдельные окна, и они не secure), в logcat нет исключений, HWUI исправно рапортует кадры, а в кадре виден только статус-бар - тоже отдельное, не защищённое окно.

Ответы на §6:

- Воспроизводится ли на API 33 и на реальном устройстве - да, воспроизводится везде, где включена настройка, и это ожидаемое поведение, а не поломка.
- Связано ли с 16 KB page size - нет.
- Какое окно чёрное - окно самой activity, потому что на нём стоит `SECURE`; корневой `DecorView` тут ни при чём.

Следствие для §3.3: решение владельца о «блокере релиза» не требуется - блокировать нечего.

Остаточная работа - методическая: зафиксировать ловушку, чтобы следующий device-тест не потратил на неё время заново. Сделано в `docs/TEST_SCENARIOS.md`.
