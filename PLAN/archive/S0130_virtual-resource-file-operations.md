## 1. Проблема

Агрегированные виртуальные ресурсы («Все фото», «Все видео», «Фото с камеры», «Вся музыка», «Все документы») создаются без права записи, что блокирует удаление, переименование и редактирование файлов через плеер. При этом сами файлы физически расположены в локальном хранилище и полностью доступны для изменения. Пользователь вынужден открывать реальную папку только для того, чтобы удалить или переименовать файл, уже открытый в плеере — это разрывает рабочий процесс.

---

## 2. Цели

1. В плеере при открытии файла из агрегированного виртуального ресурса доступны кнопки удаления, переименования и редактирования (crop/compress/draw/edit).
2. Агрегированные виртуальные ресурсы по-прежнему недоступны в качестве получателя копирования/перемещения — панель «Копировать в» и «Переместить в» не предлагает их как цель.
3. Ресурс «Недавние» (`virtual://recent`) не затронут — он агрегирует разнородные типы и его сценарий использования иной.

**Non-goals:**

- Создание реальной папки при операции записи в виртуальный ресурс как источник.
- Изменение логики копирования/перемещения файлов между ресурсами.
- Создание виртуальных ресурсов-получателей любого рода.
- Изменение ресурса «Недавние».

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Существующие виртуальные ресурсы у установленных пользователей автоматически получают право записи после обновления — без ручного редактирования каждого ресурса.

### 3.2 Жёсткие ограничения

- **Flavor:** все варианты сборки (standard, lite, photos, legacy).
- **API level:** без API-специфики.
- **Wear OS:** не затрагивается.
- **Производительность:** нет дополнительной нагрузки.
- **Совместимость данных:** требуется миграция данных — разовое исправление флага `isWritable` для существующих агрегированных виртуальных ресурсов в БД при старте приложения; без изменения схемы Room.
- **Локализация:** строки не добавляются.
- **Доступность:** не затрагивается.

---

## 4. Контекст текущей архитектуры

Виртуальные ресурсы — это предустановленные записи в БД с путями `virtual://all_*` и `virtual://camera_photos`. Они создаются при первом запуске с `isWritable = false` и `isDestination = false`. Логика доступности кнопок в плеере (`canWrite`) определяется полем `isWritable` ресурса. Поскольку поле `isWritable = false`, все операции записи — удаление, переименование, редактирование — недоступны, несмотря на то что операции физически выполняются над локальными файлами, а не над самим виртуальным контейнером.

Аналогичная проблема с облачными ресурсами и некоторыми локальными ресурсами уже была устранена через startup-фиксеры (паттерн `fixCloudResourcesIsWritable`, `fixLocalResourcesIsWritable`). Тот же паттерн применим здесь.

## 5. Предлагаемый подход

### 5.1 Основные столпы

**Provisioning — новые установки**

При создании агрегированных виртуальных ресурсов на первом запуске выставлять `isWritable = true` и `isDestination = false`.

**Startup migration — существующие установки**

При старте приложения, по аналогии с существующими startup-фиксерами, найти все ресурсы с агрегированными виртуальными путями, у которых `isWritable = false`, и установить `isWritable = true`. «Недавние» (`virtual://recent`) явно исключаются.

### 5.2 Потоки данных и событий

Старт приложения → startup-фиксер проверяет агрегированные виртуальные ресурсы → для каждого с `isWritable = false`: обновляет запись в БД → `isWritable = true`. При следующем открытии плеера: `canWrite = true` → кнопки удаления/переименования/редактирования видны. Панель получателей: `isDestination = false` → виртуальные ресурсы не предлагаются как цель.

### 5.3 Точки расширяемости

Добавление новых агрегированных виртуальных путей в будущем: достаточно добавить путь в `isAggregateVirtualPath()` — фиксер и provisioning подхватят автоматически.

## 9. Архитектурные решения (ADR)

**ADR-1: startup-фиксер вместо схемной миграции Room**

- **Решение:** исправлять `isWritable` через startup-фиксер при старте, без изменения версии схемы Room.
- **Альтернативы:** Room Migration, добавляющая SQL-апдейт по виртуальным путям.
- **Почему:** паттерн startup-фиксера уже используется в проекте для аналогичных задач; он изолирован от схемы и не требует инкремента версии БД.

## 11. Критерии готовности (strategic-level)

1. При открытии изображения из ресурса «Все фото» в плеере видны кнопки удаления, переименования, crop/compress/draw.
2. При открытии видео из ресурса «Все видео» видны кнопки удаления, переименования, редактирования.
3. Ни один из агрегированных виртуальных ресурсов не появляется в панели «Копировать в» / «Переместить в».
4. Ресурс «Недавние» не изменил поведения.
5. У пользователей с уже установленным приложением кнопки операций появляются после обновления без ручного редактирования ресурса.
