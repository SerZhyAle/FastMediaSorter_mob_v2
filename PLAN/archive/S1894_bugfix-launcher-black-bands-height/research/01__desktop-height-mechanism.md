# 01 - Как сегодня определяется вертикальный размер экрана лаунчера

**Тикет:** S1894
**Дата:** 2026-08-21
**Метод:** чтение исходников `app_v2` (сорс-сет `launcherEnabled`), поиск по каталогу классов, поиск по каталогу спек.

---

## Что установлено

### Три независимых механизма делят высоту

1. **Отступы под системные врезки.** Корневой контейнер экрана лаунчера получает padding, равный врезкам системных панелей и выреза. Окно при этом объявлено edge-to-edge (декор не подгоняется под системные окна).
2. **Разметка экрана.** Внутри отступов - три области: полоса состояния лаунчера (фиксированные 28dp, скрыта, пока не включена замена системной строки состояния), прокручиваемая область рабочего стола, панель задач (фиксированные 56dp, по умолчанию прижата к низу).
3. **Собственный обмер полотна рабочего стола.** Полотно - кастомная `ViewGroup`. Её `onMeasure` рапортует высоту `padding + rows * cellSize + padding` и **игнорирует переданный ей `heightMeasureSpec`**.

### Ключевая находка

Прокручиваемая область объявлена с `fillViewport="true"`, то есть она обязана растянуть дочернее полотно до высоты вьюпорта. Но растяжение работает только если ребёнок уважает `EXACTLY`-спеку. Полотно её не уважает - оно всегда самоопределяется по числу занятых строк. Поэтому **растянуть рабочий стол до высоты экрана сегодня невозможно в принципе**, сколько бы места ни оставалось.

Число строк вне режима редактирования берётся строго по занятому контенту; число строк вьюпорта в этот момент осознанно отбрасывается (в коде это помечено как намеренное решение: "один экран плюс прокрутка вниз", без страниц рабочего стола). В режиме редактирования, наоборот, берётся `max(занято + запас, строк во вьюпорте)` - то есть нужная арифметика в коде уже есть и применяется, просто не в покое.

### Почему «даже после сброса»

Сброс лаунчера чистит ячейки, закрепления, журнал и статистику и возвращает настройки лаунчера к значениям по умолчанию, но сам стартовый набор ячеек не пересевает - это делает следующий запуск экрана лаунчера. Результат: после сброса рабочий стол гарантированно разрежен, то есть занятых строк заведомо меньше, чем помещается на экран. Сброс не лечит симптом, а воспроизводит его наиболее чисто.

### Почему полосы именно чёрные

Обои по умолчанию - брендовый анимированный слой (волны и частицы). В нелайтовой теме он заливает свой буфер чистым чёрным. Этот слой лежит под всей стопкой, поэтому любой незанятый вертикальный зазор проявляется как настоящий чёрный прямоугольник, а не как цвет поверхности темы. Это совпадает с описанием владельца дословно.

### Чего в коде НЕ нашлось

- Для активности лаунчера нигде не объявлен режим работы с вырезом дисплея. В сочетании со скрытием системной строки состояния это известный сценарий, при котором на аппаратах Samsung сверху остаётся полоса, которую приложение не видит и не может обмерить. Из кода это не подтверждается и не опровергается - нужен замер на устройстве.
- Нет ни одного юнит- или инструментального теста на геометрию рабочего стола. Обмер полотна - чистая детерминированная арифметика, то есть ровно тот класс дефекта, который тест ловит дешевле всего.

### Дубликатов нет

Поиск по каталогу спек по одиночным словам (`insets`, `edge`, `geometry`, `height`, `fullscreen`) не дал ни одного тикета про высоту экрана лаунчера. Ближайшие соседи - тикет про восстановление высоты после возврата из фона (закрыт) и черновик про плотность ярлыков при сбросе.

---

## Что из этого следует для спеки

Есть **две независимые причины** одинакового симптома, и они требуют разных правок:

- зазор **внутри** UI лаунчера - между последней строкой ячеек и панелью задач - объясняется обмером полотна и политикой числа строк;
- полосы **снаружи** всего UI лаунчера - между физическим краем экрана и полосой состояния или панелью задач - обмером не объясняются и указывают на размер самого окна.

Различить их без снимка с устройства нельзя. Поэтому спека держит этот вопрос открытым и делает замер на устройстве первым шагом, а не последним.
