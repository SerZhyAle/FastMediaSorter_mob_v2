камера - при нажатии на экран там по идее должен производится автофокус по этой области - я прицел вижу, а смены фокуса - нет

---

## 1. Проблема / симптом

Касание экрана съёмки рисует прицел автофокуса, но фокус не меняется. То есть обратная связь есть, а действия нет - и по экрану это неотличимо от «сфокусировался, просто разница не видна».

---

## 2. Корневая причина

Прицел показывается за **разрешение** сфокусироваться, а не за **поданный** запрос фокуса.

Решение о прицеле принимает `CameraCaptureGestureCallbackHandler:21`:

```kotlin
if (flowManager.onTapToFocus(x, y)) focusRingOverlay.showAt(x, y)
```

А `CameraCaptureFlowManager.onTapToFocus` проверяет ровно одно условие и дальше отвечает «да» независимо ни от чего:

```kotlin
if (!currentCapabilities.supportsTapToFocus) return false
session.startFocusAndMetering(x, y)
return true
```

При этом `CameraCaptureSessionManager.startFocusAndMetering` возвращает `Unit` и имеет **три** собственных тихих отказа, о которых верхний слой не узнаёт:

- камера или `previewView` ещё не привязаны (`control == null || preview == null`);
- повторная проверка `supportsTapToFocus`;
- макро-охрана S1189: при удерживаемом фиксированном фокусе запрос намеренно игнорируется, «rather than half-applied».

Плюс четвёртый: сама подача обёрнута в `runCatching { .. }.onFailure { Timber.w(..) }` - отказ CameraX только пишется в лог.

В каждом из четырёх случаев `onTapToFocus` уже вернул `true`, прицел нарисован, а фокус никто не запрашивал. Собственный KDoc метода - «returns whether the focus ring should be shown» - описывает контракт, которого код не выполняет; по правилу 8 это требование, а не комментарий.

Отдельно: `CameraControl.startFocusAndMetering` возвращает `ListenableFuture<FocusMeteringResult>`, и результат нигде не читается. Поэтому случай «устройство приняло запрос и не смогло сфокусироваться» сегодня тоже выглядит как успешный прицел.

**Границы.** Устранение подмены обратной связи доказуемо здесь. Какой именно из четырёх путей сработал на устройстве владельца - этим не решается: после правки прицел просто перестанет врать, а лог назовёт причину. Если окажется, что запрос подавался и принимался, а фокус всё равно не двигался, - это уже другая причина, и §2 придётся дополнять.

---

## 3. Исправление

- `startFocusAndMetering` возвращает `Boolean` - подан ли запрос на самом деле; каждый ранний выход отдаёт `false`, неудача `runCatching` - тоже.
- `onTapToFocus` возвращает этот результат, а не константу, - и тогда его KDoc становится правдой.
- Временный зонд на месте подачи: он печатает сам факт подачи, чем и отвечает на вопрос «какой из четырёх путей сработал».

**Чего сознательно не делаем.** Первая редакция читала `ListenableFuture<FocusMeteringResult>` через `addListener`, чтобы отделить «устройство не приняло» от «приняло и не смогло». Гейт симметрии слушателей это отклонил - и по делу: он считает `addListener` без парного `removeListener`, а исключений не поддерживает. Утечки здесь нет (`ListenableFuture` срабатывает единожды и API снятия не имеет), но обходить гейт переименованием - значит сломать его для всех остальных. Первичный вопрос §2 закрывается и без этого: он про то, подавался ли запрос вообще. Наблюдение за исходом - отдельное улучшение, и делать его надо вместе с механизмом исключений в гейте, а не вопреки ему.

### Расхождение: status note требует строку, которой в коде нет

Status note отправляет тестировщика искать `S1419: focus request settled successful=..`. Этой строки нет: единственный зонд - `Timber.d("S1419: focus request submitted")` в `CameraCaptureSessionManager.kt:557`. §3 объясняет, почему так и задумано: чтение `ListenableFuture<FocusMeteringResult>` через `addListener` отклонил гейт симметрии слушателей, и наблюдение за исходом сознательно не делали. Status note остался написан под ту, отменённую редакцию.

Что из этого следует. Лог отвечает на вопрос «подавался ли запрос» - это и был первичный вопрос §2, и он закрыт. Отличить «устройство сфокусировалось» от «приняло и не смогло» этот лог не может; здесь разница снята оптически - по кадрам видно, что сцена действительно стала резкой. То есть исход известен, но не из лога.

Правка кода по этому расхождению не делалась - фиксация, а не исправление. Кандидат на `/spec-update S1419`: привести status note к строке, которую код печатает.

### Попутное наблюдение

Задний основной объектив на 1x при активном профиле Normal подписан как `Macro` (эвристика S0753 по дистанции фокусировки). На поведение фокуса это не влияет: охрана смотрит на `macroEnabled`, а не на подпись. Отдельный тикет не заводился - тему подписи объектива уже ведёт **S1479**.
