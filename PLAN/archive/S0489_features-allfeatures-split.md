## 1. Проблема

Сегодня `docs/FEATURES*` пытается быть одновременно двумя несовместимыми вещами: маркетинговой витриной (что показать пользователю и на сайте) и техническим инвентарём (полный перечень реализованного для девелоперов и как скелет документации). Из-за этого витрина раздута техническими деталями, а полного инвентаря всё равно нет: множество реализованного функционала нигде не зафиксировано как структурированные данные. Спеки описывают свой результат в разрозненных местах (журнал, changelog, тело спеки), единой «базы данных функционала» не существует. Это блокирует написание документации настроек и программы (S0440), потому что нет источника истины о том, что вообще умеет приложение.

## 2. Цели

1. Развести два документа по назначению: `FEATURES*` - кураторская публичная витрина (уникальный/полезный функционал, идёт на сайт); `ALL_FEATURES` - полный технический инвентарь всего реализованного функционала как структурированная текстовая база данных.
2. Пересмотреть текущий `FEATURES*`: оставить только то, что действительно стоит показывать пользователю и на сайте.
3. Полностью просканировать приложение параллельными агентами и популировать `ALL_FEATURES` всем фактически реализованным функционалом.
4. Зафиксировать в правилах проекта и скилах: спеки пишут результат в `ALL_FEATURES`; `FEATURES*` трогается только для действительно витринных возможностей.
5. Дать S0440 готовый источник истины о функционале для написания документации настроек и программы.

**Non-goals:**

- Написание самой документации настроек/программы (это S0440, потребитель данных).
- Редизайн сайта или его движка - только наполнение витрины выверенным составом.
- Изменение поведения приложения - работа чисто с описанием/инвентаризацией.

3. `FEATURES*` после ревизии - компактная витрина, без технического шума.

- **Локализация:** `FEATURES*` (витрина) - EN/RU/UK обязательно; `ALL_FEATURES` - EN-only.

## 4. Контекст текущей архитектуры

`docs/FEATURES.md` (+ `_RU`/`_UK` и gitignored `_noLegal*`) - сейчас единственный человекочитаемый инвентарь возможностей, организованный по разделам с метками доступности `[Standard / VR]` и т.п. Параллельно существует `dev/FUNCTIONALITY.log` - хронологический журнал жизненного цикла user-visible функционала (ADD/CHANGE/DELETE/FIX, привязка к `Sxxxx`), пишется через `scripts/add_to_functionality_log.ps1`; его шапка прямо указывает на `FEATURES.md` как на каталог. Скилы и правила (`/spec-dev`, `/spec-check`, `/doc-update`, `quick`, CLAUDE.md §11) ссылаются на `FEATURES*` как на место фиксации user-facing изменений. То есть «снимок текущего состояния» и «поток изменений» сегодня размазаны: журнал - хронология, `FEATURES` - смесь витрины и инвентаря, а структурированной базы текущего состава функционала нет.

## 5. Предлагаемый подход

Свести функционал к двум артефактам: `ALL_FEATURES` - JSONL-инвентарь всего реализованного (источник истины, заменяет `dev/FUNCTIONALITY.log`), и `FEATURES*` - кураторская витрина для пользователя/сайта. Хронология изменений берётся из git-истории `ALL_FEATURES` и релизных диффов, а не из отдельного журнала.

### 5.1 Основные столпы / модули

1. **Инвентаризация (популяция ALL_FEATURES).** Полное сканирование приложения параллельными агентами по областям/модулям; каждая запись - единица функционала с описанием, областью, доступностью по flavor и привязкой к спеке-источнику (если есть).
2. **Ревизия FEATURES.** Из текущего `FEATURES*` оставить только витринные возможности по согласованному критерию; остальное переезжает/отражается в `ALL_FEATURES`.
3. **Миграция журнала.** Перенести существующие записи `dev/FUNCTIONALITY.log` в `ALL_FEATURES` и вывести журнал из эксплуатации.
4. **Правила и скилы.** Развести в правилах: спеки пишут запись в `ALL_FEATURES` (вместо журнала); `/skill-release` наполняет витрину из релизного диффа базы; `FEATURES*` руками не дополняется на каждую фичу.
5. **Гейт связности.** Механическая проверка: новая/изменённая user-facing возможность из спеки отражена в `ALL_FEATURES`; витрина не дублирует технический шум.

### 5.2 Потоки данных и событий

- код/спеки → инвентаризация → запись/обновление JSONL в `ALL_FEATURES` (EN-only база).
- спека закрывается → апдейт записи фичи в `ALL_FEATURES` вместо строки в `dev/FUNCTIONALITY.log`; хронология берётся из git-истории файла.
- релиз → `/skill-release` читает дифф `ALL_FEATURES` с прошлого релиза → важные решения добавляются/правятся в `FEATURES*` (EN/RU/UK) → авто-публикация на сайт.
- `ALL_FEATURES` → потребитель S0440 (документация настроек/программы).

### 5.3 Точки расширяемости

- Запись `ALL_FEATURES` расширяема под доп. атрибуты (тип, экран, связи с настройками) без переписывания витрины.
- База расширяема под `wear`-модуль и под flavor-добавки (noLegal) по аналогии с `FEATURES_noLegal*`.
- Флаг/поле важности в записи может в будущем подсказывать `/skill-release` кандидатов витрины, не ломая схему.

## 9. Архитектурные решения (ADR)

**ADR-1: ALL_FEATURES (JSONL) заменяет dev/FUNCTIONALITY.log как источник истины о функционале.**

- **Решение:** единая EN-only JSONL-база записей функционала; спеки обновляют запись фичи вместо строки в журнале; хронология читается из git-истории файла и релизных диффов.
- **Альтернативы:** держать журнал и базу параллельно; генерировать базу из журнала.
- **Почему:** одно место ведения, машиночитаемость для S0440 и `/skill-release`, отсутствие двойного учёта.

**ADR-2: FEATURES наполняется релизным конвейером, а не вручную и не флагом в базе.**

- **Решение:** `/skill-release` диффит `ALL_FEATURES` между релизами и переносит в `FEATURES*` (EN/RU/UK) только важные решения; витрина авто-публикуется на сайт.
- **Альтернативы:** ручная курация владельцем; поле `showcase` в каждой записи.
- **Почему:** витрина обновляется ровно в момент релиза, без отдельной ручной синхронизации и без раздувания схемы базы.
