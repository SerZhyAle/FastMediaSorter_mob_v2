## 0. Захваченный материал (inbox)

**Захвачено:** 2026-08-11

**Текст:**

Camera bring-up does synchronous filesystem work on the main thread - four StrictMode-confirmed sites on the camera-open path, none covered by an existing ticket

Найдено попутно во время `/spec-sweep` на реальном устройстве RFCR110NBQJ (Samsung Galaxy S21+, SM-G996U1, Android 15 / SDK 35), standard debug. Не относится к проверявшимся тикетам - запарковано без переключения активной задачи.

**Как получено.** StrictMode в этой сборке взведён (`FastMediaSorterApp.setupDebugStrictMode`, `ENABLE_DEBUG_STRICT_MODE = true`, `detectDiskReads` + `detectDiskWrites` + `penaltyLog`). Из полного среза logcat взяты все нарушения, у каждого пройден стек до первого кадра `com.sza.fastmediasorter.*`. Во всех строках pid == tid (`28020 28020`), то есть это именно главный поток, а не унаследовавший политику воркер.

**Площадки (все четыре перепроверены по текущему исходнику, а не только по логу):**

- `CameraCaptureFlowManager.resolveOutput()` - `DiskReadViolation ~33 ms`. Обычная не-suspend функция, внутри `File(dir).apply { mkdirs() }.isDirectory`.
- `CameraCaptureSessionManager.offeredExtensions()` (вызов из `bindToLifecycle`) - `DiskReadViolation ~32 ms`. Три подряд `ExtensionsManager.isExtensionAvailable(..)` на HDR/NIGHT/BOKEH; CameraX читает вендорную конфигурацию расширений с диска.
- `MainCameraCaptureManager.createScratchDir()` - `DiskReadViolation ~15 ms` + `DiskWriteViolation ~14 ms`. `getExternalFilesDir(null)` плюс `mkdirs()`.
- `CaptureDestinationPolicy.resolveCameraDirectory()` - `DiskReadViolation 0..1 ms` (трижды). `Environment.getExternalStoragePublicDirectory(..)`, `exists()`, `mkdirs()`.

**Оговорка по эвиденсу.** Лог снят со сборки `v2.60.8082.309-DEBUG` (16:22). В том же срезе были ещё десять `DiskWriteViolation` через `CameraCaptureSaver.save`, но это **S1573**, починенный в 17:04 и закрытый в 17:10 - то есть артефакт APK, собранного до фикса, и в эту заявку он не входит. Четыре площадки выше проверены отдельно по дереву на момент захвата и синхронной работы с диском не потеряли.

**Почему это отдельный тикет, а не довесок.** Соседние тикеты про главный поток закрывают другие места: S1480 - `CameraCaptureResultManager.showGalleryThumbnail`, S1569 - загрузчик миниатюр в browse, S1573 - `CameraCaptureSaver.save`, S1517 - keystore в настройках, S1324 - удаление временных файлов шаринга. Ни один не называет ни одну из четырёх площадок.

## 2. Корневая причина

Расследовано 2026-08-11 по текущему исходнику. Причины две, и они разной природы - это и есть ответ на первый
открытый вопрос захвата.

**Причина A - подготовка каталога стоит в синхронной развилке.** Три площадки (`resolveOutput`,
`createScratchDir`, `resolveCameraDirectory`) не просто трогают диск: каждая возвращает решение, от которого
немедленно ветвится вызывающий код. `CameraCaptureActivity.setupViews` строит экран строкой
`if (!flowManager.resolveOutput()) return` (`CameraCaptureActivity.kt:160`), а `MainCameraCaptureManager` -
строкой `val dir = createScratchDir() ?: run { .. return }` (`MainCameraCaptureManager.kt:68`). Пока ответ
нужен на месте вызова, унести работу в фон нельзя, не переставив саму развилку.

**Причина B - опрос расширений повторяется на каждой перепривязке.** `offeredExtensions` вызывается из
`bindToLifecycle` (`CameraCaptureSessionManager.kt:768`), то есть на каждое применение настроек, смену режима
и смену объектива, и каждый раз делает три `isExtensionAvailable`, за которыми CameraX читает вендорную
конфигурацию с диска. Между вызовами ответ измениться не может: это функция ровно от двух вещей - объектива
за `baseSelector` и признака `videoMode`, - и никакого состояния сессии она не читает (её собственный KDoc:
«Lives outside the session class .. it reads no session state»). Повторное чтение диска не даёт ни одного
нового бита.

Отсюда ответ на второй открытый вопрос захвата: ключ кэша - пара «идентификатор объектива + `videoMode`», а
не «текущий объектив». Такой ключ по построению не может разойтись со сменой линзы: у нового объектива другой
ключ, и он промахивается мимо чужой записи, а не отдаёт её.

---

## 3. Исправление

Две правки, по одной на причину.

**Правка A - каталог готовится вне главного потока, развилка переезжает за ответ.** Дисковую часть трёх
площадок (`mkdirs`, `exists`, `isDirectory`, `getExternalFilesDir`, `getExternalStoragePublicDirectory`)
вынести в `suspend`-функции на `Dispatchers.IO`, а вызывающий код перестроить так: экран собирается сразу,
а отрицательный ответ приводит к тому же терминальному действию, что и сегодня, - сообщение об ошибке и
закрытие. Гонку «спуск раньше ответа» закрывает уже существующая блокировка: `btnCapturePhoto.isEnabled`
выставляется в `false` при сборке экрана (`CameraCaptureActivity.kt:165`), поэтому включать кнопку следует
только после подтверждённого каталога.

**Правка B - опрос расширений считается один раз на ключ.** Завести карту
`Map<Pair<String, Boolean>, Intents>` по ключу «объектив + режим» и отдавать из неё готовый ответ. Первый
промах по-прежнему стоит те же ~32 ms, поэтому карта прогревается вне главного потока при старте экрана
камеры, до первой привязки; привязка, случившаяся раньше прогрева, платит цену один раз, как сегодня, и
дальше карта тёплая. Запись живёт столько же, сколько процесс: доступность вендорного расширения на объективе
по ходу сессии не меняется.

Границы: обе правки трогают только путь подъёма камеры. Ни порядок привязки, ни выбор расширения
(`CameraExtensionSelector`), ни поведение при отказе объектива (S1189) не меняются.

## 4. Проверка

1. Сценарий на устройстве со взведённым StrictMode: открыть камеру с главного экрана, применить настройку,
   переключить режим, сменить объектив.
2. Положительный контроль обязателен: показать в том же прогоне хотя бы одно живое нарушение StrictMode с
   другого пути. Ноль нарушений в прогоне, где StrictMode вообще не сработал, не доказывает ничего.
3. Правка B проверяется счётом: `isExtensionAvailable` вызывается один раз на пару «объектив + режим» за
   сессию, а не на каждую перепривязку.

Минимум: повторить сценарий на устройстве со взведённым StrictMode и показать ноль `DiskReadViolation` / `DiskWriteViolation`, чей стек проходит через любую из четырёх площадок. Обязателен положительный контроль - доказать, что StrictMode в этом прогоне вообще срабатывает, иначе ноль ничего не значит.

#### Что чинилось после прошлого аудита

Прошлый прогон нашёл расхождение реализации с §3: прогрев карты вызывался из колбэка `onReady`, то есть строго после первой привязки, и обогнать её не мог. Теперь пара «объектив + режим», которую запросит эта самая привязка, прогревается на `Dispatchers.IO` внутри `bind()` до вызова `bindToLifecycle`; сама привязка ставится в очередь главного потока уже после прогрева.

Прогревается ровно одна пара, а не все восемь: прогрев всех до привязки задержал бы первый кадр видоискателя на их суммарную стоимость, то есть заменил бы один дефект другим. Остальные пары по-прежнему догревает хост после `onReady`, где цена лежит вне критического пути.

Идентификация сборки двойная: имя версии на устройстве (`dumpsys package` -> `versionName=2.60.8120.227-DEBUG`) отличается от прошлой прогонной сборки, и в срезе присутствуют пробы `S1579:`.

#### Device-test run 2026-08-11 (RFCR110NBQJ, Samsung SM-G996U1, Android 15 / SDK 35, standard debug `2.60.8111.809-DEBUG`) - прошлый, FAIL

Идентификация сборки не по имени версии - оно не поменялось с пересборкой. Различитель - сам набор проб: все три строки `S1579:` присутствуют в срезе, значит прогон шёл на исправленной сборке.

Сценарий: открытие камеры с главного экрана (More actions -> Camera), переключение режима PHOTO/VIDEO и обратно, две смены объектива, снимок, два применения настроек со сменой соотношения сторон 4:3 -> 16:9 -> 4:3. Привязок насчитано **7**, двумя независимыми счётчиками, сошедшимися до строки: `CameraUseCaseAdapter: addUseCases` (лог самого CameraX) и `S1581: macro label` (пишется внутри `bindToLifecycle`).

Нарушений StrictMode в прогоне 12, все на главном потоке (`pid == tid == 12182`). Разложены по первому кадру `com.sza.fastmediasorter.*`:

- `offeredExtensions` - 7, все в окне 21:07:34.682-683, то есть внутри первой привязки. На шести последующих привязках - ноль.
- `resolveOutput`, `createScratchDir`, `resolveCameraDirectory` - ноль.
- Прочие пути (в зачёт тикета не идут, это положительный контроль): `BrowseFileTransferCoordinator.<init>` ~321 ms, `ResourceLaunchWidgetProvider.onUpdate` (строки 27 и 28), два нарушения без кадра приложения.

Счёт по кэшу: 8 строк `S1579: extension query`, все в пределах 82 ms от старта экрана. Одна на главном потоке (`tid 12182`) - промах первой привязки; семь на `tid 12223` - прогрев на `Dispatchers.IO`. Набор объективов `[2, 0, 1, 3]`, режимов два, итого 8 пар - ровно один запрос на пару. Шесть перепривязок после прогрева не дали ни одного запроса. Правка B в части «один раз на пару» доказана.

Причина остатка - расхождение реализации с §3. Спецификация требует прогревать карту «до первой привязки»; в коде `warmOfferedExtensions()` вызывается из колбэка `onReady` (`CameraCaptureActivity.kt:357`), то есть строго после того, как `bindToLifecycle` уже отработал. Прогрев по построению не может опередить первую привязку, и оговорка «привязка, случившаяся раньше прогрева, платит цену один раз» превращается из редкого случая в единственный. Симптом из §1 - задержка первого кадра видоискателя - остаётся ровно там, где был.

Проверка на неучтённое состояние: соотношение сторон прочитано до правки (4:3), изменено на 16:9 и возвращено в 4:3, повторное чтение после прогона подтверждает 4:3. Размер кольцевого буфера logcat поменять не удалось (прошивка держит потолок 5 MiB), поэтому срез снимался непрерывным потоком в файл, а не выборкой из буфера, - `logcat -d` терял окно открытия камеры за две минуты.

Эвиденс: `temp/S1579/` - `stream_final.log` (полный поток), `clean.log` (без строк `adbd`, чтобы счётчики не считали собственную командную строку), `stageA.log` (первый прогон, независимо воспроизводит те же 7 нарушений на другом pid), `parse_strictmode.py` (разбор по первому кадру приложения).
