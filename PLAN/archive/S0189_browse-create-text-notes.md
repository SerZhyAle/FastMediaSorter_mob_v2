## 1. Проблема

В Browse пользователь может создавать папки, но не может создать новый пустой текстовый файл для быстрых заметок в текущем каталоге. Из-за этого приходится переключаться в сторонние приложения или заранее подготавливать файлы вне FastMediaSorter.

Такой разрыв ухудшает сценарии, где заметка должна лежать рядом с медиа или документами в конкретной папке: комментарии к файлам, TODO, служебные пометки перед копированием, локальные инструкции для каталога. Дополнительно сейчас не сформирован целевой UX для «создать документ и сразу редактировать его» именно из Browse-команды.

---

## 2. Цели

1. Дать пользователю возможность создать новый текстовый файл заметки прямо из Browse в текущем открытом пути ресурса документов.
2. После создания файла сразу открывать его в существующем текстовом редакторе в режиме редактирования.
3. Предоставить пользователю управляемый способ выбора размера отображаемого шрифта в текстовом экране.
4. Обеспечить быстрые явные действия сохранения и отмены изменений в редакторе без неочевидных промежуточных шагов.
5. Поддержать сценарий переименования документа в момент сохранения.
6. Добавить в меню операций Browse действие отправки текущего текстового содержимого в Google Keep как новой заметки.
7. Сохранить единый контракт поведения для локальных, сетевых и облачных ресурсов, где запись поддерживается.

**Non-goals:**

- Полноценный редактор заметок с расширенным форматированием.
- История версий заметок внутри приложения.
- Совместное редактирование или синхронный multi-user режим.
- Отдельный тип заметок со своей БД или метаданными вне файловой системы.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Точка входа в создание заметки должна быть нативной частью Browse-команд, а не скрытым обходным сценарием.
2. Созданный файл должен сразу открываться на редактирование, без дополнительного ручного открытия из списка.
3. В редакторе должны быть быстрые понятные действия «сохранить» и «отменить изменения».
4. При сохранении пользователь должен иметь возможность изменить имя документа.
5. В Browse должно появиться отдельное действие отправки текста в Google Keep без предварительного ручного копирования содержимого.
6. Первая итерация должна работать на уже поддерживаемых ресурсах без внедрения отдельного storage-движка для заметок.

### 3.2 Жёсткие ограничения

- **Flavor:** standard, lite, photos, legacy; доступность действия определяется реальной поддержкой текстовых файлов и возможностью записи в текущий ресурс.
- **API level:** без изменения нижней границы API.
- **Wear OS:** не затрагивается.
- **Производительность:** создание заметки не должно запускать тяжёлые пересканы; допустим только локальный refresh текущего списка. Операции save/cancel/rename должны быть отзывчивыми и не блокировать UI на длинный путь без обратной связи.
- **Совместимость данных:** новый файл создаётся как обычный текстовый файл в целевой папке, без скрытых проприетарных контейнеров.
- **Локализация:** EN/RU/UK обязательно. Новые пользовательские строки должны соответствовать `docs/COMMUNICATION_POLICY.md`; tone checklist из §6 политики является обязательным gate перед интеграцией.
- **Доступность:** действие и диалог должны быть полностью управляемы с клавиатуры и TalkBack, с понятными сообщениями об ошибках.

## 4. Контекст текущей архитектуры (AS-IS baseline)

Архитектура Browse уже поддерживает файловые команды для операций с объектами файловой системы и умеет работать с разными типами ресурсов через единый слой доменных операций. Также присутствует текстовый viewer/editor для открытия и редактирования существующих текстовых файлов.

По результатам первичного AS-IS анализа:

- В текстовом экране уже есть edit/save, auto-save и undo/redo.
- Есть динамическая настройка размера шрифта для текстового контента (жестами), но нет подтверждённого продуктового контракта под новый сценарий «документ-заметка из Browse».
- В Browse уже есть паттерн создания папки через явную команду и предикаты доступности.

Сейчас отсутствует единый пользовательский сценарий создания нового текстового файла в текущем каталоге с немедленным входом в редактирование и с согласованной моделью save/cancel/rename. Поэтому пользователь не может завершить «создать заметку рядом с контентом» внутри одного потока Browse и вынужден делать лишние шаги.

## 5. Предлагаемый подход

На стратегическом уровне функция должна быть оформлена как новая командная возможность в Browse, использующая уже существующие механизмы проверки прав, подтверждений, сообщений об ошибках и обновления списка файлов. Итоговый артефакт — обычный текстовый файл заметки, создаваемый в текущем контексте ресурса и сразу открываемый в редакторе.

### 5.1 Основные столпы / модули

**UI-команда создания заметки**

Нужна явная пользовательская команда в Browse, доступность которой определяется текущим типом ресурса и правами записи.

**Сценарий ввода и валидации**

Нужен унифицированный диалог ввода имени с проверкой недопустимых символов, пустого имени, конфликта с существующим файлом и ограничений ресурса.

**Создание файла через существующий файловый слой**

Создание заметки должно выполняться как обычная файловая операция в том же архитектурном контуре, что и другие file ops.

**Немедленный переход в режим редактирования**

После создания документ должен быть открыт в текстовом редакторе без промежуточных действий пользователя.

**Экспорт текста в Google Keep**

Пользователь должен иметь возможность отправить текущий текст в Google Keep как новую заметку без ручного копирования и без лишних промежуточных экранов.

**Контур редактирования с быстрыми действиями**

В текстовом экране должны быть явные быстрые действия для сохранения и отмены, а также сценарий rename-on-save.

**Управление размером шрифта**

Пользователь должен иметь контролируемый способ выбирать размер отображаемого шрифта в текстовом контенте, совместимый с текущими настройками и жестами.

**Обновление состояния UI после операции**

После успешного создания список должен отражать новый файл немедленно, а при ошибке пользователь должен получать понятную и дружелюбную причину отказа.

### 5.2 Потоки данных и событий

- Пользователь инициирует команду создания заметки в Browse.
- Пользователь инициирует команду отправки текста в Google Keep из меню операций.
- UI собирает имя файла и подтверждение действия.
- Слой применения проверяет доступность операции для текущего ресурса и пути.
- Выполняется создание нового текстового файла в текущем каталоге.
- UI получает результат и сразу открывает новый документ в редакторе.
- Пользователь редактирует текст, при необходимости меняет размер шрифта.
- Пользователь выполняет быстрое сохранение или отмену, при сохранении может изменить имя документа.
- При успехе список и контекст ресурса синхронизируются с фактическим именем/содержимым документа, при ошибке показывается понятное сообщение и состояние экрана остаётся стабильным.

### 5.3 Точки расширяемости

- Поддержка шаблонов содержимого заметки (например, дата/время, заготовка TODO).
- Выбор расширения заметки (txt/md) по пользовательской настройке.
- Политики конфликта имён: авто-суффикс, overwrite с подтверждением, skip.
- Персистентная настройка размера шрифта именно для текстового viewer/editor (не только session-scoped).
- Повторное использование механизма обмена/внешней отправки, если он уже существует и подходит под Google Keep.

## 6. Открытые вопросы / Research items

### 6.1 Technical/Product research items

1. **Расширение файла по умолчанию**
   - **Решение:** дефолт `.txt`. Пользователь может изменить и имя, и расширение в диалоге сохранения.
   - **Статус:** Resolved

2. **Поведение при конфликте имён**
   - **Решение:** silent auto-suffix — к имени добавляется `-ss` (текущие секунды) и файл записывается; без диалога подтверждения.
   - **Статус:** Resolved

3. **Пост-успех сценарий**
   - **Решение:** безусловное авто-открытие в редакторе (см. ADR-4); настройка не вводится.
   - **Статус:** Resolved

4. **Матрица поддерживаемых источников записи**
   - **Решение:** все writable ресурсы с поддержкой текста (LOCAL, SMB, SFTP, FTP, CLOUD). На сетевых/cloud файл стейджится в Downloads и копируется на ресурс при сохранении (см. §6.3).
   - **Статус:** Resolved

5. **Контракт быстрого save/cancel**
   - **Решение:** одна кнопка commit без диалога; отмена = закрытие без сохранения; auto-save остаётся safety-net (см. ADR-5).
   - **Статус:** Resolved

6. **Rename-on-save UX**
   - **Решение:** имя задаётся в диалоге сохранения перед commit. Default name `YY-MM-dd_HH-mm.txt`. Пользователь может менять имя и расширение в одном поле.
   - **Статус:** Resolved

7. **Контракт выбора размера шрифта**
   - **Решение:** жесты согласно текущему паттерну — вверх/вниз = прокрутка, влево/вправо = increase/decrease font. Default = max font из настроек программы (`ocrDefaultFontSize` → multiplier HUGE), auto-shrink до 12sp при росте контента.
   - **Статус:** Resolved

8. **Google Keep integration contract**
   - **Решение:** только plain text через `ACTION_SEND` `text/plain` + `setPackage("com.google.android.keep")`. Если Keep не установлен/недоступен — кнопка скрыта (см. §6.3).
   - **Статус:** Resolved

### 6.2 Опросник заказчика работ (обязательный до реализации)

До перехода к `/spec-tech` нужны письменные ответы или явная делегация решений по каждому пункту ниже. Если хотя бы один ответ не дан, задача остаётся на этапе уточнения.

1. Для каких ресурсов команда «Создать текст» должна быть видна в v1: только writable documents-ресурсы или все writable ресурсы с поддержкой текста?
Ответ: все writable ресурсы с поддержкой текста

2. Какой дефолт расширения нужен в v1: только `.txt` или выбор `.txt/.md`?
Ответ: txt, но пользователь может изменить и имя и расширение при сохранении

3. Авто-открытие нового файла в редакторе должно быть обязательным или настраиваемым?
Ответ: оно вроде достаточно логичное, чтобы быть обязательным

4. Где размещать команду в Browse: toolbar-кнопка, overflow, обе точки входа?
Ответ: обе точки входа - команда в тулбаре, как и прочие - с низким приоритетом, то есть попадет в ниспадающее меню на узких экранах

5. Что считать «быстрым сохранением»: одна кнопка commit без диалога, или commit с минимальным подтверждением?
Ответ: одна кнопка

6. Как трактовать «отмену сохранения»: отмена текущих несохранённых изменений, выход из режима редактирования, или оба сценария?
Ответ: закрытие без сохранения

7. Rename при сохранении: это «Save As», переименование текущего файла перед commit, или разрешены оба режима?
Ответ: только с указанием имени перед выходом. имя по-умолчанию YY-MM-dd_hh-mm.txt

8. Если имя занято, какая политика приоритетна: fail с сообщением, авто-суффикс, overwrite с подтверждением?
Ответ: автодобавление -ss (текущие секунды) к имени и запись

9. Размер шрифта: нужен глобальный дефолт, отдельный дефолт для текстового редактора, или только session-scoped изменение?
Ответ: дефолт - самый крупный шрифт и уменьшается по мере увеличения контента вплоть до 12sp, потом начинается появляться возможность прокрутки. Пересчитывается после ввода символа или вставки из буфера. Шрифт берётся из настроек программы - он там есть, найди

10. Какой UI для размера шрифта обязателен для v1: кнопки +/- , слайдер, жесты, комбинированный режим?
Ответ: жесты, как у нас уже принято. жесты вверх вниз это прокрутка по тексту, а влево-вправо увеличение или уменьшение шрифта

11. Нужно ли показывать пользователю явный индикатор dirty-state (например, «есть несохранённые изменения»)?
Ответ: да, цвет командной панели

12. Нужно ли после save возвращаться в Browse, оставаться в редакторе, или это настраивается?
Ответ: нужны команды в виде иконок сохранить, сохранить и закрыть, сохранить и отправить, отправить в keep (без созранения но и не закрывая), отмена. 
Соханить и отправить - сразу инициирует механиз "отправить в" встроенный в андроид


13. Нужна ли отдельная блокировка функции для read-only и virtual путей с разными текстами ошибок?
Ответ: нет


14. Какие сценарии являются блокирующими для приёмки: локальные папки, SMB, FTP/SFTP, cloud провайдеры?
Ответ: никакие открывать можно текст где угодно, Например при открыти созднаи нового текста на SFTP - это будет реализовано как локальный файл сохранённый в downloads, потом копируемый к ресурсу в сети. Если на момент сохранения ресурс недоступен - мы покажем ошибку, но файл останется сохранённым, если файл удачно скопировался - то локально удаляетсмя и пользователь даже не осознает что он был в downloads


15. Для Google Keep нужно ли отправлять только plain text, или также заголовок заметки и/или текущий filename?
Ответ: plain text


16. Если Google Keep не установлен или недоступен, какой fallback нужен: сообщение, системный share sheet, или скрыть пункт?
Ответ: кнопку должно быть не видно

После ответов должны быть однозначно зафиксированы:

- точка входа команды создания заметки;
- точка входа отправки в Google Keep;
- дефолтный формат файла;
- поведение save/cancel;
- правило rename-on-save;
- контракт управления размером шрифта;
- fallback при отсутствии Google Keep.

### 6.3 Locked decisions (2026-05-16)

Финальные ответы по §6.2 закреплены в файле выше. Сводный список зафиксированных контрактов:

- **Точка входа создания:** toolbar-кнопка `btnCreateTextFile` (низкий приоритет → авто-overflow на узких экранах) + пункт `action_create_text_file` в `menu_resource_ops.xml` + клавиатурный shortcut.
- **Видимость команды:** writable ресурсы документ-семейства, у которых `allFiles == true` **или** `supportedMediaTypes` пересекается с `{TEXT, PDF, EPUB}`; virtual-пути исключены. В аудио/видео/фото-only библиотеках команда скрыта — созданная `.txt` всё равно не попала бы в список файлов. Гейт применяется ко всем точкам входа (toolbar-кнопка, overflow-меню, keyboard-shortcut). Уточнение от 2026-05-17 после feedback'а пользователя.
- **Дефолтный формат файла:** `.txt`. Пользователь меняет имя и расширение в финальном save-диалоге.
- **Default file name:** `YY-MM-dd_HH-mm.txt` (формируется в момент save из текущего времени устройства).
- **Конфликт имени:** silent auto-suffix `-ss` (секунды), запись без подтверждения.
- **Сетевой/cloud staging:** файл создаётся локально в `Downloads/FastMediaSorter/notes/`, при save копируется на ресурс; при успешном копировании локальная копия удаляется, при ошибке — остаётся (пользователь видит ошибку, файл не теряется).
- **Авто-открытие в редакторе:** обязательное, после успешного create.
- **Набор кнопок-иконок в редакторе:** Save · Save & Close · Save & Send (Android share sheet) · Send to Keep (без save/без close) · Cancel.
- **Dirty-state индикатор:** изменение цвета командной панели редактора при наличии несохранённых правок.
- **Контракт размера шрифта:** default = max из persistent setting (`ocrDefaultFontSize` → `TranslationFontSize.HUGE`); авто-уменьшение по росту контента до пола 12sp, далее прокрутка; пересчёт после ввода/вставки; manual override через swipe влево/вправо (паттерн уже реализован в `TextViewerManager`).
- **Read-only / virtual paths:** команда просто скрыта, отдельных текстов ошибок нет.
- **Send to Keep — fallback:** кнопка скрыта если `com.google.android.keep` отсутствует или не резолвится для `ACTION_SEND text/plain`.

## 9. Архитектурные решения (ADR)

**ADR-1: Заметка — это обычный текстовый файл в существующей файловой модели**

- **Решение:** не вводить отдельный тип сущности заметки и не хранить заметки во внутренней БД как primary source.
- **Альтернативы:** внутренний note-store; гибрид с экспортом в файл.
- **Почему:** это сохраняет совместимость, простоту и прозрачность для пользователя.

**ADR-2: Создание заметки реализуется как расширение текущего Browse file-ops контракта**

- **Решение:** встроить действие в существующую архитектурную цепочку файловых операций.
- **Альтернативы:** отдельный «мини-модуль» с параллельной логикой и особыми правилами.
- **Почему:** единый контракт снижает риск расхождения поведения и упрощает поддержку.

**ADR-3: V1 ориентирован на минимальный, надёжный сценарий создания**

- **Решение:** в первой итерации сфокусироваться на создании пустого файла и корректной обратной связи.
- **Альтернативы:** сразу включать шаблоны, форматирование и расширенный post-create workflow.
- **Почему:** это снижает риск регрессий и быстрее даёт пользователю реальную ценность.

**ADR-4: Немедленный переход в редактор после создания обязателен для v1**

- **Решение:** после успешного create пользователь сразу попадает в режим редактирования нового документа.
- **Альтернативы:** оставаться в Browse и открывать вручную; делать авто-открытие опциональным по умолчанию.
- **Почему:** сценарий заметок ценен именно скоростью ввода «создал -> сразу пишу».

**ADR-5: Явные save/cancel при сохранении auto-save как safety-net**

- **Решение:** в UX закрепляются быстрые явные действия save/cancel, при этом auto-save остаётся страхующим механизмом до финализации контракта в тактической фазе.
- **Альтернативы:** только auto-save без ручного save/cancel; полный отказ от auto-save.
- **Почему:** ручной контроль нужен пользователю, но защита от потери правок тоже критична.

## 11. Критерии готовности (strategic-level)

1. Пользователь может создать текстовый файл заметки в текущей папке Browse без выхода во внешние приложения.
2. Команда доступна только там, где ресурс и текущий путь реально поддерживают запись.
3. После создания документ автоматически открывается в режиме редактирования.
4. Пользователь может быстро сохранить изменения или отменить их через явные действия в редакторе.
5. Пользователь может изменить имя документа в сценарии сохранения.
6. Пользователь может управлять размером отображаемого шрифта в текстовом экране.
6. Пользователь может отправить текущее текстовое содержимое в Google Keep из меню операций.
7. При конфликте имени и при ошибках записи пользователь получает предсказуемое и понятное поведение.
8. После успешного сохранения список в Browse отражает актуальный файл/имя в том же контексте ресурса.
9. Пользовательские строки и документация функции синхронизированы в EN/RU/UK.
