## 0. Захваченный материал (inbox)

**Захвачено:** 2026-08-15

**Текст:**

Владелец: «а может полезно чтобы у нас не было зоопарка систем VIEEW и всё более-менее рашалось в одном стиле? Скольк у нас ещё таких лоскутков от разных стилей?»

Замер по состоянию на 2026-08-15:

- `app_v2`: 2857 файлов `.kt`, 404169 строк. Из них Compose - **6 файлов, 1330 строк** = 0.33%
- `wear`: 78 файлов `.kt`, из них 16 на Compose, XML-макетов **ноль** - модуль целиком на Compose
- Точек входа `setContent {` в `app_v2` ровно пять: экран Wear-компаньона, диалог передачи на часы и три экрана настройки виджетов (ярлык ресурса, фоторамка, быстрый снимок камеры)

Предложение, вынесенное владельцу в чате и им принятое к заведению тикета: **не** переводить app_v2 на Compose (переписывание 404 тысяч строк без видимого пользователю результата и с большим риском регрессий), а зафиксировать границу - **app_v2 = View, wear = Compose**. Новых Compose-экранов в app_v2 не заводить; существующие пять убирать оппортунистически, когда до них дойдут по другой причине, а не отдельной кампанией.

Почему тикет заводится сейчас, хотя сама породившая его ошибка уже закрыта: 2026-08-15 обнаружилось, что ни одна из пяти вставок не была обёрнута в тему приложения, и все они рисовались заводской сиреневой палитрой Material3 вместо выбранного пользователем акцента. Починено общим мостом `FastMediaSorterComposeTheme` (ui/common/compose/), правило записано в docs/ARCHITECTURE.md разделом «Compose Island Theming (MANDATORY)». То есть срочности больше нет - остаётся зафиксировать границу, чтобы шестая вставка не завелась.

Известная зацепка при удалении вставок: `androidx.compose.material:material-icons-extended` просто так не выкидывается - иконки `Pause`/`SkipNext`/`SkipPrevious` есть только в расширенном наборе, их придётся заменить на векторные картинки. См. отдельно зафиксированное наблюдение по S0385.

Замер воспроизводится:

```
grep -rn "setContent {" app_v2/src --include=*.kt
grep -rl "androidx.compose" app_v2/src --include=*.kt | xargs wc -l | tail -1
```

## 1. Проблема

В `app_v2` сосуществуют две системы построения UI: View с XML-разметкой (99.67% кода) и несколько
островков Compose. Граница между ними нигде не записана, поэтому решение «на чём делать следующий экран»
каждый раз принимается заново и вслепую - и число островков растёт само по себе.

Пользователь этого не видит напрямую, пока островок не расходится с окружением. Один раз это уже
произошло: до 2026-08-15 ни одна вставка не наследовала тему приложения, и все они рисовались заводской
сиреневой палитрой Material3 вместо выбранного пользователем акцента. Тот конкретный дефект закрыт общим
мостом темы, но породившая его причина - незаписанная граница - осталась.

Область: `app_v2` целиком, точки входа Compose в настройках и в экранах настройки виджетов.

---

## 2. Цели

1. Разработчик, начинающий новый экран в `app_v2`, читает границу как правило, а не выводит её из
   пропорции существующего кода.
2. Попытка завести новый островок Compose в `app_v2` останавливается механически, в том же прогоне,
   что и правка - а не замечается через месяцы при следующем аудите.
3. Число островков может только уменьшаться: снятый островок опускает планку, вернуть её вверх нельзя
   без явного решения.
4. Условие снятия последней зависимости Compose из `app_v2` записано заранее, чтобы тот, кто уберёт
   последний островок, не обнаружил его как сюрприз.

**Non-goals:**

- Перевод app_v2 на Compose - явно вне объёма, решение принято обратное.
- Отдельная кампания по переписыванию пяти существующих вставок - они уходят оппортунистически.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Не разводить зоопарк систем построения UI - формулировка владельца от 2026-08-15, §0.
2. Не платить за это переписыванием: кампания по переводу `app_v2` на Compose отвергнута там же.
3. Существующие островки уходят попутно, когда до них дойдут по другой причине.

### 3.2 Жёсткие ограничения

- **Flavor:** все шесть. Граница проходит по модулю, а не по варианту сборки, и ни один островок не
  живёт во флейворном source set.
- **API level:** без API-специфики.
- **Wear OS:** затрагивается только как вторая половина границы - `wear` остаётся на Compose, и ни одно
  правило этого тикета не должно запрещать `setContent` там.
- **Производительность:** не критично; тикет ничего не исполняет в рантайме.
- **Совместимость данных:** не затрагивается.
- **Локализация:** новых пользовательских строк нет, поэтому EN/RU/UK неприменимо.
- **Доступность:** пользовательского UI не добавляется.

### 3.3 Owner inputs (Approval gate)

- **Граница:** `app_v2` = View, `wear` = Compose. Принято владельцем 2026-08-15, дословная формулировка
  и контекст - в §0.
- **Перевод app_v2 на Compose:** отвергнут владельцем там же, зафиксирован как non-goal.
- **Судьба пяти (ныне шести) существующих островков:** снимаются оппортунистически, отдельной кампании
  нет. Решение владельца 2026-08-15.
- **Форма фиксации (правило или механический гейт):** гейт, дополняющий правило. Решение не выносилось
  владельцу отдельно: `dev/RULE_AND_SKILL_AUTHORING.md` в разделе «When NOT to add a rule» уже отвечает -
  «The rule is mechanically checkable and would be ignored as prose - write the gate directly», а
  измерение §6.1 показывает рост числа островков за пять дней.
- **Related tickets:** S1693 (findViewById против ViewBinding) и соседний тикет о трёх параллельных
  механизмах хранения - оба из того же аудита 2026-08-15, ни один не блокер. S0385 - зависимость
  `material-icons-extended`, предусловие для §6.2.

## 4. Контекст текущей архитектуры

`app_v2` построен на View: экраны - фрагменты и активности с XML-разметкой, цвета приходят из View-темы
приложения и наложенного пользователем акцента. Островок Compose встраивается в эту иерархию как
отдельная вьюха-хост и живёт по своим правилам: собственная система тем, собственный набор иконок,
собственные зависимости в файле сборки. Мост темы, добавленный 2026-08-15, приводит цвета островка к
цветам окружения, но не отвечает на вопрос, должен ли островок вообще появляться.

Решить проблему §1 сегодня нечем, потому что граница существует только как наблюдаемая пропорция кода.
Ни правило, ни проверка её не выражают: в репозитории записан лишь способ правильно оформить островок,
если он уже решён, - то есть документация подсказывает, как добавить вставку, и молчит о том, стоит ли.

## 5. Предлагаемый подход

Тикет ничего не исполняет в рантайме и не меняет ни одной ответственности в коде приложения. Он
добавляет ровно две вещи: формулировку границы там, где формулируются правила, и механическую проверку
там, где такие проверки уже живут.

### 5.1 Основные столпы / модули

**Столп 1 - правило.** Граница формулируется как нумерованное правило в файле правил репозитория и
повторяется в двух полных дайджестах, которые обязаны цитировать каждое нумерованное правило. Правило
говорит две вещи: новый экран `app_v2` делается на View, а существующий островок снимается попутно, а не
кампанией. Правило не запрещает Compose в модуле часов.

**Столп 2 - счётчик-храповик.** Проверка считает точки входа Compose в основном source set телефонного
модуля и сравнивает с записанной планкой. Появление новой точки - отказ. Снятие точки требует опустить
планку, и планка не поднимается обратно без явного решения. Проверка добавляется как ещё одно измерение
в уже существующий набор лексических правил, а не отдельным скриптом: этот набор уже подключён и к
закрывающему фасаду, и к быстрой батарее проверок, поэтому новое измерение попадает в оба места без
единой строки проводки.

**Столп 3 - записанное предусловие снятия зависимостей.** Условие, при котором из файла сборки
телефонного модуля можно убрать строки Compose, формулируется заранее и хранится рядом с правилом, а не
восстанавливается тем, кто уберёт последний островок.

### 5.2 Потоки данных и событий

Потоков данных нет. Единственный поток - проверочный: правка исходников → закрывающий фасад или быстрая
батарея → измерение считает точки входа → сравнение с планкой → отказ или проход.

### 5.3 Точки расширяемости

- Планка обязана уметь опускаться: каждый снятый островок опускает её на единицу, и это штатный путь, а
  не исключение.
- Измерение задаётся текстовым образцом в общем наборе правил, поэтому уточнение образца не требует
  трогать ни фасад, ни батарею.
- Граница сформулирована по модулям, а не по экранам, поэтому появление третьего модуля решается
  добавлением строки в правило, а не пересмотром подхода.

## 6. Открытые вопросы / Research items

1. **Чем фиксировать границу - правилом или механическим гейтом**
   - **Вопрос:** достаточно ли записи в CLAUDE.md/ARCHITECTURE.md, или нужен `assert-*`, отказывающий новому `setContent` в app_v2
   - **Ответ:** правило плюс счётчик-храповик. Два независимых довода, оба проверяемые.
   - **Довод первый - измерение повторено 2026-08-20 и разошлось с исходным.** Замер §0 от 2026-08-15
     давал пять точек входа, шесть файлов, 1330 строк. Тот же замер сегодня даёт **шесть точек входа,
     семь файлов, 1877 строк**. Шестая точка - экран настройки виджета сетевого монитора, приехавший с
     S1440. Нарушения правила тут нет: правила ещё не существует. Именно это и есть довод - популяция
     островков растёт сама, без чьего-либо решения её растить, и растёт быстрее, чем аудит успевает её
     пересчитывать.
   - **Довод второй - доктрина авторства правил репозитория отвечает прямо.**
     `dev/RULE_AND_SKILL_AUTHORING.md`, раздел «When NOT to add a rule»: «The rule is mechanically
     checkable and would be ignored as prose - write the gate directly». Число точек входа Compose в
     одном модуле - величина, вычисляемая обычным текстовым поиском, то есть случай ровно этот.
   - **Что НЕ подтвердилось:** предположение, что незаписанное правило уже приводило к нетемизированным
     островкам, к сегодняшнему дню неверно - все шесть островков обёрнуты в общий мост темы, включая
     новый. Правило темизации, записанное 2026-08-15 в `docs/ARCHITECTURE.md`, работает. Обобщать
     «правила без гейта не работают» на его примере нельзя, и в §7 это записано как риск обратного вывода.
   - **Статус:** Resolved

2. **Что делать с зависимостями Compose в app_v2 после ухода последней вставки**
   - **Вопрос:** какие строки сборки снимаются вместе с последней вставкой и что для этого нужно сделать заранее
   - **Ответ:** снимаются плагин компилятора Compose, флаг `compose = true`, спецификация версий и
     восемь строк зависимостей в файле сборки телефонного модуля - но только после того, как выполнено
     предусловие ниже. Список строк проверен на дереве 2026-08-20.
   - **Предусловие, а не следствие:** три иконки управления воспроизведением - пауза, следующий,
     предыдущий - берутся из расширенного набора иконок Material, и в базовом наборе их нет. Проверено
     на дереве 2026-08-20: все три используются и сегодня. Их замена на векторные картинки - работа по
     UI, которая должна быть сделана ДО снятия зависимости, иначе сборка перестаёт компилироваться.
     Ровно это уже случилось однажды в S0385, когда аудит зависимостей объявил расширенный набор мёртвым.
   - **Границы вопроса:** снятие зависимостей не входит в объём этого тикета и не может входить - пока
     жив хотя бы один островок, ни одна из строк не снимается. Тикет обязан лишь записать условие так,
     чтобы будущий исполнитель нашёл его, а не переоткрывал.
   - **Статус:** Resolved

## 9. Архитектурные решения (ADR)

**ADR-1: Граница проходит по модулям, а не по экранам**

- **Решение:** app_v2 остаётся на View, wear остаётся на Compose. Смешение внутри одного модуля не допускается.
- **Альтернативы:** перевести app_v2 на Compose; оставить как есть и не фиксировать ничего.
- **Почему:** перевод - переписывание 404169 строк без видимого пользователю результата; оставить как есть - значит позволить шестой вставке завестись тем же путём, что и первые пять. Граница по модулям совпадает с технической необходимостью: на часах у Compose нет разумной альтернативы, в телефонном приложении у View нет причины уходить.
- **Постскриптум 2026-08-20:** шестая вставка успела завестись, пока тикет лежал в Draft (§6.1). Довод «оставить как есть» больше не гипотетический - он проверен на практике и проиграл.

**ADR-2: Граница держится счётчиком-храповиком, а не отдельным гейтом**

- **Решение:** проверка добавляется как ещё одно измерение в уже существующий набор лексических правил
  над исходниками, с планкой, равной сегодняшнему числу точек входа. Отдельный скрипт `assert-*.ps1` не
  пишется.
- **Альтернативы:** только правило в файле правил; отдельный гейт-скрипт со своей проводкой в фасад и в
  быструю батарею.
- **Почему:** только правило отвергнуто доводами §6.1. Отдельный скрипт отвергнут по цене: набор
  лексических правил уже подключён и к закрывающему фасаду, и к быстрой батарее, и уже реализует
  контракт «планка только вниз» для двадцати измерений. Новое измерение получает и проводку, и
  контракт, и формат отчёта бесплатно, а отдельный скрипт всё это дублировал бы - что прямо запрещает
  раздел доктрины «The rule would duplicate an existing rule or gate».

## 11. Критерии готовности (strategic-level)

1. Попытка добавить седьмую точку входа Compose в основной source set `app_v2` заканчивается отказом
   проверки, и отказ называет границу и тикет, а не только счётчик.
2. Дерево в его текущем виде проверку проходит: шесть существующих островков не считаются нарушением.
3. Правка, добавляющая точку входа Compose в модуле часов, проверку проходит.
4. Снятие любого из шести островков с опусканием планки проверку проходит, а попытка вернуть планку
   вверх - нет.
5. Граница сформулирована как нумерованное правило и процитирована в обоих полных дайджестах правил;
   проверка синхронности дайджестов проходит.
6. Условие снятия зависимостей Compose из файла сборки телефонного модуля записано вместе с
   предусловием про три иконки, и найти его можно, не читая этот тикет.
