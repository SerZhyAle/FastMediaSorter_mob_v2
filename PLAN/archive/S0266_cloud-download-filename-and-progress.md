## 1. Проблема

При копировании файла из облачного хранилища (Google Drive, Dropbox, OneDrive) на локальный накопитель или сетевое хранилище итоговый файл сохраняется под именем «голый облачный идентификатор» — без расширения и без исходного имени. Пример: вместо `MyVideo.mp4` в `/Download` появляется `17S0TkB5sDhJCSnJeHqFww0O08a8JxlKG`. Файл физически скопирован, но непригоден к использованию: системные плееры и галерея не определяют формат, MIME-тип потерян, иконка превью отсутствует, операция «Открыть с..» бесполезна.

Сценарий усугубляется тремя сопутствующими дефектами наблюдаемого поведения. Во-первых, диалог прогресса во время скачивания крупного файла (десятки секунд) не получает обновлений и до самого конца показывает дизайнерские плейсхолдеры («file.jpg», «0 / 10», «1.5 МБ/с») — у пользователя возникает впечатление, что копируется не тот файл и неизвестно с какой скоростью. Во-вторых, для `noLegal` flavor попытка запустить APK прямо из облака не доводится до системного установщика: даже если бы файл скопировался с правильным именем, отсутствует автоматическая передача его в `PackageInstaller`, а вспомогательное копирование выставляется на видимый универсальный диалог копирования, что для запуска APK избыточно. В-третьих, дизайнерские плейсхолдеры случайно живут в продакшен-локализациях (EN/RU/UK), а не в `tools:text`-разметке, поэтому показываются конечному пользователю независимо от наличия колбэков.

Область затронута: облачные источники чтения, базовый слой файловых операций, диалог выбора пункта назначения, диалог прогресса операции, flavor-специфичный сценарий установки APK.

## 2. Цели

1. Копирование одного или нескольких файлов из облачного источника в локальную или сетевую папку сохраняет исходное имя файла и расширение — пользователь видит `MyVideo.mp4`, а не идентификатор облака.
2. Диалог прогресса операции отображает реальное имя файла, реальный счётчик «текущий / всего», и реальную текущую скорость скачивания, начиная с момента, когда облачный клиент отдаёт первый блок данных.
3. До прихода первого байтового события диалог отображает индикативное состояние («Подготовка..» или эквивалент), а не дизайнерский плейсхолдер.
4. Для flavor с поддержкой установки APK из облака (`noLegal`): запуск APK из браузера облака не показывает обычный диалог копирования, выполняет скачивание в кеш-каталог в фоне с минимальным неблокирующим индикатором и сразу передаёт файл системному установщику с правильным расширением и MIME-типом.
5. Локализационные ресурсы EN/RU/UK освобождены от строк, которые были задуманы как дизайнерские плейсхолдеры — они уходят в `tools:text` слой разметки.

**Non-goals:**

- Копирование «облако → облако» — отдельная история, имя и так берётся из облачных метаданных по другому пути.
- Загрузка с локального устройства в облако — на этом пути имя берётся из локального файла и проблема не воспроизводится.
- Прогресс-бар для отдельно стоящих фоновых задач (предзагрузка миниатюр, фоновый импорт) — не затрагивается.
- Замена нижележащего стека HTTP-клиента или библиотек облачных провайдеров.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Реальная скорость в диалоге обновляется чаще одного раза в секунду — но не настолько часто, чтобы цифры мелькали.
2. Сообщения вокруг операции (тосты, статусы) проходят через единый стиль формулировок проекта (`docs/COMMUNICATION_POLICY.md`).
3. Для сценария «запуск APK из облака» допустим короткий ненавязчивый Toast/Snackbar, чтобы пользователь понимал, что идёт подготовка, и не нажимал кнопку повторно.

### 3.2 Жёсткие ограничения

- **Flavor:** `standard` — фикс имени и прогресса виден пользователю. `noLegal` — наследует `standard` плюс тихий запуск APK. `vr` — наследует `standard` без особенностей. `lite`, `photos`, `legacy` — облако отключено через `BuildConfig`, объём изменений не должен затрагивать эти варианты сборки. Любая flavor-специфичная логика для `noLegal` подчиняется правилам `dev/FLAVOR_DEVELOPMENT_RULES.md`: интерфейс в общем коде, реальная реализация в `noLegal` source set, No-Op в общем коде, биндинг через flavor-специфичный Hilt-модуль. Запрещено добавлять `BuildConfig.IS_NO_LEGAL_FLAVOR`-проверки в общий код (Strict Rule §15).
- **API level:** изменения совместимы с минимальным уровнем Android по умолчанию для затронутых flavor'ов. Для `PackageInstaller` использовать поведение, поддерживаемое начиная с минимума `noLegal` flavor.
- **Wear OS:** не затрагивается — облачное копирование живёт только в основном модуле.
- **Производительность:** добавление байтового колбэка не должно увеличить время скачивания крупного файла больше, чем на 1% — обновления UI троттлятся в диалоге, а не в облачном клиенте.
- **Совместимость данных:** существующие сохранённые ссылки на облачные файлы (`cloud://<provider>/<fileId>`) продолжают работать. Никаких миграций хранилища не требуется.
- **Локализация:** новые пользовательские строки добавляются одновременно в EN/RU/UK; удаляемые строки выносятся из всех трёх локализаций синхронно. Проверка `scripts/check_strings_localized.ps1` обязательна.
- **Доступность:** диалог прогресса остаётся читаемым TalkBack — `contentDescription` для процента и оставшегося времени сохраняются.
- **Стиль текстов:** все пользовательские сообщения по операции проходят чек-лист `docs/COMMUNICATION_POLICY.md` §6 перед коммитом.

## 4. Контекст текущей архитектуры

Облачное чтение, выбор пункта назначения и собственно выполнение операции живут в трёх раздельных слоях. Слой источника данных умеет получать у провайдера и список файлов, и метаданные конкретного файла, и поток байтов — отображаемое имя файла в нём известно. Слой пользовательского интерфейса оперирует «легковесными ссылками на файлы» — представлением вида «строка-путь + длина», построенным поверх стандартных файловых обёрток платформы. Слой выполнения операции принимает на вход эти ссылки и для облачных путей вынужден извлекать имя из последнего сегмента пути — что для облачных схем даёт идентификатор, а не отображаемое имя.

Сейчас невозможно решить проблему §1 локально внутри слоя выполнения операции, потому что отображаемое имя не приходит снаружи. Слой источника данных это имя знает, но к моменту, когда пользователь нажимает «Копировать», оно уже отброшено промежуточной обёрткой. Аналогично сценарий «запуск APK из облака» не складывается в общем коде, потому что требует и потокового скачивания в кеш, и системного установщика, и flavor-условности — каждое из этих звеньев в общем коде живёт по своим правилам, и `noLegal` имеет право вмешаться только через выделенный source set.

## 5. Предлагаемый подход

Перенести отображаемое имя облачного файла как явное поле через все промежуточные ссылки на ресурс — от слоя источника данных до слоя выполнения операции. Слой выполнения операции для облачных источников читает это поле напрямую, не пытаясь восстановить имя из строки пути. Параллельно слой облачного клиента получает возможность сообщать наружу о ходе скачивания через стандартный канал байтовых событий, который уже используют сетевые клиенты SMB/SFTP/FTP в проекте. Для flavor-специфичного сценария установки APK вводится дополнительная роль, которая инкапсулирует «скачать в кеш с минимальным UX и запустить установщик» — общий код только опознаёт намерение и делегирует роли, а реальное поведение задаётся выбранной flavor-реализацией.

### 5.1 Основные столпы / модули

#### 5.1.1 Перенос отображаемого имени облачного файла

Слой источника данных уже знает отображаемое имя — оно приходит из ответа REST-провайдера. Промежуточные ссылки на файл, которыми обмениваются UI и операционный слой, должны нести это имя как явное поле. Слой выполнения операции для облачных путей читает поле напрямую и использует его при создании выходного файла. Если поле отсутствует (унаследованные кодовые пути или сценарии, где имя не успело прийти) — используется текущий fallback, но он перестаёт быть основным сценарием. Для облачных провайдеров, у которых имя не пришло вместе с открытым потоком, должен существовать способ запросить метаданные по идентификатору перед записью.

#### 5.1.2 Сквозной канал прогресса для облачного скачивания

Облачные клиенты (Google Drive, Dropbox, OneDrive) принимают тот же необязательный байтовый колбэк, что и сетевые клиенты SMB/SFTP/FTP. Слой выполнения операции для облачных загрузок пробрасывает колбэк от вызывающего кода до облачного клиента без потерь. Колбэк вызывается во время потокового чтения данных из облака с разумной частотой и не блокирует загрузку, если потребитель колбэка работает медленно. Слой UI-диалога троттлит обновления экрана независимо от частоты колбэка.

#### 5.1.3 Поведение диалога прогресса до прихода первого события

Диалог прогресса при создании показывает индикативное состояние, явно отличающееся от «всё уже готово» (пустые поля или короткий нейтральный текст в духе «Подготовка..»). Все три текстовых поля (имя файла, счётчик, скорость) на момент первого показа гарантированно не содержат дизайнерских плейсхолдеров. Дизайнерские значения, которые видны разработчику в редакторе разметки, изолированы от продакшен-локализаций.

#### 5.1.4 Тихий запуск APK из облака (flavor-специфичный)

Запуск APK из браузера облачного хранилища в `noLegal` flavor — отдельный сценарий, который не должен переиспользовать общий диалог копирования. Вводится новая роль уровня feature-флоу: «подготовить и запустить APK по облачной ссылке». В общем коде существует декларация роли с No-Op реализацией. В `noLegal` source set живёт реальная реализация: она скачивает файл в кеш-каталог приложения под исходным именем (с расширением `.apk`), минимально уведомляет пользователя о факте подготовки, передаёт файл системному установщику с корректным MIME-типом и обрабатывает отказ установщика как ошибку с предсказуемым сообщением. В `standard` сборку этот код не попадает.

#### 5.1.5 Чистка локализационных плейсхолдеров

Три текстовых ключа диалога прогресса, которые сейчас несут дизайнерские примеры значений и продублированы в трёх локализациях, выводятся в слой разметки как `tools:text` (видны только в редакторе, не попадают в run-time). Поведение во время реальной работы определяется кодом диалога.

### 5.2 Потоки данных и событий

- Чтение каталога облака: источник данных → сборка ссылок на ресурсы с явным отображаемым именем → UI-каталог.
- Запуск копирования: UI выбирает источники и пункт назначения, передаёт в слой операций ссылки со всем известным контекстом (включая имя).
- Слой операций: для облачного источника читает имя из ссылки, открывает поток скачивания у облачного клиента, передаёт байтовый колбэк, пишет временный файл, переименовывает или копирует в финальное расположение с правильным именем.
- Прогресс: облачный клиент эмитирует байтовые события → слой операций транслирует в верхнеуровневый канал прогресса → диалог троттлит и отображает.
- Запуск APK из облака (`noLegal`): UI каталога опознаёт «это APK», обращается к роли «запустить APK по облачной ссылке» — общий код делегирует во flavor-реализацию, реализация выполняет скрытое скачивание и системный установщик. Общий диалог копирования не используется.

### 5.3 Точки расширяемости

- Новый интерфейс «запустить APK по облачной ссылке» — расширяемая точка для будущих flavor'ов, которым может потребоваться альтернативный установщик (заранее не закрывать поведение).
- Существующий канал байтовых событий должен оставаться универсальным: облачные клиенты подключаются к тому же контракту, что и сетевые, без облако-специфичных усложнений на стороне колбэка.
- Хранение «отображаемого имени» в промежуточной ссылке должно поддерживать ту же поверхность вызовов, что используется для сетевых файлов — чтобы будущие источники (например, новый облачный провайдер) подключались без переписывания UI-слоя.

## 6. Открытые вопросы / Research items

1. **Способ переноса отображаемого имени через файловую обёртку UI**
   - **Вопрос:** Использовать существующее наследование `java.io.File` с переопределением одного дополнительного поля, или ввести новый доменный тип для «выбранного источника», который покрывает и локальные, и сетевые, и облачные файлы.
   - **Варианты:** (а) Минимально-инвазивный — расширить только облачную File-обёртку добавочным полем `displayName`. (б) Архитектурно правильный — отказаться от `java.io.File` в `sourceFiles` UI-диалога в пользу доменной модели, которая уже несёт имя как обязательное поле.
   - **Нужно выяснить:** Объём изменений вызывающего кода для варианта (б). Если меньше определённого порога, лучше идти по правильному пути; иначе фиксируем (а) и оставляем долг.
   - **Статус:** Open — решение в `/spec-tech`.

2. **Где запрашивать метаданные облачного файла, если имя не пришло вместе с потоком**
   - **Вопрос:** В каких сценариях `displayName` может отсутствовать на момент запуска копирования (например, копирование по recovered last-viewed файлу).
   - **Варианты:** (а) Делать защитный `getFileMetadata(fileId)` в слое выполнения операции прямо перед записью. (б) Гарантировать наполнение `displayName` на этапе формирования источников и не доспрашивать.
   - **Нужно выяснить:** Полный перечень точек, откуда `sourceFiles` приходит в диалог.
   - **Статус:** Open — решение в `/spec-tech`.

3. **Уровень UX-индикации для тихого запуска APK**
   - **Вопрос:** Допустим ли минимальный визуальный отклик во время скачивания (Toast/Snackbar/Notification), или весь процесс должен быть полностью невидимым до момента вызова системного установщика.
   - **Варианты:** (а) Короткий Toast «Подготавливается установка..» + системный установщик. (б) Notification с прогрессом (если скачивание длится > N секунд). (в) Полностью без визуала.
   - **Нужно выяснить:** Поведение конкурирующих менеджеров APK на устройстве (например, что показывает «Files by Google» при аналогичной операции).
   - **Статус:** Open — финальное решение в `/spec-tech`. Дефолт для согласования — (а).

4. **Канал получения отображаемого имени для существующих сохранённых ссылок**
   - **Вопрос:** Существующие сохранённые пути (lastViewed, history) в формате `cloud://<provider>/<fileId>` не несут имени. Что делать при их перечитке.
   - **Варианты:** (а) Доспросить метаданные при первом обращении и закешировать. (б) Пометить имя как «неизвестно» и показать fallback на идентификатор только до прихода метаданных.
   - **Нужно выяснить:** Частота сценария «открыли историю → нажали Copy» без предварительного захода в каталог.
   - **Статус:** Open — `/spec-tech`.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Распространение `displayName` через все вызовы потребует затрагивания большого числа точек | Средняя | Раздутый объём патча, неполная замена в одном из путей → имя продолжает теряться | Сделать поле опциональным с явным fallback, заменять точки последовательно по приоритету, в первую очередь — основной путь Copy/Move |
| Колбэк прогресса от облачного клиента создаст лишний оверхед при скачивании мелких файлов | Низкая | Незаметное замедление, ничего критичного | Эмитировать события не чаще раз в N килобайт; UI-троттлинг независимо |
| Тихий запуск APK обходит общий диалог копирования — пользователь может не понять, что что-то происходит, особенно для медленного интернета | Средняя | UX-регрессия для `noLegal` | Дефолт — короткий Toast при старте, опциональная Notification, реш-точка в §6.3 |
| Изменение поведения `extractFileName` для облачных путей сломает сценарий, где имя приходит null/пусто | Средняя | Возврат к мусорному имени или NPE | Покрыть unit-тестом основные ветки, явный fallback на текущее поведение если поле отсутствует |
| `noLegal` source set не имеет нужной инфраструктуры для скачивания (отсутствуют биндинги в существующих модулях) | Низкая | Усложнение в `/spec-tech` | Использовать существующие облачные клиенты, инжектируемые в общий код, плюс flavor-специфичную обёртку только над сценарием запуска |

## 8. Влияние на пользователя (docs/FEATURES)

Стандартная сборка: исправление, а не новая фича — без изменений в `docs/FEATURES.md`.

`noLegal` сборка: «запуск APK прямо из Google Drive без видимого копирования» — фактически новая способность, которой раньше не было корректно работающей. Описание добавляется в `docs/FEATURES_noLegal.md` (и `_RU`, `_UK`), не в публичные feature-файлы (Strict Rule по `noLegal`-фичам).

## 9. Архитектурные решения (ADR)

**ADR-1: Перенос отображаемого имени как явного поля, а не реконструкция из пути**

- **Решение:** Имя облачного файла идёт через все промежуточные ссылки как явное поле, а не извлекается каждый раз из строки пути.
- **Альтернативы:** (а) Делать «умный» парсер пути, который по схеме `cloud://` запрашивает метаданные у клиента; (б) Хранить пары «id → name» в общем кеше и доспрашивать на стороне выполнения операции.
- **Почему:** Парсер пути не решает корневую проблему «UI отбросил имя ещё на этапе формирования источников», а общий кеш создаёт зависимости и состояние там, где их нет. Передача имени по цепочке — самый прямой и поддерживаемый путь.

**ADR-2: Прогресс облачного скачивания идёт через тот же байтовый колбэк-контракт, что и сетевые клиенты**

- **Решение:** Облачные клиенты подключаются к существующему контракту байтовых событий, без введения отдельного облако-специфичного канала.
- **Альтернативы:** Отдельный progress-механизм для облачных клиентов (например, поток процентов).
- **Почему:** Унификация поверхности контракта снижает количество мест, где UI-диалог должен подписываться, и упрощает добавление новых облачных провайдеров.

**ADR-3: Тихий запуск APK как отдельная feature-роль, не как «параметр диалога копирования»**

- **Решение:** Запуск APK из облака — это отдельная роль уровня feature-флоу, с flavor-специфичной реализацией.
- **Альтернативы:** Параметризировать существующий диалог копирования флагом «hide UI» и переключать его в общем коде.
- **Почему:** Флаги «hide UI» в общем диалоге смешивают ответственность UI и сценария установки и нарушают flavor-изоляцию (потребуется проверка `BuildConfig` в общем коде, что запрещено). Отдельная роль изолирует логику в правильном source set.

**ADR-4: Дизайнерские плейсхолдеры — через `tools:text`, не через продакшен-строки**

- **Решение:** Текстовые примеры в разметке диалога прогресса задаются атрибутом `tools:text` и не существуют в локализационных файлах.
- **Альтернативы:** Оставить локализованные строки, но никогда их не показывать (требует кода, который инициализирует поля пустыми ещё до layout-inflate).
- **Почему:** Цель `tools:text` — ровно такая. Хранить «пример для редактора» в локализационных файлах — отдельный источник багов, который уже сработал.

## 11. Критерии готовности (strategic-level)

1. Пользователь копирует файл из Google Drive в локальную папку — итоговый файл имеет исходное имя и расширение, открывается стандартными плеерами и галереей.
2. Во время скачивания крупного файла (десятки секунд) пользователь видит в диалоге прогресса реальное имя файла, реальный счётчик «текущий / всего» и реальную скорость в МБ/с или КБ/с.
3. До прихода первого байтового события диалог не показывает дизайнерских плейсхолдеров.
4. В `noLegal` сборке клик по APK-файлу в Google Drive — не показывает универсального диалога копирования, после короткой подготовки запускает системный установщик.
5. Языковые ресурсы EN/RU/UK не содержат строк-плейсхолдеров диалога прогресса — проверка локализации проходит без замечаний.
6. Сценарий «копирование облако → SMB/SFTP/FTP» сохраняет правильное имя файла (без регрессий).
