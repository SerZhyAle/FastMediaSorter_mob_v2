Mechanical gate: a test in the shared app_v2/src/test must not reference a type that lives only in a flavor-scoped source set. Found while fixing S1450, which repaired two such clusters by hand (src/testStreamingEnabled, src/testCloudEnabled). The defect class is silent: src/test compiles for every flavor, so one misplaced test breaks unit-test COMPILATION on every flavor mounting the disabled counterpart, and nobody routinely runs unit tests on lite/photos, so it surfaces only when a release gate asks for them - docs/RELEASE_READINESS_STANDARD.md requires PermissionRegistryManifestParityTest on lite as a release blocker, and it could not run at all while lite unit tests did not compile. Also worth covering: the mount map for a capability test set must mirror the main set's mount list, since drift between them reintroduces the defect.

## 1. Проблема

Общий набор юнит-тестов компилируется для каждого из шести флейворов, поэтому тест, положенный туда для класса из флейвор-областного набора исходников, ломает не сам себя, а **компиляцию всего тестового набора** на каждом флейворе, который монтирует противоположный (disabled) набор. Дефект молчаливый: на урезанных флейворах (`lite`, `photos`) юнит-тесты никто не гоняет регулярно, поэтому поломка всплывает только тогда, когда её спрашивает релизный гейт - а он спрашивает обязательный к релизу тест паритета разрешений именно на `lite`, где он и не мог запуститься.

S1450 починил два таких кластера вручную и записал человеческое правило (`dev/FLAVOR_DEVELOPMENT_RULES.md`, RULE 7), S1433 добавил третий кластер уже по правилу. Правила без механического гейта в этом репозитории держатся плохо: собственный аудит маршрутизации из `CLAUDE.md` фиксирует 1-8 % соблюдения у негейтированных правил против ~99 % у гейтированных.

Область: конфигурация наборов исходников модуля `app_v2` и батч быстрых статических гейтов.

## 2. Цели

1. Ссылка из общего тестового набора на тип, живущий только во флейвор-областном наборе, отвергается механически - до сборки и без gradle.
2. Расхождение карты монтирования общего тестового набора с картой его основного двойника отвергается тем же гейтом.
3. Гейт полноты юнит-прогона считает знаменатель по эффективному набору источников варианта, а не по одному общему каталогу, и потому перестаёт завышать коэффициент покрытия.
4. Карта монтирования остаётся ровно в одном месте - build-файле модуля; ни один гейт не заводит её копию.
5. Новая синтаксическая форма монтирования в build-файле приводит к громкому «не смог проверить», а не к тихому сужению зоны контроля.

**Non-goals:**

- Компиляция юнит-тестов всех шести флейворов в батче быстрых гейтов - это gradle-задача под общей блокировкой сборки, её цена несовместима с быстрым батчем.
- Перенос уже существующих тестов между наборами: на момент постановки известные кластеры перенесены (S1450, S1433, S1455); гейт лишь удерживает результат.
- Модуль `wear`: флейворов у него нет, значит нет и этого класса дефекта.
- Инструментальные тесты (`androidTest`): у них другая модель компиляции и другой набор монтирований.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Гейт живёт в батче быстрых статических гейтов и не добавляет к нему заметной задержки.
2. Сообщение о нарушении называет не только файл и строку, но и флейворы, на которых сборка тестов сломается, - чтобы стоимость ошибки была видна сразу.
3. Гейт подсказывает целевой набор для переноса теста, а не только констатирует нарушение.

### 3.2 Жёсткие ограничения

- **Flavor:** все шесть - `standard`, `noLegal`, `lite`, `photos`, `legacy`, `vr`; дефект по определению межфлейворный.
- **API level:** без API-специфики - проверка статическая, вне рантайма.
- **Модуль `wear`:** не затрагивается.
- **Производительность:** проверка обходит порядка 2650 файлов `.kt` - общий набор исходников, флейвор-областные наборы и общий тестовый набор - и обязана укладываться в бюджет быстрого батча, то есть в единицы секунд без обращения к gradle. Общий набор входит в обход потому, что имя, объявленное в нём, видно всем флейворам и обязано быть исключено из индекса. Замерено 1.4 с на 2026-08-09.
- **Совместимость данных:** не затрагивается - гейт не хранит состояния между запусками, кроме, возможно, счётчика-храповика.
- **Пользовательские строки:** не затрагиваются - гейт печатает только в консоль сборки.
- **Доступность:** не применима - пользовательской поверхности нет.

### 3.3 Owner inputs (Approval gate)

- **Flavor scope:** все шесть флейворов одновременно; гейт не имеет флейвор-специфичного поведения и запускается один раз на весь модуль.
- **Validation level:** запуск гейта на текущем дереве с фиксацией кода возврата, плюс негативная проверка на заведомо нарушающем временном файле; полный прогон юнит-тестов не требуется.
- **Owner sign-off:** не требуется - изменение не пользовательское, поверхности приложения не касается.

## 4. Контекст текущей архитектуры

Соответствие «набор исходников - флейвор» задано единственным блоком конфигурации в build-файле модуля `app_v2` и нигде не продублировано. Там же заданы монтирования общих тестовых наборов, зеркалящие основные. AGP при этом подхватывает одноимённые флейвору каталоги по соглашению, без явного монтирования, поэтому эффективный путь исходников флейвора складывается из трёх источников: общий набор, одноимённый набор, явно смонтированные общие наборы.

Батч быстрых статических гейтов (`scripts/quality/assert-fast-gates.ps1`) - готовая точка подключения: он уже запускает два десятка проверок в одном процессе, печатает построчный вердикт и падает, если упала любая. Гейт полноты юнит-прогона (`scripts/quality/assert-test-suite-complete.ps1`) - второй потребитель той же карты, и сейчас он её не читает, а неявно предполагает, что источники варианта исчерпываются общим каталогом.

Решить проблему §1 сегодня нельзя ни одним из существующих гейтов: ни один из них не разбирает карту монтирования, а без карты нельзя ответить на главный вопрос - на каких флейворах данный тип отсутствует.

## 5. Предлагаемый подход

Ввести один разборщик карты монтирования и двух её потребителей. Карта читается из build-файла при каждом запуске, копий не заводится.

### 5.1 Основные столпы / модули

**Разборщик карты монтирования.** Читает блок конфигурации наборов исходников и возвращает для каждого флейвора список смонтированных наборов, а для каждого общего набора - список флейворов. Обязан учитывать каждую строку монтирования: строка, которую он не сумел отнести к набору, обязывает вернуть «не смог проверить», а не молча сузить зону контроля. Условное монтирование трактуется как негарантированное.

**Индексатор объявлений.** Собирает по флейвор-областным наборам объявления **верхнего уровня** вместе с их пакетом. Вложенные члены иерархий в индекс не попадают - именно они давали основной шум в ad-hoc-версии. Из индекса исключается любое имя, объявленное в общем наборе исходников или во всех шести флейворах: такое имя компилируется везде и дефектом не является.

**Сканер общего тестового набора.** Ищет два вида ссылок: явный импорт индексированного имени и простое имя, объявленное в том же пакете, что и сам тест. Прочие совпадения простых имён игнорируются - это снимает вторую категорию шума, платформенные типы. Нарушение сообщается вместе со списком флейворов, на которых сборка тестов сломается, и с целевым набором для переноса.

**Проверка зеркала.** Для общего основного набора, у которого существует тестовый двойник, множества монтирующих флейворов обязаны совпадать. Тестовый набор без основного двойника - законная форма группировки по возможности, а не дрейф, и под правило не подпадает.

**Потребитель карты в гейте полноты.** Гейт полноты получает эффективный список корней исходников для своего варианта от того же разборщика: общий набор, одноимённый варианту набор при наличии каталога на диске, и смонтированные в него общие тестовые наборы.

### 5.2 Потоки данных и событий

- build-файл -> разборщик карты -> индексатор объявлений -> сканер общего тестового набора -> вердикт в батче быстрых гейтов.
- build-файл -> разборщик карты -> проверка зеркала -> тот же вердикт.
- build-файл -> разборщик карты -> гейт полноты юнит-прогона -> его собственный вердикт.

### 5.3 Точки расширяемости

- Добавление флейвора или общего набора не требует правки гейта: карта выводится из build-файла.
- Разборщик карты - отдельная переиспользуемая единица, а не внутренняя деталь одного гейта; третий потребитель подключается без копирования логики.
- Набор индексируемых видов объявлений расширяем, если появится форма, которую текущий список не покрывает.

## 9. Архитектурные решения (ADR)

**ADR-1. Статический анализ вместо компиляции.**
Полное покрытие проверкой компиляцией требует юнит-тестовых сборок всех шести флейворов, потому что каждый флейвор монтирует свою половину пар enabled/disabled. Такая проверка стоит минут и общей блокировки сборки, то есть не может быть механическим гейтом на каждое изменение. Статический скан двух областей по 265 и 470 файлов укладывается в секунды и потому становится гейтом, а не ритуалом.

**ADR-2. Карта монтирования не копируется, а выводится.**
Копия карты в скрипте - это второе место, где она дрейфует, и ровно тот механизм, который тикет закрывает. Поэтому карта читается из build-файла при каждом запуске, а неспособность её разобрать сообщается как отказ проверить.

## 11. Критерии готовности (strategic-level)

1. Заведомо нарушающий тест, временно положенный в общий тестовый набор, отвергается гейтом с указанием файла, строки и списка флейворов, на которых сломается сборка тестов.
2. Легальные соседи не срабатывают: тест на тип с копиями во всех флейворах и тест, упоминающий платформенный тип с совпадающим простым именем, проходят гейт.
3. Расхождение монтирования общего тестового набора с его основным двойником отвергается гейтом.
4. Неразобранная строка монтирования в build-файле даёт отдельный код «не смог проверить», отличимый от «нашёл нарушение».
5. Гейт полноты юнит-прогона считает знаменатель по эффективному набору источников варианта и на текущем дереве даёт тот же вердикт, что и раньше, но на исправленном числе классов.
6. Батч быстрых гейтов с новой проверкой остаётся в своём бюджете времени; фактическая длительность зафиксирована.
