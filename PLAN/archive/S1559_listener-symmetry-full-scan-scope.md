## 1. Проблема

У одного гейта две области. Дельта-режим судит каждый source set обоих модулей, а полный скан считает только `src/main`, поэтому несимметричная регистрация, уже лежащая во флейворном наборе, для целочисленного базлайна не существует и не будет существовать никогда. Расхождение задокументировано в самом скрипте как временное и ждёт выравнивания. Область - инструментарий проверок; на пользователя не влияет напрямую, но влияет на то, какие утечки слушателей доезжают до сборки.

## 2. Цели

1. Полный скан считает те же source set, что уже судит дельта-режим, - все, кроме тестовых, в обоих модулях.
2. Дисконт формы, которую гейт признаёт безобидной, только уменьшает перекос и никогда его не создаёт.
3. Число в базлайне после выравнивания получено измерением, а не подгонкой, и каждая оставшаяся под ним площадка названа.
4. У гейта появляется регрессионная батарея, которая падает при возврате любой из этих двух правок.

**Non-goals:**

- Не сужать обратно область дельта-режима ради формального единообразия - она расширена по делу.
- Не чинить сами перекосы во флейворных наборах. Это правка Kotlin в `vr` со своей сборкой и своим объёмом; они входят в базлайн как названный долг.
- Не менять `Abs` на «считать только сторону утечки». Это отдельная гипотеза о смысле метрики, а не следствие расхождения областей.

Разбор этих восьми показал, что половина - вовсе не регистрации:

- Строка `import androidx.activity.addCallback` считается как добавление, потому что счёт идёт по всему тексту файла без различения строк импорта.
- `document.addEventListener(..)` внутри строкового литерала с HTML - вызов DOM, а не Kotlin.
- Две площадки - `lifecycle.addObserver(this)`: наблюдатель снимается самим жизненным циклом при его уничтожении. Это ровно то рассуждение, которое S1433 уже записал для `onBackPressedDispatcher.addCallback`.

Отдельная находка, найденная при попытке эти формы вычесть:

- Вычитание из числа добавлений с последующим взятием модуля разности **создаёт** перекос там, где его нет. Файл, который парно снимает регистрацию, после вычитания добавления читается как «ноль добавлений против одного снятия», то есть как перекос в единицу. Поймано на `LauncherStatusStripManager.kt`, который S1501 как раз вылечил.
- Оба уже существующих дисконта записаны той же формой. Сегодня она у них не выстреливает - парной площадки ни у одного нет, и переход на безопасную форму оставляет счёт по `src/main` ровно на 115. То есть для старых дисконтов это профилактика, а для новых - условие работоспособности.

Счёт в трёх вариантах:

- Сегодняшняя эвристика: 115 по `src/main`, 123 по всем наборам.
- Наивное вычитание трёх новых форм: 109 и 114.
- Дисконт, который не умеет создавать перекос: **102** и **106**.

Отсюда главный вывод: 106 меньше 115, поэтому выравнивание области вместе с исправлением дисконта двигает базлайн **вниз**, а не вверх. Ни пере-посева вверх, ни ослабления запрета на подъём не требуется - предпосылка захваченного материала измерением снята.

## 5. Предлагаемый подход

### 5.1 Основные столпы / модули

**Одна область на два режима.** Перечень сканируемых корней перестаёт быть списком из двух путей и становится тем же правилом, по которому дельта-режим отбирает файлы: любой source set обоих модулей, кроме тестовых. Правило записывается один раз и читается обоими режимами, иначе они разъедутся снова.

**Дисконт, который умеет только уменьшать.** Признание формы безобидной перестаёт быть вычитанием из числа добавлений и становится уменьшением уже посчитанного перекоса в сторону утечки. Перекос в обратную сторону - снятий больше, чем добавлений - дисконт не трогает вовсе. Правило применяется ко всем дисконтам сразу, включая два уже существующих.

**Три новые безобидные формы.** Строка импорта не считается регистрацией. Вызов регистрации обработчика DOM не считается регистрацией. Наблюдатель, отданный жизненному циклу, снимается этим жизненным циклом.

**Регрессионная батарея.** Каждая из форм получает случай, который падает при откате правки, и парный случай, доказывающий, что законная форма не тронута.

### 5.2 Потоки данных и событий

1. Оба режима спрашивают у общего правила, входит ли файл в область.
2. Для файла считаются пары «добавление против снятия» по пяти категориям.
3. Категория, у которой есть дисконт, уменьшает свой перекос на число безобидных форм, но не ниже нуля и только если перекос в сторону утечки.
4. Сумма по файлам сравнивается с базлайном; базлайн двигается только вниз.

### 5.3 Точки расширяемости

- Новая безобидная форма добавляется одной записью и автоматически получает защиту от создания перекоса.
- Правило области живёт в одном месте, поэтому следующий source set попадает под счёт без правки скрипта.

## 9. Архитектурные решения (ADR)

**ADR-1. Область скана выводится из правила, а не перечисляется.** Два списка путей разъезжаются при следующем добавлении source set, и именно это здесь и произошло. Правило «любой source set обоих модулей, кроме тестовых» уже написано в дельта-режиме; полный скан начинает читать его же.

**ADR-2. Дисконт уменьшает перекос, а не число добавлений.** Вычитание из добавлений измеримо создаёт перекос на парной площадке. Форма «уменьшить уже посчитанный перекос, только в сторону утечки, не ниже нуля» даёт тот же эффект на непарных площадках и не даёт ложного на парных. Применяется и к двум существующим дисконтам, потому что они болеют тем же.

**ADR-3. Базлайн идёт вниз штатным путём.** Измерение сняло необходимость подъёма, поэтому запрет `-UpdateBaseline` на подъём остаётся как есть. Ослабление запрета «на всякий случай» было бы изменением без повода.

**ADR-4. Четыре площадки `vr` входят в базлайн, а не чинятся здесь.** Это правки Kotlin во флейворном наборе, требующие своей сборки `vr debug`, и они не следуют из расхождения областей. Их место - отдельный тикет, названный в §10.
