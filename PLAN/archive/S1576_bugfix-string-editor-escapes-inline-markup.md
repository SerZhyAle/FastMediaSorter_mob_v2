## 0. Захваченный материал (inbox)

**Захвачено:** 2026-08-11

**Захвачено во время:** S1570 (сырые переводы строк в телах `<string>`)

**Текст:**

set-android-string.ps1 не умеет редактировать строки с inline-разметкой: ConvertTo-XmlText прогоняет значение через SecurityElement::Escape, поэтому переданный -Value с <b>..</b> / <i> / <u> / <xliff:g> попадает в файл как &lt;b&gt; и разметка ломается. Обнаружено на S1570: ключ welcome_default_player_hint (values, values-ru, values-uk) пришлось править вручную, потому что штатный редактор строк его бы испортил. Сейчас скрипт молча портит разметку - ни отказа, ни предупреждения. Нужен либо whitelist inline-тегов, пропускаемых как есть, либо явный отказ с понятным сообщением.

---

## 1. Проблема / симптом

Штатный редактор строк молча портит значение, если в нём есть inline-разметка. `-Action set -Value ".. <b>Always</b>."` записывает в файл `&lt;b&gt;Always&lt;/b&gt;`, и пользователь видит на экране literal `<b>`, а не жирный текст.

Отказа нет, предупреждения нет, а `-DryRun` не помогает: он печатает исходное `-Value`, а не то, что будет записано (строка 370). То есть предпросмотр показывает то, что вы дали, а не то, что получится, - ровно там, где расхождение и возникает.

Обнаружено на S1570: ключ `welcome_default_player_hint` в `values`, `values-ru`, `values-uk` несёт `<b>..</b>`, и его пришлось править руками, обойдя инструмент, который правило проекта предписывает использовать.

---

## 2. Корневая причина

`ConvertTo-XmlText` (строки 210-214) прогоняет всё значение через `[System.Security.SecurityElement]::Escape`, а тот по построению экранирует любой `<`. Функция не различает два вида `<` в теле `<string>`:

- литеральный текст, который экранировать нужно;
- inline-разметку, которую Android разбирает и рендерит и которую экранировать нельзя.

Второй случай в коде просто не предусмотрен, поэтому обрабатывается как первый. Дополнительный слой - `-DryRun` в `Invoke-Set` печатает `$Value`, а не `$escapedValue`, поэтому единственный механизм, способный показать подмену до записи, её не показывает.

---

## 3. Исправление

- Разделить экранирование на два режима внутри `ConvertTo-XmlText`: фрагменты, совпавшие с whitelist inline-тегов, переносятся дословно; всё между ними экранируется как раньше.
- Whitelist - теги, которые Android действительно разбирает в теле строки: `b`, `i`, `u`, `em`, `strong`, `sup`, `sub`, `strike`, `tt`, `big`, `small`, `br`, `xliff:g`.
- Отказ вместо порчи для всего остального: если вне whitelist встречается `<`, за которым идёт буква или `/` - то есть нечто по форме тег, - редактор отказывает с сообщением, называющим фрагмент и список поддерживаемых тегов. Молчаливое экранирование неизвестного тега - это тот же дефект, только для следующего случая.
- Литеральный `<`, за которым идёт не буква и не `/` (например `1 < 2`), по-прежнему экранируется как текст - это не разметка.
- `-DryRun` дополнительно печатает строку `Escaped:` - то, что реально попадёт в файл. Без неё предпросмотр не способен показать ни исправление, ни его отсутствие.
- Обратное преобразование не трогается: `ConvertFrom-XmlText` уже возвращает `<b>` как `<b>`, поэтому сторож `-ExpectedOldValue` продолжает сравнивать одно с одним.
- `-Action add` получает то же поведение бесплатно: он экранирует через ту же функцию.

## 4. Проверка

- Разметка выживает: `-Action set -Locale en -Key welcome_default_player_hint -Value "<..> <b>Always</b>." -DryRun` печатает `Escaped:` с сохранённым `<b>..</b>`, а не `&lt;b&gt;`. `expected: <b> present | actual: ..`.
- Неизвестный тег отклоняется, а не портится: то же значение с `<font color="#fff">` даёт отказ с названием фрагмента, ненулевой код выхода, файл не тронут.
- Литеральный `<` остаётся текстом: значение `1 < 2` даёт `1 &lt; 2`.
- Прежнее поведение для обычного текста не изменилось: `&` даёт `&amp;`, апостроф даёт `\'`.
- Сторож не сломан: `-ExpectedOldValue` с текущим значением ключа, несущего `<b>`, совпадает - то есть кодирование и декодирование остались взаимно обратными.
- `pwsh -NoProfile -File scripts/quality/assert-exit-contract.ps1` - `expected: exit 0`.
- `scripts/post-change.ps1 -ChangeType Script -ScopeToFile` - все гейты зелёные.

### Замечание

Отказ - это `throw`, то есть код выхода 1, а не отдельный код. Так и задокументировано в заголовке скрипта: 1 покрывает и неверные аргументы, и непроходимую разметку. Отдельный код здесь дал бы мало: вызывающему в обоих случаях нужно исправить вход, а не ветвиться.
