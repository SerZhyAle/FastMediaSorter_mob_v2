# S0719 Performance + R8/Release Audit - Findings

Date: 2026-06-26. Scope: `app_v2` + `wear`. Method: static review across 5 dimensions - allocation churn on hot paths, autoboxing / wrong collection types, RecyclerView/DiffUtil update hygiene, repeated expensive work not memoized, and R8/release keep-rule correctness - covering Layers 6+7 of `docs/CODE_AUDIT_PROTOCOL.md`. Findings were deduplicated and adversarially verified (each candidate re-checked against source call sites, with severity adjusted on confirmation). This was a static pass only: no benchmark/measured evidence was captured, and actual release-build R8 verification (release `mapping.txt` confirmation of obfuscated field names) is run separately by the parent. 19 candidates were verified; 17 confirmed and 2 refuted/rejected.

### P1

#### Backup Gson models have no keep rule / no @SerializedName (release-only silent data loss)
- File: `app_v2/src/main/java/com/sza/fastmediasorter/domain/usecase/BackupData.kt:15`
- Symbol: `BackupPayload / BackupSettings / BackupResource / BackupNetworkCredential`
- Dimension: R8/release keep-rule correctness (static)
- Confidence: high
- Rationale: Confirmed static R8 defect. All backup models in `com.sza.fastmediasorter.domain.usecase` (`BackupPayload`/`BackupSettings`/`BackupResource`/`BackupNetworkCredential`/`BackupWebAuthSession`/`BackupCookie` etc.) use plain field names with NO `@SerializedName`. Gson is built with plain `GsonBuilder().create()`/`.setLenient()` (`BackupToGoogleDriveUseCase.kt:171`, `ImportSettingsUseCase.kt:518`) -> default `FieldNamingPolicy.IDENTITY`, so JSON keys are the reflected field names. Release minifies: `build.gradle.kts:748` `isMinifyEnabled=true` with `proguard-android-optimize.txt` + `proguard-rules.pro`. Every keep rule was checked: the only `<fields>` keeps are scoped to `@SerializedName`-annotated fields (lines 141-143, 233-235), `R$*`, `PopupMenu`, `SharedPreferences`, and kotlinx volatile - none cover `domain.usecase`. The `-keepclassmembers class * { public <init>(...); }` rule (147-149) pins constructors, not instance field names, so it does not stop Gson-relevant field renaming. `proguard-nolegal.pro` adds only `-dontwarn`. So R8 obfuscates these field names. Deserialization does not throw on key mismatch (`ImportSettingsUseCase.kt:519` catches `JsonSyntaxException` only) -> unmatched keys silently fall back to Kotlin data-class defaults, including the version gate, causing silent settings/resource/credential loss. Two caveats temper the original "non-portable across all builds" wording but do not negate the defect: R8 is deterministic, so a backup restores fine on the SAME app version/flavor on another device (same-version cross-device portability is intact); the real breakage is (a) cross-VERSION restore - the explicit purpose of the version-gated schema, since field sets shift across releases (S0406/S0326/S0003 additions visible in comments) and remap differently - and (b) debug(real names)->release(renamed) restores. This is a cold/one-time path, not hot-path, but it is release-breaking silent data loss on the advertised cross-version Google Drive restore, so it qualifies. Confidence high on the static reasoning; not empirically confirmed via a release `mapping.txt` (no release artifacts built), but default obfuscation + absent keep + no `@SerializedName` is well-established R8 behavior.
- Fix sketch: Add to `proguard-rules.pro`: `-keepclassmembers,allowobfuscation class com.sza.fastmediasorter.domain.usecase.Backup** { <fields>; }` (or annotate every model with `@Keep` / move them to `domain.model` which already has `-keep` at line 21), then re-verify with a release `mapping.txt`.

### P2

#### Per-bind date formatting on the 1000+ paged file list
- File: `app_v2/src/main/java/com/sza/fastmediasorter/ui/browse/PagingMediaFileAdapter.kt:422`
- Symbol: `PagingMediaFileAdapter.ListViewHolder.buildFileInfo`
- Dimension: allocation churn on hot paths
- Confidence: medium
- Rationale: Frequency confirmed: `buildFileInfo()` runs inside `ListViewHolder.bind()` (line 210), invoked from `onBindViewHolder` on a `PagingDataAdapter` explicitly documented for 1000+ file lists (line 36) - genuinely a per-bind, scroll-sensitive path, not cold/one-time. Per call it allocates a `java.util.Date` plus runs `android.text.format.DateFormat.format("yy-MM-dd HH:mm", Date)`, and `formatFileSize` -> `core.util.formatFileSize` uses `String.format(Locale,..)` (`FileSize.kt:16-26`), allocating a `Formatter`/`StringBuilder`. So the allocation churn is real and the path is hot. Two caveats lower it from P1 to P2: (1) the evidence's mechanism is partly inaccurate - the import is `android.text.format.DateFormat`, NOT `java.text.SimpleDateFormat`, so it does NOT recompile a pattern via `SimpleDateFormat`; it iterates the format chars and allocates a `Calendar.getInstance()` + `SpannableStringBuilder` per call (`Calendar.getInstance` is actually the costlier piece, not pattern parsing). (2) `onBindViewHolder` fires only when a row scrolls into view (RecyclerView recycles), so it is per-scroll-event, not per-frame, and the bind path is dominated by `loadThumbnail`/Glide, not string formatting. No measured jank; no correctness or R8/release-breaking impact (R8 angle is N/A here). A worthwhile micro-optimization, but moderate, not P1.
- Fix sketch: Hoist a reusable formatter into a companion (e.g. a `ThreadLocal<SimpleDateFormat>` or precomputed pattern) and reuse a single `StringBuilder`, or precompute the info string when the page is loaded instead of on each bind.

#### Non-memoized per-bind date label in shared file-info formatter
- File: `app_v2/src/main/java/com/sza/fastmediasorter/ui/browse/AdapterFileInfoFormatter.kt:96`
- Symbol: `AdapterFileInfoFormatter.buildLegacyFileInfo / buildFileInfo / buildAudioDetailLine`
- Dimension: repeated expensive work not memoized
- Confidence: medium
- Rationale: Verified against source. `AdapterFileInfoFormatter.buildFileInfo` (line 96 `buildLegacyFileInfo`, line 38 `buildAudioDetailLine`, line 84 image dateTaken) is reached from `MediaFileAdapter.onBindViewHolder` -> `ListViewHolder.bind()` (lines 770/767) and `updateAudioMetadataText` (640/637). This is the standard DiffUtil `ListAdapter` full-bind path: it runs once per row whenever a new item enters the viewport during scroll, so it genuinely scales with list traversal (hot path, not a one-time cold load). The mechanism is correct: `android.text.format.DateFormat.format("yy-MM-dd HH:mm", Date(file.createdDate))` has no pattern cache - each call allocates a `Date`, a `GregorianCalendar` (`Calendar.getInstance` with locale/timezone resolution - the dominant cost), a `SpannableStringBuilder`, parses the literal pattern character-by-character, then `.toString()` allocates a final String. So real per-bind allocation churn on the browse-list scroll path. Caveats lowering it from a clear P2 toward the boundary: the cost is moderate allocation pressure / minor scroll-jank contributor, not a frame-dropping catastrophe; the partial-bind payload paths (favorite/playback/thumbnail) correctly avoid re-formatting, so churn is bounded to genuinely-new rows. The R8/release framing in the prompt is a red herring - there is no reflected/serialized type and no proguard concern here; it is purely an allocation/perf finding. Minor wording nit in the claim: "yy-MM-dd HH:mm" is a literal pattern, not a skeleton, but the char-by-char-parse and no-cache assertions hold.
- Fix sketch: Replace per-call `DateFormat.format` with a cached `ThreadLocal<SimpleDateFormat>("yy-MM-dd HH:mm")` in `AdapterFileInfoFormatter` (or precompute the formatted date string once at `MediaFile` mapping time), reusing one formatter per thread to memoize the pattern parse and avoid the per-bind Calendar/Spannable allocations.

## Method

Static review only, no benchmarks. For each of the 5 dimensions the relevant call sites were enumerated by grep, the hot-path candidates were read in full, and each candidate function was traced to its actual invocation context (`onBindViewHolder`/per-bind/per-frame vs cold/one-time) before flagging - frequency was treated as load-bearing, so several suspected P1/P2 items were downgraded to P3 once confirmed to be viewport-bounded or cold. Findings were deduplicated by symptom and adversarially verified against source: each was re-checked for an inaccurate mechanism, an overstated frequency, or an existing guard/cache that negates it (e.g. the `MediaFileAdapter.setSelectedPaths` claim was partially refuted because `AdapterThumbnailLoader.lastLoadedKey` prevents the asserted Glide reload). R8 findings rest on well-established default Gson + absent-keep behavior; per protocol Layer 7 they remain STATIC - actual release-build R8 verification via a minified release `mapping.txt` is run separately by the parent before any fix lands. Of 19 verified candidates, 17 were confirmed and 2 refuted/rejected.
