## 1. Проблема

Встроенный скриншотер сейчас целиком живёт только в sideload-сборке (noLegal) и недоступен в магазинной сборке (standard). Причина - единственный способ запустить захват привязан к постоянной экранной полоске по краю экрана (рисование-поверх-окон) и к сервису-«помощнику для людей с ограничениями», который молча делает скриншоты. Оба механизма - повод для отклонения при ревью Google Play, поэтому весь функционал был оставлен вне магазина. В итоге пользователь магазинной сборки полностью лишён возможности сохранить кадр экрана, хотя сам захват через системное подтверждение - разрешённый магазином сценарий.

---

## 2. Цели

1. Пользователь магазинной сборки (standard) может сделать скриншот, запустив захват из меню приложения (явное действие), с системным подтверждением захвата экрана.
2. Жестовый запуск (полоска по краю экрана) и молчаливый захват через сервис-помощник остаются только в sideload-сборке (noLegal) и не попадают в магазинные сборки.
3. Магазинный путь не тянет за собой ни разрешение «поверх других окон», ни специальный тип foreground-сервиса, ни сервис-помощник - только подтверждаемый пользователем захват экрана.
4. Поведение noLegal не меняется: жест + молчаливый захват работают как прежде.

**Non-goals:**

- Не добавляем жестовый запуск или молчаливый (без подтверждения) захват в магазинные сборки.
- Не переписываем сам движок захвата и сохранения кадра - он переиспользуется как есть.
- Не трогаем Wear OS.
- Не вводим расписание/автоматический захват - запуск только по явному действию пользователя.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Меню-действие должно быть единым «сделать скриншот сейчас», без настройки направлений жеста (направления - атрибут жестового пути и остаются в noLegal).
2. Желательно переиспользовать существующие выбор папки-назначения и сохранение кадра, чтобы поведение результата совпадало между сборками.

### 3.2 Жёсткие ограничения

- **Flavor:** standard получает меню-путь; noLegal сохраняет полный жестовый+помощник стек. Прочие сборки (photos/legacy/vr/lite) меню-путь не получают (quiz 2026-06-20).
- **API level:** подтверждаемый захват экрана доступен на всех поддерживаемых уровнях (standard minSdk 26, legacy minSdk 23) - API-специфичного блокера нет. Подтверждение запрашивается при каждом запуске.
- **Wear OS:** не затрагивается.
- **Производительность:** захват по требованию, без постоянного foreground-сервиса и без полоски-overlay; ресурсы захвата освобождаются сразу после кадра.
- **Совместимость данных:** миграций нет; персистентные настройки назначения скриншота переиспользуются.
- **Локализация:** EN/RU/UK обязательно для нового пункта меню и любых связанных строк.
- **Доступность:** пункт меню обязан быть доступен с клавиатуры/D-pad/мыши (focusable, clickable, nextFocus*), как и прочие действия.

### 3.3 Owner inputs (Approval gate)

- **Related tickets:** S0418 (создал edge-gesture+MediaProjection захват, изначально метил в standard, архивирован), S0405 (молчаливый путь через сервис-помощник для noLegal, архивирован), S0423 (откатил весь скриншотер в noLegal-only на релиз из-за Play-риска SYSTEM_ALERT_WINDOW/SPECIAL_USE), S0472 (отправка скриншота получателям, BlockNeedUserTest - смежная, не зависимость).

## 4. Контекст текущей архитектуры

Захват экрана сегодня состоит из трёх частей. Движок захвата - подтверждаемый системой захват экрана плюс молчаливый захват через сервис-помощник - и сохранение кадра уже переиспользуемы и частично живут в общем слое. Запуск же существует в единственном виде: постоянная полоска по краю экрана, по свайпу с которой стартует либо подтверждаемый захват (старые API), либо молчаливый захват через сервис-помощник (новые API в noLegal). Эта полоска требует разрешения «поверх других окон» и специального foreground-сервиса, а молчаливый захват - сервиса-помощника; всё это смонтировано исключительно в noLegal и спрятано в остальных сборках через пустой набор контроллеров жеста.

Решить задачу «из коробки» нельзя, потому что у движка захвата нет ни одной точки запуска, которая не зависела бы от полоски-overlay или сервиса-помощника. Чтобы дать магазинной сборке скриншот, нужен запуск, не тянущий запрещённые магазином разрешения, - то есть отдельный путь «по явному действию из меню».

---

## 5. Предлагаемый подход

Разделить функцию по линии «способ запуска», а не «движок»: движок подтверждаемого захвата и сохранение кадра выносятся в слой, доступный магазинным сборкам, а оба «тяжёлых» способа запуска (полоска-overlay и сервис-помощник) остаются исключительно в noLegal.

### 5.1 Основные столпы / модули

- **Общий движок захвата:** подтверждаемый системой захват экрана и сохранение кадра в выбранное назначение - доступен и магазинной, и sideload-сборке.
- **Магазинный запуск (новый):** пункт меню «сделать скриншот», который напрямую инициирует подтверждаемый захват, без полоски-overlay, без сервиса-помощника, без разрешения «поверх окон» и без специального foreground-сервиса.
- **Sideload-запуск (без изменений):** полоска по краю экрана (жест) и молчаливый захват через сервис-помощник - только noLegal, с прежними разрешениями и настройками направлений жеста.

### 5.2 Потоки данных и событий

- Магазин: пользователь выбирает действие в меню → системный запрос подтверждения захвата → захват кадра → сохранение в выбранное назначение → уведомление пользователю.
- noLegal: свайп с полоски (или жест на новых API) → подтверждаемый или молчаливый захват → сохранение → уведомление. Поток не меняется.
- Сохранение кадра, выбор назначения и уведомление - общие для обоих путей.

### 5.3 Точки расширяемости

- Точка запуска остаётся абстрактной: меню-действие и жестовая полоска - два независимых триггера одного движка; в будущем можно добавить ещё триггеры (например, действие в шторке) без правок движка.
- Граница «способ запуска per flavor» задаётся монтированием источников и набором контроллеров, а не флаговыми проверками в общем коде.

## 6. Открытые вопросы / Research items

1. **Resolved (quiz 2026-06-20):** пункт меню магазинного запуска - единое действие «сделать скриншот сейчас» в глобальном меню/настройках приложения. Точная вёрстка и расположение всё равно проходят через `/ui-clarify` до реализации.
2. **Resolved (quiz 2026-06-20):** охват меню-пути - только standard. photos/legacy/vr/lite меню-путь не получают; noLegal сохраняет жестовый+молчаливый стек как прежде.
3. **Resolved (quiz 2026-06-20):** магазинный путь переиспользует существующую настройку назначения скриншота из общего слоя; отдельный UI выбора назначения под standard не добавляется.
4. **Resolved (quiz 2026-06-20):** системное подтверждение показывается при каждом захвате (платформенный дефолт, Play-safe); сессионное/одноразовое подтверждение в рамках задачи не исследуется.
5. **Resolved (implementation note):** устаревший комментарий, называющий overlay-полоску «единственным путём захвата на магазинных сборках», приводится в соответствие при реализации - не владельческое решение, а правка по факту изменения.

### Quiz decisions (2026-06-20)

- Охват флейворов → только standard (буквально по захваченному тексту «уровень STANDARD»; noLegal сохраняет жестовый+молчаливый стек в любом случае).
- Назначение сохранения → переиспользовать существующую настройку (`screenshot_destination_resource_id` уже в общем слое; без нового UI).
- Поверхность меню → глобальное меню/настройки приложения (единое действие; точная вёрстка - `/ui-clarify`).
- UX подтверждения → подтверждение при каждом захвате (платформенный дефолт MediaProjection, Play-safe, без доп. сложности).

| Риск | Вероятность | Последствия | Митигация |

| Магазинный путь случайно потянет запрещённые разрешения (поверх окон / специальный FGS / сервис-помощник) через общий слой | Средняя | Отклонение при ревью Google Play | Держать запрещённые разрешения и компоненты только в источниках noLegal; проверять итоговый манифест магазинной сборки на их отсутствие |

## 8. Влияние на пользователя (docs/FEATURES)

Появляется новая видимая возможность магазинной сборки: сделать скриншот из меню приложения с системным подтверждением захвата. Одна строка в docs/FEATURES (+ _RU + _UK) при релизе; запись в `docs/ALL_FEATURES.jsonl` на этапе реализации. Жестовый и молчаливый пути остаются возможностью только sideload-сборки (noLegal) и в публичный showcase магазина не идут.

## 11. Критерии готовности (strategic-level)

1. На магазинной сборке (standard) пользователь делает скриншот из меню; появляется системный запрос подтверждения; кадр сохраняется в выбранное назначение с уведомлением.
2. В итоговом манифесте магазинной сборки нет разрешения «поверх других окон», специального foreground-сервиса и сервиса-помощника для скриншотов.
3. На noLegal жестовая полоска и молчаливый захват работают как до изменения.
4. Поведение результата (назначение, уведомление) одинаково для меню-пути и жестового пути.
5. EN/RU/UK строки нового действия присутствуют и локализованы.
