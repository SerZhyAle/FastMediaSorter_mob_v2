## 1. Проблема

`dev/CATALOG` каталогизирует все ~700+ Kotlin-классов проекта — полезен для поиска в целом, но неудобен как справочник именно по точкам входа приложения. Android Activities — главные навигационные анкоры (entry points): именно они задают экраны, интенты, deeplink-маршруты. Чтобы найти, какая Activity отвечает за конкретный сценарий, агент вынужден фильтровать полный каталог и читать несколько файлов. Специализированного, машиночитаемого и удобочитаемого справочника по Activity-точкам входа не существует — ни для людей, ни для скилов.

---

## 2. Цели

1. Появляется выделенный каталог всех Activity-классов проекта (основное приложение + Wear) с описаниями назначения, обрабатываемых интентов и flavor-ограничений.
2. Агент или разработчик находит нужную Activity за один запрос вместо серии grep/glob.
3. Каталог обновляется одной командой после добавления или удаления Activity.
4. Скилы могут использовать каталог как первый шаг при разборе навигации, deeplink-маршрутов, intent-фильтров.

**Non-goals:**

- Каталог не заменяет `dev/CATALOG` — он дополняет его и фокусируется только на Activity-точках входа.
- Каталог не охватывает Fragments или Composables — только классы-Activity.
- Никакой автогенерации документации для пользователей.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Поиск по имени, назначению и flavor-метке из командной строки (PowerShell).
2. Человекочитаемый Markdown-рендер для быстрого просмотра в IDE.
3. Структура аналогична `dev/CATALOG`: JSONL-источник + render-скрипт + query-скрипт.
4. Обновление каталога через скил или отдельный скрипт — без ручного редактирования JSONL.

### 3.2 Жёсткие ограничения

- **Flavor:** standard, lite, photos, legacy — каталог должен отражать flavor-принадлежность каждой Activity.
- **API level:** без API-специфики; каталог — инструмент разработки, не рантайм.
- **Wear OS:** Wear-модуль включается в каталог наравне с основным приложением.
- **Производительность:** скрипты сканирования и запроса должны завершаться за разумное время на текущем объёме кода.
- **Совместимость данных:** при добавлении полей в JSONL-схему ручные поля (`role`, `intents`, `noFlavors`) сохраняются — merge по `path + class`.
- **Локализация:** каталог является инструментом разработки; пользовательский текст отсутствует. Требование EN/RU/UK не применяется.
- **Доступность:** не применяется — инструмент разработки.

## 4. Контекст текущей архитектуры

В проекте уже есть `dev/CATALOG/` — JSONL-база всех Kotlin-классов с автоматическими полями (LOC, инъекции, side-effects) и ручными полями (role, status, noFlavors). Инфраструктура: `scan.ps1` (парсинг AST/grep), `render.ps1` (JSONL → MD), `query.ps1` (фильтрация), `set.ps1` (ручные правки).

Activity-классов в проекте около десяти. Сейчас они размазаны по общему каталогу без специальной группировки. При навигационном анализе агент вынужден сначала фильтровать `dev/CATALOG` по layer=`ui` и затем угадывать, какой класс является Activity. Отдельного индекса intent-фильтров и deeplink-схем нет нигде.

---

## 5. Предлагаемый подход

Создать `dev/ACTIVITY_CATALOG/` — независимый каталог, сфокусированный только на Activity-классах, с упрощённой схемой по сравнению с `dev/CATALOG`.

### 5.1 Основные столпы / модули

**JSONL-база (источник истины)**
- Каждая запись = одна Activity.
- Автополя: путь к файлу, имя класса, модуль (app_v2/wear), LOC, дата последнего коммита, список intent-фильтров (из `AndroidManifest.xml`), launcher-флаг, flavor-тег.
- Ручные поля: назначение (одна строка), deeplink-схемы, примечания.
- Merge-ключ при ресканировании: `path + class`.

**scan-скрипт**
- Читает `AndroidManifest.xml` обоих модулей.
- Обходит исходники, собирает LOC и дату коммита для каждой найденной Activity.
- Сохраняет записи в JSONL, сохраняя ручные поля.

**query-скрипт**
- Фильтрация по: имени класса (glob), модулю, launcher-флагу, flavor, наличию/отсутствию ручного описания.
- Вывод: текстовая таблица или JSON (для пайпинга в другие скрипты).

**render-скрипт**
- JSONL → Markdown-таблица: имя, модуль, описание, интенты, flavors.
- Результат: `dev/ACTIVITY_CATALOG/app_v2.md` и `dev/ACTIVITY_CATALOG/wear.md`.

**set-скрипт**
- Обновление ручных полей (`role`, `deeplinks`, `notes`) для конкретной записи.
- Автоматически перегенерирует MD после правки.

### 5.2 Потоки данных и событий

`AndroidManifest.xml` + исходники → `scan.ps1` → JSONL → `render.ps1` → MD.  
Агент/разработчик → `query.ps1` → отфильтрованный список.  
Ручная правка → `set.ps1` → обновлённый JSONL → автоматический рендер.

### 5.3 Точки расширяемости

- Поле `intents[]` допускает рост — новые intent-action теги добавляются без изменения схемы.
- При появлении новых модулей (например, TV-specific) достаточно добавить новый параметр `-Module` в скрипты.
- Каталог может быть расширен для охвата Services/BroadcastReceiver — параметром типа, без изменения структуры JSONL.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Intent-фильтры в манифесте неполные или динамические | Низкая | Каталог пропускает некоторые entry points | Скрипт выдаёт предупреждение при пустом `intents[]` |

## 9. Архитектурные решения (ADR)

**ADR-1: Отдельный каталог вместо расширения `dev/CATALOG`**

- **Решение:** Создать `dev/ACTIVITY_CATALOG/` как самостоятельную директорию.
- **Альтернативы:** Добавить тег `isActivity: true` в существующий `dev/CATALOG` и фильтровать его.
- **Почему:** Схема `dev/CATALOG` оптимизирована под общие классы; Activity-специфичные поля (intent-фильтры, deeplinks, launcher-флаг) захламят общую схему. Отдельный каталог имеет меньше записей, быстрее парсится и проще в поддержке.

**ADR-2: Парсинг `AndroidManifest.xml` как первичный источник Activity-списка**

- **Решение:** Сканер читает манифест для получения полного списка зарегистрированных Activity, затем сопоставляет с исходниками.
- **Альтернативы:** Grep по исходникам на предмет наследования от `AppCompatActivity` / `ComponentActivity`.
- **Почему:** Манифест — единственный авторитетный источник того, что реально зарегистрировано в приложении. Grep по иерархии классов ненадёжен при использовании базовых классов.

## 11. Критерии готовности (strategic-level)

1. Запуск `scan.ps1` из `dev/ACTIVITY_CATALOG/scripts/` корректно заполняет JSONL для обоих модулей без ручного вмешательства.
2. `query.ps1` возвращает отфильтрованный список Activity менее чем за 3 секунды.
3. `render.ps1` генерирует человекочитаемый Markdown с именем, описанием, intent-фильтрами и flavor-меткой для каждой Activity.
4. После добавления новой Activity в манифест и запуска `scan.ps1` запись появляется в каталоге автоматически.
5. Агент может ответить на вопрос «какая Activity обрабатывает воспроизведение?» за один вызов `query.ps1`.
