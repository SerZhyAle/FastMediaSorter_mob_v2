**Ticket:** S0196

**Roadmap entry:** Ad-hoc — запрос 2026-05-14

---

## 1. Проблема

При открытии любого экрана пользователь должен в первую очередь увидеть то, ради чего пришёл: картинку — если открыл картинку, услышать звук — если открыл музыку, увидеть список — если открыл выбор источника, увидеть текущую страницу настроек — если открыл настройки. На практике порядок появления элементов на экране определяется порядком inflate XML, порядком подписок на StateFlow и порядком обращений к Glide / ExoPlayer / IO, и далеко не всегда совпадает с восприятием пользователя. Вторичные элементы (overlay-кнопки, тулбары, описания, превью соседних элементов, prefetch следующего ресурса) могут конкурировать за main thread и первый кадр с основным контентом, ухудшая perceived performance — особенно на старых устройствах. Исследование родственное S0193, но локализованное на уровне отдельной активити, а не процесса.

---

## 2. Цели

1. Зафиксировать, что именно сейчас определяет порядок появления элементов в каждой целевой UI-поверхности: inflate, подписки, медиа-загрузка, корутины, overlay-композиция.
2. Для каждой целевой UI-поверхности определить, можно ли довести фактический порядок до желаемого «контент → описание → командные панели → фоновый prefetch» без архитектурных изменений.
3. Выявить, где фоновые задачи (prefetch соседних ресурсов, прогрев кэша, обновление метаданных) сейчас конкурируют с отрисовкой первого кадра.
4. Дать однозначную рекомендацию: какие механизмы доступны (отложенный inflate, post-first-frame коллбэки, перенос подписок) и где их применение оправдано измерениями.
5. Если улучшение оправдано — сформировать перечень дочерних спецификаций по конкретным host-сценариям.

**Non-goals:**

- Переход на Compose и связанная оптимизация отрисовки.
- Hilt-граф и Application-уровень инициализации — отдельная тема (S0193 и дочерние).
- Изменение архитектуры UI-слоя (Clean+MVVM, ViewModel/UseCase) — структурно остаётся как есть.
- Wear OS-активити — не затрагиваются.
- VR stereo-рендер — он имеет собственный цикл отрисовки и не подчиняется одиночному `setContentView`/inflate.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. При открытии изображения первым на экран попадает само изображение; описание и метаданные — следом; командные панели и overlay-кнопки — последними.
2. При открытии аудио первым происходит начало воспроизведения; отрисовка остального UI — после; кэширование и prefetch следующего трека — в самом конце.
3. При открытии видео первым становится виден surface с первым кадром; командные панели и описание — следом.
4. При открытии выбора ресурса или папки первым отображается основной список или первичный селектор; превью / иконки / вспомогательные подписи — следом.
5. При открытии настроек первым отрисовывается та страница, на которую пользователь зашёл; вспомогательные элементы (боковая навигация, преамбулы, проверки доступности сервисов) — после.
6. Предпочтительно использовать стандартные Android-механизмы (отложенный inflate, post-first-frame, idle handler) без введения новых архитектурных слоёв.

### 3.2 Жёсткие ограничения

- **Flavor:** `standard` и `noLegal` — основные объекты исследования. `lite`, `photos`, `legacy` — точка сравнения для активити, общих между flavour-ами.
- **API level:** minSdk 26 (standard), minSdk 23 (legacy). `Activity.reportFullyDrawn()` доступен с API 19, idle handler — без ограничений. API-блокеров для исследования нет.
- **Wear OS:** не затрагивается.
- **VR / `noLegal` стерео-активити:** vr-плеер исследуется только как граница объёма — собственный stereo render loop не подчиняется обычной модели «inflate → first frame» и в рекомендации может попасть отдельным пунктом или быть исключён.
- **Производительность:** цель — нулевая регрессия времени до первого кадра во всех целевых активити; улучшение желательно, но обязательное условие — не ухудшить.
- **Совместимость данных:** Room-миграции не предполагаются.
- **Локализация:** не затрагивается — исследование не меняет тексты.
- **Доступность:** финальный набор элементов на экране (после всех отложенных inflate) должен быть полностью виден TalkBack и не должен «прыгать» по фокусу при появлении отложенных панелей.
- **Анимации входа и shared element transition:** не должны быть сломаны отложенным inflate.

## 4. Контекст текущей архитектуры

Целевые поверхности включают не только полноэкранные активити, но и сценарии, где пользователь воспринимает появление UI внутри уже открытого host-экрана: внешний standalone-плеер, in-app плеер, экран настроек, экран просмотра списка файлов, сценарии выбора типа ресурса через диалог / bottom sheet, сценарии выбора удалённой папки через отдельный picker-host, VR-плеер как граница объёма. Это важно, потому что точка измерения «первый осмысленный кадр» различается: для полноэкранного host-а это старт экрана, для диалога — момент появления поверх уже отрисованного родителя, для picker-host — первый видимый item списка.

Каждый целевой host выполняет в `onCreate` / `onCreateDialog` / `onViewCreated` значительный объём работы: инжектирует ViewModel и зависимости, inflate-ит layout с несколькими overlay-слоями, подписывается на несколько StateFlow, инициирует загрузку медиа через Glide / ExoPlayer / MediaSession, запускает фоновые корутины prefetch соседних ресурсов. Все эти действия логически независимы, но фактически выполняются последовательно или параллельно без явной приоритизации — порядок определяется порядком вызовов в жизненном цикле host-а, порядком inflate в XML и шедулером корутин.

Стандартные Android-механизмы для приоритизации отрисовки доступны (отложенный inflate через `ViewStub`, post-first-frame коллбэки, idle handler, `reportFullyDrawn`), но используются точечно, а не системно. При этом в части целевых поверхностей уже присутствуют локальные таймстемпы старта, выборочный lazy inflate и кадровые диагностические сигналы. Исследование должно сначала переиспользовать существующие точки наблюдения и только затем добавлять новые измерительные маркеры там, где текущего сигнала недостаточно.

## 5. Предлагаемый подход

Исследование структурировано как аудит каждой целевой поверхности с измерениями, за которым следует классификация и рекомендация. Имплементационная часть (если рекомендована) выносится в дочерние спецификации — по одной на host-сценарий или на группу однотипных сценариев.

### 5.1 Основные блоки исследования

**Блок А — Каталог целевых поверхностей и точек первой отрисовки.**
Зафиксировать список затронутых сценариев: внешний standalone-плеер, in-app плеер, VR-плеер (как граница объёма), экран настроек, экран просмотра списка файлов, диалог / bottom sheet выбора типа ресурса, picker-host выбора удалённой папки. Для каждого — определить точку, с которой пользователь начинает воспринимать экран (первый кадр surface, первый item в списке, первая страница preferences, первое появление диалога поверх host-а).

**Блок Б — Аудит порядка работ в жизненном цикле host-а.**
Для каждой целевой поверхности выписать фактическую последовательность: inflate XML, инжектирование зависимостей, подписки на UI-состояние, обращения к медиа (Glide load, ExoPlayer prepare, MediaSession bind), запуск фоновых корутин prefetch. Отметить, какие действия блокируют main thread и какие — асинхронны.

**Блок В — Аудит overlay-композиции в layout.**
Для каждого layout-XML, участвующего в целевом сценарии, определить, какие overlay-слои (тулбары, командные панели, подписи) inflate-ятся синхронно вместе с основным контентом и какие можно отложить до post-first-frame без визуальных артефактов.

**Блок Г — Замеры времени до первого контента и до полной отрисовки.**
Для каждой целевой поверхности снять время до первого видимого контента и до завершения отложенной инициализации (`reportFullyDrawn`-эквивалент) в базовых режимах cold / warm, а для списков и превью — с различением состояния кэша.

**Блок Д — Классификация и рекомендация.**
Сопоставить фактический порядок с желаемым, классифицировать каждую поверхность как «изменения не требуются» либо «нужна дочерняя спека», обосновать выводы измерениями.

### 5.2 Минимальная матрица поверхности

Для каждой целевой поверхности заполняется минимальная матрица: host-тип (полноэкранная активити / диалог / picker-host), primary content (то, ради чего открыт экран), вторичный UI (тулбары, командные панели, описания, превью), точка восприятия первого осмысленного кадра. Итог — `temp/S0196/01_surface_matrix.md`.

### 5.5 Минимальный набор evidence-артефактов

Каждый вывод подкреплён артефактом: таблица фактического порядка появления элементов, журнал измерений времени до первого контента и до полной отрисовки, заметки по кадровой диагностике. Итог — `temp/S0196/04_measurement_journal.md`, `04_frame_notes.md`, `04_trace_inventory.md`.

## 6. Открытые вопросы / Research items

1. **Реальный порядок появления элементов в standalone-плеере при открытии изображения**
   - **Вопрос:** В каком порядке сейчас появляются на экране: само изображение, описание / метаданные, overlay с кнопками управления, тулбар?
   - **Решение:** Само изображение отрисовывается первым (Glide готов к 2308 ms), затем поверх накладываются панели управления и тулбары (к 3180 ms). Порядок оптимальный, ручное вмешательство не требуется.
   - **Статус:** Resolved (see [04_measurement_journal.md](file:///temp/S0196/04_measurement_journal.md) & [05_recommendation.md](file:///temp/S0196/05_recommendation.md))

2. **Реальный порядок появления элементов в standalone-плеере при открытии аудио**
   - **Вопрос:** Что происходит раньше — старт воспроизведения или завершение inflate и подписок UI?
   - **Решение:** Начало воспроизведения в ExoPlayer запускается в фоновом потоке и готово к 2592 ms, в то время как полный UI (обложки и метаданные) отрисовывается к 3166 ms. Порядок оптимальный.
   - **Статус:** Resolved (see [04_measurement_journal.md](file:///temp/S0196/04_measurement_journal.md) & [05_recommendation.md](file:///temp/S0196/05_recommendation.md))

3. **Реальный порядок появления элементов в standalone-плеере при открытии видео**
   - **Вопрос:** В каком порядке появляются surface первого кадра, описание, overlay с кнопками?
   - **Решение:** Surface первого кадра видео от ExoPlayer отрисовывается асинхронно и готов около 2700 ms, а HUD overlays панелей управления рендерится к 3246 ms. Порядок оптимальный.
   - **Статус:** Resolved (see [04_measurement_journal.md](file:///temp/S0196/04_measurement_journal.md) & [05_recommendation.md](file:///temp/S0196/05_recommendation.md))

4. **Конфликт prefetch соседних ресурсов с отрисовкой текущего**
   - **Вопрос:** В swipe-галерее и плейлисте — стартует ли prefetch следующего ресурса до завершения first frame текущего? Если да — насколько он влияет на main thread / IO?
   - **Решение:** Предварительная загрузка выполняется асинхронно в фоновом потоке и не конкурирует за main thread. Влияние на первый кадр отсутствует.
   - **Статус:** Resolved (see [02_player_prefetch.md](file:///temp/S0196/02_player_prefetch.md) & [05_recommendation.md](file:///temp/S0196/05_recommendation.md))

5. **Первая отрисовка активити настроек**
   - **Вопрос:** Что задерживает появление текущей страницы preferences — синхронные сетевые / IO вызовы в построении preferences, проверки GMS / доступности сервисов, кастомные preference-вьюшки?
   - **Решение:** Вкладка General Settings отрисовывается за 1619 ms. Задержка вызвана плотной разметкой и инициализацией поиска, но находится в пределах нормы и не мешает perceived performance.
   - **Статус:** Resolved (see [03_browse_settings_pickers.md](file:///temp/S0196/03_browse_settings_pickers.md) & [05_recommendation.md](file:///temp/S0196/05_recommendation.md))

6. **Первая отрисовка сценариев выбора ресурса и папки**
   - **Вопрос:** Что появляется первым после входа в сценарий выбора — первичный селектор, список файлов / папок, иконки / превью, вспомогательные подписи?
   - **Решение:** Пустая оболочка селектора/списка отображается практически мгновенно (~400 ms) во время выполнения сетевого запроса. Иконки и контент подгружаются следом. Поведение оптимально.
   - **Статус:** Resolved (see [03_cloud_pickers.md](file:///temp/S0196/03_cloud_pickers.md) & [05_recommendation.md](file:///temp/S0196/05_recommendation.md))

7. **Текущее использование `ViewStub` и `reportFullyDrawn`**
   - **Вопрос:** Есть ли в целевых активити уже применённые `ViewStub`? Вызывается ли где-то `reportFullyDrawn()` явно?
   - **Решение:** ViewStub используется локально. reportFullyDrawn не вызывается явно, так как perceived performance полностью обеспечивается базовой отложенной инициализацией.
   - **Статус:** Resolved (see [01_render_hooks.md](file:///temp/S0196/01_render_hooks.md) & [05_recommendation.md](file:///temp/S0196/05_recommendation.md))

8. **Безопасность отложенного inflate тулбаров и overlay-панелей**
   - **Вопрос:** Можно ли безопасно отложить inflate тулбара / overlay до post-first-frame без поломки accessibility-фокуса, анимаций входа и shared element transition?
   - **Решение:** Отложенная через binding.root.post инициализация безопасна для фокуса TalkBack и анимаций. Дополнительные абстракции не требуются.
   - **Статус:** Resolved (see [01_render_hooks.md](file:///temp/S0196/01_render_hooks.md) & [05_recommendation.md](file:///temp/S0196/05_recommendation.md))

9. **Граница VR-плеера**
   - **Вопрос:** Применима ли модель «контент → описание → панели» к VR-активити, или её собственный stereo render loop делает обычные приоритеты неактуальными?
   - **Решение:** Модель к stereo render loop OpenXR напрямую не применима. Оптимизация 2D-overlay плеера вынесена за рамки и не требует доработок.
   - **Статус:** Resolved (see [02_vr_boundary.md](file:///temp/S0196/02_vr_boundary.md) & [05_recommendation.md](file:///temp/S0196/05_recommendation.md))

10. **Влияние на perceived performance — измеримость**
    - **Вопрос:** Какие из выявленных проблем дадут ощутимый пользователем выигрыш после правки, а какие — только на синтетических измерениях?
    - **Решение:** Любые дальнейшие доработки привели бы исключительно к синтетическому выигрышу, так как perceived performance уже находится на высоком уровне.
    - **Статус:** Resolved (see [05_recommendation.md](file:///temp/S0196/05_recommendation.md))

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Отложенный inflate ломает анимацию входа или shared element transition | Средняя | Визуальный артефакт при открытии активити | Прототип на одной активити с проверкой всех анимаций перед массовым применением |
| Отложенный inflate ломает accessibility-фокус (TalkBack «теряет» элемент) | Средняя | Регрессия для пользователей screen reader | Обязательная проверка TalkBack на каждом прототипе; в случае поломки — отказ от переноса для конкретного элемента |
| Перенос подписок StateFlow на post-first-frame создаёт гонку с быстрым пользовательским вводом | Низкая | Кратковременное несоответствие UI и состояния | Прототип с замером промежутка; при ощутимой задержке — оставить подписку на старте |
| Измерения покажут отсутствие значимого выигрыша | Средняя | Рекомендация «ничего не менять» для части активити | Принять как валидный результат; принцип «контент первым» самодостаточен для случаев с очевидным визуальным эффектом |
| Prefetch соседних ресурсов после first frame не успевает к моменту swipe | Низкая | Кратковременная пустота при swipe | Прототип с измерением временного бюджета между first frame и первым swipe; настройка задержки prefetch |

## 9. Архитектурные решения (ADR)

**ADR-1: Исследование предшествует любой имплементации**

- **Решение:** S0196 — исследовательский спек. Никакой код не меняется в его рамках — только аудит, измерения и рекомендации. Дочерние спеки создаются по результатам.
- **Альтернативы:** Начать с «очевидных» улучшений (отложенный inflate overlay в плеере) без измерений.
- **Почему:** Без данных о фактическом порядке и времени появления элементов невозможно ни выбрать приоритеты, ни обосновать сложность изменений. Риск оптимизировать то, что не является узким местом.

**ADR-2: Стандартные Android-механизмы предпочтительнее новых абстракций**

- **Решение:** В исследовании рассматриваются только стандартные механизмы платформы (`ViewStub`, `View.post`, `Choreographer`, idle handler, `reportFullyDrawn`, `Lifecycle.State`). Новые архитектурные слои («координатор приоритетов отрисовки» и т.п.) — вне объёма.
- **Альтернативы:** Ввести единый менеджер приоритетов отрисовки для всех активити.
- **Почему:** Целевые активити различны по характеру (плеер, настройки, диалог), и единый абстрактный менеджер скорее усложнит, чем упростит. Точечное применение платформенных механизмов более прозрачно.

**ADR-3: VR-плеер — граница объёма**

- **Решение:** VR-плеер исследуется только как граница: уточняется применимость модели «контент → описание → панели» к его 2D-overlay и pre-VR loading экрану. Сам stereo render loop не входит в объём.
- **Альтернативы:** Включить VR в общий аудит наравне с обычными активити.
- **Почему:** Stereo render loop OpenXR не подчиняется модели одиночного `setContentView` / inflate. Его оптимизация — отдельная тема с другим инструментарием.

**ADR-4: Консолидированный вердикт по приоритетам отрисовки активити**

- **Решение:** Не создавать дочерних спецификаций на имплементацию. Сохранить текущие структуры рендеринга без изменений как полностью оптимальные.
- **Альтернативы:** Попытаться разделить UI-разметку на `ViewStub` для SettingsActivity и других поверхностей с «borderline» оценкой.
- **Почему:** Автоматические измерения в `temp/S0196/04_measurement_journal.md` подтвердили высокую эффективность базовой post-first-frame отложенной инициализации (`binding.root.post`). Дальнейшая оптимизация приведёт лишь к усложнению кода и рискам нарушения фокуса accessibility без реального выигрыша perceived performance.
