## 0. Контекст: что такое VR-сборка сегодня

- **Целевое устройство:** Meta Quest 3, HorizonOS, Android 14 (API 34), OpenXR-флейвор `vr` / `vrUnlicensed`.
- **Архитектура VR-плеера:** нативный OpenXR-цикл (C++) + Kotlin-оркестрация. Видео — отдельный composition layer (`PROJECTION` / `EQUIRECT_2` / `CYLINDER` / `QUAD_CINEMA`). HUD — отдельный плоский layer (1024×256, статически зашит). Панель управления — третий composition layer (`VR_UI_COMPOSITION_LAYER_ENABLED=true` с 2026-05-03).
- **Ввод:** контроллеры Touch + hand-tracking. Ray-vs-plane intersection реализован (`OpenXrInput.cpp:syncControllerAimRay`). Hover-highlight на HUD-кнопках работает (S0024 Verified, 1449 событий за сессию). Видимая отрисовка луча — добавлена через GLES3 VBO в S0065 (статус Implemented, требуется проверка).
- **Стерео-форматы:** SBS, OU, VR180 (fisheye), VR360 (equirect/cylinder). Детектирование по имени файла + ExoPlayer-метаданным.
- **Маршрутизация:** `BrowseRoutingDecision` в Browse + `VrRouteDecisionHelper` в активити (S0018 Verified, S0026 — на проверку).

## 1. Подзадача — Луч контроллера и курсор-точка не отрисовываются на гарнитуре

**Источник:** `S0065 vr-controller-ray-visual` (Implemented по файлу, BlockNeedUserTest по журналу).

**Симптом:** в иммерсивной сессии пользователь не видит, куда направлен контроллер. Math-pass луча работает (зафиксировано 1449 hover-событий), но визуального индикатора нет — нельзя точно прицелиться по кнопкам HUD. На Quest 3 аппаратный LED контроллера не виден в фокусированной XR-сессии.

**Что должно быть:**

- Тонкая полупрозрачная линия от aim-точки контроллера до точки пересечения с зарегистрированной плоскостью (HUD / panel).
- Маленький курсор (диск) на точке пересечения, размер ≥ 5° телесного угла на 2 м.
- При промахе по всем плоскостям — луч обрезается на 5 м (или скрывается).
- Hand-tracking aim использует тот же визуальный примитив.

**Что нужно проверить на устройстве:**

- Запустить иммерсив с любым стерео-файлом, направить контроллер в HUD — луч и курсор видны.
- Направить контроллер в воздух (вне HUD) — луч обрезан или скрыт согласно решению.
- Проверить hand-tracking путь.
- FPS не падает ниже 72 при включённом луче.

## 2. Подзадача — Интерактивная панель управления в иммерсиве (полный playback UI)

**Источник:** `S0008 vr-immersive-controls-panel` (BlockNeedUserTest, P60).

**Симптом:** в иммерсиве по нажатию кнопки контроллера не открывается полноценная панель управления плеером — только пассивная полоска прогресса (HUD из S0009). Невозможно изменить громкость, выбрать аудио-дорожку, переключить субтитры, поменять стерео-формат, не выходя из VR.

**Что должно быть:**

- Кнопка контроллера «Открыть управление» открывает плавающую полупрозрачную панель в нижней части FOV.
- На панели: пауза/воспроизведение, перемотка вперёд/назад, seek-слайдер, регулятор громкости, яркости, выбор аудио-дорожки и субтитров, скорость воспроизведения, индикатор стерео-формата + кнопка ручного переключения, выход из иммерсива.
- Размер интерактивных зон ≥ 5° телесного угла на 2 м.
- Панель автоматически скрывается через 10 секунд бездействия.
- FPS не ниже 72 при открытой панели + 4K видео.

**Что нужно проверить на устройстве:**

- Открытие панели одним нажатием кнопки контроллера.
- Все элементы кликабельны лучом.
- Seek-слайдер реагирует на drag (триггер удерживается, луч ведётся по слайдеру).
- Изменение стерео-формата вступает в силу немедленно.
- Авто-скрытие через 10 с.

**Что нужно проверить на устройстве:**

## 5. Подзадача — Моргание иммерсивом при открытии стерео-файла

**Источник:** `S0026 bugfix-vr-stereo-route-flicker` (BlockNeedUserTest, P85).

**Симптом:** при выключенном тумблере «авто-вход в иммерсив» открытие стерео-файла из Browse даёт цикл «активити создалась — упала в фолбэк»: пользователь на ~1 с видит запуск иммерсива, затем сворачивание, и плеер открывается на панели. Лишний XR-сеанс, лишнее окно в task switcher Quest 3.

**Что должно быть:**

- Маршрут вычисляется в `BrowseEventHandler` ДО запуска активити: если результат — панель, intent отправляется в `PlayerActivity` напрямую, без промежуточной `VrPlayerActivity`.
- При запуске VR-активити intent-extras уже содержит `EXTRA_DETECTED_STEREO_MODE` — активити не обнуляет режим до `MONO`.
- Лог-строка `RouteDecision` уникальна, содержит поля `detected, requested, effective, autoImmersiveSetting, route, reason` в одной записи.
- 5 подряд открытий разных стерео-файлов без промежуточного цикла «активити создалась — закрылась через фолбэк».

**Статика PASS:** Phase 01 + F03 коммит залиты, тесты `BrowseRoutingDecisionTest` (14 кейсов) и `VrRouteDecisionHelperTest` зелёные.

**Что нужно проверить на устройстве (4 сценария):**

- **S1** — `auto-immersive=OFF` + стерео файл → стандартный плеер, нет моргания.
- **S2** — `auto-immersive=ON` + стерео файл → иммерсив без фолбэка.
- **S3** — `auto-immersive=ON` + плоский 2D → cinema иммерсив.
- **S4** — `auto-immersive=OFF` + плоский 2D → стандартный плеер.

## 6. Подзадача — VR180 fisheye: пикселизация на Quest 3 («кубики»)

**Источник:** `S0041 debug-vr180-fisheye-quality-regression` (BlockNeedUserTest, P90 — самый высокий приоритет среди VR-багов).

**Симптом:** при просмотре эталонного файла `18VR_The_Best_is_Yet_to_Come_7K_180_180x180_3dh.mp4` в иммерсиве картинка сильно пикселизована — как при низком разрешении. ExoPlayer декодирует HEVC 7168×3584 правильно (подтверждено `VR_QUALITY_DEBUG: selected track format`), `EQUIRECT_2` слой назначен корректно, но визуальный результат — «кубики».

**Гипотезы (от наиболее к наименее вероятной):**

- **A — Fisheye UV-параметры:** FOV / crop / UV scale изменились → масштабирование «zoom в центр», создающее эффект пикселизации.
- **D — `centralAngle=π` не соответствует реальному 180° fisheye линз:** изображение растянуто.
- **C — Видео-эффекты ExoPlayer не применяются:** SurfaceTexture получает данные с масштабированием.
- **E — `GL_SRGB8_ALPHA8` swapchain:** двойная gamma-correction → quantization artifacts.

**Что нужно сделать:**

- Phase 1 — добавить расширенное логирование (`VR_QUALITY_DEBUG: fisheye uniforms fov=.. uvOffset=.. uvScale=..`, `selected track format`, swapchain format), запустить сессию, собрать данные.
- Phase 2 — на основе логов выбрать гипотезу, исправить, переснять видео.

**Что нужно проверить на устройстве:**

- Эталонный 7K-файл показывается без «кубиков», резкость соответствует исходнику.
- Регрессионная проверка на других VR180-файлах меньшего разрешения.

## 7. Подзадача — Выход из иммерсива клонирует окно в HorizonOS task switcher

**Источник:** `S0038 bugfix-vr-exit-immersive-new-window` (Implemented, P85). Phase 01 применена и работает (`flags=0x30020000` подтверждены в логе), но клонирование сохраняется.

**Симптом:** за одну сессию пользователь накапливает N+1 окон в task switcher Quest 3 (N = количество входов/выходов в иммерсив). HorizonOS сохраняет task-запись после `onDestroy` потому что приложение не вызывает `finishAndRemoveTask()`.

**Что должно быть:**

- В `VrTaskTransition.exitImmersiveToFlatPlayer()` после `startActivity(panelIntent)` добавить `activity.finishAndRemoveTask()` — это удалит окно из switcher.
- В switcher не появляется лишний промежуточный `VrPlayerActivity` или extra flat-panel window.
- Повторное открытие того же стерео-файла не получает `FLAG_ACTIVITY_BROUGHT_TO_FRONT` (=Android нашёл живой task и переиспользовал его).

**Что нужно проверить на устройстве:**

- 5 циклов вход → выход → вход для разных файлов: в task switcher остаётся ровно одно окно.
- Повторное открытие того же файла не создаёт второе окно.
- Регрессионная проверка для `S0028 vr-multi-window-playback` — пользователь по-прежнему может явно открыть второе окно через осознанную команду.

## 8. Подзадача — SBS_FULL и SBS_HALF рендерятся как QUAD_CINEMA вместо PROJECTION

**Источник:** `S0078 bugfix-vr-sbs-full-half-layer-factory` (Implemented, P85).

**Симптом:** SBS_FULL/SBS_HALF файлы детектируются корректно (`StereoDetector → SBS_FULL`), но в иммерсиве пользователь видит широкое плоское side-by-side изображение — оба глаза получают одинаковую полную картинку. Стерео отсутствует.

**Root cause:** в `DefaultVrLayerFactory.describe()` ветка `stereo in PROJECTION_STEREO_MODES && renderMode == FULL_STEREO -> projectionDescriptor(stereo)` требует `FULL_STEREO`, но при стандартном `renderMode=CINEMA` падает в `else` → `quadCinemaDescriptor()` (плоский квад). Тот же баг был у `OU` и был исправлен раньше — для SBS аналогичная mode-независимая ветка не добавлена.

**Фикс реализован:** условие `&& renderMode == FULL_STEREO` удалено, `PROJECTION_STEREO_MODES` уже точно определяет, когда нужен projection.

**Что нужно проверить на устройстве:**

- Открыть SBS_FULL файл — видно настоящее 3D, левый и правый глаз получают разные половины кадра.
- Открыть SBS_HALF файл — аналогично.
- Регрессионная проверка для OU и VR180 fisheye.
- Лог должен показать `renderQuad first stereo=SBS_FULL layer=PROJECTION` и `uScale=0.5`.

## 9. Подзадача — HUD swapchain зашит на 1024×256 — нечитаем на Quest 3

**Источник:** `S0080 enh-vr-hud-swapchain-resize` (Implemented, P70).

**Симптом:** HUD занимает ~12-14% высоты глаза на Quest 3 (eye buffer 1680×1760). Текст элементов управления нечитаем, пользователь не видит реакции на нажатие триггера.

**Что должно быть:**

- HUD swapchain создаётся с размером, пропорциональным eye buffer: `hudWidth = eyeWidth × HUD_WIDTH_RATIO`, `hudHeight = eyeHeight × HUD_HEIGHT_RATIO`. Кандидаты: 80% × 22% (1344×388) или 70% × 22% (1176×387).
- При изменении eye buffer (другая конфигурация OpenXR) HUD адаптируется автоматически.
- (Опционально) В VR-настройках появляется опция супер-сэмплинга eye buffer: `OFF / 1.0× / 1.25× / 1.5×`.

**Что нужно проверить на устройстве:**

- Лог показывает `HUD swapchain: NxM` где N > 1024, M > 256.
- Текст HUD читается с типичной дистанции HUD-плоскости.
- FPS не падает ниже 72.

## 10. Подзадача — VR180 7K превью-кадр null (`getFrameAtTime`)

**Источник:** `S0032 bugfix-vr180-frameat-null` (BlockNeedUserTest, P45).

**Симптом:** при паузе плеера превью-кадр для эталонного 7K VR180 файла остаётся пустым. `MediaMetadataRetriever.getFrameAtTime` возвращает `null` из-за конкуренции декодеров (ExoPlayer уже занял аппаратный) и/или нехватки native heap (в логе `Native: 138MB/147MB (free: 9MB)`).

**Что должно быть:**

- При `getFrameAtTime == null` показать fallback: thumbnail из Browse-кэша (он уже есть для этого файла, подтверждено в логе `CACHE_HIT_DEBUG`), либо серая заглушка.
- В логе расширенный маркер причины: `getFrameAtTime returned null reason=decoder-busy|oom|unsupported|unknown`.
- Превентивно: если ExoPlayer держит аппаратный декодер для того же файла → `getFrameAtTime` не вызывается, сразу fallback.
- Превентивно: для файлов > N ГБ или при `native heap free < M MB` `getFrameAtTime` пропускается.

**Что нужно проверить на устройстве:**

- Эталонный 7K VR180 — при паузе виден thumbnail из Browse-кэша.
- Обычный (не 7K, не VR180) файл работает как раньше, без регрессии.
- TalkBack озвучивает заглушку.

## 14. Подзадача — XR cold-start latency: измерение и решение

**Источник:** `S0014 vr-xr-cold-start` (BlockNeedUserTest, P70).

**Симптом:** первый вход в XR-сессию на Quest 3 занимает 1093 мс (повторные ~144-201 мс). Воспринимается как «тормозной» вход в VR. Никем не разложено по стадиям, поэтому нельзя честно решить, оптимизировать или нет.

**Что нужно сделать:**

- Phase 1 — добавить stage-by-stage метрики:
  - `onCreate → BaseActivity.setupViews START`
  - `startXrInitialization → OpenXrSessionManager.initialize begin`
  - `EGL create`
  - `nativeInitialize`
  - `onSessionReady`
  - `initializeVrRenderPipeline → first usable frame`
- Phase 2 — на основе данных принять явное решение:
  - **Optimize now** — если есть дешёвая безопасная оптимизация с измеримым выигрышем.
  - **Won't fix now / backlog** — если задержка приемлема, документ закрывает задачу без потери в эфире.

**Что нужно проверить на устройстве:**

- Stage breakdown снят минимум на 3 cold-start сессиях.
- Сравнение «до» / «после» (если оптимизация применена) показывает измеримый выигрыш.
