# S1123 - Edge-gesture config dialog degrades to single column when rotated while open

**Ticket:** S1123
**Status:** Archived
**Priority:** 30
**Date:** 2026-07-19
**Tier:** 3 - Moderate (ad-hoc)

---

## 0. Захват находки (verbatim, из device-sweep S1035 2026-07-19)

Обнаружено при `/spec-sweep` device-верификации S1035 (edge-gesture-config-dialog) на emulator-5554 (Android 15, build 2.60.7182.317-DEBUG).

**Симптом:**
- Открыть диалог конфигурации краевых жестов (Настройки -> Операции -> «Настроить жесты»).
- Повернуть устройство в ландшафт, **пока диалог уже открыт**.
- Раскладка деградирует до одной колонки: схема на всю ширину сверху, вкладки под ней, зона и группа «Общие настройки» обрезаны/наезжают.
- Контрпример (корректно): если открыть диалог заново, уже находясь в ландшафте, раскладка правильная - схема слева, `header/tabs/zone/general` в одной правой колонке.

**Причина (гипотеза):** артефакт пересоздания `DialogFragment` при config-change (поворот). `EdgeGestureConfigDialogFragment` пересоздаётся на поворот, но восстановленный диалог не переинфлейтит/не переприменяет ландшафтную двухколоночную раскладку (`layout-land/dialog_edge_gesture_config.xml`) - окно диалога сохраняет портретную геометрию либо теряет состояние выбора layout-варианта. Смежные паттерны в памяти: configChanges-no-recreate (S-streams), BaseActivity-posts-setupViews, values-swNNNdp-shadows-land.

**Scope:** вне критериев готовности S1035 - те описывают установившуюся ландшафтную раскладку (при свежем открытии в ландшафте выполняется, S1035 Verified 2026-07-19). Здесь отдельный failure-mode: устойчивость к config-change при открытом диалоге. Возможно, общий паттерн для полноэкранных `DialogFragment` с раздельными `layout/` + `layout-land/`, а не только этого диалога - проверить при ресёрче.

**Evidence:** `temp/S1035/landscape_dialog_a11y_after_rotate.txt` (single-column geometry после поворота) против `temp/S1035/landscape_dialog_a11y_fresh.txt` (корректная двухколоночная при свежем открытии).

**Severity:** низкая (P3) - пользователь поворачивает устройство при открытом конкретном диалоге настроек; данные не теряются, повторное открытие исправляет.

## 1. Проблема

Полноэкранный `DialogFragment` конфигурации краевых жестов не переживает поворот экрана при открытом диалоге: восстановленный после config-change экземпляр рендерит одноколоночную (портретную) раскладку в ландшафте вместо ландшафтной многоколоночной, с обрезкой контента зоны и общей группы.

---

## 2. Корневая причина

Подтверждено по коду (device-free). `SettingsActivity` (host диалога) объявляет
`android:configChanges="orientation|screenSize|keyboardHidden"`
(`app_v2/src/main/AndroidManifest.xml:255`). При повороте Activity НЕ
пересоздаётся - Android шлёт `onConfigurationChanged` вместо recreate. Следствие
для открытого `EdgeGestureConfigDialogFragment`:

- Фрагмент не пересоздаётся; его `onCreateView` повторно не вызывается.
- Уже надутое view (портретный `layout/dialog_edge_gesture_config.xml`, надутый
  при открытии в портрете) остаётся как есть - квалификатор `layout-land/`
  никогда не переприменяется.
- `onStart` тоже не перезапускается, но он лишь ставит окну `MATCH_PARENT` (окно
  на весь экран). Поэтому окно полноэкранное, а КОНТЕНТ - портретный
  одноколоночный. Точно совпадает с симптомом (схема на всю ширину сверху,
  вкладки под ней, зона/общие обрезаны).

Контрпример подтверждает: свежее открытие в ландшафте надувает `layout-land/` в
`onCreateView` -> корректная двухколоночная раскладка.

Это общий класс дефекта для полноэкранных `DialogFragment` с раздельными
`layout/` + `layout-land/`, хостящихся в Activity с `configChanges`-обработкой
поворота (прецедент `DefaultAppsDialogFragment`, S1035 §4) - не уникально этому
диалогу.

---

## 3. Исправление

Направление. Диалог должен реагировать на смену конфигурации, которую глотает
host-Activity. Fragment получает `onConfigurationChanged`, когда его Activity
обрабатывает configChanges. Кандидат:

- Переопределить `onConfigurationChanged(newConfig)` в
  `EdgeGestureConfigDialogFragment`; при смене ориентации пересобрать view
  (teardown binding -> re-inflate конфиг-корректным inflater ->
  `manager.setup()` / `render()`), заново применить window-params, сохранив
  состояние выбора (вкладка/зона/скролл).
- Либо общий базовый full-screen `DialogFragment`, переинфлейтящий контент на
  orientation-change (покрывает и `DefaultAppsDialogFragment`).

**Реализация отложена (device-gated).** Правка в известно-хрупкой области (поворот
+ re-inflate `DialogFragment` in-place + сохранение состояния). Единственная
верификация - наблюдение корректной двухколоночной раскладки И сохранения
состояния после поворота на устройстве (§4). Устройство офлайн; слепая правка
re-inflation рискованна и непроверяема. Реализовать в device-сессии, итеративно
сверяясь.

### 3.4 Реализовано 2026-07-31 (/spec-next round 5, device-сессия)

Отсрочка снята: `emulator-5556` онлайн, правка сделана и проверена итеративно, как §3 и требовал.

Взят первый вариант - `onConfigurationChanged` в самом фрагменте. Общий базовый класс для
полноэкранных диалогов (второй вариант §3) не заводился: пока это один подтверждённый случай,
а `DefaultAppsDialogFragment` никто не измерял.

Три детали, которые определили форму правки:

- **`manager` перестал быть `by lazy`.** Он захватывает `binding`, поэтому после переинфляции
  оставался бы менеджером видов, которых уже нет на экране. `by lazy` не сбрасывается - стал полем
  с фабрикой.
- **Сборщик `collectOnLifecycle` обращается к полю, а не к экземпляру.** Он регистрируется один раз
  и живёт по `viewLifecycleOwner`, который при подмене контента не перезапускается. Захвати он
  менеджер - продолжил бы кормить мёртвый. Это несущая деталь, вынесена в комментарий.
- **`onStart` тоже не повторяется.** Параметры окна, клавиатурный делегат и фокус вынесены в
  `applyDialogChrome()` и вызываются из обеих точек.

### 3.5 Дефект, внесённый самой правкой, и его устранение

Первая версия проходила всё статическое и выглядела готовой: сборка зелёная, detekt чистый,
раскладка после поворота двухколоночная, обе пробы в логе, обратный поворот возвращал исходную
геометрию. И тем не менее была неполной.

Сравнение дампов показало: до поворота активна зона `blockZoneRightBottom`, после -
`blockZoneLeftTop`. Выбор вкладки молча сбрасывался на первую, а §4 требует его сохранения
отдельным пунктом.

Причина: выбранная зона живёт не в менеджере, а внутри самого `TabLayout`, который переинфляция и
заменяет. Из кода это не видно - видно только по геометрии на устройстве. Исправлено чтением
`selectedTabPosition` до разрушения и восстановлением после `setup()`.

Формально это дефект, внесённый этим тикетом: до правки диалог поворот не переживал вовсе, терять
было нечего. Введение переинфляции создало новый способ потерять состояние - и его поймал заранее
написанный критерий §4.

## 4. Проверка

- On-device (device-gated): открыть диалог краевых жестов в портрете -> повернуть
  в ландшафт -> раскладка становится двухколоночной (схема слева,
  header/tabs/zone/general справа), контент не обрезан, состояние выбора
  сохранено. Обратный поворот -> корректная портретная. Probe `S1123:` в логе
  подтверждает прохождение `onConfigurationChanged`-пути.
- Регресс: свежее открытие в ландшафте по-прежнему корректно (S1035 Verified).
