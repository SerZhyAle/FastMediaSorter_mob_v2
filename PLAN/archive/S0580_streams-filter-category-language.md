## 1. Проблема

На экране Трансляций фильтрация работает только по одному признаку - тематике (topic). Хотя данные каждой трансляции уже несут признаки категории и языка, а слой состояния умеет фильтровать по ним, пользователь не может выбрать эти фильтры из интерфейса. Кнопка фильтра выглядит общей, но по факту скрывает только тематику, поэтому отбор по категории и языку для пользователя не существует.

Каталог трансляций большой, и языков в нём много. Пользователю нужно отбирать трансляции по категории и/или языку, причём оба списка длинные - прокручивать их неудобно. Нужен выбор с вводом текста, который сужает список по мере набора (например «Ukr» → «Ukrainian»).

---

## 2. Цели

1. Пользователь может отфильтровать список трансляций по языку.
2. Пользователь может отфильтровать список трансляций по категории.
3. Категорию и язык можно применять совместно (оба фильтра активны одновременно).
4. Выбор категории и языка выполняется через поле с вводом текста, которое сужает варианты по набранной подстроке (совпадение по началу и по вхождению, регистронезависимо).
5. У языков, где это применимо, рядом с названием отображается флаг - по аналогии с уже существующим выбором языка в переводчике.
6. Активные фильтры наглядно видны, и пользователь может быстро их сбросить.

**Non-goals:**

- Не меняем источник и формат загрузки каталога трансляций (отдельный процесс импорта).
- Не добавляем фильтрацию по новым, ещё не существующим в данных признакам.
- Не трогаем воспроизведение трансляций и инлайн-плеер.
- Не вводим перевод содержимого трансляций - речь только об отборе по языковому признаку записи.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. По возможности переиспользовать уже реализованный в переводчике выбор языка с флагами и поиском по тексту, а не строить второй такой же компонент с нуля.
2. Поле выбора должно работать как дроп-даун с поиском, чтобы не листать длинный список.
3. Поддержать сценарий, когда у трансляции язык не указан - пользователь должен понимать, попадают такие записи в выборку или нет.

### 3.2 Жёсткие ограничения

- **Flavor:** функция актуальна только для вариантов сборки, где включён экран Трансляций (standard, legacy, noLegal); в lite и photos экран отсутствует и фичи там нет. Реализация следует `dev/FLAVOR_DEVELOPMENT_RULES.md`: фильтр трансляций не должен тянуть зависимости, доступные только при включённом переводчике; общий выбор-с-поиском выносится за интерфейс в `src/main/`, а специфика переводчика остаётся изолированной.
- **API level:** без API-специфики; учесть, что отрисовка флага уже имеет обходной путь для старых API (минимум сборки legacy - 23), переиспользовать существующее решение, не вводить новый API-зависимый код.
- **Wear OS:** не затрагивается.
- **Производительность:** фильтрация выполняется над списком в памяти; ввод текста в поле поиска не должен подвешивать UI - отбор вариантов идёт без обращения к сети и диску.
- **Совместимость данных:** колонка языка у трансляций уже существует, новой миграции хранилища не требуется. Значение языка приходит из внешнего каталога свободной строкой - сопоставление с компонентом выбора (флаги/локализованные названия) должно деградировать мягко, если код языка не распознан.
- **Локализация:** все новые видимые строки (заголовки полей, плейсхолдеры поиска, пустые состояния, подпись «язык не указан», подпись сброса) - EN/RU/UK обязательно.
- **Доступность:** поля и элементы списка доступны с клавиатуры, D-pad/TV и мыши; активный фильтр различим не только цветом; touch target соблюдён.

### 3.3 Owner inputs (Approval gate)

- **Flavor scope:** standard, legacy, noLegal (где включён экран Трансляций); lite и photos - вне объёма, экран там отсутствует.
- **UI placement contract:** выбор категории и языка вызывается с экрана Трансляций из элемента управления фильтром; конкретная форма (расширение существующего диалога фильтра против отдельных полей/чипов) - предмет §6, решается до реализации через `/ui-clarify`.
- **Accessibility:** клавиатура + D-pad/TV + мышь, не-цветовое отличие активного фильтра, корректные focus-порядок и contentDescription для полей поиска.
- **Localization:** EN/RU/UK для всех новых строк фильтра, обязательно.
- **Communication policy:** новые строки (плейсхолдер поиска, пустое состояние «ничего не найдено», подпись «язык не указан») проходят тон-чеклист `docs/COMMUNICATION_POLICY.md` перед интеграцией.
- **Data compatibility:** опираемся на существующую колонку языка; формат значения в каталоге уточняется в §6 (item 1) и определяет глубину сопоставления с выбором-с-флагами.
- **Validation level:** сборка целевого варианта (standard) + ручная проверка на устройстве отбора по категории, по языку и совместно; решение по null-языку проверяется явно.
- **Owner sign-off:** 2026-06-21.
- **Related tickets:** none.

## 4. Контекст текущей архитектуры

За экран Трансляций отвечает связка «экран → слой состояния → сценарии наблюдения за источниками → репозиторий → локальное хранилище». Слой состояния уже моделирует фильтр по нескольким признакам (категория, тематика, язык) и вычисляет наборы доступных значений (фасеты) при каждом изменении каталога. Каждая запись трансляции уже хранит признаки категории и языка, причём язык заполняется для записей, пришедших из внешнего каталога.

Проблему из §1 нельзя закрыть «само собой», потому что разрыв находится в слое экрана: элемент управления фильтром выводит только один признак и не вызывает уже существующие точки применения фильтра по категории и языку. Дополнительно, готовый компонент выбора языка с поиском и флагами создавался для переводчика и привязан к его словарю поддерживаемых языков и к подписям возможностей перевода, поэтому его нельзя переиспользовать «как есть» без развязки от специфики переводчика.

## 5. Предлагаемый подход

Экран Трансляций получает полноценный отбор по двум признакам - категории и языку - поверх уже существующих в слое состояния точек фильтрации. UI перестаёт прятать только тематику и начинает выставлять выбор категории и языка. Выбор каждого признака реализуется как поле с вводом текста и подбором вариантов по подстроке.

Компонент «поиск по списку с подбором» выделяется в переиспользуемую роль, не зависящую от переводчика: он принимает множество вариантов и предикат совпадения, а отрисовку названия/флага получает извне. Существующий выбор языка переводчика становится частным применением этой роли (его словарь и подписи возможностей остаются на стороне переводчика), а фильтр трансляций - вторым применением, питающимся языками из самого каталога трансляций.

### 5.1 Основные столпы / модули

- **Расширение UI отбора на экране Трансляций.** Цель: дать выбор категории и языка из интерфейса. Требование: оба фильтра применяются к точкам фильтрации в слое состояния; активные фильтры видны и сбрасываются; доступен переключатель режима совмещения И/ИЛИ.
- **Режим совмещения фильтров.** Цель: пользователь выбирает, пересекать (И) или объединять (ИЛИ) фильтры категории и языка. Требование: слой состояния поддерживает оба режима; записи без указанного языка остаются в выборке при активном языковом фильтре.
- **Переиспользуемый выбор-с-поиском.** Цель: единый компонент ввода-с-подбором для длинных списков. Требование: не зависит от переводчика, принимает произвольное множество вариантов и способ их отображения; подбор по началу и вхождению, регистронезависимо.
- **Языковое отображение вариантов.** Цель: показывать флаг и читаемое название языка там, где это возможно. Требование: переиспользует уже существующую логику флагов/названий; для нераспознанных кодов языка деградирует до простого текста без ошибки.
- **Источник вариантов фильтра.** Цель: списки категорий и языков берутся из реального каталога. Требование: варианты строятся из фактических значений записей, включая решение по записям без языка (см. §6).

### 5.2 Потоки данных и событий

- Каталог трансляций → слой состояния вычисляет наборы доступных категорий и языков (фасеты) из полного списка записей.
- UI открывает выбор-с-поиском, передавая ему набор вариантов соответствующего признака и способ отображения; пользователь набирает текст → список сужается по подстроке.
- Выбор варианта → UI сообщает слою состояния выбранную категорию/язык → слой состояния пересобирает отфильтрованный список → экран обновляется.
- Сброс фильтра → слой состояния возвращает полный (с учётом прочих активных фильтров) список.

### 5.3 Точки расширяемости

- Роль «выбор-с-поиском» остаётся открытой к новым применениям (другие длинные списки в приложении), поэтому её контракт не привязывается к языкам или трансляциям.
- Способ отображения варианта (текст, текст+флаг, текст+бейдж) передаётся снаружи, чтобы добавление новых видов подписи не меняло сам компонент.
- Развязка от переводчика делается так, чтобы фильтр трансляций работал в вариантах сборки без включённого переводчика (через интерфейс в общем коде + изоляцию специфики переводчика по `dev/FLAVOR_DEVELOPMENT_RULES.md`).

## 6. Открытые вопросы / Research items

1. **Формат значения языка в каталоге трансляций**
   - **Вопрос:** в каком виде хранится язык в внешнем каталоге - код BCP-47 / ISO 639-1 (например `uk`) или отображаемое имя (`Ukrainian`)?
   - **Решение:** язык в каталоге - строчное английское название (`ukrainian`, `english`), иногда несколько через запятую (`russian,ukrainian`). Фасет языков должен разбивать значение по запятой и предлагать отдельные языки; сопоставление с флагом - через нормализацию названия в код языка с мягкой деградацией до текста. Миграция хранилища не нужна (колонка `country` в каталоге есть, но не сохраняется и не используется).
   - **Артефакт:** `PLAN/S0580_streams-filter-category-language/research/01__catalog-language-format.md`
   - **Статус:** Resolved (ресёрч, 2026-06-21)

2. **Семантика совместного фильтра: И против ИЛИ**
   - **Вопрос:** при выбранных и категории, и языке - показывать пересечение (категория И язык) или объединение (категория ИЛИ язык)?
   - **Решение:** переключатель режима И/ИЛИ в UI фильтра - пользователь сам выбирает пересечение или объединение. Слой состояния расширяется поддержкой режима совмещения.
   - **Статус:** Resolved (владелец, 2026-06-21)

3. **Степень переиспользования выбора языка из переводчика**
   - **Вопрос:** адаптировать существующий выбор языка под общий случай или ввести отдельный обобщённый выбор-с-поиском, частным случаем которого станет языковой?
   - **Решение:** ввести отдельный обобщённый выбор-с-поиском (вход - список вариантов с опциональным флагом + текущий выбор + колбэк), переиспользовать в нём существующую отрисовку флага. Фильтр трансляций - его первое применение. Существующий выбор языка переводчика в этом тикете не переписывается (в нём специфика OCR-подписей); его перевод на общий компонент - отдельная задача (см. §10).
   - **Статус:** Resolved (ADR-1, 2026-06-21)

4. **Поведение для записей без языка**
   - **Вопрос:** трансляции без указанного языка - скрывать при активном языковом фильтре или показывать через явный пункт «язык не указан»?
   - **Решение:** всегда показывать - записи без языка остаются в выборке независимо от активного языкового фильтра, выборка не урезается молча.
   - **Статус:** Resolved (владелец, 2026-06-21)

5. **UI-поверхность для двух фильтров**
   - **Вопрос:** как разместить два независимых фильтра (категория и язык) на экране - расширить текущий диалог фильтра, заменить на чипы активных фильтров или добавить отдельные точки входа?
   - **Варианты:** единый диалог с секциями; чипы/пилюли активных фильтров; раздельные элементы управления.
   - **Решение:** единый диалог по существующей кнопке фильтра - строки «Категория» и «Язык» (каждая открывает выбор-с-поиском), тумблер И/ИЛИ, действие «Сбросить». Активное состояние показывается маркером на кнопке фильтра (форма-точка, различимо не только цветом) плюс сброс внутри диалога; чипов и отдельной строки активных фильтров нет. Маркер - подмена иконки кнопки в рантайме, поэтому правок activity_streams (портрет/ландшафт) не требуется.
   - **Статус:** Resolved (`/ui-clarify`, владелец, 2026-06-21)

## 9. Архитектурные решения (ADR)

**ADR-1: Обобщённый выбор-с-поиском вместо привязки фильтра к компоненту переводчика**

- **Решение:** ввести/выделить переиспользуемую роль «выбор-с-поиском» с внешним отображением варианта; языковой выбор переводчика и фильтр языка трансляций - её применения.
- **Альтернативы:** напрямую переиспользовать выбор языка переводчика; построить отдельный самостоятельный фильтр для трансляций.
- **Почему:** прямой reuse тянет словарь и подписи переводчика и зависимость от его наличия в сборке; отдельный самостоятельный компонент дублирует логику поиска. Общая роль убирает дублирование и сохраняет флейвор-изоляцию.

## 11. Критерии готовности (strategic-level)

1. На экране Трансляций пользователь открывает выбор языка и отбирает трансляции по языку.
2. На экране Трансляций пользователь открывает выбор категории и отбирает трансляции по категории.
3. Категория и язык применяются совместно; пользователь переключает режим И/ИЛИ (§6.2).
4. В поле выбора ввод текста сужает список вариантов по подстроке (например «Ukr» оставляет «Ukrainian»).
5. Для распознанных языков рядом с названием виден флаг; нераспознанные показываются простым текстом без сбоя.
6. Активные фильтры видны пользователю и сбрасываются; записи без указанного языка остаются в выборке при активном языковом фильтре (§6.4).
7. Функция доступна в standard/legacy/noLegal и отсутствует в lite/photos без сбоев сборки.
