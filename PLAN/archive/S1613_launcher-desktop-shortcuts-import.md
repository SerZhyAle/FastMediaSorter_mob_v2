## 1. Проблема

Когда приложение впервые становится домашним экраном, а также после «Сбросить настройки лаунчера», рабочий стол собирается заново только из фиксированного стартового набора, привязанного к профилю устройства. Всё, что пользователь получил туда позже, исчезает - в первую очередь ярлыки, которые другие приложения сами закрепили на нашем столе через системный запрос закрепления.

Данные для восстановления при этом никуда не делись: система продолжает числить эти ярлыки закреплёнными именно нашим лаунчером, и лаунчер вправе их прочитать. Их просто никто не читает, поэтому сброс, который пользователь понимает как «вернуть стандартный стол», на деле означает «потерять ярлыки, которые сюда положили другие приложения, и закрепить каждый заново вручную».

Область - домашний экран приложения: посев рабочего стола и сброс настроек лаунчера.

---

## 2. Цели

1. После сброса настроек лаунчера ярлыки, ранее закреплённые на столе другими приложениями, появляются на нём снова - без обхода этих приложений и повторного закрепления.
2. Первое появление домашнего экрана и сброс дают один и тот же предсказуемый результат: пользователь видит стартовый набор плюс всё, что система умеет вернуть.
3. Импорт не создаёт мёртвых плиток: ярлык удалённого, отключённого или больше не публикуемого приложения на стол не попадает.

**Non-goals:**

- Импорт раскладки чужого лаунчера (штатного, вендорского, стороннего). Публичного API для чтения чужого рабочего стола нет, и §5 объясняет, почему обходного пути тоже нет.
- Импорт виджетов и обоев - только ярлыки.
- Сообщение пользователю о числе восстановленных ярлыков. Новый элемент на домашнем экране - решение о размещении, которого владелец не принимал, а конвейер такие решения не выдумывает (§6.3).
- Wear OS: у часов нет домашнего экрана этого вида.
- Экспорт и перенос стола между устройствами.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Импорт срабатывает сам, без вопроса пользователю в момент первого показа стола - домашний экран не место для диалога.
2. Восстановленные ярлыки узнаваемы на столе по подписи, которую дало приложение-издатель, а не по имени пакета.
3. Порядок стартового набора не ломается: импортированное добавляется после него, а не вперемешку.

### 3.2 Жёсткие ограничения

- **Flavor:** только сборки с `SUPPORT_LAUNCHER` (`docs/FLAVOR_MATRIX.md`: standard, noLegal). Код живёт в наборе исходников домашнего экрана и в общих слоях, доступных всем сборкам, но поведение включено только там, где лаунчер вообще существует.
- **API level:** чтение закреплённых ярлыков доступно с API 25; минимальный уровень тех сборок, где лаунчер включён, равен 26, поэтому отдельная ветка для старого API не нужна. `legacy` с его 23 лаунчер не собирает.
- **Права:** источник импорта отвечает данными только пока приложение реально удерживает роль домашнего экрана; роль может быть отозвана между проверкой и вызовом, поэтому пустой ответ - штатное состояние, а не ошибка.
- **Wear OS:** не затрагивается.
- **Производительность:** импорт выполняется внутри уже существующего посева стола, на фоновом потоке, до первой отрисовки сетки. Запрос к системе делается только когда стол действительно будет засеян - засеянный стол не платит за него.
- **Совместимость данных:** новых сущностей хранения не появляется; импортированный ярлык укладывается в существующую ячейку стола с уже существующим видом команды «закреплённый ярлык». Миграции нет.
- **Локализация:** новых пользовательских строк не появляется, переводить нечего.
- **Доступность:** восстановленная плитка ничем не отличается от закреплённой вручную - та же цель касания, та же подпись для скринридера, то же длинное нажатие.
- **Интерфейс:** ни один экран, разметка или элемент управления не меняется. Изменение целиком лежит в слоях данных и предметной области.

### 3.3 Owner inputs (Approval gate)

- **Flavor scope:** standard и noLegal - те и только те сборки, где `SUPPORT_LAUNCHER` включён. В lite, photos, legacy, vr изменение неактивно.
- **API level constraints:** без отдельной ветки. Нижняя граница лаунчера 26 выше требуемого 25.
- **Data compatibility:** без миграции. Импортированный ярлык - обычная ячейка стола существующего вида, отличается только происхождением.
- **Localization:** n/a - новых пользовательских строк нет.
- **UI placement contract:** n/a - ни один элемент интерфейса не добавляется и не переносится. Импортированные ярлыки укладывает существующий упаковщик сетки после стартового набора, отдельно для портретной и ландшафтной раскладок, тем же правилом, по которому уже сейчас ложится стартовый набор.
- **Accessibility:** новых элементов управления нет; восстановленная плитка наследует поведение закреплённой.
- **Validation level:** сборка standard debug плюс проверка на устройстве - роль домашнего экрана, закрепление ярлыка, сброс, повторное появление ярлыка.
- **Owner sign-off:** не получен. Объём §3.3 заполнен конвейером при авто-одобрении, а не владельцем; спорны решения §6.2 и §6.3.

## 4. Контекст текущей архитектуры

Рабочий стол лаунчера засевается один раз на ориентацию: сценарий посева спрашивает профиль устройства, собирает стартовый набор как чистые данные, раскладывает его собственным упаковщиком и отдаёт репозиторию, который вставляет ячейки только в пустую раскладку. Повторный вызов ничего не делает, пока в состоянии стола взведены флаги «засеяно».

Сброс настроек лаунчера намеренно не пересевает стол сам: он чистит ячейки, закрепления панели задач, журнал запусков, статистику и лаунчерные поля настроек, а вместе с состоянием стола снимает и флаги «засеяно». Геометрию сетки знает только сам домашний экран в момент отрисовки, поэтому пересев происходит на следующем показе стола через тот же сценарий посева. Из этого следует главное для данной задачи: «первое объявление» и «сброс» - для механизма посева одно и то же событие, и обе цели §2 закрываются одной точкой изменения.

Чего сейчас нет: посев знает только фиксированный список кандидатов - несколько известных пакетов, которые проверяются на присутствие. Ни одного источника, который спросил бы систему, что она сама помнит про этот стол, в сценарии посева не участвует. При этом seam к системному сервису лаунчера в проекте уже есть: через него принимаются запросы закрепления от других приложений и проверяется живость закреплённого ярлыка перед запуском. Он умеет спрашивать про конкретный пакет и конкретный ярлык, но не умеет перечислить всё закреплённое разом.

## 5. Предлагаемый подход

Импорт - это ещё один вклад в уже существующий посев, а не новый сценарий рядом с ним. Посев перестаёт быть «стартовый набор», а становится «стартовый набор плюс то, что удалось вернуть», и обе ветки укладываются одним и тем же упаковщиком, чтобы ячейки гарантированно не пересекались.

Почему именно так, а не «импорт при сбросе»: сброс не знает ширины сетки той ориентации, которую устройство ещё ни разу не показывало, и по этой причине уже отказался пересевать стол сам. Импорт, привязанный к сбросу, унаследовал бы ровно ту же поломку.

Почему нельзя импортировать чужой лаунчер: раскладка чужого домашнего экрана - его приватные данные, публичного доступа к ним нет. Системный флаг «показать ярлыки, закреплённые любым лаунчером» существует, но работает лишь при системном разрешении, которого нет в публичном наборе платформы и которое обычному приложению не выдаётся; без него флаг молча игнорируется. Проверено по публичному описанию платформы уровня 36. Поэтому единственный честный источник - то, что система числит за нашим собственным лаунчером.

### 5.1 Основные столпы / модули

**5.1.1 Источник импорта.** Расширение существующего seam к системному сервису лаунчера: перечислить всё, что числится закреплённым за этим лаунчером, по всем пакетам сразу, а не по одному запрошенному. Только чтение. Без роли домашнего экрана возвращает пусто. Отключённый или неопубликованный ярлык отсеивается здесь же, чтобы дальше по потоку мёртвая плитка не дошла - это тот же критерий живости, по которому уже сейчас гасится закреплённая ячейка перед запуском.

**5.1.2 Слияние с посевом.** Сценарий посева получает второй список вкладов. Стартовый набор идёт первым и сохраняет свой порядок, импортированное добавляется следом и раскладывается тем же упаковщиком в свободные слоты. Дубли отсекаются по цели ячейки: ярлык, который стартовый набор и так поставил, второй раз не появляется.

**5.1.3 Инвариант сброса.** Сброс лаунчера обязан продолжать чистить ячейки стола и не трогать системную запись о закреплении - именно она и есть источник импорта. Это записывается как явный пункт инвентаря сброса, потому что «освободить закрепления» выглядит логичным дополнением уборки и молча уничтожило бы всю функцию.

**5.1.4 Тишина.** Восстановление ничего не сообщает: вернувшийся ярлык виден сам по себе, и это ровно то, чего пользователь ждал от сброса. Любое сообщение - новый элемент домашнего экрана, то есть решение о размещении, принимать которое вправе только владелец (§6.3).

### 5.2 Потоки данных и событий

- Первый показ домашнего экрана -> сценарий посева -> профиль даёт стартовый набор, источник импорта даёт восстановленное -> упаковщик кладёт оба списка в сетку -> репозиторий вставляет ячейки в пустую раскладку -> состояние стола помечается засеянным.
- Настройки -> сброс лаунчера -> ячейки и флаги «засеяно» сняты, системная запись о закреплении не тронута -> следующий показ домашнего экрана повторяет тот же поток целиком.
- Отсутствие роли домашнего экрана -> источник импорта возвращает пусто -> посев ведёт себя ровно как сегодня.

### 5.3 Точки расширяемости

- Список вкладов в посев остаётся открытым: следующий источник (например, восстановление стола из резервной копии приложения) добавляется как ещё один вклад, не трогая ни стартовый набор, ни упаковщик.
- Критерий отсева мёртвых целей остаётся в одном месте, чтобы новый вид ячейки получил его бесплатно.

## 6. Открытые вопросы / Research items

1. **Живучесть системной записи о закреплении при смене домашнего экрана**
   - **Вопрос:** сохраняет ли система список ярлыков, закреплённых нашим лаунчером, после того как пользователь временно сделал домашним другой лаунчер и вернулся обратно?
   - **Варианты:** запись переживает смену роли - импорт работает и в этом сценарии; запись очищается вместе с потерей роли - импорт покрывает только сброс настроек внутри одной установки.
   - **Нужно выяснить:** на устройстве закрепить ярлык, сменить домашний экран на системный, вернуть наш, прочитать список.
   - **Статус:** Resolved - на проектирование не влияет и реализацию не задерживает. Импорт читает системную запись, какова бы она ни была: переживёт смену роли - выигрыш шире, не переживёт - остаётся ветка сброса внутри одной установки, ради которой задача и заведена. Наблюдение перенесено в проверку на устройстве (§3.3 Validation level) отдельным шагом «сменить домашний экран туда-обратно», где оно измеряется бесплатно.

2. **Объём импорта на самом первом запуске**
   - **Вопрос:** на первом запуске закреплённых ярлыков ещё нет по определению - должен ли «импорт» на этом шаге подхватывать что-то ещё, например инвентарь установленных приложений?
   - **Варианты:** ничего сверх стартового набора; полный инвентарь приложений; ограниченный набор по признаку присутствия.
   - **Нужно выяснить:** ожидание владельца против принятой практики лаунчеров.
   - **Статус:** Resolved - ничего сверх стартового набора. Полный инвентарь установленных приложений на столе дублирует список приложений и делает первый экран нечитаемым; стартовый набор уже отбирает кандидатов по присутствию пакета. На первом запуске импорт корректно возвращает пусто, и это не дефект, а определение: возвращать нечего. Вся ценность задачи лежит на ветке сброса. Решение дешёво обратимо - обратное потребует лишь ещё одного вклада в посев (§5.3).

3. **Сообщение о числе восстановленных ярлыков**
   - **Вопрос:** нужно ли говорить пользователю, сколько ярлыков вернулось после сброса?
   - **Варианты:** молчать; недиалоговое сообщение на домашнем экране; строка в журнале лаунчера.
   - **Статус:** Resolved - молчать, и вопрос вынесен из объёма (§2 Non-goals). Сообщение - новый элемент домашнего экрана, а решения о размещении элементов интерфейса принимает владелец: догаданное размещение остаётся крупнейшим классом правок. Возврат ярлыка виден сам по себе, поэтому молчание не скрывает от пользователя ничего. Захотеть сообщение можно отдельным тикетом, ничего в §5 для этого не переделывается.

## 8. Влияние на пользователя (docs/FEATURES)

Сброс настроек лаунчера перестаёт стирать ярлыки, которые другие приложения закрепили на домашнем экране: после сброса они возвращаются на стол сами.

## 9. Архитектурные решения (ADR)

**ADR-1. Импорт живёт в посеве стола, а не в сбросе.** Сброс не знает геометрии сетки той ориентации, которую устройство ещё не показывало, и по этой причине уже отказался пересевать стол; импорт, привязанный к сбросу, унаследовал бы ту же поломку. Посев вызывается на первом показе стола, то есть покрывает оба триггера из §2 одной точкой.

**ADR-2. Чужие лаунчеры не импортируются.** Их раскладка приватна, а системный флаг «закреплено любым лаунчером» требует разрешения, отсутствующего в публичном наборе платформы, и без него молча игнорируется. Единственный источник - то, что система числит за нашим лаунчером.

**ADR-3. Источник импорта - расширение существующего seam, а не новый класс рядом.** Проверки роли, обработка отзыва роли и критерий живости ярлыка уже живут там; второй вход к тому же системному сервису означал бы две копии этих правил и два места, где они разойдутся.

## 11. Критерии готовности (strategic-level)
