## Objective

Persist the results of manual measurements in Room with a size cap, and serialise them to a shareable text file. One schema change, isolated in its own phase.

---

## Plan corrections - re-planned 2026-08-08, phase unblocked

The phase was blocked the same day by `/spec-dev` on two stale premises; both are re-derived against the
working tree below and written into the steps. Nothing had been started or written when it blocked.

1. **Schema hop re-derived: 48 -> 49, not 46 -> 47.** `AppDatabase.kt` reads `version = 48` - other tickets
   bumped the schema after this plan was authored, and `MIGRATION_46_47` / `MIGRATION_47_48` already exist.
   Following the original text would have moved the database backwards and duplicated an existing hop. The
   new hop is `MIGRATION_48_49`.
2. **The migration lives in its own file, not in `AppDatabase.kt`.** Every hop since 44 follows one shape:
   a `MigrationNNToMM.kt` file in `data/local/db/` holding private `SCHEMA_VERSION_FROM` / `SCHEMA_VERSION_TO`
   constants and one top-level `val`, registered by import plus a list entry in `core/di/DatabaseModule.kt`.
   `AppDatabase.kt` itself gains only the entity, the version and the DAO accessor.
3. **The binding site is `di/NetworkMonitorDataModule.kt`.** `com.sza.fastmediasorter.di.NetworkMonitorModule`
   is declared by `src/networkMonitor` and `src/networkMonitorDisabled`, and every flavor mounts exactly one
   of them, so no such file exists in `src/main` to modify. Phase 02 already created the `src/main` module
   under the non-colliding name; this phase binds into it.
4. **The hop gets an instrumented migration test.** Each of the last five hops carries an
   `AppDatabaseMigrationNNToMMTest.kt` under `src/androidTest`, which is what proves the Done Criterion "a
   pre-existing installation upgrades without data loss". Added as step 03.6.

### Step 03.1 - Define the measurement entity and DAO

**Files:** `data/local/db/NetworkMeasurementEntity.kt`
**Depends on:** - start of phase

**Prompt for developer:**

> Define `NetworkMeasurementEntity` with an autogenerated id, a timestamp, a measurement kind (speed test, resource check, external IP, subnet scan), the network label the measurement was taken on, a numeric result set (down Mbps, up Mbps, latency ms - all nullable), a short text result and a success flag. Add `NetworkMeasurementDao` in the same file with insert, an observed newest-first query, delete-all, and a delete-older-than-the-newest-N statement. Store no credentials and no external IP address in a column that survives beyond the row's own text result.

**Why:**

Strategic §6.9 puts the results of manual measurements in a Room table with automatic trimming, and §3.2 keeps secrets out of storage, so the shape of the row is what enforces both.

### Step 03.2 - Bump the database and add the migration

**Files:** `data/local/db/Migration48To49.kt`, `data/local/db/AppDatabase.kt`, `core/di/DatabaseModule.kt`
**Depends on:** Step 03.1

**Prompt for developer:**

> Add `Migration48To49.kt` in `data/local/db/` following the shape of the neighbouring `Migration47To48.kt`: private `SCHEMA_VERSION_FROM` / `SCHEMA_VERSION_TO` constants, the `CREATE TABLE IF NOT EXISTS` statement as a private const, and one top-level `val MIGRATION_48_49`. The migration only creates the measurement table - it alters no existing table, so no copy-and-rename. In `AppDatabase.kt` register `NetworkMeasurementEntity` in the `@Database` entity list, raise `version` from 48 to 49 and add the DAO accessor. In `core/di/DatabaseModule.kt` add the import and the list entry for `MIGRATION_48_49`. Do not rename or edit any prior migration.

**Why:**

Strategic §3.2 requires the history to survive restarts, and an added entity without a migration crashes every existing installation on first launch.

## Phase-boundary audit - 2026-08-08

Layers 1, 2 and 4 of `docs/CODE_AUDIT_PROTOCOL.md`; Layer 3 is not engaged, the phase registers no listener and holds no view.

- Layer 1 - PASS. Layering is `UseCase -> Repository -> DAO` with the domain model in `domain/model/networkmonitor/` and the Room entity confined to `data/local/db/`. Naming matches the project's `NounRepository` / `VerbNounUseCase` forms, both new Hilt bindings are deliberately `@Singleton`, and no file approaches the size rule.
- Layer 2 - PASS. No `GlobalScope`, no hardcoded dispatcher in business logic (the use case takes the injected `@IoDispatcher`), and the export's broad catch calls `rethrowIfCancellation()` before it logs, so cancellation is not swallowed.
- Layer 4 - one **P2**, fixed in-phase. `observeHistory()` returned the Room `Flow` without `distinctUntilChanged`, which the protocol's Room checklist names explicitly: Room invalidates per table, and `record()` writes twice inside one transaction, so a trim that deleted nothing would re-emit an identical list. Fixed by `.distinctUntilChanged()`; the retention test re-ran green afterwards. Everything else on that checklist holds - the DAO is `suspend`/`Flow` only, the insert and the trim share one transaction, `ORDER BY takenAtMillis` is indexed, the query is bounded by the 200-row cap itself, and the schema change ships both a migration and a migration test with no destructive fallback.

Document-registry loop: `dev/TECH_REQUIREMENTS.md` (area `architecture`) and `docs/DEV_OPS.md` (area `developer-operations`) were the affected records and both were updated to schema 49. Their siblings were grepped for a restated schema version and none carries one, so none needed the same edit. Two unregistered documents still state version 41 (`dev/PRODUCT_COMPLEXITY_ASSESSMENT.md`, `dev/handoff/streams-source-spec/02_data_model.md`); they are out of this ticket's scope and are parked as S1516.
