## 1. Проблема

Когда SFTP-сервер отказывает в удалении файла по правам доступа (внутри операции «переместить» — копия прошла, а удаление исходника не дали), приложение показывает обобщённое «Не удалось переместить/удалить файл» без указания причины. Пользователь не понимает, что дело не в приложении и не в сети, а в правах на сервере (например, монтирование только на чтение или чужой каталог) — и не знает, что предпринять. То же относится к другим SFTP-операциям, упирающимся в отказ прав (удаление, переименование, создание/запись в каталог).

---

## 2. Цели

1. При отказе SFTP-операции по правам доступа на сервере пользователь видит сообщение, явно называющее причину — «сервер отклонил операцию: нет прав» — а не обобщённую неудачу.
2. Сообщение подсказывает направление действий (проверить права на сервере / каталог только для чтения), не уходя в технические детали протокола.
3. Различение «отказ по правам» и прочих причин отказа SFTP (нет сети, файл не найден, диск переполнен, разрыв сессии) — каждая ведёт к своему понятному сообщению, без сваливания в общий «не удалось».
4. В логе причина отказа фиксируется структурированно (код статуса SFTP / класс ошибки), чтобы диагностика не зависела от текста UI.

**Non-goals:**

- Не менять саму логику операций перемещения/удаления/переименования по SFTP — только классификацию ошибок и текст уведомлений.
- Не добавлять автоматический обход (повтор с другими правами, смена владельца и т.п.) — отказ остаётся отказом, меняется только его подача.
- Не трогать другие протоколы (SMB/FTP/WebDAV/Cloud) сверх минимальной унификации формулировок, если она уже есть.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Желательно единое место классификации ошибок SFTP-операций, чтобы и UI-сообщение, и лог брали причину из одного источника.
2. Желательно, чтобы при отказе перемещения по правам было понятно, что копия уже сделана (файл на месте назначения есть), а исходник остался — пользователь не должен думать, что данные потеряны.

### 3.2 Жёсткие ограничения

- **Flavor:** все варианты, где доступен SFTP (та же область, что и остальная SFTP-функциональность).
- **API level:** без API-специфики.
- **Wear OS:** не затрагивается.
- **Производительность:** не критично; классификация ошибки — разбор уже полученного ответа сервера.
- **Совместимость данных:** изменений хранимых настроек/кэшей не требуется.
- **Локализация:** EN/RU/UK — обязательно для всех новых/изменённых пользовательских строк.
- **Доступность:** уведомление об ошибке читается TalkBack; не применимо в части визуальных требований.
- **Тон сообщений:** новые/изменённые строки проходят чек-лист тона из `docs/COMMUNICATION_POLICY.md` (§6) перед интеграцией — спокойная формулировка с указанием причины и следующего шага, не алармовая.

---

## 4. Контекст текущей архитектуры

За операции с файлами по SFTP отвечает слой работы с сетевыми источниками; ошибки операции поднимаются наверх и проецируются в обобщённый результат «успех / неудача с текстом». Сейчас отказ сервера по правам приходит как ошибка протокола с кодом статуса, но на пути наверх этот код теряется — остаётся только факт неудачи, который маппится в один общий пользовательский текст. Точки классификации сетевых ошибок в проекте уже есть (transient/permanent и т.п.), но «отказ по правам» в них отдельно не выделен для SFTP-операций записи/удаления.

---

## 5. Предлагаемый подход

Выделить «отказ по правам сервера» в отдельную категорию исхода SFTP-операции и провести её от места возникновения (ответ сервера) до UI без потери, чтобы UI выбрал понятное сообщение.

### 5.1 Основные столпы / модули

- **Классификация исхода операции.** К существующим категориям результата SFTP-операции добавляется «отклонено сервером — нет прав»; код статуса протокола, означающий отказ прав, маппится именно в неё.
- **Сквозной проброс причины.** Категория исхода доходит до слоя представления операций без сведения к обобщённой неудаче.
- **Выбор сообщения по категории.** Слой представления выбирает текст по категории исхода; для перемещения с уже выполненной копией — отдельная формулировка, поясняющая, что файл скопирован, а исходник не удалён.
- **Диагностический канал.** Лог фиксирует категорию исхода и исходный код статуса протокола одной записью.

### 5.2 Потоки данных и событий

- SFTP-операция → ответ сервера с кодом отказа прав → классификация исхода как «нет прав» → проброс наверх → слой представления выбирает соответствующее сообщение → пользователь видит понятный текст; лог содержит структурированную причину.

### 5.3 Точки расширяемости

- Набор категорий исхода SFTP-операции должен расширяться добавлением новой категории и её сообщения без переписывания маппинга.
- Маппинг «код статуса протокола → категория» — таблица, пополняемая при появлении новых наблюдаемых кодов.

## 6. Открытые вопросы / Research items

1. **Какие именно коды статуса SFTP относить к «нет прав»**
   - **Вопрос:** помимо явного «permission denied» — относить ли сюда смежные коды (например, отказ из-за «операция не поддерживается», «только чтение»).
   - **Нужно выяснить:** какие коды реально приходят от типовых SFTP-серверов в сценариях read-only mount и чужого каталога; не сливать ли часть из них в общую категорию «сервер отклонил операцию» с уточнением в логе.
   - **Статус:** Open — уточняется на этапе тактической реализации.

## 9. Архитектурные решения (ADR)

**ADR-1: «отказ по правам» — отдельная категория исхода операции, а не текст в обобщённой неудаче**

- **Решение:** причина пробрасывается как структурированная категория исхода до UI; текст выбирается на стороне представления.
- **Альтернативы:** прокидывать готовую строку ошибки снизу вверх; оставить как есть.
- **Почему:** структурированная категория позволяет и UI выбрать локализованный текст, и логу зафиксировать причину без парсинга строк; согласуется с уже существующей классификацией сетевых ошибок.

## 11. Критерии готовности (strategic-level)

1. При перемещении файла по SFTP, когда сервер запрещает удаление исходника, пользователь видит сообщение, явно называющее причину (нет прав на сервере) и поясняющее, что копия на месте назначения сделана.
2. При прямом удалении / переименовании по SFTP с отказом по правам — то же понятное сообщение, а не обобщённая неудача.
3. Прочие причины отказа SFTP-операции (нет сети, файл не найден, диск переполнен, разрыв сессии) ведут к своим формулировкам, не сливаясь с «нет прав».
4. В логе на такой отказ есть одна запись с категорией исхода и исходным кодом статуса протокола.
