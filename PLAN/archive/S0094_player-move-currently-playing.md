## 1. Проблема

Когда пользователь инициирует файловую операцию (перемещение, удаление или переименование) над файлом, который в данный момент воспроизводится плеером, приложение не останавливает воспроизведение перед началом операции. Это актуально для всех типов ресурсов: локальных файлов, SMB (Samba), FTP, SFTP и облачных хранилищ (Google Drive, Dropbox и др.). В результате медиа-стрим (файловый дескриптор, сетевой сокет или облачный поток) остаётся открытым, пока файл физически перемещается, удаляется или переименовывается — это приводит к ошибкам ввода-вывода, ложным тостам «ошибка загрузки» и некорректным переходам.

Дополнительные проявления:
- Переход к следующему файлу происходит только после завершения фоновой операции (может занять несколько секунд), хотя с точки зрения пользователя действие должно быть мгновенным.
- Удаление файла ведёт к той же гонке потоков, что и перемещение, но лишено механизма оптимистичной навигации.
- Переименование файла при открытом стриме приводит к IO-ошибке; последующий полный перезапрос списка файлов (`reloadAfterRename`) может нарушить позицию в плейлисте, если сортировка изменила порядок.
- Текущая логика удаления из списка по индексу (а не по пути) ошибочно удаляет неверный файл после оптимистичной навигации.

## 2. Цели

**Общие (все операции, все типы ресурсов):**

1. При инициировании любой операции (move / delete / rename) над текущим файлом воспроизведение немедленно останавливается до начала дисковой/сетевой операции. Стрим закрывается синхронно, на главном потоке.
2. Поведение одинаково для локальных файлов, SMB, FTP, SFTP и облачных хранилищ.
3. Ошибки типа «прерванный поток» (`InterruptedException`, `Pipe closed`, `IOException`), вызванные намеренной остановкой воспроизведения, не приводят к тостам об ошибке.
4. Удаление файлов из списка после операции всегда выполняется по пути (не по текущему индексу), чтобы оптимистичная навигация не удалила неверный файл.

**Специфично для move:**

5. Плеер мгновенно переходит к следующему файлу — пользователь не ждёт завершения переноса.
6. Перемещённый файл исключается из списка по завершении операции в фоне.
7. Если перемещался последний файл — плеер переходит к первому (кольцевая навигация).
8. Если список оказывается пустым после перемещения — плеер закрывается и управление возвращается в Browse.

**Специфично для delete:**

9. Поведение навигации идентично move (оптимистичный переход к следующему файлу до завершения удаления).
10. Если удалялся единственный файл — плеер закрывается.

**Специфично для rename:**

11. После переименования плеер остаётся на том же файле (не переходит к следующему).
12. Путь файла в списке обновляется точечно (in-place) без полного перезапроса списка — сортировка и позиция в плейлисте не нарушаются.

**Non-goals:**

- Отмена уже начатой дисковой операции (undo для перемещения — отдельный тикет).
- Изменение поведения при операции над файлом, который НЕ является текущим (фоновые операции из Browse не затрагиваются).
- Изменение UX диалогов выбора папки назначения и переименования.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Если перемещение завершилось ошибкой, вернуться к перемещавшемуся файлу (если он ещё в списке) или остаться на текущем.
2. На время фоновой операции показывать индикатор прогресса без блокировки воспроизведения следующего файла.

### 3.2 Жёсткие ограничения

- **Flavor:** все флейворы (standard, lite, photos, legacy).
- **API level:** без API-специфики (minSdk 23/26 в зависимости от флейвора).
- **Wear OS:** не затрагивается.
- **Типы ресурсов:** локальные файлы, SMB (SMBJ), FTP (Apache Commons Net), SFTP (SSHJ/JSch), облачные хранилища (Google Drive, Dropbox, MSAL). Механизм остановки воспроизведения (освобождение ExoPlayer) не зависит от типа ресурса. Обнаружение IO-ошибок в `BackgroundMusicManager` покрывает все протоколы через цепочку `IOException`.
- **Производительность:** остановка воспроизведения должна занимать < 50 мс (синхронный вызов на main thread), переход к следующему файлу — стандартный путь навигации без дополнительных задержек.
- **Совместимость данных:** без изменений схемы хранилища.
- **Локализация:** EN/RU/UK — строки ошибок и тостов обязательны во всех трёх локалях.
- **Доступность:** не затрагивается (операция не меняет визуальные элементы управления).

## 4. Контекст текущей архитектуры

Файловые операции (move, delete, rename) инициируются из плеера через слой файловых операций, который выполняет фактическую работу в фоновой корутине, пережившей жизненный цикл Activity. По завершении операции callback уведомляет плеер, который обновляет список файлов во ViewModel и вызывает навигацию. Воспроизведением управляет отдельный компонент (ExoPlayer-обёртка), который получает команду начать воспроизведение нового файла только тогда, когда callback сработает.

Таким образом, между инициированием операции и сменой трека существует окно в несколько секунд, в течение которого ExoPlayer продолжает читать файл через открытый стрим. Это приводит к гонке: локальный файл может быть заблокирован; SMB/FTP/SFTP-сокет остаётся открытым; облачный HTTP-стрим продолжает запрашивать удалённый/переименованный объект. Все эти ситуации завершаются `IOException` с разными обёртками, зависящими от протокола.

Навигационная логика (следующий/предыдущий файл, кольцевой переход) уже реализована во ViewModel-координаторе и корректно обрабатывает пустой список и граничные индексы. Её нужно вызывать в правильный момент (до начала операции, а не после). Слой файловых операций достаточно абстрактен, чтобы добавление pre-operation hook не требовало изменений для каждого протокола в отдельности.

## 5. Предлагаемый подход

### 5.1 Основные столпы

**A. Немедленная остановка воспроизведения (pre-operation, универсально)**
До запуска любой фоновой операции (move / delete / rename): остановить воспроизведение и освободить медиа-ресурс (закрыть стрим). Это устраняет гонку независимо от типа ресурса: локальный файловый дескриптор, SMB/FTP/SFTP-сокет, облачный HTTP-стрим — все освобождаются синхронным вызовом ExoPlayer на главном потоке.

**B. Оптимистичная навигация (pre-move / pre-delete)**
Сразу после остановки воспроизведения — перейти к следующему файлу по стандартному пути навигации. Применяется для move и delete. Для rename — навигации нет, пользователь остаётся на переименованном файле.

**C. Фоновая операция (async)**
Операция (move / delete / rename) выполняется в фоне без изменений в слое использования и протокола.

**D. Пост-операционная сверка (post-move / post-delete)**
По завершении (успех): удалить файл из списка по **пути** (не по текущему индексу). Проверить результирующий список:
- Не пуст → оставаться на текущем файле.
- Пуст → закрыть плеер.

По завершении (ошибка): файл остаётся в списке; тост с точной причиной; текущее воспроизведение не прерывается.

**E. Подавление ложных ошибок ExoPlayer**
`InterruptedException`, `Pipe closed` и иные `IOException`, возникающие при намеренной остановке воспроизведения, не должны порождать тост «ошибка загрузки». Механизм охватывает все протоколы через цепочку `java.io.IOException` в cause chain и диапазон Media3 IO-кодов 2000–2999.

**F. Удаление при воспроизведении (pre-delete)**
Тот же паттерн, что и move (столпы A + B + D), применённый к операции удаления. В том числе: дебаунс двойного нажатия, путь-based удаление из списка, finish() при пустом списке.

**G. Переименование при воспроизведении (pre-rename + in-place update)**
Останавливает воспроизведение перед IO (столп A). После успешного переименования: точечно обновляет путь файла в списке (не перезапрашивает весь список) — сортировочная позиция не нарушается; воспроизведение возобновляется с новым путём на той же позиции в плейлисте.

### 5.2 Потоки данных и событий

```
Move / Delete:
  Пользователь нажимает кнопку операции
  → [Main] Остановить воспроизведение / освободить стрим (все протоколы)
  → [Main] Навигация к следующему файлу (оптимистично)
  → [IO] Начать фоновую операцию
       ↓ успех                    ↓ ошибка
  [Main] Удалить файл из списка  [Main] Тост с ошибкой
         по пути                         (файл остаётся)
         Список пуст? → finish()

Rename:
  Пользователь подтверждает новое имя
  → [Main] Остановить воспроизведение / освободить стрим
  → [IO] Выполнить переименование
       ↓ успех                    ↓ ошибка
  [Main] Обновить путь файла     [Main] Тост с ошибкой
         in-place (по старому            Возобновить воспроизведение
         пути), возобновить             со старым путём
         воспроизведение
```

### 5.3 Точки расширяемости

- Паттерн `onBeforeOperation(filePath)` в `FileOperationCallback` является общим hook-ом для любой будущей файловой операции, где та же гонка теоретически возможна.

## 6. Открытые вопросы / Research items

1. **Поведение при ошибке перемещения**
   - **Вопрос:** Если перемещение завершилось ошибкой, а пользователь уже перешёл на другой файл — надо ли автоматически возвращаться к не-перемещённому файлу или просто показать тост?
   - **Решение:** тихий тост с точной причиной ошибки (из исключения/результата операции), остаться на текущем треке. Файл НЕ удаляется из списка — пользователь может вернуться к нему вручную.
   - **Статус:** Verified

2. **Пре-фетч следующего файла и остановка**
   - **Вопрос:** Если в момент нажатия «Переместить» идёт prefetch следующего файла по сети — нужно ли его отменять или дождаться?
   - **Решение:** не отменять — prefetch продолжается, поскольку мы переходим именно к следующему файлу. Отмена была бы контрпродуктивной.
   - **Статус:** Verified

3. **Audio Service и фоновое воспроизведение при перемещении из Browse**
   - **Вопрос:** Если сервис воспроизводит файл в фоне, а пользователь перемещает этот же файл из Browse (плеер не на экране) — какое поведение сервиса?
   - **Решение:** сервис не получает pre-move сигнал от Browse. Когда сервис обнаруживает, что файл недоступен (IO-ошибка), он тихо переходит к следующему треку без тостов и UI-ошибок. Все ошибки логируются в Timber. Это симметрично поведению при потере сетевого соединения.
   - **Статус:** Verified

## 9. Архитектурные решения (ADR)

**ADR-1: Оптимистичная навигация (до завершения операции)**

- **Решение:** переходить к следующему файлу до завершения перемещения, а не после.
- **Альтернативы:** (а) ждать завершения и тогда переходить (текущее поведение); (б) блокировать UI на время операции.
- **Почему:** пользователь инициировал сортировку — он ожидает мгновенного движения по списку. Ожидание секунд перед сменой трека — плохой UX для быстрого просмотра-сортировки. Блокировка UI неприемлема для сетевых операций.

**ADR-2: Удаление по пути, а не по индексу в пост-сверке**

- **Решение:** идентифицировать перемещаемый файл по его пути (захваченному до начала операции), а не по `currentIndex` в момент завершения.
- **Альтернативы:** удалять по `currentIndex` (текущее поведение).
- **Почему:** к моменту завершения фоновой операции `currentIndex` уже указывает на другой файл (пользователь перешёл). Удаление по индексу удалит неверный файл.

## 11. Критерии готовности (strategic-level)

**Move:**
1. Пользователь нажимает «Переместить» на воспроизводимом аудио/видео-файле (локальный, SMB, FTP, SFTP, облако) — воспроизведение останавливается немедленно, следующий файл начинает играть до того, как тост о начале переноса исчезнет.
2. По завершении переноса перемещённый файл отсутствует в списке; пользователь продолжает слушать текущий трек без прерывания.
3. Если переносился единственный файл — плеер закрывается и отображается Browse.
4. Если переносился последний файл (конец списка) — воспроизводится первый файл.
5. При ошибке переноса — тост с причиной; текущее воспроизведение не прерывается; файл остаётся в списке.

**Delete:**
6. Пользователь нажимает «Удалить» на воспроизводимом файле — воспроизведение останавливается немедленно, следующий файл начинает играть.
7. После удаления единственного файла — плеер закрывается.

**Rename:**
8. Пользователь переименовывает воспроизводимый файл — воспроизведение прекращается перед IO; после успеха плеер возобновляет воспроизведение под новым именем на той же позиции в плейлисте.
9. Позиция в плейлисте не смещается после переименования даже если новое имя меняет алфавитный порядок.

**Все операции:**
10. Логи не содержат `Error reading`, `error_loading_media` и IO-тостов при штатном выполнении операций над воспроизводимым файлом для любого из поддерживаемых протоколов.
