## 1. Проблема

В проект добавлен `docs/CODE_AUDIT_PROTOCOL.md` - протокол аудита кода из 8 слоёв (статика+читаемость, lifecycle+конкурентность, владение памятью, Room/БД, main-thread/старт, производительность, release/R8, механические гейты) с таксономией серьёзности P0-P3 и evidence ladder. Документ есть, но он ничего не меняет сам по себе:

1. **Текущий код по протоколу не прогонялся.** Неизвестно число P0/P1-находок: утечки (несбалансированные `register/unregister`, удержанные `Activity`/`View`, неосвобождённые player/cursor), гонки на общем состоянии, Room-запросы на main-thread, churn на горячих путях. Намерено навскидку: 132 `!!` и 129 точек `release/addListener/removeListener` в `src/main` - это поверхность риска, а не диагноз.
2. **Инфраструктура не принуждает протокол.** Нет `detekt`/`ktlint`, нет `Macrobenchmark`/Baseline Profiles, нет гейта симметрии слушателей, нет custom Android Lint, LeakCanary не подключён к инструментальным тестам.
3. **Правила проекта не кодируют протокол.** В `CLAUDE.md`/`AGENTS.md` нет таксономии серьёзности, правила симметрии `register/unregister`, запрета main-thread Room, требования проверять reflection/DI на минифицированной сборке.

Итог: протокол есть, исполнения и принуждения - нет. Без этого тикета документ останется декларацией.

## 2. Цели

1. **Прогнать текущий код** `app_v2/` и `wear/` по каждому слою протокола; каждую находку классифицировать по таксономии P0-P3 с доказательством на нужной ступени evidence ladder; нетривиальные находки парковать отдельными fix-тикетами (CLAUDE.md 3.1).
2. **Довести инфраструктуру** до уровня, где протокол принуждается механически: статанализ читаемости, гейт симметрии слушателей, custom Lint на архитектурные правила, перф-харнесс, LeakCanary в инструментальных тестах.
3. **Зашить правила протокола** в `CLAUDE.md`/`AGENTS.md` и dev-доки, чтобы новый код проходил аудит by construction, а не постфактум.

**Non-goals:**

- Переписывание функциональности или рефакторинг ради рефакторинга - меняем только то, что протокол помечает как риск.
- UI/дизайн-ревью, копирайт - вне области протокола.
- Продуктовые приоритеты.

**Дочерние тикеты (Done зонтика = все дочерние Verified):**

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Фокус на чистом, быстром, читаемом коде без утечек памяти - не на UI.
2. Использовать уже существующие в репозитории инструменты (`measure-hotspots.ps1`, `audit-shared-state-writers.ps1`, гейты `scripts/quality/`), а не плодить параллельные.
3. Предпочесть механическое принуждение (гейт/lint/порог) разовым ревью там, где находка повторяема.

### 3.2 Жёсткие ограничения

- **Модули:** `app_v2/` и `wear/`. Изменения поведения не вносятся аудит-проходами без отдельного fix-тикета.
- **Флейворы:** корректность подтверждается на release/целевом варианте по всей матрице (standard, lite, photos, legacy), а не только на standard-debug.
- **Поведение:** аудит-проходы не меняют пользовательское поведение; правки - только устранение помеченного риска под отдельным тикетом.
- **Изоляция флейворов:** без `BuildConfig.IS_*`-гвардов в `src/main` (Rule 15).
- **Существующие гейты:** новые гейты следуют образцу `scripts/quality/assert-*.ps1` (ratchet-baseline, подключение в `post-change.ps1`), не ломают зелёные сборки в день один.

### 3.3 Owner inputs (Approval gate)

- **Scope:** оба модуля; обе семьи (аудит + инфраструктура/правила).
- **Flavor scope:** вся матрица флейворов; верификация на минифицированной сборке.
- **Wear OS:** входит в область. Решено (research 2026-06-26): `wear/` нетривиален (75 файлов / 7776 LOC, собственные ExoPlayer-плееры, корутины, SMB-сеть) -> полный прогон слоёв памяти (S0715) и конкурентности (S0716); Room/perf/R8 - по применимости.
- **CI:** Решено (research 2026-06-26): CI существует - GitHub Actions `.github/workflows/android-ci.yml` (lint `lintStandardDebug` -> unit -> build standard/lite/photos/legacy -> R8 release-check) + `maestro-tests.yml`. Принуждение в два слоя: локальный `post-change.ps1` + джоба в `android-ci.yml`. Emulator/instrumented-джобы нет - её добавление требуется для LeakCanary-в-тестах (S0721) и Macrobenchmark (S0722).
- **Findings policy:** Решено: тривиальные безопасные находки - чинить inline в рамках прохода с валидацией; нетривиальные - парковать fix-тикетами (CLAUDE.md 3.1).
- **Baseline policy:** Решено: ratchet (заморозить текущее, запрещать рост), паттерн существующих `scripts/quality/*-baseline.txt`.
- **Related tickets:** S0715-S0723 (дочерние).

## 5. Предлагаемый подход

Две волны, частично параллельные:

- **Волна B (инфраструктура/правила, S0720-S0723)** даёт рычаги: статанализ, гейты, харнесс, кодифицированные правила. Логично начать с неё - дальнейшие аудит-проходы опираются на эти инструменты и baseline.
- **Волна A (аудит-проходы, S0715-S0719)** прогоняет код слой за слоем, используя инструменты волны B; находки классифицируются и парковываются fix-тикетами.

Каждый дочерний тикет независимо разбивается `/spec-tech` и исполняется `/spec-dev`. Зонтик закрывается, когда все дочерние Verified и протокол принуждается механически для нового кода.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Аудит-проходы вскрывают большой объём P1/P2 находок | Высокая | Раздувание бэклога fix-тикетов | Классифицировать по серьёзности; чинить P0/P1, парковать остальное по приоритету |
| Внедрение detekt/ktlint роняет зелёную сборку из-за массы существующих нарушений | Высокая | Блокировка повседневной работы | Ratchet-baseline: заморозить текущее, запрещать только рост |
| Поведение меняется при «попутном» рефакторинге в аудит-проходе | Средняя | Регрессии без отдельного тикета | Аудит-проход не меняет поведение; правки - отдельным fix-тикетом с валидацией |
| Custom Lint/Macrobenchmark - заметная инфраструктурная работа | Средняя | Затягивание волны B | Дочерние тикеты независимы; приоритезировать дешёвые высокоценные (гейт симметрии, правила) первыми |

## 8. Влияние на пользователя (docs/FEATURES)

Прямого пользовательского эффекта нет - это внутреннее качество кода. Косвенно: меньше крашей, утечек, ANR и jank, выше стабильность горячих путей (плеер, просмотр больших библиотек, старт). Записи в `docs/FEATURES*.md` не требуется; в `docs/ALL_FEATURES.jsonl` уместна инженерная запись о принятом протоколе аудита при закрытии зонтика.

## 9. Архитектурные решения (ADR)

**ADR-1: Зонтик + дочерние тикеты, а не один мега-тикет**

- **Решение:** разбить принятие протокола на 9 независимых дочерних спек под зонтиком S0714.
- **Альтернативы:** один большой тикет «принять протокол»; два тикета (аудит + правила).
- **Почему:** каждый слой/инструмент - самостоятельная единица с собственной валидацией и приоритетом; мега-тикет нарушил бы «одна идея» и завис бы целиком на самом тяжёлом куске.

**ADR-2: Ratchet-baseline, а не блокировка с первого дня**

- **Решение:** новые статанализаторы и гейты замораживают текущее состояние и запрещают рост, а не требуют одномоментной чистки всего кода.
- **Альтернативы:** жёсткий гейт с нуля (красная сборка до полной чистки).
- **Почему:** проект - один разработчик, много тикетов в файле; одномоментная чистка заблокировала бы работу. Существующие гейты `scripts/quality/` уже используют этот паттерн.
