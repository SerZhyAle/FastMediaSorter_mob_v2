## 1. Проблема

При первом запуске приложения список получателей (destinations) пуст. Пользователь открывает плеер, видит панель с кнопками получателей — и она пустая, без объяснений и без подсказки «добавить». Это создаёт ощущение недоделанного продукта и заставляет новых пользователей сразу идти в настройки вместо того, чтобы начать пользоваться основной функцией — сортировкой медиа.

При инсталляции приложение уже создаёт ресурс «Downloads» на основе папки загрузок локального устройства (реальный путь, не виртуальный). Однако этот ресурс не помечается как получатель, хотя папка загрузок — наиболее очевидный и безопасный выбор: она всегда существует, доступна на запись, знакома любому пользователю Android.

---

## 2. Цели

1. После установки и первого запуска список получателей содержит хотя бы одну запись — «Downloads» — без каких-либо действий со стороны пользователя.
2. Пользователь может немедленно начать копировать/перемещать файлы в Downloads прямо из плеера, не заходя в настройки ресурсов.
3. Ресурс «Downloads» остаётся полноценным ресурсом-источником, его статус получателя — лишь дополнительная роль.
4. Поведение не ломает существующих пользователей: у тех, кто уже настроил получателей (или уже имеет ресурс Downloads), ничего не дублируется и не перезаписывается.

**Non-goals:**

- Добавление других стандартных папок (Pictures, Music, DCIM) в получатели по умолчанию.
- Изменение иконки, цвета или порядка уже настроенных получателей у существующих пользователей.
- Принудительный сброс получателей при обновлении приложения.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Цвет кнопки получателя для Downloads выбирается по стандартной палитре (первый свободный слот).
2. Ресурс «Downloads» в роли получателя ведёт себя идентично любому другому получателю: его можно удалить из панели, изменить цвет, переставить.

### 3.2 Жёсткие ограничения

- **Flavor:** все флейворы (`standard`, `lite`, `photos`, `legacy`) — Downloads-папка существует на любом Android-устройстве.
- **API level:** без API-специфики (Downloads-папка доступна с API 8+, значительно ниже minSdk).
- **Wear OS:** не затрагивается.
- **Производительность:** провизионирование выполняется однократно при первом запуске, в фоновом потоке — нет бюджетных ограничений.
- **Совместимость данных:** изменение схемы БД не требуется; модель ресурса уже содержит поля `isDestination` / `destinationOrder` / `destinationColor`. Миграция для существующих пользователей не нужна — условие срабатывает только при нулевых получателях.
- **Локализация:** имя ресурса «Downloads» следует механизму локализации, который уже применяется к quick-add ярлыку. EN/RU/UK — обязательно.
- **Доступность:** изменение не затрагивает визуальных компонентов непосредственно; цветовое обозначение кнопки получателя должно дублироваться меткой (уже реализовано).

## 4. Контекст текущей архитектуры

При первом запуске слой приложения запускает провизионирование ресурсов по умолчанию. Условие срабатывания — база данных ресурсов пуста. Создаются шесть виртуальных ресурсов (Recent, All Music, All Videos, Camera, All Images, All Documents); все они имеют флаг `isDestination = false`, потому что виртуальные пути явно исключены фильтром получателей.

Ресурс «Downloads» на данный момент присутствует только как ярлык быстрого добавления в интерфейсе создания ресурса. Его путь — реальная локальная директория устройства, а значит, он удовлетворяет всем критериям получателя: не виртуальный, не read-only, имеет валидный `destinationOrder`.

Провизионирование получателей (`isDestination = true`) — отдельная ответственность от провизионирования источников. Сейчас нет ни одного места, где получатели создаются по умолчанию: пользователь обязан добавить их вручную.

## 5. Предлагаемый подход

Расширить процесс первоначального провизионирования: параллельно с созданием виртуальных ресурсов-источников создать реальный ресурс «Downloads» и сразу пометить его как получателя с порядковым номером 0.

### 5.1 Основные столпы / модули

**Столп A — Провизионирование Downloads-ресурса**

На этапе первого запуска, если в базе данных ещё нет получателей, создать ресурс-локальную-папку, указывающий на стандартную директорию загрузок устройства. Ресурс получает:
- имя согласно строковому ресурсу «Downloads» (уже локализован),
- тип «локальный», профиль «все файлы»,
- флаг `isDestination = true` и `destinationOrder = 0`,
- цвет из стандартной палитры для слота 0.

**Столп B — Условие идемпотентности**

Перед созданием проверять: существует ли уже любой получатель с тем же физическим путём (Downloads-директория). Если да — пропустить. Это защищает существующих пользователей при гипотетическом повторном срабатывании и предотвращает дублирование.

**Столп C — Независимость от флейвора**

Путь к Downloads-директории определяется стандартным API Android, одинаковым для всех флейворов. Специальной логики ветвления не требуется.

### 5.2 Потоки данных и событий

```
Первый запуск
  → Провизионирование источников (6 виртуальных ресурсов)
  → Провизионирование Downloads-получателя
      → Проверка: есть ли уже получатели?
          → Нет: создать ресурс Downloads с isDestination=true, order=0
          → Да:  пропустить
  → Запись в БД
  → UI главного экрана загружает список ресурсов
  → Панель получателей в плеере отображает кнопку «Downloads»
```

### 5.3 Точки расширяемости

Логика провизионирования получателей по умолчанию должна быть выделена так, чтобы в будущем можно было добавить дополнительные папки-получатели по умолчанию без изменения кода ядра провизионирования источников.

## 9. Архитектурные решения (ADR)

**ADR-1: Провизионирование получателей — в том же init-блоке, что и источники**

- **Решение:** Логика создания Downloads-получателя вызывается сразу после провизионирования виртуальных источников в том же init-потоке ViewModel.
- **Альтернативы:** (1) Отдельный migration use case по аналогии с `migrateS0059UseCase`; (2) Отложенный запуск при первом открытии плеера.
- **Почему:** Init-блок уже гарантирует однократное выполнение при первом запуске; встраивание в него минимизирует количество мест, с которыми нужно разобраться при отладке. Отложенный запуск (вариант 2) создаёт риск race condition, если пользователь откроет плеер до завершения провизионирования.

## 11. Критерии готовности (strategic-level)

1. Пользователь, установивший приложение впервые, открывает плеер и видит кнопку «Downloads» в панели получателей без каких-либо настроек.
2. Ресурс «Downloads» отображается на главном экране как обычный источник — с иконкой и всеми стандартными действиями.
3. У пользователя, уже настроившего получателей до обновления, ничего не меняется — ни порядок, ни количество.
4. Удаление кнопки «Downloads» из панели получателей работает штатным образом (ресурс остаётся как источник, флаг `isDestination` снимается).
5. Имя «Downloads» корректно отображается на всех трёх языках (EN/RU/UK).
