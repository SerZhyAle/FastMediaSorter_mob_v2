**Контекст:** пользователь хочет пересмотреть поведение существующей кнопки выхода в левом верхнем углу. Идея в том, что приложение перестало быть только одноэкранной программой и стало лаунчером с набором функций, часть которых может работать в фоне. В таких сценариях кнопка должна не завершать процесс/приложение, а уводить его в фон, если активны соответствующие возможности.

**Вложения:**

Вложений нет.

---

## 1. Проблема

Исторически кнопка выхода в левом верхнем углу была удобным быстрым способом полностью закрыть приложение. Это соответствовало прошлой модели использования, где завершение программы одной кнопкой было безопасным и ожидаемым действием.

Сейчас приложение всё больше ведёт себя как launcher-платформа с несколькими самостоятельными возможностями, часть которых может быть полезна или даже задумана как фоновая. Полное закрытие по старой кнопке начинает конфликтовать с такими сценариями: пользователь может хотеть убрать UI с экрана, но не останавливать фоновую музыку, жесты или другие долгоживущие функции.

---

## 2. Цели

1. Пересмотреть семантику кнопки выхода в левом верхнем углу с учётом того, что приложение теперь используется как launcher с фоновыми возможностями.
2. Если активны определённые фоновые функции или режимы, нажатие на кнопку должно не закрывать приложение полностью, а сворачивать его.
3. В качестве явных примеров таких режимов уже зафиксированы фоновый музыкальный проигрыватель и жесты с левого края.
4. Новое поведение должно определяться не жёстко "всегда сворачивать", а через понятное правило, зависящее от активных возможностей и/или настроек.
5. Пользователь не должен случайно терять работающую в фоне функциональность из-за старой семантики кнопки выхода.

**Non-goals:**

- Не превращать draft сразу в реализацию полного менеджера жизненного цикла всех фоновых модулей.
- Не менять по этому тикету сами фоновые функции, если они уже работают корректно.
- Не утверждать без отдельного решения, что полное закрытие приложения больше никогда не доступно.

---

## 3. Черновые пожелания и ограничения

- Поведение кнопки должно зависеть от реального состояния приложения, а не только от исторического названия "выход".
- Нужно сохранить возможность полного закрытия там, где фоновых активностей нет и сворачивание не даёт пользы.
- Нельзя допустить ситуацию, когда пользователь думает, что всё выключил, а важные фоновые функции продолжают работать без ясного сигнала.
- Новая логика должна учитывать не только уже названные фоновые режимы, но и другие долгоживущие возможности, которые могут появиться или уже существовать в проекте.
- Для launcher-сценария важно различать "убрать с экрана" и "полностью остановить".

### 3.3 Owner inputs (Approval gate)

- **Related tickets:** none (примыкает к background audio / edge-gestures, но блокеров нет - см. §5).
- **UI placement:** существующая кнопка выхода в левом верхнем углу главного окна; новых элементов не добавляется.
- **UI behavior:** иконка переключается выход <-> свернуть по реальной активности фоновых функций; long-press = полный выход.
- **Exit path:** при minimize-режиме полный выход - long-press, с toast и задержкой ~2 с перед остановкой сервисов и `finishAffinity()`.
- **Trigger set:** любой активный foreground-сервис (музыка, запись, плановые файловые операции) или включённый edge-gestures overlay.
- **Default behavior:** при отсутствии активных фоновых функций кнопка по-прежнему полностью закрывает приложение.
- **Flavor reach:** все флейворы; завязка на реально активные возможности, отдельного флейвор-гейтинга нет.
- **Indication:** minimize - уведомление foreground-сервиса; полный выход - toast + ~2 с.

## 4. Открытые вопросы / Research items

> Ресёрч по кнопке выхода и инвентарю фоновых функций выполнен.
> **Артефакт:** [research/01__exit-button-and-background-features-inventory.md](S0759_exit-button-minimize-when-background-active/research/01__exit-button-and-background-features-inventory.md)

### Установлено ресёрчем

- Текущий выход - `MainActivity.finishAffinity()` (`:389`, `:865`). Перед выходом намеренно останавливается `AudioPlaybackService` (`:1236`): иначе ОС перезапускает процесс (~1 с) из-за живого foreground-сервиса.
- Примитив «свернуть» уже есть в коде: `WelcomeActivity.moveTaskToBack(true)` (`:106`). Отдельного API не нужно.
- **Ключевое противоречие:** ветка close намеренно гасит `AudioPlaybackService`, а ветка minimize не должна его трогать. Это и есть основная техническая развилка - её надо реализовать аккуратно, иначе вернётся double-startup (close) или утечёт сервис (minimize).
- Фоновые foreground-сервисы: `AudioPlaybackService` (музыка, назван владельцем), `QuickAudioRecorderService` (запись), WorkManager `SystemForegroundService` (плановые файловые операции). Плюс edge-gestures (назван владельцем) - это настройка/overlay, не сервис; возможно TTS, стримы, слайдшоу.

### Решено через `/spec-quiz` (2026-06-28)

1. **Набор триггеров (Q1) -> любая фоновая работа.** Minimize, если активен любой foreground-сервис (музыка `AudioPlaybackService`, запись `QuickAudioRecorderService`, плановые файловые операции WorkManager `SystemForegroundService`) ИЛИ включён overlay edge-gestures. Владелец подтвердил: операции по расписанию тоже считаются.
2. **Правило (Q2) -> по реальной активности.** Minimize только если релевантная функция реально активна (сервис запущен / overlay включён) в момент нажатия; иначе - полное закрытие. Совпадает с §3 ("закрывать, когда фона нет").
3. **UX кнопки (Q3) -> менять иконку.** Иконка переключается выход <-> свернуть по текущему режиму (есть активная фоновая работа -> "свернуть", иначе -> "выход").
4. **Путь к полному выходу (Q4) -> long-press.** Долгое нажатие = полный выход, без диалога-переспроса. Перед фактическим закрытием показать toast ("фоновые функции остановлены"), выдержать ~2 секунды (чтобы пользователь успел увидеть), затем остановить сервисы и `finishAffinity()`.

### Резолвится из существующей инфраструктуры / стандартов

- **Семантика minimize (Q5) -> `moveTaskToBack(true)`.** Примитив уже есть (`WelcomeActivity:106`); minimize НЕ трогает `AudioPlaybackService` (ядро развилки).
- **Scope (Q6) -> только кнопка выхода в левом верхнем углу.** Явный запрос §0; системный back и прочие close-пути - вне итерации 1 (возможный follow-up).
- **Индикация (Q7) -> для minimize хватает уведомления foreground-сервиса.** Каждый переживающий триггер - это FGS, у которого по контракту Android уже есть постоянное уведомление (нужный "ясный сигнал" из §3). Для полного выхода сигнал - toast+2 с из Q4. Отдельной индикации для minimize не вводим.

После этих решений тикет готов к `/spec-tech`: правило по реальной активности, переключение иконки кнопки, ветки minimize (`moveTaskToBack`, не трогать сервисы) и close (toast + ~2 с + стоп сервисов + `finishAffinity`), long-press на полный выход.

### Quiz decisions (2026-06-28)

- Набор триггеров -> любая фоновая работа (любой активный FGS + edge-gestures; владелец добавил плановые операции).
- Правило -> по реальной активности в момент нажатия (close, когда фона нет; совпадает с §3).
- UX кнопки -> менять иконку выход/свернуть по режиму (предсказуемость, §6 критерий 4).
- Путь к полному выходу -> long-press без переспроса, но toast + ~2 с перед смертью, чтобы пользователь увидел, что фон остановлен.

## 6. Критерии готовности (strategic-level)

1. Определено понятное правило, когда кнопка в левом верхнем углу полностью закрывает приложение, а когда только сворачивает его.
2. Если активна хотя бы одна релевантная фоновая функция, нажатие на кнопку не убивает приложение прежним образом.
3. Пользователь не теряет фоновую музыку, жесты или другие согласованные долгоживущие функции из-за этой кнопки.
4. Поведение кнопки остаётся предсказуемым и объяснимым для пользователя.
5. Способ полностью закрыть приложение при необходимости остаётся доступным и понятным.
