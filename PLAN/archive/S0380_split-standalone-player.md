## 1. Проблема

Текущая реализация автономного плеера использует одну универсальную активность для воспроизведения всех типов медиафайлов (картинок, видео, аудио, PDF, EPUB, TXT и офисных документов). При получении системного интента на просмотр файла запускается тяжеловесный процесс инициализации:

1. Выполняется разбор (inflation) единого XML-макета, содержащего разметку для всех возможных вьюеров и панелей управления одновременно.
2. Виртуальная машина вынуждена загружать в память и верифицировать классы множества неиспользуемых библиотек (ExoPlayer, Glide, WebView, PDF-рендереры) при открытии любого, даже простейшего текстового файла.
3. Граф внедрения зависимостей перегружен неиспользуемыми в рамках конкретного запуска компонентами.

Это приводит к заметному замедлению холодного старта (Cold Start Latency) автономного плеера на устройствах пользователей.

---

## 2. Цели

1. **Разделение точек входа:** Создание специализированных активностей для групп форматов (изображения и видео, аудио, текстовые файлы, текстовые документы/книги).
2. **Снижение времени открытия (Time-to-Play):** Сокращение времени парсинга макетов и инициализации компонентов за счёт использования облегчённых XML-макетов для каждой активности.
3. **Устранение избыточной загрузки библиотек:** Исключение загрузки неиспользуемых тяжёлых SDK (ExoPlayer, Glide, PDF-библиотеки, WebView) для неподходящих типов файлов.
4. **Облегчение DI-графа:** Уменьшение количества разрешаемых зависимостей при запуске каждого конкретного типа плеера.
5. **Синхронизация возможностей (Feature Parity):** Приведение функционала автономного плеера к паритету с основным внутренним плеером перед разделением, чтобы их возможности и интерфейс не расходились.

**Non-goals:**

- Добавление принципиально новых функций в плееры (вне рамок синхронизации возможностей с основным внутренним плеером).
- Оптимизация внутреннего плеера приложения (который работает в контексте списков воспроизведения и требует поддержки перехода между файлами разных типов в рамках одной сессии).

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Переиспользовать общую логику файловых операций (удаление, шеринг, информация, переименование), жестов и клавиатурных сочетаний без дублирования кода.
2. Сохранить бесшовный запуск автономного плеера из внешних файловых менеджеров без вызова лишних системных диалогов выбора приложения (для этого корректно настроить MIME-типы).
3. Перед началом разделения на отдельные активности синхронизировать функционал и интерфейс существующего автономного плеера с основным внутренним плеером приложения, чтобы исключить отставание возможностей.
4. Спроектировать решение так, чтобы код для всех видов плееров (основного внутреннего и специализированных автономных) был максимально общим в тех местах, где логика совпадает, исключая избыточное клонирование и дублирование кода.

### 3.2 Жёсткие ограничения

- **Flavor:** Изменения применимы ко всем сборкам (`standard`, `lite`, `photos`, `legacy`, `vr`, `noLegal`); flavor-специфика реализуется по `dev/FLAVOR_DEVELOPMENT_RULES.md` (общий интерфейс в `src/main`, при необходимости impl в `src/<flavor>/java` плюс flavor Hilt-модуль), без `BuildConfig`-гейтов в `src/main`.
- **API level:** Без использования платформозависимых API; поддержка обратной совместимости на текущем уровне baseline.
- **Wear OS:** Не затрагивается.
- **Производительность:** Время холодного запуска автономного плеера для текстовых файлов и изображений должно снизиться.
- **Совместимость данных:** Изменения не должны затрагивать базы данных или изменять настройки приложения.
- **Локализация:** Без добавления новых строк.
- **Доступность:** Сохранение фокуса кнопок, D-pad навигации и размеров интерактивных элементов для людей с ограниченными возможностями.

### 3.3 Owner inputs (Approval gate)

- **Flavor scope:** Все сборки (`standard`, `lite`, `photos`, `legacy`, `vr`, `noLegal`); реализация по `dev/FLAVOR_DEVELOPMENT_RULES.md` — общий интерфейс в `src/main`, flavor-impl в `src/<flavor>/java` плюс flavor Hilt-модуль, без `BuildConfig`-гейтов в `src/main`.
- **Wear OS:** Вне объёма — companion-модуль не затрагивается.
- **Performance budget:** Снижение времени холодного старта и инфлейта автономного плеера для текста и изображений; ориентир — §11 (inflate −40% для фото/видео и текста); без eager-загрузки тяжёлых SDK для неподходящих типов.

## 4. Контекст текущей архитектуры

На данный момент автономный плеер реализован в виде единой активности, которая делегирует отображение менеджеру вьюеров. Менеджер вьюеров на основании переданного типа файла активирует нужный визуальный компонент (например, Glide для фото, ExoPlayer для видео, специализированные менеджеры для текстовых файлов или PDF).

Единый XML-макет содержит декларативные оверлеи для всех форматов. Несмотря на то, что в рамках спецификации `S0365` было проведено профилирование и оптимизация (перевод на `dagger.Lazy` и использование `ViewStub`), ClassLoader Android всё равно загружает все задействованные в активности классы тяжеловесных библиотек при старте процесса, что ограничивает возможности дальнейшего ускорения запуска в рамках одной активности.

## 5. Предлагаемый подход

Реализация разделения автономного плеера строится по принципу «сначала синхронизация и унификация кода, затем разделение точек входа».

Существующий автономный плеер выравнивается по возможностям с основным внутренним плеером приложения. Вся общая логика воспроизведения, управления жестами, D-pad/клавиатуры и операций с файлами переносится в единый слой переиспользуемых менеджеров и хелперов, общих для всех видов плееров (как внутренних, так и автономных).

После этого универсальный автономный плеер разделяется на четыре специализированные активности, зарегистрированные в манифесте для соответствующих MIME-типов:

1. **Автономный фото/видео плеер:** обрабатывает изображения, GIF и видео. Использует макет, содержащий только элементы рендеринга Glide/ExoPlayer и их панель управления.
2. **Автономный аудио плеер:** обрабатывает музыкальные файлы. Интегрируется с фоновой службой воспроизведения.
3. **Автономный документ-плеер:** обрабатывает PDF, EPUB и офисные документы. Загружает WebView и PDF-библиотеки.
4. **Автономный текстовый плеер:** обрабатывает простые текстовые файлы. Использует простейший текстовый контейнер, не загружает медиа-библиотеки.

Неопределённые или обобщённые системные интенты (`*/*`, отсутствие MIME-типа) принимает отдельная сверхлёгкая активность-диспетчер без UI: она быстро определяет реальный формат по сигнатуре/расширению и форвардит интент в нужную специализированную активность, не подтягивая тяжёлые медиа-библиотеки. Диспетчер не входит в число четырёх content-активностей и сам по себе ничего не рендерит.

### 5.1 Основные столпы / модули

- **Выравнивание функционала (Functional Alignment):** Предварительный этап выявления расхождений между существующим автономным плеером и основным внутренним плеером и приведение их к минимальному критичному паритету: выравниваются только расхождения, мешающие вынести общий слой логики, а крупные недостающие возможности выносятся отдельными тикетами.
- **Унифицированный слой логики (Unified Playback Logic):** Создание общих переиспользуемых менеджеров воспроизведения и жестов, исключающих дублирование кода между внутренним плеером и специализированными автономными активностями.
- **Регистрация в системе (Manifest Routing):** Настройка соответствующих intent-фильтров для каждой активности с указанием точных MIME-типов для предотвращения конфликтов.
- **Базовая инфраструктура (Common Controller):** Выделение общего интерфейса возможностей хоста плеера и единого хелпера файловых операций, чтобы избежать дублирования логики удаления, шеринга и переименования.
- **Специализированные макеты (Targeted Layouts):** Создание четырёх независимых XML-файлов разметки вместо одного перегруженного.
- **Активность-диспетчер (Dispatcher Trampoline):** Отдельная no-UI точка входа для неопределённых / обобщённых MIME-типов, выполняющая быстрое определение формата и перенаправление без загрузки тяжёлых SDK.

### 5.2 Потоки данных и событий

Основной поток для известного MIME-типа:

1. Система принимает Intent (`ACTION_VIEW` / `ACTION_SEND`).
2. Android выбирает конкретную Activity по MIME-типу.
3. Запускается специализированная Activity.
4. Выполняется легковесный инфлейт макета.
5. Поднимается легковесный DI-граф.
6. Начинается воспроизведение контента.

Поток для интента без MIME-типа или с обобщённым `*/*`:

1. Интент принимает активность-диспетчер.
2. Диспетчер определяет реальный формат по сигнатуре/расширению.
3. Диспетчер форвардит интент в нужную специализированную Activity.
4. Далее выполняется основной поток выше.

### 5.3 Точки расширяемости

- Возможность добавления новых специализированных активностей для редких форматов (например, 3D-моделей или архивов) без изменения существующего кода воспроизведения картинок/видео.
- Граница для flavor-специфичных хостов плеера (`vr` / `noLegal`) задаётся общим интерфейсом возможностей хоста в `src/main`; реализации живут в соответствующих flavor source set по `dev/FLAVOR_DEVELOPMENT_RULES.md`.

   - **Вопрос:** Какая активность должна открывать файл, если MIME-тип не передан или передан как обобщённый `*/*`?

## 9. Архитектурные решения (ADR)

**ADR-1: Переиспользование общей логики через композицию, а не наследование**

- **Решение:** Общая логика (файловые операции, жесты, D-pad/клавиатура, метаданные) выносится в переиспользуемые менеджеры/делегаты в `src/main`; специализированные активности остаются тонкими и собирают поведение через композицию. Общий базовый класс активности как основной механизм переиспользования не используется.
- **Альтернативы:** Единый базовый класс активности с делегатами; дублирование кода операций в каждой активности.
- **Почему:** Композиция лучше согласуется с правилом «no logic in Activity» и flavor-изоляцией (`vr`/`noLegal`), проще тестируется и не создаёт хрупкую иерархию наследования с риском разрастания «God base class».

**ADR-2: Создание унифицированного слоя логики плееров (Unified Playback Logic)**

- **Решение:** Выделить общую логику управления воспроизведением, жестов, D-pad навигации и обработки метаданных в независимые компоненты, которые будут использоваться как основным внутренним плеером, так и новыми автономными активностями.
- **Альтернативы:** Дублирование кода воспроизведения и управления жестами/клавиатурой между основным плеером и специализированными автономными плеерами.
- **Почему:** Предотвращает рассинхронизацию возможностей (feature drift) в будущем и обеспечивает простоту внесения изменений в логику воспроизведения и управления во всех плеерах одновременно.

**ADR-3: Неопределённые MIME-типы обрабатываются отдельной активностью-диспетчером**

- **Решение:** Интенты без MIME-типа или с обобщённым `*/*` принимает сверхлёгкая no-UI активность-диспетчер, определяющая формат и перенаправляющая в нужную специализированную активность.
- **Альтернативы:** Назначить одну из content-активностей (например, фото/видео) точкой входа по умолчанию; полагаться на системный диалог «Открыть с помощью».
- **Почему:** Content-активность как catch-all подтянула бы медиа-библиотеки даже для текста и обнулила выигрыш холодного старта; системный селектор плодит лишний диалог. Диспетчер сохраняет лёгкий старт и бесшовный запуск из внешних приложений.

## 11. Критерии готовности (strategic-level)

1. Успешно скомпилированы и зарегистрированы 4 специализированные активности для автономного просмотра файлов.
2. Файлы изображений, видео, аудио, документов и текстов открываются из внешних приложений в соответствующих им активностях.
3. Время инфлейта разметки (Layout Inflation Time) для фото/видео и текста снижено минимум на 40% по сравнению с универсальной активностью.
4. Отсутствует загрузка классов ExoPlayer при открытии текстовых файлов (подтверждается логами или инспекцией кучи).
5. Активность-диспетчер корректно перенаправляет интенты без MIME-типа и с обобщённым `*/*` в соответствующую специализированную активность без загрузки тяжёлых медиа-библиотек.
