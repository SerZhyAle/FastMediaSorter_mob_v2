## 1. Проблема

Закрытие любого изменения в репозитории — это ритуал из семи шагов, прописанный в `CLAUDE.md` §"Post-Change Steps": dev-log, feature docs, functionality log, string locale audit, catalog sync, spec catalog sync, branch context. Для типичного Kotlin-рефакторинга шаги 2, 3, 4 — это "пропустить", но агент перечитывает всю секцию каждую сессию, чтобы принять это решение. Решение детерминировано типом правки, но текущая инструкция требует прозы каждый раз.

Парк скриптов для этого ритуала уже есть. `scripts/post-change.ps1` пытается их склеить, но делает это с дефектами, которые видны в аудите `dev/development_audit.md` (раздел G):

- Дочерние вызовы `pwsh` идут без `-NoProfile`. На каждый шаг — холодный старт PowerShell с загрузкой профиля. Три-четыре таких старта за один ритуал — это сотни миллисекунд, потраченные на ничто.
- Каталоговая часть ритуала вызывает `scan.ps1` и `render.ps1` как два независимых процесса, минуя `scripts/catalog_sync.ps1` — обёртку, которая ровно для этой цепочки и существует. Это противоречит правилу C из `CLAUDE.md` §"PowerShell Efficiency".
- Скрипт не возвращает явных кодов выхода по каждому шагу. Если шаг провалился внутри, наружу выходит общий exit-код, и агент не может опереться на fail-closed правило из секции "Post-Change Steps".
- Никакого роутинга по типу правки нет. Скрипт всегда пытается сделать каталоговый scan + render — даже если правка чисто в `.md` файле, где Kotlin-индекс не релевантен. Параметр `-SkipScan` есть, но это инверсия проблемы: агент должен помнить, когда пропустить, вместо того чтобы сказать, что он делает.

Параллельно в `CLAUDE.md` §"Post-Change Steps" шаг 5 прямо предписывает коммитить файлы `dev/CATALOG/<module>.jsonl` + `<module>.md` вместе с кодом. Оба файла находятся в `.gitignore`. Инструкция не просто бесполезна — она невыполнима, и каждый агент в какой-то момент об неё спотыкается.

Проверка текущего состояния `scripts/post-change.ps1` на 2026-05-20 подтверждает, что скрипт всё ещё опирается на `-SkipScan`, вызывает `scan.ps1` и `render.ps1` напрямую и не использует маршрутизацию через `-ChangeType`.

Итог: закрывающий ритуал — самая часто исполняемая последовательность в репозитории — построен на скрипте с известными дефектами и на инструкции с известной ошибкой. Стоимость каждой отдельной правки невелика, но интегральная стоимость превышает любую разовую оптимизацию билда.

## 2. Цели

1. Закрытие любой правки агентом сводится к одному вызову: `scripts/post-change.ps1` с явным указанием типа правки. Внутри скрипт сам решает, какие шаги ритуала актуальны для этого типа, и пропускает неактуальные молча.
2. Все дочерние процессы PowerShell, которые порождает ритуал, стартуют с `-NoProfile`. Холодный старт с загрузкой профиля как побочный эффект ритуала исчезает.
3. Каталоговая часть ритуала идёт через `scripts/catalog_sync.ps1`. `scan.ps1` и `render.ps1` напрямую из `post-change.ps1` больше не вызываются — они доступны как примитивы, но ритуал ими не пользуется.
4. Каждый шаг ритуала возвращает явный признак результата (PASS/FAIL и код выхода), и при FAIL ритуал останавливается на этом шаге, не выполняя последующие. Это поведение совпадает с правилом fail-closed из `CLAUDE.md` §"Post-Change Steps" — но теперь оно реализовано в коде, а не зависит от внимательности агента.
5. `CLAUDE.md` §"Post-Change Steps" сокращается до короткой инструкции "запустить `scripts/post-change.ps1 -ChangeType <X>`" с таблицей `ChangeType` → что покрывается. Семь подробных шагов остаются как справочное описание, но обязательная последовательность — это одна команда.
6. Ошибка про коммит каталоговых файлов в `CLAUDE.md` исправляется в рамках того же редактирования: инструкция меняется на "регенерировать через `scripts/catalog_sync.ps1`; файлы локальные, в индекс git не идут".
7. Skills, которые уже сегодня вызывают `scripts/post-change.ps1` (`/spec-dev`, `/spec-fix`, `/spec-arc`, `/quick`, и так далее), продолжают работать без правки на их стороне после реализации этого тикета. Совместимость с текущим контрактом параметров сохраняется в той форме, в которой это возможно.

**Non-goals:**

- Не вводится новая абстракция "agent_validate" или "ritual orchestrator" поверх `post-change.ps1`. Ритуал и сейчас один — диспетчер встраивается в существующий скрипт, а не надстраивается над ним.
- Не меняется логика любого из вызываемых под-скриптов (`add_to_dev_log.ps1`, `catalog_sync.ps1`, `check_strings_localized.ps1`, `add_to_functionality_log.ps1`, `scripts/spec_catalog/update.ps1`). Это контракты, диспетчер просто решает, какие из них вызывать.
- Не вводится автоматическое определение `ChangeType` по списку изменённых файлов. Тип передаётся агентом явно — он знает, что делает, лучше любой эвристики на списке расширений.
- Не затрагивается слой `agent_bootstrap` — он принадлежит S0268.
- Не правится `.vscode/settings.json` и `.gitignore` для уменьшения шума рабочей директории — это S0270.
- Не вводится сверка `docs/TECH_STACK.md` против Gradle — это S0271.
- Не добавляется новый MCP-сервер для запуска ритуала через инструмент. PowerShell-вызов остаётся каноническим интерфейсом.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Контракт командной строки скрипта должен читаться вслух одной фразой. Если агент после правки видит "это был чистый рефакторинг Kotlin", он должен сразу написать команду без обращения к `--help`. Это значит — `-ChangeType` с короткими, очевидными значениями, и минимум обязательных параметров для самого частого типа.
2. Список значений `ChangeType` должен соответствовать таблице из `CLAUDE.md` §"Validation Requirements". Те же шесть классов: `Doc`, `Script`, `Config`, `Kotlin`, `Xml`, `Mixed`. Введение нового класса требует одновременной правки обоих мест — таблицы и диспетчера.
3. Вывод скрипта должен быть скуп. Один блок на шаг ритуала, понятное "PASS / FAIL / SKIP" и итоговая строка с общим результатом. Никаких бесконечных лент log-spam от внутренних скриптов.
4. Если шаг ритуала упал — скрипт обязан явно назвать его и не пытаться скрыть провал бодрым "Done in 2.3 s". Fail-closed на уровне визуального вывода так же важен, как fail-closed на уровне exit-кода.
5. После реализации этой задачи `/quick` и `/spec-dev` должны вызывать `post-change.ps1` ровно с одним параметром-роутером (`-ChangeType`) плюс обязательные параметры дев-лога. Никаких флагов "`-SkipScan`", "`-SkipStrings`", "`-NoFeatureDocs`" наружу выставляться не должно.

### 3.2 Жёсткие ограничения

- **PowerShell:** Скрипт остаётся PowerShell 7+. Запускается под Windows, не под bash. Все правила из `CLAUDE.md` §"PowerShell Efficiency" применяются изнутри: `-NoProfile` на дочерних вызовах, цепочка в одном процессе там, где это допустимо, fail-fast по `$LASTEXITCODE`.
- **Совместимость:** Все вызовы из существующих skills (`/spec-dev`, `/spec-check`, `/spec-fix`, `/spec-arc`, `/quick`, `/skill-fix-release`, `/spec-all`, и так далее) после правки продолжают работать. Если контракт параметров расширяется, новый параметр имеет умное значение по умолчанию, чтобы старые вызовы не падали.
- **Fail-closed:** Если любой шаг ритуала вернул ненулевой exit-код, оставшиеся шаги не выполняются, скрипт завершается с тем же exit-кодом, и в выводе явно обозначено, на каком шаге произошёл сбой.
- **Идемпотентность:** Повторный запуск ритуала с теми же параметрами по уже изменённому файлу не приводит к двойной записи в дев-лог или дублям в functionality log. Это требование к диспетчеру: он обязан передавать всю информацию в подскрипты без дополнения, а решение о дублировании остаётся на стороне `add_to_dev_log.ps1` / `add_to_functionality_log.ps1` (их контракт не меняется, см. Non-goals).
- **Локализация:** Аудит локалей через `check_strings_localized.ps1` запускается тогда и только тогда, когда `ChangeType` — это `Xml` (включающий `strings.xml`) или явно указан `Mixed` с ключевым префиксом. Лишние запуски не приветствуются: они стоят дороже, чем кажется при больших prefix-сёрчах.
- **Каталоговая синхронизация:** Запускается тогда и только тогда, когда `ChangeType` — это `Kotlin` или `Mixed` с явным указанием модуля. `Doc`/`Script`/`Config`/`Xml` не запускают каталог. Это исключает текущий регресс, когда ритуал сканит весь модуль ради дев-лог-записи в `.md`-файле.
- **Spec catalog sync:** Не идёт через `post-change.ps1`. Решение о смене статуса спеки принимает skill (`/spec-dev`, `/spec-check`, и так далее) и вызывает `scripts/spec_catalog/update.ps1` напрямую. Это сознательная граница: `post-change.ps1` — про закрытие правки, не про управление статусом тикета. Шаг 6 из `CLAUDE.md` остаётся ответственностью skill-слоя.
- **Documentation truth:** Эта спека не вводит новый источник правды о `ChangeType`. Источник — таблица в `CLAUDE.md` §"Validation Requirements". Любое расширение списка типов идёт через правку этой таблицы и обновление диспетчера в одном коммите.

## 4. Контекст текущей архитектуры

Закрытие правки в этом репозитории — это композиция из независимых утилит, исторически написанных в разное время и связанных вручную в `CLAUDE.md`. Дев-лог пишется одним скриптом, functionality log — другим, аудит локалей — третьим, каталоговая синхронизация — парой (`scan` + `render`) с обёрткой-консолидатором. Управление спек-каталогом — отдельный набор CLI, доступ к нему агенту даёт `scripts/spec_catalog/`. Эти утилиты в сумме покрывают всё, что нужно сделать после правки. Они работают.

Поверх этих утилит существует `scripts/post-change.ps1` — попытка склеить часть из них в один вызов. Скрипт реально вызывают `/spec-dev`, `/spec-fix`, `/quick`, `/spec-arc`, `/skill-fix-release`, `/spec-all`. То есть он на критическом пути и сегодня. Дефекты (профильный холодный старт на каждый шаг, обход обёртки `catalog_sync.ps1`, отсутствие явных exit-кодов на шаг, отсутствие роутинга по типу) — это последствия органического роста, а не проектные решения.

`CLAUDE.md` §"Post-Change Steps" описывает семь шагов прозой и просит агента каждый раз сверять свою правку с каждым шагом. Это работает, но требует от агента семь решений вместо одного, на каждой задаче. Шаги 2 (feature docs) и 3 (functionality log) почти всегда — "пропустить". Шаг 4 (string locale audit) релевантен только при правке `strings.xml`. Шаг 5 (catalog sync) релевантен только при правке Kotlin. Шаг 6 (spec catalog sync) — релевантен только при смене статуса спеки и уже сегодня обслуживается skill-слоем. Шаг 7 (branch context) — автоматически делает `add_to_dev_log.ps1`. Остаётся ровно один шаг, который выполняется всегда — дев-лог.

То есть фактическая обязательная часть ритуала — один универсальный шаг (дев-лог) плюс условные шаги, выбираемые по типу правки. Это и есть тот самый "ChangeType-аware диспетчер" — формализация того, что агент уже делает в голове.

Ещё один аспект: текст `CLAUDE.md` шага 5 предписывает коммитить каталоговые файлы (`dev/CATALOG/<module>.jsonl` + `<module>.md`). На самом деле оба файла находятся в `.gitignore` — каталог — это локальный индекс, который регенерируется. Инструкция в `CLAUDE.md` физически невыполнима и каждый раз создаёт у агента маленький конфликт между текстом правила и состоянием репо. Исправление — одна строка в `CLAUDE.md`, и оно делается в рамках того же редактирования, что и общее сокращение секции.

## 5. Предлагаемый подход

Подход — формализация существующего распорядка под один обязательный вход с явным указанием типа правки.

### 5.1 ChangeType-аware диспетчер

`scripts/post-change.ps1` расширяется параметром `-ChangeType` со списком допустимых значений: `Doc`, `Script`, `Config`, `Kotlin`, `Xml`, `Mixed`. Список совпадает с таблицей `CLAUDE.md` §"Validation Requirements" — это сознательное переиспользование классификации, чтобы не плодить две параллельные.

Логика диспетчера:

- Шаг "dev-log" исполняется всегда, независимо от `ChangeType`. Это универсальный шаг ритуала.
- Шаг "catalog sync" исполняется тогда и только тогда, когда `ChangeType` равен `Kotlin`. Запуск идёт через `scripts/catalog_sync.ps1` — то есть `scan` и `render` запускаются в одном PowerShell-процессе, как требует `CLAUDE.md` §"PowerShell Efficiency" правило C.
- Шаг "strings locale audit" исполняется тогда и только тогда, когда `ChangeType` равен `Xml` и при этом передан ключевой префикс через существующий параметр `-KeyPrefix`. Если префикс не передан, шаг пропускается с явным SKIP и кратким напоминанием в выводе. `Mixed` обрабатывается как сумма применимых шагов.
- Шаги "feature docs" и "functionality log" из `CLAUDE.md` остаются обязанностью skill-слоя — диспетчер не пытается их выполнять. В выводе ритуала просто отмечается, что эти шаги — на стороне skill, чтобы агент видел границу.
- Любой шаг, который провалился (exit-код ненулевой), останавливает ритуал. Оставшиеся шаги не выполняются. Итоговый exit-код скрипта равен exit-коду провалившегося шага.
- Каждый шаг печатает один блок: имя шага, результат (`PASS` / `FAIL` / `SKIP`), время в миллисекундах. Итог — одна строка с общим результатом и общим временем.

`Mixed` — это вход для случаев, когда правка реально пересекает классы (например, правка `.kt` + правка `strings.xml`). Внутри диспетчер выполняет оба применимых шага в порядке "catalog sync" → "strings". Если оба применимых шага выполнены, ритуал считается успешным.

### 5.2 Корректность под Windows/PowerShell

Все правила из `CLAUDE.md` §"PowerShell Efficiency" должны соблюдаться диспетчером и при тактической реализации:

- Дочерние вызовы под-скриптов идут через `pwsh -NoProfile -File <path>` без исключений. Текущий механизм определения пути к pwsh.exe сохраняется или упрощается, но `-NoProfile` появляется во всех вызовах.
- Цепочка scan + render заменяется одним вызовом `scripts/catalog_sync.ps1`, что устраняет лишний холодный старт.
- Любые проверки `$LASTEXITCODE` пишутся без обратного слэша перед знаком доллара (правило из `CLAUDE.md` про литеральные знаки доллара в командной строке).
- Скрипт не использует длинные `-Command "<inline script>"`-обёртки с переменными внутри — там, где нужна логика, она пишется в теле .ps1-файла, а не в строке-аргументе.
- Скрипт остаётся однопроходным: один запуск — одна последовательность шагов. Никаких ретраев, никаких параллельных подскриптов внутри.

### 5.3 Исправление CLAUDE.md §"Post-Change Steps"

Текст секции сокращается до короткой формы:

- Основное обязательное действие — один вызов `scripts/post-change.ps1 -ChangeType <X>` с указанием обязательных параметров дев-лога.
- Таблица `ChangeType` → что покрывается. Те же значения, что и в §"Validation Requirements".
- Шаги "feature docs" (новые публичные капабилити) и "functionality log" (изменение пользовательского поведения) остаются прозой — это решения агента, а не функции скрипта. Они привязываются к классам правок, для которых релевантны.
- Шаг "spec catalog sync" остаётся прозой и указывает на skill-слой (`/spec`, `/spec-dev`, и т.д.), который сам зовёт `scripts/spec_catalog/update.ps1`.
- Шаг "branch context" удаляется как самостоятельный пункт — он автоматически выполняется внутри `add_to_dev_log.ps1`.
- Строка про коммит `dev/CATALOG/<module>.jsonl` + `<module>.md` исправляется: каталоговые файлы — локальный индекс, регенерируются скриптом, в индекс git не идут.

После правки секция становится короче и не содержит инструкций, которые невозможно или не нужно выполнять.

### 5.4 Обратная совместимость для skills

Skills, которые уже вызывают `post-change.ps1`, продолжают работать после реализации. Контракт обязательных параметров `-File`, `-Target`, `-Description` сохраняется. Параметр `-Module` сохраняется со значением по умолчанию `app_v2`. Параметр `-KeyPrefix` сохраняется опциональным.

Новый параметр `-ChangeType` добавляется обязательным для нового использования, но имеет значение по умолчанию (например, `Kotlin` или `Mixed` — точный выбор берётся на тактическом уровне), которое воспроизводит сегодняшнее поведение скрипта максимально близко. Это позволяет skill-слою обновляться к новому контракту без одновременного релиза всех вызовов.

Параметр `-SkipScan` остаётся доступным как deprecated-вход, ведущий себя как `-ChangeType Doc` (или эквивалент). Skill-слой переводится на `-ChangeType` инкрементально, без обязательного coordinated change.

После того как все известные skill-вызовы будут переведены на `-ChangeType`, `-SkipScan` помечается удалённым отдельным маленьким тикетом (вне рамок этой спеки). Это не часть критериев готовности S0269.

## 6. Research items - resolved

1. **Значение `-ChangeType` по умолчанию для обратной совместимости**
   - **Решение:** Значение по умолчанию остаётся `Kotlin`, если вызывающая сторона не передала `-ChangeType`, `-SkipScan` и `-KeyPrefix`.
   - **Основание:** Это ближе всего к прежнему поведению скрипта, где каталоговый шаг выполнялся всегда, и даёт самый безопасный режим для старых skill-вызовов.
   - **Статус:** Resolved.

2. **Поведение `Mixed` при отсутствии `-Module` или `-KeyPrefix`**
   - **Решение:** Для `-Module` сохраняется default `app_v2`; отсутствие `-KeyPrefix` не валит ритуал, а переводит `strings-audit` в явный `SKIP`.
   - **Основание:** Это сохраняет fail-closed только для реальных ошибок дочерних шагов и не ломает смешанные вызовы, где строковый аудит к текущей правке не относится.
   - **Статус:** Resolved.

3. **Granularity вывода шагов**
   - **Решение:** Вывод дочерних скриптов сохраняется, а диспетчер добавляет поверх него компактные блоки `PASS` / `FAIL` / `SKIP` с именем шага и временем.
   - **Основание:** Такой режим не теряет диагностику при провале и при этом делает границу шагов читаемой для агента.
   - **Статус:** Resolved.

4. **Имена под-блоков в выводе**
   - **Решение:** Используются канонические лейблы `dev-log`, `catalog-sync`, `strings-audit`, согласованные с сокращённой секцией `CLAUDE.md`.
   - **Основание:** Это убирает лишнее расхождение между кодом диспетчера и операторской инструкцией.
   - **Статус:** Resolved.

5. **Расширение `ChangeType` для будущих типов правок**
   - **Решение:** Набор `ChangeType` остаётся фиксированным: `Doc`, `Script`, `Config`, `Kotlin`, `Xml`, `Mixed`.
   - **Основание:** Новые типы должны появляться только при одновременной правке таблицы `CLAUDE.md` и `ValidateSet` в диспетчере, а не как скрытая открытая точка расширения.
   - **Статус:** Resolved.

## 7. Риски

- **Регресс существующих skill-вызовов.** Skills `/spec-dev`, `/spec-fix`, `/spec-arc`, `/quick`, `/skill-fix-release`, `/spec-all` уже зовут `post-change.ps1`. Если контракт параметров сломается, ритуал перестанет работать сразу для всех. Митигация: расширение параметров идёт исключительно через добавление, с умолчаниями, воспроизводящими текущее поведение. Никакого breaking change без предварительной правки вызывающих сторон.

- **Скрытие реальной ошибки за дружелюбным выводом.** Если диспетчер начнёт суммировать вывод подскриптов, агент потеряет возможность увидеть конкретную причину FAIL. Митигация: FAIL обязан показывать stdout/stderr провалившегося подскрипта целиком, без сокращения, и явно называть, какой шаг упал.

- **`-ChangeType Doc` для правки, которая на самом деле тронула `.kt`.** Если агент ошибочно классифицировал правку как `Doc`, каталоговая синхронизация будет пропущена, и `dev/CATALOG/*.jsonl` разойдётся с реальностью до следующего scan. Митигация: каталог локальный, не блокирующий — следующий запуск `/catalog` или ритуала с `ChangeType Kotlin` догонит индекс. Это допустимая стоимость, чтобы не вынуждать диспетчер угадывать тип по списку файлов.

- **`Mixed` как "молоток" — соблазн использовать его всегда.** Если агент начнёт ставить `Mixed` по умолчанию, чтобы "наверняка", диспетчер вернётся к текущему дефекту "всегда scan + всегда strings". Митигация: документация в CLAUDE.md явно описывает `Mixed` как режим "правка реально пересекла классы", а не "не уверен — поставил Mixed". Skills, которые знают свой класс правки (`/quick` — обычно `Mixed` или `Kotlin` в зависимости от ввода, `/spec-dev` — обычно `Kotlin`), передают точное значение.

- **Каталог не догнал реальность к моменту коммита.** Если `Kotlin` ритуал упал на шаге catalog-sync, агент рискует закоммитить код без обновлённого индекса. Митигация: fail-closed обязан остановить ритуал, и агент видит провал. Так как каталог в .gitignore, расхождение не блокирует коммит, но диагностически сигнализируется.

- **Расхождение между таблицей `ChangeType` в CLAUDE.md и реализацией.** Если расширили один список и забыли другой, агенты будут передавать значение, которое скрипт не знает. Митигация: одно из критериев готовности — таблица в CLAUDE.md и список допустимых значений в диспетчере покрывают одно и то же множество. Тактическая спека закрепляет проверку на согласованность.

- **Деградация скорости в режиме `Mixed`.** `Mixed` запускает и каталог, и strings-audit. На больших prefix-сёрчах strings-audit стоит дороже всего ритуала вместе взятого. Митигация: документация явно указывает, что `Mixed` дороже `Kotlin` или `Xml` по отдельности, и просит классифицировать точнее. Skill-слой переводится на точные значения, `Mixed` остаётся для реально смешанных правок.

## 9. Архитектурные решения (ADR)

**ADR-1: Один диспетчер вместо нескольких параллельных скриптов**

- **Решение:** Расширение существующего `scripts/post-change.ps1` параметром `-ChangeType`. Никакого нового `scripts/agent_validate.ps1` или `scripts/ritual_orchestrator.ps1`.
- **Альтернативы:** (а) Ввести новый скрипт-обёртку поверх `post-change.ps1` и подскриптов, оставив `post-change.ps1` без правки. (б) Распилить ритуал на несколько маленьких скриптов и вызывать их раздельно из skills.
- **Почему:** `post-change.ps1` уже на критическом пути и его уже зовёт skill-слой. Введение второго уровня обёртки — это новый источник правды и новая точка отказа. Распиливание на несколько скриптов перекладывает оркестрацию на skill, что повторяет ровно ту проблему, которую этот тикет решает. Один диспетчер с явным параметром-роутером — самое лаконичное решение.

**ADR-2: `ChangeType` передаётся явно, а не выводится из списка файлов**

- **Решение:** Тип правки агент сообщает явно через `-ChangeType`. Никаких эвристик "если файл `.kt`, то `Kotlin`" внутри скрипта.
- **Альтернативы:** Автоопределение типа по расширению переданного `-File` или по `git status`.
- **Почему:** Эвристика ошибается. Изменение `.kt`-файла бывает чисто косметическим (правка комментария — `Doc` по сути), и наоборот, правка `.gradle.kts` — это `Config`, а не `Kotlin`. Передача типа агентом — это явное волеизъявление: агент видел изменение, он знает, что класс этой правки. Скрипт его не оспаривает.

**ADR-3: Spec catalog sync остаётся обязанностью skill-слоя**

- **Решение:** Шаг "spec catalog sync" из `CLAUDE.md` §"Post-Change Steps" не выполняется диспетчером `post-change.ps1`. Изменение статуса спеки вызывает skill (`/spec`, `/spec-dev`, и т.д.), который зовёт `scripts/spec_catalog/update.ps1` напрямую.
- **Альтернативы:** Добавить в `post-change.ps1` параметры `-SpecId` и `-SpecStatus`, чтобы один и тот же ритуал закрывал и закрытие правки, и смену статуса спеки.
- **Почему:** Это разные оси. `post-change.ps1` — про "правка случилась, закрыли её механически". `spec_catalog/update.ps1` — про "статус тикета сменился, потому что фаза работы перешла в следующую". Смешение этих двух осей в одном скрипте создаёт ложное впечатление, что spec status — это побочный эффект правки. Это не так: статус — это решение, и оно принимается skill-слоем по логике, а не по факту правки.

**ADR-4: `CLAUDE.md` §"Post-Change Steps" сокращается, но не удаляется**

- **Решение:** Текущая прозаическая секция сокращается до короткой инструкции "запустить `scripts/post-change.ps1 -ChangeType <X>`" с таблицей значений. Описание шагов остаётся справочным, не обязательным.
- **Альтернативы:** Удалить секцию целиком, перенеся её содержание в README скрипта.
- **Почему:** `CLAUDE.md` — это первый файл, который читает агент при инициализации. Удаление секции и расчёт на то, что агент пойдёт читать README скрипта — это ставка против структуры внимания. Сокращение секции до одной обязательной команды — рабочий компромисс: основное действие на виду, расшифровка — рядом, но не на пути.

**ADR-5: Параметр `-SkipScan` остаётся как deprecated, не удаляется в рамках этого тикета**

- **Решение:** `-SkipScan` сохраняется и продолжает работать (эквивалент `-ChangeType Doc`). Удаление параметра — отдельный микро-тикет после миграции всех вызовов skills на `-ChangeType`.
- **Альтернативы:** Удалить `-SkipScan` в рамках S0269 одновременно с правкой всех вызывающих skills.
- **Почему:** Coordinated change по всему skill-слою — это лишняя зона риска для тикета, цель которого — поправить дефект и сократить инструкцию. Migration в две фазы (сначала добавить новое, потом удалить старое) безопаснее и проще откатывается, если что-то пойдёт не так.

## 11. Критерии готовности (strategic-level)

1. `scripts/post-change.ps1` принимает параметр `-ChangeType` со значениями `Doc`, `Script`, `Config`, `Kotlin`, `Xml`, `Mixed`. Скрипт документирует все значения во встроенной справке.
2. Все дочерние вызовы `pwsh` внутри `scripts/post-change.ps1` выполняются с `-NoProfile`.
3. Каталоговая часть ритуала идёт через `scripts/catalog_sync.ps1`. Прямых вызовов `scan.ps1` или `render.ps1` из `scripts/post-change.ps1` больше нет.
4. Каждый шаг ритуала возвращает явный признак результата (`PASS` / `FAIL` / `SKIP`) и кратко обозначает время. При `FAIL` ритуал останавливается на текущем шаге, оставшиеся шаги не запускаются, итоговый exit-код скрипта равен exit-коду провалившегося подскрипта.
5. `ChangeType Doc`, `Script`, `Config`, `Xml` не запускают каталоговую синхронизацию. `Doc`, `Script`, `Config`, `Kotlin` не запускают аудит локалей. `Mixed` запускает оба применимых шага, если их условия выполнены (модуль / префикс).
6. Все известные сегодняшние вызовы `post-change.ps1` из skill-слоя (`/spec-dev`, `/spec-fix`, `/spec-arc`, `/quick`, `/skill-fix-release`, `/spec-all`, и любые другие, обнаруженные на тактической фазе) продолжают работать без правки на стороне skill — за счёт обратной совместимости параметров и разумного значения по умолчанию для `-ChangeType`.
7. `CLAUDE.md` §"Post-Change Steps" сокращён до короткой инструкции "запустить `scripts/post-change.ps1 -ChangeType <X>`" с таблицей значений. Шаги "feature docs", "functionality log", "spec catalog sync" остаются прозой в зонах ответственности skill-слоя.
8. В `CLAUDE.md` §"Post-Change Steps" удалена ошибочная инструкция о коммите `dev/CATALOG/<module>.jsonl` + `<module>.md`. Заменена на корректное описание: "каталоговые файлы — локальный индекс, регенерируются скриптом, в git не идут".
9. Список значений `ChangeType`, поддерживаемых диспетчером, совпадает с таблицей `CLAUDE.md` §"Validation Requirements". Согласованность двух мест проверена на тактической фазе.
10. Запуск `scripts/post-change.ps1 -ChangeType Doc` для правки чистого `.md`-файла не запускает ни каталоговый scan, ни strings-audit, отрабатывает заметно быстрее, чем текущий полный прогон, и при успехе возвращает exit-код 0 с одним PASS на шаге dev-log.
