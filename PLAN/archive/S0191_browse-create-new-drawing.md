## 1. Проблема

В Browse пользователь может создавать папки и (после S0189) текстовые заметки, но не может создать новый пустой рисунок в текущем каталоге. Чтобы получить новый холст рядом с медиа или документами, приходится переключаться в стороннее приложение и потом подкладывать файл вручную.

Такой разрыв ломает сценарии, где рисунок нужен рядом с контентом: скетч поверх фото, графическая пометка к документу, быстрая зарисовка в каталоге проекта, графический TODO. Дополнительно не сформирован контракт «создал холст и сразу рисую» именно через Browse-команду, а контур взаимодействия редактора рисования с save/cancel/share-операциями расходится с уже принятым в S0189 для текстовых заметок.

---

## 2. Цели

1. Дать пользователю возможность создать новый рисунок прямо из Browse в текущем открытом пути ресурса изображений.
2. После создания файла сразу открывать его в существующем редакторе рисования в режиме редактирования.
3. Подбирать стартовый цвет фона по общесистемной night-mode (Android `UiModeManager`):
   - light → белый фон;
   - dark → чёрный фон.
4. Обеспечить быстрые явные действия сохранения, отмены и шаринга в редакторе без неочевидных промежуточных шагов.
5. Поддержать сценарий переименования рисунка в момент сохранения.
6. Добавить действие отправки текущего изображения через системный share-интент.
7. Сохранить единый контракт поведения для локальных, сетевых и облачных ресурсов, где запись поддерживается.
8. Не дублировать логику с S0189: переиспользовать общие куски (filename, conflict, remote staging, editor-action contract, dirty-tint), а различия выносить в drawing-локальные модули.

**Non-goals:**

- Полноценный графический редактор с расширенным набором инструментов и слоёв.
- Введение нового формата хранения рисунков (собственного контейнера).
- Изменение текущего pipeline редактирования уже открытых изображений.
- История версий рисунков внутри приложения.
- Совместное редактирование или multi-user режим.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Точка входа в создание рисунка должна быть нативной частью Browse-команд, в одном ряду с «новая папка» и «новая заметка» из S0189.
2. Созданный файл должен сразу открываться на редактирование, без дополнительного ручного открытия из списка.
3. В редакторе должны быть быстрые понятные действия «сохранить», «сохранить и закрыть», «сохранить и отправить», «отправить» и «отмена», по аналогии с S0189.
4. При сохранении пользователь должен иметь возможность изменить имя файла и его расширение.
5. Цвет фона при создании должен совпадать с общесистемной night-mode без вопроса пользователю.
6. Первая итерация должна работать на уже поддерживаемых writable-ресурсах без внедрения отдельного storage-движка для рисунков.
7. Общая часть с S0189 должна быть реализована один раз и переиспользована, а не скопирована.

### 3.2 Жёсткие ограничения

- **Flavor:** standard, lite, photos, legacy; доступность действия определяется реальной поддержкой изображений и возможностью записи в текущий ресурс. Лагинг по flavor-флагам не вводится, новых `BuildConfig`-гейтов не добавляется.
- **API level:** без изменения нижней границы API.
- **Wear OS:** не затрагивается.
- **Производительность:** создание рисунка не должно запускать тяжёлые пересканы; допустим только локальный refresh текущего списка. Save/cancel/share-операции должны быть отзывчивыми и не блокировать UI на длинный путь без обратной связи.
- **Совместимость данных:** новый файл создаётся как обычное изображение в целевой папке, без скрытых проприетарных контейнеров.
- **Локализация:** EN/RU/UK обязательно. Новые пользовательские строки должны соответствовать `docs/COMMUNICATION_POLICY.md`; tone checklist из §6 политики — обязательный gate перед интеграцией.
- **Доступность:** действие и диалог должны быть полностью управляемы с клавиатуры и TalkBack, с понятными сообщениями об ошибках.
- **Зависимость от S0192:** тулбар редактора рисования финализируется в S0192; команды save/save+close/save+share/share/cancel из S0191 встраиваются в этот тулбар, а не создают собственную панель.

## 4. Контекст текущей архитектуры (AS-IS baseline)

Архитектура Browse уже поддерживает файловые команды для операций с объектами файловой системы и умеет работать с разными типами ресурсов через единый слой доменных операций. Также присутствует контур рисования по уже открытому изображению.

По результатам первичного AS-IS анализа:

- В редакторе рисования уже есть инструменты рисования и сохранение в исходный файл; контракт пустого холста как стартовой точки не оформлен как сценарий из Browse.
- В Browse уже есть паттерн команды «создать сущность» (папка, текст из S0189) с предикатом доступности и обновлением списка.
- Контракт «создал локально → скопировал в удалённый ресурс → удалил локально» формируется в рамках S0189 для текстовых заметок; для рисунков нужен тот же контур, но над байтами изображения.
- Активная тема приложения доступна, но единая точка чтения «текущая тема для целей создания фона» сейчас не зафиксирована и должна быть подтверждена в AS-IS.

Сейчас отсутствует единый пользовательский сценарий создания нового рисунка в текущем каталоге с немедленным входом в редактирование и с согласованной моделью save/cancel/rename/share. Поэтому пользователь не может завершить «создать холст рядом с контентом» внутри одного потока Browse.

## 5. Предлагаемый подход

На стратегическом уровне функция должна быть оформлена как новая командная возможность в Browse, использующая уже существующие механизмы проверки прав, подтверждений, сообщений об ошибках и обновления списка файлов. Итоговый артефакт — обычный графический файл, создаваемый в текущем контексте ресурса и сразу открываемый в редакторе рисования.

### 5.1 Основные столпы / модули

**UI-команда создания рисунка**

Нужна явная пользовательская команда в Browse, доступность которой определяется текущим типом ресурса и правами записи. По разметке точки входа — в одном ряду с «новая папка» и «новая заметка».

**Сценарий ввода и валидации**

Унифицированный диалог ввода имени с дефолтом по дате/времени, проверкой недопустимых символов, пустого имени, конфликта с существующим файлом и ограничений ресурса. Тот же диалог, что и в S0189, с разным дефолтным расширением.

**Подбор стартового фона**

Цвет фона нового холста определяется общесистемной night-mode (Android `UiModeManager` / `Configuration.uiMode`): light → белый, dark → чёрный. Без диалога выбора в v1.

**Создание файла через существующий файловый слой**

Создание рисунка должно выполняться как обычная файловая операция в том же архитектурном контуре, что и другие file ops, включая remote-staging через Downloads для удалённых ресурсов.

**Немедленный переход в редактор рисования**

После создания файл должен быть открыт в редакторе рисования без промежуточных действий пользователя.

**Контур редактирования с быстрыми действиями**

В редакторе рисования должны быть явные быстрые действия: save, save+close, save+share, share-without-save, cancel; dirty-state индикатор через цвет тулбара. Контракт совпадает с S0189; набор кнопок встраивается в тулбар редактора рисования, финализируемый в S0192.

**Обновление состояния UI после операции**

После успешного создания список должен отражать новый файл немедленно, а при ошибке пользователь должен получать понятную и дружелюбную причину отказа.

### 5.2 Потоки данных и событий

- Пользователь инициирует команду создания рисунка в Browse.
- UI собирает имя файла, дефолт `YY-MM-dd_hh-mm.jpg` (JPEG 85%); пользователь может изменить имя и расширение.
- Слой применения проверяет доступность операции для текущего ресурса и пути.
- Определяется стартовый цвет фона по активной теме приложения.
- Выполняется создание нового файла изображения в целевой папке (или в Downloads-staging для удалённых ресурсов).
- UI получает результат и сразу открывает новый файл в редакторе рисования.
- Пользователь редактирует холст, использует доступные инструменты.
- Пользователь выполняет одну из быстрых команд: save, save+close, save+share, share, cancel.
- При успехе список и контекст ресурса синхронизируются с фактическим именем/содержимым файла; при ошибке показывается понятное сообщение, а локальная staging-копия в Downloads остаётся.

### 5.3 Точки расширяемости

- Дополнительные пресеты фона помимо автоподбора по теме.
- Дополнительные форматы файла (JPG, WebP) по пользовательской настройке.
- Конфигурируемый размер холста (квадрат, разрешение экрана, кастом).
- Шаблоны стартового содержимого (сетка, базовые направляющие).
- Персистентная настройка дефолтного цвета фона/формата отдельно от темы.

### 5.4 Общая модель с S0189 (кандидаты на shared code)

Перечень частей, которые в тактической фазе должны быть выделены как переиспользуемые модули, а не дублироваться:

- **Filename generator** — общий генератор имени по шаблону `YY-MM-dd_hh-mm.<ext>` с расширением как параметром.
- **Name conflict policy** — общий resolver конфликта имён через авто-суффикс `-ss` (текущие секунды) с пересчётом до уникального имени.
- **Browse command entry pattern** — общий способ регистрации команды «создать сущность X в текущей папке»: место в тулбаре, приоритет collapse в overflow на узких экранах, capability-предикат, обработка ошибок.
- **Remote-resource staging contract** — общий контракт «создать локально в Downloads → скопировать в целевой удалённый ресурс → при успехе удалить локальную копию → при ошибке оставить локальную копию и показать сообщение». Над байтами абстрагируется от типа контента (текст / изображение).
- **Editor action contract** — общий набор семантических действий редактора: `save`, `saveAndClose`, `saveAndShare`, `share`, `cancel`. UI-привязка разная (текстовый редактор vs canvas), но набор и состояния идентичны.
- **Dirty-state toolbar tint** — общий механизм окрашивания командной панели редактора в зависимости от наличия несохранённых изменений.
- **System share invocation** — общий вызов системного «Send to» интента после save+share / share без save.

Drawing-локальные части, не выносимые в shared:

- Определение цвета фона по активной теме.
- Создание стартового битмапа нужного размера, формата и фона.
- Привязка editor action contract к тулбару рисования (S0192) и к canvas-состоянию.

## 6. Открытые вопросы / Research items

### 6.1 Technical/Product research items

1. **Дефолтный размер холста** — closed
   - **Решение:** разрешение текущего экрана устройства (`Resources.displayMetrics` в момент создания). См. §6.2 п.9 — там тот же ответ.

2. **Дефолтный формат файла** — closed
   - **Решение:** JPEG с качеством 85% (расширение `.jpg`). Дефолт имени становится `YY-MM-dd_hh-mm.jpg`. Это сознательное отличие от S0189 (где `.png` для текстовых заметок невозможен, а рисунки реально выигрывают от JPG-сжатия по размеру). Пользователь может изменить расширение в диалоге сохранения. См. §6.2 п.2 и §6.2 п.7 — синхронизированы.

3. **Источник темы для подбора фона** — closed
   - **Решение:** общесистемная night-mode (Android `UiModeManager.nightMode` / `Configuration.uiMode & UI_MODE_NIGHT_MASK`), а не in-app theme override. light → белый, dark → чёрный. См. ADR-5.

4. **Матрица поддерживаемых источников записи** — closed
   - **Решение:** все writable ресурсы с поддержкой изображений (совпадает с §6.2 п.1).

5. **Граница shared-модулей с S0189** — closed
   - **Решение:** все 6 общих модулей из §5.4 (filename generator, name-conflict policy, Browse command entry pattern, remote-resource staging contract, editor action contract, dirty-state toolbar tint, system share invocation) выделяются в shared-код синхронно с реализацией S0189. S0191 в момент разблокировки только подключается к ним без дополнительного рефакторинга. Владелец shared-извлечения — тактическая фаза S0189.

### 6.2 Опросник заказчика работ (обязательный до реализации)

Ответы перенесены из S0189 для совпадающих пунктов; drawing-специфичные пункты помечены как Open до явного ответа заказчика.

1. Для каких ресурсов команда «Новый рисунок» должна быть видна в v1: только writable photos-ресурсы или все writable ресурсы с поддержкой изображений?
   Ответ: все writable ресурсы с поддержкой изображений (по аналогии с S0189).

2. Какой дефолт расширения нужен в v1: только `.png` или выбор `.png/.jpg`?
   Ответ: `.jpg` по умолчанию (JPEG 85%, см. §6.1 п.2 — сознательное отличие от S0189). Пользователь может изменить и имя, и расширение при сохранении.

3. Авто-открытие нового файла в редакторе рисования должно быть обязательным или настраиваемым?
   Ответ: обязательным (по аналогии с S0189).

4. Где размещать команду в Browse: toolbar-кнопка, overflow, обе точки входа?
   Ответ: обе точки входа — команда в тулбаре с низким приоритетом, попадает в ниспадающее меню на узких экранах (по аналогии с S0189).

5. Что считать «быстрым сохранением»: одна кнопка commit без диалога, или commit с минимальным подтверждением?
   Ответ: одна кнопка (по аналогии с S0189).

6. Как трактовать «отмену сохранения»: отмена текущих несохранённых изменений, выход из режима редактирования, или оба сценария?
   Ответ: закрытие без сохранения (по аналогии с S0189).

7. Rename при сохранении: это «Save As», переименование текущего файла перед commit, или разрешены оба режима?
   Ответ: только с указанием имени перед выходом; имя по умолчанию `YY-MM-dd_hh-mm.jpg` (расширение из §6.1 п.2). Отличие от S0189 (там `.png` для текстовых заметок не применимо, а у рисунков базовый формат — JPEG).

8. Если имя занято, какая политика приоритетна: fail с сообщением, авто-суффикс, overwrite с подтверждением?
   Ответ: автодобавление `-ss` (текущие секунды) к имени и запись (по аналогии с S0189).

9. Размер холста: разрешение экрана устройства, фиксированный 1080×1080, настраиваемый?
   Ответ: разрешение текущего экрана устройства (`Resources.displayMetrics.widthPixels × heightPixels`). Закрыто синхронно с §6.1 п.1.

10. Какой UI для редактирования обязателен в v1: контракт инструментов и тулбара берётся из S0192; новые команды save/save+close/save+share/share/cancel встраиваются в существующий тулбар рисования?
    Ответ: да, тулбар рисования финализируется в S0192; S0191 добавляет в этот тулбар команды save/save+close/save+share/share/cancel (по аналогии с S0189).

11. Нужно ли показывать пользователю явный индикатор dirty-state (например, «есть несохранённые изменения»)?
    Ответ: да, цвет командной панели (по аналогии с S0189).

12. Нужно ли после save возвращаться в Browse, оставаться в редакторе, или это настраивается?
    Ответ: нужны команды в виде иконок «сохранить», «сохранить и закрыть», «сохранить и отправить», «отправить» (без сохранения и не закрывая), «отмена». «Сохранить и отправить» сразу инициирует механизм «отправить в» Android share. (По аналогии с S0189; вместо отдельной кнопки «отправить в Keep» — единый системный share, так как Keep не является родным графическим редактором.)

13. Нужна ли отдельная блокировка функции для read-only и virtual путей с разными текстами ошибок?
    Ответ: нет (по аналогии с S0189).

14. Какие сценарии являются блокирующими для приёмки: локальные папки, SMB, FTP/SFTP, cloud провайдеры?
    Ответ: никакие — создавать рисунок можно где угодно. При создании рисунка на удалённом ресурсе (например SFTP) файл сначала сохраняется локально в Downloads, затем копируется в сетевой ресурс. Если на момент сохранения ресурс недоступен — показывается ошибка, локальная копия остаётся; при успехе локальная копия удаляется и пользователь не замечает staging. (По аналогии с S0189.)

15. Цвет фона при создании: только автоподбор по теме (light → белый, dark → чёрный), или нужен ручной выбор перед созданием?
    Ответ: только автоподбор по общесистемной night-mode без диалога в v1 (источник — §6.1 п.3).

16. Системный share-target: единая кнопка «Поделиться» через системный Android share, или отдельные кнопки для Keep / Photos / Gallery?
    Ответ: единая системная кнопка «Поделиться» через Android share-интент (отличие от S0189, где Keep — отдельная цель: для рисунков такой выделенной цели нет, поэтому используется generic share). Если share-таргетов в системе нет — кнопка скрыта (по аналогии с S0189 fallback).

После ответов однозначно зафиксированы (2026-05-17):

- точка входа команды создания рисунка — Browse, в одном ряду с «новая папка» и «новая заметка»; обе точки входа (тулбар низкого приоритета + overflow);
- дефолтный формат файла — JPEG 85%, расширение `.jpg`;
- дефолтный размер холста — разрешение текущего экрана устройства;
- источник темы для подбора фона — общесистемная night-mode (`UiModeManager` / `Configuration.uiMode`);
- поведение save/cancel — единая кнопка commit без диалога; cancel = закрытие без сохранения;
- правило rename-on-save — указание имени перед выходом; auto-suffix `-ss` при конфликте;
- контракт share-интента — единый системный share (`ACTION_SEND`), кнопка скрывается, если в системе нет ни одного таргета;
- граница shared-модулей с S0189 — все 6 модулей §5.4 выделяются в тактической фазе S0189; S0191 их только потребляет.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Неодинаковая поддержка записи на разных источниках приведёт к непредсказуемому UX | Средняя | Пользователь видит действие, которое локально не срабатывает на части ресурсов | Явный предикат доступности команды по capability ресурса и понятные причины недоступности |
| Конфликты имён будут обрабатываться не в едином стиле с остальными file ops и S0189 | Средняя | Поведение функции будет казаться «особенным» и ломать ожидания | Переиспользовать общий name-conflict resolver из §5.4 |
| Создание рисунка вызовет лишний полный перескан каталога | Низкая | Просадки производительности на крупных и сетевых папках | Использовать локальное обновление списка без полного refresh, где это возможно |
| Явные save/cancel действия конфликтуют с auto-save или с состоянием canvas в редакторе рисования | Средняя | Пользователь теряет понимание, что реально сохранено, либо теряет правки | Зафиксировать единый editor action contract совместно с S0192 и переиспользовать из S0189 |
| Rename-on-save приведёт к случайному overwrite | Средняя | Потеря данных при коллизии имён | Обязательная политика коллизий + явное подтверждение для рискованных действий |
| Цвет фона по теме определяется не той точкой приложения | Низкая | Создаётся холст с «не своим» фоном при системной смене темы или гибридных режимах | Зафиксировано в ADR-5: единственный источник — общесистемная night-mode (`UiModeManager`/`Configuration.uiMode`). |
| Share-интент не имеет ни одного таргета на устройстве | Низкая | Пользователь нажимает share, но Android ничего не открывает | Capability-check перед показом кнопки share, скрытие кнопки при отсутствии таргетов |
| Дублирование кода с S0189 вместо выделения общих модулей | Средняя | Расхождение поведения двух «create new …» сценариев через 1–2 итерации | Выделить общие модули из §5.4 синхронно с реализацией S0189 |
| Неполная локализация пользовательских сообщений | Низкая | Часть UX окажется неоднородной по языку | Обязательная EN/RU/UK проверка и применение communication policy перед релизом |

## 9. Архитектурные решения (ADR)

**ADR-1: Рисунок — это обычный графический файл в существующей файловой модели**

- **Решение:** не вводить отдельный тип сущности «рисунок» и не хранить рисунки во внутренней БД как primary source.
- **Альтернативы:** внутренний draw-store; гибрид с экспортом в файл.
- **Почему:** это сохраняет совместимость, простоту и прозрачность для пользователя.

**ADR-2: Создание рисунка реализуется как расширение текущего Browse file-ops контракта**

- **Решение:** встроить действие в существующую архитектурную цепочку файловых операций, рядом с «новая папка» и «новая заметка» из S0189.
- **Альтернативы:** отдельный «мини-модуль» с параллельной логикой и особыми правилами.
- **Почему:** единый контракт снижает риск расхождения поведения и упрощает поддержку.

**ADR-3: V1 ориентирован на минимальный, надёжный сценарий создания**

- **Решение:** в первой итерации сфокусироваться на создании пустого холста с фоном по теме и корректной обратной связи.
- **Альтернативы:** сразу включать пресеты, выбор размера, выбор формата.
- **Почему:** это снижает риск регрессий и быстрее даёт пользователю реальную ценность.

**ADR-4: Немедленный переход в редактор рисования после создания обязателен для v1**

- **Решение:** после успешного create пользователь сразу попадает в режим редактирования нового файла.
- **Альтернативы:** оставаться в Browse и открывать вручную; делать авто-открытие опциональным.
- **Почему:** сценарий «создать новый рисунок» ценен именно скоростью входа «создал → сразу рисую».

**ADR-5: Цвет фона определяется общесистемной night-mode, без диалога**

- **Решение:** источник темы — Android `UiModeManager.nightMode` / `Configuration.uiMode & UI_MODE_NIGHT_MASK`, **не** in-app theme override. light → белый, dark → чёрный.
- **Альтернативы:** in-app theme override; диалог выбора цвета; настройка дефолтного цвета.
- **Почему:** общесистемная night-mode стабильно доступна вне UI-стека Activity, не зависит от состояния AppCompat и не требует пробрасывать тему сквозь Browse-команду. Снижает число лишних диалогов в v1.

**ADR-6: Контракт editor actions заимствуется из S0189 и общим модулем**

- **Решение:** набор save/save+close/save+share/share/cancel и dirty-tint реализуются как общий модуль, разделяемый с S0189; UI-привязка делается в тулбаре рисования (S0192). Извлечение модуля — обязательная часть тактической фазы S0189 (см. §6.1 п.5).
- **Альтернативы:** независимые реализации для текста и для рисования; копирование без выделения общего модуля.
- **Почему:** без общего модуля гарантировано расхождение поведения двух «create new …» сценариев.

**ADR-7: Удалённые ресурсы пишутся через staging в Downloads**

- **Решение:** при создании рисунка в удалённом ресурсе файл сначала пишется локально в Downloads, затем копируется в целевой ресурс; локальная копия удаляется только при успехе.
- **Альтернативы:** прямая запись в удалённый ресурс; ошибка при недоступности без staging.
- **Почему:** это совпадает с контрактом S0189 и защищает пользователя от потери данных при потере связи.

## 11. Критерии готовности (strategic-level)

1. Пользователь может создать новый рисунок в текущей папке Browse без выхода во внешние приложения.
2. Команда доступна только там, где ресурс и текущий путь реально поддерживают запись изображений.
3. После создания файл автоматически открывается в редакторе рисования.
4. Цвет фона нового холста соответствует общесистемной night-mode (light → белый, dark → чёрный).
5. Пользователь может быстро сохранить изменения, отменить их или поделиться через явные действия в редакторе.
6. Пользователь может изменить имя и расширение файла в сценарии сохранения.
7. При конфликте имени и при ошибках записи пользователь получает предсказуемое и понятное поведение, согласованное с S0189.
8. После успешного сохранения список в Browse отражает актуальный файл/имя в том же контексте ресурса.
9. Удалённые ресурсы обрабатываются через Downloads-staging с тем же контрактом, что и в S0189.
10. Общие модули из §5.4 реализованы один раз и переиспользованы между S0189 и S0191.
11. Пользовательские строки и документация функции синхронизированы в EN/RU/UK.

## 13. Результат первичного ресёрча (снимок на 2026-05-14)

- В продуктовой документации зафиксирован контур редактирования по уже открытому изображению; сценарий пустого холста как стартовой точки из Browse не оформлен.
- В Browse уже существует проверенный UX-паттерн команды создания сущностей с делегированием операций создания в доменный слой.
- В S0189 параллельно формируется контракт «создать новую сущность в Browse → сразу редактировать → быстро save/cancel/share → при удалённом ресурсе — staging через Downloads»; этот контракт является прототипом для S0191 и источником общего кода.
- Новая задача не стартует с нуля: требуется донастройка существующих контуров под сценарий «создать рисунок → сразу рисую → быстро сохранить/отменить/поделиться → при сохранении опционально переименовать», с переиспользованием общих модулей из §5.4.
