# Стратегическая спецификация: S0347 - Приоритет исполнителя и порог уверенности при автоопределении трека по имени файла

> **Scope:** STRATEGIC. Цели, ограничения, открытые вопросы. Без имён классов, путей, лимитов строк, миграций Room, модулей Hilt.

## 1. Проблема

Когда у аудиофайла нет встроенных метаданных (нет тегов, обложки, исполнителя и названия), приложение пытается определить трек по имени файла через онлайн-сервисы и показать обложку и метаданные. Сейчас это работает неважно по двум причинам.

Во-первых, при поиске фактически выше приоритет у названия композиции, а не у имени исполнителя. Имя файла вида «Исполнитель - Название» сплющивается в один плоский набор слов, и сервис ранжирует результат по более «заметным» словам названия. В итоге часто находится другой исполнитель с одноимённой песней, и пользователю показывается чужая обложка и неверные метаданные.

Во-вторых, у найденного результата нет понятия уверенности совпадения. Берётся первый результат провайдера без проверки, что найденный исполнитель/название вообще соответствуют запросу. Программа нередко «цепляется за несколько букв или одно слово», не связанных с оригинальным треком, и всё равно показывает обложку как достоверную.

Затронутая область - аудиоплеер и онлайн-определение обложки/метаданных по имени файла (capability AUDIO).

---

## 2. Цели

1. При разборе имени файла выделять исполнителя и название как отдельные части и придавать имени исполнителя больший вес в поисковом запросе и при отборе результата.
2. Ввести оценку уверенности совпадения найденного результата с исходным запросом (сравнение исполнителя в первую очередь, затем названия).
3. При низкой уверенности не показывать обложку и метаданные - использовать обычное пустое состояние вместо заведомо чужой обложки.
4. Снизить частоту показа метаданных «не того исполнителя» при совпадении только по названию композиции.

**Non-goals:**

- Не меняем определение трека по встроенным тегам (ID3/Vorbis) - там данные уже достоверны.
- Не вводим новую UI-надпись «возможно, это …» / индикатор догадки (рассматривается как открытый вопрос §6, не цель первой итерации).
- Не добавляем новых провайдеров поиска и не меняем список используемых сервисов.
- Не трогаем параллельную фичу поиска текстов песен, кроме переиспользования общей логики разбора имени.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Лучше не показать обложку вовсе, чем показать чужую - ложноположительный показ хуже пустого состояния.
2. Разбор имени файла должен переиспользовать уже существующую в проекте логику выделения «исполнитель - название» (по разделителю и со снятием ведущего номера трека), а не дублировать её.
3. Артиста, выведенного из родительской папки альбома, использовать как дополнительный сигнал для проверки уверенности, а не только как добавку к запросу.

### 3.2 Жёсткие ограничения

- **Flavor:** фича существует во всех вариантах с capability AUDIO (`standard`, `legacy`, `lite`, а также `vr`, наследующий `standard`); отсутствует в `photos` (AUDIO выключен). Поведение определения должно быть единым для всех AUDIO-вариантов; расхождение между документацией и фактическим набором флейворов разрешить в §8 / открытом вопросе.
- **API level:** без API-специфики.
- **Wear OS:** не затрагивается.
- **Производительность:** допускается запрашивать у провайдеров несколько результатов вместо одного для последующего отбора по уверенности; рост сетевого трафика и задержки должен оставаться в разумных пределах и уважать настройку «искать обложки только по Wi-Fi». Бюджет: один дополнительный набор результатов на трек, без повторных запросов в цикле.
- **Совместимость данных:** локальный кэш найденных метаданных должен корректно работать при добавлении признака уверенности; ранее закэшированные «угаданные» результаты не должны навсегда фиксироваться как достоверные. Форма миграции кэша - без номера версии хранилища, детали в `/spec-tech`.
- **Локализация:** EN/RU/UK - обязательно, если появятся новые пользовательские строки (по умолчанию новых строк не вводится).
- **Доступность:** при суппрессии обложки используется уже существующее пустое состояние - отдельных не-цветовых отличий не требуется.

### 3.3 Owner inputs (Approval gate)

- **Flavor scope:** все AUDIO-варианты (`standard`, `legacy`, `lite`, `vr`) - единое поведение; `photos` вне области (AUDIO выключен).
- **Performance budget:** не более одного дополнительного набора результатов на трек; повторных запросов в цикле нет; настройка Wi-Fi-only соблюдается.
- **Data compatibility:** кэш расширяется признаком уверенности без жёсткой ломки прежних записей; низкоуверенные результаты не кэшируются как достоверные.
- **UI placement contract:** при низкой уверенности показывается существующее пустое состояние обложки; новых элементов интерфейса не добавляется.
- **Accessibility:** изменений нет - переиспользуется текущее пустое состояние.
- **Validation level:** юнит-тесты на разбор имени, формирование запроса и отбор по уверенности; ручная проверка на наборе файлов без тегов (в т.ч. «исполнитель - название», одноимённые песни разных исполнителей).
- **Owner sign-off:** 2026-06-04 - запрос владельца.
- **Related tickets:** none.

## 4. Контекст текущей архитектуры

За определение обложки и метаданных по имени файла отвечают слой применения (use-case онлайн-поиска обложки и общий помощник формирования поискового запроса), слой удалённых источников (поиск через внешние сервисы), драйвер плеера (решает, что показать: встроенную обложку, локальный кэш или результат онлайн-поиска) и слой локального кэша найденных метаданных.

Сейчас задачу из §1 нельзя решить «как есть» потому, что: общий помощник формирования запроса сплющивает имя файла в плоский набор слов и не передаёт провайдеру, какая часть - исполнитель; результат каждого провайдера берётся как первый из ответа без какой-либо проверки соответствия запросу; в модели результата отсутствует поле уверенности; решение «показывать» сводится к «есть ссылка на обложку → показать». Логика выделения «исполнитель - название» уже существует в смежной фиче (поиск текстов), но не переиспользуется в пути определения обложки.

---

## 5. Предлагаемый подход

Сместить логику с «первый результат провайдера» на «лучший результат, прошедший порог уверенности», и сделать исполнителя первичным сигналом и в запросе, и в отборе.

### 5.1 Основные столпы / модули

- **Структурный разбор имени файла.** Перед формированием запроса имя файла разбирается на исполнителя и название с использованием уже существующей в проекте логики (разделитель «исполнитель - название», снятие ведущего номера трека). Артист из родительской папки используется как дополнительный кандидат-исполнитель. Результат - не плоская строка, а структурированный запрос с явной ролью исполнителя.
- **Оценка уверенности.** Для отбора результата вводится оценка соответствия между запросом и кандидатом, где совпадение исполнителя имеет больший вес, чем совпадение названия. Провайдеры запрашиваются на несколько кандидатов; среди них выбирается лучший по оценке. Если лучший не дотягивает до порога - результат считается ненадёжным.
- **Гейт показа по уверенности.** Драйвер плеера показывает обложку и метаданные только если уверенность не ниже порога; иначе - существующее пустое состояние. Низкоуверенный результат не закрепляется в локальном кэше как достоверный.

### 5.2 Потоки данных и событий

Имя файла → структурный разбор (исполнитель + название + кандидат из папки) → формирование запроса с приоритетом исполнителя → запрос к провайдерам (несколько кандидатов) → оценка уверенности каждого кандидата → выбор лучшего и сравнение с порогом → решение «показать обложку/метаданные» либо «пустое состояние» → запись в локальный кэш с учётом уверенности.

### 5.3 Точки расширяемости

- Оценка уверенности и порог - отдельная переиспользуемая абстракция, чтобы её мог применять и путь определения обложки, и (потенциально) смежные пути (тексты песен).
- Логика разбора «исполнитель - название» консолидируется в общем помощнике запроса и переиспользуется обеими фичами вместо дублирования.
- Модель результата расширяется признаком уверенности так, чтобы пороговое решение и кэширование могли его читать.
- Поведение единое для всех AUDIO-флейворов; флейвор-специфичных реализаций не вводится (Rule 15 не затрагивается).

## 6. Открытые вопросы / Research items

1. **Определение метрики уверенности**
   - **Вопрос:** на чём строить оценку - на перекрытии токенов запроса и полей результата (исполнитель/название) или на нормализованном сравнении строк?
   - **Варианты:** токенное перекрытие с весами; нормализованное расстояние; комбинация. Провайдеры числовой скор не возвращают.
   - **Нужно выяснить:** какой подход даёт лучшее отсечение ложных совпадений при кириллице и транслитерации.
   - **Статус:** Open

2. **Значение порога и поведение ниже порога**
   - **Вопрос:** какой порог считать «достаточным» и что делать при пограничной уверенности - полностью скрывать обложку, либо показывать обложку но скрывать текстовую строку метаданных?
   - **Варианты:** единый порог «показать/скрыть»; два порога с промежуточным режимом.
   - **Нужно выяснить:** приемлемый баланс «реже чужое» против «реже пусто» на реальном наборе файлов.
   - **Статус:** Open

3. **Сколько кандидатов запрашивать у провайдеров**
   - **Вопрос:** какое число результатов запрашивать вместо одного, чтобы хватило для отбора, но не раздувать трафик.
   - **Нужно выяснить:** разумный предел с учётом настройки Wi-Fi-only.
   - **Статус:** Open

4. **Кэширование низкоуверенных результатов**
   - **Вопрос:** хранить ли в кэше факт «надёжного совпадения не найдено», чтобы не дёргать сеть повторно, и при этом не показывать угаданное как достоверное.
   - **Статус:** Open

5. **Документация флейворов**
   - **Вопрос:** фича в документации помечена как Standard/VR, но AUDIO включён также в `legacy`/`lite`. Привести документацию в соответствие или сузить поведение?
   - **Статус:** Open

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Слишком высокий порог уверенности скроет даже корректные обложки | Средняя | Регресс: меньше обложек, чем сейчас | Подбор порога на реальном наборе; открытый вопрос §6.2 |
| Слишком низкий порог не отсечёт чужие совпадения | Средняя | Цель §1 не достигнута | Приоритет исполнителя в метрике; ручная проверка на одноимённых песнях |
| Рост задержки/трафика из-за запроса нескольких кандидатов | Низкая | Медленнее показ обложки, расход трафика | Лимит кандидатов; соблюдение Wi-Fi-only; без повторов в цикле |
| Кириллица/транслитерация искажает оценку соответствия | Средняя | Ложные отсечения или ложные показы | Нормализация и учёт скрипта при сравнении |
| Старые «угаданные» записи в кэше показываются как достоверные | Низкая | Сохранение прежней проблемы | Учёт уверенности при чтении/записи кэша |

## 9. Архитектурные решения (ADR)

**ADR-1: Отбор по уверенности вместо «первого результата»**

- **Решение:** перейти от «первый результат провайдера» к «лучший кандидат, прошедший порог уверенности», с приоритетом совпадения исполнителя.
- **Альтернативы:** оставить первый результат, но улучшить только запрос; показывать всегда, но с пометкой «возможно».
- **Почему:** только проверка соответствия устраняет показ чужого исполнителя; пометка «возможно» не убирает дезинформацию, а лишь смягчает её и требует новой UI-строки (вынесено в non-goal).

**ADR-2: Переиспользование существующего разбора «исполнитель - название»**

- **Решение:** консолидировать имеющуюся логику разбора имени файла в общем помощнике и применять её в пути определения обложки.
- **Альтернативы:** написать отдельный парсер для обложек.
- **Почему:** дублирование уже приводит к расхождениям; единый разбор даёт явную роль исполнителя в запросе и для метрики.

## 11. Критерии готовности (strategic-level)

1. Для файла вида «Исполнитель - Название» без тегов запрос и отбор отдают приоритет исполнителю, и при совпадении только по названию чужого исполнителя обложка не показывается.
2. При низкой уверенности совпадения пользователь видит обычное пустое состояние обложки, а не чужую обложку/метаданные.
3. При достоверном совпадении (исполнитель и название совпадают с запросом) обложка и метаданные показываются как прежде.
4. Низкоуверенный результат не закрепляется в локальном кэше как достоверный.
5. Поведение одинаково во всех вариантах сборки с capability AUDIO.
