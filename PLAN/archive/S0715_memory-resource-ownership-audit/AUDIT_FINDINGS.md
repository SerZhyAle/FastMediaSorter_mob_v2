# S0715 Memory & Resource Ownership Audit - Findings

Date: 2026-06-26. Scope: `app_v2` + `wear` (all source sets). Method: Layer 3 of `docs/CODE_AUDIT_PROTOCOL.md`, swept across 6 ownership dimensions (ContentObserver/BroadcastReceiver symmetry; addListener/addCallback/addObserver vs matching removal; ExoPlayer/Media3 player ownership + release; Glide/bitmap request ownership; retained Context/View/Activity/Fragment references; unbounded caches / leaked delayed work / unclosed Closeables / leaked scopes). Candidates were deduplicated across dimensions and put through adversarial verification: each suspected finding was re-derived against source, severities were re-rated (several downgraded), and refuted angles were dropped. 9 confirmed findings remain; 5 of 14 verified candidates were rejected/refuted.

## Confirmed findings

### P2

- `wear/src/main/java/com/sza/fastmediasorter/wear/di/WearAppModule.kt:59` - symbol `WearAppModule.provideExoPlayer / @Singleton ExoPlayer`. Dimension: addListener/addCallback/addObserver vs matching removal (Media3 Player.Listener and lifecycle registrations). Rationale: `provideExoPlayer` is `@Singleton` (lines 59-65, `@ApplicationContext`) so one ExoPlayer lives for the whole process; searching all of `wear/src` for `.release()`/`clearVideoSurface`/`setVideoSurface` finds only an unrelated `events.release()` in `WatchWearListenerService.kt:60`. Both `VideoPlayerViewModel.onCleared` (333-341) and `AudioPlayerViewModel.onCleared` (301-308) call `removeListener+stop+clearMediaItems` but never `release()`; no wear Application/MainActivity teardown releases it. The Player.Listener dimension is symmetric (SAFE), but the native ExoPlayer (audio renderer, playback thread, last surface) is never released. Downgraded P1->P2: bounded single-singleton retention, not unbounded growth. fixSketch: give the singleton an owner that calls `exoPlayer.release()` on real teardown (e.g. wear `Application.onTerminate`), or drop `@Singleton` and let each player ViewModel own + release a per-screen ExoPlayer in `onCleared`. Confidence: high.

- `wear/src/main/java/com/sza/fastmediasorter/wear/ui/player/audio/AudioPlayerViewModel.kt:301` - symbol `AudioPlayerViewModel.onCleared()`. Dimension: addListener/addCallback/addObserver vs matching removal (Media3 Player.Listener and lifecycle registrations). Rationale: ExoPlayer is `@Singleton` (`WearAppModule.kt` provideExoPlayer 49-65, `SingletonComponent`) and injected into both AudioPlayerViewModel (line 52) and VideoPlayerViewModel (line 47). Both add the listener in `init` and `removeListener+stop+clearMediaItems` in `onCleared` (Audio 301-308, Video 333-341); neither calls `release()`. The only `.release()` in the wear module is the unrelated `WatchWearListenerService.kt:60`; `FastMediaSorterWearApp.kt` (20 lines) has no `onTerminate`/release; `VideoPlayerScreen.kt` only receives the player. The required `ExoPlayer.release()` is missing - the singleton's playback HandlerThread, audio renderer, AudioTrack/audio-focus and codec resources are held process-wide. The listener part of the dimension is symmetric (no listener leak); "two owners of one player" is a valid Layer-3 single-owner smell but adds no leak beyond the missing release. Downgraded P1->P2: bounded fixed retention. fixSketch: give the singleton a single lifecycle owner (release in `FastMediaSorterWearApp.onTerminate`), or stop `@Singleton` scoping and create/release a player per player-screen ViewModel calling `exoPlayer.release()` in `onCleared`. Confidence: high.

- `wear/src/main/java/com/sza/fastmediasorter/wear/di/WearAppModule.kt:59` - symbol `provideExoPlayer`. Dimension: ExoPlayer/Media3 player ownership + release. Rationale: `provideExoPlayer` is `@Singleton` in `@InstallIn(SingletonComponent)` (57-65) - one ExoPlayer per process. Both `AudioPlayerViewModel.onCleared()` (301-308) and `VideoPlayerViewModel.onCleared()` (333-341) inject this singleton and on teardown call only `removeListener+stop+clearMediaItems`, never `release()`. Module-wide search for `\.release\(\)` finds only `events.release()` in `WatchWearListenerService.kt:60` (a WearableListenerService Tasks resource, unrelated). `VideoPlayerScreen.kt` `DisposableEffect onDispose` (179-183) only `Timber.d`-logs; `FastMediaSorterWearApp.kt` has no `onTerminate`. The codec/audio-focus/decoder/renderer resources of the singleton are never freed for process lifetime. Downgraded P1->P2: shared singleton is stopped+cleared (not re-instantiated) between screens, so the leak is bounded to one instance, not per-screen accumulation; note it cannot be `release()`d in a ViewModel `onCleared` under the current singleton design (the other VM would get a dead player), so the fix changes ownership. fixSketch: stop sharing one `@Singleton` ExoPlayer across both player VMs - provide a non-singleton ExoPlayer (or per-VM factory) so each VM owns and `release()`s its instance in `onCleared`; if a single shared player is intentional, release it from a process/lifecycle-aware owner (ProcessLifecycleOwner observer or MediaSessionService) on app stop. Confidence: high.

- `wear/src/main/java/com/sza/fastmediasorter/wear/ui/player/video/VideoPlayerScreen.kt:179` - symbol `VideoPlayerContent / DisposableEffect`. Dimension: ExoPlayer/Media3 player ownership + release. Rationale: `AndroidView` factory (141) and update (148) both set `view.player = player`, binding the singleton ExoPlayer to a freshly-created PlayerView (registering the video surface). `DisposableEffect onDispose` (179-183) only logs `VideoPlayerScreen disposed` and never calls `view.player = null` / `clearVideoSurface()`. Module-wide grep for `clearVideoSurface|.player = null|setPlayer(null)|onDetachedFromWindow|DisposableEffect` finds only the import and the no-op DisposableEffect. Player is a process-lifetime `@Singleton` built with `@ApplicationContext` (player itself doesn't leak an Activity, but a bound PlayerView does). `VideoPlayerViewModel.onCleared()` (333-341) has no PlayerView reference and does not `setPlayer(null)`. In Media3 1.2.1 `PlayerView.setPlayer()` registers an internal ComponentListener and does not auto-detach in `onDetachedFromWindow`, so the singleton retains each disposed PlayerView (inner ComponentListener -> PlayerView -> Activity/Compose context), accumulating one per video-screen visit on a never-reset singleton. P2 (not P1): accumulation needs repeated navigation and Wear has a single Activity (no Activity-instance multiplication). fixSketch: in `VideoPlayerContent`'s `DisposableEffect onDispose`, capture the PlayerView (hoist via `remember` or `AndroidView onRelease`) and call `view.player = null` (and optionally `clearVideoSurface()`) so the singleton drops the PlayerView/listener on leaving composition. Confidence: medium.

- `app_v2/src/main/java/com/sza/fastmediasorter/ui/player/helpers/BackgroundMusicManager.kt:531` - symbol `release()`. Dimension: ExoPlayer/Media3 player ownership + release. Rationale: `BackgroundMusicManager` is `@Singleton` (line 32) with no DI module overriding scope, injected as `Lazy<BackgroundMusicManager>` into PlayerActivity (451/469). Listeners are registered in `PlayerManagerInitializer.kt:177` and `:184` with lambdas capturing the PlayerActivity (`activity.runOnUiThread`, `activity.dialogAndUiStateManager`, `Toast.makeText(activity,..)`). `release()` (531-552, the onDestroy teardown via `PlayerLifecycleManager.kt:187`) cancels jobs, releases+nulls the ExoPlayer and resets state but never sets `onTrackChangedListener=null` / `onMusicErrorListener=null` (grep for `*Listener = null` across `app_v2/src` returned zero hits). Decisive corroboration: the sibling `AudioBackgroundPhotosManager`, also `@Singleton` and released two lines below in the SAME teardown block, DOES null its listeners (`AudioBackgroundPhotosManager.kt:319-320`) - so the omission is a true asymmetry. Retention path: singleton -> listener field -> lambda -> destroyed PlayerActivity (full view tree/window). Bounded to one Activity instance (self-corrects when the next PlayerActivity overwrites the listeners), reproducible on every player exit. fixSketch: in `BackgroundMusicManager.release()`, add `onTrackChangedListener = null` and `onMusicErrorListener = null` (mirroring `AudioBackgroundPhotosManager.release` lines 319-320). Confidence: high.

- `wear/src/main/java/com/sza/fastmediasorter/wear/ui/player/video/VideoPlayerViewModel.kt:333` - symbol `onCleared`. Dimension: Memory ownership: unbounded caches, leaked delayed work, unclosed Closeables, leaked scopes (Layer 3). Rationale: suspected P0 ("same singleton ExoPlayer leaked", "remove every Player.Listener") was partly REFUTED: ExoPlayer is `@Singleton` (`WearAppModule.kt:50,58`) shared with AudioPlayerViewModel, so not calling `release()` in a per-ViewModel `onCleared` is the intended lifecycle (releasing it would break the next screen/audio VM) - the player is not leaked per-screen; and `addListener` (123) is symmetric with `removeListener` (338). What IS real and narrower: the surface is never detached. PlayerView gets the singleton via `view.player=player` (`VideoPlayerScreen.kt:141,148`), but the composable's `onDispose` (180-182) only logs and never sets `view.player=null`. The long-lived singleton therefore retains the disposed PlayerView and its Context on every video-screen exit - a recurring View/Context retention, bounded (Wear, limited visits, no per-visit player allocation), not the alleged P0. Downgraded P0->P2. fixSketch: in `VideoPlayerScreen.kt` `VideoPlayerContent`, change `DisposableEffect onDispose` to detach the surface - capture the PlayerView and call `playerView.player = null` on dispose (or use a DisposableEffect keyed to the PlayerView that nulls its player) so the singleton no longer retains the disposed view/Context. Confidence: high.

- `app_v2/src/main/java/com/sza/fastmediasorter/core/util/MediaMetadataHelper.kt:337` - symbol `extractVideoAudioInfo`. Dimension: Memory ownership: unbounded caches, leaked delayed work, unclosed Closeables, leaked scopes (Layer 3). Rationale: `val extractor = MediaExtractor()` at 337; `extractor.release()` at 378 sits inside the try body. The catch (380-381) only logs; the finally (382-384) releases ONLY the `MediaMetadataRetriever`, never the extractor. Any throw between 337 and 378 - `setDataSource` on a corrupt/truncated source, `getTrackFormat(i)`, or `format.getString(KEY_MIME)` on malformed media - propagates to the catch and skips `extractor.release()`, leaking the native MediaExtractor. The method explicitly documents handling partial files lacking a moov atom (381/388), so the exception path is realistic. No other release/`.use{}`/finally covers the extractor; the sibling `SafUriExtractor.extractVideoAudioInfo` (145-176) wraps its extractor work in a nested try/catch + `ParcelFileDescriptor.use`, confirming this path is the asymmetric one. Short-lived per-call local -> conditional native-resource leak on the error path (P2, not P1). fixSketch: hoist `val extractor` outside try (or use a dedicated try/finally) and call `extractor.release()` in a finally so it is released on every path, mirroring the retriever's finally. Confidence: high.

### P3

- `app_v2/src/main/java/com/sza/fastmediasorter/ui/player/VideoPosterExtractor.kt:149` - symbol `tryGlideMemoryCache`. Dimension: Glide/bitmap request ownership. Rationale: in `tryGlideMemoryCache` (138-154) the FutureTarget returned by `.submit()` is consumed inline by `.get(50, MILLISECONDS)` and never assigned, so on TimeoutException (or any exception) `catch (_: Exception){null}` returns without calling `Glide.with(context).clear(future)`. Glide's `RequestFutureTarget.doGet()` does NOT cancel/clear the underlying `SingleRequest` on timeout; the target stays registered with the RequestManager (the documented reason its javadoc requires explicit `clear()` for non-view targets) - so the required release is asymmetrically missing. Call site `VideoPlayerManager.onRenderedFirstFrame` (508-531) runs on `Dispatchers.IO` with the Activity context (`VideoPlayerManager.context`, line 88). Two bounding factors drop below P2: the RequestManager is Activity-lifecycle-tied so orphaned targets clear on Activity `onDestroy` (Activity-scoped churn, not process-wide); and `onlyRetrieveFromCache(true)` prevents network/source loads (worst case a disk-decode timeout), firing once per video first-frame render, not in a tight loop. Real but bounded -> P3. fixSketch: capture the FutureTarget in a `val` and call `Glide.with(context).clear(target)` in a finally so a timed-out/failed request is released instead of left pending. Confidence: medium.

- `app_v2/src/main/java/com/sza/fastmediasorter/core/util/AudioMetadataLoader.kt:87` - symbol `memoryCache`. Dimension: Memory ownership: unbounded caches, leaked delayed work, unclosed Closeables, leaked scopes (Layer 3). Rationale: class is `@Singleton` (line 59); `memoryCache` is a plain `ConcurrentHashMap<String,AudioMetadata>` (line 87) written at 150/188/226 with NO `removeEldestEntry`, NO `.clear()`, NO size cap anywhere in the file or callers (MediaFileAdapter, BrowseResourceLoadManager, PlayerAudioMetadataManager, FileInfoAudioDisplayHelper); the owning scope (line 80) is never cancelled. The asymmetry with the sibling `failedCache` (99-106, FIFO-bounded at `FAILED_CACHE_MAX_SIZE=5000`) is real, so the cache is never evicted for process lifetime. Impact minor: keys are network-only audio paths (`loadIfNeeded` early-returns for local/content paths at line 123), values are tiny `AudioMetadata` data classes (no bitmaps, no Context/View; cover bytes persisted to disk via `saveCover`, not held in the map). Growth bounded in practice by distinct network audio files browsed per session at ~hundreds of bytes each - churn-only, cannot realistically OOM or retain an Activity/Context. Low-impact hygiene gap -> P3. fixSketch: replace the plain ConcurrentHashMap with a bounded `LinkedHashMap` (synchronized, `removeEldestEntry`) mirroring `failedCache`, e.g. cap ~5000 entries, so `memoryCache` gains LRU/FIFO eviction parity with its sibling. Confidence: high.

## Method

Each of the 6 ownership dimensions from Layer 3 of `docs/CODE_AUDIT_PROTOCOL.md` was swept across both Gradle modules (`app_v2` all source sets + `wear/src`) by grepping the relevant registration/acquisition primitives, then Reading each candidate site together with its full lifecycle teardown path; candidates were deduplicated across dimensions (the wear singleton ExoPlayer surfaced under three dimensions and collapses to one `WearAppModule` root cause plus its dependent surface/release symptoms), and every suspected finding was put through adversarial verification - re-deriving the claim against source, refuting overstated angles (the wear Player.Listener "leak" and the alleged P0 per-screen player leak were both refuted as symmetric/intended), corroborating with sibling code (AudioBackgroundPhotosManager, failedCache, SafUriExtractor), and re-rating severity (P1->P2 for bounded singletons, P0->P2 for the surface-only retention, P2->P3 for Activity-scoped Glide churn and the tiny network-path cache) - yielding 9 confirmed findings (0 P0, 0 P1, 6 P2, 3 P3) and 5 rejected candidates.
