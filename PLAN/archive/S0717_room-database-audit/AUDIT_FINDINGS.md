# S0717 Room / Database Audit - Findings

Date: 2026-06-26. Scope: `app_v2` (main app) and `wear` (Wear OS) modules. Method: Layer 4 of `docs/CODE_AUDIT_PROTOCOL.md`, sweeping five dimensions - main-thread Room queries, `@Transaction` atomicity, unbounded queries + cursor handling, missing indexes + N+1 patterns, and Flow-query dedup + schema migrations. Each candidate was deduplicated across dimensions and put through adversarial verification (attempting refutation at code level) before being confirmed and graded. Of 16 verified candidates, 4 were refuted/rejected and 12 are confirmed below. Several findings overlap on `DatabaseModule` (destructive migration + broad-catch delete) and are retained because they surfaced from distinct dimensions; they describe the same code paths and should be remediated together.

## Severity summary

| Severity | Count | Theme |
| --- | --- | --- |
| P0 | 0 | - |
| P1 | 3 | Destructive migration fallback + broad-catch DB delete shipped in release; widget main-thread Room read |
| P2 | 4 | Non-atomic destructive open-catch; non-atomic tile-swap; no migration test gate |
| P3 | 5 | Non-atomic merge/restore (self-healing); N+1 legacy cache migration; Flow re-emit without distinctUntilChanged |

## Confirmed findings

### P1

#### 1. Destructive migration fallback ships in release (atomicity dimension)
- File: `app_v2/src/main/java/com/sza/fastmediasorter/core/di/DatabaseModule.kt:110`
- Symbol: `DatabaseModule.buildDatabase`
- Dimension: `@Transaction` atomicity (Room / DATABASE - Layer 4)
- Confidence: high
- Rationale: Verified and not refutable. `buildDatabase()` chains 35 explicit migrations then unconditionally calls `.fallbackToDestructiveMigration(dropAllTables = true).build()`; there is no debug/variant guard, so the destructive fallback ships in release. `AppDatabase` is `version=36`, `exportSchema=false`, with 17 entities including user-critical data (`ResourceEntity`, `NetworkCredentialsEntity`, `FavoritesEntity`, `ScheduledOperationEntity`, `StreamSourceEntity`). Confirmed zero migration tests: Glob for `*Migration*Test*` returns only the unrelated UI `CollapsibleSectionStateMigrationTest`; the androidTest tree contains no migration test; and `exportSchema=false` means no schema JSONs exist to back a `MigrationTestHelper`. The protocol invariant ("every schema change ships a migration AND a migration test; no destructive fallback in release") is genuinely violated. Adversarial mitigation that downgrades P0 -> P1: (1) the migration chain currently has NO gap - 1->18 plus incremental 2..17->18, 18..30->31, 31..35->36 fully cover version 36 - so the destructive path is not firing on any known upgrade at HEAD; (2) per `dev/CHANGELOG.md` this is a deliberate, documented design re-introduced after a prior real data-loss incident (2026-03-08 "Fix data loss on upgrade"), now paired with a try/catch auto-reset + user-facing toast (`provideAppDatabase`, lines 45-65) as a chosen last-resort to avoid hard crashes. The defect is a latent regression-prevention gap (a future schema change can ship a silent full-table wipe undetected), not an actively-firing catastrophic data-loss bug. Real and ticket-worthy, but P1 not P0.
- fixSketch: Set `exportSchema=true` with a `schemaLocation`, add a Room `MigrationTestHelper` androidTest covering 1->36 (and each new bump), and in release replace the bare destructive fallback with a guarded path (e.g. backup-then-reset or `fallbackToDestructiveMigrationFrom` only for known-bad versions) so an unhandled migration cannot silently drop user tables.

#### 2. Destructive migration fallback reachable in release (Flow/migrations dimension)
- File: `app_v2/src/main/java/com/sza/fastmediasorter/core/di/DatabaseModule.kt:110`
- Symbol: `buildDatabase / fallbackToDestructiveMigration(dropAllTables = true)`
- Dimension: Flow-query dedup and schema migrations (Room 2.7.0)
- Confidence: high
- Rationale: Verified in `DatabaseModule.kt:110` - `buildDatabase()` unconditionally calls `.fallbackToDestructiveMigration(dropAllTables = true)`, and it is the sole DB builder used by `provideAppDatabase` for every flavor/variant with no `BuildConfig.DEBUG` guard (grep found the call only in this one production file). `AppDatabase.kt` (`@Database version=36, exportSchema=false`) holds irreplaceable user data - `ResourceEntity`, `NetworkCredentialsEntity`, `FavoritesEntity`, `ScheduledOperationEntity`, `StreamSourceEntity`, `AppLaunchPanelTileEntity` - not just caches, so destruction is real data loss. Refutation failed on every axis: not debug-only, not a small/cache table, and there is NO migration test gate (`exportSchema=false` plus zero `MigrationTestHelper`/`schemaLocation`/`runMigrationsAndValidate` hits across the repo; the lone `*MigrationTest` file is an unrelated UI widget-state test). `provideAppDatabase` even adds a second destructive path: any migration `Exception` triggers `context.deleteDatabase(DB_NAME)` then rebuild. Downgraded from P0 to P1 because current migrations 1->36 are complete and the schema matches version 36, so no active data loss exists today - this is a latent foot-gun (any future schema bump shipped without a matching/working `Migration` silently wipes everything in release) rather than a live crash/corruption.
- fixSketch: Gate destructive fallback to debug only (e.g. apply `.fallbackToDestructiveMigration(true)` and the catch-all `deleteDatabase` only when `BuildConfig.DEBUG` via a flavor-neutral interface), set `exportSchema=true`, and add a Room `MigrationTestHelper` test that runs every migration to version 36 in CI.

#### 3. Widget refresh runs Room Flow query on the main thread
- File: `app_v2/src/main/java/com/sza/fastmediasorter/widget/ScheduledTasksWidgetProvider.kt:123`
- Symbol: `ScheduledTasksWidgetProvider.updateAppWidget`
- Dimension: main-thread Room access
- Confidence: high
- Rationale: Independently verified against source. `ScheduledOperationDao.getAll()` (`ScheduledOperationDao.kt:14`) returns `Flow<List<...>>` and is NOT suspend; `ScheduledOperationRepositoryImpl.getAll()` (line 20-21) re-exposes that Flow. `SettingsRepositoryImpl.getSettings()` (line 240-241) returns a Flow backed by DataStore (`dataStore.data`). In `updateAppWidget` (`ScheduledTasksWidgetProvider.kt:123-131`) both are collected via `.first()` inside a plain `runBlocking { }` with NO dispatcher argument, so the call blocks the calling thread on the Room read plus a DataStore read until first emission. `updateAppWidget` is invoked synchronously from the framework `onUpdate` (line 46-53), which `AppWidgetProvider` (a `BroadcastReceiver`) dispatches on this app process's main thread - so the main thread blocks on DB+DataStore I/O. Refutation attempts failed: (a) not main-safe - method is Flow, not suspend, and no `Dispatchers.IO`; (b) the `goAsync`/`Dispatchers.IO` offload exists only on the `onReceive` action branch (line 62-63) and the re-renders at line 92, NOT on the `onUpdate` entry path - this asymmetry confirms the IO concern was known but missed here; (c) table scale is not the gating factor - real ANR/jank risk is DB lock contention (a concurrent WorkManager/`ExecuteScheduledOperationUseCase` write transaction stalls the main-thread read). Genuine main-thread blocking-I/O defect. Downgraded from P1 to P2 in the per-finding verdict, but reads are normally fast and the table is small, so it is jank/ANR-risk rather than a guaranteed ANR.
- Note: Per-finding verdict severity is P2 (jank/ANR-risk, not guaranteed ANR); grouped under P1 in the suspected list. Treat as the highest-priority main-thread item.
- fixSketch: Move the status read off the main thread: in `onUpdate` use `goAsync()` + `CoroutineScope(Dispatchers.IO)` (as `onReceive` already does) to fetch ops/settings, then post `updateAppWidget`; or split the `runBlocking` into `withContext(Dispatchers.IO)` so the Flow `.first()` collection no longer blocks the main thread.

### P2

#### 4. Broad-catch DB delete on any open exception (Flow/migrations dimension)
- File: `app_v2/src/main/java/com/sza/fastmediasorter/core/di/DatabaseModule.kt:50`
- Symbol: `provideAppDatabase catch block / context.deleteDatabase(DB_NAME)`
- Dimension: Flow-query dedup and schema migrations (Room 2.7.0)
- Confidence: high
- Rationale: Verified against source. `provideAppDatabase` in `DatabaseModule.kt` (lines 45-65) force-opens `writableDatabase` and wraps it in `catch (e: Exception)` that unconditionally calls `context.deleteDatabase(DB_NAME)` then rebuilds an empty DB, with only a Toast. The data-loss claim is accurate. This is a real ADDITIONAL destructive path beyond the Room-internal `fallbackToDestructiveMigration(dropAllTables=true)` at line 110: the catch swallows EVERY `Exception` kind from open/migration - not just missing-migration version mismatches that Room handles, but also transient/recoverable failures (`SQLiteFullException` disk-full, `SQLiteDiskIOException`, locking/`IllegalStateException`) and buggy-migration throws. On any of these it permanently destroys NON-reconstructable user data: `ResourceEntity`, `NetworkCredentialsEntity`, `FavoritesEntity`, `ScheduledOperationEntity`, `StreamSourceEntity`, `AppLaunchPanelTileEntity`, `InputBindingEntity` - confirmed in `AppDatabase.kt` `@Database` entities (v36). No backup/export/telemetry is taken before deletion. Caveats that lower it from P0: this is an error-path, not the happy path - it requires an exception during DB open/migration, so it does not fire in normal operation; it is a DI/open-time concern, not the Flow-query-dedup dimension the finding's label states (label is misframed, substance is correct). Severity P2: silent, unrecoverable loss of user config on transient/recoverable errors in release builds.
- fixSketch: Narrow the catch to genuine-corruption types only (`SQLiteCorruptException`/`SQLiteDatabaseCorruptException`) and rethrow others; before `deleteDatabase`, copy the `.db` file to a timestamped backup in `temp/` (or trigger an export) so recovery is possible, and log via Timber with cause class for telemetry instead of relying on a Toast.

#### 5. Broad-catch DB delete compounds destructive-fallback risk (atomicity dimension)
- File: `app_v2/src/main/java/com/sza/fastmediasorter/core/di/DatabaseModule.kt:50`
- Symbol: `DatabaseModule.provideAppDatabase`
- Dimension: `@Transaction` atomicity (Room / DATABASE - Layer 4)
- Confidence: high
- Rationale: Verified against `DatabaseModule.kt:44-65`, `AppDatabase.kt` (`@Database version=36`), `NetworkCredentialsEntity.kt`, and `dev/CHANGELOG.md` history. The code matches the finding: `provideAppDatabase` force-opens `writableDatabase` and on `catch (e: Exception)` calls `context.deleteDatabase(DB_NAME)` then rebuilds fresh, plus `fallbackToDestructiveMigration(dropAllTables=true)` is set unconditionally in `src/main` (line 110), violating the project's own rule ("Never `fallbackToDestructiveMigration()` in prod"). The dimension label "@Transaction atomicity" is a mislabel - this is not a DAO write/atomicity issue - but the substantive data-loss claim holds. Refutation attempts failed: (1) destructive config is NOT debug-only; (2) the broad catch is a SECOND destructive trigger beyond Room's missing-migration fallback - it also fires on failing migrations AND transient `SQLiteException`/`SQLiteDiskIOException`/locked-file errors at first open, where a retry would recover; (3) the wiped data is durable, irreplaceable user config (`NetworkCredentialsEntity` stores server/username/encrypted password/SSH keys, plus `ResourceEntity`, `FavoritesEntity`, `StreamSourceEntity`, `ScheduledOperationEntity`), not just regenerable cache; (4) there is no retry, no backup, and no copy-before-delete. CHANGELOG shows the team already reverted destructive migration once for "data loss on upgrade" (2026-03-08) then re-added it with a toast (2026-03-11), so the destructive-fallback itself is an accepted product decision - that mitigation plus the relative rarity of a transient first-open failure caps incremental severity below P1. Real defect: a transient/non-corruption open error is treated identically to corruption and irreversibly wipes credentials.
- fixSketch: Narrow the catch to corruption-only (`SQLiteDatabaseCorruptException` / `IllegalStateException` from migration), back up the `.db` file before `deleteDatabase`, and add a bounded retry for transient `SQLiteException`/locked/disk-IO errors instead of wiping.

#### 6. Non-atomic tile-swap permanently loses a launch tile on crash
- File: `app_v2/src/main/java/com/sza/fastmediasorter/data/repository/AppLaunchPanelRepositoryImpl.kt:25`
- Symbol: `AppLaunchPanelRepositoryImpl.moveTile`
- Dimension: `@Transaction` atomicity (Room / DATABASE - Layer 4)
- Confidence: high
- Rationale: Verified independently. `moveTile` (`AppLaunchPanelRepositoryImpl.kt:25-38`) does a read-modify-write across 4 separate writes: `deleteBySlot(fromSlot)`, `deleteBySlot(toSlot)`, `upsert(source.copy)`, conditional `upsert(target.copy)`. The DAO (`AppLaunchPanelTileDao.kt`) has every method as a plain `@Insert`/`@Query` suspend call with NO `@Transaction`; confirmed zero `withTransaction`/`runInTransaction` in the whole codebase and `@Transaction` present only in `ResourceDao`. The entity (`AppLaunchPanelTileEntity`) is durable user config (`type`/`targetId`/`labelOverride`/`addedAt`) with `slotIndex` as `@PrimaryKey` - not a rebuildable cache, and there is no reconstruction source, so a process kill or thrown exception after the two deletes but before the upserts permanently drops the source tile's config (it lives only in the in-memory `source` var). The atomicity gap is real. Refutations that lower severity: all DAO calls are suspend on `viewModelScope` (main-safe, not ANR); the table is a fixed 0..14 / 15-slot grid per the entity KDoc, not library-scaled, so blast radius is at most one tile; the loss window is the brief gap between two local-SQLite writes; there is no concurrency amplifier and no broader corruption; and the user can re-add the tile. Real but bounded and recoverable - P2.
- fixSketch: Add a `@Transaction suspend` method on `AppLaunchPanelTileDao` (or wrap in `db.withTransaction { }`) that performs the two `deleteBySlot` + two `upsert` calls atomically, and have `moveTile` call it.

#### 7. No migration test gate; exportSchema disabled
- File: `app_v2/src/main/java/com/sza/fastmediasorter/data/local/db/AppDatabase.kt:33`
- Symbol: `@Database(version = 36, exportSchema = false)`
- Dimension: Flow-query dedup and schema migrations (Room 2.7.0)
- Confidence: high
- Rationale: Verified the factual claims directly. `exportSchema=false` at `AppDatabase.kt:33` with no checked-in `schemas/` source dir; zero `MigrationTestHelper` / migration-test class hits; androidTest has no migration test. In `DatabaseModule.kt` the fallback is `.fallbackToDestructiveMigration(dropAllTables = true)` at line 110 and is UNCONDITIONAL - not `BuildConfig.DEBUG`-gated - and `provideAppDatabase` (lines 45-64) catches any migration failure, calls `context.deleteDatabase(DB_NAME)`, shows only a Toast, and rebuilds empty. So user-owned tables (resources, network_credentials, scheduled_operations, favorites) can be wiped on a broken migration. The genuine defect is the resilience/coverage gap: a column-order/type/hash mismatch from a future migration is resolved by silently destroying user data, and no migration test exists to catch it before release. However the suspected P1 is overstated: (1) the evidence's central technical claim is WRONG - Room still validates the runtime schema hash against the compiled-in `identityHash` even with `exportSchema=false` (`exportSchema` only governs writing JSON snapshots for tooling), so a mismatch fails LOUDLY with `IllegalStateException`, it is not "undetected"; (2) the migrations are unusually defensive - `hasColumn`/`hasTable`/`hasIndex`/`ensureIndex` idempotency guards plus `IF NOT EXISTS` throughout - lowering the odds of a silently-bad migration; (3) all PRAGMA/`sqlite_master` cursors are closed via `.use{}` (lines 741-781), so no cursor-leak issue. No DAO/Flow/atomicity concern is implicated. Net: a real robustness gap (no migration test + unconditional destructive wipe) but not an active data-corruption bug; P2.
- fixSketch: Set `exportSchema=true`, commit `schemas/` JSON, add a Room `MigrationTestHelper` test covering 1->36, and gate `fallbackToDestructiveMigration` to debug-only (release should surface the failure / attempt backup rather than silently wipe).

### P3

#### 8. Non-atomic catalog merge (self-healing cache)
- File: `app_v2/src/main/java/com/sza/fastmediasorter/data/repository/StreamSourceRepository.kt:64`
- Symbol: `StreamSourceRepository.mergeCatalog`
- Dimension: `@Transaction` atomicity (Room / DATABASE - Layer 4)
- Confidence: high
- Rationale: Verified against source: `StreamSourceRepository.mergeCatalog` (lines 64-90) issues N `updateCatalogByUrl`/`insertIgnore` writes then a final `deleteCatalogNotIn` with NO `@Transaction`/`withTransaction`/`runInTransaction` (grep across data layer confirms none for this table; only unrelated `ResourceDao` uses transactions). The non-atomicity claim is factually true. However the suspected P2 overstates impact, and three refutation angles weaken it: (1) all `StreamSourceDao` methods are suspend (main-safe) and each is its own atomic SQLite transaction, so no row is half-written; a real partial commit needs an abnormal process kill (OS/power) in a narrow window between writes - an ordinary `SQLiteException` is caught by `ImportStreamCatalogUseCase`'s try/catch and returned as Failure, not a crash. (2) The table is a re-fetchable CATALOG cache that fully self-heals on the next import. (3) MANUAL/IMPORTED user rows are never touched - every catalog write is scoped `WHERE sourceOrigin='CATALOG'` and `insertIgnore` returns -1 on a user-owned url. `url` is a unique index and `id` is the PK, so no missing-index angle. Worst real outcome after an abnormal kill: transiently stale/partial catalog rows in `observeSources()` until next import - no data loss, no corruption, no crash. Real but minor - P3.
- fixSketch: Wrap the per-row writes + `deleteCatalogNotIn` in `mergeCatalog` inside a single Room transaction (`db.withTransaction { .. }` or a `@Transaction suspend` DAO/repository method) so the merge commits atomically and emits one `observeAll()` update.

#### 9. Non-atomic full backup restore (merge-only, re-runnable)
- File: `app_v2/src/main/java/com/sza/fastmediasorter/domain/usecase/ApplyBackupPayloadUseCase.kt:43`
- Symbol: `ApplyBackupPayloadUseCase.invoke`
- Dimension: `@Transaction` atomicity (Room / DATABASE - Layer 4)
- Confidence: high
- Rationale: Verified the claim is structurally accurate but over-rated. `invoke()` (`ApplyBackupPayloadUseCase.kt:43-170`) runs 6 sequential sections with no overarching transaction. `AppDatabase.kt`: credentials/resources/favorites/scheduled_operations entities all live in one Room `AppDatabase` (v36), so sections 2-5 COULD be wrapped in a single `withTransaction{}` but are not - confirming the non-atomicity. However: (1) DAOs are suspend (`FavoritesDao.kt` all suspend) so no ANR/main-thread issue; (2) settings live in DataStore Preferences (`SettingsRepositoryImpl.kt:40`) and webAuthSessions in `EncryptedCookieStore` (`AuthSessionRepositoryImpl.kt:23`), so a Room `@Transaction` cannot span the whole restore - full-restore atomicity is architecturally impossible, only the Room subset is wrappable; (3) restore is merge-only by key (`credentialId` / `path+type` / `uri`) with no pre-wipe, plus per-item try/catch, so a process death mid-loop leaves an incomplete-but-not-corrupt state that re-running fully repairs; (4) favorites store `resourceId` resolved at insert time with no FK constraint, so no dangling-reference corruption results. Net: a real durability gap (observable partial restore after a crash) but recoverable, low-likelihood, no corruption/ANR - P3.
- fixSketch: Wrap the Room-backed sections (credentials, resources, favorites, scheduled ops) in a single `appDatabase.withTransaction { }` so the relational subset commits atomically; settings/web-sessions stay outside as separate stores.

#### 10. Non-atomic legacy XML import (merge-only, re-runnable)
- File: `app_v2/src/main/java/com/sza/fastmediasorter/domain/usecase/ImportSettingsUseCase.kt:376`
- Symbol: `ImportSettingsUseCase.invoke (legacy XML path)`
- Dimension: `@Transaction` atomicity (Room / DATABASE - Layer 4)
- Confidence: high
- Rationale: Verified the legacy XML path in `ImportSettingsUseCase.kt` (lines 367-503): settings, credentials, resources, then scheduled ops are written sequentially with no `withTransaction`/`runInTransaction` wrapper - confirmed no transaction primitive exists in the repository layer (`ScheduledOperationRepositoryImpl`, grep for `withTransaction`/`@Transaction`). So the atomicity gap is real. However the suspected P2 overstates impact: (1) all DAO ops are suspend = main-safe, no ANR angle. (2) Mid-import failure does NOT crash or orphan data - scheduled ops resolve source/target from the post-merge live DB (lines 454-477) and on a miss skip with `Timber.w` + `return@forEach`, not an exception; `ScheduledOperationEntity` FKs use `onDelete=CASCADE`, so a dangling op referencing a nonexistent resource is impossible by construction. (3) The whole import is idempotent/re-runnable: resources merge by `path|type` keeping existing id, credentials merge by `credentialId`, ops upsert - re-running after a crash converges to the full correct state. (4) Decisive refutation of the "legacy defect" framing: the modern/primary JSON restore path `ApplyBackupPayloadUseCase.invoke` does the IDENTICAL multi-section non-atomic sequence. So this is the deliberate, consistent design of the entire backup/restore subsystem, not a legacy-path oversight. (5) Runs only on an explicit, rare, user-initiated import action - not a hot path, not library-scaled. Worst realistic outcome is a half-applied import the user simply re-runs. Real but low impact - P3.
- fixSketch: Wrap the apply-all sequence (both XML import and `ApplyBackupPayloadUseCase`) in a single Room `db.withTransaction { }` so settings/credentials/resources/ops commit atomically; do the `WorkManager.scheduleOperation` calls after the transaction commits.

#### 11. N+1 full-table load in legacy thumbnail cache migration
- File: `app_v2/src/main/java/com/sza/fastmediasorter/data/repository/ThumbnailCacheRepositoryImpl.kt:252`
- Symbol: `ThumbnailCacheRepositoryImpl.migrateLegacyCache`
- Dimension: Room/Database unbounded queries and cursor handling
- Confidence: high
- Rationale: Verified directly. In `migrateLegacyCache()` (line 230), `oldFiles.forEach` (line 248) calls `thumbnailCacheDao.getAllThumbnails()` (line 252) inside the loop. `ThumbnailCacheDao.getAllThumbnails()` (DAO line 84) is `@Query("SELECT * FROM thumbnail_cache")` with no LIMIT/WHERE/projection, returning the entire table as a List each call. The result is only used for `entries.find { File(it.thumbnailPath) == oldFile }` - a linear scan that is also re-walked per file. Net cost is O(legacyFiles x cacheRows), and both scale with library size (~one thumbnail file per cached row), so it is genuinely quadratic. Refutation caps severity: (1) off-main - `migrateLegacyCache` is suspend, invoked from `AppStartupInitializer.migrateThumbnailCache()` -> `runDeferredStartupTasks()`, which runs inside `DeferredStartupWorker` (`CoroutineWorker`, off the UI thread), so no ANR; (2) the DAO method is suspend (Room main-safe); (3) one-time per upgrade - migration only fires when legacy `cacheDir/thumbnails` exists and deletes that dir on completion (line 282); (4) the migrating population shrinks (only users upgrading from the old `cacheDir` scheme); (5) `thumbnail_cache` is LRU size-capped elsewhere, bounding n. No atomicity/cursor-leak/destructive-fallback involved. Real but bounded to first launch after upgrade - P3.
- fixSketch: Hoist `getAllThumbnails()` out of the loop once into a Map keyed by `thumbnailPath` (or by `File(thumbnailPath)`), then look up per `oldFile` inside the forEach.

#### 12. Favorites Flow re-emits without distinctUntilChanged
- File: `app_v2/src/main/java/com/sza/fastmediasorter/data/repository/FavoritesRepositoryImpl.kt:18`
- Symbol: `getAllFavorites() / FavoritesDao.getAllFavorites + isFavorite`
- Dimension: Flow-query dedup and schema migrations (Room 2.7.0)
- Confidence: high
- Rationale: Verified DAO (`FavoritesDao.kt`), entity (`FavoritesEntity.kt`), repo (`FavoritesRepositoryImpl.kt:18-24`), and call sites. Core claim is factually correct: both `getAllFavorites()` and `isFavorite()` pass the raw Room Flow through with no `distinctUntilChanged`. Room observes at table granularity via `InvalidationTracker`, so any write to the favorites table re-emits even when the result value is unchanged. Refutation axes mostly fail to kill it but greatly shrink impact: (1) main-safety - both are Flows collected on `ioDispatcher` (`BrowseStateSyncManager.loadFavorites`), no main-thread DB work; (2) indexing - `uri` has unique index `idx_favorites_uri` and `isFavorite` is an EXISTS point lookup, so each redundant re-query is cheap; (3) atomicity - `insert`/`deleteByUri` are single statements; (4) cursor `.use{}` present in raw queries; (5) no `fallbackToDestructiveMigration` in this scope. Impact is over-stated: the `isFavorite` Flow has ZERO live collectors in `app_v2/main` (production toggle uses `isFavoriteSync`; Flow variant only appears in `.first()` tests), so "re-emit identical Boolean to UI observers" does not actually occur. `getAllFavorites` Flow has exactly one live collector (`BrowseStateSyncManager`) which does redundant work (full list rebuild + cache rewrite + `updateState`) on each favorites write - but favorites is a small, user-curated table written only on user toggle, not library-scaled or high-frequency. Real but trivial inefficiency, not a correctness bug - P3.
- fixSketch: Wrap both repo Flows in `.distinctUntilChanged()` at the `FavoritesRepositoryImpl` boundary (lines 19, 23) to suppress redundant re-emissions to the `BrowseStateSyncManager` collector.

## Coverage notes

### main-thread Room access
`wear/src` has NO Room database (no `@Database`/`@Dao`/`@Entity`/`RoomDatabase` anywhere under `wear/src` - confirmed). `allowMainThreadQueries()` appears only in test code (`InMemoryRoomHelper.kt`, acceptable). Full DAO enumeration done across all 17 DAOs in `app_v2/src/main`: every method is suspend or returns Flow/LiveData (main-safe by Room contract) EXCEPT (a) the documented S0677 `ThumbnailCacheDao *Blocking` twins, called only from Glide's decode/data-fetch executor threads (`NetworkVideoFrameDecoder`, `ThumbnailCacheRepositoryImpl` blocking twins) - off-main by Glide contract, safe; and (b) the two `ResourceDao` blocking queries, which are `withContext(IO)`-wrapped. All `db.query(...)` direct SupportSQLite calls are inside Migration code (Room migration thread, off-main). All `contentResolver.query(...)` hits are MediaStore, not Room (out of scope). Other `runBlocking` sites over Room (`FavoritesWidgetService.onDataSetChanged`, `ScheduledTasksWidgetService.onCreate/onDataSetChanged`) run on the framework `RemoteViewsFactory` binder background thread, not main - safe. `RandomPhotoFrameWidgetRefresher` uses `runBlocking(Dispatchers.IO)`. `MainActivity.kt:733` `runBlocking` reads DataStore (`getSettings`), not Room - out of scope for this dimension (separate Layer 5 main-thread DataStore concern). Not truncated. Confirmed defects: 1.

### @Transaction atomicity (Room / DATABASE - Layer 4)
Full coverage. Schema located at `app_v2/src/main/.../data/local/db` (`AppDatabase` v36, 17 entities, 17 DAOs); `wear/src` has NO Room database (grep for `@Database`/`@Dao`/`RoomDatabase` returned zero). ### Room/Database unbounded queries and cursor handling

## Method
Per Layer 4 of `docs/CODE_AUDIT_PROTOCOL.md`, the audit swept five dimensions (main-thread Room queries, `@Transaction` atomicity, unbounded queries + cursor handling, missing indexes + N+1, Flow-query dedup + schema migrations) across `app_v2` and `wear`. Candidates were deduplicated across dimensions (e.g. the `DatabaseModule` destructive-fallback and broad-catch findings surfaced from both the atomicity and migrations sweeps). Each candidate was then adversarially verified: the symbol, file:line, DAO signatures, entity declarations, call sites, dispatcher context, and migration chain were read directly, and an explicit refutation pass attempted to disprove the claim (debug-only? cache-only? off-main? indexed? self-healing?). Findings that survived refutation were graded by real-world impact, which downgraded several suspected severities (P0->P1, P2->P3). 16 candidates were verified; 4 were refuted/rejected, leaving the 12 confirmed findings above. No `EXPLAIN QUERY PLAN` or runtime profiling was run - this is a static code-level audit.
