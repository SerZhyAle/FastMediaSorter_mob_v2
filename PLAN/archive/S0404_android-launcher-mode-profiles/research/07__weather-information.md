# 07 - Источник погодной информации (независимый info-блок домашнего экрана)

**Связано с §6 спеки S0404 (новый item) и §5.3 (расширяемость info-блоков).** Дата: 2026-06-15.

Пожелание: на домашней поверхности лаунчера (в первую очередь профиль «фоторамка») показывать погоду рядом с часами/датой. Это **независимый источник информации**, который подключается к уже спланированному контракту info-блоков профиля (§5.3: «..позже добавлять источники (например, погода/уведомления) без изменения контракта профиля»). Launcher-ядро (роль Home, реестр приложений, строка состояния, профили) при этом не меняется. Поэтому погода не входит в объём итерации-1 S0404 и кандидат на вынос в отдельный технический спек.

## Что нужно для погоды на устройстве

Три ортогональных вопроса: откуда данные (weather API), для какой точки (локация), и как часто обновлять (батарея/сеть).

## 1. Источник данных (weather API)

- **Open-Meteo** - бесплатный, без API-ключа, без регистрации; отдельные эндпоинты прогноза и геокодинга (город → координаты). Лимиты free: <10 000 вызовов/день, 5 000/час, 600/мин - с запасом для одного устройства с редким обновлением. Коды погоды - стандартные WMO. **Ограничение:** free-tier лицензирован **только для non-commercial** использования; данные под CC-BY 4.0 - обязательна атрибуция «Weather data by Open-Meteo.com» рядом с показом. Коммерческое использование / выше лимитов требует платной подписки с выделенным эндпоинтом и API-ключом.
- **OpenWeatherMap** - free-tier требует API-ключа. Ключ, зашитый в APK, извлекаем из пакета (риск утечки/злоупотребления квотой). Тоже свои ограничения на коммерцию.
- **Прочие keyless-источники** (wttr.in и т.п.) - без SLA/гарантий, не подходят как основной источник для постоянно работающего устройства.

**Развилка для коммерции.** Приложение публикуется в Play (флейворы `standard`/`legacy`/`photos`) и имеет платные аспекты - значит non-commercial free-tier Open-Meteo формально неприменим на Play-флейворах. Возможные ответы (решение - в техническом спеке):

- платная подписка Open-Meteo + API-ключ через секрет-конфиг (не в `src/main`-открыто);
- источник на Play-флейворах с коммерчески-дружественной лицензией, free-tier Open-Meteo - только на `noLegal` (сайдлоад, вне Play);
- BYO-key: пользователь вводит собственный ключ выбранного провайдера (перекладывает лицензию/квоту на него) - уместно для выделенных устройств.

## 2. Локация (для какой точки погода)

- **Ручной ввод города** - **без каких-либо разрешений**: пользователь вводит название → геокодинг (например, Open-Meteo Geocoding, keyless, 300k+ городов, многоязычно) → координаты. Идеален для стационарной фоторамки/медиабокса, который не двигается. Должен быть путём по умолчанию.
- **Автолокация по `ACCESS_COARSE_LOCATION`** - приблизительная точность (~3 км) более чем достаточна для погоды; это runtime-разрешение на API 23+. `ACCESS_FINE_LOCATION` для погоды не нужен. Опционально, с деградацией к ручному вводу при отказе/отсутствии служб локации.
- **Без локации вовсе** - блок просто не показывается, если город не задан и автолокация не разрешена. Никаких падений.

Согласуется с правилом доступности/привилегий S0404: на базовом уровне не запрашивать лишних чувствительных прав; coarse-локация - опт-ин, не обязательное условие фичи.

## 3. Обновление, сеть, кэш

- Сеть: нужен только `INTERNET` (уже декларирован). `ACCESS_NETWORK_STATE` (normal) уже нужен строке состояния S0404 - переиспользуется для «нет сети → показать кэш».
- Батарея: устройство-фоторамка работает постоянно → редкий интервал обновления (порядка 15-30 мин), кэш последнего ответа, без поллинга на каждый возврат на Home. Совпадает с требованием производительности §3.2 S0404 (лёгкая отрисовка, ленивые источники).
- Деградация: при отсутствии сети показывать последний кэш с пометкой устаревания; при пустом кэше - блок скрыт.

## Архитектурная вписка (почему независимо)

- Погода - реализация контракта info-блока профиля (§5.3), а не часть launcher-ядра. Добавление/удаление блока не меняет роль Home, реестр приложений и строку состояния.
- Слой данных - обычный Clean-стек: `WeatherRepository` (источник + кэш) ← `GetWeatherUseCase` ← VM info-блока. Источник абстрагирован интерфейсом, чтобы менять провайдера без переписывания UI.
- Флейвор-разделение лицензии источника ложится на ту же дисциплину source-set'ов, что и реестр приложений в S0404 (контракт в `src/main/`, провайдер по флейвору) - но это уже детализация технического спека.

## Выводы для спеки

- Погода **технически тривиальна и независима**: keyless-источник (Open-Meteo) + ручной ввод города дают рабочий блок **без новых чувствительных разрешений**.
- Единственный нетривиальный вопрос - **лицензия источника под коммерческий Play-релиз** (non-commercial free-tier неприменим на `standard`); это owner-решение, а не технический блокер.
- Реализацию правильно **вынести в отдельный независимый спек (S0426)**, а не раздувать итерацию-1 S0404: погода не нужна для роли Home и запуска приложений, и должна уметь жить как опциональный блок в любом профиле.
- В S0404 ничего реализовывать не нужно - достаточно сохранить расширяемость контракта info-блоков (§5.3 уже это гарантирует).
