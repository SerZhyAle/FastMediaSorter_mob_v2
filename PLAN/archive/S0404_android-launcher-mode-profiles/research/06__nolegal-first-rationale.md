# 06 - noLegal-first: обоснование порядка и лестница способностей

**Связано с §6 спеки S0404 (новый item).** Дата: 2026-06-11.

Владелец: сначала отработать режим лаунчера на `noLegal`, потом перенести на `standard`. Это технически обоснованно, а не просто порядок работ.

## Почему noLegal первым

- **noLegal - сайдлоад-флейвор, не публикуется в Play** (см. `app_v2/build.gradle.kts` и `dev/CATALOG`-память: `standard ⊂ vr ⊂ noLegal`, noLegal - всё-инклюзивный сайдлоад). Значит, на него **не распространяются ограничения Play Console**: допустимы агрессивные подходы (широкая видимость пакетов, device-admin/owner-сценарии, kiosk), которые в Play либо запрещены, либо требуют деклараций/ревью.
- **Целевые устройства фичи - выделенные** (настенная фоторамка, медиабокс, читалка). Их провизионят один раз вручную → реально сделать приложение **device owner** через `adb dpm set-device-owner`, что разблокирует полный kiosk и собственную строку состояния (см. `04`). Для сайдлоада это органичный сценарий установки.
- На noLegal можно сразу строить **полный** режим лаунчера (kiosk + свой status bar + полный список приложений), не оглядываясь на Play-политику, и отладить его.

## Лестница способностей (capability ladder)

Одна и та же фича существует на двух уровнях; флейвор выбирает доступный максимум:

- **Полный (noLegal, + device owner):** системный status bar скрыт, собственный бар постоянный; lock task без подтверждения (истинный kiosk); полный список приложений; запуск настроек Android; гарантированный секретный выход.
- **Базовый (standard, Play-safe):** домашняя поверхность как Home-роль; immersive sticky + оверлейный собственный бар (системный бар достижим свайпом); перечисление приложений только Play-совместимым способом (`<queries>`, без `QUERY_ALL_PACKAGES`); запуск настроек Android; обычные переходы. Без device owner / kiosk-блокировки.

`legacy`/`photos` идут по базовому уровню (как `standard`), с поправкой на возможности флейвора (`photos` - только профиль фоторамки, см. `03`). `lite` - под вопросом владельца. `vr` исключён.

## Архитектурное следствие

- Способность лаунчера абстрагируется интерфейсом в `src/main` с **флейвор-специфичными реализациями разного уровня**: noLegal-реализация несёт kiosk/owner/собственный-бар-полный; standard/legacy/photos - базовый Play-safe вариант; vr/lite - «нет-способности». Это укладывается в `dev/FLAVOR_DEVELOPMENT_RULES.md` (интерфейс + flavor source sets + flavor Hilt-модули), без `BuildConfig.IS_*` в общем коде.
- Порядок реализации (когда дойдёт до тактики): общий контракт и базовый уровень → полный уровень в noLegal → перенос Play-safe подмножества в standard. Это разные тактические объёмы; не смешивать в одной волне.

## Выводы для спеки

- noLegal-first - не «сначала там, потом скопировать», а **разные уровни одной способности**: полный (kiosk/owner) технически возможен только вне Play.
- Флейвор-контракт должен допускать уровень способности, а не только её наличие/отсутствие.
- Device-owner-провизионинг - операционное требование к устройству для полного уровня, фиксируется как ограничение, а не реализуется «по кнопке».
