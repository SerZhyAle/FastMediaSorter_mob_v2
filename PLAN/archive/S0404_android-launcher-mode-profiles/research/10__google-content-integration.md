# 10 - Операции с Google-контентом на домашней поверхности

**Связано с §6 спеки S0404 (новый независимый item 10).** Дата: 2026-06-15.
**Породил спек:** `PLAN/S0429_home-screen-google-content.md` (research → возможный технический спек).

## Запрос

С домашней поверхности лаунчера (S0404) «оперировать с Google-контентом»: YouTube, музыка (YouTube Music), Gmail, Google Keep и т.п. - показывать контент-блоки и/или запускать действия, в идеале не уходя в чужое приложение. Как и call/SMS (item 9), это укладывается в лестницу способностей эпика: Play-safe базовый уровень на всех флейворах + более глубокий уровень там, где это допустимо.

## Главное ограничение (дороже, чем у других items)

Любой доступ к *данным* пользователя в Google-сервисах (письма Gmail, заметки Keep, подписки/история YouTube, файлы Drive) - это **OAuth 2.0** через Google Identity Services / Google Sign-In + проект Google Cloud + экран согласия (OAuth consent screen) + scope под каждое API.

- **Sensitive** и тем более **restricted** scope (Gmail, контент Drive) требуют **верификации приложения** в Google, а restricted - дополнительно ежегодной независимой **security assessment (CASA)**. Это серьёзная стоимость и постоянный комплаенс для публикуемого приложения.
- Верификация OAuth-клиента - на стороне Google-аккаунта, **не Play**. Поэтому restricted scope одинаково тяжелы и на `standard` (Play), и на `noLegal` (сайдлоад): сайдлоад не обходит верификацию OAuth.
- **Вывод:** «дорогой» уровень - не флейворная развилка, как обычно в S0404, а продуктово-комплаенсное owner-решение. Дешёвые уровни (deep-link, MediaController) OAuth не требуют вовсе.

## По сервисам

### YouTube
- **Данные:** YouTube Data API v3 (OAuth + API-ключ, дневная квота) - поиск, каналы, плейлисты, подписки, метаданные видео. Чтение подписок/активности аккаунта = OAuth (account-scoped).
- **Воспроизведение:** нативный **YouTube Android Player API устарел** и не поддерживается. Встроить плеер на Android реально только через **IFrame Player API в WebView** (веб-путь, с ограничениями ToS). Чистого нативного «проиграй это видео у меня в приложении» нет.
- **Реалистично:** deep-link в приложение YouTube (`vnd.youtube:<id>` / `https://youtu.be/<id>` через `ACTION_VIEW`) для воспроизведения; Data API - для glance-метаданных (например «свежее из подписок»), если добавлен OAuth.

### Музыка (YouTube Music)
- Google Play Music закрыт в 2020 - неактуален.
- У YouTube Music **нет публичного API**.
- **«Сейчас играет» достижимо БЕЗ какого-либо Google API** через Android-механизм медиасессий: `MediaSessionManager.getActiveSessions(...)` в связке с `NotificationListenerService` (special access `BIND_NOTIFICATION_LISTENER_SERVICE`, выдаётся пользователем в системных настройках). Лаунчер читает активный `MediaController` (название/исполнитель/обложка) и шлёт транспортные команды (play/pause/next) тому медиаприложению, что играет сейчас - YT Music, Spotify, **или наш собственный плеер**.
- Это провайдер-агностичный и реалистичный путь «now playing + управление»; он же закрывает потребность аудио-профиля S0404 в «текущем воспроизведении».
- Запуск самого приложения YT Music - через deep-link/launch-intent.

### Gmail
- **Данные:** Gmail API (OAuth, scope `gmail.readonly` - **restricted** → верификация + CASA). Счётчик непрочитанных / темы последних писем = restricted-территория.
- Неофициальный content-provider Gmail (`content://com.google.android.gm/...`, label/unread) требует проприетарного разрешения `com.google.android.gm.permission.READ_CONTENT_PROVIDER`, недокументирован и нестабилен, работает только если приложение Gmail установлено - не Play-чистый и ненадёжный путь.
- **Реалистично (Play-safe):** deep-link/launch в приложение Gmail + написать письмо через `ACTION_SENDTO mailto:` (без чувствительных разрешений). Glance-«непрочитанные» - дорого (restricted scope) или практически недостижимо чисто.

### Google Keep
- **Нет публичного consumer-API.** Keep API существует только для **Google Workspace Enterprise** через service-аккаунты (админ/eDiscovery), не для обычных аккаунтов.
- **Реалистично:** только deep-link/launch приложения Keep, либо создание заметки через `ACTION_SEND` (share-текст). Прочитать/показать содержимое заметок нельзя.

## Сквозные моменты

- **Подпись OAuth-клиента:** OAuth-клиент Android привязан к SHA-1 сертификата подписи **на каждый signingConfig** → разные флейворы/кейстораы требуют отдельных OAuth client ID в проекте Google Cloud (та же история, что с MSAL-хэшем подписи в этом проекте).
- **Переиспользование:** в проекте уже есть Google-аккаунт-плумбинг (архивные S0200 account-central-binding, S0233/S0294 Drive-auth) - потенциальный фундамент для Google Sign-In, не блокер.
- **Производительность S0404:** домашняя поверхность открывается по Home постоянно - любые сетевые запросы (Data API) должны быть редкими + кэш, без поллинга на каждый возврат.

## Реалистичная лестница способностей (рекомендуемая рамка)

- **Уровень 0 - Play-safe deep-link-плитки (zero OAuth, zero чувствительных прав).** Плитки домашней поверхности, запускающие YouTube / YT Music / Gmail / Keep (и compose письма через `mailto:`), поверх реестра приложений S0404 (research 02/08). Все целевые флейворы, без новых рисковых разрешений. Реалистичный первый результат.
- **Уровень 1 - блок «сейчас играет» (special access, без Google API).** `NotificationListenerService` + `MediaSessionManager` - показ и управление тем, что играет (закрывает «музыку» для YT Music/Spotify/нашего плеера). Один special access (доступ к уведомлениям), выдаётся пользователем, допустим для лаунчер-типа при честной disclosure. Провайдер-агностичен.
- **Уровень 2 - блок метаданных YouTube (OAuth, non-restricted scope).** Google Sign-In + YouTube Data API «свежее из подписок» glance-списком → тап deep-link'ит в приложение YouTube. Нужен OAuth-клиент + управление квотой + верификация consent-экрана (non-restricted = легче).
- **Уровень 3 - Gmail-glance (OAuth + restricted scope + CASA).** Непрочитанные/темы через Gmail API restricted scope → верификация + ежегодная security assessment. Тяжёлый комплаенс; ROI под вопросом для лаунчера медиасортера. Вероятно вне объёма / owner-решение.
- **Keep-контент: не реализуемо** (нет consumer-API) - только deep-link запуск, без контент-блока.

## Вывод

- Полезный Google-контент-слой достижим на **уровнях 0-1 без единого Google API** и без новых рисковых разрешений (только опт-ин доступ к уведомлениям) - это реалистичный объём первого технического спека.
- **Уровни 2-3** добавляют реальную стоимость (верификация OAuth, restricted-scope CASA) и должны быть owner-gated.
- **Keep-контент инфизибл** - честно зафиксировать как «только запуск».
- Способность независима от launcher-ядра S0404 и ложится на контракт info-блоков/плиток (§5.3); технический спек вынесен в S0429.
