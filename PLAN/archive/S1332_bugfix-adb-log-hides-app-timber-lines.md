## 0. Захваченный материал (inbox)

**Захвачено:** 2026-07-31 (обнаружено при проверке S1277 на устройстве, не запрос владельца)

**Захвачено во время:** S1277

**Текст:**

При проверке S1277 на `emulator-5556` проба не находилась:

```
pwsh -NoProfile -File scripts/devtest/adb.ps1 log -Tail 4000 -Grep "S1277|AudioWaveParticleView"
OK 0 line(s) (window 4000); full capture: temp/scratch/adb_log_20260731_113849.log
```

При этом сохранённый той же командой файл захвата содержит искомое **три раза**, а сырой
`adb logcat -d --pid=<pid>` показывает строку целиком:

```
07-31 11:38:14.427 24469 24469 D AudioWaveParticleView: S1277: animators off, painting static backdrop 2400x1080
```

Причина в `scripts/devtest/adb.ps1`, verb `log` (строки 408-415 на дереве 2026-07-31). Порядок
операций такой: сначала строки фильтруются по трём образцам - имя пакета, `BASE_PACKAGE` и литерал
`FastMediaSorter`, и только потом к уже отфильтрованному применяется `-Grep`.

Собственные логи приложения этот предфильтр не переживают. Timber ставит тегом имя класса, поэтому
строка `D AudioWaveParticleView: S1277: ..` не содержит ни имени пакета, ни слова `FastMediaSorter`.
В выборке остаются почти только системные строки, где пакет упомянут снаружи -
`AppWidgetServiceImpl`, `CarrierSvcBindHelper`, `WindowManager`.

Комментарий в коде честно называет намерение и его причину: «Keep app lines + the project's named
tags; logcat does not stamp every line with the pid». Но logcat умеет фильтровать по pid - ключ
`--pid=`, - и именно так строка и нашлась.

**Почему это важнее, чем выглядит.** На этом verb'е держится вся проверка `BlockNeedUserTest`:
`/spec-test-device` и `/spec-sweep` ищут в логе пробы `Timber.d("Sxxxx: ..")`, а тег у пробы - имя
класса. То есть инструмент систематически не показывает ровно те строки, ради которых его зовут, и
отвечает при этом `OK 0 line(s)` - вид успешного запуска. Отсюда возможен ложный вывод «проба не
сработала, значит код не выполнился» и ошибочный `Broken` у здорового тикета.

Симптом для поиска дубликатов: `adb.ps1 log -Grep` возвращает 0 строк, хотя они есть в файле
захвата, который эта же команда только что записала.

---

## 1. Проблема / симптом

`adb.ps1 log` применяет `-Grep` к выборке, из которой логи приложения уже удалены предфильтром по
имени пакета. Результат `OK 0 line(s)` неотличим от честного «совпадений нет».

---

## 2. Корневая причина

Предфильтр пытается опознать строки приложения по содержимому текста, тогда как признак
принадлежности процессу - это pid, который logcat умеет фильтровать сам.

---

## 3. Исправление

Отбор строки решается по двум признакам, объединённым через ИЛИ, а не по одному тексту:

- pid из колонки `threadtime` входит в множество pid приложения;
- либо текст строки называет пакет - прежние три образца сохранены.

Множество pid собирается из трёх источников и склеивается: `pidof <pkg>` (основной процесс),
`ps -A -o PID,NAME` (ловит `:sub`-процессы, которых `pidof` не видит - он сравнивает имя целиком),
и строки `Start proc <pid>:<package>` из самого захвата (восстанавливает процесс, который уже
завершился, но чьи строки ещё в буфере). Оба вызова adb идут с `-AllowFail`, поэтому пустое
множество pid - законное состояние, а не ошибка: фильтр вырождается в сегодняшнее текстовое
поведение.

Вместо `logcat --pid` выбран разбор колонки pid уже полученного захвата. Причина: `--pid`
принимает один pid, отбросил бы `:sub`-процессы и, главное, выкинул бы системные строки о
приложении (`ANR in <pkg>`, `AndroidRuntime: Process: <pkg>`), которые идут под pid system_server и
нужны ровно тогда, когда что-то сломалось. Формат `-v threadtime` теперь закреплён явно - он и так
по умолчанию, но разбор колонки не должен зависеть от настройки устройства.

Второе изменение важнее первого: при `-Grep` считается, сколько строк с этим образцом было в сыром
окне и сколько дошло до вызывающего. Расхождение переводит вердикт из `OK` в `WARN` с числом
проглоченных строк. Молчаливый `OK 0 line(s)` и был настоящим дефектом - неотличимость «совпадений
нет» от «фильтр их съел». Код выхода в обеих ветках остаётся 0: предупреждение не ошибка, иначе
сломались бы все вызывающие. Сам образец в вывод не печатается - `smoke.ps1` и
`prerelease-prepare.ps1` сопоставляют свой crash-регексп со всем stdout этого скрипта.

Решение вынесено в `scripts/devtest/lib/adb-log-filter.ps1` - три чистые функции над массивами
строк, без обращения к устройству, поэтому боевой verb и регрессионный набор гоняют один и тот же
код.

## 4. Проверка

Выполнена на `emulator-5556` (sdk_gphone64_x86_64, Android 13 / SDK 33) 2026-07-31.

- Положительная: запустить приложение, затем
  `adb.ps1 log -Tail 3000 -Grep "MainActivity|MainViewModel"`. Ожидалось - строки с тегом-именем
  класса находятся. Получено - три строки, среди них `D BaseActivity: onCreate: MainActivity` под
  pid 25509, то есть ровно тот класс строк, который старое правило выбрасывало.
- Негативная: `adb.ps1 log -Tail 500 -Grep "ZZZ_NO_SUCH_PATTERN_XYZ"`. Ожидалось - 0 строк с
  вердиктом `OK` и без `WARN`. Получено - `OK 0 line(s)`.
- Предупреждение: `adb.ps1 log -Tail 3000 -Grep "Finsky|SurfaceFlinger|zygote"`. Ожидалось - `WARN`,
  потому что образец совпадает и с чужими строками, которые фильтр обязан отбросить. Получено -
  `WARN 4 line(s)` плюс `the filter dropped 8 line(s) matching the pattern`.
- `-Json`: полезная нагрузка получила `rawMatched`, `suppressed`, `appPids`; `ok`, `exitCode`,
  `matched`, `file` не тронуты.

(Script). Бюджеты строк: библиотека 90 при лимите 90, `adb.ps1` 533 при лимите 540.

**Побочное следствие, шире самого тикета.** `prerelease-prepare.ps1:287` зовёт этот же verb с
`-Grep 'FATAL|beginning of crash|ANR in'` и затем сопоставляет тот же регексп со stdout. Строка
`E AndroidRuntime: FATAL EXCEPTION: main` не содержит ни имени пакета, ни слова `FastMediaSorter`,
поэтому старый предфильтр её отбрасывал - и предрелизный скан падение Java-уровня не видел вовсе,
только ANR (`ANR in <pkg>` называет пакет в той же строке и проходил). То есть проверка запуска
могла отчитаться PASS на приложении, которое упало. Теперь строка проходит по pid-плечу; кейс
«keeps both crash rows, including the header that names no package» в наборе фиксирует ровно это.
Разделитель буфера по-прежнему отбрасывается намеренно - иначе скан отчитывался бы о падении на
любом устройстве с непустым crash-буфером.

Остаточных находок P0/P1 нет. Заметка для будущего читателя: набор `adb-log-filter.tests` намеренно
не подключён ни к `a.ps1`, ни к `post-change.ps1` - как и шесть уже существующих наборов. Постоянным
сторожем служит не он, а вердикт `WARN` в самом verb'е, который срабатывает на каждом вызове.
