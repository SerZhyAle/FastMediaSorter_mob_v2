## 1. Проблема

Фото из встроенной камеры приложения не содержат GPS-координат в EXIF, хотя при просмотре «место» ожидается наряду с поворотом и временем. Конвейер CameraX пишет JPEG, но шаг записи метаданных локации не вызывается, источника `Location` нет, и разрешение на геолокацию в потоке камеры не запрашивается. Включить геотегирование «по умолчанию» нельзя: координаты съёмки - чувствительные приватные данные, требующие явного согласия и раскрытия в Play Data Safety. Поэтому нужна опциональная, по умолчанию выключенная опт-ин возможность с корректным запросом разрешения и поведением «без блокировки спуска».

## 2. Цели

1. Пользователь может включить геотегирование фото камеры опт-ин настройкой (по умолчанию **выключено**).
2. При включённой настройке и выданном разрешении на геолокацию снятое фото содержит GPS-координаты в EXIF («место»), читаемые штатным просмотрщиком и внешними приложениями.
3. Геотег корректно переносится и для снимков с цифровым зумом (через путь сохранения EXIF при кропе, уже существующий после S0765).
4. Отсутствие разрешения, выключенная настройка или недоступная локация **никогда не блокируют спуск** - снимок сохраняется без GPS.
5. Возможность геотегирования распространяется на все пути съёмки фото единообразно (в т.ч. запуск камеры из виджетов), без отдельной настройки на каждый путь.

**Non-goals:**

- Поворот/время EXIF (закрыто в S0765).
- Геотегирование видео (только фото).
- Непрерывная синхронизация ориентации превью/захвата (домен S0754).
- Реверс-геокодинг / отображение названия места в UI.
- Карта/трек/история локаций.

## 4. Контекст текущей архитектуры

- Захват фото идёт через CameraX (единственный путь, S0359). Менеджер сессии камеры строит опции вывода файла и поручает кодирование JPEG самому CameraX; шаг записи метаданных локации в опции вывода не вызывается, поэтому GPS-тегов в выходном файле нет.
- При активном цифровом зуме файл off-thread пере-кодируется ради центрального кропа; путь сохранения/восстановления EXIF (S0765) уже переносит GPS-теги, если они присутствуют в исходном JPEG. Значит при записи GPS на этапе захвата зум-снимок сохранит геотег без дополнительных правок кропа.
- Менеджер сессии камеры инстанцируется хостом вручную (не через DI) и получает зависимости параметрами; `Context` доступен через вью превью.
- Рантайм-разрешения камеры/микрофона запрашиваются хостом камеры через стандартные лаунчеры результата, исходы маршрутизируются во flow-менеджер. Прецедент опт-ин записи звука откладывает запрос разрешения до первого использования.
- Настройки хранятся в DataStore (доменная модель настроек + хранилище capture-флагов + мост репозитория); UI камера-настроек живёт в существующем блоке вкладки Operations.
- Источника локации в проекте нет (нет ни использования системного сервиса локации, ни GMS-провайдера, ни разрешений в манифесте) - инфраструктура вводится этим тикетом.
- Запуск камеры из виджетов идёт через тот же экран камеры как чёрный ящик - если геотег выполняется внутри экрана камеры, виджет-пути покрываются автоматически.

## 5. Предлагаемый подход

Ввести опт-ин настройку геотегирования (по умолчанию выкл). Когда камера открыта и настройка включена при выданном разрешении на локацию, прогревать источник локации (системный сервис) на время сессии и держать последний известный фикс. На спуске затвора, если фикс доступен, записывать его в метаданные локации опций вывода CameraX, чтобы координаты попали в EXIF исходного JPEG; путь кропа сохранит их без изменений. Любое отсутствие условий (выкл настройка, нет разрешения, нет фикса, видео) -> снимок без GPS, спуск не блокируется. Запрос разрешения на локацию выполняется в контексте включения настройки в Operations (как у опт-ин записи звука): при включении тоггла, если разрешения нет, оно запрашивается, и настройка остаётся включённой только при выдаче; камера повторно разрешение не запрашивает - просто молча геотегирует при наличии флага и разрешения.

### 5.1 Основные столпы / модули

- Опт-ин настройка геотегирования: булев флаг (хранилище + доменная модель + мост репозитория) и тоггл в существующем блоке камеры вкладки Operations.
- Источник локации: лёгкий помощник поверх системного сервиса локации - прогрев/останов по жизненному циклу открытой камеры, выдача последнего известного фикса; без новых GMS-зависимостей.
- Интеграция захвата: запись фикса в метаданные локации опций вывода CameraX на спуске (только фото); перенос GPS при кропе уже обеспечен S0765.
- Разрешения/манифест: новые location-разрешения + `uses-feature` GPS (`required="false"`); рантайм-запрос через стандартный лаунчер хоста камеры, отложенный до первого использования.
- Локализация: строки опции и обоснования разрешения (EN/RU/UK).

### 5.2 Потоки данных и событий

- Открытие камеры -> если настройка вкл и разрешение есть, прогрев источника локации (иначе при первом использовании запросить разрешение).
- Источник держит последний известный фикс, обновляя его, пока камера открыта.
- Спуск фото -> при наличии фикса он кладётся в метаданные локации опций вывода -> CameraX пишет GPS в EXIF -> (если зум) кроп сохраняет GPS-теги.
- Закрытие камеры -> останов источника локации (без утечек слушателей).
- Любая ветка без фикса/разрешения/настройки -> снимок без GPS, без блокировки спуска.

### 5.3 Точки расширяемости

- Набор переносимых при кропе GPS-тегов уже централизован (S0765) - не дублируется.
- Источник локации изолирован за узким контрактом - в будущем заменяем на более точный провайдер без изменения интеграции захвата.
- Опт-ин флаг - единая точка управления для всех путей съёмки (включая виджеты).

## 6. Открытые вопросы / Research items

Разрешены в ходе research (артефакт §0); зафиксированы как решения:

1. **Стратегия разрешения** -> опт-ин настройка (по умолчанию выкл) + рантайм-запрос `ACCESS_FINE_LOCATION` при включении тоггла в Operations (паттерн опт-ин записи звука); настройка остаётся включённой только при выданном разрешении. Камера повторно не запрашивает. Тоггл - в блоке камеры вкладки Operations.
2. **Источник и свежесть локации** -> прогрев системного сервиса локации на время открытой камеры; штамп последнего известного фикса на спуске. Синхронный fresh-fix перед спуском не делается (не блокировать затвор). Платформенный сервис, без GMS.
3. **Поведение без разрешения/локации** -> снимок сохраняется без GPS, спуск не блокируется, без модальных ошибок (мягкий лог).
4. **Виджет-пути** -> геотег выполняется внутри экрана камеры, поэтому виджет-съёмка наследует поведение без отдельной настройки.
5. **`uses-feature` GPS** -> `required="false"`, чтобы не сузить охват устройств в Play (release-gate: без регрессии охвата).

Остаточный внешний пункт (не блокирует разработку): обновление Play Data Safety для precise location - владелец/релиз (см. §7, финальный отчёт).

## 9. Архитектурные решения (ADR)

- **ADR-1: Платформенный сервис локации вместо GMS FusedLocationProvider.** Беззатратно по зависимостям/размеру APK, работает на всех флейворах и minSdk 23; для разовой записи геотега точность/энергоэффективность Fused избыточны. Источник изолирован за контрактом - замена возможна позже.
- **ADR-2: Геотег внутри экрана камеры, не в caller.** Один источник истины для всех путей съёмки (включая виджеты); опт-ин читается централизованно, виджеты не дублируют логику.
- **ADR-3: Прогрев источника на сессию + штамп последнего фикса, без синхронного fresh-fix.** Соблюдает «спуск не блокируется»; симметричный register/unregister по жизненному циклу.

## 11. Критерии готовности (strategic-level)

1. Опт-ин настройка геотегирования присутствует в настройках камеры, по умолчанию выключена, локализована EN/RU/UK.

3. Зум-снимок при тех же условиях также содержит GPS.
4. При выключенной настройке, отсутствии разрешения или недоступной локации фото сохраняется без GPS и спуск не блокируется.
5. Геотег применяется и при запуске камеры из виджетов без отдельной настройки.
6. Новые разрешения и `uses-feature` GPS (`required="false"`) объявлены; охват устройств в Play не сужен.
