## 0. Захваченный материал (inbox)

**Захвачено:** 2026-08-15

**Захвачено во время:** S1156

**Текст:**

Release flow does not retain R8 mapping.txt and native debug symbols keyed by versionCode. docs/RELEASE_READINESS_STANDARD.md lines 98-99 and 166 declare retention REQUIRED for every production release ("mapping.txt and the native symbols are retained and keyed by versionCode ... Missing retention = operational loss (post-release triage capability)"), but nothing in the repo implements it. Evidence gathered 2026-08-15 while working S1156: the only local mapping is app_v2/build/outputs/mapping/standardRelease/mapping.txt in the release worktree /p/ANDROID/FastMediaSorter_release, dated 2026-08-12 20:40, i.e. the artifact of the most recent release build only. Gradle overwrites it on every release build, so the mapping for any earlier release is gone locally. Consequence, observed live: S1156 sat in BlockExternal for three weeks because the three obfuscated symbols from Play Console release 2.60.7221.704 (2026-07-22) could not be resolved - the only surviving copy of that mapping is the one Play Console holds. Every post-release triage of an older release hits the same wall. Design constraint worth noting up front: mapping.txt for this app is ~178 MB and mapping.prt another ~27 MB, so a naive "copy every release into the repo" is not viable - the ticket needs a retention scheme (compression, pruning window, out-of-repo archive location) as part of its research, not just a copy step. Candidate archive keying: versionCode (e.g. 260722170 for 2.60.7221.704).

---

## 1. Проблема

Стандарт готовности релиза объявляет хранение артефактов деобфускации обязательным для каждого продакшн-релиза, но в репозитории этого не делает ничто. Gradle перезаписывает `mapping.txt` при каждой релизной сборке, поэтому локально существует ровно один экземпляр - от последней сборки. Как только релиз ушёл в магазин и поверх него собрали следующий, расшифровать стек-трейс из него уже нечем.

Эффект наблюдался вживую, а не предполагается: S1156 простоял в `BlockExternal` три недели, потому что три обфусцированных символа из релиза 2.60.7221.704 нечем было разрешить.

---

## 2. Цели

1. Для любого выпущенного релиза можно взять его артефакты деобфускации и расшифровать стек-трейс, не завися от того, сколько сборок прошло после.
2. Артефакты адресуются по `versionCode`, то есть по тому же ключу, которым релиз опознаётся в магазине.
3. Нарушение хранения обнаруживается автоматически, а не выясняется через три недели при разборе аварии.

**Non-goals:**

- Не хранить артефакты внутри репозитория: размеры это исключают.
- Не менять сам процесс сборки релиза и не трогать подпись.
- Не заводить хранение для отладочных сборок - у них нет обфускации.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Схема хранения не должна требовать ручного шага на каждом релизе - забытый шаг равнозначен отсутствию хранения.
2. Восстановление артефакта по номеру версии должно быть однокомандным.

### 3.2 Жёсткие ограничения

- **Flavor:** релизные варианты, где включена минификация; отладочные не затрагиваются.
- **API level:** без API-специфики - это процесс сборки, не код приложения.
- **Wear OS:** модуль `wear` собирается отдельно, его релиз минифицируется, поэтому он попадает в схему в тех релизах, где публикуется.
- **Производительность:** не относится к приложению; относится к времени релизной сборки и к месту на диске.
- **Совместимость данных:** не относится.
- **Локализация:** новых пользовательских строк нет.
- **Доступность:** не относится, пользовательского интерфейса нет.

### 3.3 Owner inputs (Approval gate)

- **Related tickets:** S1156 (пострадал от отсутствия хранения, простоял три недели в `BlockExternal`), S1674 (в его ходе mapping впервые начали читать программно - гейт сверяет по нему имена констант перечислений, то есть у артефакта появился второй потребитель помимо разбора аварий), S1157 (сужение keep-правил - меняет содержимое mapping и потому заинтересован в истории)
- **Состав удерживаемого:** только артефакты деобфускации - `proguard.map` и нативные `.so.dbg`, извлечённые из выпущенного AAB и сложенные сжатыми. Весь бандл целиком не хранится.
- **Место архива:** облачная папка `c:\GD\WORK\FastMediaSorter`, куда скрипты сборки уже кладут APK.
- **Глубина хранения:** все релизы, скользящего окна нет.
- **Охват:** те варианты, которые релиз действительно опубликовал, то есть список флейворов, с которым отработал `/skill-release`, включая `wear`, когда он публикуется.

Все открытые вопросы §6 закрыты опросом владельца 2026-08-15 (см. блок решений в конце файла).

## 4. Контекст текущей архитектуры

Релизная сборка идёт в отдельном git-worktree, не в основной рабочей копии, и складывает результат в стандартный каталог выходных артефактов Gradle. Ни один скрипт репозитория не упоминает `mapping.txt`, `mapping.prt` или нативные символы - проверено поиском по всему каталогу скриптов, совпадений ноль. То есть артефакт создаётся, живёт до следующей сборки и молча исчезает.

История теряется дважды, а не один раз. Помимо `build/outputs`, релизный бандл копируется в `DOWNLOADS/` под **фиксированным** именем `FastMediaSorter_standard_release.aab`, поэтому следующий релиз затирает и его. Каталог `DOWNLOADS/` целиком в `.gitignore`, так что git историю тоже не держит.

Замеры, снятые 2026-08-15 с выпущенного бандла (`unzip -v`), меняют оценку задачи:

- Бандл уже содержит оба нужных артефакта: `BUNDLE-METADATA/com.android.tools.build.obfuscation/proguard.map` и `BUNDLE-METADATA/com.android.tools.build.debugsymbols/*/*.so.dbg`.
- В сжатом виде mapping занимает **14.2 МБ** при 178.9 МБ исходного текста, сжатие 92%.
- Нативные символы всех четырёх ABI в сумме дают **около 7.9 МБ** сжатыми.
- Полный комплект деобфускации одного релиза - **около 22 МБ**, а не 200 МБ, как предполагалось при захвате.

Причина, по которой проблему нельзя решить из §1 текущими средствами: единственная переживающая копия старого mapping принадлежит магазину, и достать её оттуда можно только вручную. Строка `ReTrace mapping file` в консоли несёт иконку удаления, а не скачивания - магазин принимает mapping, но не отдаёт его обратно. Реально копия извлекается из строки `Original file`, то есть скачиванием всего AAB на 85 МБ с последующей распаковкой.

## 5. Предлагаемый подход

Ввести шаг удержания, привязанный к релизной сборке, а не к памяти человека: после успешной сборки релиза его артефакты деобфускации извлекаются из бандла и укладываются в облачную папку `c:\GD\WORK\FastMediaSorter` под ключом `versionCode`. Плюс обратная операция - достать по номеру версии - и проверка, которая на предрелизном прогоне убеждается, что предыдущий релиз действительно уложен.

### 5.1 Основные столпы / модули

#### Укладка

Автоматический шаг в конце релизной сборки: взять из готового AAB `proguard.map` и нативные `.so.dbg`, положить их сжатыми по ключу версии. Извлекать из бандла, а не из `build/outputs`, потому что бандл - это ровно то, что ушло пользователю, и вопрос «совпадает ли артефакт с выпущенной сборкой» отпадает сам.

Источник запечатан внутри AAB уже сжатым, поэтому шаг стоит одного распаковывания записи, а не пережатия 179 МБ текста.

#### Извлечение

Однокомандное получение артефакта по `versionCode` для разбора аварии.

#### Контроль

Проверка, включаемая в предрелизный прогон: у предыдущего выпущенного релиза артефакты на месте. Нарушение видно на следующем релизе, а не через три недели.

### 5.2 Потоки данных и событий

Релизная сборка → артефакты деобфускации → сжатие → внешнее хранилище по ключу версии. Разбор аварии → номер версии → извлечение → расшифровка.

### 5.3 Точки расширяемости

Ключ - `versionCode`, а не имя файла или дата, чтобы к той же схеме можно было добавить артефакты других модулей и других вариантов сборки без смены адресации.

## 6. Открытые вопросы / Research items

1. **Нужно ли локальное хранение вообще, если магазин уже хранит.**
   - **Вопрос:** магазин хранит mapping загруженных сборок - именно оттуда в итоге взяли копию для S1156. Значит ли это, что задача не «хранить», а «сделать доступ к хранимому магазином быстрым и однокомандным»?
   - **Почему это не выводится:** зависит от того, насколько владелец готов зависеть от внешнего сервиса и его политики хранения.
   - **Статус:** Resolved - хранить своё. Магазин не отдаёт mapping как файл, только внутри AAB, поэтому «быстрый доступ» к нему всё равно означал бы ручной вход в консоль и скачивание 85 МБ. Своя копия стоит 22 МБ и достаётся командой; магазин остаётся фолбэком для релизов, выпущенных до внедрения схемы.

2. **Где живёт архив.**
   - **Вопрос:** внешний диск, облачная папка, отдельный репозиторий артефактов? В репозиторий нельзя - размеры это исключают.
   - **Почему это не выводится:** это решение о чужой инфраструктуре и о том, что переживёт переустановку машины.
   - **Статус:** Resolved - облачная папка `c:\GD\WORK\FastMediaSorter`. Скрипты сборки уже пишут туда APK, то есть место обжитое, синхронизируется само и переживает переустановку машины.

3. **Глубина хранения.**
   - **Вопрос:** держать все релизы или скользящее окно из N последних? Каждый релиз - около 200 МБ до сжатия.
   - **Почему это не выводится:** размен места на способность разобрать старую аварию задаёт владелец.
   - **Статус:** Resolved - все релизы, окна нет. Исходная посылка вопроса была завышена вшестеро: замер даёт 22 МБ на релиз, то есть сто релизов - 2.2 ГБ. Окно экономило бы копейки и однажды удалило бы именно тот релиз, который понадобился.

4. **Охват.**
   - **Вопрос:** только `standard`, или все минифицируемые варианты, и попадает ли сюда модуль `wear`?
   - **Почему это не выводится:** зависит от того, какие варианты реально выпускаются пользователям.
   - **Статус:** Resolved - те варианты, которые релиз действительно опубликовал. Охват привязан к списку флейворов, с которым отработал `/skill-release`: `standard` всегда, остальные и `wear` - когда они ушли пользователям. Собирать релизно неопубликованные флейворы ради архива не нужно.

## 9. Архитектурные решения (ADR)

**ADR-1. Хранить самим, магазин - только фолбэк.** Магазин не выдаёт mapping отдельным файлом: в консоли эта строка предлагает удаление, а не скачивание, и единственный путь к копии - скачать весь бандл и распаковать его. Значит «быстрый доступ к хранимому магазином» упирается в ручной вход и 85 МБ трафика на каждый разбор. Собственная копия снимает и то, и другое, а магазин остаётся страховкой для релизов, выпущенных до внедрения схемы.

**ADR-2. Удерживать извлечённые артефакты, а не весь бандл.** Бандл целиком стоит 85 МБ и несёт APK, которые при разборе аварии не нужны. Извлечённые mapping и символы - около 22 МБ, вчетверо дешевле при том же результате.

**ADR-3. Источник извлечения - выпущенный AAB, а не `build/outputs`.** Бандл есть ровно то, что ушло пользователю, поэтому совпадение артефакта с релизом обеспечено самим способом получения, а не дисциплиной. Дополнительно бандл хранит нужные записи уже сжатыми.

**ADR-4. Место - облачная папка `c:\GD\WORK\FastMediaSorter`.** Она уже используется скриптами сборки, синхронизируется без участия человека и переживает переустановку машины. Репозиторий исключён размерами, локальный каталог - тем, что он и есть текущая точка потери истории.

**ADR-5. Хранение без окна.** Замер (14.2 МБ mapping плюс 7.9 МБ символов) делает окно бессмысленной экономией: удаление старого релиза сберегает 22 МБ и стоит ровно того сценария, ради которого заводится тикет.

**ADR-6. Охват задаётся фактом публикации.** Схема удерживает то, что релиз опубликовал, и читает список флейворов из самого релизного прогона. Жёсткий список пришлось бы править при каждом изменении набора каналов.

**ADR-7. У вариантов без бандла источник - `build/outputs` того же прогона.** Замер 2026-08-15 при тактическом планировании: бандл собирается только для `standard` (`bundleStandardRelease` в `scripts/builders/build-aab-release.ps1`), а все прочие флейворы и `wear` идут через `assemble*Release` в `scripts/release/build-release-spectrum.ps1`. Извлекать из AAB там нечего - его не существует. Переключать спектр на `bundle*Release` запрещено non-goal'ом §2 «не менять сам процесс сборки релиза», поэтому mapping этих вариантов берётся из `build/outputs/mapping/<variant>/mapping.txt`. Гарантия ADR-3 у них слабее - совпадение обеспечено не запечатанностью в бандле, а тем, что файл написан тем же прогоном, - и потому источник записывается в манифест явным значением (`bundle` либо `outputs`), чтобы разница не терялась.

**ADR-8. Нативные символы удерживаются один раз с `standard`, кроме VR.** ABI-наборы флейворов - подмножества `standard` (`vr` - `arm64-v8a`, `noLegal` - `arm64-v8a` и `x86_64`, `standard` - все четыре), а сами `.so` являются прибилдами, общими для флейворов, поэтому символы из `standard`-бандла покрывают APK-варианты того же релиза. Исключение одно: `vr` дополнительно компилирует собственный OpenXR-рантайм через `externalNativeBuild.cmake`, и этих символов нет ни в одном бандле - они удерживаются отдельно из каталога объектов CMake.

**ADR-9. Провал укладки не роняет релизную сборку.** Укладка вызывается после того, как бандл уже собран и лежит на диске, поэтому аварийное завершение уничтожило бы годный релиз из-за проблемы с архивом. Шаг предупреждает, а не падает; ответственность за обнаружение несёт предрелизный гейт §5.1, который для того и заведён, что укладка может не сработать молча.

## 11. Критерии готовности (strategic-level)

1. Для последнего выпущенного релиза его артефакты деобфускации достаются по номеру версии одной командой.
2. После следующего релиза артефакты предыдущего по-прежнему доступны - то есть перезапись Gradle больше не уничтожает историю.
3. Отсутствие артефактов у предыдущего релиза обнаруживается автоматически до выпуска следующего.
