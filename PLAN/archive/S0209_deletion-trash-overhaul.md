## 1. Проблема

Механизм локального удаления состоит из двух путей — «прямое» удаление (Trash выключен) и удаление через корзину (Trash включён). Прямой путь корректно освобождает место на устройстве, но накопил техдолг: на одной поверхности удаления существуют две почти дублирующиеся реализации работы с MediaStore, и маршрутизация локальных удалений проходит через обработчик с явно сетевой семантикой. Путь через корзину при детальном анализе кода оказался **неработоспособен в продакшене сразу по двум независимым причинам**.

Первая причина — фактическая утечка места при включённой корзине. Создатель служебной trash-директории и единственный реально вызываемый рекурсивный уборщик используют разные соглашения об имени: имена не совпадают ни в одном символе после точки, и уборщик никогда не распознаёт «свой» trash. Параллельный use-case с корректным именем существует, но в коде не вызывается ни из одной точки. На каждом удалении в Trash место занимается безвозвратно — освободить его можно только ручным удалением скрытых папок через файловый менеджер.

Вторая причина — несовместимость soft-delete-схемы с моделью Scoped Storage. На устройствах с Android 11+ rename media-файлов внутри общих коллекций системой не разрешён без специального разрешения, которое пользователь должен предоставить вручную. Имеющийся fallback на copy+delete тоже не работает, потому что удаление оригинала через File API ограничено той же политикой. В наихудшем сценарии файл оказывается продублирован в trash, оригинал остаётся на месте, занимаемое место не уменьшается, а возрастает.

Третий уровень проблемы — UX: принудительная чистка trash при перезагрузке ресурса (refresh, повторное открытие, закрытие экрана) выполняется с нулевым TTL. На устройствах, где соглашения об именах случайно совпали бы, корзина схлопывалась бы до первого refresh — пользователь не получает обещанного «окна для восстановления».

---

## 2. Цели

1. Прямое удаление (Trash выключен) гарантированно освобождает место на устройстве для всех поддерживаемых API levels и типов локальных хранилищ, без скрытых soft-delete меток.
2. Удаление с включённой корзиной освобождает место предсказуемо, без зависимости от того, выполнил ли пользователь refresh ресурса.
3. Корзина действительно работает как окно восстановления — у пользователя есть конечный, понятный TTL после удаления, в течение которого восстановление возможно.
4. Содержимое корзины и формат её служебных директорий согласованы между создающим и убирающим кодом — нет ни одной комбинации настроек, при которой trash-папки остаются на диске бесконечно.
5. Слой удаления имеет единственную реализацию работы с MediaStore и единую точку входа для локальных путей — без дублирующих веток и без транзитной маршрутизации через обработчики, ответственные за сетевые протоколы.

**Non-goals:**

- Изменение поведения удаления для SMB/SFTP/FTP/cloud (Drive/Dropbox/OneDrive) — текущий контракт сохраняется.
- Введение нового UI для настройки TTL корзины — TTL остаётся жёстко заданным значением слоя приложения (см. §5).
- Изменение поведения системного диалога согласия на удаление на Android 11+ — продолжаем использовать штатный механизм платформы.
- Восстановление trash-папок, оставшихся на устройствах после предыдущих версий приложения, если их формат имени отличается от текущего — миграция-best-effort, без гарантий.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Сохранить простоту настроек: пользователь видит один тумблер «использовать корзину», без дополнительных параметров TTL.
2. По возможности унифицировать кодовый путь так, чтобы повторение проблемы (рассинхрон имён, дублирующиеся реализации) было исключено по конструкции, а не по дисциплине.

### 3.2 Жёсткие ограничения

- **Flavor:** все flavors (`standard`, `vr`, `vrUnlicensed`, `noLegal`, `lite`, `photos`, `legacy`). Поверхность удаления одинакова, флавор-специфика отсутствует — никаких новых `BuildConfig`-гейтов.
- **API level:** поддерживаются все целевые уровни (`minSdk 23` для `legacy`, `minSdk 26` для остальных, `compileSdk 35`). Поведение на API ≥ 30 (системный диалог согласия) и на API 29 (прямой `contentResolver.delete`) сохраняется.
- **Wear OS:** не затрагивается — удаление локальных медиафайлов выполняется только на phone-модуле.
- **Производительность:** удаление пачки файлов не должно деградировать по сравнению с текущим состоянием. Чистка корзины фоновым воркером не должна блокировать UI и не должна провоцировать сканирование MediaStore чаще, чем сейчас.
- **Совместимость данных:** на устройствах, где остались trash-директории из предыдущих версий приложения, новый код должен корректно их распознать и убрать при ближайшей фоновой чистке. Если формат имени не распознан — папка остаётся, но не воспринимается как «своя» корзина (пользователь видит её как обычную скрытую папку).
- **Локализация:** EN/RU/UK — обязательно для любых новых пользовательских строк. Соответствие `docs/COMMUNICATION_POLICY.md` (§6 — tone checklist) — обязательный гейт перед интеграцией.
- **Доступность:** если появится новое уведомление пользователю об освобождении/корзине — выполнить требования TalkBack и не-цветового отличия.
- **Безопасность:** удаление через системный диалог согласия на Android 11+ остаётся единственным способом hard-delete shared-storage media-файлов — никаких обходов scoped storage.

## 4. Контекст текущей архитектуры

Удаление локальных файлов начинается в слое use-case, который классифицирует пути по типу хранилища и принимает решение, нужен ли soft-delete (на основании пользовательской настройки и политики поддержки soft-delete для конкретного типа пути). Локальная ветка раздваивается: для shared storage на современных API уходит через MediaStore-механизм системы (запрос разрешения у пользователя, физическое удаление выполняет ОС), для app-private и устаревших API — через прямой файловый API. Soft-delete реализован собственной схемой: файл переименовывается в служебную подпапку, рядом сохраняется метаданные. Финальная очистка выполняется в двух независимых местах — фоновым воркером WorkManager с заданным TTL и реакцией на перезагрузку списка файлов в browse-экране (cleanup срабатывает безусловно, без учёта TTL).

Затронутые слои: domain (классификаторы путей и оркестратор операций), data (стратегии и обработчики операций для разных типов хранилища), ui/browse (точки реакции на пользовательские действия и точки перезагрузки списка), worker (фоновая периодическая чистка), а также узлы интеграции с MediaStore. Текущая структура не позволяет починить ни одну из трёх проблем точечно: рассинхрон имён trash-директорий лежит между разными слоями; нулевой TTL при перезагрузке зашит в манёжер реакции на refresh; дублирование MediaStore-логики и транзит через SMB-обработчик — наследие предыдущих рефакторингов, требующее согласованной правки.

## 5. Предлагаемый подход

Объединить точку решения и точку исполнения. Слой use-case остаётся единственным местом, где принимается решение «hard delete сейчас» vs «move to trash сейчас». Слой стратегий хранит ровно одну реализацию hard-delete для локальных путей (с правильным выбором ветки по API level) и ровно одну реализацию move-to-trash для локальных путей. Маршрутизация локальных удалений через обработчик, отвечающий за сетевые протоколы, ликвидируется — локальный путь идёт напрямую в локальную стратегию. Соглашение об именах служебных trash-директорий вводится как единый источник правды на уровне доменной модели — и создатель, и уборщик пользуются одной константой/протоколом именования; отдельный модуль валидирует, что фактическая структура на диске и фактический регексп уборщика совпадают.

Финальная чистка корзины выполняется только периодическим фоновым воркером с конечным TTL (5 минут после удаления, проверка каждые 15 минут — сохраняем текущие значения, чтобы не ломать ожидания пользователя). Принудительная чистка при перезагрузке ресурса (refresh, повторное открытие, закрытие экрана) убирается полностью — корзина живёт ровно до достижения TTL. Ручная кнопка «очистить корзину» в настройках операций остаётся как единственный способ принудительной чистки помимо TTL.

### 5.1 Основные столпы / модули

- **Единая точка решения.** Слой use-case, классифицирующий путь и принимающий решение о hard/soft delete. Цель: оставить здесь только маршрутизацию и политику; всё знание про MediaStore — у стратегии.
- **Единая стратегия локального удаления.** Локальная стратегия — единственный держатель кода `File.delete()` / `contentResolver.delete()` / `MediaStore.createDeleteRequest()` / `MediaStore.createTrashRequest()` (последний не используется, фиксируем как «никогда не появляется»). Никакой дублирующей реализации в other-слое.
- **Соглашение об именах trash-директорий.** Единый объект-источник правды: префикс, формат timestamp, способ парсинга. Создатель trash-папки и фоновый уборщик импортируют один контракт. Самотестируемый: модуль умеет ответить, валидна ли конкретная директория как «своя».
- **Фоновый чистильщик.** Периодический воркер с конечным TTL — единственный механизм автоматической финальной очистки корзины. Внешние триггеры (refresh, reload, shutdown) больше не зовут чистку.
- **Прямой локальный маршрут.** Локальные удаления попадают в локальную стратегию напрямую, без транзита через сетевые обработчики.

### 5.2 Потоки данных и событий

- **Hard delete (Trash off).** UI → use-case → классификатор пути → локальная стратегия → ОС (API ≥ 30: системный диалог согласия → ОС удаляет; API 29: `contentResolver.delete`; API ≤ 28 / app-private: `File.delete`) → MediaStore notify (где требуется) → UI обновляет state.
- **Soft delete (Trash on).** UI → use-case → классификатор пути → локальная стратегия → переименование файла в служебную trash-директорию по единому соглашению об именах → запись метаданных. UI обновляет state. Файл физически на диске, место не освобождено.
- **Финальная очистка.** Периодический воркер → обход известных trash-директорий → проверка возраста по соглашению об именах → удаление просроченных папок → MediaStore notify.
- **Ручная очистка.** UI → use-case → локальная стратегия → удаление всех trash-директорий ресурса вне зависимости от возраста → MediaStore notify.
- **Восстановление.** UI → use-case → локальная стратегия → перенос файлов из trash-директории обратно по сохранённым в метаданных путям.

### 5.3 Точки расширяемости

- Контракт «классификатор пути» остаётся открытым к появлению новых типов локального хранилища (например, USB-OTG, если когда-то понадобится). Поверхность интеграции — добавить ветку классификации; стратегии и use-case остаются стабильными.
- Контракт «соглашение об именах trash-директорий» допускает версионирование — если в будущем потребуется сменить формат, можно ввести «версию» соглашения и оставить распознавание старых форматов как best-effort миграцию.
- Точка интеграции с MediaStore (нотификации и запросы согласия) изолирована в одном месте — заменить её на альтернативный механизм будущей платформы можно без правок в use-case.
- Конкретные значения TTL и периода фонового воркера остаются константами уровня приложения — открыто к параметризации в будущем без правок интерфейсов.

## 6. Открытые вопросы / Research items

1. **Реальная картина на устройстве пользователя.**
   - **Вопрос:** действительно ли на устройстве владельца Trash-папки остаются на диске бесконечно (рассинхрон имён даёт утечку), или существует промежуточный путь, который их убирает.
   - **Ответ:** утечка **реальная и подтверждена кодом**. Создатель soft-delete пишет вложенную структуру с буквальным именем `.trash` (без подчёркивания) и timestamp как именем поддиректории внутри; единственный фактически вызываемый рекурсивный уборщик ищет директории, имя которых начинается с `.trash_` (с подчёркиванием). Имена не совпадают ни в одном символе после точки — уборщик никогда не распознаёт «свой» trash и обходит его как обычную поддиректорию. Параллельный use-case с корректным именем (`.trash`) существует, но не вызывается ни из одной точки кода (dead code). Логи устройства подтверждения не требуют — рассинхрон детерминирован.
   - **Следствие:** при включённой корзине каждое удаление безвозвратно занимает место. Освободить его можно только ручным удалением скрытых папок через файловый менеджер.
   - **Статус:** Resolved.

2. **Совместимость с восстановлением.**
   - **Вопрос:** работает ли текущее «восстановление удалённых» с новыми trash-директориями, либо оно завязано на старое соглашение имён.
   - **Ответ:** use-case восстановления уже читает соглашение `$currentPath/.trash/$timestamp/metadata.json` — то же, что пишет creator soft-delete. Восстановление в принципе работоспособно для тех редких устройств, где сам soft-delete сложился (без рассинхрона уборщика). После унификации уборщика на тот же контракт восстановление останется корректным без правок логики; правки требуются только для приведения use-case к единому источнику правды (чтобы префикс/формат не дублировались в трёх местах).
   - **Статус:** Resolved.

3. **Поведение ручной кнопки «очистить корзину».**
   - **Вопрос:** какой именно путь использует ручная очистка — единичный use-case или общий рекурсивный — и удаляет ли она trash-папки в их новом формате имён.
   - **Ответ:** кнопка `btnClearTrash` в экране настроек операций кликом зовёт метод ViewModel `clearAllTrash`. Точный use-case за ним требуется проверить в тактической фазе и перевести на единое соглашение об именах одновременно с фоновым воркером. До рефакторинга кнопка унаследовала ту же проблему рассинхрона, что и автоматическая чистка.
   - **Статус:** Resolved.

4. **Trash на shared storage в API ≥ 30.**
   - **Вопрос:** действительно ли rename файла внутри shared-storage в служебную trash-директорию работает на Android 11+ без обращения к MediaStore (scoped storage запрещает прямой rename media-файлов вне app-collection).
   - **Ответ:** работает условно, по сценариям:
     - На устройстве с предоставленным `MANAGE_MEDIA` (special permission, запрашивается отдельно через настройки системы) — rename и последующее ручное удаление работают без диалогов; soft-delete целостный.
     - На устройстве без `MANAGE_MEDIA` — `renameTo` shared-storage media-файла системой не разрешён; код имеет fallback на copy+delete, но `File.delete()` оригинала на shared storage в API ≥ 30 также не работает без MediaStore. В наихудшем сценарии: файл оказывается продублирован в `.trash/<ts>/`, оригинал остаётся на месте, занимаемое место не уменьшается, а возрастает.
     - На устройствах с API < 30 — rename работает напрямую, soft-delete корректный.
   - **Следствие:** на типичном современном устройстве без вручную выданного `MANAGE_MEDIA` корзина в её нынешнем виде ломает само наблюдение «файл удалён».
   - **Статус:** Resolved.

5. **Учёт TTL после рестарта приложения.**
   - **Вопрос:** TTL считается от времени удаления (timestamp в имени папки) или от первого срабатывания воркера после рестарта.
   - **Ответ:** от timestamp в имени папки — рекурсивный уборщик парсит число после префикса и вычитает его из текущего системного времени, реализация устойчива к рестартам. Этот контракт сохраняется в новой версии.
   - **Статус:** Resolved.

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Накопленные trash-папки на устройствах пользователей не убираются после обновления | Высокая (на устройствах с включённой Trash они уже там) | Существенно занятое место остаётся занятым до ручной очистки или до фоновой чистки нового кода | Включить best-effort миграционный обход всех известных форматов имён в фоновом воркере; не падать на нераспознанном формате; в release notes описать, что после обновления при ближайшем фоновом проходе освободится место |

## 9. Архитектурные решения (ADR)

**ADR-1: Финальная чистка только периодическим воркером**

- **Решение:** удалить вызов чистки корзины из реакций на refresh/reload/shutdown ресурса. Финальная автоматическая чистка — только фоновый периодический воркер с TTL 5 минут (как сейчас).
- **Альтернативы:** оставить чистку на reload, но с не-нулевым TTL; ввести настраиваемый TTL в UI; чистить вручную.
- **Почему:** нулевой TTL на reload фактически нивелирует Trash как окно восстановления. Настраиваемый TTL противоречит пожеланию владельца «один тумблер». Только-вручную — слишком высокий риск утечки места.

**ADR-2: Единое соглашение об именах trash-директорий**

- **Решение:** ввести один объект-источник правды для формата имени служебной trash-директории. Создатель и уборщик пользуются им; сторонний код не имеет права писать или искать trash-папки по собственному регекспу.
- **Альтернативы:** оставить два независимых соглашения, добавить тест на их синхронность; переключить уборщик на текущее имя creator'а без рефакторинга.
- **Почему:** нынешний рассинхрон — следствие отсутствия общего контракта. Тест на синхронность лечит симптом, не причину. Просто поменять регексп — оставить ловушку для следующего рефакторинга.

**ADR-3: Локальный путь не маршрутизируется через сетевой обработчик**

- **Решение:** локальные удаления вызывают локальную стратегию напрямую из use-case; обработчик, отвечающий за SMB и связанные протоколы, не задействуется как транзит.
- **Альтернативы:** оставить транзит и переименовать обработчик в нейтральное имя.
- **Почему:** транзит — наследие предыдущих рефакторингов и непрерывный источник путаницы для нового кода и нового читателя.

## 11. Критерии готовности (strategic-level)

1. После hard-delete (Trash off) файлов из любой локальной директории на любом поддерживаемом API level свободное место на устройстве увеличивается на сумму размеров удалённых файлов (проверяется измерением до/после на physical device).
2. После soft-delete (Trash on) и истечения TTL место на устройстве реально освобождается, без необходимости пользователю выполнять refresh, повторно открывать ресурс или закрывать экран — на устройствах, где у приложения есть `MANAGE_MEDIA` (Android 12+) или где shared-storage ограничения не применяются (API < 30).
3. На устройстве без `MANAGE_MEDIA` и с API ≥ 30 пользователь либо успешно выполняет soft-delete (если приложение успело получить право), либо получает понятное сообщение о том, что для конкретного файла soft-delete недоступен и выполнено hard-delete — поведение детерминировано, без молчаливого дублирования файла на диске.
4. Refresh, повторное открытие ресурса и закрытие browse-экрана не вызывают принудительное удаление содержимого корзины — TTL отсчитывается строго от момента soft-delete по timestamp служебной директории.
5. На устройствах с предыдущей версии приложения, где остались trash-директории в любом из известных исторических форматов имён, новый фоновый воркер при первом срабатывании распознаёт и убирает их (best-effort).
6. В коде существует ровно одна реализация работы с MediaStore для локальных удалений и ровно один источник правды о формате имени trash-директорий; параллельные use-case и helper-функции с устаревшими соглашениями имён удалены.
7. Локальные удаления не проходят через сетевой обработчик ни в одном сценарии (browse-batch-delete, player undo, single delete).
