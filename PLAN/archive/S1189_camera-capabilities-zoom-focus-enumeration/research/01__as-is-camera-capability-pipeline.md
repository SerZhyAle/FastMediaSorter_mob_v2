# S1189 / Research 01 - AS-IS: как приложение определяет возможности камеры

**Дата:** 2026-07-25
**Метод:** чтение живого кода (`dev/CATALOG/scripts/query.ps1` -> целевые файлы), сверка с контрактами CameraX 1.5.3 и Camera2.
**Статус:** закрыт - выводы перенесены в §4/§5/§6 стратегической спеки.

## 1. Где сейчас живёт логика

- Перечисление камер, снимок возможностей линзы и эвристика макро сосредоточены в одном probe-классе слоя `ui/cameracapture/helpers`.
- Снимок возможностей - неизменяемая модель в `ui/cameracapture/model`, её читает UI; CameraX напрямую экран не опрашивает.
- Привязка сессии, переключение линз, зум, макро и ручные параметры - менеджер сессии в том же helpers-пакете.
- Диагностический канал в приложении уже есть: контракт «дополнительных секций» системного отчёта в `core/systeminfo`, но реализации подключены только во flavor-исходниках noLegal.

## 2. Три подтверждённых механизма и их потолок

### 2.1 Набор камер

- Источник - `ProcessCameraProvider.availableCameraInfos`, отсортированный «задние первыми».
- Это **только логические камеры**, которые платформа вернула в `CameraManager.getCameraIdList()`.
- Начиная с Android 11 в этот список **не попадают** физические подлинзы, входящие в логическую камеру: они доступны лишь через `CameraCharacteristics.getPhysicalCameraIds()` у логической камеры (API 28+, capability `LOGICAL_MULTI_CAMERA`).
- Отсюда наблюдаемое «видим только 2 камеры»: на устройстве, где OEM объединил ширик/макро/теле в одну логическую заднюю камеру, приложению видны ровно две записи - задняя логическая и фронтальная.
- CameraX 1.5.3 умеет разворачивать логическую камеру в физические: `CameraInfo.getPhysicalCameraInfos()`, а привязка к конкретной подлинзе делается через Camera2-interop расширение `setPhysicalCameraId` на билдерах use-case.

### 2.2 Нижняя граница зума

- Берётся из `zoomState.minZoomRatio` привязанной камеры.
- CameraX на API 30+ читает `CONTROL_ZOOM_RATIO_RANGE`; ниже - использует crop-region, где нижняя граница жёстко равна 1.0.
- Значит `0.6x` достижимо двумя разными путями, и на конкретном устройстве работает ровно один из них: либо логическая камера сама объявляет диапазон с нижней границей < 1, либо `0.6x` - это отдельная физическая ширикоугольная линза, невидимая по п. 2.1.
- Текущий код закрывает только первый путь. Эквивалентный множитель (`фокусное линзы / фокусное главной`) считается **между уже перечисленными** камерами, поэтому невидимая подлинза в расчёт не попадает вовсе.

### 2.3 Фокус и макро

- Макро предлагается по эвристике: минимальная дистанция фокусировки `LENS_INFO_MINIMUM_FOCUS_DISTANCE` >= 10 диоптрий.
- Включение макро - не смена линзы, а фиксация фокуса: `CONTROL_AF_MODE_OFF` + `LENS_FOCUS_DISTANCE` через Camera2-interop поверх активной линзы.
- Три причины, по которым это не срабатывает на реальном устройстве:
  - Линза с фиксированным фокусом или неоткалиброванная (`LENS_INFO_FOCUS_DISTANCE_CALIBRATION = UNCALIBRATED`) сообщает 0 - тумблер не появляется вовсе.
  - Значение читается у **логической** камеры, а не у выделенной макро-подлинзы, которая по п. 2.1 не перечислена.
  - Даже когда тумблер появился, последующий tap-to-focus возвращает автофокусный режим и молча снимает фиксацию - обратной блокировки нет.
- У OEM «макро» почти всегда реализовано как переключение на выделенную физическую линзу, а не как фиксация дистанции.

### 2.4 Разрешение фото

- Список разрешений строится из `SCALER_STREAM_CONFIGURATION_MAP.getOutputSizes(JPEG)`, дедуплицируется, сортируется по убыванию и **обрезается первыми шестью**.
- Не используется `getHighResolutionOutputSizes` (API 31+): на сенсорах с capability `ULTRA_HIGH_RESOLUTION` полное разрешение объявлено именно там, поэтому максимум, который видит пользователь, ниже физического.
- Полное разрешение также требует у CameraX явного режима «предпочесть разрешение частоте кадров» в селекторе разрешений - сейчас селектор строится только от соотношения сторон.

## 3. Что из этого проверяемо без устройства

- Проверяемо статически: сам факт, что перечисляются только логические камеры; что нижняя граница зума не пересчитывается между подлинзами; что список разрешений усечён шестью и не включает high-resolution-набор; что фиксация фокуса не защищена от сброса автофокусом.
- **Не** проверяемо статически: какие именно идентификаторы, диапазоны зума и дистанции фокуса вернёт конкретный аппарат. Это и есть причина, по которой первым шагом нужен диагностический дамп возможностей, а не сразу правка перечисления.

## 4. Ограничения по уровням API

- `getPhysicalCameraIds` / `getPhysicalCameraInfos` - API 28+.
- Диапазон зума с нижней границей < 1 (`CONTROL_ZOOM_RATIO_RANGE`) - API 30+.
- `getHighResolutionOutputSizes` - API 31+.
- Минимальный уровень flavor `legacy` - API 23, остальных - API 26. Значит каждая из трёх возможностей обязана иметь путь деградации до текущего поведения, а не быть предусловием.

## 5. Предшественники

- Мультилинзовое перечисление, пресеты зума, ночной режим и эвристика макро пришли из уже закрытых тикетов расширения возможностей камеры; эквивалентный множитель зума и цифровой доводочный зум - оттуда же.
- То есть S1189 - не «сделать с нуля», а «снять потолок логической камеры», который те тикеты не трогали.
