## 1. Проблема

`close-and-log.ps1` - фасад закрытия тикета, через который проходит каждая спека, доставившая пользовательскую возможность. Его шаг `all-features` при отсутствии `-FeatArea` / `-FeatName` / `-FeatFlavors` не отказывает, а подставляет выдумку: имя режется из описания по 80 байт, область становится `General`, список сборок - `standard`. Результат структурно валиден, `validate.ps1` его принимает, шаг рапортует успех. Неверная запись обнаруживается только глазами и только если посмотреть сразу.

Это не косметика: `docs/ALL_FEATURES.jsonl` - вход `/skill-release`, который собирает публичную витрину `docs/FEATURES*.md` из диффа инвентаря между релизами. Неверные `flavors` уводят возможность в витрину не той сборки, обрубленное имя уходит в текст витрины.

---

## 2. Цели

1. Вызов, записывающий возможность, обязан сообщить область, имя и список сборок - иначе отказ до первой мутации.
2. Скрипт перестаёт выводить имя из описания: обрубок по 80 байт не бывает верным именем.
3. Документированная форма вызова во всех скилл-доках даёт верную запись, а не бедную.

**Non-goals:**

- Не чинить ретроспективно уже записанные записи. Выборка по 42 записям в `area: General` - отдельная работа, см. §5.
- Не трогать `-FeatId`: его вывод из `<area-slug>.<name-slug>` - не выдумка, а та же информация в другой форме, и контракт уже приведён в порядок S0665.
- Не трогать идентичность на `-FuncOp DELETE` (см. §5, наблюдение вне объёма).

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

Владелец эту находку не заказывал - она запаркована по CLAUDE.md 3.1 при закрытии S1061.

### 3.2 Жёсткие ограничения

- **Совместимость вызовов:** ужесточение ломает документированную форму. Пять скилл-доков (`spec-dev`, `spec-all`, `spec-check`, `spec-arc`, `spec-fix`) правятся в этом же изменении - иначе каждое закрытие по доке начнёт падать. S1063 доказал эту связь на практике.
- **Механизм отказа:** только пре-флайт `Reject()` + exit 2, не `[Parameter(Mandatory)]`. Две причины: (1) обязательность условная - поля нужны, только когда задан `-FuncOp`, а `[Parameter(Mandatory)]` этого не выражает без parameter sets; (2) `Mandatory` в PowerShell **интерактивно спрашивает** недостающее значение, и вызов из необслуживаемой агентской сессии повиснет вместо падения.
- **Exit-контракт:** `Reject()` обязан звать `Write-Error ... -ErrorAction Continue` - при `$ErrorActionPreference = 'Stop'` голый `Write-Error` рвёт скрипт до `exit 2`, и код 2 деградирует в 1 (поймано в S1063).
- **Локализация:** не затрагивается, скрипт не пользовательский.

### 3.3 Owner inputs (Approval gate)

- **Related tickets:** S1063 (предыдущий баг того же скрипта, Verified 2026-07-16; дал пре-флайт-контракт и регрессионный харнес), S1061 (на нём поймано), S0665 (привёл в порядок контракт id записи), S0489 (завёл инвентарь).
- **API:** меняется контракт вызова `close-and-log.ps1` - три параметра становятся обязательными при заданном `-FuncOp`. Форма вызова в пяти скилл-доках правится в этом же изменении.

## 4. Контекст текущей архитектуры

Инвентарь возможностей пишется двумя путями. Прямой - `all_features/add.ps1`, требующий все поля явно. Фасадный - `close-and-log.ps1 -FuncOp/-FuncDesc`, который собирает аргументы для `add.ps1` сам.

Задумка фасада была «быстрая запись одной строкой», и на момент расследования `spec-dev.md` фиксировал это прямым текстом: «For richer record, run `scripts/all_features/add.ps1` directly with `-Id <area>.<feature> -Area -Name -Description -Flavors` instead of `-FuncOp` shortcut». То есть разделение «фасад = бедная запись, add.ps1 = богатая» было осознанным. (Эта строка переписана в фазе 2.2: после исправления оба пути дают одинаковую запись.)

Дефект в том, что «бедная» на деле означает «неверная». Терпимая бедность - это короткое имя или общее описание. Здесь же `flavors` - утверждение о факте (в каких сборках возможность существует), которое фасад угадывает, а `name` - обрубок предложения. Ни одно из двух не является упрощением правды; оба - ложь, неотличимая от истины ни для `validate.ps1`, ни для человека, читающего витрину.

Поймать это ниже по течению нельзя: `General` - легальная область (42 записи), `["standard"]` - легальный и часто верный список, обрубленное имя структурно неотличимо от короткого. Единственное место, где известна правда, - вызывающая сторона. Значит, и требовать её надо там.

## 5. Предлагаемый подход

Перенести требование правды на границу входа: если вызов записывает возможность, он обязан её описать.

### 5.1 Основные столпы / модули

- Пре-флайт `close-and-log.ps1` - место отказа, до первой мутации. Контракт (`Reject` + exit 2) уже построен S1063, нужно лишь добавить три проверки.
- Тело шага `all-features` - оттуда уходит вывод имени из описания.
- Регрессионный харнес `close-and-log.tests/Run-Tests.ps1` (18 кейсов, S1063) - туда ложатся новые кейсы.
- Пять скилл-доков - форма вызова.

### 5.2 Потоки данных и событий

Вызов -> пре-флайт проверяет: задан `-FuncOp` и не задан `-SkipFuncLog` -> обязаны быть `-FeatArea`, `-FeatName`, `-FeatFlavors`; иначе exit 2, ноль мутаций. Дальше шаг `all-features` передаёт полученные значения в `add.ps1` как есть, ничего не выводя.

### 5.3 Точки расширяемости

Проверка живёт рядом с остальными пре-флайт-проверками и повторяет их форму, поэтому четвёртое обязательное поле (если появится) добавляется одной строкой.

### 5.4 Наблюдения вне объёма

- **`-FuncOp DELETE` и идентичность записи.** Без `-FeatId` id выводится из слуга имени. Для DELETE это значит, что id считается из *нового* описания и может не совпасть с id существующей записи - тогда `add.ps1` заведёт новую запись со `status: removed` вместо того, чтобы пометить старую. Для пометки удаления профильный инструмент - `patch.ps1 -Status removed`, а не `add.ps1`. Не проверял; отдельный тикет, если подтвердится.
- **Ретроспектива по `area: General`.** 42 записи. Сколько из них осознанные, а сколько - осадок этого пути, неизвестно; выборка и починка через `patch.ps1` - отдельная работа.

## 9. Архитектурные решения (ADR)

- **ADR-1: отказ вместо умолчания.** Умолчание `flavors = standard` - не упрощение, а утверждение о факте, которое скрипт не знает. S1063 уже установил для этого скрипта принцип «падать на границе, а не писать полуправду»; здесь он же.
- **ADR-2: пре-флайт `Reject`, а не `[Parameter(Mandatory)]`.** Обязательность условная (только при `-FuncOp`), а `Mandatory` вдобавок интерактивно спрашивает недостающее - в агентской сессии это зависание вместо падения.
- **ADR-3: имя не выводится.** Убрать `Substring(0, 80)` целиком, а не «улучшить» (первое предложение и т.п.): любой вывод имени из описания остаётся угадыванием.
