## 1. Проблема

Уровню B тикета S0421 («подключение по уникальному ID + пароль», без проброса порта) нужна стабильная точка встречи в интернете: и Android-клиент, и Windows-компаньон обычно находятся за NAT без входящего доступа, поэтому самостоятельно найти друг друга не могут. Нужен общедоступный по фиксированному адресу узел, к которому обе стороны подключаются исходящими, который раздаёт/резолвит идентификатор и сводит стороны, помогая им установить прямое P2P-соединение. Без такого узла модель «по ID» невозможна. Жёсткое условие: узел НЕ переносит медиатрафик (не релей) - только метаданные знакомства.

---

## 2. Цели

1. По фиксированному адресу (IP/домен) доступен узел, к которому Windows-компаньон и Android-клиент подключаются исходящими соединениями.
2. Компаньон регистрируется и получает стабильный уникальный идентификатор; клиент по этому идентификатору находит нужного компаньона.
3. Узел сводит стороны и проксирует обмен служебной информацией для установления прямого соединения (кандидаты адресов, согласование), после чего стороны общаются напрямую.
4. Узел остаётся недоверенным: служебные сообщения пейринга (PAKE) и пользовательские данные проходят сквозь него непрозрачно - он не может ни вывести пароль, ни прочитать медиа.
5. Узел дешёв в эксплуатации и устойчив к злоупотреблениям (rate-limiting, защита от перебора ID).

**Non-goals:**

- Не переносить медиатрафик (никакого TURN/релея); при невозможности прямого P2P узел не подменяет соединение.
- Не хранить пользовательский контент и учётные данные в открытом виде; узел оперирует только метаданными знакомства.
- Не реализовывать собственную крипту/NAT-traversal - опираться на проверенный OSS-стек, согласованный с S0421.
- Не быть единственной точкой отказа для уровня A тикета S0421 (LAN и port-forward работают без этого узла).

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Минимальная стоимость владения (дешёвый VPS, «крошечная VM»).
2. Совмещение ролей по возможности: на том же узле - signaling, директория ID и (опц.) STUN.
3. Простая эксплуатация: предсказуемое потребление, понятный мониторинг, малое обслуживание.
4. Возможность для продвинутого пользователя указать собственный self-hosted узел.

### 3.2 Жёсткие ограничения

- **Роль:** только rendezvous/signaling (+ опц. STUN). Перенос медиа запрещён архитектурно.
- **Доступность:** фиксированный публичный адрес (IP или домен) с TLS.
- **Доверие:** узел недоверенный; сквозная безопасность обеспечивается между пирами, не узлом.
- **Стоимость:** трафик узла - только мелкие управляющие сообщения; никакой оплаты по медиатрафику.
- **Приватность:** хранится минимум метаданных; политика согласована с приватностью S0421.
- **Совместимость:** протокол signaling согласован с выбранным на стороне S0421 P2P-стеком (кандидат - WebRTC-подобный без TURN).

### 3.3 Owner inputs (Approval gate)

- **Related tickets:** S0421 (потребитель; этот узел обслуживает только его уровень B).

## 4. Контекст текущей архитектуры

У проекта сейчас нет собственного backend-сервиса: FastMediaSorter - это Android-клиент, а в рамках S0421 добавляется Windows-компаньон (отдельный субпроект). Уровень B S0421 вводит P2P-доступ «по ID», который структурно требует посредника знакомства - его в текущей архитектуре нет. Данный тикет описывает этот посредник как отдельный разворачиваемый артефакт, чтобы клиентский тикет S0421 оставался сфокусированным на UX и транспорте, а инфраструктура имела свой жизненный цикл, security-surface и эксплуатацию.

---

## 5. Предлагаемый подход

### 5.1 Основные столпы / модули

- **Точка входа по фиксированному адресу:** домен/IP + TLS; обе стороны держат исходящее соединение к узлу.
- **Директория идентификаторов:** регистрация компаньона под стабильным уникальным ID; резолв ID при запросе клиента. Энтропия ID достаточна, чтобы исключить сканирование/перебор.
- **Сведение и signaling:** сопоставление клиента с нужным компаньоном и проксирование служебного обмена для установления прямого соединения; после установления узел из тракта данных выходит.
- **Опциональный STUN:** помощь сторонам узнать свои внешние адреса (на том же узле либо публичный).
- **Защита от злоупотреблений:** rate-limiting, экспоненциальный backoff, одноразовость попыток пейринга, лимиты на регистрацию/резолв.
- **Непрозрачный канал пейринга:** служебные сообщения PAKE между пирами проходят сквозь узел как непрозрачные - узел не участвует в выводе ключа.

### 5.2 Потоки данных и событий

- Компаньон при старте устанавливает исходящее соединение к узлу, регистрируется и получает/подтверждает свой ID; держит соединение для входящих запросов на знакомство.
- Клиент по введённому ID обращается к узлу; узел проверяет лимиты и сводит клиента с компаньоном.
- Через узел стороны обмениваются служебной информацией (PAKE-сообщения, кандидаты адресов) и пытаются установить прямое P2P-соединение.
- При успехе данные (SFTP-поверх-туннеля по S0421) идут напрямую, минуя узел; при неудаче - честный отказ на стороне клиента, узел медиа не подменяет.

### 5.3 Точки расширяемости

- Адрес узла конфигурируется на клиенте и компаньоне (узел владельца по умолчанию, допускается self-hosted).
- Роли (signaling/директория/STUN) разделяемы, чтобы при росте нагрузки их можно было развести по узлам.
- Протокол signaling версионируется для совместимости клиента/компаньона разных версий.
- Базовая модель идентификатора опирается на стабильный долгоживущий ID компаньона для постоянного unattended-доступа; поверх неё в будущем можно добавить одноразовые per-session коды, не ломая основной сценарий.

## 6. Открытые вопросы / Research items

1. Технологический стек и рантайм узла (что дёшево хостится, легко эксплуатируется и согласуется с P2P-стеком S0421).
2. Протокол signaling: использовать сигнальный слой выбранного OSS-стека или минимальный собственный (напр. на постоянных исходящих соединениях поверх TLS) - решается вместе с выбором транспорта в S0421.
3. Модель учёта идентификаторов при уже выбранном постоянном доступе: как выдаётся и хранится стабильный долгоживущий ID компаньона, нужна ли минимальная персистентность (мелкая БД) и допускаются ли поверх него одноразовые коды в будущих итерациях.
4. Энтропия ID и анти-сканирование: длина/формат ID, троттлинг резолва, одноразовость кодов пейринга.
5. TLS/домен/сертификат: автоматизация (напр. Let's Encrypt), фиксированный IP vs домен, обновление.
6. STUN: совмещать на узле или использовать публичный; влияние на стоимость/нагрузку.
7. Защита от DoS/злоупотреблений и предотвращение случайного превращения в релей (жёсткий отказ переносить полезные данные).
8. Приватность/юридика: какой минимум метаданных хранить, срок хранения, нужна ли privacy-нота; согласовать с S0421.
9. Эксплуатация: мониторинг, алертинг, обновления, оценка стоимости при малом и среднем числе пользователей.
10. Self-host: насколько просто продвинутому пользователю поднять свой узел и как это документировать.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Случайное превращение в релей (перенос данных) | Средняя | Рост трафика/стоимости, нарушение принципа | Архитектурный запрет на проксирование полезных данных; только служебные сообщения; лимиты размера |
| Злоупотребление/DoS, перебор ID | Средняя | Деградация сервиса, утечка соответствий ID | Высокая энтропия ID; rate-limiting/backoff; одноразовые коды; квоты |
| Единая точка отказа уровня B | Средняя | При недоступности узла «по ID» не работает | Уровень A (LAN/port-forward) не зависит от узла; авто-выбор пути в S0421; возможный self-host |
| Рост стоимости при масштабе | Низкая | Неожиданные счета | Только управляющий трафик; мониторинг; разнесение ролей при росте |
| Компрометация узла | Низкая | Доступ к метаданным знакомства | Недоверенная модель: пейринг PAKE и данные сквозные; минимум хранимых метаданных |
| Расхождение протокола клиент/компаньон | Средняя | Несовместимость версий | Версионирование signaling; обратная совместимость |

## 9. Архитектурные решения (ADR)

- **ADR-1:** Только signaling/rendezvous, без TURN/релея. Причина: жёсткое условие владельца «без оплаты трафика»; данные строго P2P.
- **ADR-2:** Узел недоверенный; сквозная безопасность (PAKE + шифрование) между пирами. Причина: минимизация ответственности и поверхности атаки.
- **ADR-3:** Обе стороны подключаются исходящими к фиксированному адресу. Причина: обход NAT без входящего доступа на пирах.
- **ADR-4:** Отдельный тикет от S0421. Причина: отдельный разворачиваемый артефакт со своим жизненным циклом, security-surface и эксплуатацией.

---

## 10. Связи с другими спеками

- S0421 - единственный потребитель; этот узел обслуживает его уровень B. Уровень A S0421 от узла не зависит.
- S0046 - паттерны безопасности SFTP/пиннинга для согласования модели доверия.

---

## 11. Критерии готовности (strategic-level)

1. По фиксированному адресу (IP/домен) с TLS доступен работающий узел.
2. Windows-компаньон регистрируется и получает стабильный уникальный идентификатор; узел переживает перезапуск без потери возможности резолва.
3. Android-клиент по идентификатору сводится с нужным компаньоном, и стороны устанавливают прямое P2P-соединение.
4. Медиатрафик никогда не проходит через узел; при невозможности прямого соединения узел его не подменяет.
5. Действуют ограничения от злоупотреблений (rate-limiting, защита от перебора ID, одноразовые коды пейринга).
6. Стоимость владения остаётся низкой и предсказуемой (только управляющий трафик).
7. Документирована возможность self-host собственного узла.
