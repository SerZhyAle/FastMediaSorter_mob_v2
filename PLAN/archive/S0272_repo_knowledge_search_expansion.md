## 1. Проблема

Текущий MCP-сервер `docs-search` индексирует только директорию `docs/`. Это охватывает публичную документацию (`FEATURES`, `ARCHITECTURE`, `TECH_STACK`, `COMMUNICATION_POLICY` и пр.), но за его пределами остаётся вся внутренняя агентская база знаний, к которой агент обращается чаще, чем к публичной документации. Сюда входят основной guidance-файл `CLAUDE.md`, его зеркало для Codex `AGENTS.md`, инструкции Copilot `.github/copilot-instructions.md`, индекс операций `dev/PROJECT_OPERATIONS_INDEX.md`, обязательный workflow `dev/AGENT_WORKFLOW.md`, журнал спецификаций `PLAN/spec-catalog.jsonl`, каталоги классов `dev/CATALOG/*` и каталог активностей `dev/ACTIVITY_CATALOG/*`.

Сейчас агент достаёт эти источники через нативные `Read` и `Grep`. Это работает, но даёт другой паттерн: чтение всего файла или regex-поиск, без структурированного MCP-ответа "релевантный фрагмент + путь + контекст". Для коротких справочных запросов ("что говорит CLAUDE.md про BuildConfig-гейты", "какой priority у S0241", "какие классы в `data/network/` помечены ролью `Repository`") нативные инструменты возвращают слишком много или слишком мало. MCP-паттерн `docs-search` уже доказал ценность на `docs/` — но именно на наиболее цитируемых guidance-файлах его нет.

Параллельно аудит `dev/development_audit.md` (§5) явно фиксирует этот разрыв как одну из шести высокоподтверждённых находок: "Repo knowledge search is too narrow — searchable knowledge should not stop at `docs/`".

Проверка `.vscode/mcp.json` на 2026-05-20 подтверждает, что сейчас зарегистрированы только четыре сервера: `docs-search`, `filesystem_rw`, `filesystem_ro`, `gradle_safe`. Отдельного read-only сервера для внутренней guidance-базы в текущем конфиге нет.

---

## 2. Цели

1. Агенты (Claude Code, Copilot в VS Code, Codex и любой другой MCP-клиент в репозитории) получают единый search-and-return-with-context механизм для guidance-файлов вне `docs/` — наравне с тем, что уже есть для публичной документации через `docs-search`.
2. Индексируемая поверхность расширяется до перечня: `CLAUDE.md`, `AGENTS.md`, `.github/copilot-instructions.md`, `dev/PROJECT_OPERATIONS_INDEX.md`, `dev/AGENT_WORKFLOW.md`, `PLAN/spec-catalog.jsonl`, `dev/CATALOG/*`, `dev/ACTIVITY_CATALOG/*`.
3. Поиск работает в режиме read-only — никаких write-операций через новый MCP-сервер не предоставляется.
4. Архитектурно отделены два разных аудиторских контура: публичная документация (`docs-search`, для внешних читателей и feature-докладов) и внутренняя guidance-база (для агентского контура). Смешивание поверхностей не происходит.
5. Решение универсально по клиенту: новый сервер регистрируется через `.vscode/mcp.json`, доступен в VS Code Copilot, и пригоден для подключения из Claude Code и Codex (если у них настроен соответствующий MCP-клиент).
6. Расход на индексацию и поиск остаётся в рамках уже принятого паттерна `docs-search` — без интеграции внешних движков, без сетевой зависимости, без долгоживущего демона за пределами того, что уже есть.

**Non-goals:**

- Не добавляются write-операции через MCP (новый сервер строго read-only).
- Не пересматриваются и не правятся существующие MCP-серверы `filesystem_rw`, `filesystem_ro`, `gradle_safe` — это отдельные аудиты.
- Не вводится векторный поиск, embedding-индексы, ML-семантика — это другой класс задач.
- Не реализуется UI просмотра результатов — клиентом остаётся существующий MCP-клиент агента.
- Не меняется поведение существующего `docs-search` сверх минимально необходимого для разграничения с новым сервером (если в итоге выбирается путь параллельного сервера).
- Не вводится индексация исходного кода Kotlin/Java — для этого уже есть `dev/CATALOG/`, и его консьюмер — отдельная история.
- Не индексируются временные/локальные файлы: `temp/`, `logs/`, `.kotlin/`, `node_modules/`, `build/`, `.gradle/`.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Архитектурно предпочтительнее не раздувать `docs-search`, а ввести отдельный read-only MCP-сервер с понятным именем — это сохраняет существующий сервер нетронутым и делает аудиторию каждого сервера очевидной.
2. Новый сервер ведёт себя как `docs-search`: тот же протокол вызова, тот же стиль возвращаемого фрагмента, та же модель "путь + сниппет + контекст".
3. Спец-каталог `PLAN/spec-catalog.jsonl` идеально подходит под структурированный запрос (по `id`, по `status`, по `priority`), а не под текстовый grep. Желательно, чтобы новый сервер умел отвечать на простые структурированные запросы по нему, а не только возвращать сырые строки JSONL.
4. Каталоги `dev/CATALOG/*` и `dev/ACTIVITY_CATALOG/*` — гибрид: их `.md`-render индексируется как текст, `.jsonl` — потенциально структурно. Окончательное решение оставляется тактической фазе.
5. Имя нового сервера должно быть осмысленным и однозначно описывать аудиторию. Финальное имя выбирается на тактическом уровне (см. §6 пункт 2).
6. Поскольку существующий `docs-search` уже опубликован и работает, новый сервер должен полностью с ним сосуществовать: одновременная регистрация двух серверов в `.vscode/mcp.json` — нормальное состояние.

### 3.2 Жёсткие ограничения

- **Read-only:** Сервер не предоставляет инструментов модификации файлов. Любая запись в индексируемые источники по-прежнему идёт через нативный `Edit`/`Write` агента и существующий `filesystem_rw` MCP.
- **Источники только из репозитория:** Сервер не выходит в сеть, не индексирует ничего за пределами WORKSPACE_ROOT. Источники объявлены явным списком в конфигурации — никакой автоматической рекурсии по неперечисленным путям.
- **Гитigniored-файлы исключаются:** Файлы вида `dev/CATALOG/<module>.jsonl` и `<module>.md` помечены `.gitignored` (см. memory `project_build_gotchas.md`). Они генерируются локально и должны индексироваться по локальному состоянию, без требования к их наличию в git.
- **Доступность для нескольких клиентов:** Регистрация в `.vscode/mcp.json` — обязательна; параллельная регистрация для Claude Code и Codex — желательна, но конкретный механизм выбирается на тактическом уровне (зависит от текущих возможностей этих агентов).
- **Производительность:** Запрос к новому серверу не должен быть медленнее, чем эквивалентный сценарий `Read` + `Grep` по тем же файлам. Конкретный бюджет фиксируется тактической фазой.
- **Обновление индекса:** Сервер обязан отражать актуальное состояние файлов на диске (репозиторий — живой; каталоги пересоздаются, спеки добавляются, guidance-файлы редактируются). Конкретная модель (ленивая индексация при запросе, watcher, кэш с TTL) выбирается на тактическом уровне.
- **Совместимость с существующим `docs-search`:** Если будет принято решение расширять `docs-search` вместо добавления отдельного сервера, его контракт с уже работающими клиентами не должен ломаться.
- **Локализация:** Не применимо — индексируется guidance-контент на смешанной кириллице/латинице, никаких пользовательских строк не добавляется.
- **Доступность:** Не применимо — сервер не имеет UI.
- **Communication policy:** Не применимо — сервер не возвращает пользовательских сообщений.

## 4. Контекст текущей архитектуры

`.vscode/mcp.json` сейчас регистрирует четыре сервера:

- **docs-search** — собственный Node-сервер из `scripts/mcp/docs-search-mcp/`, проинициализирован с `DOCS_ROOT=${workspaceFolder}/docs`. Это означает, что его область поиска жёстко ограничена директорией `docs/` — расширить её без изменения конфигурации или кода сервера невозможно.
- **filesystem_rw** — стандартный `@modelcontextprotocol/server-filesystem` от npm-пакета, выдаёт чтение и запись по всему WORKSPACE_ROOT. Универсальный, но грубый: даёт доступ к файлам как к файлам, без сниппет-извлечения.
- **filesystem_ro** — собственный Node-сервер из `scripts/mcp/docs-search-mcp/filesystem-ro-server.js`, read-only-вариант filesystem-доступа.
- **gradle_safe** — собственный Node-сервер для безопасного запуска Gradle-задач.

Соответственно, на текущий момент агентский контур получает доступ к guidance-файлам тремя способами:

1. Нативный `Read` — целиком грузит файл в контекст. Для коротких справок это избыточно, для длинных файлов (`CLAUDE.md`, `dev/PROJECT_OPERATIONS_INDEX.md`) — расточительно.
2. Нативный `Grep` — возвращает совпадения по regex, без структурирования контекста (что за раздел, какой соседний абзац).
3. `filesystem_ro` MCP — повторяет тот же паттерн "файл целиком", только через MCP-протокол; не даёт сниппета.

То есть текущая поверхность работает, но в ней нет аналога `docs-search`-паттерна для внутренней guidance-базы. Внешняя публичная документация имеет привилегированный канал, а внутренние ежедневные источники — нет.

Аудит (§5, §В, §Г) подтверждает: чаще всего агент ходит именно в guidance-файлы (`CLAUDE.md`, `dev/PROJECT_OPERATIONS_INDEX.md`, `PLAN/spec-catalog.jsonl`), а не в `docs/`. Узкая поверхность поиска именно там, где запросов больше всего.

## 5. Предлагаемый подход

### 5.1 Выбор между расширением docs-search и добавлением отдельного сервера

Возможны два пути:

**(a) Расширение текущего `docs-search` MCP.**

Подход: добавить новые источники к существующему `docs-search` сервера через расширение `DOCS_ROOT` или конфигурируемый список путей. Один сервер обслуживает обе аудитории — публичную документацию и внутренний guidance.

- Плюс: одно место конфигурации, одна точка обслуживания, одна история коммитов.
- Минус: смешивание двух разных аудиторий в одном пространстве поиска. Публичные `docs/FEATURES.md` и внутренний `CLAUDE.md` начинают конкурировать в выдаче по одинаковым ключевым словам, и при этом семантически адресованы разным читателям. Сервер `docs-search` уже используется некоторыми клиентами в его текущем виде — расширение области приведёт к скрытой смене поведения у этих клиентов.

**(b) Параллельный read-only сервер для guidance-базы.**

Подход: оставить `docs-search` без изменений, добавить отдельный MCP-сервер в `.vscode/mcp.json` с явным именем, отражающим аудиторию (например, `repo-knowledge`, `agent-guidance`, `internal-search` — окончательное имя выбирается на тактическом уровне, см. §6 пункт 2). Источники нового сервера — guidance-файлы и каталоги, перечисленные в §2 цели 2.

- Плюс: чёткое разграничение аудиторий, существующий `docs-search` нетронут, ни один клиент его поведение не теряет, каждый сервер виден в `.vscode/mcp.json` под своим именем и его область очевидна.
- Минус: два сервера вместо одного, чуть больше кода и конфигурации в репозитории.

**Выбор:** путь (b). Аудитории действительно разные: `docs-search` обслуживает публичные feature-доклады и пользовательскую документацию, новый сервер — внутренние агентские guidance-файлы и каталоги. Стоимость второго сервера невелика — паттерн уже отлажен на `docs-search`. Гарантия неизменности поведения существующих клиентов перевешивает экономию одного файла конфигурации.

### 5.2 Перечень индексируемых источников

Новый сервер индексирует следующие источники в режиме read-only:

- `CLAUDE.md` — основной guidance для Claude Code.
- `AGENTS.md` — зеркало guidance для Codex.
- `.github/copilot-instructions.md` — инструкции для GitHub Copilot.
- `dev/PROJECT_OPERATIONS_INDEX.md` — индекс операций и feature-to-path-карта.
- `dev/AGENT_WORKFLOW.md` — обязательный многошаговый процесс.
- `PLAN/spec-catalog.jsonl` — журнал всех спецификаций (id, name, status, priority, file, created, updated).
- `dev/CATALOG/*` — каталог классов модулей (рендеры `.md` и индексные `.jsonl`).
- `dev/ACTIVITY_CATALOG/*` — каталог активностей и навигационных потоков.

Источники объявляются явным списком в конфигурации сервера. Никакой автоматической рекурсии за пределы перечня нет.

### 5.3 Режим доступа

- Все источники доступны только для чтения. Сервер не предоставляет инструментов изменения файлов.
- Сервер не выходит в сеть. WORKSPACE_ROOT — единственная допустимая граница.
- Сервер уважает гитигнор только в смысле "не падать, если файла нет на диске" (например, `dev/CATALOG/<module>.jsonl` локально может ещё не быть сгенерирован) — но если файл присутствует локально, он индексируется независимо от его статуса в git.

### 5.4 Интеграция с прочими агентами помимо VS Code Copilot

Регистрация в `.vscode/mcp.json` — основная точка входа, обеспечивает доступность для VS Code Copilot. Для других агентских клиентов:

- **Claude Code** — текущая поверхность Claude Code в этом репозитории использует MCP-серверы, перечисленные в `.vscode/mcp.json` через соответствующий механизм проекта. Способ подключения нового сервера к Claude Code конкретизируется на тактическом уровне (зависит от того, какой конфигурационный артефакт читается Claude Code: тот же `.vscode/mcp.json`, отдельный `.claude/mcp.json`, или другая поверхность).
- **Codex** — подключение через конфигурацию Codex, аналогично. Конкретный механизм — на тактическом уровне.
- **Другие MCP-клиенты** — поскольку сервер реализует стандартный MCP-протокол, любой совместимый клиент сможет подключиться.

Принципиальная гарантия: сервер сам по себе клиент-агностичен, и его пригодность для каждого конкретного агента определяется тем, читает ли этот агент его регистрацию из соответствующего конфигурационного файла.

### 5.5 Что меняется и что не меняется

**Меняется:**

- `.vscode/mcp.json` получает регистрацию нового сервера.
- В репозитории появляется новый Node-сервер (расположение, имя пакета, структура — задача тактической фазы; стиль повторяет `docs-search`).

**Не меняется:**

- Поведение `docs-search` — нетронуто.
- Поведение `filesystem_rw`, `filesystem_ro`, `gradle_safe` — нетронуто.
- Сами guidance-файлы не редактируются и не реструктуризируются под новый сервер.
- Существующие нативные пути `Read`/`Grep` к guidance-файлам остаются доступны — новый сервер дополняет, а не вытесняет их.

## 6. Открытые вопросы / Research items

1. **Структурированный или сырой доступ к `PLAN/spec-catalog.jsonl`**
   - **Решение:** гибрид. Общий поиск индексирует `PLAN/spec-catalog.jsonl` как часть repo-knowledge search surface, а отдельный read-only MCP tool даёт структурированный доступ по `id`, `status`, `priority` и `tier` для частых операторских запросов.
   - **Почему:** это закрывает оба паттерна без усложнения общего поискового контракта: обычный query возвращает сниппет и путь, а частый сценарий работы со спекой не деградирует до grep по JSONL.
   - **Статус:** Resolved inline during `/spec-all` tactical stage.

2. **Имя нового MCP-сервера**
   - **Решение:** `repo-knowledge`.
   - **Почему:** это имя уже последовательно предлагается внутренними аудитами (`dev/development_audit.md`, `dev/gpt_audit.md`, `dev/codex_audit.md`, `dev/claude_audit.md`), визуально не конфликтует с `docs-search` и прямо описывает область покрытия: знания о репозитории, а не публичную документацию.
   - **Статус:** Resolved inline during `/spec-all` tactical stage.

3. **Модель обновления индекса**
   - **Решение:** ленивая индексация read-from-disk на каждый запрос, без долгоживущего кэша и без watcher'ов.
   - **Почему:** текущий `docs-search` уже использует build-on-request паттерн, а curated surface для нового сервера невелика. Это даёт актуальность сразу после `insert.ps1`, `update.ps1` и `catalog_sync.ps1` без дополнительной инвалидации.
   - **Статус:** Resolved inline during `/spec-all` tactical stage.

4. **Индексация `dev/CATALOG/*` — `.md` или `.jsonl` (или оба)**
   - **Решение:** индексируются оба представления. `.md` остаётся human-readable surface для разделов и summaries, `.jsonl` индексируется построчно как source-of-truth для точных class/path/role/injected queries.
   - **Почему:** локальные каталоги уже существуют в двух формах, и каждая из них обслуживает свой тип вопроса. Отказ от одной из поверхностей либо ухудшает сниппет-контекст, либо теряет структурные поля.
   - **Статус:** Resolved inline during `/spec-all` tactical stage.

5. **Граница регистрации для Claude Code и Codex**
   - **Решение:** in-repo registration делается только через `.vscode/mcp.json`; для остальных клиентов tactical implementation ограничивается документацией по ручному подключению, если они не потребляют этот файл автоматически.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Новый сервер дублирует функциональность существующих `filesystem_ro` или `docs-search` без явной добавленной ценности | Низкая | "Лишний" сервер в `.vscode/mcp.json`, без реального использования агентами | Чётко разграничить аудитории на тактическом уровне; в acceptance — сценарий, где новый сервер даёт результат, недостижимый через `filesystem_ro`/`docs-search`/`Read`/`Grep` |
| Несогласованность с `docs-search` в стиле возвращаемого фрагмента | Средняя | Агенты получают разный UX для двух семантически близких серверов | Тактическая спека обязана зафиксировать контракт ответа — сниппет, путь, контекст вокруг — точно повторяя `docs-search` |
| Кэш индекса устаревает после `insert.ps1`/`update.ps1` или регенерации каталогов | Средняя | Сервер возвращает данные на старую версию `spec-catalog.jsonl` после добавления новой спеки | Модель обновления индекса (см. §6 пункт 3) обязана учитывать частоту записи в каждый источник; для `spec-catalog.jsonl` — никакого долгоживущего кэша без инвалидации |
| Конфигурация `.vscode/mcp.json` поломается на старых клиентах при добавлении сервера | Низкая | VS Code Copilot не загрузится в репозитории до обновления MCP-протокола в клиенте | Стандартный stdio-MCP — широко поддерживаемый паттерн, риск близок к нулю; verify локально перед коммитом |
| Read-only обещание сервера нарушается в реализации (например, через символическую ссылку или path traversal) | Низкая | Через MCP-сервер возможна неконтролируемая модификация файлов | Тактическая спека фиксирует требование "только методы чтения в API сервера" + явный отказ от любых tools, имена которых содержат `write`/`edit`/`delete`/`mutate` |
| Производительность хуже, чем у нативного `Read` + `Grep` | Низкая | Агенты не пользуются новым сервером, продолжая ходить нативно | Бюджет производительности — критерий приёмки тактической фазы; реалистичный сценарий — поиск ключевого слова в `CLAUDE.md` без полной загрузки файла |
| Имя нового сервера конфликтует с уже существующим в каком-либо агентском контексте | Низкая | Регистрация игнорируется, сервер не виден | Имя выбирается на тактическом уровне (§6 пункт 2) с проверкой уникальности по всем известным MCP-конфигам репозитория |

## 9. Архитектурные решения (ADR)

**ADR-1: Отдельный сервер вместо расширения `docs-search`**

- **Решение:** Вводится новый read-only MCP-сервер; `docs-search` остаётся в текущем виде.
- **Альтернативы:** Расширить `docs-search`, передав ему список источников за пределами `docs/`.
- **Почему:** `docs-search` обслуживает публичную документацию — целевая аудитория этой поверхности отличается от целевой аудитории guidance-файлов и каталогов. Смешивание ведёт к конкуренции в выдаче по одним ключевым словам с разной интерпретацией. Цена параллельного сервера невелика — паттерн уже отлажен на `docs-search`. Гарантия неизменности поведения существующих клиентов перевешивает экономию одного файла конфигурации.

**ADR-2: Read-only без исключений**

- **Решение:** Новый сервер не предоставляет ни одного инструмента модификации файлов. Запись в guidance-файлы и каталоги по-прежнему идёт через нативный `Edit`/`Write` или `filesystem_rw`.
- **Альтернативы:** Добавить write-операции для частных случаев (например, append к `spec-catalog.jsonl`).
- **Почему:** Запись в `spec-catalog.jsonl` уже строго регламентирована через CLI скрипты `scripts/spec_catalog/` (см. CLAUDE.md Rule 13). Введение альтернативного пути записи через MCP противоречит этому правилу. Read-only-граница делает контракт сервера простым и аудируемым.

**ADR-3: Источники объявляются явным списком, без рекурсии**

- **Решение:** Сервер индексирует только перечисленные в §5.2 источники. Никакой автоматической рекурсии по подкаталогам, кроме явно перечисленных (`dev/CATALOG/*`, `dev/ACTIVITY_CATALOG/*`).
- **Альтернативы:** Индексировать всё, кроме `temp/`, `logs/`, `build/`, `.gradle/`, `node_modules/`.
- **Почему:** Явный список делает поверхность сервера предсказуемой и не позволяет случайно проиндексировать содержимое, не предназначенное для агентского поиска (например, бэкапы в `temp/`, выгрузки логов). Расширение списка — это сознательный коммит в репозиторий, видимый при code-review.

**ADR-4: Локальное состояние имеет приоритет над git-состоянием**

- **Решение:** Если файл `dev/CATALOG/<module>.jsonl` или `.md` сгенерирован локально (он `.gitignored`), он индексируется. Если он отсутствует — сервер просто не отдаёт ничего для этого источника, без падения.
- **Альтернативы:** Игнорировать `.gitignored`-файлы.
- **Почему:** Эти каталоги — критический агентский ресурс, и они существуют именно в локальном состоянии разработчика. Привязка к git-состоянию обесценила бы их.

## 11. Критерии готовности (strategic-level)

1. В `.vscode/mcp.json` зарегистрирован новый MCP-сервер с именем, отражающим его аудиторию (agent-internal guidance + каталоги).
2. Существующий `docs-search` остался в текущем виде — его регистрация и поведение не изменились.
3. Новый сервер read-only — у него нет ни одного метода/инструмента, имя которого содержит запись, изменение или удаление файла.
4. Перечень индексируемых источников включает: `CLAUDE.md`, `AGENTS.md`, `.github/copilot-instructions.md`, `dev/PROJECT_OPERATIONS_INDEX.md`, `dev/AGENT_WORKFLOW.md`, `PLAN/spec-catalog.jsonl`, `dev/CATALOG/*`, `dev/ACTIVITY_CATALOG/*`.
5. Запрос к новому серверу возвращает сниппет с путём и контекстом — паттерн, эквивалентный `docs-search`.
6. Сервер не выходит в сеть и не индексирует ничего за пределами WORKSPACE_ROOT.
7. Локально сгенерированные `.gitignored`-файлы в `dev/CATALOG/*` индексируются, если они присутствуют на диске; их отсутствие не вызывает ошибок.
8. Сервер доступен в VS Code Copilot из коробки через `.vscode/mcp.json`. Для Claude Code и Codex — либо доступен из того же конфига, либо механизм подключения зафиксирован в тактической спеке (если требуется отдельная регистрация).
9. Производительность запроса не хуже эквивалентного нативного `Read` + `Grep`-сценария по тем же источникам (конкретный бюджет — критерий приёмки тактической фазы).
10. `docs/FEATURES.md` не изменён (внутренняя инфраструктура, не пользовательская функциональность).
