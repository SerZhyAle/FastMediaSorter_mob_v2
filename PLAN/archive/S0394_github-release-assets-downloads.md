## 1. Проблема

Сейчас релизные APK после сборки расходятся только по приватным каналам: локальная папка `DOWNLOADS/` (в `.gitignore`), Google Drive (сырой APK + ZIP под паролем) и tc-папка. Публичный GitHub Release заполняется отдельным ручным шагом и только для двух сборок (standard и vr). Остальной спектр (lite, photos, legacy, Wear OS, noLegal) в публичные ассеты не попадает вообще.

На сайте программы карточка «Download APK Builds» ведёт на текстовый документ, который честно говорит «APK в репозитории нет — качайте с Google Drive по паролю». Для постороннего пользователя это лишний барьер: нужно идти на Google Drive, знать пароль от ZIP, выбирать вариант вслепую.

В итоге есть готовый публичный канал доставки (GitHub Releases), но он недонаполнен, а сайт на него не опирается. Пользователь не может в один клик скачать нужную сборку с официальной страницы.

---

## 2. Цели

1. После сборки релизного спектра каждый собранный APK автоматически попадает в один GitHub Release как ассет: standard, vr, lite, photos, legacy, Wear OS и noLegal.
2. Все ассеты одного релиза несут единую версию в имени — устранён разнобой версий между флейворами, собранными в разное время.
3. Страница сайта (index на EN/RU/UK) показывает прямые кнопки скачивания публичных сборок (standard, vr, lite, photos, legacy, Wear OS), берущие файл из последнего GitHub Release, с актуальной версией.
4. noLegal-сборка публикуется как ассет, но ссылка на неё доступна только со страниц `nolegal*.html`, не с главной.
5. Документы «Downloads» (EN/RU/UK) указывают на GitHub Release как на основной источник, сохраняя упоминание Google Drive как зеркала.
6. Шаг публикации в GitHub Release задокументирован как часть релизного конвейера (матрица каналов дистрибуции).

**Non-goals:**

- Не меняем каналы Google Drive, tc-папки, Google Play, 4pda (остаются как есть, в роли зеркал).
- Не трогаем внутренний код приложения и сорс-сеты флейворов — спека про сборку и публикацию артефактов, не про функции в приложении.
- Не вводим автоматический CI на серверах GitHub — публикация выполняется из существующего релизного конвейера на машине разработчика.
- Не меняем схему именования, ломающую сторонние индексаторы (IzzyOnDroid).

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Минимум ручных шагов: в идеале публикация всего спектра — один прогон, а не отдельный запуск на каждый флейвор.
2. Сайт не должен требовать ручной правки ссылок на каждый релиз — версия и адреса файлов подтягиваются сами.
3. Деградация при сбое: если данные о релизе недоступны, у пользователя остаётся рабочая ссылка на страницу релизов.

### 3.2 Жёсткие ограничения

- **Flavor:** затрагиваются все релизные варианты — standard, vr, lite, photos, legacy, noLegal, плюс отдельный артефакт Wear OS. Это касается только *дистрибуции уже собранных* артефактов; новый код в сорс-сетах флейворов не добавляется, поэтому правила `dev/FLAVOR_DEVELOPMENT_RULES.md` (интерфейс в `src/main` + реализация в `src/<flavor>`) здесь неприменимы — нет flavor-специфичного кода приложения.
- **noLegal-граница:** noLegal публикуется как ассет, но на публичной главной странице не упоминается и ссылок на него там нет — только на `nolegal*.html`. Это сохраняет действующую политику «noLegal не для публичных сторов/витрин».
- **Подпись:** все релизные флейворы подписываются единым release-ключом (на уровне build type), поэтому один ожидаемый отпечаток покрывает весь спектр. Wear OS — отдельный модуль, его конфигурацию подписи нужно подтвердить отдельно (см. §6).
- **Именование ассетов:** имена файлов сохраняют версию в имени, чтобы не сломать сторонний индексатор, который ищет ассеты по маске с версией.
- **API level:** без API-специфики — задача инфраструктурная (сборка, публикация, веб-страница).
- **Локализация:** тексты на сайте и в документах Downloads — EN/RU/UK в паритете, всегда обязательно.
- **Совместимость данных:** миграций данных нет.

### 3.3 Owner inputs (Approval gate)

- **Flavor scope:** ассеты релиза — standard, vr, lite, photos, legacy, Wear OS, noLegal. На главной странице сайта — только публичная шестёрка (без noLegal). noLegal — ссылка только на `nolegal*.html`.
- **Wear OS:** включён отдельным артефактом-ассетом и отдельной ссылкой для ручной установки; обычным приложением не ставится.
- **Localization:** сайт и документы Downloads — EN/RU/UK в паритете.
- **UI placement contract:** кнопки скачивания живут в существующем блоке «Download APK Builds» на `index*.html`; noLegal-кнопка — только на `nolegal*.html`. Размещение подтверждено владельцем 2026-06-10.
- **Validation level:** релизная/целевая сборка спектра проходит, публикация создаёт релиз со всеми ожидаемыми ассетами, страница сайта отдаёт рабочие ссылки на эти ассеты.

## 4. Контекст текущей архитектуры

Релизные сборки выполняются из выделенного git-worktree на ветке `main`; каждый билдер сам штампует версию из текущего времени, кладёт APK в локальную `DOWNLOADS/`, зеркалит на Google Drive и в tc-папку, дописывает строку в журнал сборок. Единой команды «собрать весь спектр» нет — есть отдельные билдеры на флейвор и оркестратор «build and push all».

Публикация в GitHub Release реализована отдельным шагом (наследие S0214): он создаёт тег `v{версия}` из `main`, проверяет отпечаток подписи по закреплённому значению, вытягивает release notes и заливает ассеты. Сейчас этот шаг знает только про standard и vr и запускается вручную после их сборки.

Проблему из §1 нельзя решить «на месте» по двум причинам. Во-первых, билдеры независимо штампуют версию по времени запуска — собранные с интервалом флейворы получают разные версии и не складываются в один тег чисто. Во-вторых, публикатор жёстко знает только две сборки и один источник отпечатка, а сайт вообще не привязан к релизам — он ссылается на статический документ.

## 5. Предлагаемый подход

Доставка опирается на GitHub Releases как на публичный канал для APK: один релиз = один тег версии = полный набор ассетов спектра. Сборка спектра и публикация разделяются по ответственности: сборка готовит артефакты с согласованной версией, публикация — единственный «загрузчик» в релиз, повторно используя уже существующий механизм S0214 и расширяя его на весь набор. Сайт — пассивный потребитель: он читает последний релиз и отображает кнопки, не зная заранее ни версии, ни конкретных адресов файлов.

### 5.1 Основные столпы / модули

**Согласование версии спектра.** Чтобы все ассеты одного релиза несли одну версию, сборка спектра должна фиксировать версию один раз и применять её ко всем флейворам, а не давать каждому билдеру штамповать своё время. Роль «согласователь версии» отвечает за то, что итоговый набор артефактов однороден по версии и публикатор может собрать их под один тег.

**Расширенный публикатор релиза.** Существующий шаг публикации расширяется с двух сборок до полного спектра: обнаружение всех ожидаемых APK, проверка отпечатка подписи для каждого, единое создание релиза и заливка всех ассетов с детерминированными именами (с версией в имени). Wear OS добавляется как отдельный ожидаемый артефакт. noLegal входит в набор ассетов, но это не влияет на то, где он показывается на сайте.

**Витрина скачивания на сайте.** Блок «Download APK Builds» на главной превращается из ссылки-на-документ в набор кнопок публичных сборок, наполняемый из данных последнего релиза (адрес файла + актуальная версия). При недоступности данных — деградация до рабочей ссылки на страницу релизов. Отдельная витрина на `nolegal*.html` показывает кнопку noLegal.

**Документы Downloads.** Тексты EN/RU/UK переориентируются на GitHub Release как основной источник, Google Drive остаётся упомянут как зеркало.

### 5.2 Потоки данных и событий

- Сборка спектра → артефакты с единой версией в локальной области выгрузки (как сейчас) → публикатор обнаруживает их → проверка подписи → создание релиза с тегом версии → заливка ассетов.
- Существующие зеркала (Google Drive, tc-папка) наполняются параллельно, как и раньше.
- Пользователь открывает страницу сайта → страница запрашивает данные последнего релиза → отрисовывает кнопки публичных сборок с версией → клик ведёт на ассет релиза. При отказе запроса → видна запасная ссылка на страницу релизов.

### 5.3 Точки расширяемости

- Набор публикуемых сборок задаётся декларативно (список ожидаемых артефактов), чтобы добавление/удаление флейвора было точечным изменением, а не правкой логики.
- Разделение «публичный набор для главной» и «полный набор ассетов» оставляется явным, чтобы граница noLegal (и любые будущие приватные сборки) регулировалась списком, а не разбросанными условиями.
- Способ получения данных релиза сайтом инкапсулируется так, чтобы запасной вариант (статическая ссылка) был всегда доступен независимо от основного.
- Источник ожидаемого отпечатка подписи допускает разные значения на случай, если Wear OS подписывается отдельным ключом (см. §6).

## 6. Открытые вопросы / Research items

1. **Подпись Wear OS**
   - **Вопрос:** подписывается ли релизный Wear OS APK тем же release-ключом, что и сборки основного модуля, или отдельным?
   - **Варианты:** общий ключ → один отпечаток на весь спектр; отдельный ключ → публикатору нужен второй ожидаемый отпечаток.
   - **Нужно выяснить:** конфигурацию подписи модуля Wear относительно основного релизного ключа.
   - **Статус:** Resolved - у модуля Wear нет release-подписи (unsigned APK); решение — подписать тем же release-ключом, один отпечаток покрывает весь спектр.
   - **Артефакт:** `PLAN/S0394_github-release-assets-downloads/research/01__wear-release-signing.md`

2. **Согласование версии без двойной сборки**
   - **Вопрос:** как зафиксировать единую версию на весь спектр — передавать заранее вычисленную версию во все билдеры, либо принять версию последнего собранного флейвора и переименовать остальные ассеты под неё при публикации?
   - **Варианты:** «фиксированная версия на входе сборки» против «нормализация версии на этапе публикации».
   - **Нужно выяснить:** какой путь меньше ломает существующие билдеры и зеркала и совместим с тем, что версия зашита в собранный APK (versionCode/Name), а не только в имя файла.
   - **Статус:** Resolved - штамповать версию один раз (app_v2 + wear) перед прогоном спектра; «build all» собирает все флейворы из одного build.gradle.kts.
   - **Артефакт:** `PLAN/S0394_github-release-assets-downloads/research/02__spectrum-version-reconciliation.md`

3. **Способ отрисовки кнопок на сайте**
   - **Вопрос:** тянуть данные последнего релиза через публичный API GitHub (адрес ассета + версия) с запасной статической ссылкой, либо использовать стабильный redirect на «последний релиз» по фиксированному имени файла?
   - **Варианты:** API-витрина с живой версией против статических ссылок «latest»; последнее требует версионно-нейтральных имён, что конфликтует с маской стороннего индексатора.
   - **Нужно выяснить:** лимиты публичного API для страницы и поведение запасного варианта при недоступности данных; подтвердить, что выбранный путь не требует второго (версионно-нейтрального) комплекта ассетов.
   - **Статус:** Resolved - GitHub Releases API (60 req/час/IP достаточно) + статический fallback на страницу релизов; версионные имена ассетов сохраняются, второй комплект не нужен.
   - **Артефакт:** `PLAN/S0394_github-release-assets-downloads/research/03__website-release-rendering.md`

4. **Команда сборки всего спектра**
   - **Вопрос:** какой оркестратор собирает весь набор за один прогон и в каком порядке, чтобы публикатор получил полный комплект?
   - **Нужно выяснить:** покрывает ли существующий «build and push all» нужный набор флейворов и Wear OS, либо нужен отдельный релизный прогон спектра.
   - **Статус:** Resolved - `build-and-push-all.ps1` уже собирает весь спектр + Wear за один двухпроходный прогон; переиспользуем его release-часть.
   - **Артефакт:** `PLAN/S0394_github-release-assets-downloads/research/04__spectrum-build-orchestrator.md`

## 9. Архитектурные решения (ADR)

**ADR-1: Публикация единым шагом, а не из каждого билдера**

- **Решение:** заливку в GitHub Release выполняет один публикатор после сборки спектра, а не каждый билдер сам по себе.
- **Альтернативы:** каждый билдер сам заливает свой ассет сразу после сборки.
- **Почему:** релиз — это один тег версии; децентрализованная заливка из билдеров со своими временными версиями порождает разнобой версий и гонки за общий тег. Единый публикатор повторно использует проверенный механизм S0214.

**ADR-2: Сайт читает релиз динамически, имена ассетов остаются версионными**

- **Решение:** кнопки на сайте наполняются из данных последнего релиза; имена ассетов сохраняют версию.
- **Альтернативы:** статические ссылки «latest» с версионно-нейтральными именами.
- **Почему:** версионно-нейтральные имена сломали бы маску стороннего индексатора; динамическое чтение даёт живую версию и нулевую ручную правку сайта на каждый релиз, при наличии статического запасного варианта.
