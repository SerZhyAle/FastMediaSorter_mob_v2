## 1. Проблема

Доставленный (de-bundled) native-набор, чей payload повреждён на устройстве или пинован под другую версию сборки, попадает в вечный тупик: каталог payload существует, поэтому инфраструктура доставки считает набор «установленным», но проверка целостности при реальной загрузке падает. Пользователь получает общую ошибку (для OCR - Toast ocr_error) при каждой попытке, без подсказки и без пути восстановления. Маркер установки не сбрасывается, экран Extensions manager продолжает показывать набор как «Installed», а единственный выход - вручную сделать uninstall + download, что неочевидно. Область - инфраструктура доставки наборов (S0386): слой проверки присутствия, загрузчик native-библиотек, экран Extensions manager и точки-потребители (OCR и прочие).

---

## 2. Цели

1. Повреждённый/несовпадающий payload перестаёт быть вечным тупиком: при обнаружении несоответствия целостности набор автоматически перестаёт считаться установленным.
2. Экран Extensions manager отражает повреждённый набор как восстановимый (предлагает повторную загрузку), а не как «Installed».
3. Пользователь-потребитель (например, OCR) при сбое целостности получает понятное, локализованное сообщение, указывающее на переустановку в Extensions, вместо общей ошибки.
4. Восстановление достижимо в один шаг (переустановка из Extensions) без ручного uninstall.
5. Механизм единообразен для всех de-bundled native-наборов, а не точечный для OCR.

**Non-goals:**

- Автоматическая фоновая ре-загрузка без действия пользователя (уважение к metered-сетям и согласию пользователя).
- Эатратная пере-верификация SHA-256 всего payload на каждый вызов проверки присутствия / на каждую попытку использования.
- Изменение схемы пиннинга, формата дескрипторов или политики хранения payload.
- Покрытие bundled-наборов (например, TRANSLATION), для которых сценарий повреждения payload структурно невозможен.

## 4. Контекст текущей архитектуры

Инфраструктура доставки (S0386) разделяет «факт установки» и «целостность payload» на два невзаимодействующих слоя. Слой проверки присутствия отвечает на вопрос «установлен ли набор» только по факту существования каталога payload - без верификации содержимого. Целостность (SHA-256 и размер каждого файла) проверяется отдельно и только в момент реальной загрузки native-библиотек; при несоответствии загрузчик бросает исключение. Экран Extensions manager и точки-потребители читают статус из слоя присутствия, поэтому повреждённый набор одновременно «установлен» (для UI и гейта) и «нерабочий» (для загрузчика). Никакой сигнал не связывает сбой загрузки обратно с маркером установки или со статусом в UI, поэтому состояние расхождения самоподдерживается до ручного вмешательства. Сбросить тупик из §1 сейчас нельзя, потому что обнаружение сбоя (загрузчик) и владелец состояния установки (маркер) не соединены.

## 5. Предлагаемый подход

Соединить обнаружение сбоя целостности с владельцем состояния установки и со статусом в UI, оставив верификацию там, где она дешева - в точке использования.

### 5.1 Основные столпы / модули

1. **Авторитетная верификация в точке использования.** Целостность проверяется при загрузке набора (как сейчас), одна верификация на процесс. Eager-перепроверка в синхронном гейте присутствия не вводится.
2. **Само-инвалидация при сбое целостности.** Когда загрузка набора падает на проверке целостности, состояние установки этого набора инвалидируется: повреждённый payload удаляется, персистентный флаг установки сбрасывается. После этого набор перестаёт сообщать «установлен».
3. **Реактивное отражение деградации в Extensions.** Поскольку флаг установки персистентный и наблюдаемый, экран Extensions manager реактивно переводит набор из «Installed» в восстановимое состояние (предлагает повторную загрузку). Повторно используется существующая семантика «сбой/восстановимо» с отдельным сообщением о повреждении.
4. **Действенное сообщение у потребителя.** В точке сбоя у потребителя (OCR и прочие) общая ошибка заменяется локализованным сообщением, указывающим на переустановку в Extensions.
5. **Единообразие по наборам.** Механизм живёт в общем слое доставки и покрывает все de-bundled native-наборы; bundled-наборы структурно не затронуты.

### 5.2 Потоки данных и событий

- Потребитель запрашивает набор -> загрузка -> верификация целостности.
- Верификация провалена -> загрузчик инвалидирует состояние установки набора (удаление payload + сброс флага) -> потребителю возвращается действенное сообщение.
- Сброс флага -> наблюдаемое состояние установки эмитит «не установлен/восстановимо» -> экран Extensions manager реактивно показывает повреждённый набор с кнопкой повторной загрузки.
- Пользователь инициирует повторную загрузку -> штатный путь скачивания + верификация -> рабочий набор восстановлен.

### 5.3 Точки расширяемости

- Инвалидация при сбое целостности - набор-агностична: новые de-bundled-наборы получают самовосстановление без точечного кода.
- Модель статуса оставляет место для выделенного состояния «повреждено», если позже потребуется отдельная UX-копия/телеметрия.

## 9. Архитектурные решения (ADR)

1. **Верификация в точке использования остаётся авторитетной.** Eager-пере-верификация всего payload в синхронном гейте присутствия отклонена: полный SHA-256 native-набора на главном потоке (порядок десятков мс) угрожает jank/ANR. Целостность проверяется при загрузке, одна верификация на процесс.
2. **Само-инвалидация при сбое целостности.** При провале целостности загрузчик удаляет повреждённый payload и сбрасывает флаг установки, чтобы набор перестал ложно сообщать «установлен» и стал восстановимым.
3. **Повторное использование существующей семантики «сбой/восстановимо».** Деградация выражается через имеющийся восстановимый статус (показывает кнопку загрузки, входит в массовую установку) с отдельным сообщением о повреждении - минимальная зона изменений. Выделенное состояние «повреждено» допускается тактикой, если окажется чище.
4. **Восстановление инициируется пользователем.** Никакого автоматического фонового скачивания при обнаружении повреждения - уважение к metered-сетям и согласию пользователя; восстановление - переустановка в один шаг.
5. **Набор-агностичный механизм в общем слое доставки.** Покрывает все de-bundled native-наборы единообразно; bundled-наборы структурно вне охвата.

## 11. Критерии готовности (strategic-level)

1. Повреждённый/несовпадающий native-payload не вызывает вечный цикл общей ошибки: первое использование после повреждения даёт действенное сообщение.
2. После обнаружения повреждения экран Extensions manager показывает набор как восстановимый (предложена повторная загрузка), а не «Installed».
3. Переустановка из Extensions в один шаг восстанавливает рабочий набор.
4. Автоматического скачивания без действия пользователя не происходит.
5. Не добавлен главнопоточный jank: целостность не пере-хешируется на каждом вызове гейта присутствия.
6. Механизм единообразно покрывает OCR_ENGINES, FFMPEG_DTS, AUDIO_VISUALIZATIONS; TRANSLATION не затронут.
7. Новые строки восстановления присутствуют в EN/RU/UK.
