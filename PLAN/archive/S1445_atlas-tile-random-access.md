## 1. Проблема

Плитка превью берётся из спрайт-листа по одной операции `BitmapRegionDecoder.decodeRegion` на плитку. У WebP нет произвольного доступа: чтобы отдать строку `Y`, декодер энтропийно разбирает весь поток сверху до этой строки, поэтому стоимость одной плитки пропорциональна её смещению по вертикали, а не её размеру (240x135).

Измерено 2026-08-06 на опубликованном ресурсе `channel-preview-atlas-v1.webp`:

- Лист - 8160x7560 (61,7 Mpx), lossy WebP, 11 358 632 байта.
- Полная декодировка листа на dev-ПК (libwebp через ffmpeg): 1,48 с и 1,49 с в двух прогонах.
- Плитка из середины листа стоит примерно половину этого на ПК; телефон в несколько раз медленнее.

Кеша плиток нет ни на одном уровне: каждый повторный `onBindViewHolder` декодирует заново. Пока плитка декодируется, ячейка успевает переиспользоваться, и охранник `boundUrl != url` выбрасывает готовый результат. Это объясняет запись в логах устройства владельца за 2026-08-01/02: проба `grid atlas-preview tile applied` сработала за четверо суток всего 9 раз при ~2000 видеоканалов в каталоге. Пользователь видит ровно то, что описал: картинки появляются по одной.

Тот же дефект - в логотипном листе (`stream-logo-atlas-v1.webp`, 8024x4352, 34,9 Mpx): архитектура слайсера скопирована один в один.

Устаревший sidecar как причина исключён измерением: опубликованная карта слотов покрывает 1881 из 2077 VIDEO-строк текущего каталога (90,6%), то есть у подавляющего большинства каналов плитка есть.

## 2. Цели

1. Стоимость получения одной плитки перестаёт зависеть от размера листа - она равна декодировке изображения 240x135.
2. Экран сетки заполняется картинками разом, а не по одной; повторный проход по уже показанному участку не декодирует ничего заново.
3. То же лечение получает логотипный лист - он ломается по той же причине.
4. Уже установленный старый payload не превращается в пустой экран: пока пользователь не обновил его, работает прежний путь чтения.
5. Спрайт-лист остаётся опубликованным как есть - контракт для сторонних потребителей каталога (S1154 Q-B) не ломается.

**Non-goals:**

- Пересъёмка кадров каналов (переупаковка идёт из уже снятых кадров/готового листа).
- Изменение геометрии плитки, порядка индексов и ключа слота (`url`).
- Онлайновое дособирание атласа на устройстве.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Обложки должны появляться сразу при вводе сетки, а не по одной.

### 3.2 Жёсткие ограничения

- **Flavor:** standard, noLegal, legacy, vr (`SUPPORT_STREAMS = true`); lite/photos - вне объёма.
- **API level:** `java.util.zip.ZipFile` и `BitmapFactory` доступны с API 23 (пол legacy).
- **Память:** запрещено декодировать лист целиком (ADR-2 из S1154 остаётся в силе); кеш плиток - ограниченный по байтам LRU.
- **Размер payload:** переупакованный ресурс не должен заметно превышать нынешние 11,4 МБ (превью) и 6,6 МБ (логотипы).
- **Целостность:** новый ресурс публикуется под новой ревизией имени (`-v2`) с новыми пинами SHA-256/размера - никогда не перезалив под тем же именем (дисциплина S0925).
- **Локализация:** новых строк не предполагается; если появятся - EN/RU/UK.

### 3.3 Owner inputs (Approval gate)

- **Related tickets:** S1154 (атлас превью, приёмка провалена этим отчётом), S1201 (логотипный атлас, Archived - тот же дефект), S0925 (дисциплина публикации).
- **UI scope:** видимых изменений интерфейса нет - меняется только скорость появления уже существующих картинок. Rule 10 не задействован.
- **Data scope:** формат скачиваемого payload меняется (лист -> контейнер плиток); схема Room не затрагивается, карта слотов `url -> index` остаётся прежней.
- **Scope decision:** спрайт-лист продолжает публиковаться для сторонних потребителей; контейнер плиток - дополнительный ресурс, а не замена.

## 4. Контекст текущей архитектуры

`ChannelPreviewAtlasStore` / `StreamLogoAtlasStore` резолвят скачанный payload в `filesDir/delivery/<SET>/`, `ChannelPreviewAtlasSlicer` / `StreamLogoAtlasSlicer` держат один открытый `BitmapRegionDecoder` и на каждый запрос вызывают `decodeRegion`. `StreamsActivity` кеширует карту `url -> index` при открытии экрана и передаёт в оба `StreamGridAdapter` лямбды `atlasPreviewLoader` / `logoTileLoader`; адаптер вызывает их в корутине привязки и отбрасывает результат, если ячейка уже переиспользована. Скачивание идёт через `DeliverableSet` + `DeliverableDescriptorCatalog` (пины SHA-256 и минимальный размер на каждый файл ресурса) + `DeliverableDownloadWorker`. Офлайн-сборка и публикация - `scripts/streams/collect-stream-candidates.ps1` (`Build-ChannelPreviewAtlas`, `Build-StreamLogoAtlas` и их функции публикации).

## 5. Предлагаемый подход

### 5.1 Основные столпы / модули

1. **Контейнер плиток вместо листа для приложения.** Офлайн-упаковщик режет уже собранный лист на отдельные изображения плиток и складывает их в ZIP без сжатия; имя записи - индекс слота. Карта `url -> index` не меняется.
2. **Чтение с произвольным доступом.** Слайсер открывает контейнер один раз (`ZipFile`) и на запрос декодирует одну маленькую запись через `BitmapFactory` - стоимость больше не зависит от размера набора.
3. **LRU-кеш плиток в памяти**, общий на payload, ограниченный по байтам - повторный показ уже виденной плитки не декодирует ничего.
4. **Совместимость назад.** При отсутствии контейнера слайсер читает старый лист прежним путём, поэтому пользователь со старым установленным payload не теряет картинки до обновления.
5. **Публикация.** Контейнер публикуется рядом с листом как новая ревизия ресурса; пины в `DeliverableDescriptorCatalog` обновляются; пользователи со старым payload получают существующее предложение обновления (`UpdateAvailable`, S1200).

### 5.2 Потоки данных и событий

- Скачивание payload -> контейнер + sidecar лежат в `filesDir/delivery/<SET>/` -> слайсер открывает контейнер.
- Рендер плитки: кеш плиток? да -> отдать; нет -> запись контейнера -> декодировать -> положить в кеш -> отдать.
- Контейнера нет (старая установка) -> прежний путь `BitmapRegionDecoder` по листу.

### 5.3 Точки расширяемости

- Один механизм чтения обслуживает оба payload (превью и логотипы) и любой будущий набор плиток.
- Геометрия плитки перестаёт быть частью контракта чтения приложения - она остаётся только в упаковщике и в документации для сторонних потребителей.

## 6. Открытые вопросы / Research items

Исследование выполнено измерением (§1), владельческих решений не требуется: изменений интерфейса нет, геометрия и ключ слота сохранены, сторонний контракт не ломается.

- **Проверить на устройстве при реализации:** сериализует ли `BitmapRegionDecoder` вызовы `decodeRegion` на одном экземпляре. Это гипотеза, усиливающая симптом, но не необходимая для диагноза - стоимость одной плитки измерена и сама по себе объясняет провал. Новый путь чтения снимает вопрос независимо от ответа.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Отдельные плитки в сумме весят заметно больше листа | Средняя | Рост скачивания | Измерить на переупаковке; при перерасходе поднять сжатие плитки |
| Пользователь не примет обновление payload | Высокая | Остаётся на медленном пути | Прежний путь чтения сохранён; предложение обновления уже существует |
| Старый лист остаётся мусором в `filesDir` после обновления | Средняя | Занятое место | Удалять неизвестные файлы набора при установке нового payload |
| Кеш плиток раздувает память | Низкая | Давление на GC | LRU с бюджетом от `memoryClass`, а не по числу элементов |
| Расхождение упаковщика и приложения по имени записи | Низкая | Пустые плитки | Один тест на круг «упаковал - прочитал» по имени записи |

## 9. Архитектурные решения (ADR)

- **ADR-1:** payload приложения - контейнер отдельных плиток с произвольным доступом (ZIP без сжатия, имя записи = индекс слота), а не спрайт-лист. Причина: измеренная стоимость `decodeRegion` по WebP пропорциональна вертикальному смещению плитки (полная декодировка листа - 1,48 с на dev-ПК), поэтому спрайт-лист непригоден для случайного доступа во время прокрутки.
- **ADR-2:** спрайт-лист продолжает публиковаться без изменений - контракт для сторонних потребителей каталога (S1154 Q-B) не ломается; оба ресурса собираются из одних и тех же кадров.
- **ADR-3:** LRU-кеш декодированных плиток с бюджетом в байтах, общий на payload. Причина: сетка переспрашивает одни и те же плитки при каждой прокрутке.
- **ADR-4:** старый путь чтения листа сохраняется как запасной, пока payload не обновлён. Причина: обновление payload - действие пользователя, а не приложения; без запасного пути неподтверждённое обновление означало бы пустые ячейки.
- **ADR-5:** нового `DeliverableSet` не заводится - меняется список файлов существующего набора и его пины (ревизия `-v2`). Причина: это тот же payload, а не второй.

## 11. Критерии готовности (strategic-level)

1. Плитка превью и плитка логотипа читаются из контейнера за время, не зависящее от числа плиток в наборе.
2. Повторный показ уже показанной плитки не выполняет декодирование.
3. Полный лист никогда не декодируется целиком в память.
4. При отсутствии контейнера приложение показывает картинки прежним путём.
5. Упаковщик собирает контейнер из тех же кадров, что и лист, и публикует его новой ревизией имени с новыми пинами.
6. Круг «упаковал - прочитал» покрыт тестом на чистых частях.
7. На устройстве: вход в сетку видеофильтра заполняет видимый экран картинками разом, без появления по одной.
