# Стратегическая спецификация: S0077 — BDMV/DVD-сетевые миниатюры не должны падать через Glide

**Ticket:** S0077
**Status:** Verified
**Priority:** 75
**Date:** 2026-05-04
**Tier:** 2 - Easy
**Roadmap entry:** Ad-hoc - полевой лог 2026-05-04 по browse списка сетевых BDMV/DVD-структур
**Tactical spec:** `PLAN/S0077_bugfix-network-video-thumbnail-routing-bdmv-dvd/` (будет создан через `/spec-tech`)

> **Scope:** STRATEGIC. Цели, ограничения, открытые вопросы. Без имён классов, путей, лимитов строк, миграций Room, модулей Hilt.

---

## 1. Проблема

При прокрутке сетевых BDMV/DVD-структур список пытается загрузить миниатюры для `.m2ts` и `.vob`, но текущая маршрутизация превью расходится сама с собой: на одном шаге файл ещё считается кандидатом на thumbnail-request, а на следующем соответствующий network video-loader отказывается его обслуживать. В результате Glide пишет `NoModelLoaderAvailableException`, адаптер получает `Thumbnail load failed`, а один и тот же файл при повторных bind/rebind снова провоцирует ошибку.

Полевой лог 2026-05-04 показал это на множестве элементов подряд: `00004.m2ts`, `00006.m2ts`, `VIDEO_TS.VOB`, `VTS_01_0.VOB` и соседних DVD/BDMV-сегментах. Пользователь видит нестабильные плейсхолдеры и более медленную стабилизацию списка, а logcat засоряется ожидаемыми, но оформленными как ошибки, сбоями превью.

---

## 2. Цели

1. Для сетевых `.m2ts` / `.vob` и смежных optical-disc контейнеров browse-пайплайн больше не доходит до `NoModelLoaderAvailableException` как штатного сценария.
2. Неподдерживаемые превью получают детерминированный placeholder или иную лёгкую fallback-стратегию сразу, без exception storm и без многократных повторов на каждом rebind.
3. Уже работающие сетевые форматы превью (например, обычные видео и изображения) не регрессируют.
4. Диагностика неподдерживаемого контейнера остаётся доступной, но уходит на корректный уровень логирования и не маскирует реальные ошибки.
5. Политика применимости сетевого видео-thumbnail остаётся централизованной и расширяемой для будущих контейнеров.

**Non-goals:**

- Реализовать полноценную генерацию кадров для всех BDMV/DVD-контейнеров в первой итерации.
- Менять playback-маршрут `.vob` / `.m2ts` — это отдельные области S0076 и S0054.
- Перегруппировывать BDMV/DVD-структуры в «один фильм» на уровне файлового браузера.
- Добавлять тяжёлый background IO, временные локальные копии или кэш-файлы только ради превью в рамках первой итерации.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Желательно показывать осмысленный placeholder, чтобы пользователь отличал «сетевое видео без превью» от «что-то реально сломалось».
2. Желательно один раз распознавать неподдерживаемый контейнер на сессию и не повторять тот же провальный маршрут на каждом bind.
3. Желательно, чтобы future-proof политика могла расширяться так же просто, как это уже сделано для AVI-подобных кейсов.

### 3.2 Жёсткие ограничения

- **Flavor:** все флейворы, где есть browse сетевых ресурсов; Wear OS не затрагивается.
- **API level:** без новых API-зависимостей.
- **Производительность:** fallback должен быть лёгким; никаких тяжёлых пробных декодирований в main thread.
- **Совместимость данных:** без миграций и без новых пользовательских настроек.
- **Локализация:** если добавляется новый текстовый placeholder-state, он обязан быть в EN/RU/UK; графический placeholder без текста допустим.
- **Доступность:** placeholder должен оставаться различимым для TalkBack через корректный content description, если соответствующий элемент озвучивается.

---

## 4. Контекст текущей архитектуры

В проекте уже есть прецедент явной политики применимости сетевых видео-превью: заведомо проблемные контейнеры можно отсеивать заранее и сразу отдавать placeholder. Однако полевая сессия 2026-05-04 показала, что BDMV/DVD-контейнеры пока остаются в промежуточной зоне: общий browse-path всё ещё инициирует thumbnail-request, но нижележащий loader уже не готов брать этот файл в работу.

Это не «реальный крэш декодера» и не нестабильная сеть. Это чистый routing mismatch между верхним уровнем выбора thumbnail-path и нижним уровнем `handles/can-process`, из-за которого ожидаемое «не умеем — покажем значок» превращается в поток исключений.

---

## 5. Предлагаемый подход

Для BDMV/DVD-контейнеров нужен такой же явный applicability-gate, как и для уже известных неподдерживаемых сетевых форматов. Решение должно приниматься до старта Glide-request, а fallback должен быть детерминированным и дешёвым.

### 5.1 Основные столпы / модули

**A. Единая applicability-policy для optical-disc контейнеров**

Сетевые `.m2ts`, `.vob` и смежные optical-disc кейсы должны либо явно помечаться как «preview not supported in this path», либо направляться в выделенный поддерживаемый path. Состояние «верхний слой запросил превью, нижний слой ответил `не умею`» должно исчезнуть.

**Б. Deterministic fallback UI**

Если контейнер для сетевого preview не поддерживается, браузер должен сразу показывать placeholder или container-aware icon. Пользователь получает устойчивый визуальный результат без 10-секундного ожидания и без exception storm.

**В. Anti-repeat поведение**

Один и тот же неподдерживаемый файл не должен заново проходить по провальному маршруту на каждом повторном bind. Нужна минимум сессионная дедупликация отрицательного результата или эквивалентная защита от бессмысленных повторов.

**Г. Корректная диагностика**

Неподдерживаемый preview-route должен логироваться как ожидаемое решение маршрутизации, а не как E/W-level ошибка. Реальные баги декодирования и реальные network failures должны оставаться видимыми отдельно.

### 5.2 Потоки данных и событий

```text
Bind item in network browse
  → classify media/container for preview
      → supported preview path → request real thumbnail
      → unsupported optical-disc container → return deterministic placeholder immediately
  → cache / dedupe negative decision for the session
  → rebind same item
      → reuse prior decision, no repeated exception path
```

### 5.3 Точки расширяемости

- Список неподдерживаемых или специально обрабатываемых контейнеров должен оставаться в одной точке истины.
- Детерминированный fallback должен допускать будущую замену placeholder на лёгкое превью, если позже появится безопасный decoder-path для optical-disc контейнеров.

## 6. Открытые вопросы / Research items

1. **Нужен ли реальный thumbnail для `.m2ts` в будущем?**
   - **Вопрос:** достаточно ли placeholder-first стратегии для первой итерации, или `.m2ts` требует отдельного lightweight-preview path?
   - **Варианты:** placeholder-only; отдельный preview path только для `.m2ts`; разная политика для `.m2ts` и `.vob`.
   - **Нужно выяснить:** насколько критичны реальные миниатюры для BDMV-рипа в типичных папках пользователя.
   - **Статус:** Verified

2. **Какой уровень дедупликации нужен?**
   - **Вопрос:** достаточно ли сессионного negative-cache, или нужен более долгий cache по URI/path?
   - **Варианты:** per-bind suppression; session cache; TTL-cache.
   - **Нужно выяснить:** как часто список повторно пересобирается и насколько заметны повторные попытки в реальном UX.
   - **Статус:** Verified

3. **Насколько детализированным должен быть placeholder?**
   - **Вопрос:** нужен ли отдельный визуальный режим для BDMV/DVD, либо достаточно общего video placeholder?
   - **Варианты:** общий video icon; отдельный disc-like icon; placeholder по container family.
   - **Нужно выяснить:** насколько это помогает пользователю различать «нет превью» и «ошибка» без лишнего визуального шума.
   - **Статус:** Verified

## 9. Архитектурные решения (ADR)

**ADR-1: Unsupported preview-route — это routing decision, а не ошибка декодера**

- **Решение:** для неподдерживаемых optical-disc контейнеров принимается явное решение «сразу placeholder».
- **Альтернативы:** продолжать запускать Glide-request и полагаться на нижний слой `handles()` или на timeout.
- **Почему:** это дешевле, чище по логам и предсказуемее по UX.

**ADR-2: Negative result должен переиспользоваться в рамках сессии**

- **Решение:** повторный bind не должен заново проходить по уже известному неподдерживаемому preview-route.
- **Альтернативы:** каждый rebind стартует заново, надеясь на «вдруг сейчас получится».
- **Почему:** контейнер не меняется между bind'ами; повторный провал не даёт новой информации и только засоряет лог/очередь.

## 11. Критерии готовности (strategic-level)

1. При прокрутке сетевой BDMV/DVD-папки пользователь видит стабильные placeholder-state для неподдерживаемых превью вместо потока срывов загрузки.
2. В логах больше нет штатных `NoModelLoaderAvailableException` для `.m2ts` / `.vob` thumbnail-path как повторяющегося нормального сценария.
3. Повторный bind того же элемента не запускает тот же провальный preview-route снова и снова.
4. Обычные работающие сетевые форматы превью не теряют реальные миниатюры.
5. Если появляется новый user-facing текст placeholder-state, он присутствует в EN/RU/UK.
