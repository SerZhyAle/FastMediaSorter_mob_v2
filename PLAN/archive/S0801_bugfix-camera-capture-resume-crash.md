## 1. Проблема

При открытии встроенной камеры из OCR-сценария экран успевает получить `resume` раньше, чем заканчивается отложенная инициализация после первого кадра. В результате пользовательский путь "запустить OCR-камеру -> открыть захват" падает сразу после создания экрана и вынуждает перезапускать приложение. Ошибка уже подтверждена отдельным crash-report и повторным предупреждением о предыдущем падении на следующем старте.

---

## 2. Цели

1. Исключить падение при первом входе во встроенную камеру из OCR- и смежных capture-сценариев.
2. Выровнять lifecycle-контракт для экранов, у которых тяжёлая инициализация откладывается до первого кадра.
3. Сохранить текущий UX камеры, но убрать окно, в котором resume-логика может обратиться к ещё не созданным помощникам.

**Non-goals:**

- Не менять визуальный дизайн камеры, OCR-экрана и связанных меню.
- Не добавлять новые возможности фото- или видеозахвата.
- Не пересматривать общую архитектуру всех Activity вне подтверждённого дефекта.

---

## 3. Пожелания и ограничения

1. Исправление должно опираться на уже собранные логи и не требовать отдельного функционального расширения для воспроизведения.
2. Решение желательно сделать так, чтобы аналогичный lifecycle-разрыв не повторялся на соседних capture-entry points.

### 3.2 Жёсткие ограничения

- **Flavor:** camera-capable `app_v2` flavors; подтверждённое воспроизведение есть в `noLegal` debug, исправление не должно расходиться по flavor-поведению

- **Wear OS:** не затрагивается
- **Производительность:** нельзя ухудшить время первого кадра ради исправления lifecycle-гонки
- **Совместимость данных:** миграций данных нет
- **Локализация:** новых пользовательских строк лучше не добавлять; если добавятся диагностические сообщения, они проходят обычный EN/RU/UK поток
- **Доступность:** фокус, touch targets и текущие клавиши камеры должны сохраниться без изменений

## 4. Контекст текущей архитектуры

Экран встроенной камеры живёт внутри общего Activity-контракта, где тяжёлая подготовка UI и помощников переносится на пост-этап после первого кадра. Это ускоряет старт, но создаёт узкий промежуток, в котором системный `resume` уже приходит, а capture-зависимости экрана ещё не созданы.

Сценарий OCR открывает соседний экран быстро и последовательно, поэтому этот промежуток становится реальным, а не теоретическим. Пока resume-ветка камеры предполагает готовность всех помощников без дополнительных гарантий, приложение остаётся уязвимым к немедленному падению при раннем lifecycle edge.

---

## 5. Предлагаемый подход

Нужно перевести resume-зависимую работу камеры в lifecycle-точку, которая гарантированно выполняется только после завершения отложенной инициализации экрана. Параллельно экран захвата должен безопасно переживать ранние `pause`/`destroy`/повторный `resume`, если часть его помощников ещё не была создана.

### 5.1 Основные столпы / модули

1. **Безопасный post-setup lifecycle-контракт**
   - Resume-зависимые обязанности экрана выполняются только после готовности view- и manager-слоя.
2. **Локальная защита capture-host**
   - Экран камеры не обращается к ещё не созданным помощникам ориентации, таймеров и вспомогательных контроллеров.
3. **Симметрия освобождения ресурсов**
   - Все помощники камеры корректно переживают ранний выход из экрана и не требуют "обязательного" полного старта перед shutdown-путём.

### 5.2 Потоки данных и событий

`Capture entry point` -> `camera host create` -> `deferred first-frame setup` -> `resume-safe activation of capture helpers` -> `normal capture session`

При раннем lifecycle edge:

`Capture entry point` -> `camera host create` -> `system resume/pause/destroy before deferred setup` -> `no-op or deferred helper activation` -> `graceful continue or finish without crash`

### 5.3 Точки расширяемости

- Общий lifecycle-паттерн для экранов с отложенной инициализацией должен остаться пригодным для других capture- и media-host сценариев.
- Диагностика должна явно различать "ранний lifecycle edge" и настоящую ошибку инициализации, чтобы следующие расследования не теряли сигнал.

   - **Нужно выяснить:** какой вариант даёт защиту без риска регрессий на соседних Activity

   - **Вопрос:** кроме OCR-потока, есть ли ещё capture-entry paths, которые могут открыть тот же host с тем же lifecycle-окном
   - **Варианты:** только OCR; OCR + прямой запуск камеры; OCR + виджет/launcher shortcuts

## 9. Архитектурные решения (ADR)

**ADR-1: Resume-зависимая логика для экранов с deferred setup живёт только после завершения post-setup этапа**

- **Решение:** работа, завязанная на manager/view helper состояние, не запускается из сырого `resume`, пока экран не прошёл отложенную инициализацию
- **Альтернативы:** расставить точечные `lateinit`-guards без изменения lifecycle-контракта; отключить deferred setup для камеры
- **Почему:** точечные guards лечат симптом, но не контракт; полный отказ от deferred setup рискует ухудшить старт экрана без необходимости

## 11. Критерии готовности (strategic-level)

1. Вход во встроенную камеру из OCR-сценария больше не приводит к закрытию приложения.
2. Повторный foreground/background цикл камеры не создаёт нового падения в той же области lifecycle.
3. После исправления в экспортированном логе отсутствует прежний crash-signature с ранним доступом к неинициализированному помощнику камеры.
4. Пользователь после падения больше не видит предупреждение о предыдущем аварийном завершении именно для этого сценария.
