# Стратегическая спецификация: S0154 — Очередь файловых операций (move / delete / rename) в плеере и сортировке

**Ticket:** S0154
**Status:** Tactical
**Priority:** 70
**Date:** 2026-05-11
**Tier:** 3 — Moderate (ad-hoc)
**Roadmap entry:** Ad-hoc — полевой инцидент 2026-05-11, лог `logs/fastmediasorter_20260511_032209.log`
**Tactical plan:** `PLAN/S0154_player-file-operation-queue/INDEX.md`

> **Scope:** STRATEGIC. Цели, ограничения, открытые вопросы. Без имён классов, путей, лимитов строк, миграций Room, модулей Hilt.

---

## 1. Проблема

При сортировке папки со смесью изображений и видео пользователь перемещает видео (фоновый перенос по сети на SMB/FTP/SFTP/облако занимает несколько секунд). Плеер по S0094 оптимистично сразу переходит к следующему файлу — изображению, — но кнопка «переместить» (или «удалить») на нём не срабатывает: операция молча отбрасывается, потому что слой файловых операций сериализует действия одним флагом «операция в процессе» и пока предыдущий перенос не завершён, новое действие игнорируется. С точки зрения пользователя кнопка «не работает» без какого-либо объяснения, и темп сортировки рушится — приходится ждать каждое сетевое перемещение. S0152 чинит только утечку этого флага в ошибочных ветках, но не сам случай «предыдущая операция легитимно ещё идёт».

---

## 2. Цели

1. Действие move / delete / rename над текущим файлом плеера принимается всегда — даже если предыдущая такая операция ещё выполняется в фоне; кнопки move / delete / rename никогда не «залипают».
2. После инициирования действия плеер немедленно переходит к следующему файлу (для move / delete) или остаётся на текущем (для rename) — пользователь не ждёт завершения фоновой операции, как и в S0094, но теперь это работает и для второго, третьего, N-го действия подряд.
3. Поставленные действия выполняются последовательно в фоне в порядке их инициирования; одновременно физически выполняется не более одной операции (чтобы не перегружать одно сетевое соединение и не плодить гонки на одном ресурсе).
4. Ошибка одной операции из очереди не блокирует и не отменяет остальные; пользователь получает понятное сообщение по конкретному не выполнившемуся файлу, очередь продолжает работу.
5. Когда очередь опустела и список файлов плеера стал пустым в результате выполненных операций — плеер закрывается и управление возвращается в Browse (как сейчас, но с учётом отложенных операций).
6. Файл, по которому действие поставлено в очередь, исключается из списка плеера сразу (оптимистично, по пути файла), а не после завершения фоновой операции — повторное действие по тому же файлу невозможно.
7. Поведение одинаково для всех типов ресурсов (локальные файлы, SMB, FTP, SFTP, облачные хранилища) и всех flavor'ов.

**Non-goals:**

- Параллельное выполнение нескольких файловых операций одновременно — очередь строго последовательная.
- Отмена (undo) уже начатой или уже завершённой операции из очереди — отдельный тикет.
- Изменение поведения фоновых операций, инициируемых из Browse (не из плеера) — затрагивается только поток «операция над текущим файлом плеера».
- Переупорядочивание / редактирование самой очереди пользователем (drag-to-reorder, удаление пункта из очереди) — не в объёме первой итерации.
- Сохранение очереди между сессиями (переживание убийства процесса) — не в объёме; незавершённые при выходе операции теряются, как и сейчас.
- Изменение UX диалогов выбора папки назначения и переименования.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Желательно показывать ненавязчивый индикатор того, что в фоне есть незавершённые операции (например, счётчик «N в очереди»), но это не блокер первой итерации.
2. Желательно при ошибке отдельной операции дать в сообщении возможность повторить её, не прерывая остальные.
3. Желательно, чтобы при rename, поставленном в очередь, последующий полный перезапрос списка (если он нужен) не нарушал текущую позицию в плейлисте — переиспользовать точечное обновление пути из S0094.
4. Желательно переиспользовать существующий механизм прогресса операций (S0074) для отображения статуса текущей выполняемой операции из очереди.

### 3.2 Жёсткие ограничения

- **Flavor:** все варианты сборки (standard, lite, photos, legacy) — фича плеера, не гейтится признаками медиа-типов.
- **API level:** без API-специфики (minSdk 23/26 в зависимости от флейвора). Если операция требует системного разрешения (batch-delete), очередь корректно ставится на паузу до ответа пользователя и продолжается после.
- **Wear OS:** не затрагивается.
- **Производительность:** постановка в очередь и оптимистичный переход к следующему файлу — мгновенные (синхронно на главном потоке, < 50 мс); фоновое выполнение операций не должно блокировать UI и воспроизведение следующего файла.
- **Совместимость данных:** без изменений схемы хранилища; очередь — runtime-структура в памяти, не персистентна.
- **Локализация:** EN/RU/UK — обязательно для всех новых/изменённых пользовательских строк (сообщение об ошибке отдельной операции, опциональный индикатор «N в очереди»).
- **Доступность:** опциональный индикатор очереди читается TalkBack; сообщения об ошибках — стандартные каналы обратной связи.
- **Тон сообщений:** новые строки проходят чек-лист тона из `docs/COMMUNICATION_POLICY.md` (§6) перед интеграцией — спокойное «файл X не удалось переместить», без алармовых формулировок.

## 4. Контекст текущей архитектуры

Файловые операции над текущим воспроизводимым файлом инициируются из UI плеера и делегируются вспомогательному обработчику файловых операций, который через use-case'ы и репозитории выполняет move / delete / rename для всех типов ресурсов. S0094 ввёл оптимистичную навигацию: плеер сразу переходит к следующему файлу, а физический перенос идёт в фоне. Однако обработчик защищён единственным флагом «операция в процессе» на уровне Activity: пока флаг взведён, любая новая операция отбрасывается guard'ом. То есть текущая архитектура допускает максимум одну незавершённую операцию на весь экран плеера, и при медленном сетевом переносе следующее действие пользователя теряется без обратной связи. S0152 устраняет случаи, когда флаг ошибочно остаётся взведённым навсегда, но не меняет саму модель «одна операция за раз без очереди».

---

## 5. Предлагаемый подход

Заменить модель «один флаг — одна операция» на модель «очередь отложенных файловых операций»: UI плеера при действии формирует описание операции (тип, файл-источник, параметры — папка назначения для move, новое имя для rename) и кладёт его в очередь; оптимистичная навигация и исключение файла из списка происходят немедленно; отдельный потребитель очереди последовательно забирает по одному описанию и выполняет фоновую операцию через существующие use-case'ы; результат каждой операции (успех / ошибка / требуется разрешение) проецируется обратно в UI без блокировки последующих.

### 5.1 Основные столпы / модули

#### A. Описание отложенной файловой операции

- Самодостаточное значение: тип операции (move / move-to-path / delete / rename), путь файла-источника, тип/идентификатор ресурса, параметры (целевая папка либо новое имя), и достаточно контекста, чтобы выполнить операцию без обращения к «текущему» состоянию плеера (которое к моменту выполнения уже изменилось).
- Снимок берётся в момент инициирования действия, пока файл ещё «текущий».

#### B. Очередь и её потребитель

- Очередь — FIFO, на уровне сессии плеера; одновременно выполняется не более одной операции.
- Потребитель: пока очередь не пуста — берёт головной элемент, выполняет фоновую операцию, по завершении (успех или ошибка) переходит к следующему.
- Если операция требует системного разрешения (batch-delete) — потребитель приостанавливается, UI запрашивает разрешение; после ответа пользователя выполнение возобновляется (грант → операция доводится, отказ → операция помечается не выполненной, очередь идёт дальше).
- Поведение «список опустел» проверяется после фактического завершения операций очереди, а не в момент оптимистичной навигации.

#### C. Оптимистичная реакция UI (расширение S0094)

- При действии: снять снимок операции → положить в очередь → исключить файл-источник из списка плеера по пути → выполнить навигацию (следующий файл для move / delete; остаться на месте для rename) → показать прогресс/индикатор по необходимости.
- Кнопки move / delete / rename больше не блокируются «операцией в процессе» — они всегда принимают действие (с разумной защитой от дабл-тапа по одному и тому же файлу: после исключения файла из списка повторное действие по нему невозможно).

#### D. Проекция результата операции

- Успех: при необходимости — точечное обновление (rename) или подтверждение исключения (move / delete); ничего не блокируется.
- Ошибка по конкретному файлу: понятное сообщение с указанием файла и (желательно) предложением повторить; очередь продолжает работу.
- Намеренные «прерванные поток» ошибки (как в S0094) по-прежнему не превращаются в тосты.

#### E. Совместимость с существующим прогрессом операций (S0074)

- Индикатор прогресса текущей выполняемой операции из очереди использует существующий механизм; добавление в очередь не открывает модальный блокирующий диалог.

### 5.2 Потоки данных и событий

- UI плеера (действие move/delete/rename над текущим файлом) → снимок операции → очередь; параллельно → исключение файла из списка по пути → навигация → опциональный индикатор «N в очереди».
- Потребитель очереди → берёт головной элемент → use-case файловой операции (для нужного типа ресурса) → результат → проекция в UI (успех / ошибка-по-файлу / запрос разрешения → пауза → возобновление) → следующий элемент.
- Очередь опустела → проверка «список плеера пуст?» → да: закрыть плеер, вернуться в Browse; нет: остаться.

### 5.3 Точки расширяемости

- Описание операции — расширяемый набор типов (на случай добавления новых файловых действий над текущим файлом).
- Потребитель очереди не зависит от типа ресурса — новые протоколы подключаются через те же use-case'ы.
- Структура очереди оставлена открытой к будущему персисту между сессиями и к пользовательскому редактированию очереди — но это явные не-цели текущей итерации.
- Если потребуется отдельная инфраструктура для фонового исполнителя очереди — её роль фиксируется на архитектурном уровне здесь, конкретные модули внедрения зависимостей — в `/spec-tech`.

## 6. Открытые вопросы / Research items

1. **Где живёт очередь — на уровне сессии плеера или шире**
   - **Вопрос:** очередь привязана к экрану плеера (умирает при выходе из плеера, незавершённые операции теряются) или к более долгоживущему компоненту (переживает выход из плеера, но не убийство процесса).
   - **Варианты:** (а) на уровне сессии плеера — проще, согласуется с текущей моделью S0094; (б) на уровне приложения/фонового исполнителя — устойчивее, но шире по объёму и пересекается с возможным WorkManager-путём.
   - **Нужно выяснить:** насколько часто пользователь выходит из плеера до завершения переносов; решение зафиксировать в тактической спеке. По умолчанию — вариант (а).
   - **Статус:** Open.

2. **Защита от дабл-тапа в пределах одного файла**
   - **Вопрос:** достаточно ли «файл исключён из списка → повторное действие по нему невозможно», или нужна дополнительная кратковременная защита кнопки от случайного двойного нажатия до завершения навигации.
   - **Варианты:** (а) только исключение файла; (б) исключение файла + краткий debounce кнопки.
   - **Нужно выяснить:** воспроизводится ли в реальности дабл-тап-гонка; решение — в тактической спеке.
   - **Статус:** Open.

3. **Поведение при ошибке: ретрай вручную или авто-ретрай**
   - **Вопрос:** при сбое операции (например, сеть отвалилась) — только сообщение с ручным «повторить», или ограниченный авто-ретрай перед показом ошибки.
   - **Варианты:** (а) только ручной ретрай; (б) 1–2 авто-ретрая, затем ошибка с ручным ретраем.
   - **Нужно выяснить:** что меньше раздражает и не приводит к зацикливанию; решение — в тактической спеке.
   - **Статус:** Open.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Оптимистичное исключение файла из списка расходится с реальным результатом операции (операция упала) | Средняя | Пользователь думает, что файл перемещён, а он на месте | Сообщение об ошибке с явным указанием файла и предложением повторить; список не «возвращает» файл автоматически, чтобы не путать позицию — повтор кладёт новую операцию |
| Очередь множит одновременные сетевые операции и перегружает соединение / создаёт гонки на ресурсе | Низкая | IO-ошибки, частичные переносы | Жёсткое ограничение: одновременно физически выполняется не более одной операции |
| Запрос системного разрешения (batch-delete) в середине очереди ломает порядок или зависает | Средняя | Очередь застряла, последующие операции не выполняются | Явная пауза/возобновление потребителя вокруг запроса разрешения; отказ — помечает текущую операцию не выполненной и идёт дальше |
| «Список опустел → закрыть плеер» срабатывает преждевременно из-за оптимистичного исключения, пока операции ещё в очереди | Средняя | Плеер закрывается, хотя операции ещё идут (в т.ч. могут упасть) | Проверку «список пуст → закрыть» делать после фактического завершения операций очереди, а не в момент навигации; пустой список + непустая очередь — держать плеер до опустошения очереди |
| Незавершённые операции теряются при выходе из плеера / убийстве процесса | Средняя | Часть файлов не перемещена без явного уведомления | На первой итерации — предупредить при выходе из плеера с непустой очередью; персист между сессиями вынесен в не-цели |

## 9. Архитектурные решения (ADR)

**ADR-1: очередь вместо одиночного флага «операция в процессе»**

- **Решение:** заменить guard «одна операция за раз, остальное отбросить» на FIFO-очередь снимков операций с последовательным фоновым потребителем.
- **Альтернативы:** оставить как есть (ждать каждую операцию); разрешить параллельные операции без очереди; просто чинить утечку флага (S0152) и считать достаточным.
- **Почему:** текущая модель ломает темп сортировки и молча теряет действия пользователя; параллельное выполнение перегружает соединения и плодит гонки; S0152 устраняет лишь утечку, но не сам случай «операция легитимно ещё идёт».

**ADR-2: одновременно выполняется максимум одна операция**

- **Решение:** очередь строго последовательная, физически в работе не более одной операции.
- **Альтернативы:** ограниченный пул параллельных операций.
- **Почему:** один сетевой ресурс/соединение плохо переносит несколько одновременных move/delete; последовательность исключает гонки и предсказуема для пользователя.

**ADR-3: оптимистичное исключение файла из списка по пути, без авто-возврата при ошибке**

- **Решение:** файл, по которому действие поставлено в очередь, сразу удаляется из списка плеера по пути; при сбое операции файл в список не возвращается — пользователю показывается ошибка с предложением повторить.
- **Альтернативы:** возвращать файл в список при ошибке.
- **Почему:** возврат файла на неопределённую позицию путает текущую позицию в плейлисте (та же причина, что в S0094 «удаление по пути, не по индексу»); явное сообщение + повтор честнее и проще.

## 10. Связи с другими спеками

- **S0094 (player-move-currently-playing, Verified):** ввёл оптимистичную навигацию и удаление из списка по пути; S0154 расширяет это на очередь из нескольких отложенных операций вместо одной.
- **S0152 (bugfix-moveinprogress-not-reset-after-batchdelete, BlockNeedUserTest):** чинит утечку флага «операция в процессе» в ошибочных ветках; S0154 заменяет саму модель этого флага очередью — после S0154 флаг как guard исчезает, поэтому реализацию S0154 имеет смысл начинать после верификации/слияния S0152, чтобы не конфликтовать.
- **S0073 (player-copy-move-custom-path-button, Verified):** кнопка move в произвольную папку — её действие тоже кладётся в очередь.

## 11. Критерии готовности (strategic-level)

1. В плеере при сортировке: переместил видео (медленный сетевой перенос идёт в фоне) → сразу перешёл к следующему файлу → нажал move / delete на нём → действие принято и файл ушёл в обработку, кнопка не «залипла».
2. Несколько действий move / delete / rename подряд (быстрее, чем выполняются фоновые операции) — все приняты, выполняются последовательно, ни одно не потеряно.
3. Ошибка одной операции из очереди — показано понятное сообщение по конкретному файлу, остальные операции очереди выполнились.
4. Если список файлов опустел в результате выполненных операций — плеер закрылся и вернулся в Browse только после фактического завершения очереди (а не пока операции ещё идут).
5. Поведение одинаково для локальных файлов, SMB, FTP, SFTP и облачных хранилищ.
6. Если операция в очереди требует системного разрешения (batch-delete) — запрос показан, после ответа очередь продолжила работу.

## 13. Last Audit

**Дата:** 2026-05-11
**Источник:** `logs/fastmediasorter_20260511_203620.log`

### Результат: Partial — очередь существует, но batch-delete resume сломан

`PlayerFileOperationQueue` уже реализован и виден в логах (`PlayerFileOperationQueue: started`, `permission required`, `failed`). Однако механизм pause/resume на batch-delete (§5.1 B) работает некорректно.

**Подтверждённый баг (→ S0163):**

При SMB Move:
1. Upload завершается SUCCESS (`uploadToSmb: SUCCESS` — лог строка 3970).
2. MediaStore требует batch-delete разрешения → `onPause` (строка 3982).
3. `PlayerLifecycleManager: Stored pending batch delete path` (строка 3981).
4. Пользователь подтверждает → `onResume` (строка 4156).
5. **`FileOperation: Starting operation: Move`** — очередь перезапускает полную операцию, а не только delete-часть (строка 4157).
6. `uploadToSmb: Local file does not exist` — файл уже удалён системой → `FAILURE` (строки 4183, 4185).

Паттерн воспроизведён на 5 файлах, 10 ошибок. Пользователь видит failure для операций, которые успешно завершены.

**Что работает корректно:**
- Постановка в очередь: `PlayerFileOperationQueue: started / permission required / failed` — сигналы есть.
- Credentials lookup с кэшем (`NetworkCredentialsRepository: cache hit`).
- Оптимистичная навигация к следующему файлу.

**Что не реализовано:**
- Сохранение промежуточного состояния «upload выполнен, ждём только delete».
- Корректное возобновление после batch-delete диалога только со стадии delete.
- Предупреждение пользователя при отказе от batch-delete (файл на SMB есть, локально не удалён).

**Ссылка:** S0163 закрывает именно batch-delete resume — как точечный bugfix, не дожидаясь полного S0154.
