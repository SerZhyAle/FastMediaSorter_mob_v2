## 1. Проблема

Wear OS компаньон и основное приложение телефона взаимодействуют только в одном направлении: телефон отправляет сетевые источники на часы по запросу. У часов нет способа сообщить телефону о событиях (открытый файл, избранное, позиция воспроизведения), а телефон не может изменить настройки или управлять воспроизведением на часах. Часть функций присутствует на одной стороне и отсутствует на другой: часы не умеют листать FTP-каталоги (только тест соединения), а телефон не отображает «что сейчас играет» на часах. Разрыв нарастает по мере развития каждой из платформ независимо.

---

## 2. Цели

1. Любые сетевые источники (SMB/FTP/SFTP), добавленные на часах, становятся доступны на телефоне по явному запросу пользователя.
2. Телефон может удалённо управлять воспроизведением (пауза/следующий) на часах через стандартный Wearable Data Layer.
3. Часы умеют читать и записывать FTP-каталоги — не только проверять соединение.
4. Настройки часов (интервал слайдшоу, разрешённые типы медиа) можно изменить как с часов, так и с телефона через экран WearSync.
5. Избранное, отмеченное на часах, попадает в базу данных телефона после синхронизации.
6. Телефон отображает актуальное состояние «сейчас играет» на часах: название, прогресс, источник.

**Non-goals:**

- Полная файловая синхронизация (переносить файлы между телефоном и часами).
- Облачные источники на часах (Google Drive, Dropbox, OneDrive).
- Потоковое воспроизведение видео с телефона на часы.
- Настройки телефона (не Wear-специфичные) на экране часов.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Анимация передачи данных на экране часов при двунаправленной синхронизации (аналогично уже реализованной для push источников).
2. Индикатор «последней синхронизации» на обеих сторонах с временной меткой.
3. Возможность принудительно повторить синхронизацию с любой стороны.
4. Предпочтительно: единый формат payload для всех типов sync-событий, расширяемый без переписывания Data Layer.

### 3.2 Жёсткие ограничения

- **Flavor:** standard (телефон) + wear (компаньон); lite и photos не затронуты.
- **API level:** minSdk 26 (телефон), Wear OS 3+ (часы).
- **Wear OS:** затрагивается как основная цель спеки.
- **Производительность:** Data Layer payload одного сообщения не должен превышать 100 КБ; батарея часов — синхронизация только по явному запросу пользователя, не по расписанию.
- **Совместимость данных:** Domain-модели payload должны быть версионированы (поле `version: Int`); обратная совместимость при добавлении полей.
- **Локализация:** EN/RU/UK — обязательно для любых новых строк UI на обеих сторонах.
- **Доступность:** новые кнопки/элементы на часах — минимальный размер касания по Wear OS HIG (48 dp).

## 4. Контекст текущей архитектуры

На телефоне реализован односторонний push: UseCase собирает сетевые источники из репозитория, упаковывает в JSON, кладёт в Data Item по пути `/fms/network_sources/push`. Сервис телефона слушает входящие сообщения от часов и умеет обработать только два пути: запрос sync и ACK. Слой часов принимает Data Item, разворачивает его через специализированный UseCase и сохраняет в зашифрованный SharedPreferences. Часы умеют запросить sync и подтвердить получение.

FTP-поддержка на часах ограничена классом проверки соединения — операций листинга и чтения файлов в слое данных нет. SFTP имеет аналогичный пустой тест. Browse работает только через SMB. Настройки хранятся на каждой платформе независимо; нет механизма для push настроек с телефона на часы. Избранное существует только на телефоне (Room DB); часы не имеют доступа к этой сущности.

## 5. Предлагаемый подход

### 5.1 Основные столпы / модули

**Столп A — Расширенный Data Layer (обе стороны)**

- Единая версионированная оболочка для всех sync-событий: тип события, версия схемы, payload в байтах.
- Определить набор path-констант для всех направлений: источники phone→watch (уже есть), источники watch→phone (новый), настройки phone→watch (новый), избранное watch→phone (новый), состояние воспроизведения watch→phone (новый), команды управления phone→watch (новый).
- Обе стороны слушают все актуальные пути через существующие WearableListenerService.

**Столп B — FTP/SFTP Browse на часах**

- Слой данных часов получает операцию листинга директории для FTP (аналогично уже реализованному SMB DataSource).
- Слой данных часов получает операцию листинга директории для SFTP.
- BrowseViewModel на часах расширяется для маршрутизации по протоколу (SMB уже есть, FTP и SFTP добавляются).

**Столп C — Синхронизация настроек (phone → watch)**

- Экран WearSync на телефоне получает секцию «Настройки часов»: переключатели для разрешённых типов медиа, управление интервалом слайдшоу.
- При изменении любого Wear-настройки на телефоне или по явной кнопке «Push settings» — отправка payload настроек на часы.
- Часы принимают payload настроек и записывают через существующий репозиторий настроек.

**Столп D — Синхронизация источников watch → phone**

- Часы могут отправить список своих источников (добавленных вручную на часах) на телефон.
- Телефон получает источники, предлагает импортировать их в основной репозиторий ресурсов с подтверждением (bottom sheet).
- Дедупликация по `server + port + protocol`; конфликт при совпадении показывает диалог выбора.

**Столп E — Состояние воспроизведения и удалённое управление**

- При активном воспроизведении на часах (аудио или видео) часы публикуют Data Item с текущим состоянием: название файла, источник, позиция, флаг паузы.
- Телефон отображает этот state на экране WearSync («Сейчас на часах»).
- Телефон может отправить команду управления (play/pause, next, previous) на часы через Message API.
- Часы реагируют на команды через WearableListenerService; плееры подписываются на поток команд.

**Столп F — Избранное watch → phone**

- При добавлении/снятии избранного на часах — часы отправляют delta (список изменений) на телефон.
- Телефон применяет delta к своей базе данных избранного.
- При следующей sync избранное отображается корректно на обеих сторонах.

### 5.2 Потоки данных и событий

- Инициатор sync на любой стороне → Data Layer (putDataItem или sendMessage) → Listener на другой стороне → UseCase обработки → Repository → UI-реакция.
- Состояние воспроизведения: плеер → Data Item (часы) → телефон получает, обновляет UI.
- Команды управления: UI телефона → Message (phone) → listener часов → плеер.
- Настройки: UI телефона → Data Item → listener часов → preferences.
- Избранное: UI часов → Message → listener телефона → favorites DB.

### 5.3 Точки расширяемости

- Payload-оболочка с `version` и `type` позволяет добавлять новые типы событий без изменения слоя транспорта.
- FTP/SFTP DataSource на часах реализуются через тот же интерфейс, что SMB — browse-логика не зависит от протокола.
- Удалённые команды описываются enum'ом; добавление новой команды не требует нового пути.

## 6. Открытые вопросы / Research items

1. **Лимит Data Item API**
   - **Вопрос:** Достаточно ли 100 КБ для payload настроек + избранных? Или нужен ChannelAPI для больших данных?
   - **Варианты:** PutDataItem (лимит ~100 КБ), MessageAPI (нет гарантии доставки), ChannelAPI (потоковый, сложнее).
   - **Нужно выяснить:** Реальный размер payload на тестовом наборе из 50 источников + 200 избранных.
   - **Статус:** Resolved — расчёт: 50 × 350 Б + 200 × 100 Б ≈ 37 КБ. PutDataItem достаточно.

2. **Батарея при публикации состояния воспроизведения**
   - **Вопрос:** Как часто обновлять Data Item с позицией воспроизведения? Каждую секунду — слишком дорого.
   - **Варианты:** Обновление только на pause/play/next/track-change; обновление каждые 10 с.
   - **Нужно выяснить:** Реальный drain на Galaxy Watch 6 при обновлении каждые 5 с.
   - **Статус:** Resolved — публиковать только при смене `isPlaying` и смене трека. Без таймера.

3. **FTP DataSource на часах — библиотека**
   - **Вопрос:** Использовать ту же Apache Commons Net, что на телефоне? Размер APK часов критичен.
   - **Варианты:** Apache Commons Net (уже в gradle, переиспользование), минимальная реализация FTP поверх Socket.
   - **Нужно выяснить:** Размер DEX от Commons Net при добавлении в `:wear`.
   - **Статус:** Resolved — `commons-net:3.10.0` (~200 КБ ProGuard) + `com.github.mwiede:jsch:0.2.17` (~130 КБ ProGuard). SSHJ исключён: конфликт BouncyCastle с SMBJ.

4. **Импорт источников watch → phone — UX**
   - **Вопрос:** Телефон получает источники от часов в фоне — как уведомить пользователя без назойливости?
   - **Варианты:** Notification (требует пермишна на Android 13+), бейдж на экране WearSync, тихое применение.
   - **Нужно выяснить:** Предпочтение владельца.
   - **Статус:** Resolved — карточка подтверждения на экране WearSync (без POST_NOTIFICATIONS).

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Data Layer недоступен при отсутствии Bluetooth | Высокая | Sync молча не проходит | Явный error state на обеих сторонах с повторным запросом |
| Размер payload избранного превышает 100 КБ | Средняя | putDataItem падает с exception | Chunked-send или ChannelAPI для крупных payloads |
| Конфликт версий схемы при rolling update | Низкая | Десериализация падает молча | Поле `version`; неизвестные версии логируются и отклоняются |
| FTP commons-net раздувает APK часов | Средняя | Превышение порога размера wear APK | ProGuard-стрипинг + измерение до реализации |
| Команды управления приходят после остановки плеера | Средняя | NullPointerException или нет эффекта | Guard-check на наличие активного плеера перед применением команды |

## 9. Архитектурные решения (ADR)

**ADR-1: Единый версионированный payload vs. отдельные pojo на каждый тип события**

- **Решение:** Единая оболочка с `eventType: String`, `schemaVersion: Int`, `data: ByteArray` для всех Data Layer сообщений.
- **Альтернативы:** Разные data-классы и пути для каждого события (как сейчас для network sources).
- **Почему:** При добавлении нового типа события не нужно менять транспортный слой; версия позволяет безопасный rolling update без crash на старом watch APK.

**ADR-2: Состояние воспроизведения через Data Item, команды через Message API**

- **Решение:** Состояние (часы → телефон) — putDataItem (гарантированная доставка при наличии связи). Команды (телефон → часы) — sendMessage (немедленность важнее гарантии).
- **Альтернативы:** Всё через Message API; всё через Data Item.
- **Почему:** Состояние нужно телефону «как можно скорее» после подключения (idempotent). Команды управления — немедленны и не имеют смысла через 30 секунд.

**ADR-3: FTP browse на часах — переиспользование Apache Commons Net**

- **Решение:** Оценить размер DEX в §6 item 3; если ≤ 300 КБ прироста — переиспользовать. Иначе — Socket-реализация LIST/RETR.
- **Альтернативы:** Только Socket.
- **Почему:** Commons Net уже в проекте, что снижает риск ошибок в FTP-парсинге. Решение принять после замера (§6 item 3 должен быть Resolved перед тактической спекой).

## 11. Критерии готовности (strategic-level)

1. Пользователь добавляет SMB-источник на часах, нажимает «Отправить на телефон» — телефон показывает диалог импорта с корректным именем источника.
2. Пользователь нажимает «Push settings» на экране WearSync телефона — интервал слайдшоу на часах меняется без ручного открытия настроек часов.
3. Файл, помеченный избранным на часах, появляется в разделе Favorites на телефоне после следующей синхронизации.
4. На экране WearSync телефона отображается название текущего трека/файла, воспроизводимого на часах, и кнопки play/pause/next работают без задержки >2 с.
5. FTP-источник, добавленный на часах, открывается в BrowseScreen часов и показывает список файлов (не только результат connection test).
6. При отсутствии Bluetooth обе стороны показывают локализованное сообщение об ошибке вместо тихого зависания.
