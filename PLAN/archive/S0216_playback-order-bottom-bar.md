# Стратегическая спецификация: S0216 — Перенос кнопки порядка воспроизведения в нижний бар плеера

**Ticket:** S0216
**Status:** Implemented
**Priority:** 50
**Date:** 2026-05-15
**Tier:** 2 — Easy (ad-hoc)
**Roadmap entry:** Ad-hoc — запрос 2026-05-15
**Tactical spec:** `PLAN/S0216_playback-order-bottom-bar/`

> **Scope:** STRATEGIC. Цели, ограничения, открытые вопросы. Без имён классов, путей, лимитов строк, миграций Room, модулей Hilt.

---

## 1. Проблема

В рамках S0104 кнопка цикла из четырёх режимов порядка воспроизведения (LOOP_LIST / PLAY_THROUGH / SHUFFLE / REPEAT_ONE) была размещена в верхней командной панели плеера — сразу после кнопки «Назад», первой среди прикладных кнопок (Info, Delete, Share, Fullscreen и т.д.). Одновременно в нижнем баре плеера (на той же строке, где Prev / Play-Pause / Next и кнопка открытия диалога управления воспроизведением) существует отдельная кнопка repeat-режима, которая работает почти бесполезно: она лишь переключает встроенный ExoPlayer `repeatMode` между OFF и ONE для видео, никак не связана с механизмом 4 режимов S0104, не работает для аудио и не отражает реальный режим, который применяется к навигации.

Эргономически правильная точка входа — нижний бар: там сосредоточены все управляющие воспроизведением кнопки, и пользователь уже привык к жесту «навёл на repeat-иконку». Текущая дублирующая кнопка в верхней панели визуально перегружает верхний бар и нарушает принцип «один род действия — одна точка входа».

---

## 2. Цели

1. Единственная точка входа в цикл 4 режимов порядка воспроизведения — нижний бар плеера, на текущем месте repeat-кнопки (первая позиция в строке с Prev / Play-Pause / Next / Control).
2. Поведение цикла полностью идентично текущей реализации S0104: одиночный тап → следующий режим по кольцу `LOOP_LIST → PLAY_THROUGH → SHUFFLE → REPEAT_ONE → LOOP_LIST`; тост с локализованным названием режима; обновление иконки и `contentDescription`; раздельная персистенция для аудио и видео; применение к навигации через существующий координатор.
3. Старая «полу-функциональная» логика repeat-кнопки (переключение `REPEAT_MODE_OFF ↔ REPEAT_MODE_ONE` только для видео через ExoPlayer) удаляется — она больше не нужна, потому что REPEAT_ONE из 4 режимов покрывает её сценарий и работает одинаково для аудио и видео.
4. Кнопка из верхней панели исчезает из видимого UI пользователя (точная судьба XML/Kotlin/overflow-записи — см. §6, вопрос 1).
5. Поведение для каждого из 4 режимов идентично между AUDIO и VIDEO: одинаковые иконки, одинаковые тосты, одинаковая навигационная семантика.

**Non-goals:**

- Изменение семантики любого из 4 режимов (логика остаётся той, что описана в S0104).
- Добавление 5-го режима SHUFFLE_ONCE (это отдельная задача из §3.1 S0104, не входит сюда).
- Изменение хранилища предпочтений воспроизведения (ключи `playback_order_audio` / `playback_order_video` остаются на месте).
- Изменение поведения слайд-шоу, кнопки «случайный файл», dice-button или любых других кнопок, отдалённо связанных с порядком.
- Замена иконок: набор `ic_loop_list / ic_arrow_downward / ic_random_nav / ic_repeat_one` сохраняется как есть.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. После переноса нижняя кнопка должна выглядеть и ощущаться как раньше — иконка уже подходит (`ic_repeat`-семейство), позиция «первая слева в нижнем ряду» сохраняется.
2. Если есть возможность одним тапом сразу видеть, какой режим сейчас активен (по иконке), — это критично; пользователь привык, что иконка меняется на каждом нажатии.
3. Желательно сохранить визуальную консистентность с верхней панелью: размер кнопки, padding и тинт — те же селекторы, что у соседних кнопок нижнего бара (не у верхнего).

### 3.2 Жёсткие ограничения

- **Flavor:** все варианты (standard, lite, photos, legacy, noLegal, vr, vrUnlicensed). Видимость — по предикату «текущий файл — AUDIO или VIDEO». На lite кнопка показывается только при VIDEO (AUDIO в lite отсутствует). На photos кнопка не показывается никогда — нижний бар плеера не используется без AUDIO/VIDEO. На остальных flavor — для обоих типов медиа.
- **API level:** без API-специфики; используются те же механизмы SharedPreferences и ExoPlayer Media3, что и сейчас.
- **Wear OS:** не затрагивается — у Wear отдельный плеер без custom controls.
- **Производительность:** перенос UI-точки входа не вносит новой нагрузки; обновление иконки — единичный `setImageResource` на каждом тапе.
- **Совместимость данных:** ключи `playback_order_audio` / `playback_order_video` остаются без изменений; пользователи, у которых уже выставлен режим, увидят его на новой кнопке сразу после обновления.
- **Локализация:** EN/RU/UK — обязательно. `contentDescription` новой нижней кнопки использует существующую динамическую строку «Playback order: %1$s», тост — существующую строку формата тоста с тем же шаблоном. Новые строки не вводятся; новой строки под кнопку нижнего бара не появится.
- **Доступность:** `contentDescription` обязан динамически отражать текущий режим (TalkBack читает имя режима); смена иконки не единственный индикатор.
- **Communication Policy:** строки переиспользуются без изменений, поэтому отдельной проверки тон-чеклиста по политике не требуется. Если на этапе `/spec-tech` всплывёт необходимость переименовать пункт или добавить пояснение — политика применяется по умолчанию.

## 4. Контекст текущей архитектуры

Верхняя командная панель плеера — это горизонтальный ряд кнопок, который инфлэйтится из общего layout-а активности плеера; его содержимым и адаптивным сокрытием при нехватке места управляет отдельный контроллер уровня UI-helpers. Нижний бар плеера — это кастомный controller layout, который инжектится в `PlayerView` ExoPlayer Media3; его кнопки и поведение управляются другим helper-классом уровня UI-helpers. Эти две панели сегодня не пересекаются: верхняя — это «командные» действия пользователя (info, delete, share, fullscreen), нижняя — собственно управление воспроизведением (prev / play-pause / next, и сейчас почти-нерабочий repeat).

Логика 4 режимов S0104 централизована в ViewModel плеера: метод цикла режима, поле состояния `playbackOrderMode` и сериализация в SharedPreferences. Применение к навигации (Prev/Next, авто-переход в конце файла) реализовано в координаторе навигации уровня UseCase/Helper. Применение к AUDIO выполняется через отдельный контроллер аудио-сервиса (он транслирует выбранный режим в команды Media-сессии и `MediaController.shuffleMode`/`repeatMode`). Применение к VIDEO — через ExoPlayer `repeatMode` (REPEAT_ONE) и через тот же координатор для SHUFFLE / PLAY_THROUGH.

То есть **бизнес-логика 4 режимов и её точка применения к плееру — уже корректны и не зависят от того, какая UI-кнопка инициирует цикл**. Задача исключительно UI-уровня: переехать из верхнего контроллера в нижний, аккуратно деактивировав старую полу-функциональную repeat-логику и не нарушив адаптивную раскладку верхней панели.

## 5. Предлагаемый подход

### 5.1 Основные столпы / модули

**UI-точка входа — нижний бар плеера**
- Существующая кнопка repeat в нижнем баре переиспользуется как новая точка входа для цикла 4 режимов.
- Старый обработчик клика (двух-состояния ExoPlayer repeat) удаляется; новый делегирует тот же контракт, что использует текущая кнопка верхней панели (вызов «следующий режим» в ViewModel плеера).
- Обновление иконки и `contentDescription` после смены режима — в helper-классе, отвечающем за нижний бар. Источник иконки — общий stateless-util с маппингом режим → drawable + строковый ресурс (см. §5.3).
- Видимость завязана на тип текущего файла: предикат `AUDIO || VIDEO` идентичен текущему предикату верхней кнопки.

**UI-точка входа — верхняя командная панель**
- Кнопка «Порядок» полностью удаляется из верхнего бара: XML в портретном и ландшафтном вариантах, обработчик клика, callback-метод в callback-интерфейсе, метод обновления иконки, дублёр в overflow-меню, запись в перечислении планировщика адаптивной раскладки.
- Никаких новых кнопок в верхнем баре не добавляется.

**Старая логика repeat-кнопки**
- Двух-состояния ExoPlayer `repeatMode` OFF↔ONE, привязанный к старой repeat-кнопке, удаляется полностью.
- Снимается визуальный индикатор «alpha=0.5 когда OFF» — новая логика всегда красит иконку с alpha=1.0, потому что у режима всегда есть выбранное значение.

**Бизнес-логика 4 режимов**
- ViewModel плеера, координатор навигации, контроллер аудио-сервиса, ключи SharedPreferences — без изменений.
- Цикл `LOOP_LIST → PLAY_THROUGH → SHUFFLE → REPEAT_ONE` остаётся той же машиной состояний.

### 5.2 Потоки данных и событий

- Пользователь тапает кнопку в нижнем баре → helper нижнего бара вызывает «следующий режим» в ViewModel плеера.
- ViewModel переключает поле `playbackOrderMode` на следующий по кольцу, пишет в SharedPreferences, эмитит обновлённый `PlayerState`.
- Helper нижнего бара подписывается на обновление и: обновляет иконку, обновляет `contentDescription`, показывает тост (или эмитит событие тоста — см. где именно сейчас живёт показ тоста).
- Применение к навигации: координатор навигации читает `playbackOrderMode` из состояния — без изменений.
- Применение к AUDIO: контроллер аудио-сервиса вызывает существующий `applyPlaybackOrderMode` — без изменений.
- Применение к VIDEO: ExoPlayer `repeatMode = REPEAT_ONE` при выборе REPEAT_ONE; для остальных режимов VIDEO ExoPlayer переходит в `REPEAT_MODE_OFF`, а PLAY_THROUGH / SHUFFLE обрабатываются координатором — без изменений.

### 5.3 Точки расширяемости

- Маппинг «режим → drawable + строковый ресурс названия» выносится в отдельный stateless-util уровня utils (общий для всех UI-helpers). Это единый источник для нижнего бара сейчас и для любого другого UI-контекста в будущем (верхняя панель read-only badge, VR-overlay, Wear-companion и т.д.) без копирования.
- Введение 5-го режима (SHUFFLE_ONCE из S0104 §3.1) не блокируется этой спекой: достаточно расширить перечисление и маппинг в utils — UI обновится автоматически.
- Если когда-нибудь понадобится показать индикатор режима в верхнем баре (например, как read-only badge при slideshow), это можно сделать поверх существующего util без перепроектирования.

## 6. Открытые вопросы / Research items

1. **Судьба верхней кнопки «Порядок»** — **Resolved**
   - **Решение:** полное удаление из видимого UI для AUDIO и VIDEO в обеих ориентациях (портрет + ландшафт). Это контексты, в которых верхняя кнопка вообще когда-либо показывалась (текущий предикат — `MediaType.AUDIO || MediaType.VIDEO`), поэтому фактически кнопка исчезает из всех сценариев.
   - **Что чистится:** XML-объявления `btnPlaybackOrderCmd` в обоих layout-вариантах активности плеера, обработчик клика и метод обновления иконки в helper-е верхней панели, callback-метод `onPlaybackOrderClicked()` в callback-интерфейсе helper-а, метод-делегат в callback-имплементации, вызов `commandPanelController.updatePlaybackOrderButtonIcon(...)` в активности плеера на инициализации и после смены режима.
   - **Статус:** Resolved.

2. **Видимость кнопки в нижнем баре для AUDIO и VIDEO на всех flavor** — **Resolved**
   - **Решение:** новая нижняя кнопка работает одинаково на всех flavor (standard, lite, photos, legacy, noLegal, vr, vrUnlicensed) — для AUDIO и для VIDEO. Видимость завязана на тот же предикат «текущий файл — AUDIO или VIDEO», что используется сейчас на верхней кнопке. На flavor без AUDIO (lite) кнопка показывается только при VIDEO; на photos (без AUDIO и без VIDEO) — не показывается никогда, потому что нижний бар плеера в принципе не используется.
   - **Технический риск (Средняя):** на AUDIO визуально кнопка может не появиться, если controller-слой ExoPlayer-а не рендерится без видеокадров. Если так — на этапе `/spec-tech` решается явным показом controller-а через `controller_show_timeout_ms` или принудительным `showController()`.
   - **Статус:** Resolved.

3. **Куда переезжает логика обновления иконки** — **Resolved**
   - **Решение:** маппинг режим → drawable + строковый ресурс названия выносится в отдельный stateless-файл уровня utils (общий util для обоих контекстов UI). Этим утилитарным маппингом пользуются:
     - **helper нижнего бара плеера** — для AUDIO и VIDEO, где живёт точка входа цикла после переноса (основной потребитель);
     - **helper верхней панели** — на случай, если в будущем понадобится индикатор режима в верхней панели для не-audio/video контекстов (read-only badge при slideshow и т.п.); сегодня помощник верхней панели не вызывает маппинг ни в одном сценарии, но точка расширения уже есть.
   - **Что НЕ перемещается:** ViewModel плеера и координатор навигации остаются без изменений; они работают с `PlaybackOrderMode` напрямую, без drawable-маппинга.
   - **Статус:** Resolved.

4. **Пункт `menu_playback_order` в overflow-меню** — **Resolved (derived)**
   - **Решение:** удалить запись из `overflow_menu_player.xml`. Overflow-меню — это резервная точка входа для адаптивного сокрытия кнопок верхней панели; раз верхняя кнопка убирается полностью (вопрос 1), её дублёр в overflow становится сиротой и тоже удаляется. Единственная точка входа цикла режимов — нижний бар, согласно цели №1.
   - **Что чистится:** XML-запись пункта в overflow меню, обработчик в `onOptionsItemSelected`-роутере активности плеера (если есть), строка `playback_order_menu_title` остаётся в `strings.xml` пока её использует, например, `contentDescription` верхней-уже-удалённой кнопки — после удаления XML её фактически перестают использовать, но решение «оставить строку или удалить» принимается на этапе `/spec-tech` по результату `check_strings_localized`.
   - **Статус:** Resolved (derived from Q1 — переподтвердить при возражении).

5. **`contentDescription` и строка тоста на новой кнопке** — **Resolved (derived)**
   - **Решение:** на новой нижней кнопке используется существующая динамическая строка `playback_order_button_desc` («Playback order: %1$s») как `contentDescription` — она уже локализована EN/RU/UK, отражает имя текущего режима и применяется сейчас на верхней кнопке. Тост при смене режима продолжает использовать `playback_order_mode_set` («Playback order: %1$s» в формате тоста) — без изменений.
   - **Альтернатива (отклонена):** статическая строка `playback_order_menu_title` («Playback order») — теряет TalkBack-информативность о текущем режиме.
   - **Старая строка `repeat`:** перестаёт использоваться как `contentDescription` repeat-кнопки. Решение оставить её в `strings.xml` или удалить — на этапе `/spec-tech` после проверки других мест использования.
   - **Статус:** Resolved (derived — переподтвердить при возражении).

6. **Запись `PLAYBACK_ORDER` в планировщике адаптивной раскладки верхней панели** — **Resolved (derived)**
   - **Решение:** удалить запись из перечисления `PlayerCommand` в планировщике вместе с любыми ссылающимися на неё строками маппинга `case PLAYBACK_ORDER -> binding.btnPlaybackOrderCmd`. Раз кнопка из верхней панели уходит полностью (вопрос 1), enum-запись становится мёртвым кодом — не оставляем «historic».
   - **Альтернатива (отклонена):** оставить как «historic» с комментарием — нарушает принцип «нет мёртвого кода», и при добавлении нового пункта планировщика возникает соблазн переиспользовать старое значение, что вносит путаницу.
   - **Статус:** Resolved (derived — переподтвердить при возражении).

7. **Поведение для AUDIO + lite/photos flavor** — **Resolved (covered by Q2)**
   - **Решение:** вопрос полностью покрыт ответом на Q2. На lite (VIDEO + IMAGES) кнопка показывается только при VIDEO; AUDIO там не существует, поэтому случай неприменим. На photos (IMAGES + ANIM) кнопка не показывается никогда — нижний бар плеера для photos не используется, потому что нет ни AUDIO, ни VIDEO. На остальных flavor (standard, legacy, noLegal, vr, vrUnlicensed) — для AUDIO и VIDEO.
   - **Статус:** Resolved.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Старая ExoPlayer-логика `REPEAT_MODE_OFF ↔ ONE` где-то ещё дёргается из кода (не только через UI-кнопку) | Низкая | После удаления обработчика остаётся «висящий» state на ExoPlayer, который не виден пользователю, но влияет на повторение | На этапе `/spec-tech` собрать все вызовы `setRepeatMode` и обновления иконки старой repeat-кнопки; убедиться что вне UI-обработчика никто не подаёт OFF/ONE напрямую |
| Кнопка в нижнем баре для AUDIO визуально не появляется (PlayerView controller не виден без видеокадров) | Средняя | Кнопка переехала, но пользователь её не видит при проигрывании MP3 | На этапе `/spec-tech` уточнить факт показа controller-слоя для AUDIO; при необходимости поднять видимость через `app:show_timeout` или явный показ контроллера |

## 9. Архитектурные решения (ADR)

**ADR-1: Переиспользовать существующую repeat-кнопку нижнего бара вместо добавления новой**

- **Решение:** новая точка входа цикла 4 режимов — это та же `ImageButton` в нижнем баре, что сейчас называется repeat-кнопкой. Никаких новых View не вводится; новая логика подменяет старую целиком.
- **Альтернативы:** (a) добавить отдельную новую кнопку рядом, оставив старую repeat-кнопку с её OFF↔ONE логикой; (b) добавить новую кнопку в нижний бар, удалив repeat-кнопку.
- **Почему:** (a) даёт две кнопки с почти одинаковой семантикой в одном баре — UX-шум; (b) увеличивает дельту изменений в layout-ах двух вариантов нижнего бара и в helper-е без выгоды по сравнению с переиспользованием.

**ADR-2: Маппинг режим → drawable выносится в отдельный stateless-util**

- **Решение:** функция вида «по `PlaybackOrderMode` вернуть drawable-ресурс + строковый ресурс названия» переезжает из helper-а верхней панели в отдельный файл уровня utils. К нему обращается helper нижнего бара (основной потребитель сейчас). Helper верхней панели больше не вызывает маппинг — но при появлении новых UI-контекстов (VR-overlay, slideshow badge) они получают доступ через тот же util.
- **Альтернативы:** (a) скопировать функцию в helper нижнего бара, оставив дубль; (b) внедрить через зависимость от ViewModel плеера; (c) оставить функцию в helper-е верхней панели и вызывать оттуда из helper-а нижнего бара.
- **Почему:** копирование создаёт два места для синхронной правки при будущем добавлении SHUFFLE_ONCE; внедрение через ViewModel размывает ответственность; кросс-зависимость helper→helper нарушает изоляцию UI-helpers.

## 11. Критерии готовности (strategic-level)

1. В нижнем баре плеера на первой позиции слева видна кнопка с иконкой, отражающей текущий режим из набора `LOOP_LIST / PLAY_THROUGH / SHUFFLE / REPEAT_ONE`.
2. Одиночный тап по этой кнопке переключает режим на следующий по кольцу, иконка меняется мгновенно, появляется тост с локализованным названием нового режима, `contentDescription` обновляется.
3. Поведение цикла идентично между AUDIO и VIDEO (где обе категории доступны на текущем flavor).
4. Все 4 режима применяются к навигации (Prev/Next, авто-переход в конце файла) точно так же, как до переноса.
5. Режим сохраняется отдельно для AUDIO и VIDEO и восстанавливается при повторном открытии плеера.
6. В верхней панели плеера кнопка порядка воспроизведения отсутствует в обеих ориентациях.
7. Старая repeat-логика (двух-состояния OFF↔ONE через ExoPlayer для VIDEO) полностью удалена; никакая комбинация действий пользователя её больше не запускает.
8. На lite кнопка появляется только при проигрывании VIDEO; на photos кнопки нет нигде; на остальных flavor — для AUDIO и VIDEO.
9. EN/RU/UK строки проходят `check_strings_localized.ps1` без ошибок (новых строк не добавляется; если какие-то старые перестают использоваться — журнал об этом фиксируется на этапе `/spec-tech`).
10. Маппинг режим → drawable доступен из stateless-util — любой будущий UI-контекст может его переиспользовать без дублирования.
