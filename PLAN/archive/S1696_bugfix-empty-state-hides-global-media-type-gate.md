**Status:** Archived
**Priority:** 90
**Date:** 2026-08-15

## 0. Захваченный материал (inbox)

**Захвачено:** 2026-08-15

**Текст:**

Browse empty state says "Здесь пусто. Мы проверили дважды" when every file was removed by the global media-type gate (Settings > Media > "Поддержка статичных изображений" = off). Observed 2026-08-15 on Galaxy S21, cloud resource "H" (Google Drive, 100 jpg files): resource had IMAGE checked, list showed 0 files, no hint about the cause. ResolveScanFilterUseCase intersects resource.supportedMediaTypes with settings.getGloballyEnabledMediaTypes(); it already has withoutSizeCeiling() to explain a size-filtered empty result, but nothing explains a type-filtered one. Proposal: rescan with the un-intersected type set and, when that yields files, tell the user which global media type is off and offer a jump to that setting.

**Эвиденс (logcat, Galaxy S21 RFCR110NBQJ, 2026-08-15 16:09-16:15):**

```
16:09:41.234 BrowseResourceLoadManager: supportedMediaTypes: [VIDEO, AUDIO, GIF, TEXT, PDF, EPUB, OFFICE_DOCUMENT]
16:09:42.318 SLog [get-media-files] Scanner returned files {count=0}
16:10:43.042 SLog [get-media-files] Scanner returned files {count=100}   # после включения allFiles на ресурсе
16:11:55.536 BrowseStateSyncManager: supportedMediaTypes: [..] -> [IMAGE, VIDEO, AUDIO, GIF, TEXT, PDF, EPUB, OFFICE_DOCUMENT]
16:11:56.662 SLog [get-media-files] Scanner returned files {count=0}     # IMAGE есть у ресурса, но выключен глобально
```

Состояние настройки в `files/datastore/settings.preferences_pb`: `support_images` = false. После включения тумблера «Поддержка статичных изображений» тот же ресурс сразу показал 100 файлов.

---

## 1. Проблема / симптом

Ресурс содержит файлы, но список пуст, и текст пустого состояния утверждает обратное («Здесь пусто. Мы проверили дважды»). Реальная причина - глобальный тумблер типа медиа выключен, из-за чего эффективный набор типов после пересечения не содержит тип файлов ресурса. Пользователь не может связать пустой экран с настройкой в другом разделе: на уровне ресурса нужный тип отмечен, счётчик карточки на главном при этом показывал 100 файлов.

Воспроизведено на облачном ресурсе Google Drive, но пересечение общее для всех типов ресурсов - локальные и сетевые затронуты так же.

---

## 2. Корневая причина

Подтверждено по дереву.

`ResolveScanFilterUseCase` строит эффективный набор типов как `resource.supportedMediaTypes.intersect(globallyEnabledTypes)` и результат пересечения никуда не сохраняет. Отброшенные типы после этого не существуют ни для кого ниже по течению, поэтому пустое состояние физически не может их назвать.

**Половина решения в этом же классе уже есть, и её надо повторить.** S1584 столкнулся с тем же классом дефекта по другой оси - фильтру размера - и решил его так:

- `withoutSizeCeiling(filter)` возвращает тот же фильтр со снятыми потолками размера.
- `BrowseResourceLoadManager.reportFilterSuppressedFiles` при пустом списке пересчитывает с ним и кладёт число в `BrowseState.filteredOutCount`.
- `BrowseObserverManager.renderEmptyState` при ненулевом счётчике печатает другое сообщение вместо «мы проверили дважды».

Ось типов ровно такой пары не имеет. Это и есть весь дефект.

**Важное для объёма:** существующее объяснение - **только текст**, сообщение плюс подсказка. Ни кнопки, ни перехода в настройку в нём нет. Значит текстовое объяснение по оси типов повторяет прецедент один в один и не требует ни одного нового решения о размещении.

---

## 3. Исправление

Повторить связку S1584 по оси типов. Ничего нового не изобретается.

Состав правки:

1. `ResolveScanFilterUseCase`: добавить `withoutGlobalTypeGate(resource, filter)` рядом с `withoutSizeCeiling`. Возвращает тот же фильтр, где набор типов взят **без** пересечения с глобальным тумблером, но по-прежнему ограничен флейвором - то есть `applyFlavorMediaTypeRestrictions(resource.supportedMediaTypes)`. Флейворное ограничение снимать нельзя: типа, который сборка не умеет открывать, у пользователя нет и включить его негде.
2. `BrowseState`: поле `typeGatedOutCount: Int = 0` по образцу `filteredOutCount`.
3. `BrowseResourceLoadManager`: в `reportFilterSuppressedFiles`, если проба по размеру ничего не объяснила, выполнить вторую пробу с `withoutGlobalTypeGate`. Ранний выход при остановленном сканировании и непустом списке уже написан и распространяется на обе пробы. Если наборы типов совпали - выйти, как это делает проба размера при совпавших фильтрах.
4. `BrowseObserverManager.renderEmptyState`: ветка при `typeGatedOutCount > 0`, ниже ветки размера. Сообщение и подсказка - новые строки.
5. Строки EN/RU/UK через `set-android-string.ps1 -Action add`.

Порядок веток в пустом состоянии: избранное, затем фильтр размера, затем фильтр типов, затем общий текст. Размер идёт первым, потому что он уже там; при обеих причинах сразу пользователь увидит одну, и это лучше, чем перечислять обе в одном абзаце.

**Что в объём не входит.** Предложение из захвата «предложить переход в эту настройку» - новая сущность: у существующего объяснения перехода нет, и прецедента для него в пустом состоянии тоже нет. Вынесено в вопрос владельцу ниже, чтобы не блокировать текстовую половину, которая полностью выводима.

### 3.3 Owner inputs (Approval gate)

- **Related tickets:** S1584 (то же расхождение между счётчиком карточки и списком; его связка `withoutSizeCeiling` - образец, повторяемый здесь)
- **UI scope:** новых элементов нет, меняется только текст пустого состояния - ровно тот механизм, что уже работает для фильтра размера. Решения о размещении не требуется.
- **Data scope:** хранилища не затрагивает, новое поле состояния живёт в памяти экрана.

**Вопрос на потом, не блокирующий эту правку:** делать ли пустое состояние кликабельным с переходом в нужный раздел настроек. Сегодня ни одно объяснение в пустом состоянии так не умеет, поэтому это отдельное решение о поведении, а не часть починки.

## 4. Проверка

1. Ресурс с файлами одного типа; глобальный тумблер этого типа выключен. Открыть ресурс: список пуст, но текст называет причиной выключенный тип, а не пустую папку.
2. Включить тумблер, вернуться: файлы на месте, текст пустого состояния не показывается.
3. Ресурс в по-настоящему пустой папке при всех включённых тумблерах: текст прежний, «мы проверили дважды» - регрессии нет.
4. Ресурс, опустошённый фильтром размера: показывается объяснение про размер, а не про типы - порядок веток соблюдён.
5. Флейвор без поддержки типа (например, документы в `lite`): объяснение про глобальный тумблер **не** показывается, потому что включать там нечего.
6. Юнит-тест на `withoutGlobalTypeGate` рядом с существующим тестом `withoutSizeCeiling` в `ResolveScanFilterUseCaseTest`: снимает пересечение с глобальным набором и сохраняет флейворное ограничение.
