## 1. Проблема

Чтобы завести новый ресурс, приходится выходить из лаунчера в приложение, проходить создание там и затем отдельным действием класть ярлык на стол. Для домашнего экрана, который и так показывает плитки ресурсов, это лишний круг: место, где ярлык нужен, и место, где ресурс заводится, разведены. Область - домашний экран лаунчера и существующий поток создания ресурса.

## 2. Цели

1. Создать ресурс можно, не покидая домашнего экрана.
2. Создание идёт **тем же самым** потоком, что и из приложения, а не упрощённой копией - владелец сказал «проходит стандартный флоу» дословно.
3. По успешному созданию ярлык на рабочем столе появляется сам, без отдельного действия пользователя.
4. Отмена или неуспех не оставляют ни ресурса, ни ярлыка.

**Non-goals:**

- Новый, отдельный от приложения мастер создания ресурса. Дублирование этого потока - самая дорогая ошибка, которую здесь можно сделать.
- Изменение самого потока создания ресурса: он вызывается как есть.
- Массовое создание и импорт нескольких ресурсов разом.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Ярлык появляется сразу, без подтверждающего диалога - формулировка «сразу создаёт» это задаёт.

### 3.2 Жёсткие ограничения

- **Flavor:** режим лаунчера живёт не во всех вариантах сборки, поэтому точка входа обязана быть в том же наборе, что и остальной домашний экран; конкретный набор берётся из `docs/FLAVOR_MATRIX.md` на этапе `/spec-tech`, не по памяти.
- **API level:** закрепление ярлыка ограничено платформой; ветка для устройств без поддержки закрепления обязана быть, иначе на них создание молча не даст ярлыка.
- **Wear OS:** не затрагивается.
- **Производительность:** не критично - действие разовое и пользовательское.
- **Совместимость данных:** новых сущностей нет, ресурс создаётся существующим путём.
- **Локализация:** EN/RU/UK обязательно - появляется как минимум подпись точки входа.
- **Доступность:** точка входа обязана иметь фокус и работать с клавиатуры и D-pad наравне с остальными элементами стола.

### 3.3 Owner inputs (Approval gate)

- **UI placement contract:** решено владельцем 2026-08-07 - точек входа три, и все три ведут в один и тот же поток создания.
  1. В диалоге выбора содержимого, на шаге выбора ресурса, пунктом «Создать новый..». Диалог уже открывается пустой ячейкой и кнопкой «+» в режиме редактирования.
  2. Пунктом в меню лаунчера.
  3. Пунктом в меню, открывающемся длительным нажатием по пустому столу вне режима редактирования при разблокированном столе. Самого меню ещё нет - оно ведётся в S1466; эта точка входа появляется вместе с ним и в объём S1423 не входит.
- **Accessibility:** точка входа фокусируема и работает с клавиатуры и D-pad наравне с остальными элементами стола (§3.2).
- **Localization:** новая подпись точки входа - EN/RU/UK сразу.
- **Related tickets:** S1466 (меню длительного нажатия - хост третьей точки входа), S1424 (полное меню ресурса у ярлыка - потребитель того же ярлыка), S1428 (группы ярлыков), S1289 (плитки ресурсов на лаунчере), S1178 - сосед по домашнему экрану

## 4. Контекст текущей архитектуры

Обе половины задачи в коде уже есть, и ни одну не нужно писать заново.

- **Поток создания ресурса** - отдельный экран со своей моделью и «финализатором», который завершает создание и знает, что ресурс успешно заведён. Это естественная и единственная точка, откуда закрепление ярлыка должно запускаться: она уже отличает успех от отмены.
- **Закрепление ярлыка на ресурс** - существующий менеджер в слое виджетов, ровно для этой задачи. У него есть работающий сосед того же вида для потоков, то есть образец применения уже отработан.
- **Приём закреплённого ярлыка** - отдельный сценарий уровня домена: приложение само выступает хостом закрепления, когда оно же является домашним экраном, и этот путь уже покрыт.

Чего нет - только точки входа на домашнем экране и связи «успешное создание -> закрепить». Поэтому задача сводится к склейке, а не к новой подсистеме.

## 5. Предлагаемый подход

Точка входа на домашнем экране запускает существующий поток создания как есть; финализатор потока по успеху обращается к существующему закреплению ярлыка; домашний экран принимает ярлык уже имеющимся путём хоста закрепления.

### 5.1 Основные столпы / модули

1. **Точки входа на домашнем экране.** Их три (§3.3), и ни одна не знает о создании ничего - каждая только запускает существующий экран создания и получает результат. Отсюда следует, что запуск должен быть одним общим вызовом, а не тремя обработчиками: три копии разойдутся при первой же правке. Третья точка входа физически появляется вместе с S1466 и в объём этого тикета не входит.
2. **Связка «успех -> ярлык».** Закрепление инициируется там, где успех уже определён - в завершающем звене потока создания, а не в вызывающем экране. Иначе создание из приложения и создание с лаунчера разойдутся в поведении, что и есть дублирование, запрещённое в §2.
3. **Ветка «закрепление недоступно».** Если платформа или текущий домашний экран закрепление не поддерживают, ресурс всё равно создаётся, а пользователь получает внятное сообщение - молчаливое отсутствие ярлыка недопустимо.

### 5.2 Потоки данных и событий

Домашний экран -> существующий экран создания -> завершение создания -> закрепление ярлыка -> домашний экран принимает ярлык и показывает его.

### 5.3 Точки расширяемости

Связка «успех -> ярлык» должна включаться флагом вызова, а не быть безусловной: создание из приложения ярлык класть не обязано, и S1424 с S1428 будут навешивать на тот же ярлык своё поведение.

## 8. Влияние на пользователя (docs/FEATURES)

Новая способность: ресурс заводится прямо с домашнего экрана и сразу получает ярлык. Одно предложение в `docs/FEATURES.md` + `_RU` + `_UK` пишется при закрытии тикета.

## 9. Архитектурные решения (ADR)

**ADR-1: закрепление инициируется завершающим звеном потока создания, а не точкой входа**

- **Решение:** связка «успех -> ярлык» живёт там же, где определяется успех создания.
- **Альтернативы:** вызывающий экран сам ловит результат и закрепляет.
- **Почему:** альтернатива разводит поведение создания из приложения и с лаунчера и делает «стандартный флоу» из §0 неправдой при первой же правке потока.

**ADR-2: существующие механизмы переиспользуются целиком**

- **Решение:** ни поток создания, ни закрепление ярлыка, ни приём закреплённого ярлыка заново не пишутся.
- **Почему:** все три уже есть и работают, у закрепления есть отработанный сосед-образец; новая здесь только склейка.

## 10. Связи с другими спеками

- S1424 - полное меню ресурса у ярлыка: потребитель того же ярлыка.
- S1428 - группы ярлыков: тот же объект на столе.
- S1289 - плитки ресурсов на лаунчере: соседняя поверхность.

## 11. Критерии готовности (strategic-level)

1. С домашнего экрана открывается тот же экран создания ресурса, что и из приложения - не копия.
2. По успешному созданию ярлык появляется на столе без дополнительных действий пользователя.
3. Отмена создания не оставляет ни ресурса, ни ярлыка.
4. Создание ресурса из приложения ярлык не кладёт - поведение прежнее.
5. На устройстве, где закрепление недоступно, ресурс создаётся и пользователь получает сообщение, а не молчание.
6. Точка входа доступна с клавиатуры и D-pad наравне с остальными элементами стола.
