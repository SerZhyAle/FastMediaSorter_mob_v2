## 1. Проблема

Сетевой слой FTP, отвечающий за чтение байт «с лимитом N», физически тянет с сервера весь файл и обрезает буфер уже после получения. На больших аудио-файлах (десятки МБ MP3) это выливается в две беды: (1) трафик и время на лишние мегабайты, которые никогда не пригодятся вызывающему коду; (2) FTP-сервер успевает посчитать передачу слишком длинной и закрывает контрольный канал по data-/idle-таймауту прямо во время чтения — последующий запрос подтверждения команды падает на уровне библиотеки и попадает в логи как ошибка. Особенно болезненно бьёт по сценарию загрузки метаданных аудио, где реально требуется лишь первые десятки КБ (заголовки тегов).

---

## 2. Цели

1. При запросе «прочитать не более N байт» сеть отдаёт **не более** N байт независимо от размера удалённого файла.
2. Передача данных корректно завершается со стороны клиента до того, как сервер выйдет на свой таймаут передачи.
3. На запросе «всё содержимое» (без верхнего лимита) поведение остаётся прежним.
4. Снижается частота обрывов контрольного канала FTP во время чтения метаданных крупных аудио-файлов.
5. Уменьшается трафик и латентность для каждой операции с лимитом байт.

**Non-goals:**

- Менять поведение SMB- и SFTP-обёрток — у них другие протокольные идиомы, проблема двухканальной FTP-передачи к ним не относится.
- Лечить уже устранённый шумный NPE в логах — это сделано отдельным узким фиксом, S0206 закрывает корневую причину, а не симптом.
- Менять размер бюджета чтения для извлечения тегов — это решение остаётся за слоем извлечения метаданных.
- Перетаскивать пайплайн потоковой загрузки на range-запросы FTP (REST/SIZE) — это самостоятельная история со своими рисками.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Поведение «считай весь файл» должно оставаться байт-в-байт прежним — это важная гарантия для существующих сценариев скачивания.
2. Желательно унифицировать механику ограниченного чтения между «пулом постоянных соединений» и «одноразовыми соединениями» FTP — обе ветки должны вести себя одинаково.
3. На случай, если штатное прерывание передачи отказывает на каком-то сервере, нужен корректный fallback — не оставлять соединение в подвешенном состоянии.

### 3.2 Жёсткие ограничения

- **Flavor:** все варианты сборки, где включён FTP (фактически — все, где `BuildConfig` пускает сетевые источники). Источниковая разделимость по флейворам не требуется — изменение в общем `src/main`-слое.
- **API level:** без API-специфики Android, ограничение чисто протокольное.
- **Wear OS:** не затрагивается — Wear FTP-источники не использует.
- **Производительность:** обязательное наблюдаемое улучшение — для запросов с лимитом N байт сетевая часть должна прочитать ≤ N + один read-буфер. Латентность операций с лимитом 64 КБ для крупных файлов должна стать «независимой от размера файла».
- **Совместимость данных:** не применимо — нет хранимых сущностей.
- **Локализация:** не применимо — изменение во внутреннем сетевом слое, без пользовательских строк.
- **Доступность:** не применимо — без UI-составляющей.

## 4. Контекст текущей архитектуры

Доступ к файлам по сети организован поверх двух обёрток FTP: одна держит постоянное соединение под пул запросов от одного источника, другая открывает одноразовое соединение под изолированную операцию. Обе предоставляют операцию «прочитать байты файла» с опциональным верхним лимитом, и обе сегодня реализуют этот лимит через «прочитать всё, потом обрезать». Сверху эту операцию использует слой извлечения аудио-метаданных, который рассчитывает на бюджет ≈ 64 КБ — достаточный для разбора заголовков тегов любого распространённого формата. Между сетью и потребителем стоит троттлинг-менеджер, ограничивающий конкурентность по хосту; на корневую проблему он не влияет, но удерживает соединение под нагрузкой ровно столько, сколько идёт фактический read — то есть весь файл.

---

## 5. Предлагаемый подход

Перевести обе FTP-обёртки на **истинное ограниченное чтение**: брать из входящего потока ровно столько, сколько запросил вызывающий, и явно сообщать FTP-серверу о завершении передачи на стороне клиента до получения подтверждения команды. На вход без лимита поведение остаётся прежним — читаем поток до конца естественным образом. Унифицировать механику между обеими обёртками, чтобы поведение совпадало вне зависимости от того, идёт ли операция через пул или через изолированное соединение.

### 5.1 Основные столпы / модули

- **Сетевая обёртка FTP — режим «ограниченное чтение».** Получает целевой лимит, читает не больше указанного, корректно сворачивает передачу до подтверждения команды. На исчерпание данных раньше лимита — отдаёт фактический размер. На любые сетевые ошибки внутри ограниченного чтения — нормальное распространение ошибки, без шума в логах сверху того, что уже принято.
- **Сетевая обёртка FTP — режим «полное чтение».** Сохраняется: читает поток до конца, подтверждает команду как сейчас. Этот режим — единственная семантика для скачиваний и должен остаться побайтно идентичным.
- **Слой извлечения аудио-метаданных.** Не меняется как клиент API — продолжает запрашивать чтение с верхним лимитом, но фактически получает первые N байт без задержки на скачивание остатка.

### 5.2 Потоки данных и событий

«Потребитель метаданных → сетевая обёртка FTP → удалённый сервер»: обёртка вычитывает запрошенный объём, выполняет процедуру штатного прерывания передачи на уровне протокола, дожидается подтверждения команды, отдаёт байты. Параллельно остаётся прежний путь «полное чтение», где никакого прерывания не происходит. Промежуточный троттлинг-слой не меняет своих контрактов.

### 5.3 Точки расширяемости

- Контракт операции «читать байты» остаётся прежним: тот же набор параметров, та же сигнатура успеха/ошибки. Это сознательно — никакой клиент API не должен переписываться.
- Внутри обёртки разделение «ограниченное чтение» / «полное чтение» оформляется так, чтобы и пул, и одноразовый клиент опирались на одну реализацию ограниченного чтения. Конкретный механизм совместного владения логикой — задача тактической спеки.
- Существующий fallback с переключением между режимами передачи (passive/active) сохраняется в обеих ветках; ограниченное чтение должно работать в обоих режимах.
- Никакие BuildConfig-флаги не вводятся — поведение должно быть единым для всех флейворов с FTP. Поэтому ограничение CLAUDE.md Rule 15 здесь не активируется: фича не флейвор-специфична.

## 6. Открытые вопросы / Research items

1. **Поведение штатного прерывания на разных FTP-серверах.**
   - **Вопрос:** одинаково ли отрабатывает процедура прерывания передачи на серверах семейств vsftpd / FileZilla Server / ProFTPD / встроенные в NAS реализации?
   - **Варианты:** (a) все возвращают позитивный отклик и закрывают data-канал; (b) часть серверов игнорирует команду, и нужен жёсткий close на стороне клиента; (c) часть отвечает кодом ошибки, и завершение команды всё равно должно засчитываться как успех на нашей стороне.
   - **Нужно выяснить:** на стенде с двумя-тремя серверами проверить отклик, поведение data-канала, состояние клиента после прерывания.
   - **Статус:** Open.

2. **Размер сетевого read-буфера при ограниченном чтении.**
   - **Вопрос:** какой размер пакета достаточен, чтобы не приходить в сервер за лишним «хвостом» сверх лимита больше, чем на 1 буфер?
   - **Варианты:** маленький буфер (4 КБ) — гарантированно тонкий хвост, но больше системных вызовов; крупный буфер (16/32 КБ) — меньше вызовов, но возможен «перебор» в пределах одного чтения; адаптивный.
   - **Нужно выяснить:** что считается дешевле для текущего бюджета метаданных (64 КБ) — определить в тактической спеке по бенчмарку или прикинуть аналитически.
   - **Статус:** Open.

3. **Совместимость с диагностикой проблем сети.**
   - **Вопрос:** не маскирует ли штатное прерывание реальные сетевые сбои, которые сейчас всплывали как «ошибка чтения»?
   - **Варианты:** (a) прерывание выполняется только при достижении лимита, иначе путь прежний — не маскирует; (b) выполняется всегда, что меняет картину логов.
   - **Нужно выяснить:** утвердить инвариант «прерываем — только когда сами выбрали уйти раньше», чтобы логирование сетевых ошибок при обычном чтении оставалось как было.
   - **Статус:** Open.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Часть FTP-серверов игнорирует команду прерывания передачи и держит контрольный канал «занятым» | Средняя | Подтверждение команды повисает либо возвращает ошибку — операция читателя «теряет» байты | После прерывания работать в строгом таймауте; считать операцию успешной, если байты уже прочитаны; помечать клиента как требующего переподключения |
| Прерывание срабатывает позже, чем сервер успевает закрыть data-канал по своему таймауту | Низкая | Возвращаемся к исходной NPE-картине, но без шума благодаря уже сделанному узкому фиксу | Брать буфер достаточно мелким, чтобы цикл чтения завершался быстро; держать жёсткий read-timeout |
| Различие в обработке между постоянным и одноразовым клиентом приведёт к расхождению поведения | Средняя | Метаданные грузятся по-разному в зависимости от того, активен ли пул | Унифицировать логику ограниченного чтения в одной общей точке; параллельный регресс на обеих ветках |
| Изменение в общем сетевом коде задевает скачивание целиком (без лимита) | Низкая | Регрессия для пользовательских скачиваний | Жёстко разделить ветку «без лимита» от «с лимитом» в обёртке; не трогать ветку полного чтения; ручной регресс на крупном файле |
| Часть серверов отвечает на прерывание кодом, который библиотека считает ошибкой подтверждения команды | Средняя | Читатель получает «failure» при фактически собранных байтах | Тактическая спека должна явно определить: если буфер заполнен до лимита и прерывание клиентом инициировано, ошибочный код подтверждения трактуется как «успех с данными» |

## 8. Влияние на пользователя (docs/FEATURES)

Без изменений в docs/FEATURES. Это инфраструктурный фикс: пользователь не получает новой способности, существующие сценарии работают как раньше, но быстрее на крупных аудио-файлах с FTP. Функциональный лог получит запись `FIX` на этапе верификации (метаданные грузятся стабильнее, прежние шумные ошибки в логах исчезают на корне).

## 9. Архитектурные решения (ADR)

**ADR-1: Истинное ограниченное чтение вместо «прочитать всё и обрезать»**

- **Решение:** читать из входного потока ровно столько байт, сколько запросил вызывающий, и сообщать серверу о завершении передачи на стороне клиента.
- **Альтернативы:**
  1. Оставить как есть, ограничиться уже сделанным узким фиксом NPE — лечит лог, не лечит трафик и не уменьшает частоту обрывов.
  2. Перейти на FTP range-запросы (REST/SIZE) — корректнее по протоколу, но требует поддержки на сервере, иногда отсутствует у NAS-реализаций.
  3. Сделать абстрактный «range-провайдер» поверх SMB/SFTP/FTP — крупная архитектурная история, неоправданная под текущую задачу.
- **Почему:** прерывание передачи — встроенная и широко поддерживаемая процедура FTP, не требует серверной поддержки сверх стандарта, не меняет внешний контракт читателя, решает обе озвученные беды (трафик и таймауты) одним приёмом.

**ADR-2: Сохранение полного режима чтения нетронутым**

- **Решение:** ветка «без лимита» не меняется в части последовательности команд и буферизации.
- **Альтернативы:** унифицировать обе ветки через общий цикл с условным завершением — сэкономило бы строк, но втянуло бы риск регрессии в путь скачиваний.
- **Почему:** скачивания — самый чувствительный для пользователя путь FTP-слоя, регрессия здесь дороже, чем дублирование небольшого участка кода.

## 11. Критерии готовности (strategic-level)

1. На запрос «прочитать не более 64 КБ» из FTP-источника на крупный аудио-файл сеть фактически передаёт не более 64 КБ + один read-буфер. Проверяется по статистике передачи или по сетевому снифферу на стенде.
2. Латентность извлечения метаданных аудио по FTP перестаёт зависеть от размера файла — для одного и того же сервера на файле 5 МБ и 50 МБ результат должен укладываться в один и тот же бюджет времени с разбросом не больше, чем шум сети.
3. Подтверждение команды от сервера после ограниченного чтения возвращается успешно (или — в задокументированных серверных кейсах — трактуется как успех с уже собранными байтами) и не вызывает повторных переподключений в нормальных условиях.
4. Поведение операции скачивания без лимита остаётся побайтно прежним — сравнение хешей файла до и после правки на репрезентативной выборке.
5. Слой извлечения аудио-метаданных продолжает корректно извлекать поля для тех же файлов, что и до правки, без новых регрессий.
6. Логи сетевого слоя при ограниченном чтении не содержат стек-трейсов уровня ERROR на сценарии «сервер закрыл канал по таймауту» — за счёт самой профилактики, а не только за счёт ранее сделанного NPE-фикса.
