## 1. Проблема

Юнит-тестовый исходный набор `app_v2` не компилируется: несколько тест-файлов вызывают конструкторы, отставшие от текущих сигнатур кода. Одна группа строит капабилити-конфигурацию (data-класс без значений по умолчанию) с неполным набором полей; другая не передаёт обязательный параметр капабилити в конструкторы юзкейсов. Поскольку сборка тестов идёт целиком, эти отставшие файлы валят компиляцию всего набора - и тогда ни один юнит-тест в `app_v2` не запускается, включая исправные и новые.

Эффект для разработки: вся юнит-проверка модуля мертва - новый тест нельзя ни прогнать, ни получить per-class отчёт. Всплыло при попытке провалидировать тест-страж из связанного тикета: сам страж корректен, но запустить его невозможно из-за соседей.

---

## 2. Цели

1. Тестовый исходный набор `app_v2` снова компилируется целиком.
2. Юнит-тесты модуля снова запускаются и дают per-class отчёты.
3. Рост числа полей капабилити-конфигурации перестаёт ломать каждый тест-сайт разом.

**Non-goals:**

- Не переписываем сами тестируемые юзкейсы и не меняем их продакшн-сигнатуры.
- Не чиним падающие по содержанию (assertion) тесты, не относящиеся к компиляции - только восстановление сборки.
- Не вводим новые тест-фреймворки.

## 4. Контекст текущей архитектуры

Капабилити-конфигурация - это data-класс без значений по умолчанию, намеренно требующий явного указания каждого поля, чтобы пропуск поля ловился компилятором в продакшн-коде. Та же строгость бьёт по тестам: каждый тест, конструирующий конфигурацию напрямую, обязан перечислять все поля, и при росте класса все такие сайты отстают одновременно. Параллельно ряд юзкейсов получил обязательный параметр капабилити, а их тесты не были обновлены. Единой тестовой точки создания конфигурации нет, поэтому правка размазывается по всем сайтам.

---

## 5. Предлагаемый подход

Восстановить компиляцию, приведя отставшие тест-конструкторы к текущим сигнатурам, и убрать корень повторяемости - ввести единую тестовую фабрику капабилити-конфигурации со значениями по умолчанию, через которую тесты создают конфигурацию вместо прямого вызова конструктора. Тогда будущее добавление поля затрагивает только фабрику, а не каждый тест.

### 5.1 Основные столпы / модули

1. **Тестовая фабрика капабилити-конфигурации** - единая точка создания конфигурации в тестах со значениями по умолчанию и точечным переопределением нужных полей. Цель: новое поле не ломает тест-сайты.
2. **Приведение отставших тест-конструкторов** - обновить вызовы, не передающие обязательные параметры (капабилити в юзкейсы, неполный набор полей конфигурации), к текущим сигнатурам.

### 5.2 Потоки данных и событий

Тест → тестовая фабрика капабилити (дефолты + переопределения) → конструирование юзкейса/субъекта с полным набором аргументов → запуск проверки.

### 5.3 Точки расширяемости

- Единая тестовая фабрика - место, куда добавляется значение по умолчанию для любого нового поля конфигурации; тест-сайты не правятся.
- Подход переиспользуем для других строго-обязательных конструкторов, если они начнут отставать в тестах.

## 9. Архитектурные решения (ADR)

**ADR-1: Единая тестовая фабрика капабилити-конфигурации вместо точечной правки каждого сайта.**

- **Решение:** ввести фабрику с дефолтами, перевести тест-сайты на неё; продакшн-конструктор остаётся строгим (без дефолтов).
- **Альтернативы:** просто дописать недостающие аргументы в каждом тесте; добавить дефолты в сам продакшн data-класс.
- **Почему:** точечная правка повторится при следующем поле; дефолты в продакшн-классе ослабят компиляторную защиту от пропуска поля в реальном коде. Фабрика даёт удобство тестам, не жертвуя строгостью продакшна.
