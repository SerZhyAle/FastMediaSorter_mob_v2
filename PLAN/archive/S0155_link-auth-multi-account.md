# Стратегическая спецификация: S0155 — Несколько аккаунтов на один хост для скачивания по ссылке

**Ticket:** S0155
**Status:** BlockNeedUserTest
**Priority:** 60
**Date:** 2026-05-11
**Tier:** 3 — Moderate (ad-hoc)
**Roadmap entry:** Ad-hoc — запрос владельца 2026-05-11 в ходе обсуждения S0151 §6.4 (логи `logs/fastmediasorter_20260511_005409.log`, `logs/fastmediasorter_20260511_032209.log`)

> **Scope:** STRATEGIC. Цели, ограничения, открытые вопросы. Без имён классов, путей, лимитов строк, миграций Room, модулей Hilt.

---

## 1. Проблема

Скачивание по ссылке (S0116/S0144/S0151) сейчас хранит максимум одну авторизованную сессию на хост: пользователь вошёл в Instagram как `@account1` → сессия сохранена; вход в тот же Instagram под `@account2` либо невозможен в рамках UX, либо затирает первую сессию. На практике у пользователя для одной и той же соцсети встречаются несколько аккаунтов (личный / рабочий / тестовый) — и приложение перед скачиванием не спрашивает, под каким из них пробовать достать контент, и какая сессия «устарела» (если устарела) — про какой именно аккаунт. Когда сессия молча применяется к ссылке, для которой нужен другой аккаунт, или когда сессия истекла и предлагается «войти заново», пользователь не понимает, про какой аккаунт идёт речь — и видит навязчивые повторные предложения входа без контекста (полевой инцидент по S0151).

---

## 2. Цели

1. Для одного хоста (например, `instagram.com`, `threads.com`, `threads.net`) можно хранить и использовать несколько авторизованных сессий, помеченных идентификатором аккаунта (имя пользователя / отображаемое имя, как площадка его называет).
2. Перед скачиванием по ссылке на хост, для которого сохранено больше одного аккаунта, приложение спрашивает у пользователя, под каким аккаунтом пробовать. Если аккаунт для хоста ровно один — спрашивать не надо, используется он.
3. Когда извлечение контента не удалось и нужно (или может быть нужно) обновить вход — диалог явно называет аккаунт («вход для `@user` устарел / недостаточен — войти заново под этим аккаунтом?»), а не показывает безличное «войти заново».
4. Пользователь может добавить второй (третий, ..) аккаунт для уже известного хоста — через явный диалог в Настройках («управление авторизациями» / тот же раздел, что и существующее управление сессиями S0116/S0144).
5. Можно явно удалить / переименовать / обновить отдельный аккаунт (вход заново именно под ним) — операции применяются только к выбранному аккаунту, не затирают другие на том же хосте.
6. Логика выбора аккаунта прозрачна в логе: видно, какой аккаунт выбран для конкретной попытки скачивания и почему (явный выбор пользователя / единственный сохранённый / последний использованный — см. §6).

**Non-goals:**

- Не делать кросс-аккаунтную слияние сессий, не строить унифицированный «провайдер идентичности» поверх соцсетей — каждый аккаунт хранится отдельной записью с собственными cookie/сессией.
- Не пытаться автоматически определять, какому аккаунту принадлежит расшаренная ссылка (анализ профиля автора поста и т.п.) на этой итерации — выбор аккаунта остаётся за пользователем (с разумным дефолтом).
- Не вводить «корпоративный» SSO / семейные аккаунты / разделение по профилям Android.
- Не реализовывать обмен / экспорт сессий между устройствами.
- Не трогать flavor'ы, где скачивание по ссылке отсутствует.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Желательно, чтобы при первом успешном входе для хоста, у которого ещё не было ни одного аккаунта, новая сессия автоматически становилась дефолтным аккаунтом для этого хоста (никакой выбор пока не нужен).
2. Желательно, чтобы при добавлении второго и последующих аккаунтов пользователь явно понимал, что добавляется именно ещё один аккаунт, а не «замена» текущего — текст диалога / пункта в Настройках должен это чётко сообщать.
3. Желательно дефолтить выбор аккаунта для шаринга на «последний успешно использованный для этого хоста», но дать возможность сменить аккаунт в момент диалога выбора без выхода в Настройки.
4. Желательно, чтобы предложение «войти заново» (когда сессия выбранного аккаунта дала «только превью» или иную неудачу) затрагивало только этот аккаунт — не предлагало переключиться на другой и не затирало другие сессии.
5. Желательно, чтобы при добавлении / удалении / переименовании аккаунта в Настройках UI оставался узнаваемым — те же визуальные паттерны, что и в существующем «управлении авторизациями» S0144 (не плодить второй стиль списка).

### 3.2 Жёсткие ограничения

- **Flavor:** все варианты, где доступна фича скачивания по ссылке (та же область, что и S0116/S0144). На сборках без неё поведение не появляется.
- **API level:** без API-специфики; работа встроенного браузера и сохранение cookie — на минимально поддерживаемом уровне.
- **Wear OS:** не затрагивается.
- **Производительность:** диалог выбора аккаунта не должен задерживать скачивание ощутимо; для одно-аккаунтного хоста — диалог не появляется, лишних задержек нет.
- **Совместимость данных:** существующие сохранённые сессии (с одной записью на хост, без идентификатора аккаунта) должны быть прозрачно мигрированы в формат «аккаунт по умолчанию для этого хоста» — без потери авторизации и без принудительного повторного входа.
- **Безопасность:** идентификатор аккаунта (имя пользователя площадки) хранится рядом с зашифрованными cookie тем же механизмом, что используется сейчас для сессий — без отдельной открытой записи в shared prefs / БД.
- **Локализация:** EN/RU/UK — обязательно для всех новых строк (диалог выбора аккаунта, диалог добавления второго аккаунта в Настройках, формулировка «вход для `@user` устарел»).
- **Доступность:** диалог выбора аккаунта читается TalkBack; стандартные touch target'ы; список аккаунтов в Настройках поддерживает крупный шрифт.
- **Тон сообщений:** новые строки проходят чек-лист тона из `docs/COMMUNICATION_POLICY.md` (§6) перед интеграцией — спокойное, нейтральное объяснение, без алармовых формулировок.

## 4. Контекст текущей архитектуры

Скачивание по ссылке имеет конвейер стратегий извлечения (прямой файл / HTML-разбор / динамический разбор во встроенном браузере / стриминговый манифест), хранилище зашифрованных сессий по хосту и встроенный браузер для входа (S0116/S0144). Сессии адресуются ключом «хост» — без понятия «аккаунт»; для одного хоста существует ровно одна актуальная запись, и любой повторный вход её перезаписывает. В Настройках уже есть раздел управления авторизациями (S0144), но он оперирует записями уровня «хост», а не «аккаунт». Реактивное предложение входа (S0144 + S0151) показывает «войти / войти заново» без контекста о том, под каким именно аккаунтом — потому что такого понятия в модели сейчас нет.

## 5. Предлагаемый подход

Ввести понятие «аккаунт» как ключ адресации сессий: вместо «одна сессия на хост» — «N аккаунтов на хост, у каждого — своя сохранённая сессия». При шаринге ссылки на хост, для которого сохранено больше одного аккаунта, перед запуском конвейера извлечения показывать диалог выбора аккаунта (с дефолтом на «последний успешно использованный»). Реактивное предложение «войти заново» при неудаче извлечения адресуется конкретному аккаунту и объясняет, почему предлагается войти именно под ним. В Настройках раздел управления авторизациями расширяется до управления списком аккаунтов на хост (добавить второй / удалить отдельный / войти заново под отдельным).

### 5.1 Основные столпы / модули

#### A. Модель «аккаунт» как первичный ключ сессии

- Запись сессии адресуется парой `(хост, идентификатор аккаунта)`; идентификатор аккаунта — то, как площадка называет пользователя (`@username` / displayName), извлекается из самой сессии после успешного входа.
- Существующие записи «одна на хост» прозрачно мигрируются: становятся первым аккаунтом для своего хоста с дефолтным идентификатором (например, площадка-специфичная попытка определить имя пользователя в момент миграции; иначе — placeholder, который пользователь может переименовать в Настройках).
- Каждая запись несёт минимум: идентификатор аккаунта, хост, cookie/сессия, отметка времени последнего успешного использования.

#### B. Выбор аккаунта перед скачиванием

- Хост, для которого сохранено 0 аккаунтов → текущее поведение (предложение войти, как в S0144).
- Хост, для которого сохранён ровно 1 аккаунт → использовать его без диалога; в логе зафиксировать «единственный сохранённый».
- Хост, для которого сохранено ≥2 аккаунтов → показать диалог выбора аккаунта с дефолтом на «последний успешно использованный для этого хоста»; пользователь может выбрать другого или отменить.
- В диалоге явно видно, что речь идёт про конкретный хост и про список аккаунтов именно для него.

#### C. Поаккаунтный re-auth и сообщения

- Когда извлечение реального медиа не удалось с выбранным аккаунтом (исход S0151 «только превью» или иная неудача, требующая входа), предложение «войти заново» называет аккаунт: «Вход для `@user` мог устареть — войти заново под этим аккаунтом?».
- Успешный повторный вход обновляет именно эту запись (по паре `(хост, аккаунт)`), не трогая остальные аккаунты того же хоста.
- Отказ — запоминается с разрезом по аккаунту (а не по хосту целиком), чтобы предложение для другого аккаунта на том же хосте не подавлялось.

#### D. Управление аккаунтами в Настройках

- Раздел «авторизации» (тот же, что в S0144) расширяется: для каждого хоста — раскрывающийся список аккаунтов; на каждый аккаунт операции «войти заново», «удалить», «переименовать»; на каждый хост операция «добавить ещё один аккаунт» (запускает встроенный браузер на нужном адресе входа; после успешного входа — новая запись).
- Текст пункта «добавить ещё один аккаунт» явно сообщает, что добавляется новый аккаунт, а не замена существующего.

#### E. Диагностика

- В лог при шаринге пишется: какой хост, сколько аккаунтов сохранено, какой выбран (по правилу «единственный» / «дефолт по последнему успеху» / «выбор пользователя»), исход попытки извлечения для этого аккаунта.

### 5.2 Потоки данных и событий

- Шаринг ссылки → распознан хост → запрос списка аккаунтов для хоста → выбор аккаунта (автоматический или через диалог) → конвейер извлечения с применением сессии выбранного аккаунта → (успех / неудача-«только превью» / иная неудача) → проекция исхода (с указанием аккаунта в любом UX-сообщении).
- Неудача-«только превью» (или иная необходимость входа) → реактивное предложение «войти заново под `@user`» → встроенный браузер на адресе входа площадки → новая сессия обновляет запись `(хост, @user)`.
- Настройки → раздел авторизаций → список хостов с раскрывающимися списками аккаунтов → операции «войти заново» / «удалить» / «переименовать» на аккаунт; операция «добавить аккаунт» на хост → встроенный браузер → новая запись добавляется к списку.

### 5.3 Точки расширяемости

- Идентификатор аккаунта берётся площадка-специфично (Instagram отдаёт `@username` иначе, чем условный X) — путь извлечения вынесен в отдельную ответственность, расширяемую новыми площадками.
- Правила «дефолт выбранного аккаунта» (последний успешный / явный пин / по типу контента ссылки) оставлены открытыми к расширению.
- Если в будущем понадобится связать аккаунт с конкретной целевой папкой загрузки или иной политикой — модель аккаунта это позволит (поля можно добавлять без миграции в смысле смены ключа).

## 6. Открытые вопросы / Research items

1. **Как извлекать идентификатор аккаунта из сессии для Instagram/Threads**
   - **Вопрос:** доступно ли имя пользователя сразу после успешного входа через встроенный браузер (например, из URL после редиректа, из cookie, из вызова конкретного эндпоинта профиля) — или придётся отдельно дёргать запрос «кто я».
   - **Варианты:** (а) разобрать URL/cookie сразу после успешного входа; (б) запросить эндпоинт «текущий пользователь» площадки после входа; (в) показать пользователю поле «как назвать этот аккаунт» и не пытаться угадать.
   - **Нужно выяснить:** какой путь самый устойчивый и не хрупкий; решение в тактической спеке.
   - **Статус:** Open.

2. **Какой дефолт выбора аккаунта при шаринге**
   - **Вопрос:** последний успешно использованный для этого хоста, или последний добавленный, или «всегда показывать диалог при ≥2».
   - **Варианты:** (а) последний успешно использованный; (б) последний добавленный; (в) всегда показывать диалог.
   - **Нужно выяснить:** что меньше раздражает; решение в тактической спеке.
   - **Статус:** Open.

3. **Запоминание «отказа» с разрезом по аккаунту**
   - **Вопрос:** «отказ от входа», который S0144 запоминает по хосту, после введения аккаунтов должен запоминаться по `(хост, аккаунт)` или по хосту целиком.
   - **Варианты:** (а) по `(хост, аккаунт)` — точнее, но больше состояния; (б) по хосту — проще, но менее точно.
   - **Нужно выяснить:** что лучше согласуется с UX «не навязывать вход»; решение в тактической спеке.
   - **Статус:** Open.

4. **Что делать с placeholder-идентификатором мигрированной записи**
   - **Вопрос:** если для существующей записи не удаётся автоматически определить имя пользователя при миграции — какой placeholder показывать и насколько настойчиво просить переименовать.
   - **Варианты:** (а) placeholder вида «Account 1» с тихой подсказкой переименовать в Настройках; (б) принудительный диалог переименования при первом шаринге; (в) дёрнуть «кто я» в момент миграции и упасть назад на placeholder только при неудаче.
   - **Нужно выяснить:** баланс между «не доставать пользователя» и «осмысленные имена в списке»; решение в тактической спеке.
   - **Статус:** Open.

## 8. Влияние на пользователя (docs/FEATURES)

`docs/FEATURES.md` (+ `_RU`, `_UK`): для одного сайта (Instagram/Threads и пр.) можно хранить несколько аккаунтов; перед скачиванием по ссылке приложение спрашивает, под каким аккаунтом пробовать (если их больше одного), и при необходимости предлагает войти заново под конкретным аккаунтом — с явным объяснением, что устарела сессия именно этого аккаунта. Добавить второй аккаунт можно из раздела «авторизации» в Настройках.

## 9. Архитектурные решения (ADR)

**ADR-1: ключ адресации сессии — `(хост, идентификатор аккаунта)`**

- **Решение:** хранилище сессий переходит с ключа «хост» на ключ `(хост, аккаунт)`; существующие записи мигрируются как первый аккаунт хоста.
- **Альтернативы:** оставить ключ «хост» и хранить «список альтернативных сессий» как поле записи; параллельное хранилище аккаунтов поверх существующего.
- **Почему:** первый вариант минимально инвазивен по чтениям («какие аккаунты у хоста?» — естественный индексный запрос); прятать аккаунты в поле приведёт к разрастанию ad-hoc логики над одним хостом.

**ADR-2: выбор аккаунта при шаринге — только когда ≥2**

- **Решение:** диалог выбора аккаунта показывается строго при наличии двух и более сохранённых аккаунтов для хоста; при 0 или 1 — без диалога.
- **Альтернативы:** всегда показывать диалог; никогда не показывать (использовать последний).
- **Почему:** одно-аккаунтный кейс — самый частый, лишний диалог раздражает; «никогда» — теряет смысл фичи.

**ADR-3: поаккаунтные re-auth и сообщения**

- **Решение:** все формулировки предложения «войти заново» и реактивные потоки re-auth адресуются конкретному аккаунту (`@user`), даже если сохранён всего один.
- **Альтернативы:** называть аккаунт только при ≥2; не называть никогда (как сейчас).
- **Почему:** даже при единственном аккаунте явное упоминание имени снимает основную причину раздражения из S0151 (повторное предложение без контекста); унифицированный текст проще локализовать.

## 11. Критерии готовности (strategic-level)

1. Для одного хоста сохранены два разных аккаунта; шаринг ссылки на этот хост показывает диалог выбора аккаунта (дефолт — на «последний успешно использованный»).
2. Шаринг ссылки на хост с единственным сохранённым аккаунтом не показывает лишнего диалога — используется этот аккаунт.
3. Когда извлечение реального медиа не удалось для выбранного аккаунта, предложение «войти заново» явно называет аккаунт (`@user`) и предлагает обновить именно его сессию; другие аккаунты этого хоста не затронуты.
4. В Настройках можно добавить второй (и т.д.) аккаунт для уже известного хоста через явный диалог; можно удалить / переименовать / войти заново под отдельным аккаунтом.
5. Существующие сохранённые сессии после обновления приложения продолжают работать без принудительного повторного входа — мигрированы как «аккаунт по умолчанию» для своего хоста.
6. В логе шаринга видно, для какого хоста сколько аккаунтов было сохранено и какой выбран и почему (явный пользовательский выбор / единственный / последний успешный).
