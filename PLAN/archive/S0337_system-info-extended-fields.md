## 1. Проблема

Базовый диалог «Сведения о системе» (S0335) показывает короткую сводку, но для диагностики и поддержки этого мало. Нужен расширенный набор технических данных об устройстве и его текущем состоянии, а также два простых бенчмарка — скорость оперативной памяти и скорость встроенного накопителя. Всё это собирается строго без опасных разрешений и без Google Play Services: владелец не хочет «привлекать внимание Google», то есть избегать любых постоянных идентификаторов, опасных разрешений и зависимостей от GMS.

---

## 2. Цели

1. В существующий диалог «Сведения о системе» добавляется расширенная сводка, сгруппированная по разделам.
2. Добавляется бенчмарк скорости оперативной памяти (пропускная способность простой операции в памяти).
3. Добавляется бенчмарк скорости встроенного накопителя (запись и чтение во временный приватный каталог приложения).
4. Показываются данные о текущей подключённой сети/сетях: тип транспорта (Wi-Fi / сотовая / Ethernet / нет), является ли соединение лимитированным (metered), активен ли VPN, включён ли режим полёта.
5. Показывается IP-адрес локального сетевого интерфейса.
6. Показывается время работы устройства с момента загрузки.
7. Добавляются все безопасные, не требующие разрешений поля из ресёрча: число ядер CPU, поддерживаемые ABI, SoC (на поддерживающих API), версия ядра, версия GLES; полный блок батареи (уровень, состояние зарядки, тип подключения, здоровье, температура, напряжение, технология); блок дисплея (частота обновления, HDR, тёмная тема, масштаб шрифта, ориентация, smallest width, число дисплеев); список локалей, 24-часовой формат; boot count; тома хранилища; источник установки; время первой установки и последнего обновления; security patch level; build fingerprint / tags / type; максимальная куча процесса.
8. Бенчмарки и сбор данных не блокируют главный поток; до получения результата UI отзывчив.

**Non-goals:**

- Не собираются постоянные идентификаторы: IMEI, серийный номер, MAC, ANDROID_ID, рекламный ID.
- Не запрашиваются опасные разрешения и не используются аккаунты, телефон, локация, контакты, состояние Bluetooth-адаптера (требует runtime-разрешения с Android 12).
- Не добавляются зависимости от Google Play Services.
- Не вводится профессиональный профайлинг или промышленный бенчмарк — только грубая оценка «порядка величины».
- Не добавляется отдельный экран; используется тот же диалог, что у S0335.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Сводка остаётся одним прокручиваемым, копируемым и отправляемым текстом (как в S0335).
2. Поля сгруппированы по понятным разделам (Hardware, Battery, Display, Network, Storage, App, Time и т.д.).
3. Бенчмарки выдают человекочитаемый результат (например, МБ/с) и помечены как приблизительные.
4. Каждое поле деградирует мягко: на старых API или при недоступности источника показывается «unknown», а не пропадает раздел.

### 3.2 Жёсткие ограничения

- **Flavor:** все варианты сборки (`standard`, `lite`, `photos`, `legacy`). Логика в общем коде, без flavor-специфичного source set; реализация следует `dev/FLAVOR_DEVELOPMENT_RULES.md`, если где-то понадобится разветвление по flavor (не ожидается — данные одинаковы для всех).
- **API level:** `minSdk 23` (`legacy`) и `26` (остальные); поля, доступные только с API 24/26/31, гейтятся по уровню и на более старых дают «unknown».
- **Wear OS:** не затрагивается.
- **Производительность:** сбор сводки и оба бенчмарка выполняются вне главного потока; бенчмарки ограничены по времени/объёму, чтобы открытие диалога не подвисало и не грелась батарея.
- **Совместимость данных:** persistent-хранилище и миграции не затрагиваются; бенчмарк накопителя пишет только во временный приватный каталог и удаляет за собой.
- **Приватность:** запрещены постоянные идентификаторы и опасные разрешения (см. Non-goals); сетевые поля используют только уже объявленные NORMAL-разрешения `ACCESS_NETWORK_STATE` / `ACCESS_WIFI_STATE`.
- **Локализация:** метка кнопки и заголовки разделов/диалога — EN/RU/UK; язык подписей полей в теле уточняется в §6.
- **Доступность:** диалог наследует доступность S0335 (скролл, начальный фокус, TalkBack).
- **Коммуникация:** любые новые пользовательские строки соответствуют `docs/COMMUNICATION_POLICY.md` (чек-лист тона §6 политики — обязательный гейт).

### 3.3 Owner inputs (Approval gate)

Каждое поле ниже содержит конкретное значение, чтобы спека могла перейти Draft → Approved. Проверка: `pwsh -NoProfile -File scripts/spec_catalog/check-owner-inputs.ps1 -Id S0337`.

- **Flavor scope:** все флейворы; общий код в `src/main`, без flavor-специфичного source set — данные не зависят от варианта сборки; отличия только в гейтинге по API level.
- **API level constraints:** поддержать `minSdk 23` (legacy) и `26`; поля API 24/26/31 (boot count, тома хранилища, SoC, HDR, wide gamut) гейтятся, на более старых API — «unknown».
- **Performance budget:** бенчмарки и сбор — вне главного потока; бенчмарк памяти и накопителя ограничены коротким бюджетом времени/объёма (конкретные пороги — §6), временные файлы удаляются.
- **UI placement contract:** результат показывается в том же прокручиваемом диалоге «Сведения о системе» (S0335), открываемом кнопкой «О системе»; новых экранов и кнопок не вводится.
- **Accessibility:** наследуется от диалога S0335 (скролл, начальный фокус, копирование/отправка); новых интерактивных контролов нет.
- **Communication policy:** заголовки разделов и любые статусы бенчмарка проходят чек-лист тона §6 политики; тело — технические данные.
- **Localization:** метка/заголовки и подписи разделов/полей тела — EN/RU/UK (решение §6.4).
- **Validation level:** целевой вариант сборки компилируется; затронутые юнит-тесты проходят; сбор полей и парсинг результатов бенчмарка покрываются юнит-тестами там, где это детерминировано.

## 4. Контекст текущей архитектуры

Диалог «Сведения о системе» и его наполнение появились в S0335: отдельная роль уровня применения собирает человекочитаемую строку из источников device-фактов и передаёт её в существующий прокручиваемый диалог (скролл + копирование + отправка). Кнопка живёт на вкладке Common рядом с «Разрешения и доступ».

Сейчас эта роль собирает только базовый набор и работает синхронно. Расширение требует: (а) значительно большего числа источников данных с гейтингом по API; (б) двух активных измерений (бенчмарков), которые нельзя выполнять на главном потоке; (в) аккуратного разделения «приватных» источников, чтобы случайно не подключить идентификатор или опасное разрешение. Поэтому ответственность сбора нужно сделать асинхронной и расширяемой по разделам.

---

## 5. Предлагаемый подход

Расширить роль сбора сводки до асинхронной, разбитой на независимые разделы (Hardware, Battery, Display, Network, Storage, App, System, Time, Benchmarks). Каждый раздел — самостоятельный поставщик строк с мягкой деградацией. Бенчмарки — отдельные короткие измерения, запускаемые вне главного потока и форматируемые в человекочитаемый результат. UI не меняется: тот же диалог получает готовый текст.

### 5.1 Основные столпы / модули

- **Асинхронный сбор сводки.** Сбор всех разделов выполняется вне главного потока; пока идёт сбор/бенчмарк, диалог не блокирует UI. Каждый раздел изолирован: сбой или недоступность одного не ломает остальные.
- **Поставщики разделов.** Логические группы полей (Hardware / Battery / Display / Network / Storage / App / System / Time) как отдельные единицы, каждая со своими источниками и гейтингом по API.
- **Бенчмарк памяти.** Грубая оценка пропускной способности операций в памяти за ограниченный бюджет; результат — человекочитаемая величина с пометкой «приблизительно».
- **Бенчмарк накопителя.** Запись и чтение временного блока данных в приватный каталог приложения с измерением скорости; временные данные удаляются; результат — человекочитаемая величина с пометкой «приблизительно».
- **Сетевой раздел.** Тип транспорта, metered, VPN, режим полёта, локальный IP — только через уже объявленные NORMAL-разрешения и framework-API, без идентификаторов.
- **Приватный фильтр.** Явный запрет на источники из списка DO NOT COLLECT, зафиксированный как требование к каждому поставщику.

### 5.2 Потоки данных и событий

Открытие диалога → запуск асинхронного сбора всех разделов и бенчмарков вне главного потока → агрегирование в один сгруппированный текст → передача готового текста в существующий диалог → пользователь листает, копирует, отправляет.

### 5.3 Точки расширяемости

- Добавление нового раздела или поля — локальное изменение одного поставщика, без правок UI.
- Бенчмарки оформлены как отдельные измерения, чтобы можно было добавить новые (например, скорость декодирования) без изменения сборщика.
- Гейтинг по API инкапсулирован в поставщиках, чтобы поднятие minSdk упрощало, а не ломало код.

## 6. Открытые вопросы / Research items

1. **Методика и бюджет бенчмарка памяти**
   - **Вопрос:** какой объём/число итераций и какой лимит времени дают стабильную, но быструю оценку, не грея устройство?
   - **Варианты:** фиксированный буфер с N проходов копирования/суммирования; ограничение по времени (например, ≤ доли секунды).
   - **Нужно выяснить:** что даёт повторяемый результат на слабых и мощных устройствах без заметной задержки.
   - **Статус:** Open (требует подбора на устройстве).

2. **Методика и бюджет бенчмарка накопителя**
   - **Вопрос:** какой размер временного файла и схема записи/чтения (sequential, sync/flush) корректно отражают скорость, не насилуя флеш-память?
   - **Варианты:** один последовательный блок с принудительным сбросом на диск; ограничение по размеру и времени.
   - **Нужно выяснить:** размер блока и нужно ли обходить кэш страниц для честного чтения.
   - **Статус:** Open (требует подбора на устройстве).

3. **Запуск бенчмарков: автоматически или по кнопке**
   - **Решение владельца (2026-06-03):** бенчмарки запускаются автоматически при открытии диалога, вне главного потока, с индикатором выполнения; результат подставляется в текст по готовности.
   - **Статус:** Resolved.

4. **Язык подписей полей в теле**
   - **Решение владельца (2026-06-03):** подписи разделов и полей локализуются EN/RU/UK (в отличие от фиксированного английского в S0335).
   - **Статус:** Resolved.

5. **Объём сетевого раздела и приватность IP**
   - **Решение владельца (2026-06-03):** показывать IP активного интерфейса (а при нескольких активных — перечнем); локальный IP включается и в копируемый, и в отправляемый текст (следствие решения по §6.6 «включить полностью»).
   - **Статус:** Resolved.

6. **Чувствительные, но безопасные по разрешениям поля (имя устройства, источник установки, метод ввода)**
   - **Решение владельца (2026-06-03):** включить полностью, в том числе в копируемый и отправляемый текст. Все эти поля читаются без разрешений и без GMS; постоянные идентификаторы по-прежнему запрещены (Non-goals).
   - **Статус:** Resolved.

7. **Бюджет и методика бенчмарков (память и накопитель)**
   - **Вопрос:** конкретный объём буфера/файла, число проходов и лимит времени для повторяемого, но быстрого результата без нагрева.
   - **Решение:** на этапе реализации взять консервативные дефолты (малый буфер/файл, жёсткий лимит времени, временный файл в приватном каталоге с удалением); точные пороги подобрать на устройстве.
   - **Статус:** Open (не блокирует фазирование; подбор порогов — на устройстве, владелец разрешил продолжать).

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Бенчмарк на главном потоке или слишком долгий | Средняя | Подвисание открытия диалога, нагрев | Вынос вне главного потока, жёсткий бюджет времени/объёма |
| Бенчмарк накопителя изнашивает флеш или оставляет мусор | Низкая | Лишние записи, занятое место | Малый временный файл в приватном каталоге, гарантированное удаление |
| Случайное подключение идентификатора или опасного разрешения | Средняя | Нарушение приватности, претензии магазина | Явный список DO NOT COLLECT как требование к каждому поставщику; ревью разрешений |
| Рост и фрагментация сборщика при ~40 полях | Средняя | Нарушение лимита размера файла | Разбиение на изолированные поставщики разделов |
| Нестабильные результаты бенчмарка вводят в заблуждение | Средняя | Ложные выводы при поддержке | Явная пометка «приблизительно», усреднение проходов |
| Поля API 24/26/31 на legacy (API 23) | Низкая | Пустые/ошибочные значения | Гейтинг по API с мягким «unknown» |

## 9. Архитектурные решения (ADR)

**ADR-1: Асинхронный сбор по изолированным разделам**

- **Решение:** сделать сбор сводки асинхронным и разбить на независимые поставщики разделов.
- **Альтернативы:** оставить один синхронный сборщик и дописывать поля в него.
- **Почему:** бенчмарки нельзя выполнять на главном потоке; ~40 полей в одном методе нарушат лимит размера и усложнят гейтинг по API; изоляция даёт мягкую деградацию.

**ADR-2: Бенчмарки — грубая оценка, не профайлинг**

- **Решение:** короткие измерения с жёстким бюджетом и пометкой «приблизительно».
- **Альтернативы:** полноценный микробенчмарк-фреймворк.
- **Почему:** цель — быстрая диагностика в баг-репорте, а не точные цифры; точность не оправдывает задержку и сложность.

**ADR-3: Приватность как явное требование**

- **Решение:** зафиксировать список DO NOT COLLECT и принцип «без опасных разрешений и без GMS» как требование к каждому поставщику.
- **Альтернативы:** оставить на усмотрение реализации.
- **Почему:** легко случайно подключить идентификатор; это прямой риск приватности и претензий магазина.

## 11. Критерии готовности (strategic-level)

1. В диалоге «Сведения о системе» видны новые разделы: Hardware, Battery, Display, Network, Storage, App/System, Time — заполненные доступными значениями.
2. Показан результат бенчмарка памяти и бенчмарка накопителя в человекочитаемом виде с пометкой о приблизительности.
3. Показаны тип сети/сетей, metered, VPN, режим полёта и локальный IP-адрес.
4. Показано время работы устройства с момента загрузки.
5. Открытие диалога и работа бенчмарков не вызывают подвисания UI.
6. В сводке нет ни одного запрещённого идентификатора (IMEI, серийный номер, MAC, ANDROID_ID, рекламный ID) и не запрашивается ни одно опасное разрешение.
7. На устройстве с API 23 отсутствующие поля показываются как «unknown», разделы не пропадают.
8. Новые пользовательские строки локализованы EN/RU/UK.
