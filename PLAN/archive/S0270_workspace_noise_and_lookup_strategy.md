## 1. Проблема

Агентский поиск по репозиторию работает на двух фронтах одновременно — и оба сейчас задают лишнюю стоимость каждой задаче.

Первый фронт — широкое перечисление файлов. `rg --files` без исключений возвращает около 9 251 файла; с исключениями `**/node_modules/**`, `**/build/**`, `**/.gradle/**` — около 2 633. Разница в 3.5× — это шум, через который проходит каждый агентский запрос и каждый watcher. Источники шума на сегодняшний день: `scripts/mcp/**/node_modules`, `temp/` (≈8 320 файлов, ≈2.2 GB), `DOWNLOADS/` (≈2.1 GB), `.venv/` (≈1 285 файлов), `logs/`, `.kotlin/`. Текущий `.vscode/settings.json` фильтрует `.gradle/`, `build/`, `.idea/`, `V1/`, `v2_6/`, `spec_v2/`, но не закрывает перечисленные выше тяжёлые каталоги. Default-паттерн исключений для `rg` нигде не задокументирован — каждый агент при необходимости собирает свой набор.

Второй фронт — правило поиска символов и файлов. Раздел "Research Order" в `CLAUDE.md` сейчас сформулирован как универсальное "catalog-first" и явно запрещает `Grep`/`Glob`/`find` для поиска Kotlin-классов. Измерения: каталог-запрос ≈423 мс, `rg` по точному имени ≈44 мс — порядок величины. Правило корректно для семантических вопросов (кто инжектит тип, у кого какие побочные эффекты, какая роль и статус, кто кандидат на декомпозицию, кто владеет фичей кросс-файлово) и переусложнено для точных совпадений (точное имя класса, имя файла, токен, ключ ресурса, тег лога, строковой литерал). В обоих случаях агент обязан проходить через `query.ps1` и платить за это PowerShell cold start и поверх него — за чтение всего `.jsonl`-индекса целиком, даже когда нужен один класс. Прямое чтение `dev/CATALOG/<module>.jsonl` для узких лукапов сейчас явно не благословлено — текст подталкивает к шеллу.

Обе подпроблемы — про точность поиска и про одну и ту же поверхность конфигурации: `.vscode/settings.json`, блок "Research Order" в `CLAUDE.md`, гайд по каталогу в `dev/CATALOG/README.md`. Поэтому собраны в один тикет.

Проверка `.vscode/settings.json` на 2026-05-20 подтверждает, что тяжёлые рабочие каталоги по-прежнему не исключены из `files.exclude`, `search.exclude` и `files.watcherExclude`: сейчас там зафиксированы только базовые `build` / `.gradle` / `.idea` и исторические read-only зоны.

## 2. Цели

1. После сохранения настроек воркспейса широкое перечисление файлов в VS Code (поиск, проводник, watcher) и в `rg` по умолчанию даёт результат сопоставимый с целевыми ≈2 633 файлами вместо текущих ≈9 251. Тяжёлые каталоги (`node_modules`, `temp`, `DOWNLOADS`, `.venv`, `logs`, `.kotlin`) перестают попадать в выдачу без явного opt-in.
2. Документирован один источник правды для default-исключений `rg`, которым агенты пользуются в работе. Список синхронизирован с `.vscode/settings.json` — поиск через VS Code и поиск через `rg` дают согласованную выборку.
3. Правило "catalog-first" из `CLAUDE.md` раздела "Research Order" переформулировано: каталог — для семантических вопросов; `rg` (или прямое чтение каталога) — для точных совпадений. Граница между двумя путями однозначна.
4. Прямое чтение `dev/CATALOG/<module>.jsonl` (один запрос — одна строка) для узких лукапов класса/файла официально разрешено и описано в `dev/CATALOG/README.md` как лёгкая альтернатива `query.ps1` — без шелл-вызова.
5. Запреты, которые остаются в силе (например, "не использовать `find` вместо каталога для семантических вопросов"), сохранены и переформулированы так, чтобы не запрещать `rg` на точных лукапах.
6. Подсветка изменений на стороне пользователя: ни одна правка не затрагивает поведение приложения, продакшен-конфигурации, build-системы, миграций, ресурсов или строк.

**Non-goals:**

- Не пересматривается набор скриптов в `dev/CATALOG/scripts/` (схема, формат полей, контракт `set.ps1`/`scan.ps1`/`render.ps1`).
- Не вводится новая MCP-точка для поиска по знаниям репозитория — это отдельная инициатива (S0272).
- Не меняется поведение `scripts/catalog_sync.ps1` и других build/post-change-обёрток.
- Не удаляются и не перемещаются содержательные тяжёлые каталоги (`temp/`, `DOWNLOADS/`, `.venv/`) — фильтруется только их видимость в search/watcher.
- Не вводится автоматический guard, проверяющий синхронность `.vscode/settings.json` и default-паттерна `rg` — синхронизация остаётся ручной (см. §6).
- Не пересматривается общий стиль "Research Order" — порядок остальных шагов (PROJECT_OPERATIONS_INDEX, доменные доки, имплементация) сохраняется.
- Не задаются временные оценки и сроки.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Список исключений должен покрывать реальных нарушителей здесь и сейчас, включая `node_modules` внутри `scripts/mcp/**`, который специфичен для этого репозитория и обычным глобальным правилом не отлавливается.
2. Граница между "семантический lookup" и "exact-match lookup" должна объясняться через примеры запросов, а не через философскую формулировку — агенту нужен прямой шаблон-классификатор, чтобы решение занимало одно мгновение.
3. Прямое чтение `.jsonl` для одиночного класса должно быть подано не как обход правила, а как штатная техника на узких задачах. Никакого упрёка в адрес `query.ps1` — у двух путей разные диапазоны применимости.
4. Любое упоминание `rg` в правилах должно быть согласовано с уже принятым стилем "PowerShell efficiency" — никаких новых длинных команд в шаблонах документации; примеры компактные.
5. Никаких изменений в фактических скриптах сейчас — это стратегическая фаза. Конкретные diff и формулировки документации фиксирует тактическая спека.

## 4. Контекст текущей архитектуры

`.vscode/settings.json` — единственный артефакт, который влияет на VS Code search/watch/explorer в этом репозитории. Сейчас он перечисляет `.gradle/`, `build/`, `.idea/`, `V1/`, `v2_6/`, `spec_v2/` в трёх независимых блоках (`files.exclude`, `search.exclude`, `java.import.exclusions`/`files.watcherExclude`). Тяжёлые рабочие каталоги (`node_modules`, `temp`, `DOWNLOADS`, `.venv`, `logs`, `.kotlin`) в этих блоках отсутствуют — поэтому search и watcher по ним проходят.

`rg` (ripgrep) в репозитории не имеет проектного конфига и работает с дефолтным набором исключений (читает `.gitignore`, но не `.vscode/settings.json`). При обычном `rg --files` агент видит все тяжёлые каталоги, попадающие в `.gitignore`-совместимый, но не в search-совместимый шум — отсюда диагноз 9 251 → 2 633.

Раздел "Research Order" в `CLAUDE.md` содержит две формулировки про каталог:

- "MANDATORY first stop for any class/file lookup" — даёт каталогу абсолютный приоритет.
- "Never use `find`/`Glob` to locate a Kotlin class — the catalogue already knows the path" — явно запрещает alternative-инструменты.

Эти формулировки появились до того, как был замерен реальный cost каталог-запроса (≈423 мс на cold-start PowerShell + парсинг). Они оптимизировались под "не пропускай семантику", а не под "exact-match за 44 мс". Раздел "When to use the catalogue" в `dev/CATALOG/README.md` повторяет ту же универсальную позицию ("query the catalogue first") без указания на разницу между семантическим и точным поиском.

`scripts/catalog_sync.ps1`, `scan.ps1`, `render.ps1`, `set.ps1`, `query.ps1` — рабочие инструменты, которые остаются основным путём для записи в каталог и для широких семантических запросов. Их не нужно дорабатывать в рамках этого тикета — речь только о правилах применения.

`dev/PROJECT_OPERATIONS_INDEX.md` упоминается в "Research Order" как первый шаг — этот шаг сохраняется. Все остальные шаги (доменные доки, имплементация) остаются на своих местах.

## 5. Предлагаемый подход

Подход распадается на пять независимых правок, объединённых общей темой "снижение шума и уточнение поиска". Каждая правка автономна — порядок применения может быть любым.

### 5.1 Расширение исключений в `.vscode/settings.json`

Все три блока (`files.exclude`, `search.exclude`, `files.watcherExclude`) дополняются записями для тяжёлых рабочих каталогов: `node_modules` (включая вложенный путь `scripts/mcp/**/node_modules`), `temp/`, `DOWNLOADS/`, `.venv/`, `logs/`, `.kotlin/`. Существующие записи (`.gradle/`, `build/`, `.idea/`, `V1/`, `v2_6/`, `spec_v2/`) сохраняются. Блок `java.import.exclusions` синхронизируется по тому же списку — Java/Kotlin индексация LSP не должна гонять по `temp/` и `DOWNLOADS/`. Конкретный JSON-патч принимает тактическая спека.

Ожидаемый эффект — выдача VS Code search/explorer/watcher сжимается до ≈2 633 файлов (с возможным небольшим отклонением от текущего замера) и перестаёт зависеть от размера `temp/` и `DOWNLOADS/`.

### 5.2 Default-паттерн исключений для `rg`

Тот же список тяжёлых каталогов фиксируется как рекомендованный default-паттерн для агентских `rg`-запросов. Технически это формулируется как: "при широком `rg --files` или `rg <pattern>` без явной цели по конкретному пути добавляй `-g '!temp/'`, `-g '!DOWNLOADS/'`, `-g '!.venv/'`, `-g '!logs/'`, `-g '!.kotlin/'`, `-g '!**/node_modules/'`" — компактным шаблоном. Список приводится один раз в `CLAUDE.md` как часть нового пункта в "Research Order"; в `dev/CATALOG/README.md` дублируется ссылкой, не текстом.

Замысел — синхронизация двух плоскостей (`.vscode/settings.json` и `rg`-паттерн) по одному и тому же списку. Совпадение проверяется человеком при правке (без автоматизации в этом тикете).

### 5.3 Ревизия правила "catalog-first" в `CLAUDE.md`

Раздел "Research Order" обновляется так, чтобы шаг про каталог явно разделял два режима:

- **Семантический lookup** — запросы с предикатами "кто инжектит тип", "что трогает диск/сеть/Room", "какие классы превышают N LOC", "какие у класса side-effects", "кто кандидат на декомпозицию", "какая роль/статус", "кто владеет фичей" — идут через `query.ps1` или (если запрос узкий) через прямое чтение `.jsonl`.
- **Exact-match lookup** — запросы про точное имя класса/файла/токена/ключа ресурса/тега лога/строкового литерала — идут через `rg` (с default-паттерном из §5.2) или, для одиночного класса с известным именем, через прямое чтение `.jsonl` (см. §5.4).

Текущая жёсткая формулировка "Never use `find`/`Glob` to locate a Kotlin class" сохраняется в усечённом виде — только для семантических вопросов и для случаев, когда `rg` неизбежно перебирает много шума без нужды. Применение `rg` к точному имени класса перестаёт быть нарушением.

Старая последовательность шагов (PROJECT_OPERATIONS_INDEX → каталог → доменные доки → имплементация) сохраняется. Каталог по-прежнему остаётся первой остановкой для семантического lookup и для понимания структуры модуля.

### 5.4 Бенедикция прямого чтения `dev/CATALOG/<module>.jsonl` для узких запросов

Для случая "знаю точное имя класса, нужен путь" агенту явно разрешается прочитать `dev/CATALOG/<module>.jsonl` напрямую через нативный read-инструмент и взять одну строку. Это не "обход" каталога — это альтернативная точка входа, которая не платит за cold start PowerShell. Этот режим применим в трёх сценариях:

1. Нужен путь к одному классу с известным точным именем.
2. Нужно посмотреть несколько полей одной записи (role, status, layer, loc).
3. Узкий регулярный поиск по `.jsonl` (например, найти все записи слоя `data`, не запуская скрипт) — допустим, если объём вывода умещается в одно чтение.

Когда выдача потенциально большая или требуется фильтрация по нескольким измерениям одновременно — остаётся `query.ps1`. Граница "узкий vs широкий" опирается на здравый смысл, не на жёсткий числовой порог: если запрос помещается в "один Read" — это узкий.

### 5.5 Обновление гайдов: `CLAUDE.md` и `dev/CATALOG/README.md`

`CLAUDE.md`:

- Раздел "Research Order" получает обновлённую формулировку шага 3 в духе §5.3 (семантика vs exact-match), с компактными примерами для каждого режима.
- Default-паттерн исключений `rg` (см. §5.2) приводится один раз в этом же разделе или в смежной заметке.
- Все остальные правила (правила 1..17, "PowerShell efficiency", "Post-Change Steps") сохраняются неизменными.

`dev/CATALOG/README.md`:

- Раздел "When to use the catalogue" переписывается под две позиции: семантический lookup (через `query.ps1`) и узкий exact-match (через прямое чтение `.jsonl`). Запись "before planning or analysing code" сохраняется как корректная для семантических задач.
- Описание скриптов (`scan.ps1`, `set.ps1`, `query.ps1`, `remove.ps1`) не меняется — это инструмент, его контракт остаётся прежним.
- Никакие новые опции/флаги в скриптах не вводятся.

Формулировки документации финализируются в тактической спеке.

## 6. Research items - resolved

1. **Согласованность `.vscode/settings.json` и `rg`-default-паттерна без авто-проверки**
   - **Решение:** Синхронизация остаётся ручной. Guard-скрипт в рамках `S0270` не вводится.
   - **Основание:** exclude-набор низкочастотный, `rg`-паттерн остаётся документационным правилом, а `ADR-3` уже выбирает manual sync как базовый режим.
   - **Статус:** Resolved.

2. **Точный список тяжёлых каталогов**
   - **Решение:** Базовый набор достаточен: `temp/`, `DOWNLOADS/`, `.venv/`, `logs/`, `.kotlin/`, `**/node_modules/**`.
   - **Основание:** локальный замер `rg --files` дал `9264`, а с этим набором — `2646`; добавление `**/build/**`, `**/.gradle/**`, `**/.idea/**`, `.github/**`, `.claude/**` больше count не уменьшает.
   - **Статус:** Resolved.

3. **Формат подачи правила про exact-match в `CLAUDE.md`**
   - **Решение:** Используется hybrid-формат: два коротких bullet-пункта (`semantic lookup`, `exact-match lookup`) с inline-примерами.
   - **Основание:** стиль `lists over tables` сохранён, а граница между режимами считывается за один взгляд.
   - **Статус:** Resolved.

4. **Сохранение или удаление старого предложения "Never use `find`/`Glob`"**
   - **Решение:** Абсолютный запрет удалён; остаётся только narrowed misuse-context rule для семантического lookup и broad class discovery.
   - **Основание:** exact-match path через `rg` и direct `.jsonl` read разрешён и предпочтителен, но blind search не должен заменять каталог там, где нужна семантика.
   - **Статус:** Resolved.

5. **Покрытие правки для агентов вне VS Code**
   - **Решение:** Модель `.vscode/settings.json` + `CLAUDE.md` + `AGENTS.md` достаточна. Отдельный source-of-truth файл не нужен.
   - **Основание:** `.vscode/settings.json` обслуживает editor defaults, `CLAUDE.md` задаёт cross-agent contract, `AGENTS.md` уже импортирует его как load-bearing source.
   - **Статус:** Resolved.

## 9. Архитектурные решения (ADR)

**ADR-1: Семантика и exact-match — разные пути; правило "catalog-first" сохраняется, но локализуется на семантику**

- **Решение:** Раздел "Research Order" формулирует два режима явно. Catalog (через `query.ps1` или прямое чтение `.jsonl`) — обязательный первый шаг для семантических запросов. `rg` (с default-паттерном) или прямое чтение `.jsonl` по точному имени — допустимый и предпочтительный путь для exact-match.
- **Альтернативы:**
  - (а) Оставить "catalog-first universal" — экономит правки документации, но игнорирует измеренный 10× cost на простых exact-match-запросах.
  - (б) Полностью отменить правило "catalog-first" и положиться на агентский здравый смысл — слишком слабо, поведение разъедется по разным агентам.
  - (в) Ввести жёсткий числовой порог "когда что использовать" (например, "если ожидаемая выдача < 5 записей — `rg`") — переусложнение без измеряемой пользы.
- **Почему:** Правило с двумя ясно очерченными режимами и compact-примерами одновременно сохраняет ценность каталога (семантика, side-effects, role/status, DI-граф) и убирает регулярный налог cold-start PowerShell на простейших задачах. Вариант (а) сохраняет универсальность ценой каждодневной задержки; вариант (б) — теряет дисциплину; вариант (в) — оверкилл.

**ADR-2: Прямое чтение `dev/CATALOG/<module>.jsonl` — штатный путь, не обход**

- **Решение:** `dev/CATALOG/<module>.jsonl` остаётся read-only-источником для агентов в режиме "узкий lookup". Запись по-прежнему только через `scan.ps1`/`set.ps1`/`remove.ps1`. Бенедикция чтения формализуется в `dev/CATALOG/README.md`, чтобы агенты не считали этот путь "грязным" хаком.
- **Альтернативы:**
  - (а) Запретить прямое чтение, оставить только `query.ps1` — теряется free win (нативный Read без cold-start PowerShell).
  - (б) Расширить `query.ps1` ключом "ультра-быстрый exact-match" — добавляет поверхность скрипта без устранения базового cold-start.
- **Почему:** `.jsonl` — open machine-readable формат. Чтение его агентом — это та же операция, что чтение любого другого репозиторного файла. Запрещать её — искусственно создавать монополию `query.ps1`. Запись — другое дело: она ломает консистентность, и для неё каждый существующий скрипт делает побочную работу (re-render Markdown, валидация перечислений). Запись остаётся исключительно через скрипты.

**ADR-3: Синхронность `.vscode/settings.json` и `rg`-default-паттерна поддерживается вручную (по умолчанию)**

- **Решение:** Списки исключений в воркспейс-конфиге и в `CLAUDE.md`-инструкции для `rg` синхронизируются вручную. Auto-guard не вводится в рамках этого тикета.
- **Альтернативы:**
  - (а) Сразу ввести `scripts/check_workspace_excludes.ps1` с CI-валидацией — повышает поверхность поддержки без подтверждённой частоты правок.
  - (б) Хранить единый источник правды в отдельном файле и автогенерировать оба артефакта — оверкилл для двух коротких списков.
- **Почему:** Заявленные exclude-списки меняются редко (раз в несколько месяцев) и сразу видны при правке. Если в будущем выяснится, что расхождения возникают регулярно — §6 пункт 1 поднимет вопрос guard'а; сейчас вводить его — расход на проблему, которой нет.

## 11. Критерии готовности (strategic-level)

1. После правки `.vscode/settings.json` широкое перечисление файлов в VS Code search/explorer/watcher не включает `node_modules`, `temp/`, `DOWNLOADS/`, `.venv/`, `logs/`, `.kotlin/`, а также все ранее исключённые `.gradle/`, `build/`, `.idea/`, `V1/`, `v2_6/`, `spec_v2/`.
2. После правки `CLAUDE.md` раздел "Research Order" явно разделяет семантический и exact-match lookup, приводит default-паттерн исключений `rg` и сохраняет первый шаг про `dev/PROJECT_OPERATIONS_INDEX.md` и `dev/CATALOG/` в семантическом режиме.
3. После правки `dev/CATALOG/README.md` раздел "When to use the catalogue" признаёт два пути — `query.ps1` для семантики и прямое чтение `.jsonl` для узкого exact-match. Описание скриптов (`scan.ps1`, `set.ps1`, `query.ps1`, `remove.ps1`) сохраняется без изменения контрактов.
4. Замер `rg --files` (или эквивалентный замер в VS Code search) после применения exclude-списков укладывается в порядок ≈2 633 файлов (с допустимым отклонением, если состав репозитория изменился между замерами).
5. Ни в одном из правленных артефактов не появляется упоминание конкретного класса, конкретного модуля или конкретного пути имплементации приложения — изменения остаются на уровне воркспейса и процесса.
6. Документация не превышает в объёме предыдущую версию более чем на разумную дельту, оправданную новыми правилами (исключений, примеров) — стиль-правила "Spec Writing Style" соблюдены (lists over tables, one idea per bullet, no section summaries, two-dot ellipsis style, `ё`/`Ё`).
7. После правки конфликтов между новой формулировкой "Research Order" и существующими правилами (`PowerShell efficiency`, Strict Rule 14, формулировка в `dev/PROJECT_OPERATIONS_INDEX.md`) нет — это явно проверено перед коммитом.
8. Поведение приложения, состав product flavors, build-конфигурация, миграции, ресурсы, строки — не меняются. Сборка `standardDebug`/`vrDebug`/`noLegalDebug` не требуется и не запускается как часть acceptance этого тикета.
