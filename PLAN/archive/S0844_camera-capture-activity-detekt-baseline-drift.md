## 4. Контекст текущей архитектуры

Экран камеры уже следует Managers-паттерну проекта (CLAUDE.md Rule 3): Activity задумана как тонкий host, бизнес-решения и I/O камеры вынесены в отдельные менеджеры (поток захвата, сессия камеры, жесты, ориентация, таймер записи, геолокация). Несмотря на это, в Activity остаётся значительный объём UI-only кода: рендеринг зум-пресетов и подписи объектива, обработчики колбэков жестового менеджера и диалога настроек камеры, применение поворота оверлеев по ориентации, формирование подписи места сохранения/сценария, логика «отправить»/открыть последний кадр и превью галереи. Всё это исторически осталось прямо в Activity, поэтому по счётчику функций и строк класс превышает detekt-пороги качества, а detekt-baseline (примораживающий находки по буквальной сигнатуре класса) не спасает от повторного «размораживания» при любом изменении списка supertype - что и произошло, когда более ранний тикет добавил Activity ещё один интерфейс колбэков и ещё один интерфейс ориентации.

## 5. Предлагаемый подход

Вынести из host-Activity в отдельные вспомогательные роли (по образцу уже существующих `ui/cameracapture/helpers/*Manager`) всю UI-only логику, которая не относится к state-machine захвата фото/видео/записи.

### 5.1 Основные столпы/модули

1. **Обработчик колбэков жестового ввода** - реализует интерфейс колбэков жестового менеджера отдельно от Activity (делегирование интерфейса), обращаясь к уже существующим менеджерам потока/сессии и к виджету зум-контролов (пункт 3) вместо прямого доступа к полям Activity.
2. **Обработчик колбэков диалога настроек камеры** - инкапсулирует показ диалога и обработку его колбэков (предпросмотр/применение/отмена настроек), делегируя интерфейс отдельно от Activity.
3. **Виджет управления зумом и подписью объектива** - рендеринг зум-пресетов, синхронизация выделения с текущим zoom, форматирование подписей.
4. **Применение поворота оверлеев по ориентации** - список view, зависящих от ориентации устройства, и применение угла поворота к ним; расчёт самого угла уже отделён (живёт в существующем менеджере ориентации), переносится только применение к view.
5. **Формирование подписи места сохранения/сценария** - определение имени папки назначения и подписи вызывающего сценария, показываемых поверх превью.
6. **Менеджер результата съёмки (send-to / галерея / открыть последний кадр)** - сохранение результата многократной съёмки, обновление миниатюры галереи, видимость и обработка кнопки «отправить», открытие последнего кадра во внутреннем плеере.

Каждая роль получает только те зависимости, которые ей реально нужны (существующие менеджеры потока/сессии, конкретные view, уже внедрённые через Hilt репозитории/юзкейсы) - без обращения к приватным полям Activity в обход этих ролей.

### 5.2 Потоки данных и событий

Activity остаётся точкой входа для событий жизненного цикла и хост-колбэков потока захвата, а также единственным владельцем state-machine самого захвата (фото/видео/автотаймер/пауза-возобновление) - эта часть не меняется. Новые роли получают события уже от Activity (клик по элементу, колбэк жестового/диалогового менеджера) и решают, как их обработать, используя существующие менеджеры потока/сессии как источник состояния - Activity не дублирует их логику.

### 5.3 Точки расширяемости

Каждая вынесенная роль получает свой файл в `ui/cameracapture/helpers/`, что позволяет в будущем добавлять новые UI-элементы (например, ещё один пресет зума или ещё одну подпись) без дальнейшего раздувания Activity.

## 9. Архитектурные решения (ADR)

**ADR-1: Интерфейсы колбэков реализует отдельный класс, а не Activity**

- **Решение:** там, где сейчас Activity реализует интерфейс колбэков (жестовый менеджер, диалог настроек камеры), реализация переносится в отдельный класс, который подставляется вместо `this` в соответствующую точку подключения (конструктор жестового менеджера, поле `callbacks` диалога настроек) - Activity перестаёт реализовывать эти интерфейсы вообще, а не делегирует их через Kotlin `by`.
- **Альтернативы:** (a) реализация интерфейса через Kotlin-делегирование (`by`) - отклонено: зависимости обработчика (менеджеры потока/сессии, view) появляются только после `setupViews()`, то есть уже после конструирования Activity, а `by`-делегат должен быть доступен в момент объявления списка supertype, что создаёт хрупкий порядок инициализации без реальной пользы по сравнению с (б); (b) оставить реализацию интерфейсов в Activity и вынести только приватные функции - не сокращает счётчик функций, поэтому не решает `TooManyFunctions`.
- **Почему:** раз потребитель интерфейса (жестовый менеджер, диалог настроек) не обязан получать именно Activity - достаточно передать ему отдельный объект, реализующий тот же интерфейс. Это устраняет объявление функций-колбэков в теле Activity без делегирования и без проблем порядка инициализации.

**ADR-2: Аппаратно-зависимая state-machine захвата остаётся в Activity**

- **Решение:** логика запуска/остановки фото- и видеосъёмки, автотаймера, паузы/возобновления записи не выносится в рамках этого тикета.
- **Альтернативы:** полная декомпозиция всех оставшихся функций Activity.
- **Почему:** это самая рискованная и наиболее аппаратно-зависимая часть экрана камеры; её изменение без сквозной проверки на реальном устройстве создаёт риск регрессии в критичной для пользователя функции. Вынесенных UI-only ролей достаточно, чтобы опустить класс ниже detekt-порогов без этого риска.
