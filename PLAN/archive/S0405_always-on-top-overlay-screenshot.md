## 1. Проблема

Сейчас FastMediaSorter живёт только внутри своих окон: захват кадра возможен лишь во встроенном видеоплеере («Video screenshot capture»), а попасть в приложение изображение может только через системный Share sheet (приложение уже выступает приёмником `ACTION_SEND image/*`). Нет способа, находясь в любом другом приложении, одним касанием снять текущий экран и положить снимок в ресурс FastMediaSorter.

Запрос владельца: исследовать, может ли приложение стать «создателем снимков экрана» (screenshot-maker) и их приёмником, и - как пример носителя такой возможности - иметь постоянный «активный край/угол» (active edge), закреплённый в углу экрана и находящийся поверх всего, через который запускается быстрое действие (флагман - снять снимок текущего экрана и направить его в ресурс приложения).

Затронутая область - продуктовая способность уровня «системного слоя» поверх ОС: плавающий оверлей-хэндл + захват экрана вне собственных окон приложения. Это не существует ни в одном flavor.

---

## 2. Цели

1. Понять, реалистично ли (технически и в рамках политик Google Play) дать приложению постоянный always-on-top оверлей, видимый поверх других приложений.
2. Понять, какими средствами приложение может снять снимок текущего экрана вне своих окон, и какой ценой (разрешения, индикаторы, согласие пользователя, минимальный API).
3. Зафиксировать, что именно из «receiver»-части уже закрыто существующим Share-приёмником, а что требует доработки (например, авто-подхват системных скриншотов).
4. Определить, на какие flavor имеет смысл выкатывать способность и как её изолировать от ядра.
5. Дать владельцу ясную карту рисков (в первую очередь - риск отклонения в Play) до начала любой реализации.

**Non-goals:**

- Полноценный экранный рекордер (видеозапись экрана) - вне объёма.
- Замена системной кнопки скриншота или системного редактора снимков.
- Оверлей-управление воспроизведением чужих приложений.
- Любая «невидимая» фоновая запись экрана без явного индикатора - запрещено по политике и продуктовым принципам.
- Воспроизведение системных действий уровня One Hand Operation + (Back/Home/Recent и т. п.) - требует AccessibilityService и policy-риска; вне первой итерации.
- Конфигурируемая позиция/край полосы, несколько полос, расширенный набор жестов, исключения по приложениям, опция «открывать снимок сразу в плеере» (с выключением тоста) - отложенные итерации.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

Модель «активного края» уточнена владельцем (2026-06-11): это не видимый хэндл-кнопка, а тонкая прозрачная полоса-ловушка жестов у края экрана; действие запускается жестом от полосы. Образец желаемого UX - «One Hand Operation +» (Samsung Good Lock): тонкие краевые хэндлы, распознавание по углу+длине, выбор края/позиции. Важно: One Hand Operation+ обходится без AccessibilityService только как привилегированное системное приложение Samsung; мы остаёмся без a11y, ограничивая действие скриншотом через MediaProjection (см. research/12 и §6.4).

1. Опция «Оверлей жестов» - общий тумблер: включает/выключает полосу-ловушку поверх других приложений.
2. Опция «Скриншот жестом вниз» - сопоставление жеста действию «снять снимок экрана».
3. Опция «Загружать скриншоты в..» - выбор ресурса-назначения; по умолчанию - папка скриншотов устройства, при её отсутствии - Downloads.
4. Прямое сохранение снимка в выбранный ресурс FastMediaSorter (локальный или сетевой).
5. Приложение как единая точка приёма снимков: и созданных жестом, и пришедших из системного Share.
6. На будущее (вне первой итерации, по образцу One Hand Operation +): опциональный выбор края/позиции полосы, настройка толщины/длины/прозрачности, несколько полос, расширение набора жестов (короткий/длинный, диагонали), исключения по приложениям.

### 3.1.1 Начальная (первая итерация) модель UX

- Полоса крепится в верхнем левом углу: вертикальный диапазон от 10% до 75% высоты окна устройства (10% сверху - свободный угол, чтобы не срабатывать там).
- Полоса тонкая и полностью прозрачная (не видимый элемент, а зона чувствительности).
- Жест «скриншот вниз»: свайп пальцем от полосы вправо-вниз под углом ~45°.
- Позиция и набор жестов в первой итерации фиксированы (не настраиваются).

### 3.2 Жёсткие ограничения

- **Flavor (фазовый rollout):** первый таргет - `noLegal` (sideload-only, без ревью Google Play) для обкатки чувствительных пермишенов; затем Play-таргеты `standard` + `photos` после обкатки и подготовки consent/disclosure. Исключить `lite` (лёгкость), `vr` (Store-VR shell), `legacy` (по умолчанию). noLegal несёт полную standard-поверхность и штатно ставится на телефоны (VR рантайм-гейтится), поэтому фича там телефонная. Реализация обязана следовать `dev/FLAVOR_DEVELOPMENT_RULES.md`: интерфейс способности в `src/main/`, реализация в `src/<flavor>/java/`, отдельный flavor-Hilt-модуль. Запрещены `BuildConfig.IS_*`-проверки в `src/main/` (CLAUDE.md Rule 15).
- **API level:** базовый minSdk проекта - 26 (standard), 23 (legacy). Оверлей `TYPE_APPLICATION_OVERLAY` доступен с API 26. Тихий `AccessibilityService.takeScreenshot` - только с API 30. На API 26..29 захват экрана возможен лишь через `MediaProjection` с согласием пользователя. Поведение должно деградировать предсказуемо.
- **Разрешения:** способность требует «Показ поверх других приложений» (SYSTEM_ALERT_WINDOW) и - в зависимости от выбранного механизма захвата - либо посессионное согласие MediaProjection, либо включение Accessibility-сервиса. Все три - чувствительные; включение строго по явному действию пользователя.
- **Индикатор захвата:** любой снимок экрана сопровождается видимым пользователю индикатором - тост с ресурсом назначения и именем файла + постоянное уведомление сервиса (без вспышки в первой итерации). Тихий захват без обратной связи не допускается. На будущее: опция «сразу в плеер» выключит тост.
- **Производительность/батарея:** постоянный foreground-сервис, удерживающий оверлей, обязан быть лёгким (без удержания тяжёлых медиа-ресурсов в простое) и явно останавливаемым пользователем; ресурсы захвата освобождаются сразу после снимка (CLAUDE.md Rule 18).
- **Совместимость данных:** сохранённый снимок встраивается в существующую модель ресурсов/файловых операций; новой формы хранения, требующей миграции, не предполагается (подтвердить в §6).
- **Назначение по умолчанию:** папка скриншотов устройства; при её отсутствии - Downloads. Пользователь может переопределить любым ресурсом.
- **Конфликт с системными жестами:** полоса на левом краю пересекается с зоной системного жеста «Назад» (Android 10+, навигация жестами). Поведение «Назад» не должно ломаться - см. §6.9 (ключевой риск выполнимости).
- **Локализация:** EN/RU/UK - обязательно для всех новых строк (разрешения, уведомление сервиса, названия опций и жестов).
- **Доступность:** прозрачная полоса не видна и не озвучивается как элемент; альтернативный доступ к действию «скриншот» (например, через UI приложения или уведомление) обязателен, чтобы способность не была доступна только жестом. Полоса не перекрывает критичные системные зоны.
- **Системные границы:** оверлей не должен заезжать под вырез/строку состояния/жесты-навигацию; учитывать `systemBars` + `displayCutout` в обеих ориентациях (CLAUDE.md Rule 17).

## 4. Контекст текущей архитектуры

За приём извне отвечает слой Share-приёмника: прозрачная активность перехватывает `ACTION_SEND`, а выбор назначения и запись идут через существующие сценарии файловых операций и диалог выбора назначения; набор приёмных точек включается/выключается в рантайме менеджером плеера по умолчанию. То есть «receiver»-часть для изображений уже частично существует - системный скриншот, отправленный через Share, уже доходит до приложения.

Чего архитектура сейчас не умеет: жить поверх других приложений (нет оверлея уровня системы, нет постоянного foreground-сервиса под оверлей) и считывать содержимое экрана вне собственных окон (нет ни MediaProjection-, ни Accessibility-пути). Захват кадра существует только внутри собственного видеоплеера и не применим к произвольному системному экрану. Поэтому цель §1 недостижима в текущих слоях без новой способности «системного слоя».

## 5. Предлагаемый подход

Предварительный, переутверждается после §6. Архитектурно способность распадается на три независимые роли, соединённые через интерфейс способности в ядре и flavor-реализацию.

### 5.1 Основные столпы / модули

**A. Полоса-ловушка жестов (active edge).**
- Роль: держать у левого края always-on-top прозрачную зону чувствительности (10–50% высоты) поверх любого приложения и распознавать жест-триггер (свайп вправо-вниз ~45°).
- Требует разрешения «поверх других приложений» и - по требованиям Android 15+ - видимого оверлей-окна перед стартом сопутствующего foreground-сервиса.
- Должна корректно сосуществовать с системным жестом «Назад» на том же краю (различение по вектору жеста; см. §6.9) и пропускать прочие касания в приложение под собой (§6.8).
- Должна явно включаться/выключаться опцией «Оверлей жестов» и переживать переключение приложений, не удерживая тяжёлых ресурсов.
- Действие жеста расширяемо (пока одно - «скриншот вниз»); позиция полосы в первой итерации фиксирована.

**B. Захват текущего экрана.**
- Роль: по запросу (касание хэндла) получить изображение текущего экрана и передать его в роль сохранения.
- Два кандидата-механизма с разным профилем согласия/индикации/минимального API - предмет §6.2; выбор влияет на policy-риск (§6.4).
- Любой захват - с видимым индикатором (см. §3.2).

**C. Маршрутизация и сохранение снимка (maker → receiver).**
- Роль: принять полученное изображение и положить его в выбранный ресурс через существующий сценарий файловых операций/выбора назначения - переиспользуя то, что уже работает у Share-приёмника.
- Назначение по умолчанию - папка скриншотов устройства, при её отсутствии - Downloads; пользователь переопределяет опцией «Загружать скриншоты в..» (§6.11).
- Сюда же логически примыкает доработка «receiver»-части: предсказуемое поведение, когда снимок приходит из системного Share (уже частично закрыто).

### 5.2 Потоки данных и событий

- Включение: пользователь явно активирует способность в приложении → запрос чувствительных разрешений → запуск foreground-сервиса, который показывает оверлей-хэндл.
- Снимок: касание хэндла → роль захвата получает кадр текущего экрана (с индикатором) → роль сохранения предлагает/применяет назначение → запись через существующий слой файловых операций → пользовательская обратная связь.
- Приём из Share: системный скриншот → Share sheet → существующая точка приёма → тот же слой сохранения.
- Выключение: пользователь убирает хэндл → сервис и оверлей-окно снимаются, ресурсы захвата освобождаются.

### 5.3 Точки расширяемости

- Способность вводится как интерфейс в `src/main/` с flavor-реализацией - ядро не знает деталей захвата/оверлея; flavor без способности компилируется без неё (no-op/отсутствие).
- Действие хэндла оставить расширяемым: снимок экрана - первое действие, но точка запуска допускает и другие быстрые действия (например, быстрый приём ссылки/изображения) без переархитектуры.
- Механизм захвата - за абстракцией, чтобы можно было держать оба пути (MediaProjection / Accessibility) и выбирать по API/политике без переписывания ролей A и C.
- Сохранение переиспользует существующий слой назначений, а не вводит свой - расширяемость идёт через него.

## 6. Открытые вопросы / Research items

1. **Механизм оверлея и его стоимость на Android 12/15.**
   - **Вопрос:** какими ограничениями обложен постоянный `TYPE_APPLICATION_OVERLAY` + foreground-сервис на актуальных версиях, и переживаемо ли это продуктово?
   - **Нужно выяснить:** требование Android 15 «видимый оверлей до старта FGS из фона»; усложнённое получение SYSTEM_ALERT_WINDOW с Android 12; `HIDE_OVERLAY_WINDOWS` (приложения могут запретить рисовать поверх себя); влияние на батарею.
   - **Статус:** Resolved (предварительно)
   - **Артефакт:** `PLAN/S0405_always-on-top-overlay-screenshot/research/01__overlay-mechanism.md`

2. **Механизм захвата экрана: MediaProjection против AccessibilityService.takeScreenshot.**
   - **Вопрос:** какой путь даёт приемлемый UX без нарушения политик и какой минимальный API у каждого?
   - **Варианты:** (а) MediaProjection - посессионное согласие + системный индикатор записи, работает с API 26; (б) `AccessibilityService.takeScreenshot` - тихо, без индикатора, но только API 30+ и требует Accessibility-сервиса.
   - **Нужно выяснить:** какой путь приемлем с учётом продуктового требования об индикаторе и policy-риска (§6.4); как деградировать на API 26..29.
   - **Статус:** Resolved (2026-06-14) - решение владельца: на API 30+ основной путь захвата - `AccessibilityService.takeScreenshot` (тихо, без диалога, разовый грант accessibility в системных настройках); на API 26..29 (тихий путь недоступен) - MediaProjection-fallback с посессионным согласием. Механизм захвата выбирается в рантайме по `Build.VERSION.SDK_INT`. Допустимо на noLegal (sideload, вне Play-ревью); выход на Play по этому пути переоткрывает §6.4.
   - **Артефакт:** `PLAN/S0405_always-on-top-overlay-screenshot/research/02__screen-capture-mechanism.md`

3. **Что из «receiver»-части уже закрыто.**
   - **Вопрос:** доходит ли системный скриншот, отправленный через Share, до приложения сегодня, и чего не хватает для бесшовного приёма?
   - **Нужно выяснить:** покрытие существующих `ACTION_SEND image/*`-приёмных точек; нужен ли авто-подхват новых системных скриншотов без участия Share; есть ли смысл в отдельной приёмной точке именно для скриншотов.
   - **Статус:** Resolved
   - **Вывод:** путь «через Share» уже реализован (`ReceiveShareActivity` + image-alias, рантайм-переключение) и переиспользуется ролью сохранения; новизна - в «maker»-части. Авто-подхват скриншотов без Share (наблюдение `MediaStore`) - кандидат в non-goal первой итерации.
   - **Артефакт:** `PLAN/S0405_always-on-top-overlay-screenshot/research/03__receiver-coverage.md`

4. **Риск отклонения в Google Play.**
   - **Вопрос:** какой из путей §6.2 и сама пара «оверлей + захват экрана» создают риск отклонения/удаления по политике?
   - **Нужно выяснить:** политика по использованию AccessibilityService не по назначению (высокий риск отклонения), требования к декларации, «Device and Network Abuse», ограничения на overlay поверх системных/чувствительных экранов, требования к раскрытию и согласию.
   - **Уточнение (research/12):** образец One Hand Operation+ обходится без a11y только как системное приложение Samsung; для нас путь без a11y - держать единственным действием скриншот через MediaProjection. Это снимает основной policy-вектор. Любое будущее действие типа Back/Home потребует a11y и отдельного policy-решения.
   - **Развязка по rollout (ADR-5):** первый таргет `noLegal` распространяется сайдлоадом и не проходит ревью Play - policy не блокирует старт реализации. §6.4 становится критичным только на этапе выхода в Play (`standard`/`photos`): нужны раскрытие, consent-модель, отсутствие тихого захвата.
   - **Статус:** Open для Play-этапа (не блокирует noLegal-итерацию)
   - **Артефакт:** `PLAN/S0405_always-on-top-overlay-screenshot/research/12__one-hand-operation-plus-analysis.md`

5. **Набор flavor и изоляция.**
   - **Вопрос:** на какие flavor выкатывать способность и как изолировать по `dev/FLAVOR_DEVELOPMENT_RULES.md`?
   - **Нужно выяснить:** ценность на `lite`/`photos`/`legacy` против веса и policy-риска; форма интерфейса способности и flavor-модулей; поведение на legacy (API 23..25), где тихий захват недоступен.
   - **Статус:** Resolved (фазовый rollout - решение владельца 2026-06-11)
   - **Вывод:** сначала `noLegal` (sideload-only, без ревью Play) для обкатки overlay+MediaProjection без policy-гейта; затем Play-таргеты `standard` + `photos` с consent/disclosure. Исключить `lite`, `vr` (Store-VR shell), `legacy`. noLegal штатно ставится на телефоны (VR рантайм-гейтится), фича там телефонная. Изоляция: интерфейс в ядре + flavor-реализация + flavor-Hilt-модуль, возможен capability-флаг. (Ранняя оценка «исключить noLegal» исправлена - см. research/05.)
   - **Артефакт:** `PLAN/S0405_always-on-top-overlay-screenshot/research/05__flavor-scope.md`

6. **UX полосы-ловушки.**
   - **Вопрос:** уточнить детали начальной модели (§3.1.1) и поведение в граничных случаях.
   - **Решения владельца (2026-06-11):**
     - Полоса: левый верхний угол, 10–50% высоты, тонкая прозрачная, жест «вниз-вправо ~45°»; позиция и набор жестов фиксированы.

     - Ориентация: только portrait в первой итерации.
     - Назначение: любой зарегистрированный ресурс, включая сетевой.
   - **Статус:** Resolved
   - **Артефакт:** (решения отражены в тактических фазах 02/03/05)

7. **Поведение foreground-сервиса и контроль пользователя.**
   - **Вопрос:** какой тип foreground-сервиса корректен и как пользователь его явно останавливает?
   - **Нужно выяснить:** допустимый `foregroundServiceType` под оверлей-хэндл/захват на Android 14+; постоянное уведомление с действием «выключить»; поведение при перезагрузке (не поднимать молча).
   - **Статус:** Resolved
   - **Вывод:** под захват - FGS типа `mediaProjection` + `FOREGROUND_SERVICE` и `FOREGROUND_SERVICE_MEDIA_PROJECTION`; порядок `createScreenCaptureIntent()` → согласие → старт FGS → `getMediaProjection()`; согласие посессионное (один экземпляр - один кадр). Постоянное уведомление с действием «выключить», на перезагрузку молча не подниматься.

8. **Прозрачная полоса: захват жеста против пропуска касаний.**
   - **Вопрос:** может ли тонкая прозрачная полоса ловить жест-триггер и при этом не красть обычные касания у приложения под собой?

## 9. Архитектурные решения (ADR)

**ADR-1: Разведка прежде реализации.**

- **Решение:** первой итерацией закрываем §6 и фиксируем policy-риск; импл не начинается до решения владельца по §6.2/§6.4.
- **Альтернативы:** сразу прототипировать оверлей + захват.
- **Почему:** ключевой риск - не технический, а policy (отклонение в Play); ранний прототип может оказаться непубликуемым.

**ADR-2: Захват по умолчанию через MediaProjection, a11y - только осознанно.**

- **Решение:** базовый путь захвата - MediaProjection с явным согласием и видимым индикатором; `takeScreenshot` через AccessibilityService рассматривается только при явном policy-обосновании и решении владельца.
- **Альтернативы:** тихий a11y-захват как основной путь.
- **Почему:** a11y не по назначению - главный вектор отклонения; индикатор согласуется с продуктовыми принципами §3.2.

**ADR-3: Способность как flavor-изолированный интерфейс.**

- **Решение:** интерфейс в ядре, реализация в flavor-source-set, отдельный Hilt-модуль; без `BuildConfig.IS_*` в `src/main/`.
- **Альтернативы:** флаговые проверки в общем коде.
- **Почему:** соответствие CLAUDE.md Rule 15 и `dev/FLAVOR_DEVELOPMENT_RULES.md`; позволяет выкатывать на подмножество flavor.

**ADR-4: UX по образцу One Hand Operation +, действие - только скриншот.**

- **Решение:** зеркалируем UX-модель краевых жест-хэндлов One Hand Operation + (тонкая краевая зона, угол+длина, выбор края - в будущем); единственное действие первой итерации - скриншот через MediaProjection.
- **Альтернативы:** повторять полный набор действий образца (Back/Home/Recent) - требует AccessibilityService.
- **Почему:** One Hand Operation+ обходится без a11y только как системное приложение Samsung; ограничение скриншотом через MediaProjection держит нас вне a11y-policy-риска (§6.4). Край осознанно занимается полосой (§6.9).

**ADR-5: Фазовый rollout - сначала sideload (noLegal), потом Google Play.**

- **Решение:** первая реализация и обкатка - на `noLegal` (sideload-only, без ревью Play); после стабилизации - подготовка к Play на `standard` + `photos` с раскрытием и consent-моделью.
- **Альтернативы:** сразу целиться в Play на standard.
- **Почему:** чувствительные пермишены (overlay + MediaProjection) на sideload не проходят ревью Play - можно безопасно обкатать UX и поведение; noLegal несёт полную standard-поверхность и штатно ставится на телефоны. Play-риск снят отказом от a11y (ADR-4), но раскрытие/consent отрабатываются заранее на noLegal.

**ADR-6: Dialog-free захват через AccessibilityService на noLegal; MediaProjection - только fallback <30.**

- **Решение:** на noLegal основной путь захвата на API 30+ - `AccessibilityService.takeScreenshot` (тихо, без посессионного диалога). Сервис сам хостит краевую полосу через окно типа accessibility-overlay (без `SYSTEM_ALERT_WINDOW`) и выполняет захват. MediaProjection (с диалогом на каждый снимок) остаётся только для API 26..29, где тихий путь недоступен. Выбор - в рантайме по `Build.VERSION.SDK_INT`.
- **Альтернативы:** оставить MediaProjection единственным путём (диалог на каждый снимок - отвергнуто владельцем); полностью убрать MediaProjection (потеря фичи на API 26..29 - отвергнуто).
- **Почему:** on-device тест (журнал Тест 2) показал, что диалог MediaProjection в оверлей-сценарии неустраним и выскакивает на КАЖДЫЙ снимок. Это уточняет ADR-4: на noLegal (sideload, вне Play-ревью) a11y-путь допустим и закрывает требование «без промежуточного диалога». Для Play (`standard`/`photos`) a11y-путь переоткрывает §6.4 - решается отдельной спекой (S0418).

## 11. Критерии готовности (strategic-level)

Разведочная стадия (первая итерация):

1. По каждому пункту §6 есть решение или явно зафиксированный остаток, ключевые - с research/-артефактом.
2. Зафиксирован выбранный механизм захвата и его policy-обоснование (решение владельца по §6.2/§6.4).
3. Определён набор flavor и форма изоляции способности.

Реализационная стадия (после одобрения, сначала на `noLegal`):

4. Пользователь включает опцию «Оверлей жестов», и краевая полоса активна поверх других приложений.
5. Жест «вниз-вправо ~45°» от полосы снимает текущий экран с видимым индикатором и сохраняет снимок в назначение из опции «Загружать скриншоты в..» (по умолчанию - папка скриншотов устройства, иначе Downloads).
6. Системный жест «Назад» при активной полосе работает приемлемо (по выбранной в §6.9 митигации).
7. Способность полностью выключается пользователем; после выключения полоса и сервис не остаются активными.
8. Снимок, пришедший из системного Share, обрабатывается тем же путём сохранения предсказуемо.

## 13. Журнал on-device тестов

### Тест 1 (2026-06-14, Samsung SM-S731B, Android 16 / SDK 36, noLegal debug 2.60.6131.623) - FAIL → исправлено

- **Симптом:** приложение падает при старте foreground-сервиса захвата/оверлея.
- **Краш:** `android.app.RemoteServiceException$CannotPostForegroundServiceNotificationException: Bad notification for startForeground`.
- **Первопричина:** оба noLegal-сервиса (`ScreenCaptureService`, `OverlayHostService`) использовали как small-icon уведомления общий ресурс `ic_widget_camera_quick_capture`, у которого `android:tint="?attr/colorControlNormal"`. Тема-атрибут `?attr` не резолвится, когда систему инфлейтит иконку статус-бара вне темы приложения; Android 16 строго валидирует small-icon при `startForeground` и отвергает уведомление. Аудио-FGS не падает, т.к. его иконка `ic_notification_audio` - белая заливка без `?attr`.
- **Исправление:** добавлена отдельная иконка `src/noLegal/res/drawable/ic_notification_screen_capture.xml` (белая заливка, без `?attr`-tint), оба сервиса переведены на неё. Общий `ic_widget_camera_quick_capture` (S0369) не трогается - он остаётся тематически тонированным для receiver-манифеста и виджет-пикера.
- **Повторный тест:** требуется на том же Android 16 устройстве - см. **Status note**.

### Тест 2 (2026-06-14, Samsung SM-S731B, Android 16, noLegal debug 2.60.6140.921)

- **Изменения в сборке:** область полосы расширена до 10–75% высоты (верхние 10% - свободный угол, §3.1.1); на строке «Оверлей жестов» в настройках добавлена кнопка-хелпер (`str_showHelp`, `setting_gesture_overlay_help_*`) с описанием EN/RU/UK как пользоваться.
- **Находка (UX захвата):** при снимке через жест система показывает запрос согласия MediaProjection на КАЖДЫЙ снимок. Для оверлей-сценария это неустранимо в рамках MediaProjection (обоснование - §6.2). Тихий захват без запроса - только `AccessibilityService.takeScreenshot`; на noLegal допустим.
- **Решение:** ожидается выбор владельца A/B (§6.2); реализация тихого захвата - отдельной фазой `/spec-tech`.

### Решение по dialog-free (2026-06-14)

- **Выбор владельца:** dialog-free через `AccessibilityService.takeScreenshot` на API 30+; MediaProjection - fallback для API 26..29 (см. §6.2, ADR-6).
- **Архитектура:** на API 30+ accessibility-сервис сам хостит краевую полосу (окно типа accessibility-overlay, без `SYSTEM_ALERT_WINDOW`) и выполняет захват; разовый грант accessibility в системных настройках. На API 26..29 - прежний путь (OverlayHostService + MediaProjection с диалогом). Выбор пути и роутинг разрешений - в рантайме по `Build.VERSION.SDK_INT`, за интерфейсом способности в ядре.
- **Статус:** реализуется (S0405 In Progress); после сборки - повторный on-device тест на Android 16 (без диалога, снимок сохранён, полоса тогглится, системный Back работает).

### Находка: Android Restricted Settings блокирует accessibility на sideload (2026-06-14)

- **Симптом (on-device, Android 16):** в системном списке спецвозможностей строка FastMediaSorter помечена «Controlled by Restricted Setting», тумблер не включается, всплывает «App was denied access .. restricted permission».
- **Первопричина:** Android 13+ Restricted Settings - ОС запрещает включать чувствительные настройки (accessibility, notification access) приложениям, установленным вне Google Play (sideload). noLegal - sideload-only, поэтому гейт срабатывает всегда на API 33+. Это не дефект приложения и не обходится программно.
- **Снятие (пользователем):** App info приложения → меню «три точки» → «Allow restricted settings» → подтверждение → затем включить службу в списке спецвозможностей.
- **Снятие (dev/adb):** `adb shell appops set <pkg> ACCESS_RESTRICTED_SETTINGS allow`.
- **Митигация в приложении:** при включении тумблера «Оверлей жестов» показывается инструктивный диалог (заголовок + пошаговая последовательность EN/RU/UK, включая снятие restricted через App info → ⋮ → Allow restricted settings). Кнопки: «Открыть настройки» (deep-link на строку службы) и «Старый способ». Программно включить службу нельзя - максимум приземлить пользователя и объяснить шаги.
- **Запасной путь (fallback):** «Старый способ» в диалоге ведёт на разрешение «поверх других приложений»; если accessibility включить не удаётся, захват идёт через MediaProjection (с запросом согласия на каждый снимок) на том же краевом жесте. Выбор пути - runtime-приоритет: accessibility (dialog-free) приоритетнее; иначе - MediaProjection. Включение accessibility позже автоматически апгрейдит до dialog-free (a11y-сервис при коннекте глушит legacy-overlay-host).
