## 1. Проблема

Авторизация SFTP-ресурсов по приватному SSH-ключу частично реализована во время выполнения (флоу теста соединения и хранение ключа в зашифрованном виде уже есть), но имеется два пробела:

1. Predefined-ресурсы из bundled XML-конфигурации не умеют декларировать key-auth — указать ключ можно только через UI добавления ресурса. Развёртывание набора ресурсов «из коробки» (для пользователя, тестов интеграции, новых хостов) для SFTP с ключом невозможно.
2. При установке соединения проверка отпечатка host-key (fingerprint pinning) отсутствует: первый ответ сервера принимается доверчиво, и подмена сервера на маршруте (LAN/WAN/VPN) не детектируется. Для эксплуатации через интернет (WAN-сценарий, обозначенный в handoff) это критично.

Эффект: пользователь не может безопасно раздавать «известные» SFTP-точки на новом устройстве; единственный способ — вводить пароль вручную или вручную импортировать ключ через мастер. Защиты от MITM — нет.

---

## 2. Цели

1. Ресурсы, описанные во встроенной XML-конфигурации, можно объявить с авторизацией по приватному ключу (вместо или в дополнение к паролю), включая опциональную парольную фразу к ключу.
2. К любому SFTP-ресурсу (созданному вручную или импортированному из XML) можно привязать ожидаемый отпечаток host-key (SHA256). При несовпадении соединение прерывается до отправки логина — ошибка показывается пользователю как явный сигнал о возможной подмене сервера.
3. Существующие password-only ресурсы продолжают работать без переноса данных и без принудительной миграции.
4. Импорт ключа в predefined-ресурс безопасен: материал ключа не лежит в plain-XML на устройстве после первого запуска и не попадает в логи.

**Non-goals:**

- Генерация ключей внутри приложения (ключ создаётся внешним инструментом).
- Поддержка алгоритмов авторизации помимо тех, что уже маршрутизирует SSHJ-клиент (RSA / ED25519 / ECDSA).
- Сертификаты SSH (CA-signed certificates) — отдельная тема, выходит за рамки этой спеки.
- TOFU-режим («Trust On First Use» с автозапоминанием первого fingerprint) — pin задаётся явно.
- Интеграция в FTP-ресурсы (FTPS-pinning) — отдельная задача.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Если в XML-описании ресурса указаны и пароль, и ключ — ключ имеет приоритет, пароль игнорируется (но не теряется в сохранённых учётных данных, чтобы пользователь мог переключиться вручную).
2. Отпечаток host-key можно указать в нескольких форматах ввода (`SHA256:<base64>`, hex с двоеточиями, чистый base64), приложение нормализует к одному внутреннему виду.
3. При отсутствии отпечатка в конфигурации режим «доверчивого» соединения остаётся, но в UI ресурса есть подсказка с предложением запиннить отпечаток после первой удачной проверки.
4. Поле passphrase у ключа — опциональное; пустое значение интерпретируется как «ключ без парольной фразы», а не как ошибка.

### 3.2 Жёсткие ограничения

- **Flavor:** все четыре (`standard`, `lite`, `photos`, `legacy`) — SFTP присутствует во всех, кроме `photos` (без сетевых ресурсов); для `photos` фича недоступна, но XML не должен ломать сборку.
- **API level:** без новых требований сверх текущего проектного `minSdk` (26 / 23 для legacy).
- **Wear OS:** не затрагивается — на часах SFTP-ресурсы не редактируются.
- **Производительность:** проверка отпечатка добавляет ≤ 50 мс к установке соединения; на пропускную способность не влияет.
- **Совместимость данных:** ресурсы и учётные данные предыдущих версий читаются без изменений; новые поля — опциональные.
- **Локализация:** EN/RU/UK обязательно для всех новых строк (метки полей, ошибки сравнения отпечатков, предупреждения).
- **Доступность:** новые поля в форме — стандартные `EditText` с описанием, поддержка TalkBack «из коробки», ошибки несовпадения отпечатка не полагаются только на цвет.

## 4. Контекст текущей архитектуры

Слой данных уже умеет хранить SSH-приватный ключ как зашифрованное поле учётных данных и передавать его в SFTP-клиент при тесте соединения и при операциях чтения/записи. Координатор формы добавления ресурса различает password-флоу и key-флоу, ключ импортируется из выбранного пользователем файла.

Чего не хватает на архитектурном уровне:

- Парсер встроенной XML-конфигурации игнорирует поля для ключа и отпечатка, а соответствующих имён атрибутов в схеме нет.
- Слой установки SFTP-соединения не имеет точки внедрения проверки отпечатка перед auth-фазой; сейчас отпечаток нигде не сравнивается со «справочным».
- Учётные данные предзагружаемых ресурсов (XML → каталог) сохраняются по тому же пути, что и ручные, поэтому добавление ключа сводится к одной развилке в инициализации, но требует, чтобы ключевой материал, попавший в bundled XML, был перенесён в защищённое хранилище **до** того, как XML будет когда-либо прочитан повторно.

## 5. Предлагаемый подход

### 5.1 Основные столпы / модули

**A. Расширение схемы предзагружаемых ресурсов.**
Атрибуты XML дополняются полями для способа авторизации (`auth=password|key`), пути к ключу (`privateKeyAsset` — ссылка на bundled-asset либо абсолютный путь на устройстве), парольной фразы (`keyPassphrase`) и ожидаемого отпечатка (`hostKeyFingerprint`). При первой инициализации ключ читается, переносится в защищённое хранилище, исходный путь забывается. Существующие записи без новых атрибутов продолжают работать как password-only.

**B. Pinning host-key fingerprint.**
В стек установки SFTP-соединения вводится верификатор отпечатка: если ресурс заявляет ожидаемый fingerprint, то перед auth-фазой полученный от сервера ключ нормализуется к канональной форме SHA256 и сравнивается константно-временно. Любое несоответствие — терминальная ошибка соединения с понятной формулировкой («ожидался отпечаток X, получен Y; возможно сервер подменён»).

**C. UI-точки.**
В форме создания/редактирования SFTP-ресурса добавляется поле «ожидаемый отпечаток host-key» (опциональное), ввод нормализуется на лету. Сообщения о несовпадении — отдельный класс ошибок, не смешивающийся с auth-ошибкой пароля/ключа. Существующий мастер импорта ключа не меняется по форме, только дополняется новым полем.

**D. Нормализация и хранение отпечатков.**
Отпечатки хранятся вместе с описанием ресурса, не как часть учётных данных (отпечаток — публичный, скрывать его не нужно; учётные данные требуют шифрования). Это разводит две сущности по разным хранилищам и упрощает экспорт/импорт ресурсов между устройствами.

### 5.2 Потоки данных и событий

- **Bootstrap predefined-ресурсов:** XML → парсер → если `auth=key`, ключ переносится в защищённое хранилище → запись описания ресурса с типом авторизации `key` и (опционально) ожидаемым отпечатком → исходный bundled-key из XML больше не используется.
- **Подключение:** репозиторий ресурсов отдаёт описание + опциональный fingerprint → сетевой слой строит SFTP-сессию, регистрирует верификатор отпечатка → если pin задан и не совпал — соединение разрывается и в UI поднимается типизированная ошибка → если совпал или pin не задан — переход к auth (password или ключ).
- **Редактирование ресурса в UI:** пользователь вводит/редактирует fingerprint → нормализатор → сохранение в описание ресурса; учётные данные не трогаются.

### 5.3 Точки расширяемости

- Верификатор отпечатков должен быть пригоден к расширению до режима TOFU и до сравнения нескольких отпечатков (миграция ключа сервера) без переписывания вызывающего кода.
- Парсер predefined-ресурсов должен оставаться тем же входом и для будущих типов авторизации (например, SSH-сертификатов), без появления параллельной XML-схемы.

## 6. Открытые вопросы / Research items

1. **Формат хранения ключевого материала из bundled XML на момент первого запуска.**
   - **Вопрос:** хранить ключи как незашифрованные `assets/`-файлы рядом с APK или как inline-base64 внутри XML?
   - **Решение (Best Practice):** отдельный `.pem` в `assets/sftp_keys/`; XML ссылается на имя файла через атрибут `privateKeyAsset`. XML остаётся человекочитаемым (без больших base64-блобов), замена ключа сводится к перезаписи одного `.pem` без правки XML, что соответствует канонической OpenSSH-модели «один ключ — один файл». Bundled-ключи не считаются секретами в строгом смысле — это публичные заготовки конфигурации; реальный секрет создаётся пользователем уже на устройстве и хранится зашифрованным.
   - **Статус:** Tactical

2. **Поведение, когда XML декларирует `auth=key`, но указанный путь к ключу недоступен.**
   - **Вопрос:** падать ли тихо до password-fallback или показывать пользователю описательную ошибку при первом запуске?
   - **Решение (Best Practice):** ресурс не создаётся; ошибка пишется в Timber-лог (`Timber.w` с именем ресурса и причиной), пользователь не видит ни Toast, ни сломанной записи. Silent fallback к паролю запрещён — это маскирует release-time ошибку и приводит к ресурсу с неконсистентным auth-методом. Toast на старте — шум без действия для конечного пользователя; недоступный bundled-ключ — это баг релиза, диагностируемый разработчиком по логам, а не задача пользователя.
   - **Статус:** Tactical

3. **Должна ли смена fingerprint на сервере (легитимная — переустановка OpenSSH) разруливаться через UI или только через ручное редактирование ресурса?**
   - **Вопрос:** показывать ли диалог «отпечаток изменился, обновить?» при несовпадении — или это плохая идея с точки зрения безопасности?
   - **Решение (Best Practice):** автоматическое обновление запрещено. При несовпадении — терминальная ошибка соединения с явным выводом ожидаемого и фактического отпечатков; обновление пина возможно только через ручное редактирование ресурса в форме. «Click-through»-диалоги на запрос подтверждения — известный вектор фишинга через привыкание; ручная правка вынуждает осознанное действие. Это согласуется с ADR-2 (отказ от TOFU) и с поведением сопоставимых клиентов (Termius, MobaXterm) при первом несовпадении.
   - **Статус:** Tactical

4. **Унификация представления отпечатка между UI и логами.**
   - **Вопрос:** в каком виде fingerprint показывается в UI (полная строка `SHA256:base64` или сокращение)?
   - **Решение (Best Practice):** в форме редактирования ресурса и в детальном виде ошибки несовпадения — полный `SHA256:<base64>`; в списках и компактных Snackbar'ах — усечение в стиле Git short-hash (первые 12 символов base64-части после `SHA256:` плюс многоточие `..`), с раскрытием по тапу. В логах — только полная форма (поиск/grep требует канонической записи).
   - **Статус:** Tactical

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Bundled-ключ из XML попадает в логи/crash-репорты при ошибках инициализации | Средняя | Утечка приватного ключа из публикации | Не логировать содержимое ключа; для диагностики использовать только отпечаток публичной половины |
| Нормализация отпечатка между форматами вносит расхождение (hex vs base64 vs `SHA256:` префикс) | Средняя | Ложные срабатывания «MITM» при корректном сервере | Канонизировать к SHA256 base64 без padding; тесты на все распространённые формы ввода |
| Пользователь импортирует ключ, забывает passphrase, теряет доступ | Средняя | Раздражение, support-запросы | Явное поле passphrase с подсказкой; отдельная ошибка «ключ есть, passphrase неверна» |
| SSHJ не поддерживает алгоритм ключа, выбранный пользователем | Низкая | Ошибка соединения | Сообщение об ошибке именует алгоритм; в FAQ — список поддерживаемых |
| Pin-режим конфликтует с балансировщиками SFTP за разными ключами | Низкая | Нестабильные подключения для редких корпоративных сценариев | Pin-режим — opt-in; без pin поведение прежнее |

## 9. Архитектурные решения (ADR)

**ADR-1: Отпечаток host-key хранится с описанием ресурса, а не с учётными данными.**

- **Решение:** fingerprint — поле дескриптора ресурса, не credentials.
- **Альтернативы:** хранить рядом с паролем/ключом в зашифрованном credentials-хранилище.
- **Почему:** отпечаток публичен, шифровать его смысла нет; разделение упрощает экспорт ресурсов между устройствами и переиспользование одного fingerprint при ротации credentials.

**ADR-2: TOFU-режим явно исключён из объёма.**

- **Решение:** автоматическое запоминание fingerprint при первой удачной проверке не реализуется.
- **Альтернативы:** TOFU как опция, TOFU по умолчанию.
- **Почему:** TOFU маскирует случаи, когда первое подключение уже произошло через MITM; это противоречит цели §2.2. Возврат к теме возможен после сбора эксплуатационного опыта.

**ADR-3: Bundled-ключ переносится из XML в защищённое хранилище при первой загрузке и больше из XML не читается.**

- **Решение:** XML — лишь источник «семечка»; live-чтение ключа в рантайме идёт из шифрованного хранилища.
- **Альтернативы:** читать ключ из assets каждый раз.
- **Почему:** один путь до credentials-хранилища (без раздвоения «assets vs DB»), и сразу же отпадает риск неожиданного переноса между устройствами при шеринге профиля.

## 11. Критерии готовности (strategic-level)

1. В bundled XML-конфигурации (и в её документации) можно описать SFTP-ресурс с авторизацией по приватному ключу и опциональной парольной фразой; после первого запуска такой ресурс подключается к серверу без участия пользователя.
2. В UI редактирования SFTP-ресурса доступно поле «ожидаемый отпечаток host-key»; некорректный ввод подсвечивается до сохранения.
3. При несовпадении отпечатка ресурс не подключается, пользователь видит ошибку, отличающуюся от ошибки авторизации, с упоминанием ожидаемого и фактического значений.
4. Все существующие password-only ресурсы остаются рабочими; их учётные данные не перезатираются и не требуют повторного ввода после обновления.
5. В логах не появляется содержимое приватного ключа; в логах при провале pin-проверки видны только отпечатки.
6. В EN/RU/UK добавлены строки для всех новых полей и сообщений об ошибках.
