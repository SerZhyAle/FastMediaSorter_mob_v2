# S1202 - transient-bars-restore-signal-unverified

**Status:** Archived
**Priority:** 40
**Tier:** 2 - Easy (ad-hoc)
**Date:** 2026-07-26

## 0. Захваченный материал (verbatim)

Обнаружено при верификации S1115 на emulator-5554 (2026-07-26, прогон
`temp/S1115/mobile_test_scenario_20260726_2105.md`).

S1115 переписал `StandaloneFullscreenManager.setupTransientBarsExitCallback`. Было:

```kotlin
decorView.setOnSystemUiVisibilityChangeListener { visibility ->
    if (visibility and View.SYSTEM_UI_FLAG_FULLSCREEN == 0) onBarsAppeared()
}
```

Стало:

```kotlin
ViewCompat.setOnApplyWindowInsetsListener(content) { _, insets ->
    if (fullscreenActive && insets.isVisible(WindowInsetsCompat.Type.systemBars())) {
        onBarsAppeared()
    }
    insets
}
```

Прогон доказал, что ложное срабатывание устранено (проба входа в полноэкранный режим
без немедленной пробы восстановления). Обратное — что колбэк срабатывает при
**настоящем** появлении баров — не проверено: свайп от края экрана не инжектируется
на этом AVD (6 попыток, оба края, mobile-mcp и raw adb; один свайп ушёл в шторку SystemUI).

## 1. Проблема

Режим `BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE` показывает системные бары поверх контента,
не меняя раскладку. Есть обоснованное подозрение, что `WindowInsetsCompat.isVisible(systemBars())`
для transient-баров возвращает `false` именно потому, что они не влияют на инсеты. Если так,
условие в новом колбэке не выполняется никогда, и путь «свайп от края возвращает командную
панель» мёртв в обоих standalone-хостах.

Пользователь при этом не заперт: S1115 добавил видимую кнопку выхода, и она проверена
(1c PASS). Это деградация запасного пути, а не потеря выхода.

## 2. Цель

Определить, какой сигнал на API 30+ действительно означает «transient-бары появились», и
привести колбэк к нему - либо подтвердить, что текущая реализация уже корректна.

## 3. Ограничения и рамки

- Оба хоста используют один и тот же метод: `PhotoVideoStandaloneActivity` и
  `StandalonePlayerActivity`. Правка обязана чинить оба.
- Нельзя вернуть старое условие по `SYSTEM_UI_FLAG_FULLSCREEN` - оно и было дефектом S1115
  (срабатывало безусловно на API 30+).
- Оба вызывающих колбэка идемпотентны (`if (!topCommandPanel.isVisible)`), поэтому
  двойной триггер безопасен, если это окажется нужным.

## 6. Открытые вопросы / Research items

1. Возвращает ли `WindowInsetsCompat.isVisible(Type.systemBars())` значение `true`, пока
   показаны transient-бары, и приходит ли при этом диспатч инсетов на `android.R.id.content`?
   Статус: Resolved. **Нет по обоим пунктам.** Замер на Galaxy S21 (SM-G996U1, Android 15, API 35),
   2026-08-14: бары физически на экране (снимок `evidence/01-transient-bars-visible.jpg` - статус-бар
   сверху, навигация справа), при этом единственный сработавший зонд прочитал
   `sys=false status=false nav=false top=0 bottom=0`, а `applyInsets` не пришёл ни разу.
   Подозрение из §1 подтверждено: условие в текущем колбэке не выполняется никогда.
2. Если нет - какой сигнал корректен? Статус: Resolved. **`WindowInsetsAnimationCompat.Callback`**
   на `android.R.id.content`. При свайпе от края приходит анимация с `typeMask=3`
   (`statusBars|navigationBars`), длительностью 373 мс. Отвергнутые кандидаты - в §12.

## 12. Результаты измерения (2026-08-14, Galaxy S21, API 35)

Метод: во все три кандидата-сигнала одновременно поставлены зонды `Timber.d("S1202: ..")`,
логи стримились в файл на протяжении всего сценария, свайп инжектировался `input touchscreen swipe`
от края экрана. Выдержка из лога - `evidence/probe-research.log`, снимок -
`evidence/01-transient-bars-visible.jpg`.

Воспроизведение: собрать debug, войти в фуллскрин в любом standalone-хосте, выполнить
`adb shell input touchscreen swipe 1200 2 1200 500 120` и снять `adb shell screencap`.

- `setOnApplyWindowInsetsListener` - не срабатывает на transient-бары вообще. При этом сообщает
  `isVisible(systemBars())=false` даже в момент, когда бары видимы на снимке экрана.
- `WindowInsetsAnimationCompat.Callback` - срабатывает: `animPrepare mask=3` -> `animEnd mask=3`.
  Это и есть искомый сигнал.
- Устаревший `setOnSystemUiVisibilityChangeListener` - сработал один раз при входе в фуллскрин
  (`sysUiVis=0x6`) и ни разу на свайп. Как триггер восстановления бесполезен, подтверждает S1115.

Два неочевидных факта, определивших реализацию:

- Анимация системных баров приходит и на собственный вызов `hide()` при входе в фуллскрин, то есть
  сама по себе она означает не «бары появились», а «бары анимируются». Разделитель - момент старта:
  собственная анимация стартует через **19 мс** после `enterFullscreen()` (17:35:11.290 -> .309),
  пользовательский свайп - через **99 секунд** (17:36:50.912). Отсюда защитное окно 500 мс.
- Авто-скрытие transient-баров по таймауту анимацию в приложение **не** доставляет: между
  `animEnd` в 17:36:51.285 и исчезновением баров со снимка новых событий в логе нет. Поэтому
  отдельная проверка направления анимации не нужна.

Отвергнуто: опрос `rootWindowInsets` по таймеру - читает то же самое состояние `InsetsState`, что и
листенер, то есть вернёт тот же `false`. `OnControllableInsetsChangedListener` - отвечает на другой
вопрос (какие типы управляемы, а не какие видимы).

Не покрыто: поведение на API 23..29 (флавор `legacy`), где действует обратно-портированный
`IMMERSIVE_STICKY`, а не `WindowInsetsController`. Устройства этого диапазона под рукой нет,
и слать непроверенный код туда хуже, чем не трогать. Вынесено отдельным тикетом - см. §10.

## 13. Приёмка на устройстве (2026-08-14, Galaxy S21, API 35)

Оба критерия §11 закрыты замером на реальном устройстве. Выдержка из лога -
`evidence/probe-acceptance.log`, снимки - `evidence/02-*.jpg` и `evidence/03-*.jpg`.

`StandalonePlayerActivity`:

- Вход в фуллскрин 17:46:21.528, собственная анимация распознана как своя
  (`barsAnimEnd self=true fs=true`), восстановление не запущено. Панель отсутствует в дампе
  иерархии, системных баров нет - ложного срабатывания нет.
- Ручное переключение кнопкой `btnFullscreenCmd` в 17:48:08.016 дало настоящую анимацию скрытия
  длиной 365 мс, и она тоже классифицирована как своя. Это более сильная проверка защитного окна,
  чем мгновенная стартовая анимация в 19 мс.
- Свайп от края 17:48:52.531 - `barsAnimEnd self=false fs=true`, следом `exited fullscreen`
  через 2 мс. Панель вернулась: в дампе `topCommandPanel` присутствует, на снимке
  `evidence/02-host-player-panel-restored.jpg` видны все её кнопки, системные бары показаны
  постоянно.

`PhotoVideoStandaloneActivity` (запуск через алиас `.StandaloneVideoPlayer`):

- Вход в фуллскрин 17:50:09.650, `self=true`, панель отсутствует в дампе - ложного срабатывания нет.
- Свайп от края 17:50:40.199 - `self=false`, следом `exited fullscreen` через 3 мс. Панель
  вернулась (дамп + снимок `evidence/03-host-photovideo-panel-restored.jpg`).

Метод замера панели: `uiautomator dump` не выводит скрытые узлы, поэтому наличие или отсутствие
`topCommandPanel` в дампе - прямое свидетельство её видимости, а не вывод по цепочке рассуждений.
Один дамп был снят слишком рано и показал ноль при уже сработавшем коде; повторный дамп того же
состояния показал панель. В приёмку взяты дампы, снятые после завершения анимации.
