То есть либо пробники были удалены, пока тикет оставался в `BlockNeedUserTest`, либо аудит зафиксировал вывод пробников, которые так и не были закоммичены. Ни один гейт этого не заметил.

**Захвачено во время:** `/spec-sweep` (Step 1 ранбука `/release`), активного тикета-владельца нет.

## 1. Проблема

Инвариант Rule 2 двусторонний: пробник `Timber.d("Sxxxx: ..")` существует в `.kt` **тогда и только тогда**, когда спека `Sxxxx` находится в `BlockNeedUserTest`. Механически проверяется только одно направление - что в постоянных логах нет `Sxxxx` (гейт тикет-логов). Обратное направление - тикет в `BlockNeedUserTest` обязан иметь пробник - не проверяется ничем.

Эффект: тикет может месяцами ждать устройственной проверки, не имея ни одного пробника. Устройственный прогон тогда не может опереться на лог и вынужден судить по скриншотам, что для части сценариев вообще нереально. Хуже - `## Last Audit` может ссылаться на вывод пробников, которых в коде нет, и это выглядит как валидный эвиденс при чтении спеки.

Область: инструментарий качества (`scripts/quality/`), каталог спек, ритуал `post-change`.

1. Механически обнаруживать спеку в `BlockNeedUserTest`, для которой в исходниках нет ни одного активного `Timber.d("Sxxxx:`.
2. Обнаруживать обратный дрейф - удаление пробника без сопутствующей смены статуса.
3. Давать список расхождений в машинно-читаемом виде, пригодном для батч-починки.

**Non-goals:**

- Автоматическая вставка пробников в точки входа изменённых потоков - выбор точки требует понимания сценария.
- Проверка осмысленности текста пробника.
- Верификация того, что цитаты в `## Last Audit` соответствуют реально существующим строкам кода (отдельная, более широкая задача).

## 4. Контекст текущей архитектуры

Статусы тикетов живут в журнале каталога и меняются только через CLI мутаторов. Пробники живут в исходниках. Связь между этими двумя мирами держится исключительно на дисциплине агента при переходе статуса, и ни один шаг ритуала `post-change` эту связь не пересматривает.

Существующий гейт тикет-логов ловит только противоположную ошибку - `Sxxxx`, забытый в постоянном логе. Он проходит по исходникам, но не сверяется с каталогом, поэтому «пробника нет, а статус требует» для него невидимо.

---

## 5. Предлагаемый подход

Сверка двух источников: перечень тикетов в `BlockNeedUserTest` из каталога против перечня id, для которых в исходниках найден активный вызов пробника. Расхождение в любую сторону - находка.

### 5.1 Основные столпы / модули

- Читатель каталога: отдаёт множество id в статусе `BlockNeedUserTest`.
- Сканер исходников: отдаёт множество id, у которых есть активный пробник, с учётом того, что вызов бывает разбит по строкам.
- Сопоставитель: две разности множеств, две категории находок.
- Ratchet-состояние: baseline уже известных расхождений, чтобы гейт был полезен с первого дня.

### 5.2 Потоки данных и событий

Каталог -> множество ожидаемых id; исходники (`app_v2/src`, `wear/src`) -> множество фактических id; сопоставитель -> отчёт + код возврата; baseline -> фильтр известных расхождений.

### 5.3 Точки расширяемости

- Подключение в батч быстрых гейтов рядом с остальными проверками.
- Режим полного аудита каталога отдельно от режима проверки одного изменения.

## 6. Открытые вопросы / Research items

1. **Куда включать гейт.** **Status: Resolved** (2026-08-14, измерением). Отдельный сканер не нужен: `scripts/quality/assert-no-ticket-logs.ps1` уже читает каталог, уже строит множество `BlockNeedUserTest` (строки 55-61) и уже обходит `app_v2/src` + `wear/src`. Обратная проверка добавляется туда же и не стоит ни лишнего чтения каталога, ни лишнего прохода по исходникам. Гейт уже стоит и в `post-change`, и в батче быстрых гейтов, поэтому вопрос «как часто» решается сам.
2. **Многострочный пробник.** **Status: Resolved** - в том же скрипте уже есть реконструкция вызова через `Get-SanitizedCall` (S0948), написанная ровно против этой ловушки. Новая проверка опирается на неё, а не на построчный grep, поэтому перенос строки пробника не превращает его в отсутствующий.
3. **Цитаты в `## Last Audit`.** **Status: Resolved** - остаётся вне объёма, как и записано в §2 non-goals. Отдельная задача, гейт её не касается.
4. **Форма ratchet.** **Status: Resolved** - счётчик отвергнут в пользу allow-list с причиной. Замер 2026-08-14: в `BlockNeedUserTest` сейчас **10** тикетов, а не 68, как предполагала §7; пробник есть у восьми. Оба исключения - **S1606** (`ticket-evidence-lives-in-temp`) и **S1620** (`archived-specs-leave-version-control`) - меняют инструментарий и документацию, а не Kotlin, то есть пробнику там просто негде стоять. Это опровергает инвариант в его буквальной форме: «в `BlockNeedUserTest` ⟹ есть пробник» верно только для тикетов, меняющих код приложения. Allow-list по id с причиной и отражает это, и стартует гейт зелёным с нуля необъяснённых пробелов, тогда как счётчик 2 просто зафиксировал бы долг без объяснения.

## 9. Архитектурные решения (ADR)

### ADR-1 (2026-08-14). Расширение существующего гейта, а не новый скрипт; allow-list вместо счётчика

**Решение.** Обратная проверка живёт в `scripts/quality/assert-no-ticket-logs.ps1`, а её исключения - в `scripts/quality/blockneedusertest-probe-baseline.txt` в форме `Sxxxx  причина`.

**Альтернативы.** Отдельный `assert-blockneedusertest-probes.ps1` с собственным обходом исходников; ratchet-счётчик, как у activity-logic и listener-symmetry.

**Почему.** Отдельный скрипт пришлось бы снабдить копией реконструкции многострочного вызова (`Get-SanitizedCall`, S0948) - самой тонкой части существующего сканера; две копии этой логики разъехались бы молча, а гейт, который молча перестал видеть перенос строки, хуже отсутствующего. Счётчик отвергнут по итогам замера: обоим сегодняшним пробелам есть законная причина - тикет не трогает Kotlin, - и счётчик записал бы её как безымянный долг, тогда как весь смысл гейта в том, что число двигается только с объяснением. Allow-list ещё и не гниёт: когда тикет уходит из `BlockNeedUserTest`, запись просто перестаёт использоваться.
