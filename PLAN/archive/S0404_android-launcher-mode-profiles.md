## 1. Проблема

Приложение умеет быть профильным медиаплеером (фоторамка, аудио, читалка), но остаётся «гостем» на устройстве: после выхода пользователь попадает в чужой системный домашний экран, а чтобы вернуться к нужному сценарию - заново ищет иконку и настраивает режим.

На выделенных устройствах (старый планшет как фоторамка на стене, автомагнитола, медиабокс под аудио, планшет под чтение) хочется, чтобы приложение само было домашним экраном: по кнопке Home открывался собранный под сценарий рабочий стол, и оттуда же запускались другие приложения, не выходя «в систему».

Сейчас этого нет: приложение не объявляет себя как Home-экран, не показывает установленные приложения и не имеет домашней поверхности.

Область: входной поток приложения, новая домашняя поверхность, реестр приложений.

### 1.1 Концептуальная модель: рабочий стол Windows

Владелец сформулировал модель как «весь интерфейс больше в логике Windows» (2026-07-16). Это несущая аналогия эпика, а не украшение: она задаёт и состав поверхности, и то, что в неё не входит.

- **Рабочий стол** - сетка ячеек, которую заполняет пользователь.
- **Ярлык** - ячейка с сохранённой командой и её параметрами (аналог `.lnk` с аргументами).
- **Гаджет** - наш интерактивный блок, занимающий несколько ячеек (список песен, список трансляций, часы с погодой).
- **Панель задач** - постоянная полоса: «Пуск», последние запуски, закреплённые иконки, трей.
- **Трей** - часы, сеть, батарея.
- **Меню «Пуск»** - разделы: наши ресурсы, все приложения, настройки, выход из режима лаунчера.

Две границы модели, где Android устроен не как Windows, и это не обходится кодом:

- **«Запущенных окон» не существует.** Приложение не может узнать, что работает в системе, без special-access разрешения, и не может «переключиться в окно» - только запустить приложение заново (система сама восстановит состояние). Поэтому «последние» строятся по собственному журналу запусков (ADR-7).
- **Системный status bar не отдаётся.** Постоянно заменить его своим может только device owner, что недостижимо для Play-установки. Наш трей живёт в своей панели и с системным баром не конфликтует (ADR-8).

### 1.2 Терминология

Эпик S0404 и спеки-сиблинги S0426-S0429 используют общие термины:

- **Роль Home** - системная роль домашнего экрана. Выдаётся только пользователем, программно не забирается.
- **Домашняя поверхность** - отдельная Activity, открываемая по кнопке Home.
- **Ячейка** - единица сетки: ярлык-команда либо часть гаджета.
- **Реестр приложений** - слой перечисления и запуска установленных приложений.

## 2. Цели

1. Пользователь может назначить приложение домашним экраном устройства штатными средствами Android и снять эту роль.
2. По нажатию Home открывается домашняя поверхность приложения.
3. Пользователь сам собирает состав рабочего стола: кладёт в ячейки ярлыки-команды и гаджеты.
4. Ячейка-ярлык хранит команду с параметрами запуска (конкретный ресурс, режим показа, плейлист, трансляция), а не только «открыть приложение».
5. С домашней поверхности запускаются другие установленные приложения - из закреплённых, из «последних» и из полного списка.
6. Панель задач даёт постоянный доступ к «Пуску», настройкам Android и выходу из режима лаунчера.
7. Режим лаунчера доступен при любом профиле устройства; профиль лишь задаёт стартовый набор ячеек.
8. Приложение остаётся полнофункциональным: обычный режим доступен по иконке и из самого лаунчера.
9. Если режим лаунчера не включён, приложение работает как раньше, без изменений сценариев и без системных диалогов.

**Non-goals:**

- Полноценная замена стокового лаунчера общего назначения: рабочие столы-страницы, папки, свайп-навигация между экранами.
- Виджеты сторонних приложений (`AppWidget`): только наши блоки (ADR-5).
- Kiosk, lock task, device owner, сокрытие системного status bar (ADR-8).
- Управление содержимым системной шторки за пределами того, что отдаёт Android.
- Управление питанием устройства (выключение/перезагрузка) - без root недоступно.
- Назначение лаунчера в обход пользователя - Android этого не позволяет и не должен.
- Готовые пресеты раскладок рабочего стола - отдельная итерация (§6, item 12).

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Автозапуск: при включении устройства сразу открывается наш рабочий стол.
2. Замена стандартного лаунчера, с возможностью вернуться назад.
3. Пользователь сам настраивает, что показывать на основном экране.
4. Весь готовый функционал приложения доступен из режима лаунчера.
5. Интерфейс в логике Windows: рабочий стол, панель задач, ярлыки, гаджеты, «Пуск», трей.
6. Гаджеты интерактивны, а не декоративны: список песен, список трансляций, часы с погодой - нажимаемые и живые.
7. Панель задач видна всегда, кроме полноэкранного воспроизведения.

### 3.2 Жёсткие ограничения

- **Флейвор:** носитель итерации-1 - `standard`. Публикация лаунчера в Play не требует ни категории, ни декларации, ни спец-ревью (research 12). `vr` исключён: своя OpenXR-оболочка и системный шелл headset'а. Охват `legacy`/`photos`/`lite` - открытый вопрос (§6, item 13). Реализация следует `dev/FLAVOR_DEVELOPMENT_RULES.md`: контракт способности в `src/main/`, поставка флейвор-специфична, без `BuildConfig.IS_*` в `src/main/`.
- **Package visibility:** только `<queries>` с `MAIN` + `LAUNCHER`. Это возвращает ровно все запускаемые приложения без разрешений и деклараций. `QUERY_ALL_PACKAGES` запрещён: лаунчеры не входят в перечень разрешённых применений, а invalid-use «задача решается менее широким методом» применяется к нам напрямую; санкция - вплоть до блокировки аккаунта разработчика (ADR-6, research 12).
- **Роль Home на API 26:** `RoleManager` доступен только с API 29. На minSdk проекта роль берётся через `enabled`-компонент: система показывает системный выбор «Always / Just once» при следующем Home. Это несущий механизм, а не запасной путь (ADR-2).
- **Нет device owner:** Play-установка device owner'ом стать не может никогда. Потолок - screen pinning, из которого пользователь выходит по своему желанию. Kiosk вне объёма эпика (ADR-8).
- **Последние запуски:** только собственный журнал. `UsageStatsManager` требует special-access `PACKAGE_USAGE_STATS` с ручным включением в системных настройках - против принципа zero-setup (ADR-7).
- **Ориентация:** две независимые раскладки (горизонтальная и вертикальная). Жёсткая фиксация ориентации запрещена: она подразумевает требование `screen.*` и режет охват устройств в Play (прецедент S0918/S0934).
- **Производительность:** домашняя поверхность открывается по Home постоянно; холодный и тёплый старт быстрые, без тяжёлой загрузки при каждом возврате; медиаресурсы освобождаются при сворачивании.
- **Совместимость данных:** конфигурация рабочего стола переживает перезапуск; форма хранения - без ломающих изменений для пользователей, не включивших режим.
- **Локализация:** EN/RU/UK - всегда обязательно.
- **Доступность:** навигация и запуск по готовой сетке работают с D-pad/пульта и клавиатуры (устройства без сенсора - ТВ-боксы, медиабоксы). Сборка сетки - палец/мышь; с пульта доступно назначение ярлыка в ячейку (§3.3).

Бывшая Phase 09 тактики снята с S0404.

Решения владельца 2026-07-17 (по итогам разведки фазы 06; обе развилки вскрылись только на гаджетах):

- **Рабочий стол - настоящая 2D-сетка, а не поток ячеек.** Ячейка стоит на своих сохранённых `(rowIndex, colIndex)`, дыры сохраняются, гаджет `2×2` реально занимает два ряда. `RecyclerView` + `GridLayoutManager` (рендерер фазы 04) заменяется своим 2D-контейнером: `GridLayoutManager` умеет только горизонтальные спаны и не умеет позиции, то есть `rowIndex`/`colIndex`/`spanH` из фазы 02 сохранялись в БД, но не доезжали до экрана. Альтернатива «поток плиток» (дёшево, рендерер фазы 04 остаётся) отклонена: это уже не Windows, а рабочий стол GNOME, и она противоречит ADR-3. См. ADR-9.
- **Данные гаджетов «плейлист» и «превью папки»: локальные ресурсы - живьём, сетевые - из кэша.** Лёгкого «дай N файлов ресурса» в проекте нет; путь виджета (`RandomPhotoFrameWidgetRefresher`, только кэш) на домашнем экране означает «Недоступно» после каждой перезагрузки, а живое сканирование бьёт по сети при каждом Home. Правило: локальный ресурс сканируется лениво при появлении гаджета на экране, сетевой/облачный читается из persisted-кэша, а при добавлении гаджета его ресурсу включается `rememberFileList` (сейчас по умолчанию `false`), чтобы и сетевые папки переживали перезагрузку. Home не касается сети никогда. См. ADR-10.

## 4. Контекст текущей архитектуры

Входной поток отвечает за маршрутизацию после старта, а механизм профилей устройства применяет пресеты под сценарий. Профиль - это интент пользователя, зафиксированный один раз: он сеет стартовые дефолты настроек, которые пользователь потом меняет. Матрица профилей - CSV-ассет, не Kotlin-таблица; `CAR_HEAD_UNIT`, `PHOTO_FRAME`, `TV_MEDIA_BOX`, `EBOOK_READER` в ней уже есть.

Профили влияют только на дефолты настроек внутри приложения - они не меняют роль приложения в системе и не дают домашней поверхности.

Сейчас приложение не объявляет себя кандидатом на роль Home, не перечисляет установленные приложения и не имеет экрана-витрины. Поэтому проблему §1 нельзя решить настройками: нужны системная роль Home, домашняя поверхность с сеткой и панелью задач, слой перечисления/запуска приложений и журнал запусков.

Существенно для §5: паттерн «профиль сеет стартовый набор, дальше пользователь владеет результатом» в проекте уже реализован для настроек. Рабочий стол получает ту же механику, а не новую сущность.

## 5. Предлагаемый подход

Ввести опциональную способность «домашний экран устройства»: приложение объявляет себя кандидатом на роль Home, по явному включению пользователем становится кандидатом, получает роль штатным системным механизмом и предоставляет настраиваемый рабочий стол.

Способность строится поверх существующего механизма профилей: профиль сеет стартовый набор ячеек, дальше рабочий стол - собственность пользователя.

### 5.1 Основные столпы / модули

- **Две точки входа.** Обычная активность приложения (иконка) и домашняя поверхность (Home) сосуществуют; система разводит их по intent'у, без runtime-переключателя режима.
- **Включение режима и роль Home.** Компонент домашней поверхности по умолчанию выключен; включение делает приложение кандидатом на Home и приводит к системному выбору; выключение возвращает устройство прежнему лаунчеру.
- **Рабочий стол.** Сетка ячеек: геометрия считается по экрану с ручной подкруткой плотности; один экран со скроллом; две независимые раскладки по ориентации.
- **Ячейка-ярлык.** Сохранённая команда с параметрами: запуск нашего сценария над конкретным ресурсом либо запуск стороннего приложения.
- **Гаджеты.** Наши интерактивные блоки на несколько ячеек, работающие поверх общего контракта блока.
- **Панель задач.** Постоянная полоса: «Пуск», последние запуски, закреплённые иконки, трей. Скрывается только на полноэкранном воспроизведении. Состав настраивается.
- **Меню «Пуск».** Разделы: наши ресурсы, все приложения, настройки (наши + Android), выход из режима лаунчера.
- **Реестр и запуск приложений.** Перечисление запускаемых приложений через декларацию видимости; запуск выбранного; переходы в настройки Android.
- **Журнал запусков.** Собственная история того, что запускалось через лаунчер, - источник «последних».
- **Конфигурация и персистентность.** Хранит раскладки, состав ячеек, настройки панели; переживает перезапуск; не влияет на пользователей, не включивших режим.

### 5.2 Потоки данных и событий

- Включение режима: настройки → включение компонента домашней поверхности → системный выбор лаунчера → возврат статуса → UI-подтверждение.
- Открытие по Home: система → домашняя поверхность → конфигурация раскладки → источники данных гаджетов и реестр приложений → отрисовка.
- Первый запуск режима: профиль устройства → стартовый набор ячеек → сохранение как пользовательской раскладки.
- Запуск ячейки: домашняя поверхность → команда с параметрами → внутренний сценарий или системный запуск приложения → запись в журнал запусков.
- Редактирование: жест на сетке → выбор содержимого ячейки → сохранение раскладки.
- Выключение режима: «Пуск» или настройки → выключение компонента → система возвращается к прежнему лаунчеру.

### 5.3 Точки расширяемости

- Контракт ячейки допускает новые типы содержимого без переделки сетки - в том числе сторонние `AppWidget` отдельным спеком.
- Контракт гаджета допускает новые блоки (погода, Google-контент) - спеки-сиблинги S0426/S0429.
- Реестр приложений абстрагирован от способа перечисления, чтобы менять механику видимости под будущие версии Android.
- Стартовые наборы ячеек - данные, а не код: добавление набора под профиль не требует изменения поверхности.

## 9. Архитектурные решения (ADR)

**ADR-1: Лаунчер как опциональная флейвор-гейтируемая способность**

- **Решение:** способность вводится через интерфейс в общем коде с флейвор-специфичной поставкой; обычный режим приложения от неё не зависит.
- **Альтернативы:** встроить логику лаунчера во входной поток для всех флейворов.
- **Почему:** `vr` не должен её нести; правило проекта запрещает `BuildConfig.IS_*` в `src/main/`; опциональность снижает риск регресса обычного сценария.

**ADR-2: Две точки входа + включение через `enabled`-компонент**

- **Решение:** обычная активность (`LAUNCHER`) и домашняя поверхность (`HOME`) объявляются обе и сосуществуют; система разводит их по intent'у. Домашняя поверхность по умолчанию выключена; настройка включает/выключает её компонент.
- **Альтернативы:** одна активность с runtime-определением режима; отдельный APK лаунчера.
- **Почему:** несёт сразу четыре свойства. Пользователь без режима не видит ничего нового (цель 9). На API 26 `RoleManager` отсутствует, и включение компонента - единственный способ привести систему к выбору лаунчера. Выключение гарантирует выход из режима, не завися от вендорского диалога (риск 2). Обычный режим остаётся доступен по иконке (цель 8).

**ADR-3: Модель рабочего стола Windows**

- **Решение:** поверхность строится как рабочий стол Windows: сетка ярлыков и гаджетов + постоянная панель задач с «Пуском» и треем.
- **Альтернативы:** профиль диктует фиксированный состав экрана; копия стокового Android-лаунчера со страницами и папками.
- **Почему:** владелец сформулировал модель явно, и она отвечает на состав поверхности целиком, включая границы (Non-goals). Модель узнаваема пользователем без обучения. Она же объясняет, почему страниц-рабочих-столов нет: на выделенном устройстве всё должно быть видно сразу.

**ADR-4: Рабочий стол независим от профиля; профиль только сеет стартовый набор**

- **Решение:** профиль устройства задаёт стартовый набор ячеек при первом включении режима; далее раскладка - собственность пользователя, смена профиля её не перезаписывает.
- **Альтернативы:** профиль диктует состав; своя раскладка на каждый профиль; смена профиля сбрасывает сетку.
- **Почему:** повторяет уже работающий в проекте паттерн пресетов настроек (профиль = интент, сеет дефолты, пользователь владеет результатом) - пользователю не надо учить вторую модель. Снимает whitelist профилей: режим доступен при любом профиле, включая `CAR_HEAD_UNIT`. Исключает злой сюрприз потери настроенного стола.

**ADR-5: Только наши блоки, без сторонних `AppWidget`**

- **Решение:** гаджеты - наши View внутри нашей поверхности. Хостинг чужих `AppWidget` вне объёма.
- **Альтернативы:** полноценный `AppWidgetHost` с выборщиком и ресайзом.
- **Почему:** все заявленные владельцем гаджеты - наши по природе (список песен, трансляции, часы с погодой). `AppWidgetHost` - несопоставимо больший объём, чужая вёрстка вне нашего контроля и разрушение D-pad-контракта. Контракт ячейки оставляет дверь открытой (§5.3).

**ADR-6: Реестр приложений через `<queries>`, `QUERY_ALL_PACKAGES` запрещён**

- **Решение:** декларация `<queries>` с `MAIN` + `LAUNCHER` во всех флейворах; флейвор-сплит реестра отменён.
- **Альтернативы:** `QUERY_ALL_PACKAGES` на sideload-флейворе; разные пути для Play и не-Play.
- **Почему:** `<queries>` возвращает ровно множество запускаемых приложений - то, что лаунчеру и нужно, - без разрешений и деклараций. `QUERY_ALL_PACKAGES` добавляет только незапускаемые пакеты, которые нечем запустить. При этом лаунчеры не входят в перечень разрешённых применений, а invalid-use «задача решается менее широким методом» бьёт прямо; для медиа-приложения аргумент core-functionality заведомо слабее, чем у чистого лаунчера. Санкция - блокировка аккаунта. Один путь вместо двух.

**ADR-7: Собственный журнал запусков вместо системной статистики**

- **Решение:** «последние» строятся по истории запусков через наш лаунчер.
- **Альтернативы:** `UsageStatsManager` с `PACKAGE_USAGE_STATS`; гибрид.
- **Почему:** мы лаунчер - через нас и запускают, поэтому на выделенном устройстве собственный журнал практически эквивалентен системному. Ноль разрешений, работает сразу. `PACKAGE_USAGE_STATS` - special access с ручным включением в системных настройках: обязательный ручной шаг против zero-setup и внимание Play к sensitive-доступу.

**ADR-8: Kiosk, lock task и device owner вне объёма эпика**

- **Решение:** лестница привилегий, device owner, скрытие системного бара и «замок» удаляются из S0404.
- **Альтернативы:** kiosk-уровень отдельной итерацией на sideload-флейворе; публикуемый flavor `kiosk`.
- **Почему:** носитель - `standard`, а Play-установка device owner'ом стать не может никогда; потолок - screen pinning, из которого пользователь выходит по желанию, то есть «замка» не выходит. Заявленные сценарии (домашняя фоторамка, магнитола) замка не требуют - владелец устройства и есть его единственный пользователь. Снятие убирает из эпика device-admin-ветку, риск «застрял в kiosk» и требование провизионинга. Возврат к теме - отдельный спек, если появится сценарий с недоверенным пользователем.

**ADR-9: Рабочий стол рисует свой 2D-`ViewGroup`, а не `RecyclerView` + `GridLayoutManager`**

- **Решение:** поверхность сетки - собственный `ViewGroup`: `onMeasure` считает `cellSize = ширина / columns`, каждому ребёнку даёт `EXACTLY(cellSize × spanW) × EXACTLY(cellSize × spanH)`, `onLayout` ставит его в `(colIndex × cellSize, rowIndex × cellSize)`. Контейнер живёт внутри вертикального скролла (§3.3 «один экран + скролл вниз»). Рендерер фазы 04 (`RecyclerView` + `GridLayoutManager` + `LauncherCellAdapter`) заменяется; слои данных, кодек и исполнение команд (фазы 01-03) не трогаются.
- **Альтернативы:** (а) оставить `GridLayoutManager` и принудительно задавать высоту гаджета `cellSizePx × spanH`; (б) признать стол потоком плиток и выкинуть `spanH` из итерации-1; (в) `android.widget.GridLayout` со `spec(row, rowSpan)`.
- **Почему:** `GridLayoutManager` - линейный поток с горизонтальными спанами: он не умеет ни вертикальный спан, ни позицию. То есть `rowIndex`/`colIndex`/`spanH`, которые фаза 02 честно пишет в БД, до экрана не доезжали вообще - сломана была не модель, а рендерер. Вариант (а) - хак: гаджет растянет свою строку, но ярлыки-соседи останутся высотой в ячейку с мёртвой дырой под ними, позиции по-прежнему игнорируются, а после поворота высоту надо принудительно перебивать; и фазе 07 (перетаскивание, §3.3) 2D-контейнер всё равно понадобится - платим дважды. Вариант (б) противоречит ADR-3: без дыр и без вертикальных спанов это рабочий стол GNOME, а не Windows. Вариант (в) отклонён из-за капризной системы весов `GridLayout` при требовании строго квадратных ячеек - свой `onMeasure` короче и предсказуемее. Побочный выигрыш своего контейнера: D-pad начинает работать лучше - `FocusFinder` ходит по геометрии реальных границ (§3.2 «навигация с пульта»), а не по порядку элементов в списке. Рециклинг не теряется: стол - это десятки ячеек, а не лента.

**ADR-10: Гаджеты-по-ресурсу: локальное сканируем лениво, сетевое читаем из кэша, `rememberFileList` включаем при добавлении**

- **Решение:** `PlaylistGadget`/`FolderPreviewGadget` читают файлы так: локальный ресурс - ленивое сканирование при появлении гаджета на экране (в IO, отмена при уходе); сетевой/облачный - только persisted-кэш; при добавлении гаджета его ресурсу включается `rememberFileList`. Home не инициирует сетевой ввод-вывод никогда.
- **Альтернативы:** только кэш (путь `RandomPhotoFrameWidgetRefresher`); всегда живое сканирование, включая сеть.
- **Почему:** лёгкого «дай N файлов по `resourceId`» в проекте нет - есть либо кэш, либо полный `GetMediaFilesUseCase` (требует разрешённый `MediaResource`, ходит в SMB/FTP/SFTP/Cloud). Только кэш ломает фичу ровно там, где она живёт: `MediaFilesCacheManager` - память процесса, `rememberFileList` по умолчанию `false`, поэтому после каждой перезагрузки домашний экран встречает пользователя двумя «Недоступно». Всегда-живое противоречит инварианту поверхности «Home нажимают постоянно, поэтому экран остаётся дешёвым» (§3.2) - сетевой скан на каждом Home жжёт трафик и батарею. Включение `rememberFileList` при добавлении гаджета - осознанная запись в настройку ресурса: пользователь явно попросил показывать эту папку на столе, и persisted-кэш это и обслуживает.

## 11. Критерии готовности (strategic-level)

1. Пользователь включает режим лаунчера в настройках и назначает приложение домашним экраном без падений на поддерживаемых версиях Android.
2. После назначения по кнопке Home открывается домашняя поверхность; при включении устройства она открывается сама.
3. При первом включении рабочий стол не пустой: на нём стартовый набор ячеек по профилю устройства.
4. Пользователь добавляет, убирает и перемещает ячейки; изменения переживают перезапуск.
5. Ячейка-ярлык запускает наш сценарий с сохранёнными параметрами, а не только «открывает приложение».
6. Гаджет на несколько ячеек показывает живые данные и реагирует на нажатие.
7. С панели задач доступны «Пуск», последние запуски, трей, настройки Android и выход из режима лаунчера.
8. Пользователь запускает стороннее приложение из закреплённых и из полного списка.
9. Горизонтальная и вертикальная раскладки настраиваются независимо и не затирают друг друга.
10. По готовой сетке можно навигировать и запускать ячейки с пульта/клавиатуры.
11. Выключение режима возвращает устройство прежнему лаунчеру без сброса и без «застревания».
12. Если режим не включён, приложение работает как раньше и не показывает системных диалогов.
13. Релизная сборка `standard` не содержит `QUERY_ALL_PACKAGES`.
