## 1. Проблема

Сохранение первого кадра GIF как статичного PNG жёстко пишет файл напрямую в публичную папку Downloads через файловый API, существовавший до Android 10, в обход системного медиахранилища. На устройствах с API 29+ и строгим scoped storage (например Pixel на Android 14+) прямой `FileOutputStream` в публичный каталог завершается ошибкой доступа (EACCES), и пользователь не получает сохранённого кадра. Поток сохранения вынесен из объёма S0522 явным non-goal.

---

## 2. Цели

1. Первый кадр GIF сохраняется без ошибки доступа на всех поддерживаемых уровнях API, включая строгий scoped storage на API 29+.
2. Сохранение идёт через тот же общий слой локальной записи с поддержкой медиахранилища, что и остальные операции сохранения в публичные коллекции.
3. Сохранённый кадр виден в системной галерее/файлах сразу после записи, без отдельного ручного уведомления медиасканера там, где медиахранилище индексирует файл само.

**Non-goals:**

- Изменение места назначения (остаётся публичная папка по умолчанию) или ввод выбора ресурса для этого потока.
- Изменение формата кадра (PNG), имени файла или UX диалога редактора GIF.
- Консолидация прочих путей `saveToDownloads` - это объём S0528.

## 4. Контекст текущей архитектуры

В проекте уже есть общий слой локальной записи, который различает публичные коллекции и непубличные пути и корректно публикует файл через системное медиахранилище на scoped storage (введён в S0231, переиспользован S0522 для записи с микрофона и съёмки). Поток сохранения первого кадра GIF появился раньше этого слоя и пишет в Downloads напрямую файловым API, поэтому не получает преимуществ медиахранилища и падает на строгом scoped storage. Проблему из §1 нельзя закрыть точечной правкой пути, потому что прямой файловый доступ к публичной папке на API 29+ запрещён независимо от пути - нужно делегировать запись общему слою.

---

## 5. Предлагаемый подход

Перенаправить запись первого кадра с прямого файлового вывода на общий слой локальной записи: классифицировать целевой путь в публичной папке по умолчанию, открыть приёмник записи через слой, поддерживающий медиахранилище, записать в него сжатый PNG и зафиксировать запись. Поток перестаёт сам открывать файловый поток в публичный каталог и делегирует это общему слою, получая фактический путь/URI сохранённого файла.

### 5.1 Основные столпы / модули

- **Делегирование записи.** Сжатый кадр пишется в приёмник общего слоя локальной записи вместо прямого файлового потока.
- **Классификация назначения.** Целевой путь в публичной папке классифицируется тем же механизмом, что и прочие операции записи, чтобы выбрать публикацию через медиахранилище.
- **Согласование уведомления медиасканера.** Там, где медиахранилище индексирует файл само, отдельный вызов уведомления медиасканера устраняется или становится безвредным.

### 5.2 Потоки данных и событий

- Диалог редактора GIF → слой применения → классификация целевого пути → приёмник общего слоя записи (медиахранилище на API 29+ / файл на более ранних) → фиксация → фактический путь результата.

### 5.3 Точки расширяемости

- Поток сохранения кадра становится ещё одним потребителем общего слоя локальной записи; сигнатура слоя не меняется.
