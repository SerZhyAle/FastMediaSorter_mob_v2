# Стратегическая спецификация: S0415 - Зависание скана SMB-папки (вечная загрузка)

**Roadmap entry:** Ad-hoc - анализ on-device лога (2026-06-14)

---

## 1. Проблема

Открытие SMB-ресурса `Media/apeflac` (LAN-сервер 192.168.1.110, ~1000 файлов, рекурсивный скан) уходит в бесконечную загрузку: скан стартует, но `scan_complete` для этого ресурса не наступает ни разу. Пользователь вынужден жать «StopScan» вручную.

Источник: `logs/fastmediasorter_20260614_045526.log` (standard debug 2.60.6121.144, Samsung SM-S731B, Android 16).

Наблюдения из лога:

- 4 попытки открыть `apeflac` (id=18) подряд (05:01:39, 05:02:56, 05:03:05, 05:03:32) - ни одна не дала `ScanMetrics: scan_complete resourceId=18`.
- Попытка 1: скан стартовал 05:01:39, в 05:01:48 сменилась сеть (`wlan0 → rmnet0`), `SmbConnectionManager: invalidating all SMB connections`, соединение `marked for close but currently in use (count=1)`. Скан продолжал висеть ещё ~70 c, пока пользователь не нажал StopScan в 05:02:49. Само по смене сети не оборвалось.
- Попытка 4: полный скан начат 05:03:47 в окне без смен сети - и тоже не завершился до ухода пользователя (~3 минуты спустя).
- Контраст: другой SMB-ресурс `Media/mp3` (id=19, **3984 файла**) в том же сеансе и том же сетевом окне отсканировался за **3.7 c** (`scan_complete .. duration_ms=3713 file_count=3984`). То есть размер папки не объясняет зависание.
- Соединение к серверу в окне `apeflac` подтверждённо рабочее: 05:02:55 `Connection test OK: Resource accessible: 192.168.1.110\Media` (134 ms).

Из этого следуют два потенциально независимых дефекта (см. §6).

---

## 2. Цели

1. Скан SMB-папки `apeflac` доходит до конца и показывает содержимое (или честную ошибку), а не висит бесконечно.
2. Активный скан прерывается быстро и предсказуемо при потере/смене сети - без многосекундного зависания на мёртвом сокете; пользователю показывается восстановимое состояние, а не вечный спиннер.
3. «StopScan» остаётся доступным, но не единственным способом выйти из зависшего скана.

**Non-goals:**

- Переписывание пула SMB-соединений целиком.
- Гарантия скана при полностью оборванном Wi-Fi (LAN недостижим - честная ошибка, не зависание).
- Перекрытие со стримингом воспроизведения SMB (это S0344 - другой путь).

---

## 3. Пожелания и ограничения

- **Flavor:** общий data-путь скана, все сборки с поддержкой SMB; без `BuildConfig`-гейтов в `src/main/` (Rule 15).
- **Сеть устройства:** в логе зафиксирована частая чехарда `wlan0 ↔ rmnet0` (11+ переключений за сеанс) - окружение нестабильно; приложение обязано деградировать предсказуемо, но «починить» Wi-Fi пользователя не может.
- **API level:** наблюдение на Android 16 / API 36; без API-специфики.
- **Связь:** S0344 (робастность SMB-стриминга воспроизведения) - родственный, но непересекающийся путь.

---

## 4. Контекст текущей архитектуры

Скан запускается через `get-media-files` → `scanFolderChunked` → `SmbClient.scanMediaFilesChunked` (рекурсивный, `scanSubdirectories=true`, `maxFiles=1000`). Отмена сейчас инициируется только пользовательским «StopScan» (`cancelScan: forceCancel=true`). `SmbConnectionManager` при смене сети логирует `invalidating all SMB connections`, но активное соединение, помеченное `in use`, закрывается лишь «после использования» - а заблокированное чтение из мёртвого сокета не возвращается, значит «после использования» не наступает.

## 5. Открытые вопросы / Research items

1. **Контент против сети.** Изолировать: воспроизводится ли зависание `apeflac` на стабильном Wi-Fi с **выключенными** мобильными данными? Если да - дефект в контенте/обходе папки, а не в сети.
   - **Нужно выяснить:** что специфично у `apeflac` против `mp3` (глубина вложенности, число подпапок, спецсимволы в именах, размер одного элемента, тип `.ape`/`.flac`, cue-листы).
   - **Статус:** Open

2. **Отмена скана при смене сети.** Почему `invalidating all SMB connections` не прерывает заблокированное чтение активного скана? Нужен ли форс-cancel `loadFilesJob` на колбэке смены сети (как при ручном StopScan) и/или socket read-timeout, чтобы скан падал быстро вместо 70-секундного зависания.
   - **Статус:** Open

3. **Read/connect timeout скана.** Есть ли на пути `scanMediaFilesChunked` эффективный таймаут чтения? В логе 70 c без срабатывания таймаута - похоже, нет. Определить бюджет и точку внедрения.
   - **Статус:** Open

## 6. Гипотезы первопричины

- **H1 (сеть):** смена активной сети инвалидцирует SMB-соединение, но заблокированное чтение активного скана не прерывается и не имеет таймаута → вечный спиннер до ручного StopScan. Подтверждено 70-секундным зависанием на попытке 1.
- **H2 (контент папки):** рекурсивный обход `apeflac` зависает на конкретном элементе/поддереве независимо от сети. Подтверждается тем, что попытка 4 не завершилась в сетево-стабильном окне, где `mp3` (вчетверо больше файлов) прошёл за 3.7 c. Требует device-репро по §5.1.

H1 и H2 не взаимоисключающие - вероятно оба вклада. H1 чинится резистентностью к смене сети + таймаутом; H2 - после изоляции на устройстве.

---

## 7. Критерии готовности (strategic-level)

1. Закрыт §5.1 (контент-vs-сеть) с device-репро.
2. Активный SMB-скан прерывается ≤ нескольких секунд при смене/потере сети, без ручного StopScan; пользователю - восстановимое состояние/ошибка.
3. `apeflac` открывается с показом содержимого либо честной ошибкой; вечной загрузки нет.
