## 1. Проблема

Проверка согласованности технической документации с проектом завершалась успешно, хотя не контролировала часть уже опубликованных значений платформы и версии схемы данных. Из-за этого изменение исходной конфигурации могло оставить документацию устаревшей без сигнала в локальной проверке или CI. Ошибка не влияет на выполнение приложения, но делает технические документы ненадёжным источником для разработки и сопровождения.

## 2. Цели

1. Проверка обнаруживает расхождение текущих значений compileSdk и targetSdk между исходной конфигурацией и технической документацией.
2. Проверка обнаруживает расхождение текущей версии схемы данных между исходным контрактом и технической документацией.
3. Исторические записи документации не выдаются за текущий контракт.
4. Регрессионные проверки подтверждают как успешный путь, так и отказ при подмене каждого нового актуального значения.

**Non-goals:**

- Изменение Android-конфигурации, схемы данных или пользовательского поведения.
- Автоматическое переписывание документации по исходному коду.
- Расширение проверки на все упоминания версий без подтверждённого владельца текущего контракта.

## 4. Контекст текущей архитектуры

Проверка строит набор канонических значений из проектной конфигурации, извлекает явные значения из технических документов и сопоставляет их по декларативному перечню. Сейчас этот перечень фиксирует лишь часть платформенных пинов, а источник версии схемы данных в нём отсутствует. Поэтому документ с устаревшим текущим утверждением способен пройти проверку как необязательный пропуск.

## 5. Предлагаемый подход

Расширить модель канонических пинов отдельными источниками для актуальной SDK-конфигурации и версии схемы данных. В декларации документации явно описать актуальные места, которые обязаны совпадать, и исключить исторический контекст из поиска текущего значения. Регрессионная оболочка будет проверять сохранение зелёного базового состояния и диагностируемый отказ при намеренном расхождении.

### 5.1 Основные столпы / модули

#### Канонические источники

Извлечение получает все проверяемые значения из фактической конфигурации и контракта данных, а не из дублирующего документа.

#### Декларативное сопоставление

Для каждого актуального документа задаются обязательность, область поиска и единый формат сравнения.

#### Регрессионная защита

Автономные сценарии фиксируют различие между актуальным контрактом и исторической справкой.

### 5.2 Потоки данных и событий

Исходная конфигурация и контракт данных -> канонические значения -> декларация документации -> извлечённые упоминания -> классификация -> стабильный отчёт и код выхода.

### 5.3 Точки расширяемости

Новые подтверждённые пины добавляются декларативно с явным источником, обязательностью и областью исключения. Источник, который не является Gradle-конфигурацией, получает отдельный узкий извлекатель вместо неявного поиска по всем исходникам.

## 9. Архитектурные решения (ADR)

**ADR-1: Явные канонические источники для не-Gradle контракта**

- **Решение:** добавить узкий источник версии схемы данных и не выводить её из документации.
- **Альтернативы:** не проверять версию схемы или искать число во всём исходном дереве.
- **Почему:** текущий контракт должен иметь единственный проверяемый источник, а широкий поиск создаёт ложные совпадения.
