## 1. Проблема

На проекте есть два качественно разных действия, которые в разговоре оба называются «сборкой», и из-за этого путаются. Первое - локальная сборка APK для проверки правки, она бесплатна и делается часто. Второе - публикация версии в сторы, которая запускает платный CI на GitHub и требует длинной последовательности шагов. Владелец опасается, что просьба «собери» приведёт к лишнему расходу минут GitHub Actions, и что при настоящей публикации что-то забудут.

Фактически разделение уже существует на уровне git и CI: разработка идёт в ветках `DEBUG-v0NN`, а все workflow-триггеры завязаны только на `main` и PR в `main`. Но это нигде не закреплено как термин, не задокументирована стоимость каждого потока, и нет защиты от случайного прямого пуша в `main`, который запустил бы платный CI вне контролируемого релизного пайплайна.

---

## 2. Цели

1. На проекте закреплены два термина с однозначным значением: «сборка» (build) - локально, бесплатно, часто; «релиз» (release) - ветка `main`, платный CI, редко.
2. Задокументирована стоимость GitHub Actions для каждого потока: «сборка» = 0 минут, платный CI стартует только при входе в `main`.
3. Существует одностраничный глоссарий, связывающий каждое понятие с уже существующими командами `a.ps1` и скилами (`/build`, `/skill-release`) - без дублирования инфраструктуры.
4. Случайный прямой пуш в `main` вне релизного пайплайна перехватывается и предупреждает разработчика до того, как запустится платный CI.
5. Мёртвый CI-триггер на несуществующую ветку `develop` удалён, чтобы конфигурация не вводила в заблуждение.

**Non-goals:**

- Не создаём новый релизный механизм - `/skill-release` остаётся единственным входом в публикацию.
- Не меняем модель ветвления (`main` + `DEBUG-v0NN`) и не трогаем релизный worktree.
- Не дублируем 13-шаговый чеклист `/skill-release` - опираемся на него ссылкой.
- Не вводим новые платные CI-прогоны и не переносим существующие на другие триггеры.

## 4. Контекст текущей архитектуры

За локальную сборку отвечает лаунчер `a.ps1` (быстрые цели `dq`/`d`, проверки `fc`/`fk`, commit+push `c`) и скил `/build`. За публикацию отвечает скил `/skill-release` с релизным worktree на ветке `main` и набором публикующих скриптов. CI-конфигурация GitHub Actions триггерится исключительно на `main` и PR в `main`, поэтому пуш в `DEBUG-v0NN` платных прогонов не вызывает.

Проблему из §1 нельзя закрыть «само собой», потому что разделение существует фактически, но не как осознанный контракт: нет термина, нет документа о стоимости, нет барьера, который бы не дал случайно отправить коммит в `main` напрямую и тем самым запустить платный CI вне `/skill-release`.

## 5. Предлагаемый подход

Закрепить «сборку» и «релиз» как формальные понятия процесса через документ-глоссарий и один защитный барьер, не создавая параллельной инфраструктуры. Существующие команды и скилы остаются единственными исполнителями; новое - только их именование, описание стоимости и страховка от ошибочного входа в `main`.

### 5.1 Основные столпы / модули

- **Глоссарий процесса.** Единый dev-документ, дающий определения «сборки» и «релиза», явную таблицу стоимости CI по веткам/триггерам и маппинг каждого понятия на конкретные команды `a.ps1` и скилы. Источник правды для терминологии; на него ссылаются `/build` и `/skill-release`.
- **Guard прямого пуша в `main`.** Барьер, который при попытке отправить коммит напрямую в `main` из обычного рабочего каталога предупреждает и требует осознанного подтверждения. Релизный поток (worktree на `main`, управляемый `/skill-release`) - легитимное исключение и не должен блокироваться.
- **Чистка CI-конфигурации.** Удаление мёртвого триггера на несуществующую ветку `develop`, чтобы карта стоимости из глоссария совпадала с реальной конфигурацией.

### 5.2 Потоки данных и событий

- Поток «сборка»: правка → локальная сборка → локальная проверка → commit+push в `DEBUG-v0NN`. Внешних эффектов нет, CI = 0.
- Поток «релиз»: `/skill-release` → merge `DEBUG-v0NN` → `main` → срабатывают CI-триггеры (`main`/PR) → сборка релизных артефактов → публикация по каналам. Единственное место расхода минут Actions.
- Поток guard: попытка записи в `main` вне релизного worktree → предупреждение → явное подтверждение или отмена.

### 5.3 Точки расширяемости

- Глоссарий должен расширяться при добавлении новых CI-workflow или новых каналов публикации - карта стоимости и маппинг команд остаются единым местом правды.
- Guard должен описываться так, чтобы список легитимных исключений (релизный worktree, ветка `main` под управлением `/skill-release`) можно было дополнять без переписывания логики.

## 6. Открытые вопросы / Research items

1. **Карта CI-триггеров и стоимости**
   - **Вопрос:** какие именно workflow и на каких триггерах расходуют минуты GitHub Actions, и подтверждается ли, что пуш в `DEBUG-v0NN` не запускает ничего.
   - **Нужно выяснить:** перечислить все workflow и их `on:`-условия, сверить с моделью ветвления.
   - **Статус:** Resolved
   - **Артефакт:** `PLAN/S0752_build-vs-release-workflow/research/01__ci-triggers-cost-map.md`

2. **Механизм guard для прямого пуша в `main`**
   - **Вопрос:** чем реализовать барьер - локальным git-хуком (`pre-push`), обёрткой в `a.ps1`, или комбинацией; как отличить легитимный релизный путь от ошибочного.
   - **Варианты:** локальный `pre-push` hook в рабочем каталоге; проверка в `commit-push.ps1`/`a.ps1`; различение по worktree-пути.
   - **Нужно выяснить:** какой вариант не мешает `/skill-release`, переносится между машинами и не требует ручной установки на каждой.
   - **Статус:** Resolved - git `pre-push` hook, активируемый через `core.hooksPath`, с различением worktree по имени каталога (релизный worktree освобождён) и env-override как запасным выходом.
   - **Артефакт:** `PLAN/S0752_build-vs-release-workflow/research/02__main-push-guard-mechanism.md`

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Guard ложно срабатывает на легитимном релизном пуше | Средняя | `/skill-release` прерывается | Явно вынести релизный worktree/`main`-под-управлением в исключения; тест на обоих путях |
| Локальный git-хук не переносится между машинами | Средняя | Защита не действует у части окружений | Хранить хук в репозитории и описать одноразовую установку, либо дублировать проверку в `a.ps1` |
| Глоссарий разойдётся с реальными CI-триггерами после будущих правок workflow | Низкая | Документ вводит в заблуждение | Зафиксировать правило обновлять карту стоимости при любой правке workflow |

## 9. Архитектурные решения (ADR)

**ADR-1: Документ + barrier вместо новой релизной обёртки**

- **Решение:** закрепить понятия глоссарием и одним guard-барьером, переиспользуя существующие `a.ps1` и `/skill-release`.
- **Альтернативы:** ввести новые umbrella-команды `a.ps1 build` / `a.ps1 release` как единые входы.
- **Почему:** инфраструктура уже существует и покрывает оба потока; новые обёртки создали бы дублирование и второй источник правды. Владелец подтвердил объём «глоссарий + guard + чистка CI», а не новые команды.

## 11. Критерии готовности (strategic-level)

1. Существует dev-документ, дающий определения «сборки» и «релиза» с явной картой стоимости CI и маппингом на команды/скилы.
2. В документе зафиксировано и подтверждено, что пуш в `DEBUG-v0NN` не запускает ни один GitHub Actions workflow.
3. Попытка прямого пуша в `main` из обычного рабочего каталога перехватывается и требует осознанного подтверждения; релизный путь `/skill-release` при этом не блокируется.
4. Мёртвый триггер на ветку `develop` удалён из CI-конфигурации.
5. Скилы `/build` и `/skill-release` ссылаются на глоссарий как на источник терминологии.
