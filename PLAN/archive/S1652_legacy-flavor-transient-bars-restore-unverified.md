# S1652 - legacy-flavor-transient-bars-restore-unverified

**Status:** Archived
**Priority:** 35
**Tier:** 2 - Easy (ad-hoc)
**Date:** 2026-08-14

## 0. Захваченный материал (verbatim)

Обнаружено при закрытии S1202 (2026-08-14), измерение на Galaxy S21, API 35.

S1202 определил, что на API 30+ сигналом «transient-бары появились» служит
`WindowInsetsAnimationCompat.Callback` на `android.R.id.content`, и привёл к нему
`StandaloneFullscreenManager.setupTransientBarsExitCallback`. Замер выполнен только на API 35.

Диапазон API 23..29 остался непроверенным. Там `WindowInsetsControllerCompat.hide()` и
`BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE` работают через обратно-портированные флаги
(`SYSTEM_UI_FLAG_IMMERSIVE_STICKY` и соседние), а не через `WindowInsetsController`, и
`WindowInsetsAnimationCompat` на этих уровнях - это compat-эмуляция поверх диспатча инсетов,
а не платформенная анимация. Sticky-бары инсеты не меняют, поэтому есть основание считать,
что compat-эмуляция там не сработает и путь «свайп возвращает командную панель» остаётся мёртвым.

Устройства этого диапазона под рукой не было. Слать туда непроверенный код хуже, чем не трогать,
поэтому S1202 закрыт с явно заявленным непокрытым диапазоном вместо догадки.

## 1. Проблема

Флавор `legacy` собирается с `minSdk 23`, остальные - с `26`. На устройствах API 23..29
восстановление командной панели свайпом от края в обоих standalone-хостах не проверено и,
предположительно, не работает.

Пользователь при этом не заперт: видимая кнопка выхода из фуллскрина (S1115) от уровня API
не зависит и работает везде. Это деградация запасного пути, а не потеря выхода - та же
формулировка, что и в S1202.

## 2. Цель

Определить, какой сигнал означает «transient-бары появились» на API 23..29, и либо привести
к нему `setupTransientBarsExitCallback` под версионной веткой, либо зафиксировать, что на этих
уровнях запасного пути нет и кнопка выхода остаётся единственным.

## 3. Ограничения и рамки

- Правка не должна менять поведение на API 30+: оно измерено в S1202 и работает.
- Кандидат номер один - устаревший `setOnSystemUiVisibilityChangeListener`. На API 30+ он
  бесполезен (S1115, подтверждено замером S1202), но именно для флагового мира он и был сделан.
- Оба вызывающих колбэка идемпотентны, двойной триггер безопасен.

## 6. Открытые вопросы / Research items

1. Срабатывает ли `WindowInsetsAnimationCompat.Callback` на API 23..29 при sticky-immersive
   свайпе, или compat-эмуляция молчит, потому что инсеты не меняются? Статус: **Resolved** - молчит.

   `WindowInsetsAnimationCompat.setCallback` ниже API 30 уходит в `Impl21.setCallback`, который
   ставит на вью прокси-`View.OnApplyWindowInsetsListener` (`Impl21OnApplyWindowInsetsListener`) и
   собирает анимацию из разницы между прошлым и новым набором инсетов. Источник прочитан локально:
   `androidx.core:core:1.16.0`, `WindowInsetsAnimationCompat.java`, строки 519-523 (выбор реализации)
   и 622-644, 743-764 (прокси-слушатель). Sticky-бары инсетов не меняют, диспатча нет - значит нет и
   анимации, которую можно было бы наблюдать.

2. Если молчит - достаточно ли `setOnSystemUiVisibilityChangeListener` под веткой
   `SDK_INT < R`, и не возвращает ли он ложное срабатывание при входе в фуллскрин?
   Статус: **Resolved** - не срабатывает вовсе, поэтому вопрос о ложных срабатываниях снимается.

   `WindowInsetsControllerCompat.Impl20.setSystemBarsBehavior` отображает
   `BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE` ровно в один флаг - `SYSTEM_UI_FLAG_IMMERSIVE_STICKY`
   (тот же файл, строки 542-545). А документация платформы про этот флаг говорит прямо: свайп
   показывает бары полупрозрачными, **ни один флаг при этом не снимается и колбэки видимости
   system UI не вызываются** ([Hide system bars for immersive
   mode](https://developer.android.com/develop/ui/views/layout/immersive)). Тот же документ называет
   и обходной путь - обычный `IMMERSIVE` вместо sticky с ручным возвратом в фуллскрин по таймеру, -
   но это смена поведения фуллскрина, а не восстановление сигнала, и §3 запрещает менять поведение.

**Вывод:** на API 23..29 доступного сигнала нет, и версионная ветка его не создаст. Работает вторая
ветка цели из §2: зафиксировать отсутствие запасного пути. Кнопка выхода (S1115) от уровня API не
зависит и остаётся единственным выходом ниже API 30.

## 7. Риски

- Требуется реальное устройство или AVD с API 23..29. На AVD свайп от края может не
  инжектироваться - ровно это заблокировало S1202 на эмуляторе.

## 10. Связи с другими спеками

- S1202 (`transient-bars-restore-signal-unverified`) - решил ту же задачу для API 30+ и явно
  вынес сюда непокрытый диапазон.
- S1115 (`player-exit-fullscreen-button`) - ввёл кнопку выхода, которая работает на всех уровнях.

## 11. Критерии готовности (strategic-level)

- На устройстве или эмуляторе API 23..29 свайп от края возвращает командную панель в обоих
  standalone-хостах, либо в спеке зафиксировано измерением, что доступного сигнала там нет.
- Поведение на API 30+ не изменилось.

## Last Audit

**Дата:** 2026-08-14
**Вердикт:** Verified

**Что сделано:** оба вопроса §6 закрыты, вывод перенесён в KDoc
`StandaloneFullscreenManager.setupTransientBarsExitCallback` - чтобы следующий, кто увидит эту дыру,
не начинал расследование заново и не добавлял версионную ветку в расчёте на несуществующий сигнал.

**Изменение поведения:** нет. Правка целиком в комментарии, исполняемых строк не тронуто, поэтому
второй критерий §11 (поведение на API 30+ не изменилось) выполнен по построению.

**Чем доказано и чем нет - честно.** Первый критерий §11 просил *измерение*. Измерения на устройстве
API 23..29 не проводилось. Вместо него вопрос закрыт статически, и вот из чего это следует:

- отображение поведения в флаг - прочитано в исходниках той версии AndroidX, которая собирается в
  этом проекте (`androidx.core:core:1.16.0` из локального кэша Gradle), а не в статье о ней;
- поведение самого флага - процитировано из документации платформы, и формулировка там отвечает
  ровно на заданный вопрос: колбэки видимости не вызываются, флаги не снимаются;
- отсутствие диспатча инсетов при sticky-барах - следствие первых двух, а не отдельное допущение.

Почему не эмулятор: образ API 26 в системе есть, но §7 уже называет риск, из-за которого S1202
встал на эмуляторе - свайп от края туда не инжектируется. Прогон, который не может показать
положительный исход, не отличает «сигнала нет» от «свайпа не было», то есть добавил бы к выводу
ноль. Если положительное измерение когда-нибудь понадобится, оно требует железа API 23..29, и в
этом случае цена вопроса - один комментарий в коде, а не поведение приложения.
