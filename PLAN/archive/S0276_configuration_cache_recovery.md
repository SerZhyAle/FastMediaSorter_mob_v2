## 1. Проблема

Gradle Configuration Cache в проекте отключён глобально через `org.gradle.configuration-cache=false` в `gradle.properties`. Причина — плагин Chaquopy 17.x, используемый только в flavor `noLegal`, удерживает в task-actions несериализуемые типы Gradle API (DefaultProject, DefaultConfigurationContainer, DefaultDependencyHandler, ReentrantLock, ReferenceQueue). Они вызывают `ConfigurationCacheError` на фазе store, причём ошибка бросается из `onError()` независимо от `problems=warn`.

Решение "выключить кэш на проект целиком" принято в S0174 / S0175 как кратчайший путь к стабильной сборке `noLegal`. Платят за это, однако, все остальные flavor: `standard`, `lite`, `photos`, `legacy`. Конфигурационная фаза Gradle прогоняется заново на каждой инкрементальной сборке тех flavor, где Chaquopy вообще не подключается (`isNoLegalBuild` остаётся `false`). В повседневной разработке преобладают именно эти flavor — `standard` для основного цикла, `lite`/`photos`/`legacy` для проверки flavor-инвариантов. Стартовый overhead Gradle конфигурации платится в каждом цикле "правка → ассемблер", и за день копится в заметные минуты.

Дополнительный фактор — крупные Kotlin-файлы и многомодульная архитектура (`app_v2` + `wear`) увеличивают абсолютный вес фазы конфигурации, что делает кэш потенциально более ценным в этом проекте, чем в среднем Android-приложении.

Проверка `gradle.properties` на 2026-05-20 подтверждает, что глобальное значение `org.gradle.configuration-cache=false` всё ещё активно, а комментарий про отдельные noLegal-скрипты с `--no-configuration-cache` остаётся в силе.

Задача — выяснить, можно ли вернуть конфигурационный кэш для не-noLegal flavor, не сломав сборку `noLegal`, и зафиксировать ответ доказательно. Если выяснится, что Gradle не предоставляет безопасных механизмов изоляции — этот вывод фиксируется как итог и работа закрывается.

## 2. Цели

2. Если ответ положительный — определить безопасную форму активации (на уровне свойств свойства, на уровне опт-аутов конкретных тасок, через дедицированные обёртки сборки) и зафиксировать её как направление для тактической спеки.

4. Не вносить регрессию в IDE-sync: Android Studio должна продолжать показывать все flavor в Build Variants и не падать на синхронизации.
5. Зафиксировать в `dev/CHANGELOG.md` и в спек-журнале путь принятия решения (включая negative result — если решение "оставить как есть").

- Не вводить параллельный buildSrc / Convention plugin layer ради обхода ограничения.
- Не переписывать `app_v2/build.gradle.kts` сверху вниз — изменения исследовательские, ограничены минимально необходимым перечнем.
- Не трогать настройки локального build cache (`org.gradle.caching`) и `org.gradle.parallel` — это смежные оптимизации со своей семантикой.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Если эксперимент показывает, что для `standard` / `lite` / `photos` / `legacy` конфигурационный кэш безопасно включается — путь активации должен быть прозрачным для повседневной работы. Идеально: разработчик, собирающий `standard`, получает кэш автоматически, без дополнительных флагов. Разработчик, собирающий `noLegal`, не делает ничего сверх того, что делает сейчас.
2. Скрипты сборки (`scripts/builders/build-*-debug.ps1`) должны оставаться единственной точкой управления — повседневный поток не требует ручных опций конфигурационного кэша на уровне CLI.
3. Если в ходе исследования выяснится, что включение конфиг-кэша даёт малый выигрыш на этом проекте (например, конфигурационная фаза дешевле, чем казалось) — это валидный итог. Решение принимается по реальной экономии, не по идеологии "кэш всегда хорошо".
4. Если выясняется частичная совместимость (например, кэш работает для `assemble*`, но ломается на `bundle*` / `connectedAndroid*` / `test*`) — это тоже валидный итог. Включаем только то подмножество, где кэш безопасен.

### 3.2 Жёсткие ограничения

- **Сборка noLegal не регрессирует.** После любой правки `scripts/builders/build-nolegal-debug.ps1` (и release-вариант) производит работоспособный APK с Chaquopy-runtime. Любое решение S0276 обязано это сохранить.

- **Конфигурационный кэш Gradle не имеет публичного API для условного отключения из `settings.gradle.kts`.** Кэш инициализируется до evaluation `settings`. Любое решение строится в рамках этого ограничения (выводы S0175 — отправная точка, не зона дискуссии).

- **Локализация:** Не затрагивается — пользовательских строк нет.

## 4. Контекст текущей архитектуры

### 4.1 Почему кэш отключён сейчас

`gradle.properties` фиксирует `org.gradle.configuration-cache=false` с подробным комментарием: Chaquopy 17.x держит в своих task-actions ссылки на типы, которые не сериализуются конфигурационным кэшем. На фазе `store` Gradle вызывает `onError()` плагина CC, и тот бросает `ConfigurationCacheError` независимо от уровня `problems` (даже при `warn`). Технический разговор задокументирован в S0174 / S0175.

Gradle CC инициализируется в самом начале — до того, как `settings.gradle.kts` начнёт evaluation. Это означает, что условный опт-аут "если в taskNames встретилось `noLegal` — выключить CC" из `settings.gradle.kts` сделать нельзя: к моменту, когда такое условие могло бы сработать, кэш уже инициализирован. Поэтому решение S0175 — глобальное выключение через `gradle.properties` плюс явный `--no-configuration-cache` в `scripts/builders/build-nolegal-debug.ps1`.

### 4.2 Где живёт Chaquopy в графе сборки

`app_v2/build.gradle.kts` применяет плагин Chaquopy **условно**, только если `isNoLegalBuild` — true. Активация определяется по трём источникам (в порядке приоритета): явный `-Pchaquopy.enabled=true|false`, авто-детект по наличию `noLegal` в `gradle.startParameter.taskNames`, fallback `chaquopy.enabled=true` в `local.properties`. Когда `isNoLegalBuild = false`, плагин **не применяется**, его task-actions не создаются, и ни один из проблемных классов в graph не попадает.

Парадокс: при `assembleStandardDebug` плагина Chaquopy в графе нет, но конфигурационный кэш остаётся выключенным. Платят за безопасность сборки `noLegal` все flavor. Это и есть пространство возможной экономии.

### 4.3 Как сегодня собирают noLegal vs standard

`scripts/builders/build-nolegal-debug.ps1` вызывает Gradle с явными флагами: `-Pchaquopy.enabled=true` и `--no-configuration-cache`. Обе опции дублируют намерение — первая включает Chaquopy, вторая отключает CC локально для этой инвокации. Глобальный `org.gradle.configuration-cache=false` делает второй флаг тавтологичным сегодня, но он останется единственной защитой, если глобальное значение будет переключено на `true`.

`scripts/builders/build-standard-debug.ps1` вызывает Gradle с `-Pchaquopy.enabled=false`. Этого достаточно, чтобы Chaquopy не подключился, но никаких опций конфигурационного кэша скрипт не передаёт — он полагается на глобальное значение из `gradle.properties`. Аналогично выглядят `build-lite-debug.ps1`, `build-photos-debug.ps1`, `build-legacy-debug.ps1`.

VR-сборка через hierarchy `standard ⊂ vr ⊂ noLegal` (S0250) исторически собиралась как `vrDebug`. После унификации S0250 sideload-VR-канал обслуживается через `noLegal`. С точки зрения этой спеки VR относится к "опт-аут пути" — той же стороны, что `noLegal`.

### 4.4 Что про это знает Gradle / AGP

Gradle 9.x объявляет конфигурационный кэш стабильным. Документация явно описывает per-task опт-аут через `notCompatibleWithConfigurationCache("<reason>")` и через DSL `tasks.named("foo") { notCompatibleWithConfigurationCache("reason") }`. Это первый кандидат на изоляцию Chaquopy-тасок — если их перечислимый набор статичен, плагин при инициализации можно "пометить" как несовместимый, и CC проигнорирует именно их, продолжая работать для остальных.

AGP 9.2.1 в основной массе тасок совместим с конфигурационным кэшем. Большинство известных регрессий в AGP 8.x исправлены в 9.x line.

Открытым остаётся вопрос: совместимы ли все тяжёлые задачи проекта (`KaptGenerateStubsTask`, KSP-задачи, Hilt-задачи, native build CMake, R8) с конфиг-кэшем в текущей версии. Это требует прямой проверки.

## 5. Предлагаемый подход

Подход исследовательский. Цель тактической фазы — собрать измеримые данные, на основании которых принимается окончательное решение. Здесь фиксируется только структура исследования, не его выводы.

### 5.1 Исследование совместимости (data-collection)

- Воспроизвести текущий baseline: время "конфигурационная фаза" замеряется отдельно от "ассемблер" для `standardDebug`, `liteDebug`, `photosDebug`, `legacyDebug`, `noLegalDebug` при выключенном CC (текущее состояние). Цель — иметь точку отсчёта для оценки потенциальной экономии.
- Прогнать каждую сборку с локальным `--configuration-cache` (без правки `gradle.properties`) и собрать список фактических ошибок CC store: какие именно задачи, какие именно классы, какие именно сериализационные проблемы. Включая `standard` / `lite` / `photos` / `legacy` — там Chaquopy не подключён, и список проблем должен быть существенно короче или пустым.
- Сравнить полученные списки для `noLegalDebug` с тем, что задокументировано в S0174 / S0175 — убедиться, что состав ошибок не изменился (если изменился — это самостоятельный сигнал, заслуживающий заметки в `dev/CHANGELOG.md`).
- Проверить, есть ли в публичных issue-трекерах Chaquopy / Gradle / AGP свежие фиксы или обходные пути за период, прошедший после принятия S0175. Источники: GitHub issues Chaquopy, Gradle release notes (9.5+, если опубликованы к моменту работы), AGP changelog.

### 5.2 Вариант A — per-task opt-out

Если выясняется, что Chaquopy-задачи имеют стабильные имена / класс-маркеры, и Gradle API `notCompatibleWithConfigurationCache` достаточно для исключения их из CC, путь становится:

- На уровне `app_v2/build.gradle.kts` после `apply(plugin = "com.chaquo.python")` дополнительно регистрируется обход по всем зарегистрированным Chaquopy-задачам с явным маркером несовместимости.
- Глобально CC включается (`org.gradle.configuration-cache=true`).
- `noLegal`-сборка получает корректное предупреждение "эти задачи не закэшированы", но падения CC store не происходит — Gradle сам обходит проблемные задачи.
- Прочие flavor получают полностью кэшируемую конфигурационную фазу.

Этот вариант — наиболее желательный, потому что он не требует разделения скриптов сборки.

### 5.3 Вариант B — per-flavor activation через свойство

Если per-task opt-out не работает (например, Chaquopy создаёт несериализуемые ссылки не в task-actions, а в hooks конфигурации, или непредсказуемо в onVariants), путь становится явный per-invocation control:

- Глобально CC остаётся выключенным (`org.gradle.configuration-cache=false`).
- В `gradle.properties` появляется маркер default-state, на CLI / в скриптах сборки явно включается `--configuration-cache` для не-noLegal flavor.
- `scripts/builders/build-standard-debug.ps1`, `build-lite-debug.ps1`, `build-photos-debug.ps1`, `build-legacy-debug.ps1` получают флаг `--configuration-cache` (или `-Dorg.gradle.configuration-cache=true`) явно.
- `scripts/builders/build-nolegal-debug.ps1` и `build-nolegal-release.ps1` остаются как есть с `--no-configuration-cache`.
- Платит за это разработчик, собирающий `noLegal` руками через `./gradlew assembleNoLegalDebug` без обёртки — он обязан помнить флаг. Это смягчается тем, что скрипт сборки — рекомендованный путь, плюс активация через `-Pchaquopy.enabled=auto` всё ещё работает.

### 5.4 Вариант C — дедицированный wrapper для noLegal

Подвариант B: вместо передачи флагов CLI создаётся wrapper-скрипт, который добавляет `--no-configuration-cache` автоматически для любого вызова с `noLegal` в task-names. Это уменьшает риск "разработчик забыл флаг". Wrapper живёт в `scripts/` (например, `scripts/builders/gradlew-safe.ps1` или extension в `a.ps1`).

Этот подвариант рассматривается, только если вариант A технически невозможен и сценарий "обычная команда Gradle на noLegal без скрипта" реалистичен в повседневной работе.

### 5.5 Fallback план — оставить как есть

Если эксперимент покажет, что:

- per-task opt-out не работает,
- разделение через свойство приводит к нестабильному IDE-sync,
- или измеренная экономия не превышает шум измерения (например, конфигурационная фаза для не-noLegal flavor занимает <2 секунд в установившемся режиме инкрементальной сборки) —

спек закрывается со статусом "проверено, бенефита нет", и в `gradle.properties` остаётся текущий комментарий, дополненный ссылкой на S0276 как доказательную базу. Это не "провал", это валидный итог исследовательской спеки.

   - **Статус:** Resolved 2026-05-20 (информационный). В публичном changelog/version summary Chaquopy 17.0 заявлена совместимость с AGP 9.2 и min API 24, но явной поддержки Gradle Configuration Cache не заявлено.

4. **CC-совместимость AGP 9.2.1 для всех тяжёлых задач проекта.**
   - **Вопрос:** Кроме Chaquopy, есть ли в текущем графе сборки задачи, ломающие CC? Возможные подозреваемые: kapt в режиме `kapt.use.worker.api=false`, KSP в режиме совместимости с `AndroidSourceSet.kotlin`, native CMake, R8 strict mode, `safeargs.kotlin` плагин навигации, Compose-плагин.
   - **Нужно выяснить:** Прогон `standardDebug` с CC, анализ ошибок.
   - **Статус:** Resolved 2026-05-20. `--configuration-cache --dry-run` на `standard`, `lite`, `photos`, `legacy` проходит с `Configuration cache entry stored`; повторный `standard` прогон показывает `Reusing configuration cache`. Дополнительный blocker вне Chaquopy в текущем task graph не подтверждён.

5. **Поведение Gradle CC при смешанной активации в multi-module build.**
   - **Вопрос:** Если CC активен для `:app_v2` через одну задачу и неактивен через другую — как Gradle разруливает это для модуля `:wear` (который Chaquopy не использует) и для root-проекта?
   - **Нужно выяснить:** Из документации Gradle CC и эмпирически.
   - **Статус:** Resolved 2026-05-20. `:wear:assembleDebug` при `-Pchaquopy.enabled=false` тоже хранит и переиспользует cache entry. Для shared root-конфига безопасен per-invocation режим: default-on CC плюс явный opt-out на noLegal-скриптах.

6. **Измеренная экономия конфигурационной фазы.**
   - **Вопрос:** Какова реальная цена конфигурационной фазы на текущем железе и worktree-state? Это секунды или десятки секунд? Достаточна ли потенциальная экономия, чтобы оправдать риск ложно-зелёных билдов?
   - **Нужно выяснить:** Baseline-замер на нескольких типичных циклах (cold start, incremental без правок, incremental с правкой одного `.kt`).
   - **Статус:** Resolved 2026-05-20. Dry-run baseline без CC: `standard` 2179 ms, `lite` 2095 ms, `photos` 2409 ms, `legacy` 2135 ms, `noLegal` 1883 ms, `wear` 2052 ms. Reuse на `standard` и `wear` опускает wall-clock до ~1 s, выигрыш достаточен для повседневого non-noLegal цикла.

7. **Стабильность IDE-sync при условной активации CC.**
   - **Вопрос:** Если глобально CC включён, а в build-скрипте `noLegal` передаётся `--no-configuration-cache`, не пытается ли Android Studio Sync включать CC и падать на Chaquopy?
   - **Нужно выяснить:** Прогон Sync с включённым CC при наличии Chaquopy в classpath (но при `isNoLegalBuild = false`, чтобы плагин не применялся вообще).
   - **Статус:** Resolved 2026-05-20. Реальный риск создавал machine-local fallback `chaquopy.enabled=true` в `local.properties`, потому что он мог активировать Chaquopy вне noLegal task-names. Тактическое решение S0276 убирает этот fallback из `build.gradle.kts`, оставляя только explicit property и task-name auto-detect.

## 7. Риски

- **Ложно-зелёные билды.** Конфигурационный кэш по своей природе кэширует граф задач. Если кэш не инвалидируется на правке `build.gradle.kts` / `settings.gradle.kts` / условий `isNoLegalBuild`, разработчик может получить успешную сборку, не отражающую реальный текущий граф. Митигация: явный `--rerun-tasks` или `gradle.properties` директивы про `org.gradle.configuration-cache.problems=warn` для прозрачности; обязательно — детектирование change-of-flavor в скриптах сборки и принудительный инвалидатор.
- **Регрессия noLegal-сборки.** Любое изменение глобальной настройки CC может косвенно затронуть инвокацию `noLegalDebug`. Митигация: после любого изменения — обязательный smoke-прогон `assembleNoLegalDebug` через скрипт сборки, без модификаций; критерий проходимости — успешный APK и Chaquopy-runtime, читаемый из логов сборки.
- **Сложность диагностики при гибридном режиме.** Если часть тасок кэшируется, часть нет, и сборка падает где-то в середине — отличить "ошибка кода" от "грязный CC store" становится труднее. Митигация: чёткое логирование на стороне скриптов сборки ("CC: on / off для этой инвокации"); при подозрительных падениях — стандартный first step "погасить CC через флаг и повторить".
- **Конфликт с локальным build cache.** В проекте `org.gradle.caching=true` (но настройки cache на Windows исторически нестабильны). Включение CC поверх этого создаёт два слоя кэширования с независимыми ключами. Митигация: документировать в `dev/development_audit.md` (тема T9) точное состояние обоих кэшей; если возникнут конфликты — приоритет за стабильностью local build cache, CC отключается.
- **Drift между gradle.properties и скриптами.** Если в `gradle.properties` стоит одно значение, а скрипт сборки явно передаёт обратное — поведение определяется CLI. Это правильно, но создаёт ловушку для разработчика, который запускает `./gradlew` напрямую и видит "включенный" по умолчанию кэш, не зная про опт-аут в скрипте `noLegal`. Митигация: явный комментарий в обоих местах + один-командный wrapper (вариант C) для случая ручной сборки `noLegal`.
- **Обратимость.** Если решение зайдёт в тупик, должна быть возможность откатить всё в одно изменение. Митигация: любое решение в S0276 — это одно семантическое изменение в `gradle.properties` + правки в `scripts/builders/`. Точечно, локализовано, откатываемо одним коммитом.
- **Документационный долг.** Если решение принимается "оставить как есть" — комментарий в `gradle.properties` должен ссылаться на S0276 как доказательную базу, иначе следующий разработчик повторит исследование с нуля.

## 9. Архитектурные решения (ADR)

**ADR-1: Конфигурационный кэш включается по умолчанию, а noLegal остаётся явным opt-out путём.**

- **Решение:** `org.gradle.configuration-cache=true` включается глобально, но каждый `noLegal` helper-script и generic helper, который может выйти на noLegal task graph, обязан явно передавать `--no-configuration-cache`.
- **Альтернативы:** Оставить глобальное `false`; либо пытаться спасать noLegal через `notCompatibleWithConfigurationCache(..)` на задачах плагина.
- **Почему:** Эксперимент подтвердил, что весь non-noLegal граф уже безопасно хранит и переиспользует CC. Явный opt-out на noLegal локализует ограничение на единственный проблемный путь и сохраняет автоматический fast path для `standard` / `lite` / `photos` / `legacy` / `wear`.

**ADR-2: Конфиг-кэш включается, только если можно надёжно изолировать.**

- **Решение:** Если эксперимент не даёт безопасной изоляции (вариант A не работает, вариант B приводит к нестабильности IDE-sync или к ложно-зелёным билдам), CC остаётся выключенным.
- **Альтернативы:** Принять риск и включить с предупреждением.
- **Почему:** Цена сломавшейся сборки `noLegal` (часы дебага, неочевидный root cause через CC store) превышает экономию десятков секунд на конфигурационной фазе. Безопасность важнее скорости в этом конкретном trade-off.

**ADR-3: Решение фиксируется доказательно, даже если оно negative.**

- **Решение:** Результат исследования — числа, не мнение. В `dev/CHANGELOG.md` и в `## Last Audit` блоке этой спеки фиксируются baseline-замеры конфигурационной фазы, перечень несовместимых задач, выводы по совместимости AGP / Gradle / Chaquopy.
- **Альтернативы:** Закрыть спек одной строкой "не подошло".
- **Почему:** Спека по build-инфраструктуре с negative result имеет полную ценность как защита от повторного исследования. Следующий разработчик / агент / релизный цикл будет иметь готовую базу, а не пустую "Archived" запись.
