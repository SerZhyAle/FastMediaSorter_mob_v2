## 1. Проблема

На первой странице Welcome-мастера строка «Use as home screen» оформлена не как остальные переключатели приложения: иконка и подпись слева, а сам switch отброшен в правый край строки (weighted TextView раздвигает их). Все прочие тогглеры приложения - в т.ч. строки возможностей второй страницы Welcome («What should the app do?») - следуют канону: switch слева, подпись сразу справа вплотную. Рассинхрон бросается в глаза именно на онбординге.

Область: `ui/welcome` (первая страница мастера), слой представления.

---

## 2. Цели

1. Строка «Use as home screen» на первой странице Welcome выглядит как канонический тогглер: switch слева, иконка и подпись сразу справа вплотную.
2. Визуальная и поведенческая идентичность со строками возможностей второй страницы Welcome (тот же компонент, те же отступы/размеры).
3. Сохранено существующее поведение: восстановление состояния после recreate без ложного колбэка, тап по всей строке переключает switch, видимость под capability-gate.

**Non-goals:**

- Логика запроса роли лаунчера из онбординга (это S1107) - трогаем только раскладку строки.
- Изменение текста подписи или иконки.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

- Внешний вид - ровно как у эталонных строк второй страницы Welcome (приложенный референс-скриншот).

### 3.2 Жёсткие ограничения

- **Flavor:** сборки с launcher-поверхностью (standard, noLegal); в остальных строка и так `gone`.
- **API level:** без API-специфики.
- **Wear OS:** не затрагивается.
- **Локализация:** без новых строк (переиспользуется существующий `launcher_welcome_toggle_title`).
- **Доступность:** touch target и фокус сохраняются (канонический компонент фокусируемый, тап по строке переключает).

### 3.3 Owner inputs (Approval gate)

- **Related tickets:** S0404 (тогглер создан в его Phase 08.4); серия доработок лаунчера S1087-S1103.
- **UI:** целевой вид задан владельцем однозначно (switch слева, подпись вплотную, как эталонные строки страницы 2) + приложен референс-скриншот - UI-неоднозначности нет.

## 4. Контекст текущей архитектуры

Строка живёт в раскладке страницы enhanced-Welcome (`page_welcome_enhanced.xml` + land-вариант) и привязывается в пейджер-адаптере онбординга. Сейчас это hand-rolled `LinearLayout` (иконка | weighted TextView | MaterialSwitch), из-за чего switch уезжает вправо. В проекте есть канонический компонент строки-тогглера (`SettingsToggleRow`, паттерн «Trigger Row» из docs/ARCHITECTURE.md), которым уже собраны строки возможностей второй страницы. Задачу нельзя закрыть косметикой отступов, не приведя строку к этому компоненту - иначе рассинхрон с каноном сохранится.

---

## 5. Предлагаемый подход

Заменить hand-rolled строку на канонический компонент строки-тогглера (switch-слева), сохранив id строки и контракт привязки.

### 5.1 Основные столпы / модули

- Раскладка страницы Welcome (portrait + land): строка лаунчер-режима = канонический тогглер-компонент с иконкой и заголовком через его атрибуты.
- Пейджер-адаптер онбординга: привязка через API компонента (тихое восстановление состояния + колбэк изменения), без ручного управления отдельным switch и ручного клика по строке.

### 5.2 Потоки данных и событий

Флаг намерения хранится во ViewModel; адаптер восстанавливает визуал строки без срабатывания колбэка (recreate-safe), пользовательский флип строки прокидывается обратно во ViewModel тем же колбэком, что и раньше.

### 5.3 Точки расширяемости

Канонический компонент поддерживает подзаголовок и trailing-слот - при будущей нужде описание/действие добавляются без новой вёрстки.

## 7. Риски

- Смена типа view у id строки ломает сгенерённый binding (вероятность средняя): пейджер-адаптер не компилируется -> обновить привязку под API компонента в том же изменении; сборка это ловит.
- Расхождение portrait/land (низкая): разный вид по ориентации -> правка обоих вариантов раскладки в одном изменении (Rule 11).

- Регрессий нет: старый id `switchWelcomeLauncherMode` устранён во всех источниках (grep чист); сборка standard debug зелёная (fc, 28s, BUILD SUCCESSFUL - dataBinding перегенерён под новый тип). Критерий 5.
- docs/FEATURES без изменений (визуальная согласованность существующего тогглера, не новая возможность).
