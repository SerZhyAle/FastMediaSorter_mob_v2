## 1. Проблема

В продукте уже есть два близких, но несвязанных механизма. Первый - режим File Manager Mode / all files, который меняет правила показа содержимого ресурса. Второй - предопределённые виртуальные ресурсы, которые создаются как отдельные точки входа в список ресурсов. Сейчас между ними нет отдельного продуктового мостика.

Если профиль устройства предполагает файловый сценарий, приложение может включить широкие настройки просмотра, но не создаёт отдельный ресурс файлового менеджера, к которому можно вернуться позже из главного списка. Аналогично на экране добавления ресурса пользователь может включить «Все файлы» для конкретного ресурса, но не получает рядом одношаговый путь создать готовый предопределённый ресурс с файловым поведением.

Из-за этого файловый сценарий остаётся скрытым в настройках и чекбоксах, хотя по смыслу это отдельный пользовательский режим входа в приложение: открыть файловый менеджер, увидеть папки устройства, работать со всеми типами файлов и сортировать содержимое как файловый список, а не как медиа-каталог.

---

## 2. Цели

1. Ввести отдельный предопределённый ресурс для файлового сценария, а не полагаться только на флаг all-files внутри других ресурсов.
2. Связать устройство/профиль, который предполагает файловый сценарий, с автоматическим созданием такого ресурса при первичной установке.
3. Дать пользователю ручной одношаговый путь создать этот ресурс рядом с чекбоксом «Все файлы», если он ещё отсутствует.
4. Сделать поведение ресурса предсказуемым: он показывает все папки и все файлы, а не только медиа, и использует сортировку по умолчанию от нового к старому.
5. Согласовать новый ресурс с уже существующим контрактом File Manager Mode, чтобы пользователь видел отдельную файловую точку входа, а не набор разрозненных флагов.
6. Не создавать дубликаты ресурса при повторном входе, повторном выборе профиля или ручном нажатии на кнопку.
7. При первом создании ставить ресурс на минимальную позицию в списке и не мешать дальнейшей ручной перестановке пользователем.

**Non-goals:**

- Не переписывать весь механизм Browse или все существующие ресурсы под новый backend.
- Не удалять автоматически ресурс, если пользователь позже сменит профиль устройства на нефайловый.
- Не обещать встроенное открытие любого бинарного формата сверх уже существующих viewer / external-open возможностей.
- Не вводить в этой стратегической фазе новые системные ярлыки, виджеты или SAF-поверхности, если они не нужны для базового сценария.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Кнопка должна располагаться рядом с галочкой «Все файлы».
2. Кнопка должна показываться только если соответствующий предопределённый ресурс ещё не создан.
3. Выбор профиля устройства при установке, который предполагает all-files-сценарий, должен создавать тот же ресурс автоматически.
4. Новый ресурс должен концептуально быть файловым менеджером.
5. Внутри ресурса папки устройства должны уметь отображаться как отдельные элементы, если такая настройка включена.
6. Сортировка по умолчанию должна быть от самого нового к самому старому.
7. При создании ресурс должен получить минимальный номер в списке.
8. Позже пользователь может передвинуть его вручную.
9. Даже при наличии похожих ручных all-files-ресурсов отдельный predefined resource всё равно создаётся.
10. После ручного создания нужно показать краткое уведомление, а кнопка создания должна скрыться.

### 3.2 Жёсткие ограничения

- **Flavor:** локальный файловый сценарий должен быть согласован для всех phone/tablet flavors, где уже есть список ресурсов и локальный Browse
- **API level:** без новой API-специфики как обязательного условия; ресурс должен работать в текущем минимальном диапазоне Android проекта
- **Wear OS:** вне объёма
- **Производительность:** создание ресурса не должно превращать first-run в тяжёлое полное сканирование всего устройства до первого открытия списка
- **Совместимость данных:** существующие ресурсы и пользовательские all-files-папки не должны ломаться; повторный триггер не должен плодить дубликаты
- **Порядок списка:** правило минимального номера применяется в момент первого создания и не должно самопроизвольно перетирать ручной reorder пользователя без отдельного owner-решения
- **Наличие эквивалентов:** даже если у пользователя уже есть ручные локальные all-files-ресурсы, отдельный predefined file-manager resource всё равно создаётся
- **Локализация:** EN/RU/UK обязательны для всех пользовательских строк после имплементации
- **Доступность:** кнопка и новый ресурс должны сохранять предсказуемость для touch, keyboard, D-pad и TalkBack
- **Поведение настроек:** новый ресурс должен уважать уже существующие настройки файлового режима там, где это не противоречит его контракту
- **UI copy:** строки должны оставаться совместимыми с уже введённым продуктовым понятием File Manager Mode

### 3.3 Owner inputs (Approval gate)

- **Implementation scope:** first-run profile apply, Settings profile re-apply with confirmation, General settings `All Files` CTA, predefined resource creation, list-order insertion, browse sorting parity, and docs/features parity.
- **Primary anchor:** рядом с существующим settings row `All Files`; CTA скрывается после появления predefined resource.
- **Naming contract:** и CTA, и сам predefined resource используют имя `Все файлы`; tactical layer не вводит второй конкурирующий пользовательский термин.
- **Creation contract:** профильные и ручные trigger-ы обязаны вести к одному и тому же idempotent predefined local resource без дублей.
- **Ordering contract:** при первом создании ресурс вставляется в top-slot среди обычных ресурсов; повторные trigger-ы не откатывают ручную перестановку пользователя.
- **Confirmation contract:** на first-run автосоздание выполняется без вопроса; при повторной смене профиля в Settings создание missing resource требует явного подтверждения.
- **Equivalent-resource contract:** наличие похожих ручных all-files-ресурсов не отменяет создание отдельного predefined entry point.
- **Validation level:** затронутые Kotlin/XML/strings изменения должны собраться; EN/RU/UK parity обязательна; ручная on-device проверка рекомендуется перед `Verified`.
- **Related tickets:** S0302 (File Manager Mode), S0327 (device profile presets and picker), S0059 (all-files local/predefined precedents).

## 4. Контекст текущей архитектуры

Сейчас файловое поведение в продукте живёт на уровне настроек и свойств ресурса. Профиль устройства может включать глобальный all-files-сценарий и соседние настройки вроде показа скрытых файлов, показа подпапок как отдельных элементов и сортировки. Отдельно система предопределённых ресурсов создаёт фиксированный набор виртуальных входов: recent, media-, image-, camera- и documents-ресурсы.

Экран добавления ресурса уже сочетает оба подхода: у пользователя есть профиль пресета, есть чекбокс «Все файлы», есть список виртуальных ресурсов, но нет готового предопределённого файлового ресурса как самостоятельного объекта. В результате файловый use case описан как режим других ресурсов, а не как отдельная стартовая сущность в списке ресурсов.

Новый запрос не требует нового типа хранилища. Он требует связать существующие механизмы профиля устройства, предопределённого ресурса и Browse-контракта в единый продуктовый поток: профиль или кнопка создают файловый ресурс, а этот ресурс затем живёт как отдельный повторно используемый вход в файловый режим.

## 5. Предлагаемый подход

### 5.1 Основные столпы / модули

- **Профиль устройства как триггер намерения:** если выбранный при установке профиль явно означает файловый сценарий, применение профиля должно не только менять глобальные настройки, но и инициировать проверку существования отдельного файлового ресурса.
- **Ручное создание из add-resource:** рядом с чекбоксом «Все файлы» должен появиться явный CTA для создания готового предопределённого ресурса, если он ещё не существует.
- **Отдельный предопределённый ресурс файлового менеджера:** ресурс должен рассматриваться как самостоятельная точка входа в локальный файловый сценарий, а не как синоним Recent или как побочный эффект случайной папки.
- **Идемпотентный жизненный цикл:** и профильный, и ручной триггер должны вести к одному и тому же результату без дублей и без разрушения уже существующих пользовательских ресурсов.
- **Первичный приоритет в списке:** новый ресурс при первом создании получает минимальную позицию в общем списке, но последующая ручная перестановка остаётся за пользователем.
- **Отдельный product root:** новый ресурс открывает псевдо-корень устройства, где папки представлены как самостоятельные элементы файлового менеджера.

### 5.2 Потоки данных и событий

1. Пользователь на первом запуске выбирает профиль устройства.
2. Слой применения профиля обновляет настройки файлового поведения.
3. Если профиль попадает в all-files/file-manager intent, система проверяет наличие предопределённого файлового ресурса и создаёт его один раз.
4. Экран добавления ресурса показывает чекбокс «Все файлы» и, пока файлового ресурса нет, соседнюю кнопку ручного создания.
5. При ручном создании выполняется та же проверка существования и записывается тот же предопределённый ресурс.
6. При первом создании ресурсу назначается минимальный номер в списке.
7. Главный список ресурсов получает новый отдельный файловый entry point.
8. Если пользователь позже вручную переставил ресурс, повторные triggers не возвращают его наверх.
9. После ручного создания пользователь получает краткое уведомление, а кнопка создания скрывается.
10. При открытии этого ресурса Browse строит список папок и файлов без медиа-фильтра, уважает настройку показа подпапок как элементов и по умолчанию применяет сортировку от нового к старому.

### 5.3 Точки расширяемости

- В будущем можно добавить несколько предопределённых файловых ресурсов для разных корней или сценариев, не меняя базовый контракт отдельного file-manager entry point.
- В будущем файловый ресурс может использоваться как источник для виджетов, ярлыков и onboarding-ярлыков, если продукт захочет усилить сценарий «открыть файловый менеджер одним тапом».
- В будущем можно развести триггеры first-run и post-install settings re-apply, если владелец захочет разное поведение для новой и уже настроенной установки.

## 6. Открытые вопросы / Research items

1. **Имя ресурса и CTA**
   - **Вопрос:** и CTA, и сам ресурс используют имя «Все файлы».
   - **Варианты:** утверждено владельцем
   - **Нужно выяснить:** tactical-слой должен согласовать это имя с уже существующим help/doc copy вокруг File Manager Mode
   - **Статус:** Resolved

2. **Граница автосоздания**
   - **Вопрос:** автосоздание происходит на первом запуске; при последующем выборе профиля в Settings требуется подтверждение.
   - **Варианты:** утверждено владельцем
   - **Нужно выяснить:** tactical-слой должен определить текст и момент показа подтверждения
   - **Статус:** Resolved

3. **Позиция в списке предопределённых ресурсов**
   - **Вопрос:** правило минимального номера уточнено как `top-1 среди обычных ресурсов, если в списке есть служебный закреплённый элемент`.
   - **Варианты:** утверждено владельцем
   - **Нужно выяснить:** tactical-слой должен перевести это в текущую модель display order
   - **Статус:** Resolved

4. **Корень файлового ресурса**
   - **Вопрос:** ресурс должен открываться как псевдо-корень с папками устройства как отдельными элементами.
   - **Варианты:** утверждено владельцем
   - **Нужно выяснить:** tactical-слой должен определить точный набор стартовых device folders / volumes
   - **Статус:** Resolved

5. **Поведение при наличии похожих ресурсов**
   - **Вопрос:** если у пользователя уже есть ручные локальные ресурсы с all-files=true, предопределённый ресурс всё равно должен существовать отдельно.
   - **Варианты:** утверждено владельцем
   - **Нужно выяснить:** tactical-слой должен сохранить идемпотентность именно для predefined resource
   - **Статус:** Resolved

6. **Подтверждение и feedback**
   - **Вопрос:** после ручного создания нужно краткое уведомление.
   - **Варианты:** утверждено владельцем
   - **Нужно выяснить:** tactical-слой выберет toast или snackbar по текущему UI-паттерну
   - **Статус:** Resolved

7. **Повторный trigger после ручной перестановки**
   - **Вопрос:** если пользователь уже передвинул файловый ресурс вниз, повторный trigger сохраняет пользовательскую позицию.
   - **Варианты:** утверждено владельцем
   - **Нужно выяснить:** tactical-слой должен зафиксировать отсутствие автоперестановки
   - **Статус:** Resolved

8. **Состояние CTA после создания**
   - **Вопрос:** после создания ресурса соседняя кнопка скрывается.
   - **Варианты:** утверждено владельцем
   - **Нужно выяснить:** tactical-слой должен решить, нужен ли spacer или полная переразметка ряда
   - **Статус:** Resolved

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Новый ресурс дублирует уже существующие ручные all-files-папки | Средняя | Главный список захламляется и становится непонятным | Сделать предопределённый ресурс идемпотентным и явно отличимым по роли |

| Псевдо-корень окажется слишком абстрактным или нестабильным между устройствами | Средняя | Пользователь увидит неожиданный набор стартовых папок | Tactical phase должна явно определить contract стартовых device folders / volumes |

## 8. Влияние на пользователя (docs/FEATURES)

После реализации `docs/FEATURES.md` + `_RU` + `_UK` должны описывать отдельный предопределённый File Manager resource, который может создаваться из профиля устройства или вручную и открывает локальный файловый сценарий со всеми папками и файлами, а не только медиа.

## 9. Архитектурные решения (ADR)

**ADR-1: Отдельный файловый ресурс важнее, чем только глобальный all-files-флаг**

- **Решение:** оформить файловый сценарий как отдельный предопределённый ресурс.
- **Альтернативы:** оставить только глобальный all-files в настройках; оставить только all-files как чекбокс конкретного ресурса.
- **Почему:** пользователю нужен повторно используемый entry point в список ресурсов, а не скрытая комбинация флагов.

**ADR-2: Автосоздание по профилю должно быть идемпотентным**

- **Решение:** профильный триггер создаёт файловый ресурс только при отсутствии готового entry point.
- **Альтернативы:** создавать всегда; никогда не создавать автоматически.
- **Почему:** профиль отражает intent пользователя, но не должен плодить дубликаты.

**ADR-3: Ручная кнопка и профильный триггер должны вести к одному контракту**

- **Решение:** оба входа создают один и тот же тип предопределённого ресурса с одинаковым поведением.
- **Альтернативы:** делать "облегчённый" ресурс из кнопки и "полный" ресурс из онбординга.
- **Почему:** разный контракт для одного сценария только усложнит UX и сопровождение.

**ADR-4: Для файлового ресурса сортировка по умолчанию фиксируется как newest-first**

- **Решение:** базовый порядок ресурса по умолчанию - от нового к старому.
- **Альтернативы:** наследовать глобальную сортировку; оставить name-asc как у части существующих виртуальных ресурсов.
- **Почему:** владелец явно задал файловый use case, где свежие изменения важнее алфавита.

## 11. Критерии готовности (strategic-level)

1. Пользователь, выбравший файловый/all-files-ориентированный профиль на первичной установке, получает отдельный файловый ресурс без ручной дополнительной сборки.
2. На экране добавления ресурса рядом с чекбоксом «Все файлы» виден отдельный CTA создания ресурса, но только пока такого ресурса ещё нет.
3. Повторный выбор того же триггера не создаёт дубликаты файлового ресурса.
4. При открытии нового ресурса пользователь видит файловый сценарий, а не медиа-фильтрацию: папки и файлы доступны в рамках текущих правил видимости.
5. Если включена опция показа подпапок как отдельных элементов, файловый ресурс сохраняет этот способ представления.
6. Сортировка по умолчанию в новом ресурсе стартует от самого нового к самому старому.
7. Терминология ресурса, кнопки и документации остаётся согласованной с File Manager Mode и не вводит отдельный конкурирующий термин.
8. В момент первого создания файловый ресурс получает минимальный номер в списке, а дальнейшая ручная перестановка пользователем не откатывается без отдельного правила.
9. Даже при наличии пользовательских all-files-ресурсов отдельный predefined file-manager resource всё равно создаётся как самостоятельный entry point.
10. После ручного создания пользователь получает краткое уведомление, а кнопка создания скрывается.
