## 1. Проблема

Документы проекта распределены между пользовательской, технической и процессной областями, а публичные страницы сайта учитываются отдельно. Текущая карта документации полезна человеку, но не даёт автоматической связи между изменением функции, кода, инструкций и обязательными обновлениями документов.

Из-за этого легко пропустить локализованную версию, страницу сайта, устаревшую ссылку или связанную инструкцию. Также разные agent workflows имеют неполный и неодинаковый набор источников для поиска.

## 2. Цели

1. Создать единый проверяемый реестр всех поддерживаемых документов, инструкций и публичных страниц.
2. Описать назначение, аудиторию, локализацию, публикацию и связи каждого зарегистрированного материала.
3. Автоматически выявлять отсутствующие записи, битые связи, несоответствие зеркал и неактуальные производные индексы.
4. Сделать реестр обязательной точкой исследования и обновления для репозиторных workflows.
5. Снизить ручное сопровождение карты документации и sitemap.

**Non-goals:**

- Не переписывать содержание существующих руководств без выявленной ошибки.
- Не публиковать внутренние документы.
- Не изменять функциональность Android-приложения.

3. Процесс поддерживает пополнение и периодическую проверку без ручной сверки нескольких списков.

## 4. Контекст текущей архитектуры

В проекте уже есть отдельные каталоги исходного кода, Activities и задач, а также карта документации и локальный поиск. Эти механизмы не объединяют публичные страницы, процессные инструкции и связь документов с функциями и областями кода.

Нужен слой знаний о документах, независимый от содержимого конкретного руководства: он должен быть источником для навигации человека, проверки автоматизацией и маршрутизации agent workflows.

## 5. Предлагаемый подход

Ввести декларативный реестр с одной записью на логический материал или группу локализованных зеркал. Каждая запись описывает статус публикации, владельца, происхождение, зависимые области продукта, ожидаемые переводы и условия обновления.

### 5.1 Основные столпы / модули

1. Реестр и схема записи.
2. Генерация человекочитаемой карты и публичной карты сайта из реестра.
3. Валидатор полноты, ссылок, локализации и производных материалов.
4. Поиск и маршрутизация по реестру для инженерных workflows.
5. Инструкции для авторов и automation-подсказки.

### 5.2 Потоки данных и событий

Изменение кода или функциональности → определение затронутой области → поиск соответствующих записей реестра → обновление обязательных материалов → проверка реестра и производных документов.

Новый материал → добавление записи → генерация индекса и sitemap при необходимости → проверка ссылок и зеркал.

### 5.3 Точки расширяемости

Реестр допускает новые типы материалов, новые локали, внешние страницы и дополнительные проверки без изменения уже зарегистрированных документов.

## 6. Открытые вопросы / Research items

1. **Гранулярность связей**
   - **Вопрос:** связывать ли документы с отдельными Kotlin-путями или с устойчивыми product-area.
   - **Варианты:** только product-area; product-area плюс glob путей.
   - **Нужно выяснить:** выбрать формат, который не создаёт хрупкие связи при рефакторинге.
   - **Статус:** Resolved - product-area являются основой, пути используются только как необязательные триггеры.

2. **Публичная карта сайта**
   - **Вопрос:** какие страницы должны попасть в sitemap.
   - **Варианты:** все опубликованные записи; только отмеченные как индексируемые.
   - **Нужно выяснить:** сохранить исключение sideload-only материалов.
   - **Статус:** Resolved - включать только явно индексируемые опубликованные записи.

## 9. Архитектурные решения (ADR)

**ADR-1: Декларативный реестр является источником правды**

- **Решение:** поддерживать один структурированный реестр и генерировать из него обзорные материалы.
- **Альтернативы:** продолжать вручную вести карту; извлекать всё эвристически из Markdown.
- **Почему:** структурированная запись проверяема, пригодна для поиска и не требует ненадёжного вывода назначения из текста.

## 11. Критерии готовности (strategic-level)

1. Для каждого поддерживаемого документа и сайта определён один реестровый владелец и статус публикации.
2. Добавление нового материала нельзя завершить без его регистрации или явного исключения.
3. Изменение функциональной области выводит список связанных обязательных документов.
4. Карта документации и sitemap воспроизводимо проверяются относительно реестра.
5. Репозиторные workflows направляют agents к реестру перед поиском и при обновлении документов.
