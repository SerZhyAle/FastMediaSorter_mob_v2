Вложений нет.

## 1. Проблема

Список трансляций уже движется в сторону более наглядных видеопревью, но текущее live-capture поведение привязано к активному захвату кадра в текущей сессии. Если пользователь уже открывал видеоканал раньше, приложение не использует этот факт как источник узнаваемой миниатюры при следующем входе.

Из-за этого канал снова стартует с пустой/базовой иконкой или ждёт нового live-захвата, хотя у приложения потенциально уже был полезный визуальный кадр. Для повторных входов это выглядит как потеря контекста.

---

## 2. Цели

1. После воспроизведения видеотрансляции сохранять локально последний пригодный кадр в низком разрешении как миниатюру канала.
2. При следующем открытии списка/экрана трансляций показывать сохранённую миниатюру сразу, до нового live-refresh.
3. Ограничить хранение по размеру и качеству так, чтобы миниатюры оставались лёгкими и не раздували хранилище.
4. Поведение должно применяться только там, где это уместно для видеотрансляций, и не ломать fallback для аудио/RTSP/каналов без кадра.

**Non-goals:**

- Не хранить полноразмерные скриншоты или историю кадров.
- Не превращать draft в решение про сложную галерею/таймлайн превью.
- Не отменять существующее live-capture/refresh поведение там, где оно уже нужно для актуализации кадра.

---

## 3. Черновые пожелания и ограничения

- Миниатюра должна быть low-res и app-private, без заметного влияния на диск и память.
- Сохранённый кадр должен быть привязан к конкретному каналу достаточно стабильно, чтобы не путаться после рестартов и импортов каталога.
- Нужен аккуратный fallback: если сохранённого кадра нет или он устарел/битый, канал ведёт себя как сейчас.
- Поведение надо согласовать с уже существующими stream-thumbnail тикетами, а не дублировать параллельный пайплайн.

1. **Граница с S0675**

   - **Статус:** Open

2. **Что считать "последним кадром"**
   - **Вопрос:** сохранять кадр при остановке просмотра, при уходе со страницы, по таймеру во время просмотра, или брать последний успешно полученный preview-кадр?
   - **Нужно выяснить:** какой момент даёт лучший баланс между свежестью кадра и сложностью реализации.
   - **Статус:** Open

3. **Какие типы каналов включать**
   - **Вопрос:** речь только про HTTP(S) video streams, или ещё про HLS/DASH/другие video-only источники; что делать с RTSP и audio-only?
   - **Нужно выяснить:** продуктовую матрицу охвата и fallback-поведение.
   - **Статус:** Open

4. **Политика устаревания**
   - **Вопрос:** сколько хранить кадр и когда считать его слишком старым для показа?
   - **Нужно выяснить:** TTL, invalidation на re-import/rename/remove канала и общий storage cap.
   - **Статус:** Open

5. **UX показа**
   - **Вопрос:** сохранённый кадр должен просто заменять favicon/empty-slot, или нужно как-то визуально отличать "старый сохранённый кадр" от live-captured текущего?

## 6. Критерии готовности (strategic-level)

1. После просмотра видеоканала приложение может показать его сохранённый low-res кадр как миниатюру при следующем входе в список трансляций.
2. Миниатюра сохраняется локально без заметного роста дискового следа и без хранения полноразмерных кадров.
3. Если сохранённого кадра нет или он недействителен, остаётся штатный fallback без регрессии.
4. Новое поведение не конфликтует с существующим live-capture/refresh для stream thumbnails.

## 8. Решения и реализация (2026-06-30)

### Ответы владельца

- **Источник кадра (Q2):** кадр из GRID-захвата. Переиспользуем существующий `StreamFrameSnapshotManager` (первый декодированный кадр http(s) VIDEO); полноэкранный плеер не трогаем.
- **UX показа (Q5):** показывать сохранённый кадр как обычный live-кадр; периодический refresh/новый захват молча перезаписывает его. Без бейджа, без `/ui-clarify`.

### Резолюция открытых вопросов

1. **Q1 (граница с S0675/S0700):** persistent-слой ПОД in-memory `StreamFrameCache`, а не конкурирующий пайплайн. S0675 архивирован; живой захват - `StreamFrameSnapshotManager` + `StreamFrameCache`.
2. **Q3 (типы каналов):** только http(s) VIDEO - тот же фильтр `isCaptureableVideo`, что и у захвата. AUDIO/RTSP -> favicon-fallback без изменений.
3. **Q4 (устаревание/cap):** файл перезаписывается на каждом новом захвате (всегда свежий); cap = 64 файла (== `MAX_ENTRIES`), LRU-эвикция по mtime; инвалидация при удалении канала. Возраст диск-кадра не блокирует показ - он лишь начальная подсказка, заменяется live-захватом в той же сессии.

### Что сделано

- `StreamFramePersistentStore` (data/repository/streams): app-private JPEG-кадры в `filesDir/stream_frames`, ключ = SHA-256(url), атомарная запись через `.tmp` + rename, cap 64, всё I/O off-main, best-effort.
- `StreamFrameCache`: запись помечается `live`. Restored-кадр с диска (`putRestored`) показывается через `get`, но не считается `isFresh` -> захват свежего кадра не подавляется; live-кадр перезаписывает диск-кадр. `hasEntry` для пропуска лишнего pre-warm.
- `StreamFrameSnapshotManager`: после `cache.put` пишет кадр на диск (`scope.launch { store.save }`).
- `StreamGridModeManager`: при входе в GRID / submit pre-warm'ит кэш с диска (`store.load` -> `putRestored` -> repaint), отменяется при уходе из GRID/`stop`.
- `StreamsViewModel.onRemove`: удаляет диск-кадр канала (без сирот).
