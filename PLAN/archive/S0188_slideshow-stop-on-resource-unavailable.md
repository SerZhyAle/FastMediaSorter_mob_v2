## 1. Проблема

Когда во время слайдшоу сетевой или облачный ресурс становится недоступен (обрыв WiFi, выключение SMB/FTP-сервера, отзыв доступа к облаку), слайдшоу продолжает тикать — без остановки и без объяснения. Зафиксированы два сценария из реального лога:

- **Сценарий A — сеть полностью пропала:** `NetworkStateMonitor` фиксирует потерю сети. Слайдшоу продолжает работать, хотя любая сетевая загрузка заведомо провалится.
- **Сценарий B — хост недоступен, но сеть «есть»:** путь к аудиофайлу не разрешается (пустой path), `AudioPlaybackService` запускает воспроизведение с пустым медиа-объектом → `playbackState=4` через ~1 секунду → "playback ended" → слайдшоу немедленно переходит к следующему файлу — и цикл повторяется. Аналогично для изображений: Glide возвращает сетевую ошибку → файл пропускается → следующий файл снова не загружается.

В обоих сценариях пользователь не получает понятного объяснения и не имеет способа остановить цикл без ручного вмешательства. Затронуты все типы ресурсов с удалённым доступом: SMB, FTP/SFTP, облако (Google Drive, Dropbox, MSAL), а также локальные ресурсы, ставшие недоступными (например, отмонтированный USB).

---

## 2. Цели

1. **Сценарий A:** когда `NetworkStateMonitor` фиксирует полную потерю сети, слайдшоу немедленно останавливается; пользователь видит информационное (не ошибочное) сообщение «соединение потеряно».
2. **Сценарий B:** когда несколько файлов подряд не загружаются (пустой путь / быстрый сбой воспроизведения), слайдшоу останавливается с уведомлением, содержащим имя ресурса.
3. Пользователь может вручную возобновить слайдшоу без перезапуска плеера — нажатием существующей кнопки слайдшоу.
4. Единичный сбой загрузки одного файла не останавливает слайдшоу — механизм пропуска сохраняется.

**Non-goals:**

- Автоматическое возобновление слайдшоу после восстановления соединения.
- Мониторинг доступности ресурса в фоне вне плеера.
- Изменение поведения слайдшоу при одиночных ошибках файлов на локальном ресурсе.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. **Сценарий A (нет сети):** сообщение информационное, не в стиле ошибки — «Подключение потеряно. Нажмите ▶, чтобы продолжить».
2. **Сценарий B (хост недоступен):** сообщение содержит имя ресурса — «Не удалось загрузить файлы с [Имя ресурса]. Нажмите ▶, чтобы продолжить».
3. Resume — это просто повторное нажатие кнопки слайдшоу (существующий UI, новых элементов управления не нужно).
4. Порог последовательных сбоев (Сценарий B) — ориентир N=3; точное значение определяется в тактической спецификации.

### 3.2 Жёсткие ограничения

- **Flavor:** затронуты все варианты сборки (`standard`, `lite`, `photos`, `legacy`), так как все поддерживают слайдшоу изображений; SMB/FTP/SFTP/Cloud фичи сохраняют свои `BuildConfig`-гейты.
- **API level:** без API-специфики, minSdk 26.
- **Wear OS:** не затрагивается.
- **Производительность:** счётчик ошибок — легковесный in-memory int в рамках сессии плеера; никакого IO или дополнительных потоков.
- **Совместимость данных:** без изменений схемы данных.
- **Локализация:** EN/RU/UK — обязательно для новых строк.
- **Доступность:** TalkBack не требует отдельных решений (Toast/Snackbar читаются автоматически).
- **Соответствие коммуникационной политике:** все новые пользовательские строки обязаны соответствовать тону и формулам из `docs/COMMUNICATION_POLICY.md` (§6 tone checklist — обязательный gate перед интеграцией строк).

## 4. Контекст текущей архитектуры

Слайдшоу в плеере управляется двумя независимыми путями:

- **Изображения / GIF:** таймер-контроллер периодически инициирует переход к следующему файлу. Загрузка изображения идёт через Glide; при ошибке сейчас показывается Toast и выполняется переход к следующему файлу.
- **Аудио / видео с `playToEndInSlideshow`:** таймер не используется; переход инициируется событием окончания воспроизведения. Когда аудиофайл не может быть загружен (пустой путь при недоступном сетевом ресурсе), `AudioPlaybackService` стартует с пустым медиа-объектом, ExoPlayer немедленно переходит в состояние «воспроизведение завершено», и слайдшоу переходит к следующему файлу — цикл повторяется каждые ~30 секунд.

`NetworkStateMonitor` уже существует и рассылает события о потере/восстановлении сети, однако плеер в режиме слайдшоу на эти события не реагирует. Нет ни прямой подписки плеера на сетевые события, ни счётчика последовательных сбоев загрузки.

---

## 5. Предлагаемый подход

Два независимых пути детекции — оба ведут к одному исходу: остановка слайдшоу + уведомление + возможность Resume.

### 5.1 Путь A — мгновенная остановка при потере сети

Плеер в режиме слайдшоу подписывается на уже существующий `NetworkStateMonitor`. При получении события «сеть полностью потеряна»:
- немедленно остановить слайдшоу (сбросить флаг активности, остановить таймер и цикл advance);
- показать информационное сообщение без слова «ошибка».

При восстановлении сети — никаких автоматических действий; Resume только по жесту пользователя (существующая кнопка слайдшоу). Подписка действует только пока слайдшоу активно; при выходе из плеера — отписка.

### 5.2 Путь B — детекция по последовательным сбоям (хост недоступен)

Для случая, когда сеть «есть», но ресурс не отвечает:

- **Для изображений:** счётчик последовательных сетевых ошибок в компоненте загрузки изображений. Сбрасывается при каждой успешной загрузке или при ручном действии пользователя. Инкрементируется только на сетевых/соединительных исключениях (не на ошибках конкретного файла). При N сбоях подряд — остановка слайдшоу с уведомлением «не удалось загрузить файлы с [Имя ресурса]».
- **Для аудио / видео с `playToEndInSlideshow`:** счётчик «мгновенных» завершений воспроизведения — когда playback-state переходит в «ended» в первые несколько секунд после старта с пустым или неразрешимым медиа-объектом. При N таких завершений подряд — остановка слайдшоу. Сбрасывается при нормальном завершении файла (длительность > порогового значения).

### 5.3 Общие принципы

- Оба пути используют одно и то же действие остановки и один и тот же способ Resume (кнопка слайдшоу).
- Счётчик сбоев — in-memory, живёт в рамках сессии плеера; сбрасывается при ручном переходе к другому файлу, смене ресурса, успешной загрузке.
- Сообщение различается по тональности: Путь A — информационное («нет подключения»), Путь B — нейтральное предупреждение («не загружается с ресурса X»).

### 5.4 Точки расширяемости

- Порог N как константа (не в настройках) — легко вынести позже.
- Детектор «мгновенного завершения» для аудио должен допускать добавление новых условий без изменения вызывающего кода.

## 6. Research results

1. **Классификация ошибок сетевых ресурсов (изображения)**
   - **Ответ:** существующий `ImageLoadingDiagnostics.isNonCriticalNetworkImageError` покрывает только benign decode/cancel/HEIC/AVIF случаи и подходит только как фильтр-исключение.
   - **Вывод:** для S0188 нужен отдельный предикат «ресурс недоступен», основанный на контексте удалённого ресурса и transport/auth markers в тексте Glide root-cause (`failed to load network file`, `connect`, `timeout`, `unknown host`, `access token`, `unauthorized`, `forbidden`). Жёстко полагаться на типы исключений нельзя, потому что `NetworkFileModelLoader` и cloud loaders часто заворачивают первичную ошибку в generic `IOException`/message.
   - **Статус:** Resolved

2. **Детекция «мгновенного завершения» аудио (playToEndInSlideshow)**
   - **Ответ:** надёжный runtime-признак — `STATE_ENDED` без предшествующего стабильного `READY`, либо `STATE_ENDED` в первые 3–5 секунд после `READY` для файла с ожидаемой длительностью больше порога.
   - **Кодовое подтверждение:** service-audio путь routed через `PlayerManagerInitializer.onAudioServiceReady/onAudioServicePlaybackEnded`; быстрый `ENDED` можно считать подряд и сбрасывать при нормальном завершении файла.
   - **Статус:** Resolved

3. **Аналогичный паттерн для видео-слайдшоу**
   - **Ответ:** нет, видео не использует `AudioPlaybackService` empty-path path. Удалённые video failures в основном приходят через `VideoPlayerManager` как playback error / timeout; quick-end остаётся полезным fallback, но primary hook для видео — именно playback error.
   - **Статус:** Resolved

4. **Разделение сообщений по протоколу**
   - **Ответ:** достаточно одного шаблона с именем ресурса. В модели уже есть `MediaResource.name`; дробить сообщения по SMB/FTP/Cloud не требуется.
   - **Статус:** Resolved

## 9. Архитектурные решения (ADR)

**ADR-1: Два пути детекции вместо единого счётчика**

- **Решение:** Путь A (NetworkStateMonitor) обеспечивает мгновенную реакцию на полную потерю сети; Путь B (счётчик сбоев) покрывает случай недоступного хоста при живой сети.
- **Альтернативы:** Только счётчик сбоев (упустит сценарий полной потери сети с быстрой реакцией); только NetworkStateMonitor (не поможет при wlan→rmnet с недоступным хостом).
- **Почему:** Из лога видно, что до официального `Network lost` (02:51:55) уже было 2 цикла пустого-path аудио (02:50:02 и 02:50:36). Только счётчик поймал бы это раньше.

**ADR-2: Счётчик Пути B — в общем player-helper, а не в ViewModel**

- **Решение:** общий helper уровня player-session принимает сигналы от `NetworkStateMonitor`, image-loading callback и playback callbacks, хранит пороговую логику и вызывает уже существующий stop/resume path плеера.
- **Почему:** stop action, manual reset и пороги живут в одном месте; image/audio/video hooks только сообщают о success/failure и не дублируют состояние.

**ADR-3: Resume — существующая кнопка слайдшоу, новых элементов UI нет**

- **Решение:** Нажатие кнопки запуска слайдшоу в плеере сбрасывает счётчик ошибок и перезапускает слайдшоу.
- **Почему:** Не нужен новый UI; поведение интуитивно понятно пользователю.

**ADR-4: Порог N как константа**

- **Решение:** N = 3 (константа, не настройка).
- **Почему:** Пользователи не меняют такие параметры; излишнее усложнение Settings UI.

## 11. Критерии готовности (strategic-level)

1. **Сценарий A:** при полной потере сети (`NetworkStateMonitor` event) слайдшоу останавливается немедленно; пользователь видит информационное сообщение (без слова «ошибка»).
2. **Сценарий B (аудио):** 3 последовательных цикла с пустым path или немедленным `STATE_ENDED` — слайдшоу останавливается с сообщением, содержащим имя ресурса.
3. **Сценарий B (изображения):** 3 последовательных сетевых ошибки Glide — слайдшоу останавливается аналогично.
4. Единичный сбой загрузки одного файла не прерывает слайдшоу — файл пропускается как прежде.
5. Нажатие кнопки слайдшоу после остановки сбрасывает счётчик и возобновляет слайдшоу.
6. Новые строки присутствуют во всех трёх локалях (EN/RU/UK) без пропусков.
7. Поведение воспроизводимо на реальном сетевом ресурсе при отключении сервера/WiFi.
