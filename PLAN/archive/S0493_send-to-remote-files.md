# Стратегическая спецификация: S0493 - «Отправить в..» для файлов с любого источника

**Ticket:** S0493
**Status:** Archived
**Priority:** 80
**Date:** 2026-06-17
**Tier:** 3 - Moderate (ad-hoc)
**Roadmap entry:** Ad-hoc - запрос владельца 2026-06-17
**Tactical spec:** `PLAN/S0493_send-to-remote-files/` (будет создан через `/spec-tech`)

> **Scope:** STRATEGIC. Цели, ограничения, открытые вопросы. Без имён классов, путей, лимитов строк, миграций Room, модулей Hilt.

---

## 1. Проблема

В плеере команда «Отправить в..» (унифицированное Send-to меню) присутствует только для файлов, лежащих локально. Для файлов с сетевых и удалённых ресурсов (FTP, SMB, облако, HTTP) меню исчезает целиком: подменю не строится, и пользователь не видит ни одного получателя, даже если в настройках все нужные получатели включены.

Поведение непрозрачно: владелец видит включённые тумблеры в настройках плеера, открывает удалённый аудио/видео/изображение и не находит команду без всякой обратной связи. С точки зрения пользователя файл «открыт и играет» - значит, и поделиться им он вправе; разница между локальным и сетевым источником не должна на это влиять.

Область: плеер (унифицированный медиаплеер) и слой подготовки контента для шаринга.

---

## 2. Цели

1. Команда «Отправить в..» присутствует в меню плеера для файла с **любого** источника - локального и удалённого - на равных.
2. Состав получателей в подменю определяется только настройками и применимостью к типу медиа, а не тем, локальный файл или сетевой.
3. Для получателей, которым нужен реальный файловый URI, удалённый файл при выборе получателя материализуется во временную локальную копию прозрачно для пользователя.
4. Пользователь видит понятную обратную связь во время подготовки (ожидание/прогресс) и при сбое (ошибка сети, нет места).
5. Подготовку можно отменить, и она не оставляет «мусора» в кэше.

**Non-goals:**

- Изменение состава получателей или их логики гейтинга по настройкам.
- Стриминговый шаринг без скачивания (передача URL вместо файла) - не цель этой итерации.
- Кэширование ради ускорения повторного воспроизведения - временная копия служит только шарингу.
- Шаринг каталогов/папок целиком.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Единообразие важнее оптимизации: «пользователю всё равно, что под капотом» - меню обязано быть одинаковым.
2. Если для получателя достаточно отдать URL без скачивания (например, системный шаринг текстом/ссылкой) - желательно не скачивать зря.
3. Желательно переиспользовать уже скачанную копию, если пользователь выбирает второго получателя для того же файла в рамках одной сессии.

### 3.2 Жёсткие ограничения

- **Flavor:** все флейворы, где доступен плеер и удалённые источники (`standard`, `lite`, `photos`, `legacy`; `noLegal`/`vr` по наследованию от `standard`). Без флейвор-специфичного кода - поведение общее.
- **API level:** без API-специфики; минимальный поддерживаемый уровень проекта.
- **Wear OS:** не затрагивается.
- **Производительность:** временная копия не должна блокировать UI-поток; для крупных файлов подготовка идёт в фоне с возможностью отмены. Контроль объёма временного кэша обязателен.
- **Совместимость данных:** без миграций. Временные копии живут в приватном кэше приложения и подлежат очистке.
- **Локализация:** EN/RU/UK обязательно для всех новых пользовательских строк (прогресс, отмена, ошибки).
- **Доступность:** индикатор подготовки и его отмена доступны через TalkBack; не-цветовое различие состояний.

### 3.3 Owner inputs (Approval gate)

- **UI placement contract:** пункт «Отправить в..» остаётся в том же месте меню плеера (верх ⋯-оверфлоу, подменю с получателями); для удалённого файла появляется промежуточное состояние подготовки до запуска получателя.
- **Accessibility:** индикатор подготовки и кнопка отмены озвучиваются TalkBack; состояние не передаётся только цветом.
- **Communication policy:** новые строки (подготовка, отмена, ошибки сети/места) проходят `docs/COMMUNICATION_POLICY.md`, тон-чеклист (§6 политики) - обязательный гейт перед интеграцией строк.
- **Localization:** EN/RU/UK в локстепе для всех новых строк.
- **Performance budget:** скачивание не на главном потоке; верхняя граница объёма временного кэша и стратегия вытеснения определяются в §6.
- **Validation level:** ручная проверка на устройстве на реальном удалённом ресурсе (FTP/SMB/cloud) для каждого основного типа медиа.
- **Owner sign-off:** 2026-06-17.
- **Related tickets:** S0459 (родительское unified send-to), S0478 (иконки получателей), S0452 (multibinding-seam получателей).

## 4. Контекст текущей архитектуры

За команду отвечает слой подготовки контента плеера: он собирает «делимый контент» (набор URI + MIME + тип медиа) и передаёт его менеджеру send-to, который строит подменю из гейтированного списка получателей. Подготовка контента опирается на построение локального файлового URI; для пути с сетевой схемой URI не строится, и сборка контента возвращает «пусто». Раннее «пусто» приводит к тому, что подменю вообще не добавляется - гейтинг получателей не доходит до выполнения.

Сейчас задачу нельзя решить точечно, потому что меню принципиально завязано на немедленную доступность локального файла. Удалённые источники у плеера читаются своим механизмом доступа, и между «файл играет из сети» и «файл можно отдать получателю как локальный URI» нет связующего звена - его и нужно ввести.

---

## 5. Предлагаемый подход

Развязать «наличие команды» от «немедленной локальной доступности файла». Команда «Отправить в..» строится всегда, когда есть открытый файл и хотя бы один применимый получатель; материализация удалённого файла в локальную копию выполняется лениво - в момент выбора получателя, которому нужен файловый URI.

### 5.1 Основные столпы / модули

**Сборка делимого контента, независимая от источника.**

- Контент описывает файл логически (тип, имя, источник), а не обязательно готовым локальным URI.
- Для локального файла URI доступен сразу; для удалённого - помечается как «требует материализации».

**Материализация удалённого файла.**

- Роль, которая по запросу скачивает удалённый файл во временную приватную область и возвращает локальный URI.
- Работает в фоне, сообщает прогресс, поддерживает отмену, корректно обрабатывает ошибки сети и нехватку места.
- В пределах сессии переиспользует уже скачанную копию того же файла.

**Управление временным кэшем шаринга.**

- Отдельная приватная область для временных копий с очисткой: по завершении/отмене, по выходу из плеера и по верхней границе объёма.

**Гейтинг получателей - без изменения семантики.**

- Список получателей строится одинаково для любого источника.
- Получатели, способные принять URL/логический источник без файла, могут запускаться без материализации; остальным предоставляется локальная копия.

### 5.2 Потоки данных и событий

- Открытие меню: UI → слой подготовки контента → строит логический контент (источник + тип) → менеджер send-to строит подменю из гейтированного списка получателей. Источник на состав подменю не влияет.
- Выбор получателя для удалённого файла: менеджер send-to → запрос материализации → фоновое скачивание (прогресс/отмена) → локальный URI → запуск получателя.
- Выбор получателя, не требующего файла: запуск напрямую, без материализации.
- Завершение/отмена/выход: очистка временной копии согласно политике кэша.

### 5.3 Точки расширяемости

- Абстракция «источник контента → локальный URI» открыта для разных типов удалённых ресурсов (FTP/SMB/облако/HTTP) за единым контрактом.
- Признак получателя «нужен ли файловый URI или достаточно логического источника» - расширяемое свойство получателя, не хардкод по id.
- Политика кэша (граница объёма, момент очистки) вынесена в отдельную роль и заменяема.
- Новая зависимость для доступа к удалённым источникам из слоя шаринга подключается на уровне роли; конкретная проводка - в `/spec-tech`.

## 6. Открытые вопросы / Research items

1. **Признак «получателю нужен файл»**
   - **Вопрос:** какие из текущих получателей могут принять удалённый источник без скачивания (например, системный шаринг ссылкой), а какие требуют реального файла?
   - **Нужно выяснить:** ревизия получателей и их способа передачи контента; ввести явный признак вместо допущения «всем нужен файл».
   - **Статус:** Open

2. **Источник локального URI для удалённого файла**
   - **Вопрос:** откуда берётся байтовый поток удалённого файла для копирования - переиспользуется механизм доступа плеера или отдельный путь?
   - **Варианты:** переиспользовать существующий доступ к ресурсу; отдельная загрузка по пути ресурса.
   - **Нужно выяснить:** наличие готового механизма чтения удалённого файла целиком и его пригодность.
   - **Статус:** Open

3. **Политика временного кэша**
   - **Вопрос:** верхняя граница объёма, момент и триггеры очистки, поведение при нехватке места.
   - **Нужно выяснить:** разумный лимит и стратегия вытеснения, чтобы не разрастаться и не мешать другим кэшам.
   - **Статус:** Open

4. **Multi-file и крупные файлы**
   - **Вопрос:** поведение при выборе нескольких файлов и для очень крупных файлов (видео) - материализовать все или по требованию получателя; пороги предупреждения.
   - **Нужно выяснить:** UX для batch-получателей и для одиночных (первый файл) при удалённом источнике.
   - **Статус:** Open

5. **Поведение при сбое и отмене**
   - **Вопрос:** как сообщать об ошибке сети/места и что происходит при отмене на середине.
   - **Нужно выяснить:** набор состояний и сообщений, согласованный с `docs/COMMUNICATION_POLICY.md`.
   - **Статус:** Open

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Скачивание крупного видео блокирует UI или копит память | Средняя | Зависание/ANR, рост потребления | Фоновая загрузка с прогрессом и отменой, потоковое копирование без буферизации целиком в память |
| Разрастание временного кэша | Средняя | Заполнение хранилища устройства | Граница объёма + очистка по завершении/выходу |
| Часть получателей не работает с локальной копией из кэша | Низкая | Получатель не запускается | Признак «нужен файл», проверка запуска и обратная связь при провале |
| Утечка временных копий при крашe/убийстве процесса | Низкая | Остаточные файлы | Очистка при входе/выходе из плеера, идемпотентная чистка области кэша |
| Ошибки доступа к удалённому ресурсу (таймаут, обрыв) | Средняя | Команда «висит» | Таймаут, явное сообщение об ошибке, безопасная отмена |

## 8. Влияние на пользователя (docs/FEATURES)

Новая воспринимаемая способность: «Отправить в..» теперь работает для файлов с сетевых и облачных источников, а не только локальных. Одно предложение для `docs/FEATURES.md` + `_RU` + `_UK` при внедрении: возможность отправлять/делиться файлами напрямую из плеера независимо от того, лежит файл локально или на удалённом ресурсе.

## 9. Архитектурные решения (ADR)

**ADR-1: Ленивая материализация в момент выбора получателя**

- **Решение:** удалённый файл скачивается во временную копию не при открытии меню, а при выборе получателя, которому нужен файл.
- **Альтернативы:** скачивать при открытии меню (заранее); никогда не скачивать (оставить ограничение).
- **Почему:** открытие меню должно быть мгновенным и бесплатным; скачивание - только при реальном намерении поделиться, и только если получателю это нужно.

**ADR-2: Команда строится независимо от доступности локального URI**

- **Решение:** наличие подменю «Отправить в..» определяется наличием открытого файла и применимых получателей, а не готовым локальным URI.
- **Альтернативы:** сохранить связку «нет URI → нет меню».
- **Почему:** именно эта связка и есть корень проблемы из §1.

## 11. Критерии готовности (strategic-level)

1. Для удалённого аудиофайла (FTP/SMB/облако) в плеере есть команда «Отправить в..» с тем же составом получателей, что и для локального файла при тех же настройках.
2. Выбор получателя, которому нужен файл, для удалённого источника приводит к успешной отправке после прозрачной подготовки.
3. Во время подготовки пользователь видит индикатор и может отменить её.
4. Отмена и завершение не оставляют временных копий сверх установленной политики кэша.
5. При ошибке сети/нехватке места пользователь получает понятное сообщение, а не молчаливое исчезновение команды.
6. Поведение единообразно для основных типов медиа (аудио, видео, изображение, документ).
