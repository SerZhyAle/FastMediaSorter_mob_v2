## 1. Проблема

Когда пользователь открывает медиафайл во внешнем (STANDALONE) режиме — приложение запущено как просмотрщик по системному `ACTION_VIEW`/`ACTION_SEND` из другого приложения — он получает урезанный набор функций по сравнению со встроенным (in-app) проигрывателем. Верхняя командная панель присутствует, но в ней мало кнопок: type-specific действия (для изображений, видео, аудио, документов), доступные в in-app плеере, в standalone отсутствуют. Кроме того, в standalone нет листания по соседним файлам папки (вперёд/назад/случайно/слайд-шоу) — просмотр ограничен одним файлом.

Отдельная проблема — действие «Открыть в FastMediaSorter» из меню standalone: сейчас оно открывает экран обзора (Browse-список), а не in-app проигрыватель нужного типа на конкретном файле. Пользователь ожидает попасть сразу в полноценный плеер на этом файле, а не в список.

Область: feature-path «Player/playback/doc viewing» и «Browse/media list operations» модуля `app_v2`. Предшественник — S0380, который раздробил единый standalone-плеер на четыре per-type экрана и ввёл контракт возможностей хоста; данная спека — следующая фаза: довести паритет до полного и переключить маршрутизацию.

---

## 2. Цели

1. В standalone-режиме верхняя командная панель показывает те же type-specific действия, что и in-app плеер, для каждого поддерживаемого типа медиа (изображение, видео, аудио, документ, текст, анимация) — в пределах того, что технически применимо к одиночному внешнему файлу.
2. В standalone-режиме восстановлено листание по соседним файлам той же папки: вперёд/назад, случайный выбор, слайд-шоу — там, где источник файла позволяет перечислить папку.
3. Действие «Открыть в FastMediaSorter» открывает встроенный проигрыватель нужного типа на конкретном файле, а не экран обзора.
4. «Открыть в FastMediaSorter» разрешает целевой ресурс по детерминированной цепочке: существующий виртуальный ресурс «Все файлы» → типовой агрегирующий ресурс («Все фотографии»/«Всё видео»/«Все документы» по типу файла) → создание нового ресурса по локальной папке файла.
5. Поведение паритета корректно деградирует по флейворам и типам источника: где функция неприменима (нет поддержки типа во флейворе, файл вне локальной файловой системы), действие скрывается или ведёт к понятному фолбэку, а не к ошибке.

**Non-goals:**

- Переписывание самого in-app проигрывателя или его командной панели.
- Добавление новых медиаформатов или кодеков.
- Изменение механизма включения/отключения приложения как обработчика внешних файлов (primary media player) — он остаётся как есть.
- Wear OS — не затрагивается.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Новый ресурс, создаваемый при «Открыть в FastMediaSorter», именуется по локальной папке файла и содержит «все поддерживаемые медиафайлы» этой папки.
2. Если в настройках приложения включён режим «все файлы», то и создаваемый ресурс — типа «все файлы» (а не сужается до типа открытого файла).
3. Паритет кнопок должен ощущаться как «тот же плеер», а не как урезанный просмотрщик.

### 3.2 Жёсткие ограничения

- **Flavor:** паритет применим только во флейворах, где приложение работает как внешний проигрыватель (`SUPPORTS_DEFAULT_PLAYER=true`): `standard`, `legacy`, `vr`, `noLegal`, а также `photos` (только image/video). Во флейворе `lite` внешние точки входа отсутствуют — паритет туда не применяется. Реализация следует `dev/FLAVOR_DEVELOPMENT_RULES.md`: различия типов медиа гейтятся через существующие `SUPPORT_*`-абстракции и source-set дисциплину, без `BuildConfig.IS_*`-проверок флейвора в `src/main/`.
- **API level:** без новой платформенной API-специфики. Уже существующие API-форки (удаление/доступ к медиа по версиям Android, типизированные/legacy способы чтения внешнего URI) переиспользуются; минимальный baseline — minSdk флейвора (23 для legacy, 26 для остальных).
- **Wear OS:** не затрагивается.
- **Производительность:** перечисление папки и резолв ресурса при «Открыть в FMS» не должны блокировать UI-поток; синхронные запросы к контент-провайдеру за метаданными выполняются вне главного потока.
- **Совместимость данных:** создание ресурса по папке использует существующий механизм ресурсов; новых форм хранения не вводится. Синтетический/одиночный контекст не должен загрязнять постоянный список ресурсов пользователя, если это не явное создание ресурса по папке.
- **Локализация:** EN/RU/UK — обязательно для всех новых пользовательских строк (имена создаваемых ресурсов, пункты меню, фолбэк-сообщения).
- **Доступность:** новые кнопки панели имеют корректные contentDescription, фокус для D-pad/TV, touch target ≥ 48dp; различие состояний не только цветом.

### 3.3 Owner inputs (Approval gate)

- **Flavor scope:** паритет в `standard`/`legacy`/`vr`/`noLegal`; `photos` — только image/video (нет audio/docs по `SUPPORT_*`); `lite` — вне объёма (нет внешних точек входа). Реализация типовых различий — через `SUPPORT_*`-гейты и флейворные source-set, не через флаги в `src/main`.
- **API level constraints:** без новых platform API; переиспользуются существующие версионные форки доступа к медиа; baseline — minSdk флейвора.
- **Performance budget:** перечисление папки и резолв ресурса — вне главного потока; цель — отсутствие видимого фриза при открытии файла извне.
- **Data compatibility:** новый ресурс создаётся через существующий механизм ресурсов; одиночный/временный контекст не попадает в постоянный список без явного создания по папке.
- **UI placement contract:** type-specific кнопки занимают те же позиции верхней командной панели, что и в in-app режиме; неприменимые кнопки скрываются, а не дизейблятся-навсегда. Точный состав кнопок по типам — §6 (Open).
- **Accessibility:** contentDescription + D-pad-фокус + ≥48dp для каждой новой кнопки; не-цветовое различие состояний.
- **Communication policy:** новые строки (имена ресурсов, фолбэки, пункты меню) проходят тон-чеклист `docs/COMMUNICATION_POLICY.md` §6 перед интеграцией.
- **Localization:** EN/RU/UK в lockstep для всех новых строк.
- **Validation level:** device-test обязателен (внешние intent-сценарии воспроизводятся только на устройстве); статус после реализации — `BlockNeedUserTest`.
- **Owner sign-off:** 2026-06-09 — объём подтверждён владельцем (полный паритет кнопок; цепочка резолва ресурса; восстановление листания по папке).
- **Related tickets:** S0380 (предшественник, раздробил standalone-плеер; должен быть подтверждён на устройстве как предусловие).

## 4. Контекст текущей архитектуры

За воспроизведение медиа отвечают два семейства хостов. In-app проигрыватель строит плейлист из контекста ресурса (зарегистрированной папки/списка) и потому всегда имеет источник данных для листания и для полной командной панели. Standalone-хосты (введённые S0380 как четыре per-type экрана плюс диспетчер для типонезависимых интентов) оперируют одиночным внешним URI без контекста ресурса — отсюда и одиночная семантика, и урезанный набор кнопок. Разветвление поведения между двумя семействами осуществляется через контракт возможностей хоста (capability-флаги), а не через прямую проверку «standalone ли это».

Корень проблемы: встроенный проигрыватель сейчас требует контекста ресурса для запуска, а standalone его не имеет. Поэтому (а) листание по соседним файлам в standalone отключено контрактом, (б) часть type-specific кнопок не протянута в standalone, (в) «Открыть в FastMediaSorter» вынужденно ведёт в обзор: чтобы открыть in-app плеер, нужно сначала получить контекст ресурса, который из внешнего URI напрямую не выводится. Механизмы обратного резолва (поиск ресурса по родительской папке локального файла) и открытия экрана «на конкретном файле внутри ресурса» в кодовой базе уже существуют — но применяются для маршрута в обзор, а не в плеер.

## 5. Предлагаемый подход

Подход состоит из трёх связанных направлений, опирающихся на существующий seam возможностей хоста и существующий механизм резолва ресурса по папке.

### 5.1 Основные столпы / модули

**Столп A — Паритет командной панели в standalone.**
Type-specific действия объявляются и показываются единообразно для in-app и standalone хостов. Видимость каждой кнопки определяется двумя осями: тип медиа (что применимо к формату) и возможности хоста (что применимо к одиночному внешнему файлу против контекста ресурса). Кнопки, неприменимые к standalone по существу (например, действия, требующие списка), управляются листанием из столпа B; кнопки, требующие только одиночного файла (поворот, обрезка, сжатие, печать, перевод/распознавание текста, тексты песен и т. п.), протягиваются в standalone с реальными реализациями вместо заглушек. Неприменимые во флейворе/типе кнопки скрываются.

**Столп B — Листание по папке в standalone.**
Standalone-хост получает возможность перечислить соседние файлы той же папки источника и включить навигацию вперёд/назад/случайно/слайд-шоу. Возможность активируется только когда источник файла перечислим (локальная файловая система); для неперечислимых источников (отдельные content-URI, сетевые) сохраняется одиночная семантика. Активация выражается через контракт возможностей хоста, а не через ветку «if standalone».

**Столп C — Маршрутизация «Открыть в FastMediaSorter» в in-app плеер.**
Действие резолвит целевой ресурс по детерминированной цепочке и открывает встроенный проигрыватель нужного типа на конкретном файле внутри найденного/созданного ресурса:

1. Если существует виртуальный ресурс «Все файлы» — открыть плеер на файле в нём.
2. Иначе — типовой агрегирующий ресурс по типу файла («Все фотографии» / «Всё видео» / «Все документы» / соответствующий типу), если он существует.
3. Иначе — создать новый ресурс по локальной папке файла: имя = имя папки, содержимое = «все поддерживаемые медиафайлы» папки; если в настройках включён режим «все файлы», создаваемый ресурс — типа «все файлы».
4. Если файл не на локальной файловой системе (нельзя вывести папку/ресурс) — понятный фолбэк (текущее поведение: обзор/главный экран), без ошибки.

### 5.2 Потоки данных и событий

- Standalone-панель: UI standalone-хоста → слой определения видимости кнопок (тип × возможности хоста) → те же обработчики действий, что и in-app, применённые к одиночному файлу или к перечисленной папке.
- Листание: standalone-хост → перечисление папки источника (вне главного потока) → формирование списка → контракт сообщает «листание доступно» → навигационные кнопки активны.
- «Открыть в FMS»: пункт меню → резолвер ресурса (по цепочке §5.1.C, чтение списка ресурсов и настройки «все файлы») → запуск in-app проигрывателя «на файле внутри ресурса» либо создание ресурса по папке → плеер; при неудаче резолва — фолбэк.

### 5.3 Точки расширяемости

- Контракт возможностей хоста расширяется новыми флагами (листание в standalone, доступность отдельных групп кнопок) — единая точка ветвления для обоих семейств хостов.
- Резолвер целевого ресурса для «Открыть в FMS» вводится как отдельная роль, переиспользуемая будущими внешними точками входа; абстрагирует цепочку «всефайловый → типовой → создать по папке».
- Перечисление папки для standalone опирается на абстракцию источника, чтобы позже расширить листание на нелокальные источники без переписывания хоста.
- Новое связывание зависимостей (резолвер ресурса, поставщик перечисления папки) подключается на уровне DI — конкретика откладывается в `/spec-tech`.

## 6. Открытые вопросы / Research items

1. **Точный состав type-specific кнопок паритета**
   - **Вопрос:** какие именно кнопки in-app панели должны появиться в standalone в рамках этой спеки, а какие вынести в отдельные тикеты?
   - **Решение владельца (2026-06-09):** протянуть в standalone сразу все кнопки in-app панели, применимые к одиночному внешнему файлу (поворот, обрезка/кроп, сжатие, печать, OCR, перевод, Google Lens, тексты песен, cast и пр.). Отдельными тикетами выносятся только те, что технически требуют контекста списка/папки и не покрываются листанием из столпа B.
   - **Архитектурная находка (2026-06-09, ресерч Phase 04):** standalone-активности НЕ используют движок in-app панели (`CommandPanelController`/`CommandPanelAvailabilityUpdater`) — у каждой своя компактная панель. Большинство type-specific хелперов (OCR, Google Lens, печать, перевод изображения, save-frame, sleep-timer, lyrics, отдельное окно, VR) жёстко привязаны к `ActivityPlayerUnifiedBinding`/`PlayerActivity` и непереиспользуемы из standalone без рефактора seam. Без рефактора готовы к standalone только **crop / cropToFile / compress / draw overlay** (generic-хелперы) и **rotation toggle** (нужен метод в VM). Документы (PDF/EPUB) уже имеют рабочие type-specific кнопки.
   - **Решение владельца (2026-06-09, уточнённое):** в S0389 реализовать только группу A (crop/cropToFile/compress/draw/rotate) через готовые generic-хелперы. Остальные действия (OCR, Lens, печать, перевод, save-frame, sleep-timer, lyrics) выносятся отдельными тикетами — каждый требует рефактора своего binding-зависимого хелпера в generic-seam. Размещение в панели — как in-app: по приоритету в командной строке, при нехватке места уходят в ниспадающее (overflow) меню.
   - **Статус:** Resolved (S0389 = группа A; остальное — follow-up тикеты, см. §10)

2. **Перечислимость источника для листания**
   - **Вопрос:** для каких типов внешних URI можно надёжно перечислить родительскую папку (прямой файловый путь, content:// с резолвом в путь, SAF-дерево)?
   - **Нужно выяснить:** границы, за которыми листание отключается и сохраняется одиночная семантика; стоимость перечисления больших папок.
   - **Статус:** Open

3. **Семантика создаваемого ресурса**
   - **Вопрос:** создаваемый по папке ресурс — постоянный (добавляется в список ресурсов пользователя) или временный на сессию?
   - **Решение владельца (2026-06-09):** постоянный — добавляется в список ресурсов пользователя. При повторном открытии файлов из той же папки переиспользуется ранее созданный ресурс (без дублей).
   - **Нужно выяснить (код-ресерч для `/spec-tech`):** ключ идентичности для переиспользования (нормализованный путь папки); поведение при изменении настройки «все файлы» между открытиями.
   - **Статус:** Resolved

4. **Идентификация «всефайлового» и типовых агрегирующих ресурсов**
   - **Вопрос:** как детерминированно определить ресурс «Все файлы» и типовые «Все фотографии/видео/документы» среди ресурсов пользователя?
   - **Нужно выяснить:** существуют ли такие виртуальные/агрегирующие ресурсы как сущности, по какому признаку их находить; что если их несколько/нет.
   - **Статус:** Open

5. **Предусловие S0380**
   - **Вопрос:** подтверждён ли S0380 на устройстве (все 4 standalone-хоста показывают панель)?
   - **Решение (2026-06-09):** владелец подтвердил работу на устройстве; S0380 переведён в `Verified` и заархивирован. Предусловие снято.
   - **Статус:** Resolved

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Файл вне зарегистрированного/локального ресурса (content://, SAF, сеть) — in-app плеер требует контекста ресурса | Высокая | «Открыть в FMS» не сможет открыть плеер | Цепочка резолва с явным фолбэком; создание ресурса по папке только для локальных путей; иначе — текущий фолбэк без ошибки |
| Часть type-specific действий в standalone сейчас заглушки (пустые callback-и) | Средняя | Кнопка видима, но ничего не делает | Перед добавлением кнопки протянуть реальную реализацию; неполноценные действия не показывать |
| Рост размера хост-классов панели/плеера за лимит сопровождаемости | Средняя | Усложнение поддержки | Выносить логику видимости и резолва в отдельные helper-роли/менеджеры |
| Перечисление больших папок на главном потоке | Средняя | Фриз при открытии файла извне | Перечисление и метаданные — вне главного потока |
| Создаваемые по папке ресурсы засоряют список пользователя | Средняя | Раздражение, дубли ресурсов | Решить семантику постоянства (§6.3); переиспользовать ранее созданный ресурс той же папки |
| Дубли в системном «Открыть с помощью» при правках intent-фильтров | Низкая | Путаница в системном диалоге | Не трогать манифестные aliases в рамках этой спеки; ограничиться внутренней навигацией |
| Расхождение паритета между флейворами (photos без audio/docs) | Низкая | Кнопка ведёт в неподдерживаемый тип | Гейт через существующие `SUPPORT_*`; скрывать неприменимое |

## 8. Влияние на пользователя (docs/FEATURES)

Новое для пользователя: внешний просмотр файла в FastMediaSorter получает полный набор действий проигрывателя и листание по папке, а «Открыть в FastMediaSorter» открывает встроенный плеер на самом файле. Предложение для `docs/FEATURES.md` + `_RU` + `_UK`: «При открытии файла из другого приложения FastMediaSorter показывает полноценный проигрыватель с командной панелью и листанием по соседним файлам папки; действие „Открыть в FastMediaSorter“ открывает встроенный плеер сразу на выбранном файле».

## 9. Архитектурные решения (ADR)

**ADR-1: Ветвление через контракт возможностей хоста, а не «if standalone»**

- **Решение:** все новые различия (листание, группы кнопок) выражаются флагами контракта возможностей хоста.
- **Альтернативы:** прямые проверки режима standalone в коде панели/плеера.
- **Почему:** сохраняет единый seam, введённый S0380; не плодит разрозненные ветки; облегчает будущее расширение на нелокальные источники.

**ADR-2: «Открыть в FMS» — цепочка резолва ресурса с фолбэком, а не безусловное создание ресурса**

- **Решение:** детерминированная цепочка «всефайловый → типовой → создать по папке → фолбэк».
- **Альтернативы:** всегда создавать новый ресурс; всегда вести в обзор.
- **Почему:** соответствует ожиданию владельца, минимизирует засорение списка ресурсов, корректно деградирует для нелокальных файлов.

## 11. Критерии готовности (strategic-level)

1. При открытии изображения/видео/аудио/документа из другого приложения пользователь видит верхнюю командную панель с тем же набором применимых type-specific действий, что и во встроенном плеере.
2. В standalone работают кнопки листания по соседним файлам папки (вперёд/назад/случайно/слайд-шоу), когда источник файла перечислим; для неперечислимых источников остаётся корректный одиночный просмотр.
3. «Открыть в FastMediaSorter» открывает встроенный проигрыватель нужного типа на выбранном файле, а не экран обзора.
4. При отсутствии всефайлового и типового ресурсов «Открыть в FastMediaSorter» создаёт ресурс по локальной папке файла (имя = папка; содержимое = поддерживаемые медиа; «все файлы», если включено в настройках) и открывает плеер в нём.
5. Для файла вне локальной файловой системы действие даёт понятный фолбэк без ошибки.
6. Поведение консистентно по флейворам: где тип не поддержан (`photos` без audio/docs) или внешних точек входа нет (`lite`), неприменимые действия скрыты.
