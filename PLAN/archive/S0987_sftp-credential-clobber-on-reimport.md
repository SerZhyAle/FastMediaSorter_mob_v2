## 0. Захваченный материал (inbox)

**Захвачено:** 2026-07-11 (out-of-scope находка при adversarial-ревью S0984).

**Симптом:** импорт companion `.fmscfg` для host:port, для которого у пользователя уже есть рабочий SFTP-ресурс, молча затирает сохранённый кред - пароль и/или SSH-приватный ключ. Данные теряются без предупреждения, ресурс перестаёт аутентифицироваться.

**Механизм (доказательство, код):**
- `ImportCompanionConfigUseCase.import()` вызывает `smbOperationsUseCase.saveSftpCredentials(host, port, username, password = config.password.orEmpty())` без `privateKey` (default `null`).
- `SmbOperationsUseCase.saveSftpCredentials` (update-ветка, `SmbOperationsUseCase.kt:355-363`) находит существующий кред по `getByTypeServerAndPort("SFTP", host, port)` и **обновляет его на месте**: `encryptedPassword = CryptoHelper.encrypt(password) ?: ""`, `username = username`, `sshPrivateKey = privateKey`. Возвращает ТОТ ЖЕ `credentialId`, на который всё ещё указывает существующий ресурс.
- Итог: (а) непустой пароль из файла перезаписывает существующий; (б) при `privateKey = null` существующий SSH-ключ обнуляется -> ключевой ресурс ломается (ключ невосстановим).

**Почему pre-existing (не регресс S0984):** поведение `saveSftpCredentials` и путь `import()` существуют с S0421; SAF-кнопка «Импорт из компаньона» имеет ту же проблему. S0984 лишь понизил порог (one-tap приём вложения) и релаксацию (пустой пароль теперь принимается парсером). В S0984 частично закрыто: `CompanionConfigImportActivity` требует непустой пароль в диалоге, что убирает клоббер пустым паролем через новый UI. Остаётся: (а) SAF-путь с passwordless-файлом; (б) обнуление SSH-ключа при любом ре-импорте на host:port с ключевой аутентификацией.

**Затронутые вызывающие (нужно исследовать перед фиксом):** `saveSftpCredentials` вызывается также из add/edit-resource флоу (`AddResourceSftpFtpCoordinator` и др.) - изменение семантики (preserve-on-blank / не-null-ить ключ) имеет blast radius на редактирование кредов. Нужен аудит всех вызывающих.

**Вложения:** нет.

**Research (2026-07-11, автономно):** аудит вызывающих + auth precedence - `PLAN/S0987_sftp-credential-clobber-on-reimport/research/01__caller-audit-auth-precedence.md`.

## 1. Проблема (черновик)

Ре-импорт/повторное сохранение SFTP-кредов для уже существующего host:port должно быть неразрушающим по умолчанию (или явно предупреждать), особенно при импорте из недоверенного файла. Сейчас пустой пароль или отсутствие ключа молча уничтожают рабочие креды.

Модель хранения: один кред-ряд на host:port, шаренный между ресурсами. `saveSftpCredentials` (update-ветка) срабатывает при коллизии CREATE/import-намерения с существующим рядом и затирает не переданные поля.

## 5. Направления решения (черновик, уточнено research)

**Установлено research:**
- Все 5 вызывающих `saveSftpCredentials` - CREATE/import-намерение. Настоящий edit идёт через `ResourceEditorUseCase.updateCredentialInPlace` (по UUID) и НЕ вызывает `saveSftpCredentials`. Значит заявленный риск Варианта A («ломает очистку в edit-флоу») не подтверждается.
- Auth precedence (`SftpConnectionPool.applyAuth`): при `privateKey != null` используется только publickey, пароль игнорируется.

**Автономно-безопасный срез (устраняет невосстановимую потерю ключа):**
- `sshPrivateKey = privateKey ?: existing.sshPrivateKey` в update-ветке. Безопасен для всех вызывающих (key-coordinator шлёт non-null ключ; password-пути сохраняют старый ключ). Готов к реализации после утверждения подхода.

**Owner-gated срез (см. §6):**
- Preserve-on-blank для пароля НЕ автономен: `encryptedPassword` переиспользуется под passphrase ключа (`AddResourceSftpKeyCoordinator` шлёт `password = keyPassphrase ?: ""`), сохранение старого пароля как passphrase сломает беспарольный ключ.
- Политика коллизии host:port - продуктовое решение (тихий merge / предупредить / отдельный ряд).

Варианты политики коллизии:
- Вариант A (тихий неразрушающий merge): не затирать не переданные поля. Минимум фрикции; при импорте пароля поверх ключа импорт «успешен», но пароль игнорируется (побеждает ключ).
- Вариант B (предупредить): при коллизии host:port диалог «у вас уже есть доступ к этому серверу - перезаписать / оставить / отмена». Явно и безопасно, больше работы.
- Вариант C (отдельный ряд): импорт из `.fmscfg` создаёт собственный кред-ряд вместо шаринга по host:port. Убирает коллизию архитектурно.

## 6. Открытые вопросы (owner decision - блокирует переход)

При CREATE/import-сохранении SFTP-кредов для host:port, у которого УЖЕ есть сохранённый кред (шаренная модель «один ряд на host:port»), и входные данные опускают поле, которое у существующего кред есть (пустой пароль либо отсутствующий SSH-ключ) - что делать?

1. Политика коллизии: Вариант A (тихий неразрушающий merge) / B (предупредить диалогом) / C (отдельный кред-ряд на импорт)?
2. Отдельно от политики: реализовать сейчас автономно-безопасный срез (не обнулять существующий SSH-ключ при `privateKey == null`) как немедленный floor против невосстановимой потери ключа - да/нет?

Пока решение не принято - тикет в BlockQuestions. Автономный research завершён; после выбора реализация близка к механической.

**Разрешено (2026-07-11, owner):** Вариант **A** - тихий неразрушающий merge. Реализовано в `SmbOperationsUseCase.saveSftpCredentials` (update-ветка):
- `sshPrivateKey = privateKey ?: existing.sshPrivateKey` - ключ не обнуляется на null.
- `encryptedPassword` через `when`: при `privateKey != null` - passphrase нового ключа; при существующем ключевом кред - сохранить его passphrase (ключ побеждает, входной пароль дропается, иначе испортил бы passphrase-слот); при пустом пароле - сохранить существующий; иначе - обновить явным паролем.
- Регрессионные тесты в `SmbOperationsUseCaseTest` (обе preserve-ветки не зовут `CryptoHelper.encrypt`, потому JVM-тестируемы).
- Опциональная доп-уверенность: on-device round-trip (импорт companion-конфига поверх существующего ключевого ресурса того же host:port -> ключ выживает) - смежно с S0984.
