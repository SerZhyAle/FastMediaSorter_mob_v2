# 01 - Способ разрешения ссылок

**Вопрос §6.1:** как отличить настоящую ссылку на флейвор-тип от совпадения простого имени?

**Дата:** 2026-08-09. **Метод:** чтение `app_v2/build.gradle.kts` (блок `sourceSets`, строки 577-756), инвентаризация наборов исходников, подсчёт файлов.

---

## Измеренная область

- Общих тестов в `app_v2/src/test`: **470** файлов `*.kt`.
- Флейвор-областных наборов: **28**, суммарно **265** файлов `*.kt`.
- Общий объём сканирования статическим гейтом: ~735 файлов. Для PowerShell-скана это единицы секунд, то есть цена совместима с батчем быстрых гейтов.

## Вариант A - косвенная проверка компиляцией

Идея из §0: компилировать юнит-тестовый набор самого урезанного флейвора. Проверка карты монтирования показывает, что одного флейвора недостаточно.

- `lite` не монтирует `streamingEnabled`, `cloudEnabled`, `networkMonitor`, `launcherEnabled`, `screenCapture`, `ocrEnabled`, `translationEnabled`, `translationMlKit`, `wearGms`, `vr`, `vrOnly` - эту половину дефектов компиляция `lite` ловит.
- Но `lite` - единственный флейвор, монтирующий `cloudDisabled`, и один из двух, монтирующих `streamingDisabled` и `ocrDisabled`. Ссылка из общего теста на тип из `cloudDisabled` компилируется на `lite` и ломает остальные пять флейворов. Эту половину компиляция `lite` не видит вообще.
- Объединение `lite` + `noLegal` всё ещё оставляет непокрытыми `standard`, `legacy`, `photos`, `vr`, `vrOnly`, `standardScreenCapture`, `standardEdgeTile`, `castDisabled`.
- Полное покрытие требует компиляции юнит-тестов всех шести флейворов. Это gradle-задача под `BUILD.LOCK` и минуты, а не секунды - вне бюджета быстрого гейта.

Вывод: компиляция годится как редкая полная проверка (предрелизный прогон), но не как механический гейт на каждое изменение.

## Вариант B - статический индекс объявлений

Двухшаговая схема, снимающая обе категории ложных срабатываний ad-hoc-версии из S1450.

1. **Индекс.** Обойти флейвор-областные наборы и собрать только объявления **верхнего уровня** (`class` / `interface` / `object` / `enum class` / `annotation class` / `typealias` / top-level `fun` / top-level `val`) вместе с их пакетом, получив FQCN.
   - Вложенные члены запечатанных иерархий (`Add`, `Block`, `Icon`, `Parsed`, `Decoded`) в индекс не попадают - это устраняет первую категорию шума, названную в §0.
2. **Разрешение.** В общем наборе `src/test` считать ссылкой только два случая:
   - явная строка `import <FQCN>`, где FQCN есть в индексе;
   - простое имя из индекса, объявленное **в том же пакете**, что и сам тест (Kotlin не требует импорта внутри пакета).
   - Платформенные типы (`android.view.KeyEvent`, `MotionEvent`) не попадают ни в один случай: их пакет никогда не совпадает с `com.sza.fastmediasorter.*`, а импортируются они не из индекса. Это устраняет вторую категорию шума.

## Уточнение индекса: FQCN с копией в каждом флейворе

S1455 описывает форму, которая выглядит как флейвор-область, но дефектом не является: `OfficeDocumentFamilyCatalog` - один FQCN с шестью пофлейворными копиями. Тест на него компилируется везде и падает только там, где каталог пуст.

Отсюда правило индекса: FQCN считается флейвор-областным, только если множество флейворов, у которых он объявлен на эффективном пути исходников, - **собственное подмножество** всех шести. FQCN, объявленный в `src/main` или во всех шести наборах, из индекса исключается.

Эффективный путь исходников флейвора = `src/main` + одноимённый набор + смонтированные общие наборы + наборы типа сборки (`debug`, `release`, `benchmark`).

## Третья категория шума: расширения верхнего уровня

Измерено 2026-08-09 пробным сканом на реальном дереве. Наивное извлечение имени - «первый идентификатор после ключевого слова» - на объявлении `fun Context.foo()` берёт **тип-приёмник**, а не имя функции. В индекс попадают `Context` и `String`, после чего совпадает почти каждый тест: пробный скан дал 10 ложных срабатываний ровно этой формы и ни одного настоящего.

Правило извлечения для `fun`, `val` и `var`: сначала снять необязательный список типовых параметров, затем необязательный приёмник вместе с точкой, и только потом взять имя. После исправления тот же скан на том же дереве даёт 325 проиндексированных FQCN и **ноль** совпадений.

## Базовое состояние дерева на 2026-08-09

Пробный скан обеими проверками - по импорту и по совпадению пакета - даёт ноль нарушений. Гейт вводится на чистом дереве, поэтому храповик с базовым счётчиком не нужен: порог сразу нулевой.

## Решение

Основной механизм - **вариант B**. Компиляция как проверка остаётся за существующим полным прогоном юнит-тестов и не дублируется гейтом.
