# Стратегическая спецификация: S0251 - Удаление устаревших VR-настроек формата

**Ticket:** S0251
**Status:** Verified
**Priority:** 50
**Date:** 2026-05-19
**Tier:** 3 - Moderate (ad-hoc)
**Roadmap entry:** Ad-hoc - запрос 2026-05-19 (визуальный аудит экрана Настройки → Медиа)
**Tactical plan:** `PLAN/S0251_cleanup-dead-vr-format-settings/INDEX.md`

> **Scope:** STRATEGIC. Цели, ограничения, открытые вопросы. Без имён классов, путей, лимитов строк, миграций Room, модулей Hilt.

---

## 1. Проблема

На экране Настройки → Медиа в VR-секции живут три контрола, которые сохраняют значения в локальное хранилище и резервную копию, но ни один компонент плеера их больше не читает. Это видимый артефакт перехода: предыдущая итерация VR-стэка удалила консьюмера принудительных стерео-форматов, а UI остался. Help-иконка рядом с заголовком "VR" раскрывает справку по SBS/OU/MONO, которая после удаления спиннеров перестаёт описывать реальные действия пользователя. На устройстве это создаёт иллюзию управляемости, которой нет: пользователь переключает формат, ничего не меняется. Параллельно в той же секции живут две настройки, которые работают, но не являются VR-специфичными - они оказались в VR-блоке только из-за совместного происхождения коммита и теперь визуально вводят в заблуждение.

---

## 2. Цели

1. Из секции Медиа исчезают три VR-настройки формата, которые не подключены к плееру (принудительный плоский формат, принудительный сферический формат, запоминание формата файла).
2. Help-иконка справки по VR появляется в блоке "Управление 3D-VR" рядом с заголовком блока, и её текст переписан под актуальный смысл (что такое 3D VR в этом приложении, требования к устройству, как работает мастер-переключатель).
3. Диагностический FPS-счётчик плоского плеера и переключатель многооконного режима остаются доступными пользователю и продолжают работать, но визуально перестают быть частью VR-секции.
4. Резервные копии, сделанные на предыдущих версиях, корректно импортируются - удалённые поля просто игнорируются, без падения и без потери остальных настроек.
5. Per-file запоминание стерео-режима через диалог плеера продолжает работать ровно как сейчас - локальный override через Room-кэш остаётся независимой фичей.
6. Внутренний механизм разрешения принудительного стерео-формата теряет связи с пользовательскими настройками-призраками и упрощается до per-file-override + детектированный режим.

**Non-goals:**

- Не меняется поведение детектора стерео-формата (SBS/OU/360°/VR180) и его реакции на медиа-метаданные.
- Не переписывается диалог выбора формата в плеере (тот, что вызывает per-file override) - он живёт по своему контракту.
- Не вводятся новые пользовательские контролы по VR-формату взамен удаляемых.
- Не пересматривается архитектура VR-стэка целиком (это задача S0240-эпика).
- Не меняется master-toggle "Включить 3D VR" в блоке "Управление 3D-VR".

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. После удаления заголовка "VR" два оставшихся переключателя (FPS-счётчик плоского плеера и многооконный режим) должны выглядеть органично - либо в общей секции Медиа без под-заголовка, либо в новой под-группе со своим заголовком. Точное место - решение фазы `/ui-clarify` тактической спеки.
2. Новый текст help-иконки в блоке "Управление 3D-VR" должен ясно объяснять, что эта функция требует XR-устройства (Meta Quest 3, Android XR) и что включение мастер-переключателя само по себе не гарантирует доступности 3D - сначала система должна обнаружить XR-runtime.
3. Резерв-копии, сделанные после релизов S0241..S0250 (где поля присутствовали в JSON, но не использовались), должны восприниматься как валидные - при импорте просто отбрасывать неизвестные поля.

### 3.2 Жёсткие ограничения

- **Flavor:** Затрагивает source-set `main` (удаление UI, доменные и data-слои, ресурсы) и `vr` (добавление help-иконки в блок "Управление 3D-VR"). Через VR-inclusion hierarchy `standard ⊂ vr ⊂ noLegal` изменения автоматически распространяются на `noLegal` (после S0250 `SUPPORT_VR_PLAYER = true`). Source-set дисциплина по `dev/FLAVOR_DEVELOPMENT_RULES.md` обязательна: новые ресурсы для блока "Управление 3D-VR" живут в VR-flavor, а не под BuildConfig-гейтом в main.
- **API level:** Без API-специфики. Изменение чисто конфигурационное и UI-уровневое.
- **Wear OS:** Не затрагивается.
- **Производительность:** Без бюджета - удаление неактивного кода уменьшает поверхность, не нагружает её.
- **Совместимость данных:** Старые резервные копии должны импортироваться без ошибки. Поля удаляются из домена, но десериализатор резерва должен игнорировать неизвестные ключи (не падать). Версия Room не меняется (схема таблиц не затрагивается).
- **Локализация:** EN/RU/UK обязательно. Удаление девяти строковых ключей и добавление двух новых должно пройти аудит локалей.
- **Доступность:** Help-иконка в новом месте обязана быть focus-доступной (D-pad / TV-remote / клавиатура) с правильным `contentDescription`. Это требование CLAUDE.md Rule 17 (UI consistency & input coverage) - применяется ко всем новым контролам.
- **Communication policy:** Новый текст help-сообщения 3D VR обязан пройти тон-чеклист `docs/COMMUNICATION_POLICY.md` §6 (дружелюбный, без жаргона, без воcклицаний, без обвинения пользователя в незнании). RU/UK переводы - не транслитерация, а адаптация.

## 4. Контекст текущей архитектуры

Экран Настройки → Медиа содержит вертикальный стек логических групп. Одна из них - VR-блок - поднимается из общего layout только в flavor-сборках с поддержкой VR-плеера; в этой же группе сейчас лежат как мёртвые (форматные настройки), так и живые (диагностика, многооконный режим) контролы. Ниже идёт отдельный блок "Управление 3D-VR", который хостится отдельным фрагментом из VR-source-set и обслуживает master-переключатель + тестовый запуск immersive-сессии. Help-иконка по VR-форматам сейчас закреплена за первой группой и текстуально завязана на терминологию мёртвых спиннеров.

Доменный слой хранит три поля настроек, которые пишутся UI-слоем в локальное хранилище и сериализуются в резерв, но не читаются плеером: ранее их применение шло через слой координатора стерео-режима, но в предыдущей итерации эпика VR-стэка код применения был удалён, оставив только хранилище. Resolver принудительного формата сейчас принимает их на вход, но получает всегда дефолтные значения - живой путь через него идёт только для per-file override (запомненный режим конкретного файла через локальный кэш).

## 5. Предлагаемый подход

Подход разделяется на три независимых среза: визуальный, доменный, информационный. Каждый срез упрощает соответствующий слой без введения новой архитектуры.

### 5.1 Основные столпы / модули

**Визуальный срез (Настройки → Медиа):**

- Из VR-блока удаляются три устаревших контрола вместе с заголовком "VR" и его справочной иконкой.
- Два живых контрола (диагностический FPS-счётчик плоского плеера, переключатель многооконного режима) перемещаются в новое визуальное место в общей секции Медиа. Точное расположение и наличие/отсутствие под-заголовка - решение фазы `/ui-clarify`.
- Блок "Управление 3D-VR" получает help-иконку рядом со своим заголовком - визуально симметрично остальным блокам приложения (Видео, Эскизы, Размеры). Иконка реагирует на нажатие, клавиатуру, D-pad, мышь - стандарт CLAUDE.md Rule 17.
- Layout-эквивалентность portrait/landscape соблюдается: оба варианта получают идентичную правку (Rule 12).

**Доменный срез (модель настроек и резерв):**

- Из доменной модели настроек удаляются три поля, связанные с принудительными форматами и запоминанием формата файла.
- Из data-слоя удаляются соответствующие ключи локального хранилища и операции чтения/записи.
- Из десериализатора резервной копии удаляются поля, но десериализатор обязан игнорировать неизвестные ключи (атрибут "только новые поля - без удаления старых из JSON-схемы") - старые резервы остаются валидными.
- Координатор стерео-режима упрощается: исчезают поля принудительных форматов и флаг "запоминать", метод применения снапшота настроек удаляется целиком. Логика разрешения форматного режима сводится к "per-file override (если есть) или детектированный режим". Per-file override через локальный Room-кэш остаётся в неизменном виде - это независимый механизм, который работает через диалог плеера.
- Resolver принудительного формата либо упрощается до тривиального вырождения (perFile-override or detected), либо инлайнится в координатор - решение принимается на тактическом уровне исходя из принципа "минимум артефактов с однострочным телом".

**Информационный срез (ресурсы):**

- Из строковых ресурсов всех трёх локалей (EN/RU/UK) удаляются ключи, связанные с устаревшими VR-форматными контролами и старым help-текстом.
- В VR-flavor source-set добавляются два новых строковых ключа для help-диалога блока "Управление 3D-VR".
- Из ресурсов массивов (entries/values для спиннеров) удаляются четыре массива, связанные с принудительными форматами.
- Опубликованные feature-списки `docs/FEATURES.md` (EN/RU/UK) проверяются на расхождение: текущая формулировка про "Dual-group format override dialog" может относиться либо к удаляемым настройкам, либо к per-file override-диалогу плеера. См. §6.

### 5.2 Потоки данных и событий

UI-слой настроек → доменный слой (модель + use-case-обёртки) → data-слой (локальное хранилище + резерв). После правки последний срез упрощается: три поля исчезают на всех уровнях согласованно, и UI не сохраняет, не читает, не сериализует их.

Плеер сохраняет цепочку: детектор стерео-режима → координатор → resolver → рендер. Параллельно цепочка per-file override: пользовательский выбор в диалоге плеера → координатор → локальный Room-кэш → resolver. После правки координатор перестаёт получать на вход параметры принудительных форматов и читает только перфайл-override + детектированный режим.

Резерв-копия: десериализатор JSON обязан остаться неконкретным к удаляемым полям. Если они присутствуют в старом резерве - игнорируются. Если их нет в новом резерве - читается значение по умолчанию (несуществующее в новой модели - его нет, удаление прозрачно).

### 5.3 Точки расширяемости

- Расширяемость UI: переход двух оставшихся переключателей (FPS-счётчик, многооконный режим) в общую секцию открывает путь к будущей логической группе "Плеер" / "Окно", если появятся ещё non-VR-специфичные настройки. Эта группа специально не вводится сейчас - сначала нужно увидеть, появятся ли соседи.
- Расширяемость VR-help: новый текст help-сообщения в блоке "Управление 3D-VR" должен быть написан с расчётом на дальнейшее обогащение (например, при появлении новых VR-настроек) - не как одноразовый FAQ, а как точка входа в VR-функциональность.
- Расширяемость координатора: после удаления параметров принудительных форматов сигнатура `applySettings` исчезает. Если в будущем понадобится снова управлять принудительными форматами через настройки - механизм восстанавливается заново через регулярный путь (use-case-обёртка над репозиторием настроек). Сейчас этот путь явно не подготавливается, чтобы не оставить ещё один dead-stub.
- Flavor-граница: новый help-диалог для блока "Управление 3D-VR" живёт в VR-source-set, как и сам блок. Если в будущем появится потребность вынести help в `standard` (например, диалог "что такое 3D VR" вне VR-сборки) - вводится отдельный интерфейс через `src/main/`, реализация остаётся в VR-flavor. Сейчас этого нет.

## 6. Открытые вопросы / Research items

1. **Семантика бюллетеня "Dual-group format override dialog" в docs/FEATURES.md**
   - **Вопрос:** К чему относится этот бюллетень в разделе "VR Edition" - к удаляемым настройкам формата или к per-file override-диалогу плеера, который остаётся?
   - **Варианты:** (а) относится к удаляемым настройкам → бюллетень удаляется или переписывается; (б) относится к per-file override-диалогу плеера → бюллетень остаётся как есть.
   - **Нужно выяснить:** какой именно UI текущий бюллетень описывает - какой экран/диалог имеется в виду. Если выяснится, что это компактное описание per-file override-диалога, текст можно оставить. Если описание исторически про настройки - переписать или удалить вместе с удаляемыми контролами.
   - **Статус:** Open. Разрешение - в фазе тактической спеки до коммита изменений.

2. **Размещение двух живых переключателей после удаления заголовка "VR"**
   - **Вопрос:** Куда визуально переезжают FPS-счётчик плоского плеера и переключатель многооконного режима?
   - **Варианты:** (а) остаются на месте без заголовка как самостоятельные строки секции Медиа; (б) объединяются в новую под-группу "Плеер" в секции Медиа; (в) поднимаются к концу общей секции Медиа выше блока "Управление 3D-VR".
   - **Нужно выяснить:** какой вариант предпочтительнее с точки зрения визуальной иерархии Settings экрана и логической группировки.
   - **Статус:** Open. Разрешение - в фазе `/ui-clarify` тактической спеки.

3. **Судьба resolver-а принудительного формата**
   - **Вопрос:** Оставить ли отдельный объект-резолвер с упрощённой сигнатурой, или инлайнить остаточную логику ("per-file-override or detected") прямо в координатор?
   - **Варианты:** (а) сохранить как отдельный объект для будущих расширений; (б) инлайнить, удалить файл и тест.
   - **Нужно выяснить:** проектная политика "минимум артефактов с однострочным телом" против "точки расширения зарезервированы заранее". Оценить по принципу "что чище читается на текущий момент".
   - **Статус:** Open. Разрешение - на этапе декомпозиции в тактической спеке.

4. **Текст нового help-сообщения для блока "Управление 3D-VR"**
   - **Вопрос:** Окончательная формулировка двух новых строковых ключей (заголовок и тело help-диалога) на EN/RU/UK.
   - **Варианты:** Не варианты, а написание - объяснить требования к XR-устройству, поведение мастер-переключателя, отсутствие принудительных форматов в этом приложении на данный момент.
   - **Нужно выяснить:** Тон и стиль соответствуют `docs/COMMUNICATION_POLICY.md`. RU/UK - адаптация, а не транслитерация.
   - **Статус:** Open. Финализируется в фазе тактической спеки.

## 8. Влияние на пользователя (docs/FEATURES)

Возможно изменение бюллетеня в разделе "VR Edition" (EN/RU/UK). Окончательное решение зависит от разрешения §6 пункта 1. Если выяснится, что текущая формулировка про "Dual-group format override dialog" описывает удаляемые настройки - бюллетень удаляется или переписывается под per-file override-диалог плеера. Если описание исторически про живой диалог плеера - оставляется без изменений.

В остальном пользователь не получает новой фичи: задача чисто cleanup-овая. После завершения некоторые путаные элементы исчезают, и одно объяснение появляется в новом месте - это не "новая фича", а возврат экрана в консистентное состояние.

## 9. Архитектурные решения (ADR)

**ADR-1: Per-file override остаётся независимой подсистемой**

- **Решение:** Per-file override стерео-режима (запомненный режим конкретного видеофайла) сохраняется в полном объёме - таблица локального кэша, путь записи через диалог плеера, путь чтения через координатор остаются неизменными.
- **Альтернативы:** Удалить вместе с настройкой "запоминать формат файла" как одну подсистему.
- **Почему:** Это разные механизмы. Удаляемый UI-переключатель в Настройках управлял глобальным флагом, который не доходил до координатора (всегда `true` по умолчанию). Per-file override - реально работающая фича: пользователь в плеере выбирает формат через диалог, и при следующем открытии файла он применяется. Удаление этой подсистемы было бы регрессом.

**ADR-2: Десериализатор резерва игнорирует неизвестные поля, без миграции**

- **Решение:** При удалении полей из доменной модели не вводится миграция резерв-копий и не повышается версия формата резерва. Старые резервы остаются читаемыми за счёт пермиссивности десериализатора.
- **Альтернативы:** Ввести версионирование схемы резерва, написать миграцию для архивных JSON.
- **Почему:** Удаление полей - "additive-safe" с точки зрения чтения, потому что отсутствие поля в новой модели эквивалентно "поле проигнорировано". Версионирование схемы - оверкилл для трёх неактивных полей. Если в будущем появятся семантически несовместимые изменения - тогда вводится версия.

**ADR-3: Help-иконка в блоке "Управление 3D-VR" живёт в VR source-set**

- **Решение:** Новая help-иконка и её строковые ресурсы добавляются в VR source-set, рядом с фрагментом блока. В `main` source-set ничего не добавляется.
- **Альтернативы:** Положить иконку в main с BuildConfig-гейтом видимости.
- **Почему:** CLAUDE.md Rule 15 явно запрещает новые BuildConfig-гейты в `src/main/`. Источник правды - `dev/FLAVOR_DEVELOPMENT_RULES.md`. Блок "Управление 3D-VR" уже целиком живёт в VR-flavor - его расширение естественно остаётся там же.
