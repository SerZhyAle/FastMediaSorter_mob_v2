## 1. Проблема

В основном файле строк приложения 396 из 3228 ключей не упоминает ни один исходник: ни код, ни разметка, ни манифест, ни меню. Пользователь этого не видит, платит за это разработка и перевод.

Цена измерима и растёт прямо сейчас. Соседняя работа переводит весь корпус на десять локалей, поэтому каждый мёртвый ключ оплачивается десять раз: около 4000 лишних машинных переводов только из этого файла, и столько же строк в ревью каждого следующего транша. На момент замера 122 из 396 уже просочились в каждую из десяти локалей, то есть окно, в котором чистка ещё дешёвая, закрывается.

Область - ресурсы строк основного модуля и оснастка работы с ними.

## 2. Цели

1. Иметь воспроизводимый способ получить список действительно неиспользуемых ключей, а не список, зависящий от того, кто и как его считал.
2. Убрать из перевода ключи, которые ничего не отображают, до того как их переведут на все десять локалей.
3. Не потерять ни одного живого ключа: ни флейворного, ни множественной формы, ни элемента массива.
4. Оставить после себя механическую проверку, а не разовую чистку.

**Non-goals:**

- Не трогать другие файлы строк, кроме основного: ключи ввода, настройки и прочие живут отдельно и считаются иначе.
- Не заниматься качеством или тоном формулировок живых строк.
- Не решать задачу S1550 про атрибутные литералы без пометки о непереводимости, хотя множества пересекаются.
- Не менять поведение приложения: у задачи нет пользовательского эффекта, кроме размера сборки.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Одна чистка, а не растянутая на месяцы серия мелких удалений.
2. Понятный след: по каждому удалённому ключу должно быть видно, на каком основании он признан мёртвым.

### 3.2 Жёсткие ограничения

- **Измерение только по своему модулю.** Модули приложения и часов - раздельные пространства ресурсов, зависимости между ними нет, поэтому ключ основного модуля не может использоваться из часов. Совместный поиск по двум деревьям даёт ложно-живые ключи: 15 имён существуют в обоих модулях.
- **Флейворы.** 216 ключей живы только через флейворные исходники. Любое измерение и любая проверка перед удалением обязаны видеть все source set, а не только основной.
- **Формы и массивы.** Ключи множественных форм и массивов не имеют сегодня никакой проверки в инструменте удаления и требуют отдельного внимания.
- **Локализация.** Удаление ключа обязано убирать его из всех локалей одним действием: ручная правка только основного файла оставляет сироту, которую ни один действующий гейт не заметит.
- **Совместимость данных:** отсутствует, ресурсы не хранят пользовательских данных.
- **Wear OS:** не затрагивается.
- **Доступность и коммуникация:** новых пользовательских строк нет.

### 3.3 Owner inputs (Approval gate)

- **Related tickets:** S1420 (переводит корпус прямо сейчас, конфликтует по файлам), S1550 (пересечение в 75 ключей), S1571 (слепота проверки перед удалением к флейворам, найдена этим исследованием, Verified 2026-08-11).
- **Data compatibility:** ресурсы не хранят пользовательских данных, миграции нет.
- **Validation level:** сборка всех вариантов, где живут флейворные ключи, плюс полный набор модульных тестов. Удаление живого ключа ломает сборку в лучшем случае и экран в худшем.
- **Owner sign-off:** получен 2026-08-11 через `/spec-quiz`. Три решения §6 закрыты: ключи удаляются, чистка идёт сейчас параллельно S1420, S1568 выполняется до S1550. Остальные значения выше выведены из кода и из исследования.

## 4. Контекст текущей архитектуры

Строки приложения лежат в одном большом файле основного модуля, переводы - в отдельных файлах локалей рядом. Ключи добавляют и удаляют скриптом, который держит локали в паритете.

Решить задачу «из коробки» сегодня нельзя: у проекта нет измерения живости ключа, которое учитывало бы флейворные исходники, поэтому наивный подсчёт расходится с реальностью на сотни ключей в обе стороны.

Вторая причина снята по ходу: проверка перед удалением, которая смотрела только в основной source set и потому отвечала «ссылок нет» ровно на самом опасном классе ключей, исправлена в S1571 (Verified 2026-08-11) - она сканирует все source set модуля. Тактика опирается на исправленный инструмент, а не воспроизводит эту работу.

Фактическая база: `PLAN/S1568_unreferenced-string-keys-audit/research/01__deadness-method-and-risk-subsets.md`.

## 5. Предлагаемый подход

Сначала измерение, потом инструмент, потом чистка. Обратный порядок означает удаление по списку, которому нельзя доверять.

### 5.1 Основные столпы / модули

#### Воспроизводимое измерение

Скрипт, который по одному модулю строит список объявленных ключей и список упомянутых, учитывая все source set, обе формы ссылки и множественные формы с массивами. Его вывод - артефакт, который можно приложить к изменению и перепроверить через месяц.

#### Надёжная проверка перед удалением

Удаление опирается на ту же логику, что и измерение, а не на собственную укороченную. Пока это не так, любой список удаления приходится перепроверять руками.

#### Сама чистка

Одним проходом, по проверенному списку, с удалением из всех локалей сразу.

### 5.2 Потоки данных и событий

Замер -> список кандидатов -> вычитание живых через флейворы, формы и массивы -> удаление кандидата из всех локалей одним вызовом -> сборка каждого варианта, где мог жить ключ -> повторный замер как доказательство.

### 5.3 Точки расширяемости

Измерение должно одинаково работать по любому файлу строк и любому модулю, чтобы следующий аудит - ключей ввода, настроек или часов - не требовал нового скрипта.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Удалён ключ, живой только во флейворе | Низкая | Сборка варианта падает, а при ссылке из разметки - падает экран | Проверка перед удалением видит все source set с S1571; измерение обязано делать то же; сборка каждого затронутого варианта до закрытия |
| Ключ удалён из основного файла, но остался в локали | Средняя | Сирота, которую не видит ни один гейт | Удалять только инструментом, который проходит по всем локалям сразу |
| Правка сталкивается с идущим переводом корпуса | Высокая | Потерянные правки в одних и тех же файлах | Работать под блокировкой кода, брать её коротким шагом на само удаление и сразу отпускать |
| Часть ключей - заготовка под невыпущенную функцию | Средняя | Удалено то, что скоро понадобится | Механического признака нет; спорные выносить в список на решение, а не удалять молча |

## 9. Архитектурные решения (ADR)

**ADR-1: Измерение по одному модулю, а не по всему дереву**

- **Решение:** живость ключа считается только внутри его собственного модуля.
- **Альтернативы:** искать ссылки сразу по приложению и часам, как это сделал первый замер.
- **Почему:** модули - раздельные пространства ресурсов без зависимости друг от друга, поэтому совместный поиск даёт ложно-живые ключи. Проверено: одно имя из пятнадцати общих оказалось живо только в часах и мертво в приложении.

**ADR-2: Проверка перед удалением опирается на то же измерение**

- **Решение:** у удаления и у аудита один источник истины о живости.
- **Альтернативы:** оставить в инструменте удаления собственную укороченную проверку.
- **Почему:** сегодня они разные, и укороченная отвечает «ссылок нет» ровно на том классе ключей, который опаснее всего удалить.

## 11. Критерии готовности (strategic-level)

1. Есть команда, которая по требованию выдаёт список неиспользуемых ключей модуля и учитывает флейворные исходники, формы и массивы.
2. Её результат совпадает с ручной перепроверкой на выборке, включая ключи, живые только во флейворе.
3. Проверка перед удалением не даёт разрешения на ключ, живой хоть в одном source set.
4. Утверждённые к удалению ключи исчезли из основного файла и из всех локалей, сирот не осталось.
5. Каждый вариант сборки, где мог жить удалённый ключ, собирается, и полный набор модульных тестов проходит.
6. Повторный замер показывает ожидаемое число оставшихся ключей.
