## 1. Проблема

Чтобы запустить часто используемую трансляцию, пользователь каждый раз открывает приложение, заходит на экран Трансляции, находит нужный канал в списке (даже с учётом прикреплённых сверху) и только потом запускает воспроизведение. Для одного-двух любимых каналов это лишние шаги.

Нет способа поместить конкретную трансляцию на домашний экран устройства: пользователь хочет указать один конкретный канал из списка трансляций и получить его ярлык на домашнем экране, чтобы по нажатию сразу играла именно эта трансляция, минуя ручной поиск.

Область - фича Трансляции и интеграция с домашним экраном (ярлыки/виджеты запуска).

---

## 2. Цели

1. Пользователь может из списка Трансляций выбрать один конкретный канал и поместить его ярлык запуска на домашний экран устройства.
2. Нажатие на ярлык сразу запускает воспроизведение именно этой трансляции, без ручного поиска в списке.
3. Ярлык несёт узнаваемую подпись (название канала) и иконку, отражающую тип канала (аудио/видео/RTSP).
4. Ярлыки разных каналов сосуществуют на домашнем экране независимо.

**Non-goals:**

- Один блок с превью/списком нескольких каналов сразу - один ярлык соответствует одному каналу.
- Живой индикатор онлайн/оффлайн на ярлыке в первой итерации.
- Управление воспроизведением (пауза/следующий) прямо с домашнего экрана - только запуск.
- Поддержка во флейворах, где экран Трансляции скрыт (lite, photos).

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Действие создания ярлыка доступно в контексте конкретного канала в списке Трансляций (прикреплённые сверху - наиболее вероятные кандидаты).
2. Иконка ярлыка визуально отличает тип канала.
3. Флоу создания - короткий: выбрал канал, подтвердил, ярлык на экране.

### 3.2 Жёсткие ограничения

- **Flavor:** только флейворы с активной фичей Трансляции - standard, legacy, noLegal, VR. Исключены lite и photos (точка входа Трансляций скрыта). Реализация следует `dev/FLAVOR_DEVELOPMENT_RULES.md`: доступность определяется наличием самой фичи Трансляции (её точки входа), без `BuildConfig.SUPPORT_*`-проверок в `src/main` (Rule 15); флейвор-специфика размещения, если потребуется, выносится в соответствующий source-set.
- **API level:** механизм закрепления ярлыка на домашнем экране доступен с Android 8.0 (API 26). Для legacy (minSdk 23) на устройствах ниже API 26 поведение деградирует (закрепление недоступно либо через устаревший путь) - см. §6 #1, §7. Виджет-альтернатива работает с API 23.
- **Wear OS:** не затрагивается.
- **Производительность:** не критично - создание ярлыка разовое, запуск переиспользует существующий поток воспроизведения.
- **Совместимость данных:** ярлык несёт стабильный идентификатор канала; изменение схемы основной БД не требуется. Канал может быть удалён из каталога уже после создания ярлыка - нужно корректное поведение при нажатии (см. §6 #5).
- **Локализация:** EN/RU/UK обязательно для всех новых строк (действие создания, подтверждение, сообщение об ошибке/недоступности).
- **Доступность:** действие создания и сам ярлык доступны через TalkBack; тип канала различим не только цветом (форма иконки и подпись); touch target не меньше минимального.

### 3.3 Owner inputs (Approval gate)

- **Flavor scope:** standard, legacy, noLegal, VR - везде, где активна фича Трансляции; lite и photos исключены (точки входа нет).
- **API level constraints:** целевой механизм закрепления требует API 26+; на legacy ниже API 26 - деградация. Этот фактор влияет на выбор «ярлык vs виджет» (§6 #1, ADR-1).
- **Localization:** EN/RU/UK для всех новых пользовательских строк.
- **UI placement contract:** действие «поместить на домашний экран» размещается в контексте конкретного канала в списке Трансляций (строка либо меню канала); точное место решается на approval (§6 #4).
- **Accessibility:** TalkBack-метки для действия и ярлыка; не-цветовое различие типа канала.
- **Communication policy:** новые строки проходят `docs/COMMUNICATION_POLICY.md` (чек-лист тона §6) перед интеграцией.
- **Validation level:** проверка на реальном устройстве с реальным лаунчером - создание ярлыка, нажатие → запуск нужного канала, деградация на удалённом канале.
- **Owner sign-off:** 2026-06-23.
- **Related tickets:** S0565 (каталог Трансляций - базис), S0568 (паттерн launch-виджета - образец), S0427 (ярлыки приложений, Draft - родственный механизм), S0593 (статус последнего воспроизведения канала).

## 4. Контекст текущей архитектуры

Фича Трансляции владеет своим экраном со списком источников, локальным закреплением каналов наверх списка и запуском воспроизведения по типу канала. Запуск сейчас инициируется только изнутри этого экрана по выбору строки - внешней точки входа, принимающей идентификатор канала и сразу запускающей его, нет.

Интеграция с домашним экраном в приложении уже представлена: семейством виджетов запуска (в т.ч. недавний config-less виджет запуска камеры) и менеджером ярлыков приложения, который публикует динамические ярлыки недавних ресурсов с deep-link в главный экран по идентификатору. То есть и механизм закреплённого/динамического ярлыка, и механизм виджета в проекте отработаны - но ни один из них не связан с конкретной трансляцией.

Закрепить конкретную трансляцию на домашнем экране сейчас нельзя по двум причинам: нет действия закрепления в контексте канала и нет внешнего deep-link, который принял бы идентификатор канала и направил его в существующий поток воспроизведения.

## 5. Предлагаемый подход

Рекомендуемый механизм - закреплённый ярлык на домашнем экране, инициируемый из списка Трансляций, по образцу уже существующих динамических ярлыков ресурсов (deep-link по идентификатору). Это соответствует описанному UX: пользователь выбирает конкретный канал внутри приложения и получает его ярлык, тогда как виджет конфигурируется со стороны лаунчера. Подход переиспользует существующий паттерн запуска по идентификатору и даёт бесплатную флейворную инкапсуляцию - нет экрана Трансляций, нет и действия закрепления.

Виджет-альтернатива не отбрасывается, а зафиксирована в ADR-1 и вынесена решением владельца в §6 #1 (ключевой довод за виджет - работа на legacy ниже API 26 и возможность ресайза/статуса).

### 5.1 Основные столпы / модули

- **Действие закрепления в контексте канала.** У конкретного канала в списке Трансляций появляется действие «поместить на домашний экран», запускающее системный диалог закрепления с подписью (название канала) и иконкой по типу.
- **Внешняя точка запуска по идентификатору.** Приложение принимает запрос «запустить трансляцию с идентификатором X» с домашнего экрана и направляет его в существующий поток запуска канала по типу, минуя ручной выбор в списке.
- **Идентификация и оформление ярлыка.** Ярлык несёт стабильный идентификатор канала, человекочитаемую подпись и иконку, отражающую тип (аудио/видео/RTSP).
- **Деградация.** Если к моменту нажатия канал удалён или недоступен - понятное сообщение и переход на экран Трансляций, без сбоя.

### 5.2 Потоки данных и событий

- **Создание:** экран Трансляции → действие на конкретном канале → системный диалог закрепления → ярлык на домашнем экране.
- **Запуск:** домашний экран → нажатие на ярлык → точка входа приложения по идентификатору → поток запуска трансляции по типу → воспроизведение.

### 5.3 Точки расширяемости

- Абстракция «запуск трансляции по идентификатору» переиспользуема для прочих внешних точек входа (голосовой ассистент, автоматизация).
- При выборе виджет-варианта общая точка запуска по идентификатору обслуживает и его - отличается лишь способ размещения и хранение привязки идентификатора к экземпляру.
- Интерфейс размещения (ярлык/виджет) остаётся в `src/main` как абстракция; флейвор-специфика (если понадобится отдельный приёмник) выносится в соответствующий source-set по `dev/FLAVOR_DEVELOPMENT_RULES.md`.

## 6. Открытые вопросы / Research items

1. **Механизм размещения на домашнем экране: закреплённый ярлык или конфигурируемый виджет**
   - **Вопрос:** делать закрепляемый ярлык (инициируется из приложения) или конфигурируемый виджет (выбор канала в конфигураторе со стороны лаунчера)?
   - **Варианты:** ярлык (рекомендация §5) / виджет / гибрид.
   - **Нужно выяснить:** решение владельца. Ярлык - короче UX и переиспользует deep-link-паттерн; виджет - работает на legacy ниже API 26, допускает ресайз и статус канала, но вводит новый для проекта паттерн конфигуратора.
   - **Статус:** Resolved - владелец выбрал закреплённый ярлык (2026-06-23). На legacy ниже API 26 - деградация по §6 #2; виджет-вариант не реализуется в этой итерации.

2. **Совместимость закрепления ярлыка с minSdk флейворов**
   - **Вопрос:** на каких устройствах доступно программное закрепление ярлыка, и что делать ниже порога?
   - **Нужно выяснить:** нижнюю границу API и поведение легаси-устройств.
   - **Статус:** Resolved - программное закрепление доступно с API 26; legacy имеет minSdk 23, поэтому на API 23-25 закрепление недоступно (или только устаревшим путём), что требует деградации либо виджет-варианта для legacy.
   - **Артефакт:** `PLAN/S0637_stream-channel-shortcut/research/02__pin-shortcut-api-availability.md`

3. **Внешняя точка запуска канала по идентификатору**
   - **Вопрос:** существует ли способ запустить конкретный канал извне приложения, или его нужно создавать?
   - **Нужно выяснить:** текущие точки входа в воспроизведение трансляции.
   - **Статус:** Resolved - внешней точки входа нет, её нужно создать; образец - существующий deep-link динамических ярлыков ресурсов (главный экран по идентификатору).
   - **Артефакт:** `PLAN/S0637_stream-channel-shortcut/research/03__stream-launch-entry-point.md`

4. **Размещение действия создания в списке Трансляций**
   - **Вопрос:** где именно вызывается создание ярлыка - на строке канала, в его меню, или только для прикреплённых?
   - **Нужно выяснить:** место, не конфликтующее с существующими действиями строки.
   - **Статус:** Resolved - владелец выбрал overflow-кнопку `⋮` в строке (2026-06-23). Меню кнопки: «На домашний экран» и «Удалить»; текущие long-press=удалить и кнопка-пин остаются без изменений.

5. **Поведение при удалённом или недоступном канале на момент нажатия**
   - **Вопрос:** что показать, если канал ярлыка уже удалён из каталога?
   - **Статус:** Resolved - понятное сообщение и открытие экрана Трансляций, без сбоя (тривиально).

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Лаунчер не поддерживает программное закрепление ярлыков (старые/кастомные) | Средняя | Пользователь не может создать ярлык | Проверять поддержку до запроса, понятное сообщение; виджет-вариант как запасной механизм |
| legacy ниже API 26 - закрепление недоступно | Средняя | На старых устройствах фича не работает | Деградация с сообщением либо виджет-вариант для legacy (см. §6 #1) |
| Канал удалён из каталога после создания ярлыка | Высокая | Нажатие ведёт «в никуда» | Точка входа обрабатывает отсутствие: сообщение + открытие Трансляций |
| Несоответствие типа канала при запуске извне | Низкая | Открывается неверный плеер | Переиспользовать существующее routing-решение по типу канала, не дублировать логику |
| Дубли ярлыков одного канала | Низкая | Захламление домашнего экрана | Стабильный идентификатор ярлыка по каналу; повтор - допустимое системное поведение |

## 9. Архитектурные решения (ADR)

**ADR-1: Закреплённый ярлык как основной механизм размещения**

- **Решение:** основной путь - закреплённый ярлык, инициируемый из списка Трансляций; виджет рассматривается как альтернатива в §6 #1.
- **Альтернативы:** конфигурируемый виджет (выбор канала в конфигураторе со стороны лаунчера); гибрид (оба механизма).
- **Почему:** соответствует описанному UX (выбор канала в приложении → ярлык), переиспользует существующий deep-link-паттерн по идентификатору, инкапсулирует флейворность через саму фичу Трансляции, добавляет минимум нового. Открыто к пересмотру: legacy ниже API 26 и потребность в ресайзе/статусе - доводы за виджет.

## 11. Критерии готовности (strategic-level)

1. В списке Трансляций у конкретного канала доступно действие помещения его ярлыка на домашний экран.
2. После подтверждения на домашнем экране появляется ярлык с названием и иконкой типа выбранного канала.
3. Нажатие на ярлык запускает воспроизведение именно этого канала без ручного выбора в списке.
4. Несколько ярлыков для разных каналов работают независимо.
5. Нажатие на ярлык удалённого/недоступного канала показывает понятное сообщение и открывает экран Трансляций, без сбоя.
6. Фича присутствует в standard/legacy/noLegal/VR и отсутствует в lite/photos.
7. Все новые строки локализованы EN/RU/UK.

### Manual device test - 2026-06-27 (Galaxy S21+ SM-G996U1, Android 15 / SDK 35, standard debug)

**Verdict: PASS (create + system pin confirmed on hardware; tap-to-play and stale-path verified by code, not visually drivable on this launcher)**

Test channel: "Mux Test HLS" (`https://test-streams.mux.dev/x36xhzz/x36xhzz.m3u8`) added via Streams add-resource UI (no real credentials).

- **Overflow action present and fires (criterion 1; expected: row 3-dot menu has "На домашний экран"; actual: present and fires).** Tapping it logs `22:45:59.013 D/StreamsActivity S0637: add-to-home-screen tapped for stream https://test-streams.mux.dev/x36xhzz/x36xhzz.m3u8` (`onAddShortcut` reached).
- **System pin request accepted (criterion 2, system side; expected: `requestPinShortcut` reaches the OS and shows the pin dialog; actual: confirmed).** Logcat shows the One UI pin-confirmation dialog and the system processor accepting it: `22:45:59.025 ... ShortcutRequestPinProcessor.requestPinItemLocked:230 ... ShortcutService.requestPinShortcut`. `ShortcutManagerCompat.requestPinShortcut` returned true (launcher supports pinning). Evidence: `09_pin_dialog.png`.
- **Pinned-shortcut auto-placement NOT visually verifiable here (NOT a defect).** Samsung One UI placed the pinned shortcut on the first free home cell, but both home pages were fully occupied by widgets (FastMediaSorter resource widget top-left + weather widget), so no tappable shortcut cell was visible on pages 1-2. The long-press app popup shows only manifest/dynamic shortcuts ("Избранное"/"Слайдшоу"), and `cmd shortcut get-shortcuts` lists only dynamic/manifest shortcuts - pinned shortcuts are owned by the launcher and not enumerable via adb. This is launcher placement policy, not app behavior.
- **Tap-to-play (criterion 3) verified by code, not by tap.** The shortcut intent targets `StreamsActivity` with `ACTION_PLAY_STREAM` + `EXTRA_STREAM_URL`; `handlePlayIntent` calls `viewModel.playByUrl(url)` (logs `S0637: home-screen shortcut launched stream %s`). Could not drive the real tap (no visible cell). adb `am start ACTION_PLAY_STREAM` is correctly rejected - `StreamsActivity` is not exported (`Permission Denial ... not exported from uid 10371`, attempt from uid 2000) - which is the intended security posture; only the privileged launcher may launch it.
- **Stale/removed-channel path (criterion 5) verified by code, not by tap.** `StreamsViewModel.playByUrl` emits `StreamsEvent.Message(R.string.streams_shortcut_channel_missing)` when no source matches the url, with Streams open and no crash. Same automation barrier prevented a live tap.

No crash during the session (`mobile_list_crashes` clean; StreamsActivity stayed alive in the background throughout).

Device-evidence ceiling: everything the app controls (action wiring, pin request, launcher-support check, intent target + extras, security non-export) is confirmed on hardware. The only unverified link is the launcher's auto-placement convenience and the consequent visual tap, both environment/automation limitations rather than app defects - mirroring (inverted) the S0683 emulator gap. Recommend a one-tap visual re-confirm by manually dragging the pinned shortcut onto a free cell on a less widget-crowded home page before flipping to Verified.
