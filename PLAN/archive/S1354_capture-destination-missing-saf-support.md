## 0. Захваченный материал (inbox)

**Захвачено:** 2026-08-02

**Текст:**

CaptureDestinationPolicy (util/CaptureDestinationPolicy.kt) resolves mic/camera/video/screen-recording save destinations (resolveMicDestination, resolveCameraDestination, resolveVideoDestination, resolveScreenRecordingDestination) as plain java.io.File, with no content://\SAF-tree branch anywhere in that path (consumed by SaveCapturedMediaUseCase.kt and data/capture/MicRecordingSaver.kt). If any of the corresponding settings (micRecordingDestinationResourceId, cameraPhotosDestinationResourceId, videoRecordingDestinationResourceId, screenRecordingDestinationResourceId) is already pointed at a LOCAL resource whose path is a SAF tree (content:// - reachable today via the normal Add-Resource folder browser, independent of any new feature), the actual capture-save is expected to fail or misbehave since nothing resolves a DocumentFile/content Uri for these four destinations. By contrast LinkDownloadWriter.kt:188 already branches on content: vs plain path, and the scheduled-ops execution path (ExecuteScheduledOperationUseCase.checkTargetReachability) was fixed for the same class of gap under S1009. Symptom to reproduce: register a LOCAL resource pointing at a SAF-picked folder (outside default app storage) as one of the four destinations above, trigger the corresponding capture (camera photo / video recording / mic recording / screen recording), and check whether the file lands in the chosen SAF tree or the save silently fails/throws. Evidence source: research pass for S1010 (write-resource-picker-local-folder tactical planning, 2026-08-02) traced these four resolve* methods end to end and found no content:// handling; videoSnapshotResourceId and screenshotDestinationResourceId write paths were not traced to file level in that pass and may or may not share the gap.

## 1. Проблема

Папка, выбранная пользователем через системный Storage Access Framework, уже может быть сохранена как локальный ресурс, но потоки записи захваченных фото, видео, аудио и записи экрана обрабатывают её как обычный путь файла. Из-за этого запись в выбранную SAF-папку не гарантирована и может завершиться ошибкой либо сохранить результат не там, где ожидает пользователь.

## 2. Цели

1. Фото, видео, аудио и запись экрана сохраняются в доступную выбранную SAF-папку так же надёжно, как в обычную локальную папку.
2. Недоступная, отозванная или неподходящая SAF-папка не приводит к потере захваченного файла: применяется существующий безопасный локальный запасной путь.
3. Обычные файловые папки, сетевые назначения и текущие значения настроек сохраняют прежнюю семантику.

**Non-goals:**

- Не добавлять новый выбор папки, экран настроек или новую модель ресурса.
- Не расширять задачу на video snapshot и accessibility screenshot без отдельной трассировки их путей записи.
- Не менять поведение сетевых и облачных назначений.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Использовать уже сохранённые разрешения SAF без повторного запроса доступа.
2. При невозможности записи сохранить результат в документированный локальный запасной каталог.

### 3.2 Жёсткие ограничения

- **Flavor:** все активные варианты основного приложения получают одинаковую обработку общего локального назначения; специализированные source set не меняются без доказанной необходимости.
- **API level:** решение совместимо с минимальными API приложения и использует поддерживаемый AndroidX SAF API.
- **Wear OS:** модуль Wear OS не затрагивается.
- **Производительность:** байты захваченного файла копируются потоково на IO-диспетчере, без загрузки всего файла в память.
- **Совместимость данных:** существующие идентификаторы назначения и уже сохранённые URI остаются действительными; миграция данных не нужна.
- **Локализация:** новые пользовательские строки не требуются.

### 3.3 Owner inputs (Approval gate)

- **Flavor scope:** все варианты `app_v2`; общий путь записи не зависит от flavor.
- **API level constraints:** minSdk приложения; использовать AndroidX `DocumentFile` и `ContentResolver` без нового API-ограничения.
- **Performance budget:** потоковое копирование на IO-диспетчере; размер захваченного медиа не удерживается в памяти.
- **Validation level:** статические проверки, стандартная debug-сборка и ручная проверка каждого типа захвата в выбранной SAF-папке.
- **Owner sign-off:** автоматическое продолжение разрешено для исправления уже доступного выбранного назначения без изменения UI или формата настроек.
- **Related tickets:** S1010 - источник первоначальной трассировки; зависимостей нет.

## 4. Контекст текущей архитектуры

Захват создаёт временный локальный файл, после чего отдельный backend выбирает назначение по настройкам и типу ресурса. Для обычных локальных путей backend использует файловую запись, а для сетевых ресурсов передаёт загрузку вызывающему слою. Проект уже имеет проверенный путь локального копирования в SAF-дерево через системный provider.

## 5. Предлагаемый подход

Добавить единый слой записи локального захваченного медиа, который определяет обычный файловый каталог или SAF-дерево и открывает корректный поток назначения. Все backend-потоки захвата используют этот слой вместо конструирования `File` из URI. Ошибка доступа к SAF рассматривается как недоступное локальное назначение и запускает уже существующий запасной сценарий, не меняя обработку сети.

### 5.1 Основные столпы / модули

#### Единая запись локального захваченного медиа

Слой создаёт файл документа в SAF-дереве, пишет данные потоково и возвращает фактическое сохранённое расположение. Для обычных путей он сохраняет действующий MediaStore-aware механизм.

#### Маршрутизация всех захватов

Фото, видео, микрофон и запись экрана передают выбранное локальное назначение через общий контракт записи. Непригодное назначение переводит поток в его текущую локальную запасную ветку.

#### Проверяемая совместимость

Тесты и ручная проверка охватывают разрешённое SAF-дерево, отозванное разрешение и прежний обычный путь, не меняя сериализацию настроек.

### 5.2 Потоки данных и событий

Захват → временный файл → выбор сохранённого назначения → единый local-save слой → файловый поток или SAF provider → результат сохранения и существующее уведомление вызывающего слоя.

### 5.3 Точки расширяемости

Общий контракт локальной записи остаётся доступен другим потокам захвата после отдельной трассировки их назначения. Реализация не вводит нового флейворного флага и не требует новой зависимости.

## 9. Архитектурные решения (ADR)

**ADR-1: единая потоковая запись для SAF-назначений**

- **Решение:** использовать общий local-save слой, который выбирает файловый или SAF поток назначения.
- **Альтернативы:** преобразовывать SAF URI в `File`; добавлять отдельную реализацию в каждый поток захвата.
- **Почему:** SAF URI не является файловым путём, а единый слой предотвращает повторение неверной интерпретации и сохраняет потоковую запись.

## 11. Критерии готовности (strategic-level)

1. Каждый из четырёх подтверждённых типов захвата помещает результат в выбранное доступное SAF-дерево.
2. При недоступном SAF-дереве пользовательский результат не теряется и оказывается в документированном запасном локальном каталоге.
3. Обычные локальные назначения продолжают сохранять медиа в прежних каталогах.
4. Стандартная debug-сборка проходит после изменения.
