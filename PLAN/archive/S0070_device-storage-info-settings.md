## 1. Проблема

В экране основных настроек (General Settings) нет информации о свободном месте на внутреннем накопителе устройства. Пользователь должен выходить в системные настройки, чтобы узнать, сколько осталось памяти. Кроме того, нет быстрого способа обновить значение, если оно становится устаревшим.

---

## 2. Цели

1. На экран основных настроек добавить панель с информацией о доступном месте в формате "На устройстве доступно: ХХХ.Х Гб".
2. Сделать значение обновляемым по нажатию кнопки (иконка обновления, 18dp).
3. Информация обновляется автоматически при открытии экрана настроек.
4. Панель располагается перед первой группой настроек (выше заголовка "Интерфейс").
5. Панель имеет нулевой вертикальный отступ сверху и снизу, чтобы визуально слиться с группой настроек ниже.

**Non-goals:**

- Отображение информации по категориям (приложения, медиа, прочее).
- Синхронизация значения с фоновыми задачами.
- Интеграция с уведомлениями о низком месте.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Текст на очень маленьком шрифте (8sp) — не должен привлекать основное внимание.
2. Кнопка обновления справа, размер шрифта (18dp), без текста — только иконка.
3. Панель компактная, одна строка (высота = высота текста + минимальные паддинги).

### 3.2 Жёсткие ограничения

- **Flavor:** все флейворы (standard, lite, photos, legacy)
- **API level:** Android 8.0+ (API 26). Использовать стандартное API для получения info о диске.
- **Wear OS:** не затрагивается
- **Производительность:** запрос к информации о диске не должен блокировать UI (асинхронный вызов).
- **Совместимость данных:** новое хранилище данных не требуется.
- **Локализация:** строка "На устройстве доступно:" требует перевода на EN/RU/UK в `strings.xml`, `strings_ru.xml`, `strings_uk.xml`.
- **Доступность:** текст должен быть читаем TalkBack. Кнопка должна иметь `contentDescription` с пояснением действия.

## 4. Контекст текущей архитектуры

В экране основных настроек (General Settings) используется View System с материальными CardView для организации групп (Interface, Permissions, Cache, etc.). Каждая группа имеет заголовок и контейнер с элементами.

Текущая архитектура SettingsActivity → GeneralSettingsFragment использует:
- `SettingsViewModel` для управления состоянием и логики, связанной с настройками.
- Helpers (GeneralSettings*Helper классы) для делегирования сложной логики из фрагмента.
- DataBinding и обновление UI через наблюдение за StateFlow/LiveData.

Для получения информации о доступном месте на устройстве требуется асинхронный запрос к файловой системе (StorageManager или StatFs). Это не должно блокировать главный UI поток.

## 5. Предлагаемый подход

### 5.1 Основные столпы

**A. Слой получения информации о диске (Domain UseCase)**

- UseCase, который асинхронно запрашивает информацию о доступном месте на внутреннем накопителе и преобразует её в единицы Гб.
- Результат обёрнут в Result-тип (Success/Error) с graceful обработкой исключений (устройство не имеет API доступа, и т.п.).

**B. ViewModel для управления состоянием**

- SettingsViewModel наблюдает за информацией о диске через StateFlow.
- Экспонирует команду `refreshDeviceStorage()` для нажатия кнопки обновления.
- Логирует запросы и ошибки через Timber.

**C. UI-слой (Fragment + Layout)**

- В layout `fragment_settings_general.xml` добавляется новая строка перед первой CardView (Интерфейс).
- Строка содержит: TextView (8sp, текст информации) + ImageButton (18dp, иконка refresh).
- LinearLayout с нулевыми вертикальными паддингами.
- Fragment подписывается на StateFlow из ViewModel и обновляет TextView при изменении значения.

**D. Ресурсы**

- Строковые константы в `strings.xml` / `strings_ru.xml` / `strings_uk.xml`: формат "На устройстве доступно: %s Гб".
- Иконка refresh (если нет встроенной Material иконки `ic_refresh`, использовать `@drawable/ic_refresh_24` или аналог).

### 5.2 Потоки данных и событий

1. **Инициализация (onViewCreated)**
   - Fragment запрашивает текущее значение у ViewModel.
   - ViewModel запускает UseCase для получения информации о диске.
   - Результат эмитится в StateFlow.
   - Fragment наблюдает за StateFlow и обновляет TextView.

2. **Нажатие кнопки обновления**
   - User нажимает ImageButton (refresh).
   - Fragment вызывает `viewModel.refreshDeviceStorage()`.
   - ViewModel повторно запускает UseCase.
   - StateFlow обновляется, TextView переотражает новое значение.

3. **Ошибка**
   - Если UseCase не может получить информацию, StateFlow содержит ошибку.
   - Fragment отображает дефолтное значение или скрывает панель (TBD через открытые вопросы).

### 5.3 Точки расширяемости

- UseCase построен так, чтобы в будущем можно было добавить запросы к другим локациям (SD card, external storage).
- ViewModel предусматривает возможность добавления обновления в фоновых сервисах (работник для периодического обновления).

1. **Получение информации о диске (API-выбор)**
   - **Вопрос:** Использовать `StatFs` (прямой доступ к inode информации) или `StorageManager` (выше уровень, требует API 26+)?
   - **Варианты:** StatFs (более простой, работает на всех API), StorageManager (более новый, может требовать дополнительных разрешений).
   - **Нужно выяснить:** Совместимость и доступность на целевых API (26+, 23 для legacy), есть ли разница в точности.
   - **Статус:** Verified

2. **Единица отображения (Гб или Гибайт)**

## 9. Архитектурные решения (ADR)

**ADR-1: Вычисление в UseCase, не в Fragment**

- **Решение:** Логика преобразования байтов в Гб, обработка ошибок и асинхронность — в специальном UseCase (GetDeviceStorageUseCase), не в Fragment.
- **Альтернативы:** Всё прямо в Fragment или ViewModel. Всё в Helper классе (как другие настройки).
- **Почему:** UseCase позволяет легко тестировать логику отдельно, переиспользовать в других местах (например, в widget-е), и соответствует Clean Architecture паттерну проекта.

**ADR-2: StateFlow для синхронизации UI**

- **Решение:** ViewModel экспонирует StateFlow<DeviceStorageState> (Success/Error), Fragment наблюдает и обновляет UI.
- **Альтернативы:** LiveData, direct function calls, Coroutine Flow.
- **Почему:** StateFlow — стандарт проекта для MVVM, автоматически управляет жизненным циклом, и типобезопасна.

## 11. Критерии готовности (strategic-level)

1. При открытии экрана основных настроек отображается панель с информацией о доступном месте (Например: "На устройстве доступно: 128.5 Гб").
2. Панель находится выше первой группы настроек (Интерфейс) и имеет нулевой вертикальный отступ.
3. При нажатии на кнопку refresh значение обновляется в течение < 500ms.
4. Панель чита TalkBack с правильным `contentDescription` для кнопки.
5. Локализация присутствует: EN/RU/UK.
6. На всех флейворах (standard, lite, photos, legacy) работает без ошибок.
7. Ошибки логируются через Timber, не вызывают краха.
