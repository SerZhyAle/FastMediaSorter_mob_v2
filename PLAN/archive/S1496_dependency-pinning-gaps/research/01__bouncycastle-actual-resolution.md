# S1496 research 01 - какая версия BouncyCastle приходит на самом деле

**Дата:** 2026-08-09
**Вопрос §6.1:** возвращать `resolutionStrategy` или принять транзитивное разрешение и задокументировать фактическую версию.

## Метод

Полный отчёт о разрешении зависимостей на runtime-классpath основного варианта:

```powershell
gradlew.bat :app_v2:dependencies --configuration standardDebugRuntimeClasspath
gradlew.bat :wear:dependencies   --configuration debugRuntimeClasspath
```

Запуск обёрнут в `temp/S1496/resolve-deps.ps1` (берёт `temp/BUILD.LOCK` по Rule 23), exit 0.
Сырые отчёты: `temp/S1496/app_v2-deps.txt`, `temp/S1496/wear-deps.txt`.

## Что разрешается

Единственное ребро BouncyCastle во всём графе `app_v2`:

```text
+--- com.hierynomus:smbj:0.12.1
|    +--- org.slf4j:slf4j-api:2.0.7 -> 2.0.9
|    +--- org.bouncycastle:bcprov-jdk18on:1.75
|    +--- net.engio:mbassador:1.3.0
|    \--- com.hierynomus:asn-one:0.6.0
```

- Фактическая версия: **`org.bouncycastle:bcprov-jdk18on:1.75`**.
- Единственный потребитель: `com.hierynomus:smbj:0.12.1`. Больше ничто в графе BouncyCastle не тянет.
- Стрелки конфликта (`->`) на этом ребре нет, то есть версию никто не поднимает и не понижает.
- `wear` разрешает ровно ту же `bcprov-jdk18on:1.75` через тот же `smbj:0.12.1`.

## Главная находка: закомментированный блок мёртв дважды

`app_v2/build.gradle.kts:1645-1652` форсит три координаты:

```kotlin
// force("org.bouncycastle:bcprov-jdk15to18:1.72")
// force("org.bouncycastle:bcpkix-jdk15to18:1.72")
// force("org.bouncycastle:bcutil-jdk15to18:1.72")
```

Ни одной из них в графе нет. Поиск по отчёту разрешения:

- `bcprov` - одно вхождение, и это артефакт `bcprov-jdk18on`, а не `bcprov-jdk15to18`.
- `bcpkix` - ноль вхождений.
- `bcutil` - ноль вхождений.
- `jdk15to18` - ноль вхождений.

`resolutionStrategy.force()` меняет версию модуля, уже присутствующего в графе, и никогда не добавляет новый. Значит блок не сработал бы, даже если его раскомментировать: он целится в артефакты `jdk15to18`, а SMBJ 0.12.1 тянет линейку `jdk18on`. Восстанавливать его - восстанавливать плацебо.

Комментарий на строке 1511 (`uses BouncyCastle jdk15to18:1.72 via resolutionStrategy`) по этой же причине неверен и должен уйти вместе с блоком.

## Совместимость с исключениями упаковки

`app_v2/build.gradle.kts:975-983` отбрасывает `org/bouncycastle/pqc/crypto/picnic/**` и один файл локализованных сообщений X.509. Эти пути живут внутри `bcprov`, то есть исключения по-прежнему адресны для линейки `jdk18on` и остаются в силе при любой версии `bcprov`. Смена мажорной версии - единственный сценарий, в котором раскладка путей может поехать.

## Вывод для §5

Транзитивное разрешение принять, закомментированный блок удалить, но добавить проверку версии на этапе конфигурации, чтобы обновление SMBJ не утащило крипто-библиотеку молча. Статический текстовый гейт этого увидеть не может - он читает текст файлов сборки, а не разрешённый граф, - поэтому проверка обязана жить внутри самой сборки.
