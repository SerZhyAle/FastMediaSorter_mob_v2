# S1496 research 02 - разъезд jsch между модулями: намеренный или забытый

**Дата:** 2026-08-09
**Вопрос §6.2:** `wear` отстаёт на девять минорных версий - это осознанное решение или недосмотр.

## Факты из файлов сборки

- `app_v2/build.gradle.kts:1515` - `implementation("com.github.mwiede:jsch:0.2.26")`.
- `wear/build.gradle.kts:196` - `implementation("com.github.mwiede:jsch:0.2.17")`, с меткой `(S0111 Phase 04)`.

Комментарий над строкой в `wear`:

```kotlin
// SFTP client - JSch (lighter than SSHJ, no BouncyCastle conflict with SMBJ) (S0111 Phase 04)
```

Он обосновывает **выбор jsch вместо sshj**, а не выбор версии `0.2.17`. Никакой записи о том, почему `wear` не должен идти дальше, ни в файле сборки, ни в `docs/TECH_STACK.md` нет: строка 149 `TECH_STACK.md` лишь констатирует факт расхождения («in both modules, with different pinned versions»), не называя причины.

Тактических материалов S0111 в `PLAN/` не осталось, поэтому реконструировать намерение по тикету нельзя.

## Есть ли техническое препятствие для `0.2.26` в `wear`

Нет, и препятствие снимается с запасом:

- `wear` объявляет `minSdk = 28`, `compileSdk = 36`, `targetSdk = 36` (`wear/build.gradle.kts`, блок `defaultConfig`).
- `app_v2` уже собирает `0.2.26` на флейворе `legacy` с `minSdk = 23`, то есть на пять уровней API ниже, чем `wear`.

Версия, работающая на API 23, тем более работает на API 28. Отдельной проверки под Wear OS библиотека не требует - это чистый Java-клиент SFTP без platform-специфичных вызовов.

## Разрешение подтверждает разъезд

Отчёты разрешения показывают обе версии живыми - модули собираются раздельно, поэтому Gradle никогда не сводит их к одной:

```text
app_v2: +--- com.github.mwiede:jsch:0.2.26
wear:   +--- com.github.mwiede:jsch:0.2.17
```

## Вывод для §5

Разъезд - забытый bump, а не решение: обоснование в комментарии относится к другому выбору, причина версии нигде не записана, технического барьера нет. Подтянуть `wear` до `0.2.26` и оставить обе строки на одной версии.
