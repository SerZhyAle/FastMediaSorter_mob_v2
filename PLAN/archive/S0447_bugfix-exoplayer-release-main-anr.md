**Текст:**

Main-thread ANR / чёрный экран при teardown standalone-плеера: ExoPlayer.release() блокирует главный поток. Симптом: открыть большое видео через внешний ACTION_VIEW (StandaloneVideoPlayer → PhotoVideoStandaloneActivity), нажать «назад», затем открыть картинку (StandaloneImagePlayer → та же PhotoVideoStandaloneActivity) — экран остаётся чёрным, через 5с ANR "Input dispatching timed out (Application does not have a focused window)".

Доказательства (логкат logs/Pixel-4-Android-17_2026-06-15_203742.logcat, эмулятор sdk_gphone16k_x86_64 Android 17, noLegal-debug v2.60.6141.930):
- L101590 START image/jpeg → .StandaloneImagePlayer (targetActivity PhotoVideoStandaloneActivity)
- L102925 Unfinished container; L105580 "Waiting because no window has focus .. wait 5000ms"; L106540 ANR
- Для image-запуска НЕ залогированы attachBaseContext/onCreate PhotoVideoStandaloneActivity (для видео L90100 — есть). Значит main заблокирован до создания Activity.
- L100405 StandaloneViewManager: release → L100459 ExoPlayerImpl Release, но потоки плеера остаются живы.

Живая диагностика по adb (процесс не перезапускался, pid 10298 висел минутами):
- dumpsys window: mCurrentFocus=null, mFocusedApp/topResumedActivity = StandaloneImagePlayer t11 (ActivityRecord 254736012 из ANR).
- /proc/10298/status: State S (sleeping), TracerPid 0, cgroup top-app (не frozen) — main припаркован на блокирующем ожидании, не GC и не заморозка.
- Перечисление 83 потоков: спустя минуты после лога Release ВСЕ потоки ExoPlayer живы (ExoPlayer:Playback x2, Frame/Loader/Media x4/Audio) + MediaCodec_loop, CCodecWatchdog, CodecLooper. Ни один не в D.

Причина: StandaloneViewManager.release() (app_v2/.../ui/player/helpers/StandaloneViewManager.kt:293) вызывает exoPlayer?.release() синхронно на главном потоке. В Media3 1.2.1 release() ждёт завершения внутренних playback/codec-потоков; на софтверном декодере после большого видео они не закрываются → main застревает в ожидании join → следующая Activity не доходит до onCreate → нет окна → ANR.

Направление фикса (на исследование): освобождать ExoPlayer вне main-потока либо с жёстким bounded-timeout/асинхронным teardown, чтобы зависший codec-поток не держал главный поток. Проверить, помогает ли setReleaseTimeoutMs и почему дефолтный timeout не сработал. Воспроизвести на реальном устройстве vs эмулятор.

## 1. Проблема

При закрытии standalone-видеоплеера (внешний ACTION_VIEW) освобождение ExoPlayer блокирует главный поток на неопределённое время. Если сразу после видео открыть картинку в том же экране, следующая Activity не успевает создать окно — пользователь видит чёрный экран, через 5 с система выдаёт ANR. Причина — известный баг Media3 1.2.1: при активном GL-конвейере video-effects (`setVideoEffects`) join GL-потока кадрового процессора при release не ограничен таймаутом. Область — standalone-видеоплеер (модуль плееров), затрагивает все flavor (код общий).

---

## 2. Цели

1. Закрытие видеоплеера никогда не блокирует главный поток — следующий экран открывается без чёрного экрана и ANR.
2. Переход «большое видео → картинка» в том же standalone-экране проходит чисто.
3. Поведение видеовоспроизведения (эффекты hue/brightness, восстановление позиции) сохраняется без регрессий.

**Non-goals:**

- Вынос плеера на выделенный playback-Looper (рассмотрено и отклонено как избыточный рефактор — см. §6).
- Подъём версии Media3 (отдельная задача, широкий риск на весь медиастек).

## 5. Предлагаемый подход

Выбрана стратегия «точечный teardown» (owner-решение 2026-06-15). Перед освобождением плеера GL-конвейер эффектов сбрасывается и выходной surface отвязывается, чтобы GL-поток кадрового процессора корректно завершился, пока EGL-контекст ещё валиден; только затем плеер останавливается и освобождается. Главный поток больше не ждёт неограниченного join.

### 5.1 Основные столпы / модули

- Менеджер представления standalone-плеера: упорядоченный teardown (drain эффектов → detach surface → stop → release).

### 5.2 Потоки данных и событий

- Lifecycle Activity (onDestroy) → менеджер представления → освобождение плеера. Никаких новых слоёв.

### 5.3 Точки расширяемости

- Если на устройстве teardown всё равно подвисает — эскалация к выделенному playback-Looper или подъёму Media3 (§6), без изменения внешнего контракта менеджера.

## 6. Открытые вопросы / Research items

1. Достаточно ли точечного teardown на реальном устройстве, или GL-поток подвисает и при сброшенных эффектах. Резолв — воспроизведение на эмуляторе/устройстве (переход видео→картинка). Эскалация при неудаче: выделенный playback-Looper (надёжно, дорого) либо Media3 ≥1.6.0 (upstream, широкий риск).

## 11. Критерии готовности (strategic-level)

1. После просмотра большого видео и нажатия «назад» открытие картинки в standalone-экране показывает изображение без чёрного экрана.
