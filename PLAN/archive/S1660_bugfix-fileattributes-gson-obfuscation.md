`com.sza.fastmediasorter.domain.model.FileAttributes` уходит в JSON как свойство `MediaFile.attributes`, то есть внутрь того же кэша списка файлов, ради которого закрывали S1630. ## 1. Проблема / симптом

Два признака файла - «только для чтения» и «скрытый» - хранятся внутри кэша списка файлов и переживают обновление приложения. Имена их полей ничем не закреплены, поэтому после обновления с новым отображением R8 запись прошлой сборки читается уже другими ключами.

Проявление тихое и оттого неприятное: Gson не находит ключей, оба поля берут значения по умолчанию, и весь закэшированный список выглядит так, будто в нём нет ни скрытых файлов, ни файлов только для чтения. Ошибки при этом никакой - список просто становится неверным.

---

## 2. Корневая причина

`FileAttributes` попадает в JSON не сам по себе, а как свойство `MediaFile.attributes`. У `MediaFile` keep-правило есть (`proguard-rules.pro:16`), но оно названо точным именем класса и на вложенный тип не распространяется - ProGuard-правило по имени класса не наследуется содержимым его полей. Ни одно из двух полей `FileAttributes` не размечено, поэтому у этого типа не было ни аннотации, ни правила: закрывая кэш на уровне `MediaFile`, S1630 закрыл только внешний слой.

---

## 3. Исправление

Оба поля закреплены `@SerializedName` с теми же именами, что и у свойств, - уже сохранённые блобы продолжают читаться. Keep-правило не добавлялось: `proguard-rules.pro:222` держит `@SerializedName <fields>` **без** `allowobfuscation` для всех классов, то есть аннотация здесь и есть механизм, а второе правило было бы дублем (тот же вывод, что зафиксирован в S1657).

Запись S1660 удалена из `scripts/quality/gson-persistence-exemptions-baseline.txt`: она описывала живой дефект, которого больше нет.
