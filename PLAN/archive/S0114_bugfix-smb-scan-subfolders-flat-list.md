# Стратегическая спецификация: S0114 — Баг: плоский список SMB не включает файлы из подпапок при включённом рекурсивном сканировании

## 1. Проблема

У SMB-ресурса включена опция «сканировать подпапки» и выключена опция «показывать подпапки как элементы» — то есть пользователь ожидает получить плоский список всех медиафайлов из всей дерево папок. Вместо этого список отображает только файлы из корневого уровня (34 файла), игнорируя все вложенные папки (6 штук с ~3950 дополнительными файлами). При этом никакой ошибки не выбрасывается — сканер находит ~3984 matching-файлов (прогресс-коллбэк подтверждает), но до адаптера доходят только 34. Пользователь видит неполный список и не может прокрутить его ниже 34-го элемента.

---

## 2. Цели

1. При `scanSubdirectories=true` и `showSubfoldersAsItems=false` плоский список содержит файлы из всех вложенных папок рекурсивно — не только из корня ресурса.
2. Кэш (как in-memory, так и персистентный) хранит полный рекурсивный список, а не усечённую версию из предыдущего сеанса с другими настройками.
3. Устаревший (orphaned) скан из предыдущего вызова не мешает отображению результатов нового сеанса.
4. Прогресс-счётчик в UI совпадает с количеством файлов, которые в итоге отображаются (нет расхождения 3984 → 34).

**Non-goals:**

- Рекурсивный просмотр для SFTP/FTP-ресурсов — в рамках этого бага не трогаем.
- Изменение логики режима «показывать подпапки как элементы» — он сейчас работает корректно.
- Оптимизация скорости сканирования или порядок появления файлов в процессе загрузки.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. После исправления плоский список должен включать файлы из всех уровней вложенности без ограничений по глубине.
2. Счётчик «Сканування: N» в UI должен показывать именно то число, которое затем окажется в списке.

### 3.2 Жёсткие ограничения

- **Flavor:** all (standard, lite, photos, legacy) — SMB доступен во всех сборках.
- **API level:** без API-специфики, SMB работает на Android 8+.
- **Wear OS:** не затрагивается.
- **Производительность:** рекурсивный скан большого SMB-дерева (~4k файлов) уже работает — бюджет не меняется.
- **Совместимость данных:** персистентный кэш файлового списка должен корректно инвалидироваться при изменении флага `scanSubdirectories` у ресурса.
- **Локализация:** EN/RU/UK — изменений в строках нет, баг поведенческий.
- **Доступность:** не затрагивается.

---

## 4. Контекст текущей архитектуры

Загрузка файлов для SMB-ресурса проходит несколько уровней кэширования до того, как попасть в адаптер. На верхнем уровне — in-memory кэш с проверкой актуальности (TTL, фильтр). На следующем — персистентный дисковый кэш с инкрементальной стратегией (сравнение mtime папки). Если любой из этих кэшей признаётся «свежим», физическое сканирование SMB пропускается, и адаптер получает данные из кэша.

Проблема в том, что кэш мог быть заполнен в момент, когда настройка `scanSubdirectories` у ресурса была выключена (или ресурс только что создан), и на тот момент записал только корневые 34 файла. При следующем открытии стратегия инвалидации признаёт кэш действительным и возвращает 34 файла — несмотря на то что флаг уже `true`. Параллельно в фоне может продолжать работать незавершённый скан из предыдущего вызова (orphaned job), чьи прогресс-события и создают иллюзию полного рекурсивного сканирования 3984 файлов.

## 5. Предлагаемый подход

### 5.1 Основные столпы

**Инвалидация кэша по флагу сканирования.**
Ключ кэша (или его метаданные) должен включать значение флага `scanSubdirectories`. При смене этого флага у ресурса кэш должен автоматически инвалидироваться, чтобы гарантировать физический пересчёт.

**Инкрементальная стратегия учитывает режим сканирования.**
Логика «можно ли пропустить скан» должна учитывать, с каким флагом рекурсии был сделан предыдущий скан. Если режим изменился — кэш не подходит, необходим свежий скан.

**Контроль orphaned-сканов.**
При запуске нового цикла загрузки файлов предыдущий незавершённый скан (если есть) должен быть отменён до старта нового. Прогресс-события от отменённого скана не должны достигать UI.

### 5.2 Потоки данных и событий

При открытии ресурса:
- Проверка кэша: если `scanSubdirectories` изменился с момента последнего кэша → кэш инвалидируется, запускается физический скан.
- Физический скан рекурсивно собирает все matching-файлы → результат записывается в кэш с записью текущего значения флага → список передаётся адаптеру.
- Новый вызов загрузки отменяет предыдущий незавершённый скан перед стартом.

### 5.3 Точки расширяемости

- Логика инвалидации кэша должна быть расширяемой: другие параметры ресурса (тип медиа, фильтр размера) в будущем тоже могут потребовать инвалидации.

## 6. Открытые вопросы / Research items

1. **Место хранения флага `scanSubdirectories` в кэше**
   - **Вопрос:** Персистентный кэш сейчас сохраняет mtime папки и timestamp скана. Хранится ли там значение `scanSubdirectories`?
   - **Варианты:** добавить в метаданные кэша, или вычислять по разнице корневых vs. рекурсивных файлов.
   - **Нужно выяснить:** схему таблицы/сущности CachedFileListRepository.
   - **Статус:** Open

2. **Orphaned-скан: место отмены**
   - **Вопрос:** Гарантируется ли отмена предыдущего `loadFilesJob` до старта нового в текущей реализации `BrowseResourceLoadManager`?
   - **Варианты:** добавить явный `cancel()` перед запуском нового job, или проверить, что это уже делается.
   - **Нужно выяснить:** последовательность вызовов `setLoadFilesJobRef` и `cancel()` в существующем коде.
   - **Статус:** Open

## 9. Архитектурные решения (ADR)

**ADR-1: Инвалидация по флагу, а не полный сброс кэша**

- **Решение:** Добавить `scanSubdirectories` в ключ/метаданные кэша; инвалидировать только при несовпадении.
- **Альтернативы:** Полностью убрать кэш для SMB-ресурсов с `scanSubdirectories=true`; принудительно пересканировать при каждом открытии.
- **Почему:** Полный сброс ухудшит UX для больших папок (нет мгновенного показа из кэша). Инвалидация по флагу точечна и не затрагивает другие ресурсы.

## 11. Критерии готовности (strategic-level)

1. При открытии SMB-ресурса с `scanSubdirectories=true` и `showSubfoldersAsItems=false` список содержит файлы из всех вложенных папок, не только из корня.
2. Число файлов в адаптере совпадает с числом файлов, которые сканер находит рекурсивно (прогресс-счётчик и финальный список согласованы).
3. При изменении флага «сканировать подпапки» в настройках ресурса и возврате к списку — список пересчитывается с новым значением флага без ручного «Обновить».
4. Нажатие «Стоп» во время рекурсивного скана по-прежнему корректно прерывает загрузку.
5. Повторное открытие ресурса (без изменений на SMB-сервере) показывает кэшированный полный список без нового скана.
