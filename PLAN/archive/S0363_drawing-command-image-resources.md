## 1. Проблема

Команда «Создать рисунок» в обзоре ресурса появляется только там, где у ресурса есть реальная папка-приёмник. Для агрегатных и виртуальных изображенческих ресурсов - «Все изображения» и «Камера» - команда не предлагается, хотя пользователь ожидает создать новый рисунок прямо отсюда.

У ресурса «Все изображения» нет единой папки, поэтому даже при показе команды непонятно, куда сохранять новый файл. Из-за этого создание рисунка из обзора этих ресурсов сейчас недоступно.

---

## 2. Цели

1. Пункт «Создать рисунок» предлагается в обзоре изображенческих ресурсов «Все изображения», «Камера» и «Загрузки».
2. Пункт встроен в панель действий ресурса наравне с прочими командами и при нехватке места уходит в ниспадающее (overflow) меню по уже существующему правилу свёртки.
3. Новый рисунок по умолчанию сохраняется в каталоге самого ресурса.
4. Для ресурса «Все изображения», у которого нет собственного каталога, новый рисунок сохраняется в «Загрузки» (Downloads).
5. Созданный рисунок открывается в существующем редакторе рисования и затем виден в списке исходного ресурса.

**Non-goals:**

- Новый редактор рисования - используется уже существующий.
- Изменение видимости команды по флейворам - остаётся как у текущей команды рисования.
- Новый механизм свёртки панели в overflow - переиспользуется существующий.
- Перенос команды на неизображенческие ресурсы (видео, аудио, документы).

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Команда доступна для трёх изображенческих ресурсов: «Все изображения», «Камера», «Загрузки».
2. По умолчанию сохранять рисунок в каталоге ресурса; для «Все изображения» - в «Загрузки».
3. Поведение в обзоре - единообразно с уже существующей командой «Создать рисунок» для обычных папок.

### 3.2 Жёсткие ограничения

- **Flavor:** видимость команды по флейворам не меняется - такая же, как у существующей команды рисования. Новых `BuildConfig.SUPPORT_*` проверок в общем источнике не вводится.
- **API level:** без API-специфики на уровне продукта; запись в публичный каталог «Загрузки» обязана соответствовать правилам хранилища платформы на всём целевом диапазоне (детали - в `/spec-tech`).
- **Wear OS:** не затрагивается.
- **Производительность:** не критично; создание одного файла.
- **Совместимость данных:** без схемы Room и миграций; меняется только выбор каталога-приёмника. Созданный файл должен индексироваться в медиатеке, чтобы появляться в агрегате «Все изображения».
- **Локализация:** новых пользовательских строк не вводится - переиспользуются существующие подпись команды и тексты ошибок создания рисунка. Если потребуется новая строка - EN / RU / UK обязательны.
- **Доступность:** пункт «Создать рисунок» и в панели, и в overflow-меню сохраняет фокус-навигацию (клавиатура, D-pad), hover мыши и корректное описание, как у соседних команд.

### 3.3 Owner inputs (Approval gate)

- **UI placement contract:** «Создать рисунок» располагается в панели действий ресурса в том же порядке, что и существующая команда рисования; при нехватке места уходит в overflow по текущему правилу свёртки - финальное расположение подтверждается через `/ui-clarify`.
- **Accessibility:** новый/расширенный пункт проходит тот же гейт `/ui-clarify`, что и правки существующих экранов; фокус и описание - как у соседних команд.
- **Validation level:** целевые варианты сборки компилируются; затронутые юнит-тесты политики выбора каталога проходят; ручная проверка создания рисунка на «Все изображения», «Камера», «Загрузки».
- **Owner sign-off:** ожидается после подтверждения развилок §6 - 2026-06-05.
- **Related tickets:** S0191 (создание рисунка из обзора - расширяется этой спекой), S0189 (создание текстовой заметки - прецедент маршрутизации виртуального ресурса в публичный каталог). Зависимостей-блокеров нет.

## 4. Контекст текущей архитектуры

Создание рисунка из обзора уже существует: команда видна, когда ресурс поддерживает изображения, а тяжёлая работа по созданию пустого файла и открытию редактора вынесена из UI в отдельный сценарий применения. Сохранение идёт в каталог, выводимый из текущего пути ресурса.

Для аналогичной команды «Создать заметку» уже действует политика, которая разрешает создание на виртуальном агрегате и перенаправляет запись в соответствующий публичный каталог, когда у ресурса нет собственной папки. Для рисунка такой политики нет: команда завязана на наличие реального каталога, поэтому виртуальные «Все изображения» и «Камера» выпадают.

Панель действий ресурса уже умеет сворачивать не помещающиеся команды в overflow-меню по существующему правилу видимости элементов. Отдельной инфраструктуры под это вводить не нужно.

Сейчас проблему §1 нельзя решить, потому что нет единого правила «для каких изображенческих ресурсов показывать команду и куда писать файл», аналогичного уже имеющемуся для заметок.

## 5. Предлагаемый подход

Ввести для рисунка правило видимости и выбора каталога-приёмника по образцу уже существующей политики для заметок: команда «Создать рисунок» предлагается для изображенческих ресурсов, включая виртуальные «Все изображения» и «Камера», а каталог записи выбирается по типу ресурса. Панель и overflow переиспользуются без изменений.

### 5.1 Основные столпы / модули

**Правило видимости команды.**
- «Создать рисунок» предлагается для изображенческих ресурсов, включая виртуальные «Все изображения» и «Камера» и обычный локальный «Загрузки».
- Видимость для неизображенческих ресурсов и для флейворов - без изменений.

**Правило выбора каталога-приёмника.**
- По умолчанию - каталог самого ресурса (текущий путь обзора).
- «Все изображения» (нет собственного каталога) - «Загрузки».
- «Камера» - её каталог; если каталог камеры не определяется, запись уходит в «Загрузки» как безопасный откат, команда при этом остаётся доступной.
- «Загрузки» - собственный каталог ресурса (уже работает).

**Индексация результата.**
- Созданный файл регистрируется в медиатеке, чтобы появляться в агрегате «Все изображения» и в списке исходного ресурса после возврата из редактора.

**Панель действий и overflow.**
- Пункт встраивается в существующую панель команд ресурса и подчиняется текущему правилу свёртки в overflow-меню при нехватке места; новой логики свёртки не вводится.

### 5.2 Потоки данных и событий

- Обзор ресурса -> правило видимости -> показ пункта в панели либо в overflow.
- Выбор пункта -> правило выбора каталога (тип ресурса) -> создание файла -> открытие редактора рисования -> индексация -> возврат в список ресурса.

### 5.3 Точки расширяемости

- Правило выбора каталога вводится как отдельная роль-политика по образцу существующей политики заметок, чтобы добавлять новые типы ресурсов-приёмников без правок UI.
- Набор изображенческих ресурсов, для которых доступна команда, остаётся данными правила, а не разветвлением в UI.

## 6. Открытые вопросы / Research items

1. **Откат каталога для «Камеры»**
   - **Вопрос:** что делать, если каталог камеры не определяется на устройстве.
   - **Варианты:** сохранять в «Загрузки» (откат) с сохранением видимости пункта; либо скрывать пункт для «Камеры» в этом случае.
   - **Решение:** откат в «Загрузки», пункт остаётся видимым - единообразно с «Все изображения» и без мерцания доступности. Владелец может пересмотреть.
   - **Статус:** Resolved

2. **Целевой публичный каталог для «Все изображения»**
   - **Вопрос:** владелец явно указал «Загрузки» (Downloads), тогда как аналог заметок пишет в публичные «Документы».
   - **Решение:** для рисунка - «Загрузки», по прямому указанию владельца; расхождение с заметками намеренное.
   - **Статус:** Resolved

| Риск | Вероятность | Последствия | Митигация |

## 9. Архитектурные решения (ADR)

**ADR-1: Политика выбора каталога по образцу заметок**

- **Решение:** видимость и выбор каталога-приёмника для рисунка выносятся в отдельную роль-политику, как уже сделано для текстовых заметок.
- **Альтернативы:** ветвление по типу ресурса прямо в UI/менеджере команды.
- **Почему:** прецедент в проекте уже есть, политика тестируема в изоляции и не размывает UI бизнес-логикой.

**ADR-2: «Все изображения» -> «Загрузки», а не «Изображения»**

- **Решение:** публичный каталог-приёмник для агрегата - «Загрузки» по прямому указанию владельца.
- **Альтернативы:** публичные «Изображения» (Pictures) - по симметрии с фактической природой файла.
- **Почему:** явное пожелание владельца; пользователь ищет свежесозданный рисунок именно в «Загрузках».

## 11. Критерии готовности (strategic-level)

1. В обзоре ресурсов «Все изображения», «Камера» и «Загрузки» доступен пункт «Создать рисунок».
2. При нехватке места пункт уходит в overflow-меню по тому же правилу, что и прочие команды.
3. Новый рисунок сохраняется в каталог ресурса; для «Все изображения» - в «Загрузки».
4. Для «Камеры» рисунок сохраняется в её каталог, а при невозможности - в «Загрузки», пункт остаётся доступным.
5. Созданный рисунок открывается в редакторе и затем виден в списке исходного ресурса, включая агрегат «Все изображения».
