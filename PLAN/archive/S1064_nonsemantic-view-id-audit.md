## 0. Захваченный материал (inbox)

**Захвачено:** 2026-07-15 (запрос владельца в чате)

**Симптом:** объекты, названные по шаблону `<тип><номер>` (`button1`, `textView2`, `imageView3`, `layout1`) - код-запах: имя не несёт роли, дублирует тип, ломается при вставке соседних вьюх. Обычно это дефолтный id, который Android Studio подставила при drag-and-drop и который забыли переименовать; через ViewBinding он всплывает в Kotlin как `binding.button1`.

**Предварительный ресёрч (2026-07-15, до написания спеки):**
- Строгий шаблон `@+id/button1` / `textView2` в layout - НЕ найдено (0 хитов).
- Числовые суффиксы в id есть, но почти все **семантические** (число кодирует значение): `btnRewind10`/`btnForward30` (секунды), `radio_op_0..100` (прозрачность), `chipSpeed025..2` / `btnSpeed05..20` (скорость), `radioVr180`/`radioCylinder180`/`btnRotate180` (градусы). Это НЕ слоп.
- Ложное срабатывание в Kotlin: `android.R.id.button1` / `button2` в `ResourceOpsMenuManager.kt:236,240` - платформенные id кнопок AlertDialog. Трогать нельзя.
- Единственный реальный кандидат: `layoutCheckboxRow1` / `layoutCheckboxRow2` в `item_resource_to_add.xml` - позиционная нумерация без роли.

**Вывод:** проблема в проекте почти отсутствует. Спека делает три вещи: (1) полный воспроизводимый аудит, (2) переименование реальных находок, (3) механический гейт против регрессий в будущем. Основная ценность - профилактика, а не текущая уборка.

## 1. Проблема и мотивация

- Имя вьюхи/переменной должно называть **роль** (`confirmDeleteButton`, `resourceTitleView`), а не `тип+порядковый номер`.
- Тип уже виден в объявлении и в сгенерённом binding-поле - дублировать его в имени избыточно.
- Порядковый номер хрупок: вставка соседа делает нумерацию врущей, но переименовывать никто не станет.
- Дефолтные id от IDE - индикатор непродуманного layout; в продакшене FastMediaSorter недопустимы.

## 2. Правила классификации (ядро ресёрча)

Разделить находки на три корзины - **никакой автозамены без этой классификации**:

- **Семантический суффикс (KEEP).** Число/цифры кодируют доменное значение: секунды, скорость, градусы, проценты, dp, VR-режим. Пример: `btnForward30`, `chipSpeed125`, `radioVr180`. Переименованию НЕ подлежит.
- **Фреймворковый / внешний id (KEEP).** `android.R.id.*`, id из подключаемых библиотек, id из inflate чужих layout. Пример: `android.R.id.button1`. Трогать запрещено.
- **Позиционный / типовой слоп (RENAME).** Число - это порядковый номер или счётчик «потому что их несколько», роли не несёт. Пример: `layoutCheckboxRow1`, гипотетические `button1`/`textView2`. Подлежит переименованию в ролевое имя.

## 3. Область работ

### 3.1. Фаза A - аудит (воспроизводимый)
- Прогнать по `res/layout*/**.xml` (`android:id`) и по `**/*.kt` (binding-обращения, локальные `val`/`var`, id-константы) шаблоны несемантичных имён.
- Явно исключить `android.R.`, известные библиотечные префиксы, и семантические суффиксы (правила §2).
- Сложить результат аудита в `temp/S1064/` как список кандидатов с корзиной (KEEP/RENAME) и обоснованием для каждого.
- Покрыть оба модуля: `app_v2/` и `wear/`.

### 3.2. Фаза B - рефакторинг находок RENAME
- Переименовать подтверждённые кандидаты в ролевые имена. На старте это как минимум `layoutCheckboxRow*` - решить финальные имена по фактической роли строк.
- Переименование id - НЕ однострочник: затрагивает `android:id` + все `@id/`/`@+id/` ссылки в том же и соседних layout (constraint-цепочки!) + `layout-land/` counterpart (Rule 11) + все обращения через ViewBinding в Kotlin + возможные `findViewById`/навигацию/`ConstraintSet`.
- Каждое переименование проверяется компиляцией (`.\a.ps1 fk`) - binding-поля генерятся из id, опечатка = ошибка сборки.

### 3.3. Фаза C - профилактика (механический гейт)
- Добавить `scripts/quality/assert-*.ps1` (по образцу существующих неврослоп-гейтов), запрещающий новые несемантичные id/имена в `src/main`, с ratchet-baseline и явными исключениями по §2.
- Подключить гейт в `scripts/post-change.ps1` (и в батч `fg`).
- Зафиксировать правило в `CLAUDE.md` (Rule 19 neuroslop-семейство) и в соответствующих skills - «предотвращать в источнике, а не только детектить».

## 4. Non-goals
- Не переименовывать семантические суффиксы (§2, корзина KEEP) - это регресс читаемости.
- Не трогать `android.R.*` и внешние библиотечные id.
- Не трогать read-only зоны: `V1/`, `v2_6/`, `spec_v2/`, `dev/archive/`.
- Не превращать в массовый передел layout - только точечные подтверждённые находки.

## 5. Критерии приёмки
- Аудит воспроизводим одной командой и даёт стабильный список с корзинами.
- Все находки корзины RENAME переименованы в ролевые имена; сборка `fk` для `app_v2` и `wear` зелёная.
- `layout-land/` counterparts синхронны (Rule 11).
- Механический гейт активен в `post-change.ps1`, ловит новый несемантичный id и пропускает семантические/фреймворковые.
- Baseline гейта отражает только осознанно оставленные исключения.

## 6. Риски
- Ложные срабатывания на семантике - главный риск; смягчается строгими правилами §2 и baseline.
- Переименование id, использованного в `ConstraintSet`/анимациях/навигации по строковому имени, может тихо сломать рантайм - проверять не только компиляцию, но и экран на устройстве, если id участвует в constraint-цепочке.
- Низкий выхлоп по текущей уборке - основная ценность в фазе C; не раздувать фазу B.
