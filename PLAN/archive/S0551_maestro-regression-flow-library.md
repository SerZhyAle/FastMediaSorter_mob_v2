## 1. Проблема

Пре-релизный прогон `/spec-prerelease` гоняет тонкий happy-path из шести шагов и держит оракул в основном на логах и перфе, а скриншоты в вердикте проверяют лишь факт «есть хотя бы один .png» - это не подтверждение функционала. Большая часть реального функционала (browse/filter/sort, операции с файлами, плеер всех типов, слайдшоу, OCR, edge-cases, resume, info-диалог, классы ресурсов) при автоматическом прогоне не проходится либо проходится дорогим agent-driven walk через mobile-mcp с тратой токенов.

Capability-набор Maestro по фичам в проекте формально уже есть (корневой `maestro/` с раскладкой smoke/critical и раннером), но в нерабочем состоянии: раннер несёт захардкоженные чужие пути и сыплет полный вывод в консоль (дорого для агента, нет стабильного exit-контракта); оракулы существующих флоу фиктивны - помечены `optional` сверху донизу, поэтому флоу не может упасть и подтверждает лишь «не свалилось»; сопровождающая документация раздута и частью фантомна (каталог заявляет десятки готовых тестов в несуществующей директории, со ссылками на чужой чекаут). Параллельно существует чистый per-ticket движок (S0420) с off-context вердиктом и настоящими утверждениями, но он не предназначен для capability-регрессии по фичам.

S0550 (краш плеера на большом изображении) показал, где реальная ценность: дефект поймал лог-сигнал в детерминированном прогоне, а не скриншот. Нужно привести capability-набор в рабочее состояние: чинибельный off-context раннер, настоящие оракулы, охват ядра матрицы фич и интеграция в пре-релизный прогон.

## 2. Цели

1. Корневой capability-набор Maestro оживлён: раннер без захардкоженных путей, с off-context логом, единой строкой вердикта и стабильными exit-кодами; полный вывод Maestro не попадает в контекст агента.
2. Существующие фиктивные оракулы (`optional`-везде) переписаны на настоящие: утверждение видимости ожидаемого элемента после действия плюс проверка лог-маркера завершения операции плюс скан крэшей в окне прогона.
3. Библиотека флоу по фичам покрывает ядро матрицы из `dev/PRE_RELEASE_MANUAL_TESTS.md`: browse/filter/sort, copy/move/rename/trash/undo, плеер video/photo/audio+lyrics/document, слайдшоу, edge-cases, resume position, info-диалог метаданных.
4. Локаторы - только по id/text из дерева доступности, никогда по координатам. Прогон устойчив к смене разрешения, ориентации, темы, масштаба шрифта и косметической перевёрстки.
5. Раздутая и фантомная документация набора удалена/сведена к одному актуальному README, отражающему реальный состав флоу на диске.
6. `/spec-prerelease` Шаг 3 использует этот набор как детерминированный слой регрессии; скриншоты понижены до улики только при FAIL; mobile-mcp/agent остаётся только для новых/неоттестированных путей.
7. Запуск всего набора одной командой без участия LLM, пригоден для локального ручного прогона владельцем и для CI-подобного использования.

**Non-goals:**

- Не добавляется никакой app-runtime код (набор и обвязка - тестовая инфраструктура, не приложение).
- Не покрываются не-`standard` флейворы (VR/noLegal/lite/photos/legacy) в этой итерации - только `standard-debug`.
- Не заменяется ручная матрица `PRE_RELEASE_MANUAL_TESTS.md` для реальных устройств - этот набор остаётся быстрым smoke поверх неё.
- Не трогается per-ticket движок S0420 (`scripts/devtest/maestro/`) - он остаётся для верификации отдельных тикетов; два набора не сливаются.
- Не покрываются сетевые/облачные ресурсы, недостижимые из эмулятора за NAT (LAN-only SMB остаётся register-only; Cloud/Network/Widgets - отложено).

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Минимум зависимости от скриншотов: оракул - утверждения и логи, скриншот только как улика при падении.
2. Один YAML на область фичи, читаемый и расширяемый, в by-capability раскладке корневого набора.
3. Дешёвый по токенам прогон, пригодный к частому повторному запуску при тестировании.
4. Набор должен опираться на ту же сидированную тест-медиа и те же ресурсы, что и ручной чеклист, чтобы «файлы те же».

### 3.2 Жёсткие ограничения

- **Flavor:** только `standard-debug`. Не-standard флейворы вне объёма этой итерации.
- **Home:** оживляется корневой capability-набор `maestro/` (раскладка smoke/critical/features); per-ticket движок `scripts/devtest/maestro/` (S0420) не затрагивается.
- **API level:** без API-специфики; целевой стенд - тот же эмулятор, что и `/spec-prerelease` (Pixel-класс, API 33+).
- **Wear OS:** не затрагивается.
- **Производительность:** прогон набора не зависит от LLM-цикла; полный вывод Maestro - в off-context лог под `temp/`, наружу только сводка.
- **Совместимость данных:** опирается на сидированную тест-медиа `setup_test_media.ps1` и предопределённые ресурсы `sza_resources.xml`; новых форм данных не вводит.
- **Локализация:** локаторы предпочитают стабильные id, а не локализованный текст; где текст неизбежен - учитывать активную локаль прогона (EN/RU/UK).
- **Доступность:** не применимо напрямую - это тестовая инфраструктура; устойчивость к font scale/ориентации обязательна как следствие id-локаторов.

### 3.3 Owner inputs (Approval gate)

- **Localization:** локаторы по id по умолчанию; для текстовых матчей фиксируется локаль прогона, чтобы избежать ложных падений на RU/UK.
- **Validation level:** каждый флоу зелёный на чистом сидированном эмуляторе; раннер даёт детерминированный PASS на эталонном билде; интеграция в `/spec-prerelease` подтверждается одним полным прогоном.
- **Owner sign-off:** 2026-06-19 - объём «библиотека core-флоу + раннер + интеграция»; 2026-06-20 - решение оживлять корневой `maestro/`, а не движок S0420.
- **Related tickets:** S0420 (per-ticket движок Maestro, Archived - остаётся отдельным), S0484 (`/spec-prerelease` обвязка), S0550 (краш-кейс, мотивация и кандидат на покрывающий флоу).

## 4. Контекст текущей архитектуры

В проекте сосуществуют два Maestro-набора. Корневой `maestro/` - capability-регрессия по фичам (smoke/critical, общие фрагменты, раннер `run-tests.ps1`, конфиг таймаутов): это и есть дом для покрытия «большинства функционала». Сейчас он нерабочий - раннер с захардкоженными чужими путями и без off-context вердикта, флоу с фиктивными `optional`-оракулами, документация раздута и частью фантомна. Второй набор - per-ticket движок S0420 (`scripts/devtest/maestro/`, раннер `maestro-run.ps1`): off-context лог, одна строка вердикта, стабильные exit-коды, настоящие утверждения; он привязан к одному тикету за прогон и используется в device-test петле, не для capability-регрессии.

Пре-релизный прогон (S0484) композирует подготовку, конфигурацию, измерение и агрегатор вердикта; его Шаг 3 - agent-driven walk через mobile-mcp по шести шагам, а вердикт сворачивает три сигнала (лог/перф/скриншот), где скриншот-сигнал вырожден.

Проблему из §1 нельзя решить «изнутри»: корневой раннер не даёт пригодного к автоматизации off-context вердикта, существующие флоу ничего не утверждают, а пре-релизный Шаг 3 не знает про Maestro. Источник намерений - что именно проверять - формализован в `PRE_RELEASE_MANUAL_TESTS.md`; не хватает рабочего машинного его воплощения и интеграции.

## 5. Предлагаемый подход

Оживить корневой capability-набор `maestro/` тремя слоями работ: рабочий off-context раннер, настоящая конвенция оракула с переписанными флоу и расширенной библиотекой, интеграция в пре-релизный прогон. Приложение не трогается. Per-ticket движок S0420 остаётся отдельным.

### 5.1 Основные столпы / модули

- **Рабочий раннер набора.** Починить раннер: убрать захардкоженные пути (поиск бинаря и JDK по тому же паттерну, что у off-context движка), писать полный трейс Maestro в off-context лог под `temp/`, отдавать наружу единственную строку вердикта со стабильными exit-кодами, поддерживать выбор подмножества (вся suite / категория / один флоу) и пин устройства.
- **Конвенция оракула и переписывание флоу.** Единый контракт «что значит зелёный флоу»: видимость ожидаемого пост-действие элемента, наличие лог-маркера завершения операции в окне прогона, отсутствие крэш-блоков. Существующие фиктивные `optional`-флоу переписать под эту конвенцию; новые - по ней же.
- **Библиотека флоу по фичам.** Декларативные YAML по областям матрицы намерений, в by-capability раскладке. Каждый флоу самодостаточен: приводит приложение в нужное состояние (запуск/clearState/навигация к сидированному ресурсу), выполняет действие, утверждает наблюдаемый результат. Общие шаги (разрешения, навигация к ресурсу) - переиспользуемые фрагменты.
- **Гигиена документации.** Удалить фантомный каталог и раздутый слоп-набор доков; оставить один README, отражающий реальный состав флоу и способ запуска.
- **Интеграция в `/spec-prerelease`.** Шаг 3 заменяет тонкий happy-path walk на прогон набора как детерминированного слоя; вердикт набора вливается в общий PASS/FAIL. Скриншоты понижены до улики только при FAIL. mobile-mcp/agent остаётся для новых/неоттестированных путей.

### 5.2 Потоки данных и событий

- Подготовка стенда (чистая установка, сидирование медиа, регистрация ресурсов) - переиспользует существующую пре-релизную подготовку.
- Раннер набора → Maestro → устройство; полный трейс → off-context лог; наружу → строка вердикта; агрегатор сворачивает per-flow результаты в единый PASS/FAIL.
- Внутри флоу: действие по UI → ожидание лог-маркера завершения операции / появления элемента → утверждение; крэш-скан над логом окна прогона.
- Сводный вердикт набора → пре-релизный агрегатор вердикта (Шаг 4) наравне с лог- и перф-сигналами.

### 5.3 Точки расширяемости

- Добавление новой области фичи = добавление одного YAML в соответствующую категорию, без правок раннера: раннер обнаруживает флоу по конвенции расположения.
- Конвенция оракула вынесена так, чтобы новый флоу переиспользовал её и общие фрагменты без копипаста проверок.
- Раннер параметризуется подмножеством (вся suite / категория / один флоу) и устройством - и полный набор, и точечная регрессия одной фичи.
- Набор остаётся открытым к будущему добавлению отложенных категорий (Cloud/Network/Widgets) и не-standard флейворов без изменения контракта раннера.

## 6. Открытые вопросы / Research items

1. **Граница покрытия первой итерации**
   - **Решение:** в первый набор - ядро (browse/filter/sort, copy/move/rename/trash/undo, плеер video/photo/audio+lyrics/document, slideshow, edge, resume, info-диалог), детерминированно зелёное на чистом сидированном эмуляторе. Cloud/Network/Widgets/OCR отложены (внешние зависимости, недостижимость из NAT).
   - **Статус:** Resolved

2. **Конвенция оракула «лог-маркер завершения»**
   - **Решение:** инвентаризованы стабильные маркеры (листинг `BrowseLoadingManager: COMPLETE`, видео `onRenderedFirstFrame`/`Playback ready`, файл-операции `FileOperationProgressDialog: Completed`, PDF `firstPageRendered`, EPUB `firstChapterRendered`, слайдшоу `Slideshow auto-start COMPLETE`, аудио/lyrics). Rename/undo/image/txt/resume/info маркера не имеют - утверждать по элементу. Оракул = видимость элемента И (маркер, если есть) И отсутствие крэша; не ослаблять до optional-only.
   - **Статус:** Resolved
   - **Артефакт:** `PLAN/S0551_maestro-regression-flow-library/research/02__oracle-markers-and-locators.md`

3. **Состояние существующих флоу и раннера**
   - **Решение:** REWRITE - app_launch, local_browse, video_prefetch, file_operations, settings, video_offload; DROP - media_play, image_view (заменяются настоящими player-флоу); KEEP - 3d-video×2, оба `_shared`. Раннер чинить: убрать захардкоженные пути, off-context лог + одна строка вердикта + стабильные exit-коды по образцу `maestro-run.ps1`.
   - **Статус:** Resolved
   - **Артефакт:** `PLAN/S0551_maestro-regression-flow-library/research/03__existing-flows-and-runner.md`

4. **Системные диалоги вне UI приложения**
   - **Решение:** переиспользовать `_shared/permissions.yaml` (optional-тапы по системным диалогам - корректный паттерн для утилитарного фрагмента) плюс pre-grant разрешений через adb на этапе пре-релизной подготовки.
   - **Статус:** Resolved

5. **Контракт suite-вердикта для пре-релизного агрегатора**
   - **Решение:** suite-раннер эмитит JSON-массив per-flow результатов (`{flow, pass}`); пре-релизный агрегатор принимает его опциональным входом и сворачивает как perf-сигнал (любой `pass=false` -> FAIL), скриншот-сигнал понижается до улики только при FAIL. Текущие exit-коды агрегатора сохраняются.
   - **Статус:** Resolved

6. **Объём чистки документации**
   - **Решение:** оставить 8 доков (README, INSTALLATION_WINDOWS, TROUBLESHOOTING, WRITING_TESTS, AVD_SETUP_FOR_TESTS, TEST_MEDIA_WORKFLOW_GUIDE, EXAMPLES, INDEX), удалить ~16 (фантомный FEATURE_TESTS_CATALOG + `*_COMPLETE`/`*_RESOLVED`/STATUS/дубли install).
   - **Статус:** Resolved
   - **Артефакт:** `PLAN/S0551_maestro-regression-flow-library/research/06__doc-cleanup.md`

7. **Precondition ресурсов для папочной медиа (video/audio/docs/file-ops)**
   - **Контекст (on-device 2026-06-20):** на сидированном эмуляторе нет зарегистрированного папочного LOCAL-ресурса; `virtual://all_video` и `all_audio` показывают 0 (MediaStore их не индексирует), индексируются только изображения (`virtual://all_images`, 43 файла).
   - **Решение (owner quiz):** полная матрица через один OWNER_TRIGGER-импорт предопределённых ресурсов (тот же путь, что у `/spec-prerelease`, S0492) - регистрирует папочный `Downloads` (`/storage/emulated/0/Download`, scanSubdirectories) и сетевые. Suite получает setup-шаг импорта; флоу не используют `clearState`, чтобы не стирать зарегистрированные ресурсы.
   - **Статус:** Resolved

8. **Файл-операции за меню `btnResourceOps` на AVD**
   - **Решение (принцип тикета, не owner-вопрос):** copy/move/rename/trash/undo доступны через меню `btnResourceOps`, которое на эмуляторе бывает не таппается (известный риск проекта). Не фейкать: подтвердить таппабельность эмпирически в Фазе 03; если на AVD глухо - пометить файл-оп флоу как device-only (отдельная категория `features/files`, исключаемая из эмуляторного прогона), не выдавать за зелёные.
   - **Статус:** Resolved

## 9. Архитектурные решения (ADR)

**ADR-1: Оживить корневой capability-набор `maestro/`, не строить новый и не расширять движок S0420**

- **Решение:** чинить раннер и переписывать флоу корневого набора, держа per-ticket движок S0420 отдельным.
- **Альтернативы:** строить библиотеку на движке S0420 с переносом флоу и удалением корневого набора; держать два набора параллельно (гибрид).
- **Почему:** решение владельца 2026-06-20 - сохранить by-capability раскладку корневого набора; CLAUDE.md Rule 13 - чинить/расширять существующее. Два набора остаются раздельными по назначению (capability vs per-ticket).

**ADR-2: Оракул - утверждение плюс лог-маркер плюс крэш-скан, скриншот только как улика**

- **Решение:** зелёный флоу = видимость ожидаемого элемента + лог-маркер завершения + отсутствие крэшей; скриншот сохраняется только при падении.
- **Альтернативы:** скриншот-диф как оракул; «не упало» (`optional`-везде) как единственный критерий - текущее фиктивное состояние.
- **Почему:** S0550 пойман логом, а не скриншотом; скриншот-диф хрупок к теме/разрешению и дорог, «не упало» не подтверждает функционал.

**ADR-3: Без app-runtime кода в этой итерации**

- **Решение:** изменения только в тестовой инфраструктуре; минимальные id-правки в вёрстке допускаются лишь если без них нет стабильного локатора.
- **Альтернативы:** добавлять app-side лог-маркеры/хуки под тесты.
- **Почему:** держать объём в тест-слое; app-side маркеры - отдельный возможный тикет после инвентаризации §6.2.

## 11. Критерии готовности (strategic-level)

1. Владелец одной командой прогоняет весь набор флоу на эмуляторе и получает единый PASS/FAIL без участия LLM; полный вывод Maestro не попадает в контекст агента.
2. Набор покрывает ядро матрицы из `PRE_RELEASE_MANUAL_TESTS.md`: browse/filter/sort, copy/move/rename/trash/undo, плеер video/photo/audio+lyrics/document, слайдшоу, edge-cases, resume position, info-диалог - детерминированно зелёный на чистом сидированном эмуляторе.
3. Каждый флоу падает на интродуцированной регрессии своей области (например, повтор сценария S0550 краснеет до фикса) - оракул реально утверждает поведение, а не только отсутствие краша; ни один флоу не остаётся `optional`-фиктивным.
4. Раннер без захардкоженных путей; полный трейс - в off-context логи; наружу - только сводка и пути к логам; стабильные exit-коды.
5. Фантомный каталог и слоп-доки удалены; остаётся один README, отражающий реальный состав.
6. `/spec-prerelease` Шаг 3 прогоняет набор как детерминированный слой; скриншоты появляются только при FAIL; вердикт набора вливается в общий PASS/FAIL.
7. Добавление новой области = один новый YAML без правок раннера.
