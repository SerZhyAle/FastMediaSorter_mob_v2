## 1. Проблема

Пользователь не может поделиться настроенным ресурсом (например SFTP-подключением) с другим человеком. Сейчас перенос ресурса возможен лишь через встроенный конфиг сборки, доступный только разработчику по скрытому owner-триггеру; обычный пользователь не имеет ни приёма внешнего файла, ни выгрузки своего ресурса наружу. Область - подсистема ресурсов и сетевых учётных данных + точки входа в настройках и через системное «открыть с помощью».

---

## 2. Цели

1. Пользователь может выгрузить выбранный ресурс (один или несколько) в переносимый файл прямо из приложения.
2. Пользователь может импортировать ресурсы, открыв такой файл «с помощью» приложения (ассоциация типа файла).
3. Пользователь может импортировать такой файл по явному действию «Импорт..» в настройках.
4. При импорте создаются новые ресурсы и обновляются уже существующие (сопоставление по пути); пользователю показывается итог (создано / обновлено / пропущено).
5. Сетевые учётные данные (пароль, SFTP-ключ) переносятся в файле и работают сразу после импорта - ресурс подключается без повторного ввода.
6. При экспорте и при импорте пользователь предупреждается, что файл содержит пароли в открытом виде и его нельзя публиковать.
7. Некорректный или чужой файл отвергается с понятным сообщением, без частичной порчи существующих данных.

**Non-goals:**

- Шифрованный / защищённый паролем файл-обмена (отдельная будущая итерация).
- Перенос OAuth-токенов CLOUD-ресурсов (токены не переносимы; CLOUD экспортируется как конфиг без авторизации, друг проходит вход заново).
- Облачная синхронизация / ссылки на скачивание - только локальный файл.
- Перенос истории/кэша файлов ресурса - только его конфигурация и доступ.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Файл-обмен по возможности должен открываться по двойному клику в любом файловом менеджере, а не только через ручной выбор внутри приложения.
2. Перед применением импорта показать, что именно будет создано и что перезаписано.

### 3.2 Жёсткие ограничения

- **Flavor:** все варианты сборки с подсистемой ресурсов (standard, lite, photos, legacy). Файл может нести типы медиа, не поддерживаемые конкретным flavor (например AUDIO в photos) - импорт обязан отфильтровать/пропустить неподдерживаемое, а не падать.
- **API level:** без API-специфики; системный выбор/создание файла и ассоциация типа доступны на минимальных уровнях обоих flavor.
- **Wear OS:** не затрагивается.
- **Производительность:** некритично - файл маленький, разовый разбор.
- **Совместимость данных:** без изменения схемы хранения - импорт пишет в существующее хранилище ресурсов и учётных данных тем же путём создания/обновления. Миграция не требуется.
- **Локализация:** EN/RU/UK - обязательно для всех новых строк.
- **Доступность:** новые элементы управления фокусируемы и доступны с клавиатуры/D-pad, предупреждение читается screen reader-ом.

### 3.3 Owner inputs (Approval gate)

- **Учётные данные в файле:** включать креды (username/password, SFTP-ключ) в файл-обмен + показывать предупреждение при экспорте и импорте, что файл содержит пароли и его нельзя публиковать. При импорте креды сразу шифруются в хранилище. (owner 2026-06-15)
- **Объём итерации:** включить и экспорт ресурса в файл, и импорт файла - полный цикл шаринга внутри приложения. (owner 2026-06-15)
- **Data scope:** запись в хранилище ресурсов + учётных данных тем же путём, что и текущий предопределённый импорт; без новой версии схемы.
- **Flavor scope:** поведение одинаково во всех flavor; неподдерживаемые типы медиа фильтруются на импорте.
- **UI scope:** точки входа - действие в настройках (импорт/экспорт) и контекстное действие экспорта у ресурса; приём файла из системного «открыть с помощью».
- **Related tickets:** S0046 (формат уже содержит атрибуты SFTP key-auth и host-key fingerprint - файл-обмен переиспользует их).

## 4. Контекст текущей архитектуры

Перенос ресурсов сегодня обслуживает один внутренний путь импорта: он разбирает встроенный в сборку конфиг предопределённых ресурсов и пишет их в хранилище, попутно сопоставляя/создавая записи сетевых учётных данных (с шифрованием), разбирая SFTP key-auth и host-key fingerprint, назначая ресурс в «назначения». Этот путь жёстко привязан к встроенному ресурсу сборки и вызывается лишь по скрытому owner-триггеру в настройках - у обычного пользователя нет ни кнопки, ни приёма внешнего файла. Слой UI настроек умеет показывать подтверждающий диалог и итог. Системного приёма файла (intent-фильтра «открыть с помощью») для конфигурации ресурсов нет. Поэтому из §1 нельзя решить задачу без обобщения существующего пути импорта на внешний источник и добавления пользовательских точек входа и обратной операции (экспорта).

## 5. Предлагаемый подход

Переиспользовать существующую логику разбора/создания ресурсов и учётных данных, отвязав её от встроенного источника: тот же формат, но источником становится произвольный пользовательский файл, а в дополнение появляется обратная операция - сериализация выбранного ресурса в файл того же формата.

### 5.1 Основные столпы / модули

- **Формат файла-обмена.** Тот же XML-формат, что у текущего конфига ресурсов (корень с элементами-ресурсами и их атрибутами, включая сетевые креды и атрибуты SFTP-ключа/fingerprint). Выделенное расширение файла и MIME для надёжной ассоциации «открыть с помощью».
- **Чтение из внешнего источника.** Обобщение пути импорта: принимать поток/URI вместо только встроенного конфига; остальная логика (креды, ключи, fingerprint, назначения, сопоставление по пути) переиспользуется без изменений.
- **Запись в файл (экспорт).** Сериализация одного или нескольких выбранных ресурсов и их учётных данных в файл формата выше.
- **Точки входа.** Действие «Импорт..» и «Экспорт..» в настройках; контекстное действие экспорта у ресурса; приём файла из системного «открыть с помощью» через intent-фильтр.
- **Предпросмотр и предупреждения.** Перед применением импорта - сводка (создать/обновить) и предупреждение о кредах; перед экспортом - предупреждение, что файл содержит пароли.

### 5.2 Потоки данных и событий

- Импорт: UI (выбор файла или приход из «открыть с помощью») → слой применения (разбор + предпросмотр + подтверждение) → хранилище ресурсов и учётных данных → итог пользователю.
- Экспорт: UI (выбор ресурса + предупреждение) → слой применения (сбор ресурса и кредов) → запись файла через системное создание документа → файл пользователю для передачи.

### 5.3 Точки расширяемости

- Формат версионируется, чтобы будущие поля (например защищённый/шифрованный обмен) не ломали старые файлы.
- Источник импорта абстрагирован, чтобы тот же путь годился и для встроенного конфига, и для пользовательского файла.
- Стратегия конфликтов (по пути) вынесена так, чтобы при необходимости добавить выбор «обновить/пропустить/дублировать».

## 9. Архитектурные решения (ADR)

- **ADR-1.** Формат файла-обмена - тот же XML-формат, что у текущего конфига ресурсов, а не новый JSON. Причина: уже существует разбор этого формата и пример-образец у владельца; минимальная новая поверхность.
- **ADR-2.** Выделенное расширение файла + MIME для ассоциации «открыть с помощью» вместо общего `.xml`. Причина: общий тип конфликтует со всем и не даёт надёжного открытия именно нашим приложением.
- **ADR-3.** Учётные данные включаются в файл с явными предупреждениями (решение владельца) и шифруются в хранилище при импорте. Причина: главный сценарий - готовый к работе ресурс у друга.
- **ADR-4.** Конфликт при импорте разрешается сопоставлением по пути (обновить существующий, иначе создать), с предпросмотром до применения. Причина: переиспользует уже существующую семантику и предотвращает скрытую перезапись.

## 11. Критерии готовности (strategic-level)

1. Из приложения можно выгрузить выбранный ресурс в файл-обмен.
2. Открытие файла-обмена «с помощью» приложения запускает импорт.
3. Действие «Импорт..» в настройках позволяет выбрать файл и импортировать его.
4. Импорт создаёт новые и обновляет существующие (по пути) ресурсы и показывает итог.
5. Сетевой ресурс из импортированного файла подключается без повторного ввода учётных данных.
6. Экспорт и импорт предупреждают о наличии паролей в файле.
7. Некорректный/чужой файл отвергается с понятным сообщением и без порчи существующих данных.
8. Поведение корректно во всех flavor; неподдерживаемые типы медиа отфильтровываются; все строки EN/RU/UK.
