## 1. Проблема

Встроенный экран съёмки показывает урезанный набор возможностей аппарата: доступны только две камеры вместо всех физических линз, нижняя граница зума упирается в 1x там, где системная камера предлагает 0.6x, а режим макро либо не предлагается, либо не даёт эффекта. Причина одна и общая - приложение опирается на список **логических** камер, который платформа отдаёт по умолчанию, и снимает характеристики только с них. Пользователь на многолинзовом телефоне видит камеру заметно беднее «родной» и не может дотянуться до широкоугольной и макро-съёмки. Область - экран съёмки и слой определения возможностей камеры.

## 2. Цели

1. Пользователь может переключиться на каждую физическую линзу, которую аппарат реально имеет, а не только на одну заднюю и одну фронтальную.
2. Нижняя граница зума на экране совпадает с физически достижимой на устройстве, включая значения меньше 1x.
3. Режим макро либо действительно включается и виден по картинке, либо не предлагается вовсе - без «мёртвого» тумблера.
4. Список разрешений фото включает полное разрешение сенсора, а не только первые несколько стандартных размеров.
5. Владелец может снять с любого аппарата отчёт о том, что именно этот аппарат сообщает о своих камерах, не подключая его к разработческой машине.
6. На аппарате, где расширенные пути недоступны, экран съёмки ведёт себя ровно как сегодня - без регрессий и без пустых элементов управления.
7. В ряду кнопок выбора зума всегда присутствуют нативный минимум и нативный максимум устройства - то есть границы **до** программного (цифрового) доувеличения, - и обе цифры выделены жёлтым, чтобы пользователь видел, где заканчивается настоящая оптика и начинается программное увеличение.

**Non-goals:**

- Собственная обработка кадра (склейка, шумоподавление, портретный боке-эффект) - остаёмся на пайплайне платформы.
- Паритет с OEM-камерой по качеству снимка; цель - паритет по **доступности** возможностей.
- Поддержка проприетарных OEM-расширений сверх стандартных механизмов платформы.
- Изменение сценариев съёмки без превью (жестовая съёмка) и распознавания текста.
- Wear OS.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Покрыть «самые распространённые» камеры, то есть типовую многолинзовую компоновку массовых аппаратов, а не единичную модель.
2. Набор линз в переключателе должен читаться как у системной камеры - по кратности (0.6x / 1x / 2x), а не по внутренним идентификаторам.
3. Диагностика возможностей должна собираться с устройства владельца силами самого приложения.

### 3.2 Жёсткие ограничения

- **Flavor:** экран съёмки живёт в общих исходниках и компилируется во все варианты сборки; отдельного flavor-гейта у возможности нет.
- **API level:** расширенные пути привязаны к разным уровням - перечисление физических линз, зум ниже 1x и высокие разрешения появляются на разных версиях Android. Минимум `legacy` - API 23, остальных - API 26, поэтому каждый путь обязан деградировать до текущего поведения.
- **Wear OS:** не затрагивается.
- **Производительность:** опрос характеристик выполняется при привязке сессии и при смене линзы; расширенный опрос не должен добавлять заметной задержки открытию экрана съёмки.
- **Совместимость данных:** сохранённые пользовательские настройки камеры должны переживать изменение набора линз - исчезнувшая линза не должна ломать восстановление состояния.
- **Локализация:** EN/RU/UK - обязательно для всех новых видимых подписей.
- **Доступность:** элементы выбора линзы и режима макро сохраняют размер зоны нажатия, описания для TalkBack и различимость без опоры на цвет.

### 3.3 Owner inputs (Approval gate)

- **API level constraints:** расширенные пути включаются по факту доступности на устройстве; на всех уровнях ниже требуемого экран работает как сегодня. Отдельного повышения `minSdk` тикет не требует.
- **UI placement contract:** переключение линз остаётся на существующем управлении экрана съёмки - ряд пресетов кратности и кнопка смены линзы; новые линзы расширяют этот ряд, новых панелей не добавляется. В этом же ряду обязательно присутствуют кнопки нативного минимума и нативного максимума, и только их цифры окрашены жёлтым (остальные сохраняют текущий белый). Макро остаётся кнопкой на самом экране съёмки (там, где она сейчас), меняется только правило её видимости. Диагностический отчёт о камерах - секция существующего системного отчёта, отдельного экрана не появляется.
- **Accessibility:** каждая новая кнопка кратности и тумблер макро получают текстовое описание, зону нажатия не меньше текущей и состояние, читаемое не только цветом.
- **Validation level:** компиляция и статические проверки - автономно; приёмка §11 - только на многолинзовом устройстве, поведение на одном аппарате не переносится на другой.
- **Owner sign-off:** требуется - выбор между «показывать все физические линзы» и «показывать только те, что дают новую кратность» меняет видимый набор кнопок.

## 4. Контекст текущей архитектуры

Экран съёмки не обращается к камере напрямую: между ним и платформой стоят два слоя - помощник, снимающий неизменяемый снимок возможностей активной линзы, и менеджер сессии, который привязывает выбранную камеру, переключает линзы и применяет зум, фокус и ручные параметры. UI рисуется исключительно от снимка возможностей, поэтому неподдерживаемый элемент управления скрывается, а не превращается в мёртвую кнопку. Это разделение стоит сохранить - оно и есть точка, куда встраивается расширенное перечисление.

Ограничение возникает на входе в этот конвейер. Список камер берётся ровно таким, каким его отдаёт библиотека камеры по умолчанию, то есть списком логических камер; всё остальное - кратности, эквивалентный множитель, эвристика макро, набор разрешений - считается уже **внутри** этого списка. Поэтому ни одна из трёх жалоб не решается правкой на уровне UI: пока в списке две записи, никакая логика поверх него не найдёт третью линзу, не опустит нижнюю границу зума ниже той, что объявила логическая камера, и не найдёт выделенную макро-оптику. Дополнительно набор разрешений собирается только из базового набора выходных размеров, а высокоразрешающий набор, в котором крупные сенсоры объявляют полное разрешение, не запрашивается вовсе.

## 5. Предлагаемый подход

Снять потолок логической камеры: развернуть каждую логическую камеру в её физические линзы там, где платформа это позволяет, и пересчитать все производные величины (кратность, нижняя граница зума, макро, разрешения) уже по расширенному набору. Каждый расширенный путь включается по факту доступности и имеет путь отката к сегодняшнему поведению. Порядок работ ведётся от наблюдаемости: сначала аппарат должен уметь рассказать о себе, и только потом меняется логика выбора.

### 5.1 Основные столпы / модули

- **Диагностика возможностей.** Отдельная роль, собирающая полный отчёт о камерах аппарата - какие камеры объявлены, какие из них физические подлинзы, какие диапазоны зума, дистанции фокуса, фокусные расстояния и наборы разрешений они сообщают, и что из этого дошло до приложения. Публикуется как секция существующего системного отчёта, доступная владельцу с любого аппарата.
- **Расширенное перечисление линз.** Роль, которая принимает список логических камер и возвращает расширенный набор записей, добавляя физические подлинзы там, где платформа их отдаёт, и помечая каждую запись тем, чем она отличается от соседей.
- **Правило отбора линз.** Роль, решающая, какие записи расширенного набора попадают в переключатель: дубликаты по кратности отсекаются, служебные линзы (только глубина, только монохром) не показываются.
- **Пересчёт диапазона зума.** Существующий расчёт кратности начинает работать по расширенному набору, так что нижняя граница берётся от самой широкой доступной линзы, а не от главной.
- **Режим макро как выбор оптики.** Макро сначала пытается стать переходом на близкофокусную линзу и только при её отсутствии остаётся фиксацией дистанции фокуса, защищённой от сброса автофокусом.
- **Полный набор разрешений.** Сбор разрешений дополняется высокоразрешающим набором и снятием жёсткого потолка на число вариантов.

### 5.2 Потоки данных и событий

- Открытие экрана съёмки -> перечисление логических камер -> расширение до физических линз -> отбор показываемых -> привязка выбранной -> снимок возможностей -> отрисовка управления.
- Смена линзы -> выбор следующей записи расширенного набора -> перепривязка -> новый снимок возможностей -> обновление кратностей и доступности макро.
- Включение макро -> при наличии близкофокусной линзы перепривязка на неё, иначе фиксация дистанции фокуса на текущей -> обновление снимка возможностей.
- Запрос системного отчёта -> сбор диагностики камер -> секция отчёта, доступная к копированию и отправке.

### 5.3 Точки расширяемости

- Правило отбора линз должно быть заменяемым: набор «показывать всё» против «показывать только уникальные кратности» - это одно решение в одном месте.
- Источник расширенного перечисления должен допускать добавление новых механизмов платформы без правки экрана съёмки.
- Диагностическая секция должна пополняться новыми полями без изменения контракта системного отчёта.

## 8.9. Проверка на устройстве владельца (Samsung S25 FE, 2026-07-30)

Проверял владелец на своём аппарате. Основное работает - переключатель предлагает больше двух вариантов, ряд зума есть - но найдены два дефекта.

### D1. Фронтальная камера предлагается дважды

**Симптом (владелец):** в переключателе камер ожидались макро, ширик, фронт; вместо этого два пункта переключают на фронтальную.

**Причина найдена по коду.** `CameraLensEnumerationManager.select` (строки 116-136) отсеивает физическую подлинзу, если она уже покрыта логической записью. Для **задних** линз сравнение идёт по фокусному расстоянию **или** по эквивалентной кратности, а для **фронтальных** - только по фокусному:

```kotlin
val sameEquivalent = entry.lensFacing == CameraSelector.LENS_FACING_BACK && ...
it.lensFacing == entry.lensFacing &&
    (sameMagnification(it.focalLengthMm, entry.focalLengthMm) || sameEquivalent)
```

Комментарий рядом объясняет, почему так сделано: «Front lenses all carry the neutral multiplier, so the equivalent leg would collapse every front sub-lens into one» - и ссылается на эмулятор, где подлинза 5.84 мм пропадала без этого послабления.

То есть правило намеренно ослаблено ради эмулятора, и на реальном аппарате оно недоотсеивает: если логическая фронтальная камера и её же физическая подлинза сообщают **разные** фокусные, обе попадают в список и обе открывают одну и ту же камеру. Эмуляторное свидетельство в комментарии - ровно противоположный случай, поэтому чинить надо так, чтобы не вернуть его.

### D2. Две кнопки зума с одинаковой подписью «1»

**Симптом (владелец):** в ряду выбора зума две кнопки подписаны «1». Ожидание: округление до половины ниже некоторого порога, то есть «0,5», «3,5», а не два одинаковых целых.

**Что видно по коду, и чего не хватает.** Дедуп по подписи уже есть (S1260): `CameraRuntimeCapabilities` строит `byLabel` с ключом `roundEquivalentForDisplay(preset * mult)` и оставляет по одной записи на подпись. Но **рисуется подпись другой функцией**: `CameraZoomControlsManager.formatZoomLabel` печатает значение как есть (`%.1f`, целые без дробной части), без `roundEquivalentForDisplay`.

Дедуп и отрисовка считают «подпись» по-разному, поэтому гарантия «двух одинаковых пилюль не будет» не выполняется. Это точка, с которой надо начинать разбор.

**Чего не хватает для однозначного диагноза:** проба печатает нужные числа - `S1189: presets=[..] native=..`. В забранных логах есть только чужой аппарат (POCO). Нужен экспорт логов **с S25 FE** после открытия камеры: строка `S1189: presets=` покажет, какие именно два значения схлопнулись в «1».

### Что из §11 подтверждено

- Критерий 2 (больше двух вариантов) - выполняется, но с дефектом D1.
- Критерий 7 (ряд зума с нативными границами) - ряд есть, но с дефектом D2.
- Остальные критерии владелец в этот заход не проверял.

## 9. Архитектурные решения (ADR)

- **ADR-1. Расширение набора камер выполняется отдельной ролью, а не внутри снимка возможностей.** Снимок описывает **одну** активную линзу и обязан таким остаться; перечисление - операция над множеством камер. Смешение этих ответственностей уже дало нынешний потолок, когда эквивалентная кратность считается по неполному набору.
- **ADR-2. Диагностика опережает функциональность.** Первой поставляется секция отчёта о возможностях камер, и только потом меняется выбор линз. Без фактов с аппарата любая правка перечисления - угадывание, а проверить её на разработческой машине нельзя.
- **ADR-3. Расширенный путь всегда откатываем.** Недоступность механизма платформы или отказ конкретной линзы означает возврат к сегодняшнему поведению, а не ошибку. Экран съёмки на аппарате без многолинзовой поддержки не должен ничего заметить.
- **ADR-4. Полное разрешение - явный выбор, а не значение по умолчанию.** Крупные сенсоры отдают полный кадр медленнее и дороже по памяти, поэтому по умолчанию сохраняется текущий режим.
