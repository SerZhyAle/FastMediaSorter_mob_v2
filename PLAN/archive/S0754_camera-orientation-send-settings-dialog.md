## 1. Проблема

Встроенная камера получила набор возможностей (зум-пресеты, ползунок, ночной режим, переключение линз, цифровой зум - S0753), но UX-каркаса экрана не хватает по нескольким пунктам, выявленным при использовании на устройстве:

- Не видно, куда сохранится снимок: пользователь не понимает, в какой ресурс назначения попадёт результат.
- Нет быстрого «Отправить в..» прямо из камеры - чтобы сразу отдать снятое получателю из заранее настроенного списка.
- При повороте телефона весь интерфейс камеры перекомпоновывается: кнопка спуска и контролы «переезжают», частично заходят под системную панель и наезжают друг на друга в альбомной ориентации. Пользователь хочет, чтобы кнопка спуска (и прочие контролы) физически оставались на одном месте экрана, как в системной камере, а поворачивались лишь иконки.
- Нет доступа к более глубоким настройкам камеры, которые реально поддерживает устройство.

---

## 2. Цели

1. Рядом с кнопкой выхода мелким шрифтом видно наименование ресурса назначения - куда сохранится результат.
2. Рядом с кнопкой затвора есть кнопка чуть меньшего размера «Отправить в..» со списком получателей; список задаётся в настройках; механизм переиспользует существующий «отправить в» (как в плеере).
3. Кнопка спуска фото/видео и прочие контролы физически не перемещаются при повороте телефона - вращаются только иконки и подписи; нет наложений контролов и заходов под системную панель ни в одной ориентации.
4. Кнопка «три точки» открывает диалоговое окно (не выпадающее меню) со всеми реально доступными на устройстве настройками камеры.
5. Полировка пресетов зума: из набора исключено значение «2» (сокращение числа кнопок); ширина ползунка зума вместе с прижатым справа текущим значением равна ширине ряда кнопок-пресетов.

**Non-goals:**

- Не меняем конвейер захвата и сохранения фото/видео (наследие S0545).
- Не добавляем настройки, которых устройство не отдаёт через публичный API.
- Не пишем новый механизм списка получателей - переиспользуем существующий «отправить в».
- Не трогаем экран OCR-перевода камеры.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Подпись назначения - мелким шрифтом у кнопки выхода.
2. «Отправить в..» - кнопка чуть меньше затвора, рядом с ним.
3. Затвор физически на одном месте при любом повороте (нативный паттерн камеры).
4. Диалог (а не дропдаун) со всеми доступными настройками камеры.
5. Пресеты без «2»; ползунок+значение по ширине ряда пресетов.

### 3.2 Жёсткие ограничения

- **Flavor:** standard, lite, photos, legacy. Камера-захват в общем коде `src/main`, во всех вариантах. В photos нет видеозахвата.
- **API level:** совместимо с minSdk 23 (legacy) и 26 (остальные). Набор доступных настроек определяется устройством и Camera2/CameraX, а не уровнем API; обработка ориентации - стандартными средствами без повышения minSdk.
- **Wear OS:** не затрагивается.
- **Производительность:** поворот иконок не должен пересоздавать сессию камеры; диалог настроек читает возможности без блокировки UI.
- **Совместимость данных:** новые настройки камеры и выбор получателя - UI/preferences-состояние, без изменения схемы хранения; список получателей берётся из существующих настроек.
- **Локализация:** EN/RU/UK обязательны для всех новых строк (подпись назначения, «Отправить в..», заголовки и подписи настроек камеры).
- **Доступность:** контролы при повороте сохраняют фокусируемость и зоны нажатия не меньше 48dp; диалог настроек навигируется с D-pad/клавиатуры; различимость не только цветом.
- **Коммуникация:** все пользовательские строки (подпись, «Отправить в..», настройки, сообщения о недоступности) - по `docs/COMMUNICATION_POLICY.md`, тон-чеклист обязателен перед интеграцией.

### 3.3 Owner inputs (Approval gate)

- **Flavor scope:** все четыре варианта (standard / lite / photos / legacy). Камера-захват не флейвор-специфична, лежит в `src/main`; все четыре пункта применимы везде (в photos «Отправить в..» относится к фото, видео нет).
- **Localization:** EN/RU/UK для всех новых строк, обязательно.
- **UI placement contract:** подпись назначения - мелким шрифтом у кнопки выхода; «Отправить в..» - кнопка меньше затвора, рядом с ним; кнопка «три точки» - в верхнем баре среди контролов; затвор и контролы остаются на фиксированных физических позициях, поворачиваются только иконки/подписи. Точные позиции при повороте финализируются через `/ui-clarify` или в `/spec-tech`.
- **Accessibility:** фокус с D-pad/клавиатуры, зоны нажатия не меньше 48dp, не-цветовое отличие.
- **Communication policy:** строки - по политике тона.
- **Validation level:** компиляция плюс проверка на реальном устройстве (AVD недостаточен для камеры, как в S0545). Матрица: видна подпись назначения; «Отправить в..» открывает список получателей и отдаёт снятое; при повороте затвор физически на месте, иконки повёрнуты, нет наложений и заходов под системную панель; диалог настроек показывает только реально доступные настройки и применяет их; пресеты без «2», ширина ползунка = ряду кнопок.

## 4. Контекст текущей архитектуры

Встроенный CameraX-хост на уровне экрана делегирует решения менеджерам-помощникам: один владеет сессией CameraX (привязка, зум, вспышка, фокус, ночной режим, цифровой кроп), другой - решениями захвата и состоянием, третий снимает возможности линзы в неизменяемый снимок, UI рендерит контролы из снимка. Сейчас экран реагирует на поворот пересозданием и сменой раскладки (portrait/landscape), отчего контролы переезжают, наезжают и заходят под системную панель. Список получателей «отправить в» и определение ресурса назначения уже существуют в других частях приложения (доменные сценарии построения списка получателей и отправки), но в камере не задействованы. Глубокие настройки камеры, которые отдаёт устройство, в UI не вынесены.

Решить задачи из §1 в текущем виде нельзя: каркас экрана завязан на перекомпоновку при повороте; подпись назначения и «отправить в» в камере отсутствуют; нет роли, читающей и применяющей доступные настройки устройства, и нет диалога для них.

## 5. Предлагаемый подход

Дорабатываем каркас экрана камеры поверх существующего CameraX-хоста: фиксируем ориентацию и вращаем только контролы; добавляем подпись назначения, кнопку «Отправить в..» (переиспользуя существующий механизм получателей) и диалог настроек, наполняемый реально доступными возможностями устройства. Конвейер захвата/сохранения не меняется.

### 5.1 Основные столпы / модули

**A. Фиксированная ориентация с поворотом контролов.**

- Экран камеры не перекомпоновывается при повороте: позиции контролов (в первую очередь кнопки спуска) физически неизменны.
- При повороте устройства поворачиваются только иконки и подписи контролов, чтобы оставаться читаемыми; превью заполняет экран, снятое сохраняется в правильной ориентации.
- Это убирает текущие альбомные дефекты - наложение миниатюры/паузы на верхний ряд и заход контролов/ползунка под системную панель.

**B. Подпись ресурса назначения.**

- Мелким шрифтом рядом с кнопкой выхода показывается наименование ресурса, куда сохранится снимок.

**C. Кнопка «Отправить в..».**

- Рядом с затвором - кнопка чуть меньше; открывает список получателей.
- Список получателей задаётся в настройках и берётся из существующего механизма «отправить в» (того же, что в плеере), а не нового.

**D. Диалог настроек камеры.**

- Контрол «три точки» открывает диалоговое окно (не дропдаун) со всеми настройками камеры, которые реально доступны на устройстве.
- Состав диалога определяется возможностями устройства (Camera2/CameraX), а не фиксированным списком; недоступное не показывается.

**E. Полировка пресетов зума.**

- Из набора кратностей исключается «2».
- Ширина ползунка зума вместе с прижатым справа текущим значением равна ширине ряда кнопок-пресетов.

### 5.2 Потоки данных и событий

- Датчик ориентации устройства -> поворот иконок/подписей контролов (без пересоздания сессии).
- Текущий ресурс назначения -> подпись у кнопки выхода.
- «Отправить в..» -> существующий сценарий списка получателей (из настроек) -> отправка снятого.
- «Три точки» -> чтение доступных возможностей устройства -> диалог с тумблерами/выборами -> применение к сессии камеры.

### 5.3 Точки расширяемости

- Диалог настроек - список, наполняемый доступными возможностями устройства; новые настройки добавляются как новые пункты без переписывания каркаса.
- «Отправить в..» переиспользует существующий механизм получателей; источник списка - настройки.
- Поворот контролов применяется единообразно ко всем элементам оверлея.
- Если какие-то настройки потребуют низкоуровневого доступа к камере, он вводится на уровне роли «камера-сессия»; конкретная проводка - в `/spec-tech`.

## 6. Открытые вопросы / Research items

1. **Состав диалога настроек камеры**
   - **Вопрос:** какие настройки камеры реально доступны через CameraX/Camera2 на типичных устройствах и стоит вынести в диалог?
   - **Решение владельца (2026-06-28):** полный про-режим - таймер автоспуска, сетка кадрирования, соотношение сторон, разрешение фото/видео, экспокоррекция, плюс баланс белого, ISO, выдержка, HDR там, где устройство отдаёт; недоступное скрывается.
   - **Нужно выяснить (в `/spec-tech`):** точный перечень того, что отдаёт публичный API и применимо к текущему конвейеру; что UI-настройка (таймер, сетка), а что сенсорная (ISO, выдержка через Camera2Interop, баланс белого, HDR).
   - **Статус:** Resolved

2. **Механизм «Отправить в..»**
   - **Вопрос:** как переиспользовать существующий «отправить в» (список получателей из настроек) из камеры для только что снятого файла?
   - **Решение (ресёрч):** в проекте уже есть доменный сценарий построения списка получателей; переиспользовать его и передать ему снятый файл, список задаётся в настройках. Точную проводку детализирует `/spec-tech`.
   - **Статус:** Resolved

3. **Подход к фиксированной ориентации**
   - **Вопрос:** как зафиксировать ориентацию экрана камеры и при этом корректно вращать иконки и сохранять правильную ориентацию снимка?
   - **Решение (ресёрч):** зафиксировать ориентацию активити камеры; слушателем поворота устройства вращать иконки/подписи контролов; ориентацию захвата задавать через CameraX targetRotation по датчику - без пересоздания сессии и без отдельной landscape-раскладки. Детали - в `/spec-tech`.
   - **Статус:** Resolved

## 9. Архитектурные решения (ADR)

**ADR-1: Фиксированная ориентация экрана камеры с поворотом только иконок.**

- **Решение:** не перекомпоновывать камеру при повороте; контролы физически неподвижны, поворачиваются лишь иконки/подписи; ориентация захвата задаётся через targetRotation.
- **Альтернативы:** отдельные portrait/landscape раскладки (текущее - даёт переезд, наложения, заход под панель); полностью свободный поворот layout.
- **Почему:** совпадает с ожиданием владельца и нативным паттерном камеры; устраняет альбомные дефекты разом.

**ADR-2: Диалог настроек наполняется реальными возможностями устройства.**

- **Решение:** состав диалога - динамический, по тому, что отдаёт устройство; недоступное скрыто.
- **Альтернативы:** фиксированный список настроек (часть мертва на многих устройствах).
- **Почему:** настройки камеры сильно разнятся; показываем только применимое.

**ADR-3: «Отправить в..» переиспользует существующий механизм получателей.**

- **Решение:** список получателей и отправка - через существующий доменный сценарий, список из настроек.
- **Альтернативы:** свой список/отправка в камере (дублирование).
- **Почему:** единый UX и одна точка правды для получателей.

## 11. Критерии готовности (strategic-level)

1. У кнопки выхода видно наименование ресурса назначения.
2. Кнопка «Отправить в..» рядом с затвором открывает список получателей из настроек и отдаёт только что снятое.
3. При любом повороте телефона кнопка спуска и контролы физически остаются на месте; иконки повёрнуты и читаемы; нет наложений контролов и заходов под системную панель.
4. Кнопка «три точки» открывает диалог со всеми реально доступными на устройстве настройками камеры, и они применяются.
5. Пресеты зума не содержат «2»; ширина ползунка зума с прижатым справа значением равна ширине ряда кнопок-пресетов.
6. Поведение подтверждено на реальном устройстве (AVD недостаточен для камеры).
