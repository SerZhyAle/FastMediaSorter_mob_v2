## 0. Захваченный материал (inbox)

**Захвачено:** 2026-08-08

**Текст:**

android.permission.BLUETOOTH is declared nowhere in the app, but on API 30 and below reading BluetoothAdapter.isEnabled() and getBondedDevices() requires it. src/networkMonitor/AndroidManifest.xml declares BLUETOOTH_ADMIN with maxSdkVersion=30 (for the S1441 toggle path) and BLUETOOTH_CONNECT with minSdkVersion=31, with nothing covering adapter reads on API 26-30. Consequence: on Android 8.0-11 the Network Monitor Bluetooth section reports NoPermission("android.permission.BLUETOOTH") forever, and a UI that offers to request it would request a permission the manifest never declares, so the request silently fails. Found while implementing S1433 step 02.4 (BluetoothSnapshotDataSource); the data source itself degrades safely and needs no change. Deciding whether to declare <uses-permission android:name="android.permission.BLUETOOTH" android:maxSdkVersion="30" /> needs its own research: it changes the store permission surface, it must not break PermissionRegistryManifestParityTest (S1442/S1454), and confirming the runtime behaviour needs an API 26-30 device or emulator, which was not attached. Modern compileSdk 36 stubs cannot answer it - they only carry the BLUETOOTH_CONNECT annotation, so Android lint is blind to the older requirement.

**Захвачено во время:** S1433

---

## 1. Проблема

На Android 8.0-11 раздел Bluetooth в Мониторе сети всегда пуст: он показывает «нет разрешения» и никогда не показывает состояние адаптера. Ниже API 31 чтение адаптера требует `android.permission.BLUETOOTH`, а этого разрешения не объявляет ни один манифест приложения, поэтому проверка гранта всегда отвечает «отказано». Ни один экран не может это починить: разрешение установочное, у него нет диалога запроса, а попытка запросить необъявленное разрешение молча ничем не заканчивается. Область - манифест источника `networkMonitor` и реестр разрешений.

---

## 2. Цели

1. На Android 8.0-11 раздел Bluetooth Монитора сети показывает состояние адаптера и число сопряжённых устройств так же, как на Android 12+.
2. Приложение объявляет ровно то, что ему нужно, и только там, где живёт функция: разрешение появляется в тех же сборках, что и сам Монитор, и исчезает на API 31+, где его место занимает `BLUETOOTH_CONNECT`.
3. Гейт паритета манифеста и реестра остаётся зелёным и продолжает объяснять, почему у этого разрешения нет строки в реестре.

**Non-goals:**

- Не вводится запрос разрешения в рантайме: ниже API 31 `BLUETOOTH` выдаётся при установке, запрашивать его нечем и не у кого.
- Не расширяется область Bluetooth-функциональности: обнаружение устройств, BLE-сканирование и имена сопряжённых устройств остаются вне объёма (артефакты 02/03 исследования S1433).
- Не трогается путь переключения радио (S1441) и его `BLUETOOTH_ADMIN`.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Не увеличивать список разрешений на витрине магазина сверх необходимого - объявление должно быть закрыто верхней границей API.

### 3.2 Жёсткие ограничения

- **Flavor:** `standard` и `noLegal` - единственные, кто монтирует `src/networkMonitor`. Остальные флейворы не должны получить объявление вообще, иначе гейт паритета уронит их сборку.
- **API level:** объявление действует на API 26-30 (`maxSdkVersion="30"`); на API 31+ действует уже объявленный `BLUETOOTH_CONNECT`.
- **Wear OS:** не затрагивается.
- **Производительность:** без изменений - читается тот же адаптер, что и сейчас.
- **Совместимость данных:** нет хранимых данных, миграции нет.
- **Локализация:** новых пользовательских строк нет; если появится строка реестра - EN/RU/UK обязательно.
- **Доступность:** визуальных изменений нет.

### 3.3 Owner inputs (Approval gate)

- **Data compatibility:** хранимых данных нет.
- **UI placement contract:** новых элементов интерфейса нет - существующий раздел Bluetooth перестаёт быть пустым на старых устройствах.
- **Validation level:** сборка `standard debug` + `.\a.ps1 fu` (гейт паритета) + проверка на эмуляторе API 26-30, где раздел должен показывать состояние адаптера.
- **Store surface:** на устройствах API ≤ 30 в списке разрешений витрины появляется Bluetooth; на API 31+ ничего не меняется. Охват (страны, минимальная версия, устройства) не сужается - канон-инвариант 2 не затронут.
- **Related tickets:** S1433 (Network Monitor - находка сделана при реализации его шага 02.4), S1441 (путь переключения радио, объявивший BLUETOOTH_ADMIN), S1442 и S1454 (parity-тест манифеста и реестра разрешений)

## 4. Контекст текущей архитектуры

Разрешения объявляются по источникам: общий `src/main` попадает в каждый флейвор, а разрешение функции живёт в манифесте её собственного source set - именно поэтому `src/networkMonitor` объявляет `CHANGE_WIFI_STATE`, `BLUETOOTH_ADMIN` (до API 30), `NEARBY_WIFI_DEVICES` (с API 33) и `BLUETOOTH_CONNECT` (с API 31). Второй слой - реестр разрешений: он перечисляет то, о чём пользователь принимает решение, и механический тест сверяет реестр с итоговым манифестом в обе стороны. Установочные разрешения из реестра исключены поимённо, со списком причин.

Проблему §1 нельзя закрыть из кода: слой чтения уже выбирает правильное имя разрешения по уровню API и корректно деградирует, когда грант отсутствует. Отсутствует само объявление, а объявление - это манифест, а не класс.

---

## 5. Предлагаемый подход

Объявить недостающее установочное разрешение в манифесте той же функции, ограничив его верхней границей API, и зафиксировать в реестре причину, по которой у него нет строки.

### 5.1 Основные столпы / модули

1. **Объявление в манифесте функции.** Разрешение появляется рядом с уже существующей парой Bluetooth-объявлений, с верхней границей API 30, чтобы на новых устройствах его не было вовсе.
2. **Именованное исключение в реестре.** Установочное разрешение не даёт пользователю решения, поэтому оно попадает в список исключений с прозаической причиной - тем же способом, что и `CHANGE_WIFI_STATE`.
3. **Подтверждение гейтом.** Тест паритета манифеста и реестра остаётся зелёным на затронутых вариантах сборки.

### 5.2 Потоки данных и событий

Установка приложения -> система выдаёт установочное разрешение -> слой чтения Bluetooth видит грант -> раздел Монитора показывает состояние адаптера вместо «нет разрешения».

### 5.3 Точки расширяемости

Если когда-нибудь понадобятся имена сопряжённых устройств ниже API 31, точка расширения - тот же манифест функции, а решение о показе имён остаётся отдельным вопросом приватности, а не следствием этого тикета.

## 6. Открытые вопросы / Research items

1. **Нужна ли строка реестра или именованное исключение.**
   - **Вопрос:** пользователь принимает решение об этом разрешении?
   - **Статус:** Resolved (2026-08-10, установлено кодом) - исключение. Ниже API 31 `BLUETOOTH` относится к установочным: диалога запроса нет, системного экрана нет, отозвать его пользователь не может. Реестр по своему определению перечисляет решения пользователя, а список исключений уже содержит ровно этот случай для `CHANGE_WIFI_STATE`.

2. **Не уронит ли объявление тест паритета.**
   - **Вопрос:** тест исполняется под `@Config(sdk = [33])`; как он видит объявление с `maxSdkVersion="30"`?
   - **Статус:** Resolved (2026-08-10, установлено кодом) - не уронит, и обе стороны проверки объясняют почему. `requestedPermissions` сам отфильтрован по SDK, поэтому под sdk 33 объявление с верхней границей 30 в нём не появляется; строка реестра для него отсутствует по решению вопроса 1, а именованное исключение закрывает случай, если тест когда-нибудь погонят на более низком SDK.

3. **Подтверждение поведения на реальном API 26-30.**
   - **Вопрос:** достаточно ли одного объявления, чтобы чтение адаптера перестало отказывать?
   - **Статус:** Open - требует эмулятора API 26-30, которого нет в этой сессии. Заглушки compileSdk 36 ответить не могут: они несут только аннотацию `BLUETOOTH_CONNECT`, поэтому lint к старому требованию слеп. Это и есть содержание проверки на устройстве.

## 9. Архитектурные решения (ADR)

**ADR-1: Объявление в манифесте функции, а не в `src/main`.**

- **Решение:** `android.permission.BLUETOOTH` с `android:maxSdkVersion="30"` объявляется в `src/networkMonitor/AndroidManifest.xml`.
- **Альтернативы:** объявить в `src/main` рядом с прочими сетевыми разрешениями.
- **Почему:** `src/main` вливается в каждый флейвор, а разрешение без стоящей за ним функции - ровно то, на чём тест паритета валит релиз (S1442, S1454). Манифест функции - единственное место, где объявление и функция появляются и исчезают вместе.

**ADR-2: Именованное исключение вместо строки реестра.**

- **Решение:** разрешение попадает в `declaredWithoutRow` с причиной.
- **Альтернативы:** строка реестра с `maxSdk = 30` и гейтом сборки `SUPPORT_NETWORK_MONITOR`.
- **Почему:** реестр перечисляет решения пользователя, а установочное разрешение решением не является - строка предложила бы включить то, что уже включено и не выключается. Прецедент рядом: `CHANGE_WIFI_STATE` описан в исключениях этой же формулировкой.
