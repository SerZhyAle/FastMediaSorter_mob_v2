## 1. Проблема

Новый пользователь проходит экран приветствия по шагам: выбор профиля, набор функций, выдача разрешений, назначение плеером по умолчанию. Для пользователя, который доверяет приложению и хочет «всё и сразу», это лишние экраны и решения.

Нет способа за одно действие сконфигурировать приложение по максимуму: выбрать универсальный профиль, включить все функции, выдать все разрешения и стать обработчиком по умолчанию для всех типов медиа.

Эффект: дольше первый запуск, выше шанс пропустить полезную возможность, которую потом трудно найти в настройках. Область - онбординг (welcome / первый запуск).

---

## 2. Цели

1. На первой странице приветствия рядом с основной кнопкой «Далее» доступно второе действие - «Включить всё».
2. По этому действию профиль устройства устанавливается в универсальный (OTHER).
3. Все функции, доступные текущему варианту сборки, включаются разом.
4. Запрашиваются все применимые разрешения - системные диалоги показываются последовательно, один за другим.
5. Приложение становится обработчиком по умолчанию для всех поддерживаемых типов медиа - системные диалоги показываются последовательно.
6. После прохождения последовательности оставшиеся страницы приветствия пропускаются, приложение завершает онбординг полностью настроенным.

**Non-goals:**

- Не обходит и не подавляет ни один системный диалог разрешения или выбора по умолчанию - пользователь по-прежнему подтверждает каждый из них (требование платформы).
- Не вводит новые типы разрешений или новые медиа-возможности сверх уже существующих в проекте.
- Не меняет порядок и состав обычного пошагового прохождения для тех, кто не нажал «Включить всё».
- Не добавляет автоматическое включение для функций, недоступных текущему варианту сборки.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Нажатие сразу запускает последовательность - без промежуточного диалога подтверждения (решение владельца 2026-06-12).
2. Устойчивость к прерыванию: если пользователь свернул приложение посреди цепочки диалогов, при возврате последовательность продолжается с того же места, а не начинается заново и не теряется.
3. Если часть разрешений или назначений пользователь отклонил, онбординг всё равно завершается, а отклонённое не блокирует выход.

### 3.2 Жёсткие ограничения

- **Flavor:** затрагиваются все варианты - standard, lite, photos, legacy, noLegal. Шаг «плеер по умолчанию» выполняется только там, где эта возможность присутствует (на lite её нет); набор включаемых функций ограничивается возможностями конкретного варианта. Реализация следует `dev/FLAVOR_DEVELOPMENT_RULES.md`: различия выражаются через инъектируемые интерфейсы-возможности и flavor-исходники, без `BuildConfig.*`-проверок в `src/main`.
- **API level:** minSdk 26 (standard/lite/photos/noLegal), 23 (legacy). Состав разрешений и механизм назначения по умолчанию зависят от уровня Android (рантайм-разрешения с 23, гранулярные медиа-разрешения с 33, специальные разрешения с 30/31, роль приложения по умолчанию). Последовательность адаптируется к доступному на устройстве набору и деградирует корректно на старых уровнях.
- **Wear OS:** не затрагивается.
- **Производительность:** влияние незначительное; массовая запись настроек выполняется в области приложения, чтобы переживать закрытие экрана.
- **Совместимость данных:** новых сущностей и миграций нет; используются существующие хранилища настроек и профиля.
- **Локализация:** EN/RU/UK - обязательно для новой подписи кнопки и любого текста подтверждения.
- **Доступность:** кнопка фокусируемая, достижима с D-pad/TV и мышью, имеет content description, отличается не только цветом, соблюдает минимальный размер цели нажатия.

## 4. Контекст текущей архитектуры

Онбординг построен как страничный мастер: каждая страница (профиль, функции, разрешения, плеер по умолчанию) - отдельный блок со своей логикой включения, а активность-хост связывает их и хранит флаг завершения. Включение функций, выдача разрешений и назначение по умолчанию реализованы как независимые действия на своих страницах, со своим асинхронным поведением.

Для разрешений уже существует пошаговый сценарий «выдать все»: один системный диалог по завершении запускает следующий, состояние переживает поворот экрана. Для назначения плеером по умолчанию диалоги запускаются по принципу «выстрелил и забыл» - без обратного сигнала о завершении.

Сейчас нельзя одним действием связать «профиль + все функции + все разрешения + все назначения по умолчанию + пропуск страниц»: это пять разных операций на разных страницах, ни одна точка не оркеструет их как единую последовательность.

---

## 5. Предлагаемый подход

Ввести на первой странице вторичное действие «Включить всё» и единую роль-оркестратор, которая последовательно проводит приложение через полную настройку и завершает онбординг. Оркестрация выносится из активности-хоста в отдельную вспомогательную роль (логика в активности запрещена, хост близок к лимиту размера).

### 5.1 Основные столпы / модули

- **Точка входа на первой странице.** Вторичная кнопка рядом с «Далее»; её появление и подпись подчиняются тем же правилам доступности и локализации, что и остальной онбординг. Нажатие сразу передаёт управление оркестратору, без диалога подтверждения.
- **Применение профиля и функций.** Профиль устанавливается в универсальный (OTHER); включаются все функции, доступные текущему варианту сборки, и смежные опт-ин возможности (фоновое аудио, приём расшаренных файлов, плеер по умолчанию и подобные). Недоступные на данной установке возможности молча пропускаются. Запись настроек выполняется устойчиво к закрытию экрана.
- **Последовательность разрешений.** Переиспользуется существующий пошаговый сценарий «выдать все»: системные диалоги показываются по одному, состояние переживает поворот и сворачивание.
- **Последовательность назначения по умолчанию.** Приложение поочерёдно предлагается обработчиком по умолчанию для каждого поддерживаемого типа медиа; диалоги идут один за другим, последовательность управляется состоянием с возможностью продолжения после возврата в приложение.
- **Завершение.** После прохождения цепочки (с учётом отклонённых пользователем шагов) онбординг помечается завершённым и приложение переходит в основной режим, минуя оставшиеся страницы.

### 5.2 Потоки данных и событий

UI (кнопка первой страницы) → оркестратор онбординга → применение профиля и настроек (слой настроек/профиля, область приложения) → последовательный запрос разрешений (системные диалоги по одному) → последовательное назначение по умолчанию (системные диалоги по одному) → установка флага завершения → выход в основной режим.

Оркестратор - конечный автомат: фиксирует, какой шаг последовательности активен, чтобы корректно возобновляться после поворота экрана и возврата из системного диалога.

### 5.3 Точки расширяемости

- Список включаемых функций, набор запрашиваемых разрешений и перечень типов для назначения по умолчанию должны быть data-driven, чтобы добавление новой функции/разрешения/типа не требовало переписывать оркестратор.
- Применимость шагов определяется инъектируемыми флагами-возможностями варианта сборки; отсутствующий шаг автоматически выпадает из последовательности без ветвлений по `BuildConfig` в общем коде.
- Точка входа спроектирована так, чтобы при необходимости её можно было показать и в других местах онбординга, не дублируя логику оркестрации.

## 6. Открытые вопросы / Research items

1. **Сигнал завершения системного диалога «по умолчанию»**
   - **Вопрос:** как оркестратору надёжно понять, что пользователь закрыл диалог назначения по умолчанию для одного типа, чтобы открыть диалог для следующего? Текущий механизм запускает выбор без обратного результата.
   - **Варианты:** (a) запуск каждого диалога через механизм с обратным результатом; (b) последовательное открытие по возврату фокуса в приложение (onResume) с отслеживанием уже показанных типов; (c) переход на системный механизм назначения роли приложения по умолчанию там, где он доступен по уровню API.
   - **Решение:** вариант (a) - каждый диалог запускается через `ActivityResultLauncher`, обратный вызов «пользователь вернулся» двигает последовательность на следующий тип; состояние переживает поворот, как в уже существующем шаге разрешений. Роли приложения по умолчанию для медиа-`VIEW` в системе нет, поэтому (c) неприменим.
   - **Статус:** Resolved
   - **Артефакт:** `PLAN/S0409_welcome-enable-all/research/01__default-player-dialog-sequencing.md`

2. **Точный состав «включить все функции»**
   - **Вопрос:** какие именно опции считаются частью «всё» - только тумблеры страницы функций или также смежные опт-ин возможности (например, фоновое аудио, приём расшаренных файлов)?
   - **Решение:** «всё» = тумблеры страницы функций плюс смежные опт-ин возможности (фоновое аудио, приём расшаренных файлов, плеер по умолчанию и подобные опт-ины) (решение владельца 2026-06-12). Явный белый список конкретных полей утверждается в тактической спеке.
   - **Статус:** Resolved

3. **Взаимодействие профиля OTHER и массового включения**
   - **Вопрос:** профиль OTHER применяет свой пресет настроек; в каком порядке это сочетается с массовым включением, чтобы пресет не перекрыл только что включённые функции?
   - **Варианты:** применить пресет профиля первым и наложить включения поверх; либо пропустить пресет и опираться только на белый список из п.2.
   - **Решение:** сперва применяется профиль OTHER (и его пресет), затем поверх - массовое включение настроек как read-modify-write свежего снимка, поэтому белый список детерминированно побеждает по своим полям независимо от содержимого колонки OTHER. Порядок сериализован, чтобы избежать гонки записей.
   - **Статус:** Resolved
   - **Артефакт:** `PLAN/S0409_welcome-enable-all/research/03__profile-preset-ordering.md`

4. **Функции, недоступные на конкретной установке**
   - **Вопрос:** как вести себя с возможностями, скрытыми по причине источника установки или варианта сборки (например, распознавание текста на части сборок)?
   - **Решение:** недоступные возможности молча пропускаются, без визуального шума и отметок (решение владельца 2026-06-12).
   - **Статус:** Resolved

## 9. Архитектурные решения (ADR)

**ADR-1: Оркестрация как отдельная роль, а не логика в активности**

- **Решение:** последовательность «профиль → функции → разрешения → плеер по умолчанию → завершение» инкапсулируется в отдельной вспомогательной роли-оркестраторе, а не в активности-хосте.
- **Альтернативы:** разместить логику прямо в активности приветствия.
- **Почему:** логика в активности запрещена правилами проекта, хост близок к лимиту размера, последовательность требует собственного состояния и переиспользования существующего пошагового сценария разрешений.

**ADR-2: Переиспользовать существующий пошаговый сценарий разрешений**

- **Решение:** для блока разрешений опереться на уже работающий механизм последовательной выдачи, а не вводить новый.
- **Альтернативы:** написать отдельную цепочку запросов под «Включить всё».
- **Почему:** механизм уже переживает поворот и показывает диалоги по одному; дублирование увеличило бы риск расхождений в поведении.

## 11. Критерии готовности (strategic-level)

1. На первой странице приветствия рядом с «Далее» виден и фокусируем элемент «Включить всё».
2. После нажатия профиль устройства - универсальный (OTHER).
3. Все функции, доступные текущему варианту сборки, включены.
4. Системные диалоги разрешений показаны последовательно, по одному.
5. Системные диалоги назначения по умолчанию показаны последовательно для всех поддерживаемых типов.
6. По завершении цепочки оставшиеся страницы приветствия пропущены, приложение в основном режиме.
7. Отказ пользователя в части диалогов не мешает завершению онбординга.
8. Прерывание (сворачивание/поворот) посреди цепочки не теряет прогресс и не запускает её заново.
9. На варианте без плеера по умолчанию (lite) шаг назначения по умолчанию корректно отсутствует, остальная последовательность отрабатывает.
