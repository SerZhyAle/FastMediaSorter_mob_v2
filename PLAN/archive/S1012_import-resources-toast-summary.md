## 1. Проблема

При импорте companion-конфигурации (`.fmscfg`) по QR/штрих-коду или из файла пользователь не получает внятной сводки результата, а повторный импорт той же конфигурации создаёт дубликаты ресурсов.

- Дубли возникают потому, что путь импорта всегда вставляет: у таблицы ресурсов нет уникального индекса по идентичности, первичный ключ автогенерируется, поэтому совпадение по содержимому не срабатывает и каждый повторный импорт добавляет копии.
- Обратной связи почти нет: текущая строка успеха перечисляет имена и host, но не показывает счётчики и не различает добавлено/обновлено; при единственном ресурсе его имя теряется в общем перечислении.

Область: companion-импорт ресурсов (in-app: QR + выбор файла).

---

## 2. Цели

1. После импорта companion-конфигурации показать тост-сводку: сколько ресурсов добавлено и сколько обновлено.
2. Если импорт затронул ровно один ресурс - показать его имя.
3. Повторный импорт пересекающейся конфигурации обновляет совпадающие ресурсы вместо создания дублей (add-or-update по идентичности companion-ресурса).
4. Обновление совпадающего ресурса сохраняет пользовательские настройки и переписывает только поля, авторитетные для конфигурации.

**Non-goals:**

- Изменение поведения ручных add-флоу (SMB/SFTP/FTP/облако/локальные) - дедуп только для companion-импорта.
- Изменение схемы Room / миграция - не требуется (идентичность выводится из существующего поля пути).
- Дедуп для не-companion типов ресурсов.
- Перенос внешнего attachment-флоу (диалог результата) на тост - вне объёма, если владелец явно не расширит.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Сводка с раздельными счётчиками добавлено/обновлено; имя - для единственного затронутого ресурса.

### 3.2 Жёсткие ограничения

- **Flavor:** все, где доступен companion-импорт - дефектный/затрагиваемый код в `src/main`.
- **API level:** без API-специфики.
- **Wear OS:** не затрагивается.
- **Производительность:** сопоставление in-memory по уже загруженному списку ресурсов, без дополнительных запросов к БД.
- **Совместимость данных:** без миграции; обновление - селективный merge, а не перезапись всей строки (иначе клоббер пользовательских полей - задокументированный риск S1001).
- **Локализация:** EN/RU/UK обязательно (новый plural + строки сводки).
- **Доступность:** тост - вспомогательное уведомление, не единственный канал результата.

### 3.3 Owner inputs (Approval gate)

- **Related tickets:** S1001 (клоббер-риск `updateResource`), S1006 (altAccessPaths), S1014 (accessNote), S1016 (read-only policy). Эталон: `SzaResourcesImporter` (импортер `.fmsr`) - match-by-path + счётчики imported/updated/skipped.
- **UI:** тост во in-app Add-Resource флоу (QR + файл); точка сборки текста - companion-координатор, рендер - существующий тост активности.
- **Данные:** add-or-update по идентичности companion-ресурса; merge сохраняет пользовательские поля.
- **Merge/счётчики (решено 2026-07-18):** политика merge - сплит по образцу `SzaResourcesImporter` (корзины полей - §6 п.1-2); «обновлено» - diff-based (§6 п.4); ключ - host+virtualPath, порт игнорируется, хвостовой слэш срезан, регистрозависимо (§6 п.3); «единственный -> имя» при added+updated == 1 (§6 п.5); внешний attachment-флоу - вне объёма (§6 п.6).

## 4. Контекст текущей архитектуры

Оба in-app входа (QR-скан и выбор файла через SAF) сходятся в общий companion-use-case, результат отдаётся через companion-координатор как событие-сообщение и рендерится существующим тостом активности добавления ресурса. Третий вход - внешний attachment (`.fmscfg` из шаринга) - обрабатывается отдельной активностью и показывает результат диалогом, а не тостом.

companion-ресурс SFTP хранит идентичность в едином составном пути вида `sftp://host[:port]/virtualPath`; отдельных полей host/virtualPath в модели и в Room-сущности нет, поэтому равенство пути среди SFTP-ресурсов - верная реализация ключа host+virtualPath из решения владельца. Путь add-or-update уже загружает полный список существующих ресурсов, так что сопоставление возможно в памяти без нового DAO-запроса. Обновление ресурса делается полнострочным `@Update`: наивная передача свежепостроенного импортного ресурса перезапишет пользовательские поля.

---

## 5. Предлагаемый подход

Ввести в use-case добавления ресурсов opt-in путь add-or-update (новый метод либо параметр со значением по умолчанию, по образцу существующего `addToTop`), вызываемый только из companion-импорта - прочие вызовы `addMultiple` не меняются. Ключ сопоставления - равенство первичного пути в пределах одного типа ресурса (для SFTP - host+virtualPath) с нормализацией: порт игнорируется, хвостовой слэш virtualPath срезается, сравнение регистрозависимое. При совпадении строить merged-копию существующего ресурса, переписывая только конфиг-авторитетные поля и сохраняя id и пользовательские/рантайм-поля. Расширить агрегат результата счётчиком обновлённых (аддитивно; инкремент только при реальном изменении конфиг-авторитетного поля), прокинуть добавлено/обновлено и имена в результат импорта, перестать отбрасывать этот результат. Сводку собирать в companion-координаторе, рендер - существующий тост. Строки - переиспользовать имеющийся plural добавленных, добавить plural обновлённых, объединяющую строку и именные варианты (EN/RU/UK) через `getQuantityString`.

### 5.1 Основные столпы / модули

- Use-case добавления ресурсов - opt-in add-or-update + селективный merge.
- companion-use-case и его результат - счётчики добавлено/обновлено + имена.
- companion-координатор - сборка текста сводки.
- Строковые ресурсы - plural обновлённых + объединяющая/именные строки.

### 5.2 Потоки данных и событий

- QR/файл -> companion-use-case -> add-or-update (match by path) -> результат (добавлено/обновлено) -> результат импорта -> событие-сообщение -> тост.

### 5.3 Точки расширяемости

- opt-in add-or-update переиспользуем будущими импортерами.
- Политика merge - единая с эталонным импортером `.fmsr`.

## 6. Открытые вопросы / Research items

Требуют решения владельца перед реализацией (полный аудит: **Артефакт:** `PLAN/S1012_import-resources-toast-summary/research/01__import-flow-and-dedup-audit.md`):

1. Политика merge при обновлении: какие поля переписывать (кандидаты в конфиг-авторитетные: endpoints/путь, credentialsId, hostKeyFingerprint, supportedMediaTypes, allFiles/scanSubdirectories/showHidden/showSubfolders, read-only policy, altAccessPaths, accessNote) и какие сохранять (пользовательские/рантайм: iconId, sortMode, displayMode, lastViewedFile/lastScrollPosition, fileCount/lastBrowseDate/lastSyncDate, displayOrder, destinationColor/destinationOrder, comment/accessPin когда конфиг их не несёт). Дефолт по образцу `SzaResourcesImporter`; нужно подтверждение (риск потери пользовательских данных).
   - **Решено (2026-07-18):** сплит по образцу `SzaResourcesImporter`. Конфиг-авторитетные (переписываются): endpoint/путь, credentialsId, hostKeyFingerprint, supportedMediaTypes, scan-флаги (allFiles/scanSubdirectories/showHidden/showSubfolders), read-only policy, altAccessPaths, accessNote. Пользовательские/рантайм (сохраняются): iconId, sortMode, displayMode, lastViewedFile/lastScrollPosition, статистика (fileCount/lastBrowseDate/lastSyncDate), displayOrder, destination slot/color, comment/accessPin.
2. Переходы `isDestination`/`isReadOnly` и переслотирование destination при обновлении уже настроенного назначения: брать из конфига или сохранять пользовательский слот/цвет?
   - **Решено (2026-07-18):** isReadOnly - конфиг-авторитетное (берётся из конфига); destination slot/color сохраняются как пользовательское поле, переслотирования настроенного назначения при обновлении нет.
3. Точность ключа: игнорировать порт при сопоставлении (чистый host+virtualPath) или считать иной порт другим ресурсом (равенство пути)? Правило нормализации virtualPath (слэши/регистр)?
   - **Решено (2026-07-18):** порт игнорируется (чистый host+virtualPath); хвостовой слэш virtualPath срезается; сравнение регистрозависимое.
4. Семантика «обновлено»: считать совпадение обновлением всегда или только при реальном изменении полей?
   - **Решено (2026-07-18):** diff-based - «обновлено» только при реальном изменении конфиг-авторитетного поля (байт-идентичный ре-импорт .fmscfg = 0 обновлено).
5. Правило «единственный -> имя»: total == 1 суммарно по обеим корзинам (проще) или по одному на корзину?
   - **Решено (2026-07-18):** имя показывается при added+updated == 1 суммарно по обеим корзинам.
6. Внешний attachment-флоу (диалог результата): включать ту же сводку или ограничиться in-app тостом?
   - **Решено (2026-07-18):** вне объёма - внешний `.fmscfg` attachment-флоу сохраняет текущий диалог результата без изменений; фича покрывает только in-app QR/file-picker тост.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Полнострочный `@Update` затирает пользовательские поля | Высокая без митигации | Потеря иконки/сортировки/статистики/цвета назначения | Селективный merge поверх существующей строки, не перезапись |
| Ложное несовпадение из-за формы пути | Средняя | Дубль вместо обновления | Нормализация пути; тесты на слэши/порт |
| Регрессия других вызовов `addMultiple` | Низкая | Меняется поведение ручных add-флоу | opt-in путь, глобально ничего не меняем |

## 9. Архитектурные решения (ADR)

- opt-in add-or-update вместо глобального изменения `addMultiple` - минимизация регрессии (9 из 10 вызовов не должны менять поведение).
- Сопоставление in-memory по уже загруженному списку вместо нового DAO-запроса - без изменения схемы.
- Равенство составного пути как реализация ключа host+virtualPath - отдельных полей в модели нет.

## 10. Связи с другими спеками

- S1001 - контекст клоббер-риска полнострочного `updateResource`.
- S1006 (altAccessPaths), S1014 (accessNote), S1016 (read-only policy) - поля, авторитетные для конфигурации.
- `SzaResourcesImporter` (импортер `.fmsr`) - эталон match-by-path и счётчиков imported/updated/skipped.

---

## 11. Критерии готовности (strategic-level)

1. Повторный импорт пересекающейся конфигурации не создаёт дублей - совпадающие ресурсы обновляются.
2. Тост после импорта показывает число добавленных и обновлённых; при единственном затронутом - его имя.
3. Обновление сохраняет пользовательские поля согласно утверждённой политике merge.
4. Прочие add-флоу (SMB/SFTP/FTP/облако/локальные) не изменены.
5. Строки EN/RU/UK на месте; юнит-тесты покрывают add-or-update (добавление, обновление, смешанный кейс, сохранение пользовательских полей).

## Owner decisions (2026-07-14)

- Повторный импорт companion-`.fmscfg`, чьи корни пересекаются с уже импортированной конфигурацией, должен ДОБАВЛЯТЬ-ИЛИ-ОБНОВЛЯТЬ совпадающие ресурсы по ключу `host` + `virtualPath`, а тост различает число добавленных и обновлённых. Следствие: в `AddResourceUseCase.addMultiple` нужен путь дедупликации/обновления (сейчас он всегда вставляет).
