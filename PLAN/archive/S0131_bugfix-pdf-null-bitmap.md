# Стратегическая спецификация: S0131 — Null bitmap при уничтожении PlayerActivity через PDF-путь

**Ticket:** S0131
**Status:** BlockNeedUserTest
**Priority:** 90
**Date:** 2026-05-09
**Tier:** 2 — Easy
**Roadmap entry:** Ad-hoc — bugfix, обнаружен по логкату 2026-05-09
**Tactical spec:** `PLAN/S0131_bugfix-pdf-null-bitmap/` [INDEX.md](S0131_bugfix-pdf-null-bitmap/INDEX.md)

> **Scope:** STRATEGIC. Цели, ограничения, открытые вопросы. Без имён классов, путей, лимитов строк, миграций Room, модулей Hilt.

---

## 1. Проблема

При каждом уничтожении `PlayerActivity` через PDF-путь (открыт документ, viewer закрывается) код очистки инициирует ленивую инициализацию PDF-менеджера, который ни разу не использовался в текущей сессии просмотра. В момент этой инициализации связанные view уже находятся в состоянии teardown — bitmap в них равен `null`. Это приводит к предупреждению `BitmapDrawable created with null Bitmap` в логкате, воспроизводящемуся стабильно при каждом выходе из плеера документов (зафиксировано 5 вхождений за одну сессию).

Побочная проблема в том же плеере: native heap постоянно заполнен на ~93% (138/148 MB), что заставляет систему предзагрузки изображений пропускать все запросы на упреждающую загрузку (8 пропусков за ту же сессию). Порог блокировки захаржкожен без учёта реального профиля памяти устройства.

---

## 2. Цели

1. Предупреждение `BitmapDrawable created with null Bitmap` перестаёт появляться при нормальном закрытии плеера.
2. Ленивая инициализация PDF-менеджера не срабатывает во время teardown активности — менеджер не создаётся, если он не был нужен.
3. Система предзагрузки корректно оценивает доступность native heap и пропускает preload только когда памяти действительно не хватает под рабочий набор.
4. Количество ложных W-предупреждений в логкате от плеера сводится к нулю при штатном сценарии.

**Non-goals:**

- Изменение логики рендеринга PDF-страниц.
- Общий рефакторинг архитектуры менеджеров плеера.
- Увеличение лимита native heap на уровне системы.
- Оптимизация Glide bitmap pool — только корректировка порога принятия решения о preload.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Если проверка «менеджер ещё не создавался» тривиальна — добавить защитную проверку состояния активности перед любым обращением к ленивым ресурсам в пути teardown.
2. Порог native heap для preload сделать адаптивным к общему объёму native heap устройства, а не фиксированным значением в MB.

### 3.2 Жёсткие ограничения

- **Flavor:** все (standard, lite, photos, legacy) — плеер присутствует во всех.
- **API level:** без API-специфики, minSdk 23 / 26.
- **Wear OS:** не затрагивается.
- **Производительность:** исправление не должно добавлять заметных задержек при открытии PDF-документа или навигации по изображениям.
- **Совместимость данных:** изменения данных не предполагаются.
- **Локализация:** пользовательских строк нет — исправление технического характера. Локализация не требуется.
- **Доступность:** не затрагивается.

## 4. Контекст текущей архитектуры

Плеер использует ленивую инициализацию специализированных менеджеров (PDF, EPUB, видео, текст) — каждый создаётся при первом обращении к соответствующему свойству активности. Код очистки (`PlayerLifecycleManager`) вызывает методы на всех менеджерах без проверки того, были ли они когда-либо созданы. В результате обращение к ленивому свойству PDF-менеджера в деструкторном пути запускает его фабричную инициализацию уже после того, как EPUB-менеджер освободил разделяемые view-ресурсы — bitmap к этому моменту равен `null`.

Система предзагрузки изображений принимает решение о пропуске preload на основе абсолютного порога свободного native heap. На устройствах, где Glide держит крупный bitmap pool в native heap, этот порог постоянно нарушается, и preload полностью отключается. Реальный риск OOM не отражается этим числом, поскольку значимым является отношение свободного к общему объёму.

---

## 5. Предлагаемый подход

Устранить оба дефекта изолированными точечными правками без изменения общей архитектуры менеджеров.

### 5.1 Основные столпы / модули

**Защита от lazy-init в пути teardown**

- В коде очистки активности добавить проверку: обращаться к ленивому менеджеру только если он уже был инициализирован (backing nullable field != null).
- Логика cleanup не должна провоцировать создание объектов, которые сразу же окажутся в мусоре.

**Адаптивный порог native heap для preload**

- Заменить абсолютный порог (фиксированное число MB) на относительный: процент свободного native heap от общего.
- Разумный диапазон: блокировать preload, если свободно менее 10–15% native heap. На устройстве с 148 MB это ~15–22 MB, что примерно соответствует текущему порогу, но на устройствах с 256+ MB native heap даст больший рабочий буфер.

### 5.2 Потоки данных и событий

**Путь teardown (до исправления):**
`onDestroy → очистка EPUB-менеджера → обращение к ленивому PDF-менеджеру → фабричная инициализация → BitmapDrawable(null)`

**Путь teardown (после исправления):**
`onDestroy → очистка EPUB-менеджера → проверка: PDF-менеджер существует? → нет → пропуск очистки PDF → нет BitmapDrawable`

**Путь preload (после исправления):**
`preloadNextImageIfNeeded → получить nativeHeapFree и nativeHeapTotal → вычислить % → если < порога → пропуск с W-логом (только в DEBUG)`

### 5.3 Точки расширяемости

- Порог % native heap должен быть именованной константой, доступной для настройки без изменения бизнес-логики.
- Защита от lazy-init должна быть обобщённой: применима ко всем менеджерам плеера, не только PDF.

## 6. Открытые вопросы / Research items

1. **Полный список мест, где teardown обращается к ленивым менеджерам**
   - **Вопрос:** Затронут ли только PDF-менеджер, или EPUB/текст/видео-менеджеры тоже могут инициализироваться в пути teardown?
   - **Варианты:** проверить все обращения к ленивым свойствам внутри `PlayerLifecycleManager` и связанных cleanup-методов.
   - **Нужно выяснить:** grep по lazy-полям и местам их вызова в cleanup-путях.
   - **Статус:** Open

2. **Оптимальный относительный порог для preload**
   - **Вопрос:** Какой процент свободного native heap является безопасным минимумом для запуска preload?
   - **Варианты:** 10%, 15%, фиксированный минимум 20 MB — что больше.
   - **Нужно выяснить:** проверить на реальном устройстве, каков типичный объём native heap и сколько занимает Glide pool при полной загрузке.
   - **Статус:** Open

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|

## 9. Архитектурные решения (ADR)

**ADR-1: Точечные правки vs. рефакторинг cleanup-архитектуры**

- **Решение:** точечные проверки существования менеджера перед обращением к нему в cleanup-путях, без изменения общей схемы ленивой инициализации.
- **Альтернативы:** переход на явную инициализацию всех менеджеров в `onCreate` (устраняет проблему концептуально, но меняет поведение старта — lazy init введён намеренно для PERFORMANCE).
- **Почему:** lazy init плеера — сознательное архитектурное решение (`Timber.d("PERFORMANCE: Lazy initializing ...")`). Менять его вне этого bugfix нецелесообразно.

**ADR-2: Относительный порог vs. абсолютный**

- **Решение:** относительный порог с абсолютным минимумом (max(N%, 15 MB)).
- **Альтернативы:** только абсолютный (текущее состояние — 20 MB); только относительный (рискует на устройствах с маленьким native heap).
- **Почему:** 20 MB при 148 MB = 13.5% — разумно. При 512 MB native heap 20 MB = 3.9% — слишком агрессивно, preload будет блокироваться зря.

## 11. Критерии готовности (strategic-level)

1. Закрытие плеера после просмотра любого PDF-документа не генерирует `W BitmapDrawable` в логкате.
2. Закрытие плеера без открытия PDF не инициализирует PDF-менеджер (отсутствие `PERFORMANCE: Lazy initializing PdfViewerManager` в логкате).
3. Навигация по галерее изображений на устройстве с native heap < 200 MB вызывает preload хотя бы в части случаев (не все 8/8 блокируются за сессию).
4. LeakCanary не репортит новых утечек, связанных с `PlayerActivity`, после применения исправления.
5. Все четыре типа файлов (видео, изображение, PDF, EPUB) открываются и закрываются без новых W/E в логкате.
