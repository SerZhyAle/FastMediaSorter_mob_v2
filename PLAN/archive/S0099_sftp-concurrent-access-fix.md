## 1. Проблема

При одновременном воспроизведении файла с SFTP-источника и копировании/перемещении любого файла с того же SFTP-сервера оба процесса падают почти одновременно — воспроизведение прерывается, копирование завершается ошибкой. Пользователь видит технические сообщения об ошибке, не понимая причины. При этом сетевое соединение с сервером устойчивое: оба устройства находятся в одной локальной сети.

Причина: слой работы с SFTP использует единый транспортный объект (SSH-сессию) для воспроизведения и для файловых операций. Библиотека JSch не гарантирует потокобезопасность при параллельном использовании каналов одной сессии — сбой в одном канале каскадирует на всю сессию.

---

## 2. Цели

1. Воспроизведение (ExoPlayer) и файловые операции (копирование, перемещение) с одного SFTP-сервера работают **параллельно без взаимных сбоев**.
2. Ошибка в файловой операции не прерывает воспроизведение; ошибка в воспроизведении не прерывает файловую операцию.
3. При временной потере SFTP-канала во время копирования — автоматический повтор (до 3 попыток с нарастающей задержкой); пользователь видит прогресс, не ошибку.
4. Если после всех попыток копирование не удалось — понятное сообщение без технических деталей: «Не удалось загрузить файл с [сервер]. Проверьте соединение.»
5. В логах каждая SFTP-операция помечена типом потребителя (воспроизведение vs. файловая операция) — диагностика будущих логов упрощается.

**Non-goals:**

- Замена библиотеки JSch на SSHJ или Apache MINA SSHD — отдельная задача другого масштаба.
- Приостановка воспроизведения при старте копирования — нежелательна; цель именно параллельная работа.
- Принудительное ограничение пропускной способности между воспроизведением и копированием.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Если сервер отказывает в открытии второго SSH-соединения (лимит на стороне сервера) — показать пользователю понятное сообщение вместо технической ошибки, дать возможность попробовать ещё раз.
2. В будущем — возможность настроить количество параллельных SFTP-сессий для конкретного источника.

### 3.2 Жёсткие ограничения

- **Flavor:** все (standard, lite, photos, legacy) — SFTP-источники доступны во всех.
- **API level:** без API-специфики (SFTP — сетевой уровень).
- **Wear OS:** не затрагивается.
- **Производительность:** открытие дополнительного SSH-соединения допустимо; суммарный объём открытых соединений должен оставаться разумным (не более 2 сессий на SFTP-источник при стандартном сценарии).
- **Совместимость данных:** изменения не затрагивают Room-схему.
- **Локализация:** новые пользовательские сообщения об ошибках — EN/RU/UK обязательно.
- **Доступность:** не визуальная фича.

## 4. Контекст текущей архитектуры

Слой SFTP организован по паттерну connection-pool: один SSH-сеанс на каждый уникальный SFTP-адрес, поверх которого открываются каналы для конкретных операций. Воспроизведение и файловые операции разделены на уровне каналов (есть именованные пулы), но оба используют **один и тот же SSH-сеанс**. Поскольку JSch передаёт все пакеты через одно TCP-соединение, повреждение состояния одного канала (например, при сбое сети или ошибке сервера) нарушает порядок пакетов для всей сессии — и соседние каналы падают без собственной причины.

Текущий retry-механизм для файловых операций создаёт новый канал на той же сессии — что бессмысленно, если сессия уже в аварийном состоянии. Отдельная сессия для воспроизведения и файловых операций устраняет общую точку отказа.

## 5. Предлагаемый подход

### 5.1 Основные столпы

#### Столп 1 — Изоляция транспортных сессий по типу потребителя

Управление SFTP-сессиями разделить на два независимых «слота»:

- **Слот ВОСПРОИЗВЕДЕНИЕ** — выделенная SSH-сессия исключительно для потоков, читающих данные для ExoPlayer. Ни один другой потребитель не может использовать эту сессию или закрыть её.
- **Слот ФАЙЛОВЫЕ_ОПЕРАЦИИ** — отдельная SSH-сессия (или пул из 1–2 сессий) для копирования, перемещения, листинга директорий.

Оба слота соединяются с одним и тем же SFTP-сервером по независимым TCP-соединениям. Сбой в одном слоте не затрагивает другой — они не разделяют общего состояния на уровне JSch.

#### Столп 2 — Retry с полным пересозданием сессии

При ошибке канала в слоте ФАЙЛОВЫЕ_ОПЕРАЦИИ (`IOException`, `SftpException`):
1. Инвалидировать всю сессию слота FILE_OPS (не только канал).
2. Создать новую SSH-сессию и новый канал.
3. Повторить операцию — до 3 попыток с backoff 1 с / 2 с / 4 с.

Retry не затрагивает слот ВОСПРОИЗВЕДЕНИЕ и не создаёт каналов в нём.

#### Столп 3 — Понятные ошибки для пользователя

Если после всех попыток файловая операция не удалась:
- Переводить техническую причину в категорию пользовательского сообщения:
  - Разрыв соединения / превышение retry → «Не удалось загрузить файл с [адрес сервера]. Проверьте соединение и попробуйте снова.»
  - Лимит соединений на сервере (SSH отказал в открытии сессии) → «Сервер [адрес] ограничивает количество одновременных подключений. Остановите воспроизведение и повторите.»
  - Доступ запрещён → «Нет доступа к файлу. Проверьте права на SFTP-сервере.»

Пользователь никогда не видит внутренние имена классов, коды исключений или «Failed to download source for bridge copy».

#### Столп 4 — Маркировка операций в логах

Каждая SFTP-операция логируется с меткой типа потребителя: `[PLAYBACK]` или `[FILE_OPS]`, идентификатор сессии и идентификатор канала. Это позволяет однозначно разделить трафик воспроизведения и файловых операций при анализе логов.

### 5.2 Потоки данных и событий

```
Воспроизведение:
ExoPlayer → SFTP-источник данных → Слот ВОСПРОИЗВЕДЕНИЕ → SSH-сессия A → SFTP-сервер

Файловая операция:
FileOperation UseCase → Обработчик SFTP-операций → Слот ФАЙЛОВЫЕ_ОПЕРАЦИИ → SSH-сессия B → SFTP-сервер

При ошибке сессии B:
  → инвалидация сессии B
  → создание сессии B'
  → retry операции (до 3 раз)
  → если исчерпаны: перевод в user-friendly ошибку
```

### 5.3 Точки расширяемости

- Количество сессий на слот ФАЙЛОВЫЕ_ОПЕРАЦИИ — параметр конфигурации (сейчас 1, в будущем до N для параллельных скачиваний).
- Политика retry (количество попыток, backoff) вынесена в константы, легко изменяемые.
- Категоризация ошибок — единый маппер, расширяемый без изменения слоёв выше.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Сервер ограничивает MaxSessions = 1 (редкие embedded NAS) | Низкая | Слот FILE_OPS не откроется | Graceful fallback с понятным сообщением (Столп 3) |
| Открытие второй SSH-сессии занимает 2–3 с (handshake) | Средняя | Задержка начала копирования | Приемлемо; retry это маскирует |
| Сложность рефакторинга пула — регрессия в существующем поведении | Средняя | Сломается листинг директорий или воспроизведение | Фазированный подход: сначала изоляция, потом retry, изменения покрыты unit-тестами |
| JSch Session объект не thread-safe при конкурентном открытии каналов | Высокая (именно это и произошло) | Новая каскадная ошибка | Стратегия изоляции снимает риск полностью |

## 9. Архитектурные решения (ADR)

**ADR-1: Два отдельных SSH-сеанса вместо одного**

- **Решение:** Воспроизведение и файловые операции получают независимые SSH-сессии (отдельные TCP-соединения к тому же серверу).
- **Альтернативы:**
  - a) Пауза воспроизведения на время копирования — проще, но ухудшает UX.
  - b) Строгая сериализация всех SFTP-операций — исключает параллельность вовсе.
  - c) Переход на SSHJ (thread-safe transport) — правильно в долгосрочной перспективе, но объём изменений несоразмерен срочности.
- **Почему это решение:** SSH-протокол поддерживает несколько сессий от одного клиента к одному серверу. Разделение устраняет общую точку отказа без изменения публичного API слоёв выше и без замены библиотеки.

**ADR-2: Retry с полным пересозданием сессии, не только канала**

- **Решение:** При ошибке канала инвалидировать всю сессию FILE_OPS и создавать новую.
- **Альтернатива:** Retry на уровне канала (текущее поведение) — не работает, если сессия уже в аварийном состоянии.
- **Почему это решение:** JSch не предоставляет способа «починить» сессию без пересоздания — частичный retry на том же объекте гарантированно завершится той же ошибкой.

## 11. Критерии готовности (strategic-level)

1. Пользователь воспроизводит музыку с SFTP и одновременно копирует файл с того же сервера — оба процесса завершаются успешно.
2. При принудительном обрыве SFTP-канала во время копирования (например, кратковременный сбой сети) копирование восстанавливается автоматически и завершается успешно — без вмешательства пользователя.
3. Принудительный обрыв SFTP-канала копирования **не** прерывает воспроизведение.
4. Если копирование не удалось после всех попыток — пользователь видит понятное сообщение на своём языке (EN/RU/UK), без технических деталей.
5. В логах строки воспроизведения и строки файловых операций чётко различимы по метке потребителя.
