---

## 1. Проблема

На устройствах, где система объявлена как multi-window capable (Quest 3, Android XR, ChromeOS, Samsung DeX), приложение по дефолту включает настройку «Разрешить новые окна», но три из четырёх точек входа в multi-window остаются недостижимы для пользователя. Per-file пункт «Открыть в новом окне» живёт только внутри per-row overflow-меню, кнопка которого гейтится отдельной настройкой и не появляется у существующих пользователей; в портретном плеере команда уходит в overflow ⋮ из-за низкого приоритета планнера; контекстное меню по правому клику мыши на файле открывает не то меню и без нужных параметров. В сумме пользователь видит вход в multi-window только через одну кнопку в тулбаре Browse и думает, что фичи нет.

Параллельно есть смежная проблема разрыва между **install-time** и **runtime** capability detection. На Samsung-телефонах (например, S25 FE) детектор намеренно не использует DeX как сигнал, потому что Samsung-телефон объявляет DeX-способность через `PackageManager` даже когда сейчас находится в обычном телефонном режиме, и включать multi-window UI «навсегда» по этому признаку - неверно. Но когда пользователь реально переходит в DeX-режим (Activity получает desktop-контейнер), детектор по-прежнему молчит, и пользователь должен искать настройку «Разрешить новые окна» вручную - хотя именно в этот момент multi-window UX становится осмысленным.

---

## 2. Цели

1. На устройствах, где способность к multi-window определена детектором, пользователь обнаруживает per-file пункт «Открыть в новом окне» без ручной настройки UI.
2. В портретном плеере команда «Открыть в новом окне» показывается inline на панели команд (при достаточной ширине), а не только в overflow ⋮ - симметрично landscape.
3. Контекстное меню по правому клику мыши на строке файла открывает корректное per-file меню с тем же набором действий, что и тап по `⋮` строки.
4. На Samsung-телефонах с поддержкой DeX (и других устройствах с поддержкой desktop/freeform-режима) точки входа в multi-window появляются автоматически в момент перехода Activity в desktop-режим и скрываются обратно при возврате в обычный режим - без ручного включения настройки.

**Non-goals:**

- Не меняется глобальный дефолт настройки сворачивания файловых операций в ⋮ для не-multi-window устройств (телефоны, планшеты).
- Не вводится новая отдельная иконка «открыть в новом окне» на строке файла - вход остаётся через существующий ⋮.
- Не меняется приоритет команды плеера в общем правиле планнера для других сценариев.
- Не затрагивается логика самих переходов в новое окно (Intent-флаги, передача `windowId`, обработка повторного входа) - только видимость элементов управления.
- В обычном телефонном режиме на Samsung S25 FE (и аналогичных) поведение остаётся без изменений: настройка multi-window OFF по дефолту, чтобы не показывать действие, не применимое в одно-окнном UX.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Symmetric capability detection: один и тот же набор сигналов (форм-фактор устройства) включает оба связанных дефолта (multi-window + сворачивание операций в ⋮).
2. Симметрия portrait/landscape поведения плеера при включённой multi-window-настройке - команда видна напрямую, а не прячется по разной логике в зависимости от ориентации.
3. Существующий пользователь, у которого настройки уже сохранены в DataStore, не должен ничего «перенастраивать» в результате релиза - изменение дефолта применяется только к ключам без сохранённого значения.

### 3.2 Жёсткие ограничения

- **Flavor:** все варианты сборки (standard, lite, photos, legacy, noLegal, vr) - фичу определяет runtime-детектор устройства, а не build-time флаг. Реализация остаётся в `src/main/` без введения новых flavor-specific source-sets, поскольку capability-detection - именно runtime-понятие.
- **API level:** без специфичных требований; задействованы только Build API, PackageManager.hasSystemFeature и существующие проверки ChromeOS.
- **Wear OS:** не затрагивается - модуль `wear/` multi-window сценарий не поддерживает.
- **Производительность:** изменения не должны добавлять перерисовку панели команд плеера в горячем пути; capability-проверки уже выполняются один раз при старте процесса.
- **Совместимость данных:** изменяется только формула дефолтного значения двух булевых preference-ключей; форма хранения не меняется. Существующее сохранённое значение пользователя сохраняет приоритет.
- **Локализация:** без новых строк - все задействованные тексты уже существуют (EN/RU/UK).
- **Доступность:** новые видимые элементы управления (inline-кнопка плеера в портрете, корректное меню по правому клику) должны проходить тот же фокус-traversal, что и аналогичные команды на той же панели/меню.

### 3.3 Owner inputs (Approval gate)

- **Flavor scope:** все варианты сборки - реализация делит runtime-детектор устройства, не флейвор-флаги.
- **UI placement contract:** per-file пункт остаётся внутри per-row overflow-меню (визуальная иконка ⋮ строки); inline-кнопка плеера в портрете занимает то же место в порядке кнопок, что и в landscape; контекстное меню мыши анкорится на строке файла, не на тулбаре; видимость точек входа реагирует на смену multi-window-режима без перезапуска Activity.
- **Accessibility:** новая inline-кнопка плеера в портретной ориентации наследует focus order, content description и contentTint от существующей кнопки в landscape; кнопка ⋮ строки файла на VR/XR/ChromeOS/DeX получает существующий contentDescription без изменений.
- **Validation level:** ручное наблюдение на Quest 3 (постоянный multi-window) - все три точки входа видимы без правки настроек, открытие нового окна по каждой работает; ручное наблюдение на Samsung S25 FE - в обычном режиме точки входа скрыты, в DeX-режиме появляются автоматически, после возврата в телефонный режим - снова скрываются.

## 4. Контекст текущей архитектуры

Multi-window поведение в приложении сейчас разнесено по трём независимым гейтам: install-time детектор устройства устанавливает дефолт настройки «Разрешить новые окна»; самостоятельная настройка «Операции с файлами в меню ⋮» включает per-row overflow-кнопку и таким образом контролирует видимость одной из трёх точек входа; layout-планнер плеера на портрете распределяет команды по приоритету и в landscape игнорируется через прямой override. Эти три гейта были введены тремя независимыми тикетами (S0184, S0253, S0028) и не были согласованы между собой. В результате on-device capability detection и discoverability расходятся.

Кроме этого, сам детектор сейчас работает только **на этапе первой записи дефолта**: он опрашивает `PackageManager.hasSystemFeature` и информацию о производителе и больше никогда не пересчитывается. На устройствах с переменным форм-фактором (Samsung-телефон с DeX, складные, планшеты с подключаемой клавиатурой) реальное наличие multi-window UX определяется не наличием фичи в манифесте системы, а текущим режимом Activity - и эта runtime-информация в существующий детектор не поступает.

## 5. Предлагаемый подход

Свести три гейта к единому источнику истины - runtime-детектору capability устройства - и использовать его как fallback для двух связанных preference-дефолтов и как override для портретной видимости одной inline-кнопки плеера. Параллельно починить регрессию маршрутизации контекстного меню мыши, которая открывает не тот менеджер меню. Все изменения - локальные внутри уже существующих ролей, без введения новых компонентов.

### 5.1 Основные столпы / модули

1. **Capability detector - runtime-aware режим** - детектор перестаёт быть чистой функцией от `PackageManager` и `Build.MANUFACTURER` и принимает Activity-контекст (или эквивалентный source `Configuration` + `isInMultiWindowMode`). Возвращает «эффективное» текущее значение capability, а не «инсталляционный» вердикт. Для устройств с переменным форм-фактором (Samsung DeX, складные, freeform) capability становится `true` тогда и только тогда, когда Activity реально находится в desktop/freeform-режиме; форм-факторы с постоянным multi-window UX (Quest 3, XR, ChromeOS) продолжают давать `true` всегда.
2. **Capability detector - парные дефолты** - расширяется парным методом, симметричным существующему: возвращает дефолт для второй связанной настройки (сворачивание файловых операций в ⋮) по тем же сигналам устройства. Логика не дублируется - оба метода делят общий приватный helper.
3. **Settings repository (preference defaults)** - формула дефолтного значения настройки «сворачивание операций в ⋮» меняется с «fresh install ? ON : OFF» на «сохранённое значение ?: capability detector ?: fresh-install fallback». Существующее сохранённое значение продолжает иметь приоритет.
4. **Player command panel - portrait branch** - получает тот же прямой гейт видимости inline-кнопки «открыть в новом окне», что уже существует в landscape-ветке. Планнер по-прежнему распределяет команды по приоритету для overflow, но кнопка перестаёт зависеть от его решения.
5. **Browse adapter context menu routing** - точка входа «правый клик мыши на файле» начинает звать тот же per-file overflow менеджер, что и тап по ⋮ строки, с тем же набором коллбеков (включая `onOpenInNewWindow`).
6. **Runtime configuration change handling** - UI слои Browse и Player подписываются на изменение режима multi-window (`onMultiWindowModeChanged` / `onConfigurationChanged`) и пересчитывают видимость точек входа без перезапуска Activity. При входе в DeX/freeform - точки появляются; при выходе - скрываются обратно (если пользователь явно не включил настройку вручную).

### 5.2 Потоки данных и событий

Capability detector становится Activity-aware - вычисляет «эффективное» значение из двух источников: install-time сигналов системы (постоянные форм-факторы) и runtime-сигналов текущей Activity (`Configuration.uiMode & UI_MODE_TYPE_DESK`, `isInMultiWindowMode()`, признаки freeform-контейнера). Settings layer читает preference-ключи и подставляет соответствующий «эффективное» значение из детектора, если значения нет в DataStore. UI слой Browse читает оба preference-флага через ViewModel и решает видимость per-row ⋮ кнопки. UI слой плеера читает один preference-флаг и делает прямой `isVisible = flag` на inline-кнопке вне зависимости от ориентации. Контекстное событие мыши в Browse-адаптере маршрутизируется в per-file overflow менеджер с уже резолвленными коллбеками. При смене режима Activity (`onMultiWindowModeChanged` / `onConfigurationChanged` с изменением `UI_MODE_TYPE_*`) detector пересчитывает значение, и затронутые UI-компоненты обновляют видимость точек входа.

### 5.3 Точки расширяемости

- Capability detector - точка добавления новых парных дефолтов в будущем (например, для VR-специфичных UI-режимов): следующий тикет добавит метод по тому же шаблону, не модифицируя существующие.
- Single source of truth для capability-сигналов сохраняется в детекторе; добавление новой формы устройства (например, складные с режимом desktop) - изменение только в одном месте.
- Activity-aware режим детектора оформляется через отдельную сигнатуру, не ломающую существующих вызывающих: один метод с Activity-параметром возвращает эффективный capability, другой (старый) без Activity-параметра остаётся для install-time use cases. Параллельно может появиться lightweight observer-источник capability-флага для UI-подписки.

## 6. Открытые вопросы / Research items

1. **Поведение one-time hint Toast на multi-window устройствах**
   - **Вопрос:** Связанный preference-флаг `fileOpsOverflowMenuHintShown` сейчас подавляет одноразовый Toast «операции переехали в меню» только для fresh install. Если по новой логике существующий пользователь на Quest 3 внезапно получит дефолт «операции в ⋮», должен ли всплыть этот Toast при первом запуске после обновления, или его тоже подавить через детектор?
   - **Варианты:** (a) подавить Toast на multi-window устройствах симметрично с дефолтом операций; (b) показать Toast - это легитимное уведомление о смене UI; (c) пересмотреть сам Toast.
   - **Решение:** Вариант (a). На capability-устройстве дефолт операций в ⋮ становится ON автоматически, значит и подавление Toast делается симметрично - пользователь не должен видеть уведомление об «изменении», которого фактически не делал.
   - **Статус:** Resolved (вариант a).
2. **Источник runtime-сигнала desktop-режима для разных производителей**
   - **Вопрос:** Какой набор runtime-сигналов корректно определяет «активный multi-window UX» на разных устройствах? Базовый `Configuration.uiMode & UI_MODE_TYPE_DESK` работает на чистом Android и AOSP-варианте Samsung DeX, но на разных версиях One UI и на сторонних desktop-режимах (Samsung Knox Desktop, Motorola Ready For, Huawei EMUI Desktop) фактическая семантика может отличаться. `Activity.isInMultiWindowMode()` ловит split-screen на телефонах, но это не desktop-UX.
   - **Варианты:** (a) использовать только `UI_MODE_TYPE_DESK` - консервативно, но может пропустить специфические режимы; (b) комбинация `UI_MODE_TYPE_DESK || (isInMultiWindowMode && screen width > 600dp)` - шире покрывает, но возможны false positive; (c) ограничиться `UI_MODE_TYPE_DESK` плюс существующие install-time сигналы.
   - **Решение:** Вариант (a). Используется только `UI_MODE_TYPE_DESK` как primary runtime-сигнал; install-time сигналы (XR/VR/ChromeOS/Meta manufacturer) сохраняются параллельно как override-true. Натурное измерение на S25 FE откладывается до известного follow-up (зафиксировано в §7 как «medium risk»); если режим не обнаружится - заведётся отдельный тикет на расширение формулы.
   - **Статус:** Resolved (вариант a, известный риск задокументирован в §7).
3. **Persistance состояния через DeX-цикл**
   - **Вопрос:** Если пользователь вошёл в DeX, открыл второе окно, потом вышел из DeX обратно в телефон - что должно произойти с открытым вторым окном? Сохраняется (висит фоновым таском), закрывается автоматически, или это вне scope текущего тикета?
   - **Варианты:** (a) явный non-goal: жизненный цикл задач определяется системой, приложение не вмешивается; (b) автоматически закрыть лишние таски при выходе из DeX.
   - **Решение:** Вариант (a). Non-goal. Жизненный цикл задач передаётся системе - стандартное Android-поведение для multi-task приложений.
   - **Статус:** Resolved (вариант a, non-goal).

## 9. Архитектурные решения (ADR)

**ADR-1: Capability detector как единый источник дефолтов для связанных multi-window preference-ключей**

- **Решение:** Расширить существующий runtime capability detector новым парным методом для второй связанной настройки. Не вводить отдельный детектор и не размазывать сигналы устройства по разным компонентам.
- **Альтернативы:**
  - (a) Дублировать набор сигналов в settings layer как «if Meta || ChromeOS || XR feature then default true» - отвергнуто, разрыв single source of truth.
  - (b) Завести отдельный «UI mode» preference, который оба настройки читают - отвергнуто, излишний уровень абстракции для двух булевых ключей.
- **Почему:** Симметрия с существующей формулой `defaultAllowSeparateWindow`, минимум новых сущностей, общий приватный helper делит логику сигналов между парными методами.

**ADR-2: Прямой override видимости inline-кнопки в портрете плеера, минуя планнер**

- **Решение:** В портретной ветке панели команд плеера привязать видимость inline-кнопки «открыть в новом окне» напрямую к значению preference, симметрично landscape. Планнер по-прежнему собирает overflow-список и распределяет остальные команды.
- **Альтернативы:**
  - (a) Повысить приоритет команды до уровня FULLSCREEN/RANDOM - отвергнуто, может выдавить более частые команды на узких экранах.
  - (b) Ввести новый «pinned» флаг команды в планнере - отвергнуто, оверкилл для одной кнопки.
- **Почему:** Уже существующий контракт в landscape, симметрия поведения, минимум кода. Если место есть - кнопка inline, если нет - layout pass решит overflow естественным образом.

**ADR-3: Runtime-aware capability через Activity-параметр, без устаревания install-time API**

- **Решение:** Capability detector получает второй метод с Activity-параметром, который комбинирует install-time сигналы (`PackageManager`, `Build.MANUFACTURER`) с runtime-сигналом (`Configuration.uiMode & UI_MODE_TYPE_DESK`). Существующий install-time метод остаётся для seed-сценария (первая запись дефолта в DataStore). Для UI-слоя добавляется observer-подписка, которая пересчитывает значение при `onMultiWindowModeChanged` / `onConfigurationChanged`.
- **Альтернативы:**
  - (a) Полностью заменить install-time детектор на runtime-метод - отвергнуто, ломает существующий контракт `SettingsRepositoryImpl` (нет Activity в момент чтения preferences).
  - (b) Хранить runtime-флаг в DataStore и обновлять при каждом `onConfigurationChanged` - отвергнуто, persisting transient state, лишний I/O.
  - (c) Сделать видимость точек входа независимой от preference и читать только runtime-сигнал - отвергнуто, пользователь теряет возможность ручного override на телефоне без DeX.
- **Почему:** Сохраняется текущий контракт «preference = пользовательское решение, capability detector = дефолт для нового пользователя». Runtime-сигнал добавляется как override только когда forming-фактор объективно изменился. Install-time API сохраняется без breaking change.

## 11. Критерии готовности (strategic-level)

1. На capability-устройстве с постоянным multi-window UX (Quest 3 / Android XR / ChromeOS) при первом запуске после обновления и без ручной правки настроек пользователь видит per-file пункт «Открыть в новом окне» в overflow ⋮ на строке файла - и в списке, и в сетке, и в портрете, и в ландшафте.
2. На том же устройстве в плеере в портретной ориентации inline-кнопка «Открыть в новом окне» видна на панели команд (или попадает в overflow ⋮ плеера только при реально недостаточной ширине, на тех же правилах что landscape).
3. На любом устройстве (включая телефон) правый клик мыши на строке файла в Browse открывает то же per-file меню, что и тап по ⋮ строки, с активным пунктом «Открыть в новом окне», если настройка multi-window активна.
4. На Samsung-телефоне с DeX (S25 FE и аналогичных) в обычном телефонном режиме настройки multi-window и операций в ⋮ остаются OFF; при переходе Activity в DeX-режим точки входа в multi-window автоматически становятся видимыми, при возврате в телефонный режим - снова скрываются (если пользователь явно не включил настройку вручную).
5. На обычном телефоне / планшете без capability-сигналов и без активного desktop-режима пользовательский опыт первого запуска не меняется: настройки multi-window и операций в ⋮ остаются OFF (или сохраняют ранее сохранённое значение).
