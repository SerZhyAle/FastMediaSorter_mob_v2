# Стратегическая спецификация: S0157 — Доработка UX предложения авторизации при загрузке по ссылке

**Ticket:** S0157
**Status:** Verified
**Implemented date:** 2026-05-11
**Priority:** 65
**Date:** 2026-05-11
**Tier:** 3 — Moderate (ad-hoc)
**Roadmap entry:** Ad-hoc — запрос владельца 2026-05-11 по итогам работы с S0144/S0155
**Tactical plan:** `PLAN/S0157_link-auth-offer-and-dismissal-ux/INDEX.md`

> **Scope:** STRATEGIC. Цели, ограничения, открытые вопросы. Без имён классов, путей, лимитов строк, миграций Room, модулей Hilt.

---

## 1. Проблема

Диалог предложения авторизации при шаринге ссылки даёт пользователю лишь два варианта: «Добавить» и «Пропустить». «Пропустить» означает постоянный отказ — предложение больше не появится для этого хоста, и отозвать решение через UI невозможно (нет записи, которую можно удалить). Пользователь не может сказать «не сейчас, но спроси позже». Дополнительно: предложение авторизации ограничено встроенным справочником известных соцсетей — ссылки с прочих хостов не получают предложения вообще, что лишает пользователя возможности авторизоваться на частном или новом ресурсе. При сохранении авторизации поле «Имя аккаунта» необязательно, и пользователь нередко попадает в список с записями без узнаваемых имён или с автоматически извлечёнными техническими строками.

---

## 2. Цели

1. Диалог предложения авторизации имеет три варианта действия: «Добавить», «Пропустить сейчас» (временно), «Не спрашивать» (постоянно).
2. Временный пропуск не записывает никаких данных — при следующем шаринге с того же хоста предложение появится снова.
3. Постоянный отказ сохраняется как запись с пустыми куки и меткой «(отказ)» в том же экране «Авторизации», что и обычные сессии; удаление этой записи отзывает отказ.
4. Предложение авторизации появляется при шаринге ссылки с **любого** `http(s)`-хоста, для которого нет ни активной авторизации, ни записи постоянного отказа — не только для хостов из встроенного справочника.
5. При сохранении авторизации после WebView-входа поле «Имя аккаунта» всегда присутствует и требует явного подтверждения; «Отмена» в этом диалоге отменяет сохранение куки.
6. В списке авторизаций каждая запись показывает имя аккаунта, дату последнего успешного использования (или «ещё не использовалась») и метку «(отказ)» для записей постоянного отказа.

**Non-goals:**

- Не синхронизировать авторизации между устройствами.
- Не изменять механику WebView-входа (обработку `intent://`, CAPTCHA, 2FA, OAuth).
- Не трогать flavor'ы, где функция загрузки по ссылке отсутствует.
- Не вводить рейтинг доверия или автоматического распознавания «нужна ли авторизация» — решение за пользователем.
- Не переделывать логику определения имени аккаунта из куки — переиспользуется то, что есть (S0155), теперь как обязательный шаг, а не опциональный.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Текст кнопки «Не спрашивать» должен быть понятен без пояснений: пользователь должен сразу понять, что это постоянное решение и что его можно отозвать в настройках.
2. Запись постоянного отказа в списке «Авторизации» визуально отличается от обычной авторизации (другой значок, серый или приглушённый стиль, метка), но управляется теми же операциями («Удалить»).
3. Предложение авторизации для неизвестных хостов (не из справочника) не должно выглядеть как «ошибка» или настойчивое навязывание: нейтральное объяснение «для этого сайта можно добавить авторизацию, чтобы скачивать приватный контент».
4. WebView-вход для неизвестных хостов открывается прямо по URL пришедшей ссылки, а не по какому-либо каноническому адресу.
5. Список авторизаций упорядочивается по активности: сначала записи с недавним `lastUsedAt`, затем ещё не использованные, потом записи постоянного отказа.

### 3.2 Жёсткие ограничения

- **Flavor:** все варианты, где доступна функция загрузки по ссылке (та же область, что S0116/S0144). На сборках без неё изменений нет.
- **API level:** без API-специфики.
- **Wear OS:** не затрагивается.
- **Производительность:** диалог предложения не должен добавлять наблюдаемую задержку в поток шаринга при наличии активной авторизации или постоянного отказа — проверка должна быть синхронной по локально кэшированному состоянию.
- **Совместимость данных:** при первом запуске версии с S0157 все существующие авторизации и dismissal-записи удаляются одноразово (migration-flag). Функция авторизации при загрузке по ссылке ещё не объявлялась пользователям — данных на устройствах нет. После очистки флаг ставится; при последующих обновлениях очистки нет.
- **Локализация:** EN/RU/UK обязательны для всех новых строк: метки кнопок диалога, заголовок и подпись диалога для неизвестных хостов, строка «ещё не использовалась», метка «(отказ)» в списке.
- **Доступность:** три кнопки диалога читаются TalkBack; записи постоянного отказа отличаются от активных не только цветом (иконка или текстовая метка).
- **Тон сообщений:** все новые строки проходят чек-лист тона из `docs/COMMUNICATION_POLICY.md` (§6) — нейтрально, без алармовых формулировок, объяснение вместо команды.

## 4. Контекст текущей архитектуры

Проактивное предложение авторизации (S0144) срабатывает только при совпадении хоста с записью в встроенном справочнике известных ресурсов. «Отказ» хранится в отдельном хранилище dismissal-записей, не связанном с хранилищем сессий. Эти два хранилища никак не пересекаются в UI — экран «Авторизации» показывает только активные сессии, dismissal-записи скрыты. При сохранении авторизации через WebView (S0155) поле имени аккаунта присутствует, но в виде опционального диалога после сохранения, а не как обязательный шаг. Экран «Авторизации» показывает только имя аккаунта (S0155) — без даты последнего использования и без отдельного визуального различия между активными и потенциально устаревшими записями.

## 5. Предлагаемый подход

Объединить хранилища «dismissal» и «сессия» в единую модель записей авторизации с типом (active / dismissed). Расширить проактивную проверку при шаринге на все хосты. Сделать шаг именования аккаунта обязательным. Доработать список авторизаций.

### 5.1 Основные столпы / модули

#### A. Унификация хранилища: активные авторизации + постоянные отказы

- Запись авторизации получает поле типа: `active` (есть куки) или `dismissed` (пустые куки, постоянный отказ).
- Проверка «есть ли авторизация или постоянный отказ» — один запрос к одному хранилищу по ключу `(хост, accountId)`.
- Существующие dismissal-записи S0144 (per-хост, без accountId) мигрируют в `dismissed`-записи с системным accountId и без куки.
- Существующие сессии S0155 не меняются — их тип считается `active`.

#### B. Трёхвариантный диалог предложения авторизации

- Диалог получает три кнопки: «Добавить», «Пропустить сейчас», «Не спрашивать».
- «Добавить» — запускает WebView-вход.
- «Пропустить сейчас» — закрывает диалог, никаких записей не создаёт, конвейер продолжает без авторизации.
- «Не спрашивать» — создаёт `dismissed`-запись для `(хост, systemAccountId)`, конвейер продолжает без авторизации.
- Тот же трёхвариантный диалог используется и в реактивном пути «войти заново» (S0151), с переформулированными кнопками в контексте «обновить» vs «пропустить».

#### C. Предложение для всех хостов

- Проверка при шаринге больше не фильтрует по справочнику известных ресурсов.
- Если для хоста нет ни `active`-, ни `dismissed`-записи — показывается диалог (столп B).
- Для хостов из справочника поведение WebView-входа остаётся специальным (канонический URL, перехват `intent://`). Для прочих хостов — WebView открывается по URL пришедшей ссылки.
- Справочник известных ресурсов остаётся как вспомогательная таблица для правильного URL входа и перехвата редиректов — не как фильтр триггера.

#### D. Обязательное именование аккаунта при сохранении

- После успешного WebView-входа и извлечения куки показывается диалог с полем «Имя аккаунта», предзаполненным из механизма автоопределения (S0155) или дефолтной строкой по локали.
- Диалог не закрывается без явного действия: «Сохранить» (записывает куки + имя) или «Отмена» (куки не сохраняются, сессия не фиксируется).
- Это касается добавления авторизации из обоих путей: шаринг → диалог предложения → «Добавить», и экран «Авторизации» → «+».

#### E. Расширенный список авторизаций

- Каждая запись показывает: имя аккаунта, хост, дату последнего успешного использования (или строку «ещё не использовалась»), тип записи (активная или «(отказ)»).
- `dismissed`-записи визуально отличаются: приглушённый стиль + текстовая метка «(отказ)»; операция «Удалить» доступна так же, как для активных.
- Сортировка: активные с `lastUsedAt` DESC, активные без `lastUsedAt`, `dismissed`-записи в конце.

### 5.2 Потоки данных и событий

- Шаринг → определён хост → проверка единого хранилища по `(хост, *)` → нет записей → трёхвариантный диалог → («Добавить» → WebView → диалог имени → сохранение `active`) / («Пропустить сейчас» → конвейер без auth) / («Не спрашивать» → сохранение `dismissed` → конвейер без auth).
- Шаринг → `active`-запись найдена → конвейер с инжектированными куки (как сейчас).
- Шаринг → `dismissed`-запись найдена → конвейер без auth, диалог не появляется.
- Экран «Авторизации» → «+» → (выбор хоста из справочника / ручной ввод) → WebView → диалог имени → `active`-запись.
- Экран «Авторизации» → удаление `dismissed`-записи → запись удалена → при следующем шаринге с этого хоста диалог появится снова.
- Реактивный путь «войти заново» (S0151) → трёхвариантный диалог с переформулированным текстом → те же три ветки.

### 5.3 Точки расширяемости

- Тип записи (`active` / `dismissed`) является полем модели — в будущем возможны дополнительные типы (например, «ожидает обновления», «заблокирован ошибкой»).
- Справочник известных ресурсов остаётся расширяемым независимо от логики триггера предложения.
- Механизм автоопределения имени аккаунта из куки (S0155) переиспользуется без изменений.

## 6. Открытые вопросы / Research items

1. **Миграция существующих авторизаций и dismissal-записей**
   - **Вопрос:** как обращаться с записями старого формата (S0116/S0144/S0155) при обновлении до версии с S0157.
   - **Resolution (2026-05-11):** функция авторизации при загрузке по ссылке ещё не объявлялась пользователям как стабильная, реальных данных нет. При первом запуске новой версии **все** существующие записи авторизаций (`EncryptedCookieStore`) и dismissal-записей (S0144 `SharedPreferences`) удаляются полностью. Очистка — одноразовая: выполняется ровно один раз через migration-flag (булев ключ в `SharedPreferences`), который ставится после очистки. При следующих запусках флаг уже выставлен — очистки нет.
   - **Статус:** Resolved.

2. **Поведение трёхвариантного диалога при реактивном пути S0151**
   - **Вопрос:** в реактивном пути «войти заново» при `SocialPreviewOnly` (S0151) диалог адресован конкретному аккаунту (`@user`). Нужна ли `dismissed`-запись на уровне `(хост, accountId)` или per-хост?
   - **Resolution (2026-05-11):** поскольку при обновлении всё чисто (§6.1), проблема совместимости со старыми per-хост dismissal-записями снимается. Новые `dismissed`-записи хранятся per-`(хост, accountId)` — консистентно с моделью S0155. Если пользователь нажал «Не спрашивать» для аккаунта A на хосте H, для аккаунта B на том же хосте диалог появляется.
   - **Статус:** Resolved.

## 8. Влияние на пользователя (docs/FEATURES)

`docs/FEATURES.md` (+ `_RU`, `_UK`): при шаринге ссылки приложение теперь предлагает авторизоваться на любом сайте — не только на заранее известных площадках; предложение можно временно пропустить или навсегда отключить; постоянные отказы видны в настройках и отзываются удалением записи. При добавлении авторизации всегда запрашивается имя аккаунта. В списке авторизаций показана дата последнего использования.

## 9. Архитектурные решения (ADR)

**ADR-1: Постоянный отказ — запись того же типа, что сессия, с пустыми куки**

- **Решение:** `dismissed`-запись хранится в том же хранилище, что `active`-сессия; тип различается полем, а не отдельным хранилищем.
- **Альтернативы:** отдельная таблица dismissal-записей; флаг в отдельном `SharedPreferences`; отдельный экран «Блокировки».
- **Почему:** единая точка хранения упрощает проверку «надо ли предлагать авторизацию» — один запрос вместо двух; позволяет показывать `dismissed`-записи в том же UI, что активные, без дублирования логики экрана.

**ADR-2: «Пропустить сейчас» не создаёт записей**

- **Решение:** временный пропуск — это отсутствие действия, а не создание временной записи с TTL.
- **Альтернативы:** запись с TTL 1 ч / 24 ч; запись «skipped once» с числом пропусков.
- **Почему:** TTL-записи требуют очистки и приводят к неинтуитивному поведению (диалог вернулся «сам»); пользователь использует «Не спрашивать», если хочет тишины; «Пропустить сейчас» — для случаев «занят, потом разберусь».

**ADR-3: Проактивное предложение для всех хостов**

- **Решение:** убрать фильтр по справочнику известных ресурсов из логики триггера диалога; справочник остаётся для выбора URL входа и обработки редиректов.
- **Альтернативы:** ввести настройку «предлагать только для известных»; показывать предложение только при `SocialPreviewOnly`.
- **Почему:** справочник не успевает за ростом числа сервисов; пользователь сам решает, нужна ли авторизация, через «Не спрашивать».

**ADR-4: Обязательный диалог именования блокирует сохранение куки**

- **Решение:** «Отмена» в диалоге имени означает отмену всей операции сохранения.
- **Альтернативы:** дефолтное имя применяется автоматически без диалога; переименование откладывается на «потом» в настройках.
- **Почему:** список с неименованными записями ухудшает UX S0155 (выбор аккаунта перед скачиванием); принудительный момент именования — единственная надёжная точка, где пользователь понимает, что именно он сохраняет.

## 11. Критерии готовности (strategic-level)

1. При шаринге ссылки с любого `http(s)`-хоста, для которого нет ни активной авторизации, ни постоянного отказа, появляется диалог с тремя кнопками: «Добавить», «Пропустить сейчас», «Не спрашивать».
2. «Пропустить сейчас» закрывает диалог без записей; при следующем шаринге с того же хоста диалог появляется снова.
3. «Не спрашивать» создаёт запись постоянного отказа; диалог для этого хоста больше не появляется.
4. Запись постоянного отказа видна в разделе «Авторизации» настроек — отличается от активных записей меткой «(отказ)» и/или приглушённым стилем; операция «Удалить» доступна.
5. После удаления записи постоянного отказа диалог при следующем шаринге с того же хоста появляется снова.
6. При добавлении авторизации через WebView-вход (любым путём: из шаринга или из настроек) диалог «Имя аккаунта» появляется всегда и требует явного «Сохранить»; «Отмена» отменяет сохранение куки.
7. В списке авторизаций каждая запись показывает имя аккаунта и дату последнего использования (или «ещё не использовалась»).
8. Существующие dismissal-записи S0144 после обновления приложения отображаются в списке «Авторизации» как `dismissed`-записи и удаляемы пользователем без потери активных сессий.
9. Для хостов из встроенного справочника WebView-вход по-прежнему открывается на каноническом URL страницы входа и обрабатывает `intent://`-редиректы.
10. Все новые строки (метки кнопок, подписи в списке, строка «ещё не использовалась») присутствуют в EN/RU/UK.
