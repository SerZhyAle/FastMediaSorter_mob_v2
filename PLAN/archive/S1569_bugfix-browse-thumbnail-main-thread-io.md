## 0. Захваченный материал (inbox)

**Текст:**

Evidence from a real-device run (SM-G996U1, Android 15, standard debug v2.60.8082.309, 2026-08-11): returning from the camera to the "Camera Photos" browse screen produced 8 StrictMode android.os.strictmode.DiskReadViolation entries on the main thread, ~duration 25-68 ms each, all inside one frame. Distinct from S1480 (camera capture thumbnail) and S1502 (stream catalog thumbnails) - this is the file-browse list bind path. ## 1. Проблема / симптом

Возврат из экрана камеры в browse-ресурс "Camera Photos" (12 файлов) даёт 8 нарушений StrictMode `DiskReadViolation` в главном потоке за один кадр, длительностью 25-68 мс каждое. Устройство SM-G996U1, Android 15 (SDK 35), flavor standard, debug-сборка v2.60.8082.309.

Стеки указывают на два места в загрузчике миниатюр списка: проверку существования файла и построение запроса на загрузку изображения, оба вызываются из `onBindViewHolder` во время layout-прохода RecyclerView. На том же главном потоке впервые инициализируется Glide (регистрация connectivity-приёмника).

Наблюдалось на папке из 12 файлов - стоимость растёт вместе с размером папки.

Не дубликат: S1480 закрывает миниатюру после съёмки в камере, S1502 - миниатюры каталога стримов. Здесь путь привязки строки в списке файлов.

---

## 2. Корневая причина

Две дисковые операции стояли прямо на пути привязки строки списка, то есть выполнялись в главном потоке во время layout-прохода.

1. Перед загрузкой миниатюры загрузчик спрашивал у диска, существует ли файл. Для обычного пути это `File.exists()`, для SAF-документа в режиме списка - запрос существования через провайдер.
2. Выбирая, что отдать в Glide, загрузчик спрашивал у диска, читается ли файл, и только при отрицательном ответе брал content-URI строки. Этот же код продублирован в ветке изображений и в ветке видео.

Обе проверки были избыточны по результату. Каждая локальная ветка загрузки уже заканчивается `.error(generatedPlaceholder)`, поэтому отсутствующий или нечитаемый файл и так приводит к тому же самому плейсхолдеру - но решение об этом Glide принимает в своём потоке, а не в главном.

Инициализация Glide на том же кадре (регистрация приёмника связности) - следствие того, что первый вызов Glide в процессе пришёлся на привязку строки, а не отдельный дефект этих двух мест.

---

## 3. Исправление

Проверка существования удалена вместе со ставшей ненужной функцией: её единственный вызов был на этом пути, а визуальный результат обеспечивает уже существующий `.error`.

Выбор модели для Glide больше не спрашивает диск. Теперь он выражен двумя чистыми функциями: основная модель - content-URI, если строка его несёт, иначе путь к файлу; запасная - путь к файлу, если основной была ссылка. Запасная попытка отдаётся Glide как `.error`-запрос, поэтому прежнее поведение сохранено по смыслу: путь используется, когда он работает, - но проверяет это Glide вне главного потока. Обе ветки, изображения и видео, переведены на общие функции вместо двух копий условия.

**Ветки документов (2026-08-11, по результату device-теста).** Тот же пробник остался в `loadPdf` и
`loadEpub`: локальная ветка каждой из них спрашивала `File(file.path).exists()` и только потом отдавала файл
в Glide. Обе проверки сняты - запрос уходит в Glide сразу. Видимый результат не меняется: у EPUB ветка `else`
рисовала `showGeneratedPlaceholder`, у PDF - её же в списке и `createExtensionBitmap("PDF")` в сетке, а
`getPlaceholderExtension` для файла с расширением `.pdf` возвращает ровно `PDF`, то есть тот же самый битмап,
который уже стоит в `.error(generatedPlaceholder)`. Отличается только поток, на котором решение принимается.

## 4. Проверка

Повторить сценарий из §1 на устройстве с включённым StrictMode: открыть browse-ресурс с миниатюрами, вернуться в него из камеры, пролистать список.

- **До:** 8 записей `DiskReadViolation` в главном потоке за один кадр, 25-68 мс каждая, стеки указывают на проверку существования файла и на выбор модели загрузки, оба из `onBindViewHolder`.
- **После (ожидается):** ни одной записи `DiskReadViolation` со стеком, проходящим через загрузчик миниатюр списка.
- Миниатюры при этом должны отображаться как прежде, включая файлы, доступные только через content-URI, и отсутствующий файл должен показывать тот же плейсхолдер, что и раньше.
- Метка `S1569` в логе подтверждает, что путь привязки исполняется без проверки файла.

`loadPdf` вызывает `File(file.path).exists()` в главном потоке на том же пути привязки строки: `onBindViewHolder(MediaFileAdapter.kt:445)` -> `bind(:798)` -> `loadThumbnail(:851)` -> `load(AdapterThumbnailLoader.kt:186)` -> `loadPdf(AdapterThumbnailLoader.kt:425)`, 18 мс, зафиксировано в 18:09:38 на строке с PDF.

Исправление сняло пробник в общем пути и в ветках изображения и видео, но не в ветках документов.

### Инициализация Glide

Два нарушения по 155-156 мс в 18:01:16 приходят из `GlideAppModule.applyOptions` через первый в процессе `Glide.with()`, вызванный из `loadImage(AdapterThumbnailLoader.kt:594)`.

Это следствие, которое §2 уже вывела за рамки тикета: платит тот вызывающий, который первым коснулся Glide.

Однократно на процесс, при прокрутке не повторяется.

### Регрессионные ветки

- Миниатюры отображаются - PASS: реальное содержимое картинок в строках JPG и PNG, `ui.xml` показывает сгенерированный плейсхолдер расширения.
- Файл только через content-URI - НЕ ПРОВЕРЕНО: `contentUri` заполняет только `MediaStoreRepositoryImpl`, то есть ресурсы `virtual://`; в проверенном ресурсе-папке поле пустое, ветка не исполнялась.
- Удалённый файл показывает плейсхолдер - НЕ ПРОВЕРЕНО: нужен ни разу не привязанный файл, иначе Glide отдаёт его из кэша по сигнатуре `path_size`; попытка прервана перезапуском приложения из чужой сессии.
