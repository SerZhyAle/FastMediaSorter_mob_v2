## 1. Проблема

После свежей установки приложение не появляется в системном шер‑шите Android, пока пользователь руками не зайдёт в Настройки → Воспроизведение и не включит свич «Принимать общие файлы». Это скрытое требование: большинство пользователей не находят свич и считают, что фича не работает. На сценарии «поделиться картинкой/видео из галереи» приложение остаётся невидимым для ОС.

---

## 2. Цели

1. На свежеустановленном APK после первого открытия приложения (даже мгновенного) — приложение появляется в шер‑листе ОС для тех MIME‑типов, которые поддерживает текущий флавор.
2. Свич «Принимать общие файлы» в настройках по умолчанию ВКЛЮЧЁН (новый пользователь видит его уже активным).
3. Существующая возможность ручного отключения свича сохраняется и не оверрайдится автоматикой при последующих стартах.

**Non-goals:**

- Появление приложения в шер‑листе ДО первого запуска (это потребовало бы менять манифестные defaults, что усложняет совместимость с существующими установками и флаворами без рантайм‑фильтра).
- Изменение поведения для флавора `lite` — там SEND‑компоненты намеренно вырезаны на уровне манифеста.
- Изменение объёма поддерживаемых MIME‑типов или фильтров шеринга.
- Изменение поведения смежного свича «Использовать как основной плеер» (только синхронизация системных компонентов с DataStore — в рамках идемпотентного хука).

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Хук применения системных компонентов должен срабатывать на КАЖДОМ старте идемпотентно, без ручных «first‑run» флагов — это закрывает кейс переустановки/clear‑data, когда `PackageManager` забывает рантайм‑оверрайды.
2. Тот же хук попутно синхронизирует состояние ACTION_VIEW‑алиасов с сохранённым в DataStore значением «основной плеер» — это устраняет рассинхронизацию после переустановки.

### 3.2 Жёсткие ограничения

- **Flavor:** `standard`, `photos`, `legacy`. Флавор `lite` не затрагивается — у него SEND‑алиасы удалены через манифест‑оверлей, дефолт настройки в нём не имеет визуального эффекта.
- **API level:** без API‑специфики. Применение состояния системных компонентов работает на minSdk 23 и выше.
- **Wear OS:** не затрагивается.
- **Производительность:** стартовый хук должен быть лёгким, без блокировки главного потока; чтения настроек идут через существующий механизм DataStore.
- **Совместимость данных:** существующие пользователи, у которых свич явно сохранён как `false`, должны остаться с `false` — изменение дефолта применяется только когда ключ в DataStore отсутствует. Существующие пользователи с явно сохранённым `true` ничего не теряют.
- **Локализация:** EN/RU/UK — без новых строк (фича не вводит UI‑надписей; меняется только дефолт уже существующего свича). Если в `docs/FEATURES*.md` понадобится правка одной фразы про дефолт — обновить три зеркала.
- **Доступность:** не применимо (нет нового UI).

## 4. Контекст текущей архитектуры

Приём расшаренных файлов сейчас реализован через ACTION_SEND‑алиасы в манифесте, помеченные `enabled="false"`, и рантайм‑переключатель в составе настроек воспроизведения. Свич сохраняется в слое настроек (DataStore), а соответствующий менеджер компонентов через `PackageManager` включает/выключает только те алиасы, которые поддерживает текущий флавор. Сегодня единственная точка вызова менеджера — обработчик пользовательского переключения свича: если пользователь не зашёл в настройки, алиасы остаются в манифестном disabled‑состоянии вне зависимости от значения флага в DataStore.

---

## 5. Предлагаемый подход

Изменение состоит из двух смысловых слоёв:

1. Поднять дефолт настройки на уровне доменной модели и репозитория настроек: при отсутствии явно сохранённого значения возвращать `true` вместо `false`. Это сразу даёт ВКЛ‑позицию свича в UI у новых пользователей и не трогает явно сохранённые значения у существующих.
2. На старте процесса приложения добавить идемпотентный bootstrap‑шаг, который читает актуальные значения настроек («принимать общие файлы», «использовать как основной плеер») и приводит состояние системных компонентов в соответствие. После переустановки или очистки данных это автоматически восстанавливает регистрацию приложения в шер‑листе ОС без участия пользователя.

### 5.1 Основные столпы / модули

- **Слой доменной модели настроек:** дефолтное значение флага меняется с выключенного на включённое; миграция данных не требуется (DataStore возвращает дефолт при отсутствии ключа).
- **Слой application‑bootstrap:** новая обязанность — при инициализации процесса прочитать настройки и применить состояние системных компонентов. Не вводит новых пользовательских флоу, не блокирует UI, не вступает в конфликт с пользовательским переключением свича.
- **Менеджер системных компонентов:** изменений роли не требуется; продолжает быть единственной точкой записи состояния алиасов.

### 5.2 Потоки данных и событий

- Старт процесса → application‑bootstrap → чтение настроек → применение состояния SEND‑алиасов и ACTION_VIEW‑алиасов согласно сохранённым значениям и поддержке текущего флавора.
- Пользователь дёргает свич в настройках → существующий поток (UI → ViewModel → менеджер компонентов + сохранение в DataStore) — без изменений.
- Следующий запуск процесса → bootstrap снова применяет состояние согласно DataStore; никакого «авто‑возврата к ВКЛ» не происходит, если пользователь явно выключил.

### 5.3 Точки расширяемости

- Bootstrap‑шаг должен быть устроен так, чтобы будущие настройки‑оверрайды системных компонентов можно было добавить туда же без размножения точек инициализации.
- Логика «дефолт зависит от поддержки флавора» при необходимости размещается в одном месте — слое доменной модели настроек.

## 6. Открытые вопросы / Research items

1. **Поведение на флаворе `photos` / `legacy` при первом старте**
   - **Вопрос:** в `photos` нет аудио/видео, в `legacy` нет облака/документов — нужно убедиться, что bootstrap не включает SEND‑алиасы для неподдерживаемых типов.
   - **Варианты:** опираться на существующий рантайм‑фильтр менеджера компонентов; не вводить новой ветки логики.
   - **Нужно выяснить:** покрыто ли это уже текущим флавор‑фильтром (по факту — да, но проверить вручную при тактической проработке).
   - **Статус:** Resolved — фильтр уже работает в менеджере компонентов; bootstrap его не обходит.

2. **Совместимость с пользователями, у которых свич уже выключен**
   - **Вопрос:** не должны ли мы при первом старте новой версии «вернуть» свич на ВКЛ?
   - **Варианты:** (а) уважать любое явно сохранённое значение и не трогать его; (б) одноразово сбросить тех, кто явно выключил, обратно на ВКЛ.
   - **Нужно выяснить:** подтверждено владельцем — выбран вариант (а). Существующее явное `false` сохраняется.
   - **Статус:** Resolved.

## 9. Архитектурные решения (ADR)

**ADR‑1: Дефолт переносится на уровень доменной модели, а не миграция данных**

- **Решение:** изменить значение по умолчанию у поля настройки в доменной модели и в дефолте чтения репозитория. Существующие сохранённые значения в DataStore не трогаются.
- **Альтернативы:** разовая миграция, явно записывающая `true` в DataStore при первом запуске новой версии для всех пользователей.
- **Почему:** «дефолт через отсутствие ключа» — стандартный паттерн DataStore в проекте, не требует версионирования миграций; уважает явный пользовательский выбор.

**ADR‑2: Bootstrap‑хук без флага «first run»**

- **Решение:** при каждом старте процесса bootstrap читает текущее значение из DataStore и применяет состояние системных компонентов.
- **Альтернативы:** хранить отдельный флаг «уже применили после установки» и пропускать повторные запуски.
- **Почему:** операция идемпотентна; флаг создаёт дополнительное состояние, которое теряется при clear‑data и снова требует ручного вмешательства; without‑flag вариант автоматически чинит рассинхронизацию после переустановки.

**ADR‑3: Манифест не меняется**

- **Решение:** оставить `enabled="false"` для SEND‑алиасов в манифесте.
- **Альтернативы:** объявить алиасы `enabled="true"` по умолчанию.
- **Почему:** манифестный `true` обходил бы рантайм‑фильтр по флавору на флаворах `photos`/`legacy` и регистрировал бы приложение для типов, которые оно не поддерживает; компромисс «после первого запуска» владельцем подтверждён.

## 11. Критерии готовности (strategic-level)

1. На свежеустановленном APK любого из флаворов `standard` / `photos` / `legacy`, после однократного запуска приложения и его закрытия, приложение присутствует в системном шер‑шите для типов, которые поддерживает данный флавор.
2. У нового пользователя свич «Принимать общие файлы» в настройках виден включённым без каких‑либо действий с его стороны.
3. Если пользователь явно выключает свич, после следующего старта приложения свич остаётся выключенным, и приложение не появляется в шер‑шите.
4. После полной переустановки приложения и одного запуска регистрация в шер‑шите восстанавливается автоматически.
5. На флаворе `photos` приложение НЕ появляется в шер‑шите для аудио и видео; на `legacy` — НЕ появляется для типов, не поддерживаемых флавором.
