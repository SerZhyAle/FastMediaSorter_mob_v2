## 1. Проблема

Основной строковый ресурс приложения разросся до ~3400 ключей и ~290-378 КБ на каждую локаль. С таким файлом тяжело работать в ходе разработки: навигация по ключам медленная, дифф любой точечной правки тонет в массиве несвязанных строк, а параллельные изменения разных фич регулярно дают merge-конфликты в одном гигантском файле. Это замедляет любую задачу, которая добавляет или меняет пользовательский текст.

---

## 2. Цели

1. Строковые ресурсы разложены по тематическим файлам, сгруппированным по фича-областям продукта, что делает навигацию и поиск нужного ключа предсказуемыми.
2. Точечная правка строк затрагивает один тематический файл, а не общий мегафайл - дифф читаемый, merge-конфликты локализуются.
3. Структура разбиения идентична во всех трёх локалях (EN/RU/UK), так что аудит паритета и навигация работают одинаково для любого языка.
4. Полный набор строковых ключей сохранён без потерь и дублей - приложение собирается и ведёт себя ровно как до миграции.

**Non-goals:**

- Не меняется ни одно строковое значение (текст, экранирование, формат) - только распределение ключей по файлам.
- Не вводятся новые ключи и не удаляются существующие.
- Не затрагиваются flavor-специфичные и уже выделенные тематические файлы строк, кроме как ориентир для именования.
- Не пересматривается схема локализации (набор поддерживаемых языков остаётся прежним).

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Имена тематических файлов узнаваемы и согласованы с уже существующими выделенными файлами строк по стилю именования.
2. Ключи, не относящиеся однозначно ни к одной фича-области, остаются в исходном общем файле как остаточный bucket, а не плодят «свалочные» файлы.
3. Разбиение выполняется автоматизированным инструментом, а не ручным переносом, чтобы исключить человеческую ошибку на объёме в тысячи строк.

### 3.2 Жёсткие ограничения

- **Flavor:** main source set (общие ресурсы всех flavor). Flavor-специфичные наборы строк вне объёма.
- **API level:** без API-специфики - распределение ресурсов по файлам не зависит от уровня Android; aapt2 объединяет их на сборке.
- **Wear OS:** не затрагивается (отдельный модуль со своими ресурсами).
- **Производительность:** нулевая рантайм-стоимость - объединение файлов происходит на этапе сборки, итоговый ресурс идентичен.
- **Совместимость данных:** не применимо - строковые ресурсы не хранятся и не мигрируют в Room.
- **Локализация:** EN/RU/UK - разбиение обязательно идентично во всех трёх локалях; набор ключей в каждой локали после миграции совпадает с набором до неё.
- **Доступность:** не применимо - визуальное поведение и текст не меняются.

## 4. Контекст текущей архитектуры

Строковые ресурсы лежат в локальных каталогах ресурсов модуля приложения, по одному набору на язык. Часть строк уже вынесена в выделенные тематические файлы (учётные записи, привязка/авторизация, операции над ресурсами, VR) - то есть инструментально многофайловая компоновка строк в проекте уже поддержана и применяется, при сборке все файлы одной локали сливаются в единый ресурс. Проблема из §1 не решается «сама»: основной файл просто никогда не растаскивался, и без явной таксономии и безопасного инструмента переноса ручная разбивка тысяч строк на объёме рискованна (потеря/дубль ключа, повреждение экранирования).

---

## 5. Предлагаемый подход

Разложить ключи основного строкового файла по набору тематических файлов, где каждая тема соответствует фича-области продукта из канонического перечня областей `docs/FEATURES.md`. Перенос выполняется существующим хирургическим инструментом работы со строками (байт-сохраняющим, держащим паритет локалей), а не ручным редактированием. Распределение ключа по теме - решение на основе семантики ключа и области, к которой он относится; неоднозначные ключи остаются в исходном общем файле как остаточный bucket.

### 5.1 Основные столпы / модули

- **Таксономия файлов.** Перечень тематических файлов выводится из фича-областей `docs/FEATURES.md`; имена файлов согласованы по стилю с уже выделенными тематическими файлами строк. Таксономия фиксируется и подтверждается владельцем до массового переноса.
- **Правило отнесения.** Для каждого ключа определяется его фича-область; ключи без однозначной области остаются в исходном общем файле. Правило детерминированное и воспроизводимое.
- **Локстеп-перенос.** Любой ключ переносится одновременно во всех трёх локалях в одноимённый тематический файл, чтобы структура оставалась идентичной по языкам.
- **Инвариант сохранности.** До и после миграции union имён ключей по всем строковым файлам каждой локали обязан совпадать; расхождение - жёсткий отказ, а не предупреждение.

### 5.2 Потоки данных и событий

Перенос - офлайн-операция над файлами ресурсов на этапе разработки. На сборке набор тематических файлов каждой локали объединяется в единый строковый ресурс; рантайм приложения работает с тем же итоговым ресурсом, что и до миграции.

### 5.3 Точки расширяемости

- Добавление новой фича-области в будущем сводится к заведению нового тематического файла строк во всех локалях по тому же правилу отнесения.
- Инструмент работы со строками остаётся точкой входа для последующего добавления/переноса ключей, чтобы паритет локалей и сохранность набора ключей поддерживались автоматически.

## 6. Открытые вопросы / Research items

1. **Гранулярность таксономии**
   - **Вопрос:** все ли фича-области заслуживают отдельного файла, или мелкие/смежные области объединяются в один тематический файл?
   - **Решение:** пороговая гранулярность - тематический файл создаётся только для группы с ≥~20 ключами; смежные мелкие группы консолидируются в одну тему; over-segmentation запрещён.
   - **Обоснование:** консенсус Android-практики (Orobator, Shrestha, Mols) прямо предостерегает от «файла на каждую мелкую фичу» и предписывает логическую группировку.
   - **Статус:** Resolved (2026-06-03, research-backed)

2. **Правило отнесения неоднозначных ключей**
   - **Вопрос:** по какому признаку ключ считается «не относящимся однозначно ни к одной области» и остаётся в остаточном bucket?
   - **Решение:** отнесение детерминированно по префиксу имени ключа. Cross-cutting группы (`error`, `dialog`, `msg`, `toast`, `tooltip`, `label`, `hint`) и любые ключи без однозначного фича-префикса остаются в остаточном `strings.xml` - он же общий (common) bucket. Префиксы, конфликтующие с уже существующими тематическими файлами (`vr`, `link`, `resource`), сливаются в существующий файл или остаются в остаточном - новый дубль-файл не заводится.
   - **Обоснование:** best-practice рекомендует единый common-файл для переиспользуемых строк (ошибки, кнопки диалогов) вместо дробления по типу; остаточный `strings.xml` уже играет эту роль (ADR-2).
   - **Статус:** Resolved (2026-06-03, research-backed)

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Потеря или дублирование ключа при переносе | Низкая | Сломанная сборка или пропавший текст в UI | Инвариант union ключей до==после; байт-сохраняющий инструмент с дубль-гардом |
| Рассинхрон структуры между локалями | Низкая | Аудит паритета краснеет, навигация расходится по языкам | Локстеп-перенос: ключ переносится одновременно во всех трёх локалях |
| Спорная принадлежность ключа к области | Средняя | Ключ оказывается «не там», навигация ухудшается | Детерминированное правило отнесения; остаточный bucket для неоднозначных |
| Повреждение экранирования/комментариев в больших файлах | Низкая | Невалидный XML, ошибка сборки | Хирургический текстовый перенос без пересериализации файла |

## 9. Архитектурные решения (ADR)

**ADR-1: Таксономия по фича-областям, а не по экранам/модулям**

- **Решение:** группировать строки по фича-областям `docs/FEATURES.md`.
- **Альтернативы:** разбиение по экранам (Activity/Fragment); разбиение по модулям кода.
- **Почему:** фича-области - стабильная, уже канонизированная в проекте номенклатура; границы экранов размыты (общие строки, тосты), а привязка к коду делает ресурсы хрупкими к рефакторингу UI.

**ADR-2: Остаточный bucket вместо принудительного распределения всех ключей**

- **Решение:** ключи без однозначной области остаются в исходном общем файле.
- **Альтернативы:** распихать все ключи по областям любой ценой.
- **Почему:** принудительное отнесение спорных ключей ухудшает навигацию и создаёт ложные связи; остаточный bucket честнее и проще в сопровождении.

## 11. Критерии готовности (strategic-level)

1. Строки основного файла разложены по тематическим файлам, именованным по фича-областям, во всех трёх локалях идентично.
2. Union имён ключей по всем строковым файлам каждой локали после миграции совпадает с набором до неё (ничего не потеряно и не задублировано).
3. Аудит паритета локалей зелёный для затронутых областей.
4. Целевой вариант приложения собирается; UI показывает тот же текст, что и до миграции.
5. Неоднозначные ключи остаются в исходном общем файле как остаточный bucket.
