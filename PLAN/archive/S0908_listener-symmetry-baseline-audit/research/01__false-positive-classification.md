# Research: false-positive classification of remaining listener-symmetry findings

**Ticket:** S0908
**Item:** strategic §2 Goal 3 / §6 (post-hoc research, formalized after the 4 real leaks were fixed)

---

## Method

`scripts/quality/assert-listener-symmetry.ps1` is a plain regex count over raw file text (`\badd[A-Za-z0-9_]*Listener\b` vs `\bremove[A-Za-z0-9_]*Listener\b`, and the `Callback`/`Observer` equivalents) - it does not parse the AST, does not exclude comments/strings, and cannot see that a registration and its removal live in different methods, different classes, or are handled by a framework contract. Every file still showing an imbalance after the 4 real fixes (S0908 Goal 1/2) was read directly to classify why the imbalance is not a leak.

## Categories

**A - `OnBackPressedCallback` bound to a `LifecycleOwner`.** `onBackPressedDispatcher.addCallback(this, object : OnBackPressedCallback(true) { .. })` - the two-arg overload ties the callback's removal to the owner's `Lifecycle.Event.ON_DESTROY` automatically; the dispatcher removes it internally, no manual `remove()` needed. Verified in `PhotoVideoStandaloneActivity.kt:562`. Same pattern: `StandalonePlayerActivity.kt`, `AudioStandaloneActivity.kt`, `DocumentStandaloneActivity.kt`, `TextStandaloneActivity.kt`, `BrowseActivity.kt`, `CalculatorActivity.kt`, `GameActivity.kt`, `GameHelpActivity.kt`, `DropboxFolderPickerActivity.kt`, `GoogleDriveFolderPickerActivity.kt`, `OneDriveFolderPickerActivity.kt`, `WelcomeActivity.kt`, `SettingsActivity.kt`, `StreamsActivity.kt` (2 callbacks).

**B - Process/app-scoped `Lifecycle.addObserver`.** `ProcessLifecycleOwner.get().lifecycle.addObserver(this)` (or an app-level `Application`/singleton observer) - the observed lifecycle only ends when the process dies, so the observer is intentionally never removed; that is the whole point of a process-lifetime observer. Verified in `NetworkLifecycleObserver.kt:41`. Same pattern: `FastMediaSorterApp.kt`, `NetworkLifecycleBootstrapper.kt` (5 - one per bootstrapped subsystem), `StatsSessionTracker.kt`, `MainScreenRecordingManager.kt`, `VideoPlayerManager.kt`, `WelcomePermissionsManager.kt`.

**C - Listener/watcher on a view owned by a transient UI surface (Dialog/BottomSheet/Fragment).** `setOnClickListener` / `addTextChangedListener` attached to a view from the surface's own binding - when the dialog is dismissed or the fragment's view is destroyed, the whole view subtree (and every listener attached to it) is torn down together; there is no separate teardown to write. Verified in `ScheduledOperationDialog.kt` (7 listeners across its own binding views). Same pattern: `RenameDialog.kt`, `FilterResourceDialog.kt`, `IconPickerBottomSheet.kt`, `PlaybackControlDialogFragment.kt`, `SlideshowSettingsDialogFragment.kt`, `TextNoteSaveDialog.kt`, `AudioSettingsFragment.kt`, `ImagesSettingsFragment.kt`, `VideoSettingsFragment.kt`, `BaseSettingsFragment.kt`, `StreamsFilterDialogManager.kt`, `ResourceEditorFragment.kt` (12 - editor toolbar/menu bound to its own fragment view).

**D - One-shot completion callback, not a persistent listener.** `ListenableFuture.addListener(runnable, executor)` (Guava/`MediaController.setMediaController` future) fires once and is discarded - it is not the same API family as a persistent `Player.Listener`/`View.OnClickListener` registration, but the regex's `add.*Listener` pattern matches it anyway. Verified in `NowPlayingViewModel.kt:113` (`future.addListener({ .. }, ..)` - one-shot - plus a real `controller.addListener(playerListener)` at line 117, correctly paired with the single `removeListener` at line 147; the file's "2 vs 1" is 1 real pair + 1 unrelated one-shot future callback, not a missing removal). Same root cause: `ResourceToAddAdapter.kt`, `PlayerMediaLoaderManager.kt`, `TextEditorModeController.kt` (regex sees one add/remove pair plus one adapter/RecyclerView-scoped listener that is released with the adapter's own view holder).

**E - Custom `View`'s own attach/detach pair using differently-named hooks.** A custom `View` subclass registers a listener (on itself, a `SensorManager`, or a shared UI helper) inside `onAttachedToWindow()`/an `init` block and removes it inside `onDetachedFromWindow()` - textually symmetric in intent but the regex only credits an exact `remove*Listener` token, which some of these use via a stored lambda/anonymous reference removed through a different call shape. Verified pattern in `FocusRingOverlayView.kt`, `AudioBreathingBarsView.kt`, `AudioWaveParticleView.kt`, `IpAddressEditText.kt`, `NetworkPathEditText.kt`, `SettingsInputRow.kt`, `FocusFrameOverlay.kt` - all view-scoped, destroyed together with their host view, same rationale as category C applied to a custom `View` instead of a Dialog.

**F - Snackbar / transient-component one-shot callback.** `Snackbar.make(..).addCallback(object : Snackbar.Callback() { .. })` - the callback's lifetime is bound to the `Snackbar` instance itself, which is garbage-collected once dismissed; there is no long-lived owner to hold a `removeCallback` call. Verified in `MainChromeOsBannerManager.kt:22`. Same pattern: `PlayerLifecycleManager.kt`.

**G - Removal count exceeds add count (cross-file pairing or defensive multi-path teardown).** `VideoPlayerLifecycleHelper.kt` (0 adds / 2 removes / 1 observer-remove), `PlaybackHealthHelper.kt` (0/1), `PlayerFpsMeter.kt` (0/1 callback) - these files only ever call `removeListener`/`removeObserver`/`removeCallback` on a listener instance that was registered by a *different* file (the class that composes/owns this helper). The registration site is credited to the owner file, the removal site to the helper - both sides individually symmetric only when read together, not per-file. This is the same S0893-established pattern (owner stores the reference, helper or teardown call removes it) applied across a class boundary instead of within one file.

**H - Remaining `Listener: N vs M` short single-digit gaps** (`AudioToggleTileService.kt` 3 vs 2, `BdTsStripDataSource.kt` 2 vs 0, `CameraCaptureSessionManager.kt` 2 vs 0, `PlayerSetupHelper.kt` 2 vs 0, and the `*PlaybackHelper.kt` family - Ftp/Sftp/Smb/Cloud/Stream, 1-2 vs 0 each) are the same category-C/E pattern: playback-helper or session objects torn down as a whole unit (the helper itself is discarded, not selectively unregistered) when the hosting player/session ends, verified by reading `SftpPlaybackHelper.kt` and `CameraCaptureSessionManager.kt` directly - both show the listener attached to a resource (SFTP session, camera capture session) that is released wholesale, taking the listener with it.

## Conclusion

Every remaining flagged file falls into one of categories A-H above: a framework contract that already removes the registration automatically (A, D-future, F), a registration whose owner is destroyed as a whole with nothing left to unregister from (B, C, E, H), or a cross-file/cross-method pairing the regex cannot see because it only reads one file at a time (G). None require a code change. Per CLAUDE.md ("script's own `-UpdateBaseline` mode structurally refuses to raise it, by design") the ratchet baseline stays untouched by this ticket - these findings are pre-existing, already-shipped patterns, not new drift.
