**Ticket:** S0193
**Status:** Implemented

**Roadmap entry:** Ad-hoc — запрос 2026-05-14
**Tactical spec:** `PLAN/S0193_lazy-init-research/` → [`INDEX.md`](S0193_lazy-init-research/INDEX.md)

> **Scope:** STRATEGIC. Цели, ограничения, открытые вопросы. Без имён классов, путей, лимитов строк, миграций Room, модулей Hilt.

---

## 1. Проблема

Приложение непрерывно наращивает функциональный стек: видеоплеер, аудио-сервис, VR-слой, облачные клиенты (Google Drive, Dropbox, OneDrive), сетевые протоколы (SMB, FTP, SFTP), noLegal-библиотеки, Translation/OCR, Cast SDK. При каждом запуске процесса Hilt-граф строится целиком и большинство синглтонов создаётся до первого взаимодействия пользователя с UI — вне зависимости от того, что пользователь намерен делать. Пользователь, открывший приложение только чтобы пролистать локальные фотографии, платит памятью и временем запуска за весь стек. На устаревших устройствах с ограниченной RAM (2–3 GB) и медленным NAND это ощутимо.

---

## 2. Цели

1. Выяснить, какие подсистемы инициализируются раньше первого обращения к ним (т.н. «горячая» инициализация), и оценить их вес (память, I/O, CPU на старте).
2. Определить, какие из них уже ленивы или откладываемы без архитектурных изменений.
3. Оценить применимость доступных механизмов: `Lazy<T>` в Hilt, ViewModel-scoped объекты, on-demand Dynamic Feature Modules (Play Feature Delivery), ручная ленивая инициализация.
4. Сравнить стратегию «ленивая загрузка внутри одного APK» с текущей стратегией «разные сборки для разных задач» (lite / photos / standard / legacy) и дать однозначную рекомендацию.
5. Если улучшение оправдано — сформировать перечень дочерних спецификаций.

**Non-goals:**

- Перевод проекта на Compose и связанная с этим оптимизация отрисовки.
- Оптимизация R8 / ProGuard shrinking (отдельная тема).
- Оптимизация размера APK / AAB (отдельная тема).
- Изменение минимального SDK.
- Рефакторинг, не связанный напрямую с временем запуска или потреблением памяти.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Если пользователь запустил приложение и пролистал папку с фотографиями — сетевые клиенты, аудиосервис и noLegal-библиотеки не должны присутствовать в heap в этот момент.
2. Инициализация тяжёлых подсистем должна происходить не раньше первого реального обращения к ним — при открытии плеера, при выборе сетевого источника, при переходе в VR-режим.
3. Предпочтительнее инкрементальные улучшения в рамках одного APK, чем введение Dynamic Feature Modules (если только исследование не докажет, что DFM — единственный жизнеспособный путь для noLegal/VR).
4. Рекомендация по пользовательской стратегии «используй правильную сборку» может быть обоснована как принципом архитектуры, так и измерениями — достаточно одного из двух.

### 3.2 Жёсткие ограничения

- **Flavor:** `standard`, `noLegal` — основные объекты исследования. `lite` и `photos` уже ограничены на уровне BuildConfig и интересны как точка сравнения.
- **API level:** minSdk 26 (standard). DFM / Play Feature Delivery требует API 21+, ограничений нет. Однако Play Feature Delivery недоступен для sideload-APK (noLegal).
- **Wear OS:** не затрагивается в исследовательской фазе.
- **Производительность:** цель — нулевое регрессирование cold start time для текущих пользователей; улучшение желательно, но не обязательно.
- **Совместимость данных:** Room-миграции не предполагаются в данном спеке.
- **Локализация:** не затрагивается.
- **Доступность:** не затрагивается.

## 4. Контекст текущей архитектуры

Точка входа процесса (`Application.onCreate`) выполняет значительный объём работы: строит Hilt-компонентный граф, инжектирует ~15 зависимостей напрямую в Application-класс (включая сетевой стек и менеджеры фоновых сервисов), инициализирует Cast SDK, запускает несколько корутин первого старта. Все эти зависимости помечены как `@Singleton` и создаются при первом обращении Hilt — что на практике означает момент `onCreate`, потому что Application-класс их инжектирует немедленно.

Flavour-матрица (lite / photos / standard / legacy) решает задачу на уровне компиляции: код тяжёлых подсистем отсутствует в APK. Это работает для пользователей, которые осознанно выбирают нужный flavour. Однако standard-сборка — единственная, доступная через Play Store без дополнительных шагов, и подавляющее большинство пользователей устанавливают именно её. Внутри standard-сборки нет механизма, откладывающего создание экземпляров неиспользуемых подсистем.

## 5. Предлагаемый подход

Исследование структурировано как аудит с измерениями, за которым следует классификация и рекомендация. Имплементационная часть (если рекомендована) выносится в дочерние спецификации.

### 5.1 Основные блоки исследования

**Блок А — Аудит точек инициализации.**
Выявить все объекты, создаваемые до первого UI-события: что именно инжектируется в Application-слой, что запускается в `AppStartupInitializer`, какие `@Singleton` попадают в граф немедленно. Разделить на группы: «нужно всегда», «нужно при первом открытии сетевого ресурса», «нужно только при открытии плеера», «нужно только при VR/noLegal».

**Блок Б — Измерение веса.**
Для каждой выявленной группы: allocation size в heap (через Android Studio Memory Profiler), вклад в cold start time (метод `reportFullyDrawn`). Особое внимание — облачным SDK (Google Drive / Dropbox / OneDrive), SMB/FTP/SFTP-стеку, Cast SDK, noLegal-библиотекам.

**Блок В — Оценка механизмов.**
- `Lazy<T>` в Hilt (`@Singleton` + lazy injection): применим без изменения архитектуры; объект создаётся при первом `.get()`, а не при инжектировании. Подходит для синглтонов, которые Application-класс получает, но не использует немедленно.
- ViewModel-scoped объекты: ExoPlayer уже создаётся на уровне ViewModel — правильный паттерн. Проверить, нет ли синглтонов, которые логичнее держать в ActivityRetainedScope.
- Ручная ленивая инициализация через `lateinit` + фабричный вызов: применима для SDK, не управляемых Hilt (например, Cast).
- Dynamic Feature Modules (DFM / Play Feature Delivery): доставка кода по требованию из Play Store. Позволяет полностью вынести VR / noLegal-код в отдельный модуль, загружаемый при первом открытии соответствующей функции. Недоступен для sideload-APK — критично для noLegal. Требует значительного рефакторинга модульной структуры.

**Блок Г — Сравнение со стратегией сборок.**
Насколько lite / photos реально легче standard при cold start? Если разница значительна — это аргумент в пользу «направляй пользователя в нужный flavour» вместо усложнения standard. Если разница мала — flavour-стратегия неэффективна и lazy init в standard даёт больший выигрыш.

**Блок Д — Рекомендация.**
Ожидаемое направление (зафиксировано как гипотеза, подтверждается Phase 01): применить `dagger.Lazy<T>` для всех Application-level синглтонов категорий `NETWORK_ONLY`, `PLAYER_ONLY`, `VR_NOLEGAL_ONLY`. Это стандартный паттерн Hilt без изменения архитектуры — объект создаётся при первом `.get()`, а не при инжектировании. Lifecycle observers, сейчас регистрируемые в `Application.onCreate` немедленно, переносятся в «trigger on first use» через соответствующий Repository или ViewModel.

Первое обращение к подсистеме может давать короткую задержку (microfreeze или анимацию загрузки) — это приемлемо. Повторные обращения мгновенны — объект уже в памяти.

Полный список вариантов на случай если гипотеза не подтвердится:
- «Достаточно текущего состояния» — если аудит покажет, что все Application-level синглтоны действительно нужны с первого кадра.
- «Ввести DFM для VR/noLegal» — только если Phase 03 покажет, что DFM применим и объём рефакторинга оправдан.
- «Усилить onboarding к нужному flavour» — если flavour-разница значима, а lazy init невозможна.
- Комбинация вариантов.

### 5.2 Потоки данных и событий

Исследование не меняет потоки данных. Его цель — понять, когда и где возникают первые обращения к тяжёлым подсистемам, и оценить, можно ли эти обращения отложить без изменения пользовательского опыта.

### 5.3 Точки расширяемости

- Результат исследования должен оставить возможность для поэтапного внедрения: сначала самые тяжёлые синглтоны, затем — менее значимые.
- Если DFM рекомендован хотя бы частично — архитектурное решение должно быть принято до любой дочерней спеки по этой теме.
- Рекомендация по flavour-onboarding, если принята, должна быть совместима с текущим UX первого запуска.

## 6. Открытые вопросы / Research items

1. **Реальный вес сетевого стека на старте**
   - **Вопрос:** Сколько памяти занимают SMB/FTP/SFTP/облачные клиенты, создаваемые в момент `Application.onCreate`?
   - **Варианты:** < 5 MB (незначительно), 5–20 MB (умеренно), > 20 MB (критично).
   - **Нужно выяснить:** Heap dump после `reportFullyDrawn` на standard-сборке без открытия каких-либо ресурсов.
   - **Статус:** Resolved (Skipped) — измерения (Phase 02) пропущены по принципу «приоритет архитектуры над цифрами», так как Phase 01 уже доказала необходимость ленивой инициализации.

2. **Применимость `Lazy<T>` к Application-уровню Hilt**
   - **Вопрос:** Можно ли безопасно заменить прямые `@Inject lateinit var` в Application-классе на `Lazy<T>` без нарушения жизненного цикла (корутины, lifecycle observers, SMB lifecycle manager)?
   - **Варианты:** Да для большинства, нет для тех, что регистрируют lifecycle observers немедленно.
   - **Нужно выяснить:** Аудит всех Application-level `@Inject` на предмет немедленного использования в `onCreate`.
   - **Статус:** Resolved — Phase 01 Step 01.1: 13 из 17 полей безопасны для прямого `dagger.Lazy<T>`. 4 поля (`networkStateMonitor`, `smbConnectionManager`, `smbBackgroundLifecycleManager`, `networkLifecycleObserver`) требуют рефакторинга: их использование в `onCreate` — синхронная регистрация lifecycle observers / OS-колбэков, переносится в Repository/Manager и стартует по первому обращению пользователя.

3. **DFM для VR / noLegal**
   - **Вопрос:** Теоретически применим ли Play Feature Delivery для изоляции VR/noLegal кода от standard-APK, учитывая что noLegal — sideload-only?
   - **Варианты:** DFM работает для standard (Play), неприменим для noLegal (sideload) — гибрид.
   - **Нужно выяснить:** Подтвердить ограничение Play Feature Delivery на sideload; оценить объём рефакторинга под DFM.
   - **Статус:** Resolved — Phase 03 Step 03.3: для `standard` технически применим, но **не рекомендован**. Экономия установки ~3–5 MB не оправдывает недели рефакторинга 12+ VR-файлов и CMake. Для `noLegal` структурно неприменим (sideload). VR-код **уже ленив** в рантайме — DFM даёт только install-size win, не heap win. Принципиальная цель исследования достигается через `dagger.Lazy<T>` без изменения модульной структуры.

4. **Разница cold start: standard vs lite vs photos**
   - **Вопрос:** Насколько lite и photos быстрее standard при холодном запуске на устройстве с 3 GB RAM?
   - **Варианты:** < 200 ms (несущественно), 200–500 ms (умеренно), > 500 ms (значительно).
   - **Нужно выяснить:** Измерение через `adb shell am start -W` или Perfetto для каждого flavour на одном тестовом устройстве.
   - **Статус:** Resolved (Skipped) — измерения (Phase 02) отложены, так как рекомендация применения `Lazy<T>` не требует количественного обоснования разницы.

5. **noLegal-библиотеки: точка загрузки**
   - **Вопрос:** Когда именно загружаются noLegal-специфичные нативные библиотеки (Chaquopy Python runtime, OpenXR bridge)? При старте процесса или при первом открытии соответствующего экрана?
   - **Варианты:** System.loadLibrary при Application init (плохо) vs при первом Activity (приемлемо).
   - **Нужно выяснить:** Поиск точек `System.loadLibrary` и `@JvmStatic` инициализаторов в noLegal-специфичном коде.
   - **Статус:** Resolved — Phase 01 Step 01.4: OpenXR (`openxr_loader`, `openxr_native`) грузится в `VrPlayerActivity.onCreate` и `OpenXrNative.ensureLoaderLoaded()`. Chaquopy `Python.start()` — внутри `ChaquopyRuntimeHolder.ensureInitialized()`, вызывается из `YtDlpExtractionStrategy` по запросу пользователя. **Ни одного `System.loadLibrary` в `Application` или `AppStartupInitializer`.** Работы по этому пункту не требуется.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Lazy<T> ломает lifecycle observer, зарегистрированный в onCreate | Средняя | Утечка соединений или NullPointerException при backgrounding | Аудит каждого кандидата перед переносом; строгое тестирование lifecycle |
| DFM несовместим с noLegal sideload → раздвоение подхода | Высокая | Два разных механизма для standard и noLegal, дублирование кода | Принять это как ограничение; DFM применять только для standard |
| Измерения покажут незначительный выигрыш | Низкая | Рекомендация «ничего не менять» | Принцип «не загружай неиспользуемое» самодостаточен; Phase 01 статической классификации достаточно для обоснования |
| Усиление flavour-onboarding раздражает пользователей standard | Низкая | Негативные отзывы | A/B тест или мягкая подсказка без принуждения |

## 9. Архитектурные решения (ADR)

**ADR-1: Исследование предшествует любой имплементации**

- **Решение:** Спецификация S0193 является исключительно исследовательской. Никакой код не меняется в рамках этого спека — только измерения, анализ и рекомендации. Дочерние спеки создаются по результатам.
- **Альтернативы:** Начать с «очевидных» улучшений (Lazy<T> для сетевого стека) сразу, без измерений.
- **Почему:** Без данных о реальном весе невозможно обосновать сложность изменений и расставить приоритеты. Риск оптимизировать то, что не является узким местом.

**ADR-2: DFM рассматривается только для Play-дистрибуции**

- **Решение:** Dynamic Feature Modules исключены для noLegal-флейвора как несовместимые с sideload-дистрибуцией. Исследование DFM ограничивается standard-сборкой.
- **Альтернативы:** Принудительная загрузка DFM через ссылку / ZIP — слишком сложно и ненадёжно.
- **Почему:** Play Feature Delivery требует Play Store как дистрибьютора; sideload-APK не имеет доступа к механизму on-demand delivery.

**ADR-3: Финальная архитектурная рекомендация — `dagger.Lazy<T>` + trigger-on-first-use**

- **Решение:** Применить два механизма ленивой инициализации без введения DFM. (1) `dagger.Lazy<T>` для 13 «лёгких» Application-полей через S0194. (2) Trigger-on-first-use для 4 сетевых lifecycle-observer-ов через S0195. Сценарий «standalone image viewer» после внедрения имеет в heap нулевой сетевой стек — эквивалентно `lite`-флейвору, но в рамках одного `standard`-APK.
- **Альтернативы:**
  - DFM — отклонён (ADR-2 + cost/benefit в Phase 03 Step 03.3).
  - Только flavour-onboarding — отклонён, не решает проблему standard-пользователей внутри их установленного APK.
  - Stay-as-is — отклонён, принцип «не загружай неиспользуемое» нарушен систематически.
- **Почему:** Phase 01 показал что 17 Application-полей делятся на 13 тривиально-ленивых + 4 трудно-ленивых. Оба механизма (`Lazy<T>` и trigger-on-first-use) — стандартные Hilt-паттерны без архитектурных изменений. Гибридные/радикальные варианты (DFM) не оправданы выигрышем относительно усилий.
