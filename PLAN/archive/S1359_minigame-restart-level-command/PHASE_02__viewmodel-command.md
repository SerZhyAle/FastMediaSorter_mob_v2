## Steps

### Step 02.1 - Add `restartCurrentLevel()` over a shared private helper

**Files:** `app_v2/src/main/java/com/sza/fastmediasorter/ui/game/GameViewModel.kt`
**Depends on:** - start of phase

**Prompt for developer:**

> Extract the body of the existing `restartLevel()` - everything after its status guard - into `private suspend fun applyLevelRestart(ready: GameUiState.Ready, restart: (GameLevelState, GameLevelState) -> GameLevelState)`, which builds the reseeded config, generates the level, calls `restart`, and publishes exactly the state `restartLevel()` publishes today. Make `restartLevel()` keep its `GAME_OVER` guard and delegate with `rulesEngine::restartLevel`. Add `fun restartCurrentLevel()` that guards on `GameStatus.PLAYING` instead and delegates with `rulesEngine::restartLevelVoluntarily`. Change no published field.

**Why:**

Strategic §4 records that `GameViewModel.restartLevel()` silently returns for a live level, so a second entry point is required; sharing one helper keeps the two paths from drifting in what they publish, which is what would break the "same as dying" equality at the UI level.
