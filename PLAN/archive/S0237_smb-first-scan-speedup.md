---

## 1. Проблема

Первое открытие SMB-каталога среднего размера (182 файла на 192.168.1.100\common) занимает 50 секунд, в то время как сам листинг директории отрабатывает за миллисекунды. Метрика подтверждает: `ScanMetrics: SLOW SCAN detected — 50082ms threshold=6000ms file_count=182`. Все 50 секунд экран остаётся в состоянии загрузки без полезной информации для пользователя, и фактически читается metadata-поток по каждому файлу под низким пределом конкурентности.

Эффект на пользователя: открытие любого ресурса, не лежащего в кэше (новый ресурс, после очистки cache или после долгого отсутствия), воспринимается как зависание. На втором заходе (cache hit) задержки нет — то есть пользователь платит весь штраф в первую сессию.

---

## 2. Цели

1. Список файлов появляется на экране сразу после завершения листинга директории — не дожидаясь metadata-pass.
2. Метаданные (EXIF / video header / ID3) подгружаются ленивее: для видимых строк в первую очередь, для остальных — по мере прокрутки, как уже работает thumbnail-pipeline.
3. Совокупное время первичного открытия большого SMB-каталога перестаёт срабатывать на текущий `SLOW SCAN` threshold (6000 мс) на типовом домашнем NAS.
4. Один зависший metadata-запрос (например, по проблемному `.avi`) не блокирует ни общий скан, ни соседние файлы — есть жёсткий per-file бюджет с тихим fallback.
5. Дублирующая работа на уровне листинга устранена: один и тот же путь не сканируется дважды за одну операцию загрузки ресурса.

**Non-goals:**

- Уменьшение времени второго и последующих заходов (там уже cache hit, проблемы нет).
- Переписывать общий SMB-transport или менять модель кэша медиафайлов.
- Гарантировать полные metadata-поля для каждого формата — допустим тихий fallback на header-only.
- Менять поведение скана на локальных файлах, FTP, SFTP, облаках — этот спек только про SMB. Возможные общие выводы фиксируются как research items, не как обязательства.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Двухфазный показ списка должен ощущаться как немедленный отклик, аналогичный `setSkipInitialThumbnailLoad` для миниатюр.
2. Параллельность SMB-чтений metadata должна быть настраиваемой, а не зашитым в код магическим числом.
3. Per-file timeout на metadata-extraction — короткий, тихий, без warn-спама в логе на каждый промах.
4. Желательно сохранить текущую метрику `ScanMetrics` (важна как long-term наблюдение) — добавления допустимы, но breaking-изменения формата нежелательны.

### 3.2 Жёсткие ограничения

- **Flavor:** все варианты сборки с SMB-сканом — `standard`, `lite`, `legacy` (там, где включён модуль SMB). Реализация остаётся в общем source set.
- **API level:** без новой Android API-специфики.
- **Wear OS:** не затрагивается — Wear не выполняет тяжёлых SMB-сканов первичного захода.
- **Производительность:** ленивый metadata-pass не должен конкурировать с playback и общим UI-потоком — приоритет ниже visible-rendering, выше idle-prefetch.
- **Совместимость данных:** формат уже сохранённых `MediaFilesCache` записей сохраняется. Если введён `metadataState` (`pending` / `partial` / `complete`), он default-совместим со старыми кэшами.
- **Локализация:** новых пользовательских строк не предполагается. Если появится индикатор «метаданные подгружаются» — обязательная EN/RU/UK тройка с проверкой `scripts/check_strings_localized.ps1`.
- **Доступность:** двухфазный показ не должен ломать TalkBack-ордер строк — имя файла читается с самого начала, дополнительные поля объявляются после их прихода.

## 4. Контекст текущей архитектуры

В сценарии загрузки ресурса слой `data` сначала вызывает `SmbDirectoryScanner` для получения списка имён, размеров и типов файлов, а затем `SmbMediaScanner` обогащает каждый элемент метаданными (EXIF, video header, ID3) до того, как результат уйдёт в UI. Параллельность чтений на одну SMB-цель ограничена коэффициентом `ConnectionThrottleManager` (текущий лимит 4), что для домашнего NAS чрезмерно консервативно. UI-слой (browse list) уже имеет паттерн отложенной загрузки через `setSkipInitialThumbnailLoad`, но он применяется только к миниатюрам, а не к остальным metadata-полям.

Сейчас экран не способен показать список сразу после листинга, потому что доменная цепочка ждёт полностью обогащённую коллекцию перед эмитом наружу. Дополнительно зафиксирована избыточная работа: листинг одного и того же `dirPath` выполняется дважды подряд (видно как два `Found N files in root` в пределах одной миллисекунды) — следствие двойного входа из вышестоящего координатора.

---

## 5. Предлагаемый подход

Разделить «листинг» и «обогащение метаданными» в отдельные фазы во времени и в потоке данных. Листинг становится first-class результатом, который UI отображает мгновенно. Обогащение становится фоновой задачей с приоритизацией по видимости и жёстким per-file бюджетом. Параллельность SMB-чтений становится параметром, а не константой.

### 5.1 Основные столпы / модули

- **Phase-A: листинг.** Слой scan-orchestration отдаёт UI коллекцию файлов сразу после `scanNonRecursive`, без metadata-pass. Каждый элемент помечен состоянием «метаданные ожидаются».
- **Phase-B: обогащение.** Background metadata-pass работает поверх отображённого списка. Очередь приоритезируется по видимости (visible rows first, off-screen — потом), переиспользует существующий SMB-конкурентный лимит и шину обновлений UI (`notifyItemChanged` с payload, без полного rebind).
- **SMB concurrency policy.** Лимит одновременных metadata-чтений на одну SMB-цель становится конфигурируемой величиной. По умолчанию — больше текущих 4. Точное значение фиксируется в тактическом spec на основе замеров.
- **Per-file metadata budget.** Каждое metadata-чтение ограничено коротким таймаутом. Истёкший таймаут → тихий fallback на header-only из листинга (имя/размер/тип), без warn-уровня в логе. Логировать таймауты агрегированно (1 строка на скан), не на каждый файл.
- **De-dup листинга.** Идентичные подряд вызовы листинга одного `dirPath` в пределах одной операции загрузки ресурса свёртываются в один. Реализация — на уровне координатора, не самого scanner'а.

### 5.2 Потоки данных и событий

- UI → координатор загрузки → SMB listing → эмит «list-ready» → UI рендерит → координатор → metadata enrichment → инкрементальные UI-апдейты по строкам.
- ScanMetrics получает два события: `listing_complete` (новое) и `enrichment_complete`. Существующий `scan_complete` остаётся как агрегат, но его пороговое значение SLOW SCAN отвязывается от UI-отклика и применяется только к фоновой фазе обогащения.

### 5.3 Точки расширяемости

- Конфигурация конкурентности metadata-чтений выносится в одно место и допускает override на уровне ресурса (для нестабильных серверов).
- Per-file budget оформлен как абстракция таймаута + fallback-провайдер, чтобы тот же паттерн позже применить к SFTP / FTP, если измерения это оправдают.
- Layer metadata-state у элемента списка (`pending` / `partial` / `complete`) пригоден для расширения: при необходимости туда добавятся другие поля без поломки UI-контракта.

## 6. Открытые вопросы / Research items

1. **Оптимальный SMB-лимит по умолчанию.**
   - **Вопрос:** значение по умолчанию для одновременных metadata-чтений на одну SMB-цель.
   - **Варианты:** 8, 12, 16; либо адаптивно от RTT.
   - **Решение:** 8 (фиксированное значение, не адаптивное в v1). Текущая база `ProtocolLimits.SMB(2, 1)` и `userDefinedNetworkLimit = 2` поднимаются до 8. Speed-test override остаётся работать поверх этой базы (recommendedThreadsCache не трогаем). Контрольная точка — наблюдение по `ScanMetrics` после первой сессии. Если домашний NAS стабильно даёт refusal — снижается через `userDefinedNetworkLimit`. Адаптивное от RTT — отдельный спек, не для v1.
   - **Статус:** Resolved (2026-05-17)
2. **Per-file metadata timeout.**
   - **Вопрос:** значение жёсткого таймаута на одно metadata-чтение.
   - **Варианты:** 1000, 1500, 2000 мс; либо двухуровневый (header 500 мс, full 2000 мс).
   - **Решение:** одноуровневый бюджет `1500 мс`. EXIF / ID3 header-чтения по типовому SMB укладываются в ~200–400 мс, video header — 400–1000 мс. 1500 мс даёт запас x1.5 для перегруженного NAS, при этом изолирует зависшие чтения за разумный срок. Двухуровневый бюджет добавляет сложность без понятной выгоды для v1.
   - **Статус:** Resolved (2026-05-17)
3. **Что показывать пока metadata ещё не пришли.**
   - **Вопрос:** строка списка с «metadata pending» — пустые поля duration / resolution / EXIF date или прочерк / спиннер.
   - **Варианты:** ничего (поля просто появляются), placeholder-дефис, мини-spinner на строке.
   - **Решение:** ничего (поля просто появляются по приходу). Имя, размер, тип, иконка типа — берутся из листинга. Поля duration/resolution/EXIF-date — рендерятся пустыми (как при отсутствии metadata) до прихода. Не вводим placeholder-дефис и spinner: первое создаёт визуальный шум, второе сигнализирует «идёт операция, дождитесь» — это противоречит цели UX (немедленный отклик). COMMUNICATION_POLICY §6 чек-лист: ничего не нарушено, нет нового текста.
   - **Статус:** Resolved (2026-05-17)
4. **Сохранять ли partial metadata в `MediaFilesCache`.**
   - **Вопрос:** при истечении per-file timeout — кэшировать ли header-only результат или оставлять элемент непокэшированным до успешного полного чтения.
   - **Варианты:** кэшировать с флагом `partial`; не кэшировать; кэшировать с TTL.
   - **Решение:** не кэшировать timeout-fallback. В `MediaFilesCache` уходит только `metadataState = COMPLETE`. `PARTIAL` остаётся in-memory на текущую сессию — следующий заход на ресурс ре-сканирует problematic files. Это «sticky partial» риск из §7 — решаем тем, что partial вообще не персистируется. Цена: повторный заход в ту же сессию выполнит metadata-pass заново на проблемных файлах. Это приемлемо.
   - **Статус:** Resolved (2026-05-17)
5. **Связь с S0229 (browse-side enrichment).**
   - **Вопрос:** S0229 уже стабилизирует browse-side enrichment в режиме idle-after-scroll. Не пересекаются ли пути этого спека и S0229 на одной и той же background-очереди?
   - **Решение:** два разных пути — не сливаем. S0229 работает в scroll-idle на уже видимых row'ах для audio metadata. S0237 работает в scan-time на всём только что отлистинговавшемся каталоге. Жизненные циклы разные (одно — post-scan, другое — post-scroll), пользовательские триггеры разные. Они могут конкурировать за `ConnectionThrottleManager` permits — это нормально, семафор уже корректно сериализует. Объединять в общую очередь — потенциальный over-engineering. Документируется в `Handoff` PHASE_06; если в проде увижу конкуренцию (двойные read'ы на одном файле) — отдельный спек на unification.
   - **Статус:** Resolved (2026-05-17)

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Повышенная конкурентность приводит к серверным throttle/refusal на слабых NAS | Средняя | Часть файлов получает timeout-fallback вместо полных metadata | Адаптивный лимит + observability через ScanMetrics + per-resource override |
| Двухфазный показ ломает текущие сортировки, зависимые от metadata (например, NAME_ASC OK, но DATE_ASC требует EXIF) | Средняя | Пользователь видит «не до конца отсортированный» список несколько секунд | Документировать поведение; для metadata-зависимых сортировок выполнять enrichment до отображения только если это явный режим |
| Tihий fallback на header-only маскирует реальные проблемы транспорта | Низкая | Скрытое снижение качества metadata для целого ресурса | Агрегированная per-scan метрика «N файлов попали в fallback» + warn только при превышении порога |
| Пересечение с S0229 даёт две конкурирующие background-очереди | Средняя | Двойная нагрузка на SMB + противоречивые приоритеты | Согласовать общую background-pipeline в фазе `/spec-tech` |
| Изменение конкурентности нарушает существующие гарантии `IdleDisconnect` / `SmbConnectionManager` | Низкая | Преждевременный disconnect под нагрузкой | Не трогать idle-policy; конкурентность ограничивается семафором, не количеством физических подключений |
| Дедупликация листинга маскирует баг во внешнем координаторе, который вообще не должен вызывать его дважды | Низкая | Скрываем root cause | Перед свёрткой залогировать факт дублирующего вызова один раз, затем чинить координатор отдельным фиксом |

## 9. Архитектурные решения (ADR)

**ADR-1: Разделение листинга и metadata-pass на две фазы.**

- **Решение:** UI получает список после Phase-A (листинг), metadata подгружаются в Phase-B инкрементально.
- **Альтернативы:** (а) оставить как сейчас и просто поднять конкурентность; (б) полностью убрать metadata-pass из скана и грузить только по visible rows.
- **Почему:** (а) даёт линейное ускорение, но не убирает «список появляется только когда всё готово» — UX-проблема остаётся. (в) теряет данные для сортировок/фильтров, зависимых от metadata. Двухфазная модель сохраняет совместимость с фичами и решает UX.

**ADR-2: Per-file metadata timeout с тихим fallback.**

- **Решение:** жёсткий таймаут на одно metadata-чтение, истечение → header-only fallback, без warn-уровня в логе.
- **Альтернативы:** (а) глобальный таймаут на весь metadata-pass; (б) retry с экспоненциальной задержкой; (в) текущий «без таймаута, до победного».
- **Почему:** (а) один зависший файл затрагивает соседние. (б) усугубляет общую длительность. (в) то, что мы видим в логе сейчас. Per-file taймаут изолирует проблемный файл и сохраняет общий темп.

**ADR-3: SMB-конкурентность как параметр, а не константа.**

- **Решение:** значение по умолчанию повышается, но остаётся настраиваемым (точка перегрузки — в тактической спеке).
- **Альтернативы:** жёсткое константное значение, как сейчас.
- **Почему:** разные NAS имеют разный server-side concurrency budget; жёсткое значение либо медленное на одних, либо вызывает refusal на других.

## 11. Критерии готовности (strategic-level)

1. На ресурсе из 150..250 файлов первичный заход (cache miss) на типовом NAS показывает список с именами/размерами/типами в течение 1 секунды после tap'а.
2. Совокупное время до полного обогащения видимых строк не превышает 6000 мс на том же ресурсе — `ScanMetrics: SLOW SCAN detected` не срабатывает.
3. Один заведомо проблемный файл (имитация: видеоконтейнер, который ранее давал warn в логе) не задерживает обогащение остальных строк дольше per-file budget'а.
4. Лог скана большого SMB-каталога не содержит per-file warn'ов от metadata-extractor'ов — только агрегированную строку «N файлов попали в timeout-fallback», если таких файлов больше нуля.
5. Лог одной операции загрузки ресурса не содержит дублирующего листинга одного и того же `dirPath`.
6. Существующие сортировки и фильтры browse-экрана работают без регрессий: список, отображённый сразу после Phase-A, после Phase-B перестраивается без визуального «скачка» отсортированных позиций (видимая стабильность для NAME_ASC; для metadata-зависимых сортировок — задокументированное поведение).
