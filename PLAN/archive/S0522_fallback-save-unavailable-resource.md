## 1. Проблема

Когда пользователь выбрал ресурс назначения сетевого или облачного типа (SMB / SFTP / FTP / CLOUD), а этот ресурс в момент сохранения недоступен (нет сети, узел не отвечает, сорвалась авторизация), часть операций сохранения молча теряет результат. Это касается скриншотов, кадров из видео, фотоснимков с камеры, видеозаписи, записи с микрофона (диктофон) и загрузок из интернета. Пользователь совершил действие, рассчитывая получить файл, но файла нигде нет.

Сегодня поведение неоднородно: загрузка из интернета и сохранение кадра уже падают в локальный каталог Downloads, а скриншот при сбое записи в сетевой ресурс возвращает ошибку и никуда файл не пишет - результат теряется безвозвратно. Снимки/видео/аудио с камеры и микрофона при неудачной выгрузке в сеть тоже не имеют локального запасного пути.

Ожидание пользователя: если выбранный ресурс недоступен, программа сохраняет результат в каталог по умолчанию для соответствующего типа медиа (Downloads / Pictures / Movies / DCIM / запись) - тот, что был назначением «по умолчанию» до выбора сетевого ресурса, - вместо потери данных.

---

## 2. Цели

1. Ни одна операция сохранения (скриншот, загрузка из интернета, кадр из видео, фото с камеры, видеозапись, запись с микрофона) не теряет результат при недоступном ресурсе назначения.
2. При невозможности записать в выбранный ресурс результат гарантированно попадает в локальный каталог по умолчанию, подобранный по типу медиа.
3. Поведение fallback единообразно для всех перечисленных операций (общий контракт, а не шесть разных реализаций).
4. Пользователь информируется о том, что файл сохранён в запасной локальный каталог из-за недоступности выбранного ресурса, и куда именно.

**Non-goals:**

- Очередь отложенной выгрузки в недоступный ресурс с повторной попыткой после восстановления сети (возможное продолжение, вне этой итерации).
- Изменение виджет-диктофона, который сегодня вовсе не использует систему ресурсов (отдельный тикет).
- Приведение разовой выгрузки первого кадра GIF к системе ресурсов и scoped storage (отдельный тикет).
- Новые типы ресурсов назначения.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Запасной локальный каталог по типу медиа: изображения/скриншоты - публичная коллекция изображений, видео - публичная коллекция видео, аудио/запись - запись по умолчанию, прочие загрузки - Downloads.
2. Единая точка принятия решения «писать в выбранный ресурс или в запасной каталог», переиспользуемая всеми операциями сохранения.
3. Сообщение о fallback - ненавязчивое (тост/снэкбар), с указанием причины и фактического каталога.

### 3.2 Жёсткие ограничения

- **Flavor:** standard, noLegal, legacy - основные. photos - скриншоты и фото с камеры. lite - только фото с камеры (запись микрофона и видео отключены флагами `SUPPORT_MIC_RECORDING`/`SUPPORT_VIDEO`, сетевые/облачные ресурсы недоступны при `SUPPORT_LOCAL_NETWORK`/`SUPPORT_CLOUD = false`). Жест-скриншот - только noLegal (изоляция через source set). Логика fallback живёт в общем коде `src/main/`, флейвор-специфика не вводится; флейвор-гейтинг операций сохранения остаётся существующим.
- **API level:** минимум 23 (legacy), 26 (остальные). Запись в публичные каталоги обязана идти через MediaStore на API 29+ и через прямой файловый доступ с `WRITE_EXTERNAL_STORAGE` на более ранних. Запасной путь обязан соблюдать это во всех затронутых операциях.
- **Wear OS:** не затрагивается.
- **Производительность:** решение о fallback не должно добавлять заметную задержку перед сохранением; затратная сетевая проба до записи нежелательна (см. §6).
- **Совместимость данных:** без миграций хранилища; используются существующие поля настроек с идентификаторами ресурсов назначения.
- **Локализация:** EN/RU/UK - обязательно для всех новых строк уведомлений.
- **Доступность:** уведомление о fallback не полагается только на цвет; текст самодостаточен.

### 3.3 Owner inputs (Approval gate)

- **API level constraints:** запасная запись в публичные каталоги - через MediaStore на API 29+, прямой файловый доступ на API 23-28; обе ветви уже существуют в проекте и переиспользуются.
- **Flavor scope:** standard / noLegal / legacy / photos / lite - операции уже разграничены флагами сборки и source set; новый общий код в `src/main/` без флейвор-веток (CLAUDE.md Rule 15).
- **Performance budget:** fallback не добавляет блокирующую сетевую пробу на «горячем» пути; пред-отсев по состоянию транспорта сети + перехват ошибки записи (см. §6 п.1).
- **Localization:** новые строки уведомлений о fallback - EN/RU/UK в lockstep.
- **Communication policy:** тексты уведомлений соответствуют `docs/COMMUNICATION_POLICY.md` (тон-чеклист §6 политики - обязательный гейт перед интеграцией строк).
- **UI placement contract:** уведомление показывается как тост/снэкбар в контексте экрана, инициировавшего сохранение; для фоновых операций (жест-скриншот, фоновая загрузка) - системное уведомление status bar. Уведомление - только при fallback по недоступности ресурса, не при «ресурс не настроен».
- **Accessibility:** текст уведомления самодостаточен, без опоры на цвет.
- **Validation level:** сборка целевых флейворов + юнит-тесты на политику выбора назначения + ручная проверка на устройстве по каждой операции с отключённой сетью.

## 4. Контекст текущей архитектуры

Сохранение файла на ресурс проходит через доменный слой применения файловых операций и слой стратегий записи (локальный публичный каталог через системное медиахранилище либо прямая файловая запись; сетевой ресурс через выгрузку). Каждая из шести операций сохранения сегодня самостоятельно резолвит цель: читает идентификатор ресурса назначения из настроек, ищет ресурс в списке назначений и пытается записать. Признак доступности ресурса в модели существует, но выставляется только при ошибке навигации/сканирования во время просмотра и при резолве цели сохранения не учитывается.

Проблему из §1 нельзя решить точечно, потому что нет единой точки выбора «ресурс или запасной каталог»: часть операций имеет собственный inline-fallback в Downloads, часть не имеет его вовсе, а признак доступности и сетевой тип ресурса при выборе цели игнорируются. Логика запасной записи в публичные каталоги к тому же продублирована в нескольких местах с расхождениями в семантике перезаписи.

## 5. Предлагаемый подход

Ввести единый контракт разрешения цели сохранения и единый контракт результата, общий для всех шести операций. Контракт получает выбранный ресурс назначения и тип медиа, возвращает либо «писать в выбранный ресурс», либо «писать в запасной локальный каталог такого-то типа». Операции сохранения перестают самостоятельно решать про fallback - они спрашивают контракт и исполняют его решение, а итог записи (успех / fallback с причиной / отказ) возвращают в едином виде, пригодном для показа уведомления.

Запасная запись во всех операциях идёт через уже существующий слой стратегий локальной записи, корректно различающий публичные коллекции (через медиахранилище) и приватные пути, - вместо разрозненных собственных реализаций записи в Downloads.

### 5.1 Основные столпы / модули

- **Политика выбора цели сохранения.** Чистая, переиспользуемая логика: по выбранному ресурсу, его типу, текущему состоянию транспорта сети и типу медиа решает, использовать ли сетевой/облачный ресурс или сразу запасной локальный каталог. Пред-отсев: нет подходящего транспорта (Wi-Fi для локальной сети, любой интернет для облака) → запасной каталог без попытки записи.
- **Источник состояния сети.** Поставщик текущего состояния транспорта (Wi-Fi / интернет), на который опирается пред-отсев политики.
- **Единый результат сохранения с причиной fallback.** Общий тип результата: успех в ресурс, fallback в локальный каталог (с причиной: ресурс не настроен / недоступен / запись не удалась) и фактическим каталогом, отказ. Позволяет каждой операции единообразно решить, показывать ли уведомление.
- **Сопоставление тип медиа → запасной каталог.** Единая таблица: изображения/скриншоты, видео, аудио/запись, прочее - в свои публичные каталоги по умолчанию, с соблюдением правил scoped storage по уровню API.
- **Слой уведомления о fallback.** Единый текст и способ показа сообщения «сохранено в <каталог>, потому что <ресурс> недоступен», локализованный EN/RU/UK.

### 5.2 Потоки данных и событий

- Операция сохранения → политика выбора цели (выбранный ресурс + тип медиа + признак доступности) → решение «ресурс / запасной каталог».
- Запись в ресурс не удалась во время выполнения → перехват → запасная запись через слой локальных стратегий → единый результат с причиной.
- Единый результат → UI/инициатор операции → уведомление пользователю при фактическом fallback.

### 5.3 Точки расширяемости

- Контракт результата оставляет место для будущей причины «отложено в очередь» (на случай реализации повторной выгрузки после восстановления сети, см. Non-goals).
- Политика выбора цели открыта для подключения дополнительных операций сохранения (например, виджет-диктофон в отдельном тикете) без изменения её сигнатуры.
- Способ детекции недоступности (признак из модели против пробы записи) инкапсулирован в политике/операции и может быть ужесточён без изменения вызывающих мест.

## 6. Открытые вопросы / Research items

1. **Пред-проверка доступности против fallback по факту ошибки записи.**
   - **Вопрос:** определять недоступность ресурса заранее или писать и перехватывать ошибку?
   - **Решение:** гибрид. Состояние транспорта сети - дешёвый пред-отсев: при отсутствии подходящего транспорта все нелокальные ресурсы считаются недоступными и запись идёт сразу в запасной каталог (нет Wi-Fi → недоступны SMB/SFTP/FTP в локальной сети; нет интернета вообще → недоступны и облачные). Перехват ошибки записи остаётся как страховка для случаев, когда транспорт есть, но узел/авторизация всё равно не отвечают.
   - **Статус:** Resolved

2. **Достоверность признака доступности ресурса.**
   - **Вопрос:** можно ли полагаться на сохранённый признак доступности (выставляется только при ошибках просмотра/сканирования, может устареть)?
   - **Решение:** не полагаться на него как на единственный источник. Источник истины для пред-отсева - текущее состояние транспорта сети на момент сохранения (см. п.1); перехват ошибки записи применяется всегда, независимо от признака.
   - **Статус:** Resolved

3. **Уведомлять ли пользователя при каждом fallback.**
   - **Вопрос:** показывать ли сообщение всегда при fallback, или молчать в части случаев.
   - **Решение:** уведомлять только при fallback по недоступности ресурса. При «ресурс не настроен» (запись сразу в каталог по умолчанию) - не уведомлять. Тексты согласуются с `docs/COMMUNICATION_POLICY.md`.
   - **Статус:** Resolved

4. **Уведомление для фоновых операций.**
   - **Вопрос:** как уведомить о fallback при жест-скриншоте и фоновой загрузке, где нет активного экрана-инициатора.
   - **Решение:** системное уведомление (status bar) с причиной и фактическим каталогом. Для операций с активным экраном остаётся тост/снэкбар.
   - **Статус:** Resolved

5. **Фильтрация недоступных ресурсов в списке назначений.**
   - **Вопрос:** исключать ли недоступные ресурсы из списка назначений на уровне получения списка, или оставлять и полагаться на fallback при записи.
   - **Решение:** список назначений не фильтруется (исключение ломает прочих потребителей списка). Недоступность учитывается только в политике выбора цели в момент сохранения - через состояние транспорта сети и перехват ошибки записи.
   - **Статус:** Resolved

6. **Состав запасных каталогов.** Открытого вопроса нет - сопоставление типов задано в §3.1 и подтверждено существующими политиками назначения.

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|

## 9. Архитектурные решения (ADR)

**ADR-1: Единый контракт выбора цели и результата сохранения вместо per-flow fallback**

- **Решение:** ввести общую политику выбора цели и единый тип результата, переиспользуемые всеми операциями сохранения.
- **Альтернативы:** дописать inline-fallback в каждую операцию по образцу загрузки из интернета.
- **Почему:** шесть расходящихся реализаций уже дали неоднородность (молчаливая потеря скриншота против fallback загрузки); единый контракт устраняет дублирование и расхождения семантики.

**ADR-2: Запасная запись только через существующий слой локальных стратегий**

- **Решение:** все запасные записи идут через слой, различающий публичные коллекции и приватные пути.
- **Альтернативы:** сохранить отдельные реализации записи в Downloads в каждой операции.
- **Почему:** устраняет дублирование и риск нарушения scoped storage в части путей.

## 11. Критерии готовности (strategic-level)

1. При отключённой сети сохранение скриншота в сетевой ресурс кладёт файл в локальный каталог изображений по умолчанию, файл не теряется.
2. При отключённой сети сохранение кадра из видео, фото с камеры, видеозаписи и записи с микрофона в сетевой ресурс кладёт файл в соответствующий локальный каталог по умолчанию.
3. Загрузка из интернета при недоступном ресурсе сохраняется в локальный каталог и сообщает о fallback.
4. Во всех случаях fallback пользователь видит уведомление с причиной и фактическим каталогом (для фоновых операций - согласованным в §6 способом).
5. Запасная запись корректно работает на API 23-28 и API 29+ (scoped storage) на целевых флейворах.
