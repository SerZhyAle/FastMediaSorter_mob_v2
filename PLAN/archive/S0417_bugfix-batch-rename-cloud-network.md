## 1. Проблема

При выборе нескольких файлов в браузере и попытке пакетного переименования операция выполняется через локальный механизм файловой системы Java, который умеет работать только с локальными путями.

Для облачных ресурсов (Google Drive, Dropbox, OneDrive) и сетевых ресурсов (SMB, SFTP, FTP) такой механизм возвращает ошибку: файлы фактически не переименовываются, пользователь видит сообщение об ошибке для каждого файла.

Одиночное переименование того же файла проходит через общий слой файловых операций и работает для всех типов ресурсов. То есть поведение зависит от количества выбранных файлов, что не ожидаемо для пользователя.

Область - браузер файлов, диалог пакетного переименования.

---

## 2. Цели

1. Пакетное переименование работает для облачных и сетевых ресурсов так же, как одиночное.
2. Поведение переименования не зависит от количества выбранных файлов.
3. Сохраняется возможность отмены (undo) выполненного пакетного переименования.
4. Сохраняется мгновенное обновление списка без полной перезагрузки.
5. Сохраняется поэлементный отчёт об ошибках (какой файл не переименован и почему).
6. Длительная операция не блокирует UI-поток.

**Non-goals:**

- Изменение одиночного переименования - оно уже работает корректно.
- Изменение логики предзаполнения имени (исправлено отдельно).
- Новые возможности переименования (шаблоны, нумерация, массовые правила).

- **API level:** без API-специфики.
- **Wear OS:** не затрагивается.
- **Производительность:** операция переименования сетевых/облачных файлов выполняется вне UI-потока; UI остаётся отзывчивым.
- **Совместимость данных:** без изменения схемы хранения; формат записи отмены (undo) сохраняется.
- **Локализация:** EN/RU/UK - используются существующие строки результата и ошибок; новые строки только при необходимости.
- **Доступность:** диалог уже существует; поведение фокуса и клавиатуры не ухудшается.

### 3.3 Owner inputs (Approval gate)

- **UI placement contract:** существующий диалог пакетного переименования сохраняется без изменения расположения и состава полей; меняется только исполнительный механизм.
- **Accessibility:** поведение фокуса первого поля и показ клавиатуры сохраняются как сейчас.
- **Communication policy:** сообщения результата и ошибок соответствуют `docs/COMMUNICATION_POLICY.md`; переиспользуются существующие строки результата/ошибок переименования.
- **Validation level:** ручная проверка на устройстве для облака (Google Drive) и хотя бы одного сетевого протокола, плюс локальный пакет для регрессии.

## 4. Контекст текущей архитектуры

Файловые операции в приложении проходят через единый прикладной слой, который выбирает подходящую стратегию по типу пути (локальный, сетевой, облачный). Одиночное переименование в браузере и переименование из плеера используют этот слой, поэтому корректно работают для всех ресурсов.

Пакетное переименование в браузере исторически реализовано отдельно и напрямую вызывает локальный механизм файловой системы. Этот механизм не знает про облачные и сетевые схемы путей, поэтому возвращает отказ. Решить проблему «на месте» нельзя, не заменив исполнительный механизм на общий прикладной слой.

---

## 5. Предлагаемый подход

Перевести исполнение пакетного переименования на тот же прикладной слой файловых операций, который уже используется одиночным переименованием и общим диалогом переименования. Диалог как UI-элемент сохраняется; меняется только то, как выполняется собственно операция над каждым файлом.

### 5.1 Основные столпы / модули

- **Единый исполнитель переименования.** Пакетное переименование вызывает прикладной слой файловых операций по каждому выбранному файлу, а не локальный механизм файловой системы. Это устраняет зависимость от типа ресурса.
- **Сохранение побочных эффектов.** После успешного переименования по-прежнему формируется запись отмены, список обновляется точечно, а ошибки собираются и показываются пользователю поэлементно.
- **Асинхронность.** Поскольку прикладной слой выполняет сетевой/облачный ввод-вывод, цикл переименования выполняется вне UI-потока с возвратом результата в UI.

### 5.2 Потоки данных и событий

UI (диалог пакетного переименования) → прикладной слой файловых операций (по файлу) → результат успех/ошибка → обновление модели списка и записи отмены → агрегированный отчёт пользователю.

### 5.3 Точки расширяемости

- Исполнительный путь остаётся единым для одиночного и пакетного переименования, чтобы будущие типы ресурсов поддерживались автоматически.
- Формирование нового пути/имени после успешного переименования должно одинаково работать для локальных, сетевых и облачных схем.

## 6. Открытые вопросы / Research items

1. **Переиспользование общего диалога против правки текущего**
   - **Вопрос:** заменить ли отдельный диалог пакетного переименования на уже существующий общий диалог (который умеет несколько файлов через прикладной слой) или оставить текущий диалог и заменить в нём только исполнительный механизм?
   - **Варианты:** переиспользовать общий диалог; либо точечно заменить исполнение в текущем диалоге.
   - **Нужно выяснить:** различия в undo, мгновенном обновлении и отчёте об ошибках между двумя путями, чтобы не потерять текущее поведение браузера.
   - **Артефакт:** `S0417_bugfix-batch-rename-cloud-network/research/01__reuse-dialog-vs-patch-executor.md`
   - **Статус:** Resolved - сохранить текущий диалог, заменить только исполнитель на `FileOperationUseCase` (стратегия §5 и owner-контракт §3.3).

2. **Поведение отмены для сетевых и облачных переименований**
   - **Вопрос:** корректно ли запись отмены восстанавливает исходные имена для облачных/сетевых ресурсов через прикладной слой?
   - **Нужно выяснить:** поддерживает ли существующий путь отмены обратное переименование для этих схем.
   - **Артефакт:** `S0417_bugfix-batch-rename-cloud-network/research/02__undo-for-network-cloud.md`
   - **Статус:** Resolved - откат тоже использует `renameTo` (сломан для сети/облака); перевести на `FileOperationUseCase`, запись отмены хранит `(currentPath, originalName)`. Корректность облака проверить на устройстве.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Потеря текущего поведения undo при смене исполнителя | Средняя | Нельзя отменить пакетное переименование | Явно сохранить формирование записи отмены и проверить откат |
| Регрессия мгновенного обновления списка | Средняя | Список не обновляется без полной перезагрузки | Сохранить точечное обновление модели после каждого успеха |
| Частичный успех (часть файлов переименована, часть нет) | Средняя | Несогласованное состояние и непонятный отчёт | Поэлементный сбор результатов и агрегированный отчёт об ошибках |
| Блокировка UI на сетевом вводе-выводе | Низкая | Подвисание интерфейса | Выполнять цикл вне UI-потока |

## 9. Архитектурные решения (ADR)

**ADR-1: Единый исполнительный слой для одиночного и пакетного переименования**

- **Решение:** пакетное переименование исполняется через общий прикладной слой файловых операций.
- **Альтернативы:** расширить локальный механизм поддержкой сетевых/облачных схем (дублирование уже существующей логики стратегий).
- **Почему:** общий слой уже умеет выбирать стратегию по типу ресурса и протестирован на одиночном переименовании; дублировать его - лишний код и риск расхождения поведения.

## 11. Критерии готовности (strategic-level)

1. Пользователь выбирает несколько облачных файлов (Google Drive) и успешно переименовывает их одной операцией.
2. То же для как минимум одного сетевого протокола (SMB/SFTP/FTP).
3. Пакетное переименование локальных файлов продолжает работать без регрессий.
4. После пакетного переименования доступна отмена, возвращающая исходные имена.
5. Список обновляется без полной перезагрузки.
6. При частичном отказе пользователь видит, какие файлы не переименованы и почему.
