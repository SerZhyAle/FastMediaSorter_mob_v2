## 1. Проблема

При открытии сетевого SFTP-ресурса листинг каталога может зависнуть навсегда: пользователь видит бесконечный индикатор загрузки без прогресса, без файлов и без ошибки. В зафиксированном случае ресурс «Home ApeFlac» (SFTP, тип AUDIO) открывался дважды - и в плеере, и в браузере - и оба раза скан стартовал, создавал сессию и затем умолкал на ~90 секунд, пока пользователь не вышел вручную.

Триггер - смена активной сети ровно в момент старта скана (Wi-Fi → мобильный интернет). SMB-стек на это событие сбрасывает свои соединения, а SFTP-стек - нет: «полуоткрытый» сокет на уже мёртвом интерфейсе остаётся формально «подключённым», и блокирующее чтение листинга зависает. Поскольку прикладного таймаута на скан нет и ошибка в UI не пробрасывается, зависание ничем не прерывается и ничем не сигнализируется.

Затронутая область - слой доступа к сетевым ресурсам (SFTP) и общий конвейер сканирования медиафайлов.

---

## 2. Цели

1. Скан SFTP-ресурса завершается за ограниченное время в любом случае - успехом, либо понятной ошибкой, но никогда не зависает навсегда.
2. Смена активной сети инвалидирует SFTP-соединения так же, как уже делается для SMB (паритет поведения сетевых протоколов).
3. При таймауте или обрыве пользователь видит явное сообщение об ошибке с возможностью повторить, а не вечный индикатор загрузки.
4. Мёртвый/«полуоткрытый» транспорт обнаруживается проактивно, а не только реактивно по уже выброшенному исключению.

**Non-goals:**

- Переписывание SFTP-стека на другую библиотеку.
- Изменение логики листинга больших каталогов и прогрессивной отдачи результатов (отдельная тема).
- Исправление нормализации пути с буквой диска Windows (`/J:/..`) - выносится в отдельный тикет, если подтвердится на устройстве (см. §6).
- Аналогичная защита для FTP - вне объёма (рассмотреть отдельно, если воспроизведётся).

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Бюджет таймаута скана - разумный потолок выше штатного сокет-таймаута, чтобы нормальный листинг успевал отработать первым, а зависание прерывалось предсказуемо.
2. Сообщение об ошибке - в духе остальных сетевых ошибок приложения, с действием «повторить».
3. По возможности - переиспользовать уже существующий механизм принудительного сброса пула SFTP, а не вводить новый.

### 3.2 Жёсткие ограничения

- **Flavor:** все флейворы с поддержкой сетевых SFTP-ресурсов; исправление целиком в общем сетевом слое `src/main`, без флейвор-специфичных source set и без `BuildConfig.IS_*`-проверок.
- **API level:** без API-специфики; поведение одинаково на minSdk и выше.
- **Wear OS:** не затрагивается.
- **Производительность:** добавляемый таймаут и keep-alive не должны замедлять штатный быстрый листинг; стоимость keep-alive-пингов пренебрежимо мала.
- **Совместимость данных:** изменений формы хранимых данных нет.
- **Локализация:** новое сообщение об ошибке - EN/RU/UK обязательно.
- **Доступность:** сообщение об ошибке различимо не только цветом; действие «повторить» доступно с клавиатуры/D-pad.
- **Communication policy:** новый пользовательский текст об ошибке проходит чек-лист тона `docs/COMMUNICATION_POLICY.md` (§6 политики) как обязательный гейт перед интеграцией строк.

### 3.3 Owner inputs (Approval gate)

- **Communication policy:** новое сообщение о таймауте/обрыве SFTP-скана следует `docs/COMMUNICATION_POLICY*.md`; нейтральный тон, действие «повторить», без техножаргона (без «socket», «timeout exception»).
- **Validation level:** воспроизведение на устройстве со сменой сети Wi-Fi→LTE на SFTP-ресурсе + подтверждение, что скан завершается ошибкой за бюджет таймаута, а не зависает; плюс позитивный кейс на стабильном Wi-Fi.
- **Owner sign-off:** 2026-06-22.
- **Related tickets:** связь с S0046 (sftp-key-auth-hardening) и S0421 (windows-sftp-folder-share-companion) - тематическое соседство по SFTP, прямой зависимости нет. S0866 (2026-07-02, mass audit): подтверждённые P1-гонки в SftpConnectionPool (потеря каналов + TOCTOU сессий -> тихое исчерпание пула) - правдоподобный root cause зависших сканов; если девайс-тест по этому тикету снова покажет зависание, чинить сначала S0866.

## 4. Контекст текущей архитектуры

За доступ к сетевым ресурсам отвечает слой данных: пул SFTP-соединений выдаёт «арендованную» сессию сканеру, сканер выполняет блокирующий листинг каталога, а use-case сканирования собирает результат и отдаёт его в UI потоком списка файлов. Мониторинг состояния сети - отдельный компонент, на изменения которого уже подписан SMB-стек, сбрасывающий свои соединения при реконнекте.

Сейчас проблему нельзя решить «изнутри», потому что: SFTP-стек не подписан на смену сети и не инвалидирует свои сессии; на цепочке сканирования нет ни одного прикладного таймаута; единственный барьер - сокет-таймаут на уровне библиотеки - не покрывает фазу записи запроса на «полуоткрытом» сокете; а конвейер сканирования отдаёт в UI только список файлов без канала ошибок, поэтому зависание не превращается ни в исключение, ни в сообщение.

## 5. Предлагаемый подход

Закрыть инцидент двумя обязательными изменениями (паритет сетевой инвалидации + прикладной таймаут с пробросом ошибки) и усилить устойчивость двумя необязательными (проактивный keep-alive, чистка мёртвой константы). Всё - на уровне ролей в общем сетевом слое, без флейвор-специфики.

### 5.1 Основные столпы / модули

**Столп A - Инвалидация SFTP при смене сети (обязательный).**
SFTP-стек подписывается на тот же сигнал смены сети, что и SMB, и при срабатывании принудительно сбрасывает свой пул соединений. Цель - закрыть «полуоткрытый» сокет на мёртвом интерфейсе, чтобы блокирующий листинг получил исключение и сработала уже существующая логика реконнекта. Требование - переиспользовать существующий механизм принудительного сброса пула, а не вводить новый канал.

**Столп B - Прикладной таймаут скана с каналом ошибки (обязательный).**
Операция листинга в рамках скана получает верхний потолок по времени. По истечении - скан прерывается и в UI приходит доменная ошибка вместо молчания. Конвейер сканирования получает явный канал ошибок (результат с состоянием успех/ошибка), чтобы таймаут и любой обрыв становились видимым сообщением. Это страхует от любых будущих сценариев «полуоткрытого» сокета, а не только от смены сети.

**Столп C - Проактивное обнаружение мёртвого транспорта (усиление).**
SFTP-сессия настраивается на периодические keep-alive-пинги с ограничением числа неответов, чтобы мёртвый транспорт ронял сессию сам за десятки секунд - снижая зависимость от внешней инвалидации.

**Столп D - Гигиена (усиление).**
Удаление мёртвой дублирующей константы сокет-таймаута, создающей ложную уверенность, что листинг защищён.

### 5.2 Потоки данных и событий

- Смена сети: мониторинг сети → SFTP-стек (новая подписка) → принудительный сброс пула → закрытие мёртвых сокетов.
- Скан: UI → use-case сканирования (таймаут-обёртка) → пул SFTP → листинг каталога. Любой обрыв/таймаут → канал ошибки use-case → UI показывает ошибку с «повторить».
- Keep-alive: фоновые пинги сессии → при превышении числа неответов сессия падает с исключением → реактивная логика реконнекта.

### 5.3 Точки расширяемости

- Бюджет таймаута и параметры keep-alive - конфигурируемые значения, потенциально единые для всех сетевых протоколов.
- Канал ошибок use-case сканирования - общий, переиспользуемый другими сетевыми сканерами (SMB, FTP), чтобы единообразно сообщать о сбоях.
- Подписка на смену сети - архитектурно та же абстракция, что уже используется SMB; новых интерфейсов в `src/main` это не требует, но проводка зависимости уточняется на тактическом уровне.

## 6. Открытые вопросы / Research items

1. **Корневая причина и механизм зависания**
   - **Вопрос:** где именно паркуется корутина и почему не срабатывает сокет-таймаут?
   - **Нужно выяснить:** подтвердить по коду цепочку листинг → пул → use-case и отсутствие таймаутов/инвалидации.
   - **Статус:** Resolved
   - **Артефакт:** `PLAN/S0624_bugfix-sftp-scan-hang-network/research/01__root-cause-analysis.md`

2. **Воспроизводится ли без смены сети**
   - **Вопрос:** зависает ли тот же ресурс на стабильном Wi-Fi (без Wi-Fi→LTE)?
   - **Нужно выяснить:** если на стабильной сети зависание уходит - подтверждает, что первопричина именно отсутствие инвалидации при смене сети.
   - **Статус:** Open - проверка на устройстве (гейт `BlockNeedUserTest`), не блокирует код-фикс.

3. **Валидность пути `/J:/MEDIA/apeflac`**
   - **Вопрос:** возвращает ли сервер листинг для пути с буквой диска Windows за ведущим слешем, или молча не отвечает?
   - **Нужно выяснить:** проверить сторонним SFTP-клиентом; если сервер молчит - это вторая независимая причина «тишины», требующая отдельного фикса нормализации пути.
   - **Статус:** Out of scope - non-goal §2 (нормализация пути выносится в отдельный тикет при подтверждении на устройстве). Не блокирует данный фикс.

4. **Размер каталога и прогрессивная отдача**
   - **Вопрос:** не является ли «тишина» следствием огромного рекурсивного дерева без промежуточного прогресса?
   - **Нужно выяснить:** число файлов в каталоге и поведение при включённом/выключенном обходе подпапок.
   - **Статус:** Open - проверка на устройстве (валидирует бюджет watchdog-таймаута против легитимного большого листинга), не блокирует код-фикс.

5. **Безопасность принудительного сброса под активной арендой**
   - **Вопрос:** корректно ли сброс пула прерывает запаркованный листинг, удерживающий мьютекс канала и активную аренду, без само-дедлока?
   - **Нужно выяснить:** перед проводкой Столпа A проверить, что сброс не ждёт того же мьютекса; при необходимости - форс-закрытие сокета в обход мьютекса.
   - **Статус:** Resolved - `disconnectAll()` берёт только `poolMutex` (свободен у запаркованного скана), не `pc.mutex`; форс-закрытие сокета разблокирует `ls`. Дедлока нет.
   - **Артефакт:** `PLAN/S0624_bugfix-sftp-scan-hang-network/research/05__forced-reset-lease-safety.md`

## 9. Архитектурные решения (ADR)

**ADR-1: Паритет инвалидации сетевых соединений при смене сети**

- **Решение:** SFTP-стек подписывается на смену сети и сбрасывает пул так же, как это уже делает SMB.
- **Альтернативы:** полагаться только на сокет-таймаут; полагаться только на keep-alive.
- **Почему:** сокет-таймаут не покрывает «полуоткрытый» сокет на мёртвом интерфейсе (подтверждено логом - тишина >90 с при таймауте 30 с); keep-alive реактивен и медленнее. Явная инвалидация при смене сети - прямое устранение первопричины и единообразие с уже работающим SMB.

**ADR-2: Прикладной таймаут поверх библиотечного как обязательная страховка**

- **Решение:** обернуть скан в прикладной таймаут с каналом ошибки в UI независимо от инвалидации.
- **Альтернативы:** доверять только инвалидации + библиотечному таймауту.
- **Почему:** инвалидация устраняет известный триггер, но «полуоткрытый» сокет может возникнуть и по другим причинам; прикладной таймаут гарантирует завершимость скана в любом сценарии и превращает молчание в сообщение.

## 11. Критерии готовности (strategic-level)

1. На SFTP-ресурсе при смене активной сети во время открытия скан завершается за ограниченное время понятной ошибкой, а не вечным индикатором загрузки.
2. На стабильной сети открытие того же ресурса проходит штатно, без регресса скорости листинга.
3. При обрыве/таймауте пользователь видит сообщение об ошибке с возможностью повторить (EN/RU/UK).
4. После смены сети повторное открытие ресурса успешно создаёт новую рабочую сессию (нет «залипших» мёртвых соединений).
