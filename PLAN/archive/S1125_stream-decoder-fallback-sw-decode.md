## 1. Проблема

На внутреннем плеере интернет-стримов (третьесторонние live HLS/RTSP) не включён decoder fallback: при отказе инициализации аппаратного декодера воспроизведение не переигрывается на альтернативном (в т.ч. программном) декодере, а падает в «канал недоступен» либо застывшую картинку. Все прочие пути воспроизведения (файлы, cloud, SMB/FTP/SFTP, фоновое радио) уже строят проигрыватель с общей фабрикой рендереров, где fallback включён, а extension-рендерер предпочтён. Параллельно headless-грабер превью для сетки каналов декодирует аппаратно и конкурирует с реальным плеером за общий пул GPU decode-surface - именно это голодание surface (а не пропускная способность) по данным инструментального аудита соседнего плеера является основной причиной «зависаний» на банке стримов.

---

## 2. Цели

1. Внутренний стрим-плеер строится с тем же профилем рендереров (decoder fallback ON, extension PREFER), что и остальные пути воспроизведения.
2. Отказ инициализации аппаратного декодера на живом стриме автоматически переигрывается на альтернативном (в т.ч. программном) декодере вместо surfacing ошибки «канал недоступен».
3. Headless-грабер превью декодирует программно и не отбирает аппаратные decode-surface у одновременно играющего реального плеера.

**Non-goals:**

- Логика буферизации / переподключения / трекинга живого края - объём S1083; здесь не меняется.
- Радио/аудио-путь - объём S1118 (`RadioStreamBufferConfig`), отдельный аудиоплеер.
- Диагностика декодера (имя HW/SW, dropped/rendered frames, time-to-first-frame) - объём S1127.
- Отгружаемый программный видео-extension-декодер как backstop - объём S1126.
- Adaptive step-down качества (S1128), stall-recovery/rebuffer (S1131), изменения persist/eviction превью (S1129/S1130).

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Форсить программный видео-декод только для измеренно-проблемных стримов, а не глобально: на мобильном SW-декод стоит CPU/батареи/нагрева. Для первой итерации достаточно fallback ON + extension available на реальном плеере; рантайм-детект «проблемного» стрима откладывается на S1127 (diagnostics).

### 3.2 Жёсткие ограничения

- **Flavor:** путь в `src/main`; охват наследуется от существующего стрим-плеера (гейт `streamProtocolSupport` / SUPPORT_STREAMS). Отдельного flavor-разветвления не вводится - общая фабрика рендереров уже используется всеми путями во всех сборках.
- **API level:** без API-специфики.
- **Wear OS:** не затрагивается.
- **Производительность:** SW-декод только в headless-грабере (короткоживущий, один кадр); реальный плеер остаётся hardware-first с fallback, без постоянного SW-оверхеда.
- **Совместимость данных:** без изменений формата/хранения.
- **Локализация:** EN/RU/UK - без новых видимых строк (внутреннее изменение воспроизведения).

## 4. Контекст текущей архитектуры

За воспроизведение отвечает UI-слой player-хелперов: оркестратор менеджера видеоплеера и набор extension-функций `play*Video`, каждая из которых строит собственный `ExoPlayer` под свой источник. Все, кроме стрим-пути, передают в билдер общую фабрику рендереров с включённым decoder-fallback и предпочтением extension-рендерера; стрим-путь исторически собрал билдер вручную (loadControl / bandwidthMeter / audioAttributes) и фабрику не подключил, унаследовав дефолтный профиль с выключенным fallback. Грабер превью в streams-слое строит отдельный короткоживущий `ExoPlayer` для снятия первого кадра тайла и тоже не задаёт профиль декодирования, получая аппаратный по умолчанию. Решить проблему из §1 «на месте» нельзя без явного подключения общего профиля рендереров к обоим билдерам и без выбора программного профиля для грабера.

## 5. Предлагаемый подход

### 5.1 Основные столпы / модули

- **Единый профиль рендереров реального плеера.** Стрим-плеер использует ту же фабрику рендереров (decoder fallback ON, extension PREFER), что и прочие пути воспроизведения - без дублирования конфигурации.
- **Программный профиль грабера.** Headless-грабер строит рендереры с предпочтением программного видео-декодера, чтобы не занимать аппаратные decode-surface и уйти с проблемных HW-декодеров.

### 5.2 Потоки данных и событий

- Открытие стрима → билдер плеера получает общую фабрику рендереров → при отказе инициализации HW-декодера media3 сам переигрывает на доступном альтернативном/программном декодере, без surfacing ошибки пользователю.
- Запрос превью тайла → грабер строит плеер с программным профилем → первый кадр → снятие bitmap → release; без конкуренции с реальным плеером за HW decode-surface.

### 5.3 Точки расширяемости

- Порог «форсить SW только для измеренных проблемных стримов» и рантайм-детект HW/SW через `AnalyticsListener` - точка расширения S1127, не в объёме первой итерации.
- Отгружаемый программный видео-extension как набор доставки - точка расширения S1126; общая фабрика уже сплайсит доставленный FFmpeg DTS (S0386), тот же механизм.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| SW-декод в грабере медленнее HW и не успевает снять первый кадр за таймаут | Средняя | Часть тайлов остаётся на favicon | Сохранить существующий 12s-таймаут и graceful favicon-fallback; SW только в грабере, не в реальном плеере |

## 11. Критерии готовности (strategic-level)

1. Внутренний стрим-плеер воспроизводит live HLS/RTSP и при отказе HW-декодера продолжает через альтернативный декодер, а не показывает «канал недоступен».
2. Профиль рендереров стрим-плеера совпадает с остальными путями воспроизведения (fallback ON, extension PREFER).
3. Headless-грабер снимает превью, не отбирая HW decode-surface у одновременно играющего реального плеера (нет всплеска dropped frames в реальном плеере при активной сетке).
4. На реальном устройстве с проблемным HW-декодером (Samsung/Exynos) грабер не роняет процесс нативно.
5. Регрессия отсутствует: радио/аудио, файлы, cloud, SMB/FTP/SFTP воспроизводятся как прежде.
