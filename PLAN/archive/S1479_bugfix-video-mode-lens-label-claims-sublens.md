## 0. Захваченный материал (inbox)

**Захвачено во время:** S1457

**Текст:**

В видеорежиме подпись объектива обещает субобъектив, которого в потоке нет. CameraUseCaseFactory.applyPhysicalCameraId() возвращает builder без изменений при videoMode (строки 84-89), а CameraCaptureSessionManager.applyMode() при переключении фото->видео не сбрасывает activeCameraIndex. Пользователь выбирает ультраширок 0.5x, переключается в видео - оптика молча становится основной, а подпись и множитель зума продолжают показывать 0.5x, потому что CameraCapabilityProbe берёт zoomMultiplier из устаревшего activeLens.equivalentMultiplier. Достижимо только на API 28+ с фьюзными многообъективными камерами.

## 2. Корневая причина

- Перечисление предлагает физический субобъектив отдельной позицией: `CameraLensEnumerationManager.select()` оставляет все логические камеры плюс каждый субобъектив, дающий кратность, которой ни одна из них не покрывает.
- Фотоконвейер эту позицию действительно исполняет: `CameraUseCaseFactory.applyPhysicalCameraId()` называет физический id и на `Preview`, и на `ImageCapture`.
- Видеоконвейер её исполнить не может: `VideoCapture.withOutput()` не даёт `ExtendableBuilder`, поэтому `applyPhysicalCameraId()` в видеорежиме - задокументированный no-op, и он выключает себя в том числе для `Preview`. И видоискатель, и запись идут с оптики логической камеры по умолчанию, то есть с основного объектива.
- Никто не приводит выбор в соответствие: `applyMode()` сбрасывает только фото-интенты (ночь, HDR, боке, спорт), а `activeCameraIndex` продолжает указывать на позицию субобъектива.
- Снимок возможностей строится по этой позиции: `bindToLifecycle()` передаёт её в `CameraCapabilityProbe.probe()`, который берёт `zoomMultiplier` из `activeLens.equivalentMultiplier`, и рядом кладёт `activeLensIsWidest` / `activeLensIsMacro`, посчитанные от той же записи.
- `CameraZoomControlsManager` рисует подпись и кратность из этого снимка - отсюда «ультраширокий» и 0.5x поверх потока с основного объектива.
- Достижимо только на API 28+ (`physicalCameraInfos` закрыт проверкой `Build.VERSION_CODES.P`) и только на фьюзной многообъективной камере, чей субобъектив пережил дедупликацию S1261.

---

## 3. Исправление

Одна точка приведения - индекс, разрешаемый непосредственно перед привязкой.

- Новая приватная top-level функция `bindableIndex()` в `CameraCaptureSessionManager.kt`: в видеорежиме позиция субобъектива разрешается в его логического родителя, в фоторежиме и для логической позиции - тождество. Top-level, а не метод класса, потому что класс упирается в потолки detekt `LargeClass` и `TooManyFunctions` (S1457).
- Вызов в `bindToLifecycle()` - закрывает все пути привязки разом: первичный `bind()` при уже включённом видеорежиме, `applyMode()`, `applyMacro()` и откат после отказа объектива открыться.
- Вызов в `bindLens()` - чтобы перебор объективов, приводящий к уже привязанному родителю, был честным no-op, а не лишней перепривязкой со сбросом всех пер-объективных интентов.
- Родитель в списке есть всегда: `select()` оставляет логические камеры безусловно. Если его всё же не окажется, индекс остаётся прежним - без падения и без изменения текущего поведения.

Намеренно вне рамок:

- Возврат выбранного в фоторежиме субобъектива при переключении видео -> фото. Сегодня этот выбор в видео и так молча игнорируется, так что ничего работающего не теряется, а память объектива между режимами - отдельное решение.
- Попытка заставить видеоконвейер реально привязать субобъектив: API `camera-video` не принимает физический id ни в одной точке.
