## 1. Проблема

Приложение запрашивает runtime-разрешения точечно и разрозненно: каждый новый экран или функция показывает системный диалог в произвольный момент без объяснения причины. Количество разрешений велико и варьируется в зависимости от версии Android (API 26–35+) и сборки (standard / lite / photos / legacy / vr). Пользователь не понимает, зачем запрашивается то или иное право, и нередко отказывает — что молча ломает связанный функционал. Повторный запрос после отказа ограничен системой Android и требует отдельной логики «отправить в настройки».

Отдельная проблема — первый запуск: пользователь сразу попадает в основной UI без какого-либо введения. Приложение не объясняет, какие возможности оно открывает и каких прав для этого попросит. Системные диалоги Android появляются «из ниоткуда» и воспринимаются как неожиданные и подозрительные.

Ситуация усугубляется внедрением новых функций, таких как запись с микрофона (S0100) и поддержкой новых версий ОС (Android 17 Local Network, S0035). Продолжение практики точечных запросов ведёт к дублированию кода и ухудшению UX.

---

## 2. Цели

1. При первом запуске пользователь видит Welcome-экран: краткое описание возможностей приложения и полный список запрашиваемых разрешений с объяснением каждого — до того, как появится первый системный диалог.
2. С Welcome-экрана пользователь может выдать или отозвать разрешения не покидая его — либо через встроенные переключатели (если Android позволяет), либо через кнопки-переходы к системному диалогу для каждого пункта.
3. Необязательные разрешения явно помечены как таковые; пользователь понимает, что может отказать без потери основного функционала.
4. Разрешения, связанные с конкретной опцией (микрофон для аудиозаписи, внешнее хранилище для определённого типа медиа и т.п.), запрашиваются контекстно — в первый раз, когда пользователь включает соответствующую настройку или впервые обращается к функции.
5. Повторный запрос после системного отказа обрабатывается единообразно: один раз показывается объяснение с переходом в настройки системы, больше не надоедает.
6. Существующие и новые разрешения (S0100: `RECORD_AUDIO`, S0035: `ACCESS_LOCAL_NETWORK`, `CAMERA`, `POST_NOTIFICATIONS` и хранилище) интегрируются в единый реестр, устраняя дублирование логики в UI-слое.

**Non-goals:**

- Реализация самих фич (например, логики записи с микрофоном — это S0100).
- Изменение манифестных разрешений или их набора по флейворам.
- Поддержка pre-API-26 (legacy минимум 23 — рассмотреть отдельно в research).

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Welcome-экран при первом запуске: короткий pitch приложения (2–3 строки) + секция разрешений ниже.
2. Группировка разрешений по тематическим блокам (медиа, сеть/cloud, система, микрофон и т.д.).
3. Каждое разрешение — иконка + название + одна строка зачем + индикатор статуса (выдано / не выдано / не применимо на этом устройстве).
4. Способ выдачи права с Welcome-экрана: предпочтительно кнопка-переход к системному диалогу для каждого пункта; встроенный тоггл — если API это позволяет без побочных эффектов (исследовать в §6).
5. Экран запроса должен быть доступен повторно из настроек приложения («Управление разрешениями»).
6. Поддержка TV/keyboard — без жёсткой привязки к тач-жестам.

### 3.2 Жёсткие ограничения

- **Flavor:** все пять (standard, lite, photos, legacy, vr); набор разрешений и описаний должен строго соответствовать включённым фичам каждого флейвора. VR-флейвор имеет собственные платформенные разрешения (отслеживание рук, passthrough-камера) — они должны присутствовать в реестре только для vr-сборки.
- **API level:** minSdk 26 (standard/lite/photos); minSdk 23 (legacy) — нужно выяснить, какие разрешения требуют отдельного пути на API < 26.
- **Wear OS:** не затрагивается.
- **Производительность:** экран разрешений — редкий кейс (онбординг + контекстные точки), требования к скорости минимальные.
- **Совместимость данных:** нет миграций схемы базы данных; нужно только хранить флаг «уже показали контекстный запрос для X» — достаточно постоянного хранилища предпочтений.
- **Локализация:** EN / RU / UK — все строки описаний обязательны во всех трёх локалях.
- **Доступность:** кнопки должны иметь достаточный touch target; элементы списка озвучиваются TalkBack с полным описанием, а не только названием разрешения.

## 4. Контекст текущей архитектуры

Runtime-разрешения сейчас запрашиваются непосредственно в точках использования — как правило, в UI-слое (активити / фрагменты) или в хелперах, вызываемых из UI. Единой точки регистрации и отслеживания разрешений нет; каждый запрос реализован самостоятельно. Это означает, что при добавлении нового разрешения (например, микрофон в S0100 или локальная сеть в S0035) разработчик пишет очередной изолированный запрос с дублированием шаблонного кода.

Приложение уже имеет развитый слой Settings, через который пользователь включает опциональные функции (например, «Аудио -> Микрофонные записи» в S0100) — именно здесь возникают «контекстные точки» для запроса связанных разрешений. Сейчас эта связь не формализована.

## 5. Предлагаемый подход

Центральный реестр разрешений: каждое разрешение описывается один раз — название, причина, флейвор-ограничение, контекстная точка (если есть), необязательность. Логика запроса и обработки результата (включая «отправь в настройки Android») сосредоточена в одном компоненте слоя приложения, а не размазана по UI.

### 5.1 Основные столпы

**Реестр разрешений** — декларативный источник истины: какие разрешения существуют, для каких флейворов, к какому тематическому блоку относятся, обязательные ли они, минимальный API. В реестр сразу войдут хранилище, камера, микрофон (S0100), локальная сеть (S0035) и уведомления.

**Welcome-экран (первый запуск)** — полноэкранный onboarding, показывается ровно один раз при первом старте приложения. Состоит из двух частей:
- *Верх* — краткое представление приложения: что оно делает и чем полезно (2–3 строки + иллюстрация или логотип).
- *Низ* — список разрешений из реестра, применимых к текущей сборке, сгруппированных по блокам. Каждая строка: иконка + название + зачем + кнопка действия.

Кнопка действия для каждого разрешения работает в одном из двух режимов (выбор — по итогам research п. 6.4):
- **Режим A (предпочтительный):** кнопка «Разрешить» → системный диалог Android → пользователь возвращается, строка обновляет статус.
- **Режим B:** встроенный тоггл-переключатель, который внутри вызывает тот же системный диалог; визуально компактнее, но требует проверки поведения на разных API.

Внизу экрана — кнопка «Продолжить» (активна всегда; необязательные разрешения не блокируют переход).

**Контекстный запрос** — при первом включении опции в настройках (или первом использовании функции) проверяется, выдано ли нужное разрешение. Если нет — показывается bottom sheet с пояснением и кнопкой «Разрешить» (тот же Режим A/B). Срабатывает ровно один раз; повторно не надоедает. Пример: включение опции записи аудио в настройках триггерит запрос `RECORD_AUDIO`.

**Обработчик отказа** — единая логика: если Android вернул «denied + don't ask again», показывается inline-объяснение с кнопкой «Открыть настройки системы». Без повторных попыток.

**Экран управления разрешениями в Settings** — повторяет список Welcome-экрана с актуальными статусами; доступен в любой момент. Кнопка «Открыть настройки системы» для каждого пункта.

### 5.2 Потоки данных и событий

**Первый запуск:**
- пользователь видит Welcome-экран (pitch + список разрешений с кнопками)
- кнопка «Разрешить» у пункта открывает системный диалог Android; после возврата строка обновляет статус
- кнопка «Продолжить» переводит в основной UI

**Включение опции X в Settings (например, запись с микрофона):**
- проверяется реестр; если нужное право не выдано, показывается контекстный bottom sheet с пояснением
- кнопка «Разрешить» открывает системный диалог; результат записывается; запрос больше не повторяется

**Повторный отказ (denied + don't ask again):**
- показывается inline-объяснение с кнопкой «Открыть настройки системы»
- повторных системных диалогов нет

**Открытие «Управление разрешениями» (Settings):**
- читается реестр и живой статус прав; список отображается с кнопками перехода в настройки системы

### 5.3 Точки расширяемости и миграция

- Добавление нового разрешения = одна запись в реестре + строки локализации. Логика запроса не трогается.
- Контекстные точки (места в Settings/фичах, откуда триггерится запрос) регистрируются отдельно и не захламляют UI-код.
- При реализации S0101 потребуется рефакторинг: существующие ad-hoc запросы в фичах (камера, микрофон из S0100, локальная сеть из S0035) заменяются на обращение к новому реестру.

## 6. Открытые вопросы / Research items

1. **Полный список runtime-разрешений по флейворам**
   - **Вопрос:** какие именно разрешения запрашивает приложение сейчас в каждом флейворе и на каких API уровнях?
   - **Нужно выяснить:** составить точный список. Известные: Storage, `RECORD_AUDIO` (S0100), `ACCESS_LOCAL_NETWORK` (S0035, API 37+), `POST_NOTIFICATIONS` (API 33+); VR-специфичные: отслеживание рук (Meta Quest, опционально), passthrough-камера (Horizon OS v74+, опционально). Обход AndroidManifest всех флейворов (включая `src/vr/`) + поиск точек запроса по кодовой базе.
   - **Статус:** Resolved — список составлен по манифестам. `READ_MEDIA_*` / `READ_EXTERNAL_STORAGE` = required (без них браузинг и воспроизведение локальных файлов недоступны). `MANAGE_EXTERNAL_STORAGE`, `MANAGE_MEDIA` = optional. VR: `HAND_TRACKING`, `HEADSET_CAMERA` = optional, только vr-флейвор. `CAMERA` в манифестах отсутствует.

2. **Поведение на API 23–25 (legacy)**
   - **Вопрос:** есть ли разрешения, которые на API < 26 предоставляются автоматически (install-time) и не требуют runtime-запроса? Нужно ли онбординг-экрану учитывать это..
   - **Нужно выяснить:** сравнение permission groups до и после API 26; проверить манифест legacy-флейвора.
   - **Статус:** Resolved — поле `minSdk` в каждой записи реестра достаточно. Специального пути для API 23–25 не нужно: `MANAGE_EXTERNAL_STORAGE` / `MANAGE_MEDIA` просто не появятся в отфильтрованном списке.

3. **UX-паттерн Welcome-экрана: один экран vs. пошаговый wizard**
   - **Вопрос:** лучше показать все разрешения сразу на одном скроллируемом экране или вести пошагово?
   - **Варианты:** (а) единый скроллируемый экран — быстро и прозрачно, пользователь видит масштаб сразу; (б) wizard «шаг за шагом» — понятнее для каждого права, но дольше; (в) только обязательные + «дополнительные» collapsed по умолчанию.
   - **Нужно выяснить:** решение владельца; предварительная рекомендация — вариант (а) или (в), т.к. wizard раздражает при большом числе шагов.
   - **Статус:** Resolved — **Вариант Б**: после завершения wizard пользователь переходит на отдельный полноэкранный экран разрешений (`PermissionsManagementFragment`). Тот же экран вызывается из настроек по кнопке, заменяя все существующие отдельные кнопки разрешений.

4. **Режим взаимодействия: кнопка-переход vs. встроенный тоггл**
   - **Вопрос:** можно ли технически реализовать тоггл-переключатель, который показывает системный диалог и сразу отражает результат, без артефактов на разных версиях Android (особенно API 29–34)?
   - **Варианты:** (а) Режим A — простая кнопка «Разрешить» → системный диалог → обновление строки; (б) Режим B — тоггл, визуально привычнее, но требует корректного round-trip через механизм обратного вызова.
   - **Нужно выяснить:** проверить поведение механизма обратного вызова при возврате из системного диалога разрешений, особенно в случае «don't ask again» — тоггл не должен застревать в неверном состоянии.
   - **Статус:** Resolved — **Режим A (кнопки)**. Встроенный тоггл отклонён: Android не позволяет выдавать разрешения без системного диалога ни на каком API. На экране — список с кнопкой-статусом + кнопка **«Выдать все недостающие»** (батч через `requestMultiplePermissions`) + кнопка **«Открыть настройки системы»** (OS-тогглы там).

5. **Хранение флага «контекстный запрос показан»**
   - **Вопрос:** SharedPreferences или DataStore? Нужна ли миграция существующих флагов (если они уже где-то есть)?
   - **Нужно выяснить:** проверить, есть ли уже разбросанные boolean-флаги «shown_X_rationale».
   - **Статус:** Resolved — `SharedPreferences`. `WelcomeViewModel` уже использует их; DataStore не даёт выгоды при такой частоте записи. Новые флаги идут в отдельный prefs-файл `perm_rationale_prefs`.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Реестр разрешений устаревает при добавлении новых фич | Средняя | Пользователь видит неполный список или не получает нужного запроса | Добавление разрешения в реестр делается обязательным шагом чеклиста для каждой фичи |
| Android меняет модель разрешений в новых API (уже было с MANAGE_EXTERNAL_STORAGE, NEARBY_WIFI, ACCESS_LOCAL_NETWORK и т.д.) | Средняя | Логика онбординга ломается на новой версии ОС | Реестр хранит минимальный/максимальный API для каждого разрешения; при обновлении compileSdk — обязательное ревью реестра |
| Пользователь дал разрешение вне приложения (через настройки системы) — состояние рассинхронизировано | Низкая | Экран показывает разрешение как «не выдано» пока приложение не перезапустить | Читать живой статус через системный API проверки разрешений при каждом открытии экрана настроек |

## 9. Архитектурные решения (ADR)

**ADR-1: декларативный реестр вместо разрозненных точечных запросов**

- **Решение:** единый источник описания разрешений; логика запроса централизована.
- **Альтернативы:** оставить точечные запросы, добавив к каждому только строку-пояснение.
- **Почему:** при точечном подходе дублирование кода обработки отказа неизбежно; реестр позволяет вписывать новые разрешения (такие как `RECORD_AUDIO` из S0100) без копипасты и даёт экран «управление разрешениями» почти бесплатно.

---

## 10. Связи с другими спеками

- **S0100** (`mic-recording-in-browse`, Tactical) — вводит запрос `RECORD_AUDIO`. Поскольку S0100 находится в статусе Tactical, она реализует собственный ad-hoc запрос микрофона. При реализации S0101 логика из S0100 должна быть мигрирована на новый единый реестр.
- **S0035** (`android17-local-network-permission`, Tactical) — вводит запрос `ACCESS_LOCAL_NETWORK`. Аналогично подлежит миграции на новый реестр разрешений.

---

## 11. Критерии готовности (strategic-level)

1. При первом запуске пользователь видит Welcome-экран: pitch приложения + полный список разрешений с объяснением и кнопками действия — до появления первого системного диалога.
2. Пользователь может выдать любое разрешение прямо с Welcome-экрана, не закрывая его; строка немедленно обновляет статус после возврата из системного диалога.
3. Кнопка «Продолжить» на Welcome-экране активна всегда — ни одно разрешение не является обязательным для входа в приложение.
4. Включение опции (например, «запись голосовых заметок» из S0100) в первый раз триггерит контекстный запрос нужного права с пояснением — без повторного надоедания после отказа.
5. В настройках доступен экран «Управление разрешениями», показывающий актуальный статус всех прав с кнопками для исправления.
6. Существующие ad-hoc запросы (S0100, S0035, камера) успешно переведены на использование нового реестра.
7. Добавление нового разрешения в будущем не требует изменений в UI-коде — только запись в реестр + строки локализации.
8. Все строки пояснений переведены на EN / RU / UK.
