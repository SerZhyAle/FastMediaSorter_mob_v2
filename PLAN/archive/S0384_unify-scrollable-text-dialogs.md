**Roadmap entry:** Ad-hoc - запрос 2026-06-07

---

## 1. Проблема

Показ блока read-only прокручиваемого текста с кнопками действий (заголовок, выделяемый текст, копировать/отправить/закрыть) реализован в проекте несколькими параллельными путями: первичный диалог детального текста/ошибки (≈15 вызовов) и вторичная утилита прокручиваемого диалога (≈9 вызовов) - это почти дубликаты, живущие в двух разных макетах и трёх кодопутях.

Из-за дублирования визуальные и поведенческие правки приходится вносить в нескольких местах, они расходятся (разные шрифты, ширина, семантика закрытия, тема диалога), а улучшение оформления одного пути не доходит до другого.

Рядом накопился мёртвый груз: одна обёртка-помощник для показа ошибок имеет ноль вызовов, и один макет журнала не используется ни из кода, ни из разметки (только осиротевшие авто-строки).

---

## 2. Цели

1. Один общий компонент и один макет отвечают за показ «заголовок + прокручиваемый read-only текст + ряд действий» для всех текущих вызовов обоих путей.
2. Оформление и поведение едины во всех вызовах: один стиль действий, одна подложка текста, одинаковая семантика закрытия, портрет и ландшафт.
3. Мёртвый код удалён: неиспользуемая обёртка показа ошибок и осиротевший макет журнала вместе с их авто-строками.
4. Все вызовы переведены на единый API; прежние точки входа удалены. Логика самих вызовов не меняется - меняется только форма точки входа.

**Non-goals:**

- Диалог сведений о файле - структурированные поля (file/EXIF/audio/video/doc-секции), иная модель контента; вне объёма.
- Диалог интеграционных тестов - интерактивный debug-инструмент; вне объёма.
- Полноэкранный ридер текстовых файлов - отдельная подсистема просмотра; вне объёма.
- Изменение состава действий конкретных вызовов - меняется представление и общий компонент, не набор действий у каждого вызова.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Единый внешний вид у всех текстовых диалогов проекта.
2. Минимальная регрессионная поверхность - вызовы по возможности не трогать.
3. Удаление мёртвого кода как часть работы, а не отдельной задачей.

### 3.2 Жёсткие ограничения

- **Flavor:** все варианты сборки - компонент общий; flavor-специфичного кода не вводится.
- **API level:** без API-специфики, минимальный уровень проекта.
- **Wear OS:** не затрагивается.
- **Производительность:** без влияния - статический макет, без новых тяжёлых зависимостей.
- **Совместимость данных:** не применимо - нет хранимых данных и схемы.
- **Локализация:** EN/RU/UK - новые строки не планируются; переиспользуются существующие описания действий, удаляются мёртвые авто-строки во всех трёх локалях согласованно.
- **Доступность:** иконочные действия несут не-цветовое описание и всплывающую подсказку; цель касания не меньше системного минимума; фокус проходит по ряду в логичном порядке; отличие области текста не опирается только на цвет. Единый компонент обязан сохранить эти свойства для всех вызовов.
- **Communication policy:** строки-описания действий проходят чек-лист тона `docs/COMMUNICATION_POLICY.md` (§6); пользовательские формулировки при объединении не ухудшаются.

### 3.3 Owner inputs (Approval gate)

- **UI placement contract:** единый компонент сводит действия в один компактный ряд под областью текста (как у базового компонента после S0378); отдельная текстовая кнопочная панель системного диалога не используется. Порядок действий и видимость опциональных слотов сохраняют смысл существующих вызовов.
- **Accessibility:** каждое иконочное действие несёт описание для скринридера и всплывающую подсказку; область текста отделена цветом подложки И видимой полосой прокрутки; цель касания ≥ системного минимума; единый компонент сохраняет это для всех вызовов.
- **Communication policy:** объединение не меняет пользовательские формулировки действий; любые затронутые строки проходят чек-лист тона перед интеграцией.
- **Validation level:** сборка целевого варианта проходит; ручная проверка репрезентативных вызовов обоих исходных путей (ошибка с details, ошибка с кастомным CTA, лог/отчёт, сведения о системе) в портрете и ландшафте.
- **Owner sign-off:** 2026-06-07 - решения по §6 подтверждены владельцем: закрывают только «Закрыть» и основное действие; единый Material-билдер; диалог журнала операций переиспользует UI единого компонента; все вызовы мигрируют на единый API.
- **Related tickets:** S0378 (база-компонент; верифицирован на устройстве и заархивирован - блокировка снята, см. §10).

## 4. Контекст текущей архитектуры

За показ текстовых диалогов отвечает общий UI-утилитный слой, но в нём сосуществуют два независимых пути: один надувает богатый макет (текст + сворачиваемые технические details + ряд действий), другой - более простой макет (текст + пара действий). Третий путь - тонкая обёртка над вторым, и он не используется.

Поскольку пути не разделяют ни макет, ни рендерер, единое изменение оформления невозможно в одной точке: правка распространяется только на свой путь. Базовый компонент после S0378 уже стал гибким (ряд иконочных действий со слотами, выделенная подложка текста, опциональные сворачиваемые details) и по возможностям является супермножеством простого пути - это делает объединение естественным, а не переписыванием с нуля.

---

## 5. Предлагаемый подход

Свести оба пути к одному рендереру и одному макету, переиспользуя гибкий компонент-базу, и ввести единый публичный API, на который мигрируют все вызовы (прежние точки входа удаляются).

### 5.1 Основные столпы / модули

**Единый рендерер текстового диалога.**
- Один компонент отвечает за «заголовок + прокручиваемый read-only текст + опциональные сворачиваемые details + ряд действий».
- Набор действий задаётся обобщённым описанием (иконка, описание для доступности, обработчик, признак закрытия по нажатию, опциональная текстовая подпись для основного действия с произвольным смыслом).
- Признаки представления, которыми сейчас отличаются пути, выражаются параметрами компонента: моноширинный шрифт для логов, доля ширины экрана, перевод начального фокуса на осмысленное действие.

**Единая точка входа.**
- Вводится один новый публичный API над единым рендерером; все вызовы обоих исходных путей мигрируют на него, прежние точки входа удаляются.
- Единая семантика закрытия (закрывают только «Закрыть» и основное действие) и единый Material-билдер/тема применяются ко всем вызовам.

**Удаление мёртвого груза.**
- Неиспользуемая обёртка показа ошибок и осиротевший макет журнала удаляются вместе с их авто-строками во всех локалях.

### 5.2 Потоки данных и событий

- Вызывающий экран → точка входа (как сейчас): передаёт заголовок, текст и логический набор действий.
- Точка входа → единый рендерер: наполняет текст, привязывает действия к ряду, скрывает неиспользуемые слоты, применяет признаки представления.
- Действия пользователя вызывают те же обработчики, что и сейчас.

### 5.3 Точки расширяемости

- Обобщённое описание действий позволяет добавлять новые действия как ещё один элемент списка без правок вызывающих экранов.
- Признаки представления (шрифт, ширина, фокус, тема) задаются параметрами, чтобы новые сценарии переиспользовали единый компонент.
- Диалог журнала операций переиспользует UI-слой единого компонента, оставаясь по жизненному циклу отдельным экраном; компонент поддерживает хост-экран, моноширинный шрифт и слот «очистить».

## 6. Открытые вопросы / Research items

1. **Единая семантика закрытия**
   - **Решение:** диалог закрывают только «Закрыть» и основное действие (CTA); копирование, отправка и сохранение оставляют диалог открытым.
   - **Почему:** совпадает с уже проверенным поведением базы S0378 и позволяет сцеплять действия (скопировать, затем отправить).
   - **Статус:** Resolved

2. **Базовый билдер диалога и тема**
   - **Решение:** единый диалог строится на Material-билдере (Material3).
   - **Почему:** даёт единый современный вид заголовка и темы, совпадающий с большинством диалогов проекта; первичный путь переходит с системного билдера на Material.
   - **Статус:** Resolved

3. **Судьба диалога журнала операций**
   - **Решение:** диалог журнала операций переиспользует UI-слой единого компонента; класс остаётся экраном со своим жизненным циклом, действие «очистить» добавляется как ещё один слот.
   - **Почему:** соответствует цели «все текстовые диалоги едины»; единый компонент обязан поддержать хост-экран, моноширинный шрифт и слот «очистить».
   - **Статус:** Resolved

4. **Стратегия миграции вызовов**
   - **Решение:** все вызовы мигрируют на один новый API; прежние точки входа удаляются.
   - **Почему:** один чистый фасад вместо двух имён; цена - правки во всех ~24 вызовах и большая регрессионная поверхность (учтено в §7).
   - **Статус:** Resolved

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Регрессия при миграции ~24 вызовов на единый API | Средняя/Высокая | Сломанный вид/действие в редком экране | Поэтапная миграция по вызову; компилятор ловит несоответствие сигнатур; ручная проверка репрезентативных вызовов обоих путей |
| Дрейф поведения закрытия | Средняя | Неожиданное закрытие/незакрытие после действия | Зафиксировать единую семантику в §6.1 до реализации |
| Расхождение темы/заголовка при смене билдера | Низкая | Иной вид заголовка в части вызовов | Выбрать единый билдер в §6.2, проверить в обеих темах |
| Реализация на непроверенной базе S0378 | Средняя | Наследование скрытого дефекта базового компонента | Начинать реализацию только после верификации S0378 (§10) |
| Удаление «мёртвого» кода, который окажется живым | Низкая | Сломанный редкий путь | Подтвердить ноль ссылок повторно непосредственно перед удалением |

## 9. Архитектурные решения (ADR)

**ADR-1: Единый рендерер на базе компонента после S0378, сигнатуры как обёртки**

- **Решение:** объединить оба пути на одном рендерере и макете, переиспользуя гибкий компонент-базу; ввести единый новый API и мигрировать на него все вызовы, прежние точки входа удалить.
- **Альтернативы:** оставить два пути; сохранить обе прежние сигнатуры как тонкие обёртки вместо миграции.
- **Почему:** база уже является супермножеством простого пути; единый API даёт один чистый фасад без двух дублирующих имён, ценой правок во всех вызовах (учтено в §7).

## 11. Критерии готовности (strategic-level)

1. Все текущие вызовы обоих исходных путей показывают диалог через один общий компонент и один макет.
2. Оформление и семантика закрытия идентичны во всех вызовах, в портрете и ландшафте.
3. Неиспользуемая обёртка показа ошибок и осиротевший макет журнала удалены вместе с их авто-строками во всех локалях.
4. Места вызова не потребовали правок своей логики (либо правки сведены к замене имени точки входа).
5. Сборка целевого варианта проходит; репрезентативные вызовы проверены вручную.
