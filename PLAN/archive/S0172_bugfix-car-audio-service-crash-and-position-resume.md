## 1. Проблема

В автомобильном сценарии (SFTP-источник, управление с руля/медиа-кнопок) при нажатии кнопки воспроизведения после паузы фоновый аудио-сервис перезапускается через broadcast-приёмник медиа-кнопок, но не переходит в foreground-состояние достаточно быстро — OS прерывает процесс с фатальной ошибкой в течение 5 секунд. Это происходит в каждой сессии, что подтверждается баннером `PREVIOUS SESSION ENDED WITH A CRASH` в двух из трёх логов.

Вторая проблема: позиция воспроизведения SFTP-аудио не сохраняется и не восстанавливается после перезапуска (будь то краш или штатный перезапуск). Трек начинается с нуля вместо продолжения с последнего места.

---

## 2. Цели

1. Фоновый аудио-сервис, запущенный через медиа-кнопку с руля/наушников, больше не крашится с ошибкой `startForegroundService did not then call startForeground`.
2. После краша или штатного перезапуска приложения SFTP-аудио-трек возобновляется с сохранённой позиции, а не с начала.
3. Позиция SFTP-аудио периодически сохраняется во время воспроизведения — с той же частотой, что и для локальных файлов.
4. Логи при старте сервиса явно показывают переход в foreground-состояние до любых других операций.

**Non-goals:**

- Изменение логики определения «последнего трека» при старте — трек уже восстанавливается корректно (через companion-поля сервиса).
- Восстановление позиции для cloud-источников (Google Drive, OneDrive, Dropbox) — за рамками данной спецификации.
- Работа в офлайн-режиме без SFTP-соединения.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. При восстановлении позиции кратко информировать пользователя (как уже сделано для локальных файлов) — тост «Продолжение с ЧЧ:ММ:СС».
2. Позицию сохранять не только периодически, но и при переключении трека / выходе из плеера, чтобы не терять прогресс при быстром пропуске.

### 3.2 Жёсткие ограничения

- **Flavor:** standard, legacy (lite и photos не поддерживают SFTP-аудио).
- **API level:** Android 8+ (API 26) — `startForeground` с типом `FOREGROUND_SERVICE_TYPE_MEDIA_PLAYBACK` обязателен для API 29+; для API 26–28 достаточно базового вызова.
- **Wear OS:** не затрагивается.
- **Производительность:** сохранение позиции выполняется исключительно в фоновом потоке (IO dispatcher); в главном потоке — только вызов `startForeground`.
- **Совместимость данных:** позиция хранится через существующий механизм `PlaybackPositionRepository`; схема Room не изменяется, миграция не нужна.
- **Локализация:** новая строка-тост для восстановления позиции SFTP — EN/RU/UK обязательно. Можно переиспользовать уже существующую строку, если она содержит подстановку времени.
- **Доступность:** нет новых визуальных элементов.

## 4. Контекст текущей архитектуры

Фоновый аудио-сервис — `MediaSessionService` (Media3), который запускается двумя путями: штатно — из плеера при начале воспроизведения, и через cold-restart — из broadcast-приёмника медиа-кнопок. Второй путь не предоставляет сервису медиа-элемент при старте, поэтому сервис оказывается в состоянии «запущен, но пустой» — без активной сессии, которая создаёт уведомление. OS Android 8+ требует, чтобы foreground-сервис вызвал `startForeground` в течение 5 секунд после `startForegroundService`; если этого не происходит — сервис убивается с `RemoteServiceException`.

SFTP-аудио воспроизводится через отдельный путь: файл предварительно скачивается в кеш, после чего сервис получает локальный URI и начинает воспроизведение с нулевой позиции. В этом потоке обращений к репозиторию позиций нет ни при запуске (restore), ни во время воспроизведения (save). Периодическое сохранение позиции работает только в параллельном пути — для локального видео и аудио через ExoPlayer в Activity.

## 5. Предлагаемый подход

### 5.1 Основные столпы

**Столп A — немедленный `startForeground` при холодном старте**

Сервис должен вызывать `startForeground` в самом начале `onCreate()` — ещё до инициализации MediaSession и ExoPlayer. Уведомление на этом этапе содержит только заглушку (без метаданных трека). После успешного связывания с медиа-сессией уведомление обновляется штатным путём через Media3 `MediaNotificationManager`.

**Столп B — сохранение позиции SFTP-аудио**

Когда сервис воспроизводит SFTP-аудио, слушатель состояния плеера запускает периодическую задачу, которая читает текущую позицию и передаёт её в репозиторий позиций. Задача останавливается при паузе/остановке, снова запускается при переходе в `STATE_READY`/`STATE_BUFFERING`. Дополнительно позиция сохраняется синхронно при смене трека или уничтожении сервиса.

**Столп C — восстановление позиции SFTP-аудио**

Менеджер загрузки медиа перед вызовом `playAudioWithMetadata` запрашивает сохранённую позицию по оригинальному SFTP-пути (не по пути в кеше). Если позиция найдена и больше нуля — передаёт её в сервис, который делает `seekTo` сразу после `prepare()`, до перехода в `STATE_READY`. Пользователь видит тот же тост, что и для локальных файлов.

### 5.2 Потоки данных и событий

**Холодный старт (медиа-кнопка с руля):**

```
Broadcast receiver (медиа-кнопка) →
  startForegroundService(AudioPlaybackService) →
    onCreate(): startForeground(placeholder notification)  ← FIX A
    createMediaSession()
    [ExoPlayer idle — нет трека]
  OS: foreground constraint удовлетворена
```

**Начало воспроизведения SFTP-аудио:**

```
PlayerMediaLoaderManager →
  prefetch SFTP → local cache URI
  getPosition(sftp_path) → savedPositionMs  ← FIX C
  controller.playAudioWithMetadata(uri, title, startPositionMs)
    AudioPlaybackService.playAudio(uri, startPositionMs)
      setMediaItem → prepare → seekTo(startPositionMs) → play
      startPositionSaving()  ← FIX B
```

**Периодическое сохранение:**

```
Handler.postDelayed (every N ms) →
  exoPlayer.currentPosition, duration →
  PlaybackPositionRepository.savePosition(sftp_path, position, duration)
```

**Завершение / смена трека:**

```
onPlaybackStateChanged(STATE_ENDED) | onDestroy() | next/prev →
  stopPositionSaving()
  PlaybackPositionRepository.savePosition(sftp_path, finalPosition, duration)
```

### 5.3 Точки расширяемости

- Логика сохранения/восстановления позиции в сервисе должна быть реализована так, чтобы её можно было распространить на SMB и FTP без дублирования кода (один вспомогательный метод принимает оригинальный URL как ключ).
- Placeholder-уведомление (столп A) должно допускать замену иконки/текста без изменения основного потока инициализации.

3. **Ключ для сохранения позиции**
   - **Вопрос:** Сохранять позицию по оригинальному SFTP-пути или по пути кешированного файла?
   - **Варианты:** (a) SFTP-путь — стабильный ключ, переживает очистку кеша. (b) Кеш-путь — теряется при очистке.
   - **Статус:** Resolved — SFTP-путь (оригинальный URL) как ключ.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Placeholder-уведомление мигает на долю секунды перед обновлением реальными метаданными | Средняя | Визуальный артефакт в статусбаре | Установить иконку и текст приложения в placeholder, чтобы переход был незаметен |
| `seekTo` при `STATE_BUFFERING` может игнорироваться некоторыми версиями ExoPlayer | Низкая | Позиция не восстанавливается | Слушать переход в `STATE_READY` и seekTo при нём, как в `VideoPlayerManager` |
| При очень коротком SFTP-файле (< savedPosition) seekTo дойдёт до конца, STATE_ENDED немедленно сработает и очистит позицию | Низкая | Неожиданное переключение трека | Проверять `savedPosition < duration` перед seek |
| Периодическое сохранение из сервиса конкурирует с сохранением из Activity (если оба активны одновременно) | Средняя | Двойные записи в DB, но данные консистентны | Документировать взаимоисключение в коде; фактического конфликта нет, т.к. SFTP-путь не идёт через VideoPlayerManager |

## 9. Архитектурные решения (ADR)

**ADR-1: Немедленный `startForeground` в `onCreate` с placeholder-уведомлением**

- **Решение:** Вызывать `startForeground` в самом начале `onCreate`, до создания MediaSession.
- **Альтернативы:** (a) Добавить `onStartCommand` с явным `startForeground` — более локальная правка, но не решает сценарий холодного старта без команды. (b) Отключить MediaButtonRestartReceiver — убирает холодный старт полностью, что ломает сценарий автомобиля.
- **Почему:** Вариант с `onCreate` гарантирует foreground-состояние независимо от того, каким путём сервис был запущен, и покрывает оба сценария (штатный + cold-restart).

**ADR-2: Ключ позиции — оригинальный SFTP-URL, не кеш-путь**

- **Решение:** Позиция сохраняется и читается по `sftp://host:port/path` — тому же значению, что передаётся в `playVideo`.
- **Альтернативы:** Кеш-путь (`file:///...`) — нестабилен, теряется при очистке кеша.
- **Почему:** Оригинальный URL является стабильным идентификатором файла на сервере и уже используется в остальных местах как ключ (Favorites, history).

## 11. Критерии готовности (strategic-level)

1. В машине: нажатие кнопки Play на руле после паузы возобновляет воспроизведение без краша (`PREVIOUS SESSION ENDED WITH A CRASH` не появляется в следующей сессии).
2. После перезапуска приложения SFTP-аудио-трек начинает воспроизведение с позиции, которая была при последней паузе/выходе (± 5 секунд), и показывает тост с временем.
3. При быстром пролистывании треков позиция каждого сохраняется и корректно восстанавливается при возврате.
4. Лог при холодном старте сервиса содержит запись о переходе в foreground до записей о создании MediaSession.
