## 1. Проблема

В проекте встречается класс дефектов, когда одно и то же общее состояние пишется из нескольких независимых слоёв без единственного владельца. Побеждает тот, кто записал последним, а порядок зависит от тайминга кадра, порядка подписок или раскладки - то есть гонка «last-write-wins», избыточная работа и потенциально небезопасные конкурентные записи.

Свежий пример - кнопка переключения списка/сетки в браузере: семантический слой корректно прятал её (`GONE`) для аудио-библиотек, а обобщённый менеджер раскладки панели тут же возвращал её видимой, не трогая enabled/alpha, оставляя «видимый, но потушенный» артефакт. Это симптом, а не единичный баг: аналогичная многослойность есть и над UI-объектами (видимость, доступность, прозрачность, текст вьюх), и над данными (строки БД, реактивные потоки состояния, хранилище настроек, кэши).

Сейчас такие конфликты находятся только постфактум - руками, по жалобе на конкретный экран. Нет ни методики, ни инструмента, чтобы выявлять их по всему проекту системно.

## 2. Цели

1. Появляется переиспользуемый промпт-исследование, который по всему проекту находит места, где общее состояние мутируется из нескольких слоёв.
2. Аудит покрывает обе поверхности: UI-объекты (свойства вьюх) и данные (сущности БД, реактивные потоки, хранилище настроек, кэши, разделяемые мутабельные структуры).
3. На выходе - ранжированный список реальных hotspot-ов с указанием писателей, поверхности конфликта и признака небезопасности (гонка порядка, конкурентная запись, избыточность).
4. Методика отделяет ложные срабатывания (одноимённые объекты на разных экранах, не сосуществующие во времени) от настоящих конфликтов в пределах одной области владения.
5. Методика ловит косвенных писателей (запись через локальную/цикловую переменную, `apply`, вспомогательные функции), которых наивный текстовый поиск по имени объекта не видит.
6. Каждый подтверждённый нетривиальный конфликт паркуется отдельным `/spec-draft` для последующего разбора, а не чинится внутри этого аудита.

**Non-goals:**

- Не чинить найденные конфликты в рамках этой спеки - только обнаружить, классифицировать, запарковать.
- Не вводить обязательный блокирующий гейт в `post-change.ps1` на первой итерации (слишком шумно до калибровки).
- Не переписывать архитектуру владения состоянием - это предмет отдельных порождённых спек.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Промпт должен быть самодостаточным - его можно отдать исследовательскому агенту и получить отчёт без дополнительного контекста.
2. Аудит должен покрывать не только интерфейс, но и данные - это явное требование владельца.
3. Результат - не «ещё один шумный grep», а ранжированная по риску картина с объяснением, почему конкретное место опасно.
4. Желательно предусмотреть и рантайм-способ подтверждения (трассировка «кто записал последним» в debug-сборке) там, где статика бессильна.

### 3.2 Жёсткие ограничения

- **Flavor:** аудит охватывает общий код всех вариантов сборки; flavor-специфика учитывается как фактор (одноимённые объекты в разных source set не считаются конфликтом). Реализация инструментов не вводит flavor-гейтов в общий код.
- **API level:** без API-специфики - анализ исходников, не рантайм-поведение конкретной версии Android.
- **Wear OS:** модуль часов входит в область аудита наравне с основным приложением.
- **Производительность:** инструмент аудита запускается по требованию, вне горячих сборочных путей; рантайм-трассировка - только debug, без влияния на release.
- **Совместимость данных:** аудит только читает исходники, ничего не мигрирует и не меняет схему.
- **Локализация:** артефакты аудита (промпт, отчёт, методика) - EN-only как инструментарий; на пользовательские строки не влияет.
- **Доступность:** не применимо - нет пользовательской поверхности.

### 3.3 Owner inputs (Approval gate)

- **Validation level:** прогон промпта на проекте даёт непустой ранжированный список с не менее чем одним подтверждённым настоящим конфликтом (известный seed - кнопка переключения вида) и корректно помечает заведомо ложные срабатывания.
- **Owner sign-off:** 2026-06-26 - владелец запросил спеку с промптом на общепроектное исследование по UI и данным.
- **Related tickets:** none.

## 4. Контекст текущей архитектуры

Приложение построено по слоям UI -> ViewModel -> UseCase -> Repository -> DataSource, состояние экранов раздаётся реактивными потоками, а UI собирается из множества узких менеджеров-помощников, каждый из которых отвечает за свой срез поведения. Именно эта декомпозиция и порождает риск: один наблюдаемый объект (вьюха или поле состояния) законно интересен сразу нескольким помощникам, и каждый пишет в него по своему условию.

Решить проблему «на месте» нельзя, потому что нет ни единого реестра владения состоянием, ни механизма, который бы доказывал, что у каждого мутируемого объекта ровно один авторитетный писатель. Конфликты невидимы в статике наивным поиском (косвенные записи) и проявляются только в рантайме при определённом порядке событий.

## 5. Предлагаемый подход

Поставить переиспользуемую методику аудита плюс готовый промпт, который проводит исследование по всему проекту и выдаёт ранжированный отчёт. Аудит работает в двух измерениях - UI-поверхность и поверхность данных - по единому принципу: для каждого общего объекта собрать множество писателей, оценить, сосуществуют ли они в одной области владения, и пометить признаки небезопасности.

### 5.1 Основные столпы / модули

1. **Сбор писателей (UI).** Для каждого объекта интерфейса собрать все места, где меняются его наблюдаемые свойства - видимость, доступность, прозрачность, текст, фокус. Учитывать прямые и косвенные записи.
2. **Сбор писателей (данные).** Для каждого разделяемого носителя состояния - сущности БД, реактивные потоки состояния, хранилище настроек, кэши, разделяемые мутабельные коллекции и одиночки - собрать все точки записи и инвалидизации.
3. **Сведение по области владения.** Группировать писателей не по имени объекта, а по фактической области сосуществования (один экран/одна область видимости/один тип привязки), чтобы одноимённые, но не пересекающиеся во времени объекты не давали ложных конфликтов.
4. **Классификатор небезопасности.** Помечать паттерны: обобщённый писатель в цикле поверх набора объектов рядом с точечным семантическим писателем; запись без явного владельца; конкурентная запись из разных корутин/потоков без синхронизации; избыточная повторная запись одного и того же значения.
5. **Ранжирование и парковка.** Сортировать по числу писателей и серьёзности признака; для подтверждённых нетривиальных конфликтов формировать кандидатов на `/spec-draft`.

### 5.2 Потоки данных и событий

Источник истины аудита - исходный код модулей приложения. Пайплайн: сбор кандидатов (статический разбор записей) -> сведение по областям владения -> классификация небезопасности -> ранжирование -> отчёт со списком парковочных кандидатов. Опциональная вторая петля - рантайм-трассировка записей в debug-сборке для подтверждения гонок порядка там, где статика даёт лишь подозрение.

### 5.3 Точки расширяемости

- Набор отслеживаемых UI-свойств и носителей данных должен быть расширяемым списком, а не зашитым перечнем.
- Форма инструмента (одноразовый отчётный скрипт, кастомное правило статического анализатора, рантайм-трассировщик) выбирается на тактическом этапе и может сосуществовать.
- Методика должна допускать постепенное ужесточение - от необязательного отчёта до калиброванного гейта, когда уровень шума станет приемлемым.

### 5.4 Переиспользуемый промпт исследования (артефакт-деливерабл)

Готовый промпт для исследовательского агента. Формулировки - на английском как инструментарий; промпт оперирует категориями фреймворка и ролями, без захардкоженных путей и имён классов проекта.

```text
ROLE: You are auditing this Android project for multi-layer, redundant, and unsafe
mutation of SHARED STATE across the whole codebase. Cover BOTH surfaces:
(A) UI interface objects and (B) data / state holders. Produce a ranked report,
not raw grep dumps. Do NOT fix anything - only detect, classify, and propose parking.

SCOPE: all Kotlin/Java sources of the app modules (main + Wear), across all flavor
source sets. Treat read-only zones as out of scope.

SURFACE A - UI OBJECTS. For every interface object, collect ALL writers of its
observable properties: visibility (visibility / isVisible), enabled state, alpha,
text, focusable/clickable/nextFocus. Include INDIRECT writers - assignments made
through a local/loop/`it` variable, inside `apply{}`/`with{}`, or via helper
functions and lambdas - because a name-based search over the object id alone misses
exactly the most dangerous case (a generic layout/partition manager that rewrites a
property for a SET of objects in a loop).

SURFACE B - DATA / STATE HOLDERS. For every shared state carrier, collect ALL write
and invalidation sites: persistent DB rows/entities, reactive state streams
(StateFlow/MutableStateFlow/LiveData), preference/settings storage, in-memory caches,
shared mutable collections, and singletons holding mutable state. Note who writes,
from which layer, and under which coroutine/thread/scope.

GROUPING (kills false positives): group writers by ACTUAL co-existence domain, NOT by
object name. Same-named objects living on different screens / binding types / source
sets that never co-exist in time are NOT a conflict. A real conflict is multiple
authoritative writers to the SAME live object within one ownership domain.

UNSAFE-PATTERN CLASSIFIER - flag and explain each hit:
  1. Authority conflict: a generic loop/partition writer over a property set coexisting
     with a point semantic writer of the same property (the list/grid toggle bug class).
  2. No single owner: a property/field written from >=2 collaborators on one screen with
     no clear last-writer contract.
  3. Ordering race: outcome depends on subscription order, frame timing, or layout pass.
  4. Concurrency hazard: writes to the same carrier from different coroutines/threads/
     scopes without synchronization or single-writer confinement.
  5. Redundancy: repeated writes of an already-equal value, or duplicated derivation of
     the same state in multiple layers.

OUTPUT: a table-free ranked list. For each finding give: object/carrier, ownership
domain, list of writers (file + symbol), surface (UI/data), pattern id from above,
a one-line why-it-is-unsafe, and a confidence level. Rank by writer count x severity.
Separate "confirmed conflicts" from "likely false positives" and say why.

VERIFICATION: for the top findings, adversarially try to REFUTE the conflict (could the
writers be mutually exclusive by guard/state?). Keep only those that survive refutation.
For ordering races that static analysis cannot prove, propose a debug-only write-tracer
(log writer identity + value per frame/transaction) as the runtime confirmation step.

DELIVERY: list each surviving non-trivial conflict as a `/spec-draft` candidate (symptom
+ evidence), so the caller can park them. Never switch task to fixing them.
```

## 6. Открытые вопросы / Research items

1. **Форма инструмента**
   - **Вопрос:** чем материализовать методику - одноразовым отчётным скриптом, кастомным правилом статического анализатора или рантайм-трассировщиком?
   - **Варианты:** отчётный скрипт в зоне качества; правило detekt/lint; debug-трассировщик записей; комбинация.
   - **Решение:** гибрид - механический отчётный скрипт-харвестер в зоне качества (дешёвый сбор кандидатов и грубая фильтрация шума) плюс закоммиченный переиспользуемый промпт, который агент прогоняет поверх кандидатов (семантика, косвенные писатели, рефьют). Рантайм-трассировщик и detekt-правило отложены до калибровки уровня шума.
   - **Статус:** Resolved

2. **Детекция на поверхности данных**
   - **Вопрос:** как надёжно собрать писателей реактивных потоков, БД и настроек, учитывая косвенные записи и конкурентность?
   - **Варианты:** статический разбор записей в потоки/репозитории; аннотации владельца; рантайм-логирование транзакций.
   - **Решение:** скрипт-харвестер собирает статические точки записи в реактивные потоки, репозитории и хранилище настроек как кандидатов; семантику и конкурентность (запись из разных корутин/областей) разбирает агент по промпту; рантайм-подтверждение транзакций отложено.
   - **Статус:** Resolved

3. **Модель серьёзности и ранжирования**
   - **Вопрос:** как калибровать признак небезопасности, чтобы отчёт был сразу actionable?
   - **Решение:** ранг = число писателей x вес паттерна, с группировкой по области владения для подавления ложных срабатываний; пороги калибруются на первом прогоне (seed - кнопка переключения вида). Первая итерация - только отчёт, без блокирующего гейта.
   - **Статус:** Resolved

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Высокий уровень шума (ложные срабатывания по одноимённым объектам) | Высокая | Отчёт игнорируют | Группировка по области владения, а не по имени; явное отделение likely-false |

## 9. Архитектурные решения (ADR)

**ADR-1: Группировать по области владения, а не по имени объекта**

- **Решение:** конфликтом считается множественная авторитетная запись в один живой объект в пределах одной области сосуществования.
- **Альтернативы:** группировать по строковому имени объекта (как наивный grep).
- **Почему:** одноимённые объекты на разных экранах/в разных source set не сосуществуют и дают массовые ложные срабатывания.

**ADR-2: Обязательный учёт косвенных писателей**

- **Решение:** аудит обязан находить записи через локальные/цикловые переменные, `apply`/`with` и хелперы.
- **Альтернативы:** искать только прямые записи по имени объекта.
- **Почему:** самый опасный класс (обобщённый цикловой писатель) невидим прямому поиску - именно он стоял за seed-багом.

## 11. Критерии готовности (strategic-level)

1. Существует переиспользуемый промпт, который можно отдать исследовательскому агенту без дополнительного контекста.
2. Прогон промпта по проекту выдаёт ранжированный отчёт, покрывающий и UI-объекты, и данные.
3. В отчёте подтверждён как минимум один настоящий конфликт (seed - кнопка переключения вида) и корректно помечены заведомо ложные срабатывания.
4. Для подтверждённых нетривиальных конфликтов сформированы кандидаты на `/spec-draft`.
5. Методика описывает рантайм-способ подтверждения гонок порядка там, где статика недостаточна.
