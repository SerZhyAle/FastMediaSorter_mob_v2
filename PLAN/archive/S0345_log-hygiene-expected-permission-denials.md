## 1. Проблема

При открытии диалога системной информации на устройстве с урезанными правами часть полей устройства недоступна по дизайну ОС, но сбор диагностики логирует эти ожидаемые отказы уровнем WARNING с полным стектрейсом. На Quest 3 (noLegalDebug `2.60.6040.037`, лог `fastmediasorter_20260604_004027`) видно два таких поля: чтение имени пользователя падает с `SecurityException` (нужны системные привилегии, которых у приложения нет), а чтение статуса политики безопасности ОС падает с `EACCES` (файл недоступен на заблокированном устройстве). Оба отказа ожидаемы на таком устройстве, но в логе выглядят как полноценные предупреждения с трассировкой стека.

Это зашумляет лог и размывает сигнал: ожидаемая «недоступность поля на этом устройстве» неотличима по уровню от настоящего сбоя сбора диагностики. На разработчика это тратит внимание, а в debug-сборке ещё и зеркалится отладочным каналом как тревога.

---

## 2. Цели

1. Ожидаемый отказ чтения поля устройства (недостаточно прав / файл недоступен на заблокированном устройстве) логируется тихо (info/debug) и без полного стектрейса.
2. Настоящий, неожиданный сбой сбора диагностического поля по-прежнему логируется заметно (warning) с достаточной детализацией.
3. Диалог системной информации продолжает показывать остальные поля, а недоступное поле деградирует понятной пометкой «недоступно», а не выглядит как сбой.

**Non-goals:**

- Получение недоступных полей через привилегии, которых у приложения нет, или обход прав ОС.
- Изменение состава диагностических полей или формата диалога.
- Пересмотр уровней логирования вне пути сбора системной информации.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Лог диагностики должен отражать реальную тяжесть: ожидаемая недоступность поля — не предупреждение.
2. Желательно различать «поле недоступно на этом устройстве» и «сбор поля неожиданно упал».

### 3.2 Жёсткие ограничения

- **Flavor:** затрагивает сбор системной информации в общем коде (`standard` и суперсеты) и расширенный диагностический сбор флейвора `noLegal`. Реализация для noLegal-части следует `dev/FLAVOR_DEVELOPMENT_RULES.md` (диагностический контрибьютор живёт в `src/noLegal/java/`); новые `BuildConfig.SUPPORT_*`-гейты в `src/main/` запрещены (CLAUDE.md Rule 15).
- **API level:** без API-специфики; наблюдение на Android 14 / API 34 (Quest 3), но недоступность полей зависит от устройства, а не от версии API.
- **Wear OS:** не затрагивается.
- **Производительность:** путь редкий (открытие диалога диагностики), бюджет некритичен.
- **Совместимость данных:** не затрагивается — нет персистентного состояния.
- **Логирование:** только Timber; постоянные строки логов без встроенного `Sxxxx`. Пересмотр уровней логов — суть тикета.
- **Локализация:** диагностические сообщения живут в логе и не локализуются; пометка «недоступно» в самом диалоге, если она user-facing, требует EN/RU/UK.

### 3.3 Owner inputs (Approval gate)

## 4. Контекст текущей архитектуры

Диалог системной информации собирает поля устройства через сценарий сбора, который агрегирует секции; на флейворе `noLegal` к ним добавляется расширенный диагностический контрибьютор. Каждое поле читается отдельно, и при исключении путь сбора ловит его и пишет в лог как предупреждение с трассировкой, чтобы поле не уронило весь сбор.

Сейчас обработчик не различает класс исключения: отказ по правам / недоступность файла на заблокированном устройстве обрабатывается так же, как неожиданный сбой, — одним уровнем WARNING со стектрейсом. Различить «ожидаемо недоступно» и «неожиданно упало» на этом уровне нельзя без классификации исключения по его природе.

---

## 5. Предлагаемый подход

Классифицировать исключения чтения диагностических полей: ожидаемые отказы доступа (недостаточно прав, файл недоступен на заблокированном устройстве) логируются тихо и без стектрейса, прочие — по-прежнему заметно. Поле в любом случае деградирует пометкой «недоступно», не роняя сбор.

### 5.1 Основные столпы / модули

#### A. Классификация ожидаемого отказа

Путь сбора поля распознаёт класс исключения: отказ доступа/недоступность как ожидаемое условие против неожиданного сбоя.

#### B. Уровень лога по классу

Ожидаемый отказ → info/debug без стектрейса; неожиданный сбой → warning с деталью. Поле помечается «недоступно» единообразно в обоих случаях.

#### C. Единая точка для обоих сборщиков

Классификация переиспользуется и общим сбором системной информации, и расширенным диагностическим сбором noLegal, а не дублируется.

### 5.2 Потоки данных и событий

- Открытие диалога → сбор полей → чтение поля бросает исключение → классификация (ожидаемо/неожиданно) → уровень лога по классу → пометка поля «недоступно».

### 5.3 Точки расширяемости

- Классификация «ожидаемый отказ доступа» остаётся переиспользуемой для новых диагностических полей и для других устройств с урезанными правами.
