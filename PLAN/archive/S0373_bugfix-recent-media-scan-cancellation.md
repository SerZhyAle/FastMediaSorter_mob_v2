## 1. Проблема

При открытии виртуального ресурса Recent Media текущий путь загрузки может получить штатную отмену фоновой coroutine уже после старта сканирования. Сейчас такой исход трактуется как полноценный сбой: в runtime-лог пишется error-level запись `failed to scan recent files`, а вниз по потоку может уходить неуспешный сигнал завершения.

При этом тот же пользовательский сценарий в приложенном логе всё равно доходит до успешного финала и отображает 206 файлов. Получается противоречивое состояние: для пользователя список загружен, а для диагностики система сообщает о сбое сканирования. Это засоряет логи ложноположительными ошибками, усложняет поиск реальных проблем MediaStore/ContentResolver и создаёт риск кратковременного ложного error/empty-path в слоях, которые ориентируются на completion-сигналы.

## 2. Цели

1. Разделить ожидаемую отмену coroutine и реальный сбой сканирования при загрузке Recent Media.
2. Исключить error-level диагностику и ложный failure-path в случаях, когда итоговый список успешно загружается.
3. Сохранить возможность быстро диагностировать настоящие сбои запроса recent media.
4. Не ухудшить производительность и поведение существующего сценария открытия Recent Media.

**Non-goals:**

- Переработка логики сортировки, лимита recent files или состава самого ресурса Recent Media.
- Исправление несвязанных ошибок из того же лога, включая дефекты записи с микрофона.
- Полный рефакторинг всей подсистемы локального сканирования вне объёма общего cancellation-контракта.

## 4. Контекст текущей архитектуры

Сценарий открытия Recent Media идёт через общий browse/load pipeline: слой загрузки ресурса запрашивает local scan для виртуального источника recent files, затем фильтрует результат, передаёт completion/progress сигналы и отдаёт итоговый список в слой отображения. На пользовательском уровне это выглядит как обычная загрузка папки с кешированием, сортировкой и последующим рендером списка.

Проблема возникает на стыке между жизненным циклом coroutine и диагностическим контрактом сканирования. Отмена одного из внутренних job-path сейчас попадает в ту же ветку, что и настоящий сбой, хотя верхний уровень всё ещё может успешно завершить тот же запрос и показать корректный результат. В итоге observability и реальный пользовательский исход расходятся.

## 5. Предлагаемый подход

Нужно ввести явное различие между expected cancellation и failure-path для Recent Media. Штатная отмена должна немедленно выходить из ветки ошибки и не производить error-level запись, которая противоречит успешному пользовательскому результату.

Отдельно нужно выровнять completion-контракт: отменённая промежуточная ветка не должна публиковать сигнал неуспеха, если тот же пользовательский запрос уже имеет успешный выигравший результат. Для настоящих проблем чтения recent media должен остаться отдельный failure-path с явной диагностикой и предсказуемым empty/error исходом.

### 5.1 Основные столпы / модули

#### A. Явная ветка штатной отмены

- Expected cancellation трактуется как контроль потока, а не как ошибка выполнения.
- Error-level логирование и failure-completion остаются только для реальных неисправностей запроса.

#### B. Единый completion/result контракт

- Промежуточная отменённая ветка не должна загрязнять итоговую семантику загрузки Recent Media.
- Верхний слой получает согласованную картину: либо успех, либо реальный failure, но не оба исхода одновременно.

#### C. Аудит соседних virtual-local путей

- Если та же ошибка generic-exception/cancellation контракта есть в других виртуальных локальных ресурсах, тактическая спецификация должна явно решить, входит ли их выравнивание в тот же фикс.

### 5.2 Потоки данных и событий

`Open Recent Media` → `start background recent scan` → `query recent items` → `filter/complete` → `render final list`

Для штатной отмены поток должен завершаться без error-path:

`Open Recent Media` → `start background recent scan` → `expected cancellation` → `stop cancelled branch without failure telemetry`

Для реального сбоя поток остаётся диагностируемым:

`Open Recent Media` → `start background recent scan` → `unexpected query failure` → `error telemetry` → `predictable empty/error outcome`

### 5.3 Точки расширяемости

- Политика обработки cancellation должна быть пригодна для переиспользования в других local scan entry-point, если они делят тот же шаблон completion/logging.
- Точные log-level решения и объём общего аудита соседних virtual-resource сценариев определяются в тактической спецификации.

## 6. Открытые вопросы / Research items

1. **Фактический источник отмены**
   - **Вопрос:** где именно возникает штатная отмена в сценарии Recent Media: при переключении collector/job, при перезапуске загрузки ресурса или на границе возврата результата из фонового dispatcher.
   - **Варианты:** отмена родительского browse job; отмена промежуточного scan job; поздняя отмена на возврате в вызывающий контекст.
   - **Нужно выяснить:** добавить точечную диагностику cancellation-path и воспроизвести сценарий с быстрым повторным входом/refresh Recent Media.
   - **Статус:** Open

2. **Политика логирования expected cancellation**
   - **Вопрос:** должна ли штатная отмена логироваться на debug/verbose или вообще не оставлять запись.
   - **Варианты:** `Timber.d`, `Timber.v`, silent-path.
   - **Нужно выяснить:** какой уровень лучше сохраняет полезность диагностических логов без повторного шумового эффекта.
   - **Статус:** Open

3. **Объём исправления для sibling virtual resources**
   - **Вопрос:** ограничивать ли фикс только Recent Media или одновременно выровнять остальные virtual-local сканы с тем же generic cancellation handling.
   - **Варианты:** только Recent Media; Recent Media + sibling virtual-local ресурсы; общий shared helper/contract.
   - **Нужно выяснить:** есть ли воспроизводимые ложные error-level записи в соседних виртуальных локальных ресурсах.
   - **Статус:** Open

## 7. Риски

- **Риск:** ошибочная классификация может понизить уровень логирования у реального сбоя.
  **Последствия:** потеря диагностического сигнала для настоящих проблем MediaStore.
  **Митигация:** различать expected cancellation и unexpected exception по типу и контексту жизненного цикла запроса.

- **Риск:** изменение completion-семантики сломает существующую обработку empty/error на верхнем уровне.
  **Последствия:** Recent Media может перестать показывать корректный пустой результат при настоящем сбое.
  **Митигация:** зафиксировать и проверить отдельно успешный путь, expected cancellation-path и real failure-path.

- **Риск:** локальный фикс только для Recent Media оставит тот же класс ложных ошибок в соседних virtual-local ресурсах.
  **Последствия:** проблема observability останется частично нерешённой.
  **Митигация:** явный аудит объёма в тактической фазе и документированное решение по de-scope.

## 9. Архитектурные решения (ADR)

**ADR-1: Expected cancellation не считается ошибкой сканирования**

- **Решение:** штатная отмена coroutine в сценарии Recent Media выходит из error-path и не публикует ложный failure-level исход.
- **Альтернативы:** оставить current catch-all поведение; заглушить все исключения без различения причин.
- **Почему:** это выравнивает диагностику с фактическим пользовательским результатом и не маскирует настоящие сбои.

**ADR-2: Итоговый semantic outcome определяется выигравшим browse request**

- **Решение:** отменённая промежуточная ветка не может объявлять неуспех для запроса, который фактически завершился успешной загрузкой списка.
- **Альтернативы:** сохранять текущую модель, где разные внутренние ветки могут публиковать конфликтующие completion-сигналы.
- **Почему:** пользователь и журнал должны видеть один и тот же финальный исход сценария.

## 11. Критерии готовности (strategic-level)

1. В сценарии воспроизведения из лога открытие Recent Media больше не создаёт ложный error-level блок `failed to scan recent files`, если список успешно загружен.
2. Expected cancellation не приводит к публикации ложного failure completion/path для того же успешного browse request.
3. Настоящий сбой чтения recent media по-прежнему приводит к явной диагностике и предсказуемому empty/error исходу.
4. Производительность и итоговое содержимое списка Recent Media не деградируют относительно текущего успешного сценария.
5. Объём распространения фикса на sibling virtual-local ресурсы явно зафиксирован в тактической спецификации как `included` или `de-scoped`.
