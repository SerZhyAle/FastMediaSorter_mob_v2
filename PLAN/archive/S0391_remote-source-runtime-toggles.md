---

## 1. Проблема

Приложение всегда предлагает пользователю все удалённые источники - SMB, SFTP, FTP и три облачных провайдера (Google Drive, OneDrive, Dropbox), - даже если человек ими не пользуется. Лишние карточки засоряют выбор типа ресурса, а фоновая сетевая активность (синхронизация, проверки соединений, попытки авторизации) может срабатывать для протоколов, которые пользователю не нужны.

Нет способа сказать «я работаю только с локальными файлами и облаком, сетевые протоколы мне не нужны». Это вопрос чистоты интерфейса и контроля фоновой активности, а не размера приложения - библиотеки остаются в сборке.

---

## 2. Цели

1. Пользователь может в настройках включить или выключить каждый удалённый источник отдельно: SMB, SFTP, FTP, Google Drive, OneDrive, Dropbox.
2. Выключенный источник исчезает из выбора типа ресурса при добавлении новой папки.
3. Для выключенного источника не выполняется никакая фоновая активность - ни синхронизация, ни проверка соединения, ни попытки авторизации.
4. Решение опирается на единую точку гейтинга, а не на разрозненные проверки в каждом слое, обращающемся к удалённым источникам.
5. Поведение по умолчанию повторяет текущее - все доступные в данном варианте сборки источники включены, апгрейд не отнимает у пользователя ничего.

**Non-goals:**

- Уменьшение веса APK или исключение библиотек из сборки - это compile-time задача, здесь не решается.
- Удаление OAuth-компонентов из манифеста - они остаются независимо от тумблеров.
- Изменение compile-time гейтинга `SUPPORT_CLOUD`/`SUPPORT_DOCUMENTS` по вариантам сборки - тумблеры действуют поверх него, а не вместо.
- Новый сетевой протокол или провайдер - объём только про управление существующими.
- Системы авторизации и аккаунтов не затрагиваются. Облачные тумблеры не связаны с наличием Google-аккаунта (другие сервисы Google продолжают работать) и не трогают сохранённые авторизации (Instagram и любые другие, включая хранимые учётные данные OneDrive/Dropbox). Выключение источника не очищает и не меняет ни одной сохранённой авторизации (поправка владельца 2026-06-13).

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Пользователь управляет тремя групповыми тумблерами: SMB, (S)FTP (объединяет SFTP и FTP) и Облако (объединяет Google Drive, OneDrive, Dropbox) - не один общий «сеть вкл/выкл» и не шесть отдельных (поправка владельца 2026-06-13). Хранилище остаётся пер-источниковым (6 флагов); групповой тумблер пишет своих членов разом, состояние «включён, если включён хотя бы один член».
2. Те же три тумблера и в настройках, и на welcome-странице - симметрично. В настройках они в отдельном разделе, у каждого - поясняющий текст и кнопка-подсказка «?» по образцу существующих рядов.
3. Понятная судьба уже добавленных ресурсов выключенного источника - пользователь не должен думать, что данные потеряны.
4. Заменить декоративную страницу сетей welcome-флоу (3 плитки: SMB (intranet), (S)FTP, Cloud - появится из каркаса S0395) на те же плитки с групповыми тумблерами, массово пишущими пер-источниковые состояния (поправка владельца 2026-06-10 при sign-off S0395). На welcome вместо изображений появляются именно действующие тумблеры - это часть объёма, не опционально (поправка владельца 2026-06-13).
5. Если не включён ни один удалённый источник (ни SMB, ни (S)FTP, ни облако), строка закладок выбора типа ресурса в главном окне исчезает целиком - остаются только «Все» и «Локальные», а локальные считаются подмножеством «Всех», поэтому выбор типа теряет смысл (поправка владельца 2026-06-13).

### 3.2 Жёсткие ограничения

- **Flavor:** функция живёт в общем коде и применима ко всем вариантам сборки. Тумблер источника виден только если этот источник вообще поддерживается текущим вариантом сборки (например, облачные тумблеры скрыты там, где облако выключено на уровне сборки). Тумблеры не подменяют и не обходят compile-time возможности; взаимодействие с возможностями сборки идёт через существующий рантайм-слой возможностей, без чтения `BuildConfig` в общем коде (CLAUDE.md Rule 14/15). Отдельных flavor-реализаций фича не требует.
- **API level:** без API-специфики; работает на всём поддерживаемом диапазоне (minSdk 23 в legacy, 26 в остальных).
- **Wear OS:** не затрагивается; объём ограничен основным приложением.
- **Производительность:** фича снижает фоновую активность, а не добавляет её; проверка состояния тумблера на горячих путях (скан, выбор источника) должна быть дешёвой и не делать ввод-вывод.
- **Совместимость данных:** уже добавленные удалённые ресурсы сохраняются в постоянном хранилище и не удаляются при выключении источника; изменение касается только их видимости/доступности, форма хранения ресурсов не меняется.
- **Локализация:** EN/RU/UK обязательно для всех новых строк настроек и любых подсказок о выключенном источнике.
- **Доступность:** тумблеры и связанные подсказки доступны для TalkBack и навигации D-pad/мышью; состояние «включено/выключено» различимо не только цветом.

### 3.3 Owner inputs (Approval gate)

- **Flavor scope:** все варианты сборки; отдельных flavor-реализаций нет - тумблер источника показывается только когда источник поддержан текущей сборкой, через существующий рантайм-слой возможностей.
- **Performance budget:** чтение состояния тумблера на горячих путях - из памяти/кэша настроек, без обращения к диску или сети; цель - сокращение фоновых сетевых пробуждений, а не их рост.
- **Data compatibility:** уже добавленные ресурсы выключенного источника не удаляются и не мигрируются; меняется только их видимость и доступность открытия.
- **Localization:** EN/RU/UK для всех новых строк настроек и подсказок - обязательно, парность ключей проверяется.
- **UI placement contract (resolved 2026-06-13):** новый сворачиваемый раздел «Удалённые источники» во вкладке «Общие», между разделами «Файловый браузер» и «Авторизация». Внутри - три групповых тумблера (SMB / (S)FTP / Облако), у каждого поясняющий текст и кнопка-подсказка «?».
- **Accessibility:** состояние тумблера и подсказка о выключенном источнике доступны TalkBack и навигации D-pad/мышью, различимы не цветом.
- **Communication policy:** любые подсказки про выключенный источник соответствуют `docs/COMMUNICATION_POLICY.md`, включая чеклист тона из §6 политики, перед интеграцией строк.
- **Validation level:** целевые сборки затронутых вариантов проходят; ручная проверка на устройстве для UX-части (BlockNeedUserTest).
- **Owner sign-off:** <YYYY-MM-DD - заполнить при подтверждении объёма>
- **Related tickets:** S0046 (SFTP key-auth hardening) - смежная область удалённых источников, прямой зависимости нет.

## 4. Контекст текущей архитектуры

Маршрутизация источников строится вокруг перечисления типов ресурсов и расходится по нескольким независимым слоям: выбор сканера, выбор стратегии файловых операций, потоковые источники воспроизведения, загрузчики миниатюр, шлюзы соединений и диалог выбора типа ресурса при добавлении папки. Единого фасада над всеми удалёнными источниками нет - облако имеет собственную абстракцию, а сетевые протоколы представлены отдельными клиентами без общего родителя.

Сейчас невозможно «выключить» источник, потому что нет ни хранимого состояния тумблера, ни единой точки, где этот выбор учитывался бы. Положительный момент: удалённые библиотеки уже инициализируются лениво и на старте приложения не активируются, поэтому задача сводится к гейтингу явных точек входа, а не к борьбе с ранней инициализацией. Ближайший существующий образец «опционального сетевого поведения за настройкой» - переключатель фоновой синхронизации, хранимый в общем слое настроек.

---

## 5. Предлагаемый подход

Ввести единый рантайм-гейт доступности удалённых источников - роль, которая отвечает на вопрос «включён ли источник X сейчас» на основе пользовательских настроек и возможностей текущей сборки. Все слои, которым нужно знать о доступности источника, обращаются к этому гейту, а не вычисляют ответ самостоятельно. Состояние тумблеров хранится в общем слое пользовательских настроек по образцу существующего переключателя фоновой синхронизации.

Гейт объединяет два уровня в один ответ: поддержан ли источник вариантом сборки (существующий рантайм-слой возможностей) и включён ли он пользователем (новые настройки). Источник доступен, только когда оба условия истинны. Это исключает рассыпание проверок и не нарушает запрет на чтение признаков сборки в общем коде.

### 5.1 Основные столпы / модули

**Столп 1 - Хранилище состояния тумблеров.**
- По одному булеву состоянию на каждый управляемый источник: SMB, SFTP, FTP, Google Drive, OneDrive, Dropbox. Хранилище гранулярное (6 флагов), хотя пользователь видит 3 групповых тумблера - группа пишет своих членов разом; гейт по-прежнему отвечает на доступность каждого источника отдельно.
- Значение по умолчанию - «включено», чтобы апгрейд не менял текущее поведение.
- Хранится в общем слое пользовательских настроек, переживает перезапуск.

**Столп 2 - Единый гейт доступности источников.**
- Принимает тип источника, возвращает признак доступности с учётом и возможностей сборки, и пользовательского тумблера.
- Единственная точка истины; прочие слои спрашивают его, а не флаги напрямую.
- Дёшев на горячих путях - без ввода-вывода в момент запроса.

**Столп 3 - Применение гейта в точках потребления.**
- Выбор сканера, выбор стратегии файловых операций, шлюзы соединений и потоковые/миниатюрные загрузчики уважают гейт: для выключенного источника новые операции не запускаются.
- Вход создания ресурса и любые внутренние диалоги выбора ресурса (включая диалог выбора типа) показывают только доступные источники.
- Уже добавленные ресурсы выключенного источника становятся невидимыми и инертными: не сканируются, не синхронизируются, не открываются; данные при этом сохраняются.
- Путь плеера для Favorites тоже уважает гейт: воспроизведение из агрегата резолвит исходный источник и заворачивается, если он выключен.
- Строка закладок выбора типа ресурса в главном окне скрывается целиком, когда не включён ни один удалённый источник.
- Фоновая синхронизация пропускает ресурсы выключенных источников.

**Столп 4 - Настройки и UX.**
- Новый сворачиваемый раздел «Удалённые источники» во вкладке «Общие», между «Файловым браузером» и «Авторизацией». Внутри три групповых тумблера: SMB, (S)FTP, Облако.
- У каждого тумблера поясняющий текст и кнопка-подсказка «?» по образцу существующих рядов.
- Тумблер виден только если его группа поддержана сборкой; облачный тумблер скрывается целиком там, где облако не поддержано сборкой.
- Групповой тумблер включён, если включён хотя бы один источник группы (без трёхпозиционного состояния); переключение пишет всех членов группы разом.
- При выключении группы с уже добавленными ресурсами - диалог-подтверждение «папки не удалены, просто скрыты».
- Welcome-страница сетей: три декоративные плитки (SMB / (S)FTP / Cloud) из каркаса S0395 заменяются теми же тремя групповыми тумблерами, что и в настройках, массово пишущими пер-источниковые состояния; по умолчанию всё поддержанное сборкой включено.

### 5.2 Потоки данных и событий

- Пользователь переключает тумблер в настройках → состояние сохраняется в слой настроек.
- Любой слой, маршрутизирующий источник, спрашивает гейт → гейт сводит «поддержано сборкой» и «включено пользователем» → возвращает доступность.
- При добавлении папки диалог выбора типа ресурса строит список из доступных источников.
- Фоновая синхронизация перед обработкой удалённого ресурса сверяется с гейтом и пропускает выключенные.

### 5.3 Точки расширяемости

- Гейт спроектирован так, что добавление будущего удалённого источника требует одной новой записи состояния и одной строки сопоставления, без новой россыпи проверок по слоям.
- Абстракция гейта - это вводимая/расширяемая роль рантайм-слоя возможностей; конкретная привязка зависимостей определяется на стадии `/spec-tech`.
- Состав управляемых источников остаётся данными, а не жёстко зашитой логикой в каждом потребителе.

## 6. Открытые вопросы / Research items

1. **Судьба уже добавленных ресурсов выключенного источника**
   - **Вопрос:** что происходит с папками выключенного источника, которые пользователь уже добавил?
   - **Решение владельца (2026-06-13):** ресурсы не удаляются, становятся невидимыми и инертными - программа с ними не взаимодействует вовсе. Выбран вариант «скрыть из списка».
   - **Коммуникация (2026-06-13):** при выключении источника с уже добавленными ресурсами показывается диалог-подтверждение «папки не удалены, просто скрыты», чтобы пользователь не думал о потере данных.
   - **Статус:** Resolved

2. **Поведение при выключении источника с активной фоновой синхронизацией**
   - **Вопрос:** нужно ли немедленно отменять уже идущую фоновую задачу для этого источника или достаточно не запускать новые.
   - **Решение владельца (2026-06-13):** намерение - полное отсутствие взаимодействия, поэтому идущую задачу для выключенного источника отменяем.
   - **Остаётся на impl:** жёсткость отмены - best-effort, так как уже синхронизированное в текущем проходе не откатывается.
   - **Статус:** Resolved (степень жёсткости - на impl)

3. **Гранулярность облачного раздела при выключенном на уровне сборки облаке**
   - **Вопрос:** показывать ли блок облачных тумблеров вообще в сборках без поддержки облака.
   - **Варианты:** скрывать весь блок; показывать неактивным с пояснением.
   - **Решение владельца (2026-06-13):** скрывать весь блок целиком - согласуется с принципом «выключенное исчезает из интерфейса».
   - **Статус:** Resolved

4. **Отображение группового тумблера при смешанном пер-источниковом состоянии**
   - **Вопрос:** что показывает групповой тумблер (welcome и настройки), если внутри группы часть источников включена, часть выключена; у `Switch` нет неопределённого состояния.
   - **Решение владельца (2026-06-13):** групповой тумблер включён, если включён хотя бы один источник группы (Switch-native, без кастомного трёхпозиционного элемента).
   - **Статус:** Resolved

5. **Гейтинг пути плеера для Favorites**
   - **Вопрос:** применять ли гейт к виртуальному агрегату Favorites (id=-100L), где тип ресурса определяется по префиксу пути.
   - **Решение владельца (2026-06-13):** гейтить и путь плеера Favorites - полное отсутствие взаимодействия; требует резолва исходного ресурса перед воспроизведением.
   - **Статус:** Resolved

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Пропущена одна из точек потребления, источник «выключен», но где-то всё равно активен | Средняя | Фоновая активность для выключенного источника сохраняется, цель не достигнута | Свести все проверки к единому гейту; составить чеклист точек потребления на `/spec-tech` |
| Пользователь выключает источник и думает, что добавленные папки удалены | Средняя | Паника, обращения в поддержку | Чёткая коммуникация на `/ui-clarify`; не удалять данные, только менять видимость |
| Дешёвая на вид проверка гейта оказывается на горячем пути с вводом-выводом | Низкая | Просадка скорости скана/листания | Состояние тумблеров держать в памяти/кэше настроек, без диска на запросе |

## 8. Влияние на пользователя (docs/FEATURES)

Новая способность, воспринимаемая пользователем: возможность включать и выключать отдельные удалённые источники (SMB, SFTP, FTP, Google Drive, OneDrive, Dropbox) в настройках. Одно предложение для `docs/FEATURES.md` + `_RU` + `_UK`: «Включайте и отключайте отдельные сетевые и облачные источники в настройках, чтобы убрать ненужные из выбора и остановить их фоновую активность.»

---

## 9. Архитектурные решения (ADR)

**ADR-1: Единый рантайм-гейт вместо разрозненных проверок**

- **Решение:** ввести одну точку, отвечающую на доступность источника, и обращаться к ней из всех слоёв-потребителей.
- **Альтернативы:** локальная проверка тумблера в каждом слое (сканер, стратегия, шлюзы, диалог) по отдельности.
- **Почему:** маршрутизация источников уже рассыпана по 6+ точкам; дублирование проверок гарантировало бы пропуски и расхождения. Единый гейт - единственная точка истины.

**ADR-2: Runtime-гейт, а не вариант сборки**

- **Решение:** управлять источниками пользовательской настройкой во время работы, библиотеки остаются в сборке.
- **Альтернативы:** исключение библиотек на этапе сборки через варианты/feature-модули.
- **Почему:** цель - UX и контроль фоновой активности, не вес APK; compile-time исключение не даёт «галочки в настройках» и не входит в объём.

**ADR-3: Тумблеры действуют поверх возможностей сборки, а не вместо них**

- **Решение:** источник доступен только при истинности обоих условий - поддержан сборкой и включён пользователем.
- **Альтернативы:** тумблер игнорирует возможности сборки.
- **Почему:** иначе тумблер мог бы «включить» облако в сборке без облачной поддержки; гейт обязан уважать compile-time границы и не нарушать изоляцию вариантов.

## 11. Критерии готовности (strategic-level)

1. В настройках есть три групповых тумблера (SMB, (S)FTP, Облако) в разделе «Удалённые источники» между «Файловым браузером» и «Авторизацией»; у каждого поясняющий текст и кнопка «?»; видны только поддержанные текущей сборкой группы.
2. При выключенном источнике он отсутствует в выборе типа ресурса при добавлении папки.
3. При выключенном источнике для него не происходит фоновой синхронизации, проверок соединения и попыток авторизации.
4. Уже добавленные ресурсы выключенного источника не удаляются; их судьба соответствует согласованному на `/ui-clarify` поведению.
5. По умолчанию (после апгрейда) все поддержанные сборкой источники включены - поведение не меняется без действия пользователя.
6. Все новые строки настроек присутствуют в EN/RU/UK.
7. Welcome-страница сетей показывает те же три групповых тумблера (SMB / (S)FTP / Облако) вместо декоративных плиток; выбор на онбординге читается и пишется теми же настройками, что и раздел настроек.
8. Если не включён ни один удалённый источник, строка закладок выбора типа ресурса в главном окне отсутствует.
9. Тумблеры не затрагивают системы авторизации и аккаунтов; выключение источника не меняет сохранённых авторизаций.
10. Воспроизведение выключенного источника из агрегата Favorites заворачивается гейтом, а не открывается.
