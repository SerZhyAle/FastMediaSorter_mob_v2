## 1. Проблема

Старый сохранённый список файлов может стать несовместимым после обновления release-сборки, если R8 изменил имена полей его Gson-модели. Такой снимок не всегда вызывает ошибку при чтении: отсутствующие обязательные данные попадают в объект как null и приводят к фатальному падению позже, когда ресурсный экран вычисляет статистику. Пользователь не может безопасно открыть или проверить затронутый ресурс после обновления приложения.

## 2. Цели

1. Сохранённые списки файлов используют стабильные JSON-ключи во всех будущих miniфицированных сборках.
2. Несовместимый или повреждённый старый снимок отбрасывается до передачи в остальной код и не вызывает падение.
3. Вычисление статистики ресурса остаётся безопасным, даже если кэш недоступен.
4. Release-проверка подтверждает сохранение требуемых имён и корректность сценария обновления.

**Non-goals:**

- Не менять структуру Room-таблицы и не добавлять миграцию базы данных.
- Не восстанавливать повреждённые списки файлов из старого блоба.
- Не менять пользовательский интерфейс или тексты.

## 4. Контекст текущей архитектуры

Список медиафайлов для ресурса хранится как один сжатый JSON-снимок в локальном кэше. Его читают несколько потоков, в том числе расчёт статистики на экране редактирования ресурса. Сейчас граница кэша принимает любой Gson-результат как пригодный объект и передаёт его дальше.

Предыдущие release-аудиты уже закрепили правило: модели, чьи JSON-поля живут между сборками без `SerializedName`, должны сохранять имена полей при R8. Этот кэш не был включён в тот целевой контракт.

## 5. Предлагаемый подход

Граница сохранённого списка получает два уровня защиты. Стабильная контрактная политика miniфикации предотвращает создание новых mapping-зависимых снимков. При чтении кэш проверяет обязательные свойства каждого элемента и удаляет снимок, если его нельзя безопасно использовать, возвращая обычный cache miss.

Потребители статистики рассматривают отсутствие валидного снимка как нулевую дополнительную информацию, а не как исключение. Обычный следующий скан создаёт новый совместимый кэш в существующем формате.

### 5.1 Основные столпы / модули

#### Стабильный сериализационный контракт

Целевая модель кэш-снимка сохраняет имена полей в минифицированных сборках.

#### Безопасная граница кэша

Слой чтения отвергает malformed и неполные элементы, очищает затронутый снимок и не пропускает их к потребителям.

#### Устойчивая статистика

Расчёт статистики продолжает работать с отсутствующим кэшем и использует данные ресурса без аварийного завершения coroutine.

### 5.2 Потоки данных и событий

Сохранение списка -> стабильный JSON-снимок -> сжатый кэш -> проверка при чтении -> валидный список или cache miss -> расчёт статистики без падения.

### 5.3 Точки расширяемости

Проверка снимка остаётся в одном владельце persistence boundary, поэтому новые обязательные поля или будущая версия формата смогут централизованно объявить снимок несовместимым.

## 9. Архитектурные решения (ADR)

**ADR-1: Несовместимый кэш отбрасывается, а не исправляется частично**

- **Решение:** Возвращать cache miss и удалять снимок, который не удовлетворяет обязательному контракту.
- **Альтернативы:** Пытаться заполнить отсутствующие значения эвристиками или позволить исключению дойти до потребителя.
- **Почему:** Кэш является производным и возобновляемым; частично восстановленный путь может исказить список или снова вызвать падение.

**ADR-2: Будущая совместимость обеспечивается узким R8 keep-контрактом**

- **Решение:** Сохранить имена полей только модели persistence-снимка.
- **Альтернативы:** Keep всего domain-пакета или только defensive null checks.
- **Почему:** Узкое правило повторяет доказанный контракт Gson-моделей и не платит размером за весь пакет; проверки чтения остаются защитой для уже повреждённых данных.
