> Журнальный статус — `BlockNeedUserTest`: реализация завершена, нужна проверка на устройстве (вход в Instagram через встроенный WebView без `ERR_UNKNOWN_URL_SCHEME`; предложение авторизации при шаринге соцссылки; верхний тулбар и кнопка «+» на экране авторизаций без перекрытия системными панелями).

---

## 1. Проблема

Скачивание медиа по ссылке (S0116) умеет хранить авторизации сайтов, но связка работает плохо. При шаринге ссылки с соцсети приложение не предлагает завести авторизацию для этого ресурса — оно делает это только если скачивание уже упало с «нужен вход» и только при определённой настройке. Экран списка сохранённых авторизаций открывается без шапки и без учёта системных панелей, поэтому кнопка «Добавить авторизацию» уезжает под нижнюю панель навигации. При ручном добавлении авторизации приходится вписывать полный адрес руками — нет выбора из известных соцсетей. И сама авторизация в Instagram через встроенный WebView падает: страница редиректит на схему `intent://…`, WebView её не понимает и показывает «Webpage not available — net::ERR_UNKNOWN_URL_SCHEME».

---

## 2. Цели

1. При получении (шаринге) ссылки с известного соцсетевого ресурса, для которого ещё нет сохранённой авторизации, приложение предлагает её добавить — до того, как пользователь столкнётся с неудачным скачиванием.
2. Экран списка сохранённых авторизаций имеет верхнюю панель с заголовком и кнопкой добавления; ни один управляющий элемент не перекрывается системными панелями ни в портретной, ни в альбомной ориентации.
3. При добавлении новой авторизации пользователь может выбрать ресурс из встроенного списка популярных соцсетей либо ввести адрес вручную.
4. Авторизация в Instagram (и других ресурсах, отдающих редирект на нестандартную схему) проходит во встроенном WebView без ошибки «неизвестная схема».

**Non-goals:**

- Не добавляем парсеры/экстракторы контента для новых соцсетей — речь только про хранение и применение авторизаций.
- Не делаем редактирование уже сохранённых авторизаций (только добавление и удаление, как сейчас).
- Не делаем синхронизацию авторизаций между устройствами.
- Список известных ресурсов не настраивается пользователем и не тянется с сети — он встроен в сборку и пополняется от версии к версии.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Стартовый список известных ресурсов — около десяти популярных площадок с медиа-контентом: Instagram, Pinterest, TikTok, X (Twitter), DeviantArt, Threads, Reddit, Tumblr, Flickr, ArtStation. Состав со временем расширяется.
2. Для ресурсов из списка использовать сразу «правильный» веб-адрес страницы входа, чтобы не натыкаться на редирект в нативное приложение.
3. Отказ пользователя добавлять авторизацию для конкретного ресурса запоминается, чтобы предложение не появлялось при каждом шаринге ссылки с того же хоста.

### 3.2 Жёсткие ограничения

- **Flavor:** все варианты, где доступна фича скачивания по ссылке (та же область, что и S0116). На сборках без неё новое поведение не появляется.
- **API level:** без API-специфики; обработка `intent://`-редиректов должна работать на минимально поддерживаемом уровне.
- **Wear OS:** не затрагивается.
- **Производительность:** не критично; новый диалог-предложение не должен задерживать обработку шаринга, когда авторизация уже есть или ресурс не из списка.
- **Совместимость данных:** добавляется хранение «отказов» по хостам — без слома существующего хранилища авторизаций; отсутствие этих данных трактуется как «отказов не было».
- **Локализация:** EN/RU/UK — обязательно для всех новых строк (заголовок экрана, текст диалога-предложения, подписи в выборе ресурса).
- **Доступность:** кнопка добавления в верхней панели — стандартный touch target ≥ 48dp; иконка снабжена content description; диалог-предложение читается TalkBack.
- **Тон сообщений:** новые пользовательские строки проходят чек-лист тона из `docs/COMMUNICATION_POLICY.md` (§6) перед интеграцией; диалог-предложение — дружелюбная формулировка, не алармовая.

## 4. Контекст текущей архитектуры

Скачивание по ссылке (S0116) состоит из приёма расшаренной ссылки, конвейера «ссылка → файл», хранилища зашифрованных cookie-сессий и встроенного WebView-диалога для входа на сайт. Предложение войти сейчас исходит только из presenter'а результата скачивания — то есть после неудачной попытки и только при включённом авто-открытии в плеере. Экран списка авторизаций — отдельный тонкий экран-хост с одним фрагментом-списком и плавающей кнопкой в углу; своей шапки и обработки системных вырезов у него нет. WebView-диалог входа открывает переданный адрес «как есть» и не вмешивается в навигацию, поэтому редирект на `intent://` доходит до движка и завершается ошибкой схемы. Курируемого списка известных соцсетевых хостов в проекте нет.

## 5. Предлагаемый подход

Все четыре правки лежат в области S0116 и не выходят за её слои: приём шаринга, экран списка авторизаций, диалог входа, и общий справочник известных ресурсов.

### 5.1 Основные столпы / модули

#### A. Справочник известных ресурсов

- Встроенный в сборку статический список: для каждого ресурса — отображаемое имя, базовый хост (для сопоставления с пришедшей ссылкой) и канонический веб-адрес страницы входа.
- Используется в трёх местах: распознавание соцсетевой ссылки при шаринге (столп B), список выбора при ручном добавлении (столп D), выбор «правильного» стартового адреса для WebView-входа (столп E).
- Точка расширения: добавление новой записи в список — единственное изменение, нужное для поддержки ещё одной площадки на уровне авторизаций.

#### B. Предложение добавить авторизацию при шаринге

- При получении расшаренной ссылки определить хост и сверить со справочником (столп A).
- Если хост известен, сохранённой авторизации для него нет и пользователь ранее не отказывался для этого хоста — показать диалог-предложение: коротко объяснить, что для этого сайта может потребоваться вход, и дать выбор «Добавить» / «Пропустить».
- «Добавить» — открыть WebView-диалог входа на каноническом адресе этого ресурса.
- «Пропустить» — продолжить обычную обработку ссылки и запомнить отказ для этого хоста.
- Если авторизация уже есть, хост не из справочника или отказ уже зафиксирован — поведение не меняется (обычная обработка ссылки).
- Предложение не блокирует и не отменяет обычный путь скачивания: это дополнительный шаг, а не замена существующей логики «нужен вход → WebView».

#### C. Экран списка авторизаций с верхней панелью

- Экран получает верхнюю панель с заголовком и действием «Добавить авторизацию» в виде иконки «+» справа.
- Прежняя плавающая кнопка в нижнем углу убирается.
- Экран корректно учитывает системные панели (статус-бар и навигация) в обеих ориентациях — ни один элемент не уходит под них.
- Содержимое (список и состояние «нет сохранённых авторизаций») остаётся прежним по смыслу, меняется только обрамление и расположение кнопки добавления.

#### D. Выбор ресурса при добавлении авторизации

- При добавлении авторизации вместо одного поля «введите адрес» пользователь сначала выбирает из списка известных ресурсов (столп A) либо пункт «Ввести вручную».
- Выбор известного ресурса сразу подставляет его канонический адрес и открывает WebView-вход; ручной ввод сохраняет нынешнее поведение (поле адреса + проверка, что это http/https).
- Список ресурсов в этом выборе и в предложении при шаринге — один и тот же справочник.

#### E. Корректная обработка редиректов в WebView-входе

- WebView-диалог входа перехватывает попытки навигации: адреса с не-http(s) схемой (`intent://`, схемы конкретных приложений, `market://` и т.п.) не загружаются движком.
- Для `intent://`-редиректа, если в нём указан запасной веб-адрес, загрузить именно его; иначе остаться на текущей странице.
- Для ресурсов из справочника входить сразу по их каноническому адресу страницы входа, чтобы по возможности вообще не доходить до редиректа в нативное приложение.
- При срабатывании перехвата — диагностический след в лог (трасса link-download), чтобы было видно, что редирект был погашен, а не привёл к ошибке.

### 5.2 Потоки данных и событий

- Шаринг ссылки → определение хоста → сверка со справочником и хранилищем авторизаций/отказов → (опционально) диалог-предложение → либо WebView-вход, либо обычный конвейер скачивания.
- Экран списка авторизаций → действие «+» в верхней панели → выбор ресурса (справочник) или ручной ввод → WebView-вход → сохранение сессии в существующее хранилище.
- WebView-вход → перехват навигации → загрузка только http(s) (или запасного веб-адреса) → по завершении входа пользователь сохраняет сессию, как сейчас.

### 5.3 Точки расширяемости

- Справочник известных ресурсов — добавление новой записи без других изменений включает площадку в предложение при шаринге, в выбор при добавлении и в выбор стартового адреса входа.
- Хранилище «отказов» по хостам — может в будущем получить сброс из настроек («снова предлагать вход для …»), но это вне объёма.

## 6. Открытые вопросы / Research items

1. **Канонические адреса страниц входа**
   - **Вопрос:** для каждой из ~10 площадок нужен веб-адрес формы входа, который открывается во встроенном WebView и не перебрасывает в нативное приложение.
   - **Нужно выяснить:** проверить на устройстве актуальные адреса входа (например, у Instagram — страница `accounts/login`), убедиться, что они работают без редиректа на `intent://`.
   - **Статус:** Open — уточняется на этапе тактической реализации/тестирования; не блокирует написание спеки.

2. **Где именно в потоке шаринга показывать диалог-предложение**
   - **Вопрос:** показывать предложение до старта конвейера скачивания или параллельно с ним (чтобы при «Пропустить» не терять время).
   - **Варианты:** (а) показать диалог, дождаться ответа, потом продолжить; (б) сразу запустить скачивание, диалог — отдельно.
   - **Нужно выяснить:** не создаёт ли вариант (б) гонок с уже существующим путём «нужен вход → WebView». Решение зафиксировать в тактической спеке.
   - **Статус:** Open.

3. **Хранение «отказов» по хостам**
   - **Вопрос:** где хранить список хостов, для которых пользователь нажал «Пропустить» — рядом с настройками или рядом с хранилищем авторизаций.
   - **Нужно выяснить:** какой из существующих механизмов хранения проще и не требует схемных изменений. Решение — в тактической спеке.
   - **Статус:** Open.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Перехват навигации в WebView слишком агрессивен и ломает легитимные шаги входа (OAuth, капча) | Средняя | Пользователь не может войти на сайт | Блокировать только не-http(s) схемы; http/https-навигацию не трогать; покрыть проверкой на реальном входе Instagram |
| Канонические адреса входа со временем меняются у площадок | Средняя | Открывается не та страница, вход затруднён | Справочник — в сборке, правится в очередном релизе; при провале — fallback на «обычный» хост площадки |
| Диалог-предложение раздражает при частом шаринге ссылок | Низкая | Негативный UX | Запоминать отказ per-host; не показывать, если авторизация уже есть |
| Новый экран с верхней панелью разойдётся с остальными «под-экранами» настроек по виду | Низкая | Визуальная несогласованность | Использовать тот же паттерн оформления, что и у других не-табных экранов настроек |

## 9. Архитектурные решения (ADR)

**ADR-1: Справочник известных ресурсов — статический ресурс в сборке, не БД и не сеть**

- **Решение:** список известных соцсетей с базовым хостом и адресом входа хранится в коде/ресурсах приложения.
- **Альтернативы:** таблица в БД (редактируемая пользователем); загрузка списка с сервера.
- **Почему:** список меняется редко и одинаков для всех; пользовательская правка и серверная доставка дают сложность без ценности на этой итерации; пополнение от версии к версии — приемлемая модель.

**ADR-2: Предложение входа — отдельный неблокирующий шаг, существующий путь «нужен вход → WebView» сохраняется**

- **Решение:** новое предложение при шаринге не заменяет реакцию на ошибку авторизации в конце скачивания, а дополняет её на входе в поток.
- **Альтернативы:** переделать весь путь авторизации вокруг нового диалога.
- **Почему:** меньше регрессионный риск для S0116; обе точки полезны (одна — проактивная, другая — реактивная).

**ADR-3: WebView-вход перехватывает только не-http(s) навигацию**

- **Решение:** в обработчике навигации гасить лишь нестандартные схемы (intent://, схемы приложений, market:// и пр.), http/https пропускать без вмешательства.
- **Альтернативы:** белый список доменов; принудительная подмена user-agent на десктопный.
- **Почему:** минимально инвазивно; не ломает капчу/2FA/OAuth; решает корневую причину ошибки `ERR_UNKNOWN_URL_SCHEME`.

## 11. Критерии готовности (strategic-level)

1. При шаринге ссылки с известной соцсети без сохранённой авторизации пользователь видит предложение её добавить; «Добавить» открывает встроенный вход, «Пропустить» — продолжает обычную обработку и больше не показывает предложение для этого хоста.
2. Если авторизация для хоста уже есть либо хост не из списка — никакого нового диалога не появляется.
3. На экране списка авторизаций видна верхняя панель с заголовком и кнопкой «+»; кнопка и список не перекрываются системными панелями ни в портрете, ни в альбоме.
4. При добавлении авторизации пользователь может выбрать ресурс из списка популярных соцсетей (минимум десять записей) либо ввести адрес вручную; выбор известного ресурса сразу открывает вход на его странице.
5. Вход в Instagram через встроенный WebView открывает страницу логина и не показывает ошибку «Webpage not available / net::ERR_UNKNOWN_URL_SCHEME»; перехват редиректа виден в логе.
6. Существующие сохранённые авторизации и их удаление продолжают работать как раньше.
