## 1. Проблема

Персистентная память между сессиями сегодня накоплена только для одного агентского профиля. Остальные именованные профили, которые уже участвуют в нетривиальной работе, стартуют почти без накопленных проектных инвариантов и повторно проходят через уже изучённые ошибки и уточнения.

Это создаёт асимметрию внутри одного харнесса: один профиль компаундирует опыт, остальные каждый раз заново реконструируют правила по Timber-тегам, flavor-isolation, PowerShell-ритуалам, post-change дисциплине и другим устойчивым ограничениям проекта. Потеря не выглядит как один крупный сбой, но ежедневно съедает время на повторное объяснение и повышает шанс регрессии в знакомых местах.

## 2. Цели

1. Каждый целевой именованный агентский профиль получает собственный каталог памяти с индексом `MEMORY.md` и минимальным стартовым набором записей.
2. Стартовый набор для каждого профиля адаптирован под его роль, а не является дословной копией памяти профиля-донора.
3. Ключевые проектные инварианты становятся доступны профилю с первой сессии без повторного ручного ввода оператором.
4. Формат памяти остаётся единообразным между профилями: индекс, frontmatter, типы записей и способ ссылок не расходятся.
5. Память профиля-донора используется только как источник чтения и не модифицируется в рамках задачи.

**Non-goals:**

- Не вводится общий shared-слой памяти между профилями.
- Не автоматизируется двусторонняя синхронизация памяти между профилями.
- Не меняется сам формат памяти, frontmatter, типы записей и синтаксис ссылок.
- Не пересобирается и не редактируется уже работающий каталог памяти профиля-донора.
- Не засеваются анонимные профили общего назначения.
- Не вводится отдельный регламент обязательной периодической ревизии засеянной памяти.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Стартовый набор должен быть компактным: лучше несколько точных записей, чем широкий каталог "на всякий случай".
2. Каждая запись должна помогать профилю оставаться в своей роли, а не провоцировать выход за неё.
3. Индекс `MEMORY.md` должен оставаться плоским и быстро читаемым.
4. Текст записей должен сохранять проектный стиль: `..` вместо трёх точек и `ё`/`Ё` в русскоязычных фрагментах.

## 4. Контекст текущей архитектуры

Память агентского профиля живёт вне основного кода продукта и представляет собой файловый слой continuity-инфраструктуры. При старте сессии профиль получает индекс памяти, а отдельные записи подтягиваются по мере релевантности. Это означает, что даже небольшой набор качественно подобранных записей влияет на поведение профиля раньше, чем чтение проектной документации или кода по месту задачи.

Сейчас memory-layer фактически специализируется только на одном профиле. Внутри этого профиля уже накоплены записи четырёх типов: поведенческие feedback-правила, project-контекст, немного user-фактов и редкие reference-указатели. Остальные профили либо не имеют такого слоя вовсе, либо не имеют рабочего индекса, поэтому не используют тот же механизм накопления опыта.

## 5. Предлагаемый подход

Базовый подход - одноразовый управляемый засев для ограниченного набора именованных профилей. Суть не в синхронизации, а в переносе нескольких наиболее ценных инвариантов из профиля-донора в роль-ориентированные стартовые наборы.

### 5.1 Основные столпы / модули

- **Профиль-донор.** Один существующий профиль с уже накопленной памятью используется как источник проверенных инвариантов.
- **Целевые профили.** Каждый профиль получает собственный независимый каталог памяти с отдельным индексом и собственным набором файлов.
- **Ролевой фильтр.** Перед переносом каждая запись проверяется на применимость к зоне ответственности конкретного профиля.
- **Адаптация содержания.** Даже подходящая запись переписывается под роль целевого профиля, прежде всего в части практического применения.

### 5.2 Потоки данных и событий

Оператор или агент подготавливает компактный список инвариантов из профиля-донора, затем для каждого целевого профиля отфильтровывает релевантные записи и создаёт локальные копии в его каталоге памяти. После этого профиль начинает читать собственный `MEMORY.md` как стартовый индекс и использовать соответствующие записи в новых сессиях.

### 5.3 Точки расширяемости

- Должна остаться возможность добавить новый именованный профиль и провести аналогичный засев тем же ручным ритуалом.
- Должна сохраниться возможность расширить bootstrap/continuity-слой диагностикой "память отсутствует" без изменения формата записей.
- Должна сохраниться возможность дальнейшей независимой эволюции памяти каждого профиля без обязательной обратной синхронизации.

## 9. Архитектурные решения (ADR)

**ADR-1: Каждый профиль хранит собственные физические копии адаптированных записей**

- **Решение:** У каждого целевого профиля появляется собственный независимый набор файлов памяти без shared-слоя и без симлинков.
- **Альтернативы:** общий shared-каталог; ссылки на записи профиля-донора; частичная дедупликация на уровне файловой системы.
- **Почему:** Независимые копии упрощают поведение харнесса, не зависят от особенностей Windows/Git и поддерживают обязательную ролевую адаптацию.

**ADR-2: Засев - это отбор и адаптация, а не механическое копирование**

- **Решение:** Каждая запись переносится в профиль только после проверки на ролевую применимость и переписывается под практическое применение этим профилем.
- **Альтернативы:** прямой copy-paste подходящих записей; единый одинаковый стартовый пакет для всех профилей.
- **Почему:** Память агента должна усиливать профильную роль, а не превращаться в общий справочник без привязки к ответственности.
