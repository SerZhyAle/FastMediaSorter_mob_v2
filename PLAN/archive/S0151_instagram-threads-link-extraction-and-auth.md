## 1. Проблема

При шаринге ссылки на Instagram-reel, на пост Instagram (в т.ч. карусель с несколькими изображениями) и на пост Threads приложение «успешно» скачивает не то: вместо видео reel'а или изображений карусели оно сохраняет превью-картинку поста (то, что сайт отдаёт в Open Graph), и считает операцию выполненной. Пользователь получает в Загрузках бесполезный мелкий снимок вместо контента. При этом авторизация не предлагается ни проактивно, ни реактивно: проактивное предложение (S0144) не появляется, если для хоста уже есть сохранённая сессия (для `instagram.com` она была), а реактивный путь «нужен вход → встроенный браузер» не срабатывает, потому что эвристика «похоже на стену логина» включается только когда вообще нет ни одного кандидата на медиа — а превью-картинка как кандидат есть, и поток завершается «успехом». Отдельно: ссылки Threads приходят с домена `threads.com` (площадка переехала), а встроенный справочник известных ресурсов знает только `threads.net`, поэтому для Threads не появляется даже проактивное предложение авторизации.

---

## 2. Цели

1. Для ссылки на Instagram-reel скачивается само видео reel'а; для поста Instagram-карусели — изображения карусели (а не одна превью-картинка); для поста Threads — медиа из поста.
2. Если по ссылке с известной соцсети удалось извлечь только превью-картинку из метаданных страницы (Open Graph) и больше ничего — это не считается успешным скачиванием контента: пользователю предлагается авторизоваться (или обновить авторизацию), а превью-картинка сама по себе в Загрузки не сохраняется (либо сохраняется только как явный осознанный выбор).
3. Предложение авторизоваться появляется и тогда, когда сохранённая сессия для хоста уже есть, но извлечь реальное медиа всё равно не удалось — потому что сессия могла истечь или быть недостаточной (предложение в этом случае — «войти заново / обновить вход»).
4. Ссылки Threads с домена `threads.com` распознаются как Threads наравне с `threads.net` — и для проактивного предложения авторизации, и для встроенного входа, и в выборе ресурса при ручном добавлении авторизации.
5. Когда реальное медиа извлечь не получилось и пользователь отказался от авторизации — он получает понятное сообщение «не удалось получить контент по этой ссылке» (а не молчаливо сохранённую превью-картинку с видом успеха).

**Non-goals:**

- Не строить полноценный универсальный экстрактор-парсер для всех соцсетей — фокус на Instagram и Threads (Meta-площадки с общей моделью входа); расширение на другие площадки — отдельные задачи.
- Не обходить ограничения площадок: если контент доступен только авторизованному пользователю и пользователь не авторизовался — скачивания нет, это ожидаемо.
- Не делать редактирование уже сохранённых авторизаций сверх того, что есть (добавление/удаление/повторный вход).
- Не менять поток скачивания для прямых файлов, для обычных HTML-страниц с явным медиа и для стриминговых манифестов — затрагивается только ветка «с известной соцсети пришла только превью-картинка».
- Не трогать flavor'ы, где скачивание по ссылке отсутствует.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Желательно переиспользовать существующий механизм входа во встроенном браузере и хранилище зашифрованных сессий (S0116/S0144) — не плодить новый.
2. Желательно, чтобы для Instagram/Threads сначала пробовался путь с применением сохранённых cookie (включая динамический разбор страницы во встроенном браузере), и только если он не дал реального медиа — предлагался вход.
3. Желательно, чтобы при отказе пользователя от входа отказ запоминался по хосту (как уже делает S0144), но «реальное медиа всё ещё не получено» не подавлялось этим отказом — то есть при следующей попытке скачивания с того же хоста сообщение «контент недоступен» всё равно показывается, просто без повторного навязчивого предложения войти.
4. Желательно отличать в логе «извлекли реальное медиа», «извлекли только превью», «требуется вход» и «вход есть, но медиа всё равно нет» — для диагностики.
5. Желательно, чтобы предложение «войти заново» появлялось только тогда, когда оно реально нужно (сессия не справилась), и было оформлено так, чтобы пользователь понимал, ПОЧЕМУ его просят войти ещё раз (объяснение «сохранённая сессия для этого ресурса не дала контент — возможно, устарела»), а не как безличный повтор. Сама проблема «навязчивости после недавнего успешного входа» (полевой инцидент 2026-05-11) решается на уровне S0155 (несколько аккаунтов на один хост + явный выбор аккаунта + поаккаунтное сообщение); до интеграции S0155 — снимается ясным текстом диалога, без эвристики «свежести сессии».

### 3.2 Жёсткие ограничения

- **Flavor:** все варианты, где доступна фича скачивания по ссылке (та же область, что и S0116). На сборках без неё поведение не появляется. Если для извлечения видео reel'а нужен путь ремукса/стриминга — он гейтится теми же признаками сборки, что и существующий стриминговый конвейер (видео-flavor'ы); на сборках без видео reel-видео не извлекается, но превью-fallback и предложение входа поведением не отличаются от текущего.
- **API level:** без API-специфики; работа встроенного браузера и обработка нестандартных схем — на минимально поддерживаемом уровне.
- **Wear OS:** не затрагивается.
- **Производительность:** дополнительный путь (применение cookie + динамический разбор страницы) не должен задерживать обработку, когда ссылка не с соцсети или реальное медиа уже найдено обычным путём; превью-картинка не должна скачиваться «на всякий случай», если она в итоге не нужна.
- **Совместимость данных:** переиспользуется существующее хранилище сессий и «отказов по хостам»; новых схемных изменений не предполагается; обновлённый справочник известных ресурсов (добавление `threads.com`) — встроен в сборку, не ломает существующие записи.
- **Локализация:** EN/RU/UK — обязательно для всех новых/изменённых пользовательских строк (предложение «войти заново / обновить вход», сообщение «контент по ссылке недоступен»).
- **Доступность:** диалоги предложения входа и сообщения об ошибке читаются TalkBack; стандартные touch target'ы.
- **Тон сообщений:** новые строки проходят чек-лист тона из `docs/COMMUNICATION_POLICY.md` (§6) перед интеграцией — дружелюбное объяснение «для этого контента нужен вход», не алармовая формулировка.

## 4. Контекст текущей архитектуры

Скачивание по ссылке (S0116/S0003) — это конвейер стратегий извлечения: прямой файл, разбор HTML-страницы, динамический разбор во встроенном браузере, стриминговый манифест; первая применимая стратегия отдаёт поток или набор элементов, который сохраняется в выбранный ресурс (или, при недоступности ресурса, — в системные Загрузки). HTML-стратегия собирает кандидатов из метаданных страницы и тегов, в том числе превью-картинку из Open Graph; если кандидаты есть — выбирается лучший и скачивается, и поток считается успешным. Эвристика «похоже на стену логина» (с предложением входа) запускается только когда кандидатов не нашлось вовсе. Проактивное предложение авторизации (S0144) при шаринге смотрит во встроенный справочник известных соцсетей и в хранилище сессий/отказов и предлагает вход только если сессии для хоста ещё нет. Встроенный браузер для входа и хранилище зашифрованных сессий уже существуют (S0116/S0144). Для Instagram/Threads страница, отдаваемая без полноценной авторизованной сессии, как правило содержит только превью-картинку в Open Graph и не содержит прямой ссылки на видео reel'а — поэтому текущий конвейер «успешно» забирает превью и на этом останавливается.

## 5. Предлагаемый подход

Ввести понятие «извлекли только превью, реального контента нет» как отдельный неуспешный (или «частично успешный, требующий решения пользователя») исход для ссылок с известных соцсетей, и в этом случае: сначала попробовать получить реальное медиа применив сохранённую сессию и динамический разбор во встроенном браузере; если и это не дало контента — предложить вход (или повторный вход, если сессия уже была); превью-картинку саму по себе в Загрузки не класть, а при окончательной неудаче — честно сообщить пользователю.

### 5.1 Основные столпы / модули

#### A. Классификация исхода «только превью»

- Когда единственный извлечённый кандидат с известного соцсетевого хоста — превью-картинка из метаданных страницы (Open Graph), исход помечается как «реального контента не получено», а не «успех».
- Для прочих хостов и прочих ситуаций (есть прямое видео, есть карусель, есть стриминговый манифест, прямой файл и т.п.) поведение не меняется.

#### B. Попытка получить реальное медиа для Instagram/Threads

- Для ссылок с этих хостов конвейер обязательно проходит через путь «применить сохранённую сессию + динамический разбор страницы во встроенном браузере» прежде, чем признать, что доступна только превью-картинка.
- Если этот путь дал видео reel'а или элементы карусели — они и скачиваются (видео — через существующий стриминговый/ремукс-конвейер на видео-сборках; набор изображений — как пакет элементов).
- Если не дал — переход к столпу C.

#### C. Предложение входа (или повторного входа) при исходе «только превью»

- Нет сохранённой сессии для хоста → предложить вход во встроенном браузере (как реактивный путь S0116/S0144).
- Сессия есть → конвейер уже попробовал применить её и не получил реального медиа → предложить войти заново / обновить вход; текст диалога объясняет, что сохранённая сессия не дала контент (возможно, устарела), а не показывает безличный повтор. Эвристика «свежести» (помечать ли сессию свежей) не вводится — сессия всегда «последняя сохранённая», новая попытка её перезаписывает.
- Пользователь вошёл → новая сессия перезаписывает предыдущую запись для хоста → повторить попытку извлечения реального медиа.
- Пользователь отказался → запомнить отказ по хосту (как S0144) и перейти к столпу D.
- Когда подключается S0155 (несколько аккаунтов на один хост), весь столп C адресуется конкретному аккаунту (выбранному перед скачиванием или установленному по дефолту) — переход с уровня «хост» на уровень `(хост, аккаунт)` без изменения остальной логики.

#### D. Честное сообщение вместо «успеха» с превью

- Превью-картинка как единственный результат в Загрузки не сохраняется автоматически.
- Пользователь получает сообщение «не удалось получить контент по этой ссылке» (с подсказкой про вход, если он отказался от него).
- Опционально (открытый вопрос §6) — оставить пользователю явную возможность всё же сохранить превью-картинку, если он этого хочет.

#### E. Справочник известных ресурсов: добавить `threads.com`

- Threads распознаётся и по `threads.com`, и по `threads.net` — во всех трёх местах использования справочника (проактивное предложение при шаринге, выбор ресурса при ручном добавлении авторизации, выбор стартового адреса входа).
- Канонический адрес входа Threads берётся актуальный для текущего домена площадки.

### 5.2 Потоки данных и событий

- Шаринг ссылки → распознан хост Instagram/Threads → конвейер извлечения с применением сохранённой сессии и динамического разбора → (получено реальное медиа) скачать его обычным путём / (получена только превью-картинка) исход «контента нет» → предложить вход или повторный вход → (вошёл) повторить извлечение / (отказался) запомнить отказ, показать «контент по ссылке недоступен»; превью-картинка в Загрузки сама не уходит.
- Шаринг ссылки с `threads.com` без сохранённой сессии → распознан как Threads → проактивное предложение авторизации (как для прочих известных ресурсов).
- Ручное добавление авторизации → в списке известных ресурсов Threads открывает актуальный адрес входа независимо от того, `.com` или `.net`.

### 5.3 Точки расширяемости

- «Список соцсетей, для которых превью-картинка не считается контентом» — параметр, расширяемый добавлением хоста; та же запись в справочнике, что используется для предложения входа.
- Путь «применить сессию + динамический разбор» должен оставаться общим для добавляемых площадок, а не быть специфичным только для Instagram.
- Диагностические исходы («реальное медиа» / «только превью» / «нужен вход» / «вход есть, медиа всё равно нет» / «отказ пользователя») — структурированные значения для лога и возможной диагностики.

## 6. Открытые вопросы / Research items

1. **Достаётся ли видео reel'а и карусель Instagram через встроенный браузер с применённой сессией без отдельного API-клиента**
   - **Вопрос:** хватает ли динамического разбора отрендеренной страницы (как делает существующая стратегия со встроенным браузером) с инжектированными cookie, чтобы получить прямую ссылку на видео reel'а и на изображения карусели — или нужен разбор внутренних JSON-структур страницы / отдельный путь.
   - **Варианты:** (а) динамический разбор страницы достаточен; (б) нужен разбор встроенного в страницу структурированного JSON (тип контента, медиа-узлы); (в) нужен отдельный путь обращения к внутренним эндпоинтам площадки (рискованно, хрупко).
   - **Resolution (2026-05-11):** архитектурный выбор (а/б/в) откладывается до полевого наблюдения. Конкретное требование, которое идёт в реализацию прямо сейчас: добавить диагностическое сообщение в лог на исходе извлечения для Instagram/Threads — какой именно набор кандидатов вернула стратегия (число и тип: real-video / carousel-image / og-preview / прочее), с какой стратегии (`html` / `dynamic` / `streaming` / `direct`), с применённой ли сессией. По этому логу на устройстве с валидной сессией становится видно, какой вариант (а/б/в) актуален для каждого типа поста — и тогда выбирается путь в тактической спеке.
   - **Статус:** Open (архитектура) — после ввода диагностического лога перепроверяется на устройстве; см. также §5.3 «диагностические исходы».

2. **Что делать с превью-картинкой при окончательной неудаче**
   - **Вопрос:** совсем не сохранять, или предложить пользователю явную кнопку «всё равно сохранить превью».
   - **Варианты:** (а) не сохранять, только сообщение об ошибке; (б) сообщение об ошибке + опция сохранить превью; (в) для постов-карусели, где часть изображений всё же извлеклась, — сохранить что извлеклось и сообщить про неполноту.
   - **Resolution (2026-05-11):** вариант **(в)** — сохранить то, что удалось извлечь, и в сообщении пользователю явно сказать про неполноту («сохранено N из ожидавшихся M»); если ничего извлечь не удалось — превью-картинка отдельно не сохраняется, показывается сообщение «контент по этой ссылке недоступен».
   - **Статус:** Resolved.

3. **Граница «известная соцсеть, где превью ≠ контент»**
   - **Вопрос:** применять правило «только превью = не контент» только к Instagram/Threads или ко всему справочнику известных ресурсов.
   - **Варианты:** (а) только Instagram/Threads на этой итерации; (б) ко всему справочнику сразу.
   - **Resolution (2026-05-11):** вариант **(б)** — правило применяется ко всему справочнику известных ресурсов. Митигация риска «легитимные OG-картинки на других площадках» (§7): прямые ссылки на изображения обрабатываются раньше HTML-стратегии и под правило не попадают; справочник «известных» — закрытый список, расширяется явно.
   - **Статус:** Resolved.

4. **Что считать «недавно успешно применённой» сессией**
   - **Вопрос (исходный):** по какому признаку решать, что сессия для хоста свежая и повторное предложение «войти заново» не нужно (исход «только превью» → сразу честное сообщение).
   - **Варианты (исходные):** (а) вход выполнен в текущем процессе приложения; (б) последнее успешное применение cookie для хоста было < N часов назад; (в) с этой сессией уже было хотя бы одно успешное скачивание контента.
   - **Resolution (2026-05-11):** ни один из (а/б/в) — эвристика «свежести» **не вводится**. Логика проще: всегда применяется самая последняя сохранённая сессия для хоста; если конвейер с ней не получил реального медиа → предлагается войти заново с явным объяснением, что сохранённая сессия не сработала (возможно, устарела); новая сессия после успешного входа перезаписывает запись. Причина: вопрос «насколько свежая» — лишний state; ясный текст диалога снимает основной симптом «навязчивого повтора», а корневое решение проблемы «один аккаунт перепутали с другим» вынесено в S0155 (несколько аккаунтов на один хост + выбор аккаунта перед скачиванием + поаккаунтное сообщение). До S0155 текст диалога делается максимально объясняющим.
   - **Статус:** Resolved.

## 9. Архитектурные решения (ADR)

**ADR-1: «извлекли только превью с известной соцсети» — отдельный исход, а не успех**

- **Решение:** превью-картинка из Open Graph как единственный кандидат с перечисленных соцсетей не завершает поток успехом — это исход «реального контента нет», ведущий к попытке получить медиа с сессией и/или к предложению входа.
- **Альтернативы:** оставить как есть (сохранять превью, считать успехом); всегда показывать предложение входа для соцсетей независимо от результата.
- **Почему:** текущее поведение даёт пользователю бесполезный файл с видом успеха; «всегда предлагать вход» — навязчиво, когда контент и так получен; новый исход точечно покрывает именно проблемный случай.

**ADR-2: предложение входа при «только превью» — реактивное, поверх существующих механизмов S0116/S0144**

- **Решение:** использовать существующий встроенный браузер для входа, существующее хранилище сессий и существующее «запоминание отказа по хосту»; добавляется лишь новый триггер реактивного предложения (исход «только превью») и формулировка «войти заново», когда сессия уже была.
- **Альтернативы:** новый отдельный поток авторизации только для Instagram/Threads.
- **Почему:** меньше дублирования и регрессионного риска; согласуется с S0144.

**ADR-3: Threads распознаётся по обоим доменам**

- **Решение:** в справочнике известных ресурсов Threads сопоставляется и с `threads.com`, и с `threads.net`; канонический адрес входа — актуальный.
- **Альтернативы:** заменить `threads.net` на `threads.com` (сломает старые ссылки); оставить только `threads.net` (текущая проблема).
- **Почему:** в обиходе встречаются оба домена; распознавание обоих — минимально и безопасно.

## 11. Критерии готовности (strategic-level)

1. Шаринг ссылки на Instagram-reel приводит к скачиванию видео reel'а (на сборках с поддержкой видео), а не превью-картинки.
2. Шаринг ссылки на пост Instagram с каруселью приводит к скачиванию изображений карусели, а не одной превью-картинки.
3. Шаринг ссылки на пост Threads приводит к скачиванию медиа из поста; ссылка с домена `threads.com` распознаётся как Threads (проактивное предложение авторизации появляется так же, как для прочих известных соцсетей).
4. Когда реальное медиа извлечь не удалось, превью-картинка сама по себе в Загрузки не попадает; пользователю предлагается вход (или повторный вход, если сессия уже была); при отказе — понятное сообщение «контент по ссылке недоступен».
5. Поведение для прямых файлов, обычных HTML-страниц с явным медиа, стриминговых манифестов и пакетов элементов не изменилось.
6. В логе на такой шаринг видно, какой исход выбран («реальное медиа» / «только превью» / «нужен вход» / «вход есть, медиа всё равно нет» / «отказ пользователя»).
7. Когда предложение «войти заново» всё-таки появляется (сессия не дала контент), его текст явно объясняет ПРИЧИНУ — «сохранённая сессия для этого ресурса не дала контент, возможно, устарела» — пользователь не видит безличного повтора. Эвристика «свежести сессии» в коде не реализуется (§6.4 Resolved).
8. После отказа пользователя от (повторного) входа последующие шаринги ссылок с того же хоста не «молча игнорируются» — на каждый показывается понятное сообщение «контент по этой ссылке недоступен» (а не молчаливый выход без какой-либо реакции).
9. Для поста-карусели, где удалось извлечь часть изображений (но не все), сохранены извлечённые элементы и пользователю сообщено «сохранено N из M» с предложением войти заново для попытки достать оставшееся (§6.2 Resolved).
10. Правило «только превью = не контент» применено ко всему справочнику известных ресурсов (§6.3 Resolved); прямые ссылки на изображения, не попадающие в HTML-стратегию, продолжают сохраняться как раньше.
11. В логе на шаринг ссылки с Instagram/Threads видно диагностическое сообщение от стратегии извлечения: какая стратегия отработала, какой набор кандидатов получен (real-video / carousel-image / og-preview / прочее), была ли применена сессия (§6.1 — диагностическая часть Resolved; архитектурный выбор остаётся Open до полевого наблюдения).
