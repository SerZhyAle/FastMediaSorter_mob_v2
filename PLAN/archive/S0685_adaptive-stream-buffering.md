## 0. Захваченный материал (inbox)

**Захвачено:** 2026-06-25

**Текст:**

Изучить улучшение приёма трансляций. Часто не хватает длительности буфера и трансляция прерывается анимацией загрузки. Возможно можно сделать адаптивный битрейт (качество видео) когда сигнал «слабый» или адаптивный размер буфера. Желательно изменить общение с пользователем.. объяснять ему где идёт «восстановление соединения», а где «загрузка в буфер (память)», пока он ждёт.

**Вложений нет.**

---

## 1. Проблема

При проигрывании сетевых трансляций воспроизведение часто прерывается анимацией загрузки: буфера не хватает для сглаживания нестабильного сигнала, а на слабом канале нет понижения качества. Пользователь не различает причину паузы - идёт ли штатное наполнение буфера или происходит восстановление оборванного соединения, поэтому ожидание выглядит как «зависание». Область - проигрывание трансляций (Streams), слой плеера и его UI-индикация состояния.

---

## 2. Цели

1. Снизить частоту видимых прерываний трансляций за счёт более устойчивой буферизации на нестабильном канале.
2. Использовать понижение качества (битрейта) на слабом сигнале там, где источник это позволяет (мульти-вариантные HLS/DASH).
3. Разделить для пользователя состояния ожидания: «загрузка в буфер» и «восстановление соединения» - с понятной текстовой подписью.

**Non-goals:**

- Reconnect для RTSP и для progressive radio (ICY) при обрыве - вынесены в отдельные драфты (см. §10).
- Изменение каталога трансляций, импорта плейлистов, кэширования.
- Любые изменения для flavor без поддержки стримов (lite, photos).

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Адаптивный размер буфера в зависимости от стабильности сигнала.
2. Адаптивный битрейт на слабом сигнале.
3. Понятное объяснение пользователю текущей фазы ожидания.

### 3.2 Жёсткие ограничения

- **Flavor:** только варианты с `SUPPORT_STREAMS` (standard, legacy, noLegal, vr). HLS/DASH/RTSP-модули - те же варианты; lite/photos - progressive-only (вне объёма).
- **API level:** без API-специфики - используемые механизмы относятся к Media3 1.2.1, доступны от minSdk 23 (legacy).
- **Wear OS:** не затрагивается.
- **Производительность:** не раздувать буфер настолько, чтобы росла задержка live-edge и потребление памяти; адаптация не должна нагружать главный поток.
- **Совместимость данных:** миграции данных нет.
- **Локализация:** EN/RU/UK обязательно для любых новых строк состояния.
- **Доступность:** текст состояния должен быть не только цветовым отличием; учитывать TalkBack.

### 3.3 Owner inputs (Approval gate)

- **Related tickets:** S0634 (archived baseline for live-edge recovery / dead-URL classification; reuse its stream-player guardrails and avoid regressing them), plus future reconnect drafts for RTSP / progressive radio if those scopes are accepted from §6.

## 4. Контекст текущей архитектуры

Проигрывание трансляций строит изолированный экземпляр плеера со стрим-специфичным контролем загрузки (отдельным от VOD/cloud/SMB). Архивированный тикет S0634 уже зафиксировал базовую устойчивость: возврат к live-edge при отставании, ограниченные повторы при кратких сетевых сбоях, уменьшенный буфер с конфигурацией live-edge. Адаптивный выбор дорожки активен по умолчанию - для мульти-вариантных источников переключение битрейта работает «из коробки», но без тюнинга порогов и потолков.

Главный разрыв для §1: в UI есть единственный сигнал «идёт буферизация» (безымянный спиннер) - он одинаков и при штатном наполнении буфера, и в момент тихого восстановления соединения. Различить фазы пользователь не может.

Жёсткой межтикетной блокировки больше нет: S0634 уже вынес в архив базовый live-recovery слой. Дальнейшие решения по буферу, ABR и пользовательской индикации должны строиться поверх этой базы, а не переписывать её заново.

## 5. Предлагаемый подход

### 5.1 Основные столпы / модули

1. Тюнинг буфера/адаптации: пороги контроля загрузки и параметры выбора дорожки для трансляций (в источнике сборки со стримами).
2. Модель состояния ожидания: явное различение «буферизация» и «восстановление соединения» как доменного состояния, а не одного булева флага.
3. Индикация в UI плеера: текстовая подпись рядом со спиннером, отражающая фазу ожидания.

### 5.2 Потоки данных и событий

Слушатель стрим-плеера -> доменная фаза ожидания (буферизация | восстановление) -> колбэк в UI -> подпись + спиннер. Источник истины о фазе - тот же слой, что ведёт recovery (после S0634).

### 5.3 Точки расширяемости

- Отдельные профили буфера для radio (ICY) и live-video, если решение об их разделении будет принято (см. §6).
- Расширение модели фаз ожидания под будущие RTSP/radio reconnect-сценарии.

## 6. Открытые вопросы / Research items

> Источник: research-отчёт android-solution-researcher (2026-06-25). После закрытия зависимости S0634 оставшиеся гейты - в основном продуктовые решения владельца перед переходом Draft -> Approved.

1. Разграничение с S0634: какие части его буфер/recovery-базы считаем зафиксированными и неприкосновенными, а что допустимо тюнить в S0685 без регресса live-edge recovery?
2. Что именно значит «адаптивный размер буфера» - динамическая runtime-адаптация по оценке полосы (в Media3 1.2.1 встроенного механизма нет, нужен custom), или это уже закрыто буфером S0634?
3. ABR: тюнинг параметров (потолок битрейта, порог буфера до повышения качества) или только зафиксировать, что для мульти-вариантных источников он уже работает? Для single-variant `.m3u8` ABR бесполезен.
4. User messaging: новый текст «Буферизация..» vs «Восстановление соединения..» - цель этого тикета или отдельный? Требует правок layout плеера (портрет + ландшафт) и колбэка.
5. Scope reconnect: включать ли RTSP и progressive radio (ICY), или только live HLS/DASH? (S0634 вынес RTSP/radio reconnect в scope-gaps.)
6. Разделять ли контроль загрузки radio vs live-video (для radio низкий порог `bufferForPlayback` может давать микро-паузы)? Продуктовое решение, нужен тест на реальных устройствах.

### 6.1 Резолюции (2026-06-25, исследованием)

1. Граница с S0634: неприкосновенна вся recovery-машина - re-anchor к live-edge на `BehindLiveWindow`, классифицированный bounded-retry с backoff, `LiveConfiguration` (target/min/max offset, catch-up speed), dead-URL классификация. Тюнингу подлежат только длительности буфера в `DefaultLoadControl` - сам код S0634 это прямо разрешает. S0685 только читает recovery-состояние для подписи фазы и меняет буфер, не трогая логику восстановления.
2. «Адаптивный размер буфера»: в Media3 1.2.1 нет встроенной runtime-адаптации буфера по оценке полосы - это кастомный `LoadControl`, эффект которого проверяем только на реальном слабом сигнале, не на стабильном эмуляторе. В этой итерации - безопасный статический retune (глубже cushion) в пределах, не регрессирующих live-edge. Bandwidth-adaptive вариант вынесен в отдельный драфт.
3. ABR: дефолтный адаптивный выбор дорожки уже активен и без потолка для мульти-вариантных HLS/DASH (на стрим-плеере не задан `TrackSelectionParameters`-cap). Для single-variant `.m3u8` ABR бесполезен в принципе. Кода не требует - подтверждено.
4. User messaging: в объёме - это firm-запрос из §0. Разделение фаз «буферизация» / «восстановление соединения» с подписью у спиннера (портрет + ландшафт), i18n EN/RU/UK, TalkBack через текст.
5. Scope reconnect: только live HLS/DASH. Никакой новой reconnect-логики для RTSP/progressive radio (уже non-goal §2). Подпись фазы переиспользует уже существующий transient-retry путь.
6. Раздельный radio vs live-video load-control: вынесено в драфт - нужен реальный device-тест микропауз. Эта итерация оставляет единый стрим-`LoadControl` (с retune).

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Повторное вмешательство в буфер/recovery после S0634 | Высокая | Регресс live-edge recovery или возврат ложного dead-URL диалога | Определить в §6 неизменяемую базу S0634 и проверять все тюнинги против неё |
| Раздувание буфера ради устойчивости | Средняя | Рост задержки live-edge и памяти | Бюджеты буфера + проверка задержки на устройстве |
| Тюнинг ABR без мульти-вариантных источников | Средняя | Нулевой эффект на типовых single-variant `.m3u8` | Сначала подтвердить наличие мульти-вариантных источников |
| Изменение колбэка буферизации | Средняя | Нужно обновить все реализации интерфейса плеера | Расширять модель фаз аккуратно, мигрировать все impl |
| Нет unit-тестов на recovery-пути стрим-плеера | Средняя | Регрессы незаметны | Параллельный драфт на тесты (см. §10) |

## 11. Критерии готовности (strategic-level)

1. На нестабильном канале видимых прерываний трансляции заметно меньше, чем до изменения.
2. На слабом сигнале для мульти-вариантного источника качество понижается вместо остановки.
3. Во время ожидания пользователь видит, какая идёт фаза: наполнение буфера или восстановление соединения.
4. Нет регресса в recovery-поведении, реализованном S0634.

## 13. Объём итерации и тактика (resolved 2026-06-25)

### 13.1 Поставляется сейчас (проверяемо на эмуляторе)

1. Подпись фазы ожидания. Доменная фаза `StreamWaitPhase { BUFFERING, RECONNECTING }`; новый default-no-op колбэк `onStreamWaitPhase(phase?)` в `PlayerCallback`; стрим-листенер выставляет `RECONNECTING`, когда активен recovery-путь (re-anchor / transient retry), иначе `BUFFERING`; на `READY`/hard-fail - очистка. UI рисует подпись рядом со спиннером в портрете и ландшафте.
2. Безопасный retune буфера стрима. Глубже steady cushion и больше post-rebuffer fill; max остаётся скромным, чтобы live-backlog не пинил playhead (сохраняет live-edge tracking S0634).
3. Подтверждение ABR. Дефолтный адаптивный выбор дорожки активен и без cap - кода не требует.

### 13.2 Тактические фазы

1. Доменная модель + контракт: `StreamWaitPhase`, `onStreamWaitPhase` (default no-op - другие реализации не трогаются).
2. Стрим-листенер: плюс buffer-retune через именованные константы; выставление фазы из `onPlaybackStateChanged` и recovery-веток `onPlayerError`.
3. UI: рендер `streamWaitLabel` из `onStreamWaitPhase`, очистка на ready/buffering-off.
4. Ресурсы: `streamWaitLabel` в обоих layout (portrait FrameLayout-overlay + landscape ConstraintLayout) + dimens; строки `stream_wait_buffering` / `stream_wait_reconnecting` (EN/RU/UK).
5. Сборка `fk` -> `fc`; проверка на эмуляторе (стрим играет; подпись «буферизация»; форс-реконнект -> «восстановление»).

### 13.3 Вынесено в отдельные драфты (не проверяемо на эмуляторе)

1. **S0688** - bandwidth-adaptive runtime-буфер (кастомный `LoadControl` по `BandwidthMeter`); нужен реальный слабый сигнал.
2. **S0689** - раздельные профили буфера radio (ICY) vs live-video; нужен device-тест микропауз.

## 14. Верификация (2026-06-25, эмулятор emulator-5556, standard-debug)

- Стрим играет: мульти-вариантный HLS (Mux test) проигрывается чисто с новым буфером (min 20s / post-rebuffer 8s) - регресса recovery нет.
- Подпись «Восстановление соединения..» отрисована по центру под спиннером во время recovery (обрыв сети -> слив буфера -> classified-retry). Заснято в портрете трижды.
- Логи подтверждают recovery-машину: `playStreamVideo: prepared` -> `Stream transient error - retrying` (attempts 1-4, backoff 2/4/8/16s) -> `surfacing to user`. Именно на этих повторах выставляется `RECONNECTING`.
- На исчерпании бюджета повторов подпись очищается (`onStreamWaitPhase(null)`) и всплывает штатный диалог S0581 - подпись не залипает за диалогом.
- «Буферизация..» использует тот же render-путь (`onStreamWaitPhase` -> `setText` -> visible) с строкой проверенного паритета; её окно на быстрой сети короче pipeline скриншота, поэтому подтверждена по конструкции, а не отдельным кадром.
- Ландшафт: тот же `binding.streamWaitLabel` и render-код; layout-land XML (ConstraintLayout, подпись под `progressBar`) валидирован сборкой (non-null binding-поле требует id в обоих layout) и код-ревью.
- Не проверяемо на стабильном эмуляторе и вынесено: реальная выгода более глубокого буфера на слабом сигнале (S0688).
