---

## 1. Проблема

При генерации миниатюры видеофайла (особенно MKV, а также AVI, MP4) извлечение кадра происходит с фиксированным смещением от начала — нередко в зоне чёрной заставки или чёрного лидера. Результирующая миниатюра представляет собой «чёрный квадрат», что не даёт пользователю никакой информации о содержимом файла и ухудшает навигацию по медиатеке. Дефект воспроизводится как на сетевых источниках (SMB/SFTP/FTP), так и при фоновом пресиживании локальных копий.

---

## 2. Цели

1. Миниатюры видеофайлов перестают быть сплошь чёрными — пользователь видит содержательный кадр.
2. Детекция «тёмного кадра» работает прозрачно: при неудаче автоматически извлекается кадр с более поздней временной метки.
3. Если ни один кандидатный кадр не прошёл порог качества, отображается заглушка с иконкой расширения файла — аналогично текущему поведению при полном сбое извлечения.
4. Уже закешированные чёрные миниатюры могут быть инвалидированы и переизвлечены без ручного вмешательства пользователя.
5. Дополнительная задержка при загрузке миниатюр остаётся незаметной для пользователя в типичном случае (≤ 1 повторного извлечения).

**Non-goals:**

- Улучшение качества миниатюр для форматов из существующего блок-листа (AVI, VOB, M2TS и т.п.) — они уже подавлены политикой извлечения.
- Цветокоррекция или ресайз миниатюр.
- Извлечение «лучшего» кадра по содержимому (scene detection) — только детекция темноты.
- Изменение разрешения или формата хранения JPEG-миниатюр.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Попробовать кадры на отметках 5 с, 15 с, 30 с — в таком порядке — прежде чем сдаться.
2. Порог темноты настраивается константой (не UX-настройкой), чтобы можно было скорректировать без релиза UI.
3. Детекция применяется по возможности и к фоновому пресиванию, и к онлайн-декодированию через Glide.
4. Если запрошено исследование через интернет — выяснить, какой порог среднего люминанса считается индустриально принятым для «чёрного кадра»; зафиксировать в ADR.

### 3.2 Жёсткие ограничения

- **Flavor:** все четыре (standard, lite, photos, legacy) — логика детекции flavor-нейтральна; флаг `showVideoThumbnails` уже управляет включением извлечения.
- **API level:** minSdk 23 (legacy); `getScaledFrameAtTime` доступен с API 27 — в legacy-ветке необходим fallback.
- **Wear OS:** не затрагивается.
- **Производительность:** каждый дополнительный вызов `getFrameAtTime` потребляет ресурс сетевого watchdog-таймера (10 с); допустимо не более 3 повторных попыток в сетевом декодере. В фоновом пресивателе ограничение мягче.
- **Совместимость данных:** при добавлении качественного поля в схему кеша миниатюр необходима миграция Room; решение (добавлять поле или обходиться без него) определяется по итогам research.
- **Локализация:** EN/RU/UK — миниатюра и заглушка — UI-строки не добавляются; пользовательски видимый текст не меняется.
- **Доступность:** не затрагивается (чисто медиа-слой).

## 4. Контекст текущей архитектуры

Извлечение кадров происходит в двух независимых путях. Первый — онлайн-путь: пользовательский Glide-декодер для сетевых источников вызывает `MediaMetadataRetriever.getFrameAtTime` с фиксированным смещением 1 с; получив ненулевой `Bitmap`, немедленно сохраняет его в кеш и возвращает. Второй — фоновый путь: воркер пресивания скачивает файл во временный локальный кеш и вызывает экстрактор с нулевым смещением (0 мкс), что особенно уязвимо к чёрному лидеру.

Оба пути на данный момент не содержат никакой проверки качества возвращённого `Bitmap`: если кадр ненулевой — он считается валидным и сохраняется в Room-кеш навсегда. Инвалидировать закешированный чёрный кадр через UI невозможно без очистки всего кеша миниатюр.

---

## 5. Предлагаемый подход

Ввести роль **оценщика качества кадра** — отдельный компонент прикладного слоя, ответственный за определение, является ли `Bitmap` «достаточно тёмным». Оценщик принимает на вход уменьшенный `Bitmap` (8×8 или 16×16 центральной области), вычисляет средний люминанс и сравнивает с порогом.

Оба пути извлечения обращаются к оценщику после каждого `getFrameAtTime`: если кадр отклонён — запрашивается следующая временная метка из заранее заданного списка (5 с, 15 с, 30 с). Если все попытки исчерпаны — возвращается наилучший найденный кадр (с минимальной темнотой) или `null`, что маппится в заглушку с расширением.

### 5.1 Основные столпы

**Оценщик темноты кадра**

- Принимает `Bitmap`, возвращает `Float` (средний люминанс 0..1) или булево «тёмный/не тёмный».
- Порог и список кандидатных смещений — константы в объекте политики.
- Не зависит от платформенного API выше minSdk 23.

**Адаптер онлайн-декодера**

- После получения `Bitmap` от `MediaMetadataRetriever` передаёт его оценщику.
- При «тёмном» результате повторяет извлечение с увеличенным смещением (максимум 3 попытки, чтобы не превысить watchdog).
- Хранит лучший результат по ходу итерации; возвращает его, даже если он не прошёл порог.

**Адаптер фонового экстрактора**

- Аналогичная логика, без ограничения по watchdog — допустимо до 4–5 попыток.
- Начальное смещение сдвигается с 0 на 5 с, чтобы сразу уйти из зоны чёрного лидера.

**Политика инвалидации кеша**

- При промахе кеша (кадр ненулевой, но тёмный) — кандидат не сохраняется; поиск продолжается.
- При хите кеша (сохранённый JPEG тёмный) — опционально: помечается как требующий переизвлечения, либо просто удаляется при следующем обращении.
- Решение о хранении поля качества в схеме Room определяется по итогам research (§6, вопрос 5).

### 5.2 Потоки данных и событий

```
Запрос миниатюры → слой извлечения → Bitmap?
    ↓ тёмный?
    Да → следующее смещение → повтор (max N раз)
    Нет → сохранить в кеш → вернуть
    Все попытки → лучший Bitmap или null → заглушка
```

### 5.3 Точки расширяемости

- Список кандидатных смещений и порог темноты должны быть конфигурируемы без изменения кода (объект политики, не хардкод внутри логики извлечения).
- Оценщик темноты должен быть заменяем (например, для будущего scene-detection).
- Инвалидация кеша должна поддерживать как мягкое (пометить), так и жёсткое (удалить) удаление записи.

## 6. Открытые вопросы / Research items

1. **Индустриальный порог среднего люминанса для «чёрного кадра»**
   - **Вопрос:** Какое значение среднего люминанса принято считать «чёрным» в медиаплеерах?
   - **Результат исследования:**
     - FFmpeg `blackframe` (vf_blackframe.c): по умолчанию luma < 32/255 (≈12.5%) для ≥ 98% пикселей.
     - FFmpeg `blackdetect` (vf_blackdetect.c): по умолчанию `pixel_black_th = 0.10` — luma < 26/255 full-range; ≥ 98% пикселей.
     - VLC Android (`ThumbnailsProvider.kt`): не использует порог люминанса — проверяет pixel-equality с пустым bitmap; при совпадении ищет кадр на 40% длительности.
     - Jellyfin: делегирует выбор кадра FFmpeg (`thumbnail=n=24`), собственного порога нет.
     - AOSP `ThumbnailUtils`: использует timestamp `−1` (выбор за реализацией), без luminance guard.
   - **Вывод:** принятый индустриальный диапазон — средний люминанс < 10..15/255. Для детекции чистого чёрного лидера выбран порог **mean luma < 15/255 (≈ 5.9%)** — строже FFmpeg default (32/255), чтобы не отбрасывать легитимно тёмные сцены.
   - **Статус:** Resolved → зафиксировано в ADR-1.

2. **Эффективный алгоритм вычисления люминанса на Android**
   - **Вопрос:** Какой подход вычисления люминанса оптимален при ограничении в 10 с watchdog?
   - **Результат исследования:**
     - Downscale до 64×64 + `getPixels` → полный скан 4096 пикселей → ~2–4 мс на mid-range CPU, приемлемо.
     - Центральная выборка 5×5 (25 пикселей) → ~0.05 мс, но пропускает периферийный чёрный border.
     - `Color.luminance()` доступен с API 26 — требует guard для legacy (minSdk 23); fallback — формула `(0.299R + 0.587G + 0.114B) / 255`.
     - `getScaledFrameAtTime` (API 27) позволяет запрашивать уменьшенный Bitmap сразу — снижает память до люминанс-скана.
   - **Вывод:** downscale `Bitmap` → 64×64 + полный `getPixels` + ручная luma-формула (совместима с API 23). На сетевом пути — только если `Bitmap` уже получен (не добавляет сетевых вызовов).
   - **Статус:** Resolved.

3. **Поведение `MediaMetadataRetriever` на MKV с чёрным лидером**
   - **Вопрос:** Какой `OPTION_*` минимизирует попадание на чёрный sync-frame?
   - **Результат исследования:**
     - `OPTION_CLOSEST_SYNC` при t=0 возвращает первый keyframe — это и есть источник проблемы.
     - `OPTION_NEXT_SYNC` при t=0 возвращает тот же первый keyframe (он уже ≥ 0).
     - Смещение `OPTION_CLOSEST_SYNC` не решает проблему изменением режима — решение только в сдвиге стартовой временной метки.
   - **Вывод:** менять `OPTION_*` смысла нет. Эффективная митигация — начинать с t=5 с; при тёмном результате пробовать 15 с, 30 с.
   - **Статус:** Resolved.

4. **Стоимость дополнительных `getFrameAtTime` на сетевом источнике**
   - **Вопрос:** Сколько retry-попыток допустимо в 10-секундный watchdog сетевого декодера?
   - **Результат исследования:** Каждый `getFrameAtTime` через `NetworkMediaDataSource` буферизует фрагмент видеопотока — на SMB 1 Гбит/с занимает 0.5–2 с; на Wi-Fi 150 Мбит/с — 2–5 с. При 3 попытках суммарно 6–15 с — watchdog будет превышен на медленных сетях.
   - **Вывод:** на сетевом пути — максимум **2 retry** (итого 3 попытки включая первую); на фоновом пути (файл скачан) — до 4 попыток.
   - **Статус:** Resolved → лимиты зафиксированы в §5.1.

5. **Room-схема: добавлять поле качества или нет**
   - **Вопрос:** Нужен ли `isBlackFrame` / `luminanceMean` в `ThumbnailCacheEntity`?
   - **Результат исследования:** Паттерн «не кешировать чёрный кадр вовсе» (вариант C) используется в Jellyfin и VLC — при неудаче просто не сохраняется ничего, следующий запрос повторяет извлечение. Это проще миграции схемы и устраняет проблему с уже существующим чёрным кешем.
   - **Вывод:** **вариант C** — при провале качества не сохранять в кеш. Никакой миграции Room не требуется. Уже сохранённые чёрные JPEG будут вытеснены LRU-механизмом при следующем запросе (cache miss → повторное извлечение с новой логикой).
   - **Статус:** Resolved → Room-схема не меняется.

6. **Инвалидация уже существующих чёрных кешей**
   - **Вопрос:** Как обработать уже накопленные чёрные JPEG после обновления?
   - **Результат исследования (вытекает из вопроса 5):** При варианте C существующие чёрные JPEG остаются в кеше до истечения LRU TTL (или ручной очистки пользователем через Settings). При следующем реальном запросе миниатюры — cache miss (файл всё ещё там, но логика не переизвлекает автоматически) — потребуется либо ручная очистка, либо ленивая проверка при хите кеша.
   - **Уточнение подхода:** при хите кеша — декодировать JPEG и прогнать через оценщик; если тёмный — удалить запись и переизвлечь. Это однократная операция на файл, ~2–4 мс, приемлемо.
   - **Статус:** Resolved → ленивая инвалидация при хите кеша (decode → luma check → evict if dark).

## 9. Архитектурные решения (ADR)

**ADR-1: Порог среднего люминанса — mean luma < 15/255**

- **Решение:** кадр считается «чёрным», если средний люминанс (по всем пикселям downscaled 64×64) < 15/255 (≈ 5.9%).
- **Альтернативы:** 10/255 (слишком строго — пропускает тёмные лидеры с едва заметным градиентом), 32/255 (FFmpeg default — слишком мягко, высокий false-positive на ночных сценах).
- **Почему:** FFmpeg `blackdetect` использует ~10% luma range (≈26/255); VLC не использует порог вовсе. Значение 15/255 — компромисс: отсекает чистые чёрные лидеры и фейды в чёрное без ложных срабатываний на тёмные ночные сцены. Значение — константа в объекте политики, меняется без перестройки логики.

**ADR-2: Оценщик темноты вынесен в отдельный компонент**

- **Решение:** Не встраивать вычисление люминанса прямо в декодер или экстрактор.
- **Альтернативы:** inline-проверка внутри существующего кода извлечения.
- **Почему:** оба пути (онлайн + фоновый) должны использовать один алгоритм; тестируемость; закон одиночной ответственности; оба существующих класса близки к лимиту по LOC.

**ADR-3: Начальное смещение — 5 с для всех путей**

- **Решение:** оба пути (онлайн и фоновый) начинают с t=5 с (ранее: онлайн — 1 с, фоновый — 0 мкс).
- **Альтернативы:** оставить текущие смещения и детектировать темноту; использовать 40% от длительности (подход VLC).
- **Почему:** 5 с надёжно перепрыгивает типичные чёрные лидеры (0–3 с), не требует знания длительности для первой попытки. Подход VLC (40%) требует парсинга метаданных до начала извлечения — дорого на сети. Для видео <5 с — fallback на 0 с проверкой `METADATA_KEY_DURATION`.

**ADR-4: Room-схема не меняется — вариант «не кешировать чёрный кадр»**

- **Решение:** чёрные кадры не записываются в `ThumbnailCacheEntity`; при хите кеша с тёмным JPEG — запись удаляется, инициируется переизвлечение.
- **Альтернативы:** добавить поле `isBlackFrame` в схему (миграция Room); всегда перепроверять люминанс при хите кеша без удаления.
- **Почему:** вариант «не кешировать» — стандартный паттерн в VLC и Jellyfin; устраняет необходимость миграции. Ленивая инвалидация при хите кеша (~2–4 мс на операцию) решает проблему с уже закешированными чёрными JPEG без фонового сканирования.

## 11. Критерии готовности (strategic-level)

1. Открыть 10 MKV/MP4-файлов с известным чёрным лидером — ни одна миниатюра не отображается чёрной.
2. Открыть 5 видео длиной <5 с — миниатюры корректно извлекаются.
3. Открыть 5 ночных видео с легитимно тёмными кадрами — отображается содержательный кадр (не чёрная заглушка без причины).
4. Скорость отображения миниатюр в сетевом браузере субъективно не изменилась по сравнению с текущей (не более одного видимого «затупа»).
5. Уже закешированные чёрные миниатюры не воспроизводятся после обновления (инвалидация по одному из сценариев из §6, вопрос 6).
6. В Settings → кеш миниатюр → очистить — функция работает как прежде.
