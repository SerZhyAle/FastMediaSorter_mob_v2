## 1. Проблема

FMS реализует только path A - headless-грабер снимает превью тайлов сетки каналов фоновым короткоживущим плеером. Path B (player-ingest) отсутствует полностью: когда пользователь открывает канал в полноэкранном плеере и видит реальную картинку, этот кадр никуда не сохраняется, хотя это самый дешёвый и надёжный источник превью. В итоге каналы, которые headless-грабер получить не может (заблокированные, медленные, только-по-запросу), навсегда остаются на favicon/букве даже после того, как пользователь их посмотрел.

## 2. Цели

1. Первый стабильный отрисованный кадр открытого пользователем стрима усыновляется как превью канала: применяется к тайлу сетки и пишется на диск.
2. Path B работает независимо от режима авто-захвата (открытие канала - осознанное действие), покрывая каналы, недоступные headless-граберу.
3. Полноэкранный плеер и сетка каналов связаны единым слой-нейтральным контрактом «первый кадр → стор превью», без дублирования логики захвата.

**Non-goals:**

- Введение пользовательской настройки «обновлять превью автоматически» - отдельная будущая работа (в FMS её сейчас нет; path B всегда ingest'ит при открытии).
- Изменение headless-грабера path A - его декодер трогает S1125; сам захват здесь не меняется.
- Политика вытеснения диска по размеру - объём S1130 (иначе новые превью вытесняют старые по file-count).
- Radio/audio - нет видеокадра.

## 4. Контекст текущей архитектуры

Превью сетки каналов сейчас пишет только headless-грабер streams-слоя в свой кэш + дисковый стор. Полноэкранное воспроизведение живёт в player-слое (отдельная Activity), запускается со streams-экрана через intent без контракта возврата кадра; player-слой не ссылается на стор превью, а его единственный `onRenderedFirstFrame`-захват постера явно исключает сетевые/облачные источники и обходится стрим-путём. Поэтому кадр, который пользователь уже увидел на живом стриме, физически некуда сохранить - между player-слоем и стором превью streams-слоя нет ни контракта, ни зависимости. Решить проблему из §1 «на месте» нельзя без слой-нейтрального seam-контракта ingest.

## 5. Предлагаемый подход

### 5.1 Основные столпы / модули

- **Контракт ingest.** Слой-нейтральный интерфейс «усынови кадр канала по URL», реализуемый streams-слоем поверх существующих кэша + дискового стора и инъектируемый в player-слой (singleton, без нового Hilt-scope).
- **Захват кадра стрим-плеером.** Стрим-путь плеера на первом стабильном кадре снимает bitmap с поверхности воспроизведения и передаёт его в контракт ingest.

### 5.2 Потоки данных и событий

- Открытие канала → плеер выходит на живой край → первый стабильный кадр → захват bitmap с surface → ingest(url, bitmap) → кэш (мгновенная перерисовка тайла при возврате в сетку) + диск (следующий запуск).
- Независимо от режима авто-захвата: ingest при открытии всегда разрешён (path A может быть выключен будущей настройкой; path B - нет).

### 5.3 Точки расширяемости

- Будущая настройка «авто-обновление превью» гейтит только path A; path B остаётся всегда-вкл - точка расширения.
- Тот же контракт ingest переиспользуем для иных источников кадра (снапшот по запросу, hover-refresh).

## 11. Критерии готовности (strategic-level)

1. Открытие ранее-«пустого» канала (favicon) в плеере и возврат в сетку показывает реальный кадр как превью тайла.
2. Превью сохраняется на диск и восстанавливается на следующем запуске (не пере-снимается только ради показа).
3. Path B срабатывает независимо от режима авто-захвата.
4. Пустой/чёрный кадр не усыновляется - тайл сохраняет прежнее состояние.
5. Регрессия отсутствует: обычное воспроизведение, path-A захват, файловые постеры не сломаны.
