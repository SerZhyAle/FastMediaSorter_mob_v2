## 1. Проблема

Companion-ресурс (Windows-компаньон раздаёт папку по SFTP, конфиг импортируется на телефон через `.fmscfg`/QR) достижим по разным адресам в зависимости от того, где сейчас телефон: по локальному адресу, когда он в домашней сети рядом с ПК, и по внешнему адресу с проброшенным портом, когда он в дороге на мобильном интернете. Конфиг несёт оба адреса, но приложение сохраняет и использует только один из них, поэтому один импортированный ресурс работает либо только дома, либо только в дороге - но не в обоих местах. Пользователь вынужден держать два ресурса или пересканировать QR при каждой смене сети. На практике это уже приводит к тому, что ресурс молча не подключается (таймаут сокета) после смены сети.

---

## 2. Цели

1. Один импортированный companion-ресурс подключается и дома (локальная сеть), и в дороге (внешний адрес с проброшенным портом) без пересоздания и пересканирования.
2. При подключении приложение само выбирает достижимый на текущий момент адрес из числа тех, что несёт конфиг, отдавая предпочтение локальному (он быстрее и не зависит от проброса).
3. Проверка подключения при добавлении/обновлении ресурса проходит, если жив хотя бы один из адресов, а не только первый.
4. Старые конфиги с единственным адресом и уже созданные ресурсы продолжают работать без изменений в поведении.

**Non-goals:**

- Не чинить реально неработающий проброс порта или CGNAT на стороне ПК - приложение выбирает живой путь, но не воскрешает мёртвый.
- Не менять формат `.fmscfg` и его версию схемы - список адресов уже предусмотрен контрактом.
- Не вводить P2P-доступ «по ID» (уровень B из S0421) - вне объёма.
- Не распространять мульти-адресность на ручные (не-companion) SFTP-ресурсы в этой итерации, кроме как естественным следствием общей модели.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Работает «с любым вариантом»: под роутером или с публичным IP на стороне ПК, за роутером или на мобильном интернете на стороне телефона - при условии рабочего проброса/UPnP.
2. Смена сети на телефоне (Wi-Fi ⇄ мобильный) подхватывается прозрачно, без действий пользователя.
3. Предпочтение локального адреса, когда он доступен, ради скорости и независимости от проброса.

### 3.2 Жёсткие ограничения

- **Flavor:** затрагивает все варианты сборки, где доступен SFTP-стек (companion-импорт живёт в основных вариантах); специфичного флейвор-разделения не вводит - изменение в общем `src/main` сетевом слое.
- **API level:** без API-специфики; работает как обычный сетевой трафик, совместимо с минимальным поддерживаемым уровнем.
- **Wear OS:** не затрагивается.
- **Производительность:** выбор адреса добавляет одну быструю проверку достижимости на холодное подключение в рамках сети; не должна платиться на тёплых/пуленных соединениях и не должна заметно замедлять открытие ресурса.
- **Совместимость данных:** дополнительное хранение списка адресов вводится как аддитивное, без потери существующих данных; ресурсы без списка ведут себя как раньше.
- **Локализация:** EN/RU/UK - обязательно для любых новых пользовательских строк.
- **Доступность:** новых визуальных элементов не предполагается; при появлении сообщений об ошибке - не-цветовое различие и совместимость с TalkBack.

### 3.3 Owner inputs (Approval gate)

- **Data compatibility:** список адресов хранится аддитивно (новое необязательное поле рядом с существующим путём ресурса), с forward-only миграцией; существующие ресурсы получают пустой список и ведут себя как одно-адресные (выбор из множества в один элемент = текущее поведение). Потери данных и обратной миграции не требуется.
- **Performance budget:** выбор адреса - одна happy-eyeballs проверка достижимости на холодное подключение в рамках одной сети, кандидаты проверяются параллельно с предпочтением локального, худший случай ограничен коротким таймаутом на кандидата; результат кэшируется по паре (ресурс + текущая сеть) с коротким временем жизни, поэтому в установившемся режиме файловые операции доп-задержку не платят. Тёплые/пуленные соединения проверку не проходят повторно.
- **Validation level:** модульные тесты на выбор адреса (гонка кандидатов, кэш, инвалидация при смене сети), на импорт мульти-адресного конфига и на миграцию хранилища; on-device проверка, что один импортированный companion-ресурс открывается и по локальной сети, и по мобильному интернету.
- **Owner sign-off:** 2026-07-12 - владелец выбрал этот подход в ходе сессии.
- **Related tickets:** S0421 (companion-доставка - источник массива адресов в `.fmscfg`), S0988 (импорт по QR, создающий такие ресурсы), S0046 (пиннинг host-key переиспользуется для каждого кандидата).

## 4. Контекст текущей архитектуры

За сетевой доступ отвечает слой источников данных: путь ресурса разбирается на адрес и удалённый путь, соединение устанавливается и переиспользуется через пул, ключёванный по адресу; тот же адрес используется при сканировании каталога, файловых операциях, потоковом воспроизведении и генерации миниатюр. Ресурс хранит ровно один путь, а импорт companion-конфига сохраняет только первый из предложенных адресов, отбрасывая остальные. Проверка подключения при добавлении бьётся ровно об один адрес.

Из-за этого решить проблему из §1 сейчас нельзя: даже когда конфиг честно несёт и локальный, и внешний адрес, ниже уровня импорта эта информация уже потеряна - в модели ресурса остаётся один адрес, и весь путь подключения жёстко привязан к нему. Смена сети телефоном не меняет сохранённый адрес, поэтому «домашний» ресурс молча не достаётся снаружи и наоборот.

## 5. Предлагаемый подход

Ключевая идея: ресурс перестаёт быть привязан к единственному адресу и хранит упорядоченный набор адресов-кандидатов; какой из них использовать - решается при установке соединения по фактической достижимости, а не фиксируется при импорте. Всё, что ниже точки выбора адреса (пул, потоковый транспорт, миниатюры, файловые операции), продолжает работать поверх уже выбранного адреса без изменений в своей логике.

### 5.1 Основные столпы / модули

- **Хранение набора адресов.** Модель и хранилище ресурса расширяются аддитивным необязательным списком дополнительных адресов рядом с основным путём. Основной путь остаётся предпочтительным и служит для отображения и обратной совместимости; дополнительные адреса - резерв. Расширение вводится так, чтобы ресурсы без списка были неотличимы от прежних.

- **Импорт всех адресов.** Импорт companion-конфига сохраняет весь упорядоченный набор адресов из конфига (контрактный порядок - локальный первым), а не только первый. Порядок из контракта сохраняется как приоритет выбора.

- **Выбор достижимого адреса.** Новая ответственность - «резолвер конечной точки»: по набору кандидатов ресурса определяет, какой адрес достижим в текущей сети, отдавая предпочтение локальному, и возвращает его пути подключения. Выбор кэшируется на связку «ресурс + текущая сеть» с коротким временем жизни и сбрасывается при смене сети телефоном, чтобы после переключения Wi-Fi ⇄ мобильный заново выбрать рабочий путь.

- **Единая точка врезки.** Выбор адреса встраивается в единственную логическую точку, где путь ресурса превращается в адрес подключения, - так, чтобы им пользовались все потребители SFTP (сканирование, файловые операции, потоковый транспорт, миниатюры и проверка подключения), а не только один из них.

- **Проверка подключения по набору.** Проверка при добавлении/обновлении ресурса считается успешной, если достижим хотя бы один кандидат; в диагностике полезно отражать, какой именно адрес сработал.

### 5.2 Потоки данных и событий

- Импорт: конфиг → набор адресов сохраняется в модель ресурса (первый как основной, прочие как резерв).
- Подключение: потребитель запрашивает соединение по ресурсу → резолвер выбирает достижимый адрес (кэш или новая проверка кандидатов с предпочтением локального) → существующий пул/транспорт работает поверх выбранного адреса.
- Смена сети: сигнал о смене сети инвалидирует кэш выбора → следующее подключение выбирает адрес заново.

### 5.3 Точки расширяемости

- Набор адресов-кандидатов - общий механизм: в будущем может наполняться не только из companion-импорта, но и, например, из ручного добавления второго адреса к SFTP-ресурсу.
- Стратегия выбора (предпочтение локального, happy-eyeballs) изолирована за ролью резолвера и может уточняться (предпочтение IPv6, иные эвристики) без изменения потребителей.
- Кэш выбора ключёван по сети, что оставляет возможность более тонкой инвалидации (например, по конкретному сетевому переходу) без смены контракта.

## 6. Открытые вопросы / Research items

1. **Единственность точки врезки выбора адреса**
   - **Вопрос:** действительно ли существует одна логическая точка, где путь ресурса превращается в адрес подключения, или потребителей несколько (сканирование, файловые операции, потоковый транспорт, миниатюры, проверка подключения) и врезку нужно поставить в каждой?
   - **Ответ:** точек несколько (~11 вызовов разбора пути); единой точки нет, учётки ищутся по host:port. Врезка - через общий резолвер в каждой точке установки соединения; при импорте учётка сохраняется на каждый кандидат.
   - **Статус:** Resolved
   - **Артефакт:** `PLAN/S1006_sftp-multipath-endpoint-fallback/research/01__sftp-address-consumers.md`

2. **Стоимость и таймаут happy-eyeballs**
   - **Вопрос:** какой таймаут на кандидата и какая схема параллельности дают быстрый выбор без ложных отказов на медленных сетях, и не добавляют ли они заметной задержки к открытию ресурса.
   - **Ответ:** дешёвая raw-TCP проверка (`Socket.connect`), короткий таймаут ~2.5-3 с на кандидата, параллельно, с предпочтением локального; кэш по (ресурс + сетевая эпоха), тёплые/пуленные соединения проверку не проходят.
   - **Статус:** Resolved
   - **Артефакт:** `PLAN/S1006_sftp-multipath-endpoint-fallback/research/02__happy-eyeballs-probe-tuning.md`

3. **Источник сигнала о смене сети для инвалидации кэша**
   - **Вопрос:** какой уже существующий в приложении механизм наблюдения за сетью использовать для сброса кэша выбора адреса.
   - **Ответ:** `NetworkStateMonitor` (`registerCallback`/`onNetworkChanged`) - тот же источник, что у SMB; сброс всего кэша выбора по событию смены/потери сети.
   - **Статус:** Resolved
   - **Артефакт:** `PLAN/S1006_sftp-multipath-endpoint-fallback/research/03__network-change-signal.md`

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Врезка выбора адреса не покрывает все точки подключения | Средняя | Часть операций (например, воспроизведение) продолжает бить в один адрес | Ревизия всех потребителей адреса; единый хелпер вместо точечных правок |
| Проверка достижимости добавляет задержку к открытию ресурса | Средняя | Заметный лаг при холодном подключении | Дешёвая TCP-проверка вместо полного хэндшейка; параллельность; кэш по сети |
| Кэш выбора не сбрасывается при смене сети | Средняя | Ресурс продолжает бить в недостижимый адрес после переключения Wi-Fi ⇄ мобильный | Инвалидация по сигналу смены сети; короткое время жизни кэша |
| Миграция хранилища ломает существующие ресурсы | Низкая | Потеря/повреждение списка ресурсов | Аддитивное необязательное поле, forward-only миграция, тест миграции |
| Пиннинг host-key не применяется к резервному адресу | Низкая | Резервное подключение отклоняется или теряет защиту | Один и тот же ожидаемый отпечаток применяется к любому выбранному кандидату |

## 9. Архитектурные решения (ADR)

**ADR-1: Выбор адреса при подключении, а не при импорте**

- **Решение:** ресурс хранит набор адресов, достижимый выбирается в момент установки соединения.
- **Альтернативы:** (а) зондировать адреса при импорте и сохранять один «победивший»; (б) хранить один адрес и переключать вручную.
- **Почему:** достижимость зависит от текущей сети телефона и меняется во времени; фиксация при импорте ломается при первой же смене сети, ручное переключение перекладывает проблему на пользователя.

**ADR-2: Happy-eyeballs с предпочтением локального адреса**

- **Решение:** кандидаты проверяются параллельно, при готовности предпочитается локальный.
- **Альтернативы:** строго последовательный перебор (локальный, затем внешний) с ожиданием таймаута на каждом.
- **Почему:** последовательный перебор платит полный таймаут на недостижимом первом адресе; параллельная гонка выбирает рабочий путь быстро, а предпочтение локального сохраняет приоритет из контракта.

**ADR-3: Не менять контракт `.fmscfg`**

- **Решение:** формат и версия схемы конфига не трогаются; приложение начинает честно использовать уже предусмотренный контрактом список адресов.
- **Альтернативы:** ввести новую версию схемы с явной разметкой путей.
- **Почему:** список адресов уже есть в контракте; изменение - в клиенте, а не в формате; обратная совместимость со старыми одно-адресными конфигами сохраняется бесплатно.

## 11. Критерии готовности (strategic-level)

1. Один импортированный companion-ресурс открывается по локальной сети, когда телефон дома, и по внешнему адресу, когда телефон на мобильном интернете, - без пересоздания и пересканирования.
2. После переключения телефона между Wi-Fi и мобильным интернетом тот же ресурс подключается по адресу, достижимому в новой сети, без действий пользователя.
3. Проверка подключения при добавлении/обновлении companion-ресурса проходит, если достижим хотя бы один из адресов.
4. Ранее созданные ресурсы и конфиги с единственным адресом продолжают работать без изменений в поведении и без потери данных.
5. Пиннинг host-key остаётся в силе для любого выбранного адреса.
6. При недостижимости всех адресов приложение честно сообщает об ошибке подключения, а не зависает дольше ожидаемого таймаута.
