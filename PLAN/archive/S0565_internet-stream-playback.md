## 1. Проблема

В текущей версии FastMediaSorter v2 отсутствует не только воспроизведение потокового аудио- и видеоконтента из интернета, но и отдельная пользовательская поверхность для управления трансляциями.. Пользователь не может открыть специальный список трансляций, загрузить открытый каталог каналов из интернета, добавить вручную собственный поток, закрепить нужный источник вверху списка или запустить такой источник из отдельного экрана.. Дополнительно отсутствует оформленный сценарий для RTSP-трансляций по локальной сети, Ethernet или через интернет.. Это ограничивает приложение как по протоколам вещания (HLS/DASH/ICY/RTSP), так и по продуктовой ценности для пользователей, которым нужен постоянный доступ к потоковым источникам..

## 2. Цели

1. Реализовать отдельную пользовательскую функцию "Трансляции" для управления потоковыми источниками внутри приложения..
2. Поддержать воспроизведение интернет-аудио, интернет-видео и согласованного объёма RTSP-трансляций в медиаплеере приложения..
3. Добавить работу с открытыми интернет-списками трансляций аудио- и видеоканалов, а также ручное добавление пользовательских источников..
4. Ввести отдельный экран списка трансляций с действиями обновления, загрузки из интернета, ручного добавления и перестановки избранных источников вверх списка..
5. Обеспечить различное поведение по типу источника: аудиотрансляция стартует прямо из списка без ухода со страницы, видеотрансляция открывается в полноэкранном просмотре..
6. Обеспечить корректное поведение плеера при работе с сетевыми задержками, буферизацией, RTSP-особенностями и обрывами соединения..

**Non-goals:**

- Интеграция с закрытыми API сторонних платформ вещания (YouTube, Twitch, т.д.)..
- Построение сложного телегида, расписаний передач, DVR/timeshift и серверной учётной системы каталогов..
- Замена существующего механизма "Избранное" в приложении - для трансляций вводится отдельная локальная логика "поднять вверх списка", а не переиспользование глобального избранного..

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. В системе появляется отдельный пункт настроек "Трансляции"..
2. В главном окне появляется новая команда "Трансляции" со своей иконкой; тот же сценарий желательно запускать и из виджета..
3. У "Трансляций" есть свой отдельный экран со списком текущих источников..
4. Экран трансляций должен уметь обновлять список, загружать открытые списки из интернета и позволять пользователю вручную добавлять свои источники..
5. Источник может быть аудио- или видеотрансляцией; долгосрочно в рамку функции включаются и RTSP-сценарии..
6. Трансляцию можно пометить как избранную не через существующий глобальный механизм, а через локальное поднятие источника в верх списка..
7. При нажатии на аудиотрансляцию проигрывание стартует прямо на экране списка, при этом сам список не исчезает..
8. При нажатии на видеотрансляцию открывается полноэкранный просмотр..
9. Возможность добавления собственных URL-адресов обязательна как для тестирования, так и для реального использования..
10. Поддержка парсинга простых списков воспроизведения (например, `.m3u`, `.pls`, JSON) рассматривается как целевой сценарий, но допускает поэтапную поставку..

### 3.2 Жёсткие ограничения

- **Flavor:** Полная поддержка (progressive + HLS/DASH) только в standard / legacy / noLegal / vr - там подключены модули потоковых протоколов. В lite / photos этих модулей нет, поэтому HLS/DASH недоступны без роста APK; для них вариант - либо только progressive-аудио, либо скрытый вход (photos вовсе без аудио/видео-возможностей). Точный выбор - owner-решение (§0 Scope boundaries). Гейтить через flavor-интерфейс/source-set, не через флаги в общем коде..
- **RTSP:** RTSP включён в рамку стратегической функции, но для 1-й итерации требуется отдельное owner-решение по обязательности, списку поддерживаемых transport-режимов и необходимости подключения/разведения зависимости по flavor..
- **API level:** Без API-специфики (минимальный уровень Android 26, определяемый проектом)..
- **Wear OS:** Не затрагивается на первом этапе (только `app_v2`)..
- **Производительность:** Плеер должен освобождать ресурсы при закрытии или переходе в фоновый режим; обработка буферизации не должна блокировать UI-поток..
- **Совместимость данных:** Базовое сохранение пользовательских URL (если потребуется локальная база данных или Preferences) должно быть обратно совместимым..
- **Локализация:** EN/RU/UK для системных сообщений об ошибках (сеть недоступна, неверный URL)..
- **Доступность:** Экран трансляций и его запуск из главного окна / виджета должны в дальнейшем поддерживать keyboard, D-pad/TV и mouse-навигацию; точная раскладка уточняется на тактическом этапе..

### 3.3 Owner inputs (Approval gate)

- **Flavor scope:** 1-я итерация включает полный streaming-scope (progressive, HLS/DASH там, где доступны модули, и обязательный RTSP) в `standard` / `legacy` / `noLegal` / `vr`; `lite` получает только ограниченный manual/progressive audio-path без полного streaming-стека; `photos` не получает entry-point "Трансляции".. Гейтинг - через flavor-интерфейс/source-set, не через `BuildConfig` в `src/main`.
- **HTTP cleartext policy:** публичные `http://` потоки разрешены без allowlist-ограничения; security-конфигурация может быть ослаблена настолько, насколько нужно для произвольных публичных stream-host'ов в рамках этой функции.. UX и документация обязаны честно отражать, что app принимает cleartext-источники.
- **RTSP scope:** RTSP обязателен уже в 1-й итерации для полноценных streaming-flavor; минимальный baseline - RTSP playback с приоритетом RTP-over-RTSP/TCP (interleaved), а UDP-only/multicast можно считать best-effort или deferred, если они мешают срокам..
- **Entry-point contract:** Settings, главное окно и widget ведут в один и тот же экран списка "Трансляции"; прямой автозапуск последнего/избранного источника через отдельный entry-point в эту итерацию не входит..
- **Favorites model:** локальное "поднять вверх" хранится только внутри функции "Трансляции" и не синхронизируется с существующим глобальным механизмом избранного..
- **Autonomy rule:** агент самостоятельно закрывает почти все tactical/product/technical forks и эскалирует только необратимые риски или решения с внешними последствиями..
- **Related tickets:** none

## 4. Контекст текущей архитектуры

Текущий плеер (модуль `app_v2`, слой `ui/player`) делегирует воспроизведение протокол-специфичным хелперам и ориентирован на локальные файлы и сетевые папки (SMB/SFTP/FTP/cloud).. Ресерч (см. §6 артефакт) выявил два ключевых разрыва.. Во-первых, модель ресурса не имеет случая «интернет-поток», и определение маршрута воспроизведения для произвольной `http(s)`-ссылки отсутствует - такой URL сейчас молча трактуется как локальный файл и падает на проверке существования файла.. Во-вторых, в продукте нет отдельной поверхности "Трансляции" со списком источников, их локальной сортировкой, импортом открытых каталогов и быстрым повторным запуском.. Поэтому прямая работа с HTTP(S)/HLS/DASH/радио/RTSP требует не только нового playback-маршрута, но и отдельного пользовательского сценария хранения, загрузки и запуска источников..

## 5. Предлагаемый подход

Ввести отдельную пользовательскую функцию "Трансляции", внутри которой источники живут как самостоятельный тип контента, а не как случайный URL без контекста.. На уровне воспроизведения нужен новый тип ресурса «интернет-поток», распознавание `http(s)`/RTSP-схем до fallback в локальный файл и отдельный путь подготовки медиа-источника на существующем движке плеера.. На уровне продукта нужен отдельный экран списка трансляций, способный принять источники из открытого интернет-списка или от самого пользователя, локально поднять избранные вверх списка и маршрутизировать запуск по типу медиа.. Сетевой источник данных настраивается на потоковую реальность (user-agent, кросс-протокольные редиректы, ICY-метаданные радио, RTSP transport policy, буферизация под стриминг).. Без новой тяжёлой инфраструктуры - переиспользовать существующий движок плеера и, для аудио/радио, существующий фоновый аудио-путь..

### 5.1 Основные столпы / модули

1. **Entry points и навигация:** отдельный пункт настроек "Трансляции", отдельная команда в главном окне, опциональный запуск из виджета, отдельный экран списка источников..
2. **Каталог источников:** локальное хранение списка трансляций, импорт из открытых интернет-списков, ручное добавление и обновление своих источников..
3. **Локальное избранное для трансляций:** независимый от существующего "Избранного" механизм подъёма конкретных источников вверх списка..
4. **Распознавание и подготовка потока:** новый случай типа ресурса + детект `http(s)`/`rtsp`-маршрута до локального fallback; построение media source с авто-детектом формата по расширению/Content-Type и явной MIME-подсказкой/фабрикой как fallback..
5. **Радио, видео и режим запуска:** progressive-путь для Icecast/Shoutcast + чтение ICY-метаданных; inline-аудио без ухода со списка; полноэкранное video/RTSP-воспроизведение с возвратом к списку..

### 5.2 Потоки данных и событий

```text
[Settings / Main window / Widget]
        -> [Translations screen]
        -> [Remote list import or manual source]
        -> [Source classification: audio / video / RTSP]
        -> [Inline audio playback OR fullscreen video playback]
```

Экземпляр плеера сообщает о состоянии воспроизведения (буферизация, проигрывание, ошибка) через существующие слушатели событий, а экран трансляций остаётся центральной поверхностью для повторного запуска и сортировки источников..

### 5.3 Точки расширяемости

- Поддержка новых протоколов вещания и новых внешних каталогов путём добавления соответствующих фабрик источников и адаптеров импорта без полной переделки пользовательского сценария..

### 5.4 Рекомендуемый объём 1-й итерации

Из ресерча (§6 артефакт):

- **Делать первым:** отдельный экран "Трансляции"; локальный список пользовательских источников; ручное добавление URL; базовая сортировка с локальным подъёмом избранных вверх; progressive http(s)-аудио; HLS VOD; базовое радио (Icecast/Shoutcast + ICY-метаданные); базовая инфраструктура потока (user-agent, редиректы, потоковый буфер, error-retry, подавление сохранения позиции для динамических источников)..
- **Отложить:** богатые каталоги/директории каналов; HLS/DASH live (live-offset, восстановление за пределами live-окна); расширенный импорт плейлистов `.m3u`/`.pls`/`.xspf`; запуск из виджета, если это конфликтует со сроками 1-й итерации; полное RTSP-покрытие до отдельного решения по dependency/scope; DRM (явный non-goal)..

## 6. Открытые вопросы / Research items

> Codebase-research выполнен 2026-06-20 (batch-прогон). Первые два пункта разрешены из кода; остальные требуют owner/product-решений по §0 Approval Gate и следующему тактическому циклу.
>
> **Артефакт:** `PLAN/S0565_internet-stream-playback/research/01__streaming-playback-research.md` - полный ресерч (источники + тестовые URL, точка интеграции в плеер с путями/строками, Media3-паттерны с Kotlin-сниппетами, матрица сложностей, рекомендация по 1-й итерации, owner-решения).

1. **Выбор библиотеки для HLS/DASH - RESOLVED**
   - **Вопрос:** Требуется ли подключать дополнительные модули Media3 (`media3-exoplayer-hls`, `media3-exoplayer-dash`) в `build.gradle.kts` или они уже включены?
   - **Находка:** Уже подключены - `androidx.media3:media3-exoplayer-hls:1.2.1` и `media3-exoplayer-dash:1.2.1` для flavors standard / noLegal / legacy / vr (`app_v2/build.gradle.kts:1134-1141`); smoothstreaming исключён. НЕ подключены для `lite` и `photos`.
   - **Вывод:** Для основных flavors новых зависимостей не нужно (`HlsMediaSource.Factory` / `DashMediaSource.Factory` доступны). Если поток должен работать и в lite/photos - добавить туда те же артефакты.
   - **Статус:** Resolved

2. **Обработка незашифрованного трафика (Cleartext) - RESOLVED (требует owner-решения по политике)**
   - **Вопрос:** Как обрабатывать `http://` потоки (многие интернет-радиостанции не поддерживают `https://`)?
   - **Находка:** `@xml/network_security_config`: `base-config cleartextTrafficPermitted="false"` (HTTPS-only по умолчанию); cleartext разрешён только для приватных диапазонов (192.168/10.0/172.16/localhost). Произвольные публичные `http://` потоки сейчас БЛОКИРУЮТСЯ.
   - **Вывод:** Поддержка `http://` требует явного security-решения: (а) per-domain allowlist в network_security_config под конкретные стрим-хосты, либо (б) ослабление base-policy (ухудшает security-постуру всего приложения). Это решение - часть owner-gate поля "Scope boundaries / forbidden areas" в §0.
   - **Статус:** Resolved

3. **RTSP в 1-й итерации - RESOLVED**
   - **Вопрос:** RTSP обязателен уже в первом релизе функции "Трансляции" или может идти следующей итерацией после HTTP(S)-источников?
   - **Контекст:** RTSP заявлен пользователем как важный сценарий для Ethernet / LAN / internet streams, но текущая стратегия и build research фокусировались прежде всего на HTTP(S)/HLS/DASH/radio..
   - **Решение:** RTSP обязателен уже в 1-й итерации для `standard` / `legacy` / `noLegal` / `vr`.. Базовый transport-приоритет - RTP-over-RTSP/TCP (interleaved) как наиболее предсказуемый для LAN/internet; UDP-only/multicast не блокируют 1-й релиз и считаются best-effort/deferred, если потребуют отдельной проработки..
   - **Статус:** Resolved

4. **Формат удалённых списков трансляций - RESOLVED**
   - **Вопрос:** Какие открытые источники каталогов должны поддерживаться первыми: прямой `.m3u`, `.pls`, JSON-список, собственный простой формат или фиксированный curated feed?
   - **Контекст:** пользователь хочет "работать как с открытыми списками" и одновременно позволить ручное добавление своих каналов..
   - **Решение:** 1-я итерация поддерживает ручное добавление URL плюс импорт простого удалённого `.m3u`-списка как минимального массового формата.. `.pls`, custom JSON и curated-feed-экосистема откладываются.. Обновление/merge - append с de-duplication по нормализованному stream-URL и сохранением локального порядка/поднятых вверх источников..
   - **Статус:** Resolved

5. **Семантика entry-point'ов - RESOLVED**
   - **Вопрос:** должны ли Settings, главное окно и виджет всегда вести в один и тот же экран списка, или часть входов может запускать сразу последний/избранный источник?
   - **Контекст:** пользователь явно просит отдельную команду в главном окне и запуск из виджета, но финальная UX-семантика ещё не утверждена..
   - **Решение:** все entry-point'ы в этой итерации ведут в один и тот же экран списка "Трансляции".. Shortcut-семантика "сразу играть последний/избранный" откладывается до отдельного follow-up, чтобы не дробить UX и не плодить разные contracts запуска..
   - **Статус:** Resolved

6. **Inline audio UX - RESOLVED**
   - **Вопрос:** как именно выглядит "аудиотрансляция играет прямо отсюда, но список не пропадает" - sticky mini-player, подсветка одной строки, нижняя control-панель или переиспользование существующего audio bar?
   - **Контекст:** это влияет на архитектуру экрана "Трансляции", обратную связь пользователю и способ остановки/переключения источника..
   - **Решение:** минимальный baseline - переиспользование существующего audio-control surface в виде нижней sticky mini-control-панели/барa с текущим источником и базовыми действиями play/stop, при этом список остаётся видимым и интерактивным.. Точная вёрстка и поведение по ориентациям уточняются на `/ui-clarify` / tactical-этапе..
   - **Статус:** Resolved

7. **Fullscreen video return path - RESOLVED**
   - **Вопрос:** как пользователь возвращается из полноэкранной видеотрансляции к списку - Back, overlay action, picture-in-picture, сохранение последней позиции списка?
   - **Контекст:** пользователь ожидает отдельный fullscreen-сценарий для video, но поведение возврата и сохранения состояния пока не зафиксировано..
   - **Решение:** базовый contract - системный Back возвращает пользователя на экран списка "Трансляции" с сохранённой позицией списка и выделением/состоянием последнего источника.. PiP и отдельные overlay-actions не входят в 1-ю итерацию, если только не достаются почти бесплатно существующим player-path'ом..
   - **Статус:** Resolved

8. **Локальное избранное vs глобальное избранное - RESOLVED**
   - **Вопрос:** хранится ли признак "поднять вверх" только внутри экрана "Трансляции" или должен синхронизироваться с другими зонами приложения?
   - **Контекст:** пользователь явно попросил не использовать существующий механизм избранных, но степень изоляции новых данных ещё не согласована..
   - **Решение:** признак "поднять вверх" живёт только внутри функции "Трансляции" и не синхронизируется ни с глобальным "Избранным", ни с другими зонами приложения.. Это отдельная локальная сортировка для списка stream-источников..
   - **Статус:** Resolved

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Блокировка cleartext `http://` (большинство публичного радио - http) | Высокая | Большая доля реальных radio-URL молча не грузится | Owner-решение по cleartext-политике (§0): per-domain allowlist vs ослабление base vs cleartext только для подтверждённых пользователем потоков |
| Разрыв покрытия flavor (lite/photos без HLS/DASH) | Высокая | HLS/DASH-URL ломаются в этих сборках | Гейт фичи через flavor-интерфейс; либо только progressive-аудио, либо скрытый вход; решение в §0 Scope |
| RTSP окажется обязательным слишком рано | Средняя | Задержка всей функции "Трансляции" из-за отдельной dependency/scope-проработки | Зафиксировать RTSP как explicit owner-decision и при необходимости вынести в 2-ю итерацию без блокировки базового HTTP(S) сценария |
| Неясный формат удалённых списков | Высокая | Импорт открытых каталогов затянет 1-ю итерацию и расползётся по edge-case'ам | Ограничить 1-й релиз ручными URL и одним минимальным форматом импорта |
| Разная семантика входов (Settings / main / widget) | Средняя | UX станет непредсказуемым, сложнее поддерживать и документировать | На тактическом этапе утвердить единый contract для всех entry-point'ов |
| Inline audio перегрузит экран списка | Средняя | Список станет нечитабельным, а контроль воспроизведения - неочевидным | Для 1-й итерации выбрать минимальный control-surface и не смешивать его с полным player UI |
| Плейлисты `.m3u`/`.pls` не парсятся нативно | Средняя | Вставка типичной radio-directory ссылки полностью падает | 1-я итерация - только прямой stream-URL; парсинг плейлистов отложен |
| Сбой авто-детекта формата (нет/неверный Content-Type) | Средняя | Поток не стартует | MIME-подсказка / явная фабрика источника как fallback |
| Буферизация/обрывы на мобильной сети | Высокая | Зависания, дропауты | Потоковый буфер + retry/backoff + переподготовка по восстановлению связи |
| Дрейф live-edge (только HLS/DASH live) | Средняя | Падение после долгой паузы | Отложено вместе с live; при реализации - переход к live-краю и переподготовка |
| Lifecycle фонового воспроизведения (radio) | Средняя | Аудио стопается в фоне/при блокировке | Переиспользовать существующий фоновый аудио-сервис (foreground + audio focus + wake/wifi lock) |
| Сохранение позиции для живого потока | Низкая | Попытка сохранить/восстановить неопределённую позицию | Подавлять save/restore позиции для динамических источников |

## 9. Архитектурные решения (ADR)

**ADR-1: Использование Jetpack Media3 (ExoPlayer)**

- **Решение:** Для воспроизведения интернет-трансляций использовать существующий ExoPlayer из состава Jetpack Media3..
- **Альтернативы:** MediaPlayer (стандартный Android), сторонние плееры (VLC-based, IJKPlayer)..
- **Почему:** ExoPlayer уже интегрирован в проект, отлично поддерживает HLS/DASH, активно развивается Google и легко расширяется фабриками источников..

### Quiz decisions (2026-06-20)

- Scope 1-й итерации → RTSP обязателен уже в первом релизе для полноценных streaming-flavor вместе с HTTP(S)-сценариями (`/spec-quiz`).
- Public HTTP policy → публичные `http://` потоки разрешены без allowlist-ограничения; security-политика приложения подстраивается под этот scope (`/spec-quiz`).
- Autonomy → агент может самостоятельно закрывать почти все дальнейшие развилки по функции "Трансляции", эскалируя только необратимые риски (`/spec-quiz`).

## 11. Критерии готовности (strategic-level)

1. Пользователь может открыть экран "Трансляции" как минимум из одного основного entry-point'а; остальные entry-point'ы (Settings / main / widget) либо реализованы, либо явно зафиксированы как deferred с понятной причиной..
2. Экран "Трансляции" показывает текущий список источников и поддерживает хотя бы базовые сценарии обновления списка и ручного добавления собственного URL..
3. Источник можно локально поднять вверх списка как "избранный" без использования существующего глобального механизма избранного..
4. При нажатии на аудиоисточник воспроизведение стартует без ухода со списка, а при нажатии на видеоисточник открывается полноэкранный просмотр..
5. Прямая `https`-ссылка на progressive-аудио (mp3/aac) проигрывается во всех затронутых flavor..
6. Тестовый HLS VOD-поток (`.m3u8`) проигрывается в flavor с потоковыми модулями..
7. Тестовая интернет-радиостанция (Icecast/Shoutcast) играет, и отображается её ICY-метаинформация (станция/трек)..
8. Сценарий RTSP либо поддержан в согласованном объёме, либо явно отмечен как deferred в тактической спецификации до следующей итерации..
9. При сетевой ошибке плеер переходит в состояние ошибки без краша и пытается переподключиться при восстановлении связи..
10. Воспроизведение проверено на реальном устройстве (тестовые URL из §6 артефакта)..
