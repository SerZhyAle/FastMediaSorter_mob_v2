## 1. Проблема

Просмотрщик, открывающий изображение из стороннего приложения (шара или «открыть с помощью»), не имеет полного набора операций основного плеера. После предыдущего этапа bitmap-only операции (распознавание текста, перевод, печать, поворот экрана) уже работают на любой картинке, но три операции по-прежнему недоступны в этом просмотрщике:
- доступ к настройкам перевода и распознавания текста (выбор языков, стиль наложения, шрифт);
- рисование поверх статичного изображения;
- кадрирование-в-файл и сжатие для картинок, у которых нет локального пути (открытых из сторонних приложений по `content://`).

В результате пользователь, открывший картинку из мессенджера или браузера, видит урезанный набор действий по сравнению с тем же файлом, открытым внутри приложения.

---

## 2. Цели

1. Из standalone-просмотрщика открывается диалог настроек перевода и распознавания текста - тот же, что в основном плеере.
2. В standalone-просмотрщике доступно рисование поверх статичного изображения с сохранением результата.
3. Кадрирование-в-файл и сжатие работают для картинок, открытых из сторонних приложений (источник без локального пути), отдавая новый файл.
4. Поведение основного плеера не меняется.

**Non-goals:**

- Редактирование/кадрирование «с перезаписью на месте» для не-локальных источников - перезапись в чужой `content://` невозможна, такие операции остаются скрытыми для не-локальных файлов.
- Видео, аудио и документы - объём только статичные изображения.
- Трансляция на внешний экран, плейлист, история - намеренно отсутствуют в standalone по архитектуре.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Переиспользовать существующие движки операций и диалоги, не дублируя их под standalone.
2. Единый механизм «материализации во временный файл» как переиспользуемая роль для будущих файловых операций.
3. Стандартные элементы доступа (пункт overflow-меню) визуально и поведенчески согласованы с уже существующими пунктами просмотрщика.

### 3.2 Жёсткие ограничения

- **Flavor:** операции перевода и распознавания текста доступны только в сборках, где эти способности скомпилированы; в сборках без них соответствующие пункты скрываются через существующую проверку доступности способностей, не через флаг внутри общего кода. Рисование и файловые операции доступны во всех сборках с поддержкой изображений.
- **API level:** без API-специфики (минимальные уровни проекта без особых требований).
- **Wear OS:** не затрагивается.
- **Производительность:** материализация источника во временный файл выполняется вне главного потока; недопустима блокировка интерфейса при открытии тяжёлой картинки.
- **Совместимость данных:** схема и миграции не затрагиваются; временные файлы размещаются во внутреннем кэше приложения и подлежат очистке.
- **Локализация:** EN/RU/UK - обязательно для нового пункта меню и любых новых сообщений.
- **Доступনость:** новый пункт меню и элементы рисования снабжаются описанием для TalkBack и фокусируемы для D-pad/TV; отличие состояний - не только цветом.

### 3.3 Owner inputs (Approval gate)

- **UI placement contract:** новый пункт «настройки перевода/OCR» размещается в overflow-меню просмотрщика рядом с распознаванием текста и переводом; вход в рисование - в overflow-меню; файловые операции (кадрирование-в-файл/сжатие) показываются для любого статичного изображения и материализуют источник по нажатию; результат сохраняется в Downloads и сканируется в галерею.
- **Accessibility:** все новые интерактивные элементы получают `contentDescription`, фокусируемость и осмысленный порядок фокуса; состояния рисования различимы не только цветом.
- **Localization:** новый пункт меню и сообщения о результатах операций добавляются в EN/RU/UK одновременно.
- **Communication policy:** тексты тостов и ошибок (результат сохранения, отсутствие текста при распознавании, недоступность операции) соответствуют `docs/COMMUNICATION_POLICY.md`; чек-лист тональности (§6 политики) - обязательный гейт перед интеграцией строк.
- **Validation level:** сборка целевого варианта + ручная проверка на устройстве на картинке из стороннего приложения и на локальной картинке.

## 4. Контекст текущей архитектуры

Специализированный standalone-просмотрщик намеренно отделён от системы ресурсов и базы данных: он показывает один внешний файл без плейлиста и истории. Из-за этого часть операций основного плеера в нём либо отключена осознанно, либо ещё не подключена.

Сейчас три операции недоступны по техническим причинам, а не по замыслу. Показ диалога настроек перевода реализован помощником, жёстко завязанным на разметку основного плеера, поэтому из урезанного просмотрщика он не вызывается. Рисование требует доступа к отрисованному изображению, которое в этом просмотрщике не предоставляется наружу. Кадрирование-в-файл и сжатие опираются на исходный путь файла, которого у картинок из сторонних приложений нет.

---

## 5. Предлагаемый подход

Довести standalone-просмотрщик до паритета с основным плеером по операциям статичного изображения там, где это архитектурно осмысленно, переиспользуя существующие движки и не меняя поведение основного плеера.

### 5.1 Основные столпы / модули

**Столп A - доступ к настройкам перевода/OCR без привязки к экрану.**
Ответственность за показ диалога настроек перевода и распознавания текста выделяется в роль, не зависящую от разметки конкретного экрана, чтобы и основной плеер, и standalone-просмотрщик вызывали её одинаково. Дублирование диалога запрещено - источник правды один.

**Столп B - предоставление отрисованного изображения для рисования.**
Просмотрщик предоставляет текущий отрисованный кадр как источник для слоя рисования и подключает существующую роль рисования поверх изображения. Результат сохраняется как файл.

**Столп C - материализация не-локального источника.**
Вводится переиспользуемая роль, которая по запросу копирует читаемый внешний источник во временный локальный файл и отдаёт путь операциям, которым нужен исходник. Операции, использующие этот путь, сохраняют результат как **новый** файл, а не перезаписывают исходник. Роль общая для кадрирования-в-файл, сжатия и сохранения рисунка.

### 5.2 Потоки данных и событий

- Настройки перевода/OCR: UI (overflow) → роль показа диалога → чтение/запись пользовательских настроек → закрытие диалога.
- Рисование: UI → запрос отрисованного кадра у просмотрщика → слой рисования → сохранение как новый файл → уведомление о результате.
- Файловые операции для не-локального источника: UI → роль материализации (фон) → локальный путь → движок операции → новый файл → уведомление.

### 5.3 Точки расширяемости

- Роль материализации источника должна быть пригодна для любых будущих файловых операций просмотрщика, не только трёх текущих.
- Роль показа диалога настроек должна оставаться переиспользуемой между основным плеером и специализированными хостами без привязки к конкретной разметке.

## 6. Открытые вопросы / Research items

1. **Развязка показа диалога настроек от разметки основного плеера**
   - **Вопрос:** как выделить показ диалога настроек перевода/OCR в роль, не зависящую от разметки, минимальным безопасным изменением.
   - **Варианты:** вынести только метод показа диалога; ввести лёгкую роль-обёртку поверх существующих настроек.
   - **Нужно выяснить:** какие зависимости диалога действительно нужны (контекст, владелец жизненного цикла, хранилище настроек) и не тянут ли они за собой разметку основного плеера.
   - **Статус:** Resolved
   - **Артефакт:** `PLAN/S0410_standalone-image-action-parity/research/01__dialog-extraction.md`

2. **Назначение и жизненный цикл результата файловых операций для не-локальных картинок**
   - **Вопрос:** куда сохранять новый файл и когда удалять временный материализованный исходник.
   - **Найдено:** существующий механизм кадрирования уже сохраняет в Downloads при отсутствии ресурса-приёмника и сканирует файл в галерею; нужен лишь локальный путь-источник (материализация). Кастомное сохранение в Pictures не требуется.
   - **Статус:** Resolved
   - **Артефакт:** `PLAN/S0410_standalone-image-action-parity/research/02__save-target-temp-lifecycle.md`

3. **Сохранение рисунка по не-локальной картинке**
   - **Вопрос:** как сохранять результат рисования, если исходник без локального пути (нет перезаписи на месте).
   - **Найдено:** рисование сохраняется через host-колбэки и слияние слоёв; для не-локального - сохранение как новый файл в Downloads тем же механизмом, что и кадрирование-в-файл/сжатие.
   - **Статус:** Resolved
   - **Артефакт:** `PLAN/S0410_standalone-image-action-parity/research/03__draw-save-nonlocal.md`

## 9. Архитектурные решения (ADR)

**ADR-1: Файловые операции для не-локальных источников - через материализацию во временный файл и сохранение как новый файл в Downloads**

- **Решение:** для картинок без локального пути исходник копируется во временный локальный файл; результат операции сохраняется как новый файл в Downloads (существующий fallback при отсутствии ресурса-приёмника) и сканируется в галерею, перезапись исходника не выполняется.
- **Альтернативы:** оставлять операции скрытыми для не-локальных источников; писать обратно в чужой `content://`; вводить отдельное сохранение в Pictures.
- **Почему:** запись в исходный `content://` стороннего приложения невозможна/ненадёжна; материализация даёт рабочий путь, а существующий механизм кадрирования уже сохраняет в Downloads при `saveTo = null` - отдельный код не нужен.

**ADR-2: Диалог настроек перевода/OCR - вынос в роль без привязки к разметке, без дублирования**

- **Решение:** показ диалога выделяется в переиспользуемую роль, вызываемую и основным плеером, и standalone-просмотрщиком.
- **Альтернативы:** скопировать диалог в standalone; оставить настройки только в общих Настройках приложения.
- **Почему:** единый источник правды для настроек; устранение завязки на разметку основного плеера без копипаста.

## 11. Критерии готовности (strategic-level)

1. Открыв картинку из стороннего приложения, пользователь видит и открывает диалог настроек перевода/OCR (в сборках, где способности доступны).
2. Пользователь рисует поверх такой картинки и сохраняет результат как новый файл.
3. Кадрирование-в-файл и сжатие для такой картинки дают новый файл; уведомление сообщает результат.
4. Для локальной картинки все операции работают, как и раньше.
5. Основной плеер не изменил поведение операций изображения и настроек перевода.
6. В сборках без перевода/распознавания соответствующие пункты не отображаются.
