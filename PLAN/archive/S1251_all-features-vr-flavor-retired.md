# S1251 - ALL_FEATURES still attributes capabilities to the retired `vr` flavor

**Status:** Archived

## Withdrawn 2026-07-28, same day it was filed - the premise is false

`vr` **is** a real, declared product flavor: `app_v2/build.gradle.kts:487`, `create("vr")`, dimension `version`, `versionNameSuffix = "-VR"`, arm64-only, with its own CMake XR runtime target. It sets `SUPPORT_STREAMS = true` at line 528.

The error was mine and worth recording so it is not repeated. I scanned `productFlavors` over a truncated line window (300-470), saw five `create(..)` calls, and treated absence inside that window as absence from the file - `create("vr")` sits at 487, just past the edge. The comment at line 276-277 then read as confirmation: "S0250: vrUnlicensed archived; noLegal now owns the sideload-VR distribution channel". That sentence retires **`vrUnlicensed`**, a different flavor. `vr` was never in it.

So the 334 `ALL_FEATURES` records carrying `vr`, and the `$validFlavors` lists that whitelist it, are all correct. Nothing to fix.

The one true observation buried in the original text is not worth a ticket: `getByName("vr")` in the `sourceSets` block would fail at configuration time if the flavor did not exist, which is a cheap way to confirm a flavor is live without reading `productFlavors` at all.

## 0. Raw capture (original, superseded)

Found while auditing S1220 (`/spec-next` round 1, 2026-07-28). Out of scope of that ticket - parked per CLAUDE.md 3.1.

S1220's inventory record reads:

```json
{"id":"streams.atlas-tile-decode-survives-cache-invalidation","area":"Streams",
 "flavors":["standard","legacy","vr","noLegal"],"spec":"S1220","status":"active"}
```

`vr` is not a build that can be produced. `app_v2/build.gradle.kts` `productFlavors` declares exactly five: `standard`, `noLegal`, `lite`, `photos`, `legacy`. The comment at `build.gradle.kts:276-277` records why:

```
(S0250: vrUnlicensed archived; noLegal now owns the sideload-VR distribution channel.)
```

## 1. Scale

Not a one-record typo - the retired name is baked into the tooling vocabulary and a majority of the inventory.

- `docs/ALL_FEATURES.jsonl`: 591 records total, **334 of them carry `vr`** in `flavors`. For comparison: `standard` 561, `legacy` 472, `noLegal` 404, `photos` 282, `lite` 245.
- `scripts/all_features/add.ps1:41`, `patch.ps1:42`, `validate.ps1:28` all hardcode `$validFlavors = @("standard", "lite", "photos", "legacy", "vr", "noLegal")`, so `validate.ps1` passes every one of those 334 records.
- `scripts/all_features/migrate_from_log.ps1:71` actively *assigns* `vr` from keyword matching (`"vr "`, `passthrough`, `openxr`, `quest`, `headset`).

## 2. Why it matters

`docs/FEATURES*.md` - the public showcase - is generated by `/skill-release` from the `ALL_FEATURES` diff. A flavor axis naming a build that no longer ships can attribute a capability to a package no user can install, and the gate that would normally catch it (`validate.ps1`) is the same file that whitelists the name.

It also defeats the rule the records exist to serve: `-FeatFlavors` is supposed to be read off the actual `BuildConfig` gate. There is no gate that evaluates to `vr`.

## 3. Open questions - the fork this ticket must resolve first

Two readings are possible and they lead to opposite fixes. Deciding between them is the first step, not an implementation detail.

- **`vr` meant the archived `vrUnlicensed` flavor.** Then all 334 occurrences are stale and the fix is a migration: map `vr` -> `noLegal` where the capability is VR-specific, drop it where the record already lists `noLegal`, then remove `vr` from the three `$validFlavors` lists and from `migrate_from_log.ps1`'s keyword map.
- **`vr` was being used as a capability axis** ("this ships in the VR-capable build") rather than a flavor name. Then the vocabulary is doing two jobs under one key, and the fix is to split them - a `capabilities` field distinct from `flavors` - or to rename the value to something that is not a flavor name.

Related: `SUPPORT_VR_PLAYER` is `true` only in `noLegal` (`build.gradle.kts:397`), false in standard/lite/photos. That asymmetry is what the `vr` value was probably standing in for.

## 4. Not in scope

Correcting S1220's own record in isolation. Editing one of 334 identically-shaped records makes the inventory inconsistent without making it truer; the vocabulary decision in section 3 has to land first.
