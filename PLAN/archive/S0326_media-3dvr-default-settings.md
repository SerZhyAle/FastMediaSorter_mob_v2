## 1. Проблема

В приложении нет единого места, где пользователь задаёт поведение 3D/VR по умолчанию для плеера изображений и видео. Часть параметров (режим рендера, авто-вход в иммерсивный режим, общий выключатель 3D, оверлей FPS) уже сохраняется и переносится в бэкап, но не имеет ни одного контрола в интерфейсе - изменить их пользователь не может. Поведение автораспознавания форматов жёстко зашито: эвристика по соотношению сторон работает всегда и даёт ложные срабатывания (обычное панорамное фото принимается за 360°), а отключить или сузить источники определения нельзя. В результате настройка 3D/VR возможна только покабельно - для отдельного файла внутри плеера, и эта поканальная настройка остаётся единственным способом влиять на поведение.

---

## 2. Цели

1. Появляется отдельный экран настроек в разделе медиа, собирающий глобальные «дефолтные» параметры 3D/VR в одном месте.
2. Пользователь управляет автораспознаванием 3D/VR: включает/выключает его целиком и выбирает, каким источникам доверять (имя файла, встроенные метаданные, эвристика по соотношению сторон - отдельно).
3. Пользователь задаёт поведение при неоднозначности: открыть как 2D либо применить лучшее предположение.
4. Пользователь задаёт режим по умолчанию, который применяется только когда формат определить не удалось (стерео-раскладка и проекция).
5. Параметры, которые сегодня сохраняются «вслепую» (режим рендера, авто-иммерсивность, общий выключатель 3D, оверлей FPS), становятся доступными для изменения через интерфейс.
6. Поканальная настройка для отдельного файла продолжает работать и всегда имеет приоритет над глобальным дефолтом.

**Non-goals:**

- Непрерывные параметры комфорта (межзрачковое расстояние, масштаб по умолчанию, обмен левого/правого глаза) - их нет в коде сегодня, в этот спек не вводятся.
- Изменение самих алгоритмов детекции форматов - меняется только конфигурируемость источников, не их логика.
- Новые проекции или стерео-форматы сверх уже поддерживаемых.
- Перенос настроек на Wear OS.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Экран структурирован по смысловым группам (автораспознавание, режим по умолчанию, иммерсивное поведение, плоский просмотр стерео, диагностика).
2. Группы, осмысленные только в VR-сборках, на остальных вариантах сборки не показываются, чтобы не путать пользователя нерабочими опциями.
3. Эвристика по соотношению сторон вынесена отдельным переключателем с пометкой о возможных ложных срабатываниях.

### 3.2 Жёсткие ограничения

- **Flavor (пересмотрено владельцем 2026-06-01):** ВЕСЬ экран настроек 3D/VR (включая автораспознавание и плоский просмотр стерео) показывается только на `vr` и `noLegal`. На `standard`/`lite`/`photos`/`legacy` секции 3D/VR в настройках нет - бэкенд работает на дефолтах, но UI для его изменения отсутствует. UI-часть размещается в существующей VR-секции media-настроек (фрагмент в `src/vr/java/`), доступность - через существующий флейвор-контракт VR-секции, НЕ через `BuildConfig`-флаг в `src/main/`. Поля настроек, детектор и координатор остаются в `src/main/` (используются на всех сборках). Реализация UI следует `dev/FLAVOR_DEVELOPMENT_RULES.md`; добавление `BuildConfig.SUPPORT_*`-проверок в `src/main/` запрещено (CLAUDE.md Rule 15).
- **API level:** без API-специфики; группы рендера естественно ограничены наличием нативного VR-рантайма в VR-сборках, а не проверкой уровня SDK.
- **Wear OS:** не затрагивается.
- **Производительность:** не критично; чтение настроек однократно при открытии файла, без работы на горячем пути рендера.
- **Совместимость данных:** новые параметры расширяют существующий набор пользовательских настроек и его бэкап/восстановление; форма - добавление полей с дефолтными значениями, без потери ранее сохранённых данных. Поканальные переопределения для файлов остаются в неизменной форме хранения.
- **Локализация:** EN/RU/UK - обязательно для всех новых строк экрана.
- **Доступность:** все новые контролы доступны с клавиатуры, D-pad/пульта и мыши; фокус-обход в том же порядке, что у соседних настроек; отличие состояний не только цветом (CLAUDE.md Rule 17).

### 3.3 Owner inputs (Approval gate)

- **Flavor scope (пересмотрено 2026-06-01):** все группы A–E показываются только на `vr`/`noLegal` через существующую VR-секцию настроек; на остальных сборках секции 3D/VR в настройках нет. Бэкенд (поля, детектор, координатор) - на всех сборках, на дефолтах.
- **UI placement contract:** новый экран внутри раздела медиа-настроек, открывается как дочерний экран; предпочтительно декларативный экран настроек (ориентационно-независимый), как у соседних медиа-настроек, чтобы не дублировать portrait/landscape-разметку.
- **Accessibility:** keyboard + D-pad + mouse для каждого контрола; состояния переключателей различимы не только цветом; фокус-порядок согласован с соседними настройками.
- **Data compatibility:** добавление полей настроек с дефолтами, без изменения формы хранения поканальных переопределений; новые поля включаются в бэкап/восстановление.
- **Localization:** EN/RU/UK для всех новых строк - обязательно.
- **Communication policy:** все подписи, описания и пояснения контролов проходят тон-чеклист `docs/COMMUNICATION_POLICY.md` (§6) перед интеграцией.
- **Validation level:** целевые сборки `standard` (флейвор-независимые группы) и `noLegal` (VR-группы) собираются; добавляются юнит-тесты на разрешение приоритета режима с новым слотом дефолта.
- **Owner sign-off:** 2026-06-01 - объём «полный экран» и модель «мягкий fallback» подтверждены владельцем.
- **Related tickets:** исторические `S0245`, `S0249`, `S0251`, `S0264`, `S0012`, `S0013` (все Archived); активных блокирующих/зависимых нет.

## 4. Контекст текущей архитектуры

За определение 3D/VR-формата отвечает каскадный детектор (метаданные контейнера, токены имени файла, теги стерео, эвристика соотношения сторон), за разрешение итогового режима - координатор плеера, объединяющий ручной выбор в сессии, поканальное переопределение и результат детекции. Глобальные настройки приложения хранят несколько VR-полей и переносят их в бэкап, но интерфейс настроек выводит лишь одно из них. Отдельный VR-блок настроек уже встроен в раздел медиа через флейвор-контракт доступности.

Сейчас проблему из §1 нельзя решить точечно: у координатора нет слота под «глобальный дефолт», источники детекции не конфигурируемы, а сохранённые VR-поля не имеют точек ввода. Нужен новый экран-владелец этих параметров плюс расширение цепочки разрешения режима.

---

## 5. Предлагаемый подход

Ввести роль «глобальные дефолты 3D/VR» как читаемый источник настроек, расширить раздел медиа-настроек новым экраном-владельцем этих параметров, и добавить в цепочку разрешения режима новый, самый нижний по приоритету слот «глобальный дефолт», применяемый только при неопределённом результате детекции. Конфигурируемость источников детекции выражается как набор флагов, которые детектор учитывает при выборе сигналов; сама логика сигналов не меняется.

### 5.1 Основные столпы / модули

- **Экран глобальных настроек 3D/VR.** Владелец групп A-E. Флейвор-независимые группы видны везде, VR-группы - только в VR-сборках через контракт доступности. Не содержит бизнес-логики - читает и пишет настройки.
- **Конфигурация автораспознавания.** Флаги: общий выключатель детекции; доверие источникам (имя файла / встроенные метаданные / эвристика соотношения сторон); поведение при неоднозначности (2D либо лучшее предположение). Детектор учитывает эти флаги при выборе сигналов.
- **Глобальный дефолт режима.** Дефолтная стерео-раскладка и дефолтная проекция, применяемые координатором только при неопределённом результате.
- **Расширение цепочки разрешения режима.** Новый слот «глобальный дефолт» ниже детекции и выше внутреннего сентинела AUTO.
- **Подключение ранее «слепых» полей.** Режим рендера, авто-иммерсивность, общий выключатель 3D, оверлей FPS получают точки ввода на экране.

### 5.2 Потоки данных и событий

- Экран настроек → слой пользовательских настроек (чтение/запись глобальных дефолтов и флагов детекции) → бэкап/восстановление.
- Открытие файла: детектор (с учётом флагов источников) → координатор: поканальное переопределение > выбор в сессии > результат детекции > глобальный дефолт > AUTO → рендер.
- Общий выключатель 3D и мастер-тумблер VR взаимодействуют по явной таблице истинности (см. §6).

### 5.3 Точки расширяемости

- Признак доступности VR-групп выражается через расширяемый флейвор-контракт доступности секции настроек (интерфейс в `src/main/`, No-Op по умолчанию, реальная реализация в VR-сборках) - без `BuildConfig`-проверок в `src/main/`.
- Конфигурация источников детекции спроектирована как открытый набор флагов, чтобы будущие источники добавлялись без переработки цепочки разрешения.
- Слот «глобальный дефолт» в координаторе изолирован, чтобы будущие параметры комфорта (вне объёма) могли подключаться без изменения приоритета поканального переопределения.

## 6. Открытые вопросы / Research items

1. **Взаимодействие общего выключателя 3D и мастер-тумблера VR**
   - **Вопрос:** как сочетаются глобальный «выключить 3D/VR» и существующий мастер-тумблер VR (живут в разных хранилищах настроек)? Какой из них главнее и что видит пользователь при их рассогласовании?
   - **Решение (2026-06-01, владелец):** объединить в один пользовательский контрол «3D/VR вкл/выкл». Оба хранящихся флага остаются, но второй становится ведомым - синхронизируется со значением единого контрола, чтобы они не могли противоречить. Таблица истинности вырождается: пользователь видит одно состояние, рассогласование невозможно.
   - **Статус:** Resolved

2. **Раздельные дефолты для изображений и видео**
   - **Вопрос:** глобальный дефолт режима - общий для фото и видео или раздельный?
   - **Варианты:** общий один набор; раздельные «дефолт для фото» / «дефолт для видео».
   - **Нужно выяснить:** ожидание пользователя; в первой итерации допустим общий, с возможностью разделить позже.
   - **Статус:** Open

3. **Видимость 3D/VR настроек на не-VR сборках**
   - **Вопрос:** показывать ли какие-либо настройки 3D/VR на сборках ниже VR?
   - **Решение (2026-06-01, владелец):** нет. Весь экран 3D/VR показывается только на `vr`/`noLegal`. На обычных сборках секции 3D/VR в настройках нет. Это распространяется и на дефолтную проекцию, и на автораспознавание, и на плоское стерео.
   - **Статус:** Resolved

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Изменение цепочки разрешения режима ломает корректно размеченный контент | Средняя | Файлы открываются не в том режиме | Глобальный дефолт строго как fallback только на неопределённом результате; покрыть приоритет юнит-тестами |
| Координатор разрешения режима сегодня без тестов | Средняя | Регресс приоритета незаметен | Добавить юнит-тесты на все ветки приоритета до правки |
| Рассогласование общего выключателя 3D и мастер-тумблера VR (разные хранилища) | Средняя | Противоречивое поведение, непонятное пользователю | Зафиксировать таблицу истинности (§6.1) до реализации |
| Видимая, но нерабочая опция проекции вне VR-сборок | Низкая | Путаница пользователя | Решить §6.3; по умолчанию скрывать VR-группы вне VR-сборок |
| Случайное добавление флейвор-гейта в общий код | Низкая | Нарушение Rule 15, протечка VR-логики в общие сборки | Доступность через флейвор-контракт, ревью на отсутствие `BuildConfig.SUPPORT_*` в `src/main/` |

## 9. Архитектурные решения (ADR)

**ADR-1: Глобальный дефолт как мягкий fallback, а не жёсткий override**

- **Решение:** глобальный дефолт режима применяется координатором только когда детекция вернула неопределённый результат; детекция и поканальное переопределение всегда выше по приоритету.
- **Альтернативы:** жёсткий override, подавляющий автоопределение для всех файлов.
- **Почему:** жёсткий override ломает корректно размеченный контент и противоречит ожиданию «дефолт = что делать, когда непонятно»; мягкий fallback безопаснее и предсказуемее (подтверждено владельцем).

**ADR-2: Доступность VR-групп через флейвор-контракт, а не BuildConfig-флаг**

- **Решение:** видимость VR-групп определяется контрактом доступности VR-секции настроек (true для `vr` и `noLegal`).
- **Альтернативы:** гейт по `BuildConfig`-флагу поддержки VR-плеера.
- **Почему:** этот флаг не монотонен между `vr` и `noLegal` - гейт по нему спрятал бы VR-группы в сборке `vr`; контракт корректно покрывает обе сборки и соответствует Rule 15.

**ADR-3: Весь UI 3D/VR - только в VR-сборках, внутри существующей VR-секции (пересмотр)**

- **Решение:** настройки 3D/VR (включая автораспознавание и плоское стерео) показываются только на `vr`/`noLegal` и размещаются в существующей VR-секции media-настроек. Отдельной всегда-видимой секции нет.
- **Альтернативы:** отдельная флейвор-независимая секция для групп A/D (исходное предположение спеки).
- **Почему:** решение владельца (2026-06-01): 3D/VR - это VR-функция; на сборках ниже VR её настройки не нужны и только засоряют интерфейс. Бэкенд остаётся в `main` на дефолтах. Это сливает исходные Phase 04 и Phase 05 в одно расширение VR-блока.

## 11. Критерии готовности (strategic-level)

1. В разделе медиа-настроек открывается отдельный экран 3D/VR.
2. На не-VR сборках видны только группы автораспознавания и плоского просмотра стерео; VR-группы скрыты.
3. На `vr`/`noLegal` видны все группы, включая иммерсивность, проекцию и диагностику.
4. Пользователь выключает автораспознавание, и файлы без поканального переопределения открываются как 2D.
5. Пользователь отключает эвристику соотношения сторон, и ложные срабатывания на панорамных фото прекращаются, при этом файлы с явной разметкой по-прежнему определяются.
6. При неопределённом формате файл открывается в заданном пользователем дефолтном режиме.
7. Поканальное переопределение для конкретного файла продолжает побеждать глобальный дефолт.
8. Ранее недоступные параметры (режим рендера, авто-иммерсивность, общий выключатель 3D, оверлей FPS) изменяются с экрана и сохраняются между запусками.
