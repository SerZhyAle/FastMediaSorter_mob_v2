## 0. Захваченный материал (inbox)

**Захвачено:** 2026-07-28

**Текст:**

Найдено при разборе пакета удалённых логов (`/newlog`, 5 сессий с устройства `ums512_1h10_Natv`).

`/newlog` шаг 2 сортирует сессии «по временной метке, зашитой в имя файла (`fastmediasorter_YYYYMMDD_HHmmss.log`), сначала старые». Имя файла создаётся на устройстве в момент старта сессии, то есть берётся из системных часов устройства.

Устройство `ums512_1h10_Natv` - прошивка с недостоверным временем (`Android Version: 14.0` при `SDK / API Level: 29`, `Security Patch: 2020-02-05`). Одна из сессий стартовала с часами, показывающими февраль 2025:

```
logs/fastmediasorter_20250217_035912.log
=== Log started: 2025-02-17 03:59:12.466 ===
=== App version: 2.60.7191.740 (260719174) ===
...
2026-07-28 10:15:33.978 W/App: [orphan-cleanup/42c4e948] found 16 orphaned credential(s) ...
```

То есть внутри того же файла время скачком выправляется на 2026-07-28 - реальная сессия произошла за минуту до `fastmediasorter_20260728_101628.log`, а по имени файла она уходит в самое начало списка, на полтора года назад.

Последствия:

- Хронологический разбор идёт в неверном порядке: самая свежая сессия анализируется первой как «самая старая», и вывод о регрессии между версиями строится задом наперёд.
- Отчёт `/newlog` (шаг 4, «most-recent session last») ставит не ту сессию последней.
- Дедуп в `import-remote-logs.ps1` идёт по `(name, size)`; имя - это те же часы устройства, так что две сессии с одинаково сбитыми часами и одинаковым размером схлопнутся в одну.

В этом заходе порядок пришлось восстанавливать вручную по строке `=== App version:` и по первой достоверной метке внутри файла.

**Захвачено во время:** разбор `/newlog` от 2026-07-28.

---

## 1. Проблема / симптом

Имя файла лога - не надёжный признак времени сессии, потому что берётся из часов устройства, а тестовое устройство их не держит. `/newlog` и `import-remote-logs.ps1` полагаются на него и для порядка анализа, и для дедупа.

---

## 2. Корневая причина

`/newlog` использует системные часы устройства, косвенно через имя файла. Они могут быть
исправлены уже во время сессии. `import-remote-logs.ps1` сравнивает только имя и размер, поэтому
не различает разные файлы с одинаковыми обоими значениями.

---

## 3. Исправление

- `import-remote-logs.ps1`: сравнивать содержимое SHA-256; уже импортированный хеш считать
  неизменённым. При конфликте имени с новым содержимым записывать второй файл с полным SHA-256
  перед расширением, не перезаписывая первую сессию.
- `/newlog`: сортировать новые файлы по максимальной корректной временной метке
  `yyyy-MM-dd HH:mm:ss.SSS` в содержимом, старые первыми. Файл без такой метки выводить после
  остальных с явным сообщением о fallback.
