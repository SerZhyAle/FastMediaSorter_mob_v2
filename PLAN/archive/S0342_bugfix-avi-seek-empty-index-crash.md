## 1. Проблема

При перемотке AVI-файла во встроенном видеоплеере воспроизведение прерывается ошибкой времени выполнения. На Quest 3 (noLegalDebug `2.60.6040.037`, лог `fastmediasorter_20260604_004413`) перемотка файла `_emule101.avi`, стримящегося по SMB, роняет сессию плеера с `errorCode=1000` (Unexpected runtime error), первопричина — `ArrayIndexOutOfBoundsException: length=0; index=0` внутри AVI-экстрактора медиа-стека при вычислении точки перемотки.

Дефект — в самом AVI-экстракторе медиа-стека: для AVI-файлов с отсутствующим или пустым индексом дорожки расчёт точки перемотки обращается к нулевому элементу пустого массива ключевых кадров. Само приложение не падает — ошибку перехватывает слушатель ошибок плеера, показывает отладочное уведомление и переходит на следующий файл. Но конкретный AVI становится «неперематываемым»: каждая попытка перемотки убивает воспроизведение и выбрасывает пользователя из файла, вместо того чтобы просто проигнорировать или ограничить перемотку.

---

## 2. Цели

1. Перемотка AVI-файла с отсутствующим или пустым индексом не прерывает воспроизведение и не выбрасывает пользователя из файла.
2. Для таких файлов перемотка деградирует предсказуемо: либо недоступна/ограничена с понятным поведением, либо обрабатывается так, что воспроизведение продолжается с корректной позиции без падения сессии плеера.
3. Регулярное воспроизведение (без перемотки) AVI-файлов с пустым индексом остаётся работоспособным, как и раньше.

**Non-goals:**

- Починка самого AVI-экстрактора медиа-стека (внешняя библиотека) — работаем на уровне приложения.
- Построение собственного индекса для AVI-файлов без индекса ради точной перемотки.
- Изменение поведения перемотки для форматов, отличных от проблемного класса AVI.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Если точная перемотка для конкретного AVI невозможна, предпочтительно сохранить хотя бы воспроизведение и не превращать перемотку в фатальный для сессии жест.
2. Пользователь не должен видеть «срыв» в другой файл при попытке перемотки — это воспринимается как краш.

### 3.2 Жёсткие ограничения

- **Flavor:** затрагивает все варианты сборки с поддержкой VIDEO (`standard`, `lite`, `legacy`, `noLegal`); дефект в общем video-пути, не привязан к флейвору и не VR-специфичен. Фикс живёт в общем коде, без новых `BuildConfig.SUPPORT_*`-гейтов в `src/main/` (CLAUDE.md Rule 15).
- **API level:** без API-специфики; наблюдение на Android 14 / API 34 (Quest 3), дефект не привязан к версии.
- **Wear OS:** не затрагивается.
- **Производительность:** перехват/проверка на пути перемотки не должны добавлять работы на горячем пути обычного воспроизведения и буферизации.
- **Совместимость данных:** не затрагивается — нет персистентного состояния.
- **Локализация:** если появится user-facing сообщение о недоступности точной перемотки — EN/RU/UK обязательны, тон по `docs/COMMUNICATION_POLICY.md`. Если деградация молчаливая (без строки) — локализация неприменима.
- **Транспортная независимость:** дефект проявился на SMB-стриминге, но первопричина — в экстракторе; фикс не должен зависеть от транспорта (локальный/SMB/cloud).

### 3.3 Owner inputs (Approval gate)

- **Performance budget:** без регресса горячего пути воспроизведения и буферизации; стоимость только на редком событии перемотки.
- **Communication policy:** если выбран вариант с user-facing сообщением о недоступной перемотке — обязательна сверка с `docs/COMMUNICATION_POLICY.md` (§6 tone checklist) перед интеграцией строки; вариант с молчаливой деградацией строки не вводит.
- **Validation level:** ручной on-device verify — перемотка проблемного AVI (`_emule101.avi` или эквивалент с пустым индексом) не роняет сессию; обычное воспроизведение не регрессирует. Опционально юнит-тест на классификацию ошибки перемотки.
- **Owner sign-off:** 2026-06-04 (по итогам анализа лога).
- **Related tickets:** S0341 (debug-уведомление об ошибке — Verified; именно оно проявило этот отказ в логе). Механизм пометки неудачных файлов сессии уже существует и переиспользуется.

## 4. Контекст текущей архитектуры

Видео-путь приложения поднимает медиаплеер поверх прогрессивного источника и AVI-экстрактора медиа-стека. Перемотка инициируется UI плеера, транслируется в команду перемотки плеера, та обращается к экстрактору за корректировкой целевой позиции по карте перемотки. Для AVI с пустым индексом эта корректировка падает внутри библиотеки до того, как управление вернётся в приложение по штатному пути.

Сейчас отказ обрабатывается уже постфактум — общим слушателем ошибок плеера, который трактует любую ошибку воспроизведения как «файл не воспроизвёлся» и переходит к следующему. Различить «файл невозможно открыть» и «файл играет, но перемотка по нему недопустима» на этом уровне нельзя — поэтому штатная перемотка по живому файлу превращается в срыв воспроизведения. Нужна развязка: распознавание класса отказа перемотки до того, как он эскалирует в гибель сессии, либо предотвращение опасной перемотки для файлов без пригодного индекса.

---

## 5. Предлагаемый подход

Не дать ошибке перемотки по AVI без индекса убить сессию плеера: либо предотвратить опасную перемотку для файлов, чья карта перемотки непригодна, либо перехватить именно этот класс отказа и восстановить воспроизведение с корректной позиции, не трактуя его как «файл не воспроизводится».

### 5.1 Основные столпы / модули

#### A. Распознавание непригодной перемотки

Путь перемотки видеоплеера должен отличать «фатальную для файла ошибку источника» от «перемотка по этому файлу недопустима, но файл играет». Класс отказа AVI-без-индекса относится ко второму и не должен эскалировать в переход на следующий файл.

#### B. Предсказуемая деградация перемотки

Для файла с непригодной картой перемотки перемотка либо предотвращается заранее (жест перемотки ограничивается/игнорируется с понятным для пользователя поведением), либо отказ перехватывается и воспроизведение продолжается без сброса плеера и без срыва в другой файл.

#### C. Переиспользование существующей обработки отказов

Решение опирается на уже существующий слой обработки ошибок плеера и пометки неудачных файлов сессии, расширяя его различением «отказ открытия» против «отказ перемотки», а не вводя параллельный механизм.

### 5.2 Потоки данных и событий

- UI плеера → команда перемотки → корректировка целевой позиции по карте перемотки → (при непригодной карте AVI) контролируемый отказ вместо исключения, всплывающего как ошибка воспроизведения.
- Слушатель ошибок плеера → классификация: «открытие/источник» (переход к следующему файлу) против «перемотка» (остаться в файле, восстановить позицию).

### 5.3 Точки расширяемости

- Классификация отказов плеера остаётся единой точкой, расширяемой новыми классами (отказ открытия / отказ перемотки / потолок декодера) без переписывания вызывающей стороны.
- Признак «перемотка по этому файлу непригодна» остаётся переиспользуемым для других форматов с проблемными картами перемотки, не только для AVI.

## 6. Открытые вопросы / Research items

1. **Стратегия деградации: предотвращение против перехвата**
   - **Вопрос:** ограничивать/отключать перемотку заранее для AVI с пустым индексом, или перехватывать ошибку перемотки постфактум и восстанавливать воспроизведение?
   - **Варианты:** (а) предетект непригодного индекса до жеста и ограничение перемотки; (б) перехват именно класса ошибки перемотки и восстановление позиции; (в) комбинация — предетект где дёшево, перехват как нижняя граница.
   - **Нужно выяснить:** доступен ли признак пустого/непригодного индекса AVI до попытки перемотки без значимой стоимости; достаточно ли надёжно классифицируется ошибка перемотки, чтобы не спутать её с реальным отказом источника.
   - **Статус:** Open — проектное решение уровня `/spec-tech`, внешнего research не требует.

2. **Поведение UI при недоступной перемотке**
   - **Вопрос:** показывать ли пользователю сигнал, что точная перемотка для файла недоступна, или деградировать молча?
   - **Варианты:** молчаливое игнорирование жеста; короткое user-facing сообщение (тогда EN/RU/UK + COMMUNICATION_POLICY).
   - **Нужно выяснить:** не станет ли молчаливое игнорирование восприниматься как «зависание» жеста.
   - **Статус:** Open.

## 9. Архитектурные решения (ADR)

**ADR-1: Обработка на уровне приложения, а не патч экстрактора**

- **Решение:** не патчить AVI-экстрактор внешней библиотеки, а распознавать и деградировать отказ перемотки на уровне приложения.
- **Альтернативы:** форк/патч библиотеки медиа-стека; построение собственного индекса AVF.
- **Почему:** патч внешней библиотеки дорог в сопровождении и хрупок при обновлениях; приложение уже владеет слоем обработки ошибок плеера, куда естественно вписать различение классов отказа.

## 11. Критерии готовности (strategic-level)

1. Перемотка AVI-файла с пустым/отсутствующим индексом не прерывает воспроизведение и не выбрасывает пользователя в другой файл.
2. Обычное воспроизведение AVI с пустым индексом (без перемотки) продолжает работать.
3. Реальный отказ источника (файл не открывается) по-прежнему корректно ведёт к переходу на следующий файл — классификация не поглощает настоящие отказы.
4. Поведение воспроизводится одинаково независимо от транспорта (локальный / SMB / cloud).
