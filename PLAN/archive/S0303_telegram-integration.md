## 1. Проблема

Сейчас приложение никак не сопрягается с Telegram. Единственное упоминание - локальная папка `Telegram`, то есть просмотр файлов, которые сам мессенджер уже сохранил на диск устройства. Пользователь, который держит медиа в Telegram или хочет быстро туда отправить отсортированное, вынужден переключаться между приложениями вручную.

Запрос владельца - изучить и реализовать сопряжение по двум направлениям:

- **Скачивание по ссылкам t.me** - получить вложения публичного поста/канала прямо в текущую папку, не открывая мессенджер.
- **Отправка/шеринг в Telegram** - переслать выбранные файлы в Telegram из браузера файлов и из плеера.

Направления «Telegram как источник» (клиентский API/TDLib) и «бот для удалённого управления» в объём не входят (см. §2 Non-goals).

---

## 2. Цели

1. Пользователь вставляет или шерит в приложение ссылку t.me на публичный пост и получает вложенные медиа в выбранной папке без открытия Telegram.
2. Скачивание t.me переиспользует существующий конвейер обработки входящих ссылок и очередь фоновых загрузок - отдельного UX-потока не появляется.
3. Из браузера файлов и из плеера пользователь отправляет один или несколько выбранных файлов в Telegram одним действием.
4. Отправка работает на публикуемых сборках без дополнительных разрешений высокого риска и без обязательного клиентского API Telegram.
5. Граница флейворов явная: что доступно в `standard`, доступно и в наследующих его сборках; тяжёлая/политически несовместимая со сторами часть включается только в `noLegal`.

**Non-goals:**

- Telegram как монтируемый источник-папка (просмотр/стриминг каналов, чатов, «Saved Messages» наравне с Drive/Dropbox) - требует клиентского API и тяжёлого рантайма, вне этой итерации.
- Бот для удалённого управления приложением и push-уведомлений о фоновых операциях.
- Скачивание из приватных чатов, требующее авторизованной пользовательской сессии Telegram.
- Двусторонняя синхронизация и оффлайн-зеркалирование переписки.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Скачивание t.me встаёт в общий каскад экстракции рядом с прочими извлекателями ссылок, а не как изолированная ветка.
2. Отправка в Telegram доступна там же, где уже живут действия «поделиться» - не вводя новую несогласованную точку входа.
3. По возможности лёгкая (нативная, без Python) реализация распознавания публичных t.me-постов, с падением на тяжёлый универсальный извлекатель только при необходимости.
4. Отправка без установленного клиента Telegram (через официальный Bot API с пользовательским токеном) - как опциональное расширение, не обязательное к первой итерации.

### 3.2 Жёсткие ограничения

- **Flavor:** скачивание по t.me - только `noLegal` (извлечение медиа из публичного контента относится к sideload-only поверхности наравне с прочими извлекателями). Отправка через системный share-intent - `standard` и все наследующие сборки. Реализация следует `dev/FLAVOR_DEVELOPMENT_RULES.md`: интерфейс в общем коде, No-Op по умолчанию, реальная реализация в исходниках целевого флейвора, привязка через флейвор-специфичный Hilt-модуль. Запрещено вводить `BuildConfig.*`-гейты внутри общего кода (CLAUDE.md Rule 15).
- **API level:** без API-специфики; целевой минимум флейворов не меняется.
- **Wear OS:** не затрагивается.
- **Производительность:** скачивание идёт в фоне через существующую очередь, не блокируя UI; распознавание t.me-поста не должно добавлять заметной задержки к приёму ссылки.
- **Совместимость данных:** новых персистентных сущностей не требуется для скачивания; для опциональной отправки через Bot API потребуется хранить пользовательский токен в существующем зашифрованном хранилище секретов - без изменения формы уже сохранённых данных.
- **Локализация:** EN/RU/UK - обязательно для всех новых строк.
- **Доступность:** новые элементы отправки следуют требованиям ввода (клавиатура, D-pad/пульт, мышь) и фокус-обходу наравне с соседними действиями (CLAUDE.md Rule 17).
- **Совместимость со сторами:** отправка не должна тянуть разрешений высокого риска и обязательного клиентского API; скачивание публичного контента не выходит в публикуемые сборки.
- **Право/ToS:** скачивание ограничено публично доступными постами; приватные сессии и обход ограничений Telegram вне объёма.

## 4. Контекст текущей архитектуры

За приём входящих ссылок и извлечение медиа уже отвечает каскад стратегий обработки ссылок (универсальный извлекатель, нативные извлекатели отдельных сайтов, извлекатель через невидимый WebView) с детерминированным порядком перебора; результат уходит в общую очередь фоновых загрузок с прогресс- и итоговыми уведомлениями. Этот конвейер целиком относится к sideload-only поверхности и собирается только в `noLegal`.

За действия «поделиться» отвечает слой UI браузера файлов и плеера, который уже формирует системные share-intent'ы и интеграции «отправить во внешнее приложение». За секреты (токены, учётные данные) отвечает существующее зашифрованное хранилище.

Решить задачу из §1 сейчас нельзя: ни одна стратегия каскада не распознаёт публичные t.me-ссылки и не извлекает из них медиа, а действие отправки не знает про Telegram как целевое приложение/канал.

---

## 5. Предлагаемый подход

Две независимые способности с разной флейвор-принадлежностью, переиспользующие уже существующие конвейеры, а не строящие параллельные.

### 5.1 Основные столпы / модули

**Столп A - Скачивание по ссылкам t.me (только `noLegal`).**

- Новый извлекатель публичных t.me-постов встаёт в существующий каскад экстракции ссылок как ещё одна стратегия с явным местом в порядке перебора.
- Лёгкий путь: распознать публичный пост и извлечь прямые URL вложений из его публично доступного представления, без тяжёлого рантайма.
- Тяжёлый путь как fallback: при неуспехе лёгкого распознавания ссылка проваливается в уже существующий универсальный извлекатель.
- Результат - один или несколько медиафайлов - уходит в общую очередь фоновых загрузок без отдельного UX-потока.

**Столп B - Отправка/шеринг в Telegram (`standard` и наследники).**

- Действие «Отправить в Telegram» появляется в существующей поверхности «поделиться» браузера файлов и плеера.
- Базовый путь: системный share-intent в установленный клиент Telegram - без разрешений высокого риска и без сетевого кода приложения.
- Опциональный путь (изначально `noLegal`): загрузка в Telegram через официальный Bot API с пользовательским токеном - работает без установленного клиента; токен живёт в существующем зашифрованном хранилище секретов.

### 5.2 Потоки данных и событий

- Скачивание: приём входящей t.me-ссылки → каскад экстракции (новая стратегия → fallback на универсальную) → очередь фоновых загрузок → файлы в целевой папке → уведомление о результате.
- Отправка (share-intent): выбор файлов в UI → действие «поделиться» → системный выбор Telegram → передача управления мессенджеру.
- Отправка (Bot API): выбор файлов → действие отправки → загрузка через слой работы с Bot API → прогресс/итоговое уведомление в приложении.

### 5.3 Точки расширяемости

- Скачивание расширяет уже существующий контракт стратегии извлечения ссылок - новая стратегия добавляется в каскад без изменения остальных.
- Отправка вводится через абстракцию «цель шеринга»: интерфейс в общем коде, No-Op реализация по умолчанию, реальные реализации (share-intent / Bot API) в исходниках целевых флейворов, привязка флейвор-специфичными Hilt-модулями - в полном соответствии с `dev/FLAVOR_DEVELOPMENT_RULES.md`.
- Оставить открытым добавление будущих режимов сопряжения (источник-папка, бот) поверх тех же абстракций без их переписывания.

## 6. Открытые вопросы / Research items

1. **Лёгкое извлечение публичных t.me-постов**
   - **Вопрос:** какой публично доступный путь даёт прямые URL вложений поста без клиентского API и без тяжёлого рантайма?
   - **Варианты:** публичная web-страница/embed-представление поста; готовая поддержка t.me в универсальном извлекателе как fallback.
   - **Нужно выяснить:** стабильность разметки публичного представления, какие типы вложений покрываются (фото, видео, документ, голосовое, кружок), поведение для многоэлементных постов.
   - **Статус:** Open

2. **Покрытие типов ссылок t.me**
   - **Вопрос:** какие формы ссылок поддерживаем в первой итерации?
   - **Варианты:** `t.me/<channel>/<id>` публичного канала; приватные `t.me/c/...` и инвайты - вне объёма.
   - **Нужно выяснить:** канонизация ссылок и однозначное отсечение неподдерживаемых форм с понятным сообщением пользователю.
   - **Статус:** Open

3. **Выбор пути отправки для первой итерации**
   - **Вопрос:** ограничиться ли share-intent'ом, или сразу включить Bot API как опцию?
   - **Варианты:** только share-intent (минимум, store-safe, `standard`); share-intent + Bot API (опция, начально `noLegal`).
   - **Решение (2026-05-30, владелец):** только share-intent. Bot API в первую итерацию не входит - Phase 03 помечена ⏭️ Skipped.
   - **Статус:** Resolved

4. **Конфигурация Bot API (если включаем)**
   - **Вопрос:** как пользователь задаёт цель отправки (токен бота и адресата) и где это живёт в настройках?
   - **Решение (2026-05-30, владелец):** неприменимо в этой итерации - Bot API отложен (см. §6.3). Вопрос вернётся при будущем расширении Phase 03.
   - **Статус:** Resolved (N/A this iteration)

## 9. Архитектурные решения (ADR)

**ADR-1: Скачивание t.me - часть существующего каскада экстракции, а не отдельный поток**

- **Решение:** новая стратегия извлечения публичных t.me-ссылок встраивается в уже существующий каскад приёма входящих ссылок.
- **Альтернативы:** отдельный изолированный поток скачивания только для Telegram.
- **Почему:** переиспользование очереди, прогресса, уведомлений и единый UX приёма ссылок; меньше дублирования и поверхностей сопровождения.

**ADR-2: Отправка вводится через абстракцию цели шеринга с флейвор-привязкой, а не через `BuildConfig`-гейт в общем коде**

- **Решение:** интерфейс цели шеринга в общем коде, реализации в исходниках флейворов, привязка флейвор-модулями.
- **Альтернативы:** условные ветки `BuildConfig.*` внутри общего UI.
- **Почему:** CLAUDE.md Rule 15 запрещает новые флейвор-гейты в общем коде; абстракция оставляет место для будущих режимов сопряжения.

**ADR-3: Граница store-совместимости проходит по типу способности**

- **Решение:** извлечение/скачивание контента → `noLegal`; отправка без разрешений высокого риска → `standard`.
- **Альтернативы:** обе способности в публикуемых сборках.
- **Почему:** соответствие уже принятой в S0156 топологии sideload-only поверхности и политикам сторов.

## 11. Критерии готовности (strategic-level)

1. Пользователь шерит/вставляет публичную t.me-ссылку и получает вложенные медиа в выбранной папке (сборка `noLegal`), без открытия Telegram.
2. Многоэлементный публичный пост приводит к скачиванию всех поддерживаемых вложений.
3. Неподдерживаемая форма t.me-ссылки (приватный чат, инвайт) даёт понятное сообщение, а не молчаливый отказ.
4. Из браузера файлов и из плеера пользователь отправляет выбранные файлы в Telegram одним действием (сборка `standard`).
5. Отправка не требует разрешений высокого риска и обязательного клиентского API Telegram.
6. В `standard`-сборке нет кода и поведения скачивания t.me.
