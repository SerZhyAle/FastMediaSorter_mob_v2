## 1. Проблема

Фоновый аудиосервис при ошибке источника (`errorCode=3003`, ExoPlayer не нашёл подходящий extractor для потока) сейчас немедленно останавливает всё воспроизведение и убирает мини-плеер/уведомление. Достаточно одного битого или нераспознаваемого файла в плейлисте, чтобы вся очередь оборвалась.

Пользователь ожидает поведения обычного аудиоплеера: проблемный трек пропускается, воспроизведение продолжается со следующего, а о пропуске сообщается коротко и понятно. Полная остановка из-за единичного файла воспринимается как сбой приложения.

Область: фоновое аудио (feature-path плеера, аудио-only путь). Видео и плеер на экране Activity не затронуты.

---

## 2. Цели

1. Единичный нераспознаваемый/битый аудиофайл в плейлисте пропускается, воспроизведение продолжается со следующего трека.
2. Пользователь получает короткое сообщение о том, что трек пропущен (без технических кодов).
3. Сервис останавливается только когда продолжать действительно нечем (пропускать некуда) или ошибка фатальна для всей сессии.
4. Сохраняется разделение «пропускаемая ошибка отдельного файла» и «фатальная ошибка сессии» (например исчезновение кэша), чтобы не маскировать настоящие сбои.

**Non-goals:**

- Изменение поведения видеоплеера и плеера на экране Activity.
- Повторные попытки/переоткрытие проблемного файла, восстановление битых данных.
- Предзагрузочная валидация форматов перед стартом очереди.
- Изменение логики автодокачки/кэша сетевых источников.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Сообщение о пропуске не должно быть навязчивым (не диалог, не серия тостов на каждый трек подряд).
2. Желательно указывать в сообщении имя пропущенного файла, если это не раздувает текст.
3. При серии подряд непроигрываемых файлов не заваливать пользователя сообщениями.

### 3.2 Жёсткие ограничения

- **Flavor:** все флейворы с поддержкой аудио (`standard`, `legacy`). `lite`/`photos` без AUDIO не затронуты. Без flavor-специфичного кода - правка в общем аудио-пути.
- **API level:** без API-специфики; поведение одинаково на minSdk 23 (legacy) и 26+.
- **Wear OS:** не затрагивается.
- **Производительность:** без влияния; обработка только в момент ошибки.
- **Совместимость данных:** изменений хранимых данных нет.
- **Локализация:** EN/RU/UK - обязательно для нового сообщения о пропуске.
- **Доступность:** сообщение должно дублироваться текстом (не только цветом/иконкой); читается TalkBack.
- **Communication policy:** текст сообщения проходит тон-чеклист `docs/COMMUNICATION_POLICY.md` (§6) перед интеграцией строк - без технического жаргона и кодов ошибок.

### 3.3 Owner inputs (Approval gate)

- **Communication policy:** сообщение о пропуске - короткое, дружелюбное, без `errorCode`/имён extractor'ов; проходит тон-чеклист `docs/COMMUNICATION_POLICY.md` §6.
- **Localization:** новая строка добавляется в EN/RU/UK в одном изменении; паритет проверяется аудитом локализации.
- **Validation level:** сборка целевого флейвора зелёная + ручная проверка на устройстве (плейлист с одним заведомо битым файлом).
- **Owner sign-off:** 2026-06-13.
- **Related tickets:** none.

## 4. Контекст текущей архитектуры

За фоновое аудио отвечает отдельный сервис на базе Media3 MediaSessionService со своим экземпляром плеера; он переживает уничтожение Activity и сам управляет уведомлением и мини-плеером. Слушатель ошибок плеера сейчас трактует любую ошибку одинаково - как сигнал немедленно завершить сессию.

Проблему нельзя решить «снаружи», потому что обработка ошибки и решение «стоп vs пропуск» живут внутри обработчика ошибок плеера сервиса. Контекст очереди (есть ли следующий трек, одиночный это файл или плейлист) доступен именно там. Логика отнесения ошибки к фатальной заложена в один общий путь и не различает категорию ошибки.

---

## 5. Предлагаемый подход

Ввести в обработчике ошибок аудио-сессии классификацию ошибки и ветвление поведения вместо безусловной остановки.

### 5.1 Основные столпы / модули

- **Классификация ошибки.** Отделить «пропускаемую» ошибку отдельного элемента очереди (источник нераспознан/битый/не читается как медиа) от «фатальной» для всей сессии (например исчезновение кэшированного файла, общесессийный сбой). Категория определяется по типу/коду ошибки плеера.
- **Решение о навигации.** При пропускаемой ошибке и наличии следующего элемента - перейти к следующему треку и продолжить воспроизведение. Если переходить некуда (одиночный файл либо очередь исчерпана) - корректно завершить сессию, как сейчас.
- **Уведомление пользователя.** Короткое неблокирующее сообщение о пропуске трека, инициируемое из фонового контекста сервиса. Сообщение - продуктовое, без технических деталей.
- **Антиспам сообщений.** Подряд идущие пропуски не должны порождать поток одинаковых сообщений (агрегация/дебаунс на уровне продуктового поведения).

### 5.2 Потоки данных и событий

Ошибка плеера → классификатор категории → если пропускаемая и есть следующий: навигация к следующему элементу + запрос на показ сообщения → продолжение воспроизведения. Если фатальная или некуда пропускать: текущий путь завершения сессии (очистка снапшота мини-плеера, остановка сервиса).

### 5.3 Точки расширяемости

- Категоризация ошибок должна допускать расширение набора «пропускаемых» причин без переписывания ветвления.
- Механизм показа сообщения из фонового сервиса должен оставаться единой точкой, переиспользуемой и для будущих пользовательских уведомлений сервиса.

## 6. Открытые вопросы / Research items

1. **Категоризация ошибок ExoPlayer для «пропуска»**
   - **Вопрос:** какие `PlaybackException.errorCode` (и их источники) считать пропускаемыми (битый/нераспознанный файл), а какие - фатальными для сессии?
   - **Решение:** skippable = `errorCode in 3000..4999` (parsing+decoding, дефект конкретного файла); fatal = остальное, включая `2xxx` IO (эвикция кэша/`FILE_NOT_FOUND` сохраняет текущее поведение остановки). Согласуется с прецедентом `2000..2999` в проекте.
   - **Статус:** Resolved
   - **Артефакт:** `PLAN/S0413_bugfix-audio-graceful-skip/research/01__error-code-classification.md`

2. **Механизм показа сообщения из фонового сервиса**
   - **Вопрос:** как показать неблокирующее сообщение, когда Activity может быть мертва (сервис в фоне)?
   - **Решение:** текстовый `Toast` с главного потока сервиса (надёжен для foreground-сервиса на API 23-35) с дебаунсом против серии пропусков. Существующий путь наблюдения ошибок в `PlayerMediaLoaderManager` не трогаем.
   - **Статус:** Resolved
   - **Артефакт:** `PLAN/S0413_bugfix-audio-graceful-skip/research/02__background-message-channel.md`

3. **Поведение при исчерпании очереди из-за пропусков**
   - **Вопрос:** что показать/сделать, если все оставшиеся треки оказались непроигрываемыми и очередь закончилась пропусками?
   - **Решение:** счётчик подряд-пропусков (сброс на `STATE_READY`); при достижении `mediaItemCount` - остановка + одно итоговое сообщение «нечего воспроизвести». Защищает от зацикливания при `REPEAT_MODE_ALL`.
   - **Статус:** Resolved
   - **Артефакт:** `PLAN/S0413_bugfix-audio-graceful-skip/research/03__queue-exhaustion-guard.md`

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Слишком широкая категория «пропускаемых» маскирует реальный сбой (кэш/сеть) | Средняя | Пользователь не узнаёт о настоящей проблеме, треки «молча» пропускаются | Узкий список кодов, фатальные ошибки оставляют текущее поведение остановки |
| Зацикливание/бесконечный пропуск при полностью битой очереди | Низкая | Лишние сообщения, дёрганье уведомления | Условие «есть следующий» + остановка по исчерпании, антиспам сообщений |
| Поток одинаковых сообщений при серии битых файлов | Средняя | Раздражающий UX | Агрегация/дебаунс по §3.1 |
| Toast/сообщение из фонового сервиса не показывается на части API | Средняя | Пропуск без обратной связи | Выбор надёжного канала в research item 2, fallback |

## 9. Архитектурные решения (ADR)

**ADR-1: Классифицировать ошибку, а не всегда останавливать сессию**

- **Решение:** обработчик ошибок различает пропускаемую ошибку отдельного файла и фатальную ошибку сессии; остановка - только для фатальных или при отсутствии следующего элемента.
- **Альтернативы:** оставить безусловную остановку (текущее поведение); глобально игнорировать все ошибки и всегда пытаться идти дальше.
- **Почему:** безусловная остановка обрывает плейлист из-за единичного файла; игнорирование всех ошибок маскирует реальные сбои (исчезновение кэша). Классификация даёт ожидаемый UX без потери диагностируемости.

## 11. Критерии готовности (strategic-level)

1. В плейлисте с одним заведомо нераспознаваемым файлом воспроизведение продолжается со следующего трека, а не останавливается.
2. Пользователь видит короткое сообщение о пропуске трека без технических кодов.
3. Одиночный непроигрываемый файл (вне плейлиста) корректно завершает сессию, как раньше.
4. Серия подряд непроигрываемых файлов не порождает поток одинаковых сообщений.
5. Фатальные ошибки сессии (например исчезновение кэша) по-прежнему останавливают сервис.
