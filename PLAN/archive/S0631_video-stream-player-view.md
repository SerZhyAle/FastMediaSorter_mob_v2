## 0. Захваченный материал (inbox)

**Захвачено:** 2026-06-22

**Текст:**

Видео-трансляция открывается в плеере. Однако большинство функций там не работают или
никак не применимы к видеопотоку. Что полезно для видеострима:

- полный экран
- снятие кадра
- поворот
- информация о файле
- PiP
- управление видео (диалог)
- Chrome Cast
- при «отправить в» - отправлять не файл, а ссылку (адрес потока), чтобы поделиться

Никакие другие функции не нужны. Вопрос: что проще - нарисовать новый плеер или создать
специальный вид для трансляций в существующем?

**Вложения:** нет.

## 1. Проблема

Видео-трансляция (live HLS/DASH/internet stream) открывается в том же полноэкранном плеере,
что и обычный медиафайл, и показывает полный набор контролов файлового плеера. Большая часть
из них к живому потоку неприменима: удаление/переименование/правка/копирование/перемещение,
слайдшоу, избранное, таймер сна и т.п. - они либо ничего не делают, либо вводят в заблуждение.
Пользователь видит «зашумлённый» интерфейс, а действительно нужная для трансляции операция -
поделиться адресом потока - сейчас пытается отправить файл, а не ссылку.

---

## 2. Цели

1. При открытии видео-трансляции плеер показывает только применимый к потоку набор контролов:
   полный экран, снятие кадра, поворот, информация, PiP, диалог управления видео, Chrome Cast,
   «отправить».
2. Все неприменимые к потоку контролы в этом режиме скрыты (а не показаны-но-нерабочи).
3. «Отправить» для трансляции делится адресом потока (ссылкой), а не пытается отдать/скачать файл.
4. Поведение обычных файлов (видео/аудио/изображения/документы) в плеере не меняется.

**Non-goals:**

- Отдельный новый экран/Activity-плеер для трансляций (решение - режим внутри существующего, см. §6.1).
- Починка движка Chrome Cast для live-URL (Cast сейчас не кастит прямой поток - отдельный тикет, см. §10).
- Улучшение устойчивости воспроизведения потока (восстановление при отставании от live-окна,
   буферизация, адаптивный битрейт) - отдельный тикет, см. §10.
- Заполнение метаданных трансляции (разрешение/битрейт/кодек) в «информации о файле».

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Минимальный, «чистый» набор контролов в режиме трансляции - ровно перечисленный в §0.
2. «Отправить» -> поделиться именно ссылкой на поток (любым приложением: мессенджер, буфер, SMS).

### 3.2 Жёсткие ограничения

- **Flavor:** применимо везде, где включена возможность трансляций (capability-гейт `SUPPORT_STREAMS`).
  Новый flavor-специфичный код не вводится; режим - рантайм-ветка в общем плеере, инертная там,
  где трансляции недоступны. Source-set разделение не требуется.
- **API level:** без новой API-специфики. PiP уже доступен с Android 12 (API 31+); на более ранних
  кнопка PiP скрыта существующим механизмом - режим трансляции это не меняет.
- **Wear OS:** не затрагивается.
- **Производительность:** нейтрально - режим только фильтрует видимость контролов.
- **Совместимость данных:** миграции хранилища нет.
- **Локализация:** EN/RU/UK - обязательно для любых новых/изменённых видимых строк.
- **Доступность:** при скрытии контролов сохранить корректный порядок фокуса (D-pad/TV),
  доступность оставшихся кнопок для TalkBack, и touch-таргеты.
- **UI-коммуникация:** новые/изменённые видимые строки (в т.ч. подпись действия «поделиться
  ссылкой») проходят `docs/COMMUNICATION_POLICY.md` (чек-лист тона §6) перед интеграцией.

### 3.3 Owner inputs (Approval gate)

- **Flavor scope:** standard и прочие сборки с `SUPPORT_STREAMS=true`; на сборках без трансляций
  ветка недостижима. Отдельной flavor-реализации не требуется.
- **UI placement contract:** режим трансляции переиспользует существующую командную панель и
  overlay управления видео; меняется только состав видимых элементов (стрим-набор из §2.1).
  Новых экранов/панелей не вводится. Portrait и landscape-варианты держатся в синхроне.
- **Accessibility:** оставшиеся контролы сохраняют focus order (D-pad/TV), TalkBack-метки и
  touch-таргеты; скрытие не оставляет «дыр» в навигации фокусом.
- **Communication policy:** да - строка действия «поделиться ссылкой» и любые сопутствующие
  тосты проходят чек-лист тона.
- **Validation level:** on-device проверка на реальной видео-трансляции (стрим-набор контролов
  виден/скрыт; «отправить» отдаёт URL; обычные файлы не регрессировали).
- **Owner sign-off:** 2026-06-22.
- **Related tickets:** S0581, S0586, S0591, S0592, S0593 (lineage трансляций); зависимые/смежные -
  Cast-for-streams fix и stream-robustness (BehindLiveWindow) запаркованы отдельными драфтами (§10).

## 4. Контекст текущей архитектуры

За полноэкранное воспроизведение отвечает единый плеерный экран с набором helper/manager-ролей:
загрузчик медиа, плеер-движок, командная панель и её планировщик видимости, overlay управления
видео, обработчики действий (снятие кадра, поворот, PiP, Cast, «отправить»), диалоги (информация,
управление). Видимость контролов уже вычисляется по состоянию (тип медиа, права записи/чтения),
и в панели есть единая точка сборки активных команд. Сейчас трансляция приходит как «обычный
видеофайл с http-адресом»: понятия «это живой поток» в состоянии плеера нет, поэтому контролы
не дифференцируются, а «отправить» идёт по файловому пути. Решить из §1 без введения признака
«трансляция» в состояние плеера нельзя - иначе фильтрацию пришлось бы размазать по многим местам.

---

## 5. Предлагаемый подход

Ввести в состояние плеера признак «это видео-трансляция», вычисляемый из синтетического признака
ресурса трансляции, и использовать его как единый гейт фильтрации контролов и ветвления действия
«отправить». Режим трансляции - не новый экран, а профиль видимости поверх существующего плеера.

### 5.1 Основные столпы / модули

1. **Признак трансляции в состоянии плеера.** Единый булев флаг, выводимый из признака
   ресурса-трансляции на этапе загрузки медиа. Источник правды для всех потребителей.
2. **Профиль видимости контролов трансляции.** Единая точка сборки активных команд и ветка
   landscape-раскладки отдают для трансляции только утверждённый набор (§2.1), скрывая остальное.
   Overlay управления видео и кнопка PiP остаются доступны.
3. **Ветвление «поделиться» для трансляции.** Действие «отправить» при активном признаке
   трансляции формирует полезную нагрузку как текст-ссылку (адрес потока) вместо файловой,
   уходя в системный шеринг текста.

### 5.2 Потоки данных и событий

- Загрузка медиа -> установка признака «трансляция» в состоянии -> состояние читают планировщик
  панели (видимость), landscape-раскладка (видимость), обработчик «поделиться» (вид нагрузки).
- UI не содержит бизнес-логики выбора набора: он читает готовый признак из состояния.

### 5.3 Точки расширяемости

- Набор «контролы трансляции» держать как единый список-источник, чтобы добавление/исключение
  контрола было правкой в одном месте (а не по менеджерам).
- Признак «трансляция» оставить пригодным для будущих стрим-специфичных решений (метаданные,
  устойчивость воспроизведения) без переопределения детекции.

## 6. Открытые вопросы / Research items

1. **Новый плеер vs режим в существующем**
   - **Вопрос:** что проще/правильнее - отдельный Activity-плеер для трансляций или режим внутри текущего?
   - **Решение:** режим (профиль) внутри существующего плеера; отдельный экран не оправдан (дублирование
     рантайма и хост-инфраструктуры без выигрыша). Детекция - по синтетическому признаку ресурса-трансляции.
   - **Статус:** Resolved
   - **Артефакт:** `PLAN/S0631_video-stream-player-view/research/01__player-stream-mode-architecture.md`

2. **Полнота набора контролов трансляции**
   - **Вопрос:** входит ли в стрим-набор что-то помимо перечисленного в §0 (например, переключатель
     дорожек/субтитров, если поток их несёт)?
   - **Решение:** следовать §0 строго (владелец явно: «никакие другие функции не нужны»). Переключатель
     альтернативных аудио/субтитров не вводится в первой итерации - отложен как out-of-scope (живые
     IPTV-релеи в свидетельствах одно-рендишные). Расширяемо позже без переопределения детекции (§5.3).
   - **Статус:** Resolved

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Видимость контролов размазана по нескольким менеджерам | Средняя | Стрим-фильтр пропущен в одном из мест | Единый признак в состоянии + единый список набора; покрыть тестом планировщика |
| Расхождение portrait/landscape раскладок | Средняя | В одной ориентации виден «лишний» контрол | Править обе раскладки в одном изменении, держать layout-land в синхроне |
| Cast-кнопка показана, но не кастит live-URL | Высокая | Пользователь жмёт Cast, поток не уходит | Зафиксировано как отдельный тикет (§10); в S0631 кнопка остаётся по запросу владельца |
| Регрессия обычных файлов при фильтрации | Низкая | У файлов пропадают нужные контролы | Гейт строго по признаку трансляции; on-device проверка файлового сценария |
| Потеря порядка фокуса при скрытии контролов | Средняя | D-pad/TV навигация «проваливается» | Проверить focus order после фильтрации на TV/эмуляторе |

## 9. Архитектурные решения (ADR)

**ADR-1: Режим трансляции внутри существующего плеера**

- **Решение:** профиль видимости контролов + ветка «поделиться» по единому признаку «трансляция»
  в состоянии плеера; без отдельного Activity.
- **Альтернативы:** отдельный плеер-экран для трансляций.
- **Почему:** отдельный экран дублировал бы движок воспроизведения, PiP, поворот, Cast, жесты,
  системные бары и инициализацию менеджеров без выигрыша; детекция трансляции и единая точка
  сборки команд уже есть.

## 11. Критерии готовности (strategic-level)

1. При открытии видео-трансляции в плеере видны только: полный экран, снятие кадра, поворот,
   информация, PiP, диалог управления видео, Chrome Cast, «отправить».
2. Все прочие контролы в режиме трансляции не показываются.
3. «Отправить» для трансляции запускает системный шеринг с адресом потока (ссылкой).
4. Открытие обычного видео/аудио/изображения/документа показывает прежний набор контролов без изменений.
5. В portrait и landscape набор контролов трансляции одинаков.
