## 1. Проблема

Текущий диалог управления воспроизведением использует взаимоисключающие radio-кнопки как переключатель разделов. Такая модель визуально выглядит как выбор значения, а не как навигация по страницам настроек, поэтому пользователь вынужден угадывать, что «кружочки» открывают разные панели. Проблема усиливается из-за динамического состава разделов: для аудио, видео и стереоконтента набор страниц разный, но интерфейс не объясняет эту адаптивность. В ландшафте и на устройствах с D-pad такой selector выглядит особенно тяжёлым: фокус проходит по устаревшим controls, а не по ясному меню.

## 2. Цели

1. Разделы диалога представлены как современная навигация по меню/вкладкам без radio-кружочков.
2. Пользователь сразу видит доступный для текущего файла набор разделов и активный раздел.
3. Для аудио остаются только применимые разделы: громкость и скорость, если других возможностей нет.
4. Для видео показываются применимые разделы: громкость, аудиодорожки, субтитры, стерео/3D при наличии контекста, HUE, яркость, скорость.
5. В портрете разделы доступны с крупными touch targets и не отнимают критичную ширину у controls.
6. В ландшафте разделы доступны как постоянное боковое меню или эквивалентный rail, чтобы D-pad переходил между меню и содержимым предсказуемо.
7. D-pad/джойстик, клавиатура, мышь и touch получают один и тот же порядок навигации: меню разделов, содержимое активного раздела, закрытие.
8. Последний выбранный раздел запоминается семантически, а не по позиции в списке; если раздел недоступен для нового файла, выбирается безопасный первый раздел.

**Non-goals:**

- Не меняется логика воспроизведения, выбор дорожек, субтитров, HUE, яркости, скорости или стереорежима.
- Не добавляются новые playback-настройки сверх уже существующих разделов.
- Не переносится диалог в глобальные настройки приложения.
- Не затрагивается Wear OS.
- Не вводится флейвор-специфичная логика через новые проверки сборочных флагов в общем коде.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Убрать выбор разделов через radio-кружочки.
2. Сделать навигацию похожей на понятное меню настроек, а не на форму выбора одного значения.
3. Сохранить динамический состав разделов для аудио, видео и стереоконтента.
4. Обеспечить удобство в портретной и ландшафтной ориентации.
5. Обеспечить удобство для пальца и джойстика/D-pad.

### 3.2 Жёсткие ограничения

- **Flavor:** все варианты сборки, где доступен плоский плеер с диалогом управления. Для VR/noLegal соблюдать флейвор-изоляцию; не добавлять новые `BuildConfig.SUPPORT_*`-проверки в общий код.
- **API level:** без API-специфики; UI должен работать на минимальных уровнях проекта, включая legacy-ветку API 23+.
- **Wear OS:** не затрагивается.
- **Производительность:** перестройка меню не должна создавать задержку при открытии диалога; состав разделов вычисляется из уже доступного состояния плеера.
- **Совместимость данных:** существующие сохранённые значения настроек воспроизведения сохраняются; формат хранения последнего раздела может быть безопасно расширен с fallback на первый доступный раздел.
- **Локализация:** EN/RU/UK - обязательно для новых или изменённых labels, state descriptions, tooltips/help text.
- **Доступность:** каждый пункт меню имеет текстовое имя, выбранное состояние, touch target не меньше 48 dp, фокусируемость для keyboard/D-pad, `Enter`/`Space` для выбора и TalkBack-описание выбранности.
- **Communication policy:** все новые или изменённые пользовательские строки проходят `docs/COMMUNICATION_POLICY.md` и тон-чеклист §6 перед интеграцией.

### 3.3 Owner inputs (Approval gate)

- **UI placement contract:** portrait uses a top segmented/tab menu without radio controls; landscape uses a left menu/rail with the same section order.
- **Visibility contract:** hide sections that are irrelevant to the current media type; show empty states inside relevant sections when tracks/subtitles are unavailable.
- **Input contract:** touch, keyboard, D-pad/joystick and mouse are in scope.
- **Accessibility:** menu items are text-labelled, expose selected state and use the same focus order as analogous player controls.
- **Localization:** EN/RU/UK for any new or changed user-facing string.
- **Validation level:** layout/content check plus `standardDebug` build; manual device check for portrait, landscape and D-pad focus traversal before leaving `BlockNeedUserTest`.
- **Owner sign-off:** 2026-06-02 - implementation requested for S0330.
- **Related tickets:** none.

## 4. Контекст текущей архитектуры

Диалог управления воспроизведением открывается из плеера только для аудио и видео. Он читает текущее состояние плеера, собирает активный список разделов и показывает одну секцию содержимого за раз. Для аудио список разделов уже сокращён до базовых controls; для видео список шире и дополнительно зависит от стерео/VR-контекста.

Проблема находится не в слоях воспроизведения, а в роли навигации внутри диалога. Текущая модель смешивает две разные семантики: radio-кнопки означают выбор значения, но используются как страницы меню. Поэтому даже корректный динамический список разделов выглядит как устаревшая форма и плохо читается при управлении с пульта.

---

## 5. Предлагаемый подход

Заменить radio-навигацию разделов на адаптивную модель меню. Разделы остаются теми же логическими страницами, но получают визуальную и доступностную семантику navigation item: label, optional icon, selected state, focus state, activation by click/Enter/Space. Содержимое выбранного раздела не меняет свою бизнес-логику; меняется способ перехода между разделами и сохранение текущего раздела.

### 5.1 Основные столпы / модули

**Столп A - Семантическая модель разделов.** Каждый раздел описывается стабильным идентификатором, пользовательским label, optional icon, accessibility label, visibility predicate и порядком. Последний выбранный раздел сохраняется по идентификатору, а не по индексу.

**Столп B - Адаптивная навигация.** В портрете навигация занимает верх диалога как scrollable tabs или segmented menu strip с крупными пунктами. В ландшафте и на широких экранах навигация занимает левую колонку как menu/rail, а содержимое находится справа. Оба варианта используют один и тот же порядок разделов и один источник доступности.

**Столп C - Управление фокусом.** Начальный фокус ставится на выбранный пункт меню или на первый активный control внутри выбранного раздела по единому правилу. D-pad перемещает фокус внутри меню, затем в содержимое, затем к закрытию; `Back` закрывает диалог или возвращает фокус из содержимого в меню, если это будет утверждено на тактическом уровне.

**Столп D - Скрытие неприменимых разделов.** Неприменимые для текущего файла разделы не занимают место в меню. Если раздел применим, но данных нет, внутри него остаётся явное empty state: например, нет аудиодорожек или субтитров.

**Столп E - Паритет ориентаций.** Портретная и ландшафтная разметка развиваются синхронно. Любое изменение навигации проверяет оба варианта, чтобы не появилось «новое меню» только в одной ориентации.

### 5.2 Потоки данных и событий

- Открытие диалога: текущее состояние плеера определяет доступные разделы.
- Список разделов фильтруется по текущему типу контента и стерео/VR-контексту.
- Восстановление последнего раздела ищет сохранённый идентификатор среди доступных разделов.
- Если сохранённый раздел недоступен, выбирается первый безопасный раздел, предпочтительно громкость.
- Пользователь выбирает пункт меню touch/click/D-pad/keyboard.
- Диалог показывает соответствующую секцию и сохраняет выбранный идентификатор.
- Если состояние плеера меняется и активный раздел исчезает, фокус переводится на ближайший доступный раздел без креша и без пустой панели.

### 5.3 Точки расширяемости

- Список разделов должен позволять добавить будущие страницы вроде sleep timer или дополнительных diagnostics без переписывания навигации.
- Видимость стерео/VR-раздела должна использовать существующую модель доступности контента; новые флейвор-гейты в общем коде не допускаются.
- Компонент навигации должен быть отделён от содержимого разделов, чтобы можно было поменять portrait-presentation без изменения логики controls.

## 6. Открытые вопросы / Research items

1. **Паттерн портретной навигации**
   - **Вопрос:** портрет должен использовать scrollable tabs/segmented strip сверху или полноценный список-меню перед содержимым?
   - **Варианты:** верхняя вкладочная полоса; раскрываемый selector с меню; вертикальный список с последующим содержимым.
   - **Нужно выяснить:** что лучше помещается на 360 dp ширине и быстрее управляется D-pad.
   - **Статус:** Resolved - верхняя segmented/tab-навигация без radio.

2. **Паттерн ландшафтной навигации**
   - **Вопрос:** ландшафт должен использовать левый navigation rail/menu или top tab strip?
   - **Варианты:** left rail с icon+label; compact text-only rail; top tabs как в портрете.
   - **Нужно выяснить:** какой вариант меньше конфликтует с длинными labels EN/RU/UK и не сжимает sliders.
   - **Статус:** Resolved - левый rail/menu.

3. **Icon+label или text-only**
   - **Вопрос:** нужны ли иконки у разделов?
   - **Варианты:** icon+label для всех разделов; text-only rows; icons only в узком rail с TalkBack label.
   - **Нужно выяснить:** доступность и визуальная ясность на TV/head-unit.
   - **Статус:** Resolved - text label обязателен; icons optional, только если не мешают ширине.

4. **Неприменимые разделы**
   - **Вопрос:** неприменимые разделы скрывать или показывать disabled?
   - **Варианты:** скрывать полностью; disabled с пояснением; группировать в overflow.
   - **Нужно выяснить:** что понятнее для динамического состава аудио/видео/стерео.
   - **Статус:** Resolved - скрывать неприменимые разделы, empty state оставлять только внутри применимого раздела.

5. **Кнопка закрытия**
   - **Вопрос:** оставить `Done` в title row или заменить close icon action?
   - **Варианты:** оставить `Done`; icon close с tooltip/contentDescription; оба варианта по ширине экрана.
   - **Нужно выяснить:** совместимость с текущими ожиданиями touch-пользователей и D-pad focus order.
   - **Статус:** Resolved - оставить `Done`.

## 9. Архитектурные решения (ADR)

**ADR-1: Навигация по разделам - menu/tabs, не radio group**

- **Решение:** разделы диалога получают семантику navigation item, а не mutually exclusive form value.
- **Альтернативы:** оставить radio-кнопки и изменить только внешний стиль; заменить на dropdown.
- **Почему:** radio-кнопки сообщают «выбери значение», а пользователю нужно «перейди в раздел настроек».

**ADR-2: Ориентационно-адаптивная навигация**

- **Решение:** портрет использует верхнюю compact-навигацию, ландшафт и wide-screen - боковое меню/rail.
- **Альтернативы:** один top strip для всех ориентаций; один left rail для всех ориентаций.
- **Почему:** портрету нужна ширина под controls, ландшафту нужна постоянная видимость разделов и удобный D-pad переход между меню и содержимым.

**ADR-3: Стабильный идентификатор раздела вместо индекса**

- **Решение:** последний раздел сохраняется по смысловому идентификатору.
- **Альтернативы:** продолжать хранить порядковый индекс.
- **Почему:** состав разделов меняется между аудио, видео и стереоконтентом; индекс может указывать на другой раздел.

**ADR-4: Hidden для неприменимых разделов, empty state для применимых пустых разделов**

- **Решение:** меню показывает только разделы, которые имеют смысл для текущего файла; пустые аудио/субтитры показываются внутри соответствующего раздела.
- **Альтернативы:** показывать disabled пункты для всех возможных разделов.
- **Почему:** динамическое меню должно быть коротким и не вводить в заблуждение нерабочими пунктами.

## 11. Критерии готовности (strategic-level)

1. В диалоге управления плеером нет radio-кружочков для перехода между разделами.
2. Пользователь видит ясное меню/вкладки разделов с активным состоянием.
3. Для аудиофайла меню содержит только применимые разделы вроде громкости и скорости.
4. Для видеофайла меню содержит применимые видеоразделы; стерео/3D появляется только при релевантном контексте.
5. В портрете меню не съедает критичную ширину controls и управляется touch без мелких targets.
6. В ландшафте меню остаётся понятным при D-pad/джойстик-навигации и не сжимает sliders до неудобного состояния.
7. `Enter`/`Space` выбирают focused menu item; D-pad traversal проходит меню и содержимое в логичном порядке.
8. Последний раздел восстанавливается по смыслу; при недоступности выбранного ранее раздела диалог открывает безопасный доступный раздел.
9. Empty states для аудиодорожек и субтитров остаются текстовыми и доступными для TalkBack.
10. Все новые/изменённые labels локализованы в EN/RU/UK и проходят строковый parity-check.
