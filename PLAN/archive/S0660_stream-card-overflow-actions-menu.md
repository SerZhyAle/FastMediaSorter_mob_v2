## 1. Проблема

Сейчас действия над конкретной трансляцией размазаны по разным жестам и точкам входа: нажатие по строке запускает воспроизведение, закрепление вынесено в отдельную кнопку, удаление живёт в long-press и частично дублируется в overflow-меню, а новые команды для канала не имеют единого места размещения. Это уже делает карточку менее предсказуемой, а с добавлением новых функций будет только усиливать фрагментацию.

После S0637 на карточке появился первый overflow с двумя пунктами, но он пока не стал полноценной командной поверхностью. Запрос владельца поднимает следующий уровень задачи: превратить меню `три точки` на карточке трансляции в каноническую точку для текущих и будущих действий по каналу, по аналогии с карточкой файла в браузере файлов.

---

## 2. Цели

1. Дать каждой карточке трансляции единое меню действий `три точки`, в котором собраны не-primary команды для канала.
2. Уменьшить зависимость от скрытых жестов и разрозненных affordance'ов при работе со списком трансляций.
3. Подготовить расширяемую поверхность для уже существующих и будущих stream-specific действий без повторного редизайна строки.
4. Явно определить, какие действия остаются прямыми на строке, а какие переезжают или дублируются в overflow.
5. В первой итерации как минимум покрыть уже существующий сценарий домашнего экрана и сформировать продуктовую рамку для удаления, редактирования и отправки ссылки.

**Non-goals:**

- Перенос основного запуска трансляции под overflow-меню.
- Полный редизайн экрана Трансляции или замена списка карточек другим представлением.
- Новая модель воспроизведения, импорта каталога или сетевой диагностики.
- Глубокий редизайн player-side меню `Отправить в..` вне той части, которая может быть переиспользована для ссылки на трансляцию.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. На карточках Трансляций должна появиться кнопка `три точки` по аналогии с карточкой файла в браузере файлов.
2. Меню должно стать местом, куда помещаются как уже реализованные, так и новые команды по каналу.
3. В числе ожидаемых действий владелец прямо назвал удаление, редакцию и сценарий `отправить в..` как ссылку.
4. Команда создания ярлыка на рабочем столе для трансляции должна быть доступна из этого меню; владелец отдельно уточнил ожидание формата `ярлык-виджет`.

### 3.2 Жёсткие ограничения

- **Flavor:** только там, где сама фича Трансляции уже доступна пользователю; по текущему capability-gate это standard, legacy, noLegal и VR. lite и photos вне объёма, потому что экрана Трансляции там нет.
- **API level:** для самого overflow-меню - без API-специфики; если первая итерация сохраняет действие домашнего экрана через pinned shortcut, остаётся ограничение Android 8.0+ для полноценного программного закрепления и деградация ниже API 26.
- **Wear OS:** не затрагивается.
- **Производительность:** открытие меню и выполнение действий по карточке не должны требовать тяжёлой фоновой подготовки или перестройки всего списка.
- **Совместимость данных:** существующие ручные, импортированные и каталоговые каналы продолжают работать как раньше; расширение action surface не должно ломать воспроизведение, pin-to-top и already pinned shortcut flows.
- **Локализация:** EN/RU/UK обязательно для новых пунктов меню, сообщений и content description.
- **Доступность:** меню и все его пункты должны корректно работать с TalkBack, D-pad/TV и мышью; нельзя завязывать понимание действий только на иконки или цвет.

### 3.3 Owner inputs (Approval gate)

Состав первой итерации overflow-меню и трактовка `ярлык-виджет` подтверждены владельцем (см. Quiz decisions ниже).

- **Состав первой итерации:** расширенный набор - `На домашний экран` (есть) + `Удалить` (есть) + `Редактировать` (новое) + `Отправить ссылку` (новое).
- **Трактовка `ярлык-виджет`:** закреплённый ярлык (pinned shortcut из S0637) считается финальной трактовкой; отдельный app widget не требуется.
- **Scope редактирования:** только каналы `sourceOrigin = MANUAL`; imported и catalog не редактируются.
- **`Отправить ссылку`:** обычный Android sharesheet с URL канала (share raw URL).
- **Дубли affordance'ов:** long-press удаление и отдельная pin-кнопка сохраняются как переходные дубли, пока overflow растёт.
- **Related tickets:** S0565, S0568, S0637, S0664

## 4. Контекст текущей архитектуры

Подсистема Трансляции уже выделена как отдельная capability со своим экраном списка каналов, быстрым запуском воспроизведения из строки, закреплением каналов наверх и отдельными stream-specific улучшениями последних тикетов. Карточка канала уже несёт несколько видов поведения: primary tap для запуска, отдельный pin affordance, long-press для удаления и недавно добавленное overflow-меню, появившееся ради действия `На домашний экран`.

То есть технический паттерн командного меню на строке уже начат, но продуктовая модель ещё не доведена до целостности. Часть действий остаётся скрытой в жестах, часть - вынесенной в отдельные кнопки, а часть пока только заявлена владельцем. Без отдельной стратегической фиксации есть риск дальше расширять карточку точечно и получить непоследовательный UX: одно действие в long-press, второе в меню, третье в плеере, четвёртое вообще отсутствует на уровне списка.

## 5. Предлагаемый подход

Сделать overflow-меню канала канонической точкой для вторичных действий по трансляции. Основное нажатие по карточке остаётся быстрым запуском воспроизведения, а `три точки` становятся входом в набор операций над самим каналом: домашний экран, удаление, редактирование, отправка ссылки и дальнейшие stream-specific команды по мере необходимости.

Первая итерация не обязана сразу перенести в меню все существующие affordance'ы. Важнее зафиксировать принцип: пользователь знает, что все команды "что сделать с этим каналом, кроме немедленного проигрывания" живут в одном predictable месте. Для отдельных high-frequency действий допустимо временное дублирование на переходный период, если это снижает риск регрессии и не ломает уже освоенные привычки.

### 5.1 Основные столпы / модули

- **Каноническая поверхность действий карточки.** Overflow становится стандартным контейнером для вторичных команд по каналу.
- **Состав меню по capability и типу источника.** Пункты меню формируются по тому, какие действия реально доступны для данного канала: домашний экран, редактирование, удаление, ссылка/отправка.
- **Переиспользование уже существующих сценариев.** Если действие уже существует в другом месте фичи, меню не изобретает новый UX, а открывает тот же сценарий из карточки.
- **Эволюция без раздутия строки.** Новые команды добавляются через меню, а не через бесконечное наращивание иконок на самой строке.

### 5.2 Потоки данных и событий

- **Воспроизведение:** пользователь нажимает на строку трансляции → запускается текущий поток воспроизведения без захода в меню.
- **Командное действие:** пользователь открывает `три точки` → видит набор доступных команд по каналу → выбирает действие → запускается соответствующий существующий или новый flow.
- **Ссылка / домашний экран:** меню карточки инициирует перенос идентичности канала наружу - как home-screen entry или как отправку ссылки - без ручного копирования URL из деталей.

### 5.3 Точки расширяемости

- Возможность позже добавлять channel-specific actions без нового редизайна строки.
- Разные наборы пунктов для ручных, импортированных и каталоговых каналов.
- Плавная миграция скрытых жестов в явное меню, если владелец захочет сделать UX более discoverable.
- Возможность разделить `ярлык`, `виджет` и `поделиться ссылкой` на разные варианты внешнего размещения канала.

## 6. Открытые вопросы / Research items

1. **Какой точный набор команд входит в первую итерацию меню**
   - **Вопрос:** ограничиваемся уже существующим `На домашний экран` + `Удалить`, или сразу добавляем редактирование и отправку ссылки.
   - **Варианты:** минимальный набор / расширенный набор / staged rollout.
   - **Нужно выяснить:** product-priority первой итерации.
   - **Статус:** Resolved - расширенный набор: домашний экран + удаление + редактирование + отправка ссылки в первой итерации.

2. **Что делать с дублированием существующих affordance'ов**
   - **Вопрос:** должны ли long-press удаление и отдельная pin-кнопка сохраниться, если их аналоги появятся или уже есть в overflow.
   - **Варианты:** оставить как есть; временно дублировать; постепенно свернуть прямые affordance'ы в пользу меню.
   - **Нужно выяснить:** допустим ли переходный период с дублями.
   - **Статус:** Resolved - временно дублировать: long-press удаление и pin-кнопка сохраняются как переходные дубли.

3. **Что владелец имеет в виду под `ярлык-виджет`**
   - **Вопрос:** достаточно текущего pinned shortcut-сценария домашнего экрана, или нужен настоящий app widget-variant для конкретной трансляции.
   - **Варианты:** закреплённый ярлык; конфигурируемый виджет; оба механизма.
   - **Нужно выяснить:** считать ли уже реализованное действие из S0637 финальной трактовкой требования, или оно лишь промежуточное.
   - **Статус:** Resolved - закреплённый ярлык (S0637) финальная трактовка; отдельный app widget не требуется.

4. **Какие каналы можно редактировать**
   - **Вопрос:** редактирование относится только к вручную добавленным каналам, или распространяется и на импортированные/каталоговые записи.
   - **Варианты:** manual-only; manual+imported; все источники с ограничениями.
   - **Нужно выяснить:** product contract редактирования без конфликтов с каталоговыми обновлениями.
   - **Статус:** Resolved - manual-only: редактируются только `sourceOrigin = MANUAL`, imported/catalog исключены.

5. **Как трактовать `отправить в.. как ссылка`**
   - **Вопрос:** это обычный Android sharesheet с URL, внутренняя команда `Отправить в` по аналогии с проигрыванием, или отдельный channel-link flow.
   - **Варианты:** share raw URL; share deep link; reuse send-to semantics from playback.
   - **Нужно выяснить:** какой пользовательский сценарий должен быть главным.
   - **Статус:** Resolved - share raw URL: обычный Android sharesheet с URL канала.

## 9. Архитектурные решения (ADR)

**ADR-1: Overflow-меню - каноническая поверхность вторичных действий**

- **Решение:** все не-primary команды по каналу должны стремиться в `три точки`, а не расползаться по отдельным иконкам и скрытым жестам.
- **Альтернативы:** продолжать добавлять отдельные affordance'ы на строку или хранить часть команд только в long-press.
- **Почему:** это делает поведение карточки discoverable и масштабируемым.

**ADR-2: Primary playback tap остаётся прямым**

- **Решение:** запуск трансляции остаётся на обычном нажатии по строке и не уходит под меню.
- **Альтернативы:** превращать карточку в чистый контейнер команд или требовать два шага для запуска.
- **Почему:** воспроизведение - главный сценарий экрана, он должен оставаться самым быстрым действием.

## 11. Критерии готовности (strategic-level)

1. На каждой карточке трансляции есть понятное меню `три точки`, где пользователь ищет вторичные действия по каналу.
2. Меню покрывает как минимум домашний экран и удаление, а состав первой итерации явно зафиксирован и не зависит от догадок разработчика.
3. Пользователь может понять, какие действия над каналом доступны, без знания скрытого long-press поведения.
4. Основной запуск трансляции остаётся быстрым и не усложняется дополнительными шагами.
5. Разница между `ярлык`, `виджет` и `ссылка` для трансляции определена на продуктном уровне и отражена в меню без двусмысленности.
6. Поведение меню согласовано для touch, D-pad/TV, мыши и TalkBack.
7. Добавление новых channel-specific действий в следующих итерациях не требует нового редизайна строки.
