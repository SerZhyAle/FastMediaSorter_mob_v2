## 1. Проблема

В плеере уже есть команды отправки файла (системный Share, Telegram, Google Keep для текста), но нет прямой команды «отправить текущий файл на Email». Пользователь, которому нужно письмо с вложением, вынужден проходить через общий системный chooser и вручную искать почтовый клиент. Фундамент S0452 даёт реестр share-таргетов и сквозной seam гейтинга, но email-таргет в нём не зарегистрирован, поэтому ни тумблера в настройках, ни команды в меню сейчас нет. Область - слой шаринга в плеере и настройки профиля.

---

## 2. Цели

1. В сворачиваемой группе «Команды отправить файл в..» (страница «Плеер») появляется тумблер «Разрешить отправку в Email», по умолчанию включённый для профилей с предполагаемым интернетом.
2. При включённом тумблере во всех меню плеера, где уже есть Share/Keep, появляется команда «Отправить в Email».
3. Команда открывает компоновщик письма почтового клиента с текущим файлом, прикреплённым как вложение.
4. Email-таргет регистрируется тонкой декларацией поверх фундамента S0452, без правки общего каркаса реестра/резолвера/настроек.

**Non-goals:**

- Предзаполнение адресата, темы или тела письма - письмо открывается пустым, пользователь заполняет его сам.
- Прямая отправка через SMTP/аккаунт без участия почтового приложения - отправку всегда выполняет внешний клиент.
- Команда Email в просмотре (browse) или иных поверхностях вне плеера - этот тикет про меню плеера (захваченный текст: «уже есть SHARE или Google KEEP», т.е. поверхности плеера).
- Множественное вложение / отправка пачки файлов - только текущий файл.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Email-команда должна появляться «везде, где это полезно» - в тех меню плеера, где уже есть Share или Google Keep.
2. Дефолт «включено» рассчитан на профили с предполагаемым интернетом.

### 3.2 Жёсткие ограничения

- **Flavor:** все варианты сборки (email-команда полезна везде; общий код, без flavor-специфики).
- **API level:** без API-специфики; видимость почтового приложения через chooser работает на всех поддерживаемых уровнях.
- **Wear OS:** не затрагивается.
- **Производительность:** проверка доступности таргета не должна блокировать UI меню; для сетевого файла подготовка вложения - вне главного потока (как у Share).
- **Совместимость данных:** новый флаг хранится в app-global DataStore (`AppSettings`), schema-bump Room нет; «миграция» = дефолт флага для существующих установок (каркас S0452).
- **Локализация:** EN/RU/UK - всегда обязательно.
- **Доступность:** недоступный таргет показывается как disabled с не-цветовым отличием (механизм группы S0452); команда меню фокусируема с D-pad/клавиатуры наравне с остальными.

## 4. Контекст текущей архитектуры

Отправка файла в плеере уже централизована: есть общий системный инвокер отправки, путь подготовки сетевого файла (скачать/закэшировать перед шарингом) и менеджер шаринга плеера, через который проходят Share, Telegram и Google Lens. Команды плеера описаны единым перечнем с приоритетами и местом показа (бар или overflow), а доступность Telegram/Keep сейчас проверяется ad-hoc прямо в обновляющем доступность компоненте панели команд. Фундамент S0452 поверх этого ввёл реестр share-таргетов, хранилище per-profile флагов в app-global DataStore, единый предикат доступности и use-case эффективного состояния флага; группа настроек строится из реестра автоматически.

Email отдельной командой пока нет: единственный путь к письму - общий системный chooser, где почтовый клиент теряется среди прочих обработчиков. Зарегистрировать email как таргет реестра нельзя «само по себе» - по решению владельца S0452 проводку гейта видимости команды в конкретные меню делает таргет-тикет, а действия отправки именно письмом (с вложением) в проекте ещё нет.

---

## 5. Предлагаемый подход

Email становится первым реальным таргетом в реестре share-команд S0452. Он добавляется как одна декларация в multibinding-набор таргетов: стабильный идентификатор, заголовок-строка, дефолт «включён при наличии интернета», правило доступности «доступен всегда» (почтовый компоновщик через системный chooser резолвим практически везде, интернет нужен для самой отправки, а не для открытия письма). Из этой декларации фундамент сам строит тумблер в группе настроек - отдельной UI-работы по настройкам тикет не несёт.

Действие отправки прикрепляет текущий файл к письму через системное действие отправки одного файла с MIME почтового типа, проходя через тот же путь подготовки сетевых файлов и выдачи URI-прав, что уже используется для Share/Telegram. Видимость команды в меню плеера решается единым seam'ом фундамента: команда показывается тогда и только тогда, когда флаг таргета включён И таргет доступен. Эту проверку тикет вплетает в существующий путь построения команд панели (решение владельца S0452: проводку гейта в свои поверхности делает таргет-тикет).

### 5.1 Основные столпы / модули

- Декларация email-таргета в наборе таргетов реестра (идентификатор, дефолт, доступность, заголовок).
- Действие отправки: прикрепление текущего файла к письму через системный компоновщик.
- Проводка гейта видимости email-команды в меню плеера через seam «флаг И доступность».

### 5.2 Потоки данных и событий

- Настройки: реестр → построитель группы → тумблер Email → запись флага профиля (каркас S0452, без нового кода).
- Меню плеера: построение активных команд → запрос «флаг Email включён И таргет доступен» → показ/скрытие команды Email → действие отправки (подготовка файла → системный компоновщик письма).

### 5.3 Точки расширяемости

- Заголовок и дефолт email-таргета меняются правкой одной декларации.
- Если позже понадобится предпочитать конкретный почтовый клиент, это добавляется в действие отправки и при необходимости в видимость пакетов манифеста, без затрагивания фундамента.

## 6. Открытые вопросы / Research items

- Resolved - действие отправки: `ACTION_SEND` с MIME `message/rfc822` (а не `ACTION_SENDTO` `mailto:`). `ACTION_SENDTO` с `mailto:` фильтрует chooser до почтовых клиентов, но не несёт вложение надёжно - почтовые приложения (в т.ч. Gmail) часто теряют `EXTRA_STREAM` при `ACTION_SENDTO`. Поскольку цель тикета - письмо именно с вложением, выбран `ACTION_SEND`/`message/rfc822` + `EXTRA_STREAM` + `ClipData` + `FLAG_GRANT_READ_URI_PERMISSION`. Это совпадает с уже существующим путём отправки файла (Share/Telegram), так что переиспользуется существующий инвокер.
- Resolved - доступность таргета: `ALWAYS`. Компоновщик письма открывается через системный chooser и резолвится практически на любом устройстве; интернет нужен для самой отправки письма, а не для его составления, поэтому привязывать видимость команды к интернету избыточно. Дефолт флага при этом - `ON_IF_INTERNET` (на устройствах без предполагаемого интернета тумблер по умолчанию выключен, но остаётся доступным).
- Resolved - видимость пакетов манифеста (`<queries>`): при `ALWAYS`-доступности и запуске через системный chooser проба пакета не выполняется, поэтому запись `<queries>` для email не требуется. Запись `<intent>`-фильтра под `ACTION_SEND`+`message/rfc822` понадобится только если действие отправки решит предварительно резолвить/предпочитать конкретный почтовый клиент (`resolveActivity`/`getPackageInfo`) - это решается на этапе имплементации действия отправки.
- Open - иконка команды Email: выделенной иконки `ic_*mail*`/`ic_*email*` в ресурсах нет. По образцу Telegram/Keep-overflow команда может переиспользовать общую иконку шаринга, либо тикет добавляет новую vector-иконку конверта. Решение - тактическая деталь шага действия/меню.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| `ACTION_SEND`/`message/rfc822` поднимает не только почтовые приложения, но и иные обработчики | Низкая | Пользователь видит в chooser лишние варианты | Это поведение Android для писем с вложением; chooser остаётся универсальным, а ограничение до почтовых клиентов несовместимо с надёжным вложением (см. §6) |
| Email-команда добавляется в горячий путь построения команд панели | Средняя | Регрессия видимости/раскладки других команд | Следовать существующему образцу Telegram/Keep-overflow (overflow-only, гейт-флаг), не трогать раскладочный планировщик |

## 9. Архитектурные решения (ADR)

- ADR-1 - Интент отправки: `ACTION_SEND` с MIME `message/rfc822`, а не `ACTION_SENDTO` `mailto:`. Причина: `ACTION_SENDTO` не несёт вложение надёжно (почтовые клиенты теряют `EXTRA_STREAM`), а вложение - суть тикета. Следствие: переиспользуется существующий путь отправки файла (chooser + ClipData + URI-grant), а не вводится отдельный mailto-путь.
- ADR-2 - Доступность `ALWAYS` при дефолте `ON_IF_INTERNET`. Причина: компоновщик письма открывается без интернета, поэтому скрывать команду оффлайн незачем; «по умолчанию для профилей с интернетом» из захваченного материала кодируется дефолтом флага, а не правилом видимости.

## 11. Критерии готовности (strategic-level)

1. На странице «Плеер» в группе «Команды отправить файл в..» есть тумблер «Разрешить отправку в Email».
2. На профиле с предполагаемым интернетом тумблер по умолчанию включён; на профиле без него - по умолчанию выключен, но переключаем.
3. При включённом тумблере в меню плеера (там, где есть Share/Keep) видна команда «Отправить в Email»; при выключенном - команды нет.
4. Выбор команды открывает компоновщик письма с текущим файлом, прикреплённым как вложение.
5. Для сетевого файла перед отправкой выполняется та же подготовка/кэширование, что и для обычного Share (письмо открывается с локально доступным вложением).
6. Заголовок команды и тумблера локализован на EN/RU/UK.
