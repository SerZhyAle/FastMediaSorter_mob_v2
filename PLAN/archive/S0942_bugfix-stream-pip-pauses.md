# Стратегическая спецификация: S0942 - Трансляция ставится на паузу при входе в Picture-in-Picture

**Ticket:** S0942
**Status:** Archived
**Priority:** 90
**Date:** 2026-07-04
**Tier:** 2 - Easy (ad-hoc)
**Roadmap entry:** Ad-hoc - запрос владельца 2026-07-04
**Tactical spec:** `PLAN/S0942_bugfix-stream-pip-pauses/` (будет создан через `/spec-tech`)

---

## 1. Проблема

Когда трансляция (сетевой стрим) сворачивается в режим «картинка в картинке» (PiP), воспроизведение останавливается: окошко PiP показывает застывший кадр, и чтобы продолжить, пользователю приходится вручную нажимать паузу/плей в PiP-окне. Ожидаемое поведение - стрим продолжает играть при входе в PiP без ручного вмешательства. Локальное видео при этом (по наблюдению владельца) в PiP не встаёт на паузу, поэтому проблема воспринимается как специфичная для трансляций.

---

## 2. Цели

1. При входе в PiP трансляция продолжает воспроизводиться без паузы.
2. Не требуется ручное нажатие паузы/плей в PiP-окне для возобновления.
3. Кнопка play/pause в PiP-окне остаётся рабочей и корректно отражает актуальное состояние (играет/пауза).
4. Поведение трансляции в PiP совпадает с уже корректным поведением локального видео.

**Non-goals:**

- Изменение поведения PiP для локальных видеофайлов, которое сейчас корректно.
- Добавление PiP для аудио-трансляций (радио) - у аудио нет визуального содержимого для PiP.
- Переработка набора PiP-действий или их иконок.
- Изменение условий авто-входа в PiP (по кнопке home / по кнопке PiP).

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Разобраться, почему пауза возникает именно на трансляциях, и закрыть корневую причину, а не маскировать симптом.
2. Проверить весь класс воспроизведения через PiP (обычный плеер, отдельные видеоплееры), чтобы фикс не оставил другой хост в том же дефекте.

### 3.2 Жёсткие ограничения

- **Flavor:** затрагиваются варианты сборки, где доступна возможность трансляций (Streams) и видео-PiP. Дефект и правка - в общем слое жизненного цикла плеера (`src/main`), флейвор-специфичного поведения и отдельных source-set'ов не требуется.
- **API level:** PiP поддерживается с Android 12+ (API 31+); правка в пределах этого диапазона, без регресса на устройствах ниже (где PiP просто отсутствует).
- **Wear OS:** не затрагивается.
- **Производительность:** без бюджета; правка не должна удерживать плеер/сеть активными, когда активность действительно уходит в фон (не PiP).
- **Совместимость данных:** миграций и персистентного состояния нет.
- **Локализация:** пользовательские строки не меняются; при появлении новых - EN/RU/UK обязательно.
- **Доступность:** PiP-действие play/pause остаётся операбельным (единственный элемент управления в PiP-окне для не-touch и touch).

### 3.3 Owner inputs (Approval gate)

- **API level constraints:** правка только в пути PiP (Android 12+/API 31+); на API ниже 31 PiP отсутствует, поведение не меняется.
- **UI placement contract:** раскладки и состав PiP-окна не меняются; правится поведение воспроизведения при переходе в PiP, а не расположение элементов. Скрытие/показ хрома в PiP остаётся как есть.
- **Accessibility:** PiP-кнопка play/pause сохраняет работоспособность и корректно отражает состояние после фикса.
- **Validation level:** обязательна проверка на устройстве (Android 12+): вход в PiP из активной трансляции (кнопкой PiP и кнопкой home) - стрим продолжает играть; регресс-проверка локального видео; сбор logcat для подтверждения корневой причины (§6.1).

## 4. Контекст текущей архитектуры

За PiP отвечает выделенный менеджер PiP поверх активности плеера, а сами трансляции воспроизводятся тем же слоем плеера, что и обычное видео (весь плейбек маршрутизируется в единую активность плеера). Активность плеера при уходе в фон гейтит остановку воспроизведения признаком «сейчас в PiP» - если активность переходит именно в PiP, штатная lifecycle-пауза пропускается. Обратный «разворот» временной lifecycle-паузы выполняется только при возврате активности в передний план, а в PiP этот путь возврата не срабатывает.

Проблему нельзя закрыть на уровне UI PiP-окна, потому что причина в согласовании жизненного цикла активности с состоянием плеера при переходе в PiP: где-то на пути входа в PiP для трансляции воспроизведение оказывается остановленным и не возобновляется автоматически. Почему это проявляется именно на трансляциях (а не на локальном видео) - ключевой вопрос, требующий подтверждения логами на устройстве (§6.1): вероятные факторы - порядок вызова lifecycle-колбэков при авто-входе в PiP, поведение аудиофокуса при сворачивании и специфика «живого края»/буферизации сетевого стрима.

---

## 5. Предлагаемый подход

Обеспечить инвариант: при переходе активности плеера в PiP воспроизведение трансляции сохраняется (или немедленно восстанавливается), а не остаётся на паузе до ручного действия. Сначала подтвердить корневую причину логами (§6.1), затем закрыть её так, чтобы инвариант держался единообразно для всех хостов воспроизведения через PiP, не ломая корректное поведение локального видео и штатную остановку при реальном уходе в фон (не PiP).

### 5.1 Основные столпы / модули

- **Согласование жизненного цикла с PiP.** Гарантировать, что вход в PiP не приводит к остаточной паузе воспроизведения: либо lifecycle-пауза не применяется при переходе в PiP, либо её разворот происходит и в PiP, а не только при возврате на передний план.
- **Единообразие по хостам воспроизведения.** Применить инвариант ко всем активностям, откуда доступен видео-PiP, чтобы фикс не оставил один из хостов в прежнем поведении.
- **Сохранение корректной фоновой остановки.** Не превратить фикс в «плеер никогда не паузится»: при действительном уходе в фон (не PiP) остановка/освобождение ресурсов остаётся как есть.

### 5.2 Потоки данных и событий

`Пользователь инициирует PiP (кнопка PiP / home) -> активность переходит в PiP -> согласование жизненного цикла: воспроизведение трансляции сохраняется/восстанавливается -> PiP-окно показывает живую картинку -> кнопка play/pause отражает актуальное состояние`. При реальном уходе в фон (не PiP) поток идёт по штатной остановке.

### 5.3 Точки расширяемости

- Инвариант «PiP не оставляет остаточную паузу» должен быть выражен в одном общем месте согласования жизненного цикла, чтобы новый хост воспроизведения наследовал корректное поведение без дублирования.
- Решение не должно завязываться на тип источника (локальный файл против сетевого стрима) сверх необходимого - целевой инвариант одинаков для обоих.

## 9. Архитектурные решения (ADR)

**ADR-1: Чинить инвариант согласования жизненного цикла, а не поведение PiP-окна**

- **Решение:** закрыть причину в слое согласования жизненного цикла активности с состоянием плеера при переходе в PiP, единообразно для всех хостов.
- **Альтернативы:** принудительно возобновлять воспроизведение из UI PiP-окна; трактовать стрим особым образом отдельной веткой.
- **Почему:** причина в жизненном цикле, а не в отрисовке PiP; точечная UI-заплатка оставила бы гонку и другие хосты незакрытыми.

## 11. Критерии готовности (strategic-level)

1. Вход в PiP из активной трансляции (кнопкой PiP) не ставит стрим на паузу - воспроизведение продолжается автоматически.
2. Вход в PiP по кнопке home из активной трансляции также не ставит стрим на паузу.
3. Кнопка play/pause в PiP-окне работает и корректно отражает актуальное состояние.
4. Локальное видео в PiP не регрессировало.
5. Поведение подтверждено на всех хостах видео-PiP, выявленных аудитом §6.2.
6. При действительном уходе в фон (не PiP) штатная остановка/освобождение ресурсов сохранены.

## 12. Корневая причина и правка (реализация)

**Корневая причина (подтверждена по коду; финальное подтверждение - logcat на устройстве).**

- `PlayerActivity` (хост live-стримов и локального видео) регистрирует `VideoPlayerManager` как отдельный `DefaultLifecycleObserver` на своём lifecycle.
- При входе в PiP активность переходит в состояние `PAUSED` -> lifecycle доставляет `ON_PAUSE` обсерверу -> `VideoPlayerLifecycleHelper.onPause()` вызывает `manager.pause()` **без PiP-гейта**. Обратный `ON_RESUME` в PiP не доставляется (активность не возвращается в `RESUMED`), поэтому воспроизведение остаётся на паузе до ручного play.
- PiP-гейт в `PlayerActivity.onPause()` (`if (isInPictureInPictureMode) return`) прикрывает только UI-паузу `viewModel.togglePause()`, но не обсервер плеера - отсюда остаточная пауза.
- Асимметрия «локальное видео не паузится»: standalone-хосты (`StandalonePlayerActivity`, `PhotoVideoStandaloneActivity`) паузят плеер из своего ручного `onPause()`, который уже гейчен по `isInPictureInPictureMode`; локальное видео обычно открывается там, поэтому не встаёт на паузу в PiP. Стримы идут через `PlayerActivity` с негейченным обсервером.

**Правка (ADR-1, единая точка согласования lifecycle).**

- `VideoPlayerLifecycleHelper.onPause()` пропускает `manager.pause()`, когда хост в PiP (`isInPictureInPictureMode`, API 24+). Гейт зеркалит уже применённый в standalone-хостах.
- `onStop()` не трогается: в PiP он не вызывается (активность видима); при реальном уходе в фон срабатывает и освобождает плеер - критерий 6 сохранён.
- Файл: `app_v2/src/main/java/com/sza/fastmediasorter/ui/player/VideoPlayerLifecycleHelper.kt`.

**Хосты видео-PiP (§6.2).**

- `PlayerActivity` - через `VideoPlayerManager` (правка закрывает).
- `StandalonePlayerActivity`, `PhotoVideoStandaloneActivity` - гейтят паузу в ручном `onPause()` (уже корректны).
