- `findViewById` - **421 обращение в 89 файлах**
- ViewBinding включён проектно (`viewBinding = true` в `app_v2/build.gradle.kts`) и используется в 225 файлах
- DataBinding не используется вообще: ни одного макета с корнем `<layout>` во всём `app_v2`

То есть доступ к элементам экрана формально одношкольный - ViewBinding без альтернатив, - но рядом живёт 421 ручное обращение по идентификатору. Часть из них законна: внутри самодельных View, в адаптерах списков и там, где разметка надувается динамически, ViewBinding не помогает или помогает хуже. Остальное - остаток старого стиля.

Почему это стоит тикета, а не разовой правки: `findViewById` возвращает результат без гарантии типа и без гарантии наличия, поэтому опечатка в идентификаторе или элемент, оставшийся только в портретной разметке, падают в момент показа экрана, а не при сборке. ViewBinding ловит ровно эти два случая на этапе компиляции, причём по каждому варианту разметки отдельно.

Замер воспроизводится:

```

grep -rl "findViewById" app_v2/src --include=*.kt | wc -l
grep -n "viewBinding\|dataBinding" app_v2/build.gradle.kts
```

Вопрос тикета: сколько из 421 обращения законны по существу, сколько механически заменяются, и стоит ли после зачистки поставить механический гейт, чтобы новые не заводились.

## 1. Проблема

Ресёрч 2026-08-21 (артефакт `research/01__call-site-classification.md`) переклассифицировал вопрос
§0. Сегодня 428 обращений `findViewById` в 92 файлах, и число растёт (+7 за шесть дней). Но ~78%
из них законны по построению: самодельные View, адаптеры, разметки, которые ViewBinding не видит
(контролы плеера через `?attr`, ViewStub, include без id), и задокументированные развязки
(S0380/S0410/S1549). Настоящий дефект-класс - смешанный стиль: файл держит живой binding, а к
элементу, у которого **уже есть** типизированное поле, тянется нетипизированным
`binding.root.findViewById` - таких ~20 вызовов в 7 файлах. Опечатка в идентификаторе или элемент,
живущий не во всех вариантах разметки, там падает при показе экрана, а не при компиляции. Плюс
рост: без механического гейта новые вызовы продолжают заводиться.

## 2. Цели

1. Ни один вызов `findViewById` не остаётся там, где у того же элемента уже есть типизированное
   поле binding: класс дефекта B из ресёрча вычищен, компилятор снова ловит опечатки id и
   расхождения вариантов разметки на этих экранах.
2. Общее число `findViewById` в продуктовых исходниках `app_v2` перестаёт расти: механический
   ratchet-гейт фиксирует базовую линию и проваливает закрытие при росте в изменённом файле.
3. Базовая линия может только снижаться - каждая конверсия по пути опускает её, как в остальных
   ratchet-гейтах проекта.

**Non-goals:**

- Массовая конверсия категории C (raw-inflate диалоги/фрагменты без binding, ~110-120 вызовов):
  уходит оппортунистически, когда другой тикет касается файла, - по той же модели, что
  Compose-острова (Rule 32). Кампания не заводится.
- Категория A не трогается вовсе: самодельные View, адаптеры, runtime-разметки и
  задокументированные развязки - законные вызовы, и гейт их не различает, он ловит только рост.
- `PlayerBindingSafeViews` не расщепляется: смешивает A и B внутри одного класса намеренно
  (S0217/S1549) и остаётся инфраструктурой как есть.
- Wear-модуль (Compose, XML нет) и тестовые source set-ы вне объёма.

## 4. Контекст текущей архитектуры

Доступ к View в `app_v2` идёт тремя путями: типизированный binding (большинство, 225 файлов);
host-нейтральные хелперы, которым View передаёт вызывающий, - часть по необходимости (runtime-
разметки), часть по задокументированному решению; и старый прямой поиск по id. Три существующих
count-ratchet гейта проекта (`scripts/quality/*-baseline.txt` + FATAL per-file delta против HEAD в
`-ScopeToFile`) - готовый механизм остановки роста, который лексика этого случая как раз позволяет:
рост считается точно, а вот законность конкретного вызова лексически не решается (задокументированная
развязка и просто неконвертированный код выглядят одинаково). Полная классификация - артефакт
`research/01__call-site-classification.md`.

## 5. Предлагаемый подход

### 5.1 Основные столпы / модули

**Зачистка класса B.** ~20 вызовов в 7 файлах, где типизированное поле уже сгенерировано
(include с id, корневой id включённой разметки), переводятся на binding-поля. Проверка -
компилятор: если поле не материализовалось, гипотеза для этого вызова неверна и вызов остаётся с
комментарием-причиной.

**Ratchet-гейт.** Новое измерение считает `findViewById` в продуктовых исходниках `app_v2`
(тестовые source set-ы исключены), сравнивает с базовой линией; рост в изменённом файле - FATAL в
закрытии, снижение обновляет линию вниз. Форма - как у существующих гейтов проекта; allowlist не
заводится (ресёрч показал, что он неизбежно рукописный и гниёт).

**Запись модели снятия долга.** Категория C уходит оппортунистически; правило записывается в
документ гейта/архитектуры, чтобы кампанию не заводили повторно.

### 5.2 Потоки данных и событий

Изменённый файл -> post-change -> измерение findviewbyid -> дельта против HEAD по файлу -> FATAL
при росте / обновление базовой линии при снижении. Ровно тот же поток, что у соседних ratchet-гейтов.

### 5.3 Точки расширяемости

Базовая линия и скрипт не привязаны к списку файлов - конверсия любого файла категории C в будущем
просто опускает число, без правки правила.

## 9. Архитектурные решения (ADR)

- **ADR-1 (2026-08-21): рост останавливается ratchet-ом, а не allowlist-ом.** Законность вызова
  лексически неразрешима (ресёрч, §6.2), поэтому правило «где можно» не пишется вовсе; пишется
  «больше не становится». Альтернатива - рукописный allowlist - отвергнута как гниющая.
- **ADR-2 (2026-08-21): категория C снимается оппортунистически, не кампанией.** Модель
  Compose-островов (Rule 32): каждый тикет, касающийся файла, опускает линию; отдельная кампания
  конверсии ~40 файлов не заводится - у неё нет пользовательского результата, оправдывающего риск.
