## 0. Захваченный материал (inbox)

**Захвачено:** 2026-08-18

**Источник:** исследование каталога логов в рамках S1805 (отчёты с часов копятся и не удаляются).

**Текст:**

Отчёт, пришедший с часов, сохраняется на телефоне файлом `watch_log_<метка времени>.txt` рядом с логами телефона. Но обе выгрузки логов - и «поделиться архивом», и «сохранить в файл» - собирают набор через `LoggingHelper.getLogFiles()`, а он отбирает файлы по имени: начинается на `fastmediasorter_` и заканчивается на `.log`. Имя `watch_log_*.txt` не подходит ни по началу, ни по концу, поэтому в архив такой файл не попадает никогда.

Единственный момент, когда отчёт часов оказывается в архиве, - это само уведомление о его приходе: там архив собирается с явной передачей только что записанного файла. Уведомление снято - и вернуться к отчёту через интерфейс приложения больше нельзя, файл остаётся лежать на диске без единого потребителя.

Проверено чтением исходников 2026-08-18: `LogExportHelper.buildLogsZip` и `LogExportHelper.writeZipToUri` берут набор из `getLogFiles()`, а `getLogFiles()` фильтрует по префиксу `fastmediasorter_` и расширению `.log`.

Почему не исправлено на месте: код правится в одну строку, но решение - продуктовое. Нужно ответить, входят ли отчёты часов в обычную выгрузку логов телефона всегда, или только по отдельному действию, и что происходит с размером архива, когда отчётов накопилось много.

## 1. Проблема

Отчёт с часов сохраняется в каталог логов и после этого недостижим.

- Пользователь нажимает «отправить логи» на часах. Телефон записывает файл и показывает уведомление, нажатие на которое собирает письмо с архивом - там отчёт есть, потому что приёмник передаёт свежий файл явным аргументом.
- Уведомление снято. Отчёт остаётся на диске, но обе кнопки выгрузки логов в настройках его не видят: они собирают набор по имени `fastmediasorter_*.log`, под которое `watch_log_*.txt` не подходит ни началом, ни концом.
- Итог: единственный шанс отправить отчёт - тот самый первый тап по уведомлению. Пропустил - и данные лежат в каталоге, который сам же пользователь выгружает кнопкой «сохранить логи», ничего о них не зная.

Это ровно та ситуация, когда файл записан «на всякий случай», а случая не наступает: писать его и не давать к нему доступа - хуже, чем не писать вовсе.

## 2. Цели

1. Обе выгрузки логов - «поделиться» и «сохранить в файл» - включают отчёты часов, лежащие в каталоге логов.
2. Отчёт, переданный явным аргументом (путь уведомления), не удваивается в архиве.
3. Форма имени отчёта записана один раз и в одном месте: и уборка, и отбор для выгрузки читают одни и те же константы.

**Не входит в цели:** отдельная кнопка «выгрузить только логи часов»; просмотр отчёта на экране телефона; изменение правила хранения (это S1805, уже закрыт); отправка чего-либо без действия пользователя.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

Не выяснялись: ответ следует из уже принятого решения, см. §3.3 и ADR-1.

### 3.2 Жёсткие ограничения

1. Выгрузка логов - действие пользователя над своими данными: включение отчётов часов не должно молча раздуть архив.
2. Отбор файлов по имени - единственный механизм, разделяющий два вида логов в одном каталоге; он обязан остаться явным.
3. Архив не должен содержать двух записей с одним именем: путь уведомления передаёт свежий файл аргументом, и после этой правки тот же файл найдётся и обходом каталога.

### 3.3 Owner inputs (Approval gate)

- **Входят ли отчёты часов в обычную выгрузку логов:** да, всегда - обе кнопки. Решение не выбирается здесь: приёмник S1802 уже кладёт отчёт в каталог логов «рядом с набором телефона» и уже собирает архив из обоих видов файлов в пути уведомления. См. ADR-1.
- **Что с размером архива:** ограничение уже есть и введено соседним тикетом. Отчётов хранится не больше пяти (S1805), каждый не больше 48 КБ (буфер журнала на часах), то есть предел добавки - около 240 КБ.
- **Отдельная кнопка только для логов часов:** n/a - два действия для одного архива заставляют пользователя выбирать между ними, ничего не зная о разнице.
- **Related tickets:** S1802 (создаёт файлы), S1805 (ограничил их число - это и делает включение безопасным по размеру).

## 4. Контекст текущей архитектуры

- `LoggingHelper.getLogFiles` - набор для обеих выгрузок; фильтр по префиксу `fastmediasorter_` и расширению `.log`. Возвращает пустой список, когда файловое дерево журналирования не поднято.
- `LoggingHelper.pruneLogFiles` (S1805) - уже умеет обходить каталог по префиксу и расширению; отбор можно взять оттуда, а не писать второй раз.
- `LogExportHelper.buildLogsZip` - принимает дополнительные файлы параметром; этим пользуется приёмник отчётов часов.
- `LogExportHelper.writeZipToUri` - дополнительных файлов не принимает вовсе.
- `WearLogReportReceiver` (`wearGms`) - владеет константами `WATCH_LOG_PREFIX`/`WATCH_LOG_SUFFIX`; для main-кода они сейчас недоступны.

## 5. Связи с другими спеками

- **S1802** (`wear-about-send-logs-email`) - создаёт эти файлы.
- **S1805** (`watch-log-files-never-pruned`) - ограничил их число пятью. Порядок важен именно в эту сторону: включать в архив неограниченный набор было бы неосторожно, а ограниченный - безопасно.

## 6. Открытые вопросы / Research items

1. **Resolved (2026-08-19).** Не раздует ли включение архив? - Нет. После S1805 отчётов не больше `MAX_LOG_FILES` (пять), а размер каждого ограничен буфером часов в 48 КБ (`WearLogBuffer.MAX_BYTES`, прочитано в исходниках). Верхняя добавка - около 240 КБ против пяти файлов телефона по 5 МБ.
2. **Resolved (2026-08-19).** Не появится ли дубликат в архиве? - Появился бы: путь уведомления передаёт свежий файл аргументом, и после правки тот же файл найдётся обходом каталога, а `ZipOutputStream` на второй записи с тем же именем бросает исключение. Поэтому набор объединяется с отбрасыванием повторов по пути файла - это требование, а не деталь реализации.
3. **Resolved (2026-08-19).** Где брать форму имени? - В `LoggingHelper`. Константы живут в `wearGms` и main-коду не видны, а нужны обоим; переносятся в `LoggingHelper` рядом с `pruneLogFiles`, который ими уже пользуется через аргументы.

## 7. Риски

1. **Дубликат имени в архиве.** Вероятность была бы высокой без §6.2 - путь уведомления сработал бы первым же приходом отчёта. Последствие - исключение вместо архива, то есть потеря всей выгрузки, а не одного файла. Снимается объединением с отбрасыванием повторов и проверяется тестом.
2. **Выгрузка «нет логов» перестаёт срабатывать.** Сегодня пустой набор логов телефона означает «нечего выгружать»; после правки один только отчёт часов уже делает выгрузку осмысленной. Это желаемое поведение, но его надо проверить явно - иначе кнопка откажет там, где данные есть.

## 8. FEATURES

Выгрузка логов теперь включает и отчёты, присланные с часов, - их больше не нужно ловить в момент прихода уведомления.

## 9. Архитектурные решения (ADR)

**ADR-1: включение в обычную выгрузку не выбирается, а доводится до конца.**

Решение «отчёт часов принадлежит архиву логов» уже принято и уже работает - в пути уведомления архив собирается из логов телефона и свежего отчёта вместе, а сам файл сохраняется, по формулировке комментария S1802, «рядом с набором телефона». Незакрытым остался только обход каталога: он ищет файлы по имени и про второе имя не знает. Поэтому здесь не вводится новая политика, а достраивается существующая.

**ADR-2: набор для выгрузки собирается в `LoggingHelper`, а не в `LogExportHelper`.**

Каталог логов и формы имён в нём - предмет `LoggingHelper`: там уже живут и правило хранения, и обход по префиксу. Если бы отбор отчётов делал экспорт, каталог описывался бы в двух местах, и следующий вид файла в нём снова попал бы только в одно из них.

## 10. Зависимости

S1805 закрыт и ограничил число отчётов - именно это делает включение безопасным по размеру. Блокирующих зависимостей нет.

## 11. Критерии приёмки

1. Отчёт часов, лежащий в каталоге логов, попадает в архив кнопки «поделиться логами» без всякого явного аргумента.
2. Он же попадает в архив кнопки «сохранить логи в файл».
3. Путь уведомления, передающий свежий отчёт аргументом, даёт архив без дубликата и без исключения.
4. Каталог, где нет логов телефона, но есть отчёт часов, выгружается, а не отвечает «логов нет».
5. Константы имени отчёта объявлены один раз и используются и уборкой, и отбором для выгрузки.

### Фаза 02 - Обе выгрузки берут этот набор

**Файлы:** `app_v2/src/main/java/com/sza/fastmediasorter/core/logging/LogExportHelper.kt`

**Prompt for developer:**

> Переведи оба сборщика архива на новый набор. Дополнительные файлы, переданные аргументом, объединяй с ним, отбрасывая повторы по пути файла. Условие «логов нет» считай по объединённому набору, а не по одним логам телефона.

**Why:**

Без отбрасывания повторов первый же приход отчёта дал бы две записи с одним именем и исключение вместо архива (§6.2, риск 1), а условие «нет логов» по старому набору отказывало бы там, где отчёт часов есть (риск 2).

**Verification:**

- `Grep` - оба сборщика читают новый набор, ни один не вызывает `getLogFiles` напрямую.
- `Grep` - объединение отбрасывает повторы по пути файла.
- `Grep` - проверка на пустоту идёт по объединённому набору.

**Status:** `[x]` done - оба сборщика читают `getExportableLogFiles(context)`; объединение с переданными аргументом файлами идёт через `distinctBy { absolutePath }`, и причина этого записана рядом: без него первый же приход отчёта дал бы вторую запись с тем же именем и исключение вместо архива.
