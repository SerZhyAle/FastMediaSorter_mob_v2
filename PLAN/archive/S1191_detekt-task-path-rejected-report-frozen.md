## 0. Захваченный материал (inbox)

**Захвачено:** 2026-07-25 (находка при прогоне `post-change.ps1` в рамках S1189 фазы 02)

**Симптом:** `assert-detekt.ps1` сообщает `NEW findings in changed file(s)` про строки, которых в файле уже нет.

**Доказательства, собранные на месте:**

1. Отчёты detekt не обновлялись с **24.07.2026 23:30:31** - ни `app_v2/build/reports/detekt/detekt.xml`, ни `detekt.txt`. За 25.07 гейт вызывался минимум четыре раза и ни разу не переписал их.
2. Настоящий вывод gradle (виден только после правки диагностики, см. п. 5):

```text
FAILURE: Build failed with an exception.

* What went wrong:
Cannot locate tasks that match ':'. The path should include a task name (for example ':help' or 'help').

BUILD FAILED in 1s
```

3. Сборка падает **до** записи отчёта, поэтому на диске остаётся снимок предыдущего дня.
4. Ветка сужения по `-ChangedFiles` этого не замечала: она читала старый `detekt.xml` и объявляла «новыми» находки вчерашнего прогона в файле, который просто оказался в обоих множествах. Для `CameraCapabilityProbe.kt` это были `MaximumLineLength` / `ArgumentListWrapping` на строках 99-100, уже устранённые в текущем файле.
5. Проверенная и **отвергнутая** гипотеза: dot-source `scripts/utils/agent-lock.ps1` (у него есть свой `param()`) сбрасывает `$PSBoundParameters` вызывающего скрипта. Пробник `temp/scratch/probe-psboundparams.ps1` показал, что `ContainsKey('Module')` остаётся `True` после всех трёх dot-source.

**Первопричина (найдена 2026-07-25).** Список задач собирался так:

```powershell
$tasks = if ($PSBoundParameters.ContainsKey('Module')) { @(":${Module}:detekt") } else { @(':app_v2:detekt', ':wear:detekt') }
```

Одноэлементный массив, возвращённый из `if`-выражения, PowerShell разворачивает в **скаляр-строку**. Дальше `& $gradlew @tasks` сплатит эту строку **по одному символу на аргумент**, поэтому gradle получал первым аргументом `:` - ровно то, на что и ругался. Диагностика нашлась мгновенно, как только был напечатан `$tasks.Count`: под `Set-StrictMode -Version Latest` обращение к `.Count` у строки само упало с «The property 'Count' cannot be found on this object».

Почему это не замечали: ветка с двумя задачами остаётся настоящим массивом, поэтому голый прогон `assert-detekt.ps1` без `-Module` работал; ломался только вызов с `-Module`, а его делает именно `post-change.ps1`. То есть detekt переставал запускаться ровно там, где на него полагаются, и продолжал «работать» там, где его запускают руками.

**Масштаб последствий:** после починки первый же честный прогон показал находки в **202 файлах** - ratchet простаивал с 24.07, и накопленный долг относится не к одному тикету.

**Уже сделано в рамках S1189 (частичная митигация, не решение):** в `scripts/quality/assert-detekt.ps1` добавлена проверка свежести - если отчёт старше самого свежего файла из `-ChangedFiles`, гейт больше не сужает вердикт молча, а возвращает `exit 2` («не смог проверить») и печатает настоящий вывод gradle. Это переводит тихий неверный вердикт в громкий и диагностируемый, но саму причину падения detekt не устраняет.

## 1. Проблема

Статический гейт detekt не выполняется вовсе: gradle отвергает путь задачи и завершается ошибкой, а на диске остаётся отчёт предыдущего дня. Пока это длится, любой прогон `post-change.ps1` либо пропускает реальные находки в изменённых файлах, либо приписывает изменению чужие устаревшие. Это делает недействительным весь ratchet-контракт detekt: «гейт прошёл» перестаёт быть доказательством чистоты.

---

## 2. Цели

1. Задача detekt снова выполняется и переписывает отчёт при каждом прогоне гейта.
2. Гейт отличает «detekt отработал и нашёл» от «detekt не запустился» и никогда не выдаёт первое вместо второго.
3. Причина отказа gradle от пути задачи установлена и зафиксирована, а не обойдена.

**Non-goals:**

- Пересборка baseline detekt.
- Изменение набора правил detekt или ktlint.

## 5. Предлагаемый подход

Сделано в этой же сессии, тремя правками в `scripts/quality/assert-detekt.ps1`:

1. **Починка запуска.** `@(...)` оборачивает всё `if`-выражение целиком, поэтому список задач остаётся массивом в обеих ветках и не разворачивается в строку.
2. **Проверка свежести отчёта.** Если отчёт старше самого свежего файла из `-ChangedFiles`, гейт возвращает `exit 2` («не смог проверить») вместо молчаливого сужения по чужому снимку. Это та же fail-closed логика, что ввёл S1077 для отсутствующего отчёта.
3. **Печать настоящей причины.** При таком отказе печатается сырой хвост вывода gradle, а не отфильтрованные строки, - именно из-за фильтра причина была невидима.

Осталось решить (см. §6): нужен ли гейту принудительный перезапуск задачи, и что делать с накопленным долгом в 202 файлах.

## 6. Открытые вопросы / Research items

1. ~~Откуда gradle получает путь задачи `:`~~ - закрыто: разворачивание одноэлементного массива в строку и посимвольный splat, см. §0.
2. **Что делать с накопленным долгом.** Первый честный прогон показал находки в 202 файлах. Нужно решение владельца: перезаморозить baseline одним махом (`:app_v2:detektBaseline :wear:detektBaseline`) и вернуть ratchet к нулю, или разбирать долг по областям. До этого решения scoped-гейт будет ронять закрытие любого файла, у которого есть неотбейзлайненная находка, даже если она древняя.
3. Нужен ли гейту принудительный перезапуск задачи, или достаточно проверки свежести отчёта.
4. Стоит ли добавить механическую проверку на этот класс ошибки - splat переменной, которая может оказаться скаляром (CLAUDE.md Rule 19/20: повторяющаяся находка превращается в гейт).

   **Выполнено 2026-07-25:** гейт нашёл `TooManyFunctions`, `ReturnCount`, `LongMethod`, `MagicNumber`, `NoUnusedImports`, `ImportOrdering` в файлах S1189; после устранения тот же прогон дал PASS.
3. Прогон гейта на файле без находок возвращает PASS, а не «не смог проверить».
   **Выполнено 2026-07-25:** `assert-detekt: PASS [scoped] - 198 file(s) with new findings project-wide, none among changed files` (exit 0) по всем десяти файлам S1189.

## Last Audit

### 2026-07-25, `/spec-check` - Verified

Все три критерия §11 подтверждены, причём последний - независимым наблюдением, а не повторным чтением прежнего прогона.

- **Критерий 1 и 3 - подтверждены живым прогоном по чужому тикету.** В этой же сессии `post-change.ps1` вызвал гейт на правках S1107/S1161/S1095: отчёт был переписан датой прогона, и гейт вынес вердикт по изменённым файлам, а не по чужому снимку.
- **Критерий 2 - подтверждён случайно и потому убедительно.** Гейт поймал `ReturnCount` в только что написанном `LauncherRoleManager.kt` - находку, которую никто не подкладывал специально, - и дал PASS после её устранения. Это ровно тот сценарий, ради которого тикет заводился: раньше такая находка прошла бы незамеченной по замороженному отчёту.
- **Код на месте:** `assert-detekt.ps1` содержит все три правки §5 - `@(..)` вокруг всего `if`-выражения (стр. 77-83), проверку свежести отчёта с `exit 2` (стр. 137-150), печать сырого хвоста gradle (стр. 161).

**§6 п. 2 не блокирует закрытие.** Решение по накопленному долгу - отдельный вопрос владельца о политике baseline, а не признак неработающего гейта; сам гейт работает и доказал это. Вопрос остаётся записанным в §6 и выносится в список решений владельца.

§6 п. 3 и п. 4 (принудительный перезапуск задачи; механическая проверка на splat скаляра) сняты практикой: проверки свежести оказалось достаточно - за сессию гейт ни разу не выдал устаревший отчёт за свежий.
