## 1. Проблема

При воспроизведении медиа по SFTP через ExoPlayer однократный сетевой сбой (закрытие pipe внутри JSCH) делает дальнейшее воспроизведение по этому хосту невозможным до перезапуска плеера. Пул переиспользует канал, в котором уже умер внутренний reader-поток, отдаёт его на следующий `open`, и любая попытка открыть файл валится с обобщённой ошибкой SSH_FX_FAILURE. Каскад продолжается на все последующие треки/файлы того же хоста — переключение на «следующий» не помогает.

---

## 2. Цели

1. После единичного I/O-сбоя на SFTP пользователь может снова запустить тот же или другой файл с того же хоста без перезапуска приложения и без ручного действия.
2. Сломанный SFTP-канал не возвращается в общий пул и не выдаётся повторно.
3. Здоровая сессия сохраняется — пересоздаётся только мёртвый канал, не вся сессия (если корневая причина — канал, а не сессия).
4. ExoPlayer-ретраи на сломанном канале прекращаются: первая же ретрай-попытка получает свежий канал.

**Non-goals:**

- Маскировка реальной сетевой ошибки (если хост недоступен — пользователь должен это видеть как и раньше).
- Изменение модели пула SMB/FTP/локальных потоков — спецификация ограничена SFTP-веткой.
- Подмена JSCH на другой SFTP-клиент.
- Расширение SLA по фоновым прокачкам/предзагрузкам — только восстановление foreground-воспроизведения.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. По возможности — без UI-уведомлений о «технической» переподготовке канала: сбой и восстановление должны быть прозрачны, на уровне внутренней телеметрии в Timber.
2. Логи должны явно различать «сломанный канал отброшен» и «канал штатно возвращён в пул» — для постмортема в logcat.
3. Если детектится повторный сбой канала на одной и той же сессии подряд — рассмотреть эскалацию с пересозданием сессии целиком.

### 3.2 Жёсткие ограничения

- **Flavor:** standard, lite, legacy (везде, где SFTP включён); photos — без изменений.
- **API level:** без специфики, исправление работает на всех поддерживаемых уровнях.
- **Wear OS:** не затрагивается — Wear не использует ExoPlayer SFTP-источник.
- **Производительность:** дополнительный учёт «здоровья» канала не должен увеличивать задержку штатного `open` ощутимо для пользователя; никакого нового I/O в горячем пути.
- **Совместимость данных:** изменений хранилища нет.
- **Локализация:** EN/RU/UK — без новых строк (изменения внутренние).
- **Доступность:** не применимо — нет UI-изменений.

## 4. Контекст текущей архитектуры

Воспроизведение SFTP-источника проходит через выделенный data-source-слой ExoPlayer, который запрашивает у пула SFTP-соединений готовый канал на сессии к нужному хосту. Пул держит сессии и список каналов на сессию, выдаёт первый «живой по флагу» канал и кладёт обратно после освобождения. Слой источника управляет только жизненным циклом своего входного потока; решение «канал жив или мёртв» делегировано пулу.

Сейчас граница ответственности дырявая: источник знает, что произошёл I/O-сбой (получил исключение в чтении или закрытии), но не сообщает об этом пулу — release выглядит идентично штатному и сбойному. Пул же опирается на флаг подключённости, который у используемой реализации SFTP остаётся истинным после смерти внутреннего pipe-читателя. Из-за этого сломанный канал переиспользуется до тех пор, пока сессия не отвалится по таймауту.

## 5. Предлагаемый подход

Передавать сигнал о «нездоровье» канала из источника в пул и эвакуировать конкретный канал на этом сигнале, не трогая остальные каналы и сессию. Базовая модель пула не меняется; добавляется явный канал обратной связи о состоянии «лизнутого» канала.

### 5.1 Основные столпы / модули

**A. Учёт состояния «здоровья» в SFTP-источнике.**

- Источник помечает канал как сломанный при любом исключении в чтении файла, при ошибке закрытия его входного потока и при ошибке открытия после успешного получения канала из пула.
- Флаг сбрасывается на штатное при успешном завершении передачи (полное чтение или нормальное закрытие без исключения).

**B. Передача сигнала при возврате канала.**

- Освобождение канала из источника обогащается информацией о его последнем состоянии.
- Пул получает не «безымянный release», а ссылку на конкретный канал и признак «broken/healthy».

**C. Эвакуация сломанного канала из пула.**

- На сигнал «broken» пул дисконнектит указанный канал и убирает его из своего реестра каналов на сессии (включая сопровождающие синхронизационные структуры).
- Штатный «healthy»-возврат остаётся семантически прежним: канал остаётся в пуле, сессия — без изменений.

**D. Эскалация на уровень сессии (опционально, для §3.1.3).**

- Если за короткий интервал на одной сессии помечено сломанными более одного канала, пул дисконнектит сессию целиком и удаляет запись о хосте; следующее обращение создаёт сессию заново.
- Порог и окно времени — параметры эскалации, без жёсткого захардкода значений на этом уровне (детали — в тактической спеке).

### 5.2 Потоки данных и событий

- Штатный путь: ExoPlayer → источник → запрос канала у пула → чтение → закрытие источника → возврат канала в пул как «healthy».
- Сбойный путь: чтение/закрытие бросает исключение → источник помечает канал «broken» → закрытие источника возвращает канал с флагом «broken» → пул дисконнектит канал и убирает его из реестра → ExoPlayer-ретрай через источник запрашивает у пула новый канал → пул открывает свежий канал на той же сессии (если жива).
- Эскалация: при достижении порога сбоев на сессии — пересоздание сессии прозрачно для источника.

### 5.3 Точки расширяемости

- Механизм «канал-возвращён-broken» применим в будущем к другим failure-режимам (например, к серверной ошибке середины передачи), без изменения публичного контракта пула.
- Параметры эскалации (порог, окно) выносятся так, чтобы их можно было ужесточить/ослабить без переписывания логики восстановления.

## 6. Открытые вопросы / Research items

1. **Эскалация на сессию**
   - **Вопрос:** включать ли в первую итерацию авто-пересоздание сессии при N сломанных каналах подряд или ограничиться отбраковкой канала?
   - **Решение:** только канал (вариант «а»). Если в логах появятся подтверждения, что свежий канал на той же сессии тоже падает — открыть отдельный спек на эскалацию сессии.
   - **Статус:** BlockNeedUserTest

2. **Признак «healthy» при частичном чтении**
   - **Вопрос:** считать ли канал здоровым, если ExoPlayer закрыл источник до полного дочтения файла (нормальный сценарий перемотки/смены трека)?
   - **Решение:** канал помечается «broken» только при пойманном исключении (вариант «а»). Нормальное закрытие, в т.ч. до EOF — всегда «healthy». Иначе пул будет необоснованно отбраковывать каналы при штатной смене трека.
   - **Статус:** BlockNeedUserTest

3. **Применимость к suspend-пути (не-ExoPlayer)**
   - **Вопрос:** распространять ли тот же сигнал «broken» на не-ExoPlayer-операции пула (например, открытие потоков для миниатюр/синка)?
   - **Решение:** только ExoPlayer-ветка (вариант «а»). Suspend-путь уже имеет собственный механизм `pool.invalidate()` + одинарный ретрай при `SSH_FX_FAILURE`/`SSH_FX_BAD_MESSAGE` (см. `SftpClient.readFileBytes`/`readFileBytesRange`/`downloadFile`); пересмотр его semantics — отдельная задача.
   - **Статус:** BlockNeedUserTest

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Ложно-положительная отбраковка здорового канала (например, нормальное закрытие потока трактуется как сбой) | Средняя | Пул будет держать меньше каналов, чем мог бы; рост числа открытий каналов | Жёсткое правило: «broken» только при пойманном исключении; нормальное закрытие — всегда «healthy» |
| Пересоздание канала маскирует серверный сбой, который нужно показать пользователю | Низкая | Пользователь не понимает, почему файл «грузится дольше» | Сохранить отображение ошибки, если повторное открытие тоже упало; не глотать второй сбой |
| Гонка: канал помечается «broken» и параллельно используется другим лизером | Низкая | Двойной disconnect или NPE | Эвакуация канала проходит под тем же поллом-локом, что и выдача; контракт «один лизер на канал в момент времени» сохраняется |
| Эскалация на сессию срабатывает на флапающей сети и каскадно дисконнектит все хосты | Низкая | Замедление воспроизведения на нестабильной сети | Эскалацию ограничить порогом и окном времени (см. §6.1); по умолчанию — только канал |
| Контракт изменился, но не все вызывающие пути обновлены | Средняя | В одних путях канал отбраковывается, в других — нет | Тактический шаг: перечислить все точки `release` и обновить их единообразно |

## 9. Архитектурные решения (ADR)

**ADR-1: Сигнал «broken» из лизера в пул, а не автодетект в пуле**

- **Решение:** ответственность за пометку канала «сломанным» лежит на потребителе (источнике), пул только реагирует на сигнал.
- **Альтернативы:** (а) пул сам опрашивает канал перед выдачей через no-op SFTP-команду (`stat` пустого пути); (б) wrapper-канал, перехватывающий исключения изнутри.
- **Почему:** автодетект в пуле требует дополнительного I/O в горячем пути выдачи и не отлавливает «канал умер во время чтения, но пока никто не дёргал». Источник видит реальный сбой первым и без дополнительного round-trip.

**ADR-2: Эвакуация канала, а не всей сессии (по умолчанию)**

- **Решение:** при сигнале «broken» дисконнектится только конкретный канал; сессия остаётся.
- **Альтернативы:** (а) полный reconnect сессии при любом сбое; (б) пометка сессии «прогретой» и перепроверка перед каждой выдачей канала.
- **Почему:** в наблюдаемом инциденте сессия живая (последующее открытие канала на ней успешно после ручного перезапуска), сбой локализован на канале. Полный reconnect сессии увеличивает задержку первого открытия после сбоя без необходимости. Эскалация на сессию остаётся как опциональный шаг (см. §6.1).

## 11. Критерии готовности (strategic-level)

1. После однократного сбоя чтения SFTP-файла повторное открытие того же файла завершается успешно с первой попытки (без 6 ретраев `SSH_FX_FAILURE`).
2. После сбоя чтения переключение на следующий файл того же хоста запускает воспроизведение без ошибки.
3. В логах после сбоя присутствует одно явное событие «канал отбракован», а не серия одинаковых `Error opening SFTP file`.
4. На стабильной сети поведение воспроизведения и пула неотличимо от текущего: каналы переиспользуются, каждое новое открытие не создаёт новый канал.
5. Если сетевой сбой действительно фатален (хост недоступен), пользователь по-прежнему видит ошибку — она не глотается «бесконечным» восстановлением.
