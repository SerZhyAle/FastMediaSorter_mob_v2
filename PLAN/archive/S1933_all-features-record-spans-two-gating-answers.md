## 0. Захваченный материал (inbox)

**Захвачено:** 2026-08-21

**Захвачено во время:** S1929 (сверка поля `flavors` с реальным гейтом флейвора).

**Текст:**

S1929 завёл у записи инвентаря необязательное поле `gate` с именем одного флага `BuildConfig` и проверку,
что `flavors` записи совпадает со строкой этого флага в `docs/FLAVOR_MATRIX.md`. Разбор восьми записей
`wear.*` показал, что для двух из них поле заполнить нечем - не потому, что гейт неизвестен, а потому,
что запись описывает сразу две возможности с противоположными ответами:

- `wear.home-sections-and-selective-transfer` (S1781). Отрисовка секций на самих часах не гейтирована
  вообще: модуль `wear` не объявляет флейворов. Но «выборочная передача», названная прямо в
  идентификаторе записи, - гейтирована: `WearSyncSettingsFragment.kt:92` включает экран выбора
  источников по `mediaCapabilities.supportsWearCompanion`, и спека S1781 это подтверждает.
- `wear.file-list-grid-view-and-thumbnails` (S1730). Сетка и превью для сетевых и локальных файлов
  часов работают без телефона - часы ходят в SMB/FTP/SFTP напрямую своими учётными данными
  (`WearThumbnailRepositoryImpl.kt:104-119`). Но та же сетка для папок телефона идёт через
  `PhoneResourceClient` -> `PhoneWearListenerService`, который смонтирован только в `wearGms`.

Поставить одной такой записи `gate` значит объявить гейтированной и ту половину, которая работает
без телефона; не ставить - оставить проверку выключенной для половины, которая гейтирована. Оба
ответа неверны, поэтому S1929 не трогает эти две записи и выносит вопрос сюда.

Это тот же довод, которым S1929 отверг список флагов вместо одного имени: возможность за двумя
разными ответами - это две возможности либо неудачно проведённая граница записи. Здесь граница
проведена по экрану («сетка с превью», «главный экран часов»), а гейт проходит поперёк неё - по
источнику данных.

**Что выяснить:**

1. Разделять ли такие записи на две (гейтированную и негейтированную) - и не ломает ли это дифф,
   из которого `/skill-release` строит публичный showcase, ведь идентификатор записи в нём опорный.
2. Либо признать, что граница записи проводится по источнику данных, а не по экрану, и тогда
   сформулировать это правилом для будущих записей.
3. Сколько ещё записей вне `wear.*` устроены так же - разбор S1929 смотрел только восемь.

## 1. Цель

Запись инвентаря `docs/ALL_FEATURES.jsonl`, половины которой отвечают по-разному на вопрос «за каким флагом
это живёт», описывает не одну возможность, а две. Тикет фиксирует правилом, где проходит граница записи,
разрезает две известные такие записи и закрывает единственный путь, которым разрез вредит - публичный
showcase релиза.

## 2. Решения

### ADR-1 - граница записи проходит по гейту, а не по экрану

Запись, обе половины которой дают разные ответы на «за каким флагом `BuildConfig` это живёт», - это две
записи. Основание уже в схеме: `gate` одно-значное, а `validate.ps1` требует, чтобы `flavors` в точности
совпадали со строкой этого флага в `docs/FLAVOR_MATRIX.md`. Такой записи нечего поставить: `gate` объявит
гейтированной негейтированную половину, отсутствие `gate` оставит гейтированную половину непроверенной.
Оба ответа неверны, поэтому чинится не значение поля, а граница.

### ADR-2 - разрез не сохраняет прежний id ни одной половине

Обе половины получают идентификаторы, называющие ровно то, что они покрывают; прежний id исчезает.
Сохранить его за одной половиной нельзя: у обеих известных записей id называет и вторую половину
(`home-sections-and-selective-transfer` называет ровно то, что отрезается), так что «сохранённый» id
вернул бы в имя ту самую неверную границу.

### ADR-3 - showcase релиза не объявляет разрез новой возможностью

`scripts/all_features/diff.ps1` сравнивает по `id` и не сообщает об исчезнувшем: разрез читается как две
добавленных записи, и `/skill-release` может объявить уже отгруженную возможность новой. Защита - одна
фраза в правилах отбора showcase: добавленная запись, чей `spec` называет тикет, не отгруженный в этом
окне, - это перекроенная запись, а не новая возможность. Ни поля в схеме, ни скрипта не заводится:
проверка читается только в момент релиза, то есть по классификации Rule 33 она релиз-объёмная, а список
правил отбора и так читается на шаге 12b целиком.

### ADR-4 - сплошной проверки остальных записей не будет

Из 787 записей `gate` несут пять. Запись, лежащая поперёк гейта, вредит только в момент, когда ей пытаются
поставить `gate`, а в этот момент `validate.ps1` уже отказывает на несовпадении `flavors` со строкой флага.
Поэтому правило применяется в момент назначения гейта, к записи, до которой дошли руки, - а не кампанией.
Это тот же порядок, которым Rule 32 выводит Compose-острова из `app_v2`.
