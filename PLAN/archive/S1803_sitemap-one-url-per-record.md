**Текст:**

Найдено при исследовании S1801 (документация Wear на сайте).

Симптом: `sitemap.xml` содержит 19 URL на весь сайт, при том что опубликованных страниц заметно больше. Генератор эмитит ровно один `<url>` на запись реестра (или по одному на локаль, если у записи есть `localized_urls`), а не по одному на файл, попавший под glob записи.

Где видно:

- `scripts/document_registry/generate.ps1`, строки 55-76: цикл идёт по записям `docs/DOCUMENT_REGISTRY.jsonl`, отфильтрованным по `published -and indexable`, и берёт `$record.url`. Поле `paths` (glob) при построении sitemap не разворачивается.
- Запись `user-guides` покрывает glob `docs/howto/*.md` и объявляет один кластерный URL `/docs/README.html` плюс `localized_urls` для en/ru/uk. В результате 9 сценарных страниц (плюс их `-ru`/`-uk` сиблинги, всего 28 файлов в `docs/howto/`) не попадают в sitemap ни одной строкой. Проверка: `grep -c "howto" sitemap.xml` даёт 0.
- Запись `wear-docs` покрывает glob `docs/WEAR_OS_*.md` (восемь файлов) и объявляет один URL `/docs/WEAR_OS_QUICK_START.html`. В sitemap попадает только он; проверка: `grep -o "WEAR_OS_[A-Z_]*" sitemap.xml` даёт единственное значение `WEAR_OS_QUICK_START`.

Каждая такая страница несёт собственный Jekyll `permalink` и собирается в отдельный публичный URL, то есть страницы существуют и доступны по прямой ссылке, но поисковой системе о них не сообщают.

Почему это отдельный тикет, а не часть S1801: поведение затрагивает все опубликованные группы реестра сразу, а не только Wear. Изменение генератора (разворачивать `paths` в набор URL либо разрешить записи нести список URL) меняет sitemap для каждой группы и требует собственного решения о том, что считать индексируемой единицей - файл или группу.

Открытый вопрос для будущей проработки: часть страниц под glob сознательно не должна индексироваться (например, внутренние dev-документы, попавшие в публичную группу), поэтому «развернуть glob целиком» - не автоматически верный ответ.

## 1. Проблема

Сайт публикует 71 страницу, каждая со своим адресом, а поисковой системе объявляет 19. Остальные 52 собираются, отвечают по прямой ссылке и не существуют для поиска. Хуже всего в группе пользовательских руководств: 47 страниц против трёх объявленных - то есть весь жанр пошаговых сценариев, самая полезная для нового пользователя часть документации, невидим целиком. Причина не в содержимом страниц, а в форме реестра: он объявляет один адрес на группу документов, сколько бы файлов в группе ни лежало.

## 2. Цели

1. Каждая опубликованная страница, у которой есть собственный адрес, попадает в карту сайта.
2. Страница, которую сознательно не хотят объявлять, не попадает туда - и причина этого записана рядом с ней, а не держится в голове.
3. Добавление новой страницы в существующую группу не требует правки реестра, чтобы страница стала видна поиску.
4. Карта сайта остаётся порождаемой из одного источника: руками её по-прежнему никто не правит.

**Non-goals:**

- Перевод сайта на тринадцать языков и унификация конвенции имён локалей - объём S1211.
- Изменение содержимого страниц, их адресов или их имён.
- Смена генератора сайта или введение плагина.
- Продвижение и регистрация в поисковых панелях - это отдельный процесс, описанный собственным документом.

## 4. Контекст текущей архитектуры

Реестр документов - машиночитаемый список групп. У группы есть набор путей с шаблонами, признаки публикации и индексируемости, набор языков и **один** объявленный адрес, плюс необязательный набор адресов по локалям. Генератор строит карту сайта, проходя по группам с признаками публикации и индексируемости и беря у каждой либо её единственный адрес, либо по одному на локаль. Поле с путями при этом не разворачивается вовсе - оно используется только для обзорной таблицы документов.

Страницы же живут иначе: статический генератор сайта собирает в страницу каждый файл, несущий заголовок с адресом публикации, независимо от того, знает ли о нём реестр. Отсюда и расхождение: адрес страницы задаёт сама страница, а объявляет его реестр, и эти две величины связаны только там, где кто-то руками вписал адрес в запись.

Пока модель «одна запись - один адрес» цела, проблему нельзя решить, добавляя записи: каждая новая страница требовала бы собственной записи реестра, то есть реестр групп превратился бы в реестр файлов и перестал бы отвечать на вопрос, ради которого заведён - какая часть документации кем поддерживается и по какому поводу обновляется.

---

## 5. Предлагаемый подход

Развести две роли, которые сейчас слиты в одном поле: **страница сама знает свой адрес**, а **запись реестра решает политику публикации** для группы страниц. Генератор перестаёт спрашивать у записи адрес и начинает спрашивать у страниц.

### 5.1 Основные столпы / модули

**Адрес берётся у страницы.** Для каждой опубликованной и индексируемой группы генератор обходит её файлы, читает объявленный на странице адрес и эмитит его. Файл без объявленного адреса страницей не является и пропускается - этим отсеиваются служебные документы, лежащие внутри группы.

**Исключения объявляются явно.** Запись получает возможность назвать страницы, которые сознательно не объявляются поиску, вместе с причиной. Пустой список означает «объявляются все», то есть запись без нового поля ведёт себя как сегодня плюс разворачивание.

**Кластерный адрес остаётся входом.** Нынешний адрес записи не выбрасывается: он продолжает означать «главная страница группы», нужен обзорной таблице и служит целью для ссылок. Меняется только то, что он больше не единственный объявляемый.

**Проверка соответствия.** Отдельная проверка сверяет объявленное с существующим в обе стороны: каждый адрес в карте сайта ведёт на существующий файл, и каждая страница группы либо объявлена, либо названа в исключениях. Расхождение - отказ, а не предупреждение, иначе поле исключений тихо зарастёт.

### 5.2 Потоки данных и событий

Сегодня: запись реестра -> её адрес -> строка карты сайта.

После: запись реестра -> её шаблоны путей -> файлы -> объявленный на странице адрес -> строка карты сайта, минус то, что названо в исключениях записи.

Обзорная таблица документов продолжает строиться из записей и меняется только тем, что может показать число страниц в группе.

### 5.3 Точки расширяемости

- Языковые альтернативы для развёрнутых адресов выводятся тогда, когда конвенция имён локалей станет одна; до тех пор механизм остаётся на уровне записи и новый код его не трогает.
- Правило «страница без объявленного адреса не страница» даёт группам возможность держать рядом служебные файлы, не заводя для них отдельной записи.
- Исключения хранятся рядом с группой, поэтому решение «эту страницу не объявляем» переносится вместе с группой и не размазывается по генератору.

## 9. Архитектурные решения (ADR)

**ADR-1: Адрес объявляет страница, политику объявляет запись**

- **Решение:** генератор берёт адрес из самой страницы, а запись реестра решает, объявляется ли группа и какие её страницы исключены.
- **Альтернативы:** хранить в записи явный список адресов; завести отдельную запись реестра на каждую страницу.
- **Почему:** адрес уже задан на странице и является единственным местом, где он не может разойтись с действительностью, - список в записи разошёлся бы при первом же добавлении файла. Запись на страницу превратила бы реестр групп в реестр файлов и лишила бы его смысла: он отвечает, какая часть документации кем поддерживается и по какому поводу обновляется, а это свойство группы, а не файла.

**ADR-2: Файл без объявленного адреса не является страницей**

- **Решение:** файлы под шаблонами группы, не несущие объявленного адреса, пропускаются молча.
- **Альтернативы:** объявлять все файлы группы; требовать, чтобы в группе не лежало ничего, кроме страниц.
- **Почему:** внутри пользовательских групп законно лежат служебные файлы - например чеклист требований к снимкам экрана рядом со сценариями, - и это удобно, потому что они меняются вместе. Требование чистоты группы породило бы переносы файлов ради генератора, а объявление всех подряд вывело бы служебное в поиск.

1. Число адресов в карте сайта равно числу опубликованных страниц минус число явно исключённых.

3. Каждая исключённая страница названа поимённо и несёт причину исключения.
4. Добавление новой страницы в существующую группу отражается в карте сайта после перегенерации, без правки реестра.
5. Запись реестра, не получившая новых полей, объявляет все свои страницы и ни одной чужой.
6. Карта сайта и обзорная таблица документов по-прежнему порождаются генератором и не правились руками.
