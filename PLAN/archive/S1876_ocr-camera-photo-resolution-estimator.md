## 0. Захваченный материал (inbox)

**Захвачено:** 2026-08-21

**Захвачено во время:** S1715 (`ocr-engine-configuration`), фаза 03 - при реализации `EstimateOcrResolutionUseCase`.

**Вопрос, дословно из S1715 §6.4:**

> По какому правилу оценивать разрешение снимка с камеры - единственного вида источника, где физический размер сцены неизвестен принципиально?

**Почему он вынесен, а не решён на месте.** S1715 закрыл три вида источника из четырёх точным вычислением, а не оценкой:

- страница документа - `pixelWidth * 72 / pageWidthPoints`, арифметика по размеру страницы в пунктах;
- скриншот - плотность экрана, известная системе;
- файл-картинка - различается по EXIF (`TAG_MAKE`, `TAG_MODEL`, `TAG_FOCAL_LENGTH`), которые приложение уже извлекает.

Остался один случай, где оценка неизбежна, и придумать для него константу молча означало бы ровно ту догадку, ради устранения которой S1715 и существует. `docs/OCR_OVERLAY_ACCURACY.md` (строка 195) прямо отвергает правило соседей: «`11` дюймов как предполагаемая страница - книжное допущение; наши входы - фотографии, скриншоты и страницы комиксов, поэтому переосмысления требует сам оценщик, а не только его константа».

**Что сделано вместо этого в S1715.** Ветка снимка объявляет пол (70), как и неизвестный вид. Это записано и в коде, и в тесте как сознательное решение:

```kotlin
OcrSourceKind.CAMERA_PHOTO -> null   // -> FLOOR_DPI
```

```kotlin
@Test
fun `camera photo declares the floor while its estimator is an open question`()
```

То есть поведение сегодня безопасное и явное, а не недоделанное: объявляется заведомо консервативное значение вместо правдоподобного, но выдуманного.

**Откуда возьмутся данные.** Замер разбивки и времени распознавания из фазы 04 S1715 даёт первую пригодную выборку на нашем материале. До него оценщик выводить не на чем.

## 1. Проблема

`EstimateOcrResolutionUseCase` объявляет распознавателю разрешение для трёх видов источника точным вычислением, а для снимка с камеры - полом `FLOOR_DPI = 70`, потому что физический размер сцены неизвестен. Пол занижает разрешение для типичного снимка документа с 25-30 см в три-четыре раза, а именно от объявленного разрешения зависит, как движок делит соседние блоки. Соседний проект решает это допущением «страница 11 дюймов», и `docs/OCR_OVERLAY_ACCURACY.md` отвергает его для нашего материала. Нужен способ, который не выдумывает размер сцены, а вычисляет его там, где данные для этого уже лежат в файле.

---

## 2. Цели

1. Ветка `OcrSourceKind.CAMERA_PHOTO` возвращает вычисленное разрешение вместо пола для снимков, чей EXIF несёт дистанцию до объекта и фокусное расстояние.
2. Снимок без этих данных по-прежнему объявляет пол - без правдоподобной, но выдуманной подстановки.
3. Вычисление остаётся арифметикой по данным файла, а не оценкой по выборке, поэтому не ждёт корпуса.

**Non-goals:**

- Лестница апскейла ниже 120 DPI - она за рамками и S1715, и этого тикета.
- Вывод оценщика для снимков без EXIF-дистанции - остаётся открытым вопросом §6.1.
- Изменение пола `FLOOR_DPI = 70`.

## 5. Предлагаемый подход

### 5.1 Уровень A - арифметика по сцене, когда EXIF её задаёт

Дистанция до объекта и фокусное расстояние вместе задают ширину сцены подобием треугольников, то есть тем же родом вычисления, что и ветка страницы документа, а не оценкой:

- `sceneWidthMm = sensorWidthMm * subjectDistanceM * 1000 / focalLengthMm`
- при `TAG_FOCAL_LENGTH_IN_35MM_FILM` величина `sensorWidthMm` равна `36` по определению самого тега, поэтому размер матрицы знать не нужно;
- `dpi = pixelWidth * 25.4 / sceneWidthMm`;
- свёрнуто: `dpi = pixelWidth * focal35Mm * 25.4 / (36 * subjectDistanceM * 1000)`.

Проверка порядка величины: снимок 4000 px, `focal35 = 26`, дистанция `0.3` м даёт 245 DPI - правдоподобное разрешение для документа, снятого с 30 см. Та же формула на 2 м даёт 37 DPI, то есть ниже пола, и вывеска издалека корректно возвращается к полу.

### 5.2 Уровень B - остаётся полом

`TAG_SUBJECT_DISTANCE_RANGE` даёт не число, а корзину (`macro` / `close view` / `distant view`). Превращать корзину в метры - ровно та подстановка, ради устранения которой существует и S1715, и этот тикет, поэтому уровень B объявляет пол и остаётся открытым вопросом §6.1 до появления материала фазы 04 S1715.

### 5.3 Защитные условия

- `subjectDistance == 0` по спецификации EXIF означает «неизвестно», а не «ноль метров» - трактуется как отсутствие.
- Неположительные `focal35Mm`, `subjectDistanceM`, `pixelWidth` - отсутствие, то есть пол.
- Результат по-прежнему проходит через `coerceAtLeast(FLOOR_DPI)`, поэтому уровень A не может ухудшить поведение относительно сегодняшнего ни на одном входе.

### 5.4 Форма сигнатуры

Два новых необязательных параметра рядом с существующими `pageWidthPoints` и `screenDensityDpi` - `focal35Mm: Float? = null`, `subjectDistanceM: Float? = null`. Домен остаётся без зависимости от `ExifInterface`: теги извлекает вызывающая сторона, как это уже делают `MediaMetadataHelper` и `SafUriExtractor`.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| EXIF-дистанция врёт или задана грубой корзиной | Средняя | Объявлено завышенное разрешение, разбивка блоков хуже пола | Уровень B не используется вовсе; уровень A применяется только к точному `TAG_SUBJECT_DISTANCE` |

## 9. Архитектурные решения (ADR)

### ADR-1 - камера становится арифметикой там, где EXIF это позволяет, и полом везде ещё

- **Контекст:** для снимка нужен размер сцены, и он неизвестен принципиально - но только при отсутствии данных о дистанции.
- **Решение:** вычислять разрешение по дистанции и фокусному расстоянию из EXIF; при их отсутствии сохранять пол.
- **Альтернатива отвергнута:** допущение «страница 11 дюймов» из соседнего проекта - отвергнуто в `docs/OCR_OVERLAY_ACCURACY.md` для нашего материала.
- **Альтернатива отвергнута:** отображение `TAG_SUBJECT_DISTANCE_RANGE` в метры - подставляет константу вместо измерения.
- **Следствие:** ветка `CAMERA_PHOTO` перестаёт быть однородной: она вычисляет либо объявляет пол, и различие видно из входных данных.

## 11. Критерии готовности (strategic-level)

1. Ветка `OcrSourceKind.CAMERA_PHOTO` возвращает вычисленную по EXIF оценку, когда дистанция и фокусное расстояние заданы.
2. Та же ветка возвращает пол, когда любой из двух входов отсутствует, нулевой или отрицательный.
3. Юнит-тест покрывает обе ветки, включая `subjectDistance == 0` как «неизвестно».
4. Ни на одном входе результат не ниже `FLOOR_DPI` - то есть уровень A не хуже пола по построению.
