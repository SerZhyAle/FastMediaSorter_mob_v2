## 1. Проблема

При шаринге в приложение ссылки на `music.youtube.com` или `youtube.com` показывается диалог «добавить авторизацию для YouTube». Если пользователь соглашается, открывается внешнее окно (Chrome Custom Tabs или приложение YouTube Music, в котором пользователь уже залогинен), пользователь возвращается в приложение, но **ни один аккаунт не сохраняется**: на следующем шаринге той же ссылки диалог появляется снова с тем же `accounts=0`. Это бесконечная UX-петля без полезного результата.

Корень — противоречие двух уже принятых решений. Спеки S0166/S0157/S0144/S0211 строят поток предложения авторизации для known-social хостов на предположении, что встроенный WebView перехватывает cookies и кладёт их в локальное хранилище аккаунтов. Спека S0200 ADR-4 ввела жёсткий запрет WebView для google-доменов (политика OAuth Google) и направляет такие хосты в Chrome Custom Tabs, у которого по дизайну нет канала возврата cookies в приложение. Запись YouTube/YouTube Music в перечне known-social хостов осталась с прошлой эпохи и теперь ведёт в тупик. Подтверждение в логе `fastmediasorter_20260521_002254.log` (строки 4925-4990): два захода подряд с одной и той же ссылкой, оба раза `accounts=0 → no stored auth → auth dialog shown → auth accepted`, и состояние не меняется.

Эффект на пользователя: ложное обещание «сейчас сохраним вход», бесполезное переключение в YouTube Music app, отсутствие кнопки «сохранить», возврат в приложение без видимого прогресса, повторение цикла при следующем шаринге. Воспринимается как сломанная функциональность.

## 2. Цели

1. Шаринг ссылки на любой google-домен из набора политики OAuth Google (google.com, accounts.google.com, youtube.com, music.youtube.com и их поддомены) не приводит к показу диалога «добавить авторизацию», который заведомо не может сохранить результат.
2. Скачивание ссылки на google-домен продолжает работать в текущем режиме без auth-канала (через существующую цепочку link-auto-download без cookies).
3. Если экстрактор не смог получить медиа для google-домена (приватное / возрастное / ограниченное содержимое), пользователь получает понятное сообщение об ограничении, а не повторный циклический диалог авторизации.
4. Сохранена прежняя логика auth-offer для не-google known-social хостов (Instagram, Threads, Facebook, Reddit, Pinterest, TikTok, X, DeviantArt, Tumblr, Flickr, ArtStation): WebView + cookie-jar остаётся рабочим путём.

**Non-goals:**

- Интеграция YouTube Data API или YouTube Music API для извлечения метаданных и стримов — это явный non-goal S0200 §2, отдельный тикет с прохождением Google Security Assessment не запрашивается.
- Расширение OAuth-scope привязанного primary Google-аккаунта (S0200) для использования в link-auto-download — primary-привязка остаётся под Drive-scope и не подменяет cookie-jar.
- Возврат WebView для google-доменов — запрещено политикой OAuth Google и решением S0200 ADR-4.
- Изменение поведения auth-offer для не-google хостов.
- Перенос cookie-jar в Chrome Custom Tabs — у CCT нет такого API.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Пользователь, ранее видевший диалог «добавить авторизацию для YouTube», на следующем шаринге той же ссылки не видит этот диалог — без отдельных действий со стороны пользователя по сбросу состояния.
2. Если решение в §5 предусматривает короткое разовое сообщение «вход в YouTube здесь не сохраняется — открою прямо», оно показывается не чаще одного раза на сессию приложения и не блокирует поток.
3. Поведение для не-google known-social хостов остаётся идентичным текущему — никаких визуальных или функциональных изменений в их потоке.

### 3.2 Жёсткие ограничения

- **Flavor:** все флейворы, в которых включён link-auto-download (текущая фактическая матрица `app_v2/build.gradle.kts`, включая `standard`, `noLegal`, `lite`, `photos`, `legacy`, `vr`, `vrUnlicensed`). - **Wear OS:** не затрагивается. Wear-модуль не имеет share-receiver и не запускает link-auto-download.
- **Производительность:** без бюджета — изменение ограничено control-flow в потоке шаринга ссылки и не влияет на горячие пути.
- **Совместимость данных:** не затрагивается. Сохранённые записи `AuthAccountDomain` для не-google хостов не мигрируют. Если в хранилище уже есть пустые записи под `music.youtube.com` / `youtube.com` (созданные тёмным углом потока), они становятся неиспользуемыми и подлежат idempotent cleanup при первом запуске обновлённой версии, без потери данных по другим хостам.

## 4. Контекст текущей архитектуры

Поток link-auto-download начинается в Activity-приёмнике системного шаринга. Принятый URL проходит через детектор known-social хостов. Если хост известен — запускается ветка с проверкой сохранённых аккаунтов и при их отсутствии показывается auth-offer диалог. Согласие пользователя в диалоге направляет URL в роутер, который для google-доменов открывает Chrome Custom Tabs, а для остальных — WebView с cookie-jar. Cookies из WebView записываются в локальное хранилище аккаунтов и используются в последующих скачиваниях. CCT не имеет такой связи с хранилищем по дизайну Android.

Сейчас в перечне known-social хостов присутствует запись «YouTube», покрывающая `youtube.com` и `music.youtube.com` через subdomain match. Эта запись была добавлена до того, как S0200 ADR-4 ввёл маршрутизацию google-доменов в CCT. После S0200 запись осталась в перечне, но её auth-канал перестал работать: WebView для этих хостов запрещён, CCT не сохраняет cookies, локальное хранилище остаётся пустым. Соединение «known-social → auth-offer → WebView → cookies → хранилище» разорвано именно для google-доменов и нигде в коде это не отражено отдельным гейтом — поэтому пользователь видит UI-обещание, которое не может выполниться.

Параллельно существует независимая ветка S0200 — карточка «Google Account» в настройках и primary-привязка через Credential Manager. Эта привязка хранит OAuth-токены под Drive-scope и не имеет отношения к cookie-jar, который нужен экстрактору ссылок. Использование primary-привязки в потоке link-auto-download невозможно без расширения OAuth-scope и интеграции отсутствующих в S0200 публичных API.

## 5. Предлагаемый подход

Развести два потока: «известный социальный хост, для которого мы можем перехватить cookies через WebView» и «известный социальный хост, для которого политика OAuth запрещает WebView». Google-домены попадают во второй класс. Auth-offer диалог показывается **только** для хостов первого класса. Для google-доменов поток шаринга продолжается так же, как для unknown-host: silent enqueue в существующий download-канал, без auth-offer; результат экстракции отображается обычным механизмом (success / NoMediaFound / SocialPreviewOnly), без эскалации в auth-offer.

Источник истины «к какому классу относится хост» — существующий gate `GoogleDomainMatcher` из S0200 (он же используется для решения CCT vs WebView). Перечень known-social хостов остаётся в одном месте; принадлежность к OAuth-only набору проверяется отдельным предикатом.

### 5.1 Основные столпы / модули

- **Классификатор хостов в потоке шаринга.** Слой принятия ссылки получает явный шаг: «является ли хост google-OAuth-only?» — если да, путь известного социального хоста не активируется, поток идёт по unknown-host ветке с silent download. Логика классификации делегируется уже существующему компоненту (single source of truth для google-доменов из S0200), без дублирования набора доменов.
- **Гейт auth-offer диалога.** В точке принятия решения о показе диалога (при `accounts=0` и при escalation после `NoMediaFound`) добавляется ранний return для google-доменов — диалог не показывается. Существующий путь для не-google хостов не меняется.
- **Запись YouTube в перечне known-social.** Запись становится либо избыточной (если §5.2 решит её удалить), либо сохраняется как маркер «known-host, но без auth-канала». Решение — в §6 (open question).
- **Idempotent cleanup пустых google-аккаунтов в хранилище.** Если в локальном хранилище аккаунтов уже есть записи под `music.youtube.com` / `youtube.com` с нулевым числом cookies (артефакт прошлого тёмного потока), они удаляются один раз при первом запуске обновлённой версии. Прочие записи не затрагиваются. Это не миграция Room — данные принадлежат тому же storage, что и сейчас.
- **Опциональное разовое объяснение.** При первом шаринге google-домена в сессии приложение может показать неинтрузивное сообщение «вход в YouTube здесь не сохраняется — открою прямо». Решение, нужно ли это сообщение, передаётся в §3.3 / §6 на усмотрение владельца.

### 5.2 Потоки данных и событий

- UI шаринга → детектор URL → классификатор хоста: google-OAuth-only? → ДА → unknown-host путь (silent enqueue → download-worker → результат экстракции в UI).
- UI шаринга → детектор URL → классификатор хоста: google-OAuth-only? → НЕТ → known-social путь как сегодня (выбор аккаунта / auth-offer / WebView + cookie-jar / silent download).
- Результат экстракции для google-домена возвращает NoMediaFound / SocialPreviewOnly → существующий механизм отображения ошибки. Эскалация в auth-offer для google-домена не выполняется.
- При первом запуске обновлённой версии: пустые записи аккаунтов для google-OAuth-only хостов очищаются один раз; флаг «cleanup выполнен» сохраняется в локальном prefs.

### 5.3 Точки расширяемости

- Набор google-OAuth-only хостов остаётся в одном месте (источник истины из S0200), расширение нового google-домена — изменение одной константы.
- Если в будущем появится канал получения cookies из CCT (или альтернативная Android-механика для google-доменов), его можно подключить в point-of-decision классификатора без правок остальной цепочки.
- Если для какого-то не-google хоста в будущем понадобится разорвать связку «known-social ↔ auth-offer» по аналогичной причине, предикат «is-OAuth-only» обобщается в свойство записи known-social, без дублирования логики.

## 6. Открытые вопросы / Research items

1. **Удалить запись YouTube из перечня known-social или сохранить как маркер?**
   - **Вопрос:** запись `YouTube` (host=youtube.com, subdomain match включая music.youtube.com) в перечне known-social хостов после введения гейта google-OAuth-only становится либо избыточной (если поток шаринга самостоятельно классифицирует хост раньше), либо полезной как метка для других подсистем (например, для иконки или метаданных в UI результата экстракции).
   - **Варианты:** (A) удалить запись — минимальная поверхность, нет «висящего» known-host без auth-канала; (B) оставить запись с новым флагом `oauthOnly = true` — сохраняем семантику «известный социальный хост», но явно помечаем отсутствие auth-канала; (C) оставить запись без изменений — гейт классификатора решает всё, запись остаётся как сегодня, нет видимого изменения смысла.
   - **Нужно выяснить:** есть ли в проекте подсистемы вне link-auto-download, которые читают эту запись и зависят от наличия YouTube в перечне (UI-иконки, метаданные результата экстракции, аналитика). Если нет — вариант A проще. Если да — вариант B сохраняет совместимость с минимальной правкой.
   - **Статус:** Open. Решение принимает тактическая спека (`/spec-tech S0281`) после быстрого инвентаризационного прохода по проекту.

2. **Показывать ли разовое объяснение пользователю при первом шаринге google-домена в сессии?**
   - **Вопрос:** молчаливо проглатывать ситуацию или показать короткое объяснение «вход в YouTube здесь не сохраняется — открою прямо», чтобы пользователь понимал отсутствие auth-диалога как осознанный отказ, а не как забытый код.
   - **Варианты:** (A) без сообщения, тихий silent enqueue; (B) toast «вход в YouTube здесь не сохраняется» один раз на сессию; (C) toast только при первом неуспешном экстракте на google-домене (NoMediaFound / SocialPreviewOnly), а не при первом шаринге как таковом.
   - **Нужно выяснить:** предпочтения владельца. Тестируемость варианта B vs C на устройстве и в логе.
   - **Статус:** Open. Решение принимает владелец на стадии Approval gate (поле в §3.3 при необходимости конкретизируется).

3. **Cleanup существующих пустых google-аккаунтов в хранилище.**
   - **Вопрос:** удалять ли разово пустые записи аккаунтов для `music.youtube.com` / `youtube.com` при первом запуске обновлённой версии, или оставить как есть (они не используются и не растут).
   - **Варианты:** (A) разовый idempotent cleanup при первом запуске; (B) leave-as-is, ничего не делать с прошлыми данными.
   - **Нужно выяснить:** содержит ли локальное хранилище аккаунтов хотя бы одну такую запись на реальном пользовательском устройстве (можно проверить по структуре `AuthSessionRepository` и его источнику данных).
   - **Статус:** Open. Решение принимает тактическая спека.

## 9. Архитектурные решения (ADR)

**ADR-1: Гейт google-OAuth-only в начале потока шаринга**

- **Решение:** ввести явный шаг классификации хоста в потоке link-auto-download до выбора пути known-social vs unknown-host. Google-OAuth-only хосты направляются в unknown-host путь.
- **Альтернативы:** (a) добавить отдельный флаг в каждую запись known-social и проверять его в нескольких местах потока (auth-offer, escalation); (b) удалить YouTube из known-social полностью и положиться на то, что unknown-host путь сработает корректно.
- **Почему:** один явный гейт в начале потока — самая узкая поверхность изменений и самая прозрачная семантика. Альтернатива (a) рассеивает решение по нескольким точкам и увеличивает шанс пропустить одну при будущей правке. Альтернатива (b) теряет семантику «известный социальный хост» для метаданных, если они когда-то понадобятся вне auth-канала.

**ADR-2: Источник истины google-доменов делегируется в существующий компонент S0200**

- **Решение:** список google-OAuth-only хостов не дублируется в новом коде; гейт переиспользует `GoogleDomainMatcher`.
- **Альтернативы:** ввести отдельный набор для link-auto-download.
- **Почему:** двойная истина приведёт к рассинхрону при добавлении нового google-домена. Существующий matcher уже покрывает весь нужный набор.

**ADR-3: Эскалация после NoMediaFound для google-домена не запускает auth-offer**

- **Решение:** существующий шаг `handleNoMediaFoundEscalation` для google-OAuth-only хостов завершает поток как сегодня делает для KnownAuthResources-хостов (без эскалации), не пытается показать auth-offer.
- **Альтернативы:** показывать auth-offer при NoMediaFound для google-домена с пометкой «вход не сохраняется, но попробуйте войти в YouTube вручную».
- **Почему:** альтернатива воспроизводит ту же UX-петлю в другом окне (пользователь снова идёт в YT Music app и обнаруживает, что войти негде, потому что уже вошёл). Это эквивалентно ничегонеделанию плюс шумный диалог.

## 10. Связи с другими спеками

- **S0200** (google-account-central-binding, Verified) — источник ADR-4 и `GoogleDomainMatcher`. S0281 опирается на эти решения, не меняет их.
- **S0211** (webview-auth-account-dedup-and-loop-prevention, BlockNeedUserTest) — соседний поток про предотвращение циклов в auth-offer. S0281 устраняет другой класс цикла (google-OAuth-only), не пересекается с дедупом аккаунтов из S0211.
- **S0166** (link-receive-and-auth-storage, Archived), **S0157** (link-auth-offer-and-dismissal-ux, Archived), **S0144** (fix-link-download-auth-ux, Archived), **S0187** (запись YouTube в KnownAuthResources, исторический контекст) — исторические тикеты, заложившие нынешний поток. S0281 корректирует one явное противоречие, не отменяя их решения.

Не блокируется внешними тикетами.

## 11. Критерии готовности (strategic-level)

1. Шаринг URL `music.youtube.com` или `youtube.com` (любой видеоролик, плейлист, трек, канал) не показывает диалог «добавить авторизацию» — ни при первом шаринге, ни при повторных.
2. Шаринг URL `music.youtube.com` или `youtube.com` запускает скачивание в фоновом режиме (silent download), результат отображается через существующий UI результата (success / NoMediaFound / SocialPreviewOnly).
3. Шаринг URL не-google known-social хоста (Instagram, Threads, Facebook, Reddit, Pinterest, TikTok, X, DeviantArt, Tumblr, Flickr, ArtStation) при `accounts=0` показывает диалог «добавить авторизацию» как сегодня; согласие открывает WebView; cookies сохраняются; следующий шаринг той же ссылки идёт через сохранённый аккаунт без диалога.
4. NoMediaFound / SocialPreviewOnly для google-домена завершает поток с понятным сообщением, не эскалирует в auth-offer повторно.
5. Локальное хранилище аккаунтов после обновлённой версии не содержит пустых записей под google-OAuth-only хостами (если вариант A в §6 Q3 принят), либо содержит ровно те же записи, что и до обновления (если вариант B принят); записи для не-google хостов не затрагиваются ни в одном варианте.
6. Если решение по §6 Q2 — показывать разовое объяснение, оно появляется не чаще одного раза на сессию приложения, не блокирует поток, локализовано в EN/RU/UK.
7. Build целевого флейвора (`standardDebug`) проходит, существующие unit-тесты не ломаются.
