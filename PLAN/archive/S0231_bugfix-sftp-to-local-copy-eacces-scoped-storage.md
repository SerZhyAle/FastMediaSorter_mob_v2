## 1. Проблема

При копировании файла с SFTP-источника в локальную публичную коллекцию (`/storage/emulated/0/Music/`, `Download/`, `Movies/`, `Pictures/`, `DCIM/`) операция падает на создании временного файла-приёмника `*.temp_copy` с `EACCES (Permission denied)` — на Android 10 без `requestLegacyExternalStorage` сырая запись через `FileOutputStream` в публичные каталоги запрещена scoped storage, а на Android 11+ работает только при наличии `MANAGE_EXTERNAL_STORAGE`, которое пользователь может не предоставить и которое в Google Play имеет ограниченное использование. В результате пользовательская функция «копирование/перемещение с сетевого ресурса на устройство» (заявленная в `docs/FEATURES.md`) на типовых устройствах с API 29+ не работает либо работает нестабильно — атомарный путь «копия → `*.temp_copy` → переименование» падает на первом же шаге, источник в порядке, приёмник не создаётся.

Эффект для пользователя: при попытке сохранить медиафайл с сетевого хранилища (SFTP, по аналогии — SMB/FTP/Cloud) в стандартную медиа-папку устройства появляется ошибка с непонятной формулировкой; обходного пути в UI нет. Затронут весь маршрут «сетевой источник → локальная публичная коллекция»: и одиночное копирование, и перемещение (где `*.temp_copy` тоже используется).

---

## 2. Цели

1. Копирование с сетевого источника в публичные медиа-коллекции (Music, Movies, Pictures, DCIM, Downloads) корректно работает на Android 10 и Android 11+ **без** зависимости от `MANAGE_EXTERNAL_STORAGE` — для пользовательских медиафайлов стандартный путь через MediaStore.
2. Перемещение (копия + удаление источника) ведёт себя как сейчас: либо завершается полностью, либо приёмник не остаётся в наблюдаемом «полузаписанном» состоянии для внешних наблюдателей (галерея, плеер, MediaStore-индекс).
3. Если пользователь явно выбрал нестандартный каталог приёмника (не из медиа-коллекций), а у приложения нет прав записи — пользователь видит понятное сообщение с указанием причины и направлением действий, а не сырой `EACCES`/`FileNotFoundException`.
4. Атомарность переноса для внешних наблюдателей сохраняется: файл становится видимым целиком и только после успешного завершения копирования; неудачные попытки не оставляют видимых наблюдателю остатков.
5. Решение единообразно для всех сетевых источников (SFTP, SMB, FTP, облака) — общая роль «приёмник в локальную публичную коллекцию», а не отдельная реализация в каждом протоколе.

**Non-goals:**

- Не вводить новые произвольные каталоги приёмника помимо уже выбираемых пользователем.
- Не перестраивать загрузку с сетевых источников целиком — менять только последний участок пути (запись в локальный приёмник).
- Не трогать обратное направление (локаль → сетевой источник).
- Не менять политику использования `MANAGE_EXTERNAL_STORAGE` для остальной части приложения (сканирование, чтение и т.п. — отдельная зона ответственности).

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Единый абстрактный «писатель в локальную публичную коллекцию», переиспользуемый всеми сетевыми источниками — чтобы исправление в одном месте применялось ко всему слою передачи.
2. Возможность в дальнейшем подключить тот же «писатель» к загрузке по URL и сохранению кадров/изображений — там, где сейчас используется похожий, но дублируемый код через MediaStore.
3. Прозрачная диагностика в логе: при падении записи в приёмник видно — что именно недоступно (целевая коллекция, конкретный относительный путь, причина — отказ системы или отсутствие прав).

### 3.2 Жёсткие ограничения

- **Flavor:** все flavor'ы, где доступны сетевые источники (`standard`, `vr`, `vrUnlicensed`, `noLegal`, `legacy`). `lite` и `photos` — затронуты в той мере, в какой у них сохранены соответствующие сетевые протоколы (исходить из текущих BuildConfig-гейтов: SFTP/SMB/FTP/Cloud в `standard`/`vr`/`noLegal`/`legacy`).
- **API level:** обязательная поддержка API 26..API 36 (минимальный SDK проекта). Ключевые поведенческие границы — API 29 (введён scoped storage) и API 30 (расширение scoped storage, `MANAGE_EXTERNAL_STORAGE`). Решение не должно опираться на наличие `MANAGE_EXTERNAL_STORAGE` для штатного сценария.
- **Wear OS:** не затрагивается.
- **Производительность:** запись через стандартные API ОС не должна заметно увеличивать длительность передачи относительно текущей записи через `FileOutputStream` (для сетевого источника узкое место — сеть, а не локальная запись). Потребление памяти — без буферизации всего файла в памяти.
- **Совместимость данных:** изменений в хранимых настройках/кэшах не требуется; путь приёмника, отображаемый пользователю и сохраняемый в истории, остаётся валидным и сопоставимым со старыми записями.
- **Локализация:** EN/RU/UK — обязательно для всех новых/изменённых пользовательских строк (ошибки записи в приёмник, объяснения отказа в правах на нестандартный каталог).
- **Доступность:** диагностические сообщения об ошибке записи читаются TalkBack; ошибки в логе достаточно структурированы для диагностики без чтения stack trace.
- **Тон сообщений:** новые/изменённые пользовательские строки проходят чек-лист тона из `docs/COMMUNICATION_POLICY.md` (§6) — спокойная формулировка с указанием причины и следующего шага, не алармовая.
- **Атомарность:** видимость файла для внешних наблюдателей (MediaStore, галерея, плеер) — «всё или ничего». Не допускается состояние, в котором наблюдатель видит частично записанный файл под целевым именем.

## 4. Контекст текущей архитектуры

За запись результата сетевой передачи в локальный приёмник отвечает слой стратегий файловых операций: на верхнем уровне — общая стратегия атомарной записи (паттерн «копия → временное имя → переименование»), под ней — протокол-специфичные стратегии (SFTP/SMB/FTP/Cloud), которые внутри своих маршрутов «загрузка в локаль» пишут в назначение через сырой `FileOutputStream`. Этот низкоуровневый путь не учитывает scoped storage: на Android 10+ публичные каталоги (`Music`, `Movies`, `Pictures`, `DCIM`, `Downloads`) недоступны для прямой записи без `MANAGE_EXTERNAL_STORAGE` или `requestLegacyExternalStorage`. В проекте уже есть точки, где локальная запись медиафайлов делается корректно через MediaStore (сохранение кадров, экспорт настроек, сохранение из URL-загрузчика), но эти знания живут в отдельных компонентах и в маршрут «сетевой источник → локаль» не вплетены. Локальная стратегия операций тоже использует MediaStore — но только для собственных локальных копирований, маршрут «сетевой источник → локаль» её не проходит. В итоге `MANAGE_EXTERNAL_STORAGE` в манифесте есть, `requestLegacyExternalStorage` не выставлен, и на API 29 без выставленного legacy-флага типовой сценарий гарантированно не работает.

## 5. Предлагаемый подход

Ввести единую роль «приёмник записи в локальную публичную коллекцию», которая знает про scoped storage и выбирает корректный механизм записи по API уровню и типу каталога. Сетевые стратегии, вместо прямой работы с `FileOutputStream`, делегируют последний участок (открытие потока на запись + закрытие + публикация результата) этому приёмнику. Атомарность сохраняется на уровне приёмника: внешние наблюдатели не видят файл до момента, когда запись успешно завершена.

### 5.1 Основные столпы / модули

- **Приёмник публичной коллекции.** Единая роль, отвечающая за: классификацию назначения (медиа-коллекция / Downloads / частный/произвольный каталог), выбор механизма записи (MediaStore с pending-флагом / private app-specific / SAF — если применимо), открытие потока на запись, фиксацию результата (снятие pending), очистку при ошибке. Возвращает наверх итоговый «видимый» путь/идентификатор для отображения пользователю и хранения в истории.
- **Адаптация атомарной стратегии.** Существующая атомарная стратегия копирования продолжает выполнять роль «успех — это всё-или-ничего», но шаг «открыть выходной поток / переименовать на финальное имя» делегируется приёмнику; промежуточная конкатенация суффикса `*.temp_copy` в публичных коллекциях больше не используется (вместо него — pending-механика MediaStore). Для частных и app-specific каталогов поведение остаётся прежним (`*.temp_copy` + rename).
- **Классификация назначения.** Логика «это публичная медиа-коллекция / Downloads / частный каталог / произвольный пользовательский каталог» — единственное место, где принимается решение о выборе механизма; сетевые стратегии классификацию не повторяют.
- **Диагностика отказа.** При отказе записи в приёмник причина классифицируется (нет прав на нестандартный каталог / системный отказ / переполнение диска) и доходит до UI отдельной категорией, согласованной с уже существующей классификацией сетевых ошибок.

### 5.2 Потоки данных и событий

- Загрузка с сетевого источника → атомарная стратегия копирования → приёмник публичной коллекции (по классификации назначения) → запись через выбранный механизм → публикация результата (для MediaStore — снятие pending) → возврат итогового пути наверх → отображение пользователю.
- При ошибке: приёмник снимает свои промежуточные следы (удаляет pending-запись MediaStore, удаляет `*.temp_copy` в частных каталогах) → атомарная стратегия возвращает наверх категорию ошибки → UI выбирает понятное сообщение.

### 5.3 Точки расширяемости

- Приёмник публичной коллекции — единая абстракция; добавление нового источника (новый сетевой протокол, URL-загрузчик, любой другой контрибьютор файла в локальную папку) не требует знания scoped storage в самом источнике.
- Набор поддерживаемых публичных коллекций расширяется добавлением классификации без переписывания остальных мест.
- Маппинг «тип назначения → механизм записи» — таблица решений, пополняемая при появлении новых сценариев (например, поддержка SAF-выбранного каталога вне публичных коллекций).
- Диагностические категории отказа записи в приёмник пополняются без переписывания UI-маппинга.

## 6. Открытые вопросы / Research items

1. **Граница «публичная коллекция vs произвольный каталог приёмника»**
   - **Вопрос:** считать ли публичной коллекцией только канонические `MediaStore.Audio/Video/Images/Downloads`, или включать сюда же подкаталоги внутри них.
   - **Решение:** публичной коллекцией считается путь, лежащий под любой из канонических медиа-папок `Environment.DIRECTORY_{MUSIC, MOVIES, PICTURES, DCIM, DOWNLOADS, PODCASTS, RINGTONES, NOTIFICATIONS, ALARMS, AUDIOBOOKS}` — включая вложенные подкаталоги, которые пробрасываются в `RELATIVE_PATH`. Вложенные пути поддерживаются API 29+.
   - **Статус:** Resolved — реализуется в Phase 01 (`LocalDestinationClassifier`).

2. **Стратегия для нестандартных пользовательских каталогов**
   - **Вопрос:** что делает приложение, если пользователь выбрал приёмником произвольный каталог вне публичных коллекций и `MANAGE_EXTERNAL_STORAGE` не предоставлен.
   - **Решение:** в этой итерации SAF-пикер не вводится. Если назначение классифицируется как «не-публичный путь», запись выполняется напрямую через `FileOutputStream` (как сейчас); при отказе OS — единая структурированная категория ошибки `LocalDestinationPermissionDenied` + локализованное сообщение с предложением сохранить в публичную коллекцию (Music/Movies/...) или Downloads. Запрос `MANAGE_EXTERNAL_STORAGE` остаётся отдельной зоной ответственности (см. существующий `MainStoragePermissionsHelper`), здесь не дублируется.
   - **Статус:** Resolved — реализуется в Phase 04 (ошибки + строки).

3. **Совместимость с не-медийными типами файлов**
   - **Вопрос:** что делать с произвольным расширением, попадающим под `Music/`/`Movies/`/`Pictures/` по пути, но не классифицируемым системой как медиа.
   - **Решение:** приоритет имеет физический путь. Если назначение классифицировано как `Music/...`, запись идёт в `MediaStore.Audio` коллекцию вне зависимости от MIME. Если MediaStore отклонит вставку (несовместимый MIME), `MediaStoreLocalDestinationWriter` делает повторную попытку через `MediaStore.Files` collection с тем же `RELATIVE_PATH`. MIME извлекается через `MimeTypeMap.getMimeTypeFromExtension()`; если не определяется — `application/octet-stream`.
   - **Статус:** Resolved — реализуется в Phase 01 (`MediaStoreLocalDestinationWriter`).

4. **Сохранение оригинального имени файла**
   - **Вопрос:** допустимо ли, что MediaStore при коллизии добавляет суффикс `(1)` к `DISPLAY_NAME`.
   - **Решение:** коллизия обрабатывается на уровне выше MediaStore. До вызова `insert()` writer проверяет наличие записи через `query` по `DISPLAY_NAME + RELATIVE_PATH`. На совпадении — обращается к существующему механизму overwrite/skip из `AtomicFileOperationStrategy` (флаг `overwrite`): при `overwrite=true` удаляет существующую MediaStore-запись и вставляет новую с исходным именем; при `overwrite=false` возвращает `FileExistsException` (как сейчас). Автоматический MediaStore-суффикс не используется.
   - **Статус:** Resolved — реализуется в Phase 01 (`MediaStoreLocalDestinationWriter`).

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| MediaStore изменяет итоговое имя файла при коллизии (суффикс `(1)`) | Средняя | Расхождение между ожиданием пользователя и фактическим именем; потенциальная порча истории операций | Обрабатывать коллизию явно до публикации; согласовать с существующим шагом «перезаписать?» |
| Pending-запись MediaStore не очищается при сбое процесса | Низкая | «Пустые» записи в галерее, не доступные пользователю | Промежуточная очистка при старте приложения; либо явный TTL для pending-записей; либо проверка/очистка в стандартном фоне |
| Падение производительности при больших файлах (видео) из-за повторной публикации через MediaStore | Низкая | Заметное увеличение времени видимости файла после сетевой передачи | Профилировать на типовых размерах (видео > 1 ГБ); если регрессия — рассматривать прямой контент-URI без re-scan |
| Регрессия в маршрутах копирования внутри локального FS (например, между двумя пользовательскими каталогами) | Низкая | Сломанное поведение для уже работающих сценариев | Чёткое разграничение: приёмник публичной коллекции вызывается только когда назначение классифицировано как публичная коллекция; маршрут «локаль → локаль» вне публичных коллекций остаётся как сейчас |
| Несогласованное поведение между протоколами после внедрения единого приёмника (один протокол использует, другой — нет) | Средняя | Один и тот же баг частично решён, частично остаётся | В рамках тактической реализации — единый порядок перевода всех сетевых стратегий на приёмник; невозможно «закрыть только SFTP» |
| Поведение `MediaStore.Audio` для подкаталогов отличается по версиям API | Средняя | На части устройств файл оказывается не в выбранном пользователем подкаталоге | Открытый вопрос §6.1 — решается на этапе тактической; при невозможности — задокументировать ограничение в FEATURES |

## 9. Архитектурные решения (ADR)

**ADR-1: единый «приёмник публичной коллекции» вместо протокол-специфичных fix'ов**

- **Решение:** ввести единую роль приёмника, которой делегируют запись все сетевые стратегии; протокол-специфичные стратегии перестают сами знать про scoped storage и MediaStore.
- **Альтернативы:** (а) точечно починить только SFTP-путь дублированием MediaStore-кода — оставляет тот же баг в SMB/FTP/Cloud; (б) выставить `requestLegacyExternalStorage="true"` в манифесте — закрывает только API 29 и до первого `targetSdk` bump'а, не решение для API 30+; (в) запрашивать `MANAGE_EXTERNAL_STORAGE` для любого копирования — ухудшает UX и риск с Google Play.
- **Почему:** баг архитектурный (нет единого места знания про scoped storage), решение должно быть архитектурным; единая абстракция переиспользуется в смежных маршрутах (URL-загрузчик, сохранение кадров) и согласована с уже существующим использованием MediaStore в локальной стратегии.

**ADR-2: атомарность через pending-механику MediaStore, а не через `*.temp_copy` в публичных каталогах**

- **Решение:** в публичных коллекциях атомарность обеспечивается атрибутом `IS_PENDING` MediaStore-записи (создаём pending → пишем → снимаем pending = делаем видимым); шаг «промежуточное имя `*.temp_copy` + rename» в публичных коллекциях не используется.
- **Альтернативы:** (а) продолжать `*.temp_copy` + rename — невозможно без `MANAGE_EXTERNAL_STORAGE`; (б) писать в app-specific каталог, потом «публиковать» в MediaStore через `INSERT` с уже готовым файлом — двойная запись большого файла, нагрузка на хранилище.
- **Почему:** pending-механика MediaStore — стандартный канонический путь, дающий атомарность для внешних наблюдателей без обхода scoped storage; не дублирует данные.

**ADR-3: маршрут «локаль → локаль» вне публичных коллекций не меняется**

- **Решение:** существующий путь «копия → `*.temp_copy` → rename» через `FileOutputStream` сохраняется для приватных и app-specific каталогов; приёмник публичной коллекции вызывается только когда классификация назначения дала «публичная коллекция».
- **Альтернативы:** перевести всё на единый механизм через MediaStore — избыточно для приватных каталогов и нарушит работающие сценарии.
- **Почему:** scoped storage касается только публичных каталогов; приватные каталоги пишутся напрямую без ограничений, текущее решение там корректно.

## 10. Связи с другими спеками

- **S0149** (`enh-sftp-permission-denied-message`, Verified) — смежная зона диагностики ошибок SFTP. Этот тикет — про **локальный** EACCES (приёмник), S0149 — про **серверный** отказ SFTP (источник). Категории ошибок в UI должны быть согласованы: «нет прав на сервере» (S0149) и «нет прав на локальный каталог» (S0231) — разные сообщения, оба понятные.

## 11. Критерии готовности (strategic-level)

1. На устройстве с Android 10 (API 29) без `requestLegacyExternalStorage` копирование файла с SFTP в `/storage/emulated/0/Music/` завершается успехом — файл появляется в галерее/плеере под выбранным именем.
2. На устройстве с Android 11+ без `MANAGE_EXTERNAL_STORAGE` копирование файла с SFTP в `/storage/emulated/0/Music/`, `Movies/`, `Pictures/`, `DCIM/`, `Download/` завершается успехом.
3. Перемещение (копия + удаление источника) с SFTP в публичные коллекции работает по той же логике, что и копирование, и не оставляет orphan-следов на источнике или приёмнике при сбое.
4. Аналогичные пользовательские сценарии работают для SMB, FTP и облачных источников — единообразно с SFTP.
5. При попытке копирования в произвольный каталог вне публичных коллекций без необходимых прав пользователь видит понятное сообщение с указанием причины и предлагаемым следующим шагом, а не сырой `EACCES`/`FileNotFoundException`.
6. Внешние наблюдатели (галерея, плеер, MediaStore-индекс) не видят файл до завершения копирования — нет состояния «полузаписанный файл с целевым именем виден приложениям».
7. В логе на каждый отказ записи в приёмник есть одна структурированная запись с указанием категории отказа, целевой коллекции и конкретного относительного пути.
