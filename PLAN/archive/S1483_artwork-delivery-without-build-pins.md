# Стратегическая спецификация: S1483 - Обложки доставлять как каталог, без хешей в сборке

## 1. Проблема

Список трансляций и обложки к нему доставляются двумя разными способами, хотя это данные одного
рода.

Каталог: постоянный адрес, пользователь нажимает «обновить», приложение проверяет структуру (первым
файлом в архиве обязан лежать `streams.csv`, атлас иконок не больше 30 МБ) и импортирует. Пересобрал
каталог - он у всех.

Обложки: набор приколочен хешем SHA-256 в коде приложения, а имя файла на хранилище несёт номер
ревизии. Пересобрал обложки - до людей они не доедут, пока не выйдет новая сборка с новыми хешами.
Хуже того, установленная копия не может даже **узнать**, что появились новые: признак «устарело»
вычисляется сравнением с хешом из своей же сборки. Владелец наткнулся на это 2026-08-07: обновил
каталог на устройстве, а обложки ему не предложили - и не могли.

Итог перевёрнутый: менее ответственные данные (картинки) защищены жёстче, чем более ответственные
(адреса потоков, которые приложение пойдёт воспроизводить).

---

## 2. Откуда взялись хеши

Механизм доставки писался для **нативного кода**: движки OCR, ffmpeg - файлы `.so`, которые
загружаются через `System.load`. Там пин хеша обязателен: подменённый файл - это выполнение чужого
кода. Обложки поехали по тому же пути просто потому, что путь уже был.

Существенно: механизм **не требует** хеша. `PayloadIntegrityVerifier` уже умеет пустой пин - такой
файл проверяется границами размера (нижняя из дескриптора, верхняя 64 МБ). Гейт по источнику
установки тоже касается только нативных наборов (`isNativeCodeSet`). То есть обложки пиновали себя
по своему выбору, а не по требованию системы.

---

## 3. Решение

1. Снять пин с наборов обложек: пустой `sha256`, осмысленные границы размера.
2. Публиковать обложки под постоянным именем, без `-vN` в имени файла, - как `stream-catalog.zip`.
3. Заменить признак «устарело»: сейчас он вычисляется из хеша в сборке, то есть сборка сама себе
   судья. Нужен признак со стороны хранилища - маленький `artwork-manifest.json` по постоянному
   адресу (размеры и время сборки наборов) либо `ETag`/`Last-Modified` самих файлов. Тогда
   пересобранные обложки становятся «доступны к обновлению» у всех сразу, без выпуска приложения.
4. Проверять целостность структурно, как это делает импорт каталога: архив открывается, имена
   записей - числа, число записей сходится с боковым файлом координат. Установка атомарная: сначала
   во временный файл, потом переименование, - чтобы оборванная закачка не стёрла рабочие картинки.
5. Нативные наборы (`OCR_ENGINES`, `FFMPEG_DTS`) остаются пинованными жёстко. Разделение политики по
   типу содержимого - это и есть суть тикета, а не ослабление правил ради удобства.

---

## 4. Что мы теряем

Подменённый или битый архив обложек не будет пойман по хешу. Худшее следствие - неверные или
отсутствующие картинки; выполнения чужого кода тут нет, файлы не исполняются. Ровно такой же риск мы
уже осознанно приняли для самого каталога, где ставка выше: там подмена подсунула бы пользователю
чужие адреса для воспроизведения.

Структурная проверка (пункт 3.4) закрывает случайную порчу - обрыв закачки, усечённый файл.

## 5. Решённые вопросы

**Признак свежести - манифест, а не заголовки HTTP.** `ETag`/`Last-Modified` у ассета релиза GitHub
приходят от хранилища объектов, куда ведёт перенаправление, и не являются частью нашего контракта:
их формат и стабильность мы не контролируем. Манифест - маленький JSON по постоянному адресу, который
пишет тот же скрипт, что публикует наборы, - это наш контракт, его можно проверить и версионировать.
Он же несёт размеры, а значит закрывает и второй вопрос.

**Размер в диалоге - показывать.** Логотипы весят 8 МБ, превью 11 МБ, и сейчас они уходят в закачку
без единого слова о размере. Размер берётся из манифеста, то есть без отдельного запроса.
