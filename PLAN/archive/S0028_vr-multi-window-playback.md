## 1. Проблема

В VR-флейворе на Quest 3 многооконная среда HorizonOS уже сейчас допускает «клонирование» приложения: при открытии стерео-файла иммерсивный плеер открывается **в отдельном окне**, окно Browse при этом не закрывается, а отдельно показывается панельный плеер, и из основного окна можно дальше запускать второй файл — он откроется как ещё одно окно. Эта возможность возникла как побочный эффект архитектуры активити, а не как осознанная фича. У этого две стороны:

**Бытовая (баг):** окна копятся, пользователь должен закрывать каждое отдельно; не понятно, какое из них «главное»; неясно, что произойдёт с фоновой задачей при закрытии Browse-окна, если из него запущена воспроизводящаяся слайдшоу/музыка.

**Полезная (фича):** на VR-устройствах с большим polished-пространством сценарий «слайдшоу фотографий в одном окне + плеер фоновой музыки в другом + основной экран приложения в третьем» — естественен и востребован. Пользователь явно просит это как future-feature: «вынести как отдельную спецификацию для реализации на будущее».

Текущая ситуация: фактическое поведение не поддерживается явно, не задокументировано и не покрыто тестами. Любой рефакторинг лайфцикла активити может случайно убить или, наоборот, сделать менее удобной. Нужно зафиксировать ожидаемое поведение и набор сценариев.

## 2. Цели

1. **Поддержанный сценарий «несколько окон одновременно»** на устройствах с системной поддержкой multi-window (VR, Samsung DeX и аналоги): пользователь может одновременно воспроизводить (a) слайдшоу фото в одном окне, (b) аудио-трек или плейлист в другом, (c) видео в третьем. Каждое окно работает независимо: пауза/возобновление, prev/next, выход — не влияют на остальные.
2. **Настройка-мастер «Разрешить запуск в отдельном окне»** в настройках приложения. По умолчанию включена на VR-флейворе, выключена на остальных. При выключенной настройке все три точки входа скрыты, поведение приложения — обычное.
3. **Три явные точки запуска нового окна:**
   - **Карточка ресурса** (Browse-список): иконка-кнопка «В новом окне» на карточке ресурса. Видима только при включённой настройке. Нажатие → Browse выбранного ресурса открывается в новом окне. Основное окно остаётся на главном экране — оно всегда одно, Browse в нём не открывается.
   - **Верхнее меню Browse** (среди команд «Удалить дубликаты», «Автоматизировать..»): кнопка «В отдельном окне». Нажатие → текущий Browse «отрывается» в новое окно с полным сохранением состояния (текущий ресурс, текущий файл, позиция скролла); в текущем окне происходит back на главный экран. Tear-off.
   - **Меню плеера** (низкий приоритет — в overflow при узкой ширине): кнопка «В отдельном окне» для любого типа файла. Видима только при включённой настройке. Нажатие → плеер открывается в новом окне для того же файла (без передачи позиции воспроизведения); в текущем окне плеер закрывается, происходит back в Browse. Tear-off.
4. **Корректное закрытие окна** не убивает соседние воспроизведения. Закрытие Browse-окна не останавливает запущенный из него аудио-плеер в другом окне, если у того окна свой собственный лайфцикл.
5. **Фоновое аудио во второстепенных окнах** работает: пользователь свернул окно с музыкой, музыка продолжает играть; восстановление окна возвращает к точке.
6. **Состояние ресурса** между окнами синхронизировано на уровне источника данных (Room/DataStore). Изменения, сделанные в одном окне (удалить файл, переименовать ресурс), видны в других без ручного refresh.
7. **Документация для пользователя**: в документацию FEATURES появляется раздел «многооконный режим», описывающий поддержанные сценарии и ограничения.

**Non-goals:**

- Не вводится поддержка стандартного split-screen Android (два приложения бок о бок) — скоп ограничен multi-instance одного приложения.
- Не покрывается одновременное воспроизведение **двух видео** через ExoPlayer в одном процессе с двумя SurfaceView (техническое ограничение Media3 — при HW-конфликте деградация под управлением Media3).
- Не вводится «менеджер окон» внутри приложения — управление окнами остаётся за системой (HorizonOS / Android multi-window).
- Не покрывается распределённая аудио-сцена (spatial audio mixing нескольких источников) — пользователь слышит сумму аудио-выходов.
- Не передаётся позиция воспроизведения при tear-off плеера — пользователь перематывает вручную (намеренное упрощение).

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Главный целевой сценарий: «слайдшоу фото + фоновая музыка + основное окно». Должно работать при включённой настройке.
2. Настройка «Разрешить запуск в отдельном окне» — мастер-переключатель. По умолчанию включена на VR; на устройствах с Android multi-window (Samsung DeX, складные, планшеты в оконном режиме) — выключена, пользователь включает вручную.
3. Три точки входа (карточка ресурса, верхнее меню Browse, overflow меню плеера) покрывают основные сценарии без лишней сложности.
4. Browse tear-off: в новое окно передаётся полное состояние (текущий ресурс, текущий файл, позиция скролла). В текущем окне происходит back на главный экран.
5. Player tear-off: в новое окно передаётся только файл. Позиция воспроизведения не передаётся — слишком сложно; пользователь перематывает сам. В текущем окне закрывается плеер, происходит back в Browse.
6. Желательно, чтобы окна выглядели как разные «приложения» в трее Quest 3 (разный заголовок, разная иконка-индикатор) — не «три копии одной программы».
7. Фича доступна не только на VR: любое устройство с Android multi-window поддержкой может её включить. VR — первый и главный случай с enabled-дефолтом.

### 3.2 Жёсткие ограничения

- **Flavor:** VR-флейвор (primary) плюс любая сборка на устройстве с системной multi-window поддержкой, определяемой через Android API во время выполнения. Manifest-изменения — в VR-флейворе; runtime-gate через системный API — для остальных.
- **API level:** без новых API-зависимостей; используются стандартные Android-механизмы task affinity / launchMode / multi-instance.
- **Wear OS:** не затрагивается.
- **Производительность:** одновременная работа трёх окон (фото-слайдшоу + аудио + UI) не должна давать просадки FPS ниже 72 в активном иммерсивном окне; фоновые окна допустимо ставить на пониженный priority.
- **Совместимость данных:** между окнами разделяется один Room-DB и один DataStore. Конфликтные записи (например, два окна одновременно меняют sortMode ресурса) разрешаются last-writer-wins с обновлением UI.
- **Локализация:** все новые строки UI (команда «открыть в новом окне», пункт документации) — EN/RU/UK.
- **Доступность:** все три точки входа «В отдельном окне» доступны с контроллера и hand-tracking (там где S0007 поддерживает).

## 4. Контекст текущей архитектуры

Приложение собрано как single-task Android-приложение: главный экран → Browse-экран → экраны плеера (панельный и иммерсивный) живут в одном task'е по умолчанию. На Quest 3 HorizonOS позволяет запустить второй экземпляр приложения через системное меню; технически это второй процесс или второй task — точное поведение определяется launchMode и taskAffinity манифеста.

Текущее поведение «второе окно появляется при открытии стереофайла» — следствие того, что иммерсивный плеер-экран запускается с флагами intent'а, заставляющими систему создать новую task (вероятно флаг создания новой задачи или специальный launchMode). Это не задокументировано, не контролируется и не покрыто тестами.

Состояние приложения — Room-DB + DataStore + in-memory ViewModel. Между процессами Room и DataStore делятся (это observed via SharedPreferences/DataStore single-process model — нужна проверка), ViewModel — нет. Сейчас экраны не рассчитаны на одновременную работу: например, репозиторий состояния возобновления хранит «последний открытый файл» в одной записи, что в multi-window даст конфликт.

Аудио в фоне технически возможно через сервис медиасессии — приложение уже использует Media3, но текущая реализация привязывает плеер к лайфциклу активити. Закрытие активити — остановка плеера.

## 5. Предлагаемый подход

Подход разделён на шесть блоков: настройка-мастер, декларация manifest, изоляция состояния, фоновое аудио, три явные точки UI, документация.

### 5.1 Основные столпы / модули

**Настройка-мастер «Разрешить запуск в отдельном окне».**
Новый boolean-параметр в настройках приложения. Дефолт по флейвору: VR — `true`, остальные — `false`. При `false` все три точки входа (§2.Цель 3) не отображаются — поведение идентично текущему. При `true` точки входа видны при условии, что устройство поддерживает multi-window (runtime check через Android API). Детали API-проверки — задача тактической спеки (§6 Q6).

**Manifest declaration of multi-instance support.**
В манифесте VR-флейвора экраны, которые могут жить в нескольких экземплярах (Browse, слайдшоу фото, аудио-плеер, иммерсивный плеер), помечаются атрибутами multi-instance (launchMode, affinity). Конкретные значения — задача тактической спеки. Цель: HorizonOS получает от приложения явный сигнал «этот экран может быть multi-instance».

**Изоляция per-window state.**
ViewModel и in-memory кэш плеера/слайдшоу — per-instance активити. Глобальные репозитории состояния расширяются ключом-идентификатором окна — каждое окно имеет свою запись «последний файл», «текущий ресурс», «позиция воспроизведения». Это требует миграции Room-схемы (детали — в тактике).

**Фоновое аудио через сервис медиасессии.**
Аудио-плеер и аудио-режим слайдшоу (если у пользователя включён background-music) выносятся в сервис медиасессии, лайфцикл которого не привязан к активити. Закрытие окна — это остановка UI окна, но сервис продолжает играть, пока пользователь не нажал «стоп» в системном пультовом меню или явно не закрыл сервис из приложения.

**Три явные точки запуска «В отдельном окне».**

*Точка 1 — карточка ресурса:* иконка-кнопка на карточке ресурса в Browse-списке. Видима только при включённой настройке. Нажатие → Intent с флагами new-task, открывает Browse выбранного ресурса в новом окне. Текущее окно остаётся на главном экране.

*Точка 2 — верхнее меню Browse (tear-off):* элемент в меню Browse рядом с «Удалить дубликаты», «Автоматизировать..». Видим только при включённой настройке. Нажатие → упаковывает текущее состояние (ресурс, файл, позиция скролла) в Intent extras, открывает новое окно с этим состоянием; в текущем окне вызывается back (возврат на главный экран). Tear-off.

*Точка 3 — overflow меню плеера (tear-off):* элемент в меню плеера с низким приоритетом (в overflow при узкой ширине). Видим только при включённой настройке. Нажатие → Intent с путём файла, открывает плеер в новом окне без позиции воспроизведения; в текущем окне плеер закрывается, происходит back в Browse. Tear-off.

Все три точки скрыты, если настройка выключена или runtime-проверка multi-window вернула `false`.

**Поведение при дубликате.**
Пользователь открывает файл, уже играющий в другом окне: открывается ещё одно окно без каких-либо проверок (§6 Q1 Resolved).

### 5.2 Потоки данных и событий

```text
── Точка 1: карточка ресурса ──────────────────────────────────────────
User → tap "В новом окне" on resource card
        │
        ▼
Intent (new-task, target=Browse, resource-id)
        │
        ▼
System creates new window → Browse initialises at resource root
Current window stays at Home screen

── Точка 2: верхнее меню Browse (tear-off) ────────────────────────────
User → tap "В отдельном окне" in Browse top menu
        │
        ▼
Pack state (resource-id, current-file, scroll-position) into Intent extras
Intent (new-task, target=Browse, full state)
        │
        ▼
System creates new window → Browse restores state from Intent
Current window → back() → Home screen

── Точка 3: overflow меню плеера (tear-off) ───────────────────────────
User → tap "В отдельном окне" in player overflow
        │
        ▼
Intent (new-task, target=Player, file-path only — no position)
        │
        ▼
System creates new window → Player starts at beginning of same file
Current window → player closes → back() → Browse

── Общий хвост для всех трёх ──────────────────────────────────────────
New window initialises with window-id (saved in instance state)
        │
        ▼
Per-window ViewModel + per-window resume-state entry
        │
        ▼
For audio/slideshow background: bind to background media service
        │
        ▼
User closes window → service keeps playing if media session still active
```

### 5.3 Точки расширяемости

- Новый тип «окна» (например, выделенный аудио-плейлист с визуализацией) добавляется как новый экран в манифесте без изменений в существующих окнах.
- Если в будущем понадобится «переключить фокус на существующее окно вместо нового» — добавляется как опция в settings, но дефолт остаётся «новое окно».
- Если HorizonOS добавит API «снять snapshot окна для миниатюры» — он подключается без изменения core логики приложения.

## 6. Открытые вопросы / Research items

1. **Поведение при дубликате окна для одного и того же файла.**
   - **Вопрос:** «открыть в новом окне» файл, уже играющий в другом окне, — открывает ещё одно окно или переключает фокус?
   - **Варианты:** (a) всегда новое окно (полный multi-instance); (b) переключить фокус на существующее (singleTop-like для конкретного файла); (c) опция в settings с дефолтом (a).
   - **Ответ:** вариант (a) — всегда новое окно без каких-либо проверок на дубликат.
   - **Статус:** Verified

2. **Два видео одновременно через ExoPlayer.**
   - **Вопрос:** Media3 ExoPlayer в одном процессе допускает несколько одновременных экземпляров с разными SurfaceView, но при ограниченных аппаратных декодерах (Quest 3 ≈ 2 H.265 hardware decoders) возможны конфликты. Можно ли позволить два видеоокна?
   - **Варианты:** (a) запретить два видео одновременно (одно в видео-окне, остальные в фото/аудио); (b) разрешить, fallback на программный декодер при дефиците; (c) разрешить только если пользователь явно подтвердил.
   - **Ответ:** разрешить без ограничений и без отслеживания — пользователь осознанно открыл второе окно. При HW-конфликте вероятно один из плееров встанет на паузу сам. Без явного предупреждения.
   - **Статус:** Verified

3. **Per-window state vs global state.**
   - **Вопрос:** что такое «глобальное» состояние (одно на всё приложение) vs «оконное» (на окно)?
   - **Ответ (обновлён 2026-05-04):** Browse теперь может быть в отдельном окне (Точки 1 и 2). Оконное состояние Browse: ресурс, текущий файл, позиция скролла — передаётся при tear-off через Intent extras. Оконное состояние плеера: только текущий файл — позиция не передаётся (намеренное упрощение, см. Non-goals §2). Глобальное: настройки приложения, тема, тумблеры, sort-режим. Из Browse-окна переход в настройки возможен; из плеера в отдельном окне — нет.
   - **Статус:** Verified

4. **Сервис медиасессии vs воспроизведение, привязанное к экрану, для VR-плеера.**
   - **Вопрос:** иммерсивный плеер-экран нельзя свернуть в фон без выхода пользователя из VR-сцены. Имеет ли смысл сервис медиасессии для VR?
   - **Варианты:** (a) только аудио и слайдшоу через сервис медиасессии; VR-видео всегда foreground; (b) VR-видео тоже через сервис медиасессии (для возможности фоновой паузы).
   - **Ответ:** вариант (a) — приоритет стабильности. Аудио и слайдшоу фото — через сервис медиасессии. VR-видео (иммерсив) — всегда foreground, привязан к активити. Сложные сценарии с OpenXR background-lifecycle — вне скопа.
   - **Статус:** Verified

5. **Закрытие Browse-окна и его последствия.**
   - **Вопрос:** Browse-окно — «корневое»? Если пользователь его закрыл, остальные окна остаются жить? Или Browse — это «launcher», без него процесс умирает?
   - **Варианты:** (a) каждое окно независимо, Browse не привилегировано; (b) Browse — launcher, при его закрытии остальные тоже завершаются (предупреждение пользователю).
   - **Ответ:** вариант (a) — каждое окно полностью независимо. Browse-окно можно закрыть и снова открыть; плеер-окна продолжают работать. Browse не имеет привилегированного статуса.
   - **Статус:** Verified

6. **Определение поддержки multi-window на не-VR-устройствах.**
   - **Вопрос:** как во время выполнения определить, что устройство поддерживает multi-window на флейворах без VR-manifest-флагов? Достаточно ли `ActivityManager.isInMultiWindowMode()`? Нужны ли дополнительные проверки для Samsung DeX?
   - **Варианты:** (a) `isInMultiWindowMode()` — определяет текущий момент, но не возможность в принципе; (b) `PackageManager.hasSystemFeature(FEATURE_PC)` / Samsung DeX API (`android.app.UiModeManager`); (c) показывать настройку всегда, пользователь решает — упрощает код, но показывает опцию там, где ничего не произойдёт.
   Ответ: далать аккуратно , без крашей с андроид 8.1. Ничего страшного если функция будет видна и выключена на устройстве, где мультиоконности нет. Главное в таком случае пользователю не ошибку выводить,а предупреждение почему этот тут не сработало.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
| ------ | :-----------: | ------------- | ----------- |
| Multi-instance экранов ломает состояние Room/DataStore (writer-conflicts, race) | Высокая | Удаление файла в одном окне «возвращает» файл в списке другого | Все mutations через Repository-слой с in-memory invalidation; Flow-based UI получает обновления автоматически |

| Репозиторий состояния возобновления хранит «последний файл» одной записью — окна перезаписывают друг друга | Высокая | После закрытия и открытия окна оно показывает файл, открытый в другом окне | Миграция: состояние возобновления per-window; ключ — идентификатор окна |

## 10. Архитектурные решения (ADR)

**ADR-1: Multi-instance — явная фича, через manifest declarations.**

- **Решение:** в манифесте VR-флейвора экраны, поддерживающие multi-instance, помечаются явно. Случайное «второе окно» через intent-флаги — больше не сценарий.
- **Альтернативы:** (а) оставить случайное multi-instance — отвергнуто, потому что не контролируется и не тестируется; (б) полностью запретить multi-instance — отвергнуто, противоречит запросу пользователя.
- **Почему:** контроль через manifest даёт детерминированное поведение и проверяется на стадии сборки.

**ADR-2: Фоновое аудио через сервис медиасессии — отвязано от активити.**

- **Решение:** аудио-плеер и фоновая музыка слайдшоу живут в сервисе, лайфцикл которого не привязан к активити. Закрытие окна не останавливает фоновое аудио.
- **Альтернативы:** (а) аудио в активити — отвергнуто, потому что закрытие окна = остановка музыки; (б) глобальный singleton-плеер — отвергнуто, не масштабируется на несколько окон.
- **Почему:** сервис медиасессии — стандартный Android-механизм для фоновой медиапотоковой работы; интегрируется с системным «media-pult» Quest 3.

**ADR-3: Per-window state через идентификатор окна в репозиториях.**

- **Решение:** репозитории состояния расширяются полем-ключом идентификатора окна. Каждое окно имеет свою запись.
- **Альтернативы:** (а) глобальное состояние — отвергнуто, окна перезаписывают друг друга; (б) state в ViewModel без персистенции — отвергнуто, не переживает recreate.
- **Почему:** идентификатор окна — стабильный ключ на жизнь экрана; persists через recreate; естественно ложится в Room.

**ADR-4: Все точки входа «В отдельном окне» управляются единой настройкой и runtime-проверкой.**

- **Решение:** настройка «Разрешить запуск в отдельном окне» — мастер-переключатель. Все три точки входа видимы только при включённой настройке И при положительном результате runtime-проверки multi-window поддержки (§6 Q6). По умолчанию: включена на VR-флейворе, выключена на остальных.
- **Альтернативы:** VR-only через BuildConfig — отвергнуто: Samsung DeX и другие multi-window устройства получают реальную пользу; управление через BuildConfig не позволяет пользователю явно включить фичу.
- **Почему:** runtime detection + настройка даёт гибкость без захламления UI на non-multi-window устройствах. VR — first-class use case с enabled-дефолтом.

**ADR-5: Browse tear-off передаёт полное состояние через Intent extras.**

- **Решение:** при tear-off из верхнего меню Browse текущий ресурс, файл и позиция скролла упаковываются в Intent extras. Новое окно инициализируется с этим состоянием. Текущее окно вызывает back на главный экран.
- **Альтернативы:** (a) новое окно начинает с корня ресурса — отвергнуто, теряет контекст пользователя; (b) shared state через DataStore — отвергнуто, несёт риск race condition и лишнюю сложность.
- **Почему:** Intent extras — стандартный Android-механизм передачи состояния при запуске активити; данных немного, размер в пределах Binder limits.

**ADR-6: Player tear-off не передаёт позицию воспроизведения.**

- **Решение:** при tear-off из overflow меню плеера в Intent передаётся только путь файла. Новый плеер стартует с начала. Пользователь перематывает вручную.
- **Альтернативы:** передавать позицию через Intent extras — отвергнуто: для стриминговых источников и части форматов позиция может быть невалидна или задержана; реализация непропорционально сложна.
- **Почему:** простота реализации; основной сценарий tear-off плеера — «хочу смотреть этот файл в другом окне», а не «перенести текущую позицию». Явно задокументировано в Non-goals.

## 12. Критерии готовности (strategic-level)

1. Настройка «Разрешить запуск в отдельном окне» присутствует в настройках приложения; по умолчанию включена на VR, выключена на остальных; при выключении все три точки входа скрыты, поведение — как без фичи.
2. **Точка 1 (карточка ресурса):** нажатие иконки «В новом окне» на карточке ресурса открывает Browse этого ресурса в новом окне; основное окно остаётся на главном экране.
3. **Точка 2 (меню Browse, tear-off):** нажатие «В отдельном окне» в верхнем меню Browse открывает новое окно с тем же ресурсом, файлом и позицией скролла; в текущем окне происходит back на главный экран.
4. **Точка 3 (overflow плеера, tear-off):** нажатие «В отдельном окне» открывает новое окно с тем же файлом (без позиции воспроизведения); в текущем окне происходит back в Browse.
5. Сценарий «слайдшоу фото в окне A + аудио-плейлист в окне B + Browse в окне C» работает одновременно: переключение фокуса не останавливает остальные.
6. Закрытие любого окна не останавливает воспроизведение в остальных окнах.
7. Per-window состояние возобновления: открыть файл в окне A, открыть другой файл в окне B; закрыть B и открыть его заново — окно B восстанавливает свой файл, не файл A.
8. Документация раздела «Multi-Window Mode» в EN/RU/UK содержит описание поддержанных сценариев (включая три точки входа) и ограничений (позиция плеера не передаётся).
9. Одновременное открытие двух видеоокон разрешено и не блокируется приложением; поведение при HW-конфликте декодеров определяет Media3.
10. На устройстве с Android multi-window (не-VR: Samsung DeX или аналог) настройка доступна для ручного включения; после включения все три точки входа работают.
