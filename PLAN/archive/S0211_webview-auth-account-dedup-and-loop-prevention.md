## 1. Проблема

Пользователь, поделившийся ссылкой на пост Instagram, который не поддаётся извлечению ни одной стратегией (например, слот карусели `?img_index=N`), попадает в бесконечный цикл «Войдите снова» в WebView. Сессия в WebView и в `EncryptedCookieStore` валидна, аккаунт реально залогинен — пользователь видит себя в окне браузера, но приложение всё равно настаивает на повторном входе. Каждый круг повторной авторизации создаёт новый дубликат «Аккаунт по умолчанию» в БД: лог зафиксировал четыре параллельные записи для `www.instagram.com` за два теста.

Сам loop уже обрезан простой правкой воркера (worker-нотификация «Sign in» теперь не показывается при `hadExistingSession=true`). Но остаются:

- БД пользователя уже засорена дубликатами и продолжит засоряться, если повторная авторизация случится по легитимной причине (приватный пост, истёкшие куки).
- Reauth-диалог не показывает, какой аккаунт уже привязан к host — пользователь не понимает, что приложение видит его существующую сессию.
- Сообщение об ошибке в нотификации звучит как «Ошибка загрузки», хотя реальная ситуация — «не удалось извлечь содержимое страницы, но вход не нужен».

Все три точки касаются noLegal-фичи скачивания по ссылке (умбрелла S0156).

---

## 2. Цели

1. Повторный WebView-логин для уже сохранённого host+identity обновляет существующую запись (`accountId` сохраняется, куки и UA перезаписываются), а не создаёт новый UUID.
2. Существующие дубликаты для одной и той же host+identity у пользователя схлопываются при первом запуске после апдейта (one-shot cleanup, идемпотентный, без потери ни одного физического аккаунта).
3. Reauth-диалог называет конкретный аккаунт, который уже привязан к host, если такой найден — вместо обезличенного `account=unknown` в логе и пустой формулировки в UI.
4. Нотификация при `SocialPreviewOnly` с валидной сессией говорит правду: «не удалось извлечь содержимое страницы (вход в аккаунт не требуется)». Текст отличим от честного «ошибка загрузки» и не подталкивает к повторной авторизации.

**Non-goals:**

- Извлечение слотов карусели Instagram `?img_index=N` и других IG/Threads-image-сценариев — это S0197.
- Поведение эвристики `previewOnlyMeansLogin = true` для Instagram — оставляется как есть. Эта эвристика правильна для случаев, когда сессия отсутствует или истекла; ложноположительные срабатывания при валидной сессии уже обработаны worker-фиксом.
- Multi-account UX (выбор «войти под другим аккаунтом» при наличии существующего) — отдельный сценарий, не покрывается этой спекой. Текущая модель «один аккаунт на host» сохраняется, dedup — это про предотвращение дублей одной и той же реальной личности, а не про управление несколькими разными.
- Кросс-платформенные identity (`facebook.com` и `instagram.com` имеют общий `c_user`/`ds_user_id` через Meta SSO) — оставляем разделёнными по host.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Cleanup существующих дубликатов идёт без диалогов с пользователем — это инфраструктурная санация, а не визуальный сценарий.
2. Сообщение в нотификации проходит `docs/COMMUNICATION_POLICY.md` checklist (§6): без обвинений пользователя, без призыва «попробуйте ещё раз», объясняет ситуацию одной фразой.
3. Если у host нет известного стабильного identity-cookie (платформа вне списка), повторный логин ведёт себя как сейчас — новый UUID. Это безопасный fallback.

### 3.2 Жёсткие ограничения

- **Flavor:** noLegal (фича link-download — часть умбрелы S0156). Standard/lite/photos/legacy/VR не затрагиваются. Реализация следует `dev/FLAVOR_DEVELOPMENT_RULES.md`: интерфейсы и общая логика в `src/main/`, специфика хранилища/харвестера — там же (фича целиком noLegal). Никаких `BuildConfig.IS_NO_LEGAL_FLAVOR` проверок внутри `src/main/` не добавляется.
- **API level:** без специфики — работает на всём поддерживаемом диапазоне noLegal.
- **Wear OS:** не затрагивается.
- **Производительность:** lookup существующего аккаунта по identity выполняется в IO-диспетчере, без блокировки UI. Один lookup на каждый успешный WebView-save. Cleanup-миграция выполняется один раз при первом запуске после апдейта, не на каждом старте.
- **Совместимость данных:** существующие данные пользователя должны быть сохранены — ни один уникальный физический аккаунт не теряется при cleanup. Если в БД есть две записи для одной host+identity, остаётся та, что использовалась позже (`lastUsedAt`), остальные удаляются вместе с их куками. Если identity невозможно вытащить (старые записи без сохранённого identity-cookie или для платформ без known identity-cookie) — запись остаётся нетронутой.
- **Локализация:** EN/RU/UK — обязательно для новой строки нотификации. Audit через `scripts/check_strings_localized.ps1`.
- **Доступность:** новая строка нотификации читается TalkBack-ом штатно (системный канал нотификаций уже доступен), доп. требований нет.
- **Communication policy:** новая user-visible строка проходит tone checklist `docs/COMMUNICATION_POLICY.md` §6 — без жёстких CTA, без обвинений.

## 4. Контекст текущей архитектуры

Скачивание по ссылке — это многослойная цепочка: share-Activity → координатор стратегий → стратегии извлечения (yt-dlp / cheap HTML / dynamic WebView) → пакетный или одиночный путь сохранения. Авторизация — отдельная подсистема: per-host хранилище зашифрованных кук + UI-фасад для логина через WebView. Сейчас они связаны через flag `hadExistingSession` в `SocialPreviewOnly` и через `accountId` в input data воркера.

Хранилище аккаунтов — host-scoped: ключ записи — пара (host, accountId), где accountId — это сгенерированный UUID. У записи есть displayName, набор кук, UA, метки `savedAt` и `lastUsedAt`. Когда WebView возвращает свежие куки, фасад логина просто вызывает «сохранить под новым UUID» — не пытаясь сопоставить с уже существующей записью для того же host.

Stable-identity концепции в хранилище сейчас нет: extractor для display-name умеет читать `username` / `ds_user` / `twid`, но возвращает их как локализуемый ярлык, не как ключ дедупликации. Чтобы понять «это та же физическая личность?», нужно либо хранить identity отдельно (новое поле записи), либо вычислять его на лету из кук.

Reauth-диалог получает host в момент показа и не пытается резолвить «а какой у меня уже аккаунт для этого host». Соответственно, заголовок диалога обезличен.

## 5. Предлагаемый подход

Ввести понятие **стабильного identity аккаунта внутри host** — извлекаемого из cookie-набора по платформо-зависимому правилу. Identity становится дедупликационным ключом для всех операций «сохранить сессию из WebView». Уже сохранённые записи поддерживают тот же ключ через one-shot миграцию.

### 5.1 Основные столпы / модули

**Pillar A — Identity extractor.**
Параллельно display-name экстрактору вводится identity-экстрактор: на вход cookie-набор, на выход стабильная строка-идентификатор для известных платформ (Instagram/Threads/Facebook → `ds_user_id`/`c_user`; X → `twid` без префикса `u=`) или null для неизвестных. Это чистая функция, без побочных эффектов, доступная и UI-слою (диалог логина), и data-слою (миграция).

**Pillar B — Upsert вместо insert при WebView-save.**
Логика «сохранить сессию из WebView» расширяется: перед генерацией нового UUID — поиск существующей записи для (host, identity). Если найдена — обновить куки/UA/displayName/`lastUsedAt`, accountId не меняется. Если не найдена или identity=null — текущее поведение (новый UUID). Результат всё ещё возвращается через тот же канал (resultBundle с accountId).

**Pillar C — One-shot cleanup существующих дубликатов.**
Идемпотентная процедура, выполняемая один раз при первом запуске после апдейта. Алгоритм: для каждого host собрать все записи → сгруппировать по identity (если identity вытаскивается из сохранённых кук); внутри группы оставить запись с максимальным `lastUsedAt` (или `savedAt`, если `lastUsedAt` null), остальные удалить. Записи без вычислимого identity не трогаются. Прогресс/результат логируются Timber-ом для диагностики.

**Pillar D — Reauth-диалог называет существующий аккаунт.**
Если для host уже есть аккаунт (после dedup — единственный или последний-использованный), его displayName подставляется в заголовок диалога: «Вы вошли как <name>. Войти снова или обновить вход?» вместо безымянного «Войти на <host>». Лог-строка `auth dialog shown` тоже получает резолв имени вместо `account=unknown`.

**Pillar E — Честная нотификация при `SocialPreviewOnly + hadExistingSession`.**
Текущее сообщение «Ошибка загрузки» (заимствованное у ветки isDismissed) заменяется на отдельную строку: «Не удалось извлечь содержимое страницы. Вход в аккаунт не требуется.» Тон — нейтральный, без призыва к действию. EN/RU/UK.

### 5.2 Потоки данных и событий

```
WebView login успешно собирает куки
    ↓
UI-фасад вызывает: identity = extractIdentity(cookies, host)
    ↓
data-слой: existingAccount = lookup(host, identity)
    ├── identity == null или not found → insert(новый UUID, ...) ← текущее поведение
    └── found → update(existingAccount.accountId, ...)
    ↓
resultBundle.accountId = (новый UUID | existingAccount.accountId)
    ↓
Worker / Activity получают accountId как раньше
```

```
Первый запуск после апдейта
    ↓
Cleanup-процедура: для каждого host → группировка по identity → keep last-used, delete rest
    ↓
Marker «cleanup выполнен» сохраняется; следующий запуск процедуру не повторяет
```

```
Reauth-диалог открывается для host
    ↓
UI читает existingAccount = listAccountsForHost(host).maxBy { lastUsedAt }?
    ↓
Заголовок: «Вы вошли как <displayName>. Войти снова?» (если есть) | «Войти на <host>» (если нет)
    ↓
Лог: `auth dialog shown type=reauth account=<displayName|none> host=<host>`
```

### 5.3 Точки расширяемости

- Список платформ с известным identity-cookie оставляется открытым на дополнение (Pinterest, Reddit, TikTok — если у них есть стабильный идентификатор в куках, добавляется по факту необходимости).
- Identity-экстрактор — чистая функция, тест-покрытие unit-уровнем, без зависимостей от storage.
- Cleanup-маркер «выполнено» — отдельная семантика, может пригодиться для других one-shot data-санаций (паттерн повторяемый).
- Решение «хранить identity как поле записи или вычислять на лету из cookieSet» оставляется открытым (§6 #1) — оба варианта совместимы с этим подходом.

## 6. Открытые вопросы / Research items

1. **Хранение identity: persisted column vs. computed.**
   - **Вопрос:** добавлять ли в запись аккаунта поле `stableIdentity` (Room-миграция), или вычислять identity на лету из сохранённых кук при каждом lookup?
   - **Варианты:** (а) добавить колонку, заполнить при cleanup и при последующих save; (б) хранить только cookieSet, identity вычислять каждый раз при lookup.
   - **Нужно выяснить:** стоимость lookup на лету при N аккаунтов (N мало — десятки), сложность миграции, риск рассинхрона если cookieSet обновится без обновления column.
   - **Статус:** Open — гипотеза «вычислять на лету» предпочтительнее: меньше схема-изменений, нет риска рассинхрона; миграция нужна только для cleanup, и она читает куки напрямую. Пересмотр — если профилирование покажет lookup-bottleneck.

2. **Идемпотентность cleanup-маркера.**
   - **Вопрос:** где хранить marker «cleanup S0211 уже выполнен»? Отдельная shared-pref, поле в `DataStore`, или версионная метка в самой БД?
   - **Варианты:** SharedPreferences (просто, изолировано); Room migration (выполнится один раз гарантированно, но требует bump версии); on-startup task с собственным версионным маркером в DataStore.
   - **Нужно выяснить:** есть ли уже в проекте устоявшийся паттерн one-shot data-санации.
   - **Статус:** Open — выбор отложен до tactical-фазы.

3. **Что делать с записями без вычислимого identity.**
   - **Вопрос:** если у старой записи нет identity-cookie в сохранённом cookieSet (например, кука была отфильтрована при сохранении, или платформа не из known-списка) — что делает cleanup?
   - **Варианты:** (а) оставить запись как есть, дублей в неё не сольётся; (б) удалить как «бесхозную», если для этого host есть другая запись с identity; (в) запросить у пользователя.
   - **Нужно выяснить:** реальная вероятность таких записей в продакшене.
   - **Статус:** Open — дефолт (а): оставить нетронутой, безопаснее всего. Пересмотр после анализа реальных БД.

4. **Поведение при несовпадении identity на повторном логине.**
   - **Вопрос:** пользователь имел аккаунт A для `instagram.com`, в WebView вошёл как B (другой аккаунт). identity отличается. Что происходит?
   - **Варианты:** (а) создать новую запись (рядом с A), как сейчас — но это «multi-account», который non-goal; (б) перезаписать A; (в) спросить пользователя.
   - **Нужно выяснить:** редкий ли это сценарий, можно ли проигнорировать. Текущая модель «один аккаунт на host» не предусматривает (а), но и (б) рискованно — пользователь не предупреждён.
   - **Статус:** Open — дефолт: (а) создать новую запись, как сейчас. Multi-account UX не входит в спеку, но dedup не должен ломать сценарий «у меня действительно два аккаунта». Пересмотр — если пользователи попросят явный multi-account.

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Cleanup удалит легитимный аккаунт | Низкая | Пользователь теряет вход для host, нужно логиниться заново | Cleanup keep-last-used гарантирует, что самая свежая запись остаётся; identity-группировка не схлопывает разные физические личности. Логируется список удалённых записей. |

## 9. Архитектурные решения (ADR)

**ADR-1: Identity как дедупликационный ключ.**

- **Решение:** для host из known-списка ключ дедупликации = пара (host, identity-cookie-value). Identity — это значение известной по платформе cookie (`ds_user_id`, `c_user`, `twid` ..). Для host вне списка identity = null, дедуп не выполняется.
- **Альтернативы:** (а) ключ = displayName (хрупко — пользователь может переименовать); (б) ключ = hash от полного cookieSet (хрупко — сессия меняется при каждом логине, sessionid отличается).
- **Почему:** identity-cookie — это серверный стабильный ID конкретной личности на конкретной платформе. Он не меняется между сессиями для одной и той же учётки. Это самый надёжный сигнал «это та же физическая личность».

**ADR-2: One-shot cleanup, не background-job.**

- **Решение:** дедупликация существующих записей выполняется один раз при первом старте после апдейта, синхронно с инициализацией хранилища. Маркер «выполнено» предотвращает повторное выполнение.
- **Альтернативы:** (а) periodic background cleanup; (б) cleanup при каждом запуске; (в) опциональная команда в дев-меню.
- **Почему:** проблема одноразовая — дубли уже сидят в БД от старых билдов, новые не создаются после Pillar B. Periodic/each-start — overkill. One-shot простой и достаточный.

**ADR-3: Identity вычисляется на лету, не хранится как column (предварительно).**

- **Решение:** identity извлекается из cookieSet при необходимости, не сохраняется как отдельное поле записи. Cleanup-миграция тоже читает identity из cookies на лету.
- **Альтернативы:** добавить колонку `stableIdentity` в Room-сущность с миграцией.
- **Почему:** меньше schema-изменений, нет риска рассинхрона между column и реальным cookie-набором. Пересмотр — если профилирование покажет lookup-bottleneck при N → большом (сейчас N ≤ десятки, lookup тривиален). См. §6 #1.

## 11. Критерии готовности (strategic-level)

1. На устройстве: пользователь шерит ссылку Instagram при валидной сохранённой сессии и получает понятную нотификацию о невозможности извлечения, без «Sign in»-кнопки и без появления второго аккаунта в БД.
2. На устройстве: пользователь принудительно делает reauth для host с существующим аккаунтом — после успешного сохранения сессии общее число аккаунтов для этого host не растёт, а displayName/куки/UA существующей записи обновляются.
3. На устройстве: пользователь с засорённой БД (≥ 2 дубликата для одного host+identity) запускает обновлённое приложение — после первого старта в `EncryptedCookieStore` остаётся одна запись на host+identity, остальные удалены, реальный аккаунт пользователя продолжает работать.
4. На устройстве: reauth-диалог для host с существующим аккаунтом показывает displayName этого аккаунта в заголовке; для host без существующего аккаунта — generic-формулировку.
5. На устройстве: повторный запуск приложения после п.3 не повторяет cleanup (марker сохранён).
6. На устройстве: шеринг ссылки на хост без known identity-cookie (например, произвольный медиа-портал) после reauth ведёт себя как раньше — новый UUID, отдельная запись.
7. Текст новой нотификации в EN/RU/UK проходит `scripts/check_strings_localized.ps1` без ошибок и соответствует tone-checklist `docs/COMMUNICATION_POLICY.md` §6.
