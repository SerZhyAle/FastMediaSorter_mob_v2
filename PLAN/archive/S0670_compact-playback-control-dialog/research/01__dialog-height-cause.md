# Research 01 - Причина чрезмерной высоты диалога

**Spec:** S0670
**Item:** §6.1
**Status:** Resolved
**Date:** 2026-06-24

## Вопрос

Почему диалог управления плеером занимает почти всю высоту экрана даже на разреженных вкладках?

## Находки (портрет, `res/layout/dialog_playback_control.xml`)

Высота диалога = `max(высота рейла, высота контента активной вкладки)` из-за компоновки:

- `MaxHeightLinearLayout` (горизонтальный) содержит рейл-ScrollView, разделитель и контент-ScrollView, все с `layout_height="match_parent"`.
- Рейл - вертикальный `MaterialButtonToggleGroup` из 7 кнопок с `minHeight="56dp"` → пол высоты ≈ 392dp, пока показаны все вкладки.
- Контент-ScrollView с `match_parent` растягивается до высоты рейла → под коротким контентом остаётся пустота (видно на скриншоте 3D-вкладки).
- Слайдеры Громкость/HUE/Яркость/Скорость - вертикальные `VerticalSeekBar` с фиксированной `layout_height="200dp"` → доминируют в высоте этих вкладок.

## Находки (ландшафт)

Слайдеры в ландшафте - `wrap_content` (горизонтальные), фиксированных 200dp нет. Высоту ландшафта определяет самая длинная вкладка (3D, две колонки форматов). Отдельная правка высоты в ландшафте не требуется.

## Решение для tech-фазы

- Уменьшить высоту портретных `VerticalSeekBar` (Громкость/HUE/Яркость/Скорость) с 200dp до ~160dp - сокращает 4 «слайдерных» вкладки, слайдер остаётся пригодным.
- Сокращение рейла достигается скрытием вкладок (3D вне VR, аудио при ≤1 дорожке, субтитры при их отсутствии) - меньше кнопок → ниже пол высоты. Для аудиофайла рейл = 2 кнопки.
- Принудительное растяжение контента под рейл само по себе безвредно: после уменьшения слайдеров и скрытия вкладок диалог становится заметно ниже без отдельной правки контейнера.
- Проверить отсутствие регресса на sw480dp/sw720dp и в ландшафте.

## Источники

- `app_v2/src/main/res/layout/dialog_playback_control.xml` (рейл 7×56dp; слайдеры 200dp; content ScrollView match_parent)
- `app_v2/src/main/res/layout-land/dialog_playback_control.xml` (слайдеры wrap_content)
- `app_v2/src/main/java/com/sza/fastmediasorter/ui/player/PlaybackControlDialogFragment.kt` (onStart: width 95%, height WRAP_CONTENT, maxHeight 95%)

## Доп. находка - 2026-06-27 (release-safety audit, после повторного FAIL критерия 1)

Правка из «Решения» (слайдеры 200->160dp + скрытие вкладок) была применена, но критерий 1 всё равно FAIL: диалог рендерился почти на весь экран с пустотой снизу даже для аудиофайла (2 вкладки). Слайдеры оказались НЕ доминирующим фактором.

Истинная причина: `MaxHeightLinearLayout.onMeasure` меряет детей спецификацией `AT_MOST(cap)` (cap = 95% экрана - chrome). Внутри портретного горизонтального рейл+контент стоял разделитель `<View android:layout_height="match_parent">`. Обычный `View` под `AT_MOST` через `getDefaultSize()` разворачивается в ПОЛНЫЙ размер spec (cap), а не в высоту соседей. То есть один разделитель тянул весь ряд на полную высоту cap; затем контентный ScrollView (`match_parent` + `fillViewport="true"`) растягивал короткий контент на весь cap -> пустота снизу.

Почему ScrollView'ы должны остаться `match_parent`: только так они скроллятся внутри ограниченного по высоте контейнера (длинная 3D-вкладка). Менять их на `wrap_content` нельзя - сломается скролл при контенте выше cap.

Правка (применена): разделитель-`<View>` заменён на встроенный разделитель LinearLayout (`android:showDividers="middle"` + `android:divider="@drawable/playback_section_divider"`, inset 10dp ~ прежний margin). Рисованный разделитель не является измеряемым ребёнком и не диктует высоту ряда -> ряд сжимается до контента, при превышении cap ScrollView'ы скроллятся.

Ландшафт правки НЕ требует (Rule 11 проверено): его `MaxHeightLinearLayout` вертикальный с единственным `fillViewport` ScrollView (корректно оборачивается под `AT_MOST`); видимый разделитель там - горизонтальная линейка 1dp ВНЕ resizable-области.

Остаётся: финальное подтверждение компактности на устройстве с вытянутым экраном (1080x2400). На квадратном AVD 2076x2152 эффект виден, но не считается conclusive по аспекту (см. Last Audit основного спека).
