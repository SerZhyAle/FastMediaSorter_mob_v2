## 0. Захваченный материал (inbox)

**Захвачено:** 2026-08-14

**Текст:**

Найдено при разборе краша S1630 (обфускация полей Gson-модели). Тот же корневой класс дефекта, но на пользовательском файле экспорта.

`FavoritesExportFile` / `ExportedFavorite` (`domain/model/FavoritesExportModel.kt`) пишутся `ExportFavoritesUseCase:96` через `gson.toJson` и читаются `ImportFavoritesUseCase:170` через `gson.fromJson`. Ни `@SerializedName`, ни keep-правила нет.

Проверено по `mapping.txt` релизной сборки standardRelease:

```
com.sza.fastmediasorter.domain.model.FavoritesExportFile -> nt4:
    java.lang.String version -> a
    java.lang.String exportDate -> b
    java.lang.String appVersion -> c
    java.lang.String deviceName -> d
com.sza.fastmediasorter.domain.model.ExportedFavorite -> nn4:
    java.lang.String uri -> a
    long resourceId -> b
    java.lang.String resourceName -> c
    java.lang.String resourcePath -> d
```

Следствия:
- Файл экспорта привязан к mapping конкретной сборки. Экспорт из версии N не импортируется в версию N+1, если mapping сдвинулся, - а именно ради переноса между устройствами и версиями функция и существует.
- Поле `version = "1.0"` в файле не спасает: оно само лежит под обфусцированным ключом, то есть проверка версии формата не отработает.
- Экспорт из debug-сборки (без минификации, настоящие имена) не читается release-сборкой, и наоборот.
- Файл заявлен как переносимый JSON, а на деле состоит из ключей `a`, `b`, `c` - непригоден для чтения человеком и для внешних инструментов.

**Вложения:** нет

## 1. Проблема / симптом

Файл экспорта избранного, записанный минифицированной сборкой, не читается ни другой сборкой, ни человеком: ключи в JSON - это `a`, `b`, `c`, потому что R8 переименовал поля модели.

Что видит пользователь при импорте такого файла, прослежено по коду, а не предположено. Gson создаёт объект в обход конструктора, поэтому при несовпадении ключей каждое поле остаётся `null`, несмотря на non-null типы Kotlin. Первое же обращение - проверка версии формата `model.version.substringBefore(".")` в `ImportFavoritesUseCase:174` - бросает NPE. Его ловит общий `catch (e: Exception)` на строке 183 и возвращает сам объект исключения, а строка 153 кладёт `e.message` в `errorMessage` результата импорта. То есть пользователю показывается сырой текст исключения Kotlin про non-null параметр - это и нечитаемо, и запрещено `docs/COMMUNICATION_POLICY.md` §6.

Эвиденс на уровне кода и mapping приведён в §0.

---

## 2. Корневая причина

Модель экспорта не покрыта ни `@SerializedName`, ни keep-правилом, в отличие от `BackupPayload` / `TrashMetadata` / `AppSettings`, где та же проблема уже закрыта (S0737/S0719).

Механизм защиты, прочитанный в `app_v2/proguard-rules.pro`, а не предположенный: строки 135-137 держат `-keepclassmembers,allowobfuscation class * { @SerializedName <fields>; }`, то есть аннотированное поле не удаляется, но переименоваться всё же может. Ключ JSON от переименования спасает не это правило, а сама аннотация - Gson берёт имя из её значения, - и `-keepattributes *Annotation*` на строке 129, благодаря которому аннотация доживает до рантайма. Защищать было нечего: аннотаций на этой модели нет.

---

## 3. Исправление

Три части, все в одном изменении:

- `@SerializedName` на каждое поле `FavoritesExportFile` и `ExportedFavorite`. Выбрана аннотация, а не keep-правило: она задаёт имя ключа явно и переживает переименование свойства в коде, а не только обфускацию. Прочие data-классы того же файла - результаты и предпросмотр импорта - живут только в памяти и Gson не сериализуются, поэтому не трогаются.
- Файлы, уже выпущенные старыми сборками, остаются нечитаемыми - восстановить mapping конкретной сборки нельзя. Решение по §3 второго пункта: не молча, но и без новой строки - разбор распознаёт файл с пустыми полями и возвращает существующее сообщение «File is corrupted or invalid» вместо NPE. Новых пользовательских строк тикет не вводит, поэтому решения о размещении UI не требуется.
- Остальные пользовательские файлы того же рода проверены: `CompanionConfigDto` уже под `@SerializedName` (кросс-репозиторный контракт), `BackupPayload` / `TrashMetadata` / игровое состояние - под keep-правилами, кэш файловых списков ведёт S1630, полезная нагрузка Wear - S1631. Найдено одно новое место того же класса, не входящее в объём этого тикета, - оно припарковано отдельным тикетом.

## 4. Проверка

Механическая часть, выполнимая без устройства:

- Сборка зелёная, `@SerializedName` стоит на каждом поле обеих моделей.
- Правило `-keepclassmembers class * { @SerializedName <fields>; }` в `app_v2/proguard-rules.pro` покрывает их без отдельной записи.

Устройство - настоящее доказательство, потому что дефект существует только в минифицированной сборке:

- Экспорт избранного на релизной сборке A, импорт на релизной сборке B с другим mapping - все избранные доезжают, счётчик в предпросмотре совпадает.
- Импорт файла, выпущенного до исправления (ключи `a`, `b`, `c`), показывает читаемое сообщение о непригодном файле, а не текст исключения.
- Открыть новый файл экспорта текстовым редактором: ключи - настоящие имена полей.
