---

## 1. Проблема

Панели «Copy to» и «Move to» распределяют кнопки назначений по строкам на основе исключительно их количества — без учёта реальной ширины панели. Результат зависит только от числа назначений: 1–5 → одна строка, 6–10 → две строки с максимумом 5 в первой.

Это не проблема ориентации, а проблема ширины. Планшет в портрете с 600–768 dp легко вмещает 6–8 кнопок в одну строку, но по-прежнему получает две. Телефон в ландшафте получает те же две строки, которые занимают ощутимую долю высоты экрана.

Размер текста на кнопке рассчитывается по длине названия (12 sp для коротких, 10 sp для длинных), а не по фактической ширине кнопки. На широких кнопках текст остаётся мелким, хотя места достаточно для крупного шрифта.

---

## 2. Цели

1. Число кнопок в строке рассчитывается по доступной ширине панели, а не по hardcoded лимиту 5: если все назначения + «..» умещаются в одну строку при ширине кнопки ≥ `minButtonWidthDp`, использовать одну строку.
2. Масштабировать размер текста кнопки пропорционально фактической ширине кнопки — чем шире, тем крупнее шрифт в определённом диапазоне.
3. На узких экранах, где ширина кнопки упала бы ниже `minButtonWidthDp`, поведение идентично текущему — без регрессий.

**Non-goals:**

- Изменение логики collapse/expand панелей.
- Изменение максимального числа назначений (настройка `maxRecipients`).
- Перекраска кнопок или смена цветовой схемы.
- Изменение поведения кнопки «..» или диалога выбора папки.
- Полный рефакторинг менеджера кнопок назначений за пределами расчёта раскладки и шрифта.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. При ширине экрана, достаточной для одной строки, не переносить кнопки на вторую — экономить вертикальное пространство.
2. Шрифт на широкой кнопке должен быть заметно крупнее, чем сейчас.

### 3.2 Жёсткие ограничения

- **Flavor:** `standard`, `lite`, `photos`, `legacy` — все флейворы (затронут один общий компонент).
- **API level:** minSdk 26 (стандарт), без API-специфики.
- **Wear OS:** не затрагивается.
- **Производительность:** расчёт числа кнопок в строке не выполняется в каждом кадре. Допустим один one-shot post-layout замер при построении панели и повторный пересчёт только при изменении доступной ширины окна/панели.
- **Совместимость данных:** миграция Room не требуется.
- **Локализация:** EN/RU/UK — текст кнопок берётся из имён назначений (не строковые ресурсы), изменений локализации нет.
- **Доступность:** минимальная высота touch-target 44 dp должна быть сохранена; масштабирование шрифта не нарушает минимальный touch-target.

## 4. Контекст текущей архитектуры

Менеджер кнопок назначений (слой UI, helpers) строит распределение по двум ветвям:

- **Стандартный режим** (`maxRecipients ≤ 10`, это единственный реально достижимый режим): жёсткая lookup-таблица «count → список строк». 1–5 → одна строка, 6–10 → две строки с лимитом 5 в первой.
- **Расширенный режим** (`maxRecipients > 10`): динамический расчёт: ≤ 10 → одна строка, ≤ 20 → две строки, > 20 → несколько строк по 10. **Мёртвый код:** `SettingsRepositoryImpl` зажимает `maxRecipients` до `1..10` при чтении и записи, поэтому эта ветвь недостижима.

Кнопка «..» добавляется **после** расчёта — дописывается в конец последней строки с шириной `WRAP_CONTENT` (≈ 40 dp), не участвует в `weight`-распределении.

Высота кнопок уже зависит от ширины экрана: `screenWidthDp < 500f` → 44 dp, иначе 56 dp (используется `displayMetrics.widthPixels`, а не window width).

Метод `createDestinationButton` принимает параметр `buttonsInRow`, но он помечен `@Suppress("UNUSED_PARAMETER")` — шрифт-по-ширине был заложен в интерфейс, но не реализован. Размер шрифта сейчас фиксирован по длине названия: ≤ 8 символов → 12 sp, 9–10 символов → 10 sp (ветка > 12 символов — мёртвый код из-за усечения названий).

Ширина панели до первого layout-прохода равна 0. При этом `bottomPanelsContainer` получает системные insets отдельно, а сами панели имеют собственные `paddingHorizontal`, поэтому `displayMetrics.widthPixels` и даже window width не являются надёжным источником истины для multi-window, freeform и split-screen. Универсальный расчёт должен опираться на **фактическую ширину контента панели после первого layout**.

---

## 5. Предлагаемый подход

### 5.1 Основные столпы

**Источник истины — реальная ширина панели, а не ширина экрана.**
После первого layout-прохода взять фактическую ширину контейнера кнопок (`copyToButtonsGrid` / `moveToButtonsGrid`) либо ширину панели минус её внутренние paddings. Этот one-shot замер выполняется при построении панелей и повторяется только при изменении доступной ширины окна/панели; расчёта в каждом кадре нет.

`displayMetrics.widthPixels` и `window width` допустимы только как аварийный fallback, если layout ещё не произошёл и кнопки нужно показать немедленно. Основной путь — post-layout измерение. Это покрывает обычный fullscreen, планшеты, multi-window, split-screen, freeform и ChromeOS-окна одной и той же формулой.

**Ширино-зависимый check поверх существующей логики.**
Вычислить `maxPerRow = floor((panelContentWidthPx - customButtonMeasuredWidthPx) / (minButtonWidthPx + horizontalMarginsPx))`. Если `count ≤ maxPerRow` — использовать `listOf(count)` (одна строка). Иначе — результат существующей lookup-таблицы остаётся без изменений. Расширенный режим (`maxRecipients > 10`) — мёртвый код, оставить как есть (не удалять, не активировать).

Значение `minButtonWidthDp` выбирается так, чтобы на 360 dp телефоне с 5 назначениями однострочный путь не сработал ошибочно. При `minButtonWidthDp ≈ 58 dp` и фактической ширине панели, близкой к текущей портретной, `maxPerRow` остаётся < 5, поэтому включается старая lookup-таблица и текущее поведение сохраняется без регрессии.

На широких окнах та же формула естественно даёт больший `maxPerRow`: планшет, desktop-mode или широкое split-screen окно не требуют отдельных breakpoints — важна только измеренная ширина контента панели.

**Масштабирование шрифта по фактической ширине кнопки.**
После определения числа строк вычислить `buttonWidthPx` из реальной ширины панели и числа кнопок в самой плотной строке, затем получить верхнюю границу шрифта через интерполяцию в `[spMin=10, spMax=16]`. Для устойчивости на длинных названиях использовать этот результат как cap для `autoSizeText`, а не как единственный жёсткий `textSize`: широкая кнопка получает право на более крупный шрифт, но длинный текст не ломает раскладку.

### 5.2 Потоки данных и событий

- `populateDestinationButtons → если ширина панели уже известна: использовать её; иначе дождаться первого layout панели one-shot способом → вычислить panelContentWidthPx → вычислить maxPerRow → count ≤ maxPerRow? → да: listOf(count); нет: lookup-таблица → вычислить cap шрифта из фактической ширины кнопки → создать кнопки → добавить «..» в последнюю строку → заполнить гриды`

### 5.3 Точки расширяемости

- Константы `MIN_BUTTON_WIDTH_DP`, `SP_MIN`, `SP_MAX`, `MAX_BUTTONS_PER_ROW` — в companion object менеджера.
- Чистые функции `computeMaxPerRow(panelContentWidthPx, customButtonWidthPx)` и `computeFontSizeSp(buttonWidthDp)` — не создают View, покрываются unit-тестами.
- Отдельный кэш последней измеренной ширины панели, чтобы не перестраивать кнопки повторно без изменения размеров окна.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Первый вызов происходит до layout, когда ширина панели ещё 0 | Средняя | Нельзя сразу посчитать универсальную раскладку | Использовать one-shot post-layout измерение и аварийный fallback только на первый краткий проход |
| Слишком мелкий `minButtonWidthDp` спровоцирует схлопывание в одну строку на портрете | Низкая | Слишком много кнопок в строке | Значение `minButtonWidthDp` подбирать от текущей регрессии 360 dp/5 кнопок, ориентир 58–60 dp; на узких окнах проверка `canFitSingleRow` вернёт false и сработает базовая логика |
| Масштабирование шрифта даёт слишком крупный текст на большом планшете или desktop-окне | Низкая | Некрасиво, но функционально | Зафиксировать `spMax` (например, 16 sp), выше которого шрифт не растёт |

## 9. Архитектурные решения (ADR)

**ADR-1: Константы компоновки — не в ресурсах dimen, а в коде**

- **Решение:** `minButtonWidthDp`, `spMin`, `spMax` хранятся как константы в companion object менеджера кнопок, а не как XML-ресурсы.
- **Альтернативы:** вынести в `dimen.xml` для возможности переопределения в flavor-ресурсах.
- **Почему:** значения являются алгоритмическими параметрами (используются в арифметике), а не дизайн-токенами; переопределять их по flavors не планируется; код проще читать, когда формула и параметры рядом.

## 11. Критерии готовности (strategic-level)

1. На 360 dp телефоне с 5 назначениями — одна строка, как сейчас (нет регрессии).
2. На 360 dp телефоне с 6 назначениями — две строки, как сейчас (нет регрессии).
3. На широком окне с контентной шириной панели, достаточной для 6–8 кнопок, используется одна строка независимо от того, это планшет, landscape-телефон или split-screen.
4. На окне с контентной шириной панели, достаточной для 10 кнопок, используется одна строка независимо от physical screen size.
5. Кнопка с большей фактической шириной отображает текст крупнее, чем более узкая кнопка при том же наборе назначений.
6. В multi-window / freeform раскладка определяется шириной текущего окна/панели, а не полной шириной дисплея.
7. Touch-target каждой кнопки ≥ 44 dp по высоте на любом экране.
