## 1. Проблема

S0483 добавил кнопку отправки отчёта в диалог об ошибке, но она работает только для ошибок, которые приложение поймало и показало. Настоящее падение - необработанное исключение, от которого приложение завершается - диалог не показывает: процесс умирает, и пользователь не может сообщить о сбое. Именно эти падения важнее всего для автора, и сейчас они уходят «в тишину» (пишется лишь крэш-файл, в release-сборке пользователь ничего не видит).

---

## 2. Цели

1. После реального падения, на следующем запуске приложения, пользователю предлагается отправить автору отчёт о сбое.
2. Предложение появляется, только если зафиксировано новое падение, и показывается один раз на падение (не повторяется при каждом запуске).
3. По согласию пользователя открывается почтовый клиент с письмом автору: получатель, тема, описание сбоя в теле и приложенный архив логов (включающий крэш-файл).
4. Поведение работает в release-сборке и единообразно во всех вариантах сборки.

**Non-goals:**

- Не вводится показ диалога в момент самого краха (процесс в этот миг нестабилен) - только на следующем запуске.
- Не вводится автоматическая отправка без согласия пользователя.
- Не меняется существующий путь S0483 (кнопка в диалоге об ошибке).
- Не вводится отдельный экран истории крэшей.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Максимально переиспользовать готовое из S0483 (формирование письма с вложением) и существующий детектор предыдущего падения.
2. Предложение ненавязчивое: одно действие «Отправить», одно «Не сейчас».

- **Совместимость данных:** без изменений Room. Признак «падение уже предложено» хранится как лёгкое локальное состояние, без схемы БД.

## 4. Контекст текущей архитектуры

Приложение уже перехватывает необработанные исключения и пишет крэш-файл, а на старте умеет определять, что в прошлый раз было падение - но сейчас этот факт лишь логируется, без действия для пользователя. Файловое логирование и упаковка логов в архив, а также формирование письма автору с вложением, уже существуют (последнее добавлено в S0483). Чего нет - это связки «обнаружили падение на старте → предложили пользователю отправить отчёт → переиспользовали готовую отправку», и механизма «предложить один раз на падение».

---

## 5. Предлагаемый подход

На запуске приложение проверяет, есть ли зафиксированное падение, о котором пользователю ещё не предлагали сообщить. Если есть - на первом экране показывается диалог-предложение. По согласию переиспользуется существующий механизм: описание сбоя (из крэш-файла) идёт в тело письма, архив логов - во вложение, письмо адресуется автору. После показа предложения падение помечается как «обработанное», чтобы не предлагать повторно.

### 5.1 Основные столпы / модули

- **Обнаружение нового падения.** Определить наличие самого свежего крэш-файла и понять, предлагали ли уже по нему отправку (лёгкий локальный признак-«водяной знак»).
- **Предложение пользователю.** Модальный диалог подтверждения на первом экране: коротко сообщить о прошлом сбое и предложить отправить отчёт; уважать выбор «Не сейчас».
- **Отправка отчёта.** Переиспользовать готовый из S0483 механизм письма автору с вложением-архивом; тело письма дополнить кратким описанием сбоя из крэш-файла. Подготовка вложения - вне главного потока.
- **Однократность.** После показа предложения отметить это падение обработанным, чтобы не беспокоить при следующих запусках.

### 5.2 Потоки данных и событий

`запуск → проверка нового падения → (если есть) первый экран показывает предложение → согласие → чтение крэш-файла + упаковка логов → системная отправка письма автору (получатель + тема + описание + вложение) → отметка «обработано»`.

### 5.3 Точки расширяемости

- Механизм отправки письма с вложением - общий с S0483, без дублирования.
- Признак «обработано» вводится так, чтобы при желании позже добавить опцию «не предлагать» или счётчик падений без переделки потока.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Повторный показ предложения при каждом запуске | Средняя | Раздражение пользователя | Отметка «обработано» сразу при показе, до отправки |

| Отправка лога без согласия | Низкая | Нарушение приватности | Отправка только по кнопке «Отправить» |

## 9. Архитектурные решения (ADR)

**ADR-1: Предложение на следующем запуске, не в момент краха**

- **Решение:** показывать предложение при следующем старте, а не пытаться показать UI в момент необработанного исключения.
- **Альтернативы:** перехватить краш и показать диалог сразу (как делает отладочный CrashActivity).
- **Почему:** в момент необработанного исключения процесс нестабилен; показ UI ненадёжен в release и может вызвать второй сбой.

**ADR-2: Переиспользование механизма отправки из S0483**

- **Решение:** использовать тот же построитель письма автору с вложением и упаковку логов, что и S0483.
- **Альтернативы:** отдельный путь отправки для крэшей.
- **Почему:** единый канал и минимум новой логики; адрес и формат уже согласованы.

**ADR-3: Однократность через лёгкий локальный признак**

- **Решение:** отмечать падение «обработанным» лёгким локальным состоянием, без изменения схемы БД.
- **Альтернативы:** хранить в основной базе настроек (миграция).
- **Почему:** это транзиентное состояние устройства, не пользовательская настройка; миграция избыточна.

## 11. Критерии готовности (strategic-level)

1. После реального падения, на следующем запуске, пользователь видит предложение отправить отчёт о сбое.
2. Предложение не появляется, если нового падения не было; не повторяется при последующих запусках того же падения.
3. По кнопке «Отправить» открывается почтовый клиент с получателем `serzhyale@gmail.com`, темой, описанием сбоя в теле и приложенным архивом логов.
4. «Не сейчас» закрывает предложение без отправки.
5. Работает в release-сборке и во всех вариантах; текст локализован (EN/RU/UK).
