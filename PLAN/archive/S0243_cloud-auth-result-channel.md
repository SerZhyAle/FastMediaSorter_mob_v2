## 1. Проблема

Контракт интерактивной cloud-аутентификации возвращает результат через три разнородных канала (синхронный опрос, обработка intent-результата, обработка onResume), которые исторически покрывали разные SDK — Dropbox/OneDrive (intent + resume) и старый Google Sign-In (immediate/intent). После миграции основного провайдера на Credential Manager его flow начал завершаться через несколько секунд интерактивного UI — уже после того, как оркестратор закончил опрос (immediate + 1с). Результат успешного входа никуда не попадал, экран добавления ресурса оставался открытым, пользователь ушёл, не создав ресурс.

Hot-fix временно добавил приватный асинхронный канал внутри одного плагина и downcast по имени класса в оркестраторе. Симптом снят, но контракт стал несимметричным: один провайдер ходит через push-канал, два других — через старые poll/intent/resume, оркестратор знает имя конкретной реализации. Любой следующий провайдер с длинным interactive flow попадёт в ту же яму, и его придётся подшивать таким же hot-fix-приёмом.

---

## 2. Цели

1. Все cloud-плагины возвращают финальный `AuthResult` через единый асинхронный канал, без условных веток в оркестраторе.
2. Снимается downcast на конкретный плагин в оркестраторе.
3. Снимается зависимость от тайминга опроса (`immediate + 1с`) — длинные flow (Credential Manager, Account Picker, броузерные re-auth) гарантированно доезжают до UI.
4. Добавление нового cloud-провайдера сводится к реализации единого контракта без правки оркестратора.
5. Контракт допускает ровно один финальный результат на попытку входа — двойная навигация исключена by design.

**Non-goals:**

- Менять `AuthResult` sealed class (включая поля `accountName` / `credentialsJson`).
- Менять UI-поток в экране добавления ресурса и в browse-cloud-auth-цепочке.
- Менять Credential Manager / MSAL / Dropbox SDK и их адаптеры внутри плагинов.
- Менять observable identity-domain (`identityRepository.state`), на который подписан Settings-card.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. По возможности — единая точка структурированного логирования начала / завершения / отмены каждого интерактивного сценария (provider + accountEmail + outcome), без дублей в каждом плагине.
2. По возможности — единый таймаут «зависшего» интерактивного flow на стороне оркестратора, не в каждом плагине отдельно.
3. По возможности — после рефакторинга подготовить почву для тестирования контракта через подменный плагин (fake) без участия настоящих SDK.

### 3.2 Жёсткие ограничения

- **Flavor:** затрагивает все flavors, у которых включён CLOUD (`standard`). Плагины OneDrive/Dropbox/GoogleDrive живут в общем `src/main/` и не уходят во flavor-overrides — это рефакторинг внутри уже существующего слоя.
- **API level:** без API-специфики; контракт не привязан к версии Android.
- **Wear OS:** не затрагивает (на часах cloud-аутентификации нет).
- **Производительность:** многократные нажатия на карточку провайдера до завершения первой попытки не должны порождать утечку корутин подписки или зависшие listener'ы; повторный вход после отмены — без артефактов предыдущей подписки.
- **Совместимость данных:** Room-миграция не требуется — рефакторинг оркестрационного слоя без затрагивания персистентного состояния.
- **Локализация:** EN/RU/UK — без новых пользовательских строк; существующие сообщения об ошибках сохраняются.
- **Доступность:** не затрагивает (нет UI-изменений).
- **UI-копирайт:** новых строк не вводится, поэтому `docs/COMMUNICATION_POLICY.md` напрямую не применяется; существующие тосты/диалоги об успехе и ошибке остаются неизменными.

## 4. Контекст текущей архитектуры

Интерактивная cloud-аутентификация устроена послойно: UI-слой (экран добавления ресурса, browse-cloud-auth) обращается к оркестратору, оркестратор хранит активного провайдера и делегирует ему запуск flow, провайдер взаимодействует со своей SDK и возвращает результат через один из трёх стандартных каналов. Контракт исторически создавался под Activity-result + onResume модели (Dropbox, OneDrive MSAL) и под immediate-failure модели (синхронный fail при отсутствии broker / неверной подписи). Длительный успех всегда приходил через onResume.

Credential Manager эту модель не использует: его flow — это suspend-функция, которая возвращает результат напрямую корутиной, без onResume и без Activity-result. Плагин Google Drive под этот случай пишет результат только в Timber и в долгоживущий identity-domain Flow, на который подписан Settings-card; в старый оркестрационный канал ничего не доезжает. Hot-fix временно решил эту конкретную асимметрию, не меняя контракт.

---

## 5. Предлагаемый подход

Свести роль провайдера к одному push-каналу финального результата. Опрос и intent/resume-каналы становятся внутренней деталью реализации провайдера: провайдер сам решает, как ему принять результат от своей SDK (suspend, callback, Activity-result, broker callback), и кладёт ровно один итоговый `AuthResult` в общий канал. Оркестратор подписывается на канал на старте попытки и снимает подписку по получении первого события или по таймауту/отмене.

### 5.1 Основные столпы / модули

- **Контракт провайдера интерактивной cloud-аутентификации.** Единственная обязанность — запустить интерактивный flow и эмитить ровно один `AuthResult` в общий канал результата. Текущие методы синхронного опроса и intent/resume-обработки уходят во внутренние детали реализации провайдера, а не контракта.
- **Общий канал результата.** Часть сигнатуры контракта (тип потока / Channel-семантика — детали в `/spec-tech`). Доступ оркестратору без условий на конкретный тип провайдера.
- **Оркестратор интерактивной cloud-аутентификации.** При старте попытки подписывается на канал активного провайдера, ждёт один результат, маршрутизирует его в общий event-стрим для UI. Без downcast.
- **Lifecycle ожидания.** Одна корутина подписки на попытку, одна точка отмены. Опциональный таймаут — единое значение в оркестраторе, не в плагинах.

### 5.2 Потоки данных и событий

- UI инициирует попытку входа для провайдера → оркестратор открывает подписку на канал результата провайдера → оркестратор делегирует запуск интерактивного flow провайдеру → провайдер ведёт переговоры со своей SDK любым внутренним способом → провайдер эмитит финальный `AuthResult` (Success / Cancelled / Error) → оркестратор обрабатывает первое событие через единую точку, переводит его в общий event-стрим и снимает подписку.

### 5.3 Точки расширяемости

- Контракт допускает любое число провайдеров без правки оркестратора.
- Канал результата — общий тип в сигнатуре контракта (конкретный примитив выбирается в `/spec-tech`).
- Новые механизмы identity (например, замена Credential Manager на иной API, добавление нового OAuth-провайдера) реализуются как ещё одна реализация контракта; ни оркестратор, ни UI-слой не меняются.
- Подменная реализация провайдера для тестов опирается на тот же канал, без специальных тестовых интерфейсов.

## 6. Открытые вопросы / Research items

1. **Семантика канала результата: однократный или поточный**
   - **Вопрос:** должен ли канал жить одну попытку (capacity=1, закрывается после receive) или быть persistent у плагина с подпиской `first()` на стороне оркестратора?
   - **Варианты:** (a) одноразовый `Channel<AuthResult>` с capacity=1, создаваемый плагином на каждую попытку; (b) персистентный `SharedFlow<AuthResult>` плагина, оркестратор берёт `first()` и снимает подписку.
   - **Нужно выяснить:** поведение при повторных нажатиях карточки провайдера до завершения первой попытки (текущий лог показывает 4 клика подряд на одну карточку).
   - **Статус:** Open
2. **Совместимость с MSAL/Dropbox callback-моделями**
   - **Вопрос:** возможно ли всем трём плагинам эмитить ровно один результат без потери текущей логики onResume / activity-result?
   - **Варианты:** (a) оставить внутренние poll/intent/resume как private detail плагина, обёрнутые в эмит в общий канал; (b) переписать на чистые callback'и SDK, отказавшись от intent/resume-точек контракта.
   - **Нужно выяснить:** какие конкретно сигналы Dropbox/OneDrive плагины сейчас ловят и в какой момент жизненного цикла Activity.
   - **Статус:** Open
3. **Поведение при отмене и лайфцикле Activity**
   - **Вопрос:** что делать с висящей подпиской и с интерактивным flow, если пользователь покинул экран добавления ресурса до завершения логина?
   - **Варианты:** (a) привязка подписки к жизненному циклу инициатора (Activity); (b) глобальный appScope с тайм-аутом и тихим dropping результата, если активный провайдер сброшен; (c) переход на flow-based picker с auto-resume при возврате.
   - **Нужно выяснить:** ожидаемый UX (продолжить с того же места при возврате или начать заново) и текущее фактическое поведение каждого провайдера.
   - **Статус:** Open
4. **Совместимость с identity-domain `state`-Flow**
   - **Вопрос:** новый канал результата и долгоживущий `identityRepository.state`, на который подписан Settings-card, не должны дублировать друг друга и не должны порождать гонку.
   - **Варианты:** оркестратор слушает только новый канал; identity-domain `state` остаётся источником истины для отображения «кто залогинен сейчас»; разделение ролей фиксируется явным комментарием в контракте.
   - **Нужно выяснить:** все ли подписчики `identityRepository.state` корректно работают, когда канал результата эмитит Success одновременно.
   - **Статус:** Open

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Регресс существующих провайдеров (Dropbox / OneDrive) | Средняя | Реальные пользователи теряют возможность добавить cloud-ресурс | Поэтапная миграция — каждый плагин отдельной фазой `/spec-tech`; ручной smoke-тест после каждой фазы (вход в каждый из трёх провайдеров до folder-picker) |

## 9. Архитектурные решения (ADR)

**ADR-1: Единый асинхронный канал вместо poll/intent/resume**

- **Решение:** контракт провайдера интерактивной cloud-аутентификации сводится к одному push-каналу финального результата. Все остальные способы получения результата от SDK становятся внутренней деталью реализации конкретного плагина.
- **Альтернативы:**
  - (a) Увеличить тайм-аут опроса до десятков секунд. Отклонено: ненадёжно для произвольных Credential-Manager / broker-flow длиной в десятки секунд, плюс race с onResume.
  - (b) Сохранить poll-цикл и добавить второй async-канал параллельно (текущий hot-fix). Отклонено: сохраняет асимметрию между провайдерами и downcast в оркестраторе.
  - (c) Callback-based контракт с регистрацией listener со стороны оркестратора. Функционально эквивалентно, но менее идиоматично для Kotlin-coroutines-кодовой базы этого проекта и хуже комбинируется с `lifecycleScope` UI-слоя.
- **Почему:** push-канал на coroutine-flow примитиве — единственный вариант, который одновременно (i) устраняет асимметрию, (ii) убирает downcast, (iii) не зависит от тайминга SDK, (iv) ложится на существующую `appScope` / `lifecycleScope` модель проекта.

## 11. Критерии готовности (strategic-level)

1. Все три существующих провайдера (Google Drive, Dropbox, OneDrive) проходят интерактивный вход до folder-picker без регрессов.
2. Оркестратор не содержит ветвлений по конкретному типу провайдера, downcast на имя класса плагина отсутствует.
3. Опрос результата с фиксированным тайм-аутом 1 секунды отсутствует в коде.
4. Добавление гипотетического нового cloud-провайдера не требует правки оркестратора — только реализации контракта.
5. Повторные нажатия карточки провайдера до завершения первой попытки не приводят к утечке подписки или к двойной навигации на folder-picker.
6. Логирование начала / завершения / отмены интерактивного flow присутствует ровно в одной точке (в оркестраторе), без дублей в каждом плагине.
