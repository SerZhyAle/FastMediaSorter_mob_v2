## 1. Проблема

Для коротких видеофайлов (например, 30 секунд) поведение возобновления воспроизведения превращается в багово-зацикленный сценарий:

1. Пользователь смотрит файл от начала до конца. На последних секундах (~28 с из 30 с) репозиторий сохраняет позицию воспроизведения как «последнюю».
2. Файл дошёл до конца → плеер автоматически переключается на следующий файл.
3. Пользователь явным действием возвращается к этому короткому файлу (например, через prev в плеере, или открыв заново из Browse).
4. Плеер «возобновляет» воспроизведение с сохранённой позиции 28 с. Играет 1-2 секунды, доходит до конца, снова автопереход на следующий.
5. Поставить на паузу или перемотать на начало пользователь физически не успевает — окно «доступности» меньше реакции человека.

В логе сессии 2026-04-29 02:22 видны записи `PlaybackPosition: Saved position 650071ms/4372252ms ... (completed=false)` (line 890) — то есть флаг `completed` есть в коде, но при этом позиция сохраняется на каждом тике, включая позицию ближе к концу. Поле `completed=false` намекает, что путь «полное окончание → completed=true» существует, но: либо не срабатывает (для коротких файлов, где автопереход идёт раньше точки сохранения), либо не приводит к очистке сохранённой позиции.

Эффект: «возобновление с последней позиции» — анти-фича для уже досмотренных файлов. Для длинного видео (1 час, посмотрел 40 минут) поведение корректное; для короткого — ломает UX.

## 2. Цели

1. Если видео/аудио было воспроизведено до конца (естественное окончание или достижение последних N% файла), сохранённая позиция **очищается**. При следующем открытии этого файла плеер играет с нуля.
2. Если воспроизведение было прервано на середине (пауза, выход в Browse, закрытие окна) — позиция сохраняется как сейчас. Возобновление с этой позиции при следующем открытии работает как сейчас.
3. Порог «считать законченным» учитывает случай, когда видеофайл имеет «технический хвост» (тишина, чёрный кадр, credit). По умолчанию — последние 5% файла или последние 5 секунд (что меньше). Конкретное значение — задача §6.
4. Поведение единое для VR-плеера и панельного плеера; единое для видео/аудио/слайдшоу с фоновой музыкой.
5. После очистки позиции в логе пишется явный маркер `ResumeStateRepository: clearState reason=playback-completed` — отличный от других путей очистки (`user-exited`, `resource-changed`).

**Non-goals:**

- Не меняется механизм сохранения позиции в принципе (тики, throttle, async-IO).
- Не вводится новый пользовательский тумблер «всегда играть с начала» (это уже опция в существующих настройках, не пересматривается).
- Не покрывается миграция уже сохранённых «грязных» позиций для досмотренных файлов в DataStore — после релиза старые «грязные» позиции остаются до следующего полного просмотра.
- Не покрывается случай «короткое видео в плейлисте, нужно при playall не возобновлять каждый раз сначала» — это другой сценарий, не связан с одиночным открытием файла.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Желательно явный лог-маркер «позиция очищена потому что досмотрели» — при разборе логов это даёт понимание, в каком состоянии плеер.
2. Желательно, чтобы порог «досмотрено» был осмысленным: видео 30 с — порог ~25 с; видео 1 ч — порог ~57 мин. Простое «N%» или «N секунд» не подходит для всех длительностей.
3. Желательно, чтобы поведение было одинаковым для всех типов плееров.

### 3.2 Жёсткие ограничения

- **Flavor:** все флейворы. Поведение универсальное.
- **API level:** без новых API.
- **Wear OS:** не затрагивается.
- **Производительность:** очистка — это одна запись в DataStore при достижении конца файла. Оверхед нулевой.
- **Совместимость данных:** изменения в логике, не в схеме хранилища.
- **Локализация:** без новых строк UI.
- **Доступность:** без изменений.

## 4. Контекст текущей архитектуры

`ResumeStateRepository` хранит для каждого файла последнюю позицию (path → ms). Запись обновляется на каждый тик плеера (обычно ~раз в секунду). Очистка происходит в нескольких местах:

- При явном выходе пользователя из плеера (`PlayerViewModel: clearResumeState — user explicitly exited player`, line 1851 в логе).
- При смене ресурса (`BrowseLifecycleSetupManager: resource changed (saved=3, current=5) — clearing resume state`, line 969).
- При нажатии Back в Browse (`BrowseResourceStateManager: clearResumeState`, line 2461).

Ветка «очистить, потому что досмотрели» в логе отсутствует — это сильный сигнал, что её нет в коде. Поле `completed` в строке `PlaybackPosition: Saved position ... (completed=false)` намекает на существование флага, но переход `completed=true` не срабатывает в наблюдаемом сценарии (или он есть, но не вызывает clearState).

`PlayerLifecycleManager` сохраняет позицию при `onPause` (line 3329: `PlayerLifecycleManager: Saved playback position 680742/4372252`). Если автопереход на следующий файл вызывает `onPause` без флага «достигнут конец» — сохраняется «почти конец», и при следующем открытии репозиторий возвращает эту позицию.

Архитектурно: автопереход на следующий файл должен помечаться как «file completed» с явным сигналом в репозиторий «очистить позицию для этого файла», а не «сохранить текущую».

## 5. Предлагаемый подход

Подход — два блока: распознавание «файл досмотрен» и реакция «очистить вместо сохранения».

### 5.1 Основные столпы / модули

**Распознавание окончания воспроизведения.**
В точке, где плеер генерирует событие «достигнут конец файла» (callback ExoPlayer `onPlaybackStateChanged → STATE_ENDED`, или эквивалент для аудио/слайдшоу), формируется сигнал «file completed». Сигнал — единый для всех типов медиа; источник — лайфцикл плеера, не таймер «позиция близка к длительности».

**Защитный порог «почти-конец».**
Дополнительно к естественному `STATE_ENDED` обрабатывается сценарий, где пользователь явно вышел в Browse в течение последних N% файла (например, 5%) или последних N секунд. Это покрывает случай «коротких 30 с» и случай «закрыл окно за секунду до конца». Конкретные значения — `min(5%, 5s)` по умолчанию; финальное значение фиксируется в §6.

**Реакция: clearState вместо saveState.**
При сигнале «file completed» репозиторий вызывает `clearState(file)` с reason=`playback-completed`. Запись «текущая позиция» удаляется. Любой после-сигнал тик `saveState` для того же файла игнорируется до следующего «file started» события (то есть до явного нового открытия пользователем).

**Идемпотентность.**
Многократный сигнал «file completed» (например, ExoPlayer повторно вызывает `STATE_ENDED` при автопереходе) даёт ровно один `clearState`. Это требует хранения «последний обработанный completed-файл» в памяти `PlayerLifecycleManager` или эквиваленте.

### 5.2 Потоки данных и событий

```
Плеер играет → on each tick → ResumeStateRepository.saveState(file, position)
                                                │
ExoPlayer STATE_ENDED                           │
        OR                                      │
position ≥ duration - max(5%, 5s) AND user exit │
        │                                       │
        ▼                                       │
Player → "file completed" signal                │
        │                                       │
        ▼                                       │
ResumeStateRepository.clearState(file, reason="playback-completed")
        │
        ▼
Subsequent saveState(file, *) ignored until next "file started" signal
```

### 5.3 Точки расширяемости

- Порог «почти-конец» — конфигурируемый константой; легко поменять без рефакторинга.
- Сигнал «file completed» — общий интерфейс; новые типы медиа (если добавятся) подключают свой источник без изменения репозитория.
- Reason-теги в clearState — список расширяемый; добавление новой ветки очистки (например, `auto-cleanup-stale`) не ломает существующие.

## 6. Открытые вопросы / Research items

1. **Порог «почти-конец».**
   - **Вопрос:** какое значение порога даёт правильный баланс для коротких (30 с) и длинных (1 ч) файлов?
   - **Варианты:** (а) `min(5%, 5s)`; (б) `min(2%, 3s)`; (в) только `STATE_ENDED` без порога — тогда 30-секундное видео, прерванное за 2 с до конца, всё равно даст «возобновить с последней позиции» при следующем открытии.
   - **Нужно выяснить:** ожидание владельца (формула: 5% или фиксированное число секунд?); проверить на 5-10 типичных видеофайлах разной длительности.
   - **Статус:** Open.

2. **Слайдшоу с фоновой музыкой.**
   - **Вопрос:** для слайдшоу с фоновой музыкой что считается «досмотрено» — все картинки прошли, или фоновая музыка кончилась?
   - **Варианты:** (a) слайдшоу не сохраняет позицию (нет смысла); (б) сохраняет позицию слайда; (в) сохраняет таймстамп аудио-трека.
   - **Нужно выяснить:** текущее поведение слайдшоу (есть ли вообще resume у слайдшоу?); ожидание владельца.
   - **Статус:** Open.

3. **Очистка для аудио-файлов.**
   - **Вопрос:** аудио-файлы (mp3, аудиокниги) — пользователь хочет «возобновлять с последней позиции» даже после досматривания одной главы?
   - **Варианты:** (а) единое поведение «досмотрел → очистить»; (б) разное поведение для аудио (никогда не очищать) vs видео (очищать при досматривании).
   - **Нужно выяснить:** ожидание владельца. Аудиокниги — кейс «возобновлять всегда»; музыкальный трек — кейс «можно сбрасывать».
   - **Статус:** Open.

4. **Миграция «грязных» позиций.**
   - **Вопрос:** после релиза в DataStore остаются позиции, сохранённые до фикса (для уже досмотренных файлов). Нужна ли миграция?
   - **Варианты:** (а) ничего не делать — пользователь сам пересмотрит, и позиция очистится; (б) при первом запуске после релиза очистить все позиции старше N дней; (в) очистить позиции, где `completed=true`.
   - **Нужно выяснить:** сохраняется ли поле `completed` в самом DataStore (по логу `(completed=false)` похоже да). Если да — миграция тривиальна.
   - **Статус:** Open.

## 7. Field evidence — Quest 3, 2026-04-29

Лог `logs/fastmediasorter_20260429_022215.log` подтверждает, что флаг `completed` не становится `true` во всей наблюдаемой сессии для 72-минутного файла:

```text
line 890:  PlaybackPosition: Saved position 650071ms/4372252ms (completed=false)
line 3304: PlaybackPosition: Saved position 664011ms/4372252ms (completed=false)
line 3374: PlaybackPosition: Saved position 650804ms/4372252ms (completed=false)
```

Позиция восстанавливается при каждом запуске: `PlaybackPosition: Restored position 650804ms`. Для 72-минутного файла на позиции ~650 с (≈ 15%) это корректное поведение. Сценарий «короткий файл → почти-конец → зацикливание» в данном логе не воспроизведён — коротких файлов в сессии не было. Тем не менее механизм подтверждён: ветка `completed=true → clearState` отсутствует — строка `ResumeStateRepository: clearState reason=playback-completed` в логе ни разу не появляется.

Открытый вопрос §6 #4: поле `completed` в лог-строках есть (`(completed=false)`) — значит, оно хранится в DataStore. Миграция `completed=false → true` для уже досмотренных файлов тривиальна.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Порог «почти-конец» слишком жадный — длинный видео-файл (1 ч) с пользовательским выходом за минуту до конца считается «досмотренным» | Средняя | Пользователь возвращается, ожидая возобновления; видит начало | Порог формулой `min(percent, seconds)`, не «процент» один; на длинных файлах работает как secondsCap |
| `STATE_ENDED` приходит несколько раз — clearState вызывается несколько раз, ломая семантику логов | Низкая | Шум в логе | Idempotency-флаг «последний обработанный completed-файл» |
| Аудио-сценарий: пользователь хочет возобновлять прерванную аудиокнигу — фикс ломает кейс | Средняя | Регрессия для аудио-флоу | Резолюция §6 #3: либо разное поведение по типу, либо аудио-tracks пользователь должен явно «вернуться к началу» (документируется) |
| Сохранение позиции на каждом тике при подходе к концу делает нелогичным «не сохранить близко к концу»: фикс — игнорировать tick'и в зоне «почти-конец» | Низкая | Если пользователь явно вышел в зоне «почти-конец», его осознанная пауза не сохраняется | Сохранение в зоне «почти-конец» работает как обычно; clearState срабатывает на STATE_ENDED, не на tick'е |

## 9. Архитектурные решения (ADR)

**ADR-1: «File completed» — событие плеера, не таймер.**

- **Решение:** сигнал «достигнут конец» исходит от лайфцикла ExoPlayer (`STATE_ENDED`) или эквивалента для аудио/слайдшоу. Не вычисляется по таймеру «позиция близка к длительности».
- **Альтернативы:** (а) опираться только на таймер — отвергнуто, потому что floating-point дельта между position и duration ненадёжна; (б) использовать только STATE_ENDED — отвергнуто, потому что не покрывает «вышел вручную за секунду до конца».
- **Почему:** комбинация «STATE_ENDED OR (порог + явный exit)» покрывает все наблюдаемые кейсы.

**ADR-2: clearState вместо saveState — единый путь.**

- **Решение:** при сигнале «file completed» репозиторий вызывает `clearState(file)`, не `saveState(file, 0)`. Логика «возобновить с нуля» работает через **отсутствие** записи, а не через запись с нулевой позицией.
- **Альтернативы:** сохранить позицию 0 — отвергнуто, потому что засоряет хранилище и противоречит существующей семантике «отсутствие записи = с нуля».
- **Почему:** единственный источник истины «был ли файл недосмотрен» — наличие записи в репозитории.

**ADR-3: Reason-тег в clearState — для наблюдаемости.**

- **Решение:** clearState принимает аргумент `reason` (enum или строка); каждая ветка вызова логирует свой reason: `user-exited`, `resource-changed`, `playback-completed`.
- **Альтернативы:** clearState без reason — отвергнуто, потому что не отличить ветки в логе.
- **Почему:** наблюдаемость в логе — ключ к диагностике любых будущих регрессий.

## 11. Критерии готовности (strategic-level)

1. На устройстве: открыть короткое (30 с) видео, посмотреть до конца → автопереход на следующий → вернуться к этому файлу → плеер начинает с 0 с, не с 28 с.
2. На устройстве: открыть длинное (1 ч) видео, посмотреть 5 минут, выйти в Browse → вернуться → плеер возобновляет с 5-й минуты, как сейчас.
3. На устройстве: открыть короткое видео, выйти за 1 секунду до конца (в зоне «почти-конец») → вернуться → плеер начинает с 0 с (порог «почти-конец» сработал).
4. В логе после полного воспроизведения видна строка `ResumeStateRepository: clearState reason=playback-completed`; при ручном выходе видна строка `clearState reason=user-exited` — две ветки различимы.
5. Loop-mode (если включён) не сбрасывает позицию между итерациями — повтор работает как сейчас.
6. Документация раздела в EN/RU/UK содержит формулировку из §8.
7. Регрессионный тест на двух файлах (короткий + длинный) проверяет обе ветки в CI.
