## 1. Проблема

При сканировании больших сетевых ресурсов (SMB-дерево с тысячами файлов) операция занимает 10..30 с (см. S0056 — зафиксированные 20 с для `resourceId=18`). Всё это время пользователь видит `"Loading"` без цифр и без кнопки отмены (кнопка STOP появляется только спустя 5 с). Внешне неотличимо от зависания.

**Важно:** инфраструктура прогресса уже существует в кодовой базе — прогресс-callback уже реализован и проброшен от сканера до UI; кнопка STOP и state-поля уже присутствуют. Проблема только в том, что текст не обновляется информативно и кнопка STOP появляется с задержкой.

---

## 2. Цели

1. Во время активного сканирования SMB-ресурса пользователь видит в существующем прогресс-блоке количество найденных файлов (`N` или `N / ~M`, если известен ожидаемый объём).
2. Для сетевых ресурсов (SMB/FTP/SFTP) кнопка STOP отображается немедленно с началом сканирования, без задержки 5 с.
3. Нажатие STOP уже реализовано и корректно работает — поведение после cancel не меняется.
4. Быстрые сканирования (`< 1 с`) не показывают индикатор с цифрами, либо он исчезает мгновенно.

**Non-goals:**

- Не менять архитектуру прогресс-канала — callback уже существует и работает.
- Не добавлять новые data-классы, flows, use cases.
- Не показывать текущий каталог — SMB сканирует параллельно и единственного "текущего пути" нет.
- Не покрывать FTP/SFTP живым прогрессом — эти протоколы возвращают список одним блоком; оставить как есть (spinner без цифр).
- Не реализовывать pause/resume.
- Не затрагивать локальные и облачные ресурсы.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. После завершения сканирования индикатор скрывается автоматически (уже работает).
2. Если у ресурса уже есть `fileCount > 0` из предыдущего скана, показывать `N / ~M` с приближённой оценкой; если нет — только `N`.
3. Cancel UI-мгновенный (`< 200 мс`) с точки зрения пользователя (уже работает).

### 3.2 Жёсткие ограничения

- **Flavor:** `standard`, `lite`, `legacy` (все с сетевыми ресурсами).
- **API level:** без специфичных требований.
- **Wear OS:** не затрагивается.
- **Производительность:** обновление текста индикатора — не чаще чем текущая частота callback (каждые 50 файлов); никаких дополнительных потоков или накладных расходов.
- **Совместимость данных:** нет изменений схемы данных; используется существующее поле `fileCount` ресурса.
- **Локализация:** EN/RU/UK — новый строковый ресурс для текста `"Scanning: N / ~M"` переводится в трёх локалях; кнопка STOP уже переведена.
- **Доступность:** программное обновление `contentDescription` у прогресс-блока при изменении счётчика.

## 4. Контекст текущей архитектуры (AS-IS)

Весь необходимый стек **уже существует:**

- `ScanProgressCallback` (`onProgress(count)`) реализован и полностью проброшен: сканер → `GetMediaFilesUseCase` → `BrowseLoadingManager` → `BrowseState.loadingProgress`.
- `BrowseState` содержит `loadingProgress: Int`, `isScanCancellable: Boolean`, `totalFileCount: Int?`.
- `activity_browse.xml` содержит `layoutProgress` (спиннер + `tvProgressMessage` + `btnStopScan`).
- `BrowseViewModel.cancelScan()` и флаг `shouldStopScan` уже корректно останавливают SMB-сканирование.

**Что не работает сейчас:**
1. `tvProgressMessage` отображает `"Loading (N)"` без формата `N / ~M`.
2. `btnStopScan` появляется только через **5 секунд** (`isScanCancellable = true` после delay 5000 мс) — для любых ресурсов.
3. SMB вызывает `onProgress` корректно; FTP и SFTP — нет (возвращают список одним блоком); принято как есть.

## 5. Предлагаемый подход (минимальные изменения)

Два целевых изменения в существующих файлах, без новых классов и абстракций:

**Изменение 1 — текст прогресса.**
В слое UI при рендере прогресс-сообщения использовать `resource.fileCount` из состояния: если `fileCount > 0` и ресурс сетевой — показывать `"Сканирование: N / ~M"`, иначе `"Сканирование: N"`. Новый строковый ресурс в EN/RU/UK.

**Изменение 2 — немедленный STOP для сетевых ресурсов.**
Для ресурсов типа SMB/FTP/SFTP устанавливать `isScanCancellable = true` сразу при старте загрузки, не ожидая задержку 5 с. Для локальных ресурсов задержка остаётся прежней.

**Что не меняется:** сам callback, сканеры, use cases, repository, схема Room, DI-модули, cancel-логика, прочие экраны.

## 9. Архитектурные решения (ADR)

**ADR-1: Не создавать новый поток/state-класс — использовать существующий `loadingProgress`**

- **Решение:** расширить формат текста `tvProgressMessage` в слое рендера; не вводить новые data-классы, sealed-состояния или flows.
- **Альтернатива:** создать `ResourceScanState` sealed class по аналогии с `DuplicateScanProgress` — избыточно при уже работающем `loadingProgress: Int` в `BrowseState`.
- **Почему:** scope задачи — улучшить информативность существующего UI, не рефакторить архитектуру прогресс-канала.

## 11. Критерии готовности (strategic-level)

1. При сканировании SMB-ресурса с `fileCount > 0` пользователь видит `"Сканирование: N / ~M"` в прогресс-блоке.
2. При сканировании SMB-ресурса без истории (`fileCount == 0`) — только `"Сканирование: N"`.
3. Для FTP/SFTP — спиннер без счётчика (поведение не хуже текущего).
4. Кнопка STOP видима сразу при открытии network-ресурса, без ожидания 5 с.
5. Cancel-поведение не изменилось: список остаётся в согласованном состоянии.
6. Новый строковый ресурс локализован в EN/RU/UK.
