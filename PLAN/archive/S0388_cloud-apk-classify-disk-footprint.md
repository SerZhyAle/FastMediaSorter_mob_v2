## 1. Проблема

В сборке noLegal/VR при просмотре облачной папки с APK-архивами приложение распознаёт VR-приложения: для каждого APK во временный кэш скачивается копия, затем рядом создаётся вторая, постоянная копия для повторного чтения классификатором.

Эта схема расходует дисковое пространство непропорционально задаче нарисовать один бейдж:

- Скачивается **весь** APK (Quest-архивы - сотни МБ), хотя для определения VR нужен только манифест.
- На время переноса на одном томе одновременно держатся **две** полные копии (временная и кэш классификации).
- Каталог постоянных копий классификации **ничем не ограничен** и не входит в общий бюджет файлового кэша, поэтому копии оседают навсегда.
- При сбое записи (нехватка места) **обрезанная** копия остаётся на диске; проверка валидности кэша смотрит только на «размер больше нуля», поэтому усечённый APK при следующем заходе принимается за валидный и читается классификатором (parse-fail → «не VR»), тихо маскируя настоящие VR-приложения.
- Неудачная классификация **не мемоизируется**, поэтому каждый повторный показ элемента (скролл/ре-байнд) заново запускает полное скачивание и повторный сбой - десятки одинаковых ошибок в логе и продолжающаяся сетевая/дисковая нагрузка на уже забитом устройстве.

На устройстве зафиксировано в логах 2026-06-08 16:05: при просмотре облачной папки с APK кэш-том заполняется до `ENOSPC (No space left on device)`, после чего распознавание тихо деградирует.

Родительский тикет S0355 сделал этот путь **неаварийным** (перехват сбоя + деградация до «не VR»), но в §6.2 явно вынес устранение корневой причины (расход диска, перенос временных файлов) в отдельный follow-up - это он.

## 2. Цели

1. Классификация облачного APK не оставляет постоянную полную копию архива в кэше: копия существует только на время чтения и удаляется сразу после.
2. Повторный показ того же элемента не приводит к повторному скачиванию APK, если результат уже известен или зафиксирован сбой нехватки места.
3. Прерванная запись копии не оставляет на диске обрезанный файл и не может быть принята за валидный кэш.
4. Если постоянный дисковый кэш копий всё же сохраняется, он ограничен по объёму либо учитывается в общем бюджете файлового кэша.

**Non-goals:**

- Изменение алгоритма определения VR (сигнатуры манифеста, набор признаков).
- Изменение визуального вида бейджа VR-приложения.
- Перенос самого крах-фикса S0355 (уже сделан и закрыт).
- Изменение поведения для локальных и сетевых (SMB/SFTP/FTP) источников, кроме общей чистки обрезанных временных файлов.

## 4. Контекст текущей архитектуры

Слой UI-менеджеров noLegal запрашивает классификацию для элементов списка и кэширует **результат** в памяти (ограниченный LRU по числу записей). Чтобы прочитать содержимое облачного APK, недоступного системному инсталлятору напрямую, используется общий слой облачных файловых операций.

Сейчас этот слой при загрузке из облака скачивает файл в **временную** копию в кэше, а затем для приёмника-кэша создаёт **вторую, постоянную** копию рядом. Постоянная копия задумана как «переиспользуемая на диске», но память уже мемоизирует результат классификации, поэтому диск-кэш дублирует роль памяти, не давая выгоды и расходуя место без ограничения. Проверка наличия копии смотрит только на ненулевой размер, не сверяя его с ожидаемым размером файла.

## 5. Предлагаемый подход

Снизить дисковый след классификации до транзиентного: читать APK во временную копию, удалять её сразу после классификации, не плодить постоянный диск-кэш и не держать две полные копии одновременно. Устранить каскад ретраев и утечку обрезков.

### 5.1 Основные столпы / модули

- **Транзиентная копия для классификации.** Слой распознавания получает локальную копию только на время чтения манифеста и освобождает её сразу после; постоянный дисковый кэш копий не ведётся (роль переиспользования закрывает память-кэш результата).
- **Устранение двойного копирования.** На пути cloud→локальный кэш не держать одновременно временную и целевую полные копии на одном томе (перенос/переименование вместо копирования, либо прямая запись в целевой файл).
- **Чистка обрезков.** При сбое записи копии частичный файл удаляется; валидность любого кэш-файла проверяется по совпадению с ожидаемым размером, а не только по «больше нуля».
- **Мемоизация сбоя нехватки места.** Сбой класса «нет места» фиксируется так, что повторный показ элемента не перезапускает полное скачивание; каскад одинаковых ошибок прекращается.

### 5.2 Потоки данных и событий

UI-список запрашивает классификацию элемента → слой распознавания получает транзиентную локальную копию через общий слой облачных операций → классификатор читает копию → копия удаляется → результат кэшируется в памяти и возвращается в UI. Повторный показ того же элемента обслуживается из памяти без обращения к диску и сети.

### 5.3 Точки расширяемости

- Чистка обрезанных временных копий и устранение двойного копирования формулируются на уровне общего слоя облачных операций, без флейвор-зависимых ветвлений.
- Политика «транзиентная vs. ограниченный диск-кэш» инкапсулируется за абстракцией резолвера архива в noLegal, чтобы при необходимости вернуть ограниченный диск-кэш без изменения вызывающего слоя.

## 6. Открытые вопросы / Research items

1. **Полный отказ от диск-кэша vs. ограниченный диск-кэш**
   - **Вопрос:** достаточно ли только транзиентной копии (память-кэш результата покрывает ре-байнды), или есть сценарии в одной сессии, где повторное чтение того же APK с диска оправдывает ограниченный по объёму диск-кэш?
   - **Нужно выяснить:** перекрывает ли ёмкость память-кэша результата типичный размер облачной папки с APK; как часто один и тот же элемент классифицируется повторно после вытеснения из память-кэша.
   - **Статус:** Resolved
   - **Вывод:** полный отказ от диск-кэша. Память-кэш результата (`VrApkClassificationCache`) - это `LruCache` на 256 записей с ключом `(path, size, lastModified)`; типичная облачная папка с APK заметно меньше 256 элементов, поэтому ре-байнды при скролле обслуживаются из памяти без обращения к диску. Постоянная копия APK на диске (`vr_apk_classification/<hash>_<size>_<name>`) дублирует роль память-кэша, не давая выгоды, и растёт без ограничения. Транзиентная копия (скачать → классифицировать → удалить) убирает накопительный рост. Риск повторного скачивания при папке >256 элементов принят; запасной вариант (ограниченный диск-кэш) остаётся за абстракцией резолвера (§5.3).

2. **Политика при нехватке места**
   - **Вопрос:** фиксировать сбой «нет места» на всю сессию (стоп классификации до перезапуска) или применять backoff с периодической повторной попыткой?
   - **Варианты:** стоп-на-сессию (просто, нет спама, но бейджи не вернутся после освобождения места до перезапуска); backoff (бейджи восстановятся, но сложнее и риск частичного спама).
   - **Нужно выяснить:** реально ли место освобождается в пределах сессии настолько часто, чтобы backoff окупался.
   - **Статус:** Resolved
   - **Вывод:** стоп-на-сессию. Нехватка места фиксируется флагом уровня сессии в `VrApkClassificationCache`; после первого сбоя «нет места» все последующие запросы классификации сразу отдают `NOT_VR` без скачивания, что обрывает каскад одинаковых ошибок. Флаг живёт в памяти и сбрасывается при перезапуске процесса, поэтому бейджи восстановятся после освобождения места и перезапуска. Backoff отклонён: нехватка места на кэш-томе Quest при просмотре крупных APK не освобождается сама по себе в пределах сессии, поэтому периодические повторы лишь вернут спам без выгоды.

3. **Сигнал пользователю о нехватке места**
   - **Вопрос:** нужен ли видимый сигнал (toast/иконка) о том, что распознавание остановлено из-за нехватки места, или тихая деградация (как сейчас, после S0355) достаточна?
   - **Нужно выяснить:** ожидание владельца по UX; не вводит ли сигнал новых строк/доступности сверх non-goals.
   - **Статус:** Resolved
   - **Вывод:** тихая деградация, как после S0355. §3.2 жёстко запрещает новые пользовательские строки, а видимый сигнал потребовал бы их (EN/RU/UK) и доступности сверх non-goals. Распознавание VR - вспомогательный бейдж; отсутствие бейджа при нехватке места эквивалентно «не VR» и не блокирует основную работу с файлами. Диагностический след остаётся в логе (один раз при срабатывании флага).

## 9. Архитектурные решения (ADR)

**ADR-1: Транзиентная копия вместо постоянного диск-кэша**

- **Решение:** держать локальную копию APK только на время чтения манифеста и удалять сразу после; переиспользование обеспечивать память-кэшем результата.
- **Альтернативы:** ограниченный по объёму/LRU постоянный диск-кэш; учёт каталога копий в общем бюджете файлового кэша.
- **Почему:** память-кэш уже мемоизирует результат по ключу (путь, размер, mtime), поэтому постоянная копия на диске дублирует его роль, расходуя место без ограничения. Транзиентность убирает накопительный рост без потери функциональности; ограниченный диск-кэш остаётся запасным вариантом по итогам §6.1.

## 11. Критерии готовности (strategic-level)

1. После просмотра облачной папки с APK в кэше не остаётся постоянных полных копий архивов.
2. Повторный показ ранее классифицированного элемента не вызывает повторного скачивания APK.
3. При нехватке места распознавание деградирует без каскада одинаковых ошибок в логе и без накопления обрезанных файлов.
4. Бейджи VR появляются для VR-APK в нормальных условиях (свободное место есть).
