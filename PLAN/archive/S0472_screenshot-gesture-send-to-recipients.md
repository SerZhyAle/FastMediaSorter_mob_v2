## 1. Проблема

У жеста-скриншота уже есть набор вариантов поведения после захвата, и среди них есть «Поделиться» - но это системный диалог выбора приложения, в котором перечислены все установленные приложения без фильтра.

Пользователь хочет ещё один вариант поведения: чтобы сразу открывался курированный диалог «Отправить в..», составленный из списка разрешённых получателей, который уже настраивается в разделе настроек «Плеер» -> «Команды отправить файл в». Сейчас этот курированный список доступен только из плеера и недостижим из жеста-скриншота.

Эффект: пользователь, у которого настроены 2-3 постоянных адресата для файлов, после жеста-скриншота вынужден пролистывать полный системный список вместо своего короткого настроенного. Область - захват экрана по жесту (видимый только в noLegal) и общий слой отправки файла получателям.

---

## 2. Цели

1. К существующему набору вариантов поведения жеста-скриншота добавляется новый вариант: «отправить в разрешённых получателей».
2. При срабатывании этого варианта после захвата сразу появляется курированный диалог «Отправить в..», а не системный chooser со всеми приложениями.
3. Список в этом диалоге берётся из тех же разрешённых получателей, что настроены в «Плеер» -> «Команды отправить файл в», с тем же правилом видимости (включённые получатели, применимые к изображению).
4. Если разрешённый получатель ровно один - отправка идёт сразу, без лишнего диалога (как в плеере).
5. Существующий вариант «Поделиться» (системный chooser) сохраняется без изменений - новый вариант добавляется рядом, не заменяет его.

**Non-goals:**

- Не меняется поведение существующего варианта «Поделиться».
- Не меняется состав и настройка списка получателей в «Плеер» -> «Команды отправить файл в» - он переиспользуется как есть.
- Не вводится отдельный от плеера список получателей только для скриншотов.
- Фича не выводится в флейворы, где жест-скриншот недоступен.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Поведение при пустом списке применимых получателей должно быть предсказуемым: либо короткая подсказка, либо откат к системному диалогу (решается в §6).
2. Новый вариант в пикере действий стоит расположить рядом с существующим «Поделиться», чтобы их связь была очевидна.

## 4. Контекст текущей архитектуры

За жест-скриншот отвечает связка из слоя захвата (видимого только в noLegal) и общего слоя пост-захватной диспетчеризации: жест распознаётся, кадр сохраняется, затем по выбранному для направления варианту выбирается дальнейшее действие. Один из существующих вариантов - «Поделиться» - вызывает системный диалог выбора приложения.

Курированный список получателей живёт в общем слое отправки файла: получатели описаны декларативно, фильтруются по признакам «включён», «доступен» и «применим к типу медиа», и предъявляются плеером либо как диалог выбора, либо как прямая отправка единственному получателю.

Сейчас проблему из §1 нельзя решить настройкой, потому что пост-захватная диспетчеризация не знает про курированный слой получателей: её вариант «Поделиться» жёстко ведёт в системный chooser, а курированный диалог предъявляется только из контекста плеера. Между двумя подсистемами нет связующего варианта поведения.

## 5. Предлагаемый подход

Ввести новый вариант поведения жеста-скриншота, который после сохранения кадра передаёт его в существующий курированный слой отправки получателям, вместо системного chooser. Связь односторонняя: захват вызывает общий слой отправки; обратной зависимости нет.

### 5.1 Основные столпы / модули

- **Новый вариант пост-захватного действия (общий слой).** Расширяется существующий набор вариантов поведения жеста ещё одним значением - «отправить в разрешённых получателей». Диспетчеризация пост-захвата получает один новый маршрут; существующие маршруты, включая «Поделиться», не меняются.
- **Переиспользование курированного слоя получателей (общий слой).** Новый маршрут обращается к уже существующему сервису отправки получателям, передавая ему сохранённый кадр и тип медиа «изображение». Состав списка определяется существующим фильтром (включённые + доступные + применимые к изображению получатели) - без отдельной настройки для скриншотов.
- **Мост предъявления UI со стороны захвата (флейвор-специфично).** Курированный диалог требует переднеплановый UI-контекст, которого у пост-захватной диспетчеризации нет (она работает из фонового сервиса). Нужен контракт, позволяющий предъявить приложенческий диалог из не-Activity контекста захвата; конкретный механизм - предмет §6.

### 5.2 Потоки данных и событий

Жест → захват кадра → сохранение → пост-захватная диспетчеризация распознаёт вариант «отправить в получателей» → передаёт сохранённый кадр и тип «изображение» в курированный слой отправки → слой строит список из общих настроек разрешённых получателей (фильтр включённости и применимости) → предъявляет курированный диалог, либо при единственном получателе отправляет сразу.

### 5.3 Точки расширяемости

- **Контракт пост-захватного действия** - расширяется новым вариантом; должен оставаться открытым к добавлению вариантов без правок остальных маршрутов.
- **Контракт курированной отправки получателям** - переиспользуется как есть; новый потребитель (захват) не должен требовать его изменения помимо вызова из нового контекста.
- **Контракт переднепланового UI-хоста** - вводимый или переиспользуемый из существующего паттерна предъявления диалога из контекста захвата; даёт курированному диалогу нужный UI-контекст без бизнес-логики на стороне захвата.

## 6. Открытые вопросы / Research items

1. **Хостинг курированного диалога из контекста захвата**
   - **Вопрос:** как предъявить курированный диалог «Отправить в..» из пост-захватного контекста, у которого нет Activity, с учётом ограничений фонового запуска Activity после остановки FGS (API 29+) и пути accessibility (API 30+)?
   - **Варианты:** прозрачная Activity-трамплин (паттерн уже существующего экрана согласия захвата); действие в уведомлении с открытием диалога по тапу; маршрут через существующий отдельный медиа-экран с авто-действием.
   - **Нужно выяснить:** какой механизм надёжно проходит ограничения фонового запуска на обоих путях захвата и даёт минимум лишних шагов пользователю.
   - **Статус:** Resolved
   - **Решение:** переиспользовать существующий standalone-просмотрщик через тот же проверенный путь `EXTRA_AUTO_ACTION`, которым диспетчер уже открывает «рисование» и «OCR-перевод»; новый авто-экшен предъявляет курированный диалог из контекста просмотрщика. Без новой Activity и нового пути фонового запуска.
   - **Артефакт:** `PLAN/S0472_screenshot-gesture-send-to-recipients/research/01__capture-to-curated-send-seam.md`

2. **Поведение при пустом списке применимых получателей**
   - **Вопрос:** что показать, если ни один разрешённый получатель не включён или не применим к изображению?
   - **Варианты:** короткая подсказка по communication policy; молчаливый откат к системному chooser; открыть настройки получателей.
   - **Нужно выяснить:** какой исход владелец считает ожидаемым; рекомендация по умолчанию - подсказка с предложением настроить получателей, без молчаливого ничего.
   - **Статус:** Resolved
   - **Решение:** зеркалить существующую конвенцию курированного слоя - при пустом списке диалог не показывается, скриншот остаётся открытым в просмотрщике как предсказуемый откат. Список почти всегда непустой за счёт системного «поделиться» как catch-all. Отдельная подсказка о пустом списке отложена как необязательная полировка (пожелание §3.1).

3. **Соотношение с существующим вариантом «Поделиться»**
   - **Вопрос:** новый вариант добавляется рядом или заменяет «Поделиться»?
   - **Нужно выяснить:** ничего - запрос явно про «ещё одну опцию», поэтому вариант добавляется рядом, системный chooser сохраняется.
   - **Статус:** Resolved

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Ограничения фонового запуска Activity после остановки FGS блокируют показ курированного диалога | Средняя | Вариант «не срабатывает» молча после захвата | Выбрать в §6.1 механизм хостинга, устойчивый к фоновым ограничениям; проверить оба пути захвата на устройстве |
| Сохранённый кадр недоступен как URI (сетевой приёмник сохранения) | Средняя | Нечего отправлять получателю | Корректный мягкий откат с подсказкой, как у существующего «Поделиться» |
| Пустой список применимых получателей | Средняя | Пустой или бесполезный диалог | Определить исход в §6.2; не показывать пустой диалог |
| Метка нового варианта неоднозначна рядом с «Поделиться» | Низкая | Пользователь путает системный и курированный варианты | Метка и тон по communication policy, явно отражающие «свой список получателей» |

## 9. Архитектурные решения (ADR)

**ADR-1: Новый вариант добавляется рядом, не заменяет «Поделиться»**

- **Решение:** ввести отдельное значение пост-захватного действия, сохранив существующий системный chooser.
- **Альтернативы:** перенаправить существующий «Поделиться» на курированный диалог.
- **Почему:** запрос явно про «ещё одну опцию»; перенаправление сломало бы поведение у тех, кто уже выбрал системный chooser.

**ADR-2: Переиспользование курированного слоя получателей вместо фильтрованного системного chooser**

- **Решение:** новый вариант вызывает существующий слой отправки получателям и его список/фильтр.
- **Альтернативы:** строить системный chooser, заранее отфильтрованный по пакетам разрешённых получателей.
- **Почему:** пользователь просит именно настроенный список из «Команды отправить файл в»; переиспользование даёт единый список, единое правило видимости и поведение «один получатель - сразу отправка».

## 11. Критерии готовности (strategic-level)

1. В пикере действий жеста-скриншота присутствует новый вариант рядом с «Поделиться», локализованный на EN/RU/UK.
2. При выборе этого варианта и срабатывании жеста после захвата появляется курированный диалог «Отправить в..» из настроенных разрешённых получателей.
3. Список в диалоге совпадает по составу с тем, что показывает плеер для изображения (включённые и применимые получатели).
4. При единственном применимом получателе отправка происходит сразу, без диалога.
5. Существующий вариант «Поделиться» (системный chooser) продолжает работать без изменений.
6. При отсутствии применимых получателей пользователь видит понятный исход (по решению §6.2), а не пустой диалог или молчание.
7. Сборка noLegal debug проходит; вариант проверен на устройстве на обоих путях захвата.

- `ScreenshotGestureActionDispatcher` (`SEND_TO_RECIPIENTS` -> `openInViewer(.., AUTO_ACTION_SEND_TO)`, probe `Timber.d("S0472:`).
