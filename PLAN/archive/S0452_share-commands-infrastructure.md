## 1. Проблема

Запрошены четыре независимые настройки видимости команд «отправить файл в..» (Keep, Email, системный Share, мессенджеры). Каждая повторяет один и тот же каркас: тумблер уровня профиля в общей группе настроек плеера, миграция с дефолтом, проверка доступности (установлен ли пакет, есть ли Google/интернет) и сквозной гейтинг видимости команды во всех меню, где она реализована. Реализация по отдельности приведёт к четырёхкратному дублированию каркаса и рассогласованному поведению. Область - настройки профиля и слой шаринга в плеере и просмотре.

---

## 2. Цели

1. Единая сворачиваемая группа «Команды отправить файл в..» на странице настроек «Плеер» как хост для всех тумблеров share-команд.
2. Расширяемый per-profile реестр share-таргетов: добавление нового таргета сводится к регистрации (идентификатор, дефолт, предикат доступности, действие отправки) без правки общего каркаса.
3. Общий механизм хранения флагов уровня профиля и их миграции с заданным дефолтом.
4. Общий предикат доступности таргета для пары профиль+устройство (пакет установлен, признак Google, признак интернета).
5. Сквозной гейтинг: команда «отправить в X» видна в любом меню тогда и только тогда, когда её флаг включён И таргет доступен.

**Non-goals:**

- Конкретные таргеты Keep/Email/Share/мессенджеры - остаются в S0443/S0444/S0445/S0446.
- Реальная отправка в мессенджеры с выбором получателя - в S0446.
- Создание самой страницы настроек «Плеер» - уже сделано в S0442.

## 4. Контекст текущей архитектуры

Страница настроек «Плеер» (бывшая «Воспроизведение») существует после S0442; группы строятся как сворачиваемые секции. Слой шаринга уже частично реализован: есть системный инвокер шаринга, обёртка над Telegram-таргетами, менеджер шаринга в плеере, share-операции в просмотре, отправка в Google Lens. Чего нет - единой точки, которая знает обо всех share-командах, держит их per-profile флаги и решает видимость по правилу «флаг И доступность». Поэтому сейчас каждый новый таргет потребовал бы собственного тумблера, миграции и проверки.

---

## 5. Предлагаемый подход

Ввести реестр share-таргетов: каждый таргет описывается идентификатором, дефолтом флага, предикатом доступности и действием отправки. Группа настроек «Команды отправить файл в..» строится из реестра. Меню шаринга в плеере и просмотре спрашивают реестр, какие команды показать, по правилу «флаг профиля включён И таргет доступен».

### 5.1 Основные столпы / модули

- Реестр share-таргетов (декларация + перебор).
- Хранилище per-profile флагов + миграция с дефолтом из декларации таргета.
- Предикат доступности (пакет установлен, Google, интернет).
- Построитель группы настроек из реестра.
- Гейтинг видимости команд в местах их вызова.

### 5.2 Потоки данных и событий

- Настройки: реестр → построитель группы → тумблеры → запись флага в профиль.
- Меню: точка вызова → запрос к реестру (флаг И доступность) → отображение/скрытие команды → действие отправки таргета.

### 5.3 Точки расширяемости

- Добавление нового таргета - одна регистрация в реестре.
- Предикат доступности расширяем новыми признаками без правки потребителей.

## 9. Архитектурные решения (ADR)

- ADR-1 - Хранилище флагов: app-global DataStore (`AppSettings`), не Room. Причина: команды управляют видимостью «по всей программе» (один on/off), «профиль» = `DeviceProfile`-пресет, прецедент - `enableGoogleLens`. Следствие: schema-bump Room не требуется, дефолты задаются по `DeviceProfileType`.
- ADR-2 - Абстракция: выделить доменный реестр `ShareTarget` + единый `ShareTargetAvailabilityResolver` (пакет установлен / есть Google / есть интернет), вместо трёх ad-hoc проверок и перегруженного layout-планировщиком enum `PlayerCommand`. Причина: смысл фундамента - тонкая регистрация новых таргетов. Следствие: настройки, панель команд и browse-overflow читают один реестр; `PlayerCommand` ссылается на записи реестра, а не дублирует доступность.

## 11. Критерии готовности (strategic-level)

1. На странице «Плеер» есть сворачиваемая группа «Команды отправить файл в..» (скрыта, пока реестр пуст).
2. Регистрация нового share-таргета не требует правки общего каркаса (Hilt `@IntoSet ShareTarget`).
3. Предоставлен единый seam гейтинга `IsShareTargetEnabledUseCase` (флаг) + `ShareTargetAvailabilityResolver.isAvailable` (доступность); фактическую проводку «команда видна iff флаг И доступность» в свои поверхности делает каждый таргет-тикет (решение владельца 2026-06-16: гейтинг делегирован S0443-S0446, чтобы не трогать горячий командный путь спекулятивно).
4. Тумблер недоступного таргета показан как disabled с не-цветовым отличием (подпись «Не установлено»).
5. Дефолт флага задаётся декларацией таргета (`ShareTargetDefault`), резолвится через capability в резолвере.
