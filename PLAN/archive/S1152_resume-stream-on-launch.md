## 0. Захваченный материал (inbox)

**Захвачено:** 2026-07-22

**Текст:**

Если из программы вышли при проиглрывания трансляции - запуск программы возобновляет эту трансляцию (как сейчас с медиафайлами)

---

## 1. Проблема

Для медиафайлов приложение уже умеет «возобновление при следующем запуске»: последнее активное воспроизведение сохраняется и на холодном старте пользователь возвращается в плеер/браузер на то же место. Для трансляций (радио и видео) этого нет - выход из приложения во время трансляции теряет контекст, и следующий запуск открывает обычный домашний экран. Пользователь, слушавший радиостанцию или смотревший трансляцию, вынужден заново открывать список трансляций и искать нужный источник.

---

## 2. Цели

1. На холодном старте, если предыдущий сеанс завершился при активной трансляции, приложение возвращает пользователя к этой трансляции - зеркально существующему «resume» для медиафайлов.
2. Радиотрансляция (AUDIO) возобновляется как воспроизводимая (продолжает играть), если она играла в момент выхода.
3. Видеотрансляция (VIDEO/RTSP) НЕ участвует в возобновлении: она не записывается в resume-слот вообще (решение владельца 2026-07-26, см. §3.1).
4. Возобновление подчиняется той же пользовательской настройке, что и медиа-resume (единый переключатель «возобновлять при следующем запуске»).
5. Запись resume живёт только пока трансляция реально играет: выход с экрана трансляций без активного воспроизведения стирает её.

**Non-goals:**

- Синхронизация позиции внутри видеотрансляции (у живых трансляций нет seek-позиции для восстановления).
- Возобновление нескольких трансляций одновременно / история трансляций.
- Изменение механизма resume для медиафайлов.
- Wear OS.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Поведение «как сейчас с медиафайлами» - переиспользовать существующий UX и настройку, не вводить отдельный переключатель.
2. Уточнение 2026-07-26 (по отчёту с устройства): первая редакция записывала в resume-слот и видеотрансляцию, а стирала запись только при явной остановке радио. Из-за этого один просмотр видеоканала на 48 часов TTL заставлял каждый холодный старт открывать экран трансляций. Владелец выбрал оба ужесточения сразу: видео не записывается никогда, и любой выход с экрана трансляций без активного воспроизведения стирает запись.

## 4. Контекст текущей архитектуры

Существующий resume реализован на слое приложения и запускается из домашнего экрана: помощник старта читает сохранённое состояние, проверяет доступность ресурса с жёстким таймаутом и маршрутизирует пользователя обратно в плеер или браузер. Состояние хранится в `SharedPreferences` (не Room), keyed по идентификатору окна, с TTL. Гейт - пользовательская настройка «возобновлять при следующем запуске».

Трансляции живут в отдельной подсистеме: экран списка трансляций проигрывает радио inline (через фоновый аудио-сервис или локальный плеер) и запускает полноэкранный плеер для видео/RTSP. Трансляции используют синтетический идентификатор ресурса и URL как путь; они НЕ участвуют в текущем resume - ни одна точка сохранения resume-состояния не срабатывает из потока трансляций. Поэтому проблему из §1 нельзя решить «само собой»: механизм resume завязан на реальный медиа-ресурс (`resourceId`, `MediaType`, `ScreenType` = PLAYER/BROWSER), а трансляция не укладывается в эту модель (радио не имеет экрана PLAYER/BROWSER, синтетический id не резолвится в медиа-ресурс).

---

## 5. Предлагаемый подход

Расширить механизм «resume при запуске» отдельной, лёгкой веткой для трансляций, не связывая синтетические stream-идентификаторы с медиа-resume-путём.

### 5.1 Основные столпы / модули

- **Хранилище stream-resume:** отдельная prefs-модель последней активной трансляции (url, заголовок, тип воспроизведения AUDIO/VIDEO, флаг «играло в момент выхода», отметка времени). Собственный store/репозиторий по образцу медиа-resume, но без завязки на медиа-ресурс.
- **Точки сохранения (в потоке трансляций):** экран списка трансляций записывает запись при старте радио, очищает её при остановке радио, при запуске видеотрансляции и при выходе с экрана без активного воспроизведения.
- **Маршрутизация на старте:** помощник старта домашнего экрана, до/рядом с существующей медиа-resume-проверкой, обнаруживает свежую stream-resume-запись и маршрутизирует на экран списка трансляций с намерением «возобновить», которое авто-запускает нужную трансляцию.
- **Гейт:** та же пользовательская настройка resume, что и для медиа.

### 5.2 Потоки данных и событий

- Запись: экран трансляций → stream-resume store (при play/stop трансляции).
- Чтение: старт приложения → помощник старта → stream-resume store → (TTL + гейт настройки) → экран трансляций с «resume»-намерением → авто-play выбранной трансляции.
- Приоритет между медиа-resume и stream-resume: «последняя активность выигрывает» по отметке времени - восстанавливается тот сеанс (медиа или трансляция), что был активен последним.

### 5.3 Точки расширяемости

- Модель stream-resume оставить расширяемой под будущие поля (напр., последняя ICY-метадата), не ломая обратную совместимость prefs.
- Правило «что вообще считается возобновляемым» держать в одной точке: сейчас это только играющее радио, запись любого другого вида на старте отбрасывается.

## 9. Архитектурные решения (ADR)

- **ADR-1:** stream-resume - отдельное prefs-хранилище и модель, а не переиспользование медиа-`ResumeState`. Причина: медиа-resume завязан на реальный `resourceId`/`MediaType`/`ScreenType`, которые не отображаются на радио и синтетические stream-id; связывание загрязнило бы медиа-путь и потребовало бы фиктивных ресурсов.
- **ADR-2:** приоритет медиа/стрим - last-activity-wins по отметке времени. Причина: простое, предсказуемое правило, зеркалит «одно последнее воспроизведение».

## 11. Критерии готовности (strategic-level)

1. Радио играло → выход из приложения → холодный запуск → приложение открывает список трансляций и радиостанция снова играет (индикатор «сейчас играет» активен).
2. Видеотрансляция шла → выход → холодный запуск → приложение открывает список трансляций с этой трансляцией, готовой к запуску (без принудительного автостарта видео).
3. Настройка resume выключена → холодный запуск НЕ возобновляет трансляцию.
4. Последним был медиафайл (не трансляция) → возобновляется медиафайл; последней была трансляция → возобновляется трансляция (last-activity-wins).
5. Устаревшая (за TTL) или недоступная трансляция → возобновление мягко деградирует к обычному старту, без ошибок.
6. Room-схема не изменена; сборки со стримами компилируются; поведение подтверждено на устройстве.

> Критерий 2 сформулирован до уточнения 2026-07-26 (§3.1) и более не действует: видеотрансляция не записывается в resume-слот,
> поэтому холодный старт после видео обязан открывать обычный главный экран. Проверено на устройстве как «streams NOT opened».
