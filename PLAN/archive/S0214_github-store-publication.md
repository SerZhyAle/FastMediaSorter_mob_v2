## 1. Проблема

Владелец хочет, чтобы приложение появилось в каталоге GitHub Store (`OpenHub-Store/GitHub-Store`) — это open-source агрегатор Android-приложений, который автоматически индексирует публичные GitHub-репозитории с установочными APK-активами в последнем релизе. Сейчас репозиторий `SerZhyAle/FastMediaSorter_mob_v2` публичен, но не удовлетворяет ни одному из критериев индексации: у репозитория нет тегов (`topics`), описание неинформативное («Fast Media Sorter mob v2»), и в `Releases` нет ни одного релиза с прикреплёнными APK. Сборка релизных артефактов происходит локально и наружу не публикуется, поэтому ни поиск GitHub Search API, ни ranking-эвристики GitHub Store приложение не находят.

Параллельная задача: после выполнения условий индексации нужно поддерживать пригодность для авто-обновления через GitHub Store (стабильный signing fingerprint, предсказуемая схема имён активов для per-app variant pinning).

---

## 2. Цели

1. Репозиторий проходит фильтр индексации GitHub Store: публичный, в последнем релизе есть хотя бы один `.apk`, выставлены релевантные `topics`, описание содержит ключевые термины для поиска.
2. Существует воспроизводимый процесс публикации релизной сборки в GitHub Releases с прикреплёнными APK-активами и единой схемой именования.
3. README репозитория содержит кликабельный бейдж «Get it on GitHub Store», ведущий на корректную deep-link страницу приложения внутри стора.
4. Авто-обновление через GitHub Store работает стабильно: между релизами сохраняется один и тот же signing fingerprint, имена активов поддерживают `asset filter regex` без ручной перенастройки пользователем.
5. Публикация выполняется только из релизного workflow (ветка `main`, fix-release или DEBUG-merge), а не из произвольной development-ветки.

**Non-goals:**

- Внутри-приложенческий экран «Доступно в GitHub Store» / напоминание / deep-link обратно в стор — оставлено за рамками первой итерации.
- Публикация в F-Droid, Obtainium, Scoop, Winget, Homebrew — это отдельные каналы со своими требованиями.
- Распространение `noLegal`-flavor через публичные каналы — категорически вне объёма (см. §3.2 и §9).
- Перенос `Wear OS`-модуля в отдельный публичный канал — не затрагивается.
- Перевод README / описания репозитория на дополнительные языки сверх EN/RU/UK.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Понимать, какие шаги обязательны, какие — желательны, а какие можно отложить (приоритизация ресёрча).
2. По возможности использовать существующие релизные скрипты и worktree-структуру `FastMediaSorter_release`, а не вводить параллельный CI/CD контур.
3. Сохранить контроль над тем, что именно публикуется в публичный канал — никакого автоматического подтягивания noLegal-сборок.
4. Минимизировать риск ломки авто-обновления при будущих fix-release циклах.

### 3.2 Жёсткие ограничения

- **Flavor:** в публичный канал GitHub Store попадает только `standard` (опционально `vr` как отдельный артефакт того же релиза — решается в §6). `vrUnlicensed`, `noLegal`, `lite`, `photos`, `legacy` публикации в этот канал не подлежат.
- **Источник сборки:** релизные APK публикуются только с веток, допустимых для релиза согласно `CLAUDE.md` «Git Branching Model» (`main` после merge DEBUG-ветки или после fix-release). Публикация с произвольной DEBUG-ветки запрещена.
- **Signing key:** ключ подписи `standard`-release остаётся стабильным между релизами; ротация ключа в публикуемом канале допускается только как осознанная операция с обновлением документации и предупреждением пользователей (auto-update в GitHub Store блокируется при mismatch fingerprint — это документированное поведение, не баг).
- **API level / Wear OS:** не затрагивается — публикуется существующий `standard` APK с текущими `minSdk 26` / `compileSdk 35`. Wear-модуль вне объёма.
- **Производительность / совместимость данных:** нейтрально — задача не вносит код в runtime-пути приложения; миграций Room и BuildConfig-гейтов не требует.
- **Локализация:** README-бейдж и сопроводительная подпись добавляются параллельно в EN/RU/UK. Текстовая часть бейджа подчиняется `docs/COMMUNICATION_POLICY.md` (тон-чеклист §6 политики — обязательный гейт перед коммитом строк).
- **Лицензионный режим `noLegal`:** правило `docs/FEATURES_noLegal*.md` сохраняется — никакие `noLegal`-only возможности не упоминаются в публичной странице репозитория, в README или в описании релиза.
- **Доступность:** README-бейдж сопровождается осмысленным `alt`-текстом, кликабельная зона достаточного размера, не-цветовое отличие сохраняется (бейдж — иконка с текстом).

## 4. Контекст текущей архитектуры

В проекте уже есть релизный pipeline: отдельный git-worktree `FastMediaSorter_release` checked out на `main`, скрипты `a.ps1 r` / `a.ps1 vr` собирают подписанные APK для `standard` и VR-вариантов. Артефакты остаются локально и распространяются вручную. История релизов фиксируется в `dev/CHANGELOG.md` и `WHATS_NEW.md`. Метаданные репозитория на GitHub (`description`, `topics`, `homepage`) не редактировались под discoverability — это видно по тому, что `topics` пуст, а описание — дефолтное.

Корень проблемы: канал «GitHub Releases» в проекте не используется как точка распространения. Соответственно, ни одна внешняя система, опирающаяся на GitHub API (GitHub Store, Obtainium, F-Droid Index — в части GitHub-релизов), приложение не видит. Чтобы попасть в GitHub Store, не нужно ничего отправлять в их репозиторий — достаточно, чтобы наш собственный репозиторий удовлетворял публичным критериям индексации.

---

## 5. Предлагаемый подход

Подход разбивается на три параллельных столпа: настройка discoverability, выстраивание канала distribution и обеспечение update-контракта. Все три на стратегическом уровне затрагивают только релизный процесс и метаданные репозитория; runtime-код приложения не модифицируется.

### 5.1 Основные столпы / модули

**Столп 1 — Discoverability (метаданные репозитория и README):**

- Описание репозитория: переписать с учётом ключевых терминов (Android, file manager, media sorter, photo / video organizer, batch sort, SMB / cloud) в пределах лимита GitHub.
- Topics: набор тегов, релевантных категоризации GitHub Store (`android`, `mobile`, `apk`, плюс предметная область — `file-manager`, `photo-organizer`, `media-sorter` и т. п.; финальный список — см. §6).
- Homepage URL: указать стабильную ссылку (например, на release-страницу или на сайт, если он появится; иначе оставить пустым осознанно — см. §6).
- README: добавить кликабельный бейдж «Get it on GitHub Store» с deep-link на `github-store.org/app?repo=<owner>/<repo>` и сопроводительной подписью. Бейдж дублируется во всех существующих локалях README (EN / RU / UK).
- Скриншоты и баннер: репозиторий уже содержит визуальные материалы — оценить пригодность для презентации в карточке GitHub Store (рендерится README верхней частью) и при необходимости перегруппировать.

**Столп 2 — Distribution (канал GitHub Releases):**

- Релизный процесс расширяется заключительным шагом в `/skill-release`: после сборки `standard_release` для Google Play и VR release APK артефакты публикуются в GitHub Releases с фиксированной схемой имени актива. Схема выбирается так, чтобы `asset filter regex` в GitHub Store детерминированно отбирал нужный артефакт даже при появлении дополнительных flavor (см. §6).
- Текст release notes автоматически берётся из `WHATS_NEW.md` (или его секции для этой версии), чтобы пользователи GitHub Store видели в карточке «Release notes» осмысленное описание изменений.
- Версионирование: формат версии (`Y.YM.MDDH.Hmm` из `CLAUDE.md` § Version Format) остаётся без изменений; релизный тег согласован с этим форматом.
- Каналы pre-release / stable: первая итерация публикует только stable; pre-release из DEBUG-плато в публичный канал не отправляются.

**Столп 3 — Update contract (стабильность для auto-update):**

- Signing fingerprint: фиксируется как «не ротировать без явного спека». Документируется в `dev/DEV_OPS.md` (или в его релизной секции).
- Asset naming: имя APK включает только flavor-marker и версию; не включает hash, дату или git-sha, потому что это ломает per-app variant pinning у пользователей.
- Совместимость состояний приложения между релизами: задача distribution не вносит ломающих изменений в схему Room или формат настроек — это уже гарантируется отдельными правилами проекта; здесь только напоминание, что в публичном канале сломанная миграция = сломанный auto-update для всех пользователей одновременно.

### 5.2 Потоки данных и событий

GitHub Search API → GitHub Store backend (curated index с fallback на live passthrough) → клиент GitHub Store на устройстве пользователя → карточка приложения с release notes / installer list / APK Inspect → клик «Install» → загрузка APK с GitHub CDN (или с зеркала) → SHA-256 проверка против published asset digest → установка через Shizuku / Sui / Dhizuku / default installer. Наш репозиторий — только источник данных в начале цепочки; всё остальное — внутренняя ответственность GitHub Store.

Обратный поток (диагностика проблем): пользователи GitHub Store сообщают через свой fed feedback flow; до нас ошибки доходят как issue в нашем репозитории — стандартный канал, специальной интеграции не требует.

### 5.3 Точки расширяемости

- **Per-flavor публикация:** схема имени актива должна выдерживать появление дополнительного публичного flavor (например, `vr`) без переделки regex у уже добавивших приложение пользователей. Структура имени проектируется как «префикс-приложения + flavor-marker + версия + расширение», где flavor-marker для `standard` — отдельный, недвусмысленный токен.
- **Дополнительные каналы (F-Droid, Obtainium, Scoop):** не входят в первую итерацию, но текущее решение по асет-нэймингу и release-notes-источнику не должно ломать будущее подключение этих каналов.
- **Pre-release канал:** оставляется открытым; если будет включён, использует тот же релизный pipeline с флагом `--prerelease` у `gh release create`.
- **Внутри-приложенческий бейдж / About-блок про GitHub Store:** относится к non-goal первой итерации, но архитектурно ничего не блокирует — будет отдельным спеком при необходимости.
- **Flavor-isolation note:** задача не затрагивает src/main-код и не вводит `BuildConfig`-гейтов; соответственно, правила `dev/FLAVOR_DEVELOPMENT_RULES.md` здесь применимы только в части «не публиковать noLegal в публичный канал» (§3.2, §9).

## 9. Архитектурные решения (ADR)

**ADR-1: GitHub Store как канал — не требует кода в приложении**

- **Решение:** интеграция реализуется исключительно через метаданные репозитория и GitHub Releases. Внутри runtime-кода приложения ничего не меняется в первой итерации.
- **Альтернативы:** A — внутриприложенческий клиент GitHub Store API для самостоятельной проверки обновлений. B — кастомный update-канал, поверх которого GitHub Store автоматически индексирует.
- **Почему:** GitHub Store работает поверх стандартных GitHub-механизмов; добавление кода в приложение увеличивает поверхность поддержки без отдачи. Auto-update пользователю предоставляет сам GitHub Store через Shizuku / Sui / Dhizuku.

**ADR-2: В публичный канал публикуется только `standard` + `vr`**

- **Решение:** `standard` и `vr` публикуются как два APK-актива одного GitHub Release. `noLegal`, `vrUnlicensed`, `lite`, `photos`, `legacy` не публикуются в GitHub Store ни при каких условиях.
- **Альтернативы:** A — публиковать все flavor для максимального охвата. B — отдельные репозитории per flavor.
- **Почему:** `noLegal` — приватный по легальным причинам; `lite` / `photos` / `legacy` — нишевые варианты для конкретных устройств, в публичном каталоге создадут путаницу; `standard` — универсальный flavor с полным функционалом.

**ADR-3: Имя APK-актива — детерминированное, без git-sha / даты**

- **Решение:** имя файла актива содержит только префикс приложения, flavor-marker, версию и расширение. Никаких git-sha, timestamp, build-number в имени файла.
- **Альтернативы:** A — включить git-sha для трассируемости. B — включить дату сборки.
- **Почему:** GitHub Store даёт пользователю «per-app variant pinning + asset filter regex». Нестабильная часть имени ломает regex на каждом релизе, и пользователь теряет auto-update без видимой причины.

## 11. Критерии готовности (strategic-level)

1. Поиск в GitHub Store по имени приложения и по ключевым предметным запросам (file manager, media sorter, photo organizer) находит приложение и показывает его в карточке.
2. Карточка приложения содержит корректное название, иконку, описание, скриншоты (через README) и список релизов с release notes.
3. Установка из GitHub Store на тестовом устройстве проходит штатно (default installer и через Shizuku, если доступен).
4. Следующий релиз (после первого published) виден в GitHub Store как доступное обновление и устанавливается без потери пользовательских данных.
5. Signing fingerprint между двумя последовательными релизами одинаков; auto-update не блокируется fingerprint-проверкой GitHub Store.
6. README репозитория во всех существующих локалях (EN / RU / UK) содержит кликабельный бейдж «Get it on GitHub Store», ведущий на корректную страницу.
7. В публичных релизах отсутствуют артефакты `noLegal` / `vrUnlicensed` / `lite` / `photos` / `legacy`-flavor.
8. Решения по всем item'ам §6 зафиксированы в тактической спеке (статус Open → Resolved) до перехода в реализацию.
