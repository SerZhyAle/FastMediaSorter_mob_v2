## 0. Захваченный материал (inbox)

**Захвачено:** 2026-07-03

**Текст:**

Облачное хранилище (например Google Drive) в плеере и браузере в заголовке названия папки или файла я виду внутренний идентификатор облака а не только имя папки или файла. Пользователю этот набор цифр ни о чем не говорит - это не нужно показывать

---

## 1. Проблема

В файловом браузере верхняя информационная строка и интерактивные хлебные крошки показывают внутренний служебный идентификатор папки облачного провайдера (Google Drive / Dropbox / OneDrive) - бессмысленный набор символов - вместо человекочитаемого имени. Это проявляется в двух местах: (а) сразу при открытии корня облачного ресурса, ещё до перехода в любую под-папку - информационная строка показывает сырой синтетический путь ресурса; (б) при переходе внутрь под-папки - и информационная строка, и кликабельные хлебные крошки показывают идентификатор вместо имени под-папки. Проверка кода плеера показала, что заголовок воспроизведения строится корректно (использует настоящее имя файла) - проблема ограничена экраном браузера.

Причина обоих проявлений одна: логика построения информационной строки и хлебных крошек в браузере рассчитана на локальные иерархические пути (`/root/Folder1/Folder2`), где имя папки можно извлечь как последний сегмент пути или сравнить с последним сегментом пути ресурса. У облачных ресурсов путь плоский - `cloud://provider/<internal-id>` - сегменты пути не являются именами папок, а последний сегмент пути ресурса никогда не совпадает с именем ресурса (это имя, а не идентификатор). Как только путь не проходит эту проверку, код показывает путь как есть или извлекает из него сырой идентификатор - вместо реального имени, которое было получено при сканировании (`MediaFile.name`), но к этому моменту уже отброшено - используется только строка пути.

---

## 2. Цели

1. При открытии корня облачного ресурса (до перехода в любую под-папку) верхняя информационная строка браузера не показывает внутренний синтетический путь/идентификатор провайдера.
2. При навигации по под-папкам облачного ресурса верхняя информационная строка браузера показывает реальное имя текущей папки, а не внутренний идентификатор провайдера.
3. Интерактивные хлебные крошки при навигации по под-папкам облачного ресурса показывают реальные имена папок на каждом уровне вложенности, а не идентификаторы.
4. Поведение для локальных и сетевых (SMB/FTP/SFTP) ресурсов, где извлечение имени из пути уже работает корректно, не регрессирует.

**Non-goals:**

- Изменение заголовка воспроизведения файла в плеере - проверка кода подтвердила, что он уже корректно использует реальное имя файла, идентификатор туда не попадает.
- Полный редизайн модели навигации браузера (единый стек `MediaFile` вместо стека путей) - решаем точечно, добавлением параллельного стека реальных имён.
- Изменение формата REST-ответов облачных провайдеров или их мапперов (Google Drive/Dropbox/OneDrive) - подтверждено исследованием, что мапперы уже корректно читают настоящее имя из ответа API, идентификатор никогда не используется как имя.

## 4. Контекст текущей архитектуры

Экран браузера (`BrowseActivity` + `BrowseViewModel`) делегирует навигацию по под-папкам классу `BrowseNavigationManager`, который хранит в `BrowseState` только строковый путь текущей папки (`currentPath`) и стек путей родительских папок (`pathStack`) - без параллельного хранения реальных имён папок. Верхняя информационная строка строится в `BrowseUtilityManager.buildResourceInfo`, интерактивные хлебные крошки - в `BrowseNavigationManager.getBreadcrumbParts` (потребитель - `BreadcrumbView` через `BrowseManagerInitializer`). Оба места независимо пытаются восстановить имя папки, отрезая от `currentPath` префикс пути ресурса и разбивая остаток на сегменty - подход, работающий для локальных/сетевых путей (где сегмент пути и есть имя папки), но принципиально неверный для облачных ресурсов, чей путь - непрозрачная идентификатор-строка провайдера.

Реальное имя папки (`MediaFile.name`) доступно в момент клика по папке (`BrowseNavigationManager.navigateToFolder(folder: MediaFile)`), но не сохраняется - используется только для построения нового `currentPath`, после чего теряется.

## 5. Предлагаемый подход

`BrowseState` получает параллельный стек реальных имён посещённых папок наряду с уже существующим стеком путей. При навигации по клику на папку (единственная точка, где доступен реальный объект файла папки) в этот стек сохраняется настоящее отображаемое имя вместо повторного извлечения его из пути позже. Оба потребителя - верхняя информационная строка и интерактивные хлебные крошки - читают уже готовый список реальных имён из состояния экрана вместо самостоятельного (и в двух местах независимо дублирующегося) разбора пути. Это устраняет расхождение между локальными путями (где разбор пути случайно совпадает с именами папок) и облачными путями (где не совпадает) одним общим механизмом, без провайдер-специфичных условий.

### 5.1 Основные столпы / модули

- **Стек реальных имён навигации** - в состоянии экрана браузера хранится список отображаемых имён посещённых папок, синхронно со стеком путей: пополняется при переходе вглубь, сокращается при переходе назад/вверх, сбрасывается при возврате к корню ресурса.
- **Единый источник данных для заголовка и хлебных крошек** - оба потребителя интерфейса читают этот список вместо независимого разбора строки пути, что чинит оба места одним изменением модели состояния.
- **Отображение корня облачного ресурса без утечки пути** - для облачного ресурса, ещё не переведённого в режим навигации по под-папкам, информационная строка не пытается показать синтетический путь ресурса (у него нет осмысленного «родительского пути» для отображения) - показывается только имя ресурса, как и для остальных полей строки.
- **Не создающий регрессию для локальных путей** - для локальных/сетевых ресурсов список реальных имён формируется тем же способом (из объекта папки при клике), так что видимый результат не отличается от текущего поведения, только перестаёт зависеть от совпадения имени папки со последним сегментом пути.

### 5.2 Потоки данных и событий

Пользователь кликает по под-папке -> менеджер навигации получает объект папки (с реальным именем) -> добавляет текущее отображаемое имя в стек, устанавливает новое отображаемое имя из объекта папки -> обновляет путь и загружает содержимое новой папки, как раньше. Верхняя информационная строка и хлебные крошки при каждой перерисовке читают стек имён + текущее имя напрямую из состояния экрана. Переход назад/вверх снимает верхний элемент стека имён синхронно со стеком путей.

### 5.3 Точки расширяемости

Любая новая точка навигации, добавляющая элемент в стек путей, обязана параллельно добавлять соответствующее отображаемое имя в стек имён - иначе для этой точки регрессирует то же расхождение, которое чинит эта спека.

## 9. Архитектурные решения (ADR)

**ADR-1: Параллельный стек имён вместо провайдер-специфичных условий**

- **Решение:** хранить реальные отображаемые имена посещённых папок в состоянии экрана параллельно со стеком путей, а не добавлять условную ветку "если облачный ресурс - разобрать по-другому".
- **Альтернативы:** (а) провайдер-специфичная ветка в каждом месте разбора пути - отклонено, плодит дублирование и не решает проблему в первопричине; (б) хранить в состоянии полный объект посещённой папки (`MediaFile`) вместо только имени - отклонено как избыточное для этой задачи, где нужно только отображаемое имя.
- **Почему:** имя папки уже доступно в момент клика для любого типа ресурса (локального и облачного) - сохранение его тогда же убирает необходимость угадывать имя из пути позже, независимо от формы пути у конкретного провайдера.
