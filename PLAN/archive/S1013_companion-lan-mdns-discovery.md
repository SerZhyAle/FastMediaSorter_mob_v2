# Стратегическая спецификация: S1013 - Обнаружение companion-сервера в локальной сети (mDNS)

**Ticket:** S1013
**Status:** Archived
**Priority:** 75
**Date:** 2026-07-12
**Tier:** 3 - Moderate (ad-hoc)
**Roadmap entry:** Ad-hoc - запрос 2026-07-12 («работает из коробки» на локальной сети).
**Tactical spec:** `PLAN/S1013_companion-lan-mdns-discovery/` (будет создан через `/spec-tech`)

---

## 1. Проблема

Companion-ресурс подключается, только если импортированный конфиг несёт достижимый адрес. Когда телефон и ПК в одной Wi-Fi (типовой случай «отсканировал QR с экрана»), но в конфиге LAN-адрес отсутствует, устарел или ПК сменил адрес в сети, ресурс не подключается - хотя сервер рядом, в той же сети. Компаньон уже анонсирует себя в локальной сети (сервис `_sftp-fms._tcp`), но приложение это объявление не слушает, поэтому не может само найти рабочий локальный адрес и завязано на то, что именно оказалось зашито в QR.

---

## 2. Цели

1. Когда телефон в одной локальной сети с ПК, приложение само находит companion-сервер и подключается по его актуальному локальному адресу - без действий пользователя.
2. Это работает независимо от того, какой адрес нёс импортированный конфиг (даже если LAN-адрес отсутствует, устарел или ПК сменил IP в сети).
3. Обнаруженный локальный адрес привязывается именно к нужному ресурсу (а не к случайному серверу) по отпечатку host-key.
4. Обнаружение не тратит батарею в фоне - активно только когда уместно.

**Non-goals:**

- Не обнаруживать серверы за пределами локальной сети - mDNS работает только в пределах одного сегмента.
- Не менять формат конфига `.fmscfg`.
- Не заменять S1006: обнаруженный адрес - ещё один кандидат для того же механизма выбора достижимого адреса.
- Не вводить ручной UI выбора найденных серверов в этой итерации (автоматическое использование по совпадению отпечатка).

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. «Из коробки»: отсканировал/получил файл - раз - и видишь рабочий ресурс, если ПК в той же сети.
2. Самоисцеление: смена адреса ПК в сети не должна ломать уже добавленный ресурс.

### 3.2 Жёсткие ограничения

- **Flavor:** общий `src/main` сетевой слой; затрагивает варианты сборки, где доступен SFTP. Флейвор-специфики нет.
- **API level:** обнаружение сервисов доступно на всех поддерживаемых уровнях; на новых требуется корректная работа с multicast и разрешением локальной сети - учесть minSdk (23 legacy / 26 остальные).
- **Wear OS:** не затрагивается.
- **Производительность:** обнаружение живёт по жизненному циклу (активно при работе с сетевым ресурсом / на переднем плане), с корректным освобождением multicast-lock; не крутится постоянно в фоне.
- **Совместимость данных:** обнаруженный адрес эфемерный, в хранилище ресурса не пишется; форма хранения не меняется.
- **Локализация:** новых пользовательских строк не предполагается; при появлении - EN/RU/UK.
- **Доступность:** UI-изменений нет.

### 3.3 Owner inputs (Approval gate)

- **API level constraints:** обнаружение сервисов через системный резолвер; требуется удержание multicast-lock на время обнаружения и разрешение доступа к локальной сети; совместимо с legacy minSdk 23. Ветки, специфичные для версии ОС, изолируются в одном месте.
- **Performance budget:** обнаружение стартует по входу в сетевой ресурс/передний план и останавливается при уходе; никакого постоянного фонового сканирования; multicast-lock освобождается симметрично.
- **Validation level:** модульные тесты на разбор объявления сервиса и сопоставление по отпечатку; on-device проверка «QR без/с устаревшим LAN-адресом на той же Wi-Fi -> ресурс всё равно подключается по обнаруженному адресу».
- **Owner sign-off:** 2026-07-12 - владелец сформулировал требование «из коробки» и поручил реализацию.
- **Related tickets:** S1006 (резолвер потребляет обнаруженный адрес как кандидат), S0046 (отпечаток host-key для сопоставления), S0421/S0988 (companion-доставка и импорт).

---

## 4. Контекст текущей архитектуры

В приложении нет обнаружения хостов в локальной сети (ни системного service-discovery, ни mDNS). Сетевой ресурс жёстко берёт адрес из своего пути и списка кандидатов (S1006). Компаньон со своей стороны публикует сервис в локальной сети с отпечатком своего ключа, но эта информация до приложения не доходит. Значит, «поймать» сервер, который физически рядом, но записан в ресурсе под другим/устаревшим адресом, сейчас нечем.

---

## 5. Предлагаемый подход

Ввести слушателя объявлений локальной сети, который находит companion-сервис, извлекает его текущий адрес и отпечаток ключа, и отдаёт этот адрес в существующий механизм выбора достижимой конечной точки (S1006) как кандидата с наивысшим приоритетом (локальный - предпочтительный). Привязка «объявление -> ресурс» идёт по отпечатку host-key, который ресурс уже хранит.

### 5.1 Основные столпы / модули

- **Слушатель локальной сети.** Новая ответственность - подписка на объявления companion-сервиса в текущей сети, извлечение адреса и метаданных (отпечаток, имя), поддержание карты «отпечаток -> актуальный локальный адрес» в памяти.
- **Сопоставление по отпечатку.** Обнаруженный сервис привязывается к ресурсу по совпадению отпечатка host-key; случайные/чужие сервисы игнорируются.
- **Питание резолвера.** Механизм выбора адреса (S1006) при разрешении companion-ресурса дополнительно рассматривает обнаруженный локальный адрес как кандидата и предпочитает его как локальный.
- **Управление жизненным циклом.** Обнаружение включается/выключается по уместному жизненному циклу (работа с сетевым ресурсом / передний план), с корректным удержанием и освобождением ресурсов приёма multicast.

### 5.2 Потоки данных и событий

- Старт обнаружения -> объявления companion-сервиса приходят -> адрес+отпечаток кладутся в карту.
- Подключение к companion-ресурсу -> резолвер спрашивает карту по отпечатку ресурса -> при наличии обнаруженного локального адреса он становится предпочтительным кандидатом.
- Смена/потеря сети -> карта обнаружения сбрасывается и наполняется заново (согласовано с инвалидацией выбора адреса в S1006).

### 5.3 Точки расширяемости

- Обнаруженный адрес - лишь ещё один источник кандидатов; в будущем сюда же встанут ручной выбор найденного сервера или иные протоколы анонса.
- Сопоставление по отпечатку оставляет возможность добавить сопоставление по иному стабильному идентификатору сервиса.

## 6. Открытые вопросы / Research items

1. **Требования multicast/разрешений по версиям ОС**
   - **Вопрос:** какие разрешения и удержания (multicast-lock, доступ к локальной сети) нужны для надёжного приёма объявлений на поддерживаемых уровнях API, включая legacy minSdk 23.
   - **Нужно выяснить:** минимальный набор манифест-разрешений и рантайм-удержаний; поведение на новых версиях (ограничения на доступ к локальной сети).
   - **Статус:** Open

2. **Метаданные объявления от компаньона**
   - **Вопрос:** какие именно поля несёт TXT-запись companion-сервиса (отпечаток, имя, версия) и в каком виде, чтобы сопоставление было надёжным.
   - **Нужно выяснить:** согласовать контракт TXT с companion-стороной (`fp=<SHA256>` и т.п.).
   - **Статус:** Open

3. **Гранулярность жизненного цикла обнаружения**
   - **Вопрос:** на каком уровне включать обнаружение (весь передний план vs только экран сетевого ресурса) ради баланса «нашлось вовремя» против расхода батареи.
   - **Нужно выяснить:** уместная точка старта/останова в существующем жизненном цикле сетевого доступа.
   - **Статус:** Open

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Роутер/сеть блокирует mDNS/multicast | Средняя | Обнаружение не срабатывает | Деградация к адресам из конфига (S1006); обнаружение - усиление, не единственный путь |
| Расход батареи от постоянного обнаружения | Средняя | Жалобы на батарею | Жёсткая привязка к жизненному циклу; симметричное освобождение multicast-lock |
| Ложное сопоставление с чужим сервисом | Низкая | Подключение не к тому серверу | Привязка строго по отпечатку host-key |
| Различия поведения по версиям ОС (доступ к локальной сети) | Средняя | Не работает на части устройств | Изоляция версионных веток; честная деградация к конфигу |

## 9. Архитектурные решения (ADR)

**ADR-1: Обнаружение как источник кандидатов, а не отдельный путь подключения**

- **Решение:** обнаруженный локальный адрес отдаётся в существующий механизм выбора достижимого адреса (S1006).
- **Альтернативы:** отдельный путь подключения только для обнаруженных серверов.
- **Почему:** переиспользование S1006 (гонка/предпочтение локального/кэш) без дублирования логики подключения.

**ADR-2: Привязка по отпечатку host-key**

- **Решение:** объявление привязывается к ресурсу по совпадению отпечатка.
- **Альтернативы:** по адресу/имени.
- **Почему:** отпечаток стабилен при смене адреса и однозначно идентифицирует конкретный сервер; переиспользует пиннинг S0046.

## 10. Связи с другими спеками

- S1006 (multi-path SFTP endpoint fallback) - потребляет обнаруженный адрес как кандидата; без него обнаружение некуда подавать.
- S0046 (SFTP host-key pinning) - отпечаток для сопоставления объявления с ресурсом.
- S0421 / S0988 - companion-доставка и импорт; companion-сторона обязана держать mDNS-анонс с отпечатком в TXT (см. `temp/S1013/companion_out_of_box_prompt.md`).

---

## 11. Критерии готовности (strategic-level)

1. На той же Wi-Fi companion-ресурс подключается, даже если импортированный конфиг не нёс LAN-адрес или нёс устаревший.
2. Смена локального адреса ПК не ломает уже добавленный ресурс - следующее подключение находит его заново.
3. Обнаруженный адрес привязывается к ресурсу по отпечатку host-key; чужие серверы не подхватываются.
4. Обнаружение активно только по уместному жизненному циклу; ресурсы приёма multicast освобождаются симметрично.
5. Когда сеть блокирует обнаружение, поведение честно деградирует к адресам из конфига (S1006) без зависаний.
