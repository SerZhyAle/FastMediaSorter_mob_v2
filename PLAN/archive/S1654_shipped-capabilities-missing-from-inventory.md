## 0. Захваченный материал (verbatim)

Обнаружено 2026-08-14 при работе над S1243 (VR-документация не описывает внутришлемный браузер).
К самому S1243 отношения не имеет - запарковано по CLAUDE.md 3.1.

Проверка инвентаря по шести тикетам линейки внутришлемного immersive-браузера:

```
S0963 -> 0 record(s)
S1116 -> 0 record(s)
S1132 -> 0 record(s)
S1222 -> 0 record(s)
S0962 -> 0 record(s)
S0964 -> 0 record(s)
```

Ни одной записи в `docs/ALL_FEATURES.jsonl`. При этом S0963 закрыт как Verified по итогам проверки
владельцем на Quest 3 (Last Audit от 2026-07-19: браузер открывается, сетка и навигация лучом,
выбор ячейки, вход в папки, запуск в immersive - работают), а S1116, S1132, S1222 и S0962/S0964
с тех пор Archived. Возможность выпущена и живёт в продукте, но в инвентаре её нет.

## 1. Проблема

`docs/ALL_FEATURES.jsonl` объявлен источником истины по выпущенным возможностям (CLAUDE.md §11,
«Specs record their delivered capability here»). Если закрытый тикет не записал свою возможность,
она невидима для всего, что строится поверх инвентаря.

Практическое следствие уже наступило дважды:

- S1395 сверял руководства именно с дельтой `ALL_FEATURES` и поэтому в принципе не мог обнаружить
  пробел по VR-браузеру - его нет ни в инвентаре, ни в руководствах.
- S1653 проектирует механический гейт покрытия руководств поверх той же дельты. С этой слепой зоной
  гейт будет уверенно докладывать «покрытие полное», пока непокрытая возможность просто отсутствует
  в исходном списке. Гейт, который молчит по несуществующей записи, хуже ручной сверки.

Масштаб неизвестен: шесть тикетов проверены точечно, сколько ещё закрытых тикетов не записали свою
возможность - не считалось.

## 2. Цель

Узнать, сколько закрытых тикетов не записали свою возможность в инвентарь, и закрыть этот пробел -
хотя бы для линейки immersive-браузера, которая послужила поводом.

## 3. Ограничения и рамки

- Не всякий закрытый тикет обязан иметь запись: багфиксы, внутренние рефакторинги, инструментальные
  и документационные тикеты возможностей не добавляют. Признак «должен был записать» нужно
  формулировать, а не считать, что запись обязана быть у каждого.
- Записи заводятся только через `scripts/all_features/add.ps1`; флаворы берутся из фактического
  гейта, а не у соседней записи (S1072).
- Для VR-линейки флаворы - `["vr","noLegal"]` по образцу соседних записей `vr-openxr.*`, но это
  предположение и его надо проверить по `docs/FLAVOR_MATRIX.md` и по тому, где реально лежит код.

## 6. Открытые вопросы / Research items

1. Какой признак отличает закрытый тикет, обязанный иметь запись в инвентаре, от того, который не
   обязан? Статус: **Resolved** - §8 собственной спеки тикета.

   Признак не надо изобретать: он уже есть в шаблоне спеки. Раздел «§8. Влияние на пользователя»
   существует ровно для того, чтобы автор сказал, меняется ли что-то видимое, и по умолчанию содержит
   «Без изменений в docs/FEATURES». Тикет обязан иметь запись в инвентаре тогда и только тогда, когда
   его §8 говорит иное. Признак хорош тем, что это утверждение автора, а не догадка постфактум по
   названию или тиру: `bugfix-` в имени ничего не решает - починка видимого поведения тоже меняет
   инвентарь, только операцией `FIX`, а не `ADD`.

   Компактные спеки багфиксов (форма «Проблема / Корневая причина / Исправление / Проверка») раздела
   §8 не имеют вовсе и признаку не подпадают - их вклад в инвентарь решается при закрытии.

2. Достаточно ли разовой засыпки, или нужен гейт на переходе в `Verified`, требующий записи для
   тикета с пользовательски видимой возможностью? Статус: **Resolved** - разовой засыпки недостаточно,
   и массовая опасна; нужен гейт, но именно советующий.

   Измерение (см. §11) показало 275 закрытых тикетов, чей §8 заявляет видимое изменение, без единой
   записи. Засыпать их скопом - ровно тот риск, который называет §7: описания возможностей, которых
   никто не проверял, и флаворы, взятые у соседа. Поэтому здесь засыпана только линейка
   immersive-браузера, ради которой тикет и заведён, а остальное остаётся измеренным долгом.

   Гейт нужен, потому что правило без гейта соблюдается в 1..8 % случаев - у репозитория есть своё
   измерение на этот счёт. Но он обязан быть **советующим**: у багфиксов, инструментальных и
   документационных тикетов записи законно нет, а жёсткий отказ на переходе сделал бы закрытие любого
   такого тикета невозможным.

   Его естественное место - `Assert-ClosingGates` в `scripts/spec_catalog/_lib.ps1`: единственная
   точка, которую проходят оба пути смены статуса (`update.ps1` и `close.ps1`), и там уже стоят два
   закрывающих гейта. Мешает ровно одно: эта функция умеет только валить транзакцию - советующего
   режима у неё нет, и добавление такого режима меняет плумбинг, через который прямо сейчас
   закрываются тикеты параллельных сессий. Это отдельная работа со своей ценой, а не деталь этого
   тикета, поэтому вынесена в `S1665`.

## 7. Риски

- Массовая засыпка задним числом легко порождает записи с неверными флаворами и придуманными
  описаниями возможностей, которых никто не проверял. Лучше меньше записей, но проверенных по коду.

## Last Audit

**Дата:** 2026-08-14
**Вердикт:** Verified

### Критерий 1 - записи заведены, флаворы проверены по коду

Заведены три записи через `scripts/all_features/add.ps1`, каждая опирается на существующий класс, а
не на пересказ тикета:

- `vr-openxr.in-headset-immersive-browser` - сетка ячеек в immersive-сцене
  (`ImmersiveBrowseActivity`, `ImmersiveBrowseGridRenderer`).
- `vr-openxr.ray-navigation-in-immersive-browser` - выбор ячейки и вход в папку лучом
  (`ImmersiveBrowseInteractionDispatcher`).
- `vr-openxr.playback-launch-from-immersive-browser` - запуск воспроизведения прямо из сетки
  (`ImmersiveBrowsePlaybackController`).

`scripts/all_features/validate.ps1 -Gate` - без замечаний; `grep` подтверждает три новых `id`
рядом с существующими `vr-openxr.*`.

**Флаворы `vr,noLegal` - проверены, а не унаследованы у соседа (§3, S1072).** Предположение §3 верно,
но не по той причине, по которой его записали:

- код лежит в `app_v2/src/vr/java/com/sza/fastmediasorter/ui/xr/browse/**` и не завёрнут ни в один
  `BuildConfig`-гейт - `grep BuildConfig.SUPPORT_VR_PLAYER` по `src/vr` даёт единственное попадание,
  и оно в `MediaCapabilitiesModule`, а не в браузере;
- сам `SUPPORT_VR_PLAYER` по `docs/FLAVOR_MATRIX.md` истинен **только в `noLegal`** - в `vr` он
  `false`, так что взять флаворы «по флагу с похожим именем» здесь означало бы потерять флавор `vr`;
- решает включение source set: `src/vr/java` компилируется в `vr` (по умолчанию) и в `noLegal`
  (явным `kotlin.directories.add`). Отсюда `vr,noLegal`.

### Критерий 2 - масштаб посчитан

Прогон по объединённому каталогу (`PLAN/spec-catalog.jsonl` + `PLAN/spec-catalog-archive.jsonl`,
последняя запись на идентификатор) против поля `spec` в инвентаре:

- записей в каталоге: **1643**;
- закрытых (`Verified` / `Implemented` / `Archived`): **1549**;
- из них имеют хотя бы одну запись в инвентаре: **380**;
- не имеют ни одной: **1169**;
- из этих 1169 подпадают под признак §6.1 (в §8 спеки заявлено видимое изменение): **275**.

То есть инвентарь описывает примерно четверть закрытых тикетов, и каждый пятый закрытый тикет
заявлял видимое изменение, но записи не оставил. Это и есть слепая зона, из-за которой S1395 не мог
найти пробел по VR-браузеру, а гейт S1653 молчал бы по несуществующей записи.

**Долг не засыпан и засыпан не будет одним заходом** - §7 называет это риском прямо. Продолжение -
`S1665`: советующий режим в закрывающем гейте плюс решение по историческим 275.
