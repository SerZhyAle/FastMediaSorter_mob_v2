**Захвачено:** 2026-06-22

**Текст:**

Chrome Cast не работает для живого видеопотока. Движок Cast (`CastMediaManager.resolveAndSend()`)
классифицирует http(s)-адрес как локальный файл: `File(path).exists()` возвращает false ->
тихий error-toast. Для сетевого/облачного файла Cast сначала скачивает копию во временный кэш и
раздаёт её через локальный прокси-сервер - для бесконечного живого потока это невозможно.

В результате: кнопка Cast в плеере для трансляции показывается (по запросу владельца в S0631
остаётся), но при нажатии поток на приёмник не уходит.

Нужно: для трансляции отдавать приёмнику адрес потока напрямую (`MediaItem.fromUri(url)` как live),
минуя скачивание во временный файл и локальный прокси.

**Источник:** исследование S0631, `PLAN/S0631_video-stream-player-view/research/01__player-stream-mode-architecture.md`
(Out-of-scope findings #1).

**Вложения:**

Вложений нет.

## 1. Проблема

Кнопка Chrome Cast в плеере для живой видеотрансляции показывается (решение S0631 - кнопку
оставили видимой), но при нажатии поток на приёмник не уходит. Движок каста умеет только два
вида источников: локальный файл раздаётся напрямую, сетевой/облачный сначала скачивается во
временный кэш и раздаётся локальным прокси-сервером. Адрес трансляции по http(s) не попадает ни
в одну сетевую ветку и ошибочно трактуется как локальный путь; проверка существования файла
проваливается, и пользователь видит только error-toast. Бесконечный живой поток в принципе
нельзя скачать в файл и раздать через прокси.

---

## 2. Цели

1. Для живой видеотрансляции каст отдаёт адрес потока приёмнику напрямую, минуя скачивание во временный файл и локальный прокси.
2. Поток на приёмнике стартует и воспроизводится как live для протоколов, которые приёмник принимает (HLS, DASH, прогрессивный http).
3. Для протокола, который приёмник не принимает (RTSP), пользователь получает понятное сообщение о невозможности вместо молчаливого сбоя.

**Non-goals:**

- Кастинг локальных и сетевых/облачных не-стримовых файлов - текущий путь через прокси не меняется.
- Кастинг аудио/радио-трансляций - объём итерации только живой видеопоток.
- Кастомный Cast-receiver, DRM или транскодинг протоколов, не принимаемых Default Media Receiver.
- Изменение видимости/наличия кнопки Cast - определено в S0631.

## 4. Контекст текущей архитектуры

Cast-вывод из плеера ведёт единый менеджер каста. Источник он различает по схеме пути: локальный
файл раздаётся напрямую, сетевой/облачный (smb/sftp/ftp/cloud) скачивается во временный кэш и
раздаётся локальным прокси-сервером, после чего приёмнику отдаётся URL прокси. Адрес по http(s)
не попадает ни в одну из сетевых веток и ошибочно трактуется как локальный путь. Живая трансляция
запускается в плеер с синтетическим идентификатором ресурса STREAM, а её путь - это http(s)- или
rtsp-адрес. Признак живого видеопотока уже вычисляется в состоянии плеера (S0631), а классификация
схемы адреса трансляции уже существует в слое воспроизведения.

---

## 5. Предлагаемый подход

Добавить в менеджер каста третью ветку обработки источника - прямую передачу адреса. Когда
источник распознан как живая трансляция (по той же классификации схемы адреса, что использует
плеер), его URL передаётся приёмнику напрямую как live: без скачивания во временный файл и без
локального прокси. Тип потока для приёмника помечается как «живой», а не «буферизованный».
Поддержку протокола определяет приёмник: для принимаемых им протоколов (HLS, DASH, прогрессивный
http) каст стартует; для непринимаемого rtsp пользователь получает сообщение о невозможности, а
попытка каста не предпринимается. Признак трансляции определяется единообразно с остальным
плеером, без дублирования логики классификации.

## 6. Открытые вопросы / Research items

1. Все ли протоколы трансляции (HLS/DASH/RTSP/прогрессивный http) принимаются приёмником Cast при прямой передаче URL? **Resolved.** Default Media Receiver принимает HLS, MPEG-DASH, SmoothStreaming и прогрессивный http; RTSP и RTMP не поддерживаются. http(s)-трансляции кастятся напрямую, rtsp - сообщение о невозможности. **Артефакт:** `PLAN/S0632_cast-live-stream-direct-url/research/01__cast-receiver-protocol-support.md`.

## 9. Архитектурные решения (ADR)

- **ADR-1 - прямой URL вместо прокси для трансляций.** Подход «скачать-раздать через прокси» неприменим к бесконечному живому потоку. Передача адреса приёмнику напрямую как live - единственный рабочий путь; ветка для трансляции отделяется от существующего пути локальных/сетевых файлов.
- **ADR-2 - опора на Default Media Receiver без кастомного receiver.** RTSP не покрывается приёмником, но кастомный receiver или транскодинг непропорционально дороги для текущей задачи. RTSP-трансляции получают сообщение о невозможности.
