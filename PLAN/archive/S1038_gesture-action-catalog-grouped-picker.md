## 0. Захваченный материал (inbox)

**Захвачено:** 2026-07-13

**Текст владельца (verbatim):**

> в варианты жестов добавить "включить/выключить фонарик", "максимальная/нормальная яркость экрана", создать заметку "Google keep", "Открыть диалог Gemini", запустить придумай ещё что-то?
>
> похоже список доступных жестов будет довольно длинный. Вероятно нам нужна тут переработка диалога выбора жеста (ну то есть поведения на жест) чтобы человек выбирал из групп вариантов поведения и мог прочитать объяснение что это значит. То есть не типовой выбор из списка, а выбор из списка но с группами.

**Решения владельца (2026-07-13, по итогам ресёрча и конкурентов):**

Включить действия (все выбраны владельцем):
- Управление устройством (все флейворы): фонарик вкл/выкл; яркость экрана макс/норма; медиа плей/пауза; следующий/предыдущий трек; громкость +/− и без звука.
- Запуск/интенты (все флейворы): создать заметку в Google Keep; открыть Gemini; открыть системного ассистента; открыть URL/закладку; поставить будильник; поставить таймер; новое событие календаря.
- Через accessibility (только `noLegal`): открыть шторку уведомлений; открыть быстрые настройки; заблокировать экран; разделённый экран; переключить на предыдущее приложение.

Плюс переработка пикера: **выбор действия из групп с пояснением к каждому варианту** (не плоский список).

---

## 1. Проблема

Каталог действий краевого жеста сейчас плоский список (~17 пунктов), выбираемый одним перечнем без группировки и без объяснения, что каждый пункт делает. Владелец хочет добавить около двадцати новых действий (фонарик, яркость, медиа, громкость, запуск ассистента/Keep/Gemini/URL, будильник/таймер/календарь, а также системные действия через accessibility). При таком объёме плоский список становится неюзабельным: пользователь не находит нужное и не понимает разницы между похожими пунктами. Нужен пикер с группами и пояснениями, а также сам расширенный набор действий с корректной диспетчеризацией, разрешениями и учётом того, что часть действий доступна только там, где есть accessibility-сервис.

---

## 2. Цели

1. Пикер выбора действия жеста показывает варианты, сгруппированные по смыслу (захват, камера, запуск, управление устройством, система, утилиты, отключено), с коротким пояснением к каждому варианту.
2. Каталог действий расширен новыми пунктами (см. §0 «Решения владельца»), каждый с понятной подписью, пояснением и корректной диспетчеризацией.
3. Действия, требующие разрешения (системная яркость), корректно запрашивают его, а без разрешения ведут себя предсказуемо (не срабатывают молча в пустоту).
4. Действия, реализуемые только через accessibility, доступны в пикере лишь там, где сервис есть (`noLegal`), и скрыты на остальных сборках.
5. Действие «открыть URL» хранит адрес отдельно для каждого из двенадцати слотов (аналогично выбору приложения) и открывает его при срабатывании.

**Non-goals:**

- Не меняются зоны/направления жестов и механика их срабатывания.
- Не переносится и не переделывается UI-хост настроек жестов - это область S1035 (пикер вызывается и из текущего UI, и из будущего диалога, одинаково).
- Не реализуется выбор приложения для `OPEN_APP` - это область S1036 (здесь только общий механизм пер-слотового payload, которым пользуются оба).

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Группы вариантов + пояснение к каждому - «выбор из списка, но с группами».
2. Максимально широкий набор полезных действий (по итогам ресёрча конкурентов - Edge Gestures, Edgest, Samsung Edge Panel, Moto Actions).

### 3.2 Жёсткие ограничения

- **Flavor:** действия управления устройством, медиа, громкости, запуска и интентов - `standard` (гейт `fms.screenCapture`) + `noLegal`. Системные действия через accessibility (шторка, быстрые настройки, блокировка, разделённый экран, предыдущее приложение) - **только `noLegal`** (accessibility-сервис существует лишь там); на `standard` они не показываются в пикере. Абстракция флейвора - существующий шов, новая не вводится; работа по `dev/FLAVOR_DEVELOPMENT_RULES.md`.
- **API level:** учесть видимость пакетов (Android 11+) для интентов запуска; системная яркость - `WRITE_SETTINGS`; блокировка экрана - глобальное действие accessibility (API 28+); разделённый экран - глобальное действие (API 24+, поведение сузилось в новых версиях - проверить). Действия, недоступные на текущем API, прячутся или деградируют явно.
- **Wear OS:** не затрагивается.
- **Производительность:** списки/интенты строятся по требованию; пикер не тяжелеет от группировки.
- **Совместимость данных:** для «открыть URL» - пер-слотовый строковый payload (двенадцать значений) в текущем хранилище настроек; общий механизм с выбором приложения (S1036), без Room-миграции.
- **Локализация:** EN/RU/UK обязательно для всех новых строк - подписи действий, пояснения, заголовки групп.
- **Доступность:** строки пикера и заголовки групп фокусируемы (клавиатура/D-pad), пояснение читается ассистивными технологиями; действия с разрешениями объясняют, что требуется.

### 3.3 Owner inputs (Approval gate)

- **Flavor scope:** `standard` (`fms.screenCapture`) + `noLegal` для большинства; accessibility-подмножество - только `noLegal`. Прочие сборки - каталог жестов недоступен целиком.
- **API level constraints:** `WRITE_SETTINGS` (яркость); accessibility global actions - lock (API 28+), split-screen (API 24+, суженное поведение в новых версиях); package visibility для интентов. Недоступное на API - скрыто/деградирует явно.
- **Data compatibility:** пер-слотовый URL-payload (12 значений) в текущем хранилище; общий механизм с S1036; без Room-миграции.
- **UI placement contract:** пикер выбора действия - группированный список с заголовками секций и пояснением к каждому варианту; вызывается из текущего UI и из диалога S1035 одинаково.
- **Accessibility:** строки/заголовки фокусируемы, пояснение доступно ассистивным технологиям.
- **Localization:** EN/RU/UK для новых строк - обязательно.
- **Validation level:** сборка `standard debug` + `noLegal` debug; on-device проверка каждого класса действий (устройство/медиа/интенты/accessibility), гейтинга по флейвору и запроса разрешения на яркость.
- **Owner sign-off:** 2026-07-13 (состав действий и группированный пикер подтверждены владельцем).
- **Related tickets:** S1035 (диалог-хост, пикер вызывается из него), S1036 (пер-слотовый payload - общий механизм с «открыть URL»), S0847 (зоны/направления), S0663 (механика запуска приложений/интентов).

## 4. Контекст текущей архитектуры

Действия жеста заданы перечислением, подписи и доступность вариантов пикера формируются менеджером-пикером (уже фильтрует часть вариантов по возможностям - например скрывает «запись экрана», когда движок захвата отсутствует). Диспетчер применяет действие до/после захвата экрана. Accessibility-сервис, через который выполняются глобальные системные действия, существует только в сборке `noLegal`. Пер-слотового строкового payload (для URL или пакета приложения) в хранилище настроек пока нет - его вводит либо этот тикет, либо S1036 как общий механизм. Пикер сегодня плоский - группировки и пояснений в нём нет.

---

## 5. Предлагаемый подход

Сначала переработать пикер выбора действия в группированный список с пояснениями, затем наполнить его новыми действиями, распределёнными по группам, с диспетчеризацией по классам механизма (устройство / медиа / интенты / accessibility) и корректным гейтингом по флейвору и API.

### 5.1 Основные столпы / модули

1. **Группированный пикер с пояснениями.** Пикер показывает варианты по секциям (заголовок группы + пояснение к каждому пункту). Каждому действию сопоставлены группа и пояснительный текст. Переиспользуется канонический механизм списка-выбора проекта, расширенный секциями/описаниями.
2. **Действия управления устройством (все флейворы).** Фонарик (переключение через системный доступ к вспышке, без камеры-превью), системная яркость макс/норма (с запросом `WRITE_SETTINGS`), громкость +/− и без звука, медиа плей/пауза и следующий/предыдущий трек (через системный медиа-канал).
3. **Действия запуска и интентов (все флейворы).** Открыть системного ассистента; открыть Gemini; создать заметку в Google Keep; открыть URL (пер-слотовый адрес); поставить будильник; поставить таймер; новое событие календаря. Учитывают видимость пакетов и отсутствие целевого приложения (безопасная деградация).
4. **Системные действия через accessibility (только `noLegal`).** Шторка уведомлений, быстрые настройки, блокировка экрана, разделённый экран, предыдущее приложение - через существующий accessibility-сервис; в пикере видны только там, где сервис доступен.
5. **Пер-слотовый payload (общий с S1036).** Строковое значение на каждый из двенадцати слотов (URL здесь, пакет приложения в S1036) в хранилище настроек - единый механизм, вводимый один раз и потребляемый обоими тикетами.

### 5.2 Потоки данных и событий

- Пользователь открывает пикер -> видит группы + пояснения -> выбирает действие -> запись в хранилище настроек (действие слота; при необходимости - payload URL).
- Выбор действия с разрешением (яркость) -> запрос `WRITE_SETTINGS` -> при отказе действие не активируется, состояние честно отражается.
- Жест сработал -> диспетчер по классу действия: устройство/медиа/громкость -> системные сервисы; интент -> запуск с деградацией при отсутствии цели; accessibility -> глобальное действие сервиса (`noLegal`).
- Пикер строит доступный набор вариантов по возможностям сборки/устройства (accessibility-подмножество только на `noLegal`; действия с недоступным API скрыты).

### 5.3 Точки расширяемости

- Метаданные действия (группа + пояснение + доступность) отделены от диспетчеризации - новое действие добавляется единообразно.
- Пер-слотовый payload не зависит от смысла значения (URL/пакет/при необходимости иное).
- Классовая диспетчеризация (устройство/медиа/интент/accessibility) открыта для добавления новых действий в существующий класс без переписывания пикера.

## 6. Открытые вопросы / Research items

1. **Гранулярность громкости и медиа.**
   - **Вопрос:** громкость - три отдельных пункта (выше/ниже/без звука) или один переключатель? Медиа - плей/пауза + следующий + предыдущий как три пункта?
   - **Рекомендация:** отдельные пункты (выше/ниже/без звука; плей-пауза/следующий/предыдущий) - предсказуемо на один жест = одно действие.
   - **Статус:** Open

2. **Точный интент «создать заметку Google Keep».**
   - **Вопрос:** прямой интент создания заметки Keep не гарантирован на всех версиях; fallback?
   - **Рекомендация:** пытаться интентом создания заметки, при отсутствии - запуск Keep, при отсутствии Keep - безопасный no-op с деградацией. Уточнить конкретный интент в `/spec-tech`.
   - **Статус:** Open

3. **«Открыть Gemini» против «открыть ассистента».**
   - **Вопрос:** Gemini - отдельный пункт (запуск приложения Gemini) при наличии общего «открыть ассистента» (`ACTION_ASSIST`)?
   - **Рекомендация:** оставить оба (владелец выбрал оба): «ассистент» - системный по умолчанию, «Gemini» - именно приложение Gemini с деградацией при отсутствии.
   - **Статус:** Open

4. **Ввод URL на слот - UI.**
   - **Вопрос:** как вводится адрес для «открыть URL» рядом со слотом - поле ввода/диалог; переиспользовать ли механику пер-слотового payload из S1036?
   - **Рекомендация:** единый пер-слотовый payload-механизм (§5.5); ввод URL - простое поле/диалог рядом со слотом, аналогично выбору приложения.
   - **Статус:** Open

Примечание: открытые вопросы уточняются в `/spec-tech` из кода/платформы, approval не блокируют.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Плоский пикер не масштабируется на ~35 действий | Высокая | Пользователь не находит нужное | Группы + пояснения (столп 1) - ядро тикета |
| Часть действий недоступна на API/флейворе | Средняя | «Мёртвые» пункты, молчаливые сбои | Гейтинг в пикере по возможностям; скрытие недоступного; явная деградация |
| Целевое приложение (Keep/Gemini) не установлено | Средняя | Жест ничего не делает | Деградация: fallback-запуск или безопасный no-op с понятным поведением |
| Отказ в `WRITE_SETTINGS` для яркости | Средняя | Яркость «не работает» | Запрос разрешения при выборе; без него действие неактивно, состояние честно отражается |
| accessibility-действия «утекают» на standard | Низкая | Нерабочие пункты на standard | Показывать accessibility-подмножество только при наличии сервиса (`noLegal`) |
| Рассинхрон payload-механизма с S1036 | Средняя | Двойная/несовместимая реализация хранения | Ввести общий пер-слотовый payload один раз (§5.5), согласовать с S1036 |

## 9. Архитектурные решения (ADR)

**ADR-1: Группированный пикер с пояснениями вместо плоского списка.**

- **Решение:** пикер выбора действия - секции по группам + пояснение к каждому варианту.
- **Альтернативы:** оставить плоский список; поиск по действиям.
- **Почему:** ~35 действий в плоском списке неюзабельны; группировка + пояснение решают находимость и понятность (запрос владельца).

**ADR-2: Классовая диспетчеризация (устройство/медиа/интент/accessibility).**

- **Решение:** диспетчер разводит действия по классам механизма; accessibility-класс - только `noLegal`.
- **Почему:** единообразное добавление действий и корректный гейтинг по флейвору/API без разрастания одной ветки.

**ADR-3: Единый пер-слотовый payload, общий с S1036.**

- **Решение:** одно строковое значение на слот (URL здесь, пакет приложения в S1036), вводится один раз.
- **Почему:** избежать двух несовместимых реализаций хранения выбранного параметра действия.

## 10. Связи с другими спеками

- **S1036** (gesture-launch-app-selection) - **общий механизм пер-слотового payload**: «открыть URL» (здесь) и «выбор приложения» (S1036) используют одно хранилище на слот. Рекомендация: общий payload-механизм ввести в рамках того тикета, что реализуется раньше (S1038 не заблокирован, S1036 ждёт S1035) - второй потребляет готовый механизм. Согласовать при `/spec-tech`.
- **S0847** (зоны/направления жестов) - слоты, к которым привязываются действия.
- **S0663** (панель быстрого запуска) - источник механики запуска приложений/интентов.

## 11. Критерии готовности (strategic-level)

1. Пикер выбора действия показывает варианты по группам с заголовками и пояснением к каждому пункту.
2. В каталоге присутствуют все выбранные владельцем новые действия (устройство/медиа/громкость/запуск/интенты/accessibility) с понятными подписями и пояснениями.
3. Каждое новое действие корректно срабатывает по жесту на соответствующей сборке; accessibility-действия доступны только на `noLegal`.
4. Действие «яркость» запрашивает `WRITE_SETTINGS`; без разрешения не активируется и честно отражает состояние.
5. Действие «открыть URL» хранит адрес на каждый из двенадцати слотов и открывает его; отсутствие цели деградирует безопасно.
6. Недоступные на текущем API/флейворе действия не показываются или деградируют явно (без молчаливых сбоев).
7. Новые строки локализованы в EN/RU/UK.
