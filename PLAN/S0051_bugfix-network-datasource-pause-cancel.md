## 1. Проблема

При воспроизведении файлов через SFTP нажатие кнопки «Пауза» в плеере не останавливает сетевые операции чтения — источник данных продолжает поглощать трафик в фоновом потоке. Только нажатие «Назад» (полное уничтожение плеера) прерывает поток. Это расходует сетевой канал, батарею и удерживает SFTP-соединение занятым, пока плеер формально стоит на паузе. Аналогичное поведение может присутствовать в других сетевых источниках (SMB, FTP, облако).

---

## 2. Цели

1. После паузы плеера (пользователь нажал «Пауза» или плеер перешёл в paused-состояние) сетевые чтения прекращаются в течение нескольких секунд.
2. При возобновлении воспроизведения (Resume) чтения корректно перезапускаются — без повторного открытия файла с нуля, если позиция не изменилась.
3. Соединения возвращаются в пул (а не удерживаются открытыми) во время паузы, если буферизация не требуется.
4. Поведение проверено и исправлено (или подтверждено как корректное) для всех сетевых источников: SFTP, SMB, FTP, облачное хранилище.

**Non-goals:**

- Изменение поведения ExoPlayer при буферизации локальных файлов.
- Реализация нового механизма кэширования сегментов для ускорения Resume.
- Поддержка фонового воспроизведения / PiP — отдельная область.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Если прерывание активного чтения технически невозможно без потери позиции — допустимо подождать завершения текущего буфера (не более ~2 с), а затем заблокировать следующий вызов `read`.
2. При возобновлении желательно использовать уже открытое соединение из пула, не создавать новое.

## 4. Контекст текущей архитектуры

ExoPlayer управляет буферизацией через внутренний `LoadControl` и фоновый поток загрузки (`Loader`). По умолчанию ExoPlayer продолжает заполнять буфер даже в paused-состоянии — это его штатное поведение. Сетевые источники данных реализованы как реализации интерфейса `DataSource` и вызываются из этого фонового потока. Жизненный цикл `DataSource` (открытие, чтение, закрытие) полностью контролируется ExoPlayer: метод закрытия вызывается только при `release()` плеера, который в текущей реализации происходит лишь в `onDestroy`.

Менеджер жизненного цикла плеера при `onPause` сохраняет позицию и приостанавливает рендеринг изображений, но не останавливает ExoPlayer и не сигнализирует источникам данных о смене состояния. Механизма «пауза буферизации» в существующей архитектуре нет ни у SFTP-, ни у SMB-, ни у FTP-источника.

## 5. Предлагаемый подход

### 5.1 Основные столпы / модули

**А. Сигнал отмены в источниках данных**
Каждый сетевой источник данных получает атомарный флаг отмены. Когда плеер переходит в paused-состояние (или завершает воспроизведение с ошибкой), флаг выставляется снаружи. При следующем вызове `read` источник проверяет флаг и возвращает признак конца потока, что заставляет `Loader` ExoPlayer'а завершить текущую загрузку.

**Б. Конфигурация LoadControl**
Рассмотреть настройку ExoPlayer так, чтобы он прекращал буферизацию при переходе в paused-состояние (параметры минимального/максимального буфера). Это снимет нагрузку без изменения кода источников.

**В. Аудит остальных источников**
Провести идентичную проверку для SMB-, FTP- и облачного источников: имеется ли там та же проблема? Если да — применить тот же паттерн отмены.

### 5.2 Потоки данных и событий

```
Пользователь нажимает «Пауза»
  → UI-слой → менеджер воспроизведения → ExoPlayer.pause()
  → [новое] флаг отмены выставлен в источнике данных
  → фоновый поток: read() видит флаг → возвращает END_OF_INPUT
  → Loader ExoPlayer'а завершает задачу
  → соединение возвращается в пул

Пользователь нажимает «Возобновить»
  → ExoPlayer.play()
  → [новое] флаг отмены сброшен
  → Loader открывает источник заново (seek к сохранённой позиции)
  → чтение продолжается
```

### 5.3 Точки расширяемости

- Флаг отмены должен быть применим к любому будущему сетевому источнику без изменения ExoPlayer-контракта.
- Механизм должен допускать паузу буферизации и при скрытии плеера в фон (Activity.onPause), не только при нажатии кнопки паузы.

## 6. Открытые вопросы / Research items

1. **Поведение ExoPlayer при сбросе флага и повторном open()**
   - **Вопрос:** Если источник данных вернул `END_OF_INPUT` досрочно — корректно ли ExoPlayer выполнит повторный seek и open() при Resume, или потребуется полный пересоздание источника?
   - **Варианты:** (a) Источник сигнализирует ошибкой → ExoPlayer перезапускает медиа; (b) EndOfInput → ExoPlayer считает файл конченным и переходит к следующему в плейлисте.
   - **Нужно выяснить:** Поведение `ProgressiveMediaPeriod` при досрочном `END_OF_INPUT` vs `IOException`.
   - **Статус:** Open

2. **LoadControl: прекращение буферизации при паузе**
   - **Вопрос:** Достаточно ли настройки `minBufferMs`/`maxBufferMs` = 0 при paused-состоянии, или нужна кастомная `LoadControl`-реализация?
   - **Варианты:** (a) DefaultLoadControl с нулевым буфером при паузе; (b) переопределение `shouldContinueLoading`; (c) флаг отмены в DataSource.
   - **Нужно выяснить:** Задокументированный способ остановки буферизации в Media3 1.2.1.
   - **Статус:** Open

3. **SMB, FTP, Cloud DataSource — аудит**
   - **Вопрос:** Присутствует ли та же проблема (продолжение чтения после паузы) в SMB-, FTP- и облачном источниках?
   - **Нужно выяснить:** Прочитать реализацию каждого источника; проверить наличие отмены или InputStream-прерывания.
   - **Статус:** Open

## 9. Архитектурные решения (ADR)

**ADR-1: Флаг отмены vs конфигурация LoadControl**

- **Решение:** Предпочтительно исследовать конфигурацию `LoadControl` первой — меньше кода, ExoPlayer управляет жизненным циклом. Флаг отмены — запасной вариант.
- **Альтернативы:** (a) LoadControl без буферизации при паузе; (b) атомарный флаг в DataSource; (c) release/recreate ExoPlayer при каждой паузе.
- **Почему:** Release/recreate при паузе слишком медленно и разрушает позицию воспроизведения. Флаг — хирургически точен, но требует изменений во всех источниках.

## 11. Критерии готовности (strategic-level)

1. Нажатие «Пауза» при воспроизведении SFTP-файла прекращает рост тэга `SftpDataSource` в логе в течение 3 секунд.
2. «Возобновить» после паузы продолжает воспроизведение с той же позиции без полной перезагрузки файла.
3. Проверено для SMB-, FTP- и облачных источников: либо проблема исправлена, либо задокументировано отсутствие проблемы.
4. Аккумулятор и сетевой трафик при паузе в течение 1 минуты сопоставимы с нулевой нагрузкой (нет фоновых READ в логе).
