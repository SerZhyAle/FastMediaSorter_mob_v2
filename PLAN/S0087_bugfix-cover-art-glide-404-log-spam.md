## 1. Проблема

При воспроизведении аудиофайла без встроенной обложки плеер выполняет поиск обложки онлайн. Если изображение для данного исполнителя/альбома не найдено на удалённом источнике (HTTP 404), Glide-запрос завершается неудачей, и в `RequestListener.onLoadFailed` фиксируется многоуровневая цепочка исключений на уровне WARNING: ~15 строк вложенных `GlideException`/`HttpException` со stacktrace. 404 от онлайн-источника обложек — штатный, ожидаемый исход (изображение просто не существует), а не ошибка. Нынешнее поведение генерирует диагностический шум в лог-файле при каждом воспроизведении трека без онлайн-обложки и потенциально засоряет pipeline аварийных отчётов.

**Контекст:** S0052 (`bugfix-sftp-datasource-log-spam`, Verified) и S0055 (`diagnostic-noise-cleanup`, Implemented) ранее устраняли аналогичный шум в других компонентах; данный источник ими не охвачен.

---

## 2. Цели

1. HTTP 404 от онлайн-источника обложек логируется одной строкой на уровне DEBUG: домен источника и код статуса — без цепочки исключений и stacktrace.
2. WARNING-запись `Glide load FAILED` со вложенными исключениями перестаёт появляться в логе при штатном сценарии «обложка онлайн не найдена».
3. Настоящие ошибки (сетевой сбой, таймаут, неожиданный код статуса) по-прежнему логируются на уровне WARNING с достаточным контекстом для диагностики.
4. Поведение UI не меняется: при неудаче отображается заглушка `CANVAS_WAVES` — как и прежде.

**Non-goals:**

- Изменение логики поиска обложки или fallback-стратегии.
- Изменение источника онлайн-обложек или политики кэширования Glide.
- Обработка других HTTP-кодов ошибок (кроме 404).

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. В `onLoadFailed` различать 404 (DEBUG, без стека) и иные ошибки (WARNING, с кратким сообщением).
2. Лог-строка для 404 содержит только домен источника и код статуса — без URL целиком (URL может содержать токены).

## 4. Контекст текущей архитектуры

Поиск обложки онлайн выполняется в компоненте UI-слоя, ответственном за загрузку и отображение обложки аудиотрека. Компонент формирует Glide-запрос с `RequestListener`, в котором метод `onLoadFailed` вызывается при любом сбое Glide. Текущая реализация передаёт объект `GlideException` напрямую в `Timber.w(e, ...)`, что приводит к выводу полной цепочки причин исключения. Glide не разграничивает «контент не найден» (404) и «сетевая ошибка» на уровне сигнатуры коллбэка — различие доступно только через анализ причины `GlideException`.

---

## 5. Предлагаемый подход

В методе `onLoadFailed` компонента загрузки обложки проанализировать причину переданного исключения: если среди корневых причин обнаружен HTTP 404, логировать только домен и статус на уровне DEBUG без передачи объекта исключения в Timber. Во всех остальных случаях сохранить текущее WARNING-поведение, заменив передачу полного исключения на краткое текстовое описание ошибки.

### 5.1 Основные столпы / модули

**A. Классификация ошибки в `onLoadFailed`**
Извлечь корневые причины `GlideException` и проверить наличие `HttpException` с кодом 404. Результат — ветка: `is404` → DEBUG; иначе → WARNING.

**B. Форматирование лог-строки для 404**
Одна строка: `"[callId]: cover art not found (404) — <domain>"`. Домен извлекается из URL-источника через `URI.getHost()`. Объект исключения не передаётся в Timber.

### 5.2 Потоки данных и событий

```
Glide.onLoadFailed(e: GlideException)
    ↓
Извлечь root causes из GlideException
    Есть HttpException(404)?
        Да → Timber.d("cover art not found (404) — <domain>")
        Нет → Timber.w("cover art load failed: <reason>")
    ↓
Показать заглушку CANVAS_WAVES (без изменений)
```

### 5.3 Точки расширяемости

- Логика классификации ошибки может быть вынесена в вспомогательный метод и повторно использована для других Glide-запросов в аудиоплеере.

## 9. Архитектурные решения (ADR)

**ADR-1: Классификация 404 внутри `onLoadFailed` vs. подавление всех ошибок Glide**

- **Решение:** различать 404 (DEBUG) и прочие ошибки (WARNING) на основе анализа `GlideException.rootCauses`.
- **Альтернативы:** понизить уровень всех Glide-ошибок до DEBUG; отключить `RequestListener` и использовать глобальный Glide `LoggingRequestListener`.
- **Почему:** избирательная классификация сохраняет диагностическую ценность настоящих ошибок и устраняет только шум от ожидаемых исходов.

## 11. Критерии готовности (strategic-level)

1. При воспроизведении трека без онлайн-обложки (HTTP 404 от источника) лог содержит не более одной строки уровня DEBUG на попытку загрузки — без stacktrace и вложенных исключений.
2. При сетевом сбое (не 404) лог по-прежнему содержит WARNING с кратким описанием причины.
3. UI отображает заглушку при обоих исходах — как и прежде.
