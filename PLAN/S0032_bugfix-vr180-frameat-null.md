## 1. Проблема

При попытке извлечь превью-кадр (poster / thumbnail) для VR180-файла с очень высоким разрешением (`18VR_The_Best_is_Yet_to_Come_7K_180_180x180_3dh.mp4`, 7K, 21 ГБ) метод `getFrameAtTime` возвращает `null`. Это происходит уже после того, как плеер запустил воспроизведение файла в `PlayerActivity`.

Лог (line 3301):

```text
02:26:03  W/App: VideoPlayerManager: getFrameAtTime returned null for
          /storage/emulated/0/Movies/18VR_The_Best_is_Yet_to_Come_7K_180_180x180_3dh.mp4
```

Эффект: превью-кадр в паузированном состоянии плеера, в диалоге управления или в любом другом месте, требующем статичного изображения текущего момента видео, остаётся пустым (либо показывает заглушку, либо предыдущий кадр, либо ничего). Пользователю это ощущается как «замороженный чёрный экран при паузе».

Вероятные причины:

1. **Конкуренция декодеров.** `VideoPlayerManager: getFrameAtTime` вызывает `MediaMetadataRetriever.getFrameAtTime`, которому для декодирования нужен отдельный декодер. Если `ExoPlayer` уже занял аппаратный декодер 7K-файла (единственный доступный на Quest 3), `MediaMetadataRetriever` не может получить ещё один экземпляр и возвращает `null`.
2. **OOM / native heap.** В логе на протяжении всей сессии фиксируются предупреждения `ImagePreloadHelper: Preload skipped — native heap low (13–18MB free)`. Для декодирования одного кадра 7K (7168×3584 = ~78 Мпкс) требуется значительный буфер в native heap. При нехватке `getFrameAtTime` аварийно возвращает `null`.
3. **Unsupported codec path.** VR180 SBS fisheye может использовать кодек или контейнер, не поддерживаемый `MediaMetadataRetriever` на данном API уровне/устройстве.

## 2. Цели

1. При невозможности получить кадр через `getFrameAtTime` приложение не падает и не логирует `W/` без последствий — ветка `null` обрабатывается с явным fallback: показать заглушку (thumbnail из кэша, постер или пустой серый фрейм с иконкой «нет превью»).
2. В логе появляется расширенный маркер причины: `getFrameAtTime returned null reason=decoder-busy|oom|unsupported|unknown` — достаточно различимый для диагностики без повторного запуска.
3. Вызов `getFrameAtTime` **не происходит** если `ExoPlayer` в данный момент держит аппаратный декодер для того же файла — в этом случае сразу применяется fallback, без дополнительного давления на декодер и native heap.
4. Для очень больших файлов (> N ГБ, конкретный порог — задача тактической спеки) и на устройствах с `native heap free < M MB` (M — задача тактической спеки) превентивно не делается попытка `getFrameAtTime`; используется кэшированный thumbnail из Browse или заглушка.
5. Поведение единое для VR-флейвора и стандартного.

**Non-goals:**

- Не вводится новый механизм извлечения кадров (background decoder pipeline) — это избыточно для одного poster-кадра.
- Не меняется общий UI плеера при паузе.
- Не покрывается проблема нехватки native heap в целом (это системное ограничение Quest 3).
- Не вводится кэш posterов как отдельная подсистема — если thumbnail уже есть в Browse-кэше, используется он.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Желательно, чтобы пользователь видел хотя бы thumbnail из Browse, а не чёрный экран — лучше «размытый thumbnail», чем «ничего».
2. Желательно, чтобы в лог можно было отличить «null из-за OOM» от «null из-за занятого декодера» от «null из-за неподдерживаемого кодека».
3. Желательно нулевой регресс для обычных (не VR180, не 7K) файлов — те должны работать как прежде.

### 3.2 Жёсткие ограничения

- **Flavor:** все флейворы.
- **API level:** без новых API-зависимостей. `MediaMetadataRetriever` — существующий инструмент; если он возвращает `null`, работаем с этим.
- **Wear OS:** не затрагивается.
- **Производительность:** fallback должен быть быстрым (< 16 мс) — не делать дополнительных IO-операций в main thread.
- **Совместимость данных:** без миграций.
- **Локализация:** без новых строк UI (заглушка не требует текста).
- **Доступность:** заглушка должна иметь content description для TalkBack.

## 4. Контекст текущей архитектуры

`VideoPlayerManager` вызывает `getFrameAtTime` для получения poster-кадра в момент загрузки файла или при паузе. Если результат `null` — в логе пишется `W/` и дальнейшая обработка не описана (по поведению: скорее всего, превью остаётся пустым).

В логе сессии (02:26:03) вызов происходит через ~0.6 с после `VideoPlayerManager.playVideo`, то есть видео уже декодируется через ExoPlayer. На Quest 3 с `native heap free: 9MB` (строка 3156: `Native: 138MB/147MB (free: 9MB)`) вызов `getFrameAtTime` для 7K-файла — почти гарантированный `null` из-за нехватки буфера.

Browse-кэш в лог-сессии зафиксировал успешный `CACHE_HIT_DEBUG: Local video loaded from RESOURCE_DISK_CACHE for 18VR_*.mp4` (line 1528) — значит, thumbnail для этого файла в кэше **есть**. Простейший fallback: при `null` взять thumbnail из Browse-кэша.

---

## 5. Предлагаемый подход

**Защитный контур с enriched логом.** Оборачиваем вызов `getFrameAtTime` в диагностический блок: до вызова — проверить `native heap free` и состояние декодера ExoPlayer; при `null` — логировать расширенный маркер с причиной; применить fallback.

**Fallback-иерархия (порядок приоритета):**

1. Browse-кэш thumbnail для данного файла (уже может быть в памяти).
2. Последний отрисованный кадр ExoPlayer (VideoPlayerManager уже держит ссылку).
3. Статичная заглушка (серый фрейм + иконка).

**Превентивный skip.** Если `ExoPlayer` активен для данного файла И `native heap free < M MB` (M ≈ 50, уточнить в тактической) — не делать `getFrameAtTime` вовсе, сразу fallback к п.1–3.

## 6. Открытые вопросы / Research items

1. **Точная причина null.**
   - **Вопрос:** decoder-busy, OOM или unsupported codec?
   - **Нужно выяснить:** добавить диагностику перед/после вызова: `native heap free`, `isDecoding`, `MediaMetadataRetriever.extractMetadata(METADATA_KEY_VIDEO_CODEC)`.
   - **Статус:** Open.

2. **Порог native heap для превентивного skip.**
   - **Вопрос:** при каком значении `native heap free` декодирование гарантированно провалится?
   - **Нужно выяснить:** эмпирически для разных разрешений (1K / 4K / 7K); на Quest 3 в первом приближении — `free < 50 MB`.
   - **Статус:** Open.

3. **Browse-кэш thumbnail — синхронный или асинхронный доступ?**
   - **Вопрос:** можно ли получить thumbnail из Browse-кэша синхронно в main thread без IO-блокировки?
   - **Нужно выяснить:** как устроен кэш Glide/ресурсов — disk cache vs memory cache; для poster-fallback нужен memory cache.
   - **Статус:** Open.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Превентивный skip ломает poster для обычных (не VR) файлов | Низкая | Пустой poster для нормального файла | Порог условия skip настроен консервативно; тест на обычном 1080p файле |
| Fallback к Browse-кэшу требует синхронного IO | Средняя | Jank в main thread | Использовать только in-memory часть кэша; если нет — сразу к заглушке |
| Диагностика причины null сложнее чем кажется | Средняя | Маркер `reason=unknown` — бесполезен | Добавить конкретные проверки (heap, decoder, codec); даже «unknown» лучше чем нынешнее W без контекста |

## 9. Критерии готовности (strategic-level)

1. `getFrameAtTime returned null` больше не пишется в лог без последующего действия: за ним следует либо успешный fallback, либо `fallback=placeholder reason=<причина>`.
2. При паузе VR180-файла пользователь видит thumbnail из Browse-кэша или заглушку — не чёрный экран.
3. Для обычных (< 4K, non-VR) файлов поведение извлечения poster-кадра не изменилось.
4. Расширенный лог-маркер включает не менее двух из трёх: `native heap free`, `decoder state`, `result`.
5. Чек-лист: протестировано на Quest 3 с 7K VR180-файлом и на телефоне с 1080p-файлом.
