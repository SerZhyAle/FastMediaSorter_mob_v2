## 1. Проблема

Стерео-состояние в VR-плеере страдает от двух независимых дефектов, каждый из которых приводит к тому, что файл воспроизводится в неверном стерео-режиме.

**Утечка режима между файлами (P2-2, P4-4):** При навигации к следующему файлу (вручную или через slideshow auto-advance) стерео-режим предыдущего файла не сбрасывается до момента маршрутизации. В результате новый файл получает разрешённый режим предшественника вместо «автоопределения». В сессии из лога mono-файл `Ess-Na-Crub_Waterfall_360_mono` получил `requested=EQUIRECT_360_SBS` от предшествующего SBS-файла.

**Ненадёжная детекция по имени файла (P2-1):** Слово `stereo` в имени файла не распознаётся как признак SBS-формата. Детектор опирается только на явные суффиксы (`sbs`, `3dh`, `lr`). Кроме того, два источника стерео-информации — имя файла и метаданные трека — конкурируют: получение метаданных трека может вернуть MONO после того, как другой путь уже установил SBS, приводя к рассинхронизации.

**Шум промежуточных состояний (P3-6):** Несколько асинхронных триггеров вызывают маршрутизацию и применение стерео-эффекта с промежуточным MONO/UNKNOWN состоянием. GL-pipeline сбрасывается 3–5 раз впустую до того как стерео-режим окончательно определён.

## 2. Цели

1. Каждый новый файл начинает воспроизведение с чистым, непривязанным к предыдущему файлу стерео-состоянием.
2. Слово `stereo` в имени файла детектируется как признак SBS (или как «возможно SBS — проверить по метаданным»).
3. Конфликт между детекцией по имени файла и метаданными трека разрешается детерминированным приоритетом с однократным применением.
4. GL-pipeline применяет стерео-эффект ровно один раз — после окончательного определения режима, а не несколько раз с промежуточными значениями.

Non-goals:

- Новые алгоритмы детекции стерео на основе анализа видеокадра (machine learning, heuristics на соотношении сторон) — вне объёма.
- Изменение самой логики рендеринга fisheye/OU — это объём `spec_vr-stereo-formats`.
- Ручное переключение формата пользователем из иммерсива — это объём `spec_vr-immersive-controls-panel`.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Детектор имён файлов должен поддерживать расширяемый список синонимов для каждого режима — без хардкода в условиях.
2. При конфликте источников (filename vs метаданные) предпочтительнее логировать предупреждение с указанием обоих значений, а не молча выбирать один.
3. Поведение должно быть одинаковым для slideshow auto-advance и ручной навигации PreviousFile/NextFile.

### 3.2 Жёсткие ограничения

- **Flavor:** `vr` — основной объём; изменения в детекторе имён файлов и координаторе стерео-состояния применяются ко всем флейворам, где детекция используется.

- **Wear OS:** не затрагивается.
- **Производительность:** синхронизация состояния должна быть мгновенной (<1 ms) — не допускается выполнение на фоновом потоке с задержкой.
- **Совместимость данных:** изменений в Room-схеме не требуется; пользовательские переопределения стерео-режима (Remember file format) должны сохраниться.

## 4. Контекст текущей архитектуры

Стерео-режим определяется на двух этапах: при открытии файла (по имени файла и пути) и при получении метаданных трека. Результат каждого этапа записывается в координатор стерео-состояния, который хранит: «детектированный», «запрошенный» (пользовательский override) и «эффективный» режимы. «Запрошенный» режим не очищается при смене файла, что является источником утечки.

Компонент маршрутизации воспроизведения читает «запрошенный» параметр в момент вызова. При переходе к следующему файлу маршрутизация вызывается до того, как координатор получает сигнал о смене файла и сбрасывает состояние. Таким образом, новый файл маршрутизируется со старым «запрошенным» значением.

Детектор по имени файла использует regex/suffix matching. Текущий набор суффиксов: `sbs`, `3dh`, `lr`, `3d`, `180`, `360`, `mono`, `ou`, `tab`, `3dv`, `halfou`. Слово `stereo` как standalone-суффикс или слово в имени файла не включено.

Несколько независимых подписчиков (UI state observer, player state observer, resume logic) одновременно реагируют на изменение стерео-режима и вызывают применение GL-эффекта. Нет центрального «settle» механизма, который ждал бы стабилизации всех источников.

## 5. Предлагаемый подход

### 5.1 Основные столпы / модули

**Столп A — Явный сброс состояния при смене файла**

Координатор стерео-состояния получает событие «файл сменился» до вызова маршрутизации. Событие очищает «запрошенный» режим (возвращает в AUTO/UNKNOWN), сохраняя пользовательские переопределения в базе данных (они загружаются отдельно для нового файла). Порядок: сброс → загрузка override для нового файла → маршрутизация.

**Столп Б — Расширяемый реестр суффиксов**

Детектор имён файлов переходит от хардкодных условий к конфигурируемой таблице: `слово/суффикс → стерео-режим`. Слово `stereo` добавляется как синоним для «вероятно SBS» с низким приоритетом (перекрывается явным `mono` в том же имени). Таблица легко расширяется без изменения логики матчинга.

**Столп В — Приоритет источников с однократным применением**

Вводится явная иерархия источников: пользовательский override > метаданные трека > детекция по имени файла. После стабилизации всех источников (т.е. после получения метаданных или таймаута «нет трек-инфо») стерео-режим применяется ровно один раз. Промежуточные MONO/UNKNOWN состояния не запускают GL-эффект — применение откладывается до «settled» события.

**Столп Г — Settled-событие**

Вводится концепция «settled state» для стерео-режима: после смены файла все источники имеют таймаут (например, 500 ms после начала воспроизведения). По истечении таймаута или после получения метаданных — финальный режим фиксируется и применяется единожды. Промежуточные вызовы GL-pipeline в период ожидания игнорируются.

### 5.2 Потоки данных и событий

```
Переход к следующему файлу / slideshow advance
    ↓
Координатор стерео-состояния: сброс запрошенного режима
    ↓
Загрузка user override для нового файла (async DB)
    ├─ filename → режим (приоритет 3)
    ├─ Метаданные трека → режим (приоритет 2)  [async]
    └─ user override loaded → режим (приоритет 1) [async]
              ↓
        Settled Gate (все источники получены ИЛИ таймаут)
              ↓
        Финальный режим → Маршрутизация → GL-эффект (1 раз)
```

### 5.3 Точки расширяемости

- Реестр суффиксов должен читаться из конфигурации — это позволит тонко настраивать детекцию без пересборки.
- Settled Gate должен поддерживать произвольное количество источников — для будущих (например, cloud metadata API, NFO/XML sidecar).

## 6. Открытые вопросы / Research items

1. **Таймаут settled gate**
   - **Решение:** Settled Gate срабатывает при получении события готовности плеера (трек-инфо доступен) ИЛИ по таймауту 500 ms с момента смены файла — что наступит раньше. Событие готовности предпочтительно: нет произвольной задержки; 500 ms — fallback если метаданные не пришли.
   - **Статус:** Resolved

2. **Конфликт `stereo` word + явный `mono` суффикс**
   - **Решение:** `mono` побеждает (явный маркер > общее слово). Алгоритм: если в имени файла присутствует явный `mono` — он имеет приоритет над `stereo`-словом независимо от порядка. Детектор логирует предупреждение о конфликте.
   - **Статус:** Resolved

3. **Поведение user override при смене файла**
   - **Решение:** Override хранится в DB per-file (ключ — путь к файлу). При возвращении к файлу A override загружается из DB и восстанавливается. Сброс «ephemeral requested» при смене файла не затрагивает persisted override.
   - **Статус:** Resolved

## 9. Архитектурные решения (ADR)

**ADR-1: Разделение ephemeral vs persisted стерео-состояния**

- **Решение:** Координатор стерео-состояния хранит два независимых свойства: временное состояние (сбрасывается при смене файла) и сохранённое переопределение (загружается из БД для каждого файла). Компонент маршрутизации читает сохранённое переопределение если оно есть, иначе — результат детекции.
- **Альтернативы:** Одно поле запрошенного состояния, которое всегда перезаписывается значением из БД (текущий подход, но с явным сбросом перед чтением).
- **Почему так:** Явное разделение предотвращает случайную утечку через любой из путей; семантика понятна без чтения кода.

**ADR-2: Settled Gate как отдельный компонент**

- **Решение:** Логика ожидания стабилизации всех источников выносится в отдельный компонент (не inline в координатор), который принимает источники как реактивные потоки и эмитит settled-событие.
- **Альтернативы:** Флаги в координаторе; асинхронный таймер задержки.
- **Почему так:** Тестируемость и расширяемость — новые источники добавляются без изменения координатора.

## 11. Критерии готовности (strategic-level)

1. Переход от SBS-файла к mono-файлу воспроизводит mono без стерео-артефактов.
2. Slideshow auto-advance между SBS и mono файлами не наследует стерео-режим предыдущего файла.
3. Файл `Boersensaal_Hamburg_stereo_360_8K_25s.webm` детектируется как SBS уже по имени файла (до получения метаданных трека).
4. GL-pipeline применяет стерео-эффект не более одного раза при открытии файла.
5. Пользовательский override («Remember file format») сохраняется при возвращении к файлу после навигации.
