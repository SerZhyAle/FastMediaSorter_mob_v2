## 1. Проблема

При попытке открыть удалённый ресурс в условиях, когда сервер заведомо недоступен, пользователь ожидает около 15 секунд прежде чем получает диалог об ошибке. Затрагивает два класса сценариев:

- **SMB при отсутствии Wi‑Fi** (только мобильный интернет, чужая Wi‑Fi сеть, самолётный режим) — текущее поведение проходит TCP precheck, попытку SMB connect и retry с расширенным таймаутом, тратя бюджетное время на заведомо обречённую попытку.
- **Любой удалённый ресурс (SMB, FTP, SFTP, Cloud) при полном отсутствии сети** — даже первичная проверка сокета занимает таймаут, хотя факт отсутствия сети известен системе мгновенно.

Признаки недоступности (тип транспорта) уже вычисляются в коде, однако используются исключительно пост‑фактум — для подмены текста уже сформированной ошибки. Эффект: воспринимаемая «зависшая» программа на 5..15 секунд при каждом нечаянном тапе по удалённому ресурсу. Затронутые слои — сетевые источники данных (SMB/FTP/SFTP/Cloud), пользовательские входы — навигация по списку ресурсов, открытие папок, плеер, виджет.

Несмотря на slug `smb-fast-fail`, scope расширен на все удалённые типы для общего случая «нет сети». SMB‑специфичные части (Wi‑Fi gate, retry decision) остаются ядром спеки.

---

## 2. Цели

1. **Универсальный no‑network gate.** При полном отсутствии сети (нет ни Wi‑Fi, ни мобильного интернета) попытка открыть любой удалённый ресурс — SMB, FTP, SFTP, Cloud — отказывается практически мгновенно, без сокетных попыток.
2. **SMB Wi‑Fi gate.** При отсутствии активной Wi‑Fi сети (мобильный интернет есть, но Wi‑Fi нет) попытка открыть SMB‑ресурс отказывается практически мгновенно. FTP/SFTP/Cloud в этой ситуации продолжают работать как сейчас (могут быть достижимы через мобильный канал).
3. **Smart retry для SMB.** При наличии Wi‑Fi, но недоступном SMB‑хосте, отказ выдаётся за время одного TCP precheck — без вторичного retry с расширенным таймаутом.
4. **Без регрессии на медленных серверах.** Расширенный retry продолжает срабатывать, если первая попытка успела установить TCP, но упала на уровне SMB‑транзакций.
5. **Тексты диалогов не меняются** — пользователь не замечает разницы, кроме того, что окно появляется быстрее.

**Non-goals:**

- Не меняем тексты ошибок и не добавляем новые локализованные строки. Существующие строки переиспользуются.
- Не оптимизируем сценарий «домашняя сеть, медленный сервер» — он и так работает корректно.
- Smart retry (Pillar B) применяется только к SMB. Аналогичная оптимизация retry для FTP/SFTP/Cloud — отдельная задача, в эту спеку не входит.
- Не вводим UI для ручного управления таймаутами или режимом «офлайн».
- Не добавляем кэш «доступных ресурсов» / «последний известный статус» — отказ остаётся реактивным, без предсказаний.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. По возможности — единая точка для precheck'ов, чтобы поведение было одинаковым для всех путей вызова SMB (открытие папки, плеер, пакетные операции, виджет).
2. Логирование причины короткого отказа в Timber, чтобы при отладке было видно: «отказали из‑за cellular gate» vs «отказали из‑за TCP precheck failure».

### 3.2 Жёсткие ограничения

- **Flavor:** no‑network gate (Pillar A1) применяется во всех flavor'ах, где есть удалённые ресурсы. SMB Wi‑Fi gate и smart retry (A2, B) — только во flavor'ах с SMB: `standard`, `lite`, `legacy`. Flavor `photos` локальный — затрагивается только в части, где он использует Cloud (если включён).
- **API level:** без API‑специфики; используются только уже задействованные системные API определения транспорта.
- **Wear OS:** не затрагивается (на часах SMB‑клиент не используется).
- **Производительность:** Wi‑Fi gate — синхронная проверка in‑memory, бюджет ≤ 1 мс. TCP precheck — без изменений по таймауту.
- **Совместимость данных:** изменений схемы и миграций нет.
- **Локализация:** существующие строки переиспользуются, новые не вводим.
- **Доступность:** не применимо — изменение прозрачно для UI.

## 4. Контекст текущей архитектуры

У каждого удалённого типа есть свой источник данных (SMB, FTP, SFTP, Cloud), вызываемый стратегией ресурса. Сетевой слой SMB реализует двухступенчатую проверку: сперва TCP precheck (короткий socket connect), затем полноценное подключение с аутентификацией и сессией; на случай редких медленных серверов добавлен retry с расширенным таймаутом. У других типов precheck'а нет — они сразу идут на полное подключение со своими таймаутами.

Анализ сетевого контекста (тип транспорта, приватность хоста) живёт в отдельном утилитарном слое и сейчас задействован только маппером сообщений об ошибках — он работает пост‑фактум, после того как соответствующий сетевой слой уже исчерпал все попытки.

Отсутствуют две вещи: общая precondition‑точка перед любым удалённым подключением (для no‑network gate, единая для SMB/FTP/SFTP/Cloud) и SMB‑специфичные различения причин сбоя первой попытки (TCP vs SMB‑транзакция). Сейчас отсутствие сети «доходит до пользователя» через таймауты сокетов, а SMB retry с расширенным таймаутом применяется одинаково ко всем сбоям первой попытки, удваивая время отказа на сценарии «хост недоступен».

## 5. Предлагаемый подход

Решение состоит из трёх взаимодополняющих частей: универсальный no‑network gate для всех удалённых типов, SMB‑специфичный Wi‑Fi gate, и smart retry для SMB.

### 5.1 Основные столпы / модули

**Pillar A1 — No‑network gate (универсальный).**
Перед началом любой попытки подключения к удалённому ресурсу (SMB, FTP, SFTP, Cloud) сетевой слой консультируется со слоем сетевого контекста: если активного транспорта нет вовсе (ни Wi‑Fi, ни мобильного), попытка отвергается синхронно. Возвращается исключение «соединение потеряно». Маппер ошибок при отсутствии транспорта формирует обычный текст «соединение потеряно» — это уже корректный пользовательский месседж.

**Pillar A2 — SMB Wi‑Fi gate.**
Дополнительно для SMB: если активного Wi‑Fi нет (есть только мобильный интернет), SMB‑подключение отвергается синхронно — мобильный канал не достаёт до локального сервера. Это единственное условие — никакой проверки IP‑диапазонов, поскольку в разных Wi‑Fi сетях IP‑адреса устройств могут пересекаться, и судить о достижимости конкретного хоста по адресу нельзя. Возвращается исключение «соединение потеряно»; существующий контекстный маппер видит «cellular + SMB» и без изменений формирует привычный текст про мобильный интернет.

**Pillar B — Smart retry для SMB (TCP‑fail vs SMB‑fail).**
Сетевой слой SMB различает причину сбоя первой попытки подключения. Если попытка не прошла TCP precheck (хост недостижим, отказ в подключении, нет маршрута), retry с расширенным таймаутом не выполняется — сервер заведомо недоступен и продление ожидания не помогает. Если же TCP установился, но операция сорвалась на SMB‑транзакциях (сервер ответил, но медленно или прервал сессию), сохраняется текущее поведение: повторная попытка с расширенным таймаутом.

### 5.2 Потоки данных и событий

Поток вызова любого удалённого источника данных:

1. **No‑network gate (новый шаг, синхронно, для всех типов).** Слой сетевого контекста → решение «есть какой‑либо транспорт / нет». При «нет» — мгновенное исключение «соединение потеряно».
2. **SMB Wi‑Fi gate (новый шаг, синхронно, только для SMB).** Если первый шаг пропустил, и тип ресурса = SMB → проверка наличия Wi‑Fi. При «нет Wi‑Fi» — мгновенное исключение «соединение потеряно».
3. **TCP precheck (как сейчас, только SMB).** Если оба гейта пропустили — выполняется короткий precheck. Результат (успех/неуспех) запоминается для решения о retry.
4. **Полное подключение (как сейчас).** Своё для каждого типа: SMB connect + auth, FTP login, SFTP handshake, Cloud auth.
5. **Retry decision (изменён, только SMB).** Ветвление по результату шага 3: при неуспехе TCP — без retry; при успехе TCP, но сбое на SMB‑транзакциях — retry с расширенным таймаутом.

### 5.3 Точки расширяемости

- No‑network gate (A1) оформляется как единая функция / стратегия, вызываемая на входе каждого удалённого источника. Расширение списка проверок (например, добавить «нет интернета по DNS» как отдельный сигнал) сводится к правке одной функции, а не каждого источника.
- Wi‑Fi gate (A2) — частный случай для SMB; реализован поверх той же функции, что и A1, через расширение её результата (тип условия), а не через дублирующую проверку.
- Smart retry (B) — желательно через отдельную явную классификацию причины сбоя (TCP fail vs протокольный fail), переиспользуемую и в логировании, и в решении о retry, чтобы не разводить две независимые проверки одной и той же сущности.

## 6. Открытые вопросы / Research items

1. **Условие гейта — наличие Wi‑Fi, без проверки IP‑диапазонов**
   - **Вопрос:** Какое именно условие должно срабатывать на гейте?
   - **Резолюция:** Гейт срабатывает по единственному критерию — отсутствие активной Wi‑Fi сети. Никакой проверки приватности IP или совпадения подсетей не выполняется: разные Wi‑Fi сети могут иметь устройства с одинаковыми адресами, поэтому из самого адреса нельзя судить о достижимости. Как именно слой сетевого контекста доставляется до места проверки (DI в нижний слой vs внешний gate перед вызовом) — тактический выбор фазы 01.
   - **Статус:** Resolved

2. **Поведение при отсутствии сети вообще**
   - **Вопрос:** Если ни Wi‑Fi, ни мобильного интернета нет, как должен вести себя гейт, и должно ли это распространяться на FTP/SFTP/Cloud?
   - **Резолюция:** Введён универсальный no‑network gate (Pillar A1) — мгновенный отказ для всех удалённых типов (SMB, FTP, SFTP, Cloud), если активного транспорта нет вовсе. SMB Wi‑Fi gate (Pillar A2) идёт сверху и срабатывает, когда мобильный есть, но Wi‑Fi нет — только для SMB. FTP/SFTP/Cloud при наличии хоть какого‑то транспорта продолжают работать как сейчас.
   - **Статус:** Resolved

3. **Кеширование вердикта Wi‑Fi gate в рамках сессии**
   - **Вопрос:** Кешировать ли результат проверки контекста между подряд идущими вызовами?
   - **Резолюция:** Не кешировать. Проверка статуса транспорта — дешёвая системная операция; кеш добавил бы инвалидацию по событиям сети без ощутимой выгоды.
   - **Статус:** Resolved

|------|:-----------:|-------------|-----------|
| Wi‑Fi gate срабатывает ложно — пользователь в локальной сети, но система определяет транспорт как cellular (например, активны и Wi‑Fi, и LTE одновременно) | Низкая | Пользователю отказывают в SMB при наличии рабочей локальной сети | Использовать существующую логику определения активного транспорта, не вводить собственную; покрыть тестами edge‑case с двумя активными транспортами |

| No‑network gate ошибочно ломает Cloud‑операции, поставленные в очередь WorkManager при отсутствии сети — они должны ждать сеть, а не падать с ошибкой | Средняя | Регрессия: фоновые задачи перестают накапливаться и сразу помечаются как failed | На этапе тактической: разделить «интерактивный вызов» (gate активен, мгновенный отказ) и «фоновое исполнение задачи» (gate не применяется, либо WorkManager сам управляет сетевыми constraints) |

## 9. Архитектурные решения (ADR)

**ADR-1: Гейт как часть нижнего сетевого слоя каждого источника, а не отдельная UI‑проверка**

- **Решение:** No‑network gate и Wi‑Fi gate выполняются внутри сетевых источников данных (SMB/FTP/SFTP/Cloud), до начала любых сокетных операций.
- **Альтернативы:** (а) проверка на уровне UI/ViewModel перед вызовом сетевого слоя; (б) отдельный middleware между UI и сетью.
- **Почему:** Единая точка гарантирует одинаковое поведение для всех путей вызова (UI, виджет, фоновые сервисы интерактивного типа), не размазывает логику доступности по слоям и не требует от каждого вызывающего знать про политику gate.

**ADR-2: Не вводить новый тип исключения для гейтов**

- **Решение:** При срабатывании любого gate выбрасывается то же исключение «соединение потеряно», что и при обычном таймауте.
- **Альтернативы:** Ввести отдельный тип `NetworkUnreachableException` или подобный.
- **Почему:** Существующий контекстный маппер сообщений уже корректно обрабатывает связку «соединение потеряно + транспорт» и показывает нужный текст. Новый тип потребовал бы синхронизации маппера, тестов и не дал бы пользовательской ценности.

**ADR-3: Различение TCP‑fail и SMB‑fail как явная классификация, а не строковая проверка**

- **Решение:** Признак «упало на TCP precheck» переносится явно — флагом или типом — в место принятия решения о retry.
- **Альтернативы:** Анализ текста / класса исключения на месте принятия решения.
- **Почему:** Анализ исключений хрупок и плохо тестируется; явная классификация делает логику retry детерминированной и проверяемой юнит‑тестами.

**ADR-4: Smart retry применяется только к SMB**

- **Решение:** Различение «TCP fail vs протокольный fail» реализуется только для SMB. FTP/SFTP/Cloud сохраняют текущее retry‑поведение.
- **Альтернативы:** Расширить smart retry на все удалённые типы.
- **Почему:** Текущая SMB‑специфика — двухступенчатая проверка с TCP precheck — даёт точку, где это различение естественно. У других типов нет аналогичного precheck'а; распространение требует переработки их клиентов и выходит за рамки этой спеки.

## 11. Критерии готовности (strategic-level)

1. **No‑network для всех типов.** При выключенной сети попытка открыть SMB / FTP / SFTP / Cloud ресурс завершается диалогом об ошибке практически мгновенно — пользователь не замечает задержки.
2. **SMB на мобильном интернете.** При наличии только мобильного интернета попытка открыть SMB‑ресурс завершается диалогом «SMB‑ресурс недоступен через мобильный интернет» практически мгновенно.
3. **SMB на чужом Wi‑Fi.** На Wi‑Fi сети, где SMB‑хост недоступен, диалог об ошибке появляется за время порядка одного TCP precheck — заметно быстрее, чем сейчас.
4. **Без регрессии.** На рабочем, но медленном SMB‑сервере соединение по‑прежнему устанавливается без ложных ранних отказов — в логах видно срабатывание retry с расширенным таймаутом.
5. **FTP/SFTP/Cloud на мобильном.** При наличии только мобильного интернета FTP/SFTP/Cloud ресурсы продолжают работать как сейчас (могут подключаться, могут падать на таймауте — но не отбиваются гейтом).
6. **Тексты не изменились.** Пользователь видит те же формулировки диалогов, что и до доработки.
7. **Все пути единообразны.** Поведение виджета, плеера, пакетных операций, навигации по ресурсам — единое: ни один интерактивный путь вызова не обходит гейт.
8. **Фоновые задачи не сломаны.** Cloud‑задачи в WorkManager / фоновых сервисах при отсутствии сети ставятся в очередь штатно (как сейчас), а не падают мгновенно с ошибкой.
9. **Логи диагностируемы.** В Timber‑логах различимы причины короткого отказа — no‑network gate vs Wi‑Fi gate vs TCP precheck failure — для последующей отладки.
