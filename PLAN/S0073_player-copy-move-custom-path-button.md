## 1. Проблема

В плеере панели «Копировать в..» и «Переместить в» отображают только кнопки ресурсов-получателей, настроенных заранее в списке ресурсов. Если пользователь хочет скопировать или переместить файл в произвольную локальную папку, которая не добавлена как ресурс-получатель, — такой возможности нет. В диалоге «Копировать в» / «Переместить в», вызываемом из Browse, уже есть кнопка «Выбрать папку», открывающая системный выбор директории; однако в inline-панелях плеера аналогичного входа нет. Пользователь вынужден выходить из плеера, чтобы воспользоваться диалогом из Browse, либо заранее заводить отдельный ресурс-получатель для каждой нужной папки.

---

## 2. Цели

1. В панели «Копировать в..» плеера всегда последней кнопкой отображается маленькая кнопка «..».
2. В панели «Переместить в» плеера всегда последней кнопкой отображается маленькая кнопка «..».
3. Нажатие «..» открывает системный выбор локальной директории — ровно так же, как это работает в Browse (через `ACTION_OPEN_DOCUMENT_TREE` / `OpenDocumentTree`).
4. После выбора папки операция копирования или перемещения выполняется немедленно — без дополнительного диалога подтверждения.
5. Кнопка «..» всегда видна независимо от числа ресурсов-получателей (даже когда их 0).
6. Визуально кнопка «..» заметно меньше и нейтральнее обычных кнопок-получателей, чтобы не конкурировать с основными назначениями.

**Non-goals:**

- Запоминание «последней выбранной через «..» папки» как нового постоянного ресурса-получателя — это отдельная функция управления ресурсами.
- Поддержка облачных хранилищ через кнопку «..» (только локальные пути).
- Изменение диалогового варианта FileOperationDestinationDialog в Browse (не затрагивается).
- Добавление кнопки «..» в диалог ARCHIVE.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Кнопка «..» стилистически похожа на кнопки навигации (серая/нейтральная, меньший размер).
2. При наличии ресурсов-получателей кнопка «..» располагается строго после них; при отсутствии — остаётся единственной кнопкой в панели.
3. Последняя использованная через «..» папка может предлагаться при следующем нажатии через системный пикер (стандартное поведение `OpenDocumentTree` с initial URI — без кастомного UI истории).

### 3.2 Жёсткие ограничения

- **Flavor:** `standard`, `lite`, `legacy`, `photos` — все flavors, в которых плеер работает с файлами.
- **API level:** minSdk 26 (`OpenDocumentTree` доступен с API 21, постоянный доступ через persistedUriPermissions — с API 19; ограничений нет).
- **Wear OS:** не затрагивается.
- **Производительность:** кнопка «..» добавляется статически при построении панели; оверхеда нет.
- **Совместимость данных:** новых Room-таблиц или миграций не требуется; опционально — хранение последнего URI пикера в AppSettings (в существующем механизме хранения настроек).
- **Локализация:** кнопка «..» — символьная, локализации не требует. Возможные accessibility-строки (content description) нужны на EN/RU/UK.
- **Доступность:** кнопка «..» должна иметь осмысленный `contentDescription` («Выбрать папку» / «Select folder»); touch target не меньше 48 dp.

## 4. Контекст текущей архитектуры

Панели «Копировать в» и «Переместить в» реализованы как inline-секции командной панели плеера. Их содержимое — кнопки ресурсов-получателей — строится динамически слоем управления кнопками назначения на основе данных, поступающих из use-case получателей. Этот слой не содержит никакого механизма выбора произвольного пути: он предполагает, что получатели — только заранее настроенные ресурсы.

Механизм выбора произвольной папки уже существует в приложении, но реализован в контексте Browse: там специализированный обработчик запускает системный Activity для выбора директории и через callback возвращает URI выбранной папки обратно в менеджер файловых операций. Этот механизм не привязан к конкретному экрану и потенциально переиспользуем — нужно лишь обеспечить его вызов из контекста плеера и правильную маршрутизацию результата в нужный use-case файловых операций.

Ключевое ограничение текущей архитектуры: результат `startActivityForResult` / `ActivityResultLauncher` требует регистрации в Activity или Fragment; плеер уже является Activity, поэтому интеграция технически прямолинейна, но требует добавления нового launcher-а в цепочку инициализации плеера.

---

## 5. Предлагаемый подход

Кнопка «..» добавляется в процедуру построения панели кнопок-получателей как последний элемент. Она создаётся с фиксированным стилем (нейтральный, меньший размер) вне зависимости от числа существующих ресурсов.

### 5.1 Основные столпы / модули

**А — Рендеринг кнопки «..» в панелях**

Слой управления кнопками назначения дополняется логикой добавления специальной кнопки «..» после всех стандартных кнопок-получателей. Кнопка создаётся с иным визуальным весом: меньший размер, нейтральный цвет (без тематической окраски ресурса), явный `contentDescription`. При нажатии — делегирует запрос выбора папки наружу через callback (не знает ни об Activity Result, ни о системном пикере).

**Б — Запуск системного выбора директории из контекста плеера**

В рамках плеера регистрируется новый обработчик выбора локальной папки — по образцу уже существующего в Browse. Он:
- запускает системный `OpenDocumentTree` с hint URI последней использованной папки (если известна);
- по возвращении запрашивает постоянное разрешение на URI;
- передаёт выбранный URI + тип операции (COPY / MOVE) в слой файловых операций.

**В — Выполнение операции с произвольным URI-путём**

Слой файловых операций плеера уже умеет принимать путь назначения; нужно убедиться, что он корректно обрабатывает URI, полученный от системного пикера (SAF URI), а не только File-пути постоянных ресурсов. Если текущая реализация FileOperationUseCase уже поддерживает SAF URI — дополнительных изменений в domain-слое нет.

### 5.2 Потоки данных и событий

```
Пользователь нажимает «..» в панели (COPY или MOVE)
  → слой кнопок назначения генерирует событие «запросить папку» с типом операции
  → обработчик запуска папок в плеере открывает системный пикер
  → пользователь выбирает директорию
  → системный пикер возвращает URI
  → обработчик сохраняет URI в настройки (hint для следующего вызова)
  → обработчик передаёт (URI, operationType, исходный файл) в слой файловых операций плеера
  → файловая операция выполняется (copy/move)
  → стандартный постоперационный flow (undo, переход к следующему файлу)
```

### 5.3 Точки расширяемости

- Интерфейс между кнопкой «..» и обработчиком выбора папки оформляется как обобщённый callback «запросить произвольный путь», чтобы в будущем его можно было переиспользовать в других панелях или диалогах.
- URI последней выбранной папки хранится в настройках — это позволит впоследствии добавить «историю» или предложить добавить папку в ресурсы, не меняя архитектуру.

## 6. Открытые вопросы / Research items

1. **SAF URI vs File-путь в FileOperationUseCase**
   - **Вопрос:** текущий UseCase файловых операций принимает назначение как `File` или как SAF `Uri`? Если только `File` — нужна дополнительная работа по конвертации URI в доступный путь (через DocumentFile) или расширение сигнатуры use-case.
   - **Варианты:** (a) use-case уже поддерживает SAF URI; (b) нужна обёртка DocumentFile → OutputStream; (c) нужно расширить сигнатуру.
   - **Нужно выяснить:** проверить сигнатуру FileOperationUseCase и то, как BrowseFolderPickerHandler передаёт результат в операции Browse.
   - **Статус:** Open

2. **Поддержка сети через SAF URI**
   - **Вопрос:** нужно ли ограничить пикер только локальными путями, или пользователь должен иметь возможность выбрать и сетевой провайдер через SAF?
   - **Варианты:** (a) не ограничивать — системный пикер сам предложит доступные провайдеры; (b) отфильтровать только локальные.
   - **Нужно выяснить:** уточнить у владельца.
   - **Статус:** Open

## 9. Архитектурные решения (ADR)

**ADR-1: Кнопка «..» рендерится вне основного алгоритма распределения кнопок**

- **Решение:** кнопка «..» добавляется в панель как самостоятельный элемент после завершения стандартного алгоритма распределения N ресурсов-получателей по строкам.
- **Альтернативы:** (a) включить «..» как N+1 элемент в стандартный алгоритм распределения; (b) всегда помещать в отдельную строку.
- **Почему:** текущий алгоритм оптимизирован под равномерную сетку одинаковых кнопок; добавление «..» с иным визуальным весом как N+1 нарушает логику симметричного распределения и делает строки неровными при нечётных числах. Отдельная строка гарантирует предсказуемое положение и простой рендеринг.

**ADR-2: Инициализация launcher-а в плеере, а не в диалоге**

- **Решение:** `ActivityResultLauncher` для `OpenDocumentTree` регистрируется на уровне плеера (Activity), callback маршрутизируется через существующую вертикаль менеджеров.
- **Альтернативы:** создать новый диалог-обёртку с собственным launcher-ом.
- **Почему:** плеер уже является Activity; регистрация launcher-а в диалоге создаёт сложности с жизненным циклом и противоречит архитектурному паттерну проекта (логика — в Manager-ах, не в диалогах).

## 11. Критерии готовности (strategic-level)

1. Кнопка «..» видна в развёрнутой панели «Копировать в..» плеера при любом числе ресурсов-получателей (0..max).
2. Кнопка «..» видна в развёрнутой панели «Переместить в» плеера при любом числе ресурсов-получателей.
3. Нажатие «..» в панели «Копировать в..» открывает системный выбор директории; выбранная папка используется как назначение операции копирования.
4. Нажатие «..» в панели «Переместить в» открывает системный выбор директории; выбранная папка используется как назначение операции перемещения.
5. Повторное нажатие «..» предлагает системному пикеру ранее выбранную папку как начальную точку навигации.
6. Отмена системного пикера не вызывает краша или зависания; плеер остаётся в рабочем состоянии.
7. После выполнения операции через «..» срабатывает стандартный постоперационный flow (возможность undo, переход к следующему файлу).
8. Кнопка «..» имеет корректный `contentDescription` и touch target ≥ 48 dp.
