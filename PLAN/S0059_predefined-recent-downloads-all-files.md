# Стратегическая спецификация: S0059 — Все файлы по умолчанию для "Recent" и "Downloads"

**Ticket:** S0059
**Status:** Tactical
**Priority:** 50
**Date:** 2026-05-03
**Tier:** 2 — Easy (ad-hoc)
**Roadmap entry:** Ad-hoc — запрос 2026-05-03 («предопределённые каталоги Recent и Downloads должны показывать все файлы, не только медиа, при установке и для уже существующих установок»)
**Tactical spec:** `PLAN/S0059_predefined-recent-downloads-all-files/`
**Tactical plan:** `PLAN/S0059_predefined-recent-downloads-all-files/INDEX.md`

> **Scope:** STRATEGIC. Цели, ограничения, открытые вопросы. Без имён классов, путей, лимитов строк, миграций Room, модулей Hilt.

## 1. Проблема

Предопределённый виртуальный каталог «Недавние медиа» создаётся при первом запуске со «строгим» режимом — отображаются только файлы из включённых медиатипов. Пользователь, открывая «Recent files», ожидает видеть **всё** недавно открытое (включая архивы, документы, неизвестные расширения), а получает урезанный список. Та же логика применима к локальному каталогу «Downloads», добавляемому через быстрый сценарий «один клик»: для папки «Загрузки» характерно смешанное содержимое, а текущая конфигурация по умолчанию фильтрует файлы по медиатипам, скрывая часть содержимого без явного объяснения.

Параллельно, у пользователей с уже установленным приложением эти ресурсы существуют в базе данных с прежней (фильтрующей) настройкой и при апгрейде сами не перенастраиваются, что приводит к расхождению поведения между «свежей установкой» и «миграцией».

---

## 2. Цели

1. На свежей установке предопределённый каталог «Recent» создаётся в режиме «показывать все файлы», т. е. без фильтрации по медиатипам.
2. На свежей установке быстрый сценарий добавления «Downloads» (системная папка «Загрузки») создаёт ресурс в режиме «показывать все файлы».
3. На существующей установке выполняется однократная миграция: если в базе есть предопределённый «Recent» и/или ресурс, указывающий на системную папку «Загрузки», их режим переводится в «показывать все файлы».
4. Поведение должно быть консистентно между новой установкой и миграцией: после первого запуска новой версии пользователь не видит расхождений между «у меня было» и «как создаётся заново».
5. Пользователь сохраняет возможность вручную вернуть фильтрацию по медиатипам через стандартный редактор ресурса — миграция не «запирает» режим.

**Non-goals:**

- Изменение режима для других предопределённых виртуальных ресурсов («All Music», «All Videos», «All Images», «All Documents», «Camera Photos») — у них фильтрация по типу остаётся осмысленной.
- Изменение режима для пользовательских (созданных вручную) локальных ресурсов, даже если они указывают на папку «Загрузки».
- Добавление новых предопределённых виртуальных каталогов (миграция работает только с тем, что уже существует или создаётся первичным провижингом).
- Любые изменения в логике сканирования содержимого или в правилах распознавания медиатипов.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Желательно, чтобы миграция была идемпотентной: повторный запуск той же версии не должен переоткрывать ранее уже мигрированные записи.
2. Желательно, чтобы факт миграции был зафиксирован в логах (одной строкой на ресурс), чтобы при разборе пользовательских отчётов можно было быстро понять, сработала ли миграция.
3. Желательно, чтобы миграция не блокировала первый запуск (выполнялась в фоне или быстро завершалась на любом разумном размере БД).

### 3.2 Жёсткие ограничения

- **Flavor:** все варианты (`standard`, `lite`, `photos`, `legacy`). «Recent» создаётся в каждом флэйворе; «Downloads» доступен в любом флэйворе с локальным сканером.
- **API level:** без API-специфики; minSdk проекта (26 / 23 для legacy) сохраняется.
- **Wear OS:** не затрагивается — модуль `wear/` не использует предопределённые виртуальные ресурсы и не имеет доступа к системной папке «Загрузки» в той же модели.
- **Производительность:** миграция должна укладываться в одно короткое обновление БД при первом запуске новой версии; недопустимо повторное полное сканирование файлов или долгие синхронные операции на UI-потоке.
- **Совместимость данных:** миграция выполняется как одноразовое обновление существующих записей ресурсов; пользовательские поля (имя, иконка, порядок, сортировка, флаги «destination/read-only») не затрагиваются. Откат на предыдущую версию приложения не требует обратной миграции — поле уже существует.
- **Локализация:** EN/RU/UK — обязательно для любых пользовательских строк, если будут добавлены новые (например, информационная надпись о миграции). Если строки не добавляются — пункт неприменим.
- **Доступность:** изменение невидимо для TalkBack как отдельная функция; touch target не появляется. Стандартный редактор ресурса остаётся каноническим способом изменить режим.

## 4. Контекст текущей архитектуры

В проекте есть два независимых пути появления указанных каталогов. Первый — автоматический провижинг предопределённых виртуальных ресурсов на пустой базе при первом запуске; именно там «Recent» сейчас рождается с фильтрацией по включённым медиатипам. Второй — быстрый сценарий добавления локальных ресурсов «в один клик», где системная папка «Загрузки» определяется по абсолютному пути и предлагается пользователю в общем списке, но создаётся как обычный локальный ресурс с настройками по умолчанию. Между этими двумя путями нет общей точки, в которой можно было бы централизованно задать «Recent и Downloads — это особые каталоги, у которых режим отображения файлов отличается от прочих». Соответственно, для существующих установок никакой автоматической доводки режима тоже не предусмотрено: пользователь, обновивший приложение, продолжает видеть прежнее поведение, отличное от новой установки.

## 5. Предлагаемый подход

Ввести явное правило «для предопределённых каталогов Recent и Downloads режим отображения файлов по умолчанию — нефильтрующий». Правило применяется в двух местах: (а) на этапе первичного провижинга предопределённых виртуальных ресурсов, (б) на этапе быстрого добавления «Downloads» из списка предложенных. Параллельно вводится одноразовая миграция существующих установок, которая опознаёт уже созданные «Recent» и «Downloads» по их каноническим признакам и приводит их режим к новому дефолту, не трогая остальные пользовательские настройки этих ресурсов.

### 5.1 Основные столпы / модули

- **Опознавание «Recent».** Канонический признак — фиксированный виртуальный путь, по которому однозначно идентифицируется этот предопределённый ресурс. Других признаков не требуется: имя пользователь мог локализовать или переименовать, путь — стабильный идентификатор.
- **Опознавание «Downloads».** Канонический признак — соответствие пути системной папке «Загрузки» текущего устройства. Любой ресурс типа LOCAL, чей путь совпадает с этим каноническим путём, считается «Downloads» в смысле этой спеки. Дополнительных эвристик (по имени, по флагам) не вводим.
- **Дефолт при создании.** На обоих путях создания (автоматический провижинг и быстрое добавление) для опознанного «Recent»/«Downloads» режим «все файлы» включён сразу. Прочие предопределённые виртуальные («All Music», «All Videos», …) и любые другие локальные ресурсы продолжают создаваться в текущем режиме без изменений.
- **Однократная миграция.** На первом запуске новой версии приложения (для уже установленных пользователей) выполняется проход по существующим ресурсам: для записей, опознанных как «Recent» или «Downloads», выставляется режим «все файлы», после чего факт прохода фиксируется как выполненный, чтобы не повторяться при последующих запусках.
- **Исключения.** Если в редакторе ресурса пользователь после миграции явно вернёт режим «по медиатипам», его выбор не должен переоткрываться повторными прогонами миграции (миграция одноразовая, см. требование идемпотентности).

### 5.2 Потоки данных и событий

Свежая установка: первый запуск → стартовый провижинг предопределённых ресурсов → для «Recent» применяется новый дефолт → быстрый сценарий добавления «Downloads» (если пользователь его выберет) применяет тот же дефолт. Существующая установка: первый запуск новой версии → проверка отметки «миграция S0059 выполнена» → если не выполнена, проход по ресурсам, обновление режима у опознанных «Recent»/«Downloads», запись отметки. UI и сканеры дальше работают со стандартным режимом ресурса — никакой особой ветки кода в путях отображения файлов не требуется, поскольку поведение «все файлы» уже поддерживается на уровне модели ресурса.

### 5.3 Точки расширяемости

- Опознавание «Downloads» сейчас завязано на системную папку «Загрузки»; если в будущем понадобится распространить правило на дополнительные системные папки (например, «Documents» / «DCIM»), таблица опознавания должна быть расширяемой — без изменения миграционной механики.
- Дефолт «все файлы» на этапе создания должен быть сосредоточен в одной точке для каждого пути создания, чтобы при появлении новых предопределённых каталогов список «особых» расширялся декларативно.

## 9. Архитектурные решения (ADR)

**ADR-1: Опознавание по каноническому признаку, а не по специальному маркеру в БД**

- **Решение:** «Recent» опознаётся по фиксированному виртуальному пути, «Downloads» — по соответствию пути системной папке «Загрузки». Никакой новой колонки/флага «is_predefined_recent» не вводится.
- **Альтернативы:** добавить отдельный флаг в записи ресурса, помечающий его как «системный предопределённый», и опираться на него.
- **Почему:** предложенный признак уже стабилен и однозначен, а введение нового поля потребовало бы миграции схемы и согласованного заполнения для всех существующих записей, что несоразмерно цели правки.

**ADR-2: Миграция — одноразовая отметка, а не «каждый раз при запуске»**

- **Решение:** факт прохода миграции для S0059 фиксируется один раз и больше не повторяется, даже если пользователь руками вернул прежний режим.
- **Альтернативы:** «лечащий» прогон при каждом запуске, который догоняет режим до нового дефолта.
- **Почему:** уважение к пользовательскому выбору; «лечащий» прогон создаёт впечатление неотключаемого поведения и противоречит §2.5.

## 11. Критерии готовности (strategic-level)

1. На устройстве с пустой базой после первого запуска предопределённый «Recent» открывается и показывает в том числе нефильтруемые по медиатипам файлы (например, архив или неизвестное расширение, лежащие в наблюдаемых папках, — если они там есть).
2. На устройстве с пустой базой после быстрого добавления «Downloads» содержимое папки «Загрузки» отображается полностью, включая немедийные файлы.
3. На устройстве с уже установленной предыдущей версией приложения, имевшей «Recent» и/или «Downloads» с фильтрацией по медиатипам, после обновления и первого запуска новой версии режим обоих каталогов автоматически переведён на «все файлы». Никакие другие поля этих ресурсов не изменены.
4. Если пользователь после миграции вручную возвращает режим «по медиатипам» в редакторе ресурса, при следующем запуске новой версии настройка остаётся такой, как её выставил пользователь (миграция повторно не срабатывает).
5. Прочие предопределённые виртуальные каталоги («All Music», «All Videos», «All Images», «All Documents», «Camera Photos») и любые пользовательские локальные ресурсы сохраняют прежнее поведение.
6. В логах виден один информационный след для каждого изменённого ресурса при миграции; при последующих запусках след не появляется.
7. Документация фичей обновлена на трёх языках одной короткой строкой согласно §8.
