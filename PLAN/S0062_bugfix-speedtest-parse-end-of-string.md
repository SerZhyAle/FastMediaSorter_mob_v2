> **Scope:** STRATEGIC. Тихий хвостовой баг: speed-тест засоряет E-уровень логов сообщением о неудачной конвертации входной строки, не нарушая функциональность. Фикс **протокол-нейтральный** — затрагивает все типы ресурсов, использующие `NetworkSpeedTestUseCase` (SMB / SFTP / FTP / Cloud / Local).
>
> **Источник бага** в Apache Commons Net FTP-парсере (`FTPClientConfig`/`MLSDListParser`), но классификация ошибок реализована на уровне общего use-case, поэтому защита распространяется на все измеряющие ветки автоматически.

---

## 1. Проблема

При старте сетевой сессии запускается speed-тест, который раз в раз пишет в лог запись уровня ERROR с текстом вида «Speed test error for <ресурс>: Conversion = 'End of String'». Само соединение в этот момент работает, тест не обязателен для пользовательского сценария, но запись уходит в общий E-канал и шумит в диагностике, маскируя реальные ошибки.

Эффект на пользователя: невидим напрямую — тест не используется для решений на uphappy-path, но любая обзорная диагностика через лог показывает «ошибку», которой нет.

---

## 2. Цели

1. Speed-тест не пишет ERROR-запись для штатных ситуаций «нет данных для измерения» или «измерение неполное».
2. Запись «Conversion = 'End of String'» не появляется в логе ни при каких регулярных условиях.
3. При действительно неожиданной ошибке парсинга остаётся одна короткая запись с понятным текстом и контекстом, без stack-trace по умолчанию.

**Non-goals:**

- Не менять методологию измерения скорости.
- Не выводить результаты теста в UI, если они там сейчас не выводятся.

## 4. Контекст текущей архитектуры

Speed-тест — вспомогательный шаг при инициализации источника, отвечает за оценку пропускной способности; результат используется для подсказок UI и/или эвристик планирования операций. На входе он получает результат измерения от транспортного слоя; парсер ожидает определённую форму строки и спотыкается, если строка пустая или обрезанная. Текущая обработка считает любое исключение парсинга «ошибкой ресурса» и пишет ERROR.

`NetworkSpeedTestUseCase` — единая точка входа для всех протоколов. Она содержит ветки `testSmbSpeed / testSftpSpeed / testFtpSpeed / testCloudSpeed / testLocalSpeed`, и **обработчик исключений общий** (`try/catch` на верхнем уровне `runSpeedTest`). Поэтому добавление классификатора «пустое измерение vs реальная ошибка» автоматически покрывает все ресурсы.

---

## 5. Предлагаемый подход

Считать «нет данных» легитимным результатом, а не ошибкой. Парсер возвращает «не удалось измерить» вместо исключения; вызывающий код спокойно опускает значение и продолжает работу. ERROR-канал оставляем только для действительно неожиданных форматов.

### 5.1 Основные столпы / модули

- **Валидатор входа парсера.** Перед попыткой конвертации проверяется форма строки; пустая / только-пробельная / обрезанная строка возвращает «измерение недоступно» без исключения.
- **Канал диагностики.** Регулярные «нет данных» уходят в DEBUG. Действительно неожиданные форматы — одна короткая запись WARNING с фрагментом строки (без полного stack-trace), уровня E не достигают.
- **Поведение потребителя.** Использует «измерение недоступно» как вариант значения, не как ошибку — никаких побочных провалов сценария.

### 5.2 Потоки данных и событий

Транспорт → результат измерения (строка/пусто) → парсер → значение или «недоступно» → потребитель применяет значение или пропускает; никакой записи на ERROR-канале по штатному пути.

### 5.3 Точки расширяемости

Стратегия диагностики (DEBUG/WARN) должна оставаться централизованной, чтобы при изменении правил парсинга поведение по уровням не разъезжалось.

## 6. Открытые вопросы / Research items

1. **Используется ли результат теста где-то ещё кроме логов?**
   - **Вопрос:** влияет ли «измерение недоступно» на эвристики выбора стратегии копирования / стриминга?
   - **Резолюция:** результат записывается в `MediaResource.readSpeedMbps / writeSpeedMbps / recommendedThreads / lastSpeedTestDate` и в `ConnectionThrottleManager` (recommended threads, buffer size, `lastSpeedMbps` для выбора SMBJ tier). При `MeasurementUnavailable` запись **не выполняется** — старые значения сохраняются, дальнейшие операции продолжают использовать прежние эвристики или дефолты. Никакой потребитель не получает «null» вместо числа.
   - **Статус:** Resolved

2. **Покрытие всех протоколов.**
   - **Вопрос:** действительно ли фикс работает для SFTP/Cloud/Local, или только для FTP/SMB?
   - **Резолюция:** `isEmptyMeasurementError` срабатывает на (а) пустом сообщении, (б) `contains "End of String"`, (в) `startsWith "Conversion"`. Эти сигнатуры идут от Apache Commons Net (FTP), но проверка не привязана к типу ресурса — любая будущая реализация измерения, которая бросит exception без сообщения или с этими паттернами, попадёт в DEBUG-канал автоматически.
   - **Статус:** Resolved

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Молчаливое подавление спрячет реальную поломку измерителя | Низкая | Реальные баги остаются незамеченными | Оставить WARNING для аномальных форматов; добавить счётчик «сколько раз подряд получено «недоступно»» — при превышении порога писать WARN |
| Потребитель ожидает число и сломается на «недоступно» | Низкая | Регрессия в зависимом коде | Перед фиксом проверить всех потребителей значения |

## 11. Критерии готовности (strategic-level)

1. ✅ На свежей сессии в логе нет ни одной записи «Conversion = 'End of String'» уровня ERROR — независимо от протокола.
2. ✅ При полностью отсутствующем измерении в логе появляется максимум одна короткая DEBUG-запись или ничего.
3. ✅ Зависимые потребители значения (`MediaResource`, `ConnectionThrottleManager.recommendedThreads/BufferSize/lastSpeedMbps`) работают без исключений в случае «измерение недоступно» — старые значения сохраняются.
4. ✅ При искусственной подмене формата результата на неизвестный — в логе одна короткая WARNING-запись (`Speed test failed for ..`) без stack-trace.
