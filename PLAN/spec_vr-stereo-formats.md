## 1. Проблема

В VR-флейворе приложения два распространённых стереоформата воспроизводятся некорректно.

**VR180 Fisheye SBS (P1-1):** Файлы с суффиксом `3dh` и разрешением типа 7168×3584 детектируются правильно как `VR180_FISHEYE_SBS`, однако рендерятся через equirectangular OpenXR слой без каких-либо предварительных преобразований. Fisheye — это другая оптическая проекция (дуальные круговые линзы, 180° FOV); подавать её на equirect-слой без remapping физически невозможно — пользователь видит полусферу без стереоразделения. В цепочке обработки видео не существует шейдера для коррекции fisheye-дисторсии.

**OU/TAB стерео (P1-2):** Файлы с суффиксами `3dv`, `OU`, `TAB`, `halfOU` детектируются верно как Over-Under, но рендерер явно не поддерживает этот формат и принудительно переключается в режим плоского кино-экрана. Пользователь теряет всё стерео. SBS поддерживается (через UV-смещение в шейдере), OU — нет. Оба типа контента широко распространены на сайтах VR-видео.

---

## 2. Цели

1. VR180 Fisheye SBS контент отображается корректно с правильным стерео: каждый глаз видит свою полусферу без артефактов fisheye-проекции.
2. OU/TAB стерео контент воспроизводится как настоящее стереоскопическое видео, а не как плоский экран.
3. Пользователь не замечает разницы при переключении между SBS и OU файлами — оба формата работают «из коробки».
4. Автоматическая детекция обоих форматов не требует ручного вмешательства пользователя.

Non-goals:

- Поддержка экзотических проекций (cubemap, stereographic, little planet) — вне объёма.
- Конвертация fisheye ↔ equirect офлайн или сохранение перекодированного файла.
- Поддержка half-SBS / half-OU при половинном разрешении каждого кадра — рассматривается отдельно после реализации полного OU.
- Изменения в алгоритме детекции стереоформата по имени файла — это объём `spec_vr-stereo-state`.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Fisheye-коррекция не должна добавлять заметную задержку при старте воспроизведения — GPU-шейдер предпочтительнее CPU-remapping.
2. Для OU контента желателен тот же качественный уровень рендеринга, что и для SBS.
3. Если fisheye-коррекция технически невозможна для конкретного файла (нет метаданных линз), желательна явная диагностика в HUD или тост.
4. Поведение должно быть одинаковым для локальных и сетевых (SMB/FTP/SFTP) источников.

### 3.2 Жёсткие ограничения

- **Flavor:** только `vr`; стандартный, lite, photos, legacy не затрагиваются.
- **API level:** minSdk 26 для VR flavor (фактически Android 14 на Quest 3, API 34); GPU-шейдеры должны работать на OpenGL ES 3.0+.
- **Wear OS:** не затрагивается.
- **Производительность:** fisheye-remapping должен работать в реальном времени на GPU Meta Quest 3 без просадки ниже 72 fps при разрешении 7K.
- **Совместимость данных:** новые типы слоёв и режимы рендеринга не требуют Room-миграции.
- **Локализация:** EN/RU/UK — обязательно для любых новых строк в UI (тост, индикатор формата).
- **Доступность:** не применимо — VR-рендеринг не использует стандартные View-компоненты Android.

## 4. Контекст текущей архитектуры

Слой рендеринга VR построен на нативном OpenXR с Kotlin-оркестровкой. Компонент, отвечающий за выбор типа OpenXR слоя, принимает решение на основе детектированного стерео-режима и возвращает дескриптор слоя: плоский cinema quad, equirectangular 360° или цилиндрический 180°. Поддержка SBS реализована через UV-смещение в вершинном шейдере — левый и правый глаз получают разные UV-координаты из одного видеотекстуры. Для OU смещение по вертикали не реализовано.

Компонент обработки видео (GL-эффекты) применяется до подачи кадра в OpenXR свопчейн. Он поддерживает цепочку эффектов (brightness, HUE, stereo), но для VR180 Fisheye эффект не создаётся — путь "no effect for MONO" вызывается, потому что fisheye не отображён ни на один из известных GL-эффектов. Нет шейдера, который принимает fisheye-кадр и выдаёт equirect-совместимое изображение.

Для OU/TAB существует явная проверка на неподдерживаемый режим, которая сразу возвращает QUAD_CINEMA fallback. Это осознанное техническое решение, которое на момент реализации не имело альтернативы.

## 5. Предлагаемый подход

### 5.1 Основные столпы / модули

**Столп A — Fisheye-to-Equirect GL-эффект**

Для VR180 Fisheye SBS вводится новый этап в цепочке GL-эффектов: fisheye undistortion/remapping. Он получает исходный fisheye-кадр (круговые линзы) и выдаёт изображение в equirectangular проекции, пригодное для подачи на `EQUIRECT_2` слой. Алгоритм remapping параметризуется: FOV линзы, отступ, соотношение сторон. Для SBS-fisheye кадр делится пополам по горизонтали, каждая половина обрабатывается независимо.

**Столп Б — OU/TAB стерео-слой**

Для Over-Under стерео вводится новый маршрут в компоненте выбора слоёв. OU-контент рендерится через соответствующий OpenXR слой (equirect или cinema) с вертикальным UV-смещением по аналогии с горизонтальным смещением для SBS. В OpenXR не существует специального OU-типа слоя — решение реализуется через UV-разбивку в шейдере (верхняя половина текстуры → левый глаз, нижняя → правый). Маршрут учитывает half-OU: когда эффективное разрешение на глаз составляет половину исходного.

**Столп В — Маршрутизация форматов**

Расширяется таблица маршрутизации компонента выбора слоёв: `VR180_FISHEYE_SBS` → equirect + fisheye GL-эффект; `OU` / `HALF_OU` → equirect/cinema + vertical UV-offset. Явные fallback с логированием W-уровня сохраняются для форматов, поддержка которых не реализована.

### 5.2 Потоки данных и событий

```
Компонент детекции стерео → режим (VR180_FISHEYE_SBS | OU)
    ↓
Компонент выбора слоёв
    ├─ VR180_FISHEYE_SBS → EQUIRECT_2 + Fisheye GL-эффект
    └─ OU → EQUIRECT_2 (или CINEMA) + Vertical UV-offset
                ↓
GL-цепочка (fisheye undistort | UV-split)
                ↓
OpenXR Swapchain → левый/правый глаз
```

### 5.3 Точки расширяемости

- GL-эффект fisheye должен быть параметризован (FOV, aspect ratio, crop margin) — это позволит в будущем поддерживать разные производителей камер с разными характеристиками линз.
- Маршрутизация слоёв должна оставаться декларативной таблицей (формат → слой + эффект), чтобы добавление нового формата не требовало изменения логики рендеринга.

## 6. Открытые вопросы / Research items

1. **Параметры fisheye-линзы для VR180 контента**
   - **Вопрос:** Какой именно FOV и модель дисторсии используется в `18VR` и других VR180-камерах? Существует ли метаданный стандарт (Google VR180 spec, `sv3d`/`st3d` box)?
   - **Варианты:** Фиксированные параметры на основе распространённых камер (Canon EOS VR, Insta360 EVO); динамическое чтение из метаданных MP4; пользовательская настройка в диалоге формата.
   - **Нужно выяснить:** Проверить наличие fisheye-параметров в `sv3d`/`st3d` MPEG-4 боксах; изучить спецификацию Google VR180 format.
   - **Статус:** Resolved — принято решение: equidistant 180° FOV как базовые параметры; параметризация шейдера оставлена как точка расширения (см. тактическую спеку).

2. **OpenXR Extension для fisheye-проекции**
   - **Вопрос:** Существует ли XR_FB_composition_layer_depth или аналогичное расширение для native fisheye projection на Meta Quest?
   - **Варианты:** Нативный слой с fisheye-параметрами; GL-remapping в шейдере на стороне приложения.
   - **Нужно выяснить:** Проверить Meta OpenXR SDK release notes и доступные расширения на Quest 3.
   - **Статус:** Resolved — нативного fisheye-расширения нет; выбран GL-remapping (ADR-1).

3. **GPU-производительность fisheye-шейдера на Quest 3**
   - **Вопрос:** Укладывается ли fisheye undistortion для 7K видео (7168×3584) в GPU-бюджет при 72fps?
   - **Варианты:** Per-vertex remapping (быстро, артефакты на границах); per-fragment (точно, дороже); предвычисленная LUT-текстура (компромисс).
   - **Нужно выяснить:** Провести GPU-профилирование на Quest 3 с тестовым шейдером.
   - **Статус:** Open — требует замера на устройстве; реализован per-fragment шейдер. Если FPS просядет — переход на LUT.

4. **OU + equirect 360°: правильный тип слоя**
   - **Вопрос:** Для OU 360° контента (stereo 360 equirect OU) — использовать EQUIRECT_2 с вертикальным UV-split или EQUIRECT_2 с двумя раздельными проходами?
   - **Нужно выяснить:** Проверить OpenXR Multi-view rendering support на Quest 3; изучить XR_KHR_composition_layer_equirect2.
   - **Статус:** Resolved — плоский OU (`StereoMode.OU`) маршрутизируется через PROJECTION-слой с вертикальным UV-split. EQUIRECT_360_OU уже работал через EQUIRECT_2 и не изменён.

## 9. Архитектурные решения (ADR)

**ADR-1: GL-remapping вместо нативного OpenXR расширения для fisheye**

- **Решение:** Fisheye undistortion реализуется как GL-шейдер в приложении, а не через нативное OpenXR расширение.
- **Альтернативы:** Использовать XR_FB_* расширение (если существует); CPU-remapping перед подачей в ExoPlayer.
- **Почему так:** Meta OpenXR SDK не документирует fisheye layer extension на момент написания спеки. CPU-remapping неприемлем по производительности для 7K видео. GL-шейдер даёт полный контроль над параметрами и работает в существующем GL-pipeline.

**ADR-2: OU через вертикальный UV-offset, а не два независимых прохода**

- **Решение:** OU стерео рендерится через вертикальное UV-смещение в существующем шейдере по аналогии с горизонтальным смещением SBS.
- **Альтернативы:** Два независимых render pass (один для каждого глаза с разными текстурными координатами); копирование верхней/нижней половины в две отдельные текстуры.
- **Почему так:** Минимальные изменения в существующем шейдере, нет дополнительных текстур, аналогия с уже работающим SBS путём снижает риск регрессий.

## 11. Критерии готовности (strategic-level)

1. Файл `18VR_.._180x180_3dh.mp4` воспроизводится в VR180 Fisheye SBS режиме с раздельным стерео для каждого глаза без видимых fisheye-артефактов.
2. Файл с суффиксом `3dv` или `OU` воспроизводится в объёмном стерео, а не в режиме плоского кино-экрана.
3. Переключение между SBS- и OU-файлами в рамках одной сессии не требует перезапуска приложения.
4. На Quest 3 не наблюдается устойчивых просадок ниже 72 fps при воспроизведении 7K VR180 fisheye контента.
5. Half-OU контент либо отображается корректно, либо показывает явное предупреждение с указанием причины.
