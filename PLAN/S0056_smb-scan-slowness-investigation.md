## 1. Проблема

В сессии 2026-05-03 03:13:30..03:13:50 встроенный `ScanMetricsRecorder` пометил сканирование SMB-ресурса как «SLOW SCAN»:

```
2026-05-03 03:13:50.325 W/App: ScanMetrics: SLOW SCAN detected — 20091ms
                                  (threshold: 6000ms) resourceId=18 type=SMB
```

20 091 мс — более чем в 3 раза превышает порог в 6 000 мс. На время сканирования пользователь смотрит на пустой/обновляющийся список без явной обратной связи о причине задержки. Параметры сети из того же лога: `networkParallelism=4`, `cacheSizeMb=4096`, активная Wi-Fi сеть `432902426637_wlan0`. SMB-сервер тот же (`192.168.1.110:445`), что и для других ресурсов, которые сканировались за разумное время в этой же сессии.

### 1.1 Что неизвестно

- Сколько файлов в этом ресурсе (resourceId=18) — лог метрики не содержит count.
- Сколько подкаталогов и какова глубина обхода.
- Какая фаза сканирования заняла 20 с: сетевой listing, чтение метаданных, фильтрация по `imageSize*`/`videoSize*`/`audioSize*`, генерация миниатюр.
- Влияет ли `ConnectionThrottle` (`limit=4`) на скорость сканирования (если scanner делит лимит с активной отрисовкой миниатюр).
- Является ли это разовым случаем (сетевая просадка) или воспроизводимым свойством структуры этого ресурса.

## 2. Цели

1. Понять, **что именно** занимает 20 с при сканировании resourceId=18.
2. Зафиксировать в `ScanMetricsRecorder` дополнительные поля (file count, subfolder count, фазы), чтобы будущие SLOW SCAN сразу указывали на узкое место.
3. Если узкое место — реальная сетевая медлительность сервера/сети — задокументировать как «expected behaviour» и добавить пользовательский индикатор прогресса (отдельная спека).
4. Если узкое место — алгоритмическая неэффективность (последовательное вместо параллельного, блокировка throttle) — устранить точечной правкой.

**Non-goals:**

- Не вводить новый кеш листингов/миниатюр (отдельная архитектурная задача).
- Не менять поведение `ConnectionThrottle` глобально.
- Не оптимизировать другие типы ресурсов (LOCAL, FTP, SFTP, Cloud) — фокус только на SMB и только если выявится общая причина.

- **API level:** без изменений.

- **Совместимость данных:** нет.
- **Сеть:** изменения тестируются на типичной локальной сети (Wi-Fi 5 GHz, SMB-сервер на gigabit Ethernet).

## 4. Контекст текущей архитектуры

`ScanMetricsRecorder` (`core/metrics/ScanMetricsRecorder.kt`) фиксирует общее время сканирования по resourceId и тип источника. Сравнивает с конфигурируемым порогом (`SLOW_SCAN_THRESHOLD_MS=6000`). При превышении печатает W-сообщение. Сейчас логирование выводит только итоговое время и тип — без разбиения по фазам, без count, без разбиения по сетевым обращениям.

`ConnectionThrottle` (`core/network/`) ограничивает одновременные SMB-операции через семафор. Лимит `networkParallelism=4` — это и для thumbnail-загрузок в RecyclerView, и (предположительно) для scanner. Если scanner и UI разделяют один семафор, активный скролл во время сканирования может тормозить обе стороны.

SMB-источник реализован через SMBJ (см. `dev/CATALOG/app_v2.md` → SMB модули). Listing директории — отдельный сетевой round-trip, метаданные файлов — ещё один (или несколько, в зависимости от того, читает ли SMBJ их одной операцией). Глубокий обход (recursive listing) для большого ресурса требует N round-trip пропорционально количеству подкаталогов.

## 5. Предлагаемый подход

### 5.1 Этапы работы

**Phase R (Research, обязательная первая):**
Расширить `ScanMetricsRecorder` или временно добавить детальные D-логи на путь сканирования SMB:
- counters: directories visited, files visited, files filtered by size/type;
- timings: разбить общее время на фазы (network listing, metadata fetch, in-memory filtering, persistence);
- per-folder timing: top-5 самых медленных папок ресурса;
- параллелизм: сколько одновременных запросов реально шло в сеть (effective parallelism vs limit).
Воспроизвести SLOW SCAN на том же ресурсе resourceId=18; собрать новые логи.

**Phase D (Decide):**
По результатам Phase R принять одно из:
- **D1.** Сетевая/серверная медлительность подтверждена → закрыть как WONT_FIX-on-app-side; открыть отдельную спеку «индикатор прогресса сканирования + опция отмены» (чтобы у пользователя не создавалось ощущения зависания).
- **D2.** Алгоритмическая проблема (например, последовательное чтение метаданных при наличии параллельного API в SMBJ) → точечный фикс в самом scanner.
- **D3.** Конкуренция за `ConnectionThrottle` между scanner и UI thumbnails → разделить семафоры (отдельный лимит для scanner) или временно отключить thumbnail prefetch во время активного scan.
- **D4.** Большой ресурс с N тысяч файлов — нормально; повысить порог SLOW SCAN до значения, зависящего от размера ресурса.

**Phase F (Fix, опциональная):** только если D2/D3 — точечная правка по итогам Phase D.

### 5.2 Точки расширяемости

- Расширенные поля метрики, добавленные в Phase R, остаются в коде после расследования — будущие SLOW SCAN-предупреждения сразу содержат разбивку.

## 6. Открытые вопросы / Research items

1. **Структура resourceId=18: сколько файлов / подпапок?**
   - **Ответ владельца (2026-05-03):** дерево с глубокой вложенностью с тысячами файлов.
   - **Статус:** BlockNeedUserTest

2. **Эффективный параллелизм SMB scanner**
   - **Ответ (анализ кода 2026-05-03, [SmbDirectoryScanner.kt:55-148](app_v2/src/main/java/com/sza/fastmediasorter/data/network/helpers/SmbDirectoryScanner.kt#L55-L148)):** scanner запускает **отдельную coroutine на каждую подпапку** через `coroutineScope { ... this.launch(smbDispatcher) { recurse } }`. Диспетчер `smbDispatcher = Dispatchers.IO` ([SmbClient.kt:76](app_v2/src/main/java/com/sza/fastmediasorter/data/network/SmbClient.kt#L76)) — IO-пул Kotlin coroutines, размер по умолчанию `max(64, processors)`. Параллелизм ограничен **только серверной стороной** (одновременные запросы к одному `DiskShare`) и пулом IO. Комментарий в коде ([SmbDirectoryScanner.kt:53](app_v2/src/main/java/com/sza/fastmediasorter/data/network/helpers/SmbDirectoryScanner.kt#L53)) подтверждает эмпирически: «2-3x speedup .. 72s -> 20-30s for 62k files». Наша 20-секундная просадка укладывается в этот ожидаемый диапазон.
   - **Статус:** BlockNeedUserTest

3. **Делит ли scanner семафор с UI thumbnail loader?**
   - **Ответ (grep 2026-05-03):** `SmbDirectoryScanner.kt` **не упоминает `ConnectionThrottle`** ни разу. Scanner идёт мимо троттлинга — напрямую через `Dispatchers.IO`. `ConnectionThrottleManager` используется только в UI-путях (`NetworkFileDataFetcher`, ряд вспомогательных мест). То есть scanner **не отнимает слоты у UI**, и наоборот UI с `limit=4` не тормозит scanner. Они идут параллельно по двум разным путям.
   - **Импликация:** D3 («конкуренция за throttle») **отпадает как гипотеза** — она физически невозможна в текущем коде.
   - **Статус:** BlockNeedUserTest

4. **SMBJ — есть ли batch-API для метаданных?**
   - **Ответ (анализ кода 2026-05-03, [SmbDirectoryScanner.kt:80-117](app_v2/src/main/java/com/sza/fastmediasorter/data/network/helpers/SmbDirectoryScanner.kt#L80-L117)):** `share.list(dirPath)` возвращает коллекцию `FileIdBothDirectoryInformation` (или аналог), где **каждый элемент уже содержит `fileName`, `fileAttributes`, `endOfFile` (size), `lastWriteTime`** — всё за **один сетевой round-trip на директорию**. N+1-проблемы нет — scanner не читает метаданные отдельно.
   - **Импликация:** оптимизация «батчинг метаданных» **бессмысленна** — всё уже одним запросом.
   - **Статус:** BlockNeedUserTest

5. **Является ли 20 с воспроизводимым или разовой сетевой просадкой?**
   - **Статус:** BlockNeedUserTest

### 6.1 Сводка после анализа кода (2026-05-03)

Phase R (инструментирование scanner) **частично пропущена**: 4 из 5 вопросов закрыты прямым чтением кода, без дополнительных метрик. Остаётся проверить только Q5 (повторяемость) — это on-device-задача, не блокирующая принятие решения.

**Гипотезы D1–D4 после анализа:**

| Вариант | Применимость | Обоснование |
|---|---|---|
| **D1** — сетевая/протокольная медлительность | **Высоко вероятна** | Дерево с глубокой вложенностью + тысячами файлов = сотни последовательных list()-round-trip. Это структурное свойство SMB1/2 + FindFirst/FindNext паттерн. |
| **D2** — алгоритмическая проблема в коде | **Маловероятна** | Scanner уже параллельный (Q2), без N+1 на метаданных (Q4). Точечной оптимизации ловить негде, кроме «листинг директорий пакетами по N штук» — но это уже изменение SMBJ-протокола. |
| **D3** — конкуренция за `ConnectionThrottle` | **Исключена** | Scanner вообще не использует throttle (Q3). |
| **D4** — большой ресурс → завышенный порог | **Применима** | Текущий `SLOW_SCAN_THRESHOLD_MS=6000` — константа, не зависит от размера ресурса. Для известных «глубоких» ресурсов 6 с физически недостижимы. |

### 6.2 Предлагаемое решение (после анализа кода)

Перейти сразу к Phase F с **комбинацией D1 + D4**:

- **D4 (lightweight):** Сделать `SLOW_SCAN_THRESHOLD_MS` зависимым от количества файлов в ресурсе. Так как модель `MediaResource` **уже содержит** поле `fileCount` (обновляемое при сканировании), дополнительных полей в БД добавлять не нужно. Порог вычислять динамически (`threshold = max(6000, fileCount * 0.4ms)` или подобная эвристика). Это уберёт ложные SLOW SCAN-предупреждения для известных больших ресурсов.
- **D1 follow-up:** открыть отдельную спеку «UI-индикатор прогресса сканирования» — пользователь должен видеть «обработано N из ~M файлов», иначе долгое сканирование выглядит как зависание. Прогресс-callback в scanner уже есть ([SmbDirectoryScanner.kt:60](app_v2/src/main/java/com/sza/fastmediasorter/data/network/helpers/SmbDirectoryScanner.kt#L60) — `progressCallback?.onProgress(results.size)`); нужна UI-привязка.

### 6.3 Что остаётся из Phase R

Расширенные логи `ScanMetricsRecorder` — добавить вывод переданного `fileCount` в `W`-сообщение (в `D`-сообщении оно уже выводится). Добавление per-phase timings по-прежнему полезно для будущих SLOW SCAN-предупреждений из других ресурсов / типов источника. Сохранить в плане как полезный side-quest, не блокирующий D4-фикс.
