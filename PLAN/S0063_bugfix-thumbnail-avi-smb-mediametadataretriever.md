# Стратегическая спецификация: S0063 — Превью AVI и тяжёлых форматов на сетевых ресурсах зря тратят 10 секунд таймаута

**Ticket:** S0063
**Status:** Verified
**Priority:** 20
**Date:** 2026-05-03
**Implemented:** 2026-05-03
**Verified:** 2026-05-03 (code audit — `NetworkThumbnailExtractionPolicy` + `NetworkVideoFrameDecoder.handles()` подтверждены)
**Tier:** 2 — Easy

**Tactical spec:** не создавался — реализация прямая (1 новый файл `NetworkThumbnailExtractionPolicy.kt`, точечная правка `NetworkVideoFrameDecoder.handles()`)
**Related:** S0060 (race превью/playback)

> **Scope:** STRATEGIC. Ускорить отображение списка медиа на **любом сетевом ресурсе** (SMB / SFTP / FTP): не тратить 10 секунд на попытку извлечь миниатюру из контейнеров, для которых системный извлекатель кадров на сетевом стриме заведомо не работает. Решение принимается до выбора конкретного протокола, поэтому одно правило работает для всех `NetworkFileData`.

---

## 1. Проблема

Для AVI-файлов на любом сетевом источнике (SMB, SFTP, FTP) системный извлекатель видео-кадров (`MediaMetadataRetriever.setDataSource(MediaDataSource)`) отказывает практически сразу со статусной ошибкой `0x80000000` (`setDataSourceCallback failed`), но текущий путь превью продолжает удерживать слот таймаута 10 секунд, после чего сообщает о провале и возвращает обобщённый плейсхолдер. Для крупных контейнеров (включая тяжёлые `mkv`) тот же путь срабатывает по таймауту 10 с, потому что чтение через сетевой источник медленное. В обоих случаях пользователь смотрит на пустой/«загружается» миникадр непропорционально долго, а пакетная генерация миниатюр для папки с такими файлами растягивается на десятки секунд впустую.

Эффект на пользователя: список медиа на сетевом ресурсе прокручивается с пустыми/задержанными миникадрами; впечатление «приложение тормозит», хотя на деле процесс заведомо обречён на каждое из этих превью.

---

## 2. Цели

1. Для контейнеров, которые системный извлекатель кадров на сетевом стриме не поддерживает (как минимум AVI), миниатюра не запрашивается у извлекателя — сразу показывается обобщённый плейсхолдер по типу контента.
2. Совокупное время «впустую» (на провальные попытки извлечения для одной видимой страницы списка) сокращается до пренебрежимо малого по сравнению с текущими 10 с на каждый файл.
3. Список миниатюр на SMB-папке с большим количеством AVI / тяжёлых видео загружается ощутимо быстрее с точки зрения пользователя.
4. Лог перестаёт засоряться повторяющимися записями «extraction TIMEOUT after 10000ms», «getFrameAtTime returned null», «Thumbnail load failed: ..» по предсказуемым причинам.

**Non-goals:**

- Не реализовывать собственный декодер для AVI/любого контейнера.
- Не подменять плейсхолдер пользовательскими кадрами через сторонние библиотеки в рамках этого тикета.
- Не оптимизировать общий пайплайн миниатюр сверх минимума, нужного для обхода известных провальных случаев.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Желательно расширяемый список «форматов, которые сразу идут на плейсхолдер на сетевом источнике»: чтобы со временем добавлять туда другие проблемные случаи.
2. Желательно различить плейсхолдер по типу контента (видео/аудио/документ) и при возможности по контейнеру (например, отдельный значок для AVI).
3. Желательно сохранить шанс извлечения миниатюры, если файл локально кэширован (а не стримится с сети).

### 3.2 Жёсткие ограничения

- **Flavor:** все, где видимы списки медиа на сетевых ресурсах (`standard`, `lite`, `legacy`).
- **API level:** без специфики.
- **Wear OS:** не затрагивается (Wear не показывает сетевых превью).
- **Производительность:** цель — снизить нагрузку на пайплайн превью, не повышать.
- **Совместимость данных:** не применимо (плейсхолдеры — внутренние ресурсы).
- **Локализация:** не применимо (плейсхолдеры графические).
- **Доступность:** плейсхолдер должен иметь content-description, отражающий тип файла (например, «видео-файл, миниатюра недоступна»).

## 4. Контекст текущей архитектуры

Слой загрузки миниатюр сейчас единообразно пытается извлечь кадр из видео-файла через системный извлекатель, опираясь на единый таймаут. Для локальных файлов это работает; для сетевых стримов на части контейнеров — заведомо нет. Решения о применимости извлекателя сейчас нет; оно подменено таймаутом.

---

## 5. Предлагаемый подход

Внести в пайплайн превью лёгкое решение «применим ли извлекатель кадров к этому файлу здесь и сейчас». Если решение «нет» — мгновенно отдавать плейсхолдер; если «да» — продолжать как сейчас. Запретный список — параметризованный, начинается с заведомо непроходимых случаев и со временем может расширяться по фактическим наблюдениям.

### 5.1 Основные столпы / модули

- **Политика применимости извлекателя.** Решение основано на: (а) типе источника (локальный файл vs сетевой стрим), (б) контейнере по расширению/MIME, (в) опциональном размере/доступности. Запретный список начинается с AVI на любом сетевом источнике (SMB / SFTP / FTP); локальный AVI допускается.
- **Единая точка истины.** Список «не применимо» живёт в одном объекте (`NetworkThumbnailExtractionPolicy`); проверка вызывается из `NetworkVideoFrameDecoder.handles()` до того, как Glide выберет конкретный протокол.
- **Плейсхолдеры по типу.** Один обобщённый видео-, один аудио-, при возможности — отдельный для AVI и других «тяжёлых» контейнеров. Ресурсы и content-description задаются единообразно.
- **Поведение пакета.** При прокрутке списка решение применяется до постановки в очередь извлечения, чтобы провальные кейсы не занимали слоты таймаута и не вытесняли проходимые задачи.

### 5.2 Потоки данных и событий

Запрос превью → определить источник (локальный/сетевой) и контейнер → проверить политику применимости → если «не применимо», вернуть плейсхолдер мгновенно; иначе — постановка в очередь извлечения как сейчас → результат или fallback на плейсхолдер по таймауту.

### 5.3 Точки расширяемости

- Список «не применимо» должен оставаться открытым для расширения без правки нескольких мест (одна точка истины).
- Возможность будущей замены плейсхолдера на «лёгкое» превью из метаданных файла (длительность/имя), если такая работа появится.

## 9. Архитектурные решения (ADR)

**ADR-1: «Запретный список» в пайплайне превью.**

- **Решение:** ввести явную политику применимости извлекателя кадров с точкой расширения.
- **Альтернативы:** оставить таймаут как есть; пытаться кешировать «провалы» по файлу в течение сессии (текущее частичное поведение через failed-cache).
- **Почему:** мгновенный плейсхолдер по типу/контейнеру даёт ощутимый прирост UX и не имеет негативных последствий, тогда как failed-cache работает только после первой 10-секундной попытки.

## 12. Реализация (2026-05-03)

### Изменённые файлы

| Файл | Изменение |
|------|-----------|
| `data/network/glide/NetworkThumbnailExtractionPolicy.kt` | Новый объект-политика: `BLOCKED_EXTENSIONS = setOf("avi")`, метод `shouldSkipNetworkExtraction(extension)`. Single source of truth для расширений, заведомо проваливающих `MediaMetadataRetriever` на сетевом стриме. |
| `data/network/glide/NetworkVideoFrameDecoder.kt` | В `handles()` вызов `NetworkThumbnailExtractionPolicy.shouldSkipNetworkExtraction(extension)` перед основной проверкой `extension in VIDEO_EXTENSIONS`. Это вызывает Glide-fallback на placeholder адаптера без 10-секундного watchdog. |

### Покрытие по типам ресурсов

| Протокол | Покрыто |
|----------|:-------:|
| SMB | ✅ |
| SFTP | ✅ |
| FTP | ✅ |
| Cloud (Google Drive — отдельный path не через `NetworkVideoFrameDecoder`) | ❌ — out of scope (cloud thumbnails идут через провайдер-нативный path, не через `MediaMetadataRetriever`) |
| Local | ❌ намеренно — извлекатель работает на локальных файлах |

`NetworkVideoFrameDecoder.handles()` вызывается до проверки префикса (`smb://` / `sftp://` / `ftp://`), поэтому одна проверка покрывает все три протокола.

### Расширение списка

Чтобы добавить новый формат — одна правка `BLOCKED_EXTENSIONS` в `NetworkThumbnailExtractionPolicy.kt`. Никаких изменений в `NetworkVideoFrameDecoder` или адаптерах не требуется.
