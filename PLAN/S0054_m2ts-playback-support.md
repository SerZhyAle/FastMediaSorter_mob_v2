## 1. Проблема

Формат `.m2ts` (Blu-ray Transport Stream) уже частично распознаётся приложением — расширение зарегистрировано, MIME-тип определяется, а для сетевых источников (SMB, SFTP, FTP) применяется слой снятия 4-байтового Blu-ray-заголовка с каждого 192-байтного пакета. Однако поддержка неполна: для **локальных файлов** этот слой не задействован, для **облачных источников** — тоже отсутствует. Кроме того, Blu-ray-файлы нередко содержат аудиодорожки в форматах TrueHD, DTS-HD MA и LPCM, которые ExoPlayer не умеет декодировать, — пользователь получает видео без звука без каких-либо пояснений. Наконец, ошибочное сообщение при неудаче воспроизведения адресует пользователя к перекодированию, не поясняя реальную причину.

---

## 2. Цели

1. Локальные `.m2ts`-файлы в Blu-ray BD-TS формате (пакеты 192 байт) воспроизводятся без ошибок на всех поддерживаемых источниках.
2. Облачные `.m2ts`-файлы (Google Drive, OneDrive, Dropbox) также получают BD-TS-слой, если это требуется.
3. Если файл является стандартным MPEG-TS (пакеты 188 байт) с расширением `.m2ts`, он воспроизводится без лишней обработки (авто-детекция формата пакета).
4. При наличии в файле аудиодорожек, которые приложение не может декодировать (TrueHD, DTS-HD MA и т.п.), пользователь видит понятное сообщение с перечнем обнаруженных дорожек, а не безмолвное видео.
5. Функциональность воспроизведения .m2ts покрыта хотя бы одним автоматическим тестом (юнит или интеграция).
6. Сообщение об ошибке для случая, когда файл действительно не может быть воспроизведён с данного источника, точно описывает причину.

**Non-goals:**

- Аппаратное декодирование TrueHD или DTS-HD MA — лицензирование и нативный код вне объёма первой итерации.
- Поддержка `.vob` (DVD) или других контейнеров MPEG-2 TS — отдельная задача.
- Расшифровка зашифрованных BD-дисков (AACS).
- Изменение минимальной версии Android (minSdk остаётся 26/23).

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Автоматически выбирать наилучшую аудиодорожку из тех, что поддаются декодированию (предпочтение: AC-3 → DTS core → AAC → LPCM/PCM → остальные).
2. Показывать в диалоге управления список всех аудиодорожек из контейнера с пометкой, какие недоступны в текущей сборке.
3. Превью-миниатюра для `.m2ts` в браузере — когда файл локальный и ExoPlayer успешно его открыл.

### 3.2 Жёсткие ограничения

- **Flavor:** `standard`, `legacy` (видеоплеер включён); `lite` (видеоплеер включён, но без background-audio); `photos` не затрагивается.
- **API level:** без API-специфики (minSdk 26 standard/lite, minSdk 23 legacy); любые задействованные API должны существовать с API 23.
- **Wear OS:** не затрагивается.
- **Производительность:** слой снятия BD-заголовка не должен добавлять более ~1 мс задержки на 100 МБ потока (уже выполнено в текущей реализации — zero-copy сдвиг в буфере).
- **Совместимость данных:** Room-миграция не требуется — данная фича не затрагивает схему БД.
- **Локализация:** EN/RU/UK — обязательно для всех новых/изменённых строк.
- **Доступность:** новые диалоги и сообщения об ошибках должны быть доступны через TalkBack.

## 4. Контекст текущей архитектуры

Видеоплеер работает поверх ExoPlayer Media3 1.2.1. При воспроизведении файлов с разных источников используются отдельные вспомогательные стратегии (local, SMB, SFTP, FTP, cloud). После code-review подтверждены следующие факты.

**SMB, SFTP, FTP (покрыты):** Каждая стратегия освобождает плеер, затем пересоздаёт ExoPlayer с кастомным media-source factory, оборачивающим BD-TS-слой. BD-TS-слой активируется по расширению файла (`.m2ts`/`.m2t`) — без проверки содержимого первых байт. Логика технически работает для BD-TS файлов, но применение слоя к 188-байтным `.m2ts` файлам сдвинет границы пакетов и сломает воспроизведение.

**LOCAL (не покрыт):** ExoPlayer создаётся один раз через общую точку инициализации без кастомного media-source factory. Воспроизведение инициируется присвоением медиа-элемента уже готовому плееру — BD-TS-слой вставить невозможно без изменения порядка инициализации. Это архитектурная несовместимость: сетевые стратегии обходят её пересозданием плеера, но LOCAL-путь этого не делает. При ошибке ExoPlayer на local-пути код уже пробует MediaPlayer как fallback (ряд OEM-прошивок поддерживает BD-TS напрямую), однако это непредсказуемо и не является надёжным решением.

**Cloud (не покрыт):** Пересоздаёт ExoPlayer с кастомным облачным data-source factory, но без BD-TS-слоя. Облачный URI содержит имя файла с расширением — extension check бесплатно доступен без дополнительных HTTP-запросов.

**Детекция формата:** Функция BD-TS-обёртки проверяет только расширение файла. Проверки первых байт нет. Следствие: любой 188-байтный `.m2ts` на SMB/SFTP/FTP уже сейчас воспроизводится с ошибкой.

**Обработка ошибок:** При ошибке ExoPlayer на сетевом `.m2ts`/`.m2t` показывается специальный диалог. Текущие строки во всех трёх языках содержат фразу «с этого сетевого ресурса» — некорректно для local и cloud сценариев.

**Аудиодорожки:** Хук отслеживания изменений дорожек существует, но используется только для stereo detection — анализа кодеков аудиодорожек нет. FFmpeg AAR подключён в `standard`/`legacy` (обеспечивает DTS core), в `lite` — нет. TrueHD, DTS-HD MA, LPCM в TS не декодируются ни в одном flavor.

**Покрытие тестами BD-TS стека:** тестов нет — ни для DataSource-слоя, ни для extension/byte logic, ни для local/cloud путей.

## 5. Предлагаемый подход

### 5.1 Основные столпы / модули

**А. Авто-детектор формата пакета TS**
Читает первые ~200 байт файла (или потока) и определяет: стандартный 188-байтный MPEG-TS или Blu-ray 192-байтный BD-TS. Результат — перечисление с тремя состояниями: стандартный 188-байтный, BD 192-байтный, неизвестный. Используется как локальными, так и всеми сетевыми/облачными стратегиями воспроизведения.

**Б. Унифицированное применение BD-TS-слоя**
Логика BD-TS-обёртки перерабатывается: вместо безусловного применения по расширению файла используется результат детектора из п. А. Таким образом, слой активируется только когда это действительно нужно, независимо от источника.

**В. Поддержка локального и облачного воспроизведения**
Стратегии воспроизведения для локальных файлов и облачных источников получают ту же BD-TS-проверку, что уже есть в SMB/SFTP/FTP. Для облачных источников детектор опирается на первые несколько байт, скачиваемых через существующий потоковый механизм.

**Г. Уточнённая диагностика аудиодорожек**
После успешного старта воспроизведения слой отслеживания дорожек анализирует, есть ли в контейнере аудиодорожки, которые проигрыватель не способен декодировать в текущей сборке. Если все доступные аудиодорожки неподдерживаемы — показывается однократный toast/snackbar с перечнем форматов и советом выбрать другую дорожку или перекодировать. Если есть хотя бы одна поддерживаемая дорожка — она выбирается автоматически.

**Д. Исправление строк ошибок**
Существующие строки `error_bdts_format_*` приводятся в соответствие с реальным сценарием: сообщение теперь объясняет, что конкретно не так (неподдерживаемый аудиоформат, недоступный источник и т.д.), а не просто предлагает перекодировать.

### 5.2 Потоки данных и событий

```
Запрос воспроизведения .m2ts
  → Определение источника (local / SMB / SFTP / FTP / cloud)
  → Детектор формата пакета: чтение первых ~200 байт upstream
      → BD-TS (192): оборачиваем data-source factory в BD-TS-слой
      → Standard (188): data-source factory без изменений
  → ExoPlayer: TS-демультиплексор разбирает стандартный 188-байтный поток
  → отслеживание дорожек: анализ аудиодорожек
      → Найдена поддерживаемая дорожка → выбор автоматически
      → Все дорожки неподдерживаемы → уведомление пользователя
  → Воспроизведение
```

### 5.3 Точки расширяемости

- Детектор формата пакета должен принимать произвольный массив байт — это позволит подключить его в тестах без реального файла.
- Логика выбора аудиодорожки должна быть отдельной стратегией с возможностью расширения (например, добавить LPCM downmix в будущем).

## 6. Открытые вопросы / Research items

1. **Формат пакета `.m2ts`: всегда ли BD-TS?**
   - **Вопрос:** Может ли файл с расширением `.m2ts` быть стандартным 188-байтным MPEG-TS?
   - **Исследование:** Ряд перекодировщиков (ffmpeg, MKVToolNix) сохраняет `.m2ts` как plain MPEG-TS. Расширение не гарантирует BD-TS. Текущий `wrapForBdTs` применяет слой безусловно по расширению — это уже сейчас потенциально ломает 188-байтные `.m2ts` на SMB/SFTP/FTP.
   - **Вывод:** Byte-level детектор необходим. Sync-байт 0x47 в позиции 0 → 188 байт; в позиции 4 → 192 байт. Проверять 3–5 последовательных пакетов от начала файла.
   - **Статус:** Закрыт — детектор реализовать обязательно.

2. **Детектор на облачном источнике: способ применения**
   - **Вопрос:** Нужно ли читать первые ~200 байт из cloud-источника или достаточно проверки расширения?
   - **Исследование:** Облачный URI содержит расширение файла в пути (`cloud://provider/folderId/file.m2ts`) — extension check бесплатно доступен без HTTP-запросов. Byte detection потребует дополнительного round-trip ~200 байт на старте.
   - **Варианты:** (a) extension → byte detection через мини-запрос для облака (детерминировано); (b) для cloud применять BD-TS-слой всегда по расширению без byte detection (проще, приемлемо если 188-байтный `.m2ts` на облаке — теоретический сценарий).
   - **Статус:** Открыт — ожидает решения по варианту (a) vs (b).

3. **TrueHD / DTS-HD MA / LPCM в ExoPlayer 1.2.1**
   - **Вопрос:** Как именно ведёт себя ExoPlayer при воспроизведении `.m2ts` с TrueHD или DTS-HD MA-only дорожками — silent skip или ошибка?
   - **Исследование:** Подтверждено по коду: FFmpeg AAR добавляет DTS core; AC-3, E-AC-3 — нативно. TrueHD и DTS-HD MA не реализованы ни в нативном ExoPlayer 1.2.1, ни в текущем FFmpeg AAR. Точное поведение на реальных файлах не тестировалось.
   - **Статус:** Открыт — требуется тест на реальных файлах с TrueHD/DTS-HD MA-only дорожками.

4. **Порядок выбора аудиодорожки при нескольких вариантах**
   - **Вопрос:** Какой приоритет дорожкам при выборе? E-AC-3 vs AC-3 vs DTS core? Учитывать пользовательский язык?
   - **Варианты:** жёстко прописанный приоритет по кодеку; или авто-выбор ExoPlayer с фильтрацией только заведомо неподдерживаемых кодеков.
   - **Статус:** Открыт.

5. **Архитектура LOCAL-пути: как вставить BD-TS-слой**
   - **Вопрос:** Текущая точка инициализации плеера создаёт ExoPlayer без кастомного media-source factory. Сетевые стратегии обходят это через освобождение плеера + пересоздание ExoPlayer. Для LOCAL-пути такой точки входа нет.
   - **Варианты:** (a) для local `.m2ts` — условное освобождение и пересоздание плеера с кастомным factory (по образцу SMB/SFTP/FTP); (b) добавить опциональный параметр data-source factory в точку инициализации плеера; (c) оставить существующий MediaPlayer fallback (непредсказуем).
   - **Статус:** Открыт — ожидает архитектурного решения.

6. **MediaPlayer fallback и `.m2ts` на local-пути**
   - **Вопрос:** Текущий код уже пробует MediaPlayer при ошибке ExoPlayer на local-пути. На ряде OEM-устройств MediaPlayer поддерживает BD-TS через системный декодер. Сохранить ли этот fallback или явно отключить в пользу детерминированного BD-TS-слоя?
   - **Варианты:** (a) сохранить fallback как последний шанс после нашего BD-TS-слоя; (b) отключить для `.m2ts` — наш слой должен решать задачу без непредсказуемого поведения.
   - **Статус:** Открыт.

## 9. Архитектурные решения (ADR)

**ADR-1: Авто-детекция формата TS вместо жёсткой привязки к расширению**

- **Решение:** Читать первые несколько пакетов файла и определять формат по позиции sync-байта 0x47 (позиция 0 → 188 байт; позиция 4 → 192 байт).
- **Альтернативы:** Всегда применять BD-TS-слой для `.m2ts` и не проверять.
- **Почему:** Безусловный слой сломает файлы `.m2ts`, которые не являются BD-TS. Детектор делает решение надёжным и расширяемым (`.mts`, `.ts` тоже могут быть BD-TS в теории).

**ADR-2: Не пытаться добавить TrueHD/DTS-HD MA декодирование в первой итерации**

- **Решение:** Диагностировать неподдерживаемые дорожки и сообщать об этом, но не декодировать.
- **Альтернативы:** Встроить TrueHD через FFmpeg в custom AAR.
- **Почему:** TrueHD требует нетривиальной сборки FFmpeg с дополнительными патчами, лицензионных рисков нет, но трудоёмкость высокая. Ценность для первой итерации несоразмерна усилиям — большинство Blu-ray-рипов содержат также AC-3 или E-AC-3 дорожку как резервную.

## 10. Связи с другими спеками

- Зависит от существующего компонента BD-TS-стриппинга (уже в коде, не тикет).
- Смежная задача — тикет на кастомный FFmpeg AAR для DTS (уже реализован в `standard`/`legacy` флейворах в виде отдельного расширения).
- Связей с другими активными спеками нет.

---

## 11. Критерии готовности (strategic-level)

1. Пользователь открывает локальный `.m2ts` файл (Blu-ray-рип) — видео воспроизводится без ошибок.
2. Пользователь открывает тот же файл через SMB, SFTP, FTP — результат аналогичен.
3. Пользователь открывает `.m2ts` через Google Drive / OneDrive / Dropbox — воспроизведение начинается или показывается понятная ошибка (не молчаливое зависание).
4. Файл `.m2ts` с расширением, но стандартными 188-байтными пакетами (plain MPEG-TS), воспроизводится корректно (слой не применяется).
5. Файл `.m2ts` с только TrueHD-дорожкой показывает предупреждение «аудиодорожка не поддерживается» вместо беззвучного воспроизведения.
6. Файл `.m2ts` с AC-3 и TrueHD дорожками воспроизводится со звуком (AC-3 выбрана автоматически).
7. Все три языка (EN/RU/UK) содержат корректные строки для новых сообщений.
