## 1. Проблема

При включённом постоянном аудио (`enablePersistentAudio=true`) приложение сохраняет путь к последнему воспроизводимому файлу. Если этот файл находится в подпапке ресурса (например, `Music/subfolder/track.mp3`), при следующем старте приложение восстанавливает путь к файлу, но кэш списка файлов построен для корневой директории ресурса, а не для подпапки. Слой восстановления не находит файл в кэше и выводит предупреждение `subfolder mismatch`, после чего инициирует полную перезагрузку корневой директории. Проблема воспроизводится на каждом старте приложения в течение одного дня в трёх разных сессиях с одним и тем же файлом (`radiohead_present_tense.mp3` в папке `Music`).

---

## 2. Цели

1. При восстановлении позиции воспроизведения из постоянного хранилища — если файл находится в подпапке ресурса — инициальная загрузка открывается прямо в этой подпапке, а не в корне ресурса.
2. Предупреждение `Cache does not contain initialFilePath … (subfolder mismatch)` перестаёт появляться в штатных сценариях.
3. Холодный старт приложения не запускает избыточное сканирование корневой директории, когда последний воспроизводимый файл известен и его подпапка существует.
4. Если подпапка была удалена между сессиями — graceful fallback к корневой директории ресурса без ошибки.

**Non-goals:**

- Изменение структуры кэша файлового списка или способа его персистирования.
- Оптимизация самого сканирования директорий (это область S0056 и смежных тикетов).
- Изменение поведения для ресурсов без подпапок или при отключённом `enablePersistentAudio`.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Решение не должно увеличивать время первого рендера — восстановление подпапки должно происходить синхронно с уже существующим flow инициализации.
2. Логика fallback (файл удалён, подпапка недоступна) должна быть прозрачной для пользователя — без диалогов, только тихий переход к корню.

### 3.2 Жёсткие ограничения

- **Flavor:** `standard`, `lite`, `photos`, `legacy` — постоянное аудио поддерживается во всех флейворах.
- **API level:** minSdk 26 (legacy minSdk 23) — без зависимости от API-специфики.
- **Wear OS:** не затрагивается.
- **Производительность:** восстановление подпапки не должно добавлять дополнительных сетевых запросов или disk I/O на старте.
- **Совместимость данных:** формат сохранённого пути в постоянном хранилище не меняется — только логика его интерпретации при восстановлении.
- **Локализация:** нет изменений в пользовательских строках; изменений в EN/RU/UK не требуется.
- **Доступность:** не затрагивается.

## 4. Контекст текущей архитектуры

Функция «последняя позиция» реализована в слое browse/loading: при старте ViewModel запрашивает сохранённый путь к файлу и передаёт его в компонент загрузки списка как `initialFilePath`. Компонент загрузки проверяет, содержит ли текущий кэш этот путь. Кэш индексируется по корневому пути ресурса; файлы из подпапок присутствуют в кэше только если он был построен с рекурсивным обходом. Если корневой кэш существует, но `initialFilePath` ведёт в подпапку — проверка возвращает «не найдено», и запускается полная перезагрузка.

Проблема в том, что при проверке кэша не учитывается, что `initialFilePath` может находиться в подпапке кэшированного корня. Вместо логики «спуститься к нужной подпапке» или «запросить кэш подпапки» всегда выбирается перезагрузка.

---

## 5. Предлагаемый подход

При восстановлении `initialFilePath` извлекать путь к родительской директории файла. Если этот путь является подпапкой текущего ресурса — использовать его как стартовый путь для загрузки, а не корень ресурса. Кэш при этом запрашивается для подпапки напрямую.

### 5.1 Основные столпы / модули

**A. Извлечение родительской директории из восстановленного пути**
Из сохранённого `initialFilePath` вычисляется путь родительской директории. Это делается один раз при инициализации; результат передаётся в слой загрузки как начальный scope.

**B. Логика выбора стартовой директории**
Если вычисленная родительская директория отличается от корня ресурса — использовать её как `startDirectory` при начальной загрузке. Если совпадает (файл в корне) — поведение остаётся прежним.

**C. Fallback при недоступности подпапки**
Если при попытке загрузки стартовой директории она не найдена (удалена, переименована, нет доступа) — тихий fallback к корню ресурса. Сохранённый `initialFilePath` при этом не сбрасывается (файл может появиться снова).

### 5.2 Потоки данных и событий

```
Persistent store → initialFilePath
    ↓
Вычисление parentDir из initialFilePath
    ↓
parentDir == resourceRoot?
    Да → загрузка как раньше (корень ресурса)
    Нет → загрузка с parentDir как startDirectory
              ↓ (ошибка доступа)
          fallback → корень ресурса
```

### 5.3 Точки расширяемости

- Логика вычисления `startDirectory` из `initialFilePath` должна быть изолирована — в будущем её можно расширить для сохранения полной цепочки breadcrumb навигации.

## 6. Открытые вопросы / Research items

1. **Глубина подпапки**
   - **Вопрос:** проблема проявляется только для одного уровня вложенности, или `initialFilePath` может указывать на файл в глубоко вложенной директории (`A/B/C/file.mp3`)?
   - **Нужно выяснить:** проверить логику формирования кэша — сохраняется ли `startDirectory` при переходе в подпапку, или только путь к файлу.
   - **Статус:** Verified

2. **Взаимодействие с рекурсивным сканированием**
   - **Вопрос:** если у ресурса включено рекурсивное сканирование — кэш строится для корня и содержит файлы подпапок; тогда `subfolder mismatch` не должен возникать. Воспроизводится ли баг только при отключённом рекурсивном сканировании?
   - **Нужно выяснить:** настройки ресурса «All Music» в тестовом устройстве (лог не содержит эту информацию).
   - **Статус:** Verified

## 9. Архитектурные решения (ADR)

**ADR-1: Хранить `parentDir` или вычислять на лету?**

- **Решение:** вычислять `parentDir` из `initialFilePath` при восстановлении — не сохранять отдельно.
- **Альтернативы:** сохранять `lastBrowseDirectory` вместе с `lastFilePath` в постоянном хранилище.
- **Почему:** изменение формата хранилища потребует миграции и увеличивает риск регрессии; вычисление `parentDir` — детерминировано и не требует схемных изменений.
