## 1. Проблема

VR-ввод и маршрутизация воспроизведения страдают от нескольких самостоятельных, но однотипных дефектов надёжности. Каждый из них уменьшает доверие пользователя к управлению.

**Уничтожение XR-сессии при 2D-контенте (P2-3):** Когда пользователь доходит в навигации до 2D-файла (обычное кино), приложение разрушает XR-сессию и запускает стандартный плеер. Пользователь неожиданно «вылетает» из VR. Ожидаемое поведение — Cinema mode (плоский экран на виртуальном кино-экране) без выхода из иммерсива.

**Многократное срабатывание ввода (P2-4, P3-4):** Одно нажатие trigger генерирует 3 команды переключения воспроизведения за 2 секунды. Аналогично команда открытия файла срабатывает 3 раза подряд без визуального фидбэка. Причина — отсутствие дебаунса на VR-команды.

**Хаптик-фидбэк не работает (P2-6):** При каждой команде, которая должна давать вибрацию, возвращается ошибка `-16` (XR_ERROR_FEATURE_UNSUPPORTED). Контроллеры не вибрируют при нажатиях.

**Игнорирование смены профиля контроллера (P3-1):** При каждой XR-сессии фиксируется необработанное событие смены профиля взаимодействия (тип 52). Переключение с контроллеров на hand tracking и обратно не перестраивает input bindings.

**Race condition HUD при выходе из иммерсива (P3-2):** При завершении XR-сессии рендерер HUD пытается создать swapchain после того, как сессия уже уничтожена. Это приводит к серии предупреждений и потенциально к нестабильному состоянию.

**Шум Touch Pro Controller (P3-3):** При каждой инициализации XR в лог пишутся 6 предупреждений о неудачной регистрации профиля Touch Pro Controller, которого нет на Quest 3.

## 2. Цели

1. 2D-контент воспроизводится в Cinema mode (плоский виртуальный экран) внутри VR без разрушения XR-сессии.
2. Каждая команда контроллера срабатывает ровно один раз независимо от длительности удержания кнопки.
3. Хаптик-фидбэк работает на Quest 3 при нажатии кнопок контроллера.
4. Переключение между режимами контроллеров (Touch ↔ Hand tracking) обрабатывается без потери ввода.
5. При выходе из иммерсива не возникает ошибок swapchain и гонок состояния.
6. Лог при штатной инициализации XR не содержит W-уровня предупреждений о Touch Pro.

Non-goals:

- Полная поддержка hand tracking с лучами и микрожестами — объём `spec_vr-hand-tracking` и `spec_vr-immersive-controls-panel`.
- Новые типы команд (seek, track selection) — объём `spec_vr-immersive-controls-panel`.
- SMB connection pooling и watchdog fixes (P2-5) — отдельная задача в сетевом слое, не специфична для VR.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Cinema mode для 2D в VR должен быть автоматическим (без явного включения пользователем) при навигации в иммерсиве.
2. Дебаунс не должен быть заметным — команда применяется немедленно при первом событии, повторные игнорируются в течение окна.
3. Хаптик должен соответствовать типу действия: лёгкий импульс при навигации, более долгий при ошибке.
4. Touch Pro warning желательно полностью убрать из лога, а не просто понизить уровень — если профиль заведомо не поддерживается, регистрировать его не нужно.

### 3.2 Жёсткие ограничения

- **Flavor:** только `vr`; изменения не затрагивают стандартный/lite/photos/legacy флейворы.
- **API level:** без Android API-специфики; OpenXR API на Quest 3 (Horizon OS, Android 14).
- **Wear OS:** не затрагивается.
- **Производительность:** дебаунс реализуется на стороне ввода (нативный уровень или Kotlin), не добавляет задержки > 50ms к первому событию.
- **Совместимость данных:** изменений в Room-схеме не требуется.
- **Локализация:** новых пользовательских строк не планируется; если появится тост «Cinema mode» — EN/RU/UK обязательно.
- **Доступность:** не применимо.

## 4. Контекст текущей архитектуры

Компонент маршрутизации воспроизведения принимает решение: запустить иммерсивный XR-плеер или стандартный Android-плеер. Для MONO/2D контента текущая логика возвращает `STANDARD_PANEL_FALLBACK`, что немедленно вызывает завершение XR-сессии и запуск стандартного плеера. Cinema mode (`QUAD_CINEMA` layer) существует в кодовой базе, но не используется как автоматический fallback для 2D.

Обработка VR-команд (тип → действие) происходит в компоненте VR-плеера как прямой dispatch без какого-либо дебаунса. События от OpenXR контроллеров поступают в нативный callback и передаются в Kotlin через JNI. Trigger-нажатие генерирует несколько событий при удержании кнопки — это нормальное поведение OpenXR, которое требует программной фильтрации.

Хаптик-система создаёт OpenXR Haptic action, но action path указан неверно или handle не инициализирован корректно — `xrApplyHapticFeedback` возвращает -16 (XR_ERROR_FEATURE_UNSUPPORTED). Это означает, что action не привязан к правильному haptic output path для Touch контроллеров Quest 3.

`pollEvents` в нативном слое обрабатывает несколько типов XR-событий, но тип 52 (`XR_TYPE_EVENT_DATA_INTERACTION_PROFILE_CHANGED`) не имеет обработчика. Реакция на смену профиля необходима для корректного rebinding при переключении контроллеры ↔ руки.

Рендерер HUD получает вызовы на управление видимостью и создание swapchain через Kotlin-callback. При выходе из иммерсива XR-сессия освобождается нативно, после чего Kotlin-код продолжает вызывать методы HUD — ссылка на XR-сессию к этому моменту уже невалидна.

## 5. Предлагаемый подход

### 5.1 Основные столпы / модули

#### Столп A — Cinema Fallback для 2D контента

Маршрутизатор воспроизведения получает новый путь: вместо `STANDARD_PANEL_FALLBACK` для MONO/2D контента возвращается `CINEMA_QUAD_IMMERSIVE`. XR-сессия не уничтожается; файл открывается в `QUAD_CINEMA` layer (плоский экран в VR). Переключение происходит прозрачно для пользователя — видеопоток перезапускается в новом режиме слоя без выхода из VR.

Отдельно: в файловом браузере или контекстном меню появляется опция «Открыть в VR Cinema» для 2D-файлов — чтобы пользователь мог явно выбрать режим. Автоматический CINEMA при навигации включается по умолчанию, но может быть отключён в настройках VR.

#### Столп Б — Дебаунс VR-команд

Вводится единый центральный дебаунсер для VR-команд. Каждая команда имеет настраиваемое окно подавления (по умолчанию 500 ms для toggle-команд, 200 ms для навигационных). При поступлении команды в течение окна она отбрасывается без выполнения. Дебаунс применяется до передачи команды в компонент VR-плеера — в одном месте, а не в каждом обработчике.

#### Столп В — Исправление хаптик action path

OpenXR Haptic action корректно инициализируется с правильным path для Touch контроллеров Quest 3: `/user/hand/left/output/haptic` и `/user/hand/right/output/haptic`. Action создаётся в том же `ActionSet`, что и остальные input actions. Интенсивность и длительность вибрации параметризуются по типу команды.

#### Столп Г — Обработка INTERACTION_PROFILE_CHANGED

В `pollEvents` добавляется обработчик для типа 52. При получении события: получить текущий active interaction profile через `xrGetCurrentInteractionProfile`; если профиль изменился (контроллеры → руки или наоборот) — обновить состояние input system, логировать смену. Это предотвращает потерю ввода при переключении режима взаимодействия.

#### Столп Д — Lifecycle guard для VrHudRenderer

Рендерер HUD получает lifecycle token от XR-сессии. Все операции с swapchain (create, update, destroy) проверяют валидность токена перед выполнением. После завершения XR-сессии токен инвалидируется; последующие вызовы на видимость и создание swapchain немедленно возвращают false без попытки обратиться к уже уничтоженной сессии.

#### Столп Е — Подавление Touch Pro warning

Регистрация bindings для `touch_pro_controller` профиля ограничивается проверкой наличия расширения или runtime capability перед попыткой регистрации. Если профиль заведомо не поддерживается устройством — регистрация пропускается полностью (без попытки, без warning). Если runtime не позволяет определить поддержку заранее — уровень логирования понижается с W до D.

### 5.2 Потоки данных и событий

```text
OpenXR Native Event (тип 52, INTERACTION_PROFILE_CHANGED)
    ↓
pollEvents → обработчик типа 52
    ↓
xrGetCurrentInteractionProfile → новый профиль
    ↓
Input System: rebind actions для нового профиля

---

Trigger Press Event (нативный callback)
    ↓
VR Command Debouncer
    ├─ в окне дебаунса → отброшена
    └─ первое событие → dispatch
              ↓
        VR-плеер → действие + хаптик
              ↓
        xrApplyHapticFeedback (исправленный path)

---

nextFile() → MONO/2D файл
    ↓
resolvePlaybackRoute → CINEMA_QUAD_IMMERSIVE (не STANDARD_PANEL_FALLBACK)
    ↓
VrPlayerActivity: переключить layer type → QUAD_CINEMA
    (XR-сессия не уничтожается)

---

ToggleImmersiveMode / Exit
    ↓
менеджер XR-сессии: release() → токен инвалидируется
    ↓
рендерер HUD: setVisible() → проверка токена → noop (не crash)
```

### 5.3 Точки расширяемости

- Дебаунсер должен поддерживать конфигурируемые окна per-команда — будущие команды (seek) могут требовать другой длительности окна.
- Cinema fallback должен быть управляем настройкой «автоматически открывать 2D в Cinema» — пользователь может предпочитать старое поведение (выход в стандартный плеер).
- Lifecycle guard токен — общий паттерн, который может быть применён к другим нативным рендерерам VR (если появятся).

## 6. Открытые вопросы / Research items

1. **Хаптик action path для Quest 3**
   - **Вопрос:** Какой именно action path и interaction profile нужны для Touch controller haptic на Quest 3? Документация Meta указывает `/user/hand/*/output/haptic`, но возможны нюансы с ActionSet binding.
   - **Нужно выяснить:** Проверить Meta OpenXR Samples для haptic setup; сравнить с текущим кодом `setupActionSet`.
   - **Статус:** Resolved — Quest 3 использует профиль `meta/touch_plus_controller`; добавлен в `setupActionSet()` в Phase 03.

2. **Cinema mode для 2D: автоматический vs явный**
   - **Вопрос:** Должен ли 2D-файл автоматически открываться в Cinema без запроса, или показывать диалог «Открыть в VR Cinema или в обычном плеере?»
   - **Варианты:** Автоматически всегда; автоматически с тостом «Cinema mode»; диалог при первом случае; настройка в VR Settings.
   - **Нужно выяснить:** Уточнить у пользователя предпочтение UX.
   - **Статус:** Resolved — автоматически, без запроса (пожелание владельца §3.1.1); реализовано в Phase 01.

3. **Дебаунс для непрерывных команд (VolumeUp/Down)**
   - **Вопрос:** VolumeUp/VolumeDown при удержании должны повторяться (auto-repeat) или только один раз? Дебаунс должен их блокировать или нет?
   - **Варианты:** Дебаунс только для toggle-команд; все команды дебаунсируются; auto-repeat для volume с разумным интервалом.
   - **Нужно выяснить:** Определить ожидаемое поведение для каждого типа команды.
   - **Статус:** Resolved — Volume/Zoom уже ограничены rate-limit (150ms/120ms) в `VrControllerInputManager`; новый дебаунс применяется только к toggle-командам (500ms) и навигационным (300ms). Phase 02.

## 9. Архитектурные решения (ADR)

### ADR-1: Cinema как новый маршрут, а не patch STANDARD_PANEL_FALLBACK

- **Решение:** Вводится отдельный маршрут `CINEMA_QUAD_IMMERSIVE` в перечислении маршрутов воспроизведения. `STANDARD_PANEL_FALLBACK` остаётся, но используется только при явном запросе пользователя (кнопка «Открыть в стандартном плеере»).
- **Альтернативы:** Патч `STANDARD_PANEL_FALLBACK` с проверкой «мы внутри XR-сессии → не выходить»; новый boolean флаг «forceImmersive».
- **Почему так:** Явный маршрут делает намерение понятным; не ломает существующую логику `STANDARD_PANEL_FALLBACK` для контекстов вне иммерсива.

### ADR-2: Lifecycle guard через invalidatable token, а не weak reference

- **Решение:** Для защиты от race condition используется явный токен (атомарный флаг или версионный счётчик), который инвалидируется при `release()`, а не weak reference на сессию.
- **Альтернативы:** Weak reference на сессию (проверка `null` перед вызовом); synchronized block вокруг create/release.
- **Почему так:** Weak reference может не собраться GC вовремя; synchronized block вводит lock contention между нативным потоком и Kotlin. Token — самый лёгкий и явный подход.

### ADR-3: Централизованный дебаунсер, а не per-command guard

- **Решение:** Единый компонент дебаунса обрабатывает все VR-команды с конфигурируемым per-type окном.
- **Альтернативы:** Отдельный дебаунс в каждом обработчике команды; дебаунс в нативном коде.
- **Почему так:** Один компонент проще тестировать и поддерживать; нативный код уже сложный, добавлять туда дополнительную логику нежелательно.

## 11. Критерии готовности (strategic-level)

1. Навигация к 2D-файлу в иммерсиве открывает его в QUAD_CINEMA без разрушения XR-сессии и без «вылета» в стандартный плеер.
2. Одно нажатие trigger генерирует ровно одну команду переключения воспроизведения; повторные нажатия в течение 500ms игнорируются.
3. Контроллеры Quest 3 вибрируют при нажатии кнопок (хаптик-фидбэк работает).
4. Переключение между контроллером и hand tracking не прерывает ввод.
5. При выходе из иммерсива в лог не пишутся W-уровня ошибки swapchain.
6. Лог инициализации XR не содержит W-уровня предупреждений о Touch Pro Controller.
