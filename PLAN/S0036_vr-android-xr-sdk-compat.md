## 1. Проблема

Сборка `vr` при запуске на **Android XR SDK** (x86\_64, API 34, Google XR-платформа) показывает чёрный прямоугольник вместо содержимого настроек и пересоздаёт `SettingsActivity` трижды за ~11 секунд. Системный компонент `EmbeddingMixedHandler` фиксирует `No WindowHierarchyInfo found` при каждом закрытии Activity, а поле `xrDesktopMode` остаётся `undefined` — признак того, что приложение не объявляет свои намерения относительно XR desktop-режима. Совокупность этих факторов делает навигацию по приложению практически невозможной: вместо содержимого экрана пользователь видит только строку вкладок и нижний колонтитул.

> **Контекст платформы.** Android XR SDK (Google) — отдельная платформа от Meta Quest. Приложение ранее тестировалось и стабилизировалось на Meta Quest 3; задачи для Quest 3 ведутся отдельно (S0014, S0026 и др.). Данная спека покрывает только Android XR SDK.

---

## 2. Цели

1. Устранить многократное пересоздание экрана настроек при запуске на Android XR SDK — экран должен создаваться ровно один раз.
2. Содержимое всех вкладок настроек должно отображаться корректно, без чёрных областей.
3. Поле `xrDesktopMode` в XR-окружении должно принимать определённое значение вместо `undefined`.
4. Ошибки `EmbeddingMixedHandler` и `Failed to open rendernode` должны исчезнуть либо быть идентифицированы как неустранимые системные предупреждения, не влияющие на UX.
5. Приложение должно корректно реагировать на конфигурационные изменения, специфичные для XR-среды (изменение геометрии виртуального окна, смена режима рендеринга).

**Non-goals:**

- Оптимизация производительности рендеринга или FPS в XR-среде.
- Поддержка XR-эксклюзивных UI-паттернов (Spatial UI, 3D-панели, composition layers) — это отдельный roadmap-item.
- Изменение поведения на Meta Quest 3 или других уже поддерживаемых устройствах.
- Выпуск отдельного APK-артефакта для Android XR SDK.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Если часть ошибок (`EmbeddingMixedHandler`) является системным поведением Android XR и не устраняется на стороне приложения — это должно быть явно задокументировано с доказательствами.
2. Решение не должно ухудшать работу на Meta Quest 3 — изменения должны быть либо XR-SDK-специфичными (через runtime detection), либо безопасными для всех VR-устройств.
3. Предпочтительно декларативное исправление (манифест, конфигурация Activity) перед программными workaround'ами.

### 3.2 Жёсткие ограничения

- **Flavor:** только `vr` (и `vrUnlicensed` как его зеркало).
- **API level:** API 34+; изменения не должны ломать минимальный `minSdk` для `vr`-флавора.
- **Wear OS:** не затрагивается.
- **Производительность:** изменения в обработке конфигурационных изменений не должны увеличивать время первого отображения экрана более чем на 200ms.
- **Совместимость данных:** без изменений схемы хранилища.
- **Локализация:** EN/RU/UK — не затрагивается (изменения инфраструктурные, не текстовые).
- **Доступность:** не затрагивается напрямую, но после исправления содержимое ViewPager должно быть доступно TalkBack-навигации как и на обычных устройствах.

## 4. Контекст текущей архитектуры

Сборка `vr` использует единую Activity-базу приложения (унаследованную от `standard`-флавора), дополненную VR-специфичным слоем поверх. Все экраны — включая настройки — написаны для обычного Android-окружения без учёта XR desktop-режима. Обработка конфигурационных изменений в Activity'ях не охватывает параметры, специфичные для XR-платформы (`screenSize`, `smallestScreenSize`, `densityDpi`, `windowLayout`), из-за чего система пересоздаёт Activity при каждом изменении геометрии виртуального окна в XR-среде.

Системный компонент `EmbeddingMixedHandler` (часть Android XR Shell) ожидает, что приложение декларирует совместимость с Activity Embedding и предоставляет информацию об иерархии окон (`WindowHierarchyInfo`). Текущий манифест этих деклараций не содержит, что приводит к ошибкам при каждом закрытии Activity. Поле `xrDesktopMode=undefined` прямо указывает на отсутствие соответствующих метаданных в манифесте.

---

## 5. Предлагаемый подход

Решение состоит из трёх независимых уровней, каждый из которых может быть реализован и проверен отдельно.

### 5.1 Уровень манифеста: декларация XR-совместимости

Добавить в манифест `vr`-флавора (источник: `src/vr/AndroidManifest.xml`) объявления, необходимые для корректной работы с Activity Embedding и Android XR Shell:

- Объявление поддержки XR desktop-режима (атрибут, задающий `xrDesktopMode` в явном виде).
- Декларация `WindowHierarchyInfo`-совместимости (если требует конкретный элемент манифеста — уточнить в ходе research).
- Расширение списка `android:configChanges` для всех Activity'й, запускаемых в XR-окружении, чтобы охватить изменения геометрии виртуального окна.

### 5.2 Уровень Activity: устойчивость к конфигурационным изменениям

Убедиться, что каждая Activity, участвующая в навигации при запуске на XR SDK (Welcome, Main, Settings), правильно обрабатывает конфигурационные изменения и не требует полного пересоздания при смене параметров XR-окна. Если декларативного решения недостаточно — реализовать `onConfigurationChanged` с сохранением состояния ViewPager (текущая позиция вкладки и состояние фрагментов).

### 5.3 Уровень диагностики: rendernode и Activity Embedding

Установить, является ли `Failed to open rendernode` ошибкой, устраняемой на стороне приложения, или системным поведением эмулятора Android XR SDK, которое не имеет workaround'а. Аналогично — выяснить, устраняется ли `EmbeddingMixedHandler: No WindowHierarchyInfo found` декларацией в манифесте, или это ожидаемое поведение при закрытии Activity, которое можно игнорировать. Поскольку реальное Android XR-устройство недоступно (см. §6 Q3), решение по этим артефактам принимается на основании поведения эмулятора плюс публичной документации Android XR SDK.

### 5.4 Потоки данных и событий

```
Android XR Shell изменяет геометрию виртуального окна
  → Activity получает изменение конфигурации
  → [сейчас] пересоздание Activity → потеря состояния ViewPager → чёрный экран
  → [цель] обработка onConfigurationChanged без пересоздания → содержимое сохранено
```

### 5.5 Точки расширяемости

Детектирование XR-платформы во время выполнения должно быть изолировано в одном месте (вспомогательный компонент или флаг сборки) так, чтобы будущие XR-специфичные адаптации (Spatial UI, composition layers) могли использовать тот же механизм определения платформы.

## 6. Открытые вопросы / Research items

> **Дата резолюции:** 2026-04-30. Ответы получены из официальной документации Android XR SDK (developer.android.com/develop/xr).

1. **xrDesktopMode: нужен ли конкретный атрибут манифеста**
   - **Вопрос:** Существует ли публично задокументированный атрибут AndroidManifest для объявления XR desktop-режима в Android XR SDK, или это внутренняя Meta-специфика?
   - **Резолюция:** Корректное публичное API — это `<property>` `android.window.PROPERTY_XR_ACTIVITY_START_MODE` внутри `<application>` (или индивидуальной `<activity>`). Допустимые значения: `XR_ACTIVITY_START_MODE_HOME_SPACE` (приложение работает как 2D-панель, side-by-side с другими) и `XR_ACTIVITY_START_MODE_FULL_SPACE_MANAGED` (полноценный immersive-режим без других окон). Дополнительно нужно объявить `<uses-feature android:name="android.software.xr.api.spatial" android:required="false" />` — `required=false`, так как `vr`-флавор запускается также на Quest, где этот feature отсутствует. Для целевого UX (Settings/Main/Welcome — flat-панель, поведение аналогично `com.oculus.intent.category.2D` на Quest) нужен `XR_ACTIVITY_START_MODE_HOME_SPACE`. Поле `xrDesktopMode=undefined` в логах исчезнет после декларации.
   - **Статус:** Verified

2. **EmbeddingMixedHandler: устраняемо или системное**
   - **Вопрос:** Можно ли подавить `No WindowHierarchyInfo found` декларацией совместимости, или это ожидаемый лог при закрытии Activity в XR Shell?
   - **Резолюция:** `EmbeddingMixedHandler` и `WindowHierarchyInfo` — внутренние компоненты Android XR Shell, **не присутствуют в публичной документации Android XR SDK**. Публичный механизм Activity Embedding (`PROPERTY_ACTIVITY_EMBEDDING_SPLITS_ENABLED`) предназначен для split-экранов внутри одного приложения, а не для интеграции с XR Shell. Гипотеза по итогам research: после декларации `PROPERTY_XR_ACTIVITY_START_MODE = HOME_SPACE` приложение становится корректным «гражданином» XR Shell, и Shell получает валидный `WindowHierarchyInfo`. Если ошибки сохранятся — задокументировать как «known XR system noise» с пометкой версии Android XR SDK. Активные действия по подавлению на стороне приложения не предусматриваем.
   - **Статус:** Verified

3. **rendernode: эмулятор vs реальное XR-устройство**
   - **Вопрос:** `Failed to open rendernode` воспроизводится только на x86\_64-эмуляторе или также на реальном Android XR-устройстве?
   - **Резолюция:** Реального Android XR-устройства в наличии нет. Won't-fix: ошибку `Failed to open rendernode` рассматриваем как артефакт x86\_64-эмулятора Android XR SDK (типичная проблема рендеринга hwui на x86 без аппаратного ускорения), исследование на реальном устройстве отложено до момента, когда оно появится. На UX в эмуляторе ошибка не влияет — это лог-warning, не блокирующий рендеринг.
   - **Статус:** Verified

4. **configChanges для XR-геометрии**
   - **Вопрос:** Какой именно набор `configChanges` необходим, чтобы Activity не пересоздавалась при изменении геометрии XR-окна?
   - **Резолюция:** Android XR Shell ведёт себя как multi-window/free-form окружение — для предотвращения recreate необходим расширенный набор: `orientation|screenSize|smallestScreenSize|screenLayout|keyboardHidden|density|navigation|uiMode|fontScale`. Этот набор уже применён в `vr/AndroidManifest.xml` для `VrPlayerActivity`. Для остальных активити (Settings, Welcome, Main и др.) текущий набор в `main/AndroidManifest.xml` существенно беднее (`orientation|screenSize|keyboardHidden`) — отсюда multi-recreate Settings на XR SDK. Дополнительно: `android:resizeableActivity="true"` объявляется на уровне `<application>` или `<activity>`, чтобы Shell не убивал процесс при resize. Изменения вносятся в манифест `vr`-флавора через `tools:replace="android:configChanges"` для overlay поверх main-манифеста, чтобы не влиять на standard/lite/photos/legacy.
   - **Статус:** Verified

## 9. Архитектурные решения (ADR)

**ADR-1: Декларативное исправление приоритетнее программного**

- **Решение:** В первую очередь использовать изменения манифеста и `android:configChanges`, а не programmatic detection + branching.
- **Альтернативы:** Runtime-проверка `isXrDevice()` с разными путями кода для XR и обычного Android.
- **Почему:** Декларативный подход не добавляет условных ветвей в production-логику и не влияет на производительность. Программный workaround нужен только если декларативный окажется недостаточным (зафиксировать в исследовании §6).

**ADR-2: Изменения только в vr-манифесте, не в общем**

- **Решение:** Все XR-специфичные декларации идут в `src/vr/AndroidManifest.xml`, не в общий манифест `src/main/`.
- **Почему:** `standard`, `lite`, `photos`, `legacy` флаворы не имеют XR-зависимостей; добавление XR-деклараций в общий манифест — избыточно и потенциально конфликтует с Play Store review.

## 11. Критерии готовности (strategic-level)

1. Открытие «Настройки» на Android XR SDK эмуляторе не вызывает более одного `onCreate` за сессию — ровно одно создание, никаких повторных.
2. Все вкладки настроек (General, Media, Playback, Operations) отображают свой контент без чёрных областей.
3. В логах Android XR SDK поле `xrDesktopMode` принимает конкретное значение (не `undefined`); либо, если поле остаётся `undefined` несмотря на корректную декларацию `PROPERTY_XR_ACTIVITY_START_MODE`, факт оформлен как «known system behavior» в `dev/CHANGELOG.md` с цитатой из лога.
4. На Meta Quest 3 поведение Settings, Welcome и Main Activity не изменилось: smoke-тест навигации (вход → смена вкладки → resize окна → выход) проходит без регрессий.
5. Все четыре открытых вопроса §6 имеют статус Resolved; все Won't-fix-резолюции явно отражены в `dev/CHANGELOG.md` либо в тактической спеке.
