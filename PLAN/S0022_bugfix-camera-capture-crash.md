# Стратегическая спецификация: S0022 — Захват фото из Browse не должен крашить приложение

**Ticket:** S0022
**Status:** Verified
**Audit:** see `PLAN/S0022_bugfix-camera-capture-crash__audit_2026-04-30_2.md`
**Date:** 2026-04-28
**Tier:** 2 — Easy
**Roadmap entry:** Ad-hoc — запрос 2026-04-28 (повторяющаяся регрессия архивированной S0011)
**Tactical spec:** `PLAN/S0022_bugfix-camera-capture-crash/` (будет создан через `/spec-tech`)

**Update 2026-04-29 (VR-сессия Quest 3, лог `logs/fastmediasorter_20260429_022215.log`):** диагностический трейс S0022-CAM работает и даёт полную картину. Падения нет — наблюдается «тихий abort» без пользовательской обратной связи. Это разворачивает §1 «приложение падает» в §1' «команда выглядит нерабочей». См. блок «§13 — Field evidence» ниже; Open-вопросы §6 #1 и §6 #3 уточнены.

**Update 2026-04-30 (implementation closed):** реализация S0022 завершена в коде: команда скрывается при отсутствии camera handler, `IOException` выводится отдельным локализованным сообщением, process-death контекст восстанавливается через `savedInstanceState`, а `docs/FEATURES*` синхронизированы с новым поведением. Для закрытия тикета остались только ручные on-device проверки из §11.

> **Scope:** STRATEGIC. Цели, ограничения, открытые вопросы. Без имён классов, путей, лимитов строк, миграций Room, модулей Hilt.

---

## 1. Проблема

Команда «сделать фото» в файловом браузере по-прежнему приводит к падению приложения. Проблема ранее закрывалась как решённая, но возвращается. В присланных свежих лог-сессиях факт попытки не зафиксирован — значит, краш мог случиться вне сессии, либо приложение падает до записи стека в файл-лог. Эффект на пользователя: команда из меню ресурса ведёт к закрытию приложения вместо ожидаемой штатной обработки (открытие штатной камеры, либо понятное сообщение «не поддерживается на этом устройстве»). Это подрывает доверие ко всем редко-используемым командам меню.

---

## 2. Цели

1. Нажатие команды «сделать фото» никогда не приводит к падению приложения. На любом устройстве и в любых условиях команда либо запускает камеру и возвращается с результатом, либо отображает локализованную ошибку и оставляет приложение работоспособным.
2. На устройстве, где штатное приложение камеры отсутствует или не отвечает на запрос, пользователь сразу видит понятное «нет приложения камеры» — без падения и без молчаливого «ничего не произошло».
3. Перезапуск процесса между вызовом камеры и возвратом результата (process death) не приводит к падению при возвращении пользователя в приложение.
4. Отказы операционной системы (нет разрешений, ошибка чтения/записи файла) — обрабатываются явной ошибкой пользователю, без попадания в общий «краш».
5. Регрессия не возвращается: добавлено наблюдаемое покрытие тестами/проверкой на устройстве.

**Non-goals:**

- Не вводится новая UX-логика для самой команды (без изменения количества шагов, диалогов переименования и пр.).
- Не вводится встроенный камера-вьюфайндер; продолжаем использовать штатную камеру системы.
- Не меняется правило видимости команды (тумблер «отключить захват камеры» остаётся как есть).
- Не охватывается захват аудио-видео из иммерсивного режима (это отдельная область).

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Желательно, чтобы при отсутствии штатной камеры команда сама по себе исчезала из меню до клика, а не показывала ошибку только после нажатия.
2. Желательно сообщение пользователю было одно и то же визуально (snackbar/toast) для всех типов отказа, с подстановкой конкретной причины.
3. Желательно, чтобы краш был наблюдаемым через диагностический канал, а не «исчезал» из-за ранней смерти процесса. Если падение всё-таки происходит — стек должен быть в логе.

### 3.2 Жёсткие ограничения

- **Flavor:** все флейворы, в которых видна команда «сделать фото». Поведение должно совпадать на телефоне и на VR-устройстве (с учётом что на VR штатной камеры может не быть).
- **API level:** без новых API-зависимостей; минимум проекта сохраняется. Поведение должно учитывать API 33/34, где режим storage permissions меняется.
- **Wear OS:** не затрагивается.
- **Производительность:** дополнительная защита не должна добавлять заметной задержки между нажатием команды и появлением камеры.
- **Совместимость данных:** временные файлы используются как сейчас, FileProvider — как сейчас; миграции базы не требуются.
- **Локализация:** все новые видимые сообщения обязательны в EN/RU/UK.
- **Доступность:** сообщения об ошибке читабельны TalkBack; команда (когда видима) имеет понятный label.

## 4. Контекст текущей архитектуры

В файловом браузере есть выделенный менеджер, отвечающий за запуск штатной камеры и обработку её результата. Менеджер хранит ссылку на временный файл в собственном поле, регистрирует системный launcher и при возвращении результата сохраняет файл в выбранный ресурс. Команда вызова присутствует в popup-меню ресурса; видимость управляется тумблером «отключить захват камеры». Визуального предохранителя «есть ли вообще обработчик у системы для запроса камеры» в текущем коде нет — запрос отправляется без предварительной проверки. Обработчик результата полагается на наличие сохранённого временного файла; если процесс перезапускался между вызовом и возвращением, поле потеряно. Нет также обвязки на типичные системные исключения (отсутствие активити, отказ в правах, ошибка ввода-вывода) — любое такое исключение всплывает как краш.

---

## 5. Предлагаемый подход

Подход разделяет защиту по четырём независимым осям: предотвращение запуска без обработчика, переживание перезапуска процесса, обвязка системных исключений и наблюдаемость крашей.

### 5.1 Основные столпы / модули

**Предохранитель видимости команды.**
Команда «сделать фото» видна в меню только когда система имеет хотя бы одного обработчика подходящего intent'а. Видимость пересчитывается при открытии меню, а не один раз на старт. Если обработчиков нет — команда отсутствует в списке, никаких «серых» пунктов и тоастов «извините» не показывается. Тумблер «отключить захват камеры» сохраняет приоритет: выключенный тумблер всегда прячет команду независимо от наличия обработчика.

**Сохранение состояния через перезапуск процесса.**
Контекст команды (выбранный ресурс, путь временного файла, целевое имя) переживает перезапуск процесса через стандартный механизм сохранения состояния активности/менеджера. После возврата системного launcher-а менеджер находит контекст из сохранённого состояния и продолжает процесс штатно. Если контекст не восстановим (длительная пауза, очистка системой, сменился ресурс) — менеджер аккуратно завершает попытку, удаляет временные артефакты и показывает локализованное сообщение «попытка не завершена; повторите».

**Обвязка системных исключений.**
Точки отправки intent'а в систему и записи временного файла обёрнуты в защитный контур, ловящий типичные системные исключения. Каждый класс исключения превращается в отдельную локализованную ошибку: «нет приложения камеры», «нет разрешений», «не удалось сохранить файл». Контур не превращается в «catch Throwable» — список ловимых классов конкретный, остальное по-прежнему всплывает наверх.

**Наблюдаемость и диагностика.**
Все ветки отказа пишут одну строку в лог с явным маркером сценария. Если падение всё же случается — сборка обязана успеть записать стек в файл-лог до закрытия процесса. Диагностический канал должен делать различимыми три ситуации: «команда не видна», «команда нажата, но обработчика нет», «обработчик есть, но процесс упал/завершился аномально».

**Покрытие тестами и проверкой на устройстве.**
Сценарии «нет камеры», «отказ в разрешениях», «process death», «успешный захват» прогоняются как набор сценариев на устройстве. Включает Quest-устройство (где штатной камеры может не быть) и обычный телефон. Проверка пишется так, чтобы её можно было повторить после каждой сборки.

### 5.2 Потоки данных и событий

Открытие меню → запрос «есть ли обработчик» → отображение/скрытие команды. Нажатие команды → создание временного файла + сохранение контекста → отправка intent'а через защитный контур → ожидание результата. Результат от системы → восстановление контекста → сохранение файла в ресурс → очистка контекста. Любая ошибка на любом шаге → локализованное сообщение + очистка временного файла + запись в лог.

### 5.3 Точки расширяемости

- Список ловимых классов исключений вынесен в одно место и легко расширяется.
- Сохранение/восстановление контекста должно быть готово к появлению других «двухшаговых» команд (например, «выбрать видео из системного picker'а»).
- Видимость команды должна уметь учитывать дополнительные условия (например, тип ресурса) без распространения логики по UI-коду.

## 6. Открытые вопросы / Research items

1. **Истинная причина крашей в текущем поле.**
   - **Вопрос:** какая из вероятных причин действительно срабатывает (нет обработчика, process death, отказ в правах, ошибка FileProvider)?
   - **Варианты:** одна причина, несколько, разные на разных устройствах.
   - **Нужно выяснить:** запросить у пользователя свежий репро-лог сразу после краша; включить промежуточные диагностические маркеры на каждом шаге, чтобы по логу было видно, на каком шаге падение произошло.
   - **Статус:** Частично отвечен. На Quest 3 (2026-04-29, §13): краша нет, наблюдается тихий abort — `handlers=0` для `android.media.action.VIDEO_CAPTURE` на HorizonOS API 34. Для phone-сборки, где краш ранее наблюдался, причина может отличаться — пункт остаётся открытым для phone-кейса.

2. **Скрытие команды в меню при отсутствии обработчика.**
   - **Вопрос:** скрывать молча или оставлять видимой и показывать ошибку при нажатии?
   - **Варианты:** «скрывать всегда» (см. предложение в §3.1), «оставлять видимой и сообщать при клике», «показывать с пометкой ‹нет камеры›».
   - **Нужно выяснить:** ожидание владельца; влияние на обнаруживаемость функции на устройствах, где камера появляется/исчезает (например, внешняя web-камера).
   - **Статус:** Отвечен. Реализация следует ADR-3: пункт меню скрывается, если `queryIntentActivities` не находит совместимый camera handler. Это уже отражено в коде и в `docs/FEATURES*`; вариант «оставлять видимой и сообщать при клике» отклонён.

3. **Поведение на VR-устройстве без штатной камеры.**
   - **Вопрос:** на Quest 3 штатная активити камеры не предполагается; должна ли команда просто отсутствовать, или предусмотреть «передать на сопряжённое устройство»?
   - **Варианты:** «всегда скрыта на VR», «скрыта по факту отсутствия обработчика», «открыть в этом случае альтернативный сценарий».
   - **Нужно выяснить:** наличие обработчиков на актуальной версии HorizonOS; ожидания владельца.
   - **Статус:** Отвечен. Empirical: Quest 3 / HorizonOS / API 34 возвращает `handlers=0 list=` для `VIDEO_CAPTURE`. Команда скрывается по ADR-3: «нет обработчика → нет пункта меню». Сценарий «передать на сопряжённое устройство» — вне скопа текущей спеки.

4. **Длительность и форма «не удалось — повторите».**
   - **Вопрос:** какое сообщение показывать при потере контекста после длительного отсутствия?
   - **Варианты:** snackbar, toast, диалог с возможностью повторить «здесь и сейчас».
   - **Нужно выяснить:** согласованность с другими long-running командами в браузере.
   - **Статус:** Отвечен. Выбран `Snackbar` с локализованной строкой `camera_capture_error_session_expired`, показанный из `BrowseCameraCaptureManager.restoreState()` / `handleResult()` на decor-root активности. Диалог и toast не используются.

5. **Гигиена временных файлов.**
   - **Вопрос:** как чистить временные артефакты, если команда «погасла» молча?
   - **Варианты:** очистка по событию старта приложения; очистка по окончании сессии; ничего не делать (полагаться на cache TTL).
   - **Нужно выяснить:** чему сейчас следует слой временных файлов; не сломать нечаянно соседние команды.
   - **Статус:** Частично отвечен. Лог (§13) подтверждает: `tempFile` и `FileProvider URI` создаются **до** проверки `queryIntentActivities`, то есть при `handlers=0` файл `CAP_*.mp4` всё равно появляется на диске. Тактическая спека (шаг 1) выносит проверку наличия обработчика **до** создания временного файла — это устраняет мусорный артефакт.

## 9. Архитектурные решения (ADR)

**ADR-1: Список ловимых исключений конечен и явен.**

- **Решение:** защитный контур ловит конкретные системные исключения, не общий `Throwable`. Список расширяется намеренно, а не по факту срабатывания.
- **Альтернативы:** (а) ловить всё подряд — отвергнуто, потому что маскирует баги; (б) полагаться на глобальный crash-handler — отвергнуто, потому что он закрывает приложение, а цель — оставить его работоспособным.
- **Почему:** конкретность списка делает диагностику точной и не превращает фикс в немой «глушитель».

**ADR-2: Сохранение контекста — стандартный системный механизм.**

- **Решение:** контекст команды сохраняется через стандартный механизм сохранения состояния (savedInstanceState/equivalent), а не через статическое поле менеджера.
- **Альтернативы:** (а) хранить в поле менеджера и надеяться на то, что менеджер не пересоздаётся — текущее положение, причина регрессии; (б) хранить в DataStore/Room — отвергнуто как избыточное.
- **Почему:** перезапуск процесса — штатный сценарий Android; правильное место для подобного контекста — соответствующий механизм платформы.

**ADR-3: Видимость команды зависит от наличия обработчика, а не только от тумблера.**

- **Решение:** правило видимости — конъюнкция «тумблер не выключен» И «у системы есть обработчик подходящего intent'а».
- **Альтернативы:** «оставлять видимой и сообщать при клике» — отвергнуто, потому что это и есть текущее ощущение «команда не работает». «Скрывать только при выключенном тумблере» — отвергнуто, потому что не покрывает Quest-сценарий.
- **Почему:** видимость = ожидание исполнимости. Кнопка «сделать фото», ведущая к ошибке «нет камеры», — анти-паттерн.

## 11. Критерии готовности (strategic-level)

1. На устройстве без штатной камеры (включая Quest 3) команда «сделать фото» отсутствует в popup-меню; нажатие на неё невозможно.
2. На телефоне со штатной камерой команда работает как сейчас: открывает камеру, возвращает фото, пользователь сохраняет результат.
3. Перезапуск процесса между запуском камеры и возвратом результата завершается без падения; пользователь либо штатно сохраняет фото, либо видит локализованное сообщение «попытка не завершена».

## 13. Field evidence — Quest 3, 2026-04-29

Свежий лог (`logs/fastmediasorter_20260429_022215.log`, lines 444–450) даёт полную трассировку команды «сделать фото» на Quest 3. Краш отсутствует — наблюдается «тихий abort» с нулевой пользовательской обратной связью. Это уточняет картину относительно §1 и §6.

**Хронология (timestamps относительные, тег `S0022-CAM`):**

```text

02:22:22.893  S0022-CAM: launch ENTRY resource={id=3, name=Все видео, type=LOCAL, path=virtual://all_video, allFiles=false}
```

**Что доказывает лог:**

1. Диагностический трейс из §3.1 п.3 уже встроен и работает — каждый шаг команды виден в логе с уникальным маркером `S0022-CAM`. Диагностический канал, требуемый ADR-1 §3 риска, в текущем коде уже есть.
2. Точка отказа — `packageManager.queryIntentActivities` для `android.media.action.VIDEO_CAPTURE` возвращает **0 обработчиков** на Quest 3 / HorizonOS / API 34. Подтверждённое empirical-наблюдение, не гипотеза.
3. `tempFile` создаётся и `FileProvider` URI получается **до** проверки наличия обработчика. Это бесполезные побочные эффекты на устройстве без камеры — стоит вынести их под условие «обработчик существует».
4. После `ABORT` пользователь не видит ничего: ни Toast, ни Snackbar, ни диалога. Это и есть «нулевая реакция на нажатие пункта меню», описанная пользователем 2026-04-29 в `PLAN/new-vr.txt` пункт 5.

**Уточнение Open-вопросов §6:**

- §6 #1 (истинная причина) — на Quest 3 **краша нет**, есть только тихий abort. Для этой платформы пункт можно считать закрытым: причина — `handlers=0`. На phone-сборке (где краш ранее наблюдался) причина может быть другой; держать пункт Open для phone-кейса.
- §6 #3 (поведение на VR-устройстве) — empirical-ответ: на Quest 3 обработчиков `VIDEO_CAPTURE` нет. Применить ADR-3 — команда «сделать фото» **скрывается** в popup-меню при `handlers=0`. Для VR это будет всегда; для phone — динамически по результату `queryIntentActivities`.
- §6 #5 (гигиена временных файлов) — в текущем коде `CAP_20260429_022222.mp4` создаётся даже когда обработчик отсутствует. После применения видимости-предохранителя §5.1 п.1 (проверка `handlers > 0` на открытии меню) этот файл не будет создаваться вовсе.

**Корректировка плана:** strategic-подход §5.1 не меняется. Тактическая спека `/spec-tech S0022` начинается с **видимости-предохранителя**: вынос `queryIntentActivities` на этап открытия popup-меню; скрытие команды при `handlers=0`. Это закрывает наблюдаемый кейс Quest 3 одной точечной правкой и оставляет существующий защитный контур работать для phone-сценариев.
