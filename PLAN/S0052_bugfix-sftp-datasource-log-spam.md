# Стратегическая спецификация: S0052 — Избыточное логирование в сетевом источнике данных

**Ticket:** S0052
**Status:** Verified
**Priority:** 50
**Date:** 2026-05-02
**Tier:** 1 — Quick Win
**Roadmap entry:** Ad-hoc — запрос 2026-05-02
**Tactical spec:** `PLAN/S0052_bugfix-sftp-datasource-log-spam/` (будет создан через `/spec-tech`)

> **Scope:** STRATEGIC. Цели, ограничения, открытые вопросы. Без имён классов, путей, лимитов строк, миграций Room, модулей Hilt.

---

## 1. Проблема

SFTP-источник данных логирует каждый вызов `read()` на уровне DEBUG в первых 10 КБ данных. ExoPlayer при детекции формата контейнера выполняет многотысячные вызовы `read()` по 1 байту — в результате за одну сессию воспроизведения генерируется 5000–10 000 строк лога. Это засоряет logcat, существенно затрудняет диагностику других проблем и создаёт накладные расходы на форматирование строк в горячем пути. Аналогичное поведение может присутствовать в SMB-, FTP- и облачном источниках.

---

## 2. Цели

1. Количество строк лога от сетевых источников данных за сессию воспроизведения сокращается минимум на 95%.
2. Диагностически важные события (открытие, закрытие, ошибки, seek, итоговая статистика) сохраняются в логе.
3. В режиме Debug-сборки остаётся возможность включить детальное логирование без перекомпиляции (через флаг или уровень Timber).
4. Аудит остальных сетевых источников (SMB, FTP, облако) — устранение аналогичных паттернов там, где они обнаружены.

**Non-goals:**

- Изменение поведения логирования в production/release-сборке (там уже тихо).
- Полное отключение логирования источников данных.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Желательны итоговые строки при закрытии источника: сколько байт прочитано, сколько вызовов `read()`, среднее время.
2. Ошибки и seek-события должны оставаться на уровне DEBUG или выше.

### 3.2 Жёсткие ограничения

- **Flavor:** все флейворы с сетевыми ресурсами (standard, lite, legacy).
- **API level:** без API-специфики.
- **Wear OS:** не затрагивается.
- **Производительность:** логирование не должно добавлять заметных затрат в горячем пути чтения.
- **Совместимость данных:** не требуется.
- **Локализация:** не требуется — логи только на английском.
- **Доступность:** не затрагивается.

---

## 4. Контекст текущей архитектуры

Сетевые источники данных реализуют интерфейс DataSource и вызываются из фонового потока ExoPlayer'а. Текущая логика логирования построена на пороговом условии: «логировать все вызовы, пока суммарно прочитано менее 10 КБ». При детекции формата ExoPlayer запрашивает данные многократно малыми порциями (1 байт), что при пороге в 10 КБ даёт тысячи строк для каждого нового файла.

Остальные источники (SMB, FTP, облако) имеют независимые реализации логирования и требуют отдельной проверки.

---

## 5. Предлагаемый подход

### 5.1 Основные столпы / модули

**А. Переход на счётчик вызовов**
Вместо порога по количеству байт использовать счётчик вызовов: логировать первые N вызовов `read()`, затем каждый M-й (например, каждый 1000-й). Это гарантирует фиксацию старта и периодические контрольные точки без лавины строк.

**Б. Итоговая строка при закрытии**
При вызове `close()` выводить одну сводную строку: суммарный объём, количество вызовов, время жизни источника. Это заменяет покустрочное логирование.

**В. Уровень логирования**
Детальные read-события переводить на уровень VERBOSE, оставляя DEBUG только для старта, завершения, ошибок и seek. В релизной сборке Timber не подключает VERBOSE-дерево — строки не появляются в продакшне.

**Г. Аудит SMB, FTP, Cloud**
Проверить реализацию каждого источника на аналогичные паттерны; применить тот же подход.

### 5.2 Потоки данных и событий

```
open()  → DEBUG: "opened file X, position=N, size=M"
read()  → VERBOSE (или счётчиком): каждые 1000 вызовов
close() → DEBUG: "closed: totalRead=NMB, calls=K, elapsed=Ts"
error() → ERROR: полное сообщение без изменений
```

### 5.3 Точки расширяемости

- Константы порогов (первые N вызовов, каждый M-й) должны быть легко настраиваемы для будущей отладки.

## 6. Открытые вопросы / Research items

1. **SMB, FTP, Cloud — аудит логирования**
   - **Вопрос:** Есть ли аналогичный паттерн в других источниках?
   - **Результат аудита (2026-05-02):**
     - **SMB**: OK — `logProgress()` с порогом 10 MB; условный `BuildConfig.LOG_SMB_IO` для детального режима. Изменений не требует.
     - **FTP**: SPAM — идентичный SFTP паттерн (`totalBytesRead ≤ 10000`). Исправлено в Phase 3.
     - **Cloud**: OK — в `read()` нет per-read логирования вообще. Изменений не требует.
   - **Статус:** Resolved

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Потеря диагностической информации при реальных ошибках чтения | Низкая | Сложнее отладить редкие ошибки | Ошибки всегда логируются на ERROR без ограничений |

## 9. Архитектурные решения (ADR)

**ADR-1: Счётчик вызовов vs порог по байтам**

- **Решение:** Счётчик вызовов read() предпочтительнее порога по байтам, т. к. не зависит от размера читаемых порций (ExoPlayer может читать и 1, и 65 536 байт).
- **Альтернативы:** (a) только итоговая строка в close(); (b) уровень VERBOSE для всех read без условия.
- **Почему:** Итоговая строка теряет временну́ю картину; VERBOSE без условия — то же, что текущий DEBUG при включённом VERBOSE-дереве.

## 11. Критерии готовности (strategic-level)

1. Сессия воспроизведения одного SFTP-файла генерирует не более 10 строк уровня D от сетевого источника (не считая ошибок).
2. При закрытии источника в логе присутствует сводная строка с суммарной статистикой.
3. Аналогичный аудит для SMB, FTP, Cloud проведён; результаты зафиксированы в тактической спеке (исправлено или «не применимо»).
4. В debug-сборке при включении VERBOSE-уровня детальные read-события снова видны.

## Last Audit

**Date:** 2026-05-02 — **Verified**

Критерий 1: SFTP и FTP источники теперь не генерируют DEBUG-строк в `read()` — только VERBOSE (первые 3 + каждый 1000-й вызов). За сессию воспроизведения от сетевого источника генерируется ≤ 5 строк уровня D.  
Критерий 2: `close()` у SFTP и FTP выводит сводную строку `totalRead / calls / elapsed`.  
Критерий 3: SMB (порог 10 MB) и Cloud (нет per-read logging) — без изменений, соответствуют требованиям.  
Критерий 4: `Timber.v()` — видим при включении VERBOSE-дерева в debug-сборке.
