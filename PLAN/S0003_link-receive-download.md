# Стратегическая спецификация: Ad-hoc — Загрузка файла по входящей ссылке

**Status:** Implemented
**Date:** 2026-04-27
**Tier:** 3 — Moderate (ad-hoc)
**Roadmap entry:** Ad-hoc — запрос 2026-04-27 (новая общая настройка «При получении ссылки — скачать» + механизм извлечения файла/blob по ссылке)
**Tactical plan:** [`PLAN/S0003_link-receive-download/INDEX.md`](S0003_link-receive-download/INDEX.md)

> **Scope:** STRATEGIC. Цели, ограничения, открытые вопросы. Без имён классов, путей, лимитов строк, миграций Room, модулей Hilt.

---

## 1. Проблема

Когда в приложение приходит из системного «Поделиться» текстовая полезная нагрузка-ссылка (браузер, Instagram, мессенджер), пользователь сейчас получает её в виде обычного `.txt`-файла во временный кэш и затем должен сам копировать содержимое, открыть ссылку в браузере, скачать файл и вернуть его в приложение. Это длинный путь для типового сценария «увидел медиа в вебе → хочу положить его в нужный мой ресурс». Нужен общий канал «приняли ссылку — скачали по ней файл прямо в выбранный ресурс-получатель», и он должен подчиняться единой настройке поведения.

---

## 2. Цели

1. Появляется общая настройка верхнего уровня «При получении ссылки — скачать» (вкл/выкл), включённая по умолчанию.
2. Появляется подчинённая настройка «Ресурс для закачки», в которой пользователь может выбрать любой зарегистрированный ресурс-получатель; пустое значение допустимо и означает fallback на системную папку Downloads (по аналогии с текущим поведением «Сохранить кадр»).
3. Появляется ещё одна подчинённая настройка «Автоматически открывать скачанное в плеере» (вкл/выкл, по умолчанию — включена): при ВКЛ — после успешной загрузки файл автоматически открывается во встроенном плеере; при ВЫКЛ — закачка идёт молча, без авто-открытия.
4. При выключенной верхней настройке весь механизм автоскачивания не работает — поведение возвращается к нынешнему (входящая ссылка трактуется как текст).
5. При включённой настройке входящая ссылка должна обрабатываться как URL: приложение пытается извлечь по ней целевой файл (прямой ресурс или встроенный media-кандидат HTML-страницы) и положить результат в выбранный ресурс-получатель (или в Downloads, если получатель не выбран либо недоступен).
6. Пользователь видит понятный прогресс/исход операции и может отменить её до завершения.

**Non-goals:**

- Полноценный универсальный «video downloader» под все мейнстрим-платформы (YouTube/TikTok/etc.) с обходом anti-bot и рестрикций провайдера — вне объёма первой итерации.
- Авторизованная загрузка из приватных аккаунтов (cookie/login share) — вне объёма.
- Перекодирование/постобработка скачанного файла — вне объёма.
- Изменения механики уже существующего приёма медиафайлов через Share-sheet (ACTION_SEND с EXTRA_STREAM) — вне объёма, эта ветка остаётся как есть.

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. UX-парность с настройкой «Сохранить кадр»: одинаковый паттерн «общий тумблер + подчинённый выбор ресурса + fallback Downloads».
2. Обе подчинённые настройки (выбор ресурса и авто-открытие) визуально/логически зависят от верхнего тумблера — при его выключении они неактивны.
3. Возможность в будущем расширить список поддерживаемых источников/паттернов извлечения (включая отдельный поиск стримовых URL) без изменения настроек пользователя.
4. По умолчанию верхний тумблер и подчинённый «Автоматически открывать скачанное в плеере» — ВКЛЮЧЕНЫ; «Ресурс для закачки» по умолчанию — пуст.
5. Размещение блока в настройках — раздел «Поделиться/Приём», подсекция «Поведение».

### 3.2 Жёсткие ограничения

- **Flavor:** одинаково во всех флейворах (`standard`, `lite`, `photos`, `legacy`); поведение и набор настроек идентичны.
- **API level:** `minSdk 26` (стандартные флейворы) и `minSdk 23` (legacy) — без зависимостей, требующих более нового API.
- **Wear OS:** не затрагивается.
- **Сеть:** допустимы любые сети (без ограничения «только Wi-Fi»). Скачивание выполняется в фоне и не блокирует UI.
- **Лимит размера:** жёсткого фиксированного лимита на размер итогового файла нет (исходим из ограничений целевого ресурса). Лимит используется только при выборе кандидата на странице (см. §5.1, столп D, и §6.3).
- **Совместимость данных:** новые поля настроек добавляются с безопасными значениями по умолчанию; старые сборки/бекапы должны продолжать загружаться без потерь.
- **Локализация:** EN/RU/UK обязательны для всех новых строк и состояний (включая ошибки и тосты прогресса).
- **Доступность:** подчинённые настройки должны явно выглядеть disabled при выключенном тумблере (не только цветом), а сообщения о результате — читаемы TalkBack.
- **Безопасность:** разрешены только `http(s)` URL; локальные/`file://`/`content://` ссылки и редиректы на них в этом канале запрещены. Запись разрешена только для медиа/документных MIME-типов, поддерживаемых приложением (whitelist).

## 4. Контекст текущей архитектуры

Сейчас текстовые ссылки, поступающие через системный Share-sheet, обрабатываются тем же приёмником, что и медиафайлы: текст оборачивается во временный `.txt` и предлагается пользователю как обычный файл. Слой настроек уже имеет рабочий паттерн «ресурс-получатель с fallback на Downloads» (применяется для сохранения кадра видео) и единый слой ресурсов-получателей, который умеет писать в локальные пути, SAF-папки, SMB/SFTP/FTP и облачные провайдеры. Сетевого слоя «открыть произвольный URL и сохранить тело ответа» как продуктовой возможности в приложении нет — есть только клиенты под конкретные протоколы и Glide для превью.

Проблема из §1 не решается без двух изменений: (а) расширение слоя настроек новой парой «общий тумблер + ресурс-получатель»; (б) появление новой роли «извлекатель файла из URL/HTML» с общим контрактом, который может быть подключён к приёмнику ссылок и в дальнейшем расширен новыми стратегиями извлечения.

## 5. Предлагаемый подход

Ввести две независимых, но связанных надстройки: декларативную (настройки + UI) и операционную (приём ссылки + извлечение + запись в ресурс). Декларативная часть — фундамент, который реализуется первым; операционная часть встраивается в уже существующий канал приёма Share-нагрузки и использует существующий слой записи в ресурсы.

### 5.1 Основные столпы / модули

**Столп A — Настройка поведения «При получении ссылки — скачать».**

- Цель: единая точка истины для верхнего тумблера.
- Требования: значение по умолчанию — включено; персистентность; экспорт/импорт в существующем механизме бекапа настроек; форвард-совместимость со старыми бекапами.

**Столп B — Подчинённая настройка «Ресурс для закачки».**

- Цель: указать целевой ресурс-получатель для скачанных файлов.
- Требования: значение по умолчанию — пусто; список выбора — все зарегистрированные ресурсы-получатели текущего профиля; пустое значение интерпретируется как fallback на Downloads; если выбранный ресурс был удалён или временно недоступен — fallback на Downloads с явным Toast-сообщением о причине fallback. Активность контрола подчинена столпу A.

**Столп B′ — Подчинённая настройка «Автоматически открывать скачанное в плеере».**

- Цель: после успешной загрузки сразу запускать встроенный плеер на полученном файле.
- Требования: значение по умолчанию — включено; при ВЫКЛ загрузка идёт молча (только итоговый Toast/уведомление, без авто-старта плеера). Активность контрола подчинена столпу A.

**Столп C — Канал приёма ссылок.**

- Цель: при включённой настройке ловить входящие ссылки и передавать их в извлекатель, а при выключенной — оставлять текущее поведение.
- Требования: единственная точка ветвления «настройка вкл / выкл»; поддерживаются только `http(s)` URL; всё, что не URL, продолжает идти текущим путём (текстовая запись). Если входящий текст содержит несколько URL, берётся первая найденная ссылка; остальное игнорируется в этом канале.

**Столп D — Извлекатель файла из URL.**

- Цель: по URL получить пригодный для записи бинарный поток с известными MIME/расширением/именем.
- Требования первой итерации: HTML-парсинг (без управляемого веб-контекста и без поиска стримовых URL); это сознательно ограниченный охват, расширения подключаются позже как новые стратегии того же контракта (см. §5.3 и §6.2).
- Стратегия извлечения, по приоритету:
  1. Прямая ссылка на файл: если ответ по URL приходит с медиа/документным `Content-Type` или URL содержит явное расширение поддерживаемого типа — сохраняется как есть.
  2. HTML-страница: парсинг разметки и поиск встроенных медиа-кандидатов (`og:video`/`og:image`/`twitter:player:stream`-подобные мета, `<video>`/`<audio>`/`<source>`/`<img>` с `src`/`srcset`, прямые ссылки на медиа в разметке).
  3. Кандидаты, представленные `data:`/`blob:`-схемами или подгружаемые исключительно скриптом, в этой итерации НЕ извлекаются (требуют управляемого веб-контекста — вне объёма первой итерации).
- Политика выбора при нескольких кандидатах: первый кандидат с известным размером ≥ 1 МБ; если ни один не достигает 1 МБ — самый большой по известному размеру; если размер ни у одного не известен — первый по порядку. Размер кандидата уточняется через `HEAD`-запрос (или `Content-Length` основного ответа); порог 1 МБ может быть скорректирован позже без изменения настроек пользователя.
- Жёсткого фиксированного лимита на итоговый размер скачивания нет; контроль идёт по факту записи в целевой ресурс (см. столп E).
- Тайм-ауты, политика follow-redirect (только `http(s)`) и whitelist MIME — конфигурируются внутри столпа, а не в приёмнике.
- Расширяемость: новые стратегии извлечения (включая стримовые) должны подключаться без изменения столпов A/B/B′/C.

**Столп E — Запись в выбранный ресурс с fallback.**

- Цель: положить полученный поток в ресурс из столпа B, а при недоступности — в системную папку Downloads.
- Требования: при недоступности целевого ресурса (удалён, оффлайн, нет прав) — запись уходит в Downloads и пользователь видит Toast с явным указанием причины fallback. Имя файла формируется по схеме «исходное имя из URL/`Content-Disposition` → нормализация → коллизия разрешается суффиксом времени», без перезаписи существующих.

**Столп F — Прогресс, обратная связь и авто-открытие.**

- Цель: пользователь понимает, что идёт скачивание, может его отменить, и (если включён столп B′) сразу видит файл в плеере.
- Требования: видимый недиспозитивный индикатор (без модального экрана поверх UI), результат — Toast/уведомление с путём/ресурсом и MIME; ошибки — отдельные понятные сообщения по классам (нет интернета, недоступный ресурс, не нашли медиа на странице, тайм-аут, MIME запрещён). При включённом столпе B′ — после успешной записи открыть файл во встроенном плеере; при ВЫКЛ — оставить только итоговое сообщение.

### 5.2 Потоки данных и событий

```text
Входящий Intent с текстом
        │
        ▼
[Канал приёма] ── текст не URL ──► существующий путь (.txt в кэш и далее)
        │
       URL & настройка ВКЛ
        │
        ▼
[Извлекатель] ── прямой файл ──► [Запись в ресурс] ──► Toast/уведомление
        │
        ▼
   HTML/страница
        │
        ▼
   Поиск кандидатов ──► выбор лучшего ──► [Запись в ресурс]
        │
        ▼
   ничего не найдено ──► пользовательское сообщение «не нашли файл по ссылке»
```

Слой настроек читается перед каждой обработкой ссылки (значение тумблера и идентификатор выбранного ресурса) — без локального кэширования вне процесса.

### 5.3 Точки расширяемости

- Реестр стратегий извлечения (порядок и набор) — для будущей поддержки специализированных источников.
- Политика выбора кандидата на странице (приоритет типов, минимальный/максимальный размер) — конфигурируема без изменения настроек пользователя.
- Сетевой профиль (Wi-Fi only / любая сеть, лимит размера) — закладывается как конфигурация столпа D, чтобы при необходимости в будущем экспонировать в UI без переписывания канала.

## 6. Открытые вопросы / Research items

1. **Охват флейворов** — **Resolved:** одинаково во всех флейворах (`standard`, `lite`, `photos`, `legacy`).

2. **Способ парсинга страниц и работы с blob-схемами**
   - **Решение первой итерации:** только HTML-парсинг без управляемого веб-контекста. `data:`/`blob:`-кандидаты и контент, подгружаемый исключительно скриптом, в эту итерацию не входят.
   - **Что остаётся открытым:** в следующей итерации добавить отдельную стратегию «поиск стримового URL» (HLS/DASH/m3u8 и подобные) и опциональный управляемый веб-контекст для blob-схем — как новые стратегии в реестре извлекателя, без изменения настроек пользователя.
   - **Статус:** Resolved для первой итерации, расширение — будущая работа.

3. **Политика выбора кандидата на странице** — **Resolved:** первый кандидат с известным размером ≥ 1 МБ; если ни один не достигает 1 МБ — самый большой по известному размеру; если размер ни у одного не известен — первый по порядку. Порог 1 МБ может быть позже скорректирован без изменения настроек пользователя.

4. **Получение размера кандидата до скачивания**
   - **Вопрос:** как технически узнавать размер кандидатов на странице, не выкачивая их полностью?
   - **Решение по умолчанию:** `HEAD`-запрос к каждому кандидату (с таймаутом и ограничением общего числа запросов на одну страницу) и/или чтение `Content-Length` основного `GET`-ответа. Кандидаты, которые не отвечают на `HEAD` или не отдают `Content-Length`, считаются «размер неизвестен» и обрабатываются по правилу «если ничего ≥ 1 МБ — берём первый по порядку».
   - **Что остаётся открытым:** допустимое число `HEAD`-запросов на одну страницу и общий тайм-аут «фазы выбора кандидата» — уточнить в тактической спеке.
   - **Статус:** Partially Resolved.

5. **Лимит размера и сетевой профиль** — **Resolved:** сетевой профиль — любая сеть; жёсткого лимита на итоговый размер скачиваемого файла нет (контроль на стороне записи в ресурс).

6. **Поведение при недоступности выбранного ресурса** — **Resolved:** fallback в Downloads с Toast-сообщением о причине.

7. **Размещение в дереве настроек** — **Resolved:** раздел «Поделиться/Приём» (Share/Receive), подсекция «Поведение». Тумблер верхнего уровня + два подчинённых селектора рядом.

8. **Обнаружение «является ли строка ссылкой»** — **Resolved:** мягкий режим — берётся первая найденная ссылка в тексте `EXTRA_TEXT`; всё, что не содержит ни одного `http(s)`-URL, идёт по старому пути (создание `.txt`).

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
| ------ | :-----------: | ----------- | --------- |
| Скачивание крупного файла на мобильной сети без явного согласия | Средняя | Расход трафика, претензии пользователя | Решение: разрешены любые сети по дизайну (см. §3.2); видимый прогресс с возможностью отмены; пользователь сам контролирует запуск канала тумблером |
| Парсер страниц не находит файл на популярных сайтах → ощущение «фича не работает» | Высокая | Снижение доверия к фиче, тикеты | Понятная ошибка «не нашли файл по ссылке»; в строках честно описан охват первой итерации (HTML, без стримов и blob); fallback к старому поведению (текст в `.txt`) опционально |
| Скачивание неподдерживаемого/потенциально вредоносного контента (исполняемые файлы, архивы) | Средняя | Безопасность, AppStore-политики | Whitelist по MIME/расширениям, остальное — отказ с явной ошибкой |
| Конфликт с включённым стандартным Share-sheet поведением для текстов | Низкая | Дубль операций, пользовательская путаница | Единая точка ветвления (§5.1, столп C): URL уходит только в новый канал; не-URL — в старый |
| Удалён/недоступен ресурс, на который указывает подчинённая настройка | Средняя | Молчаливая «потеря» файла «не туда» | Fallback в Downloads + явный Toast о причине fallback |
| Скрытые редиректы на `file://`/`content://` или внутренние схемы | Низкая | Потенциальный вектор атаки | Жёсткое ограничение: разрешены только `http(s)`, follow-redirect только по `http(s)` |
| Ожидание пользователя «как в YouTube-downloader» | Высокая | Жалобы «не работает с ..» | В пользовательских строках честно описать охват: «прямые ссылки и встроенные медиа HTML-страницы»; без обещаний по конкретным платформам и стримам |
| Авто-открытие нежелательного контента в плеере сразу после загрузки | Средняя | Внезапное проигрывание звука/видео в неподходящий момент | Подчинённая настройка «Автоматически открывать скачанное в плеере» (включена по умолчанию, но легко выключается одним тапом) |
| Множество `HEAD`-запросов на странице с десятками медиа-кандидатов | Низкая | Лишний трафик, замедление выбора | Лимит числа `HEAD`-запросов и общий тайм-аут «фазы выбора кандидата» (тактическая деталь, см. §6.4) |

## 8. Влияние на пользователя (docs/FEATURES)

«Share/Receive → Поведение: при получении ссылки приложение пытается автоматически скачать связанный файл (прямую ссылку или встроенное медиа HTML-страницы) в выбранный ресурс-получатель; при отсутствии выбора или недоступности ресурса — в системную папку Downloads с уведомлением. ## 9. Архитектурные решения (ADR)

### ADR-1: UX-парность с «Сохранить кадр»

- **Решение:** новая пара настроек повторяет существующую модель «общий тумблер + опциональный ресурс + Downloads-fallback».
- **Альтернативы:** отдельный экран «Загрузки по ссылке» с расширенными опциями; модальное «куда сохранить?» при каждом приёме ссылки.
- **Почему:** пользователь уже знаком с этим паттерном, минимизируется когнитивная нагрузка и количество новых строк.

### ADR-2: Извлекатель — отдельный столп с реестром стратегий

- **Решение:** канал приёма ссылок не знает деталей извлечения; стратегии (прямой файл / HTML-парсинг / возможный рендеринг страницы) сменяются за единым контрактом.
- **Альтернативы:** жёстко вшить парсинг в приёмник; отдать всё облачному сервису.
- **Почему:** позволит расширять охват источников без правок в настройках/UI и без регрессий в каналах Share-sheet.

### ADR-3: Whitelist MIME/расширений для записи

- **Решение:** автоскачивание разрешено только для медиа/документных типов, заявленных приложением; всё остальное — отказ с пользовательской ошибкой.
- **Альтернативы:** скачивать всё, MIME-фильтр на стороне UI.
- **Почему:** безопасность, соответствие политикам сторов, согласованность с разрешёнными медиатипами флейвора.

### ADR-4: Авто-открытие в плеере по умолчанию ВКЛЮЧЕНО

- **Решение:** третья настройка «Автоматически открывать скачанное в плеере» включена по умолчанию; при ВЫКЛ — закачка идёт молча.
- **Альтернативы:** всегда молчать (только Toast); всегда открывать; запрашивать у пользователя на каждый файл.
- **Почему:** типичный сценарий «увидел медиа в вебе → хочу посмотреть/положить» — пользователь почти всегда хочет немедленный preview; оставляем явный одно-кликовый отказ для тех, кому нужен только бэкграунд-сбор.

### ADR-5: Первая итерация — только HTML-парсинг, без стримов и blob

- **Решение:** на первой итерации извлекатель ограничен прямыми ссылками и статическим HTML; стримовые источники (HLS/DASH) и `data:`/`blob:` — следующая итерация как новые стратегии.
- **Альтернативы:** сразу делать управляемый веб-контекст и стрим-парсер.
- **Почему:** контроль объёма, быстрая поставка пользы, реестр стратегий уже заложен в столпе D — расширение не требует пересмотра настроек/UI.

## 11. Критерии готовности (strategic-level)

1. В настройках виден включённый по умолчанию тумблер «При получении ссылки — скачать» и подчинённый ему пустой по умолчанию селектор «Ресурс для закачки».
2. При выключенном тумблере поведение приёма входящих ссылок не отличается от текущего.
3. При включённом тумблере и пустом селекторе входящая ссылка-прямая на файл скачивается в системную папку Downloads, и пользователь видит итог операции.
4. При включённом тумблере и выбранном ресурсе скачанный файл оказывается в этом ресурсе; при недоступности ресурса — в Downloads, с пользовательским сообщением о причине fallback.
5. Для ссылки на HTML-страницу с одиночным встроенным медиа файл успешно скачивается в выбранный ресурс/Downloads без необходимости вручную открывать браузер.
6. Если по ссылке не удалось найти файл, пользователь получает понятное сообщение, и приложение не оставляет «битых» файлов в целевом ресурсе.
7. Все новые пользовательские строки (тумблер, селектор, прогресс, ошибки) присутствуют в EN, RU, UK.
8. Существующие сценарии Share-sheet с медиа-вложениями (`EXTRA_STREAM`) не регрессируют.
