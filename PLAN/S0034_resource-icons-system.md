---

## 1. Проблема

В настоящее время много ресурсов отображаются с одинаковыми иконками (обычно картинка какашки для неопределённых типов, нотка для музыки). Пользователю сложно быстро различать ресурсы в главном экране, особенно когда у него много библиотек одного типа. Отсутствует визуальное разнообразие и персонализация интерфейса.

---

## 2. Цели

1. Каждый ресурс получает уникальную, случайно выбранную иконку из тематического набора в зависимости от типа ресурса
2. Пользователь может менять иконку ресурса при создании и редактировании через удобный селектор
3. Главный экран становится визуально более разнообразным и узнаваемым
4. Предопределённые ресурсы ("Все фото", "Вся музыка") получают фиксированные иконки для консистентности между устройствами

**Non-goals:**

- Анимированные иконки
- Пользовательские изображения как иконки (только из встроенной библиотеки)
- Изменение подложек типов соединения (локальный/SMB/FTP/облачные)

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Векторные иконки для чёткого отображения на всех плотностях экрана
2. Тематические наборы: домики/цветочки/машинки для фототек, ноты/инструменты для музыки, кинопленки для видео
3. 10 иконок для музыки, 10 для видео, 10 для изображений, 10 для документов, 20 для остального
4. Возможность дополнения в наборах в будущих версиях

### 3.2 Жёсткие ограничения

- **Flavor:** standard, lite, photos, legacy — все затронуты
- **API level:** без API-специфики
- **Wear OS:** не затрагивается
- **Производительность:** иконки должны загружаться мгновенно, без заметной задержки UI
- **Совместимость данных:** миграция базы данных для добавления поля иконки существующим ресурсам
- **Локализация:** EN/RU/UK — названия иконок в селекторе (если нужны)
- **Доступность:** content description для каждой иконки, поддержка TalkBack

---

## 4. Контекст текущей архитектуры

Система ресурсов управляется слоем `data/repository` с хранением в Room базе данных. UI отображение происходит через адаптеры в главном экране и в редакторе ресурсов. Текущая логика определения иконок основана только на типе ресурса (`ResourceType`) и статичные иконки задаются в адаптере. Нет персональных настроек иконок для отдельных ресурсов.

---

## 5. Предлагаемый подход

### 5.1 Основные столпы / модули

**Библиотека иконок** — встроенная коллекция векторных drawable с уникальными идентификаторами, сгруппированная по типам ресурсов (музыка, видео, фото, документы, остальное).

**Система назначения** — логика случайного выбора иконки при создании ресурса с учётом типа, сохранение выбора пользователя, фиксированные иконки для предопределённых ресурсов.

**UI селектор** — интерфейс выбора иконки в форме создания/редактирования ресурса с предпросмотром и группировкой по типам.

### 5.2 Потоки данных и событий

`UI создания ресурса → случайный выбор иконки по типу → сохранение в Room → отображение в адаптерах`. При редактировании: `UI селектора → выбор пользователя → обновление в Room → обновление отображения`. Миграция существующих ресурсов происходит при обновлении базы данных с назначением случайных иконок.

### 5.3 Точки расширяемости

Система должна поддерживать добавление новых наборов иконок без изменения схемы базы данных. Идентификаторы иконок должны быть стабильными между версиями приложения.

## 6. Открытые вопросы / Research items

1. **Композитная иконка или отдельные элементы**
   - **Вопрос:** создавать композитную иконку (подложка типа соединения + тематическая иконка) программно или использовать отдельные слои?
   - **Варианты:** LayerDrawable в коде, готовые композитные drawable, Canvas рисование
   - **Решение:** LayerDrawable с двумя слоями — прозрачный квадрат с маленьким значком типа источника в левом верхнем углу (фон) + центрированная иконка из библиотеки поверх него. Пользователь видит неизменяемый индикатор типа источника в углу и настраиваемую тематическую иконку в центре.
   - **Статус:** Resolved

2. **Хранение идентификатора иконки**
   - **Вопрос:** как хранить связь ресурс-иконка для стабильности между версиями?
   - **Варианты:** числовой ID, строковый ключ, enum
   - **Решение:** строковый формат `ico-[xx]-[nnn]` где xx — тип ресурса от 01-99 (например, 01 для аудиотеки), nnn — порядковый номер 001-999 в наборе. Позволяет легко пополнять наборы и группировать по типам.
   - **Статус:** Resolved

3. **Промпт для дизайнера**
   - **Вопрос:** нужен ли готовый промпт для заказа векторных иконок у дизайнера?
   - **Варианты:** детальное ТЗ, референсы стиля, размеры и форматы
   - **Решение:** да, нужен полный промпт на все наборы с указанием размеров, технических условий и детального описания тематики каждого набора для передачи дизайнеру.
   - **Статус:** Resolved

4. **Размещение селектора иконок**
   - **Вопрос:** где в UI формы создания/редактирования ресурса разместить кнопку выбора иконки?
   - **Варианты:** в шапке формы, в секции "Дополнительно", отдельный экран
   - **Решение:** в шапке формы, прижато к правому краю экрана для быстрого доступа без прокрутки.
   - **Статус:** Resolved

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Большой размер APK из-за множества векторных drawable | Средняя | Увеличение размера приложения на несколько МБ | Оптимизация векторов, использование общих элементов |
| Производительность отрисовки композитных иконок | Низкая | Подтормаживания в списках ресурсов | Кэширование растровых версий, ленивая загрузка |
| Миграция базы данных сломает существующие ресурсы | Низкая | Потеря данных пользователей | Тщательное тестирование миграции, резервные копии |

## 8. Влияние на пользователя (docs/FEATURES)

Визуальные иконки ресурсов — персонализация и улучшенная навигация в библиотеках медиа-файлов с тематическими наборами иконок.

## 9. Архитектурные решения (ADR)

**ADR-1: Встроенная библиотека иконок vs внешние ресурсы**

- **Решение:** все иконки встраиваются в APK как векторные drawable
- **Альтернативы:** загрузка иконок из сети, пользовательские изображения
- **Почему:** гарантированная доступность, контроль качества, отсутствие зависимости от сети

**ADR-2: Композитная отрисовка vs готовые варианты**

- **Решение:** программная композиция LayerDrawable (подложка + тематическая иконка)
- **Альтернативы:** заранее подготовленные комбинации всех вариантов
- **Почему:** меньший размер APK, гибкость добавления новых типов соединений

## 11. Критерии готовности (strategic-level)

1. При создании нового ресурса пользователь видит случайно назначенную тематическую иконку
2. Пользователь может изменить иконку ресурса через селектор в форме редактирования (нажав на иконку)
3. Главный экран показывает разнообразные иконки вместо однотипных изображений
4. Предопределённые ресурсы ("Все фото", "Вся музыка") имеют одинаковые иконки на всех устройствах
5. Существующие ресурсы получают случайные тематические иконки при первом запуске новой версии
