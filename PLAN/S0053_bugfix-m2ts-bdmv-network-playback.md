---

## 1. Проблема

Файлы `.m2ts` из структуры Blu-ray (каталог `BDMV/STREAM`) не воспроизводятся через сетевые ресурсы (SFTP, SMB, FTP). ExoPlayer не распознаёт формат и немедленно выдаёт ошибку. Fallback на системный MediaPlayer при этом не срабатывает, хотя такой fallback существует для локальных файлов. Пользователь видит ошибку воспроизведения без объяснения причины и без альтернативы. Аналогичное поведение ожидаемо для других контейнеров Blu-ray (`.m2t`, Blu-ray TS с 192-байтовыми пакетами).

---

## 2. Цели

1. Файлы `.m2ts` из сетевых источников воспроизводятся — либо через настройку ExoPlayer для работы с 192-байтовыми BD-пакетами, либо через fallback на системный MediaPlayer.
2. Если воспроизведение технически невозможно (кодек не поддерживается устройством) — пользователю показывается понятное сообщение об ошибке с указанием причины (формат не поддерживается), а не молчаливая ошибка.
3. Fallback на MediaPlayer при ошибке ExoPlayer на сетевом пути работает по тем же правилам, что и для локального пути — либо разрешается, либо явно запрещается с документированным обоснованием.
4. Поведение при воспроизведении `.m2ts` через локальный источник не ухудшается.

**Non-goals:**

- Поддержка полного Blu-ray меню/навигации.
- Декодирование DRM-защищённых BD-дисков.
- Поддержка форматов HD DVD.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Если ExoPlayer не может воспроизвести формат — желателен автоматический fallback на MediaPlayer без вмешательства пользователя.
2. Желательна поддержка `.m2ts` через SMB и FTP аналогично SFTP.

### 3.2 Жёсткие ограничения

- **Flavor:** standard, lite, legacy (все флейворы с видео).
- **API level:** minSdk 26; MediaPlayer доступен на всех поддерживаемых версиях.
- **Wear OS:** не затрагивается.
- **Производительность:** fallback не должен добавлять более 3 секунд к времени начала воспроизведения.
- **Совместимость данных:** изменений схемы Room не требуется.
- **Локализация:** строка сообщения об ошибке — EN/RU/UK (если добавляется новый текст).
- **Доступность:** не затрагивается.

## 4. Контекст текущей архитектуры

ExoPlayer в текущей конфигурации использует набор встроенных экстракторов для детекции контейнера. MPEG-TS экстрактор ожидает 188-байтовые пакеты; Blu-ray Transport Stream использует 192-байтовые пакеты (4 байта заголовка + 188 байт MPEG-TS). Это приводит к ошибке «None of the available extractors could read the stream».

Механизм fallback на MediaPlayer существует в слое управления воспроизведением, но текущая реализация явно его пропускает для сетевых путей (зафиксировано в логе: «MediaPlayer fallback skipped»). Причина пропуска — предположение, что MediaPlayer не может открыть сетевой URI напрямую, однако это верно лишь для части протоколов; SMB и SFTP недоступны для MediaPlayer, тогда как HTTP/HTTPS — доступны.

## 5. Предлагаемый подход

### 5.1 Основные столпы / модули

**А. Исследование ExoPlayer: поддержка BD-пакетов**
Проверить, поддерживает ли Media3 1.2.1 192-байтовые BD-пакеты через параметры экстрактора или флаги `DefaultExtractorsFactory`. Если да — включить соответствующий флаг.

**Б. Ревизия логики fallback**
Текущий запрет fallback на сетевых путях пересмотреть: определить, может ли системный MediaPlayer получить данные через локальный прокси (уже используемый в проекте для других целей). Если прокси доступен — разрешить fallback через него.

**В. Диагностическое сообщение об ошибке**
Если ни ExoPlayer, ни MediaPlayer не могут воспроизвести файл — показывать информативный диалог с указанием формата и рекомендацией (например, перекодировать). Не молчать.

**Г. Проверка для других сетевых протоколов**
Убедиться, что поведение идентично для SMB и FTP (не только SFTP).

### 5.2 Потоки данных и событий

```
Открытие .m2ts через сетевой источник
  → ExoPlayer пробует экстракторы
     → Вариант A: BD-пакеты поддерживаются → воспроизведение идёт
     → Вариант B: ошибка детекции
          → проверить: доступен ли прокси для MediaPlayer
             → да → fallback через прокси
             → нет → показать понятную ошибку пользователю
```

### 5.3 Точки расширяемости

- Логика выбора fallback должна допускать добавление новых проверок (например, для будущих протоколов) без переписывания основного пути.

## 9. Архитектурные решения (ADR)

**ADR-1: ExoPlayer с BD-флагом vs прокси для MediaPlayer**

- **Решение:** Сначала исследовать путь А (флаг ExoPlayer) — нулевые накладные расходы. Путь Б (прокси) — запасной вариант с бо́льшей сложностью.
- **Альтернативы:** (a) ExoPlayer BD-флаг; (b) прокси для MediaPlayer; (c) скачивание первых MB файла во временный буфер и передача MediaPlayer.
- **Почему:** Вариант (c) неприемлем для файлов 500+ МБ. Прокси уже существует — переиспользование предпочтительнее нового кода.

**ADR-2: Информативная ошибка как минимум**

- **Решение:** Независимо от результата исследования ExoPlayer/прокси — минимальный исход: показывать пользователю конкретную ошибку «формат не поддерживается» вместо молчаливого сбоя.
- **Альтернативы:** Оставить текущее поведение.
- **Почему:** Молчаливый сбой нарушает базовый UX-принцип: пользователь должен знать, почему файл не открывается.

## 11. Критерии готовности (strategic-level)

1. Файл `.m2ts` из BDMV-структуры открывается через SFTP и воспроизводится (видео+аудио), или пользователь видит внятное сообщение «формат не поддерживается» — никакого молчаливого сбоя.
2. Seek работает корректно (прыжок к середине файла 500+ МБ).
3. Аналогичное поведение проверено на SMB и FTP источниках.
4. Воспроизведение `.m2ts` через локальный источник не изменилось.
