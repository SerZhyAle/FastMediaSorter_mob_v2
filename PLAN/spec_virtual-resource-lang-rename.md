## 1. Проблема

Приложение предоставляет шесть предопределённых виртуальных ресурсов («Недавние медиа», «Вся музыка», «Все видео» и т.д.), имена и описания которых задаются из строковых ресурсов в момент создания. При переключении языка (EN → RU → UK) ранее созданные ресурсы остаются с именами и комментариями на исходном языке, даже если пользователь никогда не редактировал их вручную. Это создаёт несогласованность интерфейса: ресурсы в главном списке показывают «All Images» при том, что весь остальной UI уже переведён на русский.

---

## 2. Цели

1. После смены языка все виртуальные ресурсы, имя/комментарий которых совпадают с дефолтным значением на одном из поддерживаемых языков, автоматически переименовываются в дефолт нового языка без участия пользователя.
2. Ресурсы, имя или комментарий которых были вручную изменены пользователем, не затрагиваются.
3. Поведение корректно для всех существующих установок (не только для свежих, созданных после выхода обновления).

**Non-goals:**

- Переименование ресурсов, добавленных пользователем вручную (физические папки, сетевые, облачные) — только предопределённые виртуальные пути.
- Немедленное переименование «на лету» во время сессии без рестарта — переключение языка всегда предполагает рестарт приложения, хук достаточно вызывать при старте.
- Поддержка дополнительных языков помимо EN/RU/UK.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Операция должна быть полностью незаметной для пользователя — никаких диалогов, уведомлений или лоудеров.
2. Сопоставление должно работать «вперёд и назад»: если пользователь создал ресурсы в RU, потом переключился на EN, и снова вернулся в RU — имена корректно восстанавливаются каждый раз.

### 3.2 Жёсткие ограничения

- **Flavor:** все флейворы (`standard`, `lite`, `photos`, `legacy`) — виртуальные ресурсы присутствуют во всех; конкретные пути ограничены `BuildConfig`-флагами уже в момент провизии, логика авторенейма их уважает.
- **API level:** без API-специфики — логика работает на уровне Room/DataStore, не зависит от версии Android.
- **Wear OS:** не затрагивается.
- **Производительность:** операция выполняется однажды при старте приложения, проверяет максимум 6 записей в базе — пренебрежимо мала по времени.
- **Совместимость данных:** схема Room не меняется; обновляются только текстовые поля существующих записей через штатный `updateResource`.
- **Локализация:** EN / RU / UK — все три языка участвуют как в качестве «источника» (прежний язык), так и «цели» (новый язык). Таблица сопоставлений жёстко закодирована в коде, строковые ресурсы Android в рантайме для определения старого языка не используются.
- **Доступность:** не применимо — фича не визуальная, не меняет UI-компоненты.

## 4. Контекст текущей архитектуры

Шесть виртуальных ресурсов создаются однократно при первом запуске: компонент провизии (в слое domain/use-cases) запрашивает строки из Android-ресурсов в активной локали и сохраняет их в Room-базу как обычные текстовые поля объекта ресурса. После сохранения эти поля живут в базе независимо от локали приложения — система локализации Android автоматически не обновляет уже сохранённые строки.

При смене языка `LocaleHelper` сохраняет выбор в DataStore/SharedPreferences и перезапускает приложение. После рестарта UI читает ресурсы из Room и отображает сохранённые (устаревшие) имена. Никакого хука «язык изменился → обнови зависимые данные» в текущей архитектуре нет — компонент инициализации приложения при старте не проверяет соответствие языка и содержимого базы.

---

## 5. Предлагаемый подход

При каждом старте приложения запускается лёгкий компонент сверки языка ресурсов. Он:

1. Читает текущий активный язык приложения.
2. Загружает из базы все ресурсы с виртуальными путями.
3. Для каждого такого ресурса проверяет, совпадает ли его имя (и/или комментарий) с **любым** из трёх зафиксированных дефолтных значений на одном из языков. Таблица сопоставлений «виртуальный путь × язык → (имя, комментарий)» жёстко задана прямо в коде — она мала, стабильна и не зависит от локализованных строк времени выполнения.
4. Если нашли совпадение с языком, отличным от текущего, — обновляем поле(я) в базе на значение для текущего языка.
5. Операция идемпотентна: повторный запуск без смены языка ничего не делает, так как имена уже соответствуют текущему языку.

Подход «сравни со всеми известными языками» (а не только с «предыдущим») гарантирует корректную работу для существующих пользователей, которые установят обновление уже имея ресурсы с именами на любом из трёх языков.

### 5.1 Основные столпы / модули

**Таблица дефолтных имён** — неизменяемый каталог: виртуальный путь × язык → (имя, комментарий). Является единственным авторитетным источником того, что считать «системным именем». Хранится рядом с логикой авторенейма, не в строковых ресурсах.

**Компонент авторенейма** — use-case в слое domain. Вызывается при инициализации приложения (не в UI-слое). Читает ресурсы из репозитория, применяет таблицу, сохраняет изменения через тот же репозиторий.

**Хук инициализации** — существующий компонент запуска приложения, который уже выполняет схожие «починочные» операции (исправление флага isWritable, миграция старых путей камеры и т.д.). Новый компонент авторенейма добавляется в ту же очередь вызовов.

### 5.2 Потоки данных и событий

```text
Старт приложения
  └→ Хук инициализации
       └→ Компонент авторенейма
            ├→ Читает текущий язык (из настроек)
            ├→ Читает все ресурсы (из репозитория)
            ├→ Для каждого виртуального ресурса
            │    ├─ Сверяет имя/комментарий с таблицей дефолтов
            │    └─ Если нашёл совпадение с другим языком → пишет новые значения
            └→ Конец (всё в фоне, UI не ждёт)
```

### 5.3 Точки расширяемости

- При добавлении нового виртуального пути в приложение достаточно добавить строку в таблицу дефолтных имён — логика авторенейма подхватит её без изменений.
- При добавлении нового поддерживаемого языка — добавить колонку в таблицу.

## 9. Архитектурные решения (ADR)

**ADR-1: Сравнение со всеми языками, а не только с «предыдущим»**

- **Решение:** вместо хранения «какой язык был активен при последнем переименовании» сравниваем каждое имя/комментарий со всеми тремя языковыми дефолтами одновременно.
- **Альтернативы:** хранить `lastRenamedLang` в настройках и сравнивать только с ним.
- **Почему так:** подход «со всеми» работает корректно для существующих пользователей, которые установили обновление в произвольном состоянии (ресурсы могут быть на любом языке). Исключает необходимость добавлять поле в настройки (нет изменений в DataStore-схеме). Таблица мала и статична, накладные расходы пренебрежимы.

**ADR-2: Жёстко закодированная таблица дефолтов вместо чтения строковых ресурсов**

- **Решение:** все 6 × 3 = 18 пар (имя, комментарий) заданы прямо в коде компонента авторенейма, а не через `context.getString()` с переключением локали.
- **Альтернативы:** динамически создавать контекст с нужной локалью и читать через `getString()`.
- **Почему так:** жёсткий вариант проще, нет риска расхождения с тем, что `getString()` вернёт при конкретной конфигурации устройства. Строки стабильны — менять их следует осознанно, одновременно обновляя и `strings.xml`, и таблицу.

## 11. Критерии готовности (strategic-level)

1. После переключения языка с EN на RU все шесть виртуальных ресурсов при следующем старте приложения показывают русские имена и комментарии — при условии, что пользователь не менял их вручную.
2. Ресурс с кастомным именем (не совпадающим ни с одним дефолтом) остаётся без изменений после смены языка.
3. Повторный старт без смены языка не вызывает никаких записей в базу.
4. Операция полностью выполняется в фоне, не блокирует запуск UI.
