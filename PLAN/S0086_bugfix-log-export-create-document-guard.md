## 1. Проблема

При нажатии кнопки «Сохранить лог» в настройках приложение запускает системный интент `ACTION_CREATE_DOCUMENT` (выбор места сохранения файла). На устройствах с кастомной прошивкой, где нет встроенного файлового менеджера (SPRD/минималистичный AOSP), система не может найти обработчика интента, и Android бросает `ActivityNotFoundException`. В текущей реализации исключение перехватывается и как логируется полный stacktrace на уровне WARNING, так и показывается диалог с предложением поделиться файлом вместо сохранения. Пользователь в итоге получает нужный результат (экспорт через Share), но в лог записывается шумный stacktrace, который засоряет диагностику и потенциально попадает в любой pipeline отчётов о сбоях.

---

## 2. Цели

1. При нажатии «Сохранить лог» на устройствах без файлового менеджера сразу показывается диалог с предложением поделиться файлом — без предварительного броска и перехвата исключения.
2. Предупреждение `LogExport: CREATE_DOCUMENT not supported — falling back to share` со stacktrace перестаёт появляться в логе в штатном сценарии (файловый менеджер отсутствует — это ожидаемо, не ошибка).
3. На устройствах с файловым менеджером поведение не меняется — `ACTION_CREATE_DOCUMENT` запускается как раньше.

**Non-goals:**

- Изменение самого flow экспорта (ZIP, share, диалог подтверждения).
- Поддержка дополнительных форматов экспорта.
- Обнаружение отсутствия файлового менеджера до нажатия кнопки (кнопку скрывать не нужно).

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Заменить catch-and-fallback паттерн на guard-and-select: проверить поддержку интента до попытки его запуска, а не ловить исключение постфактум.
2. Если решение guard с `resolveActivity` несовместимо с API 11+ (manifest `<queries>` requirement для `ACTION_CREATE_DOCUMENT`), выбрать наиболее надёжный альтернативный способ проверки.

### 3.2 Жёсткие ограничения

- **Flavor:** `standard`, `lite`, `photos`, `legacy` — экспорт лога доступен во всех флейворах.
- **API level:** minSdk 26 (legacy minSdk 23). `resolveActivity()` без `<queries>` работает корректно для системных интентов (`ACTION_CREATE_DOCUMENT` — implicit query, не требует явного объявления). На Android 11+ (API 30) для кастомных интентов потребовалось бы изменение манифеста, но для `ACTION_CREATE_DOCUMENT` этого не нужно.
- **Wear OS:** не затрагивается.
- **Производительность:** не затрагивается.
- **Совместимость данных:** нет изменений.
- **Локализация:** нет изменений в строках.
- **Доступность:** не затрагивается.

## 4. Контекст текущей архитектуры

Кнопка «Сохранить лог» живёт в настройках приложения. Логика обработки нажатия вынесена во вспомогательный класс UI-слоя, который управляет `ActivityResultLauncher` (зарегистрированным для `ACTION_CREATE_DOCUMENT`) и отображает диалоги. При нажатии кнопки лаунчер вызывается напрямую без предварительной проверки поддержки интента. Android бросает `ActivityNotFoundException` внутри системного кода запуска, который перехватывается в catch-блоке и логируется вместе со stacktrace.

Проблема в том, что использование catch-блока для управления потоком выполнения (flow control) вместо предусловия считается анти-паттерном, и в данном случае это приводит к ложно-позитивному шуму в диагностических логах — тем более что SPRD-устройства воспроизводят это на каждом нажатии.

---

## 5. Предлагаемый подход

Перед попыткой запуска лаунчера проверить, есть ли в системе активити, способное обработать `ACTION_CREATE_DOCUMENT` (через `resolveActivity` или `queryIntentActivities` менеджера пакетов). Если обработчик не найден — немедленно вызвать логику показа диалога «не поддерживается», не запуская лаунчер. Исключение в этом сценарии не бросается.

### 5.1 Основные столпы / модули

**A. Предварительная проверка поддержки интента**
Формирование тестового `Intent(ACTION_CREATE_DOCUMENT)` и вызов системного API проверки наличия обработчика. Результат (bool) определяет ветку: запустить лаунчер или перейти к диалогу fallback.

**B. Сохранение fallback-диалога**
Существующий диалог «сохранение не поддерживается» (с кнопкой «Поделиться») остаётся без изменений — он просто вызывается напрямую, а не через catch.

### 5.2 Потоки данных и событий

```
Нажатие «Сохранить лог»
    ↓
Проверка: есть ли обработчик ACTION_CREATE_DOCUMENT?
    Да → запустить ActivityResultLauncher (поведение без изменений)
    Нет → показать fallback-диалог (без броска исключения)
```

### 5.3 Точки расширяемости

- Логика проверки интента изолирована — в будущем можно использовать тот же паттерн для других условных интентов (например, `ACTION_PRINT`).

## 9. Архитектурные решения (ADR)

**ADR-1: `resolveActivity()` vs. `try/catch` как способ определения поддержки интента**

- **Решение:** использовать `resolveActivity()` до запуска лаунчера.
- **Альтернативы:** оставить `try/catch`, но понизить уровень лога с `w` до `d` при известном сценарии отсутствия файлового менеджера.
- **Почему:** guard-подход семантически корректен и не генерирует исключение как инструмент flow control. Понижение уровня лога в `catch` убирает шум, но оставляет анти-паттерн в коде.

## 11. Критерии готовности (strategic-level)

1. На устройстве SPRD (или любом Android без файлового менеджера): нажатие «Сохранить лог» показывает fallback-диалог без `ActivityNotFoundException` в логе.
2. На обычном Android-устройстве с файловым менеджером: нажатие «Сохранить лог» открывает системный пикер сохранения файла — как раньше.
3. Лог не содержит stacktrace `ActivityNotFoundException` в контексте экспорта логов в штатных сценариях.
