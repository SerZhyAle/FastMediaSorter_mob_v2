## 1. Проблема

- У семейства `/spec*` нет единого операторского слоя поверх журнала спек.
- Базовые CLI-примитивы уже существуют, но типовые сценарии по-прежнему собираются вручную из нескольких низкоуровневых действий.
- Из-за этого промпты начинают дублировать исполняемую логику каталога: сами ищут следующий id, сами описывают составные переходы статусов, сами знают детали поиска.
- Это увеличивает RTT, делает поведение скиллов хрупким и ведёт к дрейфу между журналом, скриптами и текстом промптов.
- Параллельно деградирует и текстовый слой: новые стратегические и тактические спеки перегружаются таблицами, псевдографикой и самоочевидными связями.
- Для кодовых спек нет явного следа в логах, который подтверждает, что изменённый путь действительно был пройден при проверке.

---

## 2. Цели

1. Следующий свободный id получается одной детерминированной командой с машинно-читаемым stdout.
2. Поиск по каталогу работает по обычной подстроке и дополнительным метаданным без знания glob-синтаксиса со стороны вызывающего.
3. Перевод спеки в финальный статус оформлен как отдельное операторское действие с предсказуемым результатом и явными защитными правилами.
4. Сводка по каталогу доступна одной командой как в консольном, так и в машинно-читаемом виде.
5. Пакетные обновления статуса и приоритета выполняются по принципу «всё или ничего».
6. Все `/spec*`-скиллы используют одну и ту же операторскую поверхность вместо дублирования логики каталога в промптах.
7. Журнал допускает расширение опциональными метаданными без обязательной миграции старых записей.
8. Новые стратегические и тактические спеки с первого черновика следуют минималистичному стилю: списки вместо таблиц, без псевдографики и самоочевидных связей.
9. Кодовые спеки получают явный верификационный след во время реализации и очищают его при финальном закрытии.

**Non-goals:**

- Графический или веб-интерфейс к каталогу.
- Интеграция с внешними трекерами.
- Синхронизация каталога между git-ветками.
- Полная замена текущего низкоуровневого CLI новым монолитным роутером.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Команда выделения следующего id печатает ровно один токен `S####` без лишнего текста.
2. Поиск принимает обычный текстовый запрос и, при необходимости, дополнительные фильтры по метаданным.
3. Сводка по каталогу имеет компактный человеко-читаемый режим и структурированный JSON-режим.
4. Пакетное обновление либо применяет весь набор изменений, либо не меняет журнал вообще.
5. Новый инструментарий остаётся совместимым с PowerShell 5.1.

### 3.2 Жёсткие ограничения

- **Flavor:** продуктовые сборки не затрагиваются.
- **API level:** без Android API-специфики.
- **Wear OS:** не затрагивается.
- **Производительность:** команды должны оставаться интерактивными на каталоге порядка нескольких сотен записей.
- **Совместимость данных:** текущий формат журнала сохраняется; новые поля только добавочные и опциональные.
- **Валидация:** проверка каталога проходит после любой поддерживаемой мутации.
- **Локализация:** скрипты и их технический вывод могут оставаться на английском.
- **Доступность:** не применимо.

---

## 4. Контекст текущей архитектуры

- Журнал спек уже обслуживается набором низкоуровневых PowerShell-скриптов и общей библиотекой функций.
- Текущий слой хранения и базовых операций покрывает выделение id, чтение, выборку, обновление, удаление, валидацию и расчёт staleness.
- Корневая проблема не в формате данных, а в отсутствии стабильного фасада для типовых операторских сценариев: выделить id, найти спеку, закрыть спеку, увидеть сводку, обновить пачку тикетов.
- Пока этого фасада нет, файлы промптов берут на себя лишнюю оркестрационную логику и становятся частью исполнения.

---

## 5. Предлагаемый подход

Добавить тонкий операторский слой поверх существующих примитивов каталога и привязать к нему правила генерации и верификации спек. Новая поверхность должна упростить типовые действия, не ломая текущий журнал и не создавая второй независимый источник истины.

### 5.1 Основные блоки

**Расширение схемы журнала**

- `title` хранит человеко-читаемое имя спеки для удобного поиска и вывода.
- `tags` вводят тематические метки, не завязанные на slug.
- `blocked_by` описывает явные зависимости между тикетами.
- `type` фиксирует вид работы: `feature`, `bugfix`, `tooling`, `research` и др.
- `closed_at` отделяет фактическое закрытие спеки от обычного обновления поля `updated`.
- `has_tactical` отражает наличие тактической декомпозиции.
- Отсутствие этих полей в старых записях остаётся валидным.

**Операторские команды**

- `next-id` возвращает следующий свободный id в машинно-дружественном виде.
- `search` находит записи по подстроке и, когда данные есть, по дополнительным фильтрам вроде status или tag.
- `close` выполняет финализацию одной спеки и фиксирует семантику закрытия.
- `stats` даёт распределение по статусам, stale-срез, недавнюю активность и приоритетные тикеты.
- `bulk-update` валидирует весь входной набор до единственной записи результата.

**Правила написания спек**

- Генераторы стратегических и тактических спек используют единый минималистичный стиль.
- Форматирование перестаёт быть «рекомендацией по вкусу» и становится частью рабочего контракта `/spec*`.

**Верификационный след для кодовых спек**

- Во время реализации на входах изменённых потоков добавляются короткие маркеры `Timber.d("Sxxxx: ...")`.
- При финальном закрытии спеки эти маркеры удаляются как часть того же жизненного цикла.

### 5.2 Операционные потоки

- Создание спеки запрашивает id у выделенной команды, затем синхронизирует журнал и артефакт спеки.
- Поиск работает напрямую по данным каталога, а не через glob-конструкции, собранные на стороне промпта.
- Закрытие спеки использует отдельную операцию финализации, а не длинную композицию низкоуровневых флагов.
- Пакетные изменения сначала валидируют весь набор идентификаторов и только затем меняют журнал.
- Сводка строится из одного снимка журнала и выдаёт согласованные данные для человека и автоматики.

### 5.3 Точки расширяемости

- Поиск может позже получить фильтры по tier, type, диапазону priority и зависимостям.
- Сводка может стать источником CI-правил для stale и blocked budget.
- Если после внедрения CLI всё ещё создаёт трение, тот же операторский слой можно будет обернуть в MCP без смены семантики жизненного цикла.

## 7. Риски

1. Операторские команды начнут копировать низкоуровневое поведение вместо повторного использования единого источника истины.

- **Вероятность:** Низкая.
- **Последствия:** дрейф семантики каталога между командами и скиллами.
- **Митигация:** фасады оркестрируют, но не дублируют базовую логику мутаций и валидации.

2. Контракт пакетных изменений останется недоопределённым.

- **Вероятность:** Низкая.
- **Последствия:** частичные изменения журнала или разные ожидания у операторов и автоматики.
- **Митигация:** принцип «всё или ничего» фиксируется как часть пользовательского контракта, а не как внутренняя деталь.

3. Семантика финализации конфликтует с процессом block-состояний.

- **Вероятность:** Средняя.
- **Последствия:** `/spec-check` и ручные сценарии закрытия начинают расходиться.
- **Митигация:** правило перехода Block -> final определяется до тактической декомпозиции.

4. Правила написания спек разойдутся с реальным поведением скиллов.

- **Вероятность:** Средняя.
- **Последствия:** CLI станет удобнее, но новые спеки всё равно останутся шумными и непоследовательными.
- **Митигация:** style и verification входят в тот же acceptance scope, что и операторские команды.

## 9. Архитектурные решения (ADR)

**ADR-1: Отдельный операторский фасад над текущим низкоуровневым CLI**

- **Решение:** добавить небольшой набор команд для типовых сценариев вместо наращивания сигнатур каждого базового скрипта.
- **Альтернативы:** продолжать собирать сценарии из низкоуровневых команд прямо в промптах; заменить текущий CLI одним монолитным роутером.
- **Почему:** это уменьшает дрейф, сохраняет текущие контракты и вводит стабильные точки входа для `/spec*`.

**ADR-2: Единый авторитетный путь изменения статуса**

- **Решение:** финализация должна переиспользовать существующую семантику мутации статусов, а не создавать второй независимый механизм записи журнала.
- **Альтернативы:** разрешить каждой новой команде менять записи каталога напрямую.
- **Почему:** логика закрытия, audit-метаданные и валидация не должны расходиться между командами.

**ADR-3: Стиль и верификация входят в ergonomics-объём этой спеки**

- **Решение:** минималистичный стиль спек и debug-маркеры рассматриваются как часть той же проблемы, что и неудобный CLI.
- **Альтернативы:** сначала чинить только команды, а текстовый и верификационный слой вынести в отдельную housekeeping-спеку.
- **Почему:** текущая боль оператора одновременно процедурная и когнитивная; исправление только CLI оставит заметную часть трения нетронутой.

## 11. Критерии готовности (strategic-level)

1. Вызывающий получает следующий id одной командой и видит в stdout только `S####`.
2. Вызывающий находит нужные спеки обычным текстовым запросом, а при наличии метаданных может сузить выборку по status или tag.
3. Финальное закрытие спеки доступно как отдельное операторское действие с предсказуемым success/failure-поведением.
4. Одна команда сводки показывает распределение по статусам, stale-счётчики, недавние изменения и приоритетные тикеты в консольном и JSON-режиме.
5. Пакетное обновление либо применяет весь набор изменений, либо оставляет журнал без изменений.
6. Валидация каталога остаётся зелёной как для старых записей без новых полей, так и для новых записей с дополнительными метаданными.
7. В слое промптов `/spec*` больше нет ручного разбора журнала и длинных низкоуровневых последовательностей для типовых операций.
8. Новая стратегическая или тактическая спека с первого прохода соответствует минималистичному стилю без таблиц там, где достаточно списков, и без псевдографики.
9. Кодовая спека во время реализации оставляет в логах `Timber.d("Sxxxx: ...")`, а после финальной верификации таких маркеров в коде не остаётся.
10. Фактическое время закрытия спеки фиксируется отдельно от рутинного обновления поля `updated`.
