## 1. Проблема

В сессии 2026-05-04 сканирование SFTP-ресурса (resourceId=33, сервер `46.54.0.135:22022`) заняло 265 757 мс — в 44 раза больше порогового значения 6 000 мс. На протяжении всего сканирования пользователь видит пустой список без каких-либо индикаторов прогресса: складывается ощущение, что ресурс недоступен. При анализе кода выявлена двойная сетевая работа: сначала протокол SSH возвращает полный каталог с атрибутами файлов (размер, тип) в одном ответе, но затем для каждого подходящего файла выполняется отдельный запрос `stat()` по той же сети — только чтобы получить уже известный размер. Итоговое число round-trip-запросов линейно зависит от количества файлов в ресурсе.

---

## 2. Цели

1. Сканирование SFTP-ресурса с несколькими сотнями медиафайлов завершается за время, сопоставимое с SMB-ресурсом аналогичного размера, — без повторных `stat()`-запросов на файлы.
2. Во время сканирования пользователь видит прогресс (счётчик обработанных файлов или процент), а не пустой список.
3. Метрика `ScanMetrics: SLOW SCAN` перестаёт срабатывать для SFTP-ресурсов с нормальным объёмом контента.
4. Если сервер использует нестандартный формат `ls`-ответа, в котором атрибуты недоступны, сканер прозрачно откатывается к старому поведению с отдельными `stat()`-запросами.

**Non-goals:**

- Кэширование результатов сканирования между сессиями (это область S0056 и смежных тикетов).
- Изменение поведения для FTP или SMB-ресурсов.
- Поддержка параллельного (многопоточного) SFTP-листинга.
- Изменение порогового значения `ScanMetrics` (6 000 мс).

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Прогресс-индикатор сканирования уже реализован (S0068) — убедиться, что SFTP-сканирование фактически вызывает имеющийся колбэк прогресса, а не просто принимает его в сигнатуре метода.
2. Обратная совместимость: если `LsEntry` сервера не содержит атрибутов (редкий случай для нестандартных реализаций SFTP) — сканирование продолжается корректно, без сбоя.

### 3.2 Жёсткие ограничения

- **Flavor:** `standard`, `legacy` — SFTP поддерживается только в них (нет в `lite`, `photos`).
- **API level:** без API-специфики.
- **Wear OS:** не затрагивается.
- **Производительность:** изменение должно снижать число сетевых запросов, а не увеличивать его; суммарный трафик не должен расти.
- **Совместимость данных:** изменений в постоянном хранилище нет.
- **Локализация:** нет изменений в пользовательских строках, кроме, возможно, уточнения текста прогресса сканирования; если строка добавляется — обязательно EN/RU/UK.
- **Доступность:** не затрагивается.

## 4. Контекст текущей архитектуры

Слой сетевого доступа к SFTP состоит из двух компонентов: низкоуровневого клиента (обёртка над JSch), который выполняет SSH-команды и управляет пулом соединений, и сканера, который интерпретирует результаты листинга и формирует список медиафайлов. Клиент имеет метод листинга директории и отдельный метод получения атрибутов файла (`stat()`).

Проблема в двойной работе на границе между этими компонентами: протокол SSH команды `ls` возвращает атрибуты всех файлов каталога одним ответом (это часть стандарта SFTP/SSH); JSch кладёт эти атрибуты в объект `LsEntry`. Однако текущая реализация метода листинга отбрасывает атрибуты и возвращает только строки-пути. Сканер затем вынужден запрашивать атрибуты заново для каждого файла через отдельный `stat()`-вызов — каждый из которых является отдельным сетевым round-trip через тот же пул соединений.

---

## 5. Предлагаемый подход

Изменить контракт метода листинга в сетевом клиенте так, чтобы он возвращал пары «путь + атрибуты» вместо только путей. Атрибуты (размер файла, флаг директории, время модификации) уже доступны в объекте `LsEntry` без дополнительных запросов. Сканер использует эти атрибуты напрямую и пропускает вызов `stat()` для каждого файла.

### 5.1 Основные столпы / модули

**A. Возврат атрибутов из листинга**
Внутренний тип данных (структура), объединяющий путь файла с его атрибутами: размер в байтах, флаг директории. Оба поля заполняются из уже имеющегося `LsEntry.attrs` — без новых сетевых запросов. Метод листинга в клиенте меняет возвращаемый тип на список таких структур.

**B. Устранение per-file `stat()` в сканере**
Сканер извлекает размер файла и флаг директории напрямую из структуры, полученной при листинге, вместо вызова `stat()`. Фильтрация по размеру (`SizeFilter`) выполняется на тех же данных. Вызов `stat()` сохраняется только как fallback для случаев, когда атрибуты в `LsEntry` недоступны или нулевые.

**C. Подключение `onProgress`-колбэка**
В цикле обработки файлов в сканере добавить вызов `onProgress` с текущим счётчиком обработанных файлов. Колбэк уже определён в интерфейсе и принимается как параметр — фактические вызовы ранее отсутствовали в SFTP-реализации.

### 5.2 Потоки данных и событий

```
SSH ls(remotePath)
    → LsEntry[] (path + attrs уже в памяти)
    → listFiles() возвращает List<{path, size, isDir}>
    ↓
SftpMediaScanner.scanFolder()
    → фильтрация по типу и размеру (без дополнительных сетевых запросов)
    → onProgress(count) на каждой итерации
    → формирование List<MediaFile>
    ↓
UI: прогресс-индикатор обновляется в реальном времени
```

### 5.3 Точки расширяемости

- Новая структура «путь + атрибуты» может быть расширена полем времени модификации для будущей инкрементальной синхронизации.
- `onProgress`-колбэк при необходимости может сообщать имя текущего файла — интерфейс это уже поддерживает.

## 6. Открытые вопросы / Research items

1. **Атрибуты в рекурсивном листинге**
   - **Вопрос:** при рекурсивном обходе подкаталогов `listFilesRecursive` тоже использует `channel.ls()` — следовательно, `LsEntry.attrs` доступны и там. Нет ли случаев, когда SFTP-сервер возвращает `LsEntry` с нулевыми атрибутами?
   - **Нужно выяснить:** проверить спецификацию JSch и поведение нескольких SFTP-серверов (OpenSSH, ProFTPD, Synology DSM).
   - **Варианты:** если атрибуты могут быть null — добавить null-check и fallback к `stat()`.
   - **Статус:** Resolved — JSch `channel.ls()` использует SFTP `readdir` (protocol v3); объект `SftpATTRS` всегда присутствует. Guard добавлен: fallback `stat()` срабатывает только если `listing.size <= 0L` при активном минимальном фильтре размера.

2. **Публичный контракт `stat()`-метода**
   - **Вопрос:** используется ли `stat()` где-либо ещё, кроме сканирования (например, в download-потоке, info-диалоге)?
   - **Нужно выяснить:** `grep` по всем вызовам `sftpClient.stat(` в кодовой базе.
   - **Статус:** Resolved — `sftpClient.stat()` вызывается в `SftpOperationStrategy` (7 сайтов, передача файлов) и `SftpDataSource` (1 сайт, воспроизведение) — оба не затронуты. 3 call-сайта в `SftpMediaScanner` устранены; остался только conditional fallback при нулевом размере.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Нестандартный SFTP-сервер, возвращающий `LsEntry` с нулевыми атрибутами | Низкая | Некорректный размер файла в списке; сбой фильтрации | Null-check на атрибутах; fallback к `stat()` если attrs == null |
| Изменение типа возврата `listFiles()` ломает другие потребители | Средняя | Компиляционные ошибки во всех местах, вызывающих `listFiles()` | Проверить все вызовы до изменения контракта (§6.2) |
| `onProgress`-вызовы замедляют сканирование из-за частых coroutine-переключений | Низкая | Минимальный регресс скорости | Вызывать `onProgress` не чаще раза на 10 файлов или раз в 500 мс |

## 9. Архитектурные решения (ADR)

**ADR-1: Изменить возвращаемый тип `listFiles()` или добавить новый метод?**

- **Решение:** изменить возвращаемый тип существующего метода `listFiles()` — добавить новый внутренний тип данных «путь + атрибуты».
- **Альтернативы:** добавить отдельный метод `listFilesWithAttributes()` и оставить `listFiles()` нетронутым.
- **Почему:** один метод с полными данными проще поддерживать; `listFiles()` имеет единственного потребителя (`SftpMediaScanner`), поэтому смена типа не рискует сломать широкий публичный контракт.

**ADR-2: Частота вызовов `onProgress`**

- **Решение:** вызывать `onProgress` каждые 10 обработанных файлов.
- **Альтернативы:** каждый файл; каждые N миллисекунд.
- **Почему:** баланс между отзывчивостью UI и минимальными накладными расходами на coroutine-dispatch; при 10 файлах/вызов пользователь видит обновления достаточно часто.

## 11. Критерии готовности (strategic-level)

1. Сканирование SFTP-ресурса с ~500 файлами завершается менее чем за 30 с (вместо 265 с) при той же скорости соединения.
2. В процессе сканирования пользователь видит счётчик обработанных файлов или прогресс-бар — такой же, как при сканировании SMB-ресурса.
3. `ScanMetrics: SLOW SCAN` не срабатывает для ресурса нормального объёма (до ~500 файлов) при стабильном соединении.
4. Поведение на нестандартных SFTP-серверах (с нулевыми атрибутами в `ls`-ответе) не ухудшилось: сканирование завершается корректно через fallback.
5. Все существующие операции, использующие `sftpClient.stat()` напрямую (info-диалог, download), продолжают работать без изменений.
