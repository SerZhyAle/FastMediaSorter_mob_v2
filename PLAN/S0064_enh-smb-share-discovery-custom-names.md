# Стратегическая спецификация: S0064 — Обнаружение SMB-шар с нестандартными именами

**Ticket:** S0064
**Status:** Implemented
**Priority:** 10
**Date:** 2026-05-03
**Tier:** 2 — Easy
**Roadmap entry:** Ad-hoc — побочное наблюдение из лога `logs/fastmediasorter_20260503_140115.log`
**Tactical spec:** `PLAN/S0064_enh-smb-share-discovery-custom-names/` (будет создан через `/spec-tech`)
**Related:** S0061 (тот же лог, основной инцидент)

> **Scope:** STRATEGIC. Дать пользователю возможность подключиться к SMB-шаре, имя которой не выдаёт стандартный механизм перечисления, и не пугать его записью «найдено мало шар» уровня предупреждения.

---

## 1. Проблема

При подключении к SMB-серверу приложение перечисляет доступные шары через стандартный системный механизм. На некоторых конфигурациях (особенно домашних NAS, Samba с нестандартными настройками, Windows-серверах со скрытыми/именованными шарами) механизм возвращает заведомо неполный список, и в логе появляется запись WARNING вида «Found only N share(s). There may be more shares with custom names». Пользователь, у которого нужная шара не показалась в списке, остаётся без рабочего пути «выбрать руками» — приложение само не предлагает ему ввести имя.

Эффект на пользователя: невозможность подключиться к корректно настроенному, но не-самоопределяющемуся серверу; видимая «бессмысленная» ошибка в диагностике для разработчика.

---

## 2. Цели

1. Если автоматическое перечисление возвращает «мало или ничего», у пользователя появляется явный способ ввести имя шары вручную и подключиться.
2. Введённое вручную имя шары запоминается и доступно для повторного использования без повторного ввода.
3. Запись «Found only N share(s)..» перестаёт быть WARNING — она диагностическая, не сигнал о проблеме приложения.
4. Никаких изменений для пользователей, у которых перечисление и так возвращает все нужные шары.

**Non-goals:**

- Не реализовывать «угадывание» шар перебором имён.
- Не трогать аутентификацию и хранение учётных данных сверх минимально необходимого для нового поля «имя шары».
- Не делать сетевую инвентаризацию (broadcast, mDNS, WS-Discovery) поверх SMB.

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Желательно сохранять историю введённых имён шар на сервер, чтобы при повторном подключении предлагать их в выпадающем списке.
2. Желательно отдельная пометка «введено вручную» в UI для таких шар.
3. Желательна валидация имени на стороне клиента: длина, недопустимые символы — до запроса на сервер.

### 3.2 Жёсткие ограничения

- **Flavor:** все, где SMB активен.
- **API level:** без специфики.
- **Wear OS:** не затрагивается.
- **Производительность:** не критично.
- **Совместимость данных:** возможна добавка поля «список ручных имён шар на сервер» — должно быть совместимо с существующими сохранёнными подключениями (миграция тривиальная, без потери данных).
- **Локализация:** EN/RU/UK для UI-строк (поле ввода, подсказка, ошибка валидации).
- **Доступность:** поле ввода — TalkBack-совместимое, подсказка озвучивается; touch target ≥ 48dp.

---

## 4. Контекст текущей архитектуры

Подключение к SMB-серверу сейчас выполняется по двух-шаговому сценарию: пользователь указывает сервер → приложение перечисляет шары → пользователь выбирает одну из списка. Если шар в списке нет, дальнейшего пути нет — нет UI-элемента «ввести вручную». Запись WARNING из логирующего слоя нацелена на разработчика и не доходит до пользователя.

---

## 5. Предлагаемый подход

Расширить шаг выбора шары: в дополнение к автоматически найденному списку добавить элемент «Ввести имя вручную». Введённое имя проверяется (валидация формата) и пробуется на подключение; при успехе — запоминается рядом с текущим сервером и в следующий раз появляется наверху списка как «ручная» с соответствующей пометкой. Параллельно — понизить уровень диагностической записи о неполном списке до INFO.

### 5.1 Основные столпы / модули

- **UI выбора шары.** Список с автоматическими элементами + строка-кнопка «Ввести имя вручную». Поле ввода с клиентской валидацией формата имени. Сохранение и повторное использование введённых имён.
- **Хранение «ручных» шар на сервер.** Привязка списка введённых имён к идентификатору сервера (host + порт). Совместимая миграция: отсутствие списка — пустой список.
- **Диагностический канал.** Запись «найдено N шар» — INFO, без эмоционально-окрашенных слов. Если шар 0 — то же INFO + UI-подсказка пользователю про ручной ввод.
- **Поведение при ошибке подключения к ручной шаре.** Понятное сообщение (доступ запрещён / шара не существует / сервер не отвечает) и сохранение введённого имени в истории, даже если первая попытка не удалась — пользователь часто хочет попробовать снова с другой учётной записью.

### 5.2 Потоки данных и событий

Сервер выбран → перечисление шар → объединить с историей ручных имён для этого сервера → показать список с разделением «найдено автоматически / введено вручную / добавить вручную». Пользователь выбирает или вводит → подключение → при успехе сохранение в историю; при неудаче — UI-сообщение и оставление имени в форме для коррекции.

### 5.3 Точки расширяемости

- История ручных имён должна быть отдельной от истории серверов: пользователь может удалять отдельные имена без потери самого подключения к серверу.
- Возможность будущего экспорта/импорта подключений вместе с ручными именами шар.

## 6. Открытые вопросы / Research items

1. **Где живёт список ручных имён.**
   - **Вопрос:** прицепить к существующей записи «сервер» или хранить отдельно с key = host:port?
   - **Варианты:** (а) поле в записи сервера; (б) отдельная коллекция; (в) общая история «последние имена шар» без привязки.
   - **Нужно выяснить:** структуру текущего хранения подключений, чтобы выбрать минимально-инвазивный вариант.
   - **Статус:** Open

2. **Поведение, если ручное имя совпало с автоматически найденным.**
   - **Вопрос:** дедуплицировать или показывать дважды (с пометкой «ручной»)?
   - **Варианты:** (а) дедуплицировать, оставив пометку; (б) показывать дважды.
   - **Статус:** Open

3. **Скрытые шары (имена с `$` на конце) и анонимный доступ.**
   - **Вопрос:** дополнительно подсказывать пользователю про шары вида `share$`?
   - **Статус:** Open

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Пользователь запомнит «битое» имя и будет регулярно получать ошибку | Средняя | Раздражение, мнение что приложение глючит | Лёгкая чистка истории: жест «удалить» из списка ручных имён; автоматическая очистка по N подряд провальным попыткам |
| Структура хранения мигрирует несовместимо со старыми подключениями | Низкая | Потеря сохранённых серверов | Пустой список ручных шар — валидное состояние; миграция «добавить пустой список» без потери данных |
| Регрессия в автоматическом перечислении из-за рефакторинга списка шар | Низкая | Часть пользователей не увидит шары вообще | Сохранить автоматический путь как первичный; ручной добавляется поверх, не вместо |

## 9. Архитектурные решения (ADR)

**ADR-1: Ручной ввод как дополнение, не замена автоматического перечисления.**

- **Решение:** автоматический список остаётся первичным; ручной ввод доступен дополнительно через явный элемент UI.
- **Альтернативы:** заменить список ручным вводом полностью; перевести всех на «прокси-имена».
- **Почему:** ломает работающий сценарий для большинства пользователей; ручной ввод — именно «escape-hatch» для частных конфигураций.

**ADR-2: История ручных имён живёт рядом с записью сервера.**

- **Решение:** список ручных имён хранится в составе записи подключения к серверу.
- **Альтернативы:** глобальная история без привязки.
- **Почему:** имена шар осмысленны только в контексте конкретного сервера; объединение приведёт к некорректным предложениям между разными серверами.

## 11. Критерии готовности (strategic-level)

1. У пользователя есть видимый способ ввести имя шары вручную в UI выбора шары.
2. Введённое имя сохраняется и появляется в следующем сеансе подключения к тому же серверу с пометкой «вручную».
3. Запись «Found only N share(s)..» уровня WARNING больше не появляется в логах при штатной работе перечисления.
4. Существующие сохранённые подключения остаются работоспособны; миграция без потерь.
5. Подсказка / поле ввода доступны для TalkBack и соответствуют требованиям к touch target.
