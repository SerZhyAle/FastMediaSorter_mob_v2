# Audio Waves Visual Upgrade

## Goal

Improve the existing `Waves and particle` audio empty-state visualization so that each fresh playback session feels more alive, less repetitive, and more entertaining.

The primary requested change is:

- today the wave motion is visually horizontal
- on every fresh start, the wave flow direction should be randomized across the full `360°`

This document expands that request into a production-ready specification with UX intent, technical direction, acceptance criteria, and safe rollout boundaries.

## Research Summary

### Current implementation

Relevant implementation points found in the project:

- `app_v2/src/main/java/com/sza/fastmediasorter/ui/player/helpers/AudioWaveParticleView.kt`
- `app_v2/src/main/java/com/sza/fastmediasorter/ui/player/helpers/AudioEmptyStateController.kt`
- `app_v2/src/main/res/layout/activity_player_unified.xml`

Current behavior in `AudioWaveParticleView`:

- the session already randomizes wave count, stroke width, hue, amplitude, particle count, particle speed, and particle palette
- particles already move freely in 2D and bounce from edges
- waves are still generated by scanning `x` from left to right and computing `y` from a sine function
- because of that, the wave field always reads as horizontally traveling lines, even when colors and particles change

### Why the current result feels repetitive

- the global silhouette is always the same: stacked horizontal bands
- random colors and particles help variation, but not enough to change the overall composition
- users quickly recognize the same visual identity after several playback starts
- the visualizer looks decorative, but not surprising

## Problem Statement

The current `CANVAS_WAVES` mode has good variation in micro-parameters, but not in macro-direction.

As a result, every session looks like a variation of the same scene instead of a new visual moment.

## Product Intent

The visualizer should feel:

- more cinematic
- less mechanically repeated
- playful and atmospheric during audio playback
- visually different on each fresh start without becoming chaotic or uncomfortable

The result should still fit the existing player architecture and remain lightweight enough for continuous animation on mobile devices.

## Platform Target

This solution must be safe for weak devices starting from Android `8.1`.

Project baseline confirmed during research:

- standard flavor supports API `26+` (`Android 8.0+`)
- therefore Android `8.1` is within the supported standard target range
- the visual upgrade must not assume modern GPU-only effects or high-end hardware

## Proposed Solution

### Core change: random 360-degree wave direction per fresh start

On every fresh `startAnimation()` session, assign one session-level direction angle:

- `waveDirectionAngleDeg` in range `0..359`
- the angle is generated once per fresh start
- resume-from-pause must keep the same angle
- stop and fresh restart must generate a new angle

Instead of treating the wave as a fixed horizontal function over screen `x`, render the wave field in a rotated coordinate space:

- define a primary movement axis from the randomized angle
- define a perpendicular axis for wave amplitude displacement
- generate the sine path along the primary axis
- project points back to view space

This makes the entire wave composition feel like it travels in any direction:

- left to right
- right to left
- top to bottom
- bottom to top
- diagonal
- any in-between angle

### Visual rule for readability

Even with full `360°` freedom, the visual should remain elegant:

- waves must still pass through or near the visual center area often enough to avoid looking detached
- the amplitude should stay bounded so diagonal modes do not clip too aggressively
- if the randomized angle creates excessive edge clipping on some aspect ratios, normalize the effective draw span rather than restricting the angle set

## Entertainment Upgrade Layer

The request is not only about randomness, but also about making the scene more entertaining. The following additions are recommended inside the same visual concept.

### 1. Direction personality per session

Each new session should feel like a different “mood”, not just a rotated copy.

Add one session archetype chosen at random:

- `Glide`: soft, slow, elegant drift
- `Storm`: higher amplitude, faster phase motion, denser particles
- `Orbit`: diagonal or circular-feeling flow with stronger parallax illusion
- `Dream`: softer palette, thinner lines, longer particle trails

This keeps the effect entertaining while still staying within the existing waves-and-particles visual language.

### 2. Center energy pulse

Add a subtle center pulse that breathes with the wave field:

- low-opacity radial glow or soft ring pulse
- should not compete with controls or text overlays
- should be visible mainly when no cover art is shown

This gives the animation a focal point and makes the scene feel less flat.

### 3. Direction-aware particle flow

Particles already move in 2D, but they should visually support the current wave direction.

Recommended adjustment:

- keep some randomness, but bias average particle velocity toward the same session direction as the waves
- allow a minority of particles to counter-drift for richness
- preserve edge-bounce behavior unless a more expensive wrap/respawn model is justified later

This aligns the whole composition into one coherent motion story.

### 4. Short intro flourish on fresh start

On a brand-new session start, add a brief `400-900 ms` flourish:

- particles brighten or expand slightly
- wave amplitude ramps in quickly
- optional center flash or soft shockwave

This creates a satisfying “scene ignition” moment and makes repeated starts feel fun instead of static.

### 5. Slow palette drift during playback

The current session palette is randomized. To increase entertainment value, allow subtle color evolution during playback:

- hue drift should be slow and low-contrast
- avoid rapid rainbow cycling
- keep the visual premium rather than arcade-like

## UX Requirements

- no extra taps required from the user
- no new settings are required for phase 1
- the effect must remain compatible with current `CANVAS_WAVES` mode behavior in settings
- animation must look good in portrait and landscape player layouts
- controls, overlays, and text must remain readable above the background
- pause/resume must not reshuffle the entire visual identity mid-session

## Technical Direction

### Rendering model

Recommended implementation model:

1. Generate a session angle on fresh start.
2. Build two normalized vectors:
	- forward axis
	- perpendicular axis
3. Sample wave points across a span large enough to cover the screen diagonal, not only the width.
4. For each sample point:
	- move along the forward axis
	- apply sine displacement along the perpendicular axis
	- translate the result around the visual center
5. Draw the path as usual into the off-screen canvas.

This avoids fake rotation tricks and produces true directional wave flow.

### Performance constraints

- keep the current lightweight canvas approach
- do not introduce heavy blur filters, shaders, or bitmap reallocations per frame
- avoid per-frame object allocations where possible
- preserve current off-screen trail buffering strategy
- target smooth playback on typical Android devices supported by the app

### Low-end device constraints

To keep the feature viable on weak Android `8.1+` devices, the implementation should treat performance as a first-class requirement.

Required limits:

- use only the existing Canvas-based rendering path for phase 1
- no OpenGL, no RuntimeShader, no RenderEffect, no expensive post-processing stack
- keep all randomness session-based, not frame-based
- reuse `Path`, `Paint`, arrays, vectors, and particle objects
- avoid any new bitmap creation during animation frames
- keep the intro flourish extremely short and mathematically simple
- center pulse must be drawable with basic primitives only, or skipped if profiling shows regressions

Recommended budgets for weak devices:

- wave count should stay conservative on low-end profiles
- particle count should remain capped and not scale aggressively with screen size
- color drift should be time-based and formula-driven, not texture-based
- diagonal coverage should use geometry math, not oversized off-screen layers

### Adaptive quality strategy

If needed, the visualizer may support internal quality tiers without exposing a new user setting.

Suggested behavior:

- `Tier A`: full effect for normal devices
- `Tier B`: reduced wave count and reduced particle count for weaker devices
- `Tier C`: keep 360-degree direction randomization, but disable center pulse and simplify intro flourish

Important rule:

- the core identity must survive on all tiers, meaning randomized 360-degree direction remains enabled even in reduced mode
- degradation should remove decorative cost first, not the main requested feature

### Android-version gate for advanced effects

Yes, Phase 2 “super effects” may be gated by Android version to reduce risk on older and weaker devices.

Recommended rule:

- `Android 13+` (`API 33+`): allow Phase 2 decorative effects
- `Android 8.1` to `Android 12L` (`API 27..32`): keep Phase 1 directional waves as the default ceiling unless profiling proves a specific effect is safe

Why this is reasonable:

- API level is not a perfect proxy for GPU or CPU strength, but it is a pragmatic first safety boundary
- newer Android versions are statistically more likely to run on newer SoCs, better GPUs, and devices with more memory headroom
- this prevents the oldest supported devices from paying the cost of purely decorative rendering upgrades

Important nuance:

- version gating should protect Phase 2 and beyond, not Phase 1
- the main requested feature, randomized 360-degree directional waves, must remain available on older supported devices
- if a Phase 2 effect is mathematically cheap after profiling, it may later be backported selectively without changing the overall rule

Suggested gating priority:

1. hard gate by `SDK_INT >= 33` for center pulse, enhanced flourish, and any richer composite effects
2. keep palette drift and other ultra-cheap formula-based changes optional and review them independently
3. if needed later, add a second guard based on measured device class or runtime profiling

### Session state

Session-level randomized values should include at least:

- wave direction angle
- wave archetype
- particle flow bias
- intro flourish profile
- base palette family

These values must be regenerated only on fresh session start, not on pause/resume.

## Acceptance Criteria

### Functional

- every fresh start of `CANVAS_WAVES` chooses a new wave direction across the full `360°` range
- wave motion is visibly non-horizontal in many starts, including diagonal and vertical-feeling sessions
- pause/resume preserves the current session direction and style
- stop and fresh restart produces a new direction and may produce a new archetype

### Visual

- repeated playback starts feel clearly more varied than the current implementation
- the animation reads as more entertaining and dynamic, not just rotated
- particles and waves feel part of one composition
- the intro moment gives the animation a clear start identity

### Quality

- no obvious clipping or broken geometry in portrait or landscape
- no severe frame pacing regressions versus current `CANVAS_WAVES`
- no overlap issues that reduce readability of player controls or audio info overlays
- the reduced-quality path, if introduced, must still look intentional rather than broken or empty
- the effect must remain acceptable on weak Android `8.1+` hardware during normal audio playback

## Non-Goals

- no requirement to add a new settings item in phase 1
- no requirement to expose manual direction selection to users
- no requirement to build a full audio-spectrum analyzer
- no requirement to replace the existing bars or video modes

## Risks

### Risk 1: rotated waves may clip on tall or wide screens

Mitigation:

- sample across the screen diagonal plus margin
- center the generated geometry rather than binding it to only left-to-right width traversal

### Risk 2: too much randomness may look noisy

Mitigation:

- randomize at session level, not every frame
- constrain archetypes to curated ranges rather than fully unconstrained values

### Risk 3: entertaining effects may become distracting

Mitigation:

- keep glow, pulse, and flourish subtle
- prioritize atmosphere over aggressive motion

### Risk 4: feature becomes too expensive for low-end devices

Mitigation:

- keep 360-degree wave direction as the mandatory core feature
- make decorative effects optional or degradable
- gate Phase 2 decorative effects to Android `13+` by default
- verify behavior on an Android 8.x class device or emulator profile with reduced resources
- profile before adding any extra pulse or trail complexity

## Recommended Delivery Phases

### Phase 1

- full `360°` session-randomized wave direction
- particle flow bias aligned to direction
- safe diagonal coverage and clipping handling
- low-end-safe implementation baseline for Android `8.1+`

### Phase 2

- session archetypes
- intro flourish
- subtle center pulse
- adaptive quality tiering if profiling shows need
- enable by default only on Android `13+` unless a specific effect is proven cheap enough for older devices

### Phase 3

- slow palette drift
- further polish based on user feedback and performance checks

## Implementation Steps

### Step 1. Freeze current baseline

Goal:

- confirm current `CANVAS_WAVES` rendering behavior before changes

Actions:

- identify all lifecycle entry points for fresh start, pause, resume, and stop
- confirm where `startAnimation()` is called from the player flow
- confirm current session-randomized parameters in `AudioWaveParticleView`
- capture current performance baseline on at least one weak-device profile or emulator

Output:

- clear understanding of where the new session angle must be generated
- baseline notes for visual and performance comparison

### Step 2. Introduce session direction model

Goal:

- make wave direction a first-class session parameter

Actions:

- add one randomized session angle for fresh starts only
- keep the angle stable through pause/resume
- regenerate it only after stop/reset and fresh new start
- define forward and perpendicular vectors derived from that angle

Output:

- stable session-level direction state ready for rendering

### Step 3. Replace horizontal-only wave sampling

Goal:

- make wave generation truly directional instead of left-to-right only

Actions:

- sample across screen diagonal plus margin
- build wave points in rotated coordinate space
- project each point back into screen space
- ensure the composition remains centered and readable

Output:

- waves can visually travel in any direction across full `360°`

### Step 4. Align particles with the wave story

Goal:

- make particles support the same directional identity as the waves

Actions:

- bias average particle velocity toward the session direction
- preserve some random variance so the motion does not look rigid
- keep existing edge-bounce behavior unless profiling justifies a better alternative
- ensure particles still look good in vertical and diagonal flows

Output:

- particles and waves read as one coherent composition

### Step 5. Make it safe for weak Android 8.1+ devices

Goal:

- protect frame pacing before adding decorative upgrades

Actions:

- reuse all draw objects and arrays
- avoid any per-frame allocations introduced by the new math
- keep the off-screen buffer strategy unchanged
- validate that the rotated geometry does not require oversized heavy buffers
- reduce wave and particle density if needed on weak profiles

Output:

- core directional feature works acceptably on weak devices

### Step 6. Add entertainment layer carefully

Goal:

- improve delight without breaking readability or performance

Actions:

- add only one small enhancement at a time: archetype, intro flourish, center pulse, then palette drift
- profile after each enhancement
- keep decorative effects subtle and degradable
- drop any effect that damages low-end performance or visual clarity

Output:

- upgraded visual remains premium, not noisy or heavy

### Step 7. Validate lifecycle and UX behavior

Goal:

- ensure the effect behaves correctly in real player usage

Actions:

- verify fresh start creates a new visual identity
- verify pause/resume preserves the current one
- verify landscape and portrait layouts
- verify controls and overlays remain readable
- verify no obvious clipping, tearing, or broken trails

Output:

- implementation is safe to merge after acceptance review
