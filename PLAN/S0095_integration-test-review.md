## 1. Проблема

Набор инструментальных (androidTest) тестов проекта состоит из двух файлов — базовые файловые операции и один UI-тест настроек. Он не покрывает ни один из флоу, реализованных после первоначального написания. Помимо этого, в существующих тестах хардкодированы конкретные строки тестовых ресурсов (имена пользователей, идентификаторы папок, адреса серверов), что делает тесты непереносимыми: другой девайс или CI-стенд без тех же заранее созданных данных упадёт без диагностики. Unit-тесты (JVM/Robolectric) охватывают большинство новых флоу, однако несколько критических путей (player file-operations, VR entry, cloud auth UI) проверяются только через моки и не имеют инструментальных аналогов.

---

## 2. Цели

1. Инвентаризировать все существующие тесты (androidTest + unit) и зафиксировать покрытие по feature-областям.
2. Ввести единое место хранения тестовых констант — имён ресурсов, папок, сетевых адресов — чтобы каждый devОтдел/CI заменял лишь один конфигурационный файл, а не правил каждый тест.
3. Привести существующие androidTest-тесты к использованию этих констант вместо вшитых строк.
4. Добавить инструментальные тесты для флоу, появившихся или кардинально изменённых в последних итерациях:
   - Перемещение/копирование файла из плеера (move-during-playback).
   - Смена ориентации экрана в плеере без потери позиции воспроизведения.
   - Ввод и сохранение сетевых реквизитов (SMB/SFTP/FTP) в редакторе ресурсов.
   - Полный сценарий входа/выхода из облачного аккаунта (cloud auth) через UI настроек.
   - Поведение плеера при незавершённом файле (BD-TS partial read).
5. Добавить граничные сценарии в существующие unit-тесты там, где они отсутствуют (пустой плейлист, нулевой прогресс, недоступный источник).

**Non-goals:**

- End-to-end тесты с реальным сетевым сервером (SMB, FTP, SFTP) — требуют внешней инфраструктуры.
- Нагрузочное или performance-тестирование.
- Тесты модуля Wear OS (выделить в отдельный тикет при необходимости).

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Тестовые константы (имена ресурсов, пути) должны читаться из одного общего объекта, доступного любому тесту — изменение одной строки меняет поведение всего набора.
2. Для сетевых тестов, требующих реального устройства, предоставить отдельный профиль (Gradle flavor или buildType), чтобы CI мог запускать только «безопасные» тесты без сетевой зависимости.
3. Документировать, какие ресурсы (папки, файлы, аккаунты) пользователь обязан создать на тестовом девайсе до запуска тестов — оформить в виде companion README рядом с androidTest.

### 3.2 Жёсткие ограничения

- **Flavor:** standard (основной акцент); проверить, не ломается ли lite/photos при регрессии.
- **API level:** minSdk 26 (стандартный); тесты не должны использовать API ниже 26.
- **Wear OS:** не затрагивается.
- **Производительность:** инструментальные тесты должны укладываться в 5 минут на одном проходе (без сетевых тестов).
- **Совместимость данных:** тесты не должны мигрировать БД — работать на чистой/тестовой базе.
- **Локализация:** EN/RU/UK — строки в тестовых константах только на EN; локализация UI-строк не тестируется в этом тикете.
- **Доступность:** не затрагивается.

## 4. Контекст текущей архитектуры

Инструментальные тесты (androidTest) живут в отдельном source set и имеют полный доступ к Android runtime — Activity, ContentProvider, SharedPreferences, файловая система устройства. Юнит-тесты (test) работают на JVM через Robolectric или с чистыми моками. Существующий androidTest покрывает только низкоуровневые файловые операции через Java File API и один Espresso-сценарий UI настроек — без Hilt-инъекций и без Room-базы.

Новые флоу (плеер, файловые операции во время воспроизведения, облачный auth) реализованы через менеджеры-помощники, делегируемые из Activity/ViewModel. Это упрощает мокирование на уровне unit-тестов, но не избавляет от необходимости инструментального теста для проверки реального Intent-флоу и сохранения состояния при пересоздании Activity.

Отсутствие единого слоя тестовых констант означает, что каждый тест хардкодит своё значение независимо — при переименовании тестового устройства или смене тестовых данных нужно обходить все файлы.

## 5. Предлагаемый подход

### 5.1 Основные столпы / модули

**A. Реестр тестовых констант**

Единый объект в androidTest source set (и, где применимо, в test source set), содержащий:
- Имена тестовых медиаресурсов (SMB-ресурс, SFTP-ресурс, FTP-ресурс, локальный ресурс, облачный ресурс).
- Типичные тестовые имена пользователей, пути к тестовым папкам на девайсе.
- Вспомогательные методы создания in-memory тестовых файлов (видео-заглушка, аудио-заглушка, изображение).

**B. Рефакторинг существующих androidTest-тестов**

- `FileOperationsInstrumentationTest` — заменить хардкод имён файлов на константы из реестра.
- `DefaultCredentialsInputTest` — заменить вшитую строку `"s0090-user"` и любые другие строковые литералы на ссылки на реестр.

**C. Новые инструментальные тесты (androidTest)**

Одна test-suite на каждый из следующих флоу:

| Флоу | Проверяемый инвариант |
|---|---|
| Player file move | После подтверждения перемещения UI плеера закрывается, файл физически появляется в новой папке |
| Player orientation | После поворота девайса позиция воспроизведения сохраняется (±2 сек) |
| Resource editor network credentials | Введённые реквизиты SMB/SFTP сохраняются и отображаются при повторном открытии редактора |
| Cloud auth lifecycle | Кнопка «выйти» в настройках очищает токен и переводит UI в состояние «не авторизован» |
| BD-TS partial file | Воспроизведение частичного .ts файла не крашится, плеер показывает ошибку или частичное видео |

**D. Граничные сценарии в unit-тестах**

Добавить в существующие test-классы:
- Пустой список файлов → ViewModel не крашится, показывает пустое состояние.
- Нулевой прогресс воспроизведения → маркировка «просмотрено» не срабатывает до порога.
- Недоступный источник (null/ошибка сети) → публикуется состояние ошибки, не выбрасывается необработанное исключение.

**E. Companion README для тестового стенда**

Markdown-файл рядом с androidTest, описывающий: какие папки, файлы и аккаунты должны присутствовать на тестовом девайсе, прежде чем запускать тесты с флагом `@Ignore` снятым.

### 5.2 Потоки данных и событий

```
Тест → Activity/Fragment (Espresso/ActivityScenario)
     → ViewModel (через тестовые зависимости)
     → UseCase / Manager
     → Android runtime (File, ContentProvider, SharedPreferences)
```

Реестр констант инжектируется статически — тест берёт константу, передаёт в Action, проверяет состояние UI или файловой системы.

### 5.3 Точки расширяемости

- Реестр констант может быть переопределён через BuildConfig или properties-файл для CI (не вшивается в APK релиза).
- Каждый новый флоу добавляет свою test suite в ту же структуру, не нарушая существующие.

1. **Ресурсы на тестовом девайсе**

   - **Статус:** Resolved — хардкод `"s0090-user"` выявлен в DefaultCredentialsInputTest; все подобные строки подлежат выносу в реестр.

2. **Gradle-профиль для сетевых тестов**
   - **Вопрос:** Нужен ли отдельный buildType/annotationProcessor для разделения «безопасных» и «сетевых» тестов, или достаточно `@Ignore` с комментарием?
   - **Варианты:** (a) `@Ignore` + README; (b) Custom test runner с фильтром аннотаций `@NetworkRequired`.
   - **Нужно выяснить:** Посмотреть, есть ли уже подобный механизм в build.gradle.kts.
   - **Статус:** Open.

3. **BD-TS тест на реальном устройстве**
   - **Вопрос:** Инструментальный тест для BD-TS требует .ts файл-заглушку. Где хранить тестовые медиафайлы-заглушки? В assets/, raw/ или программно генерировать минимальный валидный контейнер?
   - **Варианты:** (a) Добавить в `androidTest/assets/`; (b) Генерировать в setUp() через FFmpeg-like библиотеку; (c) Только unit-тест с моком.
   - **Нужно выяснить:** Размер ограничений APK для тестовых assets.
   - **Статус:** Open.

## 9. Архитектурные решения (ADR)

**ADR-1: Единый реестр тестовых констант вместо scattered literals**

- **Решение:** Ввести один kotlin object в androidTest source set как единственный источник всех тестовых строк.
- **Альтернативы:** properties-файл, BuildConfig поля.
- **Почему:** Проще рефакторить, не требует изменений build-скриптов, видно всем тестам без дополнительной конфигурации.

**ADR-2: Инструментальные тесты для UI-флоу — только ActivityScenario + Espresso**

- **Решение:** Не вводить Compose Test или UIAutomator для существующих тестов — придерживаться Espresso, которое уже используется в DefaultCredentialsInputTest.
- **Альтернативы:** UIAutomator (более robust к изменениям layout), Compose Test.
- **Почему:** Проект использует View-based UI; смена фреймворка увеличила бы объём изменений за пределами задачи.

5. Все новые тесты проходят на стандартном debug build (assembleStandardDebug); сетевые тесты помечены аннотацией и пропускаются без инфраструктуры.
