---

## 1. Проблема

Окно «Информация о файле» отображает критически мало данных для аудио и для сетевых источников. На FLAC по SFTP пользователь видит лишь длительность, маркер «Stereo» и кодек «RAW» — теряются артист, альбом, заголовок, год, жанр, обложка, sample rate, bit depth, битрейт. Текущий путь извлечения тянет всё через системный `MediaMetadataRetriever` поверх 1–5 МБ временной копии — для FLAC/OGG этот путь часто не отдаёт Vorbis-теги и битрейт, а на крупных файлах ещё и платит сетью за лишние мегабайты. Параллельно блок «Информация о файле» для сетевых путей выводит сырую SFTP/SMB/FTP-строку одной длинной строкой без разделения хост/каталог/имя, без MIME, без кнопки копирования и без раздельного `lastModified`.

---

## 2. Цели

1. На FLAC/MP3/M4A/OGG в info-диалоге пользователь видит: артист, альбом, заголовок, дату/год, жанр, номер трека, sample rate, bit depth, битрейт (точный или расчётный) и обложку — независимо от типа источника (локально / SFTP / SMB / FTP / SAF).
2. Для сетевых источников эти данные подтягиваются без полной загрузки файла и без кеширования больших фрагментов — стоимость открытия диалога остаётся в пределах десятков килобайт.
3. Блок «Информация о файле» читается с одного взгляда: для сетевого пути хост, шара/корень, каталог, имя файла разнесены построчно; видно расширение и MIME; есть отдельная кнопка копирования полного пути.
4. Дата изменения и дата создания показываются раздельно, если источник их различает.
5. Где источник возвращает атрибуты read-only/hidden — они отображаются.

**Non-goals:**

- Запись/правка тегов аудио. Только чтение.
- Полноценный плеер/визуализация спектра и waveform — info-диалог не превращается в audio inspector.
- Извлечение тегов из видеоконтейнеров (MP4/MKV) — остаётся текущая `MediaMetadataRetriever`-ветка.
- Разбор вложенных архивов и ZIP-EPUB поверх SFTP — это отдельная задача.
- Унификация с медиа-библиотекой/каталогом артистов — диалог остаётся «по одному файлу».

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Обложку показывать миниатюрой в углу диалога; по тапу — увеличение.
2. Для FLAC отображать lossless-маркер и значения ReplayGain (track/album), если они есть.
3. Кнопка копирования пути копирует именно полный канонический путь (со схемой), а не отрисованную многострочную форму.
4. Для аудио без тегов вместо пустых полей выводить «—» один раз, а не строкой «Артист: » с пустым значением.
5. По возможности на одном языке с UI — лейблы переведены EN/RU/UK.

### 3.2 Жёсткие ограничения

- **Flavor:** standard, lite, photos, legacy. В `photos` аудио не показывается — раздел «Информация об аудио» не должен компилироваться в граф вызовов этого варианта; блок «File Information» актуален во всех вариантах.
- **API level:** работа в пределах текущего `minSdk` проекта (26 для основных вариантов, 23 для legacy). Никаких API из Android 14+, отсутствующих на 8.0.
- **Wear OS:** не затрагивается.
- **Производительность:** открытие диалога для аудио по сети — не более десятков килобайт сетевого трафика на чтение метаданных; UI-поток никогда не блокируется чтением сети или диска. Декодирование обложки выполняется лениво и не задерживает первый кадр диалога.
- **Совместимость данных:** новые поля метаданных не персистируются в БД проекта. Если кэш расширяется — без миграций пользовательских данных.
- **Локализация:** EN/RU/UK обязательно для всех новых лейблов и кнопок. Числа форматируются по локали.
- **Доступность:** все новые строки доступны TalkBack; кнопка копирования имеет content description; миниатюра обложки имеет описательный alt; все новые цвета/иконки имеют не-цветовой признак (текст или форма).

## 4. Контекст текущей архитектуры

Info-диалог сейчас собирает данные в два прохода: синхронно из доменной модели медиафайла (имя, размер, дата, путь, базовый тип) и асинхронно через единый помощник извлечения метаданных, который для сетевых путей скачивает временный фрагмент файла (1–5 МБ) и натравливает на него системный native-экстрактор медиа. Именно эта ветка теряет на аудио теги, sample rate и битрейт — системный экстрактор слабо обрабатывает Vorbis-комментарии, FLAC-STREAMINFO и нерегулярные MP3 без LAME-заголовка.

Параллельно в проекте уже существует другой, более продвинутый путь — потоковый аудио-экстрактор, читающий ~64 КБ заголовка из произвольного источника через сетевые клиенты SMB/SFTP/FTP и парсящий ID3v2 / Vorbis / FLAC-текстовые теги через Media3-`MetadataRetriever` (Java-реализация, без native-краша). Он уже подключён к плееру для отображения «исполнитель — альбом — название» и к загрузчику обложек, имеет собственный file-based-LRU-кэш с TTL-30-дней и резерв под `thumbnailPath`. Но в info-диалог этот пайплайн не маршрутизируется, обложку из заголовка не извлекает (FLAC `PictureFrame` явно игнорируется, ID3v2 `APIC` не читается), и не возвращает технических полей — sample rate, bit depth, точный битрейт.

Блок «File Information» рисуется одной XML-разметкой и заполняется одним методом, который не различает локальный путь и сетевую URL-строку: `tvFilePath` получает целиком SFTP-URL, не разбирая его компоненты.

## 5. Предлагаемый подход

Спецификация делится на два независимых модуля. Их можно реализовывать и выпускать в любом порядке; оба наследуют существующий контракт info-диалога и расширяют его.

### 5.1 Основные столпы / модули

**A. Расширение существующего потокового аудио-экстрактора и его маршрутизация в info-диалог.**

Опорная роль уже существует в проекте — «потоковый аудио-экстрактор», читающий заголовок небольшим диапазоном байт через сетевые клиенты и разбирающий ID3v2 / Vorbis / FLAC-текстовые теги через Java-парсер метаданных Media3. Спецификация расширяет именно его, а не вводит параллельный модуль:

- Захватывать в нём же бинарные блоки обложки: FLAC `METADATA_BLOCK_PICTURE`, ID3v2 `APIC`, MP4/M4A `covr`, OGG Vorbis `METADATA_BLOCK_PICTURE`. Размер чтения адаптивный: стартовое окно — текущие ~64 КБ; если объявленный размер блока картинки больше — расширять чтение точечно до нужного смещения, ограничивая абсолютным верхним лимитом, при превышении пропускать обложку без потери текстовых тегов.
- Возвращать наряду с тегами технические параметры: sample rate, bit depth, число каналов, маркер lossless/lossy. Точный битрейт берётся из заголовка контейнера, где он есть; иначе вычисляется из размера файла и длительности (для CBR — корректно; для VBR без xing/lame-заголовка точное значение получить нельзя — поле скрывается, см. §6.2).
- ReplayGain (track/album) для FLAC/Vorbis читается из тех же Vorbis-комментариев и пробрасывается в результат.
- Аудио-ветка info-диалога маршрутизируется через этот расширенный пайплайн **до** обращения к текущей системной экстрактор-ветке. Если расширенный пайплайн вернул валидный результат — системный экстрактор для аудио не вызывается. Если расширенный пайплайн не распознал формат, выбросил исключение или не подключён для конкретного типа источника — текущая ветка остаётся резервом, диалог не пуст.
- Обложка хранится в существующем file-based-кэше аудио-метаданных (поле под `thumbnailPath` уже зарезервировано) — без введения отдельного хранилища. Декодирование в `Bitmap` асинхронное, рендеринг — через тот же графический загрузчик, что и остальные миниатюры в проекте.

**B. Расширенный блок «File Information».**

Вводится логическая роль «представление пути»: единичная функция получает каноническую URL-строку источника и возвращает разложение на смысловые поля (схема, хост, порт, шара/корень, относительный каталог, имя файла, расширение). Для локальных и SAF-путей разложение упрощённое. Сам диалог обращается к этому представлению, а не парсит путь на месте.

Тут же появляются:

- Отображение MIME-типа рядом с полем «Тип». Цепочка определения: сначала по расширению через системный `MimeTypeMap`; при `null` — точечная проверка сигнатур известных контейнеров (16–32 байта из начала файла); финальный fallback `application/octet-stream`. Сигнатурный sniffing вызывается только когда расширения нет или оно неизвестно — на типичных файлах сетевой запрос не нужен.
- Кнопка «Копировать путь», работающая на уровне канонической URL, а не построчного представления.
- Раздельный вывод даты создания и даты изменения, если у источника они различны.
- Атрибуты read-only/hidden для тех источников, что их возвращают.

### 5.2 Потоки данных и событий

Для аудио на сетевом источнике поток открытия диалога становится таким: UI запрашивает «расширенные метаданные»; слой извлечения сначала пробует потоковый парсер — он у провайдера запрашивает несколько небольших диапазонов (заголовок, опциональный «хвост» для ID3v1/MP4-trailer, опциональный диапазон для PICTURE-блока); парсер возвращает структуру; UI рендерит лейблы и асинхронно декодирует обложку. На локальном файле и SAF поток тот же, провайдер «случайного чтения» — обёртка над файловым дескриптором.

Для блока «File Information» поток синхронный: представление пути формируется в момент построения диалога, далее UI забирает оттуда отдельные поля и MIME. Кнопка копирования работает с исходной канонической строкой.

### 5.3 Точки расширяемости

- Контракт «случайного чтения» оставляет возможность подключить новые сетевые провайдеры (например, WebDAV) без правок парсеров.
- Парсеры аудио оформлены так, что добавление APE/WV/AIFF — это новый обработчик без изменений контракта и без изменений UI.
- Представление пути расширяется на новые схемы (cloud://, content://) без расширения интерфейса диалога.
- Декодер обложки изолирован — позже его можно повторно использовать для виджетов, уведомлений и аудио-оверлея плеера.

## 6. Открытые вопросы / Research items

1. **Контейнер для обложки в кэше и переиспользование существующей инфраструктуры.**
   - **Вопрос:** хранить ли декодированную обложку в существующем кэше или вводить новый?
   - **Статус:** Verified
   - **Найдено в кодовой базе (research):**
     - Уже существует параллельный путь извлечения аудио-метаданных, работающий потоково по сети: тянет ~64 КБ из заголовка через сетевые клиенты (SMB/SFTP/FTP) и парсит ID3v2 / Vorbis / FLAC-текстовые теги через **Media3 MetadataRetriever** (Java-реализация, без native-краша). Кэширует артиста/альбом/заголовок в памяти и в Room.
     - Уже существует репозиторий кэша аудио-метаданных: file-based LRU 500 МБ с TTL 30 дней, поддерживает атомарную запись, хранит JSON метаданных и **байты обложки на диске** рядом — поле `thumbnailPath` в Room-сущности уже зарезервировано.
     - Уже существует загрузчик обложек для плеера: для локальных файлов берёт `MediaMetadataRetriever.embeddedPicture`, для сетевых — `ExoPlayer.mediaMetadata.artworkData` во время воспроизведения; есть онлайновый fallback через iTunes/Deezer/MusicBrainz; рендеринг через Glide с memory-tier-оптимизацией.
     - Текущий пробел: при потоковом разборе FLAC `PictureFrame` явно игнорируется, ID3v2 `APIC` не извлекается; в info-диалоге нет ни `ImageView` для обложки, ни маршрутизации через этот существующий пайплайн — info-диалог идёт через отдельного помощника, который для аудио использует системный native-`MediaMetadataRetriever` поверх временной копии и теряет данные.
   - **Решение:** новый кэш обложек НЕ вводить. Переиспользовать существующий репозиторий кэша аудио-метаданных и его `thumbnailPath`-поле; расширить существующий потоковый экстрактор аудио, чтобы он захватывал `PictureFrame` (FLAC) и `APIC` (ID3v2) одновременно с текстовыми тегами; маршрутизировать аудио-ветку info-диалога через этот пайплайн вместо текущего системного экстрактора. Размер захвата заголовка адаптивный: стартовать с тех же ~64 КБ; если в STREAMINFO/ID3v2 объявлен `PICTURE`-блок большего размера — расширить чтение точечно до объявленного смещения, ограничив сверху разумным лимитом, при превышении — пропустить картинку (текстовые теги остаются).
   - **Архитектурное последствие:** ADR-1 теряет актуальность в исходной формулировке (см. предложение **P-1** ниже).

2. **Поведение парсера на «битых» MP3 без ID3 и без LAME-заголовка.**
   - **Вопрос:** показывать ли расчётный битрейт `size*8/duration` на VBR-MP3 без xing/lame-заголовка?
   - **Статус:** Verified
   - **Решение:** скрывать поле. Никаких приблизительных значений с пометкой «≈» не показывать. Если экстрактор возвращает `null` — строка битрейта в UI отсутствует, как и любые другие отсутствующие поля.

3. **Диапазонные чтения для FTP.**
   - **Вопрос:** во всех ли конфигурациях FTP-клиент проекта поддерживает чтение по смещению?
   - **Статус:** Verified
   - **Решение:** не блокировать спеку этим вопросом. Всю цепочку «получить расширенные метаданные» обернуть в `try`-обработчик, так что любое исключение (включая отсутствие поддержки `REST` на конкретном FTP-сервере) приводит к мягкой деградации — info-диалог показывает только базовые поля без расширенной аудио-секции и без обложки, без ошибок и крашей. Функциональность вокруг info-диалога не основная; стабильность приоритетнее покрытия.

4. **MIME для редких расширений и файлов без расширения.**
   - **Вопрос:** определять ли MIME по сигнатуре первых байт, если расширение неизвестно?
   - **Статус:** Verified
   - **Best Practice (Android):** официальный `MimeTypeMap` сознательно работает только по расширению; `URLConnection.guessContentTypeFromStream` на Android покрывает лишь несколько типов. De facto-стандартная цепочка для отображения MIME в UI без security-границы: (1) расширение → `MimeTypeMap`; (2) при `null`/отсутствии расширения — точечная проверка по сигнатурам известных контейнеров (JPEG/PNG/PDF/MP4/ZIP); (3) fallback `application/octet-stream`. Сниффинг для всех файлов подряд избыточен — расширение надёжно в подавляющем большинстве случаев.
   - **Решение:** реализовать описанную трёх-ступенчатую цепочку. Сигнатурная проверка вызывается только когда `MimeTypeMap` вернул `null` (нет расширения или расширение неизвестное); читает 16–32 байта из начала файла; стоимость — несколько десятков байт по сети, что укладывается в бюджет §3.2. Перечень распознаваемых сигнатур ограничен расширениями, которые приложение в принципе поддерживает (медиа-контейнеры, архивы, документы).

5. **Поведение кнопки «Копировать путь» для облачных источников.**
   - **Вопрос:** что копировать в буфер для путей `cloud://..`?
   - **Статус:** Verified
   - **Решение:** копировать человекочитаемый путь, который сейчас рендерится в диалоге (то, что приложение показывает пользователю — `cloudDisplayPath` для облачных источников и каноническую URL для остальных). Вариант с долгим нажатием для выбора режима не вводить.

## 7. Риски

| Риск | Вероятность | Последствия | Митигация |
|------|:-----------:|-------------|-----------|
| Потоковый парсер на нестандартном FLAC/MP3 падает или возвращает мусор | Средняя | Диалог покажет неверные теги или вообще ничего | Жёсткая валидация диапазонов и контрольных сумм блоков; при любом исключении — fallback на текущий путь через системный экстрактор |
| Сетевой провайдер не поддерживает «случайное чтение» в нужном объёме | Низкая | На некоторых FTP-серверах расширенные метаданные не появятся | Явный fallback: если провайдер не умеет — показывать только то, что даёт текущий путь, без regress по сравнению с поведением до фичи |
| Большая обложка (несколько МБ) тормозит UI или ест трафик | Средняя | Долгое открытие диалога на медленном SFTP | Декодирование обложки полностью асинхронное, ограничение размера PICTURE-блока сверху, отказ от загрузки если блок превышает порог |
| Разложение пути на части ломает существующий UX («путь как одна строка для копирования») | Низкая | Пользователь теряет привычное поведение | Сохранить отдельную кнопку «Копировать путь», копирующую полную каноническую URL; построчное представление — только визуальное |
| Локализация отстаёт от добавления полей | Средняя | Пользователи RU/UK видят английские лейблы | Все новые строки обязательно вводятся одним коммитом по EN/RU/UK; не-локализованные поля не релизятся |

## 9. Архитектурные решения (ADR)

**ADR-1: Расширение существующего потокового аудио-экстрактора (Media3 Java-`MetadataRetriever`) вместо параллельных собственных парсеров и вместо системного native-экстрактора.**

- **Решение:** для FLAC/MP3/M4A/OGG переиспользовать и расширить уже существующий в проекте потоковый аудио-экстрактор (Media3 Java-реализация поверх диапазонных чтений сетевых клиентов): добавить захват бинарных блоков обложки (`PictureFrame` / `APIC` / `covr`), sample rate, bit depth, ReplayGain, lossless-маркер; маршрутизировать через него аудио-ветку info-диалога.
- **Альтернативы:** (а) оставить системный native-`MediaMetadataRetriever` и увеличивать размер скачиваемого временного фрагмента — не лечит причину, ест трафик, теряет Vorbis-комментарии у FLAC; (б) написать параллельные собственные парсеры FLAC/MP3/M4A/OGG — дублирование с уже работающим пайплайном, два источника истины для аудио-метаданных; (в) подключить стороннюю библиотеку чтения тегов (Jaudiotagger / TagLib через JNI) — лишний размер APK и юридические условия.
- **Почему:** Media3-пайплайн уже корректно вытаскивает текстовые теги из всех четырёх контейнеров и стабильно работает по сети (диапазонные чтения через существующие SMB/SFTP/FTP-клиенты), уже имеет file-based-кэш с зарезервированным полем под обложку, уже подключён к плееру и загрузчику обложек. Расширить его дешевле и безопаснее, чем строить параллельный путь.

**ADR-2: Контракт «случайного чтения» вместо «загрузить во временный файл».**

- **Решение:** парсеры работают через абстракцию `read(offset, length)`; конкретная реализация поверх SFTP/SMB/FTP/local/SAF — обязанность провайдера.
- **Альтернативы:** оставить текущую модель «качаем временный файл, читаем как локальный».
- **Почему:** контракт `read(offset, length)` уже естественно реализуется существующими сетевыми клиентами проекта; временный файл создаёт паразитный трафик и заставляет ждать «достаточно ли мы скачали» до начала разбора.

**ADR-3: Разложение пути — представление, а не строка.**

- **Решение:** ввести структурированное представление пути и обращаться к его полям из UI вместо подстрочных манипуляций со строкой URL.
- **Альтернативы:** оставить разбор пути в самом диалоге.
- **Почему:** диалог — не единственное место, где удобно разложение; представление переиспользуется в логах, экспорте, share-sheet.

## 11. Критерии готовности (strategic-level)

1. На FLAC по SFTP info-диалог показывает артиста, альбом, заголовок, год, sample rate, bit depth и битрейт; обложка появляется в течение секунды-двух после открытия.
2. На MP3 по SMB info-диалог показывает ID3-теги, sample rate и точный битрейт для CBR / VBR с xing/lame-заголовком; для VBR-MP3 без xing/lame строка битрейта отсутствует (поле скрыто, не показывается приблизительное значение).
3. На OGG Vorbis и M4A info-диалог показывает Vorbis/iTunes-теги без полной загрузки файла.
4. На локальном файле и SAF поведение не хуже текущего: ни одно из ранее отображавшихся полей не пропало.
5. Блок «File Information» для пути вида `sftp://host:port/share/.../file.flac` показывает хост, порт, шару/корень, каталог и имя файла отдельными строками.
6. Рядом с типом видно расширение и MIME.
7. Кнопка копирования копирует полную каноническую URL источника (со схемой), что подтверждается вставкой в любое внешнее приложение.
8. Дата изменения и дата создания показываются раздельно, если источник их различает; при совпадении выводится одна.
9. На источниках, возвращающих атрибут read-only/hidden, он виден в диалоге.
10. Все новые лейблы и кнопки локализованы EN/RU/UK; нет фрагментов без перевода.
11. Открытие info-диалога для аудио по сети не загружает мегабайты файла — суммарный сетевой трафик на метаданные ограничен десятками килобайт (без обложки) и, опционально, объёмом самой обложки.
12. На источнике или формате, где парсер не справляется, поведение мягко деградирует к текущему — диалог не пуст, ошибок не показывает.
