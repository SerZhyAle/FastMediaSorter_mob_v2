# Стратегическая спецификация: S0035 — Android 17 Local Network Permission

**Ticket:** S0035
**Status:** Draft
**Priority:** 70
**Date:** 2026-04-30
**Tier:** 0 — Security/Compliance (urgent)
**Roadmap entry:** Ad-hoc — запрос 2026-04-30 (Android 17 Beta 4, локальная сеть блокируется по умолчанию для приложений, таргетирующих API 37+)
**Tactical spec:** `PLAN/S0035_android17-local-network-permission/` (будет создан через `/spec-tech`)

> **Scope:** STRATEGIC. Цели, ограничения, открытые вопросы. Без имён классов, путей, лимитов строк, миграций Room, модулей Hilt.

---

## 1. Проблема

Начиная с Android 17 (API 37), приложения, явно таргетирующие API 37+, лишаются доступа к локальной сети по умолчанию — без нового пермишна `ACCESS_LOCAL_NETWORK` все попытки подключиться к SMB/SFTP/FTP-серверам и обнаружить устройства Chromecast в LAN будут молча блокироваться на уровне ОС. FastMediaSorter не объявляет этот пермишн и не содержит ни runtime-запроса, ни graceful fallback для отказа. Как только `targetSdk` поднимется до 37, функции сетевых источников (Windows-шары, NAS, FTP-серверы) и трансляция на Chromecast перестанут работать без предупреждения.

---

## 2. Цели

1. При запуске на Android 17+ пользователь видит понятный запрос разрешения на доступ к локальной сети, прежде чем приложение попытается установить сетевое соединение.
2. При отказе в разрешении приложение показывает ёмкое объяснение и предлагает открыть настройки — без крэша и без зависания.
3. Все сетевые источники (SMB, SFTP, FTP) корректно отражают недоступность, а не воспроизводят таймаут или бесконечную загрузку.
4. Chromecast-обнаружение корректно пропускается, если разрешение не выдано, — без ошибок и без ложных уведомлений об отсутствии устройств.
5. На Android ≤ API 36 поведение не меняется: новая ветка пермишна не затрагивает старые версии ОС.
6. Все четыре флейвора работают корректно: `standard` (все сетевые протоколы + Cast), `lite` (FTP/SFTP/SMB без облака), `legacy` (FTP/SFTP/SMB), `photos` (нет сетевых источников, нет Cast — без изменений).

**Non-goals:**

- Повышение `targetSdk` до 37 в рамках этой спецификации — это отдельный релизный шаг.
- Изменение UI экрана добавления ресурса (кроме блокировки при отсутствии пермишна).
- Реализация постоянного хранилища состояния пермишна (достаточно проверки в runtime).
- Обработка пермишна `ACCESS_LOCAL_NETWORK` на Wear OS (там сетевых источников нет).

---

## 3. Пожелания и ограничения

### 3.1 Пожелания владельца

1. Единая точка проверки пермишна, переиспользуемая всеми сетевыми протоколами, — не дублировать логику в каждом месте вызова.
2. Rationale-диалог на русском, английском и украинском языках.
3. Возможность повторно запросить пермишн из настроек ресурсов — без необходимости перезапускать приложение.

### 3.2 Жёсткие ограничения

- **Flavor:** `standard`, `lite`, `legacy` — затронуты полностью; `photos` — пермишн объявляется для единообразия манифеста, но runtime-проверка не требуется.
- **API level:** пермишн и runtime-ветка активны только для API ≥ 37; на API ≤ 36 проверка пропускается без каких-либо изменений.
- **Wear OS:** не затрагивается.
- **Производительность:** проверка пермишна — синхронная, на главном потоке, без сетевых вызовов; не влияет на бюджет CPU/памяти/батареи.
- **Совместимость данных:** изменений схемы БД нет.
- **Локализация:** EN/RU/UK — обязательно для всех новых строк UI.
- **Доступность:** rationale-диалог должен быть читаем TalkBack; кнопки — не менее 48 dp touch target.

---

## 4. Контекст текущей архитектуры

Сетевые соединения инициируются в слое данных: отдельные источники для каждого протокола (SMB, SFTP, FTP) реализуют общий интерфейс репозитория. Вызовы к ним поступают через use cases, которые запускаются из ViewModel при открытии ресурса или при выполнении файловых операций. Chromecast-обнаружение живёт в отдельном компоненте уровня `core/`, независимом от сетевых источников файлов. Текущий `PermissionHelper` охватывает только хранилище; никакой логики для сетевых пермишнов нет ни в `PermissionHelper`, ни в сетевом слое. В манифесте отсутствует объявление `ACCESS_LOCAL_NETWORK`. Именно поэтому при подъёме `targetSdk` до 37 все вызовы к локальной сети будут немедленно заблокированы ОС.

---

## 5. Предлагаемый подход

Решение строится на двух столпах: декларативном (манифест) и imperative (runtime-проверка перед первым сетевым вызовом).

### 5.1 Основные столпы

**Столп A — Объявление пермишна в манифесте.**
Пермишн `ACCESS_LOCAL_NETWORK` добавляется в манифест `app_v2` с атрибутом `android:minSdkVersion="37"`, чтобы Play Store корректно отображал его на совместимых устройствах и не показывал на более старых.

**Столп Б — Единая точка runtime-проверки.**
Существующий `PermissionHelper` расширяется: добавляется проверка `hasLocalNetworkPermission()` с ветками «API < 37 → true без запроса», «API ≥ 37 → стандартный runtime-запрос». Этот метод становится обязательной точкой входа для всех компонентов, устанавливающих сетевые соединения.

**Столп В — Graceful fallback в сетевом слое.**
Каждый сетевой источник (SMB, SFTP, FTP) перед попыткой соединения делегирует проверку пермишна и при отрицательном результате возвращает конкретный код ошибки «доступ к локальной сети не разрешён», а не обобщённый IOException.

**Столп Г — Обработка отказа в UI.**
ViewModel и экраны сетевых ресурсов интерпретируют новый код ошибки и показывают rationale-диалог с двумя действиями: «Открыть настройки» и «Отмена». Логика идентична паттерну, уже применяемому для `MANAGE_EXTERNAL_STORAGE`.

**Столп Д — Chromecast.**
Cast-компонент проверяет наличие пермишна перед инициализацией сессии обнаружения. При отказе Cast-функциональность отключается без ошибок; в настройках приложения появляется состояние «недоступно — нет разрешения на локальную сеть».

### 5.2 Потоки данных и событий

```
Пользователь открывает сетевой ресурс
  → ViewModel запрашивает use case
    → use case проверяет LocalNetworkPermission
      → [API < 37] разрешено → продолжить соединение
      → [API ≥ 37, разрешение есть] → продолжить соединение
      → [API ≥ 37, нет разрешения] → вернуть PermissionError
        → ViewModel → UI: показать rationale-диалог
          → «Открыть настройки» → Settings deeplink
          → «Отмена» → ресурс остаётся недоступным

Chromecast init (при запуске экрана плеера)
  → Cast-менеджер проверяет LocalNetworkPermission
    → [нет] → skip init, пометить Cast как недоступный
    → [есть] → стандартный flow обнаружения
```

### 5.3 Точки расширяемости

- Метод проверки пермишна должен принимать callback или возвращать `Flow`, чтобы в будущем поддерживать реактивный пересчёт после смены разрешения из Settings (без перезапуска приложения).
- Код ошибки «нет разрешения на локальную сеть» должен быть именованной константой в доменном слое, а не строковым литералом.

## 6. Открытые вопросы / Research items

1. **Поведение Chromecast SDK при отсутствии LAN-доступа**
   - **Вопрос:** бросает ли Google Cast SDK исключение при старте обнаружения без `ACCESS_LOCAL_NETWORK`, или молча не находит устройств?
   - **Варианты:** (а) SDK бросает `SecurityException` → нужен try/catch; (б) SDK возвращает пустой список → достаточно проверки до инита.
   - **Нужно выяснить:** протестировать на эмуляторе Android 17 Beta 4 с отозванным пермишном.
   - **Статус:** Open

2. **Поведение SMBJ/SSHJ/Apache Commons Net без пермишна**
   - **Вопрос:** какое исключение бросают библиотеки при попытке TCP-соединения в заблокированной LAN — `SecurityException` или `ConnectException`?
   - **Варианты:** ОС может блокировать на уровне сокета с `EPERM` → `ConnectException`; или выдавать `SecurityException` напрямую.
   - **Нужно выяснить:** тест на эмуляторе Android 17 Beta 4.
   - **Статус:** Open

3. **Пермишн как normal или dangerous на API 37**
   - **Вопрос:** является ли `ACCESS_LOCAL_NETWORK` dangerous-пермишном (требует runtime-запроса) или signature/normal (выдаётся автоматически)?
   - **Варианты:** по документации Beta 4 — runtime dangerous; но это может измениться к финальному релизу.
   - **Нужно выяснить:** проверить финальную документацию Android 17 при выходе стабильного релиза.
   - **Статус:** Open

## 9. Архитектурные решения (ADR)

**ADR-1: Единая точка проверки пермишна в use case, а не в каждом DataSource**

- **Решение:** проверка `ACCESS_LOCAL_NETWORK` выполняется в use case до передачи вызова в репозиторий/источник данных.
- **Альтернативы:** проверка внутри каждого DataSource (SMB, SFTP, FTP по отдельности).
- **Почему:** дублирование в трёх источниках данных нарушает DRY и усложняет тестирование; use case — правильный слой для кросс-протокольной политики доступа.

**ADR-2: Минимальный API guard через атрибут манифеста, а не через `BuildConfig`-флаг**

- **Решение:** `android:minSdkVersion="37"` на объявлении пермишна в манифесте.
- **Альтернативы:** runtime `if (Build.VERSION.SDK_INT >= 37)` везде.
- **Почему:** атрибут манифеста делает намерение явным для Play Store и инструментов анализа; runtime-ветка всё равно нужна, но дублировать её в манифесте не требуется — это разные concerns.

## 10. Связи с другими спеками

- S0017 (bugfix-smb-scanner-metadata-exception, Verified) — не блокирует, но затрагивает ту же область SMB; при реализации S0035 проверить, что fallback-обработка ошибок согласована.
- S0025 (smb-fast-fail, Implemented) — не блокирует; логика fast-fail должна уметь различать «нет пермишна» и «хост недоступен».

Подъём `targetSdk` до 37 (отдельный будущий тикет) должен явно зависеть от `Verified`-статуса S0035.

## 11. Критерии готовности (strategic-level)

1. На устройстве/эмуляторе с Android 17 и `targetSdk 37` при первом открытии SMB/SFTP/FTP-ресурса пользователь видит системный диалог запроса `ACCESS_LOCAL_NETWORK`.
2. При отказе ресурс показывает состояние ошибки с объяснением — без крэша, без бесконечного спиннера.
3. Кнопка «Открыть настройки» в rationale-диалоге ведёт на страницу разрешений приложения.
4. После выдачи разрешения в настройках и возврата в приложение ресурс открывается без перезапуска.
5. На Android ≤ API 36 поведение приложения не изменилось: ни новых диалогов, ни изменений в сетевом потоке.
6. Chromecast-обнаружение на Android 17 без пермишна не вызывает крэша; в UI отображается состояние «Cast недоступен».
7. Все три локализации (EN/RU/UK) содержат корректные строки rationale-диалога.
8. Флейвор `photos` не демонстрирует никаких изменений поведения.
