# S3371 froze this list; S3376 decided what it is. Destructive operations in the transfer strategy
# trees that register the mutation journal through their CALLER, not here. One
# "<relative path>#<operation>" token per line.
#
# Why none of them can register where it is declared (S3376 ADR-1): every journal entry is keyed by a
# resource id, and this layer addresses a path and credentials - a resource is a concept one or more
# layers up, where the Browse reconciler that consumes the journal also lives. Registration therefore
# belongs to the caller that owns the resource: the Player, the local FileObserver, the scheduler and
# the watch bridge all do it, each from a place that has the id in hand.
#
# So this is a named STRUCTURAL EXCLUSION, not a queue of work. Do not try to "drain" it by adding a
# resourceId parameter to 21 files across six protocols; that approach is recorded as refuted in
# dev/REFUTED_APPROACHES.md, with the measurement, and the reasoning is in
# PLAN/S3376_transfer-layer-operations-bypass-mutation-journal/research/01__journal-seam-and-undo-capability.md
#
# Calling these rows read-only to reach a green run would still be the one genuinely wrong answer: the
# allowlist beside this file would then assert something false about deleteFile.
#
# This list may SHRINK - when an operation leaves the trees - and may never grow. Regenerate with
# -UpdateBaseline only when a new destructive transport operation is deliberately admitted, which is
# rare and needs the registering caller named in the same change.
#
# The gate over the CALLERS does not exist yet. S3386 carries that question with the measurement that
# makes it a design pass rather than a wider grep.
