S0720 (Verified 2026-06-26) added a detekt 1.23.8 + detekt-formatting (ktlint ruleset) static-analysis gate, applied per-subproject via a `subprojects { }` block in the root `build.gradle.kts` (plugin declared `apply false` in root `plugins{}`). Config: `config/detekt/detekt.yml` (buildUponDefaultConfig + formatting + complexity thresholds, no type resolution). Frozen ratchet baselines: `config/detekt/baseline-app_v2.xml` (~12706 findings), `config/detekt/baseline-wear.xml` (~254). Wrapper: `scripts/quality/assert-detekt.ps1 -Gate`.

**Why:** the gate is now chained into `scripts/post-change.ps1` for ChangeType **Kotlin** and **Mixed** (`$runsDetektGate`), so any Kotlin/Mixed post-change now invokes a full `:app_v2:detekt :wear:detekt` gradle run - it is no longer a fast static-only facade for .kt changes. detekt is deliberately NOT wired into `assemble*`, so normal debug/release builds and `.\a.ps1 fk/fc/d` are unaffected.

**How to apply:**
- Expect `post-change.ps1 -ChangeType Kotlin|Mixed` to take tens of seconds (gradle detekt), not ~2s. Budget for it; it is not a hang.
- detekt fails only on findings NOT in the baseline. If a legit refactor trips it, re-freeze with `.\gradlew.bat :app_v2:detektBaseline :wear:detektBaseline` (don't hand-edit baseline XML).
- **Prefer fixing over re-freezing (baseline is a ratchet DOWN).** Extracting a new method during a refactor makes detekt analyse it fresh - common new flags: `LongMethod` (>80 lines), `CyclomaticComplexMethod` (>20), `ReturnCount` (>2 returns), `ImportOrdering` (adding imports shifts the file's existing ImportOrdering finding so it reports as new). Fix them - split the method into sub-methods, merge guard returns to <=2, fully sort imports (ktlint layout `*,java.**,javax.**,kotlin.**` - kotlinx stays in `*`; case-sensitive ASCII so `ScheduledOpType` < `ScheduledOperation`) - rather than re-freezing, which would bake the new debt in. Verified concretely on S0732 (2026-06-26): extracted `applyLegacyXmlSections` tripped all four, split into 4 sub-methods + import sort -> gate PASS and even removed the pre-existing ImportOrdering finding.
- **Carve-out - re-freeze when the resurfaced finding is PRE-EXISTING/out-of-scope debt your line-shift merely un-matched, not new debt you authored.** Distinguish: (a) you extracted/wrote the flagged code -> fix it (above); (b) your import insertion or ctor-signature edit shifted an *already-baselined* finding on an *already-noncompliant* block, OR the failing lines are in files OTHER tickets are editing in the dirty tree. Case (b) "fixes" = reorder 40+ pre-existing imports / refactor a ctor you only shrank / edit another ticket's file -> all out-of-scope churn or ticket-isolation breach, so re-freeze instead. Verified on S0730 (2026-06-26): removing an unused ctor param (11->10) un-matched its baselined `LongParameterList`; added imports un-matched whole-block `ImportOrdering` on 4 files already grouped `javax`-in-middle; plus 2 findings in untouched dirty-tree files (`ExecuteScheduledOperationUseCase`, `SmbFileOperationHandler`) -> `detektBaseline` re-freeze was correct, gate PASS.
- detekt 1.23.8 is the version that resolves from gradlePluginPortal and runs cleanly under Gradle 9.2 / Kotlin 2.2.10 / JDK17-21 (lexical, no type resolution). Network to the plugin portal works in this environment.
- `source.setFrom(files("src"))` per module is what makes detekt scan flavor source sets (`src/standard/java`, `src/noLegal/java`, …) where .kt actually live - the plugin default misses them.
- CI form of the gate is an open question of umbrella S0714 (owner-gated), out of scope; only local enforcement via post-change.ps1 was implemented.
