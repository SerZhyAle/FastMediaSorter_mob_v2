## 1. Communication & Style
- **Language & tone**: one home, canon `rules/AUTHOR.md` "Language" + "Working style". Ask if ambiguous.
- **House text style** and its scope: one home, canon `rules/DOCUMENTATION_CONCEPT.md` section 5 "House text style". Repo extension past that scope: long dashes are banned in `.kt` too (Rule 19, gate `scripts/quality/assert-neuroslop.ps1`).
- **Timestamps** and **brevity on request**: one home, canon `rules/AI_USAGE.md` section 7 - no clock-time prefix, and `caveman` compresses prose only, never a check or a gate's reason. Repo trigger: `/caveman`.
- **Spec Writing**: Lists over tables (tables only for 3+ columns). No pseudographics. No self-evident links. One idea per bullet. No section summaries. Draft specs exempt.
- **No self-cost estimates anywhere in planning output** (owner ruling 2026-08-25): never write how long a change will take, how much effort it is, or how many lines it will add - no hours, no `~150 LOC`, no `Line budget` column, no "estimated phases", in a spec, a phase file, a plan or a chat reply. There is no budget these numbers feed, so each one is output nobody reads, and they are measurably wrong: S1431's phase table missed its own line budgets on three of its phases by 4-23 lines. Describe what a change **is** - which files, which layers, which gates it trips - never what it will **cost**. Sizes read off disk are untouched by this: Rule 2's 2000-LOC ceiling and Rule 5's 500-LOC backup threshold measure a real file, they do not predict one.

## 2. Debug Verification Tags (Sxxxx)
- Invariant: `Timber.d("Sxxxx: <desc>")` exists in `.kt` **if and only if** spec `Sxxxx` is in `BlockNeedUserTest`.
- **Into BlockNeedUserTest**: insert one tag at entry point of changed flows before final build.
- **A probe owns its line, whole (owner ruling 2026-09-02).** One `Timber.d("Sxxxx: ..")` statement, alone on its own line, never wrapped across lines, never sharing a line with code that has to survive it. The reason is mechanical: a probe is deleted in bulk by whoever removes it - a sweep over 176 files at the release of 2.60.9021.951 - and a deletion can only be safe if dropping the line drops exactly the probe. It was not: `}.also { Timber.d("S2354: ..") }` was also the closing brace of a `when`, `).also { .. }` closed an argument list, and removing those lines broke the build with `Unresolved reference 'gcd'` several hundred lines away. Forbidden shapes, all measured that day: `}.also { Timber.d(..) }`, `).also { .. }`, `if (cond) Timber.d(..)`, `LaunchedEffect(x) { Timber.d(..) }`, and any `Timber.d(` whose arguments continue on the next line. Gate: the `probe-line-shape` check in `scripts/quality/assert-no-ticket-logs.ps1`.
- **Out of BlockNeedUserTest**: delete all matching `Timber.d("Sxxxx:` lines immediately. **A release archives that status too (owner ruling 2026-09-02), and that is an exit like any other** - `/skill-release` step 12c sweeps `Implemented` + `Verified` + `BlockNeedUserTest` into `PLAN/archive/`, so it deletes their probes in the same sweep and proves it with `assert-no-ticket-logs.ps1`. Skipping the deletion leaves a tag whose ticket is `Archived`, which fails every later closure in every session.
- Permanent logs must not contain `Sxxxx`.

## 3. Skill Routing (Auto-trigger prompts)

Every skill's own `description` is injected fresh each turn (see the "Available skills" system reminder) - do not restate it here. This section holds only what that injection cannot supply on its own: the owner's short aliases, and the size-tier ordering across commands whose descriptions overlap.

- **Short aliases are real command files, and they are generated.** Claude Code has no native alias field: a command is addressed by its **file name**, and `name:` is ignored in `.claude/commands/*.md`, so a second invocable name can only be a second file. Fourteen hand-typed commands therefore each answer to three extra names - a two-letter Latin one (`/sd`), its Cyrillic transliteration (`/сд`), and the same physical keys typed on the ЙЦУКЕН layout (`/ыв`), which is the one that survives forgetting to switch layout. Each alias file only delegates: it invokes the canonical command and passes `$ARGUMENTS` through, so no body is ever duplicated. **The table is the source of truth in `scripts/utils/generate-command-aliases.ps1`** - never hand-write or hand-edit an alias file; add a row and regenerate (`-Check` verifies, `-Prune` retires). Every generated file carries `disable-model-invocation: true`, so the alias stays typeable by the owner while staying out of the model-facing skill listing and costing nothing per turn. `/arc` = `/spec-arc` is now one of these files, not a chat-only expansion. Non-ASCII command names are undocumented upstream, so the two Cyrillic sets are an empirical bet: if the CLI ever stops routing `/сд`, `-Prune -Sets latin` drops them without touching the Latin set.
- **Size tier, smallest first:** `/quick` (single string/typo/design tweak, no spec/build) -> `/skill-fix` (fast bug/UI fix, and the doc/config/script tweak that needs no gradle; skips doc/git/build/dev-log/spec) -> `/spec-next`/`/spec-do` (full ticket pipeline; `/spec-do` is the same picker minus both stops - the context threshold and the empty queue - so it idles, re-checks, and runs until the operator stops it). Picking too heavy a command for a small fix is the common miss - try the smallest tier first. **Nudged mechanically** by the `UserPromptSubmit` hook `.claude/hooks/nudge-small-task-tier.ps1`, which fires on a micro-task-shaped prompt and names the two cheap tiers at the moment of routing; advisory by construction and always exits 0. Why this is an event and not a paragraph - including this repo's own measurement that put it there - is canon: `rules/AI_USAGE.md` section 5.
- **Unattended batches run as processes, not as one long session (2026-08-25).** The principle has one home, canon `rules/AI_USAGE.md` section 3 ("For an unattended batch, make the PROCESS boundary the reset"), and the 83%-above-150k measurement it carries is this repo's. Repo mechanism: `scripts/utils/run-spec-queue.ps1` takes the next ticket off `PLAN/RELEASE_QUEUE.md` through the same preflight ranker, runs `/spec-all` for it in a **fresh `claude -p` process**, and repeats however that run ended - which is the shape `/spec-do` cannot produce. Two or three instances may run in parallel (`-Instance b`, `-StartDelaySeconds 20`); a ticket a live sibling holds is already skipped by the ranker, and the few-second window left is resolved by the child's own lease claim. The model is chosen per ticket by `-ModelPolicy tiered`, **status before tier**: the decision states (Draft, Approved, Tactical, In Progress, Partial, Broken, BlockQuestions) and tier 4+ take the strong model; the code-complete states (`Implemented`, `BlockNeedUserTest`, where the run audits code the tree already carries) and tiers 1-3 take the cheap one. Prefer it over `/spec-do` for anything left running unattended; `/spec-do` remains the interactive form.
- **Device-free sibling of `/spec-all`:** `/spec-code` runs the same pipeline with every on-device step removed - no device probe, no install, no emulator, no `/spec-test-device`. The build is the only test, and a ticket that edited anything shipping in an APK ends at `BlockNeedUserTest` for `/spec-sweep` to drain; a docs/scripts-only ticket still audits through to `Verified`. Pick it when no device is attached, the connected device belongs to another session, or the owner's phone must not be touched; pick `/spec-all` when a device is available and the ticket's acceptance is on-device.

**Command file shape.** A command is a driver at `.claude/commands/<name>.md`, injected in full and permanently on invocation. The six largest pipeline commands carry a companion at `.claude/reference/<name>.md` holding their tables, literal formats and edge-case catalogues, read only when the driver names the condition. Verbatim file skeletons live once in `.claude/templates/`. Neither store sits under `.claude/commands/`, because everything there is registered as an invocable command. Follow this shape for a new command.

### 3.1 Auto-capture of out-of-scope findings (`/spec-draft`)
- At **any** stage - research, development, audit, code review, device test, log analysis - when you discover a problem meeting ALL three conditions, invoke the `/spec-draft` procedure to park it, without asking:
  1. Unrelated to the current task/ticket (out of scope).
  2. Not trivial enough to fix on the spot (more than a one-liner, or fixing now would derail current work).
  3. Requires its own research and execution.
- Before creating: dedup-check by symptom (`scripts/spec_catalog/search.ps1`); if an open ticket already covers it, reference that id instead of drafting a duplicate.
- Batch discovery: a general log analysis / audit / review surfacing several qualifying problems → one `/spec-draft` per distinct problem (after dedup).
- Non-disruptive: park it, report `parked: Sxxxx <slug>` in chat, then resume the original task. Never switch the active ticket because of a parked finding.
- Do NOT park: in-scope work, trivial fixes (do them inline), cosmetic nitpicks not worth a ticket, or already-ticketed issues.
- Read-only contexts (e.g. `android-solution-researcher`) cannot mutate the catalog: instead list the qualifying findings as `/spec-draft` candidates in the report for the caller to capture.

## 4. Spec Catalog (Sxxxx tickets)
- Specs: `PLAN/Sxxxx_<slug>.md`. Directory: `PLAN/Sxxxx_<slug>/`.
- Journal: `PLAN/spec-catalog.jsonl` (never hand-edit). CLI: `insert.ps1`, `update.ps1`, `select.ps1`, `delete.ps1`.
- Status header sync: catalog mutators update the first `**Status:**` line in spec file automatically.
- **Block* note (mandatory):** every transition INTO a `Block*` status must supply `-StatusNote '<reason>'` to `update.ps1` / `close-and-log.ps1`. `BlockNeedUserTest` → describe what the user must test on device. `BlockExternal` / `BlockByOtherTask` / `BlockQuestions` → describe the blocker and what resolves it. For `BlockByOtherTask` that description must additionally carry the id as a literal `Blocker: Sxxxx` token, in the note or in §10: that token is the only thing the tooling reads, because §10 prose lists consumers and neighbours next to blockers and as often denies the dependency it mentions, so a bare id there cannot state which way the arrow points (S1482). A ticket that records none is skipped as `blocker-unresolvable`, which means "fix the spec", not "wait". The note is written to the spec header as `**Status note:**` immediately after `**Status:**` so it is readable at a glance. Leaving a `Block*` status auto-clears the note.
- **Carried open item (mandatory on closing):** a transition INTO `Implemented` or `Verified` requires every item in the spec's research section ("Открытые вопросы / Research items") to be `Resolved`, or to carry a literal `Carrier: Sxxxx` token naming the ticket that now owns the question. Like `Blocker: Sxxxx` above, only the literal token is read - the surrounding prose names neighbours as often as owners. The carrier is an ordinary catalog record, so it reappears in `PLAN/RELEASE_QUEUE.md` on its own and the queue's ordering rule 6 batches it into `/spec-quiz`; no separate registry of owner decisions exists. Without this, a closed ticket leaves the queue and takes the question with it - measured 2026-08-13, 134 of 1506 closed specs stranded 372 such items. `Archived` is deliberately not gated: it closes a ticket that already passed. Gate: `scripts/spec_catalog/check-open-items-carried.ps1`, invoked with the durable-evidence gate (S1606) from `Assert-ClosingGates` in `_lib.ps1`, which `update.ps1`, `close.ps1` and `bulk-update.ps1` all call - a gate wired into only one of them guards the path used least (S1607).
- **Recorded audit (mandatory on `Verified`, S2298):** `Verified` means "the audit passed", and the audit's verdict lives in exactly one place - the spec's `## Last Audit` block, which `/spec-check` writes and `/spec-fix` reads; no separate audit registry exists. A transition INTO `Verified` therefore requires that block to be present and non-empty, a heading with nothing under it being the same absence of evidence with a table of contents. `Implemented` is deliberately **not** gated, unlike the two bullets above: it asserts only that the code is done, which is true before any audit has run, so demanding the block there would require a verdict ahead of the run that produces one. Measured 2026-09-01 across every live `Verified` spec: 7 of 129 carry no block (`S1783`, `S1872`, `S2002`, `S2053`, `S2197`, `S2263`, `S2280`), and their files attribute the closure to `/spec-all`, to `/spec-code` and to no marker at all - three paths, one missing check, which is why it sits in `Assert-ClosingGates` rather than in a command. The block is found by heading TEXT, so the numbered form `## 6. Last Audit` counts: the literal `## Last Audit` test that preceded this reported it as absent both in the measurement that opened the ticket and in `preview.ps1`'s `last_audit_present`, whose false negative reaches `/spec-all` step 0a-drift and re-audits finished work. Gate: `scripts/spec_catalog/check-audit-recorded.ps1`; the shared heading pattern lives beside the research parse in `_research-items.ps1` so the gate's verdict and the operator's flag cannot disagree (S1621).
- **Present probe (mandatory on `BlockNeedUserTest`, S2324):** that status parks a ticket for a human to watch on a device, so a transition INTO it requires one of exactly two things - at least one `Timber.d("Sxxxx: ..")` in `app_v2` or `wear`, or a row in `scripts/quality/blockneedusertest-probe-baseline.txt` giving the reason a probe cannot exist. Without the probe the log cannot tell "the scenario went through the new code" from "the scenario never reached it", so the device pass proves nothing. The refusal names **both** exits, because refusing a ticket that changed only documentation, scripts or resources would make it unclosable, which is worse than the gap. This is Rule 2's reverse half; the forward half (a probe whose ticket is not in the status) is `assert-no-ticket-logs.ps1`, and the two decide "carries a probe" through one shared helper, `scripts/quality/lib/blockneedusertest-probes.ps1`, so the closing gate cannot refuse what the tree gate passes (S1621) - not hypothetical, since a Timber call may span physical lines and a per-line search finds a strictly smaller set. Why a gate and not a sweep: measured 2026-09-02, 17 tickets sat in the status with no probe, and the set had turned over rather than shrunk, gaining three in a day. Why nothing caught it: `post-change.ps1` hands the tree gate `-ChangedFiles` under `-ScopeToFile`, which by S1912's design downgrades the missing-probe half to an advisory exit 3, leaving the project-wide `.\a.ps1 fg` as the only fatal run - red for whichever session happened to run it, over debt belonging to other tickets that session could not fix. Unlike the three bullets above this is not a closing status, so it brings this checker alone and the capability advisory is suppressed: a ticket entering it has not finished shipping anything. An id no record carries exits 2, not 1 - "this ticket does not exist" and "this ticket forgot its probe" call for opposite reactions. Gate: `scripts/spec_catalog/check-probe-present.ps1`, invoked from `Assert-ClosingGates` in `_lib.ps1`.
- **Unique section heading (mandatory on every gated transition, S2357):** a spec file may carry the same section twice, and no other check can see it - the shared parser `Get-SpecSectionLines` stops at the next `## ` once it has entered a section, so all four body-reading gates read the FIRST copy and the rest of the file does not exist for them. The duplicate therefore does not add noise, it silently substitutes whichever copy sorted higher, and it can **invert** an existing gate rather than merely evade it: measured 2026-09-02, S1884's `## Last Audit` block had been split in two, and `check-audit-recorded.ps1` - the S2298 gate whose entire job is to refuse a `Verified` with no recorded verdict - answered PASS on the resulting three-line stub carrying no `**Outcome:**`, while the real block with its counts and eight device checks sat below, unread by anything. Two other shapes existed in the same sweep of all 1395 files under `PLAN/`: S1955's `PHASE_02` held `## Phase Done Criteria` twice with opposite ticks, all `[x]` against all `[ ]`, so one file asserted both that the phase was done and that it had not started; S2156 carried an unfilled skeleton. The repeat is judged **inside one level-1 block, not across the file**, because a compact spec holds several `# Phase NN` blocks that each legitimately own `## Steps` and its neighbours - judging per file reports six offenders on the current tree of which three are those legitimate compact specs, judging per block reports exactly the three real ones. Scope is the ticket's own files, strategic spec plus every `.md` in its tactical folder, which is where S1955's copy lived. Unlike the four bullets above it runs for **every** gated status including `BlockNeedUserTest`: whether a file contradicts itself does not depend on the ticket being finished. Origin is agent-side, not scripted - no `spec_catalog` script writes spec body content and no command driver instructs an append, and S1884's newline seam (CRLF through line 293, LF from 294, exactly where the duplicate starts) shows a second writer appending onto the first one's file. Gate: `scripts/spec_catalog/check-headings-unique.ps1`, invoked from `Assert-ClosingGates` in `_lib.ps1`.
- **Verdict against the CURRENT task (mandatory on `Verified` and `BlockNeedUserTest`, S2367):** a closing verdict is a claim about a task, and the task is edited under a running pipeline - by the owner, by `/spec-quiz` writing an answer into the spec, by a sibling session - while the pipeline reads the spec once at Stage 0 and works from that reading for the rest of the run. So the `## Last Audit` block records a `**Task fingerprint:**`, twelve hex of SHA-256 over the spec body with the parts the pipeline itself writes removed (the `**Status:**` / `**Status note:**` / `**Priority:**` header lines and the audit block), and the gate refuses the transition when the file no longer hashes to it. The exclusions are what make it usable rather than noise: without them the fingerprint would move on the very status flip it guards, and a gate that fires on its own trigger gets switched off. The fix is never a re-stamp - re-read the task and re-run the audit, and if the re-read shows the work no longer covers it, that is `Partial` or `Broken` with the gap written into the spec. **`BlockNeedUserTest` gains the S2298 audit-block requirement in the same ticket**, because it hands work to a human and is therefore a coverage claim exactly as `Verified` is: measured 2026-09-02, 72 of the 158 tickets sitting in that status carried no audit block at all. That was not forgetfulness but a written instruction - `/spec-code` step 4 forbids running `/spec-check` before parking, since it would flip the ticket out of the status and delete the probes the device test needs (S2324) - so the verdict is written by the parking command itself as a **pre-handoff block** (`.claude/reference/spec-all.md` section 11a), which touches no `.kt` and moves no status. `Implemented` stays ungated for S2298's reason: it asserts only that the code is done, before any audit has run. Gates: `scripts/spec_catalog/check-audit-current.ps1` and the widened `check-audit-recorded.ps1`, both invoked from `Assert-ClosingGates` in `_lib.ps1`; the hashed text is defined once in `_task-fingerprint.ps1` and printed by `task-fingerprint.ps1` (S1621).
- **Open manual check (mandatory on closing, S1899):** the principle has one home, canon `rules/TESTING_AND_QA.md` section 1 - a check only a human can run has not happened yet, and the incident it carries is this repo's S1697 (declared done on one unticked device line; an hour on a real phone-watch pair failed one of its five acceptance criteria). Repo mechanism: `/spec-check` counts every unticked `- [ ]` line in a spec's `## Last Audit` as `MANUAL`, and `MANUAL` no longer satisfies `Verified` - a run with zero WARN and FAIL but at least one open manual line scores `BlockNeedUserTest` instead. Only a device pass converts it, which is what `/spec-sweep` drains.
- **A found problem ends `BlockNeedUserTest` (owner ruling 2026-08-31).** `BlockNeedUserTest` means "the verdict is not in yet", never "a known defect is parked here". The moment a problem is found - by a device test, a sweep, an audit, a log read or the owner - the ticket leaves that status in the same action: `update.ps1 -Id Sxxxx -Status <Broken|Partial|In Progress|Approved|Draft> -StatusNote '<the finding, and what must happen next>'`, picking the state by what the finding needs - research reopens it as `Draft`/`Approved`, a known fix as `In Progress`/`Partial`, a regression as `Broken`. This puts it back into `PLAN/RELEASE_QUEUE.md` (work still left), which is the only place unfinished work is safe from being lost; left in `BlockNeedUserTest` it sits in `PLAN/RELEASE_READY.md` and reads as finished content. Never write the finding into the spec and leave the status alone, and never re-close a ticket to `BlockNeedUserTest` for a re-test while the finding is still open. Rule 2's probe invariant follows automatically: leaving `BlockNeedUserTest` deletes every `Timber.d("Sxxxx:` line, and re-entering it re-inserts them.
- Statuses: Draft, Approved, Tactical, In Progress, Implemented, Verified, Partial, Broken, Block*, Archived (soft-delete).
- Priority: 0..100 (default 50).
- **Release plan - two files, split by "is there work left".** `PLAN/RELEASE_QUEUE.md` = work still left (every status below `Implemented`, blocked included). `PLAN/RELEASE_READY.md` = finished content (`Implemented`, `Verified`, `BlockNeedUserTest`). Column `rel` = release package number, `--` = not scheduled. **All three of those statuses archive at the release** (owner ruling 2026-09-02): a device check that has not happened by then was written against a build the release supersedes, so it does not survive it - a defect found later is a fresh ticket against the released version, written from what the user saw. That is why `BlockNeedUserTest` sits in the READY file at all: its code ships either way.
- **The queue decides what gets worked on next - always recommend from it, and obey it.** Package ascending, then the owner's line order inside it; catalog `priority` is only a tiebreak for tickets neither file lists. A deviation needs a stated reason. Catalog owns STATUS, the two files own ASSIGNMENT + ORDER - every catalog write reconciles both automatically, in either direction; no other script may reorder lines or touch `rel`. Enforcing scripts: `scripts/spec_catalog/spec-next-preflight.ps1`, `release-plan.ps1`, `release-queue.ps1` (`-Reconcile`/`-Validate`/`-List`/`-SetCurrent`/`-Ship`).

## 6. Proactive Research & Parallelism
- **Web Search**: autonomy is canon (`rules/AI_USAGE.md` section 1). Repo's preferred sources: developer.android.com, kotlinlang.org, GitHub issues, StackOverflow.
- **Parallel Subagents**: Concurrently run independent tasks (e.g. a catalog query alongside a docs sweep, or two independent file searches). **Never more than one gradle-backed invocation at a time IN ONE BUILD DOMAIN** - a build, a compile check, detekt, the unit suite. Rule 23 orders the second one mechanically through that domain's lock; parallelise everything that does not touch gradle. Since S2109 the two modules are separate domains and their checks may genuinely run at once - measured 2026-08-27, `.\a.ps1 fw` and `.\a.ps1 fk` together took 12 s with no queue wait and no cache contention - so "one gradle call at a time" now means one per module, not one per machine.
- **Background long jobs - the 120 s threshold**: the two-sided rule is canon (`rules/AI_USAGE.md` section 1); this repo pins the boundary to the Bash tool's own foreground timeout and names the targets. **Above it, background**: `d/db/dav/cd/nd/nl/r/fu` - a cold gradle daemon exceeds the timeout. **Below it, do not**: `fk/fkn/fc/fr/dq` and `assert-detekt` measure 14-21 s on a warm daemon, `fg` measures 32 s (S2451, 2026-09-03), and the three wear targets `fw/fwr/fwu` measure 2 s / 1 s / 11 s (S1807, warm daemon - the watch module is far smaller than `app_v2`, so even its full unit suite stays foreground) (`docs/BUILD_TEST_FAST_PATH.md`, "Foreground or background") - wait and read the verdict in the same turn. Enforced by Rule 26. `fg` is quoted separately because it was the one target that crossed the threshold: 45 gates running one at a time reached 142.8 s and were preempted into the background twice, delivering the verdict the way Rule 26 forbids. S2451 made the children concurrent (117 s -> 32 s, same gates, same verdicts), so the margin is real again - but it is now bounded by the slowest single gate, not by the batch's size.
- **Cost discipline**: canon `rules/AI_USAGE.md` section 3. Repo playbook: `docs/AGENT_COST_PLAYBOOK.md` - `/compact` at task boundaries, `/clear` on task switch, raw artifacts to `temp/Sxxxx/` (or `temp/scratch/`), `mobile-mcp` only for exploratory UI walks (`adb.ps1`/Maestro first).
- **Subagent MCP isolation**: canon `rules/AI_USAGE.md` section 3 requires it; the repo mechanic is an explicit `tools:` frontmatter allowlist omitting every MCP tool name - omitting `tools:` entirely grants the parent's full set, MCP included. (S1348: `enable_mcp_tools` is not a real Claude Code option - do not use it.)

## 8. Project Structure & Tech Stack

No lock, queue or lease branches on its content, and no verdict that reaches a spec or a gate may rest on a finding someone else wrote - a finding relieves you of repeating cheap idempotent WORK (a release-scope gate run whose scope is intact, a READY device probe), never of reporting, and a gate reuses only the caller's own session's finding while an environment probe reuses any live one. Identity is one chain in `scripts/utils/agent-identity.ps1` - `FMS_AGENT_ID`, then `CLAUDE_CODE_SESSION_ID`, then the **ancestor host process** `host-<name>-<pid>-<startTicks>`, then `pid-<PID>` - and is never empty; `Get-AgentSessionId` reads it, so lock, lease, queue and chat name one agent the same way, and a subagent inherits its parent's (measured 2026-09-02). The third step is S2408 and exists because the fourth cannot identify a session: a runtime that spawns a fresh shell per command gets a new pid every time, and one measured hour produced 46 identities with 46 nicknames for one session, whose lease then read as dead from its first minute and whose every release was forced. So the walk climbs past shells and interpreters to the first process that outlives a command, and where it runs into a machine-wide process it adopts the ancestor standing directly below that one (S2417) - that ancestor is the root of a single session's tree, so the owner's three `a.ps1 r1/r2/r3` runners started from one `explorer` stay three identities, while the machine-wide process itself is still never adopted and merging every session on the box stays impossible. Only a walk with no ancestor to adopt at all - a trail that ended, the depth bound - falls back to `pid-<PID>`, because a `host-` id minted from a shell that lives one command claims a lifetime it does not have. Which of those happened is recorded on the identity itself as `hostWalk` and rides into every chat message, so the next such failure names its own process instead of needing a measurement in live processes, which is how S2417 had to be diagnosed. `startTicks` is what stops a recycled pid from naming the wrong process. Two chats inside one host process (two Copilot chats in one VS Code window) therefore share one identity: accepted deliberately, one id for two sessions being far better than forty-five for one. A runtime with no hooks sets `FMS_AGENT_ID` **first** - one value kept for its whole session, before `FMS_AGENT_RUNTIME` and `FMS_AGENT_MODEL` - and `FMS_AGENT_HOST_WALK=0` turns the walk off for a runtime the merge would harm. **Every agent speaks under a nickname** (owner ruling 2026-09-02): `<adjective>-<animal>-<MMdd>-<HHmm>`, taken once per session at its first identity resolution (the session-start hook, or the first script it runs), kept in `temp/AGENT-CHAT/names/<id>.json` so every process of the session answers with the same name, overridable through `FMS_AGENT_NAME`, printed on every chat line, in `Status`, in the monitor and in refusal context - the owner reads names, scripts compare ids only. `agent-chat.ps1 -Verb Whoami` says which you are. The chat is one liveness signal among five, which S2408 orders: the owner's own process when the id names one (`host-`/`pid-`), then a ticket's heartbeat, then the transcript, then the chat (ADR-7), then the enqueue time. Every one of them can only extend a life, never shorten one, and the transcript now counts the newest write under `<session>/subagents/**/*.jsonl` as well as `<session>.jsonl` - a session working through a subagent writes nothing to its own file, and eleven such minutes cost a live session its `Code.Scripts` lock on 2026-09-03. A runtime without hooks posts `-Kind session` itself at start and end (AGENTS.md section 9.1). Windows come from the lock timings table, not a second one: progress retention 180 min, finding TTL `SpecTicket.TicketCeilingMinutes`, silence `SpecTicket.SessionStaleMinutes`; every write and every read sweeps first, and the caps are 400 progress files and 200 findings. Contract suite: `scripts/utils/agent-chat.tests/`; mechanism: `docs/DEV_OPS.md` "Agent chat".
35. Device fleet - **which device is attached decides what you may do to it**, and `docs/DEVICE_FLEET.md` is the roster plus the only home of a per-device permission. Read it and match the serial before the first `adb` call of a task: authorization is per device, never per "a device is attached", and the `pm clear` that is routine on the test phone destroys irreplaceable content on the row above it. The fleet in one line each - **Galaxy S21+** (`SM-G996U1`) dedicated test phone, free hand, and **not** paired with the watch; **Galaxy S25 FE** (`SM-S731B`) the owner's personal phone carrying his live `noLegal` debug with real private data **and** the store STANDARD build he watches updates on, so a fresh `noLegal` debug installed over the top plus `pm grant` and read-only probing are allowed while `pm clear`, `uninstall`, a system role, a device settings change and the store build are not; **Galaxy Watch 7** (`SM-L310`) the development watch, everything allowed including reboot, paired with the S25 FE; **Galaxy S20 FE** (`SM-G781B`) a rare guest phone, read-only; **emulators**, free hand at any form factor, created and deleted without asking; and **this workstation**, personal as well as build machine - no shutdown or reboot, and never kill a process this session did not start. Default target when a ticket needs "some device": emulator -> S21+ -> S25 FE, a deviation stated. No command, skill or agent may restate a device permission - point at the file instead, because a restated permission goes stale silently and the stale copy is the one that gets read.

## 12. Validation & Post-Change
- The evidence rule has one home, canon `rules/DEVELOPMENT.md` section 5 / `rules/INVARIANTS.md` 7. Repo form: record `expected: X | actual: Y` for all checks. Red-flag words that mean you are about to claim without proof: "should", "probably", "seems", "looks fixed", "I think it passes" - stop and run the check first.
- Mechanical closure: `pwsh -NoProfile -File scripts/post-change.ps1 -File "<path>" -Target "<target>" -Description "<desc>" -ChangeType <Doc|Script|Config|Tooling|Kotlin|Xml|Mixed> [-Module <app_v2|wear>]`. Use `Tooling` for one set spanning build/config files and repo scripts; source-specific gates require matching files in the set. Skills SHOULD route mechanical closure through this facade instead of hand-rolling each step.
- Dirty-tree closure (S0826/S1338): name the **whole** changed set - `-Files "a.kt,b.kt"` for a multi-file change, `-File` for a single one - then add `-ScopeToFile` to judge every scoped gate against that whole set. detekt fails only on findings inside the set, and the count-ratchet gates (neuroslop / listener-symmetry / flavor-flag / deprecated-pm / public-mutable-flow / focus-highlight) judge a FATAL per-file delta against HEAD instead of a project-wide count, so other tickets' in-flight WIP does not block the close. Only the repo-wide re-render gates (icon-inventory, script-cheatsheet, device-profile-matrix) stay advisory. Omit `-ScopeToFile` for release/CI to get the strict full-project gate. Naming one file while changing four certifies one file - the verdict covers exactly what you passed.
- Closure verdict and exit codes (S1338): `post-change: PASS` is printed only when every gate passed; an advisory gate that found something prints `PASS WITH ADVISORIES (n)` and names each one - read it, the bare word is the only clean verdict. Exit codes: **0** passed, **1** a gate failed, **2** could not verify (invalid, absent or unexpanded file argument; missing tooling). A caller must distinguish 1 from 2 - "found a defect" and "did not look" are different answers. The gates run before the mutating steps, so a failed closure writes no changelog row and re-running after a fix produces exactly one. A closure that passed **with advisories** returned 0 and did write its row - re-running that one after fixing what the advisory named still leaves exactly one row, because the dev-log guard identifies the change and ignores the size of its file set (S1622); before that, fixing an advisory usually regenerated a file, the file joined the `[set of N: ..]` tail, and the tail alone made the second row look new.
- Journaling granularity: one dev-log entry per logical change/ticket, not per touched file (batch multi-file changes via `close-and-log.ps1 -DevLogs`); run `catalog_sync.ps1` once per ticket, not per `.kt` edit.
- Validation Ladder:
  - Doc: Grep for content.
  - Script: Run, exit 0.
  - Config: Target build passes.
  - Kotlin/Java: prefer `.\a.ps1 fk` for compile-only symbol changes; escalate to `.\a.ps1 fc`, targeted `--tests`, or full `.\a.ps1 d` only when the touched area needs packaging/resource proof.
  - Python: Syntax check + test.
  - Layout/manifest: Target build passes - and since S1915 this rung is **enforced**, not merely asked for. The principle has one home, canon `rules/DEVELOPMENT.md` section 15 ("The closure RUNS the ladder's rung; it does not merely ask for it"), and the incident it carries is this repo's S1881. Repo mechanism: the `resource-link-gate` in `post-change.ps1` links the changed resources whenever the set carries one (`check-standard-fast.ps1 -Mode Resources`, variant chosen from the touched source set, `BUILD.LOCK` taken by the helper) and fails the closure on the aapt error - nothing else in the facade runs aapt, and `fk` compiles Kotlin without linking anything. Cost measured 1.9-41.8 s per flavor, all foreground: `docs/BUILD_TEST_FAST_PATH.md`.

## 13. Code Audit Protocol
- Full protocol: `docs/CODE_AUDIT_PROTOCOL.md` (layered audit, evidence ladder, per-layer checklists). Read and apply it whenever an **audit trigger** fires - do not re-derive the checks. Use the cheapest evidence rung that matches the risk.
- **Audit triggers**: new screen/manager/worker/repository/long-lived helper; lifecycle change; coroutine/Flow/callback/listener/observer change; shared-mutable-state/synchronization/dispatcher change; Room entity/DAO/query/migration/transaction change; player/image-loading/caching/network-path change; startup-path change; DI scope or singleton-ownership change; build/manifest/R8/keep-rule change affecting profiling/startup/minification/process; reported crash/ANR/OOM/jank/leak; **phase boundary in a multi-phase task** (tactical spec phase, or any large task split into sequential phases) - audit the phase just finished before starting the next.
- **Phase-boundary audits are mandatory, not deferred to pipeline end**: fixing a defect costs roughly one phase's worth of rework when caught at the next phase boundary, versus every subsequent phase's worth when it surfaces only at the final audit (`/spec-check`) or in a later ticket. `/spec-dev` runs this automatically per phase (see its "Phase-boundary audit" step); apply the same discipline manually for any multi-phase work driven outside `/spec-dev`.
- Per-layer checklists (severity taxonomy, listener symmetry, Room main-safety, concurrency correctness, player/Glide ownership, R8/minified proof) live only in `docs/CODE_AUDIT_PROTOCOL.md` Layers 1-8 - read them there when a trigger fires, do not expect a copy here.
- Recurring finding -> convert to a mechanical gate (`scripts/quality/assert-*.ps1`), per Rule 19/20 and Layer 8. Do not duplicate the protocol text in rules - link to it.
- Authoring a new rule / gate / command / skill: follow `dev/RULE_AND_SKILL_AUTHORING.md` (observe the failure first, write minimal, close rationalizations, promote recurring rules to gates; trigger-focused `description` fields).
