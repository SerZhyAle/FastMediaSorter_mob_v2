> **Universal conventions (canon):** the portfolio-wide rules are the SZA Unified Rules, shipped as the `sza` Claude Code plugin (`/plugin marketplace add SerZhyAle/sza-unified-rules`; `/plugin install sza@sza-unified-rules`) - consumption model **REFERENCE**, not mirrored here. This repo is overlay B and the **reference the core was extracted from**, so the rules below are not a re-authoring of the canon - they are this repo's Android operational layer (exact `a.ps1` targets, gate names, the flavor matrix, the Sxxxx spec/probe lifecycle) plus the deltas and channel matrix recorded in the canon at `rules/contrib/fastmediasorter_mob_v2.md` (adoption stamp: `.sza-canon.json`). When a rule here restates a universal principle, the canon is the source of truth; fix universal rules in a canon session, not here.

> Parallel rule set for non-Claude agents: `AGENTS.md` (import order `CLAUDE.md` -> `.github/copilot-instructions.md` -> prompt; stricter wins). When changing shared rules, sync `AGENTS.md` too.

## 1. Communication & Style
- **Language & tone**: one home, canon `rules/AUTHOR.md` "Language" + "Working style". Ask if ambiguous.
- **House text style** and its scope: one home, canon `rules/DOCUMENTATION_CONCEPT.md` section 5 "House text style". Repo extension past that scope: long dashes are banned in `.kt` too (Rule 19, gate `scripts/quality/assert-neuroslop.ps1`).
- **Timestamps** and **brevity on request**: one home, canon `rules/AI_USAGE.md` section 7 - no clock-time prefix, and `caveman` compresses prose only, never a check or a gate's reason. Repo trigger: `/caveman`.
- **Spec Writing**: Lists over tables (tables only for 3+ columns). No pseudographics. No self-evident links. One idea per bullet. No section summaries. Draft specs exempt.
- **No self-cost estimates anywhere in planning output** (owner ruling 2026-08-25): never write how long a change will take, how much effort it is, or how many lines it will add - no hours, no `~150 LOC`, no `Line budget` column, no "estimated phases", in a spec, a phase file, a plan or a chat reply. There is no budget these numbers feed, so each one is output nobody reads, and they are measurably wrong: S1431's phase table missed its own line budgets on three of its phases by 4-23 lines. Describe what a change **is** - which files, which layers, which gates it trips - never what it will **cost**. Sizes read off disk are untouched by this: Rule 2's 2000-LOC ceiling and Rule 5's 500-LOC backup threshold measure a real file, they do not predict one.

## 3. Skill Routing (Auto-trigger prompts)

Every skill's own `description` is injected fresh each turn (see the "Available skills" system reminder) - do not restate it here. This section holds only what that injection cannot supply on its own: the owner's short aliases, and the size-tier ordering across commands whose descriptions overlap.

- **Short aliases are real command files, and they are generated.** Claude Code has no native alias field: a command is addressed by its **file name**, and `name:` is ignored in `.claude/commands/*.md`, so a second invocable name can only be a second file. Fourteen hand-typed commands therefore each answer to three extra names - a two-letter Latin one (`/sd`), its Cyrillic transliteration (`/сд`), and the same physical keys typed on the ЙЦУКЕН layout (`/ыв`), which is the one that survives forgetting to switch layout. Each alias file only delegates: it invokes the canonical command and passes `$ARGUMENTS` through, so no body is ever duplicated. **The table is the source of truth in `scripts/utils/generate-command-aliases.ps1`** - never hand-write or hand-edit an alias file; add a row and regenerate (`-Check` verifies, `-Prune` retires). Every generated file carries `disable-model-invocation: true`, so the alias stays typeable by the owner while staying out of the model-facing skill listing and costing nothing per turn. `/arc` = `/spec-arc` is now one of these files, not a chat-only expansion. Non-ASCII command names are undocumented upstream, so the two Cyrillic sets are an empirical bet: if the CLI ever stops routing `/сд`, `-Prune -Sets latin` drops them without touching the Latin set.
- **Size tier, smallest first:** `/quick` (single string/typo/design tweak, no spec/build) -> `/skill-fix` (fast bug/UI fix, and the doc/config/script tweak that needs no gradle; skips doc/git/build/dev-log/spec) -> `/spec-next`/`/spec-do` (full ticket pipeline; `/spec-do` is the same picker minus both stops - the context threshold and the empty queue - so it idles, re-checks, and runs until the operator stops it). Picking too heavy a command for a small fix is the common miss - try the smallest tier first. **Nudged mechanically** by the `UserPromptSubmit` hook `.claude/hooks/nudge-small-task-tier.ps1`, which fires on a micro-task-shaped prompt and names the two cheap tiers at the moment of routing; advisory by construction and always exits 0. Why this is an event and not a paragraph - including this repo's own measurement that put it there - is canon: `rules/AI_USAGE.md` section 5.
- **Unattended batches run as processes, not as one long session (2026-08-25).** `scripts/utils/run-spec-queue.ps1` takes the next ticket off `PLAN/RELEASE_QUEUE.md` through the same preflight ranker, runs `/spec-all` for it in a **fresh `claude -p` process**, and repeats however that run ended. The process boundary is the context reset, and unlike a `/clear` it cannot be forgotten: every ticket starts empty instead of being billed against everything the session already carried - measured 2026-08-25, 83% of a week's usage was spent above 150k of carried context, and that is the shape `/spec-do` produces by construction. Two or three instances may run in parallel (`-Instance b`, `-StartDelaySeconds 20`); a ticket a live sibling holds is already skipped by the ranker, and the few-second window left is resolved by the child's own lease claim. The model is chosen per ticket rather than fixed: Opus wherever a decision is left, Sonnet for `Implemented` (an audit of code that already exists) and tier 1-2. Prefer it over `/spec-do` for anything left running unattended; `/spec-do` remains the interactive form.
- **Device-free sibling of `/spec-all`:** `/spec-code` runs the same pipeline with every on-device step removed - no device probe, no install, no emulator, no `/spec-test-device`. The build is the only test, and a ticket that edited anything shipping in an APK ends at `BlockNeedUserTest` for `/spec-sweep` to drain; a docs/scripts-only ticket still audits through to `Verified`. Pick it when no device is attached, the connected device belongs to another session, or the owner's phone must not be touched; pick `/spec-all` when a device is available and the ticket's acceptance is on-device.

**Command file shape.** A command is a driver at `.claude/commands/<name>.md`, injected in full and permanently on invocation. The six largest pipeline commands carry a companion at `.claude/reference/<name>.md` holding their tables, literal formats and edge-case catalogues, read only when the driver names the condition. Verbatim file skeletons live once in `.claude/templates/`. Neither store sits under `.claude/commands/`, because everything there is registered as an invocable command. Follow this shape for a new command.

### 3.1 Auto-capture of out-of-scope findings (`/spec-draft`)
- At **any** stage - research, development, audit, code review, device test, log analysis - when you discover a problem meeting ALL three conditions, invoke the `/spec-draft` procedure to park it, without asking:
  1. Unrelated to the current task/ticket (out of scope).
  2. Not trivial enough to fix on the spot (more than a one-liner, or fixing now would derail current work).
  3. Requires its own research and execution.
- Before creating: dedup-check by symptom (`scripts/spec_catalog/search.ps1`); if an open ticket already covers it, reference that id instead of drafting a duplicate.
- Batch discovery: a general log analysis / audit / review surfacing several qualifying problems → one `/spec-draft` per distinct problem (after dedup).
- Non-disruptive: park it, report `parked: Sxxxx <slug>` in chat, then resume the original task. Never switch the active ticket because of a parked finding.
- Do NOT park: in-scope work, trivial fixes (do them inline), cosmetic nitpicks not worth a ticket, or already-ticketed issues.
- Read-only contexts (e.g. `android-solution-researcher`) cannot mutate the catalog: instead list the qualifying findings as `/spec-draft` candidates in the report for the caller to capture.

## 4. Spec Catalog (Sxxxx tickets)
- Specs: `PLAN/Sxxxx_<slug>.md`. Directory: `PLAN/Sxxxx_<slug>/`.
- Journal: `PLAN/spec-catalog.jsonl` (never hand-edit). CLI: `insert.ps1`, `update.ps1`, `select.ps1`, `delete.ps1`.
- Status header sync: catalog mutators update the first `**Status:**` line in spec file automatically.
- **Block* note (mandatory):** every transition INTO a `Block*` status must supply `-StatusNote '<reason>'` to `update.ps1` / `close-and-log.ps1`. `BlockNeedUserTest` → describe what the user must test on device. `BlockExternal` / `BlockByOtherTask` / `BlockQuestions` → describe the blocker and what resolves it. For `BlockByOtherTask` that description must additionally carry the id as a literal `Blocker: Sxxxx` token, in the note or in §10: that token is the only thing the tooling reads, because §10 prose lists consumers and neighbours next to blockers and as often denies the dependency it mentions, so a bare id there cannot state which way the arrow points (S1482). A ticket that records none is skipped as `blocker-unresolvable`, which means "fix the spec", not "wait". The note is written to the spec header as `**Status note:**` immediately after `**Status:**` so it is readable at a glance. Leaving a `Block*` status auto-clears the note.
- **Carried open item (mandatory on closing):** a transition INTO `Implemented` or `Verified` requires every item in the spec's research section ("Открытые вопросы / Research items") to be `Resolved`, or to carry a literal `Carrier: Sxxxx` token naming the ticket that now owns the question. Like `Blocker: Sxxxx` above, only the literal token is read - the surrounding prose names neighbours as often as owners. The carrier is an ordinary catalog record, so it reappears in `PLAN/RELEASE_QUEUE.md` on its own and the queue's ordering rule 6 batches it into `/spec-quiz`; no separate registry of owner decisions exists. Without this, a closed ticket leaves the queue and takes the question with it - measured 2026-08-13, 134 of 1506 closed specs stranded 372 such items. `Archived` is deliberately not gated: it closes a ticket that already passed. Gate: `scripts/spec_catalog/check-open-items-carried.ps1`, invoked with the durable-evidence gate (S1606) from `Assert-ClosingGates` in `_lib.ps1`, which `update.ps1`, `close.ps1` and `bulk-update.ps1` all call - a gate wired into only one of them guards the path used least (S1607).
- **Open manual check (mandatory on closing, S1899):** `Verified` requires that nothing is left for a human to observe. `/spec-check` counts every unticked `- [ ]` line in a spec's `## Last Audit` as `MANUAL`, and `MANUAL` no longer satisfies `Verified` - a run with zero WARN and FAIL but at least one open manual line scores `BlockNeedUserTest` instead, because nothing is broken and something is simply unobserved. Before this, `Verified` accepted `MANUAL`, so S1697 was declared done carrying an unticked device line and an hour on a real phone-watch pair showed one of its five acceptance criteria failing outright. A check a machine cannot run has not happened yet; only a device pass converts it, which is what `/spec-sweep` drains.
- Statuses: Draft, Approved, Tactical, In Progress, Implemented, Verified, Partial, Broken, Block*, Archived (soft-delete).
- Priority: 0..100 (default 50).
- **Release plan - two files, split by "is there work left".** `PLAN/RELEASE_QUEUE.md` = work still left (every status below `Implemented`, blocked included). `PLAN/RELEASE_READY.md` = finished content (`Implemented`, `Verified`, `BlockNeedUserTest`). Column `rel` = release package number, `--` = not scheduled.
- **The queue decides what gets worked on next - always recommend from it, and obey it.** Package ascending, then the owner's line order inside it; catalog `priority` is only a tiebreak for tickets neither file lists. A deviation needs a stated reason. Catalog owns STATUS, the two files own ASSIGNMENT + ORDER - every catalog write reconciles both automatically, in either direction; no other script may reorder lines or touch `rel`. Enforcing scripts: `scripts/spec_catalog/spec-next-preflight.ps1`, `release-plan.ps1`, `release-queue.ps1` (`-Reconcile`/`-Validate`/`-List`/`-SetCurrent`/`-Ship`).

## 6. Proactive Research & Parallelism
- **Web Search**: autonomy is canon (`rules/AI_USAGE.md` section 1). Repo's preferred sources: developer.android.com, kotlinlang.org, GitHub issues, StackOverflow.
- **Parallel Subagents**: Concurrently run independent tasks (e.g. a catalog query alongside a docs sweep, or two independent file searches). **Never more than one gradle-backed invocation at a time IN ONE BUILD DOMAIN** - a build, a compile check, detekt, the unit suite. Rule 23 orders the second one mechanically through that domain's lock; parallelise everything that does not touch gradle. Since S2109 the two modules are separate domains and their checks may genuinely run at once - measured 2026-08-27, `.\a.ps1 fw` and `.\a.ps1 fk` together took 12 s with no queue wait and no cache contention - so "one gradle call at a time" now means one per module, not one per machine.
- **Background long jobs - the 120 s threshold**: the two-sided rule is canon (`rules/AI_USAGE.md` section 1); this repo pins the boundary to the Bash tool's own foreground timeout and names the targets. **Above it, background**: `d/db/dav/cd/nd/nl/r/fu` - a cold gradle daemon exceeds the timeout. **Below it, do not**: `fk/fkn/fc/fr/fg/dq` and `assert-detekt` measure 14-21 s on a warm daemon, and the three wear targets `fw/fwr/fwu` measure 2 s / 1 s / 11 s (S1807, warm daemon - the watch module is far smaller than `app_v2`, so even its full unit suite stays foreground) (`docs/BUILD_TEST_FAST_PATH.md`, "Foreground or background") - wait and read the verdict in the same turn. Enforced by Rule 26.
- **Cost discipline**: canon `rules/AI_USAGE.md` section 3. Repo playbook: `docs/AGENT_COST_PLAYBOOK.md` - `/compact` at task boundaries, `/clear` on task switch, raw artifacts to `temp/Sxxxx/` (or `temp/scratch/`), `mobile-mcp` only for exploratory UI walks (`adb.ps1`/Maestro first).
- **Subagent MCP isolation**: canon `rules/AI_USAGE.md` section 3 requires it; the repo mechanic is an explicit `tools:` frontmatter allowlist omitting every MCP tool name - omitting `tools:` entirely grants the parent's full set, MCP included. (S1348: `enable_mcp_tools` is not a real Claude Code option - do not use it.)

## 9. Common Commands (a.ps1 launcher)
- Build: `.\a.ps1 d` (fast reusable debug APK), `db` (fast debug no-zip), `dav` (debug APK with timestamped app version), `dq` (quiet), `cd` (clean debug), `nd`/`nl` (noLegal debug/release), `r` (release AAB - builds in a dedicated git worktree, not the main checkout; driven by `/skill-release`), `bf` (build failure structured digest).
- Checks: `.\a.ps1 fk` (Kotlin compile, standard), `fkn` (Kotlin compile, noLegal), `fr` (resources/manifest), `fc` (code + resources), `fg` (fast static gates batch - neuroslop+pm+listener+flavor+ticket-log in one process, `-IncludeDetekt` opt-in), `ch` (typos & lint), `ss` (unresolved specs), `ivn` (install noLegal debug APK).
- Tests: `.\a.ps1 fu` (full unit suite - acquires `BUILD.LOCK` per Rule 23; never call `gradlew.bat` directly). kapt recovery: `scripts/utils/recover-kapt-stall.ps1`.
- **Wear module has its own three targets, and the phone ones do not cover it (S1807):** `fw` (Kotlin compile), `fwr` (resources/manifest), `fwu` (unit suite). `fk`/`fkn`/`fr`/`fc`/`fu` all check `app_v2` and exit 0 without compiling a single watch file, so quoting one under a `wear/` change records a verdict about the other module - measured five times across S1710, S1730 and S1781. Every fast check now prints the module it checked in its banner; read that line before quoting the exit code.
- Device (ad-hoc, ~0 tokens): `scripts/devtest/adb.ps1 <verb>` or `.\a.ps1 adb <verb>` for quick chores against a connected emulator/device - `devices`, `props`, `current`, `launch`, `stop`, `logcat-clear`, `install`, `shot`, `log -Tail N -Grep <regex>`, `tap/swipe/text/key`, `prefs`, `shell -Cmd`, and the UI-tree verbs `uidump` / `tap-id -ResourceId <s>` / `tap-label -Label <s>` / `clip-check` (S1847, S1879). Auto-discovers adb (not on PATH); supports `-DeviceId`/`-Release`/`-OutDir`/`-Json` with stable exit codes. **Tap by label or by id, never by a remembered coordinate:** a list that scrolled between the dump and the tap sends `tap -X -Y` into the neighbouring row, which happened twice in one wear sweep; both tap verbs re-read the tree in the same call and exit 8 rather than tapping something else. **Between the two, prefer the id:** a label is translated and a `resource-id` is not, so a call aimed at a label works on the locale it was written on and returns 8 on every other one (S1879) - `tap-id` takes the short name straight from the layout, and `uidump` prints that name beside every label (`-Ids` also lists the nodes that carry nothing else). `tap-label` stays right where there is no id, which is most of Compose on the watch. `clip-check` reads the display shape off the device, so the round watch and the rounded-corner phone use one rule. Shortcuts: `adb-devices/-shot/-log/-current/-launch/-logcat-clear`. **Two verbs are one-way and refuse without `-Yes`: `wipe-data` and `uninstall`.** The verb once called `clear` is gone - it sat two lines from `log` in the verb list and was twice read as "clear the log", wiping app data instead (S1167, S1572); it now refuses and names both replacements. "Clear the log" is `logcat-clear`, which touches no app state. Prefer over raw `adb` for one-off work; `mobile-mcp` stays for agent-driven UI walks, Maestro for repeatable flows.

23. Concurrent-agent build/code locks, **split by domain** (S1432, S1448, S2098, S2109): the queue design - queue rather than refuse, a distinct "queued" code, ticket identity, eviction by liveness - is canon, `rules/DEVELOPMENT.md` section 10; this repo owns the scripts, the codes and the domains. A coordination resource is a **pair, type plus domain**, not one global word. Five domains exist, and the table in `scripts/utils/agent-lock-domains.ps1` is their only home: `Build.Phone` and `Build.Wear` for gradle, `Code.Phone`, `Code.Wear` and `Code.Scripts` for edits. Two sessions collide only where their domains overlap - a watch edit and a phone edit proceed at once, and so does a scripts edit beside either. **The domain is derived, never declared** (ADR-1): pass the changed set, `enter-code-lock.ps1 -Files "<paths>" -Reason "<ticket/skill>"`, and it maps them; a gradle entry point derives its domain from the module it already builds. **A set that does not decompose takes the full set** (ADR-2) - a build file, a path the table does not know, or no file set at all, because being over-protected is the safe direction to be wrong. Every script invoking `gradlew`/`gradlew.bat` acquires its build domains via `Enter-BuildLockOrExit -Domain <..>` and releases the same set after (success or failure); a caller that names none still takes both build domains and serialises exactly as before the split. Multi-domain work is taken **all at once, in the table's canonical order, all-or-nothing** - a set that cannot be completed releases everything it had taken, because holding half a set in a hand-picked order is what turns a split into a deadlock. `enter-code-lock.ps1` still exits **4** meaning "queued, not yet your turn - do not edit sources yet". **The waiting contract, which no script can enforce for you:** when you are queued, run `pwsh -NoProfile -File scripts/utils/wait-for-lock-turn.ps1 -Name <domain> -Reason "<why>"` as a **background** task - its exit is the "your turn" signal, and a multi-domain wait is granted only when you are head in *every* domain of your set - and keep working on what needs no lock: reading, research, specs, catalog, documentation, log analysis. Sources, resources, build files and repository scripts need the lock; nothing else does. Take the lock immediately before an edit and release it right after - never hold it for a whole ticket, because everyone behind you waits. **Abandon a queued intent and you must withdraw your own place** (S2098): `pwsh -NoProfile -File scripts/utils/withdraw-lock-ticket.ps1 -Name <domain>`, or `.\a.ps1 uqb` / `uqc`. Nothing else will do it - the eviction sweep judges the owning *session*, your session is alive, and it is the *intent* that was dropped, so an abandoned ticket sits at the head forever while every sibling waits behind it. This is the case that hits you when the operator switches you to another ticket, when a wait is interrupted, or when a phase collapses mid-queue. Inspect the order any time with `lock-status.ps1 -Name <domain> -Queue`, which prints one section per domain when given a bare `Build` or `Code`. Coordination state written before the split is honoured: a pre-split `temp/BUILD.LOCK` or `temp/CODE.LOCK` holds **every** domain of its type until its owner releases it. Ticket ownership, eviction, the head-of-queue reservation, the outcome marker (never trust a background task's exit code) and re-entrancy: `docs/DEV_OPS.md` "Concurrent-agent locks".

The failure it prevents reports **exit 0**, so a failed build masquerades as passing. Route through the interpreter: `pwsh -NoProfile -File ./a.ps1 <cmd>` from the repo root. No slash-command name as an argument value in a Bash-tool `pwsh` call (`-Reason "/spec-dev .."`): one home, canon `rules/GITHUB_INTERACTION.md` section 6, refused by the plugin's `guard-bash.ps1`. MSYS rewrites it to the Git installation root **silently** - nothing fails, the exit code stays 0, and the mangled text lands in the code-domain lock file, the queue tickets and the ticket leases, where that reason is the only record of who is working on what (S1458). Accepted forms: `//spec-dev ..`, `MSYS2_ARG_CONV_EXCL='*'`, or the PowerShell tool. Repo-specific residue: the canon guard treats a first path segment that is a POSIX root (`run`, `dev`, `var`, `bin`, `etc`, `opt`, `lib`, `tmp`, `usr`..) as a real path, so a future command named after one would not be caught - none of the current 32 collide.

No command in the Bash tool that cannot exist there - a **PowerShell cmdlet** in command-head position (`ls | Select-Object -First 3`), an **uninstalled interpreter** (`node`, `npm`, `npx`), or the **`& { .. }` batching idiom**, which in Bash backgrounds an empty group: one home, canon `rules/GITHUB_INTERACTION.md` section 6, refused by the plugin's `guard-bash.ps1`. Run the pipeline in the PowerShell tool, or pass it to `pwsh -NoProfile -Command "<pipeline>"`. **`python3` is deliberately NOT refused**: `~/bin/python3` shims to the `python` on PATH, and making a name work beats guarding it. Hooks intercept your tool calls, and one may **refuse** a call, **rewrite** its input, **observe** its result or **warn** you. `docs/AGENT_HOOKS.md` is the complete inventory: every registered hook, its event, its verdict shape, its escape hatch, and whether it is global (per-machine, absent on a fresh checkout) or project (travels with the repository). A refusal is self-sufficient - it names its hook and rule on stderr, which is shown to you - so read the inventory when a call is refused or a result looks altered. Two live hooks are named in no rule above and are worth knowing before you act: `guard-catalog-before-kt-search` **refuses** an unnarrowed `.kt` search until the class catalogue was queried this session, and `guard-uncapped-read` **rewrites** a `Read` that carries no explicit window, so a long file you did not window is only partly read. Registering, removing or re-registering a hook requires editing the inventory in the same change: `scripts/quality/assert-hook-inventory.ps1` (in `.\a.ps1 fg`) fails on any divergence, judging the project half strictly and the global half only where it is readable.

An island that does exist still obeys `docs/ARCHITECTURE.md` "Compose Island Theming". 33. Gate placement - per ticket or per release scope (S1939): a gate whose subject is the state of the whole tree or a shipped artifact does not belong in the per-ticket closure. Applied to one changed file it cannot attribute its finding to that change, so it either fails on another session's work in flight or is demoted to advisory and stops meaning anything - measured 2026-08-22, three such gates produced 68 of the 191 red lines across 53 `fg` runs, and `assert-device-profile-matrix` spent 33 minutes of closure time in a month to report one finding. **Release-scope** (`scripts/quality/assert-release-scope-gates.ps1`, step 0.4 of `/spec-prerelease`) when all four hold: between releases the defect cannot reach a user; the subject is the tree or a shipped artifact, not the changed file; the finding names its own location so no attribution is needed; batch fixing costs no more than per-ticket fixing. **Per-ticket** when any one holds: later work builds on the defect (compilation, resource linking, a migration, a cross-module contract); the evidence exists only at the moment of the change (author's intent, a ticket status a probe is bound to); or agents read the artifact between releases, where staleness poisons decisions (S1392 - a stale summary misled four documents). Two corollaries. A relocation is a **script with an exit code**, never a line of prose in a command file: gated rules hold at ~99%, prose rules at 1-8%, so prose changes a rule's force rather than its stage. And age is not the test - no gate in this repo is older than 68 days, so "we were burned long ago" describes no gate that exists. A new gate names its class at birth; unnamed means per-ticket, which is how the imbalance arose.

## 12. Validation & Post-Change
- The evidence rule has one home, canon `rules/DEVELOPMENT.md` section 5 / `rules/INVARIANTS.md` 7. Repo form: record `expected: X | actual: Y` for all checks. Red-flag words that mean you are about to claim without proof: "should", "probably", "seems", "looks fixed", "I think it passes" - stop and run the check first.
- Mechanical closure: `pwsh -NoProfile -File scripts/post-change.ps1 -File "<path>" -Target "<target>" -Description "<desc>" -ChangeType <Doc|Script|Config|Tooling|Kotlin|Xml|Mixed> [-Module <app_v2|wear>]`. Use `Tooling` for one set spanning build/config files and repo scripts; source-specific gates require matching files in the set. Skills SHOULD route mechanical closure through this facade instead of hand-rolling each step.
- Dirty-tree closure (S0826/S1338): name the **whole** changed set - `-Files "a.kt,b.kt"` for a multi-file change, `-File` for a single one - then add `-ScopeToFile` to judge every scoped gate against that whole set. detekt fails only on findings inside the set, and the count-ratchet gates (neuroslop / listener-symmetry / flavor-flag / deprecated-pm / public-mutable-flow / focus-highlight) judge a FATAL per-file delta against HEAD instead of a project-wide count, so other tickets' in-flight WIP does not block the close. Only the repo-wide re-render gates (icon-inventory, script-cheatsheet, device-profile-matrix) stay advisory. Omit `-ScopeToFile` for release/CI to get the strict full-project gate. Naming one file while changing four certifies one file - the verdict covers exactly what you passed.
- Closure verdict and exit codes (S1338): `post-change: PASS` is printed only when every gate passed; an advisory gate that found something prints `PASS WITH ADVISORIES (n)` and names each one - read it, the bare word is the only clean verdict. Exit codes: **0** passed, **1** a gate failed, **2** could not verify (invalid, absent or unexpanded file argument; missing tooling). A caller must distinguish 1 from 2 - "found a defect" and "did not look" are different answers. The gates run before the mutating steps, so a failed closure writes no changelog row and re-running after a fix produces exactly one. A closure that passed **with advisories** returned 0 and did write its row - re-running that one after fixing what the advisory named still leaves exactly one row, because the dev-log guard identifies the change and ignores the size of its file set (S1622); before that, fixing an advisory usually regenerated a file, the file joined the `[set of N: ..]` tail, and the tail alone made the second row look new.
- Journaling granularity: one dev-log entry per logical change/ticket, not per touched file (batch multi-file changes via `close-and-log.ps1 -DevLogs`); run `catalog_sync.ps1` once per ticket, not per `.kt` edit.
- Validation Ladder:
  - Doc: Grep for content.
  - Script: Run, exit 0.
  - Config: Target build passes.
  - Kotlin/Java: prefer `.\a.ps1 fk` for compile-only symbol changes; escalate to `.\a.ps1 fc`, targeted `--tests`, or full `.\a.ps1 d` only when the touched area needs packaging/resource proof.
  - Python: Syntax check + test.
  - Layout/manifest: Target build passes - and since S1915 this rung is **enforced**, not merely asked for. The `resource-link-gate` in `post-change.ps1` links the changed resources whenever the set carries one (`check-standard-fast.ps1 -Mode Resources`, variant chosen from the touched source set, `BUILD.LOCK` taken by the helper) and fails the closure on the aapt error. It matters because nothing else in the facade runs aapt and `fk` compiles Kotlin without linking anything, so before this gate a broken layout closed green and the ticket reached `BlockNeedUserTest` - "install this and test it" - without the thing being installed ever having been built (S1881). Cost measured 1.9-41.8 s per flavor, all foreground: `docs/BUILD_TEST_FAST_PATH.md`.

## 13. Code Audit Protocol
- Full protocol: `docs/CODE_AUDIT_PROTOCOL.md` (layered audit, evidence ladder, per-layer checklists). Read and apply it whenever an **audit trigger** fires - do not re-derive the checks. Use the cheapest evidence rung that matches the risk.
- **Audit triggers**: new screen/manager/worker/repository/long-lived helper; lifecycle change; coroutine/Flow/callback/listener/observer change; shared-mutable-state/synchronization/dispatcher change; Room entity/DAO/query/migration/transaction change; player/image-loading/caching/network-path change; startup-path change; DI scope or singleton-ownership change; build/manifest/R8/keep-rule change affecting profiling/startup/minification/process; reported crash/ANR/OOM/jank/leak; **phase boundary in a multi-phase task** (tactical spec phase, or any large task split into sequential phases) - audit the phase just finished before starting the next.
- **Phase-boundary audits are mandatory, not deferred to pipeline end**: fixing a defect costs roughly one phase's worth of rework when caught at the next phase boundary, versus every subsequent phase's worth when it surfaces only at the final audit (`/spec-check`) or in a later ticket. `/spec-dev` runs this automatically per phase (see its "Phase-boundary audit" step); apply the same discipline manually for any multi-phase work driven outside `/spec-dev`.
- Per-layer checklists (severity taxonomy, listener symmetry, Room main-safety, concurrency correctness, player/Glide ownership, R8/minified proof) live only in `docs/CODE_AUDIT_PROTOCOL.md` Layers 1-8 - read them there when a trigger fires, do not expect a copy here.
- Recurring finding -> convert to a mechanical gate (`scripts/quality/assert-*.ps1`), per Rule 19/20 and Layer 8. Do not duplicate the protocol text in rules - link to it.
- Authoring a new rule / gate / command / skill: follow `dev/RULE_AND_SKILL_AUTHORING.md` (observe the failure first, write minimal, close rationalizations, promote recurring rules to gates; trigger-focused `description` fields).
