> **Universal conventions (canon):** the portfolio-wide rules are the SZA Unified Rules, shipped as the `sza` Claude Code plugin (`/plugin marketplace add SerZhyAle/sza-unified-rules`; `/plugin install sza@sza-unified-rules`) - consumption model **REFERENCE**, not mirrored here. This repo is overlay B and the **reference the core was extracted from**, so the rules below are not a re-authoring of the canon - they are this repo's Android operational layer (exact `a.ps1` targets, gate names, the flavor matrix, the Sxxxx spec/probe lifecycle) plus the deltas and channel matrix recorded in the canon at `rules/contrib/fastmediasorter_mob_v2.md` (adoption stamp: `.sza-canon.json`). ## 1. Communication & Style
- **Language & tone**: one home, canon `rules/AUTHOR.md` "Language" + "Working style". Ask if ambiguous.
- **House text style** and its scope: one home, canon `rules/DOCUMENTATION_CONCEPT.md` section 5 "House text style". Repo extension past that scope: long dashes are banned in `.kt` too (Rule 19, gate `scripts/quality/assert-neuroslop.ps1`).
- **Timestamps** and **brevity on request**: one home, canon `rules/AI_USAGE.md` section 7 - no clock-time prefix, and `caveman` compresses prose only, never a check or a gate's reason. Repo trigger: `/caveman`.
- **Spec Writing**: Lists over tables (tables only for 3+ columns). No pseudographics. No self-evident links. One idea per bullet. No section summaries. Draft specs exempt.
- **No self-cost estimates anywhere in planning output** (owner ruling 2026-08-25): never write how long a change will take, how much effort it is, or how many lines it will add - no hours, no `~150 LOC`, no `Line budget` column, no "estimated phases", in a spec, a phase file, a plan or a chat reply. There is no budget these numbers feed, so each one is output nobody reads, and they are measurably wrong: S1431's phase table missed its own line budgets on three of its phases by 4-23 lines. Describe what a change **is** - which files, which layers, which gates it trips - never what it will **cost**. Sizes read off disk are untouched by this: Rule 2's 2000-LOC ceiling and Rule 5's 500-LOC backup threshold measure a real file, they do not predict one.

## 2. Debug Verification Tags (Sxxxx)
- Invariant: `Timber.d("Sxxxx: <desc>")` exists in `.kt` **if and only if** spec `Sxxxx` is in `BlockNeedUserTest`. Into the status: one tag at the entry point of each changed flow before the final build. Out of it - the release archive sweep included - delete every `Timber.d("Sxxxx:` line at once.
- A probe owns its line, whole (owner ruling 2026-09-02): one statement, alone on its line, ending in `)`, never wrapped, never sharing a line with code that must survive it. Gate: `probe-line-shape` in `scripts/quality/assert-no-ticket-logs.ps1`.
- Permanent logs must not contain `Sxxxx`. Full contract and its incidents: `.claude/rules/spec-catalog.md` (loads with any `PLAN/` file).

## 3. Skill Routing (Auto-trigger prompts)

Every skill's own `description` is injected fresh each turn (see the "Available skills" system reminder) - do not restate it here. This section holds only what that injection cannot supply on its own: the owner's short aliases, and the size-tier ordering across commands whose descriptions overlap.

- **Short aliases are generated command files.** Fourteen hand-typed commands each answer to `/sd`, `/сд` and `/ыв` - real files under `.claude/commands/`, generated from the table in `scripts/utils/generate-command-aliases.ps1` (`-Check` verifies, `-Prune` retires), never hand-written or hand-edited; `/arc` = `/spec-arc` is one of them. Why a file and not an alias field, and the Cyrillic bet: `.claude/rules/command-authoring.md`.
- **Size tier, smallest first:** `/quick` (single string/typo/design tweak, no spec/build) -> `/skill-fix` (fast bug/UI fix, and the doc/config/script tweak that needs no gradle; skips doc/git/build/dev-log/spec) -> `/spec-next`/`/spec-do` (full ticket pipeline; `/spec-do` is the same picker minus both stops - the context threshold and the empty queue - so it idles, re-checks, and runs until the operator stops it). Picking too heavy a command for a small fix is the common miss - try the smallest tier first. Nudged mechanically by the `UserPromptSubmit` hook `.claude/hooks/nudge-small-task-tier.ps1` (advisory, always exits 0).
- **Unattended batches run as processes, not as one long session (2026-08-25).** `scripts/utils/run-spec-queue.ps1` runs `/spec-all` for the next `PLAN/RELEASE_QUEUE.md` ticket in a fresh `claude -p` process and repeats; two or three instances may run in parallel (`-Instance b`); `-ModelPolicy tiered` picks the model by status before tier. Prefer it over `/spec-do` for anything left unattended; `/spec-do` remains the interactive form. Principle: canon `rules/AI_USAGE.md` section 3; mechanism: `.claude/rules/command-authoring.md`.
- **Device-free sibling of `/spec-all`:** `/spec-code` runs the same pipeline with every on-device step removed - no device probe, no install, no emulator, no `/spec-test-device`. The build is the only test, and a ticket that edited anything shipping in an APK ends at `BlockNeedUserTest` for `/spec-sweep` to drain; a docs/scripts-only ticket still audits through to `Verified`. Pick it when no device is attached, the connected device belongs to another session, or the owner's phone must not be touched; pick `/spec-all` when a device is available and the ticket's acceptance is on-device.

**Command file shape.** Driver at `.claude/commands/<name>.md`, companion at `.claude/reference/<name>.md`, verbatim skeletons in `.claude/templates/` - neither of the last two under `.claude/commands/`, where every file is an invocable command. Detail: `.claude/rules/command-authoring.md` (loads with any file under `.claude/commands/`).

### 3.1 Auto-capture of out-of-scope findings (`/spec-draft`)
- At **any** stage - research, development, audit, code review, device test, log analysis - when you discover a problem meeting ALL three conditions, invoke the `/spec-draft` procedure to park it, without asking:
  1. Unrelated to the current task/ticket (out of scope).
  2. Not trivial enough to fix on the spot (more than a one-liner, or fixing now would derail current work).
  3. Requires its own research and execution.
- Before creating: dedup-check by symptom (`scripts/spec_catalog/search.ps1`); if an open ticket already covers it, reference that id instead of drafting a duplicate.
- Batch discovery: a general log analysis / audit / review surfacing several qualifying problems → one `/spec-draft` per distinct problem (after dedup).
- Non-disruptive: park it, report `parked: Sxxxx <slug>` in chat, then resume the original task. Never switch the active ticket because of a parked finding.
- Do NOT park: in-scope work, trivial fixes (do them inline), cosmetic nitpicks not worth a ticket, or already-ticketed issues.
- Read-only contexts (e.g. `android-solution-researcher`) cannot mutate the catalog: instead list the qualifying findings as `/spec-draft` candidates in the report for the caller to capture.

## 4. Spec Catalog (Sxxxx tickets)
- Specs: `PLAN/Sxxxx_<slug>.md`. Directory: `PLAN/Sxxxx_<slug>/`.
- Journal: `PLAN/spec-catalog.jsonl` (never hand-edit). CLI: `insert.ps1`, `update.ps1`, `select.ps1`, `delete.ps1`.
- Status header sync: catalog mutators update the first `**Status:**` line in spec file automatically.
- **Gated transitions** (`Assert-ClosingGates` in `_lib.ps1`, run by `update.ps1`, `close.ps1` and `bulk-update.ps1`): every entry INTO a `Block*` status needs `-StatusNote '<reason>'`, and `BlockByOtherTask` a literal `Blocker: Sxxxx` token; `Implemented` / `Verified` need every research item `Resolved` or carrying `Carrier: Sxxxx`; `Verified` and `BlockNeedUserTest` need a non-empty `## Last Audit` block whose `**Task fingerprint:**` still hashes the spec body (re-audit, never re-stamp); `BlockNeedUserTest` needs a probe in `app_v2`/`wear` or a row in `scripts/quality/blockneedusertest-probe-baseline.txt`; every gated transition needs each section heading unique inside its level-1 block; an unticked `- [ ]` line in the audit is `MANUAL` and scores `BlockNeedUserTest`, not `Verified`. Gates: `scripts/spec_catalog/check-*.ps1`. Each gate's incident, measurement and exact fix: `.claude/rules/spec-catalog.md` (loads with any `PLAN/` file).
- **A found problem ends `BlockNeedUserTest`** (owner ruling 2026-08-31): that status means "the verdict is not in yet", never "a known defect is parked here". On any finding move the ticket in the same action - `update.ps1 -Id Sxxxx -Status <Broken|Partial|In Progress|Approved|Draft> -StatusNote '<the finding, and what must happen next>'` - so it returns to `PLAN/RELEASE_QUEUE.md`; never write the finding into the spec and leave the status alone, and never re-close for a re-test while the finding is open.
- Statuses: Draft, Approved, Tactical, In Progress, Implemented, Verified, Partial, Broken, Block*, Archived (soft-delete).
- Priority: 0..100 (default 50).
- **Release plan - two files, split by "is there work left".** `PLAN/RELEASE_QUEUE.md` = work still left (every status below `Implemented`, blocked included). `PLAN/RELEASE_READY.md` = finished content (`Implemented`, `Verified`, `BlockNeedUserTest`); all three archive at the release (owner ruling 2026-09-02). Column `rel` = release package number, `--` = not scheduled.
- **The queue decides what gets worked on next - always recommend from it, and obey it.** Package ascending, then the owner's line order inside it; catalog `priority` is only a tiebreak for tickets neither file lists. A deviation needs a stated reason. Catalog owns STATUS, the two files own ASSIGNMENT + ORDER - every catalog write reconciles both; no other script may reorder lines or touch `rel`. Enforcing scripts: `scripts/spec_catalog/spec-next-preflight.ps1`, `release-plan.ps1`, `release-queue.ps1` (`-Reconcile`/`-Validate`/`-List`/`-SetCurrent`/`-Ship`).

## 6. Proactive Research & Parallelism
- **Web Search**: autonomy is canon (`rules/AI_USAGE.md` section 1). Repo's preferred sources: developer.android.com, kotlinlang.org, GitHub issues, StackOverflow.
- **Parallel Subagents**: Concurrently run independent tasks (e.g. a catalog query alongside a docs sweep, or two independent file searches). **Never more than one gradle-backed invocation at a time IN ONE BUILD DOMAIN** - a build, a compile check, detekt, the unit suite. Rule 23 orders the second one mechanically through that domain's lock; parallelise everything that does not touch gradle. Since S2109 the two modules are separate domains and their checks may genuinely run at once - measured 2026-08-27, `.\a.ps1 fw` and `.\a.ps1 fk` together took 12 s with no queue wait and no cache contention - so "one gradle call at a time" now means one per module, not one per machine.
- **Background long jobs - the 120 s threshold**: the two-sided rule is canon (`rules/AI_USAGE.md` section 1); this repo pins the boundary to the Bash tool's own foreground timeout and names the targets. **Above it, background**: `d/db/dav/cd/nd/nl/r/fu` - a cold gradle daemon exceeds the timeout. **Below it, do not**: `fk/fkn/fc/fr/dq` and `assert-detekt` measure 14-21 s on a warm daemon, `fg` measures 32 s (S2451, 2026-09-03), and the three wear targets `fw/fwr/fwu` measure 2 s / 1 s / 11 s (S1807, warm daemon - the watch module is far smaller than `app_v2`, so even its full unit suite stays foreground) (`docs/BUILD_TEST_FAST_PATH.md`, "Foreground or background") - wait and read the verdict in the same turn. Enforced by Rule 26. `fg` is quoted separately because it was the one target that crossed the threshold: 45 gates running one at a time reached 142.8 s and were preempted into the background twice, delivering the verdict the way Rule 26 forbids. S2451 made the children concurrent (117 s -> 32 s, same gates, same verdicts), so the margin is real again - but it is now bounded by the slowest single gate, not by the batch's size.
- **Cost discipline**: canon `rules/AI_USAGE.md` section 3. Repo playbook: `docs/AGENT_COST_PLAYBOOK.md` - `/compact` at task boundaries, `/clear` on task switch, raw artifacts to `temp/Sxxxx/` (or `temp/scratch/`), `mobile-mcp` only for exploratory UI walks (`adb.ps1`/Maestro first).
- **Subagent MCP isolation**: canon `rules/AI_USAGE.md` section 3 requires it; the repo mechanic is an explicit `tools:` frontmatter allowlist omitting every MCP tool name - omitting `tools:` entirely grants the parent's full set, MCP included. (S1348: `enable_mcp_tools` is not a real Claude Code option - do not use it.)

## 9. Common Commands (a.ps1 launcher)
- Build: `.\a.ps1 d` (fast reusable debug APK), `db` (fast debug no-zip), `dav` (debug APK with timestamped app version), `dq` (quiet), `cd` (clean debug), `nd`/`nl` (noLegal debug/release), `r` (release AAB - builds in a dedicated git worktree, not the main checkout; driven by `/skill-release`), `bf` (build failure structured digest).
- Checks: `.\a.ps1 fk` (Kotlin compile, standard), `fkn` (Kotlin compile, noLegal), `fr` (resources/manifest), `fc` (code + resources), `fg` (fast static gates batch - neuroslop+pm+listener+flavor+ticket-log in one process, `-IncludeDetekt` opt-in), `ch` (typos & lint), `ss` (unresolved specs), `ivn` (install noLegal debug APK).
- Tests: `.\a.ps1 fu` (full unit suite - acquires `BUILD.LOCK` per Rule 23; never call `gradlew.bat` directly). kapt recovery: `scripts/utils/recover-kapt-stall.ps1`.
- **Wear module has its own three targets, and the phone ones do not cover it (S1807):** `fw` (Kotlin compile), `fwr` (resources/manifest), `fwu` (unit suite). `fk`/`fkn`/`fr`/`fc`/`fu` all check `app_v2` and exit 0 without compiling a single watch file, so quoting one under a `wear/` change records a verdict about the other module - measured five times across S1710, S1730 and S1781. Every fast check now prints the module it checked in its banner; read that line before quoting the exit code.
- Device (ad-hoc, ~0 tokens): `scripts/devtest/adb.ps1 <verb>` or `.\a.ps1 adb <verb>` for quick chores against a connected emulator/device - `devices`, `props`, `current`, `launch`, `stop`, `logcat-clear`, `install`, `shot`, `log -Tail N -Grep <regex>`, `tap/swipe/text/key`, `prefs`, `shell -Cmd`, and the UI-tree verbs `uidump` / `tap-id -ResourceId <s>` / `tap-label -Label <s>` / `clip-check` (S1847, S1879). Auto-discovers adb (not on PATH); supports `-DeviceId`/`-Release`/`-OutDir`/`-Json` with stable exit codes. **Tap by label or by id, never by a remembered coordinate:** a list that scrolled between the dump and the tap sends `tap -X -Y` into the neighbouring row, which happened twice in one wear sweep; both tap verbs re-read the tree in the same call and exit 8 rather than tapping something else. **Between the two, prefer the id:** a label is translated and a `resource-id` is not, so a call aimed at a label works on the locale it was written on and returns 8 on every other one (S1879) - `tap-id` takes the short name straight from the layout, and `uidump` prints that name beside every label (`-Ids` also lists the nodes that carry nothing else). `tap-label` stays right where there is no id, which is most of Compose on the watch. `clip-check` reads the display shape off the device, so the round watch and the rounded-corner phone use one rule. Shortcuts: `adb-devices/-shot/-log/-current/-launch/-logcat-clear`. **Two verbs are one-way and refuse without `-Yes`: `wipe-data` and `uninstall`.** The verb once called `clear` is gone - it sat two lines from `log` in the verb list and was twice read as "clear the log", wiping app data instead (S1167, S1572); it now refuses and names both replacements. "Clear the log" is `logcat-clear`, which touches no app state. Prefer over raw `adb` for one-off work; `mobile-mcp` stays for agent-driven UI walks, Maestro for repeatable flows. **What you may do to the device that answers is Rule 35 / `docs/DEVICE_FLEET.md`** - this bullet lists the verbs, never the permission to use one.

No slash-command name as an argument value in a Bash-tool `pwsh` call (`-Reason "/spec-dev .."`): one home, canon `rules/GITHUB_INTERACTION.md` section 6, refused by the plugin's `guard-bash.ps1`. MSYS rewrites it to the Git installation root **silently** - nothing fails, the exit code stays 0, and the mangled text lands in the code-domain lock file, the queue tickets and the ticket leases, where that reason is the only record of who is working on what (S1458). Repo-specific residue: the canon guard treats a first path segment that is a POSIX root (`run`, `dev`, `var`, `bin`, `etc`, `opt`, `lib`, `tmp`, `usr`..) as a real path, so a future command named after one would not be caught - none of the current 32 collide.

Only a *head* is refused - a cmdlet in a quoted string, a heredoc body or an argument is untouched.

A refusal is self-sufficient - it names its hook and rule on stderr, which is shown to you - so read the inventory when a call is refused or a result looks altered. Two live hooks are named in no rule above and are worth knowing before you act: `guard-catalog-before-kt-search` **refuses** an unnarrowed `.kt` search until the class catalogue was queried this session, and `guard-uncapped-read` **rewrites** a `Read` that carries no explicit window, so a long file you did not window is only partly read. ## 12. Validation & Post-Change
- The evidence rule has one home, canon `rules/DEVELOPMENT.md` section 5 / `rules/INVARIANTS.md` 7. Repo form: record `expected: X | actual: Y` for all checks. Red-flag words that mean you are about to claim without proof: "should", "probably", "seems", "looks fixed", "I think it passes" - stop and run the check first.
- Mechanical closure: `pwsh -NoProfile -File scripts/post-change.ps1 -File "<path>" -Target "<target>" -Description "<desc>" -ChangeType <Doc|Script|Config|Tooling|Kotlin|Xml|Mixed> [-Module <app_v2|wear>]`. Use `Tooling` for one set spanning build/config files and repo scripts; source-specific gates require matching files in the set. Skills SHOULD route mechanical closure through this facade instead of hand-rolling each step.
- Dirty-tree closure (S0826/S1338): name the **whole** changed set - `-Files "a.kt,b.kt"` for a multi-file change, `-File` for a single one - then add `-ScopeToFile` to judge every scoped gate against that whole set. detekt fails only on findings inside the set, and the count-ratchet gates (neuroslop / listener-symmetry / flavor-flag / deprecated-pm / public-mutable-flow / focus-highlight) judge a FATAL per-file delta against HEAD instead of a project-wide count, so other tickets' in-flight WIP does not block the close. Only the repo-wide re-render gates (icon-inventory, script-cheatsheet, device-profile-matrix) stay advisory. Omit `-ScopeToFile` for release/CI to get the strict full-project gate. Naming one file while changing four certifies one file - the verdict covers exactly what you passed.
- Closure verdict and exit codes (S1338): `post-change: PASS` is printed only when every gate passed; an advisory gate that found something prints `PASS WITH ADVISORIES (n)` and names each one - read it, the bare word is the only clean verdict. Exit codes: **0** passed, **1** a gate failed, **2** could not verify (invalid, absent or unexpanded file argument; missing tooling). A caller must distinguish 1 from 2 - "found a defect" and "did not look" are different answers. The gates run before the mutating steps, so a failed closure writes no changelog row and re-running after a fix produces exactly one. A closure that passed **with advisories** returned 0 and did write its row - re-running that one after fixing what the advisory named still leaves exactly one row, because the dev-log guard identifies the change and ignores the size of its file set (S1622).
- Journaling granularity: one dev-log entry per logical change/ticket, not per touched file (batch multi-file changes via `close-and-log.ps1 -DevLogs`); run `catalog_sync.ps1` once per ticket, not per `.kt` edit.
- Validation Ladder:
  - Doc: Grep for content.
  - Script: Run, exit 0.
  - Config: Target build passes.
  - Kotlin/Java: prefer `.\a.ps1 fk` for compile-only symbol changes; escalate to `.\a.ps1 fc`, targeted `--tests`, or full `.\a.ps1 d` only when the touched area needs packaging/resource proof.
  - Python: Syntax check + test.
  - Layout/manifest: Target build passes - and since S1915 this rung is **enforced**, not merely asked for. The principle has one home, canon `rules/DEVELOPMENT.md` section 15 ("The closure RUNS the ladder's rung; it does not merely ask for it"). Repo mechanism: the `resource-link-gate` in `post-change.ps1` links the changed resources whenever the set carries one and fails the closure on the aapt error; the gate's own comment carries the incident and the measured cost.
